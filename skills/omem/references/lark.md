# 飞书（lark）

发飞书消息的 `lark_*` 工具和以本人身份写飞书文档的 `lark_doc_*` 只在 omem 自己的运行里可用（外部调用会被拒绝），能发的会话由本次运行限定；草稿模式下回复先变成给本人的确认卡片。

## 消息与卡片

- `lark_send` / `lark_card` / `lark_react` / `lark_send_file`：发消息、卡片（带 `message_id` 就是原地更新那张已发的卡片）、表情回应、发文件。自己生成的文件（表格、压缩包、图片）用 `lark_send_file` 作为附件发出。
- `lark_card` 带按钮或表单、又用 `allowed` 限定了处理人时，发在群里会在卡片开头 @ 这些人（只 @ 机器人认识的 id；给了 `mentions` 就只按 `mentions`，几个人都能处理、只 @ 当班的那位时这样写），不用自己再拼 @。`allowed` 里用 `lark_read` 查到的 open_id 也可以，工具会换成机器人一侧的 id。表单每个字段的 `label` 写成要问的话：显示成字段上方的一行粗体，几个问题时自动编号。
- `mentions` 可填姓名、邮箱、已核实的机器人应用侧 open_id/user_id 或 all。普通姓名按授权目标群的完整成员列表核对，群内重名拒绝；确认不在群内的普通 mentions 自动跳过，正文和其他人的提醒继续发送，回执说明跳过对象，不需重发或在群内解释。权限或分页错误不算缺席，urgent / only_to 不静默降级；邮箱查不到时，可改用明确的群成员姓名，不把邮箱记录按姓名强行合并。@ 机器人优先传名字：群成员列表不含机器人时，工具会用发送机器人的身份查目标群最近 200 条消息的提及，按机器人和群缓存 10 分钟；近期重名或分页、权限错误会拒绝。不能用 app_id 或个人采集应用的 open_id。只有当前应用的历史也没有可核实的提及时，才需要本人补一次真正的 @，不要求和助理在同一条消息里。用 markdown 发、又 @ 了别的应用的机器人时，整条改成富文本消息发出，开头是真正的 @（卡片里的 @ 机器人收不到，只显示一串 id）。
- 发送前会转换 Markdown 里的引用：文档链到原文，飞书聊天行和来自飞书的消息链到飞书里那条消息；代码、工作文件、记忆、Wiki 在配置了网页地址时变成只读分享链接，否则省略。属于句子的引用保留文字，句末的变成 (1) (2) 编号链接。沿用 omem 引用格式即可，不用自行拼跳转地址或分享链接。
- `meeting_suggest(point, basis, answer)`：只在规则打开了“会上主动查”的会议旁听运行里有。会上提到、你查清楚了的一点交给本人：`point` 一句话说会上提到什么，`basis` 写查到的内容和依据（代码位置、文档、数据口径和时间）给本人看，`answer` 是可以发到会里的两三句（所有参会人可见，不写本人的私事和个人记忆）。本人在卡片上决定发不发；你自己不在会里说话。每个点交一次，返回到了上限或本人暂停了就停止主动查。按会议性质怎么找点，见内置技能 `meeting-assist`。
- `reply_to_asker(text)` 写什么：查到了能直接给对方的结论（答案、数据、明确的时间或决定）才拟，否则不调用它，只在给本人的提醒里说清情况。照任务里“本人以往怎么回”的长短和口吻写：先说结论，一两句，不铺垫、不客套、不复述对方的问题、不解释怎么查的。远长于本人平时的回复会被退回一次，让你改短；确实需要这么长，原样再交一次。
- `reply_to_asker(text)`：只在处理“有人找你”的运行里有（本人在 设置 → 代你回复 → 有人找你 打开了这个渠道的回复对方时，飞书是 `mentions.reply.lark`）。目标固定是这次找本人的人，怎么发由消息所在的渠道决定、写在任务里。飞书：群里机器人在对方那条消息的话题里回复（机器人不在群里时宿主用本人身份把它拉进来）；私聊按设置拉本人、对方和机器人的群回复，或以本人身份带署名回复。“草稿”档先记下，处理结束时附在给本人的提醒下面、同一张卡片（本人可以改了再发），提醒正文不要再抄这段回复，最后调用 `stay_quiet` 时草稿不发；“自动”档直接发，只在分诊认为不用本人拍板时才是自动，否则也是草稿。一次处理只回一次；只写要发给对方的话，用本人这边的口吻，涉及承诺、排期、审批、权限的不回，把建议的话写进给本人的提醒。
- `set_chat_watch`：设一个「关注」，之后它的群里的消息按批交给主助手或更合适的档案。本人说“帮我盯一下这个群”时用；长期分工（报警群交给告警档案）也用它。几个群合成一个关注传 `chat_id` 加 `chats`，改已有的传 `context`：关注 id，或本人叫它的名字（本人说“把退款值班的关注改成只看 @ 我的”就传 `context: "退款值班", listen: "addressed"`；同名或名字里含这几个字的不止一个时会报出候选，问本人是哪个）。关注页“设置”里的每一项都对应一个参数，本人对你说一句，你改的就是那一页。`batch_minutes` 是来了新消息后等几分钟、攒成一批再看（@ 本人或机器人的 30 秒内看，没有新消息不看）；讨论正热时调小，平静了调回。配了决策模型时每批消息先由它筛一遍（@ 本人或机器人的不筛），本人要这个群每批都看（或都筛）时传 `prefilter`。机器人不在群里时先 `lark_invite`（`bots: ["self"]`）。
  - 关注一件事传 `item`（事项 id）：群默认是这件事和下面各项关联的群（之后关联或移除的群自动跟上），默认只读、不限期，群、会话和文档里的新内容记成这件事的变化。本人要多看一个群传 `chat_id`，要它只看某几个群传 `chats`（完整列表，没列的不再看）：之后照这个读，不会被事项的材料改回去；加的群要是采集过的群，私聊不行。线在观察中（已上线）时，处理和跟进的任务里会写明只关心报错、用户反馈和数据异常。本人要你在这些群里回答这件事的问题时再给 `reply` 和 `brief`，处理时会带上这件事现在的样子（状态、截止时间、流程走到哪、最近的变化）。事项开始走流程时宿主会自动建一个只读的，流程结束就停；本人用 `set_chat_watch(item)` 设过的不随流程停。
  - 事项跟进会放下助手挂的连续空批的群，群列表随之更新。本人手动在列表里加的群继续读；从列表拿掉的群会保留这次选择，要恢复时再加一次。
  - 要在群里回复（`reply` 为 draft 或 auto）必须带 `brief: {handle, skip, valid}`：先读这个群最近的消息，按本人的话写要处理哪些、不处理哪些（问本人的、要本人拍板的、找别人或别的机器人的一般放这里）、什么样的结论才值得发。宿主把它发成只有本人看得到的卡片（本人在群里时是群里的临时卡片，否则私聊），本人改了确认后照新的做。
  - `reply: auto` 先试运行：回复先是只有本人看得到的草稿卡片（可以改了再发，不发时选原因：不该回、该我来定、结论不对或没依据、没帮上忙、我自己回），连续照发 5 条后宿主问一次要不要直接发；本人明确说“不用给我看、直接发”才传 `trial: false`。直接发以后本人对哪条点了不满意的表情，这个群改回草稿。
  - 本人的每个决定记在这个盯群上，之后每批消息和预筛都会带上最近的；不发、改过、不满意累计 3 次后，处理那一批时会被要求按这些决定修订 `brief`（传完整的新版本），新版本再发给本人确认。
  - 事情型关注（`item`）有 `assist`：off（不主动接手）/ suggest（只读核对，写入留建议）/ act（默认：只读先做，写入等本人确认）。
  - 盯之前的消息不处理；本人说“别自动回了”改成 `reply: draft` 或 `none`，说“不用盯了”才 `remove`。

## 拉人进群

- `lark_invite(invites, reason, bots_seen_in?)`：以本人身份把人或机器人拉进本人所在的群。`invites` 每项 `{ chat_id, people?, bots? }`，一批群一次调用（最多 20 个群、合计 200 个成员）；`reason` 是给本人看的一句话。
- 群：`chat_id`（`oc_…`），用 `lark_read` 的 `["im","+chat-search","--query",<群名>]` 查；本人要在群里，单聊不行。
- 人：本人身份（lark-cli）下的 open_id、邮箱或姓名。用 `lark_read` 的 `["contact","+search-user","--query",<姓名或邮箱>]` 查 open_id；重名时工具会列出候选（姓名、邮箱、部门、open_id），把候选给本人挑，或用邮箱、open_id 指明，不要猜。机器人应用侧的 open_id 不能用。
- 机器人：`self`（omem 自己的机器人）、`lark.bots` 里的 id、app_id（`cli_…`）或名字。别的机器人要在本人的某个群里见过才认得：用 `lark_read` 的 `["im","+chat-members-list","--chat-id",<它在的群>,"--member-types","bot"]` 查 app_id，并把那个群放进 `bots_seen_in`。
- 要 @ 或要审批的人不在群里（`lark_send` / `lark_card` 回执写“已跳过不在目标群的 @ 对象”）：只是知会的不用管；要他在群里参与的（审批卡片只给他点、要他确认或回复）先 `lark_invite` 把他拉进来，等本人批准、执行完再发，不要只在结论里写“他不在群里”。本人常打交道的人按姓名就能认出（之前在群里、私聊或通讯录里见过的都记着本人身份下的 open_id）。
- 审批：只要有人，整次调用都要本人批准（卡片发到本人和机器人的私聊，列出每个群、每个人和机器人；批准后一次全部执行，本人只想拉一部分会拒绝并说明，按说明重新调用）。只拉认得出的机器人默认直接执行，执行后在回复里告诉本人拉了谁进哪个群；本人在 设置 → 代你回复 → 拉人进群 打开“拉机器人进群也要我批准”后，机器人也要批准（omem 自己的机器人在本人亲自要求的那一轮除外）。同样的请求在等批准时不会再发卡片，用 `wait_answer` 等结果。
- 结果逐群列出：拉进了谁、谁在等群主或管理员审批、谁无效或不存在、哪一批失败及原因。解析有问题时一次列出全部，改好后整个重新调用。

## 规则换身份

规则用 `act_as(user)` 换成已同意的成员后，`lark_read`、`lark_doc_fetch`、`list_lark_chats`、消息附件读取、飞书链接的 `import_url` 和 `lark_wiki_crawl` 都用该成员的飞书连接。知识库爬取续跑时沿用开始时的成员身份。没有可用的连接时，宿主提醒成员授权，本次跳过他。

`lark_write`（包括评论）及文档的新建、编辑、移动、复制按该成员判断文件归属。写共享文件、处理任务或用 `lark_doc_authorize` 申请目录授权时，机器人私聊给该成员发批准卡片。他的批准只对自己的身份生效。实际写入有运行和审计记录。`lark_write` 禁止执行 high-risk-write 命令。

机器人负责消息、卡片、表情和发文件，`lark_chat_history` 也以机器人身份读取。文档工具传 `identity: "bot"` 时仍走机器人。调用 `lark_invite` 或修改本人的采集设置前先 `act_as(null)`。

## 飞书文档

- 在接活设备上，`lark_doc_fetch` 和 `lark_read` 的 `docs +fetch --doc` 可读任务空间内已归档文档的现文。群记录用 `im +chat-messages-list --chat-id`，指定消息用 `im +messages-mget --message-ids`（逗号分隔，最多 50 条）。按读者保存的 wiki 文档也可用 docx 链接读取，链接可带 `#share-…` 选区。读取整群要求群的归属和各月归档都在范围内。续页时保留原查询参数，添加 `--page-token` 和上页返回的 `page_token`。消息过长时，响应首行单独给出分页信息，其后的正文按长度截断。按消息 ID 读取时，只要本空间仍有有效副本就能读。任一目标未知或越界时整条请求被拒绝。接活任务无法通过这些工具搜索整个飞书账号。
- `lark_doc_create` / `lark_doc_update` / `lark_doc_move` / `lark_doc_copy`：以本人身份写飞书文档，只在本人要求时用。完整复制知识库文档用 `lark_doc_copy(doc, target, summary, title?)`，调用官方节点复制，保留表格、图片和排版，不把正文重建成新文档，也不递归复制子页面；成功后回读返回的新节点核对，状态不明先查远端。做法和 DocxXML / Markdown 写法在内置技能 `lark-docs`。
- 成员收到完整复制的授权链接时，「让助手写文档」包含读取目标文档、定位知识库和复制所需的权限。工具已给出授权链接的，等对方确认后接着做。
- 本人希望某个目录一次审批时，`lark_doc_authorize(under, operations, summary)`：`under` 填本人指定的知识库节点链接，`operations` 从 `create`（新建）、`copy`（复制到范围内）、`edit`（局部编辑）、`move`（范围内移动）中选。卡片说明节点、操作和用途，发到本人机器人私聊；批准后包含节点自身、全部后代和以后新建的子页面，跨会话、定时规则和失败重试复用。执行时按飞书当前层级核对，不按标题或本地旧目录推断；移动须来源和目标都在范围内。整篇覆盖、范围外写入另行批准；最近的拒绝阻止沿用旧授权。申请不执行文档写入，批准后照常调用具体工具。
- 改已有文档：先 `lark_doc_fetch` 读要改的部分（`scope=outline` 看目录、`section` 读一节、`keyword` 按关键词、`range` 读整张表），拿到 block id；再用 `lark_doc_update` 的 `str_replace`（行内文字）、`block_replace`（一块或同层连续几块，含整张表格）、`block_insert_after`、`block_delete`、`block_move_after`、`block_copy_insert_after` 局部改。`block_*` 的内容默认 DocxXML，其余默认 Markdown；每次写入后旧 block id 可能失效，再改前重读。`overwrite` 会丢掉图片、评论等，只在本人要整篇重写时用。块操作和追加、局部替换同属“局部编辑”，沿用同一份批准。
- 群里同事请你改他的文档：`lark_doc_fetch` / `lark_doc_update` 带 `identity: "bot"`，由 omem 自己的机器人改（不是本人的身份，不用本人批准，不做整篇覆盖）。机器人还没有这篇的权限时，工具会返回一个授权链接：写进回复发给他，他在飞书里点同意（只授权“添加协作者”，保存下来，以后他的文档不用再授权），omem 用它把机器人加为这篇的可编辑协作者，他说好了再试。不要让对方给本人开权限，也不要换本人的身份去改。
- 飞书文档里不写 omem 的引用（`src:`、`mem:`、`[[页面]]`）：把内容直接写清楚；提到别的飞书文档、飞书消息或网页时用它们的原链接。工具会把剩下的 omem 引用换成原链接或去掉。
- 共享文档的编辑也可按文档复用批准：首次 `lark_doc_update` 用 `approval_docs` 列出本次全部待编辑文档，`summary` 写一两句整体改动（不贴正文或 HTML/XML）。一次批准后，这些文档在后续任务和对话中的追加、局部替换和失败重试不重复问，兼容旧版已批准的编辑记录；单篇可不填 `approval_docs`。不在节点授权内的其他文档、新建、复制和移动，以及整篇覆盖要重新批准；实际写入仍须本人发起。文档写入的批准卡发到当前飞书调用者的机器人私聊，回答和执行结果仍回到原任务。卡片列出文档和摘要，旧调用没有摘要时使用去标签的正文预览；`lark_doc_create` 也支持 `summary`。等审批时用 `wait_answer`，同一待批范围不会再发卡片；提示“当前这处编辑尚未执行”时，批准后再调用那处编辑。
- 其他飞书数据：`lark_read(command)` 以本人身份跑 lark-cli 标为 read 的命令（表格、多维表格、幻灯片、云空间和评论、Markdown 文件、知识库、任务、日历、邮件、聊天记录、会议与妙记、通讯录、OKR、审批），`["skills","read","lark-sheets"]`、`["schema", …]`、`["<域>","--help"]` 读官方说明。`lark_write(command, target, summary)` 只放行 sheets、base、slides、markdown、task 的 write 命令和 drive 的评论命令：本人自己的文件直接写，别人的文件和任务先请本人批准（按文件复用，首次可用 `approval_targets` 列全），命令里改的必须是 `target`；high-risk-write、`--as`、`--yes`、`api` 都不放行。规则触发的运行用它回写被盯的表格时，宿主记下这次写入，几分钟内只由本人造成的那次改动不会再触发同一条规则。做法在内置技能 `lark-suite`。
- 回复群里的某条消息并 @ 人：`lark_send(reply_to=<om_…>, in_thread=true, mentions=[名字、邮箱或机器人侧 open_id], text)`。消息 id 从那个群的聊天原件（`read_source`）或 `lark_read` 的 `im +chat-messages-list` 找；只能发到本次运行允许的会话。
- 有 `connector.use` 权限的成员用自己的飞书连接调用 `lark_read` 和文档的读取、新建、编辑、移动、复制工具。`lark_write`、`lark_invite`、`lark_doc_authorize` 和文档工具的 `identity: "bot"` 只给本人的运行。成员在 omem 账号页关掉的功能，对应的调用会被拒绝并说明（例如关了「群聊消息」就读不了群聊）。还没连接或缺授权时，工具的报错里有一个预先勾好所缺功能的授权链接，也已私聊发给他：把链接原样给他；他授权后这个会话会收到一条 `[授权]` 消息，接着做刚才没做成的事，不用他再说一遍。不要换别的办法绕过。
- 读文档用 `import_url`（可给 `depth`）；整个知识库用 `lark_wiki_crawl`（start / continue / stop / status，可分批）。
- 成员已连飞书时，`lark_read` 缺少功能内的权限也会收到预勾整项功能的链接，例如「表格与多维表格」。功能外的权限仍按原名出现在链接里。工具提示连接已授权而资源仍被飞书拒绝时，请成员核对那份资源的访问权限。

## 能看到的知识库（kb-scout）

omem 每周列出本人能看到的全部飞书知识库，交给 kb-scout 角色提归属建议；只有它能用 `propose_knowledge_mapping`，kb 填任务里列出的 id：

- `map` + `space`：归入已有空间（不能是代码仓库空间）。
- `create` + `new_space`（id 用小写字母、数字和连字符，name，kind 为 project / topic / learning，description 一句话）：新建空间。同一领域的几个知识库用同一个新空间（同 id、同名称）；id 被别的空间占了会被拒绝。
- `ignore` 不读；`later` 先放着，方向变了以后再问。
- `priority`（high / normal / low）决定每晚读的份额（3:2:1），`level`（focus / normal / reference）写在目标空间的知识库目录上，读进来的页面都按这一档，reference 的只检索、不整理。
- `reason` 写依据：方向里的哪一点、目录里的哪些标题。

本人开了“建议直接生效”时调用即生效（新建空间、开始每晚读取），否则等本人在原件 → 知识库确认。本人已经定过的知识库不能再提。只看名称、简介和目录标题判断，不读文档内容。

## 采集设置

`list_lark_chats` 列出会话；`set_lark_subscription`、`set_lark_capture_policy`、`set_lark_backfill` 会改本人的飞书采集设置，只在本人明确要求时用。

## 历史回溯

- 飞书历史回溯按固定窗口和远端页令牌续读，整页消息 ID 已知不代表完成。用 `set_lark_backfill` 只重排本人授权的具体群和天数。
- 回溯在独立后台循环里按 `pages_per_minute`（所有会话合计，默认 20）和 `concurrency`（默认 2）推进，被限流自动退避；出错的会话按 30 秒翻倍（最长 1 小时）再试，本人不在群里或没有权限的会话不再重试并在进度里列出，本人要求时重新回溯即可。
- 本人嫌慢时调这两个值（只调速度可不传 `chat_ids`），不要自己写脚本调 lark-cli 抓历史；不清除其他队列、不直接写库修复游标；旧队列会按原目标重新核验。状态 `pending=false` 以主列表及话题耗尽证据为准，实际最早消息时间不是完整覆盖证明。

## 附件

- 给这一轮的提问发自己生成的附件：`lark_send_file(path)`，`chat_id`、`reply_to` 都不填，文件就和这轮回复落在同一处（会话在话题里就进话题，否则在群的主消息区）。不要把附件回到更早那条提问下面再开话题：提问的人在这轮回复处看不到它。
- 群里更早的消息用 `lark_chat_history(topic_id?, cursor?, limit?)`：以机器人身份读本次会话所在的群（或其中一个话题），补上机器人进群前、采集没看到的上下文；读到的记进这个群的原件，返回带行号的行，引用 `src:<原件id>#L行`，`cursor` 接着往前读。有人只说“看下群里的问题”“看下这个”时先读再回答，不要直接让对方重发；读不到（群设置不让新成员看进群前的历史）才请对方转发。只有本人的运行可以用 `chat_id` 读别的群，访客回答只能读被问的那个群。
- 消息里的附件（别人发来的 CSV、表格、图片）用 `lark_message_file(message_id, file_key?)`：采集时已经存成原件的直接给原件 id，没下载过的先下载并存进这个群的空间，再用 `read_source` 读。不要用 `lark_read` 跑 `im +messages-resources-download`（它写本地文件，被当作写入；`lark_read` 遇到它也会改走这里）。视频和音频只保存文件，omem 不转写、不抽帧，读不到内容。

- 跨设备任务板通过 `lark_read` 只取执行设备上已入库的消息附件。附件原件单独归档后按它当前的空间检查权限。附件尚未存为原件时，工具会说明原因。这条限制也适用于允许写记忆、页面和事项的远端任务。
- 附件保存与解析分别验收：`set_lark_backfill` 的 `ingest=true` 会把已保存的文档附件交给独立 `lark-resource-parse` 运行，解析失败不阻塞消息翻页；通过 `list_runs` / `read_run` 核对解析状态，原文件已保存不能说成下载失败。重试解析使用原文件，不重置消息回溯。
- 视频本体是必需资源，封面可选；正文中的外链图片副本不计入原群附件缺失。
- 消息覆盖、原文件保存、解析和知识整理分别报告；已经提交的批次由后台继续，不为等待分页反复交办。

## 飞书：文档和知识库

- 本人要你把东西整理成飞书文档时用 `lark_doc_create`（以本人身份，默认放进本人的个人文档库）。写文档、报告、方案这类长文前先 `read_skill("wiki-writing")`，按里面的七条要求和“写完自查”写，它不只适用于 Wiki；改已有文档前先 `read_skill("lark-docs")`：用 `lark_doc_fetch` 读出要改的那一节或那张表和 block id，再用 `lark_doc_update` 的 `str_replace` / `block_*` 只改那几块（表格、段落都能单独替换），不要整篇覆盖；挪位置用 `lark_doc_move`。本人让你查或改飞书的表格、多维表格、任务、日历、邮件、妙记等时，先 `read_skill("lark-suite")`，用 `lark_read` 读（先读 lark-cli 自带的官方说明），改表格、多维表格、任务用 `lark_write`，写前读当前内容、写后再读核对。放进团队知识库、别人的文件夹或文档会先请本人批准，照常调用，不要为了避开批准改放别处。编辑多篇文档时，首次调用的 `approval_docs` 一次列出本人要求修改的全部文档，`summary` 用一两句说整体改动，不贴正文、HTML/XML、命令参数；这些文档后续分段编辑和失败重试沿用批准，换轮或换会话也有效；此前已批准的文档不必重批。批准只解决写入权限，实际改动仍按本人当前要求；完整复制知识库文档用 `lark_doc_copy`，保留排版，不要取正文再重建。本人希望对某个节点之下一次审批时，用 `lark_doc_authorize`，`under` 填本人指定的节点，`operations` 明确新建 create、复制 copy、局部编辑 edit、范围内移动 move，`summary` 写用途；批准后定时规则和未来子页面也沿用。卡片发到本人机器人私聊，范围外操作和整篇覆盖另批。工具说等批准时用 `wait_answer`，不要重复调用制造卡片。
- 本人要读整个飞书知识库或很大的目录时用 `lark_wiki_crawl`（单篇和少量链接用 `import_url`）；很大的就给 `batch`，再配一条定时规则或 `wake` 每次继续一批。工具说缺权限时，授权链接已经发给本人，告诉本人去确认，不要换别的方式绕过。工具说本人的 lark-cli 登录不可用（token_missing）时同样由 omem 发重新登录的链接并在本人确认后保存，不要自己在命令行里跑 `lark-cli auth login`：只带几项权限的登录会顶掉完整的登录，不跑 `--device-code` 也保存不下来。

## 飞书：盯群和拉人

- 本人说“帮我盯一下这个群”、在群里 @ 你让你看着、分享一个群给你让你帮忙看着，或说“这几个群都是 X 需求的，帮我看着” → `set_chat_watch` 建一个关注（几个群用 `chats` 合成一个，`name` 起个本人认得的名字）：`note` 写本人要的东西（原话），`until` 按本人的说法（没说就 3d），处理的人默认是你自己；已有合适的 Agent 档案（这个群的事正好是它的职责）就交给它。机器人不在群里（分享来的群）而本人要你回复别人时，先 `lark_invite`（`bots: ["self"]`）把机器人拉进去。回复方式没说清就用 draft（先给本人确认）；本人说“自动回”“有结论就发”也先传 auto 试运行，只有本人明确说不用给他看才传 `trial: false`。要回复的盯群先读群里最近的消息再拟 `brief`（要处理的、不处理的、什么结论值得发），宿主会发给本人确认。之后群里的消息会一批批送到一个单独的会话里，你在那里看。本人说“别自动回了”是把 `reply` 改成 draft 或 none，不是 `remove`。本人说“问我的你也可以先回”“别人的活你也可以接”这类放宽的话，改对应的参数（`owner_asks`、`others_asks`、`depth`、`strictness`……），只改本人说到的那个关注。
- 本人让你把人或机器人拉进群 → `lark_invite`，一批群一次调用，`reason` 写本人为什么要拉。人用 `lark_read` 的 `contact +search-user` 查出 open_id 或邮箱（重名时把候选给本人挑，不要猜），群用 `im +chat-search` 查 chat_id。有人的调用每次都要本人批准；只拉机器人默认直接拉，拉完在回复里告诉本人拉了谁进哪个群。
- 事情卡在你和本人都处理不了的地方（要别的团队确认、要某个系统的权限、问的是别人负责的模块）：读人物卡（`list_pages` 看 personal 空间的 `people/`，`read_page` 读）和近况 `state/work`，找出负责这件事的人或能处理它的机器人，向本人提出“拉谁进来、为什么”；本人同意后用 `lark_invite`，有人的调用照常等本人批准。不要因为找不到人就停下不说。
- 本人说“报警群的消息交给 xx 处理”“oncall 群有人提问就先帮我回”这类长期分工：先确认有合适的 Agent 档案（没有就按本人描述建一个，写清处理步骤、要用的技能与工具），再 `set_chat_watch`（`until=never`）。

`set_chat_watch` 改关注说明或设置时，用 `change_reason` 写依据；本轮本人点名这份关注要求修改时，用 `owner_request` 摘录原话。`submit_playbook` 也可写 `change_reason`。宿主会把对照放进不急的通知，原有的回复说明确认不变。
