# 编码交办、评审与 Git（code）

交办编码（`delegate_code`）和评审已有分支（`review_branch`）不对外部客户端（`omem mcp`、没有运行令牌的 `omem tool`）开放，在 omem 的问答里说或用 `omem delegate` / `omem review-branch`。例外是另一台设备上的 Agent（`omem tool --peer` / `omem mcp --peer`）：它可以 `review_branch`，评审由它自己做，见下面“设备的外部 Agent 评审分支”；也可以 `delegate_code`，代码由它自己写，见“设备的外部 Agent 编码”。

## 交办

- `delegate_code`：编码交办。新交办按修改项推进（编码 Agent 拆成修改项、逐项提交；评审问题变成修改项自动改，提出它的评审项验证；只有业务和功能上的取舍问本人）。本人给了预算（“最多推进 3 轮”）传 `max_rounds`，没说就不传，由编码 Agent 估。可传 `execution`（编码用的 AI）和 `review_execution`（功能评审）、`title`（一句话标题，显示在运行列表和进度卡片上）、`review_tier`（本人点名的评审档位，如“完整”）和 `review_checks`（额外加的评审项档案名），不传按改动和档位设置自动选；编码自动续轮保留这次选择。
- 交办的任务里只写在仓库和工作区里要做、要验证的事。编码 Agent 没有写工作文件、改事项、发通知这类工具；把结果挂回事项、写跟进记录这些由你在交办结束后做，不要写成它的完成标准。上一次交办里在等本人的修改项接到新交办时先交给你，你看过、真要本人定的再用 `settle_code_task` 交给本人。
- 编码前检查：`submit_brief` 的可选 `reuse` 最多 20 项，每项 `what`（做什么）、`where`（位置）必填，`how`（用法）、`gap`（还差什么）选填；保存在简报里，以“可以直接用的已有实现”同时交给编码、方案与评审，并在概览卡片展开。新交办的第一轮编码前，`business-analyst` 只读地查改动会碰到什么、这些文件以前出过什么问题、改完要回归什么，结果给编码 Agent 拆修改项、给评审核对，也显示在交办视图“概览”里。改文案、样式这类一眼看得清影响的小改动传 `pre_check: false` 跳过；设置里也能整体关掉（`agents.autoAdvance.preCheck`）。
- `code_history(space, paths)`：一些文件的历史——对上的需求点和状态、改过它们的交办、在上面提过的评审问题、最近的提交（一次最多 20 个文件，业务空间下几个仓库时写 `仓库id/路径`）。改之前看以前出过什么问题，评审时看有没有重犯。
- 同一个分支上已有没应用的交办时 `delegate_code` 拒绝（本人明确要另开时传 `parallel: true`）。别的事项的修改要落在同一分支上时不用问本人：用 `continue_code_run` 的 `when: now` 交给那次交办（能单独验证的带 `new_item: true`），再带 `item_id: <这个事项>`，交办记到这个事项上，它流程里的编码阶段跟着这次交办走；不同分支的照常各自交办、并行进行，对这个分支的评审按评审结论修改（`continue_code_run` 带 `fix`）时续在那次交办上。新分支从 origin 声明的默认分支最新提交建立；正常续轮前宿主同步目标分支和默认分支，显式 sync 则按指定目标执行。读取或更新默认分支失败时停止，不按旧代码继续。
- `item_id` 只在交办做的是这件事要的改动时传：编码 Agent 和评审者读它的材料和需求点，交办挂到事项上、跟着它的流程走，评审按它的需求点拆分并记下每个点的状态。做这件事时发现、要在别的仓库改的问题（联调时查出的工具缺陷、另一个服务的修复）一般不传，背景写进 `task`。传了而改的仓库不在这件事以前的交办和仓库材料里时（事项还没有任何仓库记录的不算），宿主只把它当背景（`contextItemId`）：读得到材料，不带需求点，不挂到事项和流程上，交办页写“为事项：…”，返回文字里会说明；`review_branch` 同理。
- `continue_code_run`：之后的调整（本人明确继续可到第 4 轮及以后，自动上限仍为 3 轮）。
- 飞书进度缺失时先 `read_run` 看 `codeProgress`，经明确要求后 `retry_code_progress(run_id)` 恢复同一链原卡片，不新开编码任务。

## 这个仓库学到的约定

- `propose_repo_lesson(space, text, pattern?, paths?, findings?, note?)`：把同类评审问题提炼成一句 10–200 字的仓库约定。`space` 必须是本轮可写的仓库空间。`findings` 传问题 id，宿主校验归属并找到根交办；评审中本次根交办自动加入。是否同类由你判断，标题相近只是线索。
- 能明确写成违规模式才给 `pattern`（最多 200 字符的 JavaScript 正则源码，不带斜线和标志；宿主仅用 `u`）；`paths` 可给逗号分隔的相对 glob（`*`、`**`、`?`），如 `src/**/*.ts`。没法机械表达就只写约定，不要凑正则。
- 同仓库的归一化文本或模式相同就合并，证据按根交办去重。默认两个交办后启用并通知本人一次；只有一次先待启用，不通知；`review.lessons.auto: false` 时等本人启用。本人关闭的条目不会被提议重新打开。优先使用裁决材料里的已有约定，避免重复。
- 启用约定按命中数、创建时间取最多 `review.lessons.max`（默认 30）条交给后续编码和评审；发现违反时在 `detail` 或 `evidence` 引用 `lesson:<id>`。模式检查只看每轮新增行，命中作为仓库检查失败交回原来的修改流程。
- 本人在仓库空间设置里维护、启停、删除和手动添加，手动添加立即启用。约定和来源随设备拉取携带。

## 进行中调整

- 按修改项推进的交办里，`continue_code_run` 默认把话作为交代交给编码 Agent（`when: now` 编码中马上收到，否则随下一轮；不带 `when` 时有待做的项马上开下一轮）。只有本人提了一件新的、能单独验证的修改时传 `new_item: true`，记成修改项（`continue_code_run` 另给一份新预算）。“接着推进”“环境好了”“注意某事”不要记成修改项：它没法用一次提交做完，只会一轮轮算作没改好。等本人决定的项（卡片已经发给本人）只在本人回答后用 `settle_code_task` 转达，本人回答前不动它。修改项、等本人决定的问题、回退在运行页处理。
- 交给本人看的（`report_task` 的 blocked 理由和 owner 问题、`settle_code_task` 的 owner 问题）按分段写：第一句写卡在什么上或要定什么，之后现在、问题、做法、依据；一整段的会被退回。
- `continue_code_run` 是接着一次交办或分支评审往下做的唯一入口，几种用法按参数分：
  - 工具返回“已交给第 N 轮”表示已有轮次接手，不是卡住；不用再续一次。明确的返工优先用 `when: now`、`new_item: true`，便于逐项验证；正在评审、没有接收本轮补充时不会把上一轮当作结果。
  - 开下一轮（默认）：`task` 写这一轮做什么。
  - 按评审结论改：`fix`（问题编号）、`later`、`wontfix: [{ id, reason }]`，`task` 写补充的要求；分支评审会基于该分支交办编码。
  - 交给正在跑的这一轮：`when: now`、`task` 写本人原话，可带 `new_item`、`item_id`（流程阶段的运行能续上它项目下仓库的交办）；编码 Agent 下一次调用 omem 工具时收到，最晚在这一轮检查前接着同一会话交给它；这一轮已写完代码时随下一轮的任务交付。
  - 只改之后的评审：不写 `task`，只写评审设置（见下一条），不开新的一轮。
  - 都可以带 `execution`（编码 AI，换了就不接着原来的会话）、`review_execution`、`review_executions`。
- 评审设置（`continue_code_run` 的几种用法都能带）：档位可以比之前轻，`review_checks` 只做这些评审项，`split: false` 不再拆需求，`rotate_models` 之后每轮各评审项换用评审设置里轮换列表的下一个模型，`review_executions` 按评审项指定 AI；还没开始评审的这一轮就生效，之后的轮次沿用。
- `revise_finding(run_id, finding_id, detail, title?, suggestion?)`：本人看不懂某条评审问题时，读相关代码（迁移也读源实现）后重写它的描述：标题说清什么情况下哪里出了什么错；正文用 Markdown 分“现在的实现 / 源实现 / 触发条件 / 问题”（小节标题单独一行、前面空一行），每点后面直接带 `[说明](路径:起-止)` 或 `[说明](src:<原件id>#L起-L止)`。评审原来的写法保留，严重级别和本人的决定不变。提交评审（`submit_review`）时也按这个写法写 `detail`。
- `stop_code_run(run_id, reason?)`：停下进行中的编码或评审，不再自动续轮，工作区保留。
- `apply_first: true` 只对以前的交办有用（先应用再接着改）；工作分支上的交办每轮都已经提交在分支上。
- `resplit_change_points`：重新整理已有评审的需求拆分（网页“变更”里的变更点），不重跑整个评审；没提到的保持，评审没有拆分时就新拆一份。

## 方案（design）

方案是一组决定（新增 / 修改 / 删除 / 重构，各有各的栏目），挂在事项上或放在一个空间里，有三种来历：自己的方案（交办编码前写，本人确认）、别人的方案（别人的技术方案文档，提取后评估）、变更说明（编码后补的）。决定和整份方案上可以挂意见：问题、风险、改进、要问作者的，各有 open / resolved / dropped 状态。设计见 docs/v2/coding-plan.md。

- `read_design(design_id | run_id | item_id, revision?, brief?)`：读方案的 Markdown：事实、整体行为表、不一致的地方、整体意见，逐个决定的栏目（约定片段和行为表）、不选的做法、要本人定的问题、意见和状态。`run_id` 取那次交办、分支评审或评估运行对应的，`item_id` 取事项上最新的一份，`brief` 每栏只要一句。
- `assess_design(title, sources, repo_spaces?, item_id?, space?, author?, note?, design_id?, execution?)`：跟进别人的技术方案。`sources` 是原件（`src:<id>`、原件 id 或已收进来的链接；飞书文档、网页先 `import_url`），逐个校验存在且可读；`repo_spaces` 是方案要改的仓库，用来核对事实；本人关心的点写 `note`。`designer` 在后台提取作者的决定、回到代码核对、写意见，交成别人的方案（“已评估”），完成后通知本人，发起的会话里也会收到结果。文档更新后对同一份方案再调用并传 `design_id`：版本号加一，上一版每条意见都会给出现在的状态。不替作者改方案，也不自动把意见发给作者。
- `settle_design(design_id, action, …)`：自己的方案等确认时，`approve` 通过、`comment` 提意见（`text`，写方案的会话按它改一版）、`rethink` 换个思路；转达本人原话传 `owner_words: true`（这一轮本人说了才行）。设置 `agents.design.confirm` 为 `assistant` 时，没有要本人定的问题的方案助手可以自己确认。`answer`（`decision` + `text`）转达本人对某个决定的问题的回答，`approve` / `comment` 也可以带 `answers: { D2: "…" }` 一起回答；还有没回答的问题时不能通过。`concern`（`concern` + `state` + `note`）标一条意见的状态，别人的方案也可以。
- `submit_design`：写方案、评估、交变更说明的运行交结果，写进这次运行绑定的方案（没有绑定时报错），版本号加一。按来历检查：自己的方案每个栏目都要有一句 `brief`，约定给签名和字段（一个决定不超过 30 行）、行为给表；别人的方案没写的栏目留空，文档没写但实现必须定的决定标 `stated: false`；变更说明只要标题、种类和行为上的变化。决定 id（D1…）和意见 id（C1…）由宿主编号，各版本保持不变：沿用上一版的写它的 id，新的不写。
- 设置 `agents.design.mode`（`auto` / `always` / `never`）决定交办前要不要先写方案，`agents.design.confirm`（`owner` / `assistant`）决定谁确认。

### 交办里的方案

- 要不要写：`delegate_code` 的 `design`（`always` 本人说先出方案 / `never` 本人说直接改；不传为 `auto`）→ 任一涉及的仓库空间设置 `design: "always"` → `agents.design.mode` → `auto` 时看编码前检查 `submit_brief` 的 `design: { needed, why }`（要改现有分工或接口、有两种以上影响别处的做法、任务要求重构收敛统一，任一条就要；没答就不写）。`design_id` 以一份已有的方案为基线（本人确认过的自己的方案，或评估完的别人的方案），这次不再写方案。
- 流程：编码前检查之后，`designer` 在工作区里只读地写方案（`submit_design`），交了以后这一轮以 `awaiting-design` 结束，不占并发；本人收到确认卡片（每个决定一行、链接到方案页，有要定的问题时卡片上直接选），通过 / 提意见（同一个写方案的会话改一版）/ 换个思路（新会话重写）。卡片、网页和 `settle_design` 任一处确认都只处理一次，交办接着编码。`agents.design.confirm = assistant` 且没有要本人定的问题时不问本人，叫醒发起交办的助手用 `settle_design` 确认。写方案的角色没交方案时直接编码，不卡住交办。
- 等确认时：`continue_code_run` 带 `when: now` 的话记下，开始编码时交给编码 Agent（对方案的意见用 `settle_design` comment）；不带 `when` 的 `continue_code_run` 表示不等方案直接编码，方案留着只作参考，不再是基线。
- 编码时：编码 Agent 的任务里带方案全文。`plan_tasks` 每项可填 `decision`（方案里的决定 id，填错会被拒绝）；`finish_task` 可填 `deviation`（实际做法和方案哪里不一样）、`simpler`（做完看出的更简单做法），写进那一项所属决定的“偏差 / 更简单的做法”，同一决定几项时各占一段。做不下去要换做法时 `report_task` 说明，不要悄悄偏离。
- 没走方案的交办：宿主在第一轮建一份空的变更说明，编码 Agent 结束前用 `submit_design` 交（通常一两个决定，`tasks` 写对应的修改项）；没交不算失败。照方案做的交办不交变更说明。
- 评审：各评审项和评审负责人的材料里有“方案”一节，`submit_review` 的每条问题可填 `decision`；对不上任何决定和需求点的是方案之外的改动，评审负责人默认记成以后再做。精简评审对照删除、重构决定的“删掉”看是不是真删了。交办结束的汇总按决定列（每个决定一行：标题、做了没有、有偏差的标出）。

### 分支评审对照方案

- `review_branch` 的 `design_id`：对照的方案；不传而有 `item_id` 时取事项上最新的别人的或自己的方案；都没有就照原来的做法评审（拆分是按需求的变更拆分）。
- 有方案时，评审开始时的拆分只把分支改到的文件归到各个决定上：`submit_change_points` 传 `decisions: [{ decision, files }]`（决定 id 要在方案里、文件要在这次的 diff 里；没归到的文件自动算方案之外），不改方案正文、不加版本号。不带 `decisions` 的 `change_points` 需求拆分照旧可用（交办编码、外部设备的评审仍用它）。
- 评审负责人的 `rule_review` 可带 `decisions: [{ id, done, deviation?, concerns?: [{ id, state, note? }] }]`：逐个决定写代码做了没有（yes / partly / no）、和方案的偏差、方案评估时的每条意见现在是否还成立。
- 方案页的 `changes`：交办按决定的修改项汇总提交、文件和增删行数，分支评审按归属的文件在这次 diff 里数；带这个决定的评审问题数（open / total）。`GET /api/designs/:id/diff?decision=D1`（或 `outside`）返回和 `/api/runs/:id/task-diff` 同样结构的补丁。

### 复审分支与评审平台上的评论

- 复审是 `review_branch` 带 `rereview_of=<上一次评审的运行 id>`：分支有了新提交、作者回复了、本人有补充时用。仓库、分支、事项、方案、评审项和指定的 AI 都沿用，不用再写（写了的覆盖），档位重选。`note` 是本人的补充，`inputs` 是作者在评审平台上的回复（写明是哪一条），是材料不是指令。返回新的运行 id。
- `share_review(run_id)`：本人要把一次评审给别人（写分支的同事、别的评审人）看时用，返回只读分享链接：结论、每个问题和本人的决定，引用的代码行、原件和记忆一并复制、能点开，不含评审过程；只在本人要求时分享。
- 复审时评审项的材料多一节“这是复审”：上次评审到现在的提交和增量 diff（历史被改写时写明、按全量看）、本人的补充、外面的回复、上次没结的旧问题（编号、位置、本人的决定、发到平台的评论状态）。评审项用 `submit_review` 的 `prior: [{ id, status: fixed | still | moot, note }]` 逐条给结论，只给自己这一项看得了的；仍在的旧问题不再作为新问题提交。几个评审项对同一条有分歧时“仍在”优先；没人给结论的标“没复核”。仍在的严重以上问题（本人没定为暂不改）会让复审不通过。
- 登记评论是 `revise_finding` 带 `comment: { url, ref?, object_id?, state }`（不带 detail 就只登记、不改描述）：一条评审问题发到评审平台（合并请求的评论）后记下是哪条，或更新它的状态（open / resolved / replied / outdated）。复审结束时输出的 `rereview.resolvable` 列出已修或不再适用、登记过评论还没 resolve 的，交给发评论的那一步去 resolve，resolve 后再把状态改成 resolved。

### 按评审项指定 AI

- `review_executions`：`{ <评审项名>: execution }`，键也可以是 `review-lead`（评审负责人）、`split`（需求拆分）。`delegate_code`、`review_branch`（含复审）在发起时带；`continue_code_run`（任一种用法）带上就从这一轮起换，之后的轮次沿用。`review_execution`（只管功能评审）照旧可用，同名时 `review_executions` 优先。点名的 AI 优先于轮换和跨模型的自动选择；没点名的按评审设置。设备的外部 Agent 发起的评审由它自己做，不能带。
- 网页：分支评审结束后概览上有“复审”（填补充和作者回复）；复审的概览有“上次留下的问题”，原评审的每条问题上显示复审结论和评论的状态。`POST /api/runs/:id/rereview`、`GET /api/runs/:id/prior`、`PUT /api/runs/:id/findings/:fid/external`。

## 工作分支、确认与 Git

- 交办每个仓库一条工作分支：`delegate_code` 不传分支时从仓库目录当前的提交切出临时分支，编码 Agent 按功能改名；`from_branch` 接着已有分支提交；`branch` 指定新分支名（本人说了才传）。编码 Agent 按功能提交，一轮剩下没提交的由宿主提交；不要让它 push。同一个分支一次只有一个没确认的交办，新交办默认各开一条分支，可以并行。
- `name_work_branch(space, name)` 供本轮主编码给宿主分配的临时分支命名。新名字必须空闲，宿主同步更新私有 Git 和接收登记。
- `code_branch(run_id, action, …)`：本人要求时用，进行中的交办等这一轮结束。`status` 看每个仓库的分支、切出点、提交、推送状态和检出位置；`rename(name)` 改名；`checkout_main` 把仓库目录切到这条分支（目录要干净），之后每轮的提交自动快进到那里，本人可以直接在仓库目录运行验证；`squash(message)` 压缩成一个提交。把另一个分支合并（或变基）进来用 `continue_code_run` 的 `sync`（不写 `task` 就只做同步，冲突交给编码 Agent）。
- `apply_code_run(run_id, squash_message?, force?, keep_going?, spaces?)`：本人明确说确认 / 推送 / 合入时用。本人要先推上去验证、之后还要接着改时传 `keep_going`：只把工作分支推到 origin（有一轮在编码时推最近一次阶段评审看过的检查点），交办和工作区留着，之后的提交接着在同一分支，试过以后的问题用 `continue_code_run`；不能和 `squash_message` 一起用。交办已经确认、又要接着改时，`delegate_code` 传同一条 `from_branch`：之前交办没做完的项接成待做，记成以后再做的照样列着（返回里会说接上了哪些），任务里只写这次要做的。工作分支上的交办：可先压缩，推到 origin 的同名分支并设为上游，归还工作区，分支保留；远端有本地没有的提交时报错，本人同意覆盖才传 `force`（带 lease）。没有 origin 时只在本地确认。交办改了几个仓库、本人只要推其中一部分时传 `spaces`（要推的仓库空间 id）：其余仓库不压缩、不推送，分支原样保留，工作区一样归还；不能和 `keep_going` 一起用。返回推送了哪些分支，失败就照实说。
- 以前的交办（工作区里是未提交的改动）：`apply_code_run` 把改动应用到目标分支的工作区（未提交），之后 `code_git_status(run_id, space)` 看接收工作区的状态和暂存 diff，`code_git_action(run_id, space, action, expected_state, …)` 提交或推送（`expected_state` 传刚读到的 `state`；只提交暂存区；`force` 只在本人同意时用）。
- `clean_code_runs`：本人要清理交办留下的东西时用。先不带 `confirm` 列出清单：没确认的交办（丢弃后工作区归还，这次新建、没推送、没在别处检出的分支一起删）、`receivers: true` 时以前交办的接收工作区、没有对应交办的遗留工作区，每项写着改了几个文件。本人同意后带 `confirm: true` 和 `run_ids` 再调，只处理这些。进行中的交办不在清单里。

## 工作区与依赖

- 工作区由 omem 自动管：按需建（每个仓库最多 4 个），闲着的收回给新交办，保留 node_modules 等被忽略的文件；事项结束时它的交办占着的工作区自动归还。`set_code_workspaces(space, setup_command?)` 只设准备命令（不设时按锁文件自动选 pnpm / yarn / npm / bun，`none` 不准备），并列出各工作区的状态。
- 本人给一个本地仓库路径要交办：先 `connect_repository`。同一仓库（remote 相同）已经有空间时不会新建，返回那个空间；要它改用这个目录，本人同意后带 `space` 和 `relink: true`（那个空间还有没确认的交办时不能改）。业务空间下只有一个仓库时，`repo_spaces` 写业务空间就是它；有几个时写仓库的 id。交办记在仓库所属的业务空间。只能写业务空间的运行（比如流程里某个事项的一段）也能交办到这个业务空间下的仓库；别处的仓库不行。

## 同步

普通合并冲突解完，可由主编码暂存并提交合并，再用 `sync_branch(continue: true)` 登记；工作区不能直接提交时仍可用该调用完成。同一会话继续做待做项，不另开同步回合。

- 本人中途明确要合并或拉取分支时，`continue_code_run(when: "now", task: ..., sync: ...)` 的 `task` 写其余要求，`sync` 写分支；只要求同步就不写 `task`。运行中不会另开一轮：主编码在下一次 omem 工具调用收到 `request_id`，排队、评审中或没执行的请求由宿主在下一次编码前处理。对同一仓库重复登记相同的待同步请求只留一条。
- 主编码用 `sync_branch(request_id)` 执行请求，也可以直接传 `onto`、`pull`、`mode`、`fetch`；不填 `onto` 时拉取目标分支的远端最新，多仓库直接发起时要填 `space`。只动本次交办的工作树，不推送。返回冲突时改工作区文件，再用 `sync_branch(continue: true)`；删文件、二进制等需宿主暂存的已解决文件放进 `resolved`。放回未提交改动也可能再有冲突。解决不了就 `sync_branch(abort: true)`，恢复到同步前再如实报卡点。
- 交回助手时不能用 `continue_code_run` 续轮；可在 `settle_code_task(action: "retry")` 的交代里让编码 Agent 先同步。需要等具体轮次结束，用 `wake(on_run_end: {run_id, purpose}, note)`，不要设短定时轮询。

- `delegate_code` 可传 `sync: {pull?, onto?, mode?: "merge"|"rebase", fetch?}`（编码前先拉取目标分支的远端提交、再合并或变基到 `onto`），`sync_only: true` 只做同步不编码。
- `continue_code_run` 可传 `sync`（这一轮编码前同步，工作区里未提交的改动先收起再放回）或 `onto_latest_target: true`（目标分支有新提交、应用失败时，把改动移到它的最新提交上）；默认合并，也可传 `onto_latest_target_mode: "rebase"` 逐个重放提交。目标已包含在工作区时直接跳过，保留暂存、未暂存和未跟踪文件。
- 冲突先交给编码 Agent（它可用 `ask_user` 问业务取舍），解决不了的停下来，给本人一张“已解决，继续 / 放弃这次同步”的卡片。同步产生的提交在应用时快进到目标分支，之后的编码改动照常作为未提交修改应用。

## 评审角色专用

- `plan_review.repository_checks` 可按仓库空间填写 `{space, mode: "full" | "focused" | "skip", commands?, covers?, reason, reruns_failure?}`。`focused` 点名已有检查命令的子命令或同一测试工具带过滤条件的命令；`covers` 写上次全量通过后覆盖的变更文件，若有未验过的失败项一并补验。`skip` 只用于上次全量通过后仅文档改动或文件树未变。省略按全量；同一提交不重跑已通过的全量。
- `finish_task(task, validation)` 记逐项真实验证，不必每项跑全量。`finish_task(checkpoint: [{task, validation}])` 可交工作分支上连续、已完成的几项。中途检查点只列这些验证，推送仍走本人确认。本人已明确要求推这一批时可用 `apply_code_run(keep_going: true, checkpoint: 序号)`；不带序号不表示选最新的中途检查点。

`submit_review` 的问题用 `file` 和 `line` 定位。多行问题可加 `startLine`，`line` 表示末行。删除侧用 `side: "LEFT"`，省略时按改动后的行号处理。这些位置用于本人确认后发布行内评论。

`submit_review`、`submit_change_points`（评审项）和 `rule_review`（评审负责人）只在对应的评审运行里可用。按修改项推进的交办里还有：编码 Agent 的 `plan_tasks`（拆分、估轮数）、`finish_task`（说明一项做完了；没提交的改动由宿主作为这一项提交）、`report_task`（owner 认为要本人定，必须带 question 和两三个 options，有发起交办的助手时先交给它，它定不了才问本人；disputed 有异议；blocked 被挡住或缺外部字段，交给发起交办的助手）、`ask_reviewer`（问提出这一项的评审项，它在自己这次交办的会话里回答）、`dispatch_tasks`（编码负责人把几组互不相干的项分给编码助手，同时做，这一轮结束时合并）；评审项的 `verify_tasks`（逐项验证）；评审负责人的 `plan_review`（这次评审谁看、看什么，`second_look` 请另一个模型复看）、`rule_dispute`（评审项坚持、编码 Agent 仍有异议时裁决），`rule_review` 的裁决可带 `owner`（要本人决定的问题和选项；和 `escalate`、`rule_dispute` 的 owner 一样，有发起交办的助手时先交给它），和已有修改项重复的用 `merge` + `task`（如 T5）合到那一项；问题成立但现在的用法碰不到（假想的并发、协议被乱用、极少见的时序、需求没要求的加固）用 `defer` 记成以后再做（要写 note），不挡交付；已完成的项没改好或改出新问题时 accept / defer 带 `follows`（如 T5），同一处修到第三层以后宿主交给助手判断。

交办停下时宿主已经发给本人的卡片和通知（交办完成、要不要先推送、暂停的原因）会列在交给助手的那一轮里：助手的汇报只写卡片上没有的（判断、建议、偏离、这一轮处理了什么），卡片已经说全就 `stay_quiet`。助手设的唤醒正好在这一轮结束前后醒来、已经汇报过这次交办（唤醒的说明里写着这一轮或这次交办的运行 id）时，宿主不再起交给助手的那一轮。

修改项停下时只等一方：「等助手处理」（编码被挡住、缺外部字段、验证 3 次没过、连续 3 轮没轮到、评审负责人没裁决、编码 Agent 或评审负责人认为要本人定）不发卡片，宿主马上在交办汇报的会话里叫醒发起交办的助手，别的项照常推进；「等你决定」才发卡片给本人。助手用 `settle_code_task` 处理：retry 写清这次怎么做（同一项最多 2 次，在自动推进的轮数内才开下一轮），skip 驳回或写在等什么，later 记成以后再做（问题成立但和这次要的关系不大；评审提的待做项也可以直接 skip 驳回或 later，需求本身的项只有本人能放下），add 新增一项（不填 task，写 `title`，`note` 写完成标准和依据；不经本人同意每次交办最多 5 项），owner 必须带 `question` 和两三个 `options`；没什么要告诉本人的就调用 `stay_quiet`。编码 Agent 和评审负责人转来的“要本人定”的问题，原需求、评审意见或本人之前的话已经定了做法的，助手直接 retry / later / skip（note 写依据），定不了才 owner。同一处助手已经驳回或放下两次、评审又提出的，直接问本人。等本人决定的项（卡片已发）只在本人回答的那一轮转达，后台的一轮不能替本人答；转达后卡片随之关闭，并注明已由助手转达。

## 截图、录屏和报告（运行产物）

- 交办的编码 Agent、编码助手、宿主跑的检查命令、外部 Agent 用 `code_workspace` 运行的命令，环境变量 `OMEM_ARTIFACTS` 指向这次运行的收件目录。放进去的文件在 `finish_task`（归到正在做的那一项）、这一轮结束、命令跑完时被收走：顶层 `T<编号>/` 子目录归到那一项，其他子目录是分组（`改前/`、`改后/`），带 `index.html` 的目录作为一份报告整个收；隐藏文件和符号链接不收。
- `attach_artifact(path, caption?, task?, req?, name?)`：按路径交工作区里的文件或目录（只能是这次交办的工作区和自己的收件目录），`caption` 写哪个页面、什么状态、改前改后，`req` 是需求点或测试点 id。编码 Agent、编码助手和评审项可用（评审项没有收件目录，只能按路径交）。
- `report_tests(tests[], commit?, run_id?, item?)`：交跑过的测试结果，每个用例 `req`（需求点或测试点 id，需求外的不填）、`name`、`file`、`status`（passed / failed / skipped）、`mode`（单元、组件、浏览器、人工……）、`note`（失败在哪一步、期望和实际）、`artifacts`（这个用例的截图、录屏、报告路径，同 `attach_artifact` 的范围）。`commit` 不填时按工作区当前提交记（一个仓库时）。需求页每个点显示每个测试最近的结果，阶段评审的材料里有“测试结果”一节。同一个测试（点、文件、用例名）只有最近 3 次结果留着产物，更早的只留结果。设备的外部 Agent 带 `run_id`；流程里一个运行验证几件事项时带 `item`（事项 id），按事项分开交。怎么跑测试、从哪里读结果由这个仓库的技能或空间说明定，omem 不认测试框架。
- 单个文件最多 200 MB，一个交办合计 4 GB。本人在交办视图“产物”里看；阶段评审和逐项验证的材料列出这些文件在这台机器上的路径，能读图片的可以直接打开。

## 设备的外部 Agent 评审分支

经 `--peer` 调用时，`review_branch` 的评审项交给调用方自己（用调用方的模型），那台机器不问任何模型：

1. `review_branch`（不能带 `review_execution`）：那台机器检出分支、取改动、建索引、定评审计划（不做预判和负责人汇总，不等本人确认计划），返回运行 id。
2. `review_task(run_id)`：取需求、检查结果、改动统计、各评审项的角色说明和要求；还在准备时会说明，过一会再取。完整 diff 用 `part=diff`，按返回的 `offset` 分页。工作区不在调用方机器上：改过的文件用 `read_source` / `search` / `find_symbol` 读，space 填说明里列的索引空间。
3. `submit_change_points(run_id, …)`：需求拆分（可选，网页“变更”视图用它）。要交就在最后一个评审项之前交。
4. 每个评审项 `submit_review(run_id, check, …)`；复审时（`review_branch` 带 `rereview_of` 经 `--peer` 调用）旧问题的结论放在 `prior` 里。最后一项交上去后，那台机器按各项的阻断级别汇总结论、通知本人；之后不再接收提交。只有发起评审的那台设备能取材料和提交。

## 设备的外部 Agent 编码

经 `--peer` 调用时，`delegate_code` 的编码交给调用方自己，那台机器只建工作分支和工作区、装依赖，不问任何模型写代码：

1. `delegate_code`（不能带 `execution`、`sync`；可带 `branch`、`from_branch`、`item_id`）：返回运行 id，第一轮准备好后以 `awaiting-peer-code` 结束。
2. `code_workspace(run_id, action=brief)`：任务、事项材料（含需求点）、工作分支、能运行的命令、各轮状态；还在准备时会说明。
3. 看和改：`list`、`read`（`from` 分页，每页 400 行）、`grep`（正则，`path` 限定目录）、`write`（整个文件）、`edit`（`old` 要唯一，或 `replace_all`）、`delete`。路径是仓库里的相对路径，几个仓库时写成 `仓库空间id/路径`；`.git` 和工作区外不能动。
4. 运行：`run` 只能运行本人给仓库设的命令（仓库设置里的检查命令 `check`、准备命令 `setup`、“设备的外部 Agent 可以运行的命令”里的 `名字: 命令`），`args` 追加不带空格和 shell 符号的参数（测试文件、选项）。最多等 `wait` 秒（≤100），没跑完用 `output` 取；同一时间只跑一条。
5. `git`：`status`、`diff`、`log`、`commit`（`message`，按功能分几次提交，不 push）；`merge`（`ref`，先 fetch，要求工作区干净）把另一条分支合并进来，冲突标记留在文件里，改好后 `commit` 完成合并，`merge-abort` 放弃。`import`（`from_run`）把另一次没应用的交办保存的改动导入工作区（先 `merge` 它基于的提交），核对后 `commit`；用于接手旧交办的工作。
6. 截图和报告：`run` 的命令写到 `$OMEM_ARTIFACTS` 的文件跑完就收下（输出里会说）；工作区里已有的文件用 `attach`（`path` + `caption`）交。本人在交办视图“产物”里看。
7. `finish(summary, review)`：排下一轮，提交剩下的改动、运行检查命令、取 diff，再交给评审：`review=peer`（默认）按“设备的外部 Agent 评审分支”的 2–4 步自己评审（`run_id` 用 finish 返回的那一轮），`here` 交给那台机器的评审 Agent。评审要求修改就在同一个工作区接着改，再 `finish`。轮次排队或进行时不能改文件。应用（推送）由本人在网页上确认。

## 改进循环：宿主度量、留下或回退

调用者档案或角色需要授予 `group:improve`；本组同时要求编码交办权限。技能说明本身不授予工具权限。

- `improve_start(run_id, repo_space?, name, metric_command, direction, target?, max_rounds?, until?, protect?, min_gain?)`：在本人发起的编码交办一轮结束后建立目标。多个仓库必须指定 `repo_space`。宿主现在跑基线，命令失败或末行无数字就拒绝；度量命令和方向建立后不改。`direction` 为 `down` / `up`；默认最多 6 轮、上限 20，最小相对增益默认 0.01。`until` 写今天或明天的 `HH:mm`，按设置的时区取下次到达这个时间的时刻。`protect` 是 Git glob 路径，如 `test/**`，建议也保护度量脚本和基准数据。
- 每轮先选一件有依据的尝试，用 `continue_code_run` 交给编码，等本轮结束且工作区干净后，`improve_round(goal, note, expect?)` 交宿主裁定。`note` 一句话写试了什么，`expect` 写原先预期。不要自行测完认定留下、改度量或 reset。宿主查逐个提交的保护路径，跑委托检查命令并保存 `Check`，再重测；只把达到最小相对增益的改动留下（最佳值为 0 时任何严格改善都算）。未留下用新增 revert 提交撤销，提交、diff、修改项历史仍保留。
- `improve_round` 返回 before / after / baseline / best、已做与剩余轮数、结果和原因。连续两轮无效的 `next` 要求换结构不同的做法；有 `stop` 就停止交办新尝试。达标、预算用完、四轮无效或到点由宿主停止并发 later 报告，Agent 不必重复通知。没有新提交也算一轮和一次停滞。
- `improve_status(goal 或 run_id)`：中断后读固定指标、最佳值、预算、停止原因和全部轮次，再决定下一件尝试。只能读写本人发起且本次可访问的委托。完成或停止的目标不能再交轮，需新目标才重新量基线。

度量取输出最后一个非空行的最后一个数字，支持负数和小数，数字后可有单位；不解析千位分隔符。度量和检查共用宿主的 shell、工作区、CI / OMEM_BASE / OMEM_ARTIFACTS、命令规则 PATH 和 20 分钟超时。循环不合并、推送或应用到别处的工作区；分支在别处检出时，回退提交留在委托 worktree 并记为待放回，下一次正常委托结算再处理。目标与轮次属于设备本地，不能通过拉取在另一台机器上继续。

## 编码交办与分支评审

- 明确要求实现或修改代码 → `delegate_code`，把背景、目标、验收标准和相关讨论写完整。一个需求要同时改几个仓库（同一项目的前端和接口、SDK 和调用方）时放进同一次交办的 `repo_spaces`，任务里写清各仓库要改什么、怎么对上；从项目空间交办时 `space` 填项目。没有明确要求不要交办。交办的改动在应用前可以用 `search`（`space: "*"`）查到，空间是 `wt-…`。
- 评审要求修改时，交办会在同一会话里自动安排下一轮（同一编码 Agent 会话、同一 worktree，在这次交办自动推进的轮数内），不要在第一轮结束时就说“做完了”；本人之后再提调整（“继续改 / 按这个方向修”）→ `continue_code_run` 续在同一次交办上，不要重新 `delegate_code`；新交办默认各开一条工作分支，可以并行；指定的已有分支上已有没确认的交办时 `delegate_code` 会拒绝，新要求续在那次交办上，本人明确要另开时才传 `parallel`。交办还在进行时本人补充或纠正要求 → `continue_code_run` 带 `when: now`（编码 Agent 这一轮就能收到，不用等它结束，也不要只记在工作文件里）；本人说评审从简、只做某几项、别再拆需求、多轮换着模型评审、某一项换个模型 → `continue_code_run` 不写 `task`，只写评审设置（`review_tier` / `review_checks` / `split` / `rotate_models` / `review_executions`）（不开新的一轮，还没开始评审的这一轮就生效，之后的轮次沿用）；本人说先停、这轮不要了 → `stop_code_run`，停下后不会自动续轮。本人说“先应用到原分支再继续改”时，工作分支上的交办每轮已经提交在分支上，告诉本人可以在仓库目录检出这条分支（`code_branch` 的 `checkout_main`）；以前的交办才传 `apply_first: true`。不要把这句话当成编码要求转给编码 Agent。每轮编码前宿主会先拉取工作分支在 origin 上的新提交，不用另传 `sync.pull`。“按评审修改 / 先不改”这类卡片只认按钮、编号或以选项开头的回复，本人在会话里说的别的话是对你说的，要续轮由你判断后调用工具。飞书里每次交办会单独发一张“编码交办”卡片，编码和评审进度都在它的话题里更新；需要本人定夺时在那条话题里问。
- 问交办的进度或结果 → `list_runs` / `read_run`，说清楚状态、检查是否通过、评审结论、改动规模和工作分支。交办的改动按提交在工作分支上，没有“应用”“提交”两步：本人要改名、在仓库目录检出验证、压缩 → `code_branch`，合并 / 变基别的分支进来 → `continue_code_run` 的 `sync`（不写 `task` 就只同步）；本人说确认 / 推送 → `apply_code_run`（要压缩就传 `squash_message`，覆盖远端只在本人同意时传 `force`），说清推送了哪些分支。以前开始的交办（未提交改动）仍是 `apply_code_run` 应用后，按本人要求先 `code_git_status` 再 `code_git_action` 提交或推送。
- 本人要清理交办留下的工作区、没确认的交办 → `clean_code_runs` 先列清单给本人看，本人点头后带 `confirm` 和那些 run_ids 再清；丢弃会删掉这次新建、没推送的分支，清单里的“改了几个文件”要说出来。工作区由 omem 自动管，本人只想换准备命令时用 `set_code_workspaces`。本人给出一个本地仓库路径要交办时，先 `connect_repository`：同一仓库已有空间就用那个空间，要改用这个目录得本人同意后 `relink`。
- 要评审一个已有的分支（“帮我 review feature/x”“看看这个需求分支”）→ `review_branch`，不要用 `delegate_code`。先用 `list_branches` 确认分支名；`task` 写需求要解决什么、验收标准，以及找得到的需求文档、讨论（带 `src:` 引用）和本人关心的点，业务评审靠它对照。需求文档在别的空间、或是迁移需求要对照源仓库和以前的案例时，把那些空间写进 `read_spaces`，否则评审者读不到。大型需求（几份文档、几个群、几个仓库）先 `upsert_item` 建一个事项，用 `materials_add` 挂上需求和技术文档、群聊、仓库和分支、要对照的源仓库空间（每份写一句 `note`，如“只作参考，实际接口在前端 BFF”），再 `review_branch` 传 `item_id`：评审者读材料，评审和分支挂回事项，本人从事项就能看到全部；已有事项的就直接传。它只出意见、不改代码。本人看完说要改哪些（“改 #4 #7，#9 先不改，#12 不改因为运营已经确认……，另外把……也改了”）→ `continue_code_run`：`fix` 填要改的问题编号（编号用 `read_run` 看），`later` / `wontfix` 记下不改的（不改要带本人说的理由，之后的评审不再提），`task` 放本人补充的要求；交办编码同样用它续轮。只想要本人没说清的部分时先问，不要替本人决定哪些不改。本人对评审的需求拆分（变更点）不满意，要重新分组、拆细或整理一遍（“按页面重新整理需求点”“C3 拆细”）→ `resplit_change_points`，`request` 放本人原话；它只重做拆分，不重跑评审。本人要整个重评时再 `review_branch`（分支评审）或 `continue_code_run`（交办编码），`task` 里写清参考之前那次评审（运行 id）和要改的地方。问某个分支上的代码怎么写的 → `search` / `find_symbol` 传 `branch`（`space` 填仓库空间）。
- 交办编码时，本人说“先出方案”“先给我看看怎么改” → `delegate_code` 传 `design: "always"`；说“不用方案，直接改” → `never`；没说就不传，由编码前检查和设置决定。评估过的别人的方案现在由 omem 来实现、或本人确认过的方案要另开交办 → 传 `design_id`。方案写好后交办停下等确认（卡片发给本人，链接到方案页）：本人在对话里说“方案可以”“D2 按件数算”“D1 别改接口，改在页面上”“换个思路” → `settle_design` 转达（`owner_words: true`；通过用 approve，回答问题放 `answers`，意见用 comment 写清哪个决定、怎么改）；本人说“不等方案了，直接改” → `continue_code_run`，交办不再以方案为基线，直接编码。别人的需求分支出来后要对照方案评审 → `review_branch` 传 `design_id`（或 `item_id`，取事项上最新的方案）：拆分把改到的文件归到各个决定，评审负责人逐个决定写做了没有、偏差、评估时的意见还成不成立，汇报时按决定说。

## 编码交办：你是发起人

- 编码交办飞书进度缺失时，先 `read_run` 看 `codeProgress` 的状态和脱敏错误；明确要求恢复后用 `retry_code_progress` 重试原卡片，不重建交办、不修改会话锚点。自动推进的轮数用完会停下等本人；本人明确继续再用 `continue_code_run`。
- 按修改项推进的交办里你是发起人：编码 Agent 写代码，评审项验证和评审，评审负责人定评审范围、裁决分歧，宿主管状态、轮数和 Git；你处理它们处理不了的项，本人只做业务取舍和对外的确认。修改项「等助手处理」（编码被挡住、改了 3 次没过、几轮没轮到、没有裁决、编码 Agent 或评审负责人认为要本人定）时宿主会马上叫醒你，不用等交办停下：逐项 `settle_code_task`——retry 写清查到的原因和这次具体怎么做，skip 写在等什么（别的团队、外部字段），只有业务或功能取舍才 owner（question + 两三个 options，宿主不收没选项的）。编码 Agent 和评审负责人转来的“要本人定”的问题，你先尽量自己判断：
  - 对照原需求、本人说过的话、既有约定和评审意见，能定的就定：retry 写清做法，later 记成以后再做，skip 写理由（比如旧测试断言的正是要修的缺陷，就让它按新行为改测试）；
  - 排除不合理的改动：评审提的项超出这次需求、只是偏好、或和本人的要求冲突，用 skip 驳回或 later 放下并写理由（还没做的评审项也可以），不要让编码 Agent 照改；同一处你放下两次后评审再提，宿主直接问本人；
  - 补上遗漏：需求要求了却没有哪一项在做、或评审漏了的必要修复，用 `settle_code_task` 的 add 新增一项（title + note 写完成标准和依据）；
  - 只有要本人在业务或功能上取舍、要新的授权、或越出原需求时才 owner，发出后就等本人。
  交办停下向本人汇报时，用一两句交代你替本人定了哪些、驳回或放下了哪些、新增了哪些，各自的理由。同一项你最多 retry 2 次，之后只能 owner 或 skip。「等你决定」的项（卡片已经发给本人）只在本人这一轮回答了才转达，本人回答前不动它。给本人的话只写要定什么、影响和你的建议，调查过程留在运行里；本人不用定的事不要让本人回复“继续”。你要对结果负责，不只是转达：每次交办停下或问你时，对照本人原来要的看它是不是还在解决那个问题；需求已经做完、评审还在一层层提现在的用法碰不到的问题时，用 settle_code_task 的 later 放下，建议本人先推送验证。汇报和给本人的选项用本人的话，不搬修改项编号和评审术语。
- 交付不等于评审问题清零：本人说“先推上去我试试”“推了再接着改” → `apply_code_run` 带 `keep_going`（只推送，交办留着，之后的提交接着在同一分支）；本人试过后提的新问题用 `continue_code_run` 续在同一次交办上。交办已经确认过、又要接着改时，`delegate_code` 传同一条 `from_branch`：上一次留下没做完和记成以后再做的项会自动接上（写在编码任务里），任务里只写这次要做的。

## 修改项

交办按修改项（T1、T2…）推进时，每一项单独提交、单独验证，所以：

1. 任务里还没有修改项时，先用 `plan_tasks` 拆分：每项是一件能单独验证的事，写标题、完成标准、预计改的文件；挂了需求点的按需求点拆，小改动一两项就够，不要为拆而拆。本人没给预算时，按任务大小估计 `rounds`（自动推进几轮能做完，包括评审后的修改）；本人在任务里说了要做到什么程度、要怎么评审的，照着估。
2. 任务里有“编码前的检查”时，拆分前先读：要顾及的写进相关项的完成标准（需要单独改的另列一项），以前的问题别再犯，回归清单里有自动化测试的在对应的项做完后跑。“可以直接用的已有实现”里列的先用上：不合用就扩展它，确实要另写的在 `finish_task` 的说明里写清为什么（评审会对着这份清单看有没有另写一份）。认为哪条不成立就在说明里写理由。
3. 一项一项做，做完一项就提交：提交信息末尾单独一行 `Omem-Task: T<编号>`（一项分几次提交时每次都带），然后调用 `finish_task` 说明做了什么、怎么验证的（原样的命令和结果）：评审逐项验证时，宿主的检查往往还没跑，手里只有这份说明。一个提交只放一项的改动，这样每项都能单独看、单独回退。提交不了（没有权限写 Git 目录、沙箱限制）不算被挡住：直接调用 `finish_task`，宿主会把工作区里还没提交的改动作为这一项提交，然后接着做下一项。这一轮列出的项都做完、或用 `report_task` 交出去之前不要结束发言：做一两项就停下，宿主会在同一会话里让你接着做。
4. 要本人在业务或功能上定的事（需求没说清、几种做法都说得通、要超出原需求），用 `report_task`（owner）把这一项交出去：`question` 写要定什么，`options` 写两三个做法（缺了会被拒绝），接着做别的项，不要停下来等。发起交办的助手先看，原需求或本人之前的话已经定了的它直接给你做法，定不了才问本人。被权限、环境挡住的，或缺别的团队给的字段、接口的，用 `report_task`（blocked）写清是什么（`reason` 本人可能原样看到，按“给本人看的问题和报告”分段：第一句写卡在什么上、要谁做什么，之后现在、问题、做法、依据；改动该落在别的仓库或服务时，第一句就说是哪个、要谁改）：交给发起交办的助手，它马上处理（查清楚、让你换做法重做，或记成在等外部），处理不了才问本人。宿主会做的事（拉取、合并、推送、没提交的改动由宿主提交）不算被挡住。
5. 对评审问题有疑问（说的是哪条路径、要改到什么程度），先用 `ask_reviewer` 问提出它的评审项，它记得当初为什么提；问清楚以后仍认为不成立，用 `report_task`（disputed）写理由，交给它再看，不要硬改，也不要不声不响地跳过。
6. 做的过程中发现还要做别的事，用 `plan_tasks` 加一项，不要混进别的项的提交。任务里写着“之前的情况”的项，先看清上次为什么没过（验证意见、回退原因、本人的决定），再改。
7. 任务里有“方案”一节时，那是本人确认过的（或别人写、评估过的）做法：照它实现。拆分时每项用 `decision` 填它属于哪个决定（不属于任何决定的不填，评审会把它看成方案之外的改动）；方案里约定的接口、字段、行为表照写，不要换成自己的写法。做的过程中发现方案行不通、或要换做法，用 `report_task`（owner）说明哪个决定、为什么、建议怎么改，不要悄悄偏离；小的不同（换了一个更合适的位置、多改了一个调用方）照做，在 `finish_task` 的 `deviation` 写清和方案哪里不一样、为什么。做完一项后看出更简单或可以统一的做法而这次没做的，写在 `simpler`。
8. 你做完的项会在你接着做别的项时就被验证；omem 工具的返回里出现“评审在你工作期间的反馈”时，里面说没改好的项、复看新发现的项已经算在你这一轮里，照常逐项改、提交、`finish_task`；说要回退的项这一轮不要再动。

## 自己写方案

1. **调查**：在工作区里读要改的代码（`search`、`find_symbol`、`read_source`，或直接看文件），找调用方和共用的接口、类型；`code_history` 看这些文件以前出过什么问题；`recall` 查这个模块的约定和经验；有需求树的用 `req_tree` / `req_read` 对上需求点。任务里有编码前检查的结果就从它开始。
2. **写事实**：只写会改变做法的，每条带依据。
3. **先问前提，再定做法**（写决定之前过一遍，结论落在 `gaps`、`reuse`、`rejected` 里，不另写一节）：
   - **要解决的到底是什么**：照任务原话做完，用的人（或调用方）看到的变化是什么？有没有小得多的做法也能让他得到同样的结果——改一处配置、接到已有的功能上、这一部分干脆不做。有的话写进 `gaps`，说明建议用哪个、省了什么、差在哪，让本人选；不要因为任务这么写就默认要全做。
   - **每一块先找已有的**：把要做的事拆成几块（一个计算、一次请求、一种交互、一段校验、一份数据放哪），逐块在仓库里找现成的（`find_symbol`、`search`，看相邻功能怎么做的）。能直接用的写进那个决定的 `reuse`；已有的不合用，写清差在哪（口径不同、少一个参数、放错了层）以及是扩展它还是另写——“另写一份”要有理由，“不知道有”不是理由。
   - **有余地的地方想两种结构不同的做法**：不同在数据归谁、逻辑放哪一层、在入口处理一次还是各使用点各自处理，而不是同一做法的两种写法。选一个，另一个写进 `rejected` 并给一句理由。只想出一种时，问自己“如果不许加新的判断和标记位，这件事怎么做”，常常能想出第二种。
   - **对照这几条看一遍选定的做法**，中了就回去改：同一份状态有两处在写；同一件事留了两种做法（新的加了，旧的没删）；只转发参数的中间层；为一个调用点建的抽象或配置；要靠人记得同步的两份清单；按“这次先改什么后改什么”拆模块，而不是按谁拥有什么；下一个照着最近的例子抄的人会不会抄出错（这个仓库以后多半由 Agent 接着改，它看到什么就照着写什么）。
4. **写决定**：自己的方案每个栏目都要有 `brief`，确实不涉及的写一句“不涉及：……”；`contract` 给签名和字段，`behavior` 给表。宿主会按这些检查，缺了会退回。
5. **留问题给本人**：只有业务或功能上的取舍、要越出原需求、两种做法都说得通而影响不同时，才写 `question`：两三个选项，`recommended` 写你建议的那个，问题本身写清要定什么、各自的影响。能从代码和材料里查清的不要问。
6. 做不到、或你认为要求本身该换做法的，写进 `gaps`，不要悄悄换成别的做法。

任务里带着上一版和本人的意见时，按意见改出新的一版：意见没提到的决定沿用它的 `id` 和内容；本人回答过的问题照回答写进做法；“换个思路”就重新考虑做法，不是改措辞。`note` 写这一版改了什么。

## 评估别人的方案

别人的方案是别人的决定。你要做的是看清楚它、核对它、指出问题，不替作者改方案。

1. **先提取，不评价**：读完文档，把作者决定了什么按上面的结构写下来。文档没写的栏目就空着，不替作者补——“这一栏方案没写”本身会显示出来，是要问作者的地方。实现时必须定、而文档没说的（比如旧数据怎么办），另列一个决定，标 `stated: false`，栏目写你从代码推断出来的现状。上线安排、发布顺序、版本组合不是决定：写进整体的行为表（`matrix`），没说清的写成整体意见。
2. **回到代码核对事实**：每个决定依赖的事实（这个接口有谁在调、这张表有没有别处在写、这个字段现在是什么含义）去仓库里查。核对的结果写进 `facts`，带位置。哪部分没核对到（代码没收进来、工具查不了）也写一条事实说明，不要写进 `gaps`——`gaps` 只写方案和它要解决的需求之间的出入。
3. **写意见**（`concerns`，挂在对应的决定上；整份方案漏掉的挂在整体上）：

   | `level` | 什么时候用 | 例子 |
   | --- | --- | --- |
   | `problem` | 照这样做会出错：和现有代码的事实冲突、漏了一种情况、数据会坏 | “对账报表读的是落库前的金额，方案没有改它，上线后两边对不上（report/daily.ts:88）” |
   | `risk` | 可能出问题，要验证或要有回退：发布顺序、兼容、性能、依赖别的团队 | “新接口先发、旧页面还在调旧字段，方案没写发布顺序” |
   | `improve` | 有更简单或更统一的做法，说清是什么、省了什么 | “订单服务里已有按行合计的函数，不用在网关再写一份” |
   | `question` | 文档没写清、要问作者的 | “旧订单的退款记录要不要回填？” |

   每条都带位置（文件:行、文档里的哪一节）和依据（`src:`、`mem:`、提交）。没把握的写成 `question`，不要写成 `problem`。整份方案漏掉的部分（没说旧数据怎么办、没说回滚、没说权限）写在整体意见里。
4. **重新评估**（任务里带着上一版）：文档更新后重新提取，同一个决定沿用上一版的 `id`；上一版的每条意见都要出现在这一版，写它的 `id` 和现在的状态：`resolved`（`note` 写文档怎么改的）、`dropped`（`note` 写为什么不再成立）、仍是 `open`。新发现的意见不写 id。

交完用两三句话说结论：几个决定，最要紧的问题是什么。
