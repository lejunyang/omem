# 一轮一轮改进到目标

适合：有一个用命令能量出数字的目标，本人说“晚上帮我把 X 改好”“持续优化 Y”。不适合：需求没定的功能开发（走方案）；没有度量的“优化一下”（先和本人把度量定下来）。

分工：**你**负责判断——量什么、每一轮改哪一件、为什么；**宿主**负责不能靠自觉的四件事——量、比、回退、停。量出来没变好的那一轮，宿主会自己回退，你不用也不能替它留下。

## 第 0 轮：把度量跑通

1. 定度量：一条命令，最后一行输出一个数（全量测试用时、构建产物大小、lint 报错数、没过核对的页数）。数越小越好还是越大越好要说清。
2. 用 `delegate_code` 开一次交办（`design: "never"`），任务只有一件事：让这条命令在工作区里能跑、最后一行是那个数——需要脚本就写一个脚本并提交，**不做任何优化**。
3. 这一轮结束后调用 `improve_start`：
   - `run_id` 这次交办（交办里有几个仓库时加 `repo_space` 指明量哪一个），`name` 给目标起个名字，`metric_command`、`direction`（`down` 越小越好 / `up` 越大越好）；
   - `target` 完成条件（“5 分钟以内”就是 300）。定不出门槛就不填，靠“连着几轮没变好就停”；
   - `max_rounds` 最多几轮（默认 6）、`until` 最晚到几点；
   - `protect` 不许动的路径：度量脚本自己、测试目录、本人点名的文件。之后哪一轮动了它们，那一轮整轮回退。不能靠删测试、放宽断言、改度量脚本来达标。
   宿主当场量一次作为基线。量不出来会拒绝并给出命令的输出：先回到第 2 步把命令修好。

本人没说的（度量、门槛、预算）你来定，并在给本人的第一条消息里写明。

## 每一轮

1. **选这一轮改什么**。先看数据：哪个测试最慢、哪个模块最大、哪类报错最多，选占比最大的一项。写下预期：“改了它，度量会从 A 到 B，因为……”。说不出预期的不做。先用 `improve_status` 看以前各轮试过什么、哪些被回退：回退过的做法不再试第二次。
2. **只做这一件**。`continue_code_run` 交给编码，任务里写清这一件事、不许动的、验证命令。一轮一次提交或几次小提交都行，但只做一件事。
3. **交给宿主量**。这一轮编码结束后调用 `improve_round`（`note` 一句话写这一轮试了什么，`expect` 写预期）。宿主会：检查有没有动不许动的路径 → 跑仓库的检查命令 → 跑度量 → 比最好的那一次至少好 1%（`min_gain`）才留下，否则用 `git revert` 把这一轮撤掉（历史保留，分支内容回到上一次留下的样子）。
4. 看返回里这一轮的结论：
   - “留下”：下一轮在它上面继续。
   - “回退”（没有变好）、“回退（检查或度量失败）”、“回退（受保护路径）”：原因写在后面。同一个做法不再试。
   - “没有提交”：这一轮编码什么都没交，也算一轮。
   - 末尾有 `next`（连着两轮没变好）：下一轮换一个结构上不同的办法——换算法、换一层做、砍掉而不是优化——不是在同一个做法上调参数。
   - 状态变成“完成”或“停止”：见下。“回退失败”说明工作区要人处理，宿主已经停了这个目标：把情况告诉本人。

长任务不要在一个会话里把所有轮次做完：一轮结束用 `wake_later` 排下一轮。被唤醒或换了会话，先 `improve_status`，从它记的地方接着做。

## 什么时候停

停不停由宿主定，停了以后 `improve_round` 不再接受：

- 达到 `target`；
- 轮数用完，或过了 `until`；
- 连着四轮没有留下任何改动。

停的时候宿主会自己给本人发一份报告（基线到现在的数字、留下的各轮、撤掉的各轮和原因）。你再补一条你的判断，需要本人决定的照常发，其余用 `urgency="later"`：

- 没达到目标：你认为的原因，和建议（放宽目标 / 先改方案 / 放弃）；
- 留下的改动建议怎么评审：至少看功能和精简两项，评审用和编码不是同一家的模型。评审要改的，按普通交办接着改，不再算进这次改进。

分支不推送、不合并，等本人看。不为了达标去改完成条件或度量方式：条件确实定错了，写进报告让本人改，重新 `improve_start`。
