# 写这一轮的小结

1. 用 `read_ledger` 读这一轮的试验。先看有没有几个问题其实是同一个：同一个原因在几个样本上出现，是一条发现，依据是那几次试验。
2. 每条准备记的发现，先读相近的已有发现（`record_finding` 会列出来）：是同一个就并进去（`same_as`），确实不是再新建（`distinct_from`）。标题写现象，不写猜测的原因。
   已有改动的发现按记录照实写“改后通过 / 没改成”，不要当成新问题再记一遍；标了“已改好”的不要再记。
3. 正文（`repro`）是给本人读、也给之后去改的人读的 Markdown，不要写成一整段。按这几节写，每节用 `###` 小标题：
   - **条件**：版本或提交、环境、前提状态，读者据此判断自己会不会碰到。
   - **现象**：照着做的步骤（命令放代码块）、期望什么、实际怎样，贴最关键的几行输出。
   - **为什么是问题**：和文档、同类工具或项目自己别处的行为对照，带代码或文档引用；可能是有意设计的，写明需要谁来定。
   - **建议**：可以怎么改、改动大概落在哪里；不确定就写两种做法各自的代价。
   试验交了截图的，`read_ledger` 会给出图片的 Markdown，界面类问题把它原样放进“现象”；流程或状态关系说不清时可以用 mermaid 画。
4. 类型：缺陷（做错了）、缺口（同类有而这里没有，或文档说有其实不行）、改进想法（只在有具体依据时记；“可以更好”不算）。没有可复现依据的不记成发现，在小结里提一句。
5. 方向的试验都跑完了、达到验收了，或试下来确定没东西可挖，用 `close_direction` 结束它（不结束的话结论是空的，下一轮定方向时只能看到“试验都跑完了”），结论写：试了什么、多少个通过、发现了什么、为什么停。方向 id 在 `read_ledger` 的“方向”一节。
6. `stage_report` 的 `note` 是给本人看的小结：这一轮试了多少个、各种结果各多少、新发现几条（一句一条）、哪些没发现问题、建议下一步。没有新发现就照实写，不拿数量当成绩。
