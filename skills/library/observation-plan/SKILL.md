# 观测计划

一个需求做完上线，本人要能回答：用的人多不多、出没出问题、比原来好没好。观测计划在编码前定好，上线后按它看数。

## 先弄清这件事

读事项、需求文档和方案（`read_item`、`req_read`、关联的原件），回答：

- 这个需求要改变什么行为或结果（谁、在哪、做什么会变多 / 变少 / 变快）。
- 是新功能、改版、还是迁移（旧平台 → 新平台、旧接口 → 新接口）。
- 影响哪些页面、接口、服务、事件；数据源目录（技能 `data-sources`）里对应的系统和对象。

## 计划写四部分

1. **埋点**：要新增或复用的事件（名字、触发时机、属性、和已有事件的关系），每个事件回答一个具体问题；能用已有事件的不新增。有专门生成埋点的技能时按它的格式出。上线前要能在测试环境验证事件上报。
2. **上线后看什么**：
   - 稳定性：相关页面的 JS 报错、白屏、接口错误率和耗时、后端服务的错误和延迟。
   - 使用：入口曝光、点击、完成率、关键步骤的漏斗。
   - 每个指标写来源系统、查法、维度、基线（上线前一周的值或旧版本的值）和多大变化要警觉。
3. **对比**（改版、迁移才有）：新旧两边同口径的指标并排（流量切分比例、成功率、耗时、业务结果），以及护栏指标（不能变差的东西）。说清对比时的口径差异。
4. **什么时候看、看到什么做什么**：上线当天按小时、之后一周按天、稳定后按周；报错升高、使用低于预期时分别找谁、怎么回滚或补救。

## 落到 omem 里

- 计划写成工作文件挂到事项（`write_file`，`item` 填事项 id，路径如 `观测/<需求名>.md`）。
- 计划里的每个指标用 `metric_define` 定义到事项上（查法写清，`direction` 和 `threshold` 按第 2、3 部分），上线前 `schedule` 先用 none，上线后改成 hourly / daily；能先取到的基线现在就用 `metric_record` 记下。
- 开会讨论数据时，先拿这份计划和 `metric_read(item=…)` 的现状发言：现在有什么数、缺什么数、建议补哪些点和看哪些指标。
