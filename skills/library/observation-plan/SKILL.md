# 观测计划

一个需求做完上线，本人要能回答：用的人多不多、出没出问题、比原来好没好。观测计划在编码前定好，上线后按它看数。

## 先弄清这件事

读事项、需求文档和方案（`read_item`、`req_read`、关联的原件），回答：

- 这个需求要改变什么行为或结果（谁、在哪、做什么会变多 / 变少 / 变快）。
- 是新功能、改版、还是迁移（旧平台 → 新平台、旧接口 → 新接口）。
- 影响哪些页面、接口、服务、事件；数据源目录（技能 `data-sources`）里对应的系统和对象。

## 计划写四部分

1. **埋点**：要新增或复用的事件（名字、触发时机、属性、和已有事件的关系），每个事件回答一个具体问题；能用已有事件的不新增。有专门生成埋点的技能时按它的格式出。上线前要能在测试环境验证事件上报。
2. **上线后看什么**：
   - 稳定性：相关页面的 JS 报错、白屏、接口错误率和耗时、后端服务的错误和延迟。
   - 使用：入口曝光、点击、完成率、关键步骤的漏斗。
   - 每个指标写来源系统、查法、维度、基线（上线前一周的值或旧版本的值）和多大变化要警觉。
3. **对比**（改版、迁移才有）：新旧两边同口径的指标并排（流量切分比例、成功率、耗时、业务结果），以及护栏指标（不能变差的东西）。说清对比时的口径差异。
4. **什么时候看、看到什么做什么**：上线当天按小时、之后一周按天、稳定后按周；报错升高、使用低于预期时分别找谁、怎么回滚或补救。

## 少而准

指标是给本人看的，不是把计划里能数的都数一遍。先写下本人对这件事真会问的三五个问题（“上线后退款接口有没有更容易出错”“新入口有没有人用”“新平台的量追上旧的没有”），每个问题对应一两个指标；回答不了任何问题的数不定义。一件需求通常三到六个指标就够。

## 落到 omem 里

- 计划写成工作文件挂到事项（`write_file`，`item` 填事项 id，路径如 `观测/<需求名>.md`），每个指标在计划里有自己的一小节或一行。
- 定义前先 `metric_read(item=…)`：看已有的指标，以及“本人对 AI 提议的指标最近是这么定的”——本人留下的是哪类，不要的是哪类、为什么；不要的那类别再提，等本人定的提议还多时先别加。
- 计划里的每个指标用 `metric_define` 定义到事项上：
  - `why` 一句话写它回答哪个问题，`plan_ref` 指向计划里那一节（`src:<计划的原件 id>#L起-L止`）。本人在数据页凭这两样决定留不留。
  - 查法写清，`direction` 和 `threshold` 按第 2、3 部分；上线前 `schedule` 先用 none，上线后改成 hourly / daily；能先取到的基线现在就用 `metric_record` 记下。
  - `view` 说网页上怎么画：新旧对比、分端这类分维度的用 `compare`，`compareBy` 写维度名（记点时 `dims` 用同一个名字），要看新的占比加 `ratio: true` 和 `focus`；看构成用 `pie`；只要一个数用 `number`；不传是走势线。
- 不是本人这一轮亲口要的，这些指标都是提议：照样取数，变化不通知本人，等本人在数据页点“保留 / 改 / 不要”。不要替本人说“已经定好了”。
- 要同时看好几张图的分析（新旧对比、构成、排行、表格）写成报表：工作文件放在 `数据/报表/<主题>.md`，挂到事项，结论在前，每个结论旁边放 ` ```chart ` 块（`metric_read(chart=true)` 给出的，或按图表格式自己写）和取数口径。工作数据页和这条线的“数据”一栏会列出报表、直接画出里面的图。
- 开会讨论数据时，先拿这份计划和 `metric_read(item=…)` 的现状发言：现在有什么数、缺什么数、建议补哪些点和看哪些指标。
