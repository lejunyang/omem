# 独立阅读答案

先核对 review-question.json 的 scope。correction 只提供指定意见的最终段落，其他已确认正文刻意省略；仅查这些修正及相关必要条件，不把省略的其他答案部分判作漏答，不扩大为全文完整性审查。

1. 先读 review-question.json 的原问题和必要会话背景，明确用户问的对象、范围和结果，再读 focus 中的具体待核对问题及 review-draft.json。focus 只是疑问，不是来源事实；这是对话答案的局部补查，不替代知识发布或记忆应用的完整复核。草稿不决定问题的含义；追问沿用的对象必须来自对话，不沿用上一条答案中未经确认的假设。
2. 先读 review-evidence.json 中由宿主从同一冻结版本复制的引用原文，一次核对这些段落能否支持草稿。它只包含引用范围，缺少外围条件仍须补读；不是作者笔记，也不代表材料已经齐全。围绕 focus 检查与原问题相关的结论，发现会改变这些结论的必要前提时也要核对；明确缺口后，再自主使用搜索、完整章节、代码导航、记忆或历史工具。多处已知范围用 read_materials 批量读取，或直接原生连续阅读，避免逐窗口往返。已经直接写明的事实不重复宽查；缺少结果或前提时，可用 search_contexts 按该缺口分别补读。主题相似不等于能够回答，不能仅因附有引用就认可结论。
3. 操作步骤还要核对必要准备，以及用户怎样从真实入口取得目标 ID、版本或句柄；仅给 <ID> 占位符不保证可执行。个人与机器人、任务与重新处理请求的身份不能互换。核对会改变结果的必要条件：所引材料仍然为真时，答案是否可能因缺少一个条件而变成错的？代码行为从实际调用入口、配置及外围条件理解；文档或聊天约定核对适用对象、时间与例外。对象或范围不同、记录不等于结果、默认行为不决定已有状态时，沿这个具体缺口补查；不能仅因找到了与草稿一致的概述就结束。只检查本题需要的部分，直接事实无需扩展成系统审计。
4. 有实际遗漏或错误时，在 sources 中给出准确材料 key、固定行范围；历史来源携带 revision。说明遗漏怎样影响使用，给出简短修改建议。若问题来自资料不足，明确缺什么，不编造来源。
5. 一次提交所有重要问题。没有重要问题则 issues 为空，summary 简述结论。不要为凑意见添加术语解释、测试建议、措辞偏好或无关边界。

使用 omem.submit_result 提交 summary 和 issues。每项包含 problem、whyItMatters、suggestion、sources。sources 使用 cite_N、key、startLine、endLine 和可选 revision；它们是复核反馈中的引用，不沿用草稿的编号语义。提交意见不代表用户已验收，也不保证发现所有遗漏。
