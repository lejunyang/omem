# 流程：让一件事自己往前走

状态：第一期服务端已实现（2026-11-15）：定义、事项阶段、推进、本人关卡、已有对象、工具与 HTTP。网页流程条与飞书进度卡的专门版式尚未实现。第 5–8、10 节及第四期仍是后续设计；第一期的具体边界见“第一期的实现”。

## 1. 要解决的问题

omem 已经能做一件事里的很多段：进群跟讨论、拆需求点、写方案、交办编码、评审、开会记录、写周报。但每一段做完就停下，等本人再开口。几个具体的断点：

- 编码评审通过以后，本人自己确认、推送；推送完要再说一句“去部署吧”。
- 需求群里有了新结论（“部分发货的运费也要退”），不会自己并进这件事，要 @ 助手补充。
- 一件事现在走到哪、卡在谁手里、已经有了哪些产物，要翻事项的时间线、交办页、群聊才拼得出来。
- 每个人、每个团队的做法不一样（有的先写方案，有的代码写完再补单），现在没有地方描述“我的流程是这样的”。

事项已经是枢纽：材料、所在的群和会话（`src/items/places.ts`）、时间线、需求点、交办、测试结果都挂在它上面。缺的是三样：

| 缺什么 | 含义 |
| --- | --- |
| 阶段 | 这件事通常要经过哪几步，现在在哪一步，下一步是什么 |
| 关卡 | 哪一步要谁点头才往下走 |
| 信号 | 什么事情发生了算“这一步完成了”或“前面的要重做” |

## 2. 取舍：不是一条线，也不是节点图

这是一种编排能力，两头都有现成的做法，都不合适。

**一条线**（固定的阶段顺序，做完一个进下一个）写起来最省事，但真实的事情不这样走：小改动不写方案；前端和后端同时做；代码先写完再补需求；评审通过以后需求又变了，要回去改；这一次临时多一个安全评审。一条线遇到这些只有两个结果：卡住，或者被绕开以后状态不再可信。

**节点图**（节点、连线、条件分支、并行网关、循环，带画布编辑器）什么都能表达，代价是：

- 要有人画、有人维护。个人和小团队不会去维护一张图，画完就过时。
- 图越完整，偏离越难处理。真实工作里的例外是无穷的，图不可能都画进去。
- 分支条件大多是判断（“这个改动大不大”“讨论里这句话算不算变更”），写不成表达式；写成表达式的那部分又和模型的判断重复。
- 和 omem 的原则相反：宿主不替模型做多步规划。

**这里的做法：阶段是一份带前提的清单，流转由前提推出来，不画连线。**

- 流程定义只列阶段。每个阶段自己声明：要等哪些阶段（`needs`）、什么情况下才需要做（`when`）、谁来承担（`by`）、怎样算完成（`done`）、进入前要不要谁点头（`gate`）。
- 宿主只算一件事：**现在哪些阶段可以开始**。前提都满足的阶段就是可以开始的，有几个算几个。
- “怎么走”不用写：
  - 一条线 = 每个阶段等上一个。这是默认写法，最短。
  - 并行 = 两个阶段等的是同一个前提。
  - 条件分支 = 阶段带 `when`，不满足就跳过并记下原因；被跳过的阶段对后面算“已满足”。
  - 返工 = 某个已完成的阶段被重新打开，依赖它的后续阶段标成“待复核”。
  - 乱序 = 可以直接给后面的阶段补上依据（代码先写完了），前面的阶段之后补录。
  - 临时加一步 = 只改这件事自己的那份流程，不动模板。
- 判断交给模型，但落在固定的口子上：`when` 和“算不算完成”可以是一句话，由承担这一段的 Agent 判断并附依据；过不过关卡由宿主按定义执行。

这样偏离常规是一等操作（跳过、提前、重开、加一步都有记录和理由），不是异常。

| 情况 | 一条线 | 节点图 | 阶段清单 |
| --- | --- | --- | --- |
| 小改动不写方案 | 卡住或手动改状态 | 画一个条件分支 | `when` 不满足，跳过并记原因 |
| 前后端同时做 | 做不到 | 并行网关 + 汇合 | 两个阶段前提相同 |
| 评审后需求变了 | 手动回退 | 画回边 | 重开“编码”，下游标待复核 |
| 代码先写完再补单 | 做不到 | 另画一条入口 | 直接给“编码”补依据，“澄清”标补录 |
| 这次多一个安全评审 | 改模板，影响所有事 | 改图 | 只改这件事的副本 |
| 谁来写、谁来维护 | 好写，很快不够用 | 要专人维护 | 一段话描述，助手起草，表单里改 |

**复杂的编排放在阶段里面，不放在阶段之间。**阶段是粗的（澄清、方案、编码、推送、部署、测试、上线），一件事通常五到十个。一个阶段内部可以很复杂：编码阶段里有修改项、逐项验证、几轮评审，那是交办自己的状态机（docs/v2/coding-loop.md）；部署阶段里有等发布锁、分批发布、逐个服务核对，那是技能和 Agent 的事。流程只关心“这个阶段背后的那个东西现在是什么状态”。所以流程不需要循环节点、定时器节点、子流程：需要这些的地方，已经有一个承担者在里面做。

不做的：表达式语言、拖拽画布、流程嵌套、补偿事务。真的需要嵌套的大事（一个项目里十几个需求），用多件事项各走各的流程，上面再用一件事项跟着它们（见第 12 节的问题 2）。

## 3. 模型

### 3.1 流程定义

文件 `library/_flows/<id>.yaml`，在知识库的 Git 里，有版本，可以随场景包分发。本人用一段话描述自己的做法，助手起草（工具 `save_flow`，本人确认后生效），之后在网页的表单里改。

```yaml
id: feature
name: 需求交付
description: 从群里提出到上线，再写进周报
for: { kinds: [todo], spaces: [demo-mall] }   # todo / waiting / watch / decision；用于建议，不限制手动选择
stages:
  - id: clarify
    name: 澄清
    by: { run: { agent: assistant, skill: req-clarify } }
    done: confirm                              # 本人确认需求点才算完成
  - id: design
    name: 方案
    needs: [clarify]
    when: 改动跨模块，或者要动数据结构           # 不满足就跳过
    by: { object: design }                     # 方案带着走：本人确认方案 = 完成
  - id: code
    name: 编码
    needs: [design]                            # 方案被跳过时也算满足
    by: { object: code-work }                  # 交办带着走：评审通过 = 完成
  - id: push
    name: 推送
    needs: [code]
    by: owner                                  # 人自己做
    done: confirm                             # 第一期由本人确认；git.pushed 信号留待第二期
  - id: deploy
    name: 部署到预发
    needs: [push]
    by: { run: { skill: deploy-staging } }
    done: 预发部署成功，附验证依据               # 插件 deployment 对象留待第三期
  - id: test
    name: 回归
    needs: [deploy]
    by: { run: { skill: regression } }
  - id: release
    name: 上线
    needs: [test]
    gate: confirm                              # 进入前要本人点头
    fixed: true                                # 这个关卡永远不提议改成自动
    by: { run: { skill: release } }
  - id: report
    name: 周报
    needs: [release]
    by: { run: { skill: weekly-update } }
```

仓库里不带任何具体平台的技能：`deploy-staging`、`release` 这类技能是本人放在数据目录里的（接内部平台的那些），流程只引用名字。

流程不限于研发。值班排查可以是：接报 → 定位 → 修复（要确认）→ 验证 → 记进案例页。出一份文档可以是：收集材料 → 初稿 → 本人改 → 发出 → 跟进反馈。

### 3.2 阶段的四个字段

**谁来承担（`by`）**，四种：

| 写法 | 含义 | 完成怎么判断（没写 `done` 时） |
| --- | --- | --- |
| `run: { agent, skill }` | 到了就起一次运行，带上这件事的全部上下文 | 运行用工具交代“做完了”并附依据 |
| `object: <类型>` | 背后是一个有自己生命周期的对象：方案、交办、评审，或插件提供的合并请求、流水线、部署单 | 对象到了终态 |
| `owner`（`person: <人>` 留待后续） | 人自己做 | 本人说做完了；信号留待后续 |
| `wait` | 什么都不做，只等 | 信号 |

**怎样算完成（`done`）**，四种，优先用靠前的：

1. 对象状态：`{ object: deployment, status: succeeded }`。确定的，宿主自己看。
2. 信号：`{ signal: git.pushed }`。确定的。
3. 本人确认：`confirm`。出一张卡片。
4. 一句话：`done: 群里的相关方都回复了没问题`。由承担这一段的 Agent 判断，申请完成时必须附依据（引用原件、运行、对象）；宿主不判断这句话，只检查有依据、关卡过了。

**进入前的关卡（`gate`）**：`auto`（默认，前提满足就开始）、`confirm`（本人点头）、`confirm: <人>`（发给那个人，等他点）。`fixed: true` 的关卡不参加下面说的升降。

**什么时候才需要（`when`）**：一句话或不写。不写就是总要做。第一期直接调用已配置的决策模型，记录选项与概率；未配置或调用失败就问事项本人。每次尝试判断一次，已经判“要做”的重开后不再判断；本人仍可跳过或重开。

### 3.3 一件事上的流程

事项开始走流程时，把定义**复制一份**到这件事上（`item_flows.definition`）。之后改模板不影响进行中的事；在这件事上加一步、去一步、改关卡，只改这份副本，页面上标出“和模板不同的地方”。

阶段的状态：

```
未到 ──前提满足──▶ 可以开始 ──（关卡）──▶ 进行中 ──▶ 完成
                      │                    │
                      ▼                    ▼
                    跳过                 卡住（等谁、为什么）
完成 ──被重开──▶ 未到（重走条件和关卡）        完成 ──上游被重开──▶ 待复核
```

- **卡住**：承担者报告做不下去（缺权限、前置条件没满足、等别人），写明等谁、等什么。等的东西到了（信号、对方回复、本人处理）再继续。
- **待复核**：上游重做完成后，逐个问这个阶段的承担者“还成立吗”：对象带着走的看对象自己（分支变了，评审自然不再有效）；运行承担的重跑或确认；人承担的问人。
- 每次变化记一行（`item_stage_log`：哪个阶段、从什么到什么、谁、依据、哪次运行），同时在事项时间线上显示。

## 4. 宿主怎么推进

只在三种时候重新算：收到一个属于这件事的信号、有人过了关卡、承担者交代了结果。算的内容是固定的：

1. 对每个“未到”的阶段：`needs` 里的阶段都是完成或跳过 → 该不该做（`when`）交给助手判断一次 → 可以开始或跳过。
2. 对每个“可以开始”的阶段：关卡是 `auto` 就开始；是 `confirm` 就出卡片，等人。
3. 开始：`run` 起一次运行；`object` 找到或建立对象（例如发起交办）；`owner` 告诉本人轮到他了；`wait` 什么都不做。
4. 对每个“进行中”的阶段：`done` 是对象状态或信号的，宿主自己判断；其余等承担者或本人。

几条约束：

- **连续自动推进有上限**（`flows.autoAdvance`，默认 3）：没有人参与的情况下连着自动开始了这么多个阶段，下一个不论关卡怎么写都先问本人。和现有的协作循环上限是同一个想法。
- **一个阶段的运行失败或超时不算完成**，运行正常结束却没交结果也卡住，不自动重试。`done: confirm` 被本人拒绝时才带意见重跑，第三次仍被拒就卡住。
- **停太久会提醒**：`gated`、`blocked` 或本人承担的 `doing` 默认停满 2 个自然日提醒一次；再隔 4 天、8 天，间隔翻倍。“先别做”重新计时，不自动通过。
- **关卡按授权阶梯升降**是第四期的设计（沿用 `src/agents/approval-ladder.ts` 的做法）：同一个流程的同一个关卡，本人连续直接同意到设定次数，问一次要不要改成自动；不满意后退回确认。第一期只保留 `fixed` 字段，不做升降。
- **推进不替人做决定**：宿主从不自己把 `confirm` 当成已确认，也不因为“等太久”自动过关。

### 4.1 重开和补录

- **重开**（工具 `stage_reopen`，或本人在页面上点）：要写原因和依据。常见的来源是上下文跟进发现需求变了（第 6 节）、评审之后又有提交、部署失败。
- **补录**（代码在前）：宿主看到某个仓库的分支上有提交，却没有任何事项关联它（信号 `git.commits`），交给助手判断：关联到已有的事项，还是建议新建一件。新建时直接给“编码”补上依据，“澄清”“方案”标成补录，由助手从提交和讨论里反推需求点，本人在一张卡片上确认。这样台账不会和实际的代码脱节。

## 5. 信号

信号是“发生了一件可能推动流程的事”，有类型和一组键（群、文档、分支、对象、运行、事项）。

| 来源 | 信号 | 现状 |
| --- | --- | --- |
| 飞书消息 | 关联的群或会话里有新消息 | 已采集，要接到流程 |
| 文档 | 关联的文档变了 | 文档变化规则已有 |
| 会议 | 关联的会议结束、纪要出来了 | 会议规则已有 |
| 交办 | 一轮结束、评审通过、已应用、被丢弃 | 事件已有，要接到流程 |
| 方案、评审 | 本人确认、评估完成 | 事件已有 |
| Git | 工作分支被推送（远端跟上了本地）、被合并、分支上有没人认领的提交 | 新增：在每小时的仓库同步里顺带比较 |
| 插件的对象 | 状态变了（合并请求合并了、流水线过了、部署成功） | 新增（第 8 节） |
| 人 | 本人或别人在卡片上的选择、对某条消息的回复 | 已有 |
| 时间 | 到了某个时刻、停了多久 | 定时任务已有 |

**信号属于哪件事**：

- 键能对上的直接归过去：事项的材料和“在哪些会话里进行”里有这个群、这份文档；事项关联了这个对象、这条分支、这次交办。
- 对不上的不猜：进候选，按现有的打分（引用了同一个链接或单号、提到同一个人、共同的词、时间相近）列出最多三件，由助手读过以后决定关联不关联。宿主不自动关联。
- 一个信号可以属于几件事（一个群里在谈两件事），各自处理。

信号记在 `flow_signals`，留 30 天，只为了能查“这件事为什么往前走了 / 没往前走”。

## 6. 上下文跟进

流程进行中的事项**订阅**它的群、会话、文档和会议：这些地方有新内容时不用 @ 助手。

- **攒一批再看**：同一件事的新消息攒够一段时间（默认 20 分钟没有新的，或攒了 30 条）才处理一次，不是每条消息一次。
- **先过预筛**：决策模型判断“这批新内容和这件事有没有关系”（新场景 `follow`，门槛和记录沿用 docs/v2/ai-models.md 的做法）。判断无关的记一行“看过，无关”，不起运行。
- **再提炼**：有关的交给事项维护角色（`item-keeper`），它只做一件事——说清这批内容让这件事**变了什么**，用工具 `note_item_change` 逐条交：
  - 类型：范围（需求点变了）、决定、截止时间、阻塞、信息（只是知道一下）。
  - 影响哪些阶段（可以没有）。
  - 依据：引用原件的行。
- **宿主按类型处理**：
  - 只是信息的：写进事项的“现状”，不打扰。
  - 影响进行中或已完成阶段的：出一张卡片（“小王说部分发货的运费也要退，影响需求点 3，编码已经评审通过。要并进这次交办，还是另开一件？”），本人选了以后重开相应的阶段或新建事项。
  - 截止时间变了：改事项的截止时间，记依据，告诉本人一次。
- **不替本人答应**：别人在群里提的新要求只会变成一条“范围”变化等本人定，不会自动进入编码。

事项的“现状”是一小段持续更新的文字（现在到哪了、最近定了什么、还有什么没定），给每个阶段的承担者当背景，也给工作近况（docs/v2/work-state.md）和周报用。

## 7. 界面

- **事项页的流程条**：一行阶段，颜色表示状态（完成、进行中、等人、卡住、未到、跳过、待复核），每个阶段下面写用了多久、几轮。
- **当前关卡**：一张卡片，写清现在等谁做什么、下一步会发生什么，带按钮（同意、先别做、跳过这一段、让它自己发现）。
- **产物按阶段归**：需求点、方案、分支和检查结果、合并请求、部署单、测试报告、周报里对应的那一段。还没有的也列出来，写“推送后由插件创建”这类说明。
- **最近的信号**：收到了什么、有没有造成变化，包括“看过，无关”的。本人能看出它确实在听，也能看出它为什么没动。
- **看板**（`#/board`）：所有在走流程的事项按阶段分列，可以筛“等我的”“卡住的”，停太久的标出来。
- **今日页**：多一栏“等你过的关卡”。每日简报读同一份数据。
- **飞书**：每件事一张进度卡，原地更新（沿用现有的一项工作一张进度卡），卡上是这条阶段线和当前关卡的按钮。
- **流程定义**：表单（阶段列表，每个阶段几个字段）加原文两种改法，不做画布。

## 8. 插件

现在的平台包（docs/v2/connectors.md）只把平台上的东西读成原件并定时同步。要让一个平台真正进到流程里，插件要能提供四样东西，都是通用接口，具体平台各自实现（GitHub 作为仓库里的例子；接内部平台的放数据目录，不进仓库）。

**对象类型**：平台上一个带状态的东西。

```ts
api.object({
  kind: "merge-request",
  label: "合并请求",
  match: (url) => keyOrNull,                       // 一个链接是不是这种对象
  read: async (ctx, key) => ({ title, status, fields: [{ label, value }], link }),
  statuses: { open: "进行中", merged: "已合并", closed: "已关闭" },   // 流程定义引用的就是这些
  final: ["merged", "closed"],
  poll: { minutes: 5 },                            // 或者由平台的回调推过来
  actions: [{ id: "merge", label: "合并", tool: "github_merge", when: ["open"] }],
});
```

- 对象可以挂到事项上（材料的一种），可以绑到某个阶段。消息或文档里出现能 `match` 的链接时，助手可以用 `attach_object` 挂上。
- 宿主存一份对象的当前状态（`flow_objects`），只在有事项关联它的时候轮询，用关联的那个人的连接去读。
- 页面上是一张状态卡：标题、状态、几个字段、链接、动作按钮。事项页、流程的阶段、飞书进度卡里都是同一张。

**信号**：对象状态一变，宿主自动发出 `object.<类型>.<状态>`，流程和规则都能用。没有对象的事件（一条报警、一次回调）插件用 `ctx.emit({ kind, keys, payload })` 发。规则页多一种事件“对象状态变化”。

**动作**：对象卡上的按钮对应插件的工具，走现有的工具审批档位（每次问 / 做完告诉我 / 不用问）。Agent 在阶段里调用的也是同一个工具，所以人点和 Agent 做是一回事。

**界面插槽**：插件的内容块（现有的 `api.block` 协议）可以声明放在宿主页面的固定位置：事项页侧栏、流程的某个阶段下面、今日页。不用跳到插件自己的页面。

```ts
api.slot("item.panel", { block: "ci-summary", when: { object: "merge-request" } });
```

**流程模板**：场景包可以带 `flows/<id>.yaml`，和它带的技能、规则、对象类型配成一套。例如“GitHub 需求交付”包 = 一份流程 + 合并请求和流水线两种对象 + 建合并请求、等检查、合并三个技能。

**安装**。已有：npm 包、本地目录（复制一份）、GitHub 的 tag。要加：

- `omem plugin link <目录>`：开发用，不复制，改了就生效。信任按目录记，页面上标“开发中”；只能链接本机的目录，不随设备同步。
- 从源码安装时构建：包里有 `build` 脚本而没有构建产物时，安装器先列出要运行的命令，本人确认后在隔离的进程里装依赖并构建，再走原来的信任确认。

## 10. 成效页

看 omem 和机器人给本人、给别人带来了什么。页面 `#/insights`，数据接口 `GET /api/insights`。不依赖流程的八个板块已实现（2026-11-15）；阶段指标随 flows 一起补入。

### 10.1 原则

- **只报看得见的**：次数、人数、时间跨度都从记录里数出来，每个数字能点进去看到是哪些运行。
- **有基线才比较**：能从库里算出“以前是多少”的（本人以往回复别人的时间、某个日期之前的同一指标）才给前后对比；没有基线的不写“节省了多少”。
- **估算就标成估算**：需要假设的换算（例如“每次代答按省 10 分钟算”）默认不显示，本人自己填了假设才出现，并标明是估算。
- **不给人排名次**：按人看的是“谁在用、用来做什么”，不做效率排行。

### 10.2 看什么

| 板块 | 指标 | 图 | 数据来源 |
| --- | --- | --- | --- |
| 用量与覆盖 | 每天的任务数；每周用过的人数（本人、成员、访客分开）；成功率 | 按场景堆叠的面积图；周活折线 | `runs`（类型、触发方式、触发人、状态） |
| 用在哪 | 场景、空间、Agent 档案或角色、触发会话的运行次数 | 条形图，可下钻到记录 | 运行行上的类型、档案、角色、触发信息；不读工具事件 |
| 替本人挡了多少 | 有人找你：进来 → 预筛掉 → 分诊 → 代查 → 代答或提醒 → 本人的反应 | 漏斗 | mention 运行、`reply_samples`、通知的结果 |
| 给别人带来什么 | 访客提问次数、不同提问身份和所在会话；回答完成用时的中位数与 P90；本人自行回复的中位数 | 会话条形图；双方各至少 10 个样本才画对比条 | 访客运行的 `verdict=answer`、创建至结束时间；`reply_samples.owner_reply_at − last_ms` |
| 质量 | 负面反馈率；回复草稿照发率；评审发现的采纳率；每晚抽检的准确率；夜间复盘的胜平负；决策模型的漏看 | 趋势线 | `feedback`、`reply_samples`、`review_findings`、`quality_audits`、复盘记录、`decisions` |
| 交付 | 发起、评审通过、应用、丢弃的交办数；轮数与发起到应用用时的中位数 | 交办去向条形图 | 编码首轮与续轮的小字段投影；阶段指标随 flows 一起补入 |
| 知识 | 期间读过的现存页面占比（全部阅读）；记忆按回答 / 整理计召回及引用率；技能复盘尝试和胜平负；仓库约定累计命中 | 召回用途条形图 | `page_reads` 没有用途与人员归属；`memory_recalls.purpose/used`；复盘 `variant.skillName`；`repo_lessons.hits` 是累计值 |
| 成本 | 各后端、各模型的运行时长和次数 | 堆叠条 | `runs.ai`、起止时间 |

### 10.3 怎么筛

已实现：7 / 30 / 90 天、自定义本地日期（最多 180 天），同跨度上一段比较；空间、触发人、机器人、触发会话、场景、Agent 档案或角色、模型、包含后台整理。筛选在 URL 中，可直接复现。流程和阶段随 flows 一起补入。

成员只看自己触发或拥有、且所在空间可读的运行；不会因共享空间而看到别人的统计。空间权限使用 `accessibleSpaces`，运行可读范围使用运行列表的 `runReadableSpaces`。全局分诊与通知、页面总阅读及仓库约定累计命中仅主人可看；按人等运行维度筛选时不显示无法归属的数据。访客只计数，接口、明细、peer 和导出均不返回消息正文。

### 10.4 实现上

- 聚合按请求算，默认最近 30 天，单次最多 180 天；每实例按人员、完整筛选与权限集合缓存 3 分钟，最多 8 份。只新增一个索引，无汇总表、触发器和后台任务。
- `runs_insights` 以 `created_at` 开头，覆盖 `id/kind/status/space_id/user_id/trigger_by/profile_id/ai/started_at/finished_at/roles/quiet`；另外索引小字段表达式：`input.spec`、`trigger.via/where`、`coalesce(input.lark.bot,input.bot)`、`input.continueFrom/waited`、`output.appliedAt/discardedAt/verdict/triage.action/handleRun/joined`。这些值在 SQLite 维护索引时提取；请求从索引读表达式值，不解析大段 input/output，不读 run_events。测试检查查询计划与字节码没有表字段读取及 JSON 函数调用。
- 场景归类统一由 `src/insights/scenes.ts` 导出；网页从接口取得同一张表作为口径说明。`RunKind` 新增但未归类时，类型检查与测试都会失败。
- 数字及图表每个数据点带“看明细”，打开 `#/insights?...&detail=指标`。`GET /api/insights/records` 返回同口径的记录标识、状态、时间及原列表链接（每页 100 条），不带正文。比例列出分母样本。采用这个明细页而非改造运行列表的全部筛选；通知、抽检、复盘及约定的原页面链接是最近的现有列表，不会进一步预选那一条，成效明细清单本身准确限定样本。
- `GET /api/insights/export?format=md|csv` 按板块导出指标、上一段、样本数、口径、图表数据及明细链接；CSV 处理引号及公式前缀。只读 peer 命令 `insights` 返回相同板块，不带正文。
- 每个板块单独计算、单独捕获错误，空表返回具体空态；一个板块错误不清空其他板块。图表复用 `UiView` 与插件 SDK 的 SVG 绘图，有键盘读数和表格替代。估算默认留空，只有主人填写每次代答的分钟假设后在浏览器换算，假设只存 localStorage。

| --- | --- |

### 10.6 漏斗与数据边界

| 步骤 | 实际计数口径 |
| --- | --- |
| 进入流程 | 所选期间的 mention 首次运行批次；排除 `input.waited > 0` 的等待重试。一批可有多条消息，不称消息条数 |
| 分诊前筛掉 | done 且 quiet，并且没有 triage.action、handleRun、joined 的首批运行；不把未完成运行或分诊后 ignore 算进去 |
| 分诊 | triage.action 已记录的运行 |
| 交给 Agent | handleRun 或 joined 已记录的运行；包含合并到已有处理的旁支 |
| 已提醒或代答 | 该批次或关联处理运行在期间有非静默、未替换、非捆绑容器通知，或对应样本的 decision 为 sent / edited / auto；按批次去重 |
| 本人的反应 | 通知 outcome 的 acted / known / read / unread / negative，另列尚未标注；沿用 outcomeStats / outcomeBreakdown 的排除口径，但支持精确起止与当前筛选，不调用会结算写库的函数 |

主路径条形图为进入 → 分诊 → 分诊后代查 → 代查后提醒或代答，显示各步占上步比例。预筛、直接提醒、合并为旁支，单列计数，不强凑成一条漏斗。

边界与后续：

- 2026-11-14 以前除回填的聊天、找人和访客外，触发信息可能缺失。缺失身份单列，不推断为主人；trigger_by 是身份键，不保证跨渠道去重到真人。where 是位置名称，同名会话会合并。机器人仅按记录的 input.lark.bot / input.bot 筛选；现有访客运行未记录接收机器人，无法按机器人归属，不能推断为 main。
- 访客提问总数含拒答、忽略；回答用时只含 done 且 verdict=answer。创建至结束含排队；没有实际送达时间和 gateOnly 的独立投影，可能含交回主助手处理的把关结果，因此不把它称为对方收到答案的精确延迟。本人基线用 reply_samples，非 lark_messages 临时扫描；两类样本不同，不推导节省用时。任一方用时样本少于 10 个不画比较条，仍显示样本数与各自统计。
- 质量正负反馈率是相应反馈的不同运行 / 获得任意有效反馈的不同运行，两个比例可重叠。草稿照发率不含持续授权 auto。评审按 check_name 及裁决规则计采纳 / 不采纳；未裁决与合并不入采纳率分母。写作与定级抽检分开；没核完不进准确率。复盘按变体胜平负，void / failed 不当作平。决策按 decisionReport 相同的 risky/taken/label 口径，保留精确期间，只纳入能关联到所选运行的记录。
- 编码按首轮发起日期分组，首轮及后续轮当前状态、轮数、应用时间按小字段读出；历史期间仍反映这一批交办的当前去向，比较不代表当时状态的快照。仅推送分支但没有 appliedAt 的不当成应用；阶段停留、等待、返工、每周过完流程等 `item_stage_log` 指标随 flows 一起补入。
- page_reads 只有页面与 UTC 日期、次数，没有运行、人员或用途：主人未按运行维度筛选时展示“全部阅读”，不冒充“被回答读过”。页面覆盖分母是当前现存页面，不做历史对比。repo_lessons.hits 没有逐次时间，标明累计，不做期间增量和对比。记忆引用率仅表示 used=1；普通技能调用和查不到的问题没有独立计数，不扫描事件补数。金额、Token 没有完整账单数据，只报记录的运行时长和次数。

## 12. 要本人定的

2026-11-15 本人定：下面七点都按建议。

1. **流程定义放哪一层**：建议全局一份清单，空间可以指定默认用哪个；不做“每个空间各存一套”。
2. **大事怎么办**：建议一件事项一个流程。一个项目里有十几个需求时，每个需求一件事项，再用一件“项目”事项关联它们、汇总进度；事项之间加“属于”关系，但不做流程嵌套。还是说先不管大事？
3. **哪些关卡默认要你确认**：建议推送、上线、任何以你的身份对外发出的东西默认 `confirm` 且 `fixed`；部署到预发、回归、周报默认自动。
4. **订阅的范围**：只读事项已经关联的群和文档，还是也读“提到这件事”的别的群？建议只读已关联的，别的群里提到时作为候选让助手决定要不要关联。
5. **补录（代码在前）要不要第一期就做**：建议第二期，它依赖 Git 信号。
6. **成效页给谁看**：建议主人看全部，成员看自己的；要不要给访客所在的群一个只读的小结（“这个群这个月问了机器人多少次”）？
7. **起步的流程**：第一期我用你说的那条（进群跟进 → 澄清 → 编码 → 你推送 → 部署 → 测试 → 上线 → 周报）作为验证用例，具体的部署、上线技能用你数据目录里已有的。可以吗？

| `src/flows/engine.ts` | 每事项串行推进、条件判断、本人提问及回调、报告、重开、结束和心跳提醒；`flow-stage` 运行复用事项材料和所在会话摘要。 |
| `src/flows/objects.ts` | 小型对象注册表，已有 `code-work`、`design`，以后再接插件。 |
| `src/flows/http.ts` | 定义与事项流程的 HTTP；路由权限集中登记在 `src/auth/routes.ts`。 |

定义最多 20 段，阶段 id 唯一；`needs` 只能指向列表中更早的阶段，不填等上一个，`[]` 无前提。`note` 最多 1000 字；`when` 和文字 `done` 最多 300 字。第一期拒绝 person、signal、插件对象；`done` 对象只可写已有的两种。代码里的事项还有 `reminder`，但流程定义的 `for.kinds` 按本期约定只接受 todo / waiting / watch / decision。

对象只查本事项：编码交办从 `item_materials(kind=run)` 找，复用 `codeWork.stage.key` 作状态；最近轮 `roundList.verdict=approved`、运行 done 且阶段为 done / review-ok / ended 时默认完成，应用前就能推进，已丢弃或被新交办接替的不选。方案先找该交办绑定的方案，再找事项的方案；必须是当前版本、状态 approved、确认记录的 `by` 等于事项本人，助手确认不算。

运行承担的阶段只拿事项所在空间的可写范围，临时技能正文像夜间复盘的附加技能一样放进这一轮任务。缺少编码对象时起助手运行，要求 `delegate_code` 带 `item_id`。缺少方案时宿主建立空方案，再调用现有 `runDesigner`，因 `submit_design` 只允许 designer 提交自己的方案；这是与“助手运行写方案”的接口适配，未放宽原角色限制。提交后等本人在现有方案页确认，未交方案则卡住。

数据库末尾追加一条迁移，只有 `item_flows`、`item_stages`、`item_stage_log` 三张表。前两表加显式 `updated_at` 供拉取比较；阶段另有 `since` 和小型 `control` JSON，保存条件已判、提问用途、当前运行、提醒次数与时间。日志的 `sync_key` 区分设备各自分配的整数 id；三个表进入 `pullTables`，键分别是 item_id、(item_id, stage_id)、映射后的日志 id。既有拉取逻辑递归改写 JSON 里的原件引用和行号，无新增投影、触发器或缓存。

HTTP 约定：

- `GET /api/flows` → `{ flows: [{ id, raw, definition, problem }] }`，无效文件仍返回原文与问题。`PUT /api/flows/:id` 收 `{ yaml }` 或 text/plain 原文，路径 id 必须与定义一致；`DELETE` 删除定义，两者限 omem 主人。
- `GET /api/items/:id/flow` → `{ flow, stages, log, suits }`。`flow` 为 null 或 `{ id, name, startedAt, endedAt, autoStreak }`；`suits` 仅在还没有流程时给适用定义。
- `stages` 每项为 `{ id, name, instruction, state, attempt, since, enteredAt, doneAt, by, waitingOn, evidence, note, gate, fixed, carrier, object?, askId? }`。`instruction` 是定义中的 note，`note` 是最近进展，避免任务书示例中重复的 note 键。`carrier: { kind, label, link? }`；`object: { title, status, link }`。`by` 是当前运行 id、对象引用、owner 或 null。日志最近 50 条，按新到旧，字段 `id / stageId / at / fromState / toState / actor / runId / refs / note`。
- `POST /api/items/:id/flow` 收 `{ flow }`；`DELETE` 停止。`POST .../stages/:stage/{confirm,hold,skip,done,reopen}` 收 `{ note? }`；skip、done、reopen 必须写 note。所有写事项流程的接口限事项本人并检查空间写权限；读接口按事项空间的阅读权限。
- 写操作均返回同一份流程视图。本人也可重开已走完或已停止流程中的阶段；走完和停止都撤回未答问题，不替本人关闭事项。

只有本人能定的事不由 Agent 代办：Agent 对本人承担的阶段报“做完了”，不会直接完成，而是变成一个问本人的确认（“这一段是你来做的，助手说已经做完了……是这样吗？”），本人确认了后面的阶段才开始；进入前要确认、完成要确认或由本人承担的阶段，Agent 不能跳过（工具返回错误，要它把理由告诉本人），本人在卡片或事项页上可以。自动的阶段 Agent 可以跳过，本人会收到一条不急的通知。

进度卡每次操作只更新一次：一次推进里改了几个阶段（开始流程时每个阶段都写一行），结束时才发一条，替换上一张。

工具是 `list_flows / save_flow / flow_start / stage_report / stage_reopen`（`group:flow`）；`save_flow` 只起草，本人选“启用”才写文件。阶段提问在记录答案前校验被问者和回答人，回调还会复核。`read_item.flow` 采用上述视图。

监听 `changed(code-task)`、`changed(design)` 和 `run`（含运行终态），按对象 id、运行主键、continueFrom / parent 及事项 run 材料限定到进行中的流程。未新增任何渠道或编码运行时的发射器。当前缺少即时事件的是：`src/agents/code.ts` 的应用、丢弃，`src/agents/code-branch.ts` 的分支确认 / 归还，以及 `src/designs/store.ts` 的创建、基础信息更新、绑定交办；阶段开始和运行事件会读到已存在的对象，心跳也重新读取，以上独立操作没有即时唤醒保证。具体缺口见本次变更记录。

尚无网页流程条、流程定义表单、专门的飞书进度卡版式、通用信号表、Git 信号、上下文订阅、插件对象、补录、阶段副本编辑、看板、成效页或关卡授权升降。设置只有 `flows: { autoAdvance: 3, staleDays: 2 }`，旧配置自动补默认值；第四期的回顾、coach 和授权阶梯也未接入。默认主助手尚需单独授予 `group:flow`，内置角色正文由后续切片维护。
