# 事项来源与关联维护

适用：原事项的有效来源混入错误引用，或某次具体进展被挂到另一个事项。维护不覆盖历史，所有修改都经过 omem 工具；不直接操作个人数据库。

## 部署

1. 在交办 worktree 完成 `pnpm run check` 和代码评审，再由主助手把 diff 应用到目标仓库。
2. 部署前备份数据目录。构建并更新安装，按实际运维流程安排服务升级；本交办不更新或重启主服务。
3. 新版首次打开库时自动增加通知 `context`、事项进展提案和维护审计表。旧通知不自动猜测归属，也不补齐全部历史来源。
4. 新开一轮主助手会话确认工具列表包含 `read_item`、`repair_item_association`、`read_item_repair`、`refresh_item_notification`。已有 Agent 会话可能缓存旧工具列表，应新开会话。

## 只纠正来源

先 `read_item(item_id)` 核对具体事项、所属空间、当前 `sourceRefs` 和事件。默认 `upsert_item.source_refs` 仍是增量合并；纠正必须显式操作：

```json
{
  "id": "i_example",
  "source_refs_mode": "remove",
  "source_refs": ["src:s_example#L3-L5"],
  "expected_source_refs": ["src:s_keep#L1-L2", "src:s_example#L3-L5"],
  "note": "这段来源属于另一项具体交付，撤回错误引用"
}
```

`replace` 替换为给定的非空集合；清空必须明确逐条 `remove`，传 `[]` 会拒绝。旧快照不匹配时重读，不盲重试。引用需存在、行号有效、属于调用者可读空间；事项本身必须可写且属于当前用户。remove 允许撤回已删除原件的旧引用。时间线记录纠正前后，不改原始事件。

## 修复一次错误关联

1. 查两个事项，核对具体交付物，而非仅按主题相似。读原件、时间线及后台运行，找出**精确事件 ID**。保留旧事项自己的其他进展。
2. 用 `inspect_item_notification(notification_id)` 读取通知及全部卡片交互，不能漏掉已有卡片。准备 `repair_item_association` 参数：`from_item_id`、`to_item_id`、`event_ids`、仅该次事件的 `source_refs`、旧事项完整 `expected_source_refs`、`run_id`、`reason`。有历史通知时带 `notification_id`、修正后的 `title/body`；有卡片时同时带 `interaction_id`。同一次进展有多条通知或多张卡片时，用 `notification_ids` / `interaction_ids` 一次传全；单值和数组可合用，正文/标题统一修正。
3. 默认 `apply: false` 只返回预览。预览与审计的 `retainedSourceRefs` 列出原事项未迁移事件仍使用的共有来源，`removedSourceRefs` 列出将从原事项移除的来源；共有来源保留在两个事项。事件必须属于旧事项，所有来源与所选事件精确对应；包含其他业务来源的混合事件拒绝移动，先调查拆分。通知/交互必须指向旧事项及同一通知，遗漏关联通知或卡片时拒绝修复，运行须有通知链接或对应工具记录。旧格式通知没有实体元数据时须同时用交互记录验证。
4. 主助手对预览逐项核对后传 `apply: true`。一个事务保存修复前快照、移动明确事件、只移除未被保留事件使用的指定引用、把来源合并到正确事项、修正通知实体和交互 payload，并给原运行结果添加 `itemAssociationCorrection`。原运行输出仍保留。两边时间线写修复标注，原卡片交互置为 expired。
5. `read_item_repair(repair_id)` 查看快照，重读两个事项、通知与运行核对。重复应用因旧快照或事件归属变化而拒绝。
6. 本人允许更新历史飞书卡片后，调用 `refresh_item_notification(interaction_id, reason)`。它只更新原消息，不新发消息；从已修正通知统一渲染按钮和来源，成功且 payload 未变化才恢复按钮。需要本人主助手和本次飞书会话权限。网络失败保留 expired，可重试，失败尝试同样有审计。

仅执行第 4 步时，飞书中旧卡片的文字和链接仍可见，但按钮已失效；第 6 步完成后旧卡片内容才同步纠正。未经允许不要刷新或新发消息。修复不会自动恢复已被错误按钮改变的事项状态或详情；先读事件，确认错误操作，再用 `upsert_item` 显式恢复并注明原因。若关联修复本身有误，凭快照调查后通过反向的显式维护修复，不直接恢复整库快照覆盖其他更新。

## 跨空间后台进展

ingest 默认能用 `list_items(space: "*")` 和 `read_item` 发现用户可访问空间里的既有事项，显式限定的运行范围仍受限；原件工具和空间写权限不随之放开。只读目标走 `propose_item_update`，不改目标，不把进展挂到其他能写的旧事项。提案会保存来源、目标、原空间、用户和运行；相同未决提案重试复用。

主助手用 `list_item_proposals` 查看，读两边材料后 `resolve_item_proposal` 应用或驳回并写原因。应用需要原空间和目标空间的实际写权限及本次运行写范围；目标仍须属于该用户。已处理提案不能重复应用。提案不会主动通知或自动放开后台写权限。

来源撤回后，新通知不能通过旧事件重新带回被撤回的来源；历史事件保留原引用。提案来源已删除时不能应用，但仍可带原因驳回。卡片回调在等待操作人信息后重新核对持久状态，在同一事务内更新事项与交互，避免维护期间的旧回调操作错误事项。

定时提醒逐项处理：来源删除、行号失效或失去访问权限时，仍发送提醒正文，但不附失效链接，并在提醒事件保留被跳过的引用；单个接收者失效不会阻断后续提醒和巡检。维护入口会主动检查原事项关联的通知与交互，不能靠省略通知参数绕过旧卡片停用。
