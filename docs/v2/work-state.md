# 工作近况与人物卡

本人的一件工作常常持续几天、一周甚至几周。巡检、“有人找你”的分诊和处理、会后说明、主助手的对话，都在替本人判断“这件事和本人有没有关系、急不急、该怎么回”，但原来它们只知道“此刻”（`src/agents/owner-now.ts` 的 `ownerNow`：正在开的会、今天开过的会、最近一小时说过话的会话）。这里补上两样东西：

- **工作近况**：本人这几周在推进哪几条线，每条到了哪一步、下一步是什么、相关的会话文档分支事项；最近活跃的会话、文档、编码交办。
- **人物卡**：本人常打交道的人，各是什么角色、负责什么、通常找本人要什么、要什么样的答复、什么事可以找他或他的机器人。

## 放在哪里：personal 空间的 Wiki 页面

| 内容 | 位置 | 页面类型 |
| --- | --- | --- |
| 工作近况 | `personal` 空间的 `state/work` | topic |
| 人物卡 | `personal` 空间的 `people/<名字>`（同名的人加邮箱前缀，如 `people/小王-wang2`） | person |

为什么用 Wiki 页面，不用工作文件或记忆：

- 网页上直接能看、能改（Wiki 页面编辑），改动进 Git 历史，可以对比和回退；工作文件是过程材料，网页上只读，还会过期。
- 页面正文可以用 `[文字](src:<原件id>#L行)` 引用原件，人物卡的每条事实都能回到原消息；记忆一条一句，放不下一个人的全貌，也不适合整页地每晚改写。
- `personal` 空间只有本人能读：访客（`gatekeeper`、`guest`）可读的空间由 `guestSpaces` 决定，永远不含个人空间；成员看不到本人的个人空间。人物卡里写的是同事的工作信息，只给本人和本人的运行用。
- Wiki 已有 `person` 页面类型，不新增存储。

### “本人补充”一节

任何页面里标题为 `## 本人补充` 的一节归本人：`write_page` 由 Agent 写入时（`ctx.actor === "agent"`），宿主把这一节恢复成写入前的原文（`keepOwnerSection`，在 Agent 新写的正文里有这一节就替换在原位置，没有就放到末尾）。本人在网页上改页面不受影响。工作近况第一次建页时，整理角色会放一个空的“本人补充”，本人在里面写：

- 内部概念（某个系统、某类单子是什么）；
- 要追踪的对象和查法（“项目 A 的上线单：用技能 release-status 查”）；
- 对近况的更正（“项目 A 已暂停”）。

内部系统怎么查不进仓库：写成数据目录 `library/_skills` 下的技能。整理角色看到本人补充里要追踪的对象，有对应技能就照着查当前状态，写回近况的“要追踪的对象”一节；没有技能就写“没有查状态的技能”，不自己猜查法。

## 宿主给的原料（只有事实）

每晚的整理由定时任务 `work-state` 起一个同名运行（`src/agents/work-state-job.ts`），宿主把下面这些事实直接写进任务材料（不另做工具：只有整理角色用，一次给齐比让它逐个查省事），时间窗口是最近 `workState.days` 天（默认 21 天，设置里 3–60）：

| 原料 | 来源 | 函数 |
| --- | --- | --- |
| 本人发言多的会话（条数、最近一次、私聊还是群） | `lark_messages` 里 `sender_kind='owner'`，`lark_cursors.kind` | `workFacts` |
| 最近的文档：打开过的、本人在消息里发过链接的 | kv `lark_doc_opened:<url>`（见下）和 `lark_recent_doc:<url>`；本人消息里的链接对上 `sources.uri` | `workFacts` |
| 编码交办与分支（阶段、现在在做什么、仓库和分支） | `listCodeWorks`（`runs` 里 kind=code） | `workFacts` |
| 打开的事项 | `listItems(status: active)` | `workFacts` |
| 会议 | `lark_meetings` | `workFacts` |
| 本人让助手做过的事 | `runs` 里 kind=ask、本人发起的 | `workFacts` |
| 今晚轮到的人和他们的新消息（带 `src:` 引用） | `lark_messages`、`lark_people` | `peopleDue` |

“最近打开的文档”：飞书的“最近打开”搜索不返回打开时间，只按打开时间排序。`captureRecentDocs` 每次采集时看第一页，上次不在第一页、这次在的文档记为此刻打开（`noteOpenedDocs`，kv `lark_doc_opened:<url>`）。只采本人自己的（成员的采集不记）。本人编辑过哪些文档拿不到，没有做。

### 谁算常打交道的人

`peopleScores` 在窗口里给每个人计分：和本人私聊里他发的每条 3 分，在群里 @ 本人每次 3 分，在本人说过话的群里、本人发言前后半小时内他发的每条 1 分；4 分以上算。只算人（`sender_kind='user'`）；机器人写在维护它的人的卡上。本人自己的 id 取本人消息里出现最多的 `sender_id`。

`peopleDue` 每晚从分数高的往下挑**有新消息**的人（他相关的消息时间晚于 kv `work_state_person:<id>` 记的上次整理位置），最多 `workState.people` 人（默认 8，0 表示不更新人物卡）。每人给最近 12 行相关消息（他的私聊、@ 本人的、本人前后的群消息，加本人在私聊里回他的），每行带 `src:<原件>#L<行>`。运行成功后才推进这个位置。

### 什么时候不跑模型

距上次整理（kv `work_state_at`）没有本人新发的消息、新的对话或交办、事项变化、新会议、新打开的文档，也没有轮到的人，且近况页已经存在：运行直接记为安静，不调用模型。

## 整理角色：work-state

内置角色 `roles/work-state.md`。工具只有读（检索、原件、会话、事项、运行、技能、`lark_read`）和 `write_page`。要点：

- 近况在已有页面上改，不每晚重写；结构是“摘要 / 在推进的事 / 最近活跃 / 要追踪的对象 / 本人补充”。
- “摘要”三到六行、300 字以内：白天的运行只读这一节。
- 一条线是本人要达成的一件事，不是一个群或一份文档；结束的线移出去。
- 人物卡只记有出处的工作事实（团队和角色、负责什么、通常找本人要什么、本人通常找他要什么、在办的事、要的答复形式、这类事可以找他或他的机器人），不记评价和私事；本人记过的 person 记忆以本人说的为准。
- 页面路径由宿主算好（`personSlug`），同名不同人不合并。

定时任务 `work-state` 默认每晚 02:50 运行（在 03:30 的整理记忆之前），默认打开；在 设置 → 定时任务 里可以关掉、改时间、点“立即运行”，同一处可改天数、每晚人物卡上限和是否注入。

## 注入：谁读、读多少

都经过 `src/agents/owner-now.ts` 的 `ownerContextParts` / `ownerContextText`，把“此刻”“近况”“本人在这个会话里”“对方的人物卡”组织在一处，各个运行只取自己要的部分，不各自拼：

| 运行 | 带什么 | 位置 |
| --- | --- | --- |
| 主助手的对话轮次 | 近况摘要；在群里时，近 14 天在这个群发过言、有人物卡的人（最多 5 人，各一句） | 新会话的“会话背景”里；已在进行的会话，近况页改过（比对 `ThreadSettings.workStateSeen`）后的第一轮在本轮消息后面再带一次。只给本人自己的轮次：同事在群里问的、盯群批次、唤醒、交办回报都不带 |
| 巡检 heartbeat | 此刻 + 近况摘要 | 任务开头 |
| 有人找你：分诊 | 此刻 + 近况摘要 + 本人在这个群里 + “发送人”一行后面加对方人物卡的那句话 | 分诊材料（决策模型的 state 或通用模型的 prompt） |
| 有人找你：处理 | 分诊材料里的同样几项 | 处理任务的“分诊时找到的上下文” |
| 会后说明 | 近况摘要 | 会后任务开头 |

摘要取近况页的“摘要”一节（没有就用页面的 summary），截到 `workState.briefChars`（默认 500 字），后面附一行“全文 read_page(…)”。`workState.inject` 关掉时都不带（页面照常整理）。

## 找合适的人

`roles/_common.md` 的“本人近况与人物卡”（只给有 `recall` 的运行：访客角色没有）和 `roles/assistant.md`：自己和本人都处理不了的事，查人物卡和近况找出合适的人或机器人，向本人提出“拉谁进来、为什么”。拉人进群只通过已有的 `lark_invite`，有人的调用每次都要本人批准；“有人找你”的处理没有这个工具，只在提醒里提出。这里没有新增任何以本人身份写飞书的路径。

## 没做的

- 本人编辑过的文档（飞书接口拿不到编辑记录）。
- 其他渠道（Telegram、QQ）的对话对象：只认飞书采集的消息。
- 人物卡之间的团队结构（谁和谁一个团队）只靠卡片正文，没有单独的数据。
