## 1. 本人说的问题和实际原因

| 本人说的 | 实际原因 |
| --- | --- |
| 让 AI 编码基本不会更新需求 | 修改项不记需求点（`plan_tasks` 没有这个字段，`code_tasks.origin` 里没有 `reqs`）。需求点状态（`req_status`）只在阶段评审做需求拆分时写，按修改项推进的交办每次只拆一次（coding-loop.md 13 节），之后几十轮都不再更新。测试点的“对应测试”没有谁负责写。coding-loop.md 第 8 节写的“需求点上的状态按验证结论更新”没有实现 |
| 新交办的编码不会放到需求里 | 交办和需求只通过事项相连：`delegate_code` 带 `item_id`，事项的 `req` 材料圈出需求点（`src/items/work.ts`）。不带 `item_id` 时，只有“接着已有分支”才沿用那条分支上旧交办的事项（`itemOnBranch`）；新开分支的交办不属于任何事项。事项没挂需求时，交办在需求页同样看不到 |
| 找编码记录要去运行记录里翻 | 编码工作只在两处出现：需求节点详情的“编码与评审”（只列挂了需求的事项的交办），和运行页（按运行列，每一轮一行，和问答、整理、规则的运行混在一起）。没有“所有交办”的地方 |
| 需求页更像系统功能划分，测试点也就那样 | 需求树由助手一次拆好，之后编码不回写；助手建的节点一直是“待本人确认”，本人没有理由回来看 |
| 编码中看不到概览这些标签 | 需求页的 `WorkPane` 和运行页都是 `v-if="hasReview"` 才显示“概览 / 变更 / 评审 / 活动”；第一次阶段评审之前只有一列修改项和活动。`WorkPane` 还按“轮”打开，几十轮的交办顶上是一排轮次按钮 |
| 分支变了，不知道“应用到原分支”落到哪、怎么推 | 新交办默认从默认分支切出临时名 `omem/<运行 id>`，靠编码 Agent 自己改名（ide.md 里还写着“从仓库目录当前的 HEAD 切出、不 fetch”，代码早已改成先刷新默认分支）。同一件事拆成几次交办时分支各走各的。工作分支的“确认”= 推送到 origin 的同名分支，只有打开交办、展开分支面板才看得到；旧的补丁式交办才有“应用到原分支”，两套说法混在一起。外部 Agent 在工作区里直接 `git push`，omem 不知道 |
| 助手不会主动跟进 | 外部 Agent（`omem tool --peer`）和网页开的交办没有会话链：结束时不叫醒任何助手，`continue_code_run` 报“找不到这次交办的会话链”。本人停下的一轮（`stoppedByOwner`）不叫醒助手（默认“谁停的谁已经说了”），从网页或另一台设备停下时就没人说。没确认也没丢弃的交办没有人管 |
| 每个代码仓库都要单独建空间，太麻烦 | 一个空间只有一个目录（`spaces.root_path`），仓库只能是独立的 `repo` 空间，和业务空间并列；“项目和它的仓库”靠空间关联表达，多是 Agent 加的。交办的运行记在哪个空间看情况（事项需求树所在的空间，否则第一个仓库；网页交办记在表单选的空间），同一个需求的交办有的在业务空间、有的在仓库空间 |

常驻服务器上的数据（2026-11-05）：10-19 以来有 21 次交办或评审既没确认也没丢弃，其中 6 次最后一轮已经评审通过，最早的一次从 10-20 等到现在；这些交办里有 5 条工作分支还是 `omem/<运行 id>` 的临时名，另有一条以临时名推到了远端（例三）。17 个空间里有 5 个是代码仓库。

### 1.1 三个例子

下面三件事都是最近真实的交办，名字换成了虚构的。

**例一：工具仓库的改进（最严重）**

| 时间 | 发生了什么 |
| --- | --- |
| 第 1 天 | 本人让助手对照现有功能列改进清单并推进。助手建了事项和需求（一个模块、6 个功能、19 个测试点，全部待确认），交办 A：带事项，从 main 切出，编码 Agent 改名为 `feat/reliability`。第一次阶段评审写了需求点状态：3 个没实现、3 个部分实现 |
| 第 1～3 天 | A 推进 44 轮。6 个需求项第一晚就做完，之后是 52 个评审修改项（coding-loop.md 4.5 的背景说的就是它）。需求点状态一直停在第 1 天的“没实现 / 部分实现” |
| 第 3 天凌晨 | 本人在网页上停下 A 的第 44 轮，半分钟后在另一台设备的外部 Agent 里开了交办 B（同一分支，`parallel`），删掉约 4100 行并发加固。B 的外部 Agent 编码前先用工作区命令把分支推到 origin（omem 没有记录），编码后自己评审通过。A、B 都没确认；A 是本人停的，不叫醒助手；B 没有会话可汇报 |
| 第 3 天上午 | 本人要修两个点击问题。助手想续在 B 上，`continue_code_run` 报找不到会话链，于是开交办 C：没带事项（需求页看不到），也没带 `from_branch`，宿主从 main 切出 `omem/<C 的 id>`；第 3 轮再由宿主把 `feat/reliability` 合进来。C 做了 6 轮，助手几次都汇报了，进展写进的是它挂在事项上的工作记录，需求树没动 |
| 现在 | 一件事三次交办、两条分支，一次都没确认。确认 C 会把临时名分支推成 origin 上的一条新分支，而不是 `feat/reliability`；需求页上 6 个功能仍显示第 1 天的状态；A、B 没人再提 |

**例二：一个页面需求（前端仓库，同一工作分支）**

- 事项挂了需求，需求树在业务空间，事项本身却建在个人空间。
- 同一条工作分支前后 6 次交办：开发准备一次（第 1 天开，第 8 天才确认）；外部 Agent 开了一次 8 分钟后丢弃、重开一次做了 13 轮、69 个修改项（没有会话链，13 轮里助手一次都没被叫醒）；不经助手、直接从网页开的一次记到了仓库空间而不是业务空间（按业务空间找不到），10 分钟后本人在网页上停下，留下 1 个“编码中”和 1 个“等你决定”的修改项一直挂着；随后又开了一次，现在还在跑。同一分支的两次分支评审（两个模型各评一次）也一直挂着没清理。
- 需求点状态被评审更新过 5 次，比例一好；但 69 个修改项一个都没挂需求点。

**例三：后端修复（两个仓库，一次交办）**

- 一次交办同时改后端和前端两个仓库，9 轮后本人确认推送，助手跟进了 7 次，是这几件里最顺的。
- 但事项没挂需求，需求页上看不到它；两个仓库里只有后端的分支被编码 Agent 改了名，前端仓库那条以临时名 `omem/<运行 id>` 推到了远端。

## 2. 要达到的

1. 编码工作有一个统一的地方看：一次交办一行，打开就是它的全部（目标、进度、分支、评审、下一步），编码中也一样。
2. 代码仓库挂在业务空间下：在业务空间里“添加仓库”就行，检索、交办、评审、编码记录都在业务空间里找得到，不用再为每个仓库建空间、建关联。
3. 交办一定属于一件事（事项）。有需求的事项，编码时需求点状态和测试点跟着更新，本人在需求页确认即可，不用去运行记录里找。
4. 一件事在一个仓库里只有一条工作分支，页面上一眼看清从哪切出、现在在哪、确认后推到哪。
5. 交办停下、卡住、搁着时助手主动跟进，本人不用记着。

## 3. 编码页

可点的原型：`docs/v2/design/coding-prototype.html`（直接用 `web/src/styles.css`，数据虚构），黄色条里能切换三种放法和空间的几屏。

推荐放在运行页：运行页顶部切到“编码”（`/runs?view=code`），一次交办一行；“全部运行”就是现在一轮一行的列表。导航不加东西。需求页里点需求点的编码，打开的是同一个交办视图。另两种放法（单独的“编码”页、需求页左边切到“编码”）见第 9 节。左边列表，右边是打开的那次交办；手机上单列。和其他页面一样跟着顶部选的空间走（业务空间包括它的仓库，第 4 节），也可以选“所有空间”。

### 3.1 列表

一行是一次交办（分支评审也列，标“评审”），按“等谁”分组：

| 分组 | 包括 |
| --- | --- |
| 等你 | 有“等你决定”的项；完成，等你确认推送；同步冲突；失败 |
| 进行中 | 编码中（谁在做哪几项）、逐项验证、阶段评审、等外部 Agent |
| 助手在处理 | 有“等助手处理”的项，或助手被叫醒正在看 |
| 搁着 | 停下了（本人停的、预算用完、暂停）而且一天没有动静；被接替的 |
| 已结束 | 已推送确认、已丢弃（默认收起） |

每行写：标题；状态；进度（`需求 6/6 · 评审修改 12/15 · 等你 2`）；事项和需求（模块或功能名，没有时标“没归到事项”）；仓库和分支（`前端 · feat/x ← main · 已推送，本地领先 3`）；最后一次动静的时间。可按事项、仓库、分支、关键词筛选。

数据走新接口 `GET /api/code-works`：和 `itemWork` 一样在 SQLite 里投影，不读补丁、检查输出和运行日志；按用户可访问的空间限定（`accessibleSpaces`）。

### 3.2 一次交办

打开一行（`/runs/<第一个运行 id>`；打开交办里的某一轮也落到这里，停在那一轮的活动上），按交办打开，不再按轮（示例数据是虚构的）：

```
退款只按已发货的行计算                                   [运行页] [提问] [在 VS Code 打开]
事项：退款改造 · 需求：售后 / 退款申请（3 个功能）
───────────────────────────────────────────────────────────────────────────────
状态   完成，等你确认 · 第 6 轮 · 需求 3/3 · 评审修改 9（以后再做 2）
下一步 确认后推送 feat/refund-shipped 到 origin，归还工作区             [确认并推送] [丢弃]
分支   商城后端：main@3f2a91c 切出（11-02）→ feat/refund-shipped · 14 个提交
       origin 上有，本地领先 3 · 在仓库目录检出 · main 之后多了 12 个提交
       同一分支还有交办「退款单取消后恢复重新申请入口」（评审通过，没确认）
───────────────────────────────────────────────────────────────────────────────
[概览] [需求点] [变更] [评审] [活动] [分支]
```

- **标签一直在**：概览（修改项、等你决定的问题、交办时的任务原文）；需求点（这次交办挂的需求点和各自状态，第 5 节）；变更（按检查点 / 修改项 / 我上次看过之后，编码中也能看已经提交的）；评审（还没评审时写“待做项做完后做第一次阶段评审”）；活动（每一轮、宿主的合并 / 回退 / 推送、助手的跟进）；分支（提交、检出、改名、推送，就是现在的 `CodeBranchPanel`）。
- **轮次**：按修改项推进的交办不再显示轮次按钮，轮次在“活动”里按时间列；按轮推进的旧交办保留切换。
- **同一个组件两处用**：运行页和需求页（打开交办时左边的树变成它的需求点地图，和现在一样）。`WorkPane` 拆成这个组件，运行页里现在那套不一样的编码详情删掉。
- VS Code 插件以后也可以用 `GET /api/code-works` 列交办，这一次不改插件。

## 4. 仓库挂在业务空间下

### 4.1 做法：仓库是业务空间的下级空间

空间表加 `parent_id`。有上级的 `repo` 空间就是那个业务空间的仓库；没有上级的仓库照旧是独立空间（omem 自己、一个不属于任何业务的工具仓库）。

仓库在内部仍是一个空间，这是有意的：代码原件的路径（相对仓库根目录）、符号和调用图（`symbols`、`code_refs` 按 `space_id`）、交办工作区和工作区池（`wt-<运行>-<仓库>`、`workspaces/<仓库>/n`）、工作分支（`code-branch.ts` 按仓库空间 id）、事项的 `repo` 材料（`仓库#分支`）、外部 Agent 的工具，全都按仓库空间 id 工作，不用动，已有的数据也不用改写。要改的只是“人怎么看到它、它算在哪个业务里”。

另一种做法是一个业务空间挂多个目录、仓库不再是空间（新表 `space_repos`）。看到的效果可以完全一样（原件树里每个仓库一个文件夹），差在要改多少：

- 原件路径现在相对仓库根目录记（`package.json`、`src/index.ts`），一个空间里路径唯一（`unique(space_id, uri)`）。同一仓库里 `a/package.json` 和 `b/package.json` 本来就不冲突；两个仓库放进一个空间，根目录下的 `package.json` 才会撞，加上仓库名前缀（`商城前端/package.json`）就解决了。这一条不难。
- 难的是按“一个空间 = 一个仓库根目录”写的地方：调用图解析 `@/x` 时找 `src/x`、Python 的绝对导入按路径后缀在整个空间里匹配（两个仓库会互相连错）；交办工作区、工作区池、工作分支、检查 / 准备 / 外部 Agent 命令、同步状态（上次同步的提交）、排除规则、事项的仓库材料、`delegate_code` 的 `repo_spaces`，都要从“空间 id”改成“空间 + 仓库”；已有仓库的原件路径和运行里的引用都要改写。
- 下级空间的做法这些都不用动，所以推荐它；界面上按原型显示成业务空间下的仓库文件夹。

### 4.2 要改的地方

| 地方 | 现在 | 改成 |
| --- | --- | --- |
| 空间选择器、空间列表 | 仓库和业务空间并列 | 只列业务空间和独立仓库；仓库列在业务空间设置的“仓库”里，名字写成“业务 / 仓库” |
| 检索 | 限定在业务空间时，要先建“相关空间”关联才读得到仓库（`relatedSpaces`） | 业务空间默认包含它的仓库和仓库的交办工作区（`wt-…`）；`search` 的 `space` 写业务空间就够，写仓库只查那一个 |
| 运行的读写范围 | 运行限定在自己的空间加相关空间（`runner.ts`） | 业务空间的运行可读它的全部仓库；仓库的运行可读上级业务空间 |
| 交办 | `repo_spaces` 填仓库空间 id；运行记在 `homeSpace`（事项需求树所在的空间，否则第一个仓库）；网页交办记在表单选的空间 | 运行一律记在仓库的业务空间（例二那次记到仓库空间的情况没有了）；`repo_spaces` 可以只写业务空间：只有一个仓库时就是它，有几个时工具列出仓库让助手选 |
| 符号、调用图、交办工作区、工作区池、分支评审索引、事项的仓库材料 | 按仓库空间 id | 不变 |
| 权限（多用户，multi-user.md） | 按空间授权 | 仓库跟着业务空间的成员和角色，不单独授权；独立仓库照旧 |
| 空间关联 | “项目 ↔ 它的仓库”靠关联表达 | 上下级取代这类关联；跨业务的关联（某仓库调用另一个业务的接口）保留 |
| 仓库的 Wiki、记忆、事项 | 仓库空间也能有 | 按第 9 节的选择（推荐：都写到业务空间，仓库只放代码和仓库里的文档） |
| 编码页、需求页、运行页、事项页 | 按选中的空间过滤 | 选业务空间时包括它的仓库 |

### 4.3 设置：只多一个“仓库”列表

不加新面板，空间设置页反而减几项：

- **业务空间设置里一个“仓库”列表**：每行写名字、目录、当前分支、上次同步时间，操作是“同步 / 设置 / 移出”。列表下一个“添加仓库”：一个输入框，本地路径或 Git 链接（就是现在 `connect_repository` 做的事，多一个 `parent`），名字从目录或链接取，可以改。
- **仓库自己的设置**（检查命令、外部 Agent 可以运行的命令、排除的路径）从空间设置页挪到仓库那一行的“设置”里，用一个小抽屉。业务空间的设置页不再出现这些。
- **新建空间**：类型里去掉“代码仓库”和“关联目录”两项，新建的就是业务空间；独立仓库从“添加仓库”时选“不属于任何业务”建。
- **对助手**：`connect_repository` 加 `parent`（挂到哪个业务空间）；本人说“把这个仓库加到 X 下”时用它。`list_spaces` 把仓库缩进列在业务空间下面。

### 4.4 已有仓库空间怎么迁移

空间 id 不变，所以原件、符号、运行、事项材料、工作区都不搬。只需要给每个已有仓库定上级：

1. 宿主为每个仓库算一个建议：本人加的关联（“是它的代码仓库”）优先；其次是它的交办记在哪个业务空间、哪些事项的仓库材料指向它；再次是 Agent 加的关联。
2. 空间设置的仓库列表上方提示“这些仓库可能属于这里：前端、后端 [归到这里]”，本人点一下确认；不确认的照旧是独立仓库。
3. 归属之后：这对“项目 ↔ 仓库”的关联删掉（已经隐含）；按第 9 节的选择，仓库空间里的 Wiki 页面移到业务空间的 `仓库/<仓库名>/` 目录（用现有的换空间功能，旧路径保留跳转），记忆和事项改到业务空间；以前记在仓库空间的交办运行改记到业务空间（只改 `runs.space_id`）。
4. 进行中的交办不受影响，下一轮起照新的规则记。

## 5. 需求联动

### 5.1 交办一定属于一个事项

`delegate_code` 没给 `item_id` 时，宿主按顺序找：

1. 接着已有分支的，沿用分支上之前交办的事项（现在就有）；
2. 这个会话里最近一次交办或分支评审的事项、这个会话所在工作话题挂着的事项；
3. 外部 Agent 的交办：同一仓库、同一分支上没确认的交办的事项。

还找不到，按第 9 节的选择处理（推荐：工具拒绝，返回这个业务空间里还开着的事项列表，要助手传 `item_id`，或传 `new_item` 新建一个事项）。网页交办的表单加“所属事项”（可新建）。新建的事项放在仓库的业务空间（例二那种建在个人空间的情况，助手照现有的整理规则移过去）。

### 5.2 修改项挂需求点

- `plan_tasks` 每项可以填 `reqs`（需求点 id，必须在事项圈定的范围里，宿主校验）。编码 Agent 的任务里已经有“需求点”一节，`roles/coder.md` 写明：事项挂了需求点时，每个需求项至少挂一个功能点。
- 评审修改项自动继承：来自评审问题的，取问题所在变更点的 `req`；有 `follows` 的，取它接着的那一项的。

### 5.3 需求点状态跟着修改项走

- 一个功能点：挂它的需求项全部完成、并且之后的阶段评审没在它上面留下待做的问题 → 已实现；有的完成有的没完成 → 部分实现；都没做 → 没实现。来源写“编码 · 第 n 个检查点”，和评审拆分写的状态放在同一张表里，需求页显示最近的一条，时间线里两种都能看到。
- 交办确认（推送）时再记一条“已推送到 `<分支>`”。

### 5.4 测试点

- `finish_task` 可以带 `tests`：这一项新增或改动的测试对应哪个测试点（测试点 id → 文件 › 用例名）。宿主把它写进测试点的“对应测试”，按 Agent 的更正记一个版本，保持“待本人确认”。
- 写了测试、却没有对应的测试点（编码时发现的新情况），留给助手在交办停下时决定要不要补测试点（5.5）。

### 5.5 助手维护需求

- 交办停下（完成、暂停、等助手、等你）叫醒助手时，消息里多一节“需求对照”：每个功能点的状态、这次写的测试、没有测试点的测试、需求外的改动、本人在交办期间说过的会改变需求的话。
- 助手用已有的 `save_requirements`：补测试点；业务上变了的写成业务变更（带本人原话的 `msg:` 或原件的 `src:` 引用）；本人要了、需求里没有的改动补成功能点。都标“待本人确认”，本人在需求页确认，和现在一样。
- 写在 `roles/assistant.md` 的交办一节，和“对结果负责，不只是转达”放在一起。宿主只拼事实，不替助手判断要不要改需求。

## 6. 分支

### 6.1 规则

1. **从哪切**：新交办先看事项在这个仓库里最近的工作分支。那次交办还没确认 → 不新开，续在它上面（`message_code_run` / `continue_code_run`，工具直接拒绝并指过去，现在只对同一分支这样做）；已经确认 → 自动 `from_branch` 接着这条分支。事项在这个仓库还没有分支，才从默认分支切。
2. **名字**：建分支时就起好，每个仓库都要有。`delegate_code` 的 `branch` 由助手按仓库已有分支的习惯起（它能 `list_branches`）；几个仓库可以分别给（`branches: {仓库: 名字}`）；网页交办表单预填一个建议名。不再用 `omem/<运行 id>` 等编码 Agent 改（例三的前端仓库就是没改）。
3. **一条分支同时只有一次交办**：外部 Agent 也一样。本人明确要另开时（`parallel`），两边页面上都标“同一分支还有交办 X”。
4. **推送只走宿主**：工作区命令里的 `git push` 拒绝，返回里写改用 `apply_code_run` 的 `keep_going`（或网页“先推送验证”）。推送都记在交办上，页面看得到推到了哪个提交。
5. **接替**：一次交办续在另一次没确认的交办的分支上（`parallel`，或者 5.1 推断到的同一分支），旧的那次标“被 X 接替”，归还工作区，不再出现在“等你”里；确认新的那次就是确认这条分支。

### 6.2 页面上的分支行

每次交办、每个仓库一行，内容固定：仓库名；切出点（分支和提交、时间）→ 工作分支（提交数）→ origin 上的情况（没推过 / 已推送，本地领先或落后几个）→ 确认后做什么（“推送到 origin/x，归还工作区”）。另外写：在哪检出（仓库目录、工作区、都没有）；切出的分支后来多了几个提交；同一分支上的其他交办。合进主干（发合并请求）由本人在代码平台做，omem 不合。

旧的补丁式交办仍显示“应用到原分支”，并写出目录和分支；新交办不再出现这个按钮，统一叫“确认并推送”。

## 7. 助手跟进

### 7.1 每次交办都有汇报的会话

现在只有从会话里交办的才有会话链（`codeChainFor` 从发起的 ask 运行取会话）。外部 Agent 和网页交办补上：用事项最近一次本人说过话的会话；没有时用本人最近一次和主助手说话的会话。有了会话链，`continue_code_run`、结果汇报、等助手处理的叫醒对它们都照常工作（例一的交办 C、例二那次 13 轮没人管，都是因为缺这个）。

### 7.2 什么时候叫醒

已有的照旧（完成、等助手处理、预算用完、暂停、不收敛、只剩打磨，见 coding-loop.md 3.1）。新增：

- **从别处停下**：本人在网页或另一台设备停下一轮，不是在汇报会话里让助手停的，也叫醒助手；它告诉本人停在哪、剩下什么（例二停下后挂着的“编码中”和“等你决定”）、建议接着做还是丢弃。
- **外部 Agent 的交办结束**：和本机的交办一样叫醒。
- **巡检**：定时一次，对每个没确认的交办看：完成后一天没确认；停下一天没动；切出的分支前进了很多；同一分支有两次交办；同一分支的分支评审没处理；事项已经完成或取消。有这些情况，在汇报会话排一轮助手（`handoff.kind = code-watch`），一次列出所有交办；没什么要说的回答 QUIET。助手能做的：建议确认或丢弃、把被接替的标上、问本人要不要接着做、按 5.5 更新需求。巡检用现有的定时任务（和做梦、夜间复盘一样，默认关，在设置里打开）。
