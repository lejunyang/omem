# 回扫：一件件看助手答得怎么样

状态：设计（2026-11-28），还没开始做。接在 [回复发出后有没有用](reply-outcomes.md) 之后：那里的登记、等待、本人改判照旧，这里改的是判什么、按什么单位判、由谁判，以及数据页能按哪些维度看。

## 为什么要改

常驻服务器上最近 30 天登记了约 1,200 条回答（工作日一天 100–130 条，分布在 30 多个会话里）。数据页给出的“回复有用的占比”是 25%，和本人的体感差得远：多数回答是有用的，只是有些答得不全，被人追着补。查下来有四层原因。

1. **第一遍不准。** 第一遍由决策模型（一个小模型）标，自己给的把握平均约 0.5，低于门槛的都按看不出算。夜里复查用的是更强的模型，在随机抽查的有把握的回答里只同意了 40%；第一遍标成“被追问”、复查过的那些，一半多被改成了解决了、被纠正或看不出。
2. **“被追问”太粗。** 它把三件事放在了一起：原来的要求没答全（漏了说好的维度、时间段、口径）；在结果上换要求、往下做一步；接着问一件新的事。连着查数时尤其明显：“看下 11 月退款申请页的 UV”→“要日均”→“PC 和移动端分开”→“再加上管理员”→“导进这篇文档”，每一步都被标成被追问，其实只有“分端”那一步是前面漏了。
3. **按运行判，不按件判。** 上面那一串是同一件事的五轮，现在算五条回答、各判各的，没有“这件事做完没有、几轮做完、中间漏了什么”。
4. **维度缺。** 不知道是哪类工作（取数、排查、报警、编码……）。提问人只有飞书 open_id，数据页显示成“飞书用户 …末四位”，其实 `lark_people` 里几乎都有姓名，约一半有邮箱。同一个模型因为后端报的名字不同被算成几个（“GPT 6.1 Sol”“GPT-6.1 Sol”“gpt-6.1-sol”）。

另外有两处统计错误已经先修掉了（提交 550905d8）：成员自己和机器人会话里说的话被当成本人说的；飞书里带 @ 的那份同样的话没被去重，每句出现两遍。11-23 以后约四分之三的回答同时挂着会话和群，都受了影响；旧记录没有重判。

## 一件事是一个单位

**一件** 是一个人在一个会话（或一个话题）里为同一个目标连着提的几次请求。上面那串 UV 是一件；接着问“这个看板的权限找谁申请”是另一件。

- 宿主给候选：一个会话或话题里的回答按发出时间排，同一个提问人、相邻两次间隔不超过 2 小时的连成一串。跨天的不连，不同提问人的不连。
- 回扫的模型只在一串里面切：连着的几次才能并成一件，不跨串，并给每件起一句标题（“11 月退款申请页 UV，分端、含管理员”）。
- 第二天接着做同一件事的，回扫的材料里带上这个会话前一晚最后一件的标题和 id，模型可以把新的回答并进去。
- 一次运行只属于一件。件存 `reply_tasks`，回答的记录多一个 `task_id`。

## 结果怎么标

### 每次回答

替换现在的五种：

| 标注 | 含义 | 算有用吗 |
| --- | --- | --- |
| 解决了 | 接受了：道谢、确认、照着做了，之后没再就这件事说话 | 算 |
| 接着往下 | 在这次结果上提下一步：换口径、加维度、画图、导进文档。原来要的已经答到了 | 算 |
| 要补充 | 原来要的没答全：说好的维度、时间段、口径没给，或只给了一半 | 不算 |
| 被纠正 | 答错了、口径错了、答非所问，或让它重查 | 不算 |
| 别人接手了 | 本人或别人自己答了、做了，没用上这条 | 不算 |
| 看不出 / 没人接话 | 后面的话和它无关；一整天没人就这件事说话 | 不计入占比 |

“接着往下”和“要补充”按一条线分：后来要的东西，提问人原来那句话里有没有。原话里有（“分 PC 和移动端”），回答没给，是要补充；原话里没有、后来才说的（“再加上管理员”），是接着往下。回答自己挑了口径又没说出来、被人指出来的（只算了运营人，没说不含管理员），算要补充。拿不准的按接着往下，依据里写一句为什么，免得像现在这样全偏到一边。

“要补充”和“被纠正”另写一句**缺的是什么**（40 字以内）：“没分端”“没说 UV 是按天去重还是区间去重”“用错了表”。这一句是后面“常缺的”的原料。

### 每件

- 结论：做完了 / 没做完（停在哪一步）/ 转给别人了 / 看不出。
- 几轮：这件里有几次回答；其中要补充几次、被纠正几次。
- **一次答完**：第一轮之后没有要补充、没有被纠正（接着往下不算）。
- 用时：从第一问到最后一次回答。

### 旧数据

已经标成“被追问”的旧记录照原样留着，数据页单列成“被追问（旧标注）”，不混进新的两种。要不要用回扫重判最近两周，见文末。

## 任务类型

两层：**类型**是一份短清单，每件选一个；**主题**是自由的短标签，可以有几个（“退款改造”“UV / 留存”）。

- 清单是数据，不写在代码里。表 `task_types`：名字、一句定义、两三个例子、范围（全部，或只用于某几个空间）、状态（待确认 / 在用 / 合并了 / 不要）、合并到哪个、谁提的。
- 第一次启用时种一份通用的起始清单，每个一句定义：取数分析、问题排查、报警与值班、编码改动、代码评审、测试与验证、文档与汇报、咨询答疑。本人可以改名、删、加。
- **不按人分清单。** 大家共用一份，每个人做的事不同，体现在各类的多少上；各建一套就没法放在一起看了。空间可以补自己的类型，只用于这个空间里的件。
- **清单会长。** 回扫给每件选一个类型；都不合适时选“其他”，并写它觉得该叫什么。宿主每晚数一次：同一个建议名（模型合并近义的）7 天里累计 5 件以上，就变成一条类型提议，带着这些件做例子。回扫也可以提“某类太宽，建议拆成两类”。提议和工作指标的提议是同一种样子：保留 / 改 / 合并到… / 不要，不要的可以写一句为什么，回扫以后会读到。
- 件按类型的 id 存，名字只用来显示：改名、合并后，旧件跟着指过去。拆分只影响之后的件；提议里可以勾选“把最近 30 天的件按新清单重排一次”。

## 谁问的、哪个模型

- **提问人的键**：成员是 `user:<id>`；飞书上的人有邮箱时是 `email:<邮箱>`，没有时是 `lark:<open_id>`。机器人和 lark-cli 看到的 open_id 不同，按 `lark_people` 认成同一个人。另存当时的显示名。别的机器人 @ 它的是 `bot:<id>`。这个键算一处，件、回答、查数记录都用它。
- **提问人类别**：本人 / 成员 / 没登记的同事 / 别的机器人。它是“回复发出后的结果”那张表的默认分行，代替现在按运行类型分（现在“对话里的回答”一行把本人、成员和没登记的同事混在一起）。
- **显示名字**：本人在数据页看到姓名，悬停看邮箱，“谁触发的”筛选和拆分也一样。成员只看到“你”和“别人”，沿用数据页现有的可见范围。
- **模型名归一**：`parseAi` 取出的模型名转小写，空白和下划线换成连字符后再比。后端（codex、traex……）另作一个维度。
- 邮箱只有一半，补全要飞书应用开通 `contact:user.email:readonly`；没开时按 open_id 记，开了以后同一个人的旧记录按 `lark_people` 合过去。

## 查数记录

不绑在某个类型名上：只要一件事的回答里给出了从某个系统查出来的数，回扫就记一条**查数记录**。

- 内容：问的是什么（一句）、口径（时间段、去重方式、范围）、来源（系统、表、看板链接）、结果在哪（回答、工作文件、文档链接）、谁问的、属于哪件。
- 放在“工作数据”页头那行小字里的“查数记录”抽屉，按时间倒序，可以按人、类型、来源筛。
- **问了几次就提成指标**：同一个口径（来源、指标、范围相近）30 天里被问了 3 次以上，不管是不是同一个人，回扫用 `metric_define` 提一个指标提议，提议里列出这几条查数记录。已有指标覆盖的就挂过去，不另提。
- 口径本身照旧在整理群聊时写进记忆，查数记录只引用，不重复写一遍。
- 可见范围和运行一样；访客的问答只计数，不进记录正文（数据页本来就不显示访客的提问）。

## 数据页

- “做得怎么样”里“回复发出后的结果”：行默认按提问人类别，右上可以切成按任务类型、按模型。列是上面六种标注，另有两个数：回复有用的占比 =（解决了 + 接着往下）÷ 判得出的；一次答完的占比（按件算）。
- 新加一块“按任务类型”：一类一行，件数、平均几轮、一次答完、要补充、被纠正、用时的中位数、用得最多的模型。点一行打开现有的拆分抽屉。行下可以展开“常缺的”：这一类里“缺的是什么”出现得最多的几条（模型归并近义的）。
- 筛选条加“任务类型”；拆分抽屉多三个维度：任务类型、提问人类别、后端。
- 类型提议放在“做得怎么样”上方的“等你确认”小条里，和工作指标的提议同一种样子。
- 按人只看分布，不出排行，沿用数据页“不给人排效率名次”的规矩。

## 谁来判、花多少

- 回扫就是现在的夜里复查，范围变大：从“一到三天前挑 30 条”改成“前一天的全部回答”，按会话分批（一批一个或几个会话，不超过 15 次回答），交给 `outcome-reviewer`。工作日约 8–10 个运行一晚。上限 `replies.outcome.sweep.max`（默认 150 次回答），超过时按现在的挑法先挑。
- 第一遍小模型的标注留作发出几小时后的**临时结论**，运行页标“临时”；数据页只算回扫、本人和表情的结论。现在读第一遍的地方（夜间复盘挑题、整理消息时“助手在这个会话里以往的回答”那一行）改读回扫的结论，还没回扫的才用临时的。
- 角色说明写进 `roles/outcome-reviewer.md`。交结果的工具 `review_reply_outcomes` 改成一次交一批件：怎么分件、每次回答的标注和依据、件的结论和标题、类型（或建议的新类型）、主题、缺的是什么、查数记录。工具改了要同步 `skills/omem/references/` 里对应的说明。
- 本人改过的仍然是事实，回扫不动；本人还可以在运行页改这件的类型。

## 数据

- `reply_tasks`：id、place（会话或群加话题）、提问人键和名字、首末时间、标题、`type_id`、topics、outcome、rounds、supplements、corrections、missing（每条缺的是什么和运行 id）、by、at、`sync_key`。
- `reply_outcomes` 加 `task_id`、`missing`；标注多 `next`、`supplement` 两个取值，`followup` 只留给旧记录。
- `task_types`：id、name、description、examples、spaces（空为全部）、status（proposed / active / merged / dropped）、merged_into、proposed_by、proposed_run、owner_note、created_at、updated_at。
- `data_queries`：id、task_id、run_id、提问人键、question、definition（口径）、sources、result_ref、metric_id、at。
- 四张表都随拉取同步（`src/core/pull-data.ts`），新接口在 `src/auth/routes.ts` 登记权限。

## 分期

1. **标注和维度**（不加类型）：新的六种标注和“缺的是什么”、回扫看前一天的全部、按提问人类别分行、名字和模型名归一、旧标注单列。上线后在常驻服务器上跑三晚，请本人抽 20 条看“接着往下 / 要补充”分得对不对，再往下做。
2. **分件和类型**：分件、类型清单和类型提议、数据页“按任务类型”、筛选和拆分的新维度。
3. **查数记录和常缺的**：查数记录、问了几次就提成指标；“常缺的”交给 coach 读，由它提角色说明或技能的改法。

## 要本人定的

1. 第一遍小模型：留作临时结论（建议），还是停掉、只等回扫。
2. 旧数据：最近两周用回扫重判一次（约 100 个回扫运行），还是只从上线那天算起、旧的单列（建议后者）。
3. 起始类型清单用上面 8 个，还是本人先给一份。
4. 成员看数据页时能不能看到别人的名字（建议不能，只看到自己）。

## 不做的

- 不在回答时让助手自己报类型：每轮要多带一段说明，而且它判自己不准。
- 不按人建不同的类型清单。
- 类型和查数记录不放进记忆：它们是用来统计的结构化数据，不是要助手记住的事。
