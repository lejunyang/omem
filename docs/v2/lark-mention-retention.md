# Oncall 本人被 @ 后保留群消息

这条规则默认关闭。启用后，omem 在确认关联的 Oncall 群里发现结构化的本人 mention，先保存命中消息，再优先读取群上下文，同时以用户鉴权邀请配置中的 omem 机器人。邀请失败不妨碍用户身份保存。规则本身不发群消息、不回复、不改工单、不恢复用户成员关系。

## 启用

先检查实际安装的新版 bytedcli 路径与版本（`osdk where node`，在对应工具目录运行 `bytedcli --no-auto-upgrade --version`），不要依赖 PATH 里可能较旧的副本。官方 `@larksuite/cli` 由 omem 依赖提供，用户应已登录。CLI 用户 open_id 与机器人应用看到的本人 open_id 是两套身份，不能混用。

在**准备应用代码时**，合并下面的字段到实例 `config.json` 的 `lark`，保留其他配置；示例租户、身份、群、工单均为虚构，不可直接用于运行实例。本功能开发和检查不会修改实例配置。

```json
{
  "lark": {
    "enabled": true,
    "appId": "cli_actual_omem_app",
    "ownerOpenId": "ou_owner_in_omem_app",
    "capture": {
      "mode": "subscribed",
      "mentionRetention": {
        "enabled": true,
        "cliOwnerOpenId": "ou_owner_in_cli_app",
        "tenantIds": ["100", "200", "300"],
        "oncallCli": "/opt/tools/bytedcli",
        "relatedTypeIds": ["800"],
        "chats": [
          {
            "chatId": "oc_verified_chat",
            "tenantId": "100",
            "flowId": "123456",
            "evidence": "已核实工单详情及关联群",
            "related": true
          }
        ]
      }
    }
  }
}
```

- `appId` 必须是当前 omem 机器人应用，不能填 CLI 应用。密钥仍沿用现有安全存储。
- `cliOwnerOpenId` 来自官方 CLI `auth status --json --verify` 的 `identities.user.openId`。运行时身份不符不会邀请，也不会继续以该用户身份优先读取旧命中群。
- `tenantIds` 只列本人已授权的租户。代码不含业务租户或群名的特判。
- `oncallCli` 可省略。配置后，遇到未知群的本人 mention，以该绝对路径执行固定的只读 `oncall flow list` / `oncall chat get`，不执行 shell，不自动升级、不更改登录。列表查询最近三天收到消息的工单，按租户完整分页，不按关单状态过滤；字段必须确认租户、工单、飞书 `open_chat_id`。工单内部 `chat_id` 不是飞书群 ID。工单侧归档或历史“解散”标记不作为飞书真实解散的证据。失败时保留工单发现进度和待确认 mention，状态可查看。
- `chats` 是已核实映射，也可用于不安装 bytedcli 的场景；只配静态映射时，新群需补充映射，不会自动识别。CLI 查询确认的映射另存在数据库，不改配置文件。
- `relatedTypeIds` 与映射的 `related` 只影响先后次序，不取代本人 mention。分类 ID 需预先核实，不从名称猜责任团队。
- 机器人必须开通接收群消息及资源权限，订阅 `im.message.receive_v1`、`im.chat.member.bot.added_v1` / `deleted_v1`、`im.chat.member.user.deleted_v1`、`im.chat.disbanded_v1`。已有应用可在开放平台核对事件，权限检查沿用 `omem lark bot-permissions`。邀请需要 CLI 用户的成员管理权限和应用可用范围，群主限制或审批仍由飞书决定。
- 保持 `lark-poll` 定时任务启用，`capture.mode` 不设 `off`。配置由实例启动时读取；应用代码、启用配置与重启需另行安排，不是本开发任务的动作。

查看规则和进度：

```bash
omem lark retention-status
```

输出包含生效配置、已命中的群、触发消息、邀请状态、尝试次数、下一次核验时间、最近采集成功/失败、机器人事件时间、生命周期事件、未确认映射的 mention 、分轮采集的分页/话题进度、待重试及已停止重试的机器人事件。不会输出应用密钥或鉴权令牌。

## 采集、延迟与失败边界

轮询先搜索本人 mention，再处理优先群，之后才读取普通群、历史、日程和妙记。常规已读群也参与发现；免打扰、单群 skip、exclude、普通群 maxChats / quietStop 均不会挡住已授权命中群。命中后的用户读取按“只保存”，不自动调用监听 Agent；规则范围内的机器人消息也不触发自动答复。搜索、群上下文及话题已返回的每页正文先保存；后续分页失败或令牌缺失/重复时不推进该页进度。CLI 身份未核实或不匹配时，记录提示并退出优先路径，原有订阅仍按常规策略采集。

轮询发现依赖飞书搜索可见性、调度间隔、前次采集是否完成、CLI 和工单查询耗时。默认配置常为每十分钟，必须检查实例实际任务设置。**机器人尚未入群且没有合法事件入口时，不是真正实时**：本人在首次轮询前已被移出、消息尚未进入搜索或超过首次 24 小时发现窗口，都可能无法读取。新增覆盖应先启用规则与事件，不能靠历史恢复替代。

未知群的 mention 会保存在群原件和待确认队列；自动重查最近三天的候选。为在本人离群前保存触发证据，未知群的首次 mention 也会先落原件，即使该群常规策略为 skip；未确认映射不会邀请或启动优先群读取，这条单消息原件不会因三天未确认而自动删除。超过三天仍未确认的候选留在状态中供核查，不继续反复扫工单。已确认群先采集；未知群的工单发现每轮最多六个只读请求，分页及待处理工单进度存库，完整扫描后至少间隔十分钟再查。工单读取失败保留当前扫描位置；mention 已持久化后搜索游标可以推进，仍会重查待确认队列。搜索本身失败则不推进搜索游标，失败分页不会被当作读完。初次优先读取从触发时间向前 `lookbackHours`（默认 72 小时）取可读上下文，随后每轮从群游标向前重读十分钟以发现近期修改；机器人另以自身权限回读近 72 小时已保存消息：每分钟按已授权群的 `(chat_id, create_ms, message_id)` 索引游标最多检查 20 条候选，不扫描全量消息；群间轮转，完成一轮后至少间隔十分钟，进度持久化，失败走事件重试队列。回读成功后保存已完成处理的消息摘要；相同摘要的后续回读跳过描述、引用查询和整理，正文确有变化才重新整理。刷新时间标记与摘要仅保留近 72 小时消息对应的数据，过期或消息已不存在时按主键范围分批清理，每类每分钟最多 40 行。此路径不依赖本人仍在群里。当前 SDK 与官方消息事件没有已核实的通用消息更新事件，不订阅假设的 `im.message.updated_v1`；更老消息需显式补采，消息量大时回读延迟增长，不保证任意历史编辑均被发现。

优先群上下文与话题共用每轮 20 次列表请求预算，单群主列表每轮最多五页、每个话题每轮最多五页、单群最多十个话题；超过预算继续普通群、日程和妙记，下一轮按持久化的时间窗口、页令牌和话题位置续读。话题按时间倒序，遇到时间窗之前的消息停止翻页；正文与资源成功保存后才推进页位置。完成整个窗口后才记录采集完成时间，群和话题游标分别在对应列表读完后推进。预算限制请求数量，不保证固定耗时，单次 CLI 的网络超时仍可能拖延本轮。状态中的 `priorityScans` 可查看尚未读完的窗口。

无论保留规则是否开启，@我消息现写入各群原件，不再新增旧的 `lark:mentions` 聚合原件；已有聚合原件保留。发送人和 mentions 的联系人学习继续执行。聊天视图按消息时间展示，原件引用行号保持稳定。

邀请使用官方 CLI：

```bash
lark-cli im chat.members create --chat-id oc_verified_chat --member-id-type app_id --data '{"id_list":["cli_actual_omem_app"]}' --as user --format json
```

邀请前后用 **omem 自己的 SDK / tenant token** 调用 `chatMembers.isInChat` 核验真实机器人成员关系，不跨应用比较 open_id，不凭机器人名称认身份。已在群不重复邀请。数据库保存十分钟重试间隔与最多三次尝试；等待审批不重发邀请，只核验是否已入群。达到上限保留失败；新 mention 不会重置次数。进程在请求途中退出时，下次先核验成员再决定是否需要重试，无法保证远端审批系统的 exactly-once，审批状态未知的异常请求仍可能在十分钟后重试，最多三次。

用户身份采集、机器人消息事件以同一 `chat_id/message_id` 关联到原件行；旧的只有原件文本的消息按行末消息 ID 恢复结构化关系，不再追加同一消息。资源引用合并，话题、引用父消息和机器人卡片原始 JSON 保留；观察到的编辑更新同一行，引用行号不变。机器人事件在确认前持久化，资源或正文保存失败由队列重试，最多失败十次后停止自动重试并保留可见失败状态。成功的实时消息事件保留独立完成回执；回读任务成功后直接删除，不累计时间桶回执。每轮最多处理 40 个到期事件。实时完成回执不再参与待处理事件扫描，重启和旧事件重投不回写旧正文，不依赖用户仍在群里。回读仅对已确认入群或收到过机器人消息且未被移除/解散的群排入，已保存的资源 key 不重复下载。卡片内嵌资源失败另排资源任务，最多十次后保留失败状态，不阻断该消息的后续正文回读与新卡片编辑。优先用户采集先保存正文，附件失败记录可见且不推进采集游标。

生命周期分别记录：

- 本人被移除：用户读取失败留状态，机器人仍收到的新消息照常保存。
- 机器人被移除：停止自动重新邀请，用户仍可读时继续采集；重新入群事件可恢复机器人成员状态。
- 飞书真实解散事件：停止该群后续优先轮询与邀请，保留已保存原件。
- 权限失败：记录实际读取/邀请失败，不推断成解散；机器人全消息权限不足时，入群也不等于完整消息覆盖。

不做真实群写操作或在线故障注入来验证这些分支。测试使用假 CLI、假 SDK 和临时数据库；上线后的权限与搜索可见性需要按实际状态验收。


## 历史完整性与旧队列恢复

历史回溯使用 `lark_history_scan` 持久检查点：固定查询窗口、远端页令牌、主列表/话题阶段、当前话题、已保存最早时间和失败信息。每轮受 `capture.backfill.pagesPerPoll` 总限额约束，活跃采集先执行，历史群按最近尝试时间公平推进。已排队群及其原目标保留，不需要写库脚本迁移。

整页 ID 已知、空页但仍有下一页、同毫秒边界都不是终止证据。正文逐页写入；已知 ID 也继续补下载资源，旧纯文本行按消息 ID 复用。正文及所请求附件保存成功后才提交该页令牌。失败后保留原令牌，重启续读。`has_more` 缺失、下一页令牌缺失/重复均报错，不能显示完成。终止仅依据主列表与所有发现话题的远端 `has_more=false`；不把 `oldest_ms` 设置为目标日期假装覆盖。

官方 CLI `1.0.97` 的本地 help/skills 与 dry-run 已核实：默认单页；返回 `has_more/page_token`；ISO 时间边界转换成秒级。API 文档未明确端点是否包含边界，因此查询边界外扩、按毫秒在本地筛选，并在固定窗口内依靠页令牌遍历，不用“最早时间减一”跳过同毫秒消息。[官方会话历史接口](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/list) 说明群容器只返回话题根、线程不支持时间筛选；为发现目标日期之前建立但期间有回复的话题，根列表从 2010 年起只读遍历，范围外正文与附件不保存，话题逐页读到耗尽，期间按授权时间窗筛选。这增加请求量，但仍分轮限额执行。

应用修复后，旧队列若只有 `oldest_ms<=target` 而没有远端耗尽证明，会重新显示 pending 并按原目标核验。已有可靠检查点续读；重复安排同一或更窄范围不会打断正在进行的扫描。已完成群若仍需显式复核，可走已有 `set_lark_backfill` 工具或 main 已有命令 `omem lark backfill <oc_群ID> --days <已授权天数>`；保留其他群队列。不用修改 `oldest_ms`、不清库、不运行直接写库的恢复脚本。只读进度由现有 backfill 状态接口返回 `pending/evidence/progress/error`（error 在 progress 内），`reachedAt` 仅表示实际保存的最早消息，不等于完整覆盖。完成证据不代表无权限消息、已撤回消息或 CLI 不支持下载的资源可恢复。

当前主仓库的通知/手动续轮、规则派发及补附件能力保留在 main 兼容补丁中；不要把旧 worktree 的整个文件覆盖到 main。应用补丁需在目标分支重新检查，本轮未实际恢复生产队列或修改实例数据。


## 空归属修复与恢复整理意图

数据库里已有消息 ID，但 `source_id/line/archive` 全为空且任何聊天原件都没有这条消息时，仍需按月补写聊天原件并修复三项归属。已存在的 ID 只用于避免重复行，不是分页完成证据；远端第一页 `has_more=true` 时必须继续消费下一页令牌，只有后续耗尽才结束。相同消息重放后，数据库记录和聊天原件行各保留一次。

旧结束请求自动重新核验后，通过正式 `set_lark_backfill` 恢复 `ingest=true`，同一或更窄范围的进行中扫描保留固定窗口、页令牌、阶段及已触及原件；耗尽后才提交这些原件整理。当前 main 的正式入参是 `{chat_ids, days:0, files:true, ingest:true}`，`files=true` 同时启动已有缺文件后台补拉。旧工作区的旧入口只有 `chat_id/days/ingest`，原树回归验证共用的 `requestBackfill` 内部语义，main 兼容树的 `test/lark-backfill-entry.test.ts` 另用真实工具注册入口验证完整参数、实际补拉和真实 ingest 运行，不能把旧 schema 的测试当成 files 验证。

附件永久失败时，历史分页仍保持 pending，失败信息保存在进度 error，不静默跳过为完整；后台补文件的失败数/错误也需单独验收。补拉成功、历史耗尽和整理运行入队是三个不同结果，不能互相替代。所有队列回归使用四十个虚构测试群及临时数据库，不读取或修改真实群队列。
