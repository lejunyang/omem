# 材料从个人空间归位

问题：个人空间很容易堆满业务文档和工作记录。原因有三个：

1. 归档角色（archivist）只看正文和空间说明，角色说明写的是“不确定时留在个人空间”，判断一次之后不再看；
2. 主助手很多轮在个人空间里跑，它为业务事项写的工作文件也落在个人空间；
3. 业务 Wiki 页面引用了个人空间的原件，协作者没有个人空间的读权限，打不开这些引用。

在一台实际使用的机器上，个人空间有三千多份文档、一百多份工作文件，一次检查里业务页面引用个人空间原件的有七十多处。

目标：业务材料不在个人空间里沉积；留在个人空间的是确实个人的或确实判断不了的；本人不用逐份处理。

分工不变：宿主只查事实（旁证）、排队和执行移动，判断交给 archivist。代码里不按空间名、群名或项目名特判；“个人空间”指本人自己的、`kind = personal` 的空间（`homeSpaces`），别人的个人空间不动。

实现在 `src/sources/homing.ts`（旁证、重判队列、每晚检查、工作文件、本人的操作）和 `src/sources/reach.ts`（引用可达性），挂接在 `src/agents/jobs.ts` 的 `archive` 运行、`src/agents/tools.ts` 的 `classify_source` / `write_file`、`src/main.ts` 的定时任务。

## 1. 判断时的旁证

`archive` 运行把每份待判断原件交给 archivist 时，附上宿主查到的 `evidence`（`archiveEvidence`，空的部分不写）：

| 字段 | 内容 | 从哪里来 |
| --- | --- | --- |
| `wiki` | 飞书知识库名、目录路径、直接父目录；`kbSpace`：本人把这个知识库归入的空间 | `meta.wikiSpaceName` / `wikiPath` / `wikiParentTitle`，`wiki_spaces.status = mapped` 的 `target_space` |
| `siblings` | 同一目录（同一 `wikiParentNodeToken`）的其他文档现在各在哪个空间、几份 | `sources.meta` |
| `citedBy` | 哪些其他空间的 Wiki 页面、事项（`source_refs` 或材料关联）、记忆引用了它，合并过的重复原件的旧 id 也算 | `page_cites`、`items`、`item_materials`、`memories`、`source_aliases` |
| `linkedIn` | 哪些采集的群在消息里贴过它（按文档 token 查），群绑定或所在的空间 | `lark_doc_links`（见第 7 节）、`chatBinding` |
| `attention` | 本人或 Agent 手动定的关注程度（规则和目录继承的不算） | `sources.attention` |
| `belongsTo` | 工作文件挂着的事项或规则，及其空间 | `meta.links` |

重新判断的原件另带 `again`：这次为什么又交给它（“被其他空间的 Wiki 页面引用”等）。

`roles/archivist.md` 改了判断方式：正文主要讲某个业务空间，或几条旁证指向同一个业务空间，就归过去，不要因为“不是百分之百确定”留在个人空间；只有一条弱旁证、旁证互相矛盾时留下并记为“判断不了”，写上候选空间；日常个人内容留下并记为“确实个人”。不新建空间、不搬多主题的群，这两条不变。

`classify_source` 多了 `verdict`（business / personal / unsure）和 `candidates`。留在个人空间的写进 `source_routes.verdict` / `suggested`；移走的把当时的旁证存进 `source_moves.detail`，`source_moves.mode` 记这次移动是怎么来的（manual / rule / binding / ai / follow）。

## 2. 重新判断

留在个人空间的原件不是一判定终身。宿主为每份交给 archivist 的原件记下当时旁证的“指纹”（`archive_evidence`：其他空间里引用它的空间、同目录文档去了的空间、知识库归入的空间）。之后：

- **有新旁证**：每晚用几条 SQL 找出“被其他空间的页面 / 事项 / 记忆引用”“知识库已归入业务空间”“同目录有文档已在业务空间”的个人空间原件，重新算指纹，和上次不同的进入重判队列 `archive_recheck`。同样的旁证不会让它反复排队。
- **空间或归档规则变了**：空间（名称、说明、上级）和已启用的归档规则的摘要变了，所有留在个人空间、可重判的原件排进队列，排在最后。第一次检查只记下当时的状态，不排队（不让三千份历史一下子全部重判；要整批重判用“整理已有材料 → 没命中的交给 AI 判断”）。
- **读者打不开的引用**（第 5 节）：送进队列最前面。

优先级：被业务页面引用、读者打不开（0）→ 被事项或记忆引用、知识库已归入（1）→ 同目录文档已归档（2）→ 空间或规则变化（3）。

可重判的只有本人个人空间里、不是代码 / 对话 / 活动 / 工作文件、归属不是本人手动指定、会话绑定或归档规则定的原件。本人移回或指定过的（`mode = manual`）永远不再进队列。

### 每晚检查

定时任务 `archive-sweep`（默认每天 01:40，开着），`sweepHoming`，在后台跑（第 7 节）：

1. 工作文件跟着事项或规则走（第 3 节）；
2. 读一批旧消息里的文档链接（最多用总时长的 40%）；
3. 收集新旁证，排队；
4. 按优先级取队列：已启用的归档规则或会话绑定现在能定的直接移走，不算预算；其余最多 `archive.nightly` 份（默认 60）标为待判断（`source_routes.reason` 以“有新旁证，重新判断”开头），交给 `archive` 运行（按来源空间每 40 份一批）；
5. 结果记在 `kv.archive_sweep_last`（含用时、是否到了时间上限），进度在 `kv.archive_sweep_progress`。

没有待判断的就不建运行、不调用模型。网页上的“现在检查”（`POST /api/archive/homing/sweep`）立即返回“已开始”，检查在后台进行，页面每两秒刷新进度。

为什么每晚 60 份：重判是读整份原件，60 份大约两三批归档运行；有新旁证的通常每晚只有个位数到几十份，空间或规则变化后的积压按这个速度几天到几十天清完，不挤占白天的整理。可在归档规则页改成 0（只移工作文件和按规则归档）、20、120、300。

## 3. 工作文件跟着事走

- `write_file` 没写 `space`、没挂事项时，如果运行在本人个人空间、而它（或它所在的那条工作线的第一个运行，`lineRoot`）的范围（`run_scope`：给它的或它动过的事项、它回答的会话、所在的群、触发它的规则）只指向一个业务空间，文件写在那个业务空间（`matterSpace`），结果里写明“跟着事项「…」放在空间 …”。指向两个以上空间时不猜，仍在个人空间。这次运行不能写那个空间时也留在原处。同一路径在个人空间里已有的旧版本一起移过去（id 不变）；本人移回过的文件不动。
- 挂了事项（`item`）的照旧放在事项所在空间；给了 `space` 就放那里，要放个人空间就明确写 `space`。
- 已经在个人空间里、挂在业务空间事项或规则上的工作文件，每晚检查时移到那个空间（`followWorkFiles`，不经过模型，`source_moves.mode = follow`）。

## 4. 看得见、撤得回

- 每次移动都记在 `source_moves`，原件详情的“换空间”历史里能看到（`GET /api/sources/:id/archive` 多返回 `mode`）。
- 归档规则页左侧列表底部新增“从个人空间归位”（`web/src/components/ArchiveHoming.vue`，不改原件页的布局）：
  - **最近自动移走的**：从本人个人空间自动移到别处的（AI 判断、归档规则、会话绑定、跟着事项），依据和时间；还在那里的可以“移回”。移回后记为本人指定（`mode = manual`），之后规则、AI 和每晚检查都不再移动它（`POST /api/archive/homing/return`）。
  - **判断不了，等你定**：archivist 记为“判断不了”或（自动移动关闭时）“建议移到某空间”的，勾选后批量放到某个空间，或批量留在个人空间；两种都记为本人指定（`POST /api/archive/homing/assign`）。
  - **页面引用的原件，读者打不开**：选一个空间看第 5 节的检查结果，可以把其中个人空间的原件送去重新判断。
  - 两个设置：AI 判断属于业务空间时是否直接移过去（`archive.autoMove`），每晚交给 AI 的份数（`archive.nightly`）。

**自动移动默认打开。** 本人的要求是及时移走、没时间逐份看；移动不改原件 id、正文、行号、引用和已有的派生知识，随时能一键移回且移回后不再被动，代价小。关闭后 archivist 的判断只记成建议，等本人在“等你定”里确认。

## 5. 引用可达性

`citationReach(app, space)`（`GET /api/spaces/:id/citation-reach`）是只读检查：列出这个空间的 Wiki 页面引用的原件里，有哪些是这个空间的某些读者打不开的。

- 读者：所有能读这个空间的启用用户（`can(user, "space.read", space)`，含本人和全局角色带来的权限，仓库空间按上级业务空间的成员算）。
- 打不开：按 `sourceVisible` 判断，不写死个人空间——原件在读者无权的空间（个人空间或别的空间），或原件本身设了仅部分人可见，都算；按飞书文档权限过滤的空间里需要问飞书的单列为“要确认”。
- 合并过的重复原件按旧 id 引用的，换成现在的原件再判断；已删除的原件不在这里报（那是失效引用）。
- 只有本人能读的空间不会报任何问题。
- 提问的人自己读不到的原件不显示标题。

`queueUnreachable`（`POST /api/spaces/:id/citation-reach/recheck`）把其中在本人个人空间、可重判的原件以最高优先级排进重判队列。Wiki 写后核对流程可以直接调用 `citationReach`。

## 6. 移动之后还找得到

`moveSource` 只改原件和索引的空间字段：

- 原件 id、正文、切分和行号不变，`src:<id>`、Wiki 引用、记忆和事项的引用照常打开；
- 全文检索跟着 `chunks.space_id` 走，向量经 `vector_log` 触发器更新到新空间的矩阵；
- `source_locations` 记住原来的采集入口：同一份文档再采集（会议、知识库、群里再贴一次链接）会更新原来那份，不在个人空间里重复建一份；群里再贴一次链接时，一天内读过的不再读（`importLinkedDocs` 现在也认已移走的文档）。

## 7. 大库上不占住服务

第一版在一个真实大小的库上（个人空间约 3000 份、全库原件一万多条加几万条代码、记忆和事项各几千、页面一千多、引用几万、消息几十万行）点“现在检查”后把服务卡死：`collectRecheck` 对几千个候选逐个算指纹，每个都对事项和记忆的 `source_refs` 做 `json_each` 全表展开、按 `json_extract(meta)` 扫整张 `sources` 表找同目录文档，全部在主线程上同步执行；判断时每份原件还对 `lark_messages.content` 做一次 `like '%token%'` 全表扫描。现在：

- **按集合算**：检查先用几条查询建出映射——引用（`page_cites`、事项、记忆按 rowid 每页 1000 行读）、“原件 → 被哪些空间引用”、“目录 → 已在哪些业务空间”（表达式索引 `sources_wiki_parent`）、“知识库 → 目标空间”、上次的指纹，再在内存里给每份留在个人空间的原件算指纹，不再按候选发查询。交给 archivist 的一批原件也一次算旁证（`archiveEvidenceFor`：事项和记忆一批只读一遍，同目录和消息链接都走索引）。
- **不占住主线程**：检查是一个后台任务，每做 30 毫秒同步工作就用 `setImmediate` 让出一次（`yielder`）；同一时间只跑一个（再点“现在检查”或定时任务撞上时不另起）；总时长上限 5 分钟（`SWEEP_MAX_MS`），到了就停，队列和读消息的进度都留着，下次接着。HTTP 接口立即返回。
- **消息里的文档链接**：新表 `lark_doc_links(token, message_id, chat_id)`。采集消息时顺手写入（`storeMessages`），已有消息由每晚检查按 rowid 每批 500 行补（游标在 `kv.lark_doc_links_backfill`，从别的设备拉来的消息 rowid 更大，也会被补上），每次检查最多用总时长的 40%。旁证里的“贴过它的群”只查这张表；补完之前，较早消息里的链接暂时看不到。
- **其他地方**：可达性检查按“读者 × 空间”算一次能不能读，只有自己设了可见范围或按飞书权限过滤的原件才逐人判断，分批读原件并让出；批量指定空间逐份让出；首页清单的查询都有索引（`source_moves_source`、`source_routes_verdict`）且有条数上限；工作文件跟随在到时间上限时停。

规模测试（`test/homing-scale.test.ts`）：3000 份个人空间原件、12000 份其他原件、事项和记忆各 3000、页面 1000、引用 20000、消息 60000。

| | 改前 | 改后 |
| --- | --- | --- |
| 一次检查总用时 | 约 28 秒 | 约 0.75 秒（含补 6 万行消息的链接）；和其他测试并行时 1.1–1.5 秒 |
| 主线程最长一次被占住 | 约 28 秒（整次检查同步） | 约 70 毫秒；并行时 100–250 毫秒 |
| 没有新旁证时再查一次 | 0.5 秒（同步） | 0.2–0.3 秒（分段让出） |
| 一批 40 份原件的旁证 | 约 2 秒 | 约 55–70 毫秒 |

写入按小批提交（排队每 100 条一个事务，交给归档的一次一个事务），磁盘忙时一次提交（尤其碰上 SQLite 的自动检查点）仍可能停顿几百毫秒，这和别处的写入一样，不是检查本身的计算。

测试：`test/homing.test.ts`、`test/homing-agent.test.ts`（真实 ACP + MCP 路径，`FAKE_MODE=archive`）、`test/homing-scale.test.ts`。

## 部署后

迁移只加列、索引和三张表（`archive_recheck`、`archive_evidence`、`lark_doc_links`），不改已有数据。之后：

1. 打开归档规则 → 从个人空间归位，点“现在检查”：第一遍会把已经被业务页面、事项、记忆引用的个人空间原件，以及挂在业务事项上的工作文件处理掉（工作文件直接移，原件每晚 60 份交给 archivist）。
2. 对有协作者的业务空间看“页面引用的原件，读者打不开”，点“送去重新判断”。
3. 自定义过 `archivist` 角色的，合并源码的新说明（`POST /api/roles/archivist/merge`），否则拿不到新写法。
4. 想一次处理历史上留在个人空间的全部材料，用“整理已有材料 → 没命中的交给 AI 判断”（每批 100 份），新的旁证会一起带上。
