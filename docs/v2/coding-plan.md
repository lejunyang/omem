# 编码交办的方案与变更说明（设计，未实现）

状态：设计稿，等本人确认后再实现。相关：[coding-loop.md](coding-loop.md)（修改项与推进）、[coding-work.md](coding-work.md)（交办视图）、[pre-check.md](pre-check.md)（编码前检查）、[review.md](review.md)、[requirements.md](requirements.md)。

## 1. 要解决的问题

- 交办里 AI 自己推进，容易越写越乱：评审提一条、编码补一层，同一处连着修几层，本人回头看到的是一堆补丁。
- 需求点回答的是“做没做”。本人评审时想知道的是“为什么这么改、有没有更简单的做法、会不会影响别处”，现在只能去 VS Code 里看整份 diff 自己推断。
- 需求点、编码前检查、修改项、变更拆分（change points）各有一套列表，互相对不上：69 个修改项一个都没挂需求点（coding-work.md 第 3 节）。

## 2. 一条线：需求点 → 决定 → 改动

不再加第四套列表，而是在需求点和修改项之间放一层**决定**，方案和变更说明是它在编码前、编码后的两个样子：

| | 回答什么 | 谁写 | 什么时候 |
| --- | --- | --- | --- |
| 需求点 | 要做什么 | 本人 / 助手（需求页） | 交办前 |
| **决定** | 怎么做：这块原来有什么问题、选什么做法、不选什么 | 写方案的 Agent | 编码前（大改动）或编码后补（小改动） |
| 修改项 | 一件能单独验证的事 | 编码 Agent | 编码中，每项挂一个决定 |
| 改动 | 这个决定最后落在哪些提交、哪些文件 | 宿主按修改项的提交汇总 | 编码后 |

### 2.1 决定分四种，各写各的内容

一个需求点可以对应几个决定，也可以一个都没有（做法没有可选的余地，直接实现）。决定按它对现有代码做的事分四种，每种要回答的问题不同，所以栏目不同：

| 种类 | 什么时候 | 必须写的栏目 |
| --- | --- | --- |
| **新增** | 加一项原来没有的能力 | 入口（用户或调用方从哪里用到它）；放在哪一层、为什么是这一层；对外的约定（类型、接口字段、表结构、配置项——只写签名和字段，不写函数体）；复用哪些已有机制、有意不复用哪些；按情况的行为表；这次不包含什么 |
| **修改** | 改变已有功能的行为 | 现在的行为和改后的行为，按情况列成对照表；改在哪一处（一处，说明为什么不用改别处）；受影响的调用方；旧数据、旧版本怎么过渡 |
| **删除** | 去掉一项功能或一段代码 | 删掉的清单；谁还在用它（调用方、页面、数据、配置）和“已经没人用”的依据，或者它们迁到哪里；删掉以后原来的入口怎么表现；要一起清理的数据、配置和文档 |
| **重构** | 行为不变，改结构 | 现在的结构问题（位置）；改成什么结构（谁拥有什么）；不变的行为有哪些、靠什么证明没变（已有的测试）；删掉和合并掉的东西 |

四种共有的栏目：

- `title`：一句话，写做法而不是写任务（“权限条件写在路由 meta 上，由一处守卫消费”）。
- `reqs`：对应的需求点；没有需求页的交办写任务原话里的哪一句。
- `rejected`：考虑过但不选的做法，各一句理由。只有一种说得通的做法时不写。
- `question`：需要本人定的，带选项和建议。

### 2.2 写到多细：到“约定”为止，不到“实现”

一句话的栏目只够扫一眼，不够评审；写成伪代码又等于提前写了一遍代码。分界线是：**方案写边界上的东西，不写边界里面的东西。**

写：

- 跨模块、跨进程、跨版本的约定：类型定义、接口的参数和返回字段、表和列、配置项、路由 meta 的字段。这些是代码，但只有签名和字段，一个决定里不超过 30 行。
- 行为表：行是情况（哪种用户、哪种数据、哪个版本组合），列是预期结果。评审最常用的就是它——“这种情况你打算怎么办”一眼能看到，漏掉的情况也一眼能看到。
- 归属：这段逻辑、这份数据归谁管，别处怎么拿到它。
- 删掉什么。

不写：函数体、控制流、变量名、怎么拆文件、测试代码。这些留给编码，评审时看 diff。

卡片有两层：收起时每栏一句话，用来扫一遍有几个决定、哪个要本人定；展开后才是上面这些（约定的代码片段、行为表）。本人只需要展开自己关心的和标了“要你定”的。

整份方案在决定之外还有三段，放在最前面，都很短：

- **影响方案的事实**：调查中发现的、会改变做法的事实（“这批接口已经全部回滚，没有线上调用方，可以重新定义”），每条带依据。评审先看这一段，事实错了后面都不用看。
- **整体的行为表**：跨几个决定的情况（发布顺序、版本组合）。
- **和要求不一致的地方**：做不到或建议换做法的，直接说。

一个真实的样本是这次接手的前端权限重写：方案先列了 4 条事实，再给路由 meta 的类型草案和三个路由的写法、一张新旧宿主和子应用四种组合的行为表、删除清单和 7 个待定问题；本人据此改了其中一个决定，编码照改后的方案做，改完的业务代码比接手时少。

### 2.3 编码后

同一张卡片多出三栏：

- `changes`：落在哪些修改项、哪些提交、哪些文件（宿主汇总，不靠模型写）。
- `deviation`：实际做法和方案不一样的地方和原因：约定变了哪个字段、行为表里哪一格和原来写的不同。没有偏差就是空。
- `simpler`：做完以后看，有没有更简单或可以统一的做法没做；没有就写为什么没有。

小改动不走方案这一步，但编码结束时同样按决定交卷：每个决定写种类、一句做法、行为上的变化（修改类写前后对照，新增类写入口和约定，删除类写删了什么、谁受影响），加上面三栏。通常只有一两个决定。所以“变更说明”对所有交办都有，“方案先行”只对值得的交办有。

## 3. 什么时候先写方案

编码前检查（`business-analyst`，已有）在简报里多答一个问题：这次要不要先定方案，理由一句。满足任一条就要：

- 要改现有的分工或接口（不只是在现有位置加逻辑）；
- 有两种以上说得通的做法，选哪种会影响别的模块；
- 任务原话里要求重构、收敛、统一；
- 本人交办时点名要方案（`delegate_code` 的 `plan: true`），或在设置里对这个仓库设了“总是先写方案”。

不满足就直接编码。本人说“不用方案，直接改”时跳过。

## 4. 谁写、谁确认

- 写方案的是一次单独的运行，可以单独指定 AI（设置 → AI → 任务选型里多一类“写方案”），建议用最强的模型；它只读代码、不改代码，交 `submit_plan`。照方案实现的编码 Agent 可以用便宜的模型。
- 确认默认是本人：整体通过、对某个决定提意见（意见回到同一个会话改一版）、或“换个思路”。设置里可以改成“没有要本人定的问题时由助手确认”。
- 通过后的方案是这次交办的基线：
  - 编码 Agent 拆修改项时每项填它属于哪个决定；做不下去要换做法时用 `report_task` 说明，方案改一版，不能悄悄偏离。
  - 评审负责人拿到决定列表。评审问题要么指向某个决定没做到，要么指向需求点；两者都对不上的归为“方案之外”，默认记成以后再做，由助手决定要不要管。
  - 精简评审（`review-simplify`）对照 `removes` 检查说要删的是不是真删了。

## 5. 在哪里看、怎么看

交办视图（运行页“编码”和需求页共用的 `CodeWork`）的标签改成：

```
[概览] [方案] [评审] [活动] [分支]
```

“方案”合并现在的“需求点”和“变更”两个标签：左边是需求点，右边是挂在它下面的决定。

编码前（等确认）。下面是收起的样子，每栏一句话；点开一个决定才显示它的约定片段和行为表（2.2）：

```
┌ 需求点 ─────────────┐┌ 方案 · 等你确认 · 3 个决定，1 个要你定 ──────────────┐
│ ▸ 退款只算已发货行 ●││ D1 退款金额在订单行上算，页面不再自己合计          │
│ ▸ 部分发货可退运费 ●││    问题  三个页面各算一遍，口径不同 (refund.ts:40 …) │
│ ▸ 导出与页面一致   ●││    做法  computeRefund(lines) 放在 order/refund.ts   │
│                     ││    删掉  RefundPanel、ExportJob 里的两份合计（约 80 行）│
│                     ││    不选  在每个页面各修一遍：以后还会不一致         │
│                     ││    影响  导出任务、对账报表；回归：部分发货的订单   │
│                     ││ D2 运费按已发货行的金额比例退        ⚠ 要你定        │
│                     ││    ○ 按金额比例（建议） ○ 按件数比例                 │
│                     ││ D3 导出走同一个函数                                  │
│                     ││                       [通过] [提意见] [换个思路]     │
└─────────────────────┘└──────────────────────────────────────────────────────┘
```

编码后（同一个位置，卡片展开多了改动）：

```
│ D1 退款金额在订单行上算，页面不再自己合计            ✓ 已完成 · 评审通过 │
│    做法  computeRefund(lines) 放在 order/refund.ts                         │
│    改动  T1 T2 · 3 次提交 · 5 个文件 +64 −118            [看 diff]         │
│    偏差  对账报表没有改：它读的是落库后的金额，不经过这个函数            │
│    更简单的做法  没有：再往下收就要改订单行的存储结构，超出这次的需求    │
│ D2 运费按已发货行的金额比例退                         ● 评审提了 1 个问题 │
```

- 点“看 diff”只看这个决定的改动（按它的修改项的提交取，已有 `task-diff` 接口），顺序是决定的顺序，不是文件名的顺序。
- 没挂到任何决定上的改动单独列在最后一组“方案之外的改动”，这一组不为空本身就是要看的信号。
- 飞书：方案写好时发一张卡片（几个决定、几个要本人定、链接）；要本人定的问题直接在卡片上选。交办结束的汇总按决定列，不按修改项列。
- VS Code 插件：侧栏树是“决定 → 文件”，点文件打开只含该决定改动的 diff；在某处写的评语作为意见发回交办。
- 需求页：需求点下面显示它的决定和状态，取代现在“这次交办挂的需求点”那一栏。

## 6. 数据与改动面（估计）

- 根运行的 `output.plan`：`{ status: draft | approved | revised, decisions: [...], approvedBy, at, revisions }`；修改项的 `origin.decision`。不加新表。
- 新工具：`submit_plan`（只给写方案的运行）、`revise_plan`；`plan_tasks` / `finish_task` 各多一两个字段（`decision`；`deviation`、`simpler`）。
- 复用：编码前检查的简报照旧给编码和评审，方案在它之后；`change_points`（评审时的需求拆分）由决定取代，旧交办按原样显示。
- 界面：`CodeWork` 的方案标签（一个新组件）、飞书卡片一种、VS Code 插件的树。
- 规模：宿主和工具约 500 行，界面约 600 行，角色说明三处（新增写方案的角色，`coder`、`review-lead` 各加几句）。

## 7. 不做的

- 不让宿主判断“这算不算偏离方案”：偏差由编码 Agent 自己报，评审负责人核对。
- 不强制每个交办都写方案；不把方案做成长文档，一个决定超过一屏说明拆得不对。
- 不在这一步解决“禁止的写法”（`void fn()` 之类）：那是按新增行匹配的确定性检查，另见第 8 节。

## 8. 相关的两件小事

- **按新增行的检查**：仓库空间设置里一组“禁止的写法”（正则 + 一句说明），宿主只对这一轮新增的行匹配，命中算检查没过，退回编码 Agent，不占评审轮次。规则内容是各仓库自己的设置数据；本人在对话里纠正某种写法时，助手可以提议加一条，本人确认后生效。
- **精简评审默认带上**（已实现）：改动到 200 行代码而它还没看过，或出现“修过的地方又修”时，这一段评审必须带上 `review-simplify`。

## 9. 待本人定

1. “决定”这一层要不要：它取代“修改项挂需求点”和“变更拆分”，成为本人看交办的主线。
2. 方案默认由谁确认：本人（建议），还是没有待定问题时由助手确认。
3. 小改动的变更说明要不要也发飞书卡片，还是只在交办视图里。
4. 先做哪一块：建议先做编码后的三栏（改动、偏差、更简单的做法）和按决定看 diff，这部分对所有交办都有用；方案确认的流程第二步做。
