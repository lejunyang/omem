# 组网运行：多台 omem 互相调用、数据各归其位、多个助手

状态：第 10 节的五项本人已定（2026-11-14，都按本稿的做法）。已实现的写在各节的“实现”里；没写的还没做。

相关文档：`multi-user.md`（账号、权限、连接器、多服务连接）、`architecture.md` 的“多台设备”、`remote-clients.md`（命令行和 MCP 连远程）。

## 1. 要解决什么

几台 omem 一起运行——本人的几台设备，或几个人各自的服务——希望：

1. 互相知道对方在、对方有哪些助手和 Agent、各自擅长什么。
2. 能问对方的 Agent、查对方共享出来的知识。
3. 自己的 AI 额度不够时借对方的 AI 跑，查的仍是自己这台的空间。
4. 数据各归其位：有的集中放在一台，有的只留在自己这台，要同步的按约定同步，不出现两边各改各的。
5. 一台机器上也能有多个助手：成员各自的机器人和助手，一个人也可以有几个。
6. 运行记录能看出一次运行是谁、从哪里、用哪台的 AI 触发和执行的。

单机多助手是组网的特例：只有一个节点，助手之间的互相感知走同一套“名片”。

## 1.1 怎么连

节点之间只走 HTTP(S)：配对码里是对方的地址（各网卡的 IP 或主机名加端口，添加时挑能连上的，之后断了自动换）和一个令牌。连不到的节点可以经另一台已配对的设备转发（`via`，最多 3 跳），转发的也是 HTTP。本人自己的设备拿本人的令牌，别人的服务拿一个服务账号的令牌。

SSH 不是组网的通道：只有 `omem peer pull <ssh 主机>` 能经 SSH 拉一份快照（对方不用开服务），名片、请教、借 AI、同步、自动备份都要对方的 omem 服务在运行并且 HTTP 能到。只有 SSH 能到的机器，先用 SSH 端口转发把它的 HTTP 端口带过来，再按地址配对。

“设备”（peer）就是组网里的节点：配对是组网的第一步，后面各节是配对之后节点之间能做的事。

## 3. 名片：谁在、有什么、擅长什么

每个节点有一张名片，对每个对端按共享授权裁剪后给出（`GET /api/fed/card`，对端每 10 分钟取一次，取不到标离线）：

```
节点：id、名字、版本、在线时间
人：这台上的用户（名字，不含邮箱）
助手：每个助手一项（见第 7 节）——名字、属于谁、一句话说明、挂的 Agent 档案、能读哪些共享空间、在哪些渠道上（飞书机器人的名字）
Agent 档案：对这个对端开放的档案——名字、说明（档案的 description）、挂的技能名
空间：共享给这个对端的空间——名字、说明、模式（查询 / 同步）、各类内容的数量、最近更新
AI：愿意借出的后端——名字、模型、此刻是否排队、今天还剩多少（只给档位：充足 / 紧张 / 用完）
```

“擅长什么”不由宿主推断，来自三处已有的文字：档案的说明、空间的说明、做梦和复盘沉淀到档案里的经验摘要（`library/_agents/<名>.md` 的 frontmatter）。名片只搬运，不生成。

名片进到两个地方：

- 主助手的常驻说明里多一段“网络里还有谁”（每个对端一两行，助手和 Agent 各一行说明），和现在群里“在场的机器人”那段同一个写法。超过 20 项只列名字，细节用工具查。
- 设置 → 设备，每个对端显示它的名片和最近一次往来。

默认名片只含节点名和在线状态；助手、档案、空间、AI 各自要在共享授权里打开才出现。

**实现（第二期，2026-11-14）**，`src/core/mesh.ts`：

- `GET /api/fed/card`（`nodeCard`）：本人自己的设备（本人令牌）看到全部——助手、所有启用的 Agent 档案、所有空间、本机的 AI 后端；别人的服务（服务账号）只看到授权给它的：共享的空间，`peer_grants` 里 `agent:<档案>` 开放的 Agent、`card:assistants` 打开后的助手、`ai:<后端>`（第四期用）。默认什么都不多给。
- 取名片：`refreshCards` 每十分钟向每个配对的节点取一次（`startMesh`），存在 `kv` 的 `mesh_card:<节点>`；取不到时保留上一张并标“连不上”。
- 常驻说明：本人的、带 `ask_agent` 的运行多一节“网络里的其他 omem”（`meshNote`）：每个节点一行，可以请教的 Agent 和说明、那里的助手、共享的空间。
- 设置 → 设备：最上面“网络里的 omem”列出每张名片，可以“重新问一遍”；每个共享对象下面可以选开放哪些 Agent、每个每天几次、是否让对方看到助手。
- 没做：名片里 AI 的排队和余量档位；档案沉淀的经验摘要进名片（现在只有档案的说明和技能名）。

## 4. 互相调用

三种调用，都落在已有的共享授权上（`peer_shares` 加两种授权对象：`agent:<档案>`、`ai:<后端>`）。

### 4.1 查对方的知识（已有）

远端检索和引用时落地不变。补一点：名片里的空间说明进检索范围的选择提示，助手知道“支付风控的资料在小王那台的 `risk` 空间”。

### 4.2 问对方的 Agent

工具 `ask_agent` 的对象可以写 `<档案>@<节点>`。宿主向对方发 `POST /api/fed/ask { agent, question, context }`：

- 在对方那台上起一个运行（类型 `agent`，身份是这个对端的服务账号，能读的空间 = 共享给它的空间；没有写入、发消息、交办类工具），用对方的 AI 和对方的知识。
- 回答带引用。引用按“引用时落地”取回成本机的镜像原件，所以本机的派生内容仍能回到打得开的原件。
- 两边各有一条运行，互相记着对方的节点和运行 id（第 8 节）。
- 对方可以给每个对端设每天的次数上限；超过时返回“今天的额度用完”，助手照常自己做。

适合：问题属于对方的领域，资料和经验都在对方那边。

**实现（第三期，2026-11-14）**：

- 被问的一方：`POST /api/fed/ask` 起一个运行并立刻返回它的 id，`GET /api/fed/ask/:id` 取结果（回答可能比一次转发请求等得久，所以分两步）。本人自己的设备问的，按主助手或档案照常跑；别人的服务问 `assistant` 时用访客角色——只读共享给它的空间，不带本人的偏好、记忆和技能；问授权过的档案时档案照自己的说明和技能回答。两种都只有只读工具（`peerToolNames({ readOnly })`，去掉再往外查的 `peer_search` / `peer_read`），空间限定在共享给对方的那些。`agent:` 授权上的 `daily` 是每天的次数，超过返回 429。运行的触发方式是“同伴设备”，输入里记着对方的节点、对方的运行 id 和提问的 Agent（`fedAsk`）。
- 提问的一方：`ask_agent` 的 `name` 写 `<档案>@<节点>`（`askPeerAgent`）：发起、每 4 秒看一次、最多等 15 分钟。回答里的 `src:<对方 id>` 逐个落地成本机的镜像原件（`peerRead`，要本机订阅了那个空间），落不了的保留原样并在结果里说明打不开。只有本人的运行能问别的节点。
- 注意：被问的 Agent 能读共享空间里的全部内容，不按共享授权里的内容类型过滤（检索接口是过滤的）；所以开放 Agent 是单独的一项授权。
- 没做：提问一方为这次请教单独记一条运行（现在只在提问运行的工具调用里）；从对方的运行页点回提问的运行。

### 4.3 借对方的 AI

现有的 `peer` 后端推广到别人的服务：对方在共享授权里写 `ai:<后端>` 和每天的上限（运行数或 token），本机把它登记成一个后端 `<后端>@<节点>`，进入换后端的顺序（设置 → AI → 并行），排在本机后端之后。

- 模型在对方那台跑，工具（MCP）在本机：读的是本机的空间，写入也照常走本机的工具和权限。对方看到的是经过它的提示和工具调用内容——这一点在借用前要讲清，授权页上写明。
- 所以只对“别人的服务”多一个开关：`ai.lend.redact`，借给别人时对方不落盘会话内容（只记次数和 token）；借别人的 AI 时，标了“仅本机”的空间（第 5 节）的内容不进这类运行，运行开始前按空间检查，命中就不选这个后端。
- 额度按借出方的上限扣。用完、对方离线或拒绝时，按现有的出错换后端逻辑继续往下换。

适合：自己的额度用完或在排队，事情是自己的。

**实现（第四期，2026-11-14）**：

- 借出方：`/api/peer/acp` 的升级连接原来只认本人令牌；现在服务账号有 `ai:<后端>` 授权且没超过每天次数时也放行（`lendAllowed`，每放行一次连接记一次，计数在 `kv` 的 `mesh_ai:<账号>:<后端>:<日期>`）。名片的 `ai` 只列本机自己的 ACP 后端，带每天上限和今天还剩几次。授权在 设置 → 设备 里每个共享对象下的“可以借用的 AI”。
- 借用方：设置 → 设备 里对方的 Agent 列表在读不到对方设置时（别人的服务）改用名片上的 `ai`；勾选后和本人设备的 Agent 一样成为一个 `peer` 后端，要不要进换后端的顺序在 设置 → AI → 并行 里排。
- 仅本机：空间设置里的“仅本机”（`settings.local`）——不能共享（`setShares` 拒绝）；在这个空间里的运行，换后端的顺序里别人的服务借出的后端被跳过，运行一开始就落在这种后端上时直接报错说明（`runner.ts`，`localOnly` / `lentByOthers`）。对方是不是“别人的服务”看它名片上的 `as`（它怎么看这台）；没拿到过名片的按别人的算。
- 没做：`ai.lend.redact`（借出时不落盘会话内容——后端自己的会话记录宿主管不到）；按 token 计的上限（现在按连接次数）；名片上的排队状态。

### 4.4 和 4.2 的区别

| | 问对方的 Agent | 借对方的 AI |
| --- | --- | --- |
| 模型在哪 | 对方 | 对方 |
| 知识和工具在哪 | 对方（它共享的空间） | 本机 |
| 谁的记忆、偏好、技能 | 对方档案的 | 本机档案的 |
| 结果 | 一段带引用的回答 | 和本机运行一样 |

## 5. 数据放在哪：按空间定

数据的单位是空间，每个空间有一个“放置方式”（`spaces.settings.placement`）：

| 方式 | 含义 | 例子 |
| --- | --- | --- |
| 仅本机 `local` | 不出这台机器：不共享、不同步、不进借来的 AI 的运行 | 个人笔记、和某人的私聊 |
| 主在本机 `home` | 这台是主：唯一写入方；可以共享给对端查询或同步成镜像 | 团队知识库放在常驻那台 |
| 主在别处 `replica` | 本机是只读镜像，内容按变更日志同步过来；在本机写入时转给主 | 笔记本上的团队空间 |

规则：

- **一个空间只有一个主。** 原件、页面、记忆、事项的写入都在主上发生；不做多主合并。
- **在镜像上写**：工具（`remember`、`upsert_item`、`write_page`、保存材料……）发现空间是镜像，就把这次写入原样转给主（`POST /api/fed/write`，以本人或成员在主上的身份、按主上的权限检查），主写完，变更再同步回来。界面上这条写入先显示“等待同步”。
- **主不在线**：写入进本机的发件箱（`fed_outbox`），恢复后按顺序补发；补发被主拒绝（权限变了、对象已删）时通知本人，不丢。发件箱里的内容本机能读到（检索时合并显示，标“未同步”）。
- **换主**：把空间的主从一台移到另一台，是一次显式操作（先同步到最新，再交换角色），不自动发生。
- **哪些永远不同步**：密钥和平台令牌、`仅本机` 的空间、受限原件、一对一私聊（除非本人把它所在的空间设成共享）、会话和运行的正文（见第 8 节，只同步摘要）。

本人的几台设备也按这个走，代替现在的“整库快照、手动拉”：常驻那台是大多数空间的主；笔记本上想只留在本机的东西放 `仅本机` 的空间；其余是镜像，离线时能读，写入进发件箱。整库快照保留，用来搬家和备份。

**实现（第五期的一部分，2026-11-14）**，`src/core/mesh-write.ts`：

- 放置方式是算出来的（`placementOf`）：有 `settings.mirror` 的是镜像，`settings.local` 的是仅本机，其余主在本机。没有另加 `placement` 字段。
- 镜像上的写入转给主：`remember`、`supersede`、`forget`、`save_note`、`write_page` 五个工具，目标空间是镜像时（`callTool` 里，`forwardToHome`）不在本机写，改调主的 `/api/peer/tool`（本人令牌，所以只对本人自己的设备有效；别人的服务的镜像由对方拒绝）。参数里的 `src:<本机 id>`、`mem:<本机 id>` 和 `memory_id` 先换成主上的 id（`peer_aliases` 反查）；引用了主上没有的原件时拒绝并说明。主写完后立刻同步这个订阅，结果以同步回来的那份为准，本机不留第二份。
- 发件箱（表 `fed_outbox`）：主连不上或返回 5xx 时把这次写入（已换成主的 id）存下，工具返回“放进了发件箱”；每次定时同步（`syncAll`）先补发，成功的再同步回来。主明确拒绝（4xx、工具返回错误）的不重试：当场的直接把原因返回给调用方，补发时被拒的标为 `rejected` 并通知本人。`/api/peer/outbox`（列出、立即补发、删除一条），设置 → 设备 里有“发件箱”。
- 同步不带的东西（标注、关注程度、事项）在镜像上照旧写在本机。
- 没做：事项进变更日志并从镜像转给主；发件箱里的内容在本机检索时可见；换主；本人的设备从整库快照换成按空间同步（现在要自己在 设置 → 设备 里关注并同步对方的空间）；别人的服务的镜像写入（要先有“可写”的共享授权）。

### 完整备份和同步的关系

现在有两条把别的设备的数据带到本机的路，目标相同，覆盖面不同：

| | 订阅同步（`federation.ts`） | 拉取（`pull*.ts`） |
| --- | --- | --- |
| 单位 | 空间 | 整个数据目录 |
| 带什么 | 原件、页面、记忆 | 全部业务表、知识库、附件、仓库、运行产物 |
| 方式 | 按变更日志增量 | 每次一份整库快照，合并 |
| id | 本机新分配，记别名 | 不变 |
| 落在哪 | 本机库里的镜像空间 | 任意一个数据目录 |

“把一台设备的全部数据留一份在本机”只有拉取做得到，所以自动备份（`src/core/peer-backup.ts`，`omem peer backup <设备> --to <目录>`）建在拉取上：定时任务每 20 分钟看一眼到期的备份（按间隔 `everyHours`，或每天 `at` 这个时间之后、当天还没成功过），先问对方在不在（直连或经别的设备），在就在子进程里跑同一个 `peer pull --to`，不在下次再看；几天没成功才提醒。它只是调度，没有另一套传输。

拉取本身也不再每次搬整库（2026-11-14，`src/core/pull-snapshot.ts`）：

- **快照按表拷**：精简模式下不再先 `vacuum into` 一份完整副本再删，而是在对活库的一次读事务里把需要的表逐张拷进新文件。检索分块、代码大纲（`chunks`、`symbols`、`code_refs`）和设备自己的表只建空表，全文索引表也空着（合并时本机重建）。十几 GB 的库不再每次在对方磁盘上写一份。完整替换（`--overwrite`）仍用整库副本。
- **只取变过的**：同一个数据目录再次从同一台机器拉取时，带上上次成功那份快照的时间（对方的时钟，留一小时余量，记在目标库 `kv` 的 `pull_since:<机器>`）。快照里 `sources` 只带 `updated_at` 在那之后的，`run_events` 只带 `at` 在那之后的——这两张表是真数据的大头；其余表照旧整张带。没带的原件在 `pull_source_keys` 里留下 id、空间和地址，合并时照样把对方的 id 换成本机的。`omem peer pull --full` 拉完整的；对方是旧版本时参数被忽略，得到的就是完整快照。
- 合并的语义没变：只新增和按更新时间覆盖，不删除；原件的删除靠墓碑。

按空间的同步补齐内容类型（事项、会话、运行、附件）之后，完整备份就是“关注全部空间和全部内容”，这层调度留用，底下从快照换成增量。在那之前两条路并存：要一份完整的、能独立打开的副本用备份；要在本机日常使用对方的某个空间（检索、引用、写入转给主）用订阅。

## 6. 有外部副作用的事：谁来做

采集、定时任务、发消息这类事同一时间只能有一台在做，否则会重复采集、重复提醒。

- **跟着连接走**：平台令牌只在建立连接的那台上（现状）。谁连的飞书谁采集、谁发消息；别的节点要这些数据就订阅它所在的空间。
- **定时任务跟着空间的主走**：整理、做梦、复盘、Wiki 核对只在空间的主上跑；镜像上这些定时不触发。
- **本人的多台设备之间**加一个租约（`fed_leases`：事情、持有节点、到期时间，存在主节点）：采集和提醒由持有租约的节点做，持有者失联超过租期后别的节点可以接手，接手前先同步。默认常驻那台持有，其他设备不抢。
- 借 AI 和问 Agent 不涉及租约：它们没有外部副作用。

## 7. 助手：成员的机器人、一个人多个助手

现在“助手”是隐含的：主机器人 = 本人的主助手；`lark.bots` 里的机器人 = 本人的某个档案。改成显式的一张表 `assistants`：

| 字段 | 含义 |
| --- | --- |
| id、名字、说明 | 说明进名片，是别人了解它擅长什么的依据 |
| 属于谁 `user_id` | 运行以这个人的身份和权限跑，读写他的个人空间、用他的偏好和记忆 |
| 档案 `agent` | 用哪个 Agent 档案（角色说明、技能、默认 AI） |
| 空间 | 默认空间和能去的空间（不超过这个人的权限） |
| 渠道 | 绑定的机器人：飞书应用（一个助手可以没有机器人，只在网页上用） |
| AI | 可以用哪些后端、每天的上限（成员的助手默认受本人给的额度限制） |

- 本人现有的主机器人和 `lark.bots` 迁成属于本人的助手，行为不变。
- **成员的助手**：成员在 设置 → 账号 → 我的助手 里新建，绑定自己的飞书机器人。它以成员的身份运行：读成员能读的空间、成员的个人空间，通知发给成员。本人在成员页能看到每个成员的助手和用量，可以停用。
- **一个人多个助手**：按用途分（值班助手、写作助手），各有自己的档案、空间和会话；在同一个群里时互相知道对方（已有的“在场的机器人”），转交受 `lark.botRelay` 限制。
- **从网页绑定飞书机器人**：现在只能在终端 `omem setup` 里扫码。网页上做同一件事：新建助手 → “用飞书创建机器人”→ 页面显示飞书的扫码链接（应用创建的设备码流程，和终端同一个接口）→ 确认后回填应用、写入密钥库、检查权限和事件订阅（已有的机器人检查），缺的给一键申请链接。已有应用的可以填 App ID 和 Secret 绑定。成员绑定的应用，密钥存在他自己的连接下（`connections`），不进全局配置。
- 助手之间的互相感知，本机内和跨节点都看名片：同一台上的直接读表，别的节点的走第 3 节。

**实现（第一期，2026-11-14）**，`src/agents/assistants.ts`：

- 没有另建 `assistants` 表：助手就是主机器人和 `lark.bots` 里的机器人，归属和说明记在机器人的配置项上（`userId`、`name`、`description`、`dailyRuns`），应用密钥照旧在 `secrets/lark.json`。没有机器人的“助手”就是在网页上用的 Agent 档案，不另记。
- 成员的助手：机器人把“建它的人”（`ownerOpenId`）认成这个成员（`botSender`），所以他的消息以他的身份和权限运行；群里“在场的机器人”那段写明是谁的助手、做什么。
- 每天的次数（`dailyRuns`，只有这台 omem 的主人能设）：按这个机器人的会话里当天的对话轮次数，超过后不起运行，回一句“今天的次数用完了”（`overDailyLimit`，在 `inbox.receive` 里）。
- 接口 `/api/assistants`（列出、新建、扫码新建、修改、移除）：所有登录用户能看到这台上有哪些助手，各自只能管理自己的，主人能管理全部。
- 网页：账号 → 我的助手（新建、改说明和回答者）；设置 → 渠道 → 助手（全部助手，含每天的次数）。新建有两种：“用飞书创建机器人”给出飞书的确认链接（`registerLarkBot`，和 `omem setup` 同一个流程），确认后自动绑定并通知；“已有飞书应用”填 App ID 和 Secret，先向飞书核对再保存。
- 没做：成员绑定的应用密钥单独存在他的连接下（现在和其他机器人一起在本机的密钥文件里）；按助手限定可读空间（现在是成员本人的权限）；移除后要重启机器人才停止回答。

## 8. 运行记录

要能看出一次运行的三件事：怎么来的、谁触发的、在哪跑的。

**已实现（这一版）**：`runs.trigger`（`src/core/run-trigger.ts`）记方式和人——对话、访客提问、有人找你、规则、定时、同伴设备、成员操作；触发人是 omem 用户、飞书上的人或别的机器人；由别的运行引起的沿用上一级的。运行页列表显示触发人，可以按人筛选；详情头部点人名看他触发的全部运行。

**后续**：

- `runs.exec`：在哪跑——本机后端，还是借的 `<后端>@<节点>`；问对方 Agent 的运行记对方的节点和运行 id，点过去打开对方网页上的那条（有权限时）。
- 对方那台上因我而起的运行：触发方式是“同伴设备”，触发人是我在那边的服务账号，带我这边的运行 id。
- 筛选加两项：方式（对话 / 访客 / 有人找你 / 规则 / 定时 / 同伴设备）、助手（哪个助手的会话）。
- 跨节点只同步运行的摘要（标题、状态、触发、用时、token），正文留在跑它的那台。

## 9. 分期

每一期单独可用：

1. **助手表与成员的助手**：`assistants`、迁移现有机器人、成员新建助手、网页绑定飞书机器人、按助手的额度。不依赖组网。
2. **名片**：`/api/fed/card`、常驻说明里的“网络里还有谁”、设置页显示。
3. **问对方的 Agent**：`ask_agent` 的 `@节点`、`/api/fed/ask`、运行互相记录。
4. **借 AI 给别人的服务**：`ai:` 授权、上限、进换后端顺序、`仅本机` 检查。
5. **按空间定主从**：`placement`、镜像上的写入转给主、发件箱、本人设备从整库快照换成按空间同步。
6. **租约**：采集和提醒在本人多台设备间的接管。

1 和 2 最先做：单机多助手马上能用，也是后面几期的前提。5 改动最大，放在调用类功能用顺之后。

进度（2026-11-14）：1、2、3、4 已实现；5 做了镜像上的写入转给主和发件箱（见第 5 节的“实现”），其余未做；6 未做。第 5 期要先定清一件事再动手：镜像上的写入转给主时，参数里的引用（`src:`、`mem:`、事项 id）要从本机的镜像 id 换回主上的 id，主写完同步回来时再换回本机的 id；现在的同步只做了从远端到本机一个方向的换算（`peer_aliases`）。

## 10. 要本人定的

1. **写入规则**：一个空间只有一个主、镜像上的写入转给主（本稿的做法），还是允许两边都写再合并。前者简单、不会冲突，代价是主不在线时写入要等。
2. **借 AI 的同意方式**：持续授权加每天上限（本稿），还是每次借用都要对方点同意。
3. **成员的助手用谁的 AI**：默认用本人配置的后端并受每人上限约束（本稿），还是成员必须自己配 API key。
4. **名片默认给多少**：默认只给节点名和在线状态、其余逐项打开（本稿），还是对本人自己的设备默认全部给出。
5. **成员的助手能不能读团队空间之外的东西**：本稿是“不超过成员本人的权限”；要不要再收紧成“只读助手上勾选的空间”。
