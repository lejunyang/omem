# 代码索引：基线、跟的分支与临时索引

本页说明代码仓库空间的索引从哪里来、什么时候更新、分支和交办的代码怎样叠加，以及回答里怎样标出依据的版本。实现在 `src/sources/code-baseline.ts`（读基线，跑在导入进程里）、`src/sources/code-index.ts`（拉取、判断要不要同步、清理临时索引、版本说明、变更通知）、`src/sources/code-index-http.ts`（接口），分支和交办的叠加索引仍在 `src/agents/worktree-index.ts`。

## 1. 原来的问题

本人问代码问题时，助手用的是之前某次交办分支上的代码。查下来有两条路都会造成这种结果，都成立：

1. **仓库的索引就是目录检出的样子。** 目录同步（`syncDirectorySpace`）读的是 `rootPath` 目录现在的文件：检出的是哪个分支、有没有未提交的改动，索引就是什么。仓库空间的目录有的是 omem 自己克隆的，有的是本人日常开发的目录；交办可以把工作分支检出到仓库目录（`code_branch` 的 `checkout_main`，之后每轮快进过去），本人也会在那里切到功能分支。目录停在功能分支上时同步一次，这个分支的代码就成了“仓库的代码”，检索结果里也看不出来。
2. **不限空间的检索把所有叠加索引都带上。** 交办工作区（`wt-<运行>-<仓库>`）和分支索引（`br-<仓库>-<分支>-<hash>`）是 `kind = 'worktree'` 的空间。`search` / `scan` / `find_symbol` 传 `space: "*"`、或主助手没有空间限制时，检索不带空间条件，所有这些临时空间里的文件都会命中（全文、符号；分支索引还有向量），而且这时“分支版本替代仓库同名文件”的规则不生效，基线和各个分支的同一个文件并排出现，只靠结果上的 `〔空间 wt-…〕` 区分。不传 `space`（当前空间加相关空间）或限定业务空间（带上名下的仓库）时不会带上叠加索引：它们没有 `parent_id`，也不在空间关联里。

另外几件让问题更明显的事：

- 定时任务 `repo-sync` 默认关闭，常驻服务器上从没跑过，有的仓库索引停在三周前；它跑的时候也只是把每个空间重新同步一遍，不拉取远端。
- 交办工作区索引按“每一轮的运行 id”建（`wt-<第 N 轮>-<仓库>`），应用、确认、丢弃、收尾时只删第一轮或被应用那一轮的（`worktreeSpacesOf` 按单个运行 id 找），其余几轮的留下；兜底清理（`sweepWorktreeSpaces`）只在工作区目录不存在时删，而可复用的工作区和工作分支的工作区目录一直在；兜底清理又只在启动和 `repo-sync` 里跑。于是交办结束多日的 `wt-` 空间一直在。
- 评审某个提交时按提交 sha 建的分支索引，`resolveRef(sha)` 永远解析得到，兜底清理永远不删。

## 2. 基线

仓库空间可以设一个**基线**（`settings.codeIndex`）：

| 字段 | 含义 | 默认 |
| --- | --- | --- |
| `mode` | `baseline` 从基线的提交里读；`directory` 读目录现状（原来的做法） | 见下面“迁移” |
| `ref` | 基线：分支、标签或提交 | 空：远端默认分支（`origin/HEAD`，没有时 `origin/main`、`origin/master`、`main`、`master`） |
| `branches` | 跟的工作分支（见第 4 节） | 无 |

按基线索引时，文件从提交里读，不碰工作目录：`git ls-tree -r -l` 列出这个目录（仓库里的子目录也可以，路径相对它）下的文件和 blob id，`git cat-file --batch` 成批读内容（每批 400 个，一个进程），过滤规则和目录同步一样（跳过的目录、锁文件、二进制、超过 1 MB、空间设置的 `exclude`）。已检出的子模块按基线记录的那个提交读；基线没动、但有子模块新检出（或被移除）时也会重读（状态里记了当时哪些子模块可读，`subKey`）。每个原件记下读它时的 blob id（`meta.blob`），blob 没变的文件不再读；基线提交没变时什么都不读。基线里没有了的文件留墓碑（和目录同步一样，只删从这个目录来的原件）。

同步完写 `settings.codeIndexState`：基线的 ref、提交、提交时间和说明、索引时间、上次拉取时间、上次的错误、跟的分支哪些没能建索引。按目录索引的空间也写一份：当时检出的分支、提交、有没有未提交改动、`HEAD` 加 `git status` 的指纹（用来判断要不要再读）。这份状态只由 omem 写，网页保存空间设置时带回来的旧值会被丢掉。

**原件 id 不变。** 原件按“空间 + 路径”定 id，按目录和按基线读出来的是同一个路径，所以切换方式、基线前进时，已有的 `src:` 引用都还指向同一个原件；文件在基线里消失时是墓碑，之后再出现时复活原来的 id。

## 3. 定期更新与拉取

`repo-sync`（每小时）现在做的是 `repoSyncTick`：

1. 按 Git 仓库分组（`git rev-parse --git-common-dir`）：一个大仓库的几个子目录各是一个空间时，只拉取一次。每组先 `git ls-remote --heads origin <这些分支>` 问远端这些空间的基线分支和跟的分支在哪个提交，只有和本地 `origin/x` 不同的才 `git fetch --no-tags origin +refs/heads/x:refs/remotes/origin/x`（一次拉齐），都没动就不 fetch；只在本地有、远端没有的分支（跟的本地分支）不拉，也不会让别的分支拉取失败。不动工作目录、不动本地分支。成功写 `fetchedAt`，失败（没权限、网络）写 `error` 和 `errorAt`，网页上能看到。
2. 每个空间判断要不要同步：按基线的看基线提交和上次索引的是否相同；按目录的看 `HEAD` 和 `git status` 指纹（在后台进程里跑，不占主线程）。要同步才排一个 `sync` 运行（已有排队或进行中的就不排）。
3. 刷新跟的分支和最近查过的分支索引（`indexBranch`，分支和基线都没动就不重读）。
4. 清理过期的临时索引（第 5 节）。

没有变化时的成本是每个仓库一次 `ls-remote`（只列几个分支）和几次 `rev-parse`，按目录的空间多一次 `git status`。所以 `repo-sync` 改为**默认打开**；从没运行过、一直关着的库在启动时打开一次（`adoptRepoSyncDefault`，记在 kv `repo_sync_default_on`，本人之后关掉就不再打开）。

## 4. 工作分支：叠加索引

分支索引（`br-…`）和交办工作区索引（`wt-…`）只含相对基线改过的文件和删掉的文件列表，和仓库一起检索时替代仓库里的同名文件（`shadowedFiles`）。

- **跟的分支**：仓库空间可以登记几条要跟的分支（本人在做的功能分支、预发分支），和基线一起每小时拉取和刷新，问到时直接可查，不会过期。
- **检索默认只看基线**：不传 `branch` 时只查仓库的基线索引。叠加索引只在两种情况下参与：明确指定了分支（`search` / `find_symbol` 的 `branch`、`/api/search?branch=`）；或这次运行属于那次交办或分支评审（运行本身或它的上级是那次交办的某一轮，`runOverlaySpaces`），这时那次交办的工作区索引和仓库一起查并替代同名文件。`search.ts` 的 `withOverlays`：列出了空间时只加允许的、且仓库也在列表里的叠加索引；没有列空间（查全部）时排除其余所有叠加索引（全文、符号、向量结果都排除）。`scan`、`find_symbol` 同样。
- 分支索引和基线比较：仓库按基线索引时，分支索引默认相对基线分叉点（原来是远端默认分支）。仓库是子目录时，分支改动按 `git diff --relative` 取，路径相对这个子目录。

## 5. 过期与清理

| 临时索引 | 什么时候删 |
| --- | --- |
| 交办或分支评审的工作区索引（`wt-…`） | 那次交办应用、确认、丢弃或被后来的交办接替时（每一轮的都删，不只第一轮）；或 14 天没有任何一轮或其下的运行在动 |
| 按提交 sha 建的分支索引 | 3 天没被检索或评审用过 |
| 按分支名建、没登记为“跟的分支”的索引 | 14 天没用过 |
| 跟的分支的索引 | 不过期；分支在仓库里没了时删 |
| 工作区目录被手动删掉、仓库或分支没了 | 随时（原来的兜底清理） |

“用过”是 `indexBranch` 被检索或评审调用时记下的 `usedAt`；定时刷新不算用过。清理在 `repo-sync` 里每小时跑一次，启动时也跑一次，所以部署后第一次启动就会清掉已经过期的。`worktreeSpacesOf` 改为按整次交办（第一轮和所有续轮）找，应用、确认、丢弃、收尾时删掉每一轮的索引。

## 6. 回答时说明依据

`search` 的结果头部、`find_symbol` 的末尾、`read_source` 的头部写“代码来自”：基线的 ref 和提交（`基线 origin/main 的提交 1a2b3c4d（提交于 …，索引于 …）`）、分支索引的分支和提交、交办工作区，或按目录索引时当时检出的分支和提交、有没有未提交改动（并提示不一定是主干）。`roles/_common.md` 要求回答代码问题时说明依据的是哪个分支，问题明显关于某个分支或交办时带 `branch` 查。

## 7. 变更通知

外部系统在仓库有推送时调用：

```
POST /api/code-index/notify
Authorization: Bearer <令牌>            （或 X-Omem-Token: <令牌>，或 ?token=<令牌>）
{"repo": "<仓库地址>", "branch": "<分支>"}  或  {"space": "<空间 id>"}
```

- 令牌在网页 设置 → 空间 → 某个仓库的“代码索引” → “变更通知令牌…”生成（`POST /api/code-index/hook`，本人；只显示一次，再生成旧的就失效；`DELETE` 撤销）。这个令牌只能调用这一个接口，拿它调别的接口是 401。本人自己的凭据也可以调。
- `repo` 按 git remote 比对（https、ssh、`git@host:path` 写法视为同一个），一个仓库对应的所有空间都会处理；`space` 给业务空间时处理它名下的仓库。`branch` 也可以写成 `ref: "refs/heads/x"`。参数也可以放在查询串里，给只能填 URL 的系统用。
- 收到后在后台做一次第 3 节的拉取和刷新（`branch` 是某个已有分支索引的分支时也拉它）。只是触发，不带代码内容；返回 202 和匹配到的空间，没匹配到返回 200 和空列表。
- 各家代码平台的 webhook 格式不同，怎么把它的推送转成上面这个调用（签名校验、取仓库地址和分支）写成数据目录的技能或规则，不进仓库。

## 8. 迁移

- **已有的仓库空间不自动切换**，继续按目录索引，行为和以前一样，只是多记一份状态（当时检出的分支、有没有未提交改动），并且检索结果会标出“按目录索引：当时检出 X”。在 设置 → 空间 → 仓库的“代码索引”里点“按基线分支”即可切换（`PUT /api/spaces/:id/code-index {"mode":"baseline"}`），切换后马上同步一次：和工作目录相同的文件不改，不同的按基线重读，只在工作目录里有的文件变成墓碑。原件 id 不变。
- **新接入的仓库**（还没同步过、有 origin）第一次同步就按基线，并把 `mode: "baseline"` 写进设置。没有 origin 的仓库保持按目录。
- `repo-sync` 从没运行过的库启动时打开一次。

## 9. 默认值

- `repo-sync`：每小时（`0 * * * *`），默认开。
- 基线：远端默认分支。
- sha 分支索引 3 天、分支名索引 14 天、交办工作区索引在交办结束时（或 14 天没动静）。常量在 `code-index.ts` 的 `OVERLAY_DAYS`。

## 10. 没做的

- 已有空间没有自动切到基线；要不要在某个版本统一切换，看本人在常驻服务器上切过几个之后的反馈。
- 按基线索引时，子模块只在仓库里已经检出、而且有基线记录的那个提交时才读；没检出的子模块不在索引里（和按目录一样）。拉取不拉子模块。
- 分支索引仍是“相对分叉点改过的文件”。基线在分叉之后又前进时，分支没改、基线改了的文件显示的是基线的新版本，不是分支上的旧版本。
- 不解析各家代码平台的 webhook 格式；不做签名校验（用令牌）。
- 网页上没有“所有仓库的索引状态”总览页，只在业务空间的仓库列表和仓库自己的设置里显示。
- 没有在常驻服务器上实测：二十来个仓库每小时 `ls-remote` / fetch 的耗时、大仓库第一次切到基线的用时（第一次切换要读一遍全部文件，和第一次目录同步相当）。

## 11. 对检索的影响

改动只决定哪些空间参与检索：没有叠加索引时 SQL 和以前一样。T2Retrieval 子集（17086 篇、400 问，全文路线，`scripts/eval-retrieval.ts`）上，改动前（928d5cc3）和改动后 nDCG@10 都是 69.01，Recall@10 67.47、Recall@50 78.17、MRR@10 79.78，平均每问 57.8 ms 对 59.2 ms（同一台机器先后跑，机器上还有别的任务，差别在噪声内）。有叠加索引时，不限空间的检索多一个 `space_id not in (…)` 条件，列表长度是临时空间的个数。
