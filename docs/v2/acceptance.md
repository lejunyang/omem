## 准备

```powershell
cd E:\Projects\omem
git fetch .\omem-v2.bundle v2:v2   # 已在 v2 分支上时改用：git fetch .\omem-v2.bundle v2; git merge FETCH_HEAD
git switch v2
osdk install && osdk deps --frozen   # 或 pnpm install
pnpm run dev                # 打开 http://localhost:5173
```

设置 → Agent：点 Codex 的“检测模型”，选 gpt-6.1-sol（或 luna）和 low。设置 → 检索：建议 `omem setup embeddings` 开启中文向量（见 evaluation.md，nDCG@10 69 → 87）。

## 已知限制

- 扫描版 PDF 没有 OCR（图片原件由 Agent 看图补文字）。
- 跨文件调用：TS/JS/Vue/Python 按导入，Go/Rust/Java/Kotlin/Swift 按包与模块解析，C/C++/C#/PHP/Ruby/Scala/Dart/Lua/Zig/Elixir/OCaml/ReScript/Solidity/Bash/Elisp 按导入提示 + 唯一同名定义解析；对变量调用方法、动态派发、依赖注入，以及 Haskell/Erlang/Elm 等未接入 tree-sitter 的语言仍是名称级候选。
- 多人只到“留口子”：用户、身份、空间成员、令牌；不做多租户隔离。
- 除 Claude Code、OpenCode 外的 ACP Agent 只验证了握手，登录后的实际表现待你验。
- LongMemEval 跨会话计数题小样本由 1/3 提升到 5/6（见 evaluation.md），样本很小。

## 编码进度故障恢复

仅在应用此补丁并由本人安排服务加载新版本后进行；本补丁的验证只使用临时数据库和假飞书客户端，不发送真实测试消息。

1. 用 `read_run` 读取原交办任一轮，确认最新一轮、`codeChain.awaitingUser / waitReason` 和 `codeProgress`。重启恢复会继续尚有重试预算的投递；对从未建成且创建阶段重试耗尽的卡片，首次启动再给一次有限预算，定期轮询不重复续预算。不修改原会话锚点；正常完成且已投递的卡片不会重复发送。
2. 若 `codeProgress.status=failed` 或重试已耗尽，调用 `retry_code_progress({run_id:"原第三轮运行 ID"})`。它只补建/更新同一链的卡片，不启动编码；再次 `read_run` 核对 `sent` 或脱敏失败原因。创建中断会先查询已存在卡片，避免重复。历史那次 API 错误已被旧代码吞掉，无法追溯，不能由补投结果倒推。
3. 本人已明确继续原交办时，调用 `continue_code_run({run_id:"原第三轮运行 ID",task:"修复第三轮独立评审剩余的两项问题，保持已通过部分并重新检查和评审"})`。应返回第 4 轮：`continueFrom` 是首轮、`resumeSessionId` 是第三轮 coderSessionId；仍在原工作区，不重新交办、不复制原功能任务。queued/running 时重复调用应报具体轮次与状态。
4. 核对同一工作话题卡片显示第 4 轮及最终独立评审摘要；若仍要求修改，自动不排第 5 轮，持久等待本人。发起主助手的原会话中有本轮结果记录，供下次消化；不会自动启动可调用编码工具的主助手绕过三轮上限。

自动回归：`test/lark-code-progress.test.ts` 覆盖创建失败重试、错误脱敏、更新失败重启恢复、缺卡恢复、多轮评审摘要、私聊与已有话题、锚点失效、有限重试与显式恢复、跨 App 租约及创建接受后中断恢复；`test/code-chain.test.ts` 覆盖自动上限、工具手动第 4 轮、原工作区/session 参数及并发去重。真实飞书 API 投递留待应用后的验收，不能把假客户端通过写成真机通过。

收尾异常回归：`test/code-settlement.test.ts` 用临时 SQLite 触发器拒绝交接消息写入，验证真实调度器的成功、失败、取消路径仍保留原终态并发出事件；撤掉故障后可幂等补记。飞书进度回归另覆盖坏历史链不阻断其他链、记账失败不阻断后续事件监听器、最终卡片送达后仍能补记交接、首次启动有限续预算，以及明确撤回或 HTTP 404 后补建卡片。取消时若已产生 approved 评审，仍应展示取消并等待处理，不能误报完成或跳过恢复。权限和限流错误不得清空卡片 ID，也不得补建重复卡片。


## 历史回溯与回读成本（2026-10-21）

- 最近一页全部 ID 已存在，下一页有未采消息：按远端 token 继续；同毫秒的多页消息全部保存，不靠时间减一推进。
- 分页失败、附件失败、缺失/重复 token、缺失 has_more：正文已保存，pending 仍为 true，重启从失败页重试；实际空的最后一页可以完成，oldest 不被伪造为 target。
- 话题根早于授权范围、回复落在范围内：仍发现并逐页保存回复；旧根/嵌套回复不会提前终止话题；仅全部远端分页耗尽后完成。
- 旧纯文本复用消息行，已知 ID 补资源；旧假完成队列保留原目标自动重新核验，正式重排接口不影响其他已排队群。
- 20,000 条无关消息下查询计划仍使用 `lark_messages_chat_cursor` 搜索，不全表扫描，候选每轮最多 20；清理每类标记最多 40 行。
- 卡片资源永久失败：独立任务十次后停止，之后卡片正文编辑仍能保存，不被失败资源永久阻断。

用例：`test/lark-history.test.ts`；仅假 CLI/SDK，不对真实群测试。
