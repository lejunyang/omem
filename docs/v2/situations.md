# 持续跟进的规则：一类会反复发生的事

地方型关注看一个地方，事项型关注跟一件事。有一类事会反复发生，例如项目 A 的例行演练：每次有各自的对象、时间窗口和事项，各次共用本人写的说明和积累的经验。这类事在本人那里就是一条规则，动作是“持续跟进”：每命中一次开一次跟进，处理者在一段时间里自己复查，结束时写小结。说明写发生时在意什么、什么时候需要本人知道，不写成固定步骤。查某个平台的方法放在处理者的技能里。

对本人只有“规则”：规则页列出它（带“持续跟进”标记和开关），在规则页新建、改触发和条件、看各次和经验。内部仍是一条 `kind = situation` 的关注加一条生成的规则，表名、工具名（`save_situation` 等）、接口路径都没有改名。

## 规则与开始条件

持续跟进是 `listen_contexts.kind = situation` 的一条记录，包含所属用户、名字、说明 `note`、一句话描述 `recognize`（可选）、处理者 `spec`、空间和关注设置。没有固定群，也没有自己的处理会话。它对应一条规则：id `situation:<关注 id>`，名字与关注同名（不加前缀），`origin: {kind:"situation", contextId, name, manual?}`。宿主固定动作 `context`，不采纳模型或页面给的动作；触发固定为每个事件判一次、不等待、没有“除非”，事件可用新消息、文档变化、对象状态变化／更新或 omem 内部事件，判断方式沿用规则的三种。规则不占用这条消息的答复权。

开始条件有两种来法：

- **从一句话生成**：保存时复用规则编译器，把 `recognize` 编成触发和条件。规则页“生成条件”也是同一个编译器（`POST /api/rules/draft` 带 `follow`），生成的结果先填进表单，保存后仍算“按那句话生成的”。
- **直接设**：规则页用和其他规则一样的触发、条件、判断控件直接改，或接口直接传 `trigger` / `conditions` / `judge` / `judgeWith`。这样保存的规则记 `origin.manual = true`。

手改过的条件不会被那句话覆盖：之后改 `recognize`（规则页、助手的 `save_situation`、关注接口都一样）只更新描述，返回 `conditionsKept: true`；本人点“重新生成条件”（`regenerate: true`）才按当前这句话重编，并清掉 `manual`。没写那句话时不能选“交给 AI 判断”或“条件 + AI 确认”，因为模型要按这句话判断。

名字、启停、删除两边一致：在规则页改名就是改这条持续跟进的名字；列表的开关就是启用／暂停；在规则页删除会删掉它并结束进行中的各次。只有本人能改，别人的请求返回 403／404。旧版生成的规则名带“情境：”前缀，启动迁移会去掉。

## 每一次的生命周期

- 命中时，没有未到期的那一次就新开；否则决策模型在进行中的各次、新开一次、不相关之间选择，不设决策模型时并到最近一次。模型报错时不猜归属。本人也可从对话或 HTTP 明确开一次。
- 每一次在 `situation_instances` 里，关联带原事件引用的事项和独立 `listen` 会话。同一次串行，不同次可并行。首轮带说明、经验、最近小结与本次信号；先查清这一次的范围，再按情况使用已有 `wake` 排窗口内的复查。异常需要本人知道时用 `notify` 私下说，不回原群。
- 新信号、外来事项进展和相关的本人发言把窗口推到至少从现在起 4 小时；处理者可更新现状、显式延长或交小结结束。复查本身不会自动延长。窗口到了只排一次收尾；没交结果或超时，宿主按最后的现状结束。结束同步收尾事项，保留会话和实例记录。会话原件与经验文件索引留在本人的个人空间，不写进共享空间。暂停只阻止新信号或手工新开，已经开始的继续收尾；删除立即结束进行中的各次。

### 开始时帮你回复

打开“帮你回复”后，每一次的首个信号先跑所选预查，再用[快速通道](first-look.md)看一眼。快模型读说明、一句话描述、触发事件和预查输出；结果与投递去处随首个信号交给处理者。答完、要本人定、超时或出错都照常开始跟进。每天按这条规则的 `perDay` 限制帮你回复的次数（只算真正看了的），超额只跳过快速通道；并入已有那一次的后续信号只跑所选预查，不再帮你回复。群消息可按设置发回触发处（直接发仍须授权）或发独享卡，其他信号和手工开始只私聊本人。后续异常由处理者私下告知，不接着在群里回复。

### 这一次的群

处理阶段默认只私下通知本人。要让每一次的进展发到不同的协作群，在规则的「设置 → 做什么 → 这一次的群里」选「先给我看」或「直接发」，并在说明里写清怎么认出这一次的群、哪些内容发到群里。这个回复档不影响快速通道的第一条。

只有这一次的处理运行能用 `update_situation(chat=群的 chat_id)` 绑定：宿主核对这是群、且本人是成员；无法确认就拒绝。每一次只绑一个群，换绑替换可发送范围，办理运行和群记到事项时间线；已有群原件则挂到事项材料，只有月度归档时挂最近的一份。绑定不发消息，也不改变开始条件。

处理者用 `lark_send` 往绑定的群发，身份始终是 omem 的机器人。「先给我看」先给本人一张确认卡片；换群或改成「不发」后，旧目标的草稿不能发。机器人不在群里时，已配置 `lark_invite` 的处理者可按原有规则把 omem 自己的机器人拉进这一次的群；未配置的处理者不增加邀请权限。`summary` 只结束和记小结；说明要求发小结就由处理者在结束前发送。

绑定不自动监听群里的新消息：其他人的消息仍须命中开始条件、再判定归入这一次，或由处理者主动查阅；本人发言和事项进展仍走原有回流。

## 别的运行怎么知道

1. 同一用户的其他对话轮次和后台运行会看到至多三条“正在进行的跟进”。范围可能相符时，先读事项，确认后记录发现；不要把正在进行误当作已经有人处理。
2. 事项事件和变化写入共用台账；外来变更批量送回实例会话，附作者或来源及运行 id。同一会话的运行自己写的不回流。
3. 宿主从已有会话和飞书采集读本人的话，逐条判断是否与这一次有关，送达时合为一批，按消息 id 去重；没有可用决策模型只送事项已关联的会话和群里的话。不会因一句话开始另一次。这条路径不代替飞书采集，机器人看不到的群仍要等个人采集读到。

## 怎么教

- 本人在规则页新建：“新建规则”里选“持续跟进”，或从工作页右栏、规则页空状态的“新建持续跟进的规则”进入（`#/rules?new=1&follow=1`）。
- 本人给说明：主助手用 `save_situation`，对本人说“持续跟进的规则”和“这一次跟进”。本人明确交代建或改的直接保存；主助手自己提出的先停用，回复后展示启用确认；提议修改已有规则时，确认前保留原版。改说明要列出前后文字。
- 做一遍：本人结束一件不属于持续跟进的事项后，宿主查关联会话和有事项依据的运行，至多取最近 12 次有助手结果且去掉合并重复的本人轮次。至少三轮才安排事项收尾判断；Agent 确认确实是逐步指挥且可复用才提议，不从普通问答提炼。提议进入“需要你处理”和“今天”：可以（保存并启用）、改一改（打开规则页填好的新建表单）、不用（写入取舍记录，不再提同类）。
- 每一次收尾：有小结的实例作为经验案例。跟其他关注一样，累计达到门槛后由 listen-coach 整理，不回写本人的说明。经验文件路径沿用旧的 `关注/情境-<id>/经验.md`（已有数据不搬），页面上不显示路径。

## 规则页

`#/rules?id=situation:<id>`，带 `tab=settings|rounds|lessons|firings`。旧链接 `#/listen/<id>` 跳到这里并保留 `tab`。

- **设置**：用一句话描述（可选，“生成条件”／“重新生成条件”）、什么时候看、满足什么，与其他规则同一套控件；“做什么”固定为持续跟进，下面是说明、处理者、空间、这一次的群里、快速通道。
- **各次**：进行中的（关于什么、何时开始、窗口到几点、现状、事项）和结束了的及小结；可以“手动开始一次”，也可以结束进行中的一次并写一句小结。
- **经验和案例**：listen-coach 整理的经验、“重新整理”和案例。
- **触发记录**：每次命中的事件摘要和结果。长的原文（机器人卡片的整段 JSON、长链接）折到三行，点“展开全部”看。

工作页右栏“持续跟进”只列名字、说明第一句和进行中几次，链接到规则页。

## 默认值

| 项 | 值 |
| --- | --- |
| 没有新活动的窗口 | 4 小时 |
| 最多同时进行 / 每天新开（每条规则，按设置时区） | 3 次 / 12 次 |
| 手动延长 | 从当前时间算，最多 24 小时，不缩短已有窗口 |
| 收尾 | 1 轮，排队与执行共给 2 分钟；否则用最后现状 |
| 送达扫描 | 常驻进程每 15 秒；每一次每批最多 30 条本人发言、30 条事项反馈 |
| 提示和案例 | 其他运行最多 3 条；实例带最近 5 个小结；5 个新案例后可排经验整理 |

## HTTP 接口

以下接口只给系统本人，使用既有认证；`id` 是路径参数。未填的修改字段保持原值。空间不传时新建用 `personal`。`kind` 创建后不变。

| 方法与路径 | 参数 | 返回 |
| --- | --- | --- |
| `GET /api/listen?kind=situation` | `kind` 可选，省略含其他关注 | 关注视图数组；持续跟进含 `kind`, `id`, `userId`, `name`, `note`, `recognize`, `spec`, `spaceId`, `knobs`, `status`, `expiresAt`, `ruleId` 等 |
| `GET /api/listen/:id` | 关注 id | 原有关注详情外壳，`context` 为同一视图；经验在 `playbook`，各次从实例列表读 |
| `POST /api/listen` | `{kind:"situation", name, note, recognize?, trigger?, conditions?, judge?, judgeWith?, spec?, spaceId?, knobs?, status?, expiresAt?}`，不用 `chats`；`recognize` 和开始条件至少给一样 | 新建的视图；默认 `active` |
| `PUT /api/listen/:id` | `{name?, note?, recognize?, trigger?, conditions?, judge?, judgeWith?, fromSentence?, regenerate?, spec?, spaceId?, knobs?, status?, expiresAt?}`；`status` 取 `active` 或 `paused`；`fromSentence` 表示传来的条件是按那句话生成后没改过的；`regenerate` 按当前这句话重编 | 修改后的视图，手改的条件被保留时带 `conditionsKept: true` |
| `DELETE /api/listen/:id` | 关注 id | `{ok:true}` |
| `GET /api/rules` | — | 持续跟进的规则带 `follow: {spaceId, note, spec, status}` |
| `PUT /api/rules/situation:<id>` | 规则页的字段：`name`、`enabled`、`description`（即一句话描述）、`trigger`、`conditions`、`judge`、`judgeWith`；`actions` 等其他字段忽略 | 修改后的规则 |
| `DELETE /api/rules/situation:<id>` | — | `{ok:true}`，同时删掉这条持续跟进 |
| `POST /api/rules/draft` | `{description, current?, follow:"<关注 id>" 或 "new"}` | 按这句话生成的开始条件（动作固定） |
| `POST /api/listen/:id/start` | `{about}`（1–2000 字） | `{instance, runId}`，`runId` 是进入会话的轮次，没排到返回 `null` |
| `GET /api/situation-instances` | `contextId?`、`status?`（`active` 或 `ended`）、`limit?`（1–100，默认 50） | 实例数组，进行中在前，各组内按开始时间倒序 |
| `GET /api/situation-instances/:id` | 实例 id | `{instance, item, events}`；事项不存在时 `item:null` |
| `POST /api/situation-instances/:id/end` | `{summary?}`（最长 3000 字，不传用最后的现状） | 结束后的实例；重复结束不改小结 |

实例对象含 `id, contextId, userId, itemId, conversationId, spaceId, title, status, startedAt, windowUntil, current, summary, endedAt, closingRun, closingDeadline`。时间是 ISO 字符串，尚未有的小结和结束信息为 `null`。无权限 `403`，查不到 `404`，停用或并发改动 `409`，开始条件编译失败或事件类型不能开始跟进 `422`，超过实例上限 `429`。名称、说明、一句话描述上限分别为 80、2000、1000 字。通用的规则存储（`saveRule`）仍拒绝写这条规则，写入只走上面这些入口。

实例另返回 `chatId`，未绑定为 `null`。`knobs.reply` 取 `none`（默认）、`draft` 或 `auto`，可用关注接口保存。主助手用 `save_situation(reply=…)` 提议时卡片列出回复档变化；只有本人本轮明确要求才传 `owner_requested=true` 直接生效。

## 没做的

增量拉取只合并已结束的实例，不从另一设备接续在办的窗口。

不给成员建持续跟进的规则，不提供任意群代发或接具体平台；拒绝过的类别按规范化名字拦截；有决策模型时还与最近 30 条拒绝过的类别做一次语义对照。没设决策模型时靠收尾 Agent 参考拒绝记录，不保证换名也能拦住。没有决策模型时不会把实例范围外的话猜成相关。
