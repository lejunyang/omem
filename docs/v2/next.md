# 整理与下一阶段

2026-11-21 起的一轮整理。到这一天为止，功能是一项一项加进来的：每项单独看都成立，合在一起有堆砌感——本人要认识的概念多、同一件事有几个入口、助手的主动行为各发各的卡。这份文档先说现在的形状，再定三条所有能力都接上去的主干，最后是六个方向各自的分期。每期后面标着状态；做完的移到 `status.md`，这里只留还没做的。

## 现在的形状

盘点时（提交 `11aad422`）数出来的：

- 本人侧栏 13 个固定入口；设置 13 个标签、一百多张卡片，其中“AI”一个标签 21 张，一半和 AI 后端无关。
- 本人没开口时宿主会起运行或发卡片的地方有三十来路（心跳里的七八种检查、十几个夜间任务、规则、关注、有人找你、会议、各条自动续跑的链）。是否起运行、是否记结果、是否推到手机，是三层各自的决定。
- 等本人处理的东西有八类入口：问答里的提问、工具和命令审批、流程关卡和变更合入、工作线的提议和下一步、事项候选、指标 / 技能 / 档案的提议、回复草稿和会议确认、带按钮的通知。工作页右栏收了其中一部分；关注和会议的草稿只在飞书卡片里，指标和档案的提议各回各的页。
- 主助手一轮对话的常驻说明约 3.1 万字符，和这一轮说的事无关的内容照样带（最多 60 条偏好、全局近况、全部技能目录）；没有工具的云端后端收到的是同一份。
- 多 Agent 的机制不少（`run_agent`、`ask_agent`、编码助手并行、多模型评审、流程阶段、设备试验），但各有各的任务记录和进度界面，本人看到的仍是“一个会话一个 Agent”。

共同的原因：能力之间靠两两对接。每加一项，就要和已有的每一项各接一次（规则和关注、事项和流程、指标和工作线……），接不全的地方就各管各的。

## 一、三条主干（助手的主动性与上下文）

不再两两对接。每项能力只和三条主干对接：**关联**（这一轮和哪件事有关）、**变化**（一件事只记一次）、**出口**（要不要现在打扰本人、等本人的东西在哪）。主动性的强弱不在于多发卡片，在于这三件事做得准。

### 关联：这一轮和哪件事有关

现在有三套各自的判断：`run-scope.ts` 找同范围的运行，`items/places.ts` 按链接、编号、人和词猜候选事项，关注和流程各自组装自己的材料。普通问答因此带着全局近况和几十条偏好，明确在说的那条线却没有稳定的现状、阶段和待定变化。

做一个共用的结果 `TurnContext`：会话、群和话题；已确认的事项和它的根工作线；关注、流程阶段；候选事项和匹配理由。判定顺序是显式入口（从线的页面、事项页、流程卡发起）→ 已确认的材料关联（这个会话或群挂在哪件事上）→ 文字候选。候选只用于提示，确认是同一件事之后才用于写入。

它被三处使用：

1. **挑上下文。** 每块有预算。关联明确时带这条线的现状（`items.now`）、当前阶段、待定的变化、最近的依据、同一关注的经验和相近案例、越线的指标；偏好按这一轮相关度取而不是最近 60 条；没有明确的线时才带短的全局近况。选了哪些块、为什么，记在运行里，运行页能看到。
2. **落写入。** 这一轮新建的事项、变化、记忆默认挂到关联的线上，不用模型自己去找上层。
3. **接界面。** `POST /api/ask` 收 `itemId`；“问这条线”不再把事项 id 拼进问题文字。

### 变化：一件事只记一次

同一条群消息现在可能被采集整理、规则、有人找你、关注的批次、只读事项的增量跟进和心跳巡检各看一遍，各自写事项事件、关注里的问题、`item_changes` 或单独的通知。

以 `item_changes` 为唯一的变化台账：盯群、流程跟进、指标、会议、评审、提交认领都按“来源事件或内容版本 + 事项 + 变化类型”幂等写入，带同一个来源引用。谁在处理这件事（规则、关注还是有人找你）记在处理记录上，后来的让开。这样时间线只有一条，助手也知道“这条消息已经提炼成了什么、谁接手了”。

关注里学到的经验同时给同一个群里直接 @ 机器人的那条路径用（现在它只带关注的目的和说明，不带相近案例）。

### 出口：要不要现在打扰，等本人的在哪

免打扰现在只管 `notify()`。`asks` 的飞书发送器、关注草稿、会议卡、流程卡各自直接发：凌晨 02:50 的工作线提议会立刻发出去，而普通通知会等到早上。

两件事：

1. **一个出口。** 所有要送到本人面前的东西先变成一条投递意图：给谁、关于哪件事或哪条线、从哪来、要本人做什么、多急、什么时候之前有效、最早什么时候送、去重键、要更新的原卡。出口按同一套策略决定现在送、并进下一次汇总还是不送，同一个去重键只更新原卡。只有三类不等：到点的提醒、正卡着一个运行的授权、马上失效的链接。
2. **一个待处理清单。** 不合并各域的数据，做一层查询投影 `PendingAction`：种类、标题、关联的线、可执行的动作（调用各域原有的写接口）、截止、处理结果。提问、审批、草稿、关卡、候选、各种提议都投影进来。工作页右栏是它的界面：按线分组、同类合并、能整组处理；飞书上每天一张“等你的”汇总指向它。助手因此能区分“提醒看过了”和“决定已经做了”。

### 节奏：每天一张，每周一份

清点（09:30）、简报（08:45）、下一步卡（10:00）、夜间整理的建议、工作线提议（02:50）、档案复盘的提议、指标提议，都在讲“最近的工作”，各自取数各自发。

收成两个固定的出口：**早上一张“今天”**（各线的下一步、等本人的、夜里各项整理提出的建议和提议、今天到期和自动收尾的），**周五一份周报**。夜间任务不再自己发卡，把提议交给出口，进早上那一张。取数共用一个按人、时间窗、工作线读取的接口。

### 通用：工作之外

工作线的骨架（一件要推进几周的事：现状、下一步、变化、材料、关注、指标）不限于工作。学习目标、调研课题、生活里要跟的事用同一套：类型只决定默认的流程模板和默认关注什么，三条主干不变。学习页和课题台账留着各自的专门界面，但它们的“下一步”和“等你的”进同一个出口。

### 团队

现在工作线只给本人。成员有自己的事项，没有线，也没有自己的待处理清单。第三期配合权限的能力项：成员能看被授权空间里的线，有自己的“等我的”；助手替本人向成员要进展、把成员的回答记成这条线的变化，走的是同一条变化台账。

## 二、多 Agent 协同

已有的：`run_agent`（可开独立工作会话，专门的 Agent 做完后排主助手的协调回合）、`ask_agent`（同步请教，可问别的 omem 节点）、`dispatch_tasks`（编码负责人把互不重叠的修改项分给最多 3 个并行助手，各自 worktree，宿主拣选合并）、多模型评审（按评审项指定 AI、跨模型家族）、流程阶段的 `needs` 并行、课题试验派到别的设备、借另一台设备的 ACP 后端。

缺的是通用的那一层：按同一份计划批量派活、等一组结果、对某一块追问或重派、取消整组；一个在重试和换人之后仍是同一个身份的子任务（目标、验收条件、依赖、产物、验收决定）；以及一张以“整件事”为单位的视图。现在的进度分散在运行页的父子链接、修改项、流程阶段和课题台账里，也没有按任务汇总的用量。

做法：

- **任务板。** 新表 `agent_work_tasks`，挂在已有的工作会话（`agent-work.ts`）下：目标、验收条件、执行者（档案或档位）、状态、历次运行、证据引用、验收决定。工具：批量派发、查状态、对某一项续问或重派、取消。
- **指挥让出槽位。** 强模型拆任务、定交付标准、派出后结束这一回合；必需的子任务都到终态后，宿主只排一次协调回合，由指挥逐项接受、退回或标阻塞，再汇总。这样不会父子争用同一个模型槽，也不会把总时长拉成串行。
- **质量靠验收，不靠多跑。** 每个子任务带验收条件和证据要求；便宜模型交的东西由指挥核对，失败只重做那一项，连续失败按档位升一档（流程里已有升档）。
- **一张协同视图。** 发起的运行和工作会话各有入口：每项任务谁在做、实际用的模型和设备、排队和执行各多久、交了什么、验收了没有；飞书进度卡显示同时在做的几项。
- **别再造一套。** 编码交办的修改项、评审记录、流程阶段、课题台账投影进同一个进度结构，各自的驱动逻辑不动。

## 三、插件

现在插件能加工具、渠道、连接器和平台读取器、外部对象（状态、修订、动作、轮询和回调）、登录方式、界面块和三处插槽、独立页面、带规则和流程的场景包。介入不到的：把外部条目变成事项并回写状态、把评审问题发成外部平台的行内评论、检索的召回和重排、按格式解析和切分原件、Wiki 的页面类型和核对、流程的阶段执行和关卡、命令和工具的审批策略、指标的确定性取数。

钩子分三种，宿主始终负责权限、落库、游标和审计：

- **提供者**：注册一个实现，宿主在明确的业务入口调用，返回类型化的数据。事项、评审平台、指标取数、原件解析、召回和重排、通知出口、阶段执行。
- **事件订阅**：业务提交之后异步投递，带版本、事件 id、实体、操作者、空间；按事件 id 去重、按实体保序、可重试和重放。只读。
- **拦截**：只留给确实要改结果或否决的入口，有固定顺序、每个回调的时限和整条链的预算；增强类的失败时放行，本人启用的强制校验超时则暂停并说明原因；只能收紧，不能放宽宿主的拒绝和审批。

权限在 `plugin.yaml` 里按能力声明（收事件、读内容、写本地、改外部状态分开），授权记录绑定插件版本和范围，新增权限要重新确认。

## 四、沙箱与高危操作拦截

现在有四道各自独立的控制：成员 AI 账号的 Linux 文件沙箱（bubblewrap：独立的 HOME、私有 `/tmp`、PID 和用户命名空间，网络不隔离）、各后端自己的权限模式、PATH 上的命令垫片（命令名加参数正则，放行 / 拒绝 / 审批）、omem 工具的审批。拦不到的：脚本或 CLI 内部发的 HTTP 请求、浏览器里点出来的写请求、额外 MCP 的工具调用、沙箱可写目录之外的本人运行。还查出几处断点：成员发起的编码交办实际以本人身份跑；设备代跑的后端不带垫片和沙箱；命令授权的键里没有 cwd 和规则版本。

做法是一份规则、几个执行点：

- **统一规则** `security.operationRules`：匹配对象分命令（可执行文件、子命令、按位置的参数正则）、HTTP 请求（方法、主机、路径正则、可选的请求体字段）、文件路径（读 / 写 / 删）、工具调用（服务名、工具名、参数）；动作分放行、拒绝、审批、只记录；范围按成员、角色、空间、后端。规则包可以随插件或技能带进来（某个命令行工具的写子命令清单），由本人启用并指定范围。
- **统一授权**：一次批准绑定成员、范围、规则和版本、目标指纹和有效期。三种选择：只这一次、这次运行里的同类操作、以后按这条规则放行（只有本人能存成长期规则）。审批阶梯从“按工具名”收窄到“按规则”。
- **执行点由轻到重**：已有的垫片、ACP 权限请求和工具入口接上规则（能看到什么就按什么匹配，看不到的字段交给该入口的默认策略）→ 补身份和覆盖的断点、加“严格模式”（沙箱不可用就拒绝启动）→ 托管浏览器的请求拦截（先用声明式规则挡固定的域和方法，要按请求体审批的在请求阶段暂停）→ 严格的 Linux 运行强制经本机代理出网（隧道级只能按主机；要看路径的，对少数受管域做解密或让工具走约定的明文接口）。

## 五、成员权限

现在是两层：全局角色（本人、管理员、成员、访客）决定能用哪些功能，空间角色（只读、贡献、编辑、管理）决定能读写哪些空间。“只读”只管检索内容；工作线、规则、关注、抽检、Agent、设置、远程整页对成员不可见；评审的查看和 Git 操作挂在同一个权限上。还查出实打实的缺口：事项的详情和基础的新建、修改没有对象授权；通用的存储文件接口只要求登录。

做成“能力项”：按区域 × 动作（看 / 操作 / 编辑 / 管理）列能力键，例如 `work.view`、`items.edit`、`sources.view`、`rules.view`、`runs.view`、`code.review.view`、`flows.operate`、`remote.view`、`remote.operate`、`settings.members`。角色是能力的预设（本人、协作者、网页只读观察者、访客），每个成员可以在预设上增减，并能限定到空间或单个对象；显式拒绝优先。`routes.ts` 里每条路由声明能力和目标，单件和列表用同一个判定器；`/api/me` 返回有效能力，侧栏、直达路由和按钮用同一份判断，只读时编辑控件不出现。Agent 的工具映射到同一套能力。

远程：AI 启动的浏览器登记成会话（属于哪个运行、哪个空间），本人可以把某个会话的“看”或“操作”授给成员，带有效期，撤权时断开已有连接；只看模式在服务端禁用输入。宿主桌面和复制本机浏览器资料仍是单独的高权限。

## 六、任务提示词

所有后端共用同一套常驻说明，按“角色获准的工具”裁剪，不看后端实际能做什么。没有工具的云端后端因此拿到全部的工具用法、技能目录、档案目录和选型说明；必须调用工具交结果的后台角色被选到它上面时会空跑。`_common.md` 里没有条件的小节混着只对某类工具或某类运行有意义的段落；主助手的角色正文和共同说明占常驻说明的 89%。

- **按能力**：后端声明怎么用到 omem 的工具（MCP / 终端里的 `omem tool` / 没有）、有没有本地工具、在本机还是云端。没有工具的只带角色的核心要求、任务和已经选好的材料。
- **交付契约**：运行声明必须能调用哪些工具；选后端和兜底时一并校验，满足不了的跳过并记原因，都满足不了就明确失败，不推进游标。
- **按场景**：小节的条件除了工具，再加运行类型、是否对话、是否允许写记忆、这一轮有没有带会话感知；只适用于这一轮的操作提示放进当轮消息，不进常驻说明。长的流程性说明移到 `omem_help` 的分组或技能正文里按需读。
- **预算进测试**：角色 × 后端能力的常驻说明各有上限，超了测试失败并报最长的三块；运行记录里记每块的字符数和系统说明这一轮是否真的发了。
- **云端会话收尾**：新建、实际恢复、保留策略用同一个结果；创建期间的取消、恢复失败转新建都要登记清理；重试到上限后保留失败记录和手动重试的入口。

## 先后和依赖

- “关联”是其余几件的前提：挑上下文、写入归属、协同任务挂到哪条线，都读它。
- “出口”和“待处理清单”先于“早上一张今天”、插件的通知出口、沙箱的统一授权卡片。
- 权限的能力项先于成员的线、远程会话授权、插件的权限声明。
- 沙箱的统一规则先于插件带规则包。
- 提示词按能力裁剪独立，随时可做；按场景拆小节在“关联”之后做更省事（那时哪些块是当轮的已经清楚）。
