# 规则：什么情况下自动叫哪个 Agent 做什么

本人用一句话描述“遇到什么情况就做什么”，omem 在消息到来、发现新群或定时巡检时判断是否满足，满足就执行动作（交给某个 Agent、开话题处理、拉机器人进群、优先采集、通知本人）。判断先用确定的条件（便宜、可预期），条件写不出来的部分交给模型判断；模型可以把一句话规则“固化”成条件，本人看得懂、改得动。

## 例子

| 本人的话 | 触发 | 条件 | 动作 |
| --- | --- | --- | --- |
| 群名包含“答疑”或群里有“问答机器人”时，把助手拉进群，等用户提问后交给 support-agent 尝试解决 | 新消息（每个群只触发一次） | 群名包含“答疑” 或 群里的机器人包含“问答机器人” | 拉机器人进群；持续监听：@ 机器人的消息交给 support-agent，回复先给本人看 |
| 报警群里，A 或 B 发报警卡片时，在卡片下开话题让 alert-analyst 分析，需要关注就 @ 值班人 | 新消息 | 群名包含“报警” 且 发送人是 A、B 之一 且 消息是卡片 | 交给 alert-analyst：从这条消息开话题，可以直接回复（结论和 @ 值班人写在话题里） |
| 值班群里我被 @，立刻把机器人拉进群，并优先采集 | 新消息（每个群只触发一次） | 群名包含“值班” 且 @ 了本人 | 拉机器人进群；优先采集这个群 |
| 有人在任何群里提到“合同到期” | 新消息 | 消息包含“合同到期” | 通知本人 |
| 每天早上看一眼发布群，有没有失败的发布 | 定时（cron） | （无，交给模型） | 交给 release-checker，结论通知本人 |
| 《差旅报销制度》有人改了标准、在里面 @ 我，半小时后提醒我看看 | 文档变化（列出这篇的链接） | @ 了本人 | 延时 30 分钟；通知本人 |
| 需求排期表里有人把状态改成“已上线”，跑一下发布检查脚本，执行前让改的人的负责人批准 | 文档变化（多维表格） | 变化类型是 record 且 变化内容包含“已上线” | 执行脚本（审批人由 AI 按说明找） |

## 模型

一条规则（表 `rules`）：

- `description`：本人的原话，规则的依据。条件和动作都可以重新从它生成。
- `trigger`：`message`（新消息，含卡片）、`chat-new`（第一次看到的群）、`schedule`（cron）、`meeting`（本人加入飞书视频会议，见下文“会议规则”）、`doc`（飞书文档、电子表格、多维表格有变化，见下文“文档变化规则”；`trigger.docs` 列出要盯的文档链接）。`once: "event" | "chat"`：每条消息都可能触发，或每个群只触发一次（拉机器人、开始监听这类）。
- `conditions`：确定的条件（JSON，见下），可以为空。
- `judge`：`code`（只看条件）、`ai`（只交给模型）、`code+ai`（条件先筛，命中的再请模型确认）。条件为空时只能是 `ai`。
- `judgeWith`：模型判断（含“模型判断”这一步）用哪个：`decision`（默认，有决策模型时用它，只给是 / 否和概率）或 `general`（通用模型，写理由）。见 [ai-models.md](ai-models.md)。
- `actions`：按顺序执行。
- `enabled`：助理替本人建的规则默认不启用；会话中保存后，在回复之后展示启用确认卡片，点击立即启用，也可在规则页启用。

### 条件

```json
{ "all": [
  { "field": "chat.name", "op": "contains", "value": "报警" },
  { "any": [ { "field": "sender.name", "op": "in", "value": ["小王", "小李"] }, { "field": "sender.email", "op": "endsWith", "value": "@example.com" } ] },
  { "field": "message.type", "op": "equals", "value": "interactive" }
] }
```

字段：`chat.id`、`chat.name`、`chat.kind`（group / p2p）、`chat.bots`（群里的机器人名字，第一次用到时用本人的 lark-cli 读成员，缓存一天）、`chat.hasOwnBot`（群里有没有 omem 自己的机器人，按 `lark.appId` 比对成员的应用 id，不看名字；机器人收到的消息直接算有；读不到成员时视为未知，is true / is false 都不成立）、`sender.name`、`sender.email`、`sender.kind`（owner / user / bot）、`message.text`、`message.type`（text / post / interactive（卡片）/ image / file…）、`message.mentionsOwner`、`message.mentionsBot`、`message.inTopic`、`message.cardTitle`。运算：`equals`、`contains`、`startsWith`、`endsWith`、`matches`（正则）、`in`（列表）、`is`（布尔）、`gte` / `lte`（比数字，用于在会人数和会邀人数）。组合：`all`、`any`、`not`。会议规则只用会议字段：`meeting.title`、`meeting.no`、`meeting.participants`（名字列表，`contains` / `in` 判断某人在不在）、`meeting.participantCount`、`meeting.host`。文档变化规则只用文档和变化的字段：`doc.title`、`doc.type`（docx / sheet / bitable）、`doc.url`、`doc.location`（知识库和目录）、`doc.space`、`change.kind`（edit / comment / record / field）、`change.text`、`change.added`、`change.sheet` / `change.row`（电子表格的工作表名和行号）、`change.recordId` / `change.tableId`（多维表格记录）、`change.action`（added / edited / deleted）、`change.editor`、`change.editorEmail`、`change.editorId`（修改人在机器人这边的 open_id，可用于 @）、`change.byOwner`（修改人只有本人；不知道修改人时不成立）、`change.mentions`、`change.mentionsOwner`、`change.mentionsBot`。

`chat.id` 的值写 `current`（`in` 列表里也行）表示“这个群”：助理在飞书会话里用 `save_rule` 保存时换成这个会话的群 id，不在飞书会话里保存会被拒绝。

“固化成代码”就是这份 JSON：宿主直接求值，不执行模型写的程序。模型从规则原话生成条件，本人在页面上看到的是一句句“群名包含 报警”，可以直接改；生成后先在最近的消息上试一遍，看命中了哪些。

### 判断

1. 触发类型和范围不对的直接跳过。
2. `code`：条件求值。`ai`：把规则原话和这条事件（群、发送人、消息正文的前一千字）交给一次模型调用（无工具），回答是否满足和一句理由。`code+ai`：条件先筛，命中的再问模型。
3. 只交给模型的消息规则，每条规则每小时最多问 60 次，超出的跳过并记录；这类规则建议先固化出群名之类的条件缩小范围。
4. 每条事件对每条规则只处理一次（机器人实时事件和本人采集都会看到同一条消息，按规则 + 消息 id 去重；`once: chat` 按规则 + 群去重）。

### 动作

- `agent`：交给某个 Agent 档案。没写 `ai` 时用档案自己的 AI，开始前按 `agents.routing.choose.rules` 自动选（architecture.md 的“运行前自动选 AI”），额度用完或后端出故障时换兜底；写了 `ai` 就只用它。`ownTopic` 在触发消息下处理（机器人要在群里）：不再先发一张“规则触发、交给某某”的卡片，Agent 的思考气泡或回答以话题回复的方式发在那条消息下，话题由它开出。`reply`：`none`（只把结论发给本人）、`draft`（它要在群里说的话先变成给本人的确认卡片）、`auto`（可以直接在这个群 / 话题里回复和 @ 人，思考气泡可见）、`silent`（静默排查，见下）。它只能往这个群发，不能发到别处。`allowUrgent` / `allowPrivate`（默认关，规则页“允许加急”“允许只给部分人看”）：它在群里发的消息可以对指定的人加急、可以只给群里某几个人看；什么情况用、对谁用写在规则说明或任务里，任务末尾会提醒它只在写到的情况用。本人说“某种情况加急某人”“只发给某人看”时，草稿生成会勾上对应的项。`ai`（规则页“指定 AI”）：这条规则交出去的运行用哪个后端、模型和思考强度，保存时按后端最近一次检测核对；不写就用档案自己的设置。规则和定时任务这类宿主自己开的运行不经过任务选型（只有会交办的运行看得到本人的选型偏好），所以要给某条规则定模型就写在这里，写在任务说明里不会生效；草稿生成在本人点名模型时填它。`fullAccess`（规则页“完全访问”，默认关）：这条规则的运行不进后端的沙箱、不经审批（ACP 的 `full-access` 模式：codex `agent-full-access`、Claude `bypassPermissions`、traex `bypass_permissions`；codex-cli / claude-cli 用对应参数；没有的后端照旧并在运行里说明），用于要联网跑命令行的排查——只读沙箱下每条这样的命令都要审批，codex-acp 偶尔把审批压几分钟。omem 工具照旧逐次检查。只有本人在规则页能打开；Agent 用 `save_rule` 打开会被拒绝，它改规则时漏写这一项则保留原值。交给别的档案（`run_agent`）和唤醒续轮沿用它；规则里的运行只看规则的开关，不看档案或主助手角色上的开关。

### 延时、模型判断、执行脚本

动作按顺序执行，这三种决定后面的动作怎么做：

- `delay`（`minutes`，1 分钟到 7 天）：后面的动作过这么久再做。宿主开一个带 `not_before` 的 `rule-fire` 运行，带上触发的事件和**当时**后面的动作，到时按它们执行（规则停用或删除就不做），触发记录里另记一条“延时到了”。延时不能是最后一个动作。和触发上的“命中后等几分钟”不同：那个是等讨论有没有人回应，这个只是推迟。
- `check`（`question`）：模型看事件、讨论和前面动作的结果，回答这个问题“是”或“否”（一次无工具的调用，不确定按否）；否就不做后面的动作，判断写进触发记录。条件写不清的中途判断用它，比如“这次改动是否涉及上线时间”。不能是最后一个动作。
- `script`（`runtime`: node / python / bash，`code`，`timeoutSec` 默认 60，`approval`）：在运行 omem 的机器上执行本人写的脚本，是一个 `rule-script` 运行（运行页能看到输出）。
  - 事件以 JSON 交给脚本：环境变量 `OMEM_EVENT` 和标准输入，不拼进代码。脚本在数据目录 `rules/scripts/<运行>` 里执行，跑完删掉；环境只带 PATH、HOME、语言、临时目录这些，拿不到 omem 的密钥和令牌。输出（各留最后两万字）和退出码记在运行里；失败或超时通知本人。
  - `approval.by`：`owner`（默认，本人批准）、`person`（`person` 写邮箱、飞书名字或 user_id）、`ai`（模型按 `hint` 从这次的事件里找审批人，比如“改这篇文档的人”；找不到由本人批准）、`none`（不批准直接执行）。要批准时，主机器人私聊审批人一张卡片（规则、触发的事件、脚本的前 30 行），运行排着但不开始；点“执行”才开始，点“不执行”取消。只有审批人能点；三天内没人处理就作废。运行开始前再核对一次是否批准，所以重启或卡片过期都不会让它没批准就执行。
  - 只有本人能保存带脚本的规则（网页或接口，`saveRule` 的 `actor` 是本人）：脚本在这台机器上执行。助理的 `save_rule`、管理员和 Agent 设的临时规则都不能写脚本，模型从原话生成规则时也不生成脚本。
  - 这条和“宿主不执行模型写的程序”不冲突：条件仍是宿主求值的 JSON，脚本是本人自己写、自己保存的。

### 文档变化规则

“《差旅报销制度》有人改了、在里面 @ 我时提醒我”：触发 `doc`，`trigger.docs` 写这篇的链接，条件 `change.mentionsOwner is true`，动作通知本人。实现在 `src/channels/lark-doc-events.ts`。

- **订阅**：机器人用自己的应用身份订阅一篇文档（`POST /open-apis/drive/v1/files/:token/subscribe?file_type=…`），知识库页面先换成它下面的文档（`wiki_nodes` 或读一次节点）。订阅结果存在 `lark_doc_subscriptions`。规则保存后的权限检查会订阅列出的文档，同时为 omem 没采集过的文档存一份当前的文字（`snapshot`），第一次改动就能说出改了什么。
- **事件**：`drive.file.edit_v1`（编辑，只说谁改了）、`drive.file.bitable_record_changed_v1`（多维表格记录，带前后值）、`drive.file.bitable_field_changed_v1`（字段）、`drive.notice.comment_add_v1`（评论或回复，机器人被 @ 或被回复时收到，不用订阅）。机器人的应用要在“事件与回调”里订阅这几个，长连接接收。
- **一次改动**：连续编辑合成一次，停下一分半钟（最多十分钟）后处理。采集过的文档按平常的导入重新读一遍并交给整理，和读之前的文字逐行比较；只有规则盯着的文档用 `snapshot` 比较。变化内容写“新增 / 删掉”的行，修改人按机器人看到的 open_id 认（omem 用户、见过的人，或通讯录）。新增的行里的 @（lark-cli 写成 `<mention-user …>`）算 `change.mentions`，是本人或机器人时 `mentionsOwner` / `mentionsBot` 为真。
- **电子表格按行**：编辑事件只说有人改了。订阅时（规则保存后的检查）用本人的 lark-cli 只读读一遍各工作表（`sheets/v3/…/sheets/query` 列工作表，`sheets +csv-get` 读内容，和读文档同一身份），每行写成“列名：值；…”（表头是第 1 行，空单元格省略，空行保留位置），存进订阅的 `snapshot`（JSON）。之后每次改动重新读、逐行比较（同文档的 `lineDiff`），每个新增或改动的行一个事件：`change.text`（“新增 / 改动「工作表」第 N 行：…”）、`change.added`（这一行）、`change.sheet`、`change.row`、`change.action`（这一行原来有别的内容、且那内容已不在表里算 edited，否则 added）。事件键 `doc:<token>:<工作表 id>:<行内容的哈希>`：同样内容的行只触发一次。第一次没有存过的只存不触发；表头变了的工作表重新存、这次不触发；没有任何行变化（只改格式）不触发。每个工作表最多比对前 2000 行、总共约 40 万字，超出的在事件里注明。修改人用这一批事件的操作人。
- **多维表格按记录**：记录事件按记录拆开，每条一个事件（`change.recordId`、`change.tableId`、`change.action`，`change.editor` 是这条记录的修改人），键 `doc:<token>:<表>:<记录>:<动作>`，修改再带上修订号（没有就用这一批的时间），所以同一条记录新增只触发一次、之后每次修改都能再触发。字段 id 换成字段名：第一次用到某张表时以机器人身份读一次它的字段（缓存一小时，字段变化事件来时作废），读不到就保留 id；文本、数字、单选多选（选项名）、人员、日期、链接、附件写成可读的文字，其余保留截短的 JSON。
- **规则自己的回写**：规则触发的运行用 `lark_write` 写成功后，宿主记下它写了哪个文档（和命令、输出里出现的记录 id），存 kv `rule_own_writes:<token>`，五分钟内这篇的改动若只由本人做出（`change.byOwner`），就不再触发**这条**规则（触发记录里写“由规则自己的回写引起，已跳过”，不计命中）；别的规则照常。和条件 `change.byOwner is false` 互补：后者把本人的所有改动都排除掉。
- **只发给管理者**：飞书只把编辑和多维表格的变化发给文档的管理者。机器人不是管理者时订阅被拒（1069603），权限检查列出“在文档右上角「…」→「添加文档应用」把机器人加进来并给可管理权限”。
- **订阅不了时定时查**（`pollRuleDocs`，每分钟看一次哪些到期）：启用的规则列出的文档里，订阅被拒的、或一个月里没收到过任何文档事件时的全部，每 `trigger.pollMinutes`（默认 30，5 到 1440）分钟用本人的 lark-cli 登录只读查一次最后修改时间（`drive metas batch_query`，和每天的文档检查同一个接口），第一次只记下时间；之后改过就和事件一样处理：采集过的重新导入并逐行比较，只被规则盯着的和 `snapshot` 比较（规则保存后的检查不管订阅成没成都会存一份），变化内容末尾注明“定时检查发现的改动”。修改人是本人 lark-cli 应用里的 open_id，采集里见过的才有名字。电子表格同样逐行比较（修改人是本人 lark-cli 应用里的 id，用来判断 change.byOwner）；多维表格查到改动时只知道改了。
- **代替定时检查**：每天检查飞书文档更新前，机器人先为一批（50 篇）已采集的文档订阅，没试过的优先，被拒的三天后再试；刚把机器人加为管理者的，用远程命令 `lark-doc-subscribe`（`link` 订阅一篇，`retryFailed` 重试被拒的）或建一条列出它的文档变化规则，马上订阅。订阅成功、且最近一个月收到过文档事件（说明应用确实订阅了这些事件）的文档，定时检查不再看它，改动时由事件触发重新读。
- **动作**：没有触发的群，只能交给 Agent、通知本人、延时、模型判断、执行脚本；不能等待回应或按讨论跳过。交给 Agent 时和定时规则一样，可以在规则上选“发到”一个会话（`conversationId`），`reply` 为 auto / draft 时它只能往那个群发（机器人身份，不开话题、不静默排查）；没选就只能“只告诉我”。它可以先读这个群的聊天记录找到对应的消息，用 `lark_send` 的 `reply_to`（`in_thread`）回在下面，`mentions` 填 `change.editorId` @ 修改人；没有指定执行空间时，它在“发到”的群所在的空间里查资料。不列文档时规则看机器人订阅了的所有文档（每天订阅的一批和其他规则列出的）。
- **权限**：应用身份 `docs:event:subscribe`、`docs:event.document_edited:read`、`docs:document.comment:read`、`base:record:read`、`base:field:read`、`drive:drive.metadata:readonly`（订阅接口还要求用户身份也开通 `docs:event:subscribe`）。设置 → 渠道 → 机器人权限与事件检查里有一行“文档变化规则”，扫码更新应用时一并申请。
- **改动和整理**：采集过的文档被重新读以后照常交给整理（一次 AI 运行），和每天的检查一样；只要读到最新内容、不要整理的，把这篇的关注程度设为“仅检索”（`scheduleIngest` 跳过仅检索和忽略的原件），或关掉空间的自动整理。规则本身只按它的动作做事，不带额外的 AI 运行。
- **还没有的**：别人在评论里只 @ 本人（没有 @ 机器人）时，事件发给本人的身份而不是机器人，omem 现在收不到；要收得以本人身份订阅用户云文档事件，不在本期。

### 处理中再次触发：并入同一会话

交给 Agent 的动作默认开启“处理中再次触发时并入同一会话”（`merge`）。同规则、同群的运行共用串行队列。开启后可选：

- **合并回复**（`mergeReply: "combined"`，默认）：新触发合并到排队中的运行；当前轮下一次调用工具时拿走这些触发，继续调查，原因相同的可以一起下结论。若当前轮先结束，排队运行续用它的 Agent 会话，带上后续触发的摘要。
- **每次触发分别回复**（`mergeReply: "separate"`）：每次触发各排一轮，依次续用前一轮的 Agent 会话。当前轮不会拿走或取消后面的触发。每轮保留本次完整事件、任务要求和回复位置，分别完成任务中的操作、核对状态并答复；前面的调查可以复用，同因不能代替逐条处理。直接回复时，回答回复本次消息；草稿、只告诉我和静默排查仍沿用各自的投递方式。

关掉 `merge` 时，每次触发使用独立运行和会话，可以并行。`mergeReply` 不生效。各群仍相互独立，权限、执行空间和 AI 按原规则限定；前一轮失败或执行设置不兼容时，新一轮使用新 Agent 会话处理本次完整任务。

### 等待与跳过：别人在处理时不插手

“我被 @ 就交给 Agent”的规则在本人已经接手、正和别人讨论时也会命中——对方在讨论里 @ 本人是常态。条件只看这一条消息，看不出来；所以触发时再看一眼它所在的讨论：

- `trigger.waitMinutes`：命中后等几分钟再动手（“10 分钟没人理再处理”）。等待是一个 `rule-fire` 运行（`not_before`），时间到了再做下面的检查。
- `trigger.unless`：动手前跳过的情况。`owner-engaged`：本人在这个话题里说过话，或在群里触发前半小时以来说过话。`answered`：话题里触发之后有发送人以外的人（非机器人）说话；不在话题里时，有人回复了这条消息。跳过的记在触发记录里（不计命中次数）。
- 讨论来自已存的消息（机器人实时收到的、本人采集的）加一次本人 lark-cli 的只读列表（话题全部，或群里前后半小时），`src/rules/context.ts`。
- 设了等待或跳过的规则，模型判断（`code+ai`、`ai`）也放到动手时做，并且带上这段讨论：本人已在讨论、对方只是 @ 本人时通常判为不处理。

### 有人直接 @ 机器人时规则让开

规则管的是没人找机器人的消息。一个人（不是机器人）@ 了 omem 机器人，而机器人会直接回答他（本人、登记的用户，或开了访客提问时任何人），这条消息就记为“已被直接回答”（`rule_handled` 里的 `@bot`），所有规则——包括等待、静默排查和对 Agent 跟进话题的接续——都跳过它，不管它后来从机器人还是本人采集送到规则。别的机器人 @ omem 机器人时照常交给规则；没有规则接手，再由访客模式的把关角色判断它说的事要不要处理。

### 和“有人找你”的先后

有人 @ 本人或私聊本人的消息，先经过规则，没被规则认领的才交给“有人找你”（[mentions.md](mentions.md)）：

```
消息到达 → 规则判断（命中就执行动作）
         → 没被认领 → 等 delayMinutes → 等同一批行的 ingest → 分诊 → 处理
```

- 认领：规则在这条消息上触发过（任何动作，跳过也算；`once: chat` 的规则按这条消息之后对这个群的触发），或认领后正在等（`rule-fire` 运行排着或在跑）。条件不符、模型判断为否不算。判断依据是 `rule_firings`、`rule_handled` 和 `runs`（`ruleClaim`）。
- 规则还在判断（模型调用没回来）时，“有人找你”等一分钟再看，最多和等 ingest 合计 8 次；所以同一条消息不会既被规则的模型判断、又被分诊判断后各处理一次。
- 规则页列表最后一条“没有规则处理的、找你的消息 → 有人找你”是它的入口（不能删除，开关在设置 → 渠道），不是规则引擎里的规则。

没有把它做成一条内置规则：它要按分诊结果分三路（不用管 / 简短提醒 / 先查）、先查时选处理者、受每天次数限制、同一人接着说时并进已有的处理、失败时发简短提醒，规则的“条件 → 一串动作”表达不了这些分叉。要对某类群另作处理，写规则即可，“有人找你”自动让开。

### 静默排查（`reply: "silent"`）

适合值班群：Agent 读讨论、查资料，群里什么都看不到，它自己决定要不要说话。

- 不开话题、不发思考气泡、最后的文字不自动发出（留在运行记录里）。
- 任务里附上正在进行的讨论（→ 标出触发的那条），说明怎么做：本人已在跟进、别人已回答或不需要处理就什么都不发；有结论或可行的排查思路时用 `lark_send` 在触发消息的话题里回复（`reply_to` + `in_thread`）；缺关键信息就在话题里问；需要本人决定的用 `notify` 告诉本人，不在群里 @ 本人。
- 它在某个话题里发过言，就跟进这个话题 24 小时：话题里的新消息不再走规则条件，一分钟后交回同一个 Agent（接着它的 Agent 会话，同一话题一次只排一个）；本人在话题里说话就不再跟进。
- 定时规则不能用等待、跳过和静默排查（没有具体的讨论）。

### 例：值班群被 @ 时先留住记录

值班群关单后本人可能被移出，lark-cli 就读不到了。“被 @ 就先保存、把机器人拉进去”用一条规则：条件 `message.mentionsOwner is true`（再加群名或 `chat.bots contains` 值班机器人缩小范围），`trigger.once = chat`，动作“优先采集”+“拉机器人进群”。机器人进群后实时收到的消息照常存进群原件，本人离群也不影响。

要确认“这真是某个工单的群”、查工单状态，写成值班技能（里面用内部命令行），挂在处理这类群的 Agent 档案上，再加一个“交给 Agent”动作让它去查。内部系统只出现在技能里，不进 omem 的代码和配置（AGENTS.md）。
- `watch`：开始监听这个群，后续消息交给某个 Agent（同 `/watch`：全部 / @ / 关键词，回复方式同上）。
- `invite-bot`：以本人身份把 omem 自己的机器人加进这个群（lark-cli `im chat.members create`，只加 omem 的 app_id，不发消息、不加别的成员）。只在本人配置的规则里发生。
- `wait-message`：等另一个会话的新消息（`chatId`、`minutes` 1–30、`contains` / `matches`、`onTimeout: notify | none`），只用于新消息触发。执行到它时排一个 `rule-fire` 运行（输入带 `wait`、`since` = 触发时间、后面的动作），`rules/fast.ts` 的 `waitThenAct` 每 10 秒用本人身份 `+chat-messages-list` 读那个会话，触发之后第一条非本人、符合条件的消息作为事件的 `awaited`，接着做后面的动作；到时没有就按 `onTimeout` 通知本人或不做。
- `forward`：把触发的消息（带来源会话、发送人、时间和本人的附言 `note`）用机器人发到 `to` 指定的会话，只用于“新消息”触发。`to.kind=group`：先查群里的机器人（`chatBots`），没有 omem 的机器人就以本人身份拉进去（同 `invite-bot`）。`to.kind=p2p`（某人和本人的私聊，机器人不能在里面发言）：第一次转发时以本人身份建一个本人、对方和机器人的群（lark-cli `im +chat-create --as user`，同私聊指令 `/ai拉群`；对方取这个私聊里采集到的最近一条非本人、非机器人消息的发送人），群 id 记在 kv `rule_forward_group:<私聊 id>`，之后都发到这个群。同一条消息重复触发只发一次（发送的 uuid 由规则、消息和目标算出）。来源可以是群，也可以是任何私聊——机器人私聊本人的消息同样会被采集并触发规则（`chat.kind=p2p`、`sender.kind=bot`），延迟是一次采集的间隔。前面有 `wait-message` 时转发的是等到的那条（`awaited`）。`to.kind=origin`：回到触发的会话，群里以机器人回复在触发消息下（没有机器人先以本人身份拉进去），私聊则对触发消息的发送人建群（同上，按那个私聊记住）；只能用在 `wait-message` 之后。目标由本人指定：规则页，或本人在对话里亲自要求的那一轮（`save_rule` 只在 `ownerAskedThisTurn` 时允许新加或改动目标，“这个群”写 `chatId: "current"`，换成本会话的飞书群；别的轮次被拒绝，不动目标的修改照常）。
- `capture`：把这个群设为“与本人有关”并立刻采集一次（之后按 ingest 策略整理）。
- `notify`：通知本人（可标紧急），正文带规则名、事件摘要和理由。

### 会议规则：本人入会时拉机器人进会

“我加入标题带‘评审’、三个人以上的会议时，问我要不要把机器人拉进去，记录会议，有人问到我时提醒我”：触发 `meeting`，条件 `meeting.title contains 评审` 且 `meeting.participantCount gte 3`，动作 `meeting-bot`。实现在 `src/channels/lark-meetings.ts`。

- **知道本人入会**：本人的 lark-cli（用户身份，只读）常驻 `event consume vc.meeting.participant_meeting_joined_v1`，另一个进程收 `…_ended_v1`；只在有启用的会议规则时运行，停时关掉 stdin 让 lark-cli 自己退订。收不到事件（没订阅、没权限、进程起不来）时每分钟查一次 `vc +meeting-list-active` 代替。每场会议记一行 `lark_meetings`，交给规则一次；没有规则命中时，入会后十分钟内参会人变了再交一次（每条规则每场会议仍只触发一次，`rule_handled` 的键是 `meeting:<id>`）。参会人来自本人身份读到的会中事件（加入减离开）。不写条件的会议规则表示每场会议。
- **拉机器人**：`bots` 是 `main` 或 `lark.bots` 的 id，每个机器人用自己的应用身份调 `POST /open-apis/vc/v1/bots/join`（`join_type: 1`，9 位会议号）。`confirm`（默认开）先由主机器人给本人发卡片（`card_interactions.purpose = meeting-join`），点“拉进去”才入会。机器人入会所有参会人都能看到；不拉机器人（`bots` 为空）只以本人身份读会中事件做记录，别人看不到，不用问。入会失败（会议没打开“允许智能体加入”、密码、等候室、缺权限）通知本人原因。没有任何以本人身份写飞书的操作。
- **两种人数**：`meeting.participantCount` 是在会人数，来自本人身份读到的会中事件（加入减离开，`user_type = 10` 的应用和机器人不算），入会那一刻往往还没到齐；`meeting.invitedCount` 是会邀人数：按会议链接（以会议号结尾）在已采集的日程里找到这场会议的日程（找不到再查本人当天的 `calendar +agenda`），以本人身份读 `calendar/v4` 的参与人，邀请的群按 `chat_members` 展开（同一人只算一次），不算会议室和拒绝的人。会邀人数在本人入会时读一次，存在 `lark_meetings.invited`；没有日程（临时会议）、读不到时是未知。“大会才问”一般用会邀人数，入会时就是准的。
- **按条件确认**：`confirm` 也能写会议条件（同上面的 `all / any / not` 结构），满足时先问，不满足直接加入。例如“当我入会时，30 人及以上先发卡片问我，否则直接拉机器人”：整条规则的 `conditions=null`，动作写 `{"type":"meeting-bot","bots":["main"],"confirm":{"field":"meeting.participantCount","op":"gte","value":"30"}}`。`conditions` 决定这场会议是否处理，`confirm` 决定处理时是否先问。只按本次触发时的数据判断，实际确认方式保存在会议计划里，之后人数或规则变化不重新切换；确认条件所需数据未知时先问，人数读取失败或没有参会人事件都不算 0 人。网页可选“始终询问 / 直接加入 / 满足条件时询问”，试运行显示入会方式，不发卡片、不拉机器人。原有布尔值保持原意。
- **在会议里拉机器人**：会议里有人把 omem 的某个机器人邀请进来时，那个机器人的应用收到 `vc.bot.meeting_invited_v1`（要在它的“事件与回调”里订阅，长连接接收），不需要规则：本人邀请的直接入会，别人邀请的先发卡片问本人。入会后按本人为这个机器人设的会议规则（有的话）记录、旁听、回答，没有就记录会议、回答点名它的问题、导入共享的文档；本人离会时不跟着离开。`card_interactions` 和卡片沿用 `meeting-join`。
- **入会事件不是必需的**：lark-cli 的应用没订阅 `participant_meeting_joined_v1` / `_ended_v1` 时，lark-cli 先报“ready”、过十几秒才因没订阅退出；omem 把监听在 45 秒内退出算作没收到，每分钟查一次 `+meeting-list-active` 代替，最多晚一分钟。规则页的权限检查这时显示一条说明（不是缺项），带订阅链接。
- **会里能拿到什么**：结构化事件，没有音视频——参会人加入 / 离开、实时转写（`sentence_id` 会被修订，按最新文本覆盖原位置）、会中聊天（表情是 `message_type = 3`）、共享文档开始 / 结束（带文档链接）。机器人在会中时用它的身份读 `GET /open-apis/vc/v1/bots/events`（按 `page_token` 增量），否则以本人身份读 `vc +meeting-events`。每 20 秒读一次，写进 `lark_meeting_lines`。
- **记录**（`record`，默认开）：整场会议是一份 `kind=meeting` 的原件（`lark:meeting:<id>`），边开边更新，会议结束后交给整理；之后每 10 分钟查一次 `vc +detail` 拿妙记，把妙记（总结、待办、章节、逐字稿）补进同一份原件，并记为已读，每小时的妙记采集不再另存一份。`importShared` 把会上共享的飞书文档导入同一空间。
- **旁听**（`spec`）：每 3 分钟（新内容超过 40 行时提前）把新的记录交给这个档案一次，同一会议串行、接着上一轮的会话（`lane = meeting:<id>`）。它不复述、不总结，只有有人点本人的名、要本人表态，或出现和本人有关的决定、待办、风险时用 `notify` 告诉本人，其余调用 `stay_quiet`（运行输入带 `meeting`，结果不投递）。`answer` 打开时，会中聊天里点名某个机器人的话立刻交给它，它用 `meeting_send` 以那个机器人的身份在会中聊天回答（只有这类运行能用这个工具）。会议结束（或本人离会）后再跑一次，给本人一份简短纪要（结论、待办、未决问题、风险），经通知送达。
- **本人离会**：读到本人的 `participant_left`（按 lark-cli 和各机器人应用里本人的 open_id 或名字认）就结束这场的跟进；`leaveWithOwner`（默认开）让机器人一起 `POST …/bots/leave`。本人回到同一场会议时按原来的安排再拉一次。
- **限制**：会议规则只能用会议字段，动作只能是拉机器人入会、通知，或交给 Agent（只告诉我）；不能等待、跳过或静默排查。机器人不能在会上说话（实时音频需要单独的协议，不在本期）。
- **排查**：服务日志里 `[omem] 会议：` 开头的行记下事件流的开始和退出、本人入会、机器人入会结果、结束跟进；飞书实际返回的数据每类留最新一份在 kv `lark_meeting_samples`（入会事件、在开的会、会中事件、会议详情），用来核对代码猜的字段名。

### 权限检查

会议规则保存后（规则页的“飞书权限”和 `save_rule` 的结果里）立即检查，`src/rules/permissions.ts`：

- lark-cli：有没有配置应用、有没有以本人身份登录；应用有没有开通用户身份的 `vc:meeting.meetingevent:read`（没开给开发者后台申请链接，`token_type=user`）；开了但登录没授权时发起只要这一项的授权，给本人确认链接（`requestUserScopes`）。入会事件要在 lark-cli 的应用里订阅（给“事件与回调”页面链接）；事件流起来后显示“正在接收”，起不来时显示 lark-cli 的报错。
- 每个要拉的机器人：用它的 App Secret 换租户令牌读已开通的权限，缺 `vc:meeting.bot.join:write`、`vc:meeting.meetingevent:read`（回答提问还要 `vc:meeting.message:write`）就给这个应用的申请链接。
- 读不到的列为注意事项：权限的数据范围（“会议的归属者 包含 与应用的可用范围一致”）、会议本身的“允许智能体加入”和 AI 纪要开关。

### 临时规则：Agent 设给自己的唤醒

本人的规则之外，Agent 可以为自己手上的事设临时的等待（`src/agents/wakes.ts`）：

- `wake_later(after, note)`：过一段时间（1 分钟到 7 天）唤醒。是一条 `kind=wake`、带 `not_before` 的排队运行，不是规则。
- `wake_on_message(chat_id, note, contains / from / mentions_owner)`：某个群里出现符合条件的新消息时唤醒。是一条 `temporary` 不为空的规则：条件由工具按参数生成（群 id 加上给的条件，默认排除机器人），唯一的动作是 `wake`，默认触发一次就删除，到期（默认 24 小时，最长 7 天）由巡检删除。只有本人的助理和 Agent 能设；`save_rule` 和规则页不能建 `wake` 动作。

唤醒的意思：设它的会话里加一条唤醒记录（不是本人的话），会话的 Agent 接着原来的会话开一轮，备注就是任务；没什么要说时调用 `stay_quiet`，本人收不到消息。指定 `agent` 时改为给那个档案开一次运行，结果发回原会话；档案在没有会话的运行里唤醒自己时，接着自己上次的会话。每个会话（或档案）最多 5 个待触发的唤醒，`cancel_wake` 列出和取消。规则页列表底部的“临时唤醒”显示两种，点开看要做什么、什么时候、谁设的（链到设它的运行和原会话）、消息唤醒的条件和触发记录，可以取消；只读，不能改。

每次触发记一条 `rule_firings`：事件、判断方式和理由、各动作结果（运行 id、错误）。规则页显示最近的触发和每条规则的命中次数。

## 界面

侧栏“规则”：左边规则列表（启用开关、命中次数、最近触发），右边编辑：

- 规则原话（必填）。
- 触发：新消息 / 新群 / 定时（cron）；每条消息触发或每个群一次。
- 判断：条件（一句句可读的条件，可增删改）+ “让 AI 从原话生成条件”；判断方式。
- 动作：按顺序的卡片，选 Agent、开话题、回复方式等。
- “用最近的消息试一试”：拿最近采集的消息（可选某个群）按当前条件求值，列出会命中的消息和理由（只交给模型的规则抽样试）。
- 触发记录。

助理也能建规则：本人在聊天里说“以后值班群里我被 @ 就把机器人拉进去”，助理用 `save_rule` 写原话、生成条件和动作，规则默认不启用，回复送达后由宿主展示启用确认卡片；点击“启用规则”直接校验并修改已保存的规则和定时任务状态，不交给 AI 再处理。规则被修改后旧确认不能启用新内容，规则页同步刷新并保留未保存的编辑；也可通过规则页核对启用。本人明确说“现在就启用”时可以直接启用。

## 实现

`src/rules/`：`types.ts`（结构与校验）、`conditions.ts`（求值与中文描述）、`store.ts`（表与去重）、`engine.ts`（事件分发、判断、试运行）、`actions.ts`、`compile.ts`（模型生成条件、模型判断）。事件来源：`lark-bot.ts`（机器人所在群的实时消息）、`lark-personal.ts`（本人采集的所有会话，含第一次读到的群）、`lark-meetings.ts`（本人入会）、定时任务 `rule:<id>`。权限检查在 `permissions.ts`。

## 所属空间与主助手

任务规则保存 `spaceId`（所属空间；没有设的是全局规则）和可选 `conversationId`（结果会话）。规则页列表每条写着所属空间或“全局”；全局规则在每个空间的列表里都会列出（`GET /api/rules?space=` 返回这个空间和全局的），不是重复。所有类型的规则都能在编辑页“所属空间”里改，走同一个保存接口。主助手代建时从创建运行保存这两项，定时触发时不重新猜。消息规则只匹配所属空间的会话；网页列表包含当前空间与全局规则。动作的 `spec` 默认 `assistant`，不再自动挑第一个或最接近的档案。执行空间优先用动作的 `space`，其次档案固定空间、规则所属空间、触发会话空间。

定时任务直接回复或先给本人看都需保存结果会话；话题 ID 随会话保留。未设置结果会话请选择“只告诉我”。“先给我看”只对飞书会话有意义：Agent 用 `lark_send` 写的话变成给本人的确认卡片，确认后发到那个群（会话是话题时发在话题里），结论另外通知本人；网页会话只有本人看，选“先给我看”按直接回复处理，界面上只给飞书会话显示这一项。主助手的后台规则运行限定空间与发送范围，不交办编码、不创建规则；它可以用 `run_agent` 把这次触发交给某个档案（比如先看一眼再交给排查 Agent）：被交办的运行沿用规则的群、回复方式、草稿、失败去向和是否隐藏思考气泡，不能再交办或请教别的 Agent，静默排查时它开的话题里的后续回复仍回到主助手。自定义档案仍按自身权限执行。

## 归档规则

网页“规则”分为任务规则与归档规则。归档规则处理材料归属，保存于 `archive_rules`；条件支持材料类型、标题 / 群名、网址 / 路径、正文、采集渠道、知识库名称、所在目录、上级目录路径，不开放 ID、token、作者或父页面地址，从上到下匹配（列表里可上移调整，编辑不改变顺序），首条命中即停止。手动指定、来源绑定优先于规则；未命中的由 `archivist` 判断，不确定留个人空间。

“让 AI 编写条件”启动 `archive-rule-draft`，由角色调用 `propose_archive_rule` 返回草稿；本人核对、保存并启用后才影响后续采集。历史材料用当前空间的预览列表逐批应用，校验原件 hash、规则版本和目标，冲突不覆盖。原件详情可手动修正归属，迁移记录、引用和原件 ID 保留。

目录匹配示例：`meta.wikiPath contains 项目 A` 匹配项目 A 目录下的各层文档，文档标题不必出现项目名；`meta.wikiParentTitle equals 周会` 只判断直接父目录。按文字匹配，不推测同义词。字段旁显示用途说明，类型与渠道用中文选项。旧原件可从整理材料面板更新飞书目录，不下载附件或重新整理正文。

### 思考气泡和失败报告

Agent 动作可勾选“隐藏思考气泡”（`hideThinking`），不影响成功结果的回复方式。“失败时”可选通知本人或发到群聊（`failureTo=owner|chat`，默认本人）。Agent 遇到无法完成的操作时用 `report_rule_failure` 报告，宿主按本次规则保存的目标发送；后端运行异常也走同一路径，群投递失败则回本人。一次运行不重复发送失败结论，原群不会再收到自动的结尾回复。

## 快速检查

`trigger.fast`（规则页“快速检查（每分钟）”，只用于新消息规则）：平常的采集（`lark-poll`，常驻服务器上每 10 分钟）之外，`rules/fast.ts` 的 `pollFastRules` 每分钟用本人的 lark-cli 搜两类消息：群里 @ 本人的（`+messages-search --at-chatter-ids <本人> --chat-type group`）和私聊的（`--chat-type p2p`），`--query` 是这些规则条件里 `message.text contains` 的词（没有就不带）。窗口从上次结束往前多看 2 分钟（搜索有延迟），只交给勾了快速检查的规则；同一条消息之后随采集再来时按 `rule_handled` 不重复触发。本人自己发的不算。实测常驻服务器上验证码机器人的私聊消息在搜索里马上能搜到（时间只到分钟）。
