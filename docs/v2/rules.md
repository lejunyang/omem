# 规则：什么情况下自动叫哪个 Agent 做什么

本人用一句话描述“遇到什么情况就做什么”，omem 在消息到来、发现新群或定时巡检时判断是否满足，满足就执行动作（交给某个 Agent、开话题处理、拉机器人进群、优先采集、通知本人）。判断先用确定的条件（便宜、可预期），条件写不出来的部分交给模型判断；模型可以把一句话规则“固化”成条件，本人看得懂、改得动。

## 例子

| 本人的话 | 触发 | 条件 | 动作 |
| --- | --- | --- | --- |
| 群名包含“答疑”或群里有“问答机器人”时，把助手拉进群，等用户提问后交给 support-agent 尝试解决 | 新消息（每个群只触发一次） | 群名包含“答疑” 或 群里的机器人包含“问答机器人” | 拉机器人进群；持续监听：@ 机器人的消息交给 support-agent，回复先给本人看 |
| 报警群里，A 或 B 发报警卡片时，在卡片下开话题让 alert-analyst 分析，需要关注就 @ 值班人 | 新消息 | 群名包含“报警” 且 发送人是 A、B 之一 且 消息是卡片 | 交给 alert-analyst：从这条消息开话题，可以直接回复（结论和 @ 值班人写在话题里） |
| 值班群里我被 @，立刻把机器人拉进群，并优先采集 | 新消息（每个群只触发一次） | 群名包含“值班” 且 @ 了本人 | 拉机器人进群；优先采集这个群 |
| 有人在任何群里提到“合同到期” | 新消息 | 消息包含“合同到期” | 通知本人 |
| 每天早上看一眼发布群，有没有失败的发布 | 定时（cron） | （无，交给模型） | 交给 release-checker，结论通知本人 |

## 模型

一条规则（表 `rules`）：

- `description`：本人的原话，规则的依据。条件和动作都可以重新从它生成。
- `trigger`：`message`（新消息，含卡片）、`chat-new`（第一次看到的群）、`schedule`（cron）。`once: "event" | "chat"`：每条消息都可能触发，或每个群只触发一次（拉机器人、开始监听这类）。
- `conditions`：确定的条件（JSON，见下），可以为空。
- `judge`：`code`（只看条件）、`ai`（只交给模型）、`code+ai`（条件先筛，命中的再请模型确认）。条件为空时只能是 `ai`。
- `actions`：按顺序执行。
- `enabled`：助理替本人建的规则默认不启用，本人在规则页启用。

### 条件

```json
{ "all": [
  { "field": "chat.name", "op": "contains", "value": "报警" },
  { "any": [ { "field": "sender.name", "op": "in", "value": ["小王", "小李"] }, { "field": "sender.email", "op": "endsWith", "value": "@example.com" } ] },
  { "field": "message.type", "op": "equals", "value": "interactive" }
] }
```

字段：`chat.id`、`chat.name`、`chat.kind`（group / p2p）、`chat.bots`（群里的机器人名字，第一次用到时用本人的 lark-cli 读成员，缓存一天）、`chat.hasOwnBot`（群里有没有 omem 自己的机器人，按 `lark.appId` 比对成员的应用 id，不看名字；机器人收到的消息直接算有；读不到成员时视为未知，is true / is false 都不成立）、`sender.name`、`sender.email`、`sender.kind`（owner / user / bot）、`message.text`、`message.type`（text / post / interactive（卡片）/ image / file…）、`message.mentionsOwner`、`message.mentionsBot`、`message.inTopic`、`message.cardTitle`。运算：`equals`、`contains`、`startsWith`、`endsWith`、`matches`（正则）、`in`（列表）、`is`（布尔）。组合：`all`、`any`、`not`。

“固化成代码”就是这份 JSON：宿主直接求值，不执行模型写的程序。模型从规则原话生成条件，本人在页面上看到的是一句句“群名包含 报警”，可以直接改；生成后先在最近的消息上试一遍，看命中了哪些。

### 判断

1. 触发类型和范围不对的直接跳过。
2. `code`：条件求值。`ai`：把规则原话和这条事件（群、发送人、消息正文的前一千字）交给一次模型调用（无工具），回答是否满足和一句理由。`code+ai`：条件先筛，命中的再问模型。
3. 只交给模型的消息规则，每条规则每小时最多问 60 次，超出的跳过并记录；这类规则建议先固化出群名之类的条件缩小范围。
4. 每条事件对每条规则只处理一次（机器人实时事件和本人采集都会看到同一条消息，按规则 + 消息 id 去重；`once: chat` 按规则 + 群去重）。

### 动作

- `agent`：交给某个 Agent 档案。`ownTopic` 在触发消息下处理（机器人要在群里）：不再先发一张“规则触发、交给某某”的卡片，Agent 的思考气泡或回答以话题回复的方式发在那条消息下，话题由它开出。`reply`：`none`（只把结论发给本人）、`draft`（它要在群里说的话先变成给本人的确认卡片）、`auto`（可以直接在这个群 / 话题里回复和 @ 人，思考气泡可见）、`silent`（静默排查，见下）。它只能往这个群发，不能发到别处。`allowUrgent` / `allowPrivate`（默认关，规则页“允许加急”“允许只给部分人看”）：它在群里发的消息可以对指定的人加急、可以只给群里某几个人看；什么情况用、对谁用写在规则说明或任务里，任务末尾会提醒它只在写到的情况用。本人说“某种情况加急某人”“只发给某人看”时，草稿生成会勾上对应的项。

### 等待与跳过：别人在处理时不插手

“我被 @ 就交给 Agent”的规则在本人已经接手、正和别人讨论时也会命中——对方在讨论里 @ 本人是常态。条件只看这一条消息，看不出来；所以触发时再看一眼它所在的讨论：

- `trigger.waitMinutes`：命中后等几分钟再动手（“10 分钟没人理再处理”）。等待是一个 `rule-fire` 运行（`not_before`），时间到了再做下面的检查。
- `trigger.unless`：动手前跳过的情况。`owner-engaged`：本人在这个话题里说过话，或在群里触发前半小时以来说过话。`answered`：话题里触发之后有发送人以外的人（非机器人）说话；不在话题里时，有人回复了这条消息。跳过的记在触发记录里（不计命中次数）。
- 讨论来自已存的消息（机器人实时收到的、本人采集的）加一次本人 lark-cli 的只读列表（话题全部，或群里前后半小时），`src/rules/context.ts`。
- 设了等待或跳过的规则，模型判断（`code+ai`、`ai`）也放到动手时做，并且带上这段讨论：本人已在讨论、对方只是 @ 本人时通常判为不处理。

### 有人直接 @ 机器人时规则让开

规则管的是没人找机器人的消息。一个人（不是机器人）@ 了 omem 机器人，而机器人会直接回答他（本人、登记的用户，或开了访客提问时任何人），这条消息就记为“已被直接回答”（`rule_handled` 里的 `@bot`），所有规则——包括等待、静默排查和对 Agent 跟进话题的接续——都跳过它，不管它后来从机器人还是本人采集送到规则。别的机器人 @ omem 机器人时照常交给规则；没有规则接手，再由访客模式的把关角色判断它说的事要不要处理。

### 静默排查（`reply: "silent"`）

适合值班群：Agent 读讨论、查资料，群里什么都看不到，它自己决定要不要说话。

- 不开话题、不发思考气泡、最后的文字不自动发出（留在运行记录里）。
- 任务里附上正在进行的讨论（→ 标出触发的那条），说明怎么做：本人已在跟进、别人已回答或不需要处理就什么都不发；有结论或可行的排查思路时用 `lark_send` 在触发消息的话题里回复（`reply_to` + `in_thread`）；缺关键信息就在话题里问；需要本人决定的用 `notify` 告诉本人，不在群里 @ 本人。
- 它在某个话题里发过言，就跟进这个话题 24 小时：话题里的新消息不再走规则条件，一分钟后交回同一个 Agent（接着它的 Agent 会话，同一话题一次只排一个）；本人在话题里说话就不再跟进。
- 定时规则不能用等待、跳过和静默排查（没有具体的讨论）。

### 例：值班群被 @ 时先留住记录

值班群关单后本人可能被移出，lark-cli 就读不到了。“被 @ 就先保存、把机器人拉进去”用一条规则：条件 `message.mentionsOwner is true`（再加群名或 `chat.bots contains` 值班机器人缩小范围），`trigger.once = chat`，动作“优先采集”+“拉机器人进群”。机器人进群后实时收到的消息照常存进群原件，本人离群也不影响。

要确认“这真是某个工单的群”、查工单状态，写成值班技能（里面用内部命令行），挂在处理这类群的 Agent 档案上，再加一个“交给 Agent”动作让它去查。内部系统只出现在技能里，不进 omem 的代码和配置（AGENTS.md）。
- `watch`：开始监听这个群，后续消息交给某个 Agent（同 `/watch`：全部 / @ / 关键词，回复方式同上）。
- `invite-bot`：以本人身份把 omem 自己的机器人加进这个群（lark-cli `im chat.members create`，只加 omem 的 app_id，不发消息、不加别的成员）。这是本人身份唯一的写操作，只在本人配置的规则里发生。
- `capture`：把这个群设为“与本人有关”并立刻采集一次（之后按 ingest 策略整理）。
- `notify`：通知本人（可标紧急），正文带规则名、事件摘要和理由。

### 临时规则：Agent 设给自己的唤醒

本人的规则之外，Agent 可以为自己手上的事设临时的等待（`src/agents/wakes.ts`）：

- `wake_later(after, note)`：过一段时间（1 分钟到 7 天）唤醒。是一条 `kind=wake`、带 `not_before` 的排队运行，不是规则。
- `wake_on_message(chat_id, note, contains / from / mentions_owner)`：某个群里出现符合条件的新消息时唤醒。是一条 `temporary` 不为空的规则：条件由工具按参数生成（群 id 加上给的条件，默认排除机器人），唯一的动作是 `wake`，默认触发一次就删除，到期（默认 24 小时，最长 7 天）由巡检删除。只有本人的助理和 Agent 能设；`save_rule` 和规则页不能建 `wake` 动作。

唤醒的意思：设它的会话里加一条唤醒记录（不是本人的话），会话的 Agent 接着原来的会话开一轮，备注就是任务；没什么要说时回 QUIET，本人收不到消息。指定 `agent` 时改为给那个档案开一次运行，结果发回原会话；档案在没有会话的运行里唤醒自己时，接着自己上次的会话。每个会话（或档案）最多 5 个待触发的唤醒，`cancel_wake` 列出和取消。规则页列表底部的“临时唤醒”显示两种，点开看要做什么、什么时候、谁设的（链到设它的运行和原会话）、消息唤醒的条件和触发记录，可以取消；只读，不能改。

每次触发记一条 `rule_firings`：事件、判断方式和理由、各动作结果（运行 id、错误）。规则页显示最近的触发和每条规则的命中次数。

## 界面

侧栏“规则”：左边规则列表（启用开关、命中次数、最近触发），右边编辑：

- 规则原话（必填）。
- 触发：新消息 / 新群 / 定时（cron）；每条消息触发或每个群一次。
- 判断：条件（一句句可读的条件，可增删改）+ “让 AI 从原话生成条件”；判断方式。
- 动作：按顺序的卡片，选 Agent、开话题、回复方式等。
- “用最近的消息试一试”：拿最近采集的消息（可选某个群）按当前条件求值，列出会命中的消息和理由（只交给模型的规则抽样试）。
- 触发记录。

助理也能建规则：本人在聊天里说“以后值班群里我被 @ 就把机器人拉进去”，助理用 `save_rule` 写原话、生成条件和动作，规则默认不启用，回复里给出规则页链接让本人确认后启用；本人明确说“现在就启用”时可以直接启用。

## 实现

`src/rules/`：`types.ts`（结构与校验）、`conditions.ts`（求值与中文描述）、`store.ts`（表与去重）、`engine.ts`（事件分发、判断、试运行）、`actions.ts`、`compile.ts`（模型生成条件、模型判断）。事件来源：`lark-bot.ts`（机器人所在群的实时消息）、`lark-personal.ts`（本人采集的所有会话，含第一次读到的群）、定时任务 `rule:<id>`。

## 所属空间与主助手

任务规则保存 `spaceId`（所属空间；旧规则未设置时仍是全局）和可选 `conversationId`（结果会话）。主助手代建时从创建运行保存这两项，定时触发时不重新猜。消息规则只匹配所属空间的会话；网页列表包含当前空间与全局规则。动作的 `spec` 默认 `assistant`，不再自动挑第一个或最接近的档案。执行空间优先用动作的 `space`，其次档案固定空间、规则所属空间、触发会话空间。

定时任务直接回复或先给本人看都需保存结果会话；话题 ID 随会话保留。未设置结果会话请选择“只告诉我”。“先给我看”只对飞书会话有意义：Agent 用 `lark_send` 写的话变成给本人的确认卡片，确认后发到那个群（会话是话题时发在话题里），结论另外通知本人；网页会话只有本人看，选“先给我看”按直接回复处理，界面上只给飞书会话显示这一项。主助手的后台规则运行限定空间与发送范围，不再交办或创建任务规则；自定义档案仍按自身权限执行。

## 归档规则

网页“规则”分为任务规则与归档规则。归档规则处理材料归属，保存于 `archive_rules`；条件支持材料类型、标题 / 群名、网址 / 路径、正文、采集渠道、知识库名称、所在目录、上级目录路径，不开放 ID、token、作者或父页面地址，从上到下匹配（列表里可上移调整，编辑不改变顺序），首条命中即停止。手动指定、来源绑定优先于规则；未命中的由 `archivist` 判断，不确定留个人空间。

“让 AI 编写条件”启动 `archive-rule-draft`，由角色调用 `propose_archive_rule` 返回草稿；本人核对、保存并启用后才影响后续采集。历史材料用当前空间的预览列表逐批应用，校验原件 hash、规则版本和目标，冲突不覆盖。原件详情可手动修正归属，迁移记录、引用和原件 ID 保留。

目录匹配示例：`meta.wikiPath contains 项目 A` 匹配项目 A 目录下的各层文档，文档标题不必出现项目名；`meta.wikiParentTitle equals 周会` 只判断直接父目录。按文字匹配，不推测同义词。字段旁显示用途说明，类型与渠道用中文选项。旧原件可从整理材料面板更新飞书目录，不下载附件或重新整理正文。
