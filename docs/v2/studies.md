# 课题：自主探索一个项目

状态：第一期和第二期服务端已实现（2026-11-15）：轮次与预算、台账、逐个试验、内置技能和流程、课题接口。第 11 节是本人已经定的取舍；课题面板由独立任务接入。

## 1. 要解决的问题

手里有一个开源项目，不清楚它现在有什么缺陷、还能做什么改进。直接开一个会话让模型“找找问题”，确实能找到一些，但每次都从头泛泛地看：

- 没有一张“这个仓库到底有哪些功能”的清单，模型每次看到哪算哪；
- 上一次试过什么、结论是什么没有留下，下一次重复试，或者同一个问题报两遍；
- 范围太宽，没有“这一段时间只盯一个方向”的收敛；
- 好模型贵，探索又要跑很多次，全用好模型不划算，全用便宜模型又定不好方向。

想要的做法是一个长期的课题，按需要转一轮（不一定每天）：

1. 用好的模型，对着仓库的功能清单提出接下来往哪个方向推，和本人确认。
2. 没人看着的时候（通常是夜里），主要用便宜的模型按确认的方案去试：跑测试、和同类项目对比、照真实的使用场景走一遍，需要时直接改代码，把结果一条条记下来。
3. 之后给本人一份小结：发现了什么、哪些方向试完了、建议下一步。一个方向做完就换下一个。

两个例子（做法本身写成技能，不进仓库，见第 9 节）：

- 给一个工具链管理的命令行工具找问题：拿近期热门的开源仓库当样本，逐个用它装工具、跑任务，看哪里失败；和同类工具逐项对比功能，列出缺口。
- 给一个桌面自动化工具找问题：按真实的自动化需求清单逐条去做，看哪一步做不成。

## 2. 三条约束

这件事容易做歪，先把不能歪的地方写下来。后面的设计都服从这三条。

**不凑数。** 课题不是每天都要有产出的任务。

- 没有值得做的方向时，提方向的那一段可以说“这一轮没有”，这是正常结果，不算失败。
- 一个试验“没发现问题”和“发现了问题”一样是结果，照实记。不设发现数量的目标，小结里也不拿数量当成绩。
- 发现必须有能复现的证据（哪次试验、什么命令、什么输出）。只是“看起来可以更好”的不记成发现，最多在小结里提一句。
- 连着几轮没有新发现，宿主停下来告诉本人，不自己换方向接着找。

**不被旧记录带偏。** 记录是为了不重复劳动，不是为了划定下一步的范围。

- 提方向时先不给台账：模型只看功能清单和外面的材料（同类项目、用户的反馈、最近的代码改动），独立提出方向。
- 提完以后宿主才拿台账对一遍，只做两件事：标出“这个对象的这件事试过，结论是……”；完全重复的试验从计划里去掉。不因为“这一片以前没发现问题”就把方向删掉。
- “不是问题”的判定只压住同一条发现，不压同一类。
- 每次提方向时附一张覆盖情况：功能清单里各项被试过几次、多久没碰。从没碰过的功能区至少提一个候选。

**不固定节奏和分工。** 多久转一轮、哪一段用哪个模型、花多少，都看当时的情况。

- 轮次默认由本人开始（“再来一轮”），也可以设成每周某几天；不默认每天。
- 好模型不只用在定方向：夜里便宜模型交不出结果、或者拿不准时，可以请好模型看一眼（升档），次数算在这一轮的预算里。
- 预算在每一轮确认方向时定，不是一个固定的每晚额度。

## 3. 现在能拼出什么，缺什么

| 需要的 | 现在有的 | 差在哪 |
| --- | --- | --- |
| 和本人确认方向 | 流程的关卡（`gate` / `done: confirm`），提问卡片 | 流程只走一遍，没有“再来一轮” |
| 不同的段用不同的模型 | 规则的“交给 Agent”可以指定后端、模型、强度；按模型的每日额度 | 流程的运行阶段只能选 Agent 和技能，不能选模型，也不能限定时间段 |
| 没人看着时自动去试、去改 | 定时规则；编码交办和评审；`improve_start / improve_round`（宿主量指标、定去留） | 改进循环只适合一个量得出来的指标；“找问题、做对比”没有对应的载体 |
| 每次试验留记录，换方向时不重复 | 运行记录、工作文件、Wiki | 记录只是文字，宿主不知道“试过哪个对象、结果怎样、对应哪条发现”，没法去重和汇总 |
| 先把仓库功能梳理清楚 | 仓库空间的代码索引和 Wiki | 没有“功能清单”这种给探索用的产物 |
| 试验放在不同的地方跑 | 本机的交办工作区；云端会话型的后端；另一台设备上的交办（见第 6 节） | 没有“这个试验在哪跑”的统一说法，另一台设备只能由本机的模型去操作，不能把试验派过去 |
| 推到代码托管上跑测试 | `code_git_action`（推送） | 每次推送都要本人明确要求，没人看着时没人批 |

## 4. 取舍：建在流程上，不另起一套编排

课题不单独做一套调度。它是：

- 一件“持续关注”类的事项（材料、所在的会话、时间线都是现成的）；
- 加一份带轮次的流程（第 5 节给流程补四样通用的能力）；
- 加一份台账（第 7 节：方向、试验、发现）。

这样一轮怎么走由流程定义决定，本人可以改（比如多一段“这周汇总”），不写死在代码里；轮次、时间段、指定 AI 这几样别的流程也用得上（每周的周报、定期的巡检都是“走完再来一轮”）。

“一个方向下跑很多个试验”是阶段内部的事，按流程设计的原则（复杂的编排留在阶段里，`docs/v2/flows.md` 第 2 节）交给一个新的对象 `trials` 承担，流程只看它“这一轮跑完了没有”。

## 5. 给流程补的四样

### 5.1 轮次

```yaml
repeat: { from: plan, every: manual }   # 最后一段做完以后，从 plan 这一段起可以再来一轮
```

- `from` 之前的阶段只做一次（梳理功能清单），之后的每轮重做。
- `every`：`manual`（默认：上一轮结束后停着，本人点“再来一轮”才开始）、一组星期几（如 `[tue, fri]`）、`day`、`done`（上一轮做完立刻开始）。按日子开始时，上一轮还没走完就不开新的。
- 每一轮的阶段状态和日志都留着（`item_stages` 加 `round`；日志本来就是追加的）。事项页的流程条显示“第 N 轮”，可以翻看以前各轮。
- 连着 `idleRounds` 轮（默认 3）没有任何新发现：这一轮结束后不再自动开始，告诉本人，由本人决定换方向、暂停还是结束。

### 5.2 阶段指定 AI、时间段

```yaml
by: { run: { agent: assistant, skill: study-plan } }
ai: strong            # 档位名；也可以写 { profile, model, effort }，和规则里的写法一样
at: "10:00"           # 这一轮在这个时刻开始（配置的时区）；不写就是轮到就开始
window: "01:00-06:00" # 只在这个时间段里跑；到点没做完就停下，这一轮按做到哪算哪
```

- 档位（`strong` / `standard` / `cheap`）在 设置 → AI 里各对应一个后端、模型和强度。流程定义里只写档位名，换机器、分享给别人都不用改。
- 档位对应的模型当天额度用完时，不自动换成更贵的：这一段等到下一个时间段，并在小结里写明。

### 5.3 升档

```yaml
ai: cheap
escalate: { to: strong, max: 2 }   # 这一轮里最多请好模型看两次
```

便宜模型做的试验交不出结果，或者它在报告里标了“拿不准”（结果说不清、怀疑是工具本身的问题、要不要改代码定不下来），宿主把这一个试验连同它的记录交给上一档的模型重看一次。每一轮有上限，用完了剩下的记成“说不清”，等本人或下一轮。

### 5.4 预算

```yaml
budget: { trials: 8, minutes: 240 }   # 这一段这一轮最多做多少
```

流程定义里的数只是起点：每一轮确认方向的卡片上带着这一轮的预算（试验数、时长、升档次数、可不可以改代码），本人可以当场改。宿主计数，到了就停，剩下的留给下一轮。

## 6. 试验在哪跑

不写死。每个方向写明它的试验在哪个执行环境里跑，一个方向也可以混用。环境是登记出来的（设置里一张表：名字、怎么进去、里面能不能执行第三方样本的代码），不在代码里按名字判断。

| 环境 | 怎么跑 | 现状 |
| --- | --- | --- |
| 本机 | 试验的运行在交办的工作区里直接执行命令，受命令规则约束。默认是它 | 已有 |
| 云端会话 | 这一段用云端会话型的后端（Agent 和它执行的命令都在提供方的云端环境里），把仓库和用例带过去，结果带回来 | 后端已有；“把哪些文件带过去、把什么带回来”要补 |
| 托管的流水线 | 把用例推到代码托管平台上登记的测试仓库或分支，由它的流水线执行，本机读结果 | 推送和读结果的技能要写；持续授权见第 8 节 |
| 另一台设备 | 把这个试验派给配对过的另一台设备，由它在自己的工作区里跑完，结果和证据记回本机的台账 | **要新做** |

另一台设备现在能做到的是三件事，都不是“把试验派过去”：

- 本机的模型在那台设备的仓库里发起交办，经 `code_workspace` 读写文件、运行那台设备上本人允许的命令。模型在本机，命令在对方执行，得本机这边一直连着。
- `ask_agent(档案@节点)`：请对方的一个档案用它自己的模型回答一个问题，一问一答。
- 固定清单里的远程命令（检查、更新），不能跑别的。

要新做的是：本机把一个试验（做什么、在哪个仓库、预算、交结果的格式）交给那台设备，那台设备起一次自己的运行去做，做完把 `trial_report` 的内容和证据文件送回来；本机的台账里记着“在哪台设备上跑的”。它建在设备互通已有的鉴权和转发上（`docs/v2/mesh.md`），只开放“接受一个试验”这一种委托，不是任意命令。

**在本机跑第三方样本要想清楚的事**：拿别人的仓库当样本，等于在这台机器上执行它的安装脚本和构建脚本。常驻的那台机器上有本人的登录态和各种命令行。所以环境登记里有一项“能不能执行第三方样本的代码”：本机默认不能，本人对某个课题明确打开才行；打开以后试验仍然只在交办的工作区里、按命令规则执行。云端会话和托管流水线是一次性的环境，默认可以。

## 7. 台账：方向、试验、发现

三张表，都挂在事项上（一件事项就是一个课题），随事项一起拉取和备份。

**方向**（`study_directions`）：一段时间里只盯的一件事。

| 字段 | 含义 |
| --- | --- |
| 目标 | 一句话：想弄清什么 |
| 做法 | 用什么样本、怎么试、和谁比、在哪个环境跑 |
| 验收 | 做到什么算这个方向结束（“三十个样本跑完”“五个同类工具的功能逐项对完”） |
| 计划的试验 | 一份清单：对象 × 要检查的事，按它排队 |
| 状态 | 提出 / 本人确认 / 进行中 / 结束（带结论）/ 放弃（带原因） |

**试验**（`study_trials`）：对一个对象做一次检查，或一次改动的尝试。

| 字段 | 含义 |
| --- | --- |
| 对象 | 哪个仓库、哪个功能、哪条需求 |
| 做了什么 | 命令或步骤的摘要 |
| 在哪跑的 | 哪个环境、哪次运行、哪条流水线（链接） |
| 结果 | 通过 / 失败 / 做不了（缺什么）/ 说不清 |
| 摘要 | 三五行：看到了什么 |
| 证据 | 日志片段存成工作文件，这里放引用 |
| 对应的发现、改动 | 零到多条发现；改了代码的话是哪次交办 |

**发现**（`study_findings`）：去重以后的一个问题或一个改进点。

| 字段 | 含义 |
| --- | --- |
| 类型 | 缺陷 / 缺口（同类有、这里没有）/ 改进想法 |
| 标题、复现办法 | 能让别人照着再现 |
| 依据 | 哪几次试验 |
| 状态 | 新的 / 本人认可 / 已有改动（哪次交办）/ 已写成 issue 草稿 / 不是问题 / 重复 |

为什么要表而不是文字：要回答“这个对象的这件事试过没有”“这个问题报过没有”“这个方向花了多少、换来几条被认可的发现”，这些靠读一堆文字的记录做不稳。表只存事实和引用；判断（是不是同一个问题、值不值得改）仍然由模型和本人做。台账什么时候给模型看、给多少，按第 2 节“不被旧记录带偏”来：提方向时不给，对账和记录时才用。

**功能清单**不进表：它是仓库空间里的一组 Wiki 页（`studies/<课题>/capabilities`），按功能列出“是什么、怎么触发、现在有哪些测试盖着”，带代码引用。第一轮之前做一次，本人看过确认；之后代码索引更新时由小结那一段顺带核对有没有新功能。

每个方向结束时写一页结论（同一目录下），以后的方向和别人都读得到。

## 8. 一轮怎么走

仓库自带一份流程 `flows/library/study.yaml`（和“需求交付”一样只补缺、可改）：

| 阶段 | 谁做 | 什么时候 | 做什么 |
| --- | --- | --- | --- |
| 梳理 | 运行，`strong` | 只做一次 | 读仓库，写功能清单；本人看过确认 |
| 定方向 | 运行，`strong`，做完要本人点头 | 本人开始这一轮时，或设定的日子 | 进行中的方向没做完就建议继续。否则只看功能清单、覆盖情况和外面的材料，提零到三个方向（目标、做法、验收、计划的试验、在哪跑、预计花多少）；没有值得做的就说没有。宿主拿台账对账后发给本人一张卡片：选、改、调预算、这一轮不跑 |
| 试验 | 对象 `trials`，`cheap`，可升档 | 时间段内，带预算 | 宿主按确认的方向一个一个排试验，每个试验一次运行，做完用 `trial_report` 交结果。交不出结果的记“说不清”，同一个对象失败两次不再重试。方向允许改代码时，试验里可以发起编码交办（见下） |
| 小结 | 运行，`standard` | 试验结束后 | 把这一轮的试验归并成发现（先和已有的比，同一个问题并进去），写小结：试了什么、哪些没发现问题、新发现几条、改了什么。方向达到验收就结束它并写结论页。小结进简报 |

**本人没回“定方向”的卡片时**：进行中的方向照常继续（它已经确认过）；没有进行中的方向，这一轮不跑。不让模型替本人定新方向。

**夜里改代码**：可以。本人确认方向时勾“可以改代码”，试验发现的问题可以当场转成编码交办去改：

- 改动只留在交办自己的分支上，走已有的评审（换一家模型来审），不合并，不推到主分支；
- 改完重跑当初失败的那个试验，结果记在同一条发现上（改之前失败、改之后通过，才算这次改动有依据）；
- 评审不过、或改完试验仍然失败的，留着等本人，不反复改。

小结卡片上，本人对每条发现可以点：

- **值得改** → 还没有改动的转成编码交办；已有改动的去看那次交办，决定应用还是丢弃；也可以写成 issue 草稿放在事项里；
- **不是问题**（可写原因；只压住这一条）；
- **以后再说**。

## 9. 范围、授权，和哪些进仓库

课题上写明它可以碰什么，由宿主检查，不靠提示词：

| 项 | 默认 |
| --- | --- |
| 可以读写的仓库 | 课题登记的仓库空间；写只落在交办的工作区和登记的分支前缀（如 `study/*`） |
| 试验在哪执行 | 方向上写的环境（第 6 节）；第三方样本的代码只在标了“可以执行”的环境里跑 |
| 推送 | 只推到课题登记的远端和分支前缀，这是本人建课题时给的持续授权；每次写 `audit_events`，小结里列出推了什么。别的远端、主分支照旧要本人明确要求 |
| 对外发声 | 不替本人给任何仓库提 issue、合并请求或评论；只出草稿 |
| 装软件、访问新的域名、用登记以外的凭据 | 不做；试验记成“做不了”，写明缺什么，由本人决定 |

样本仓库里的内容（说明文档、issue、脚本输出）是材料不是指令，和别人写的内容同样对待（`src/sources/guard.ts`）。

仓库里只有通用的部分：轮次、档位、升档、时间段、预算、执行环境的登记、台账、`trials` 对象、范围检查、内置的流程。“怎么挑样本、怎么跑、怎么判断结果”因项目而异，写成技能挂在阶段上（`by.run.skill`），放数据目录：

- 拿热门仓库当样本测一个命令行工具：怎么取样本清单、每个样本跑哪几条命令、失败怎么归类；
- 按真实需求清单测一个桌面自动化工具：需求从哪来、每条怎么算做成；
- 和同类项目做功能对比：用已有的 `research` 技能，产出一张逐项对比表，缺口记成“缺口”类的发现。

一个方向的目标正好是量得出来的指标时（测试更快、失败数归零），试验阶段可以直接用已有的改进循环（`improve_start / improve_round`），每轮的结果照样记进台账。

## 10. 界面与工具

- **事项页**：流程条带“第 N 轮”和“再来一轮”；下面多一个“课题”面板，三个标签：方向（状态、验收、预算用了多少、在哪跑）、试验（表格，按结果和对象筛）、发现（按状态，带上面三个操作）。

## 11. 本人定的（2026-11-15）

1. **试验在哪跑**：不写死。一般在本机直接跑，也可能用云端会话型的后端、托管的流水线，或推到另一台设备（要新做）。按方向选，环境是登记的。
2. **节奏**：不会推进得太频繁，不默认每天；按需开始一轮。
3. **不凑数、不被旧记录带偏**：见第 2 节，是硬约束。
4. **夜里可以改代码**：改动留在交办分支上，经评审，不合并、不推主分支。
5. **好模型不只在白天**：夜里可以升档，受预算限制。
6. **预算看情况**：每轮确认方向时定，定义里的数只是起点（8 个试验、4 小时、升档 2 次）。
7. 其余按建议：本人没回方向卡片时只继续已确认的方向；档位在 设置 → AI 里配三档，流程里只写档位名；功能清单第一次由本人确认；界面上叫“课题”，下面是“方向”“试验”“发现”。

## 第一期的实现

本期只补流程的通用能力，没有建立课题台账或课题界面。

- `repeat: { from, every }`：`from` 之前只做一次，从它起每轮重做。默认 `manual`，本人说“再来一轮”时助手用 `flow_round(item)`，也可调用 `POST /api/items/:id/flow/round`。上一轮没做完不能开新的；`done` 自动接下一轮，`day` / 星期在上一轮完成后的下一个符合日开始，配置时区按 `app.config.timezone`。自动推进仍受 `flows.autoAdvance` 限制；停机错过的日子不补跑。
- 当前轮次、开始时间、完成时间和下一轮时间在 `item_flows`；当前阶段和追加日志带 `round`。`item_flow_rounds` 保存每轮结束时各段的状态、完成时间、备注、依据和执行控制信息，随事项拉取，引用照旧映射。视图返回最近 10 轮。
- `agents.tiers` 的 `strong / standard / cheap` 各对应 `{ profile, model?, effort? }`，默认都空。运行阶段可写档位或直接写这三个字段，变成 `execution`（`source: flow`，原因写明流程和阶段）。没配档位时沿用角色或档案自己的 AI，一阶段一轮只记一次；配置不可用时卡住。模型达到每日额度或账号额度用完时保留未开始，写清恢复时刻，由巡检重试，不换其他模型。worker 真正开始前再检查一次。
- `at` 是本轮开始日期的当地时刻下限；跨过这一天后不会再等同一个时刻。`window` 是允许开始的时间段，含开始、不含结束，可跨午夜。时间计算在 `src/flows/timing.ts`，巡检传入的时间用于推进和预算判断，测试不用实际等待。
- `budget.minutes` 计这一段本轮各次运行的累计时间（不算宿主队列等待和等本人确认），巡检发现用满时调用已有 `cancelRun`，卡住等本人。`budget.trials` 只校验、保存和返回。`escalate` 只用于写了 `ai` 的运行阶段：没交结果就结束，或 `stage_report(blocked, unsure: true)` 时，用目标档位重做，带上前一次的结论或错误；每轮最多 `max` 次，用完卡住。重开同一轮不会清空升档次数或已用时间。
- 本人可用 `POST /api/items/:id/flow/stages/:stage/budget` 改副本，收 `{ budget?: { minutes?, trials? }, escalate?: { max } }`。`budget` 替换该段预算，`escalate.max` 只改现有升档上限；不改模板，后续轮沿用，仍可再次调整。提高预算后，已卡住的阶段由本人重开。
- `describeStage` 增加 `ai / time / budget`，`describeFlow` 说明重复方式；定义校验与启用确认卡片共用这些文字。`flowView` 只加字段，返回轮次、是否可手动开始、等待时刻、指定和实际 AI、预算与已用分钟、升档次数、最近各轮快照。网页入口由独立任务负责，本期未改 `web/`。

与设计稿的差异：第 5.2 节原写“时间段结束就停”，本期按任务约定只限制开始，运行由分钟预算限制；升档重做整个运行阶段，尚没有单个试验可供重看。日期循环在上一轮结束后安排下一次，不为错过的日期排队。时间预算由已有巡检检查，取消会有一个巡检间隔的延迟。没有台账前无法判断“连续没有新发现”，所以 `idleRounds` 不在本期实现；自动推进上限先承担无人看守时的停止边界。

未做：台账三表、`study` 工具、`trials` 对象、内置 `study.yaml`、课题面板、执行环境登记、按范围持续授权推送、另一台设备执行试验、课题简报与数据页。它们仍按第 12 节分期。

## 第二期的实现

本期只做服务端、测试和内置材料，没有改 `web/`。

| 文件 | 职责 |
| --- | --- |
| `src/studies/store.ts`、`schema.ts` | 方向、试验、发现的事实和参数；规范化对账、相近标题提示、合并依据、结束方向和连续无发现轮数。 |
| `src/studies/service.ts` | 提案、本人提问及回答校验、试验交结果与产物、台账阅读限制、课题视图。 |
| `src/studies/trials.ts` | 在流程的事项串行队列里逐个起 `study-trial`，处理重试、升档、额度、时间段和本轮预算；没有增加定时任务。 |
| `src/studies/materials.ts` | 功能清单工作文件的位置、二级标题的粗略覆盖次数与最近日期、可读仓库最近 20 条提交标题。 |
| `src/studies/http.ts` | 按空间可读、写限事项本人的三条课题接口。 |
| `flows/library/study.yaml`、`skills/library/study-*/SKILL.md` | 梳理 → 定方向 → 试验 → 小结；流程与四个技能沿用补缺播种，正文按本期约定。 |
| `test/studies.test.ts` | 假运行、实际工具调用、HTTP、产物与内置材料的验证。 |

三张台账表在迁移末尾建立，按事项建普通索引，进入 `pullTables`，均用已有的 `updated_at` 比较；它已在 `pull.ts` 的时间列正则中。没有投影表或触发器。为保存确认前的计划和对账结果，方向另存 `plan / removed / note`；候选发现和拿不准标记留在试验的 `findings / unsure`，后端失败次数与是否已升档也随试验保存，避免跨轮后重复重试。正式发现另记创建时的流程起点与轮次；连续无发现按这两个字段计数，更新判定和合并旧依据不会冒充新发现。拉取通用 SQL 给列名加了引号，支持试验的 `check` 保留字；正文、JSON 和引用照原有流程映射。

提案允许零到三个方向。只把有结果、对象和检查项在去掉首尾空白、大小写和连续空白后完全相同的试验去掉，并保存以前结果与摘要首行；同对象的新检查保留，带 `prior`。方向本身不会因以前通过而删掉。提案先存 proposed，选中以后才建 queued 试验；本人可附要求，进入方向的 note 和每个试验任务。没选的方向记 dropped（“本轮未选”）；空提案也要本人点“知道了”，或本人选“这一轮不跑”后，余下阶段写原因并跳过。自由文本没有选项时会重新提问，不擅自选择。有 active / confirmed 方向且还有试验时，下一轮直接跳过定方向。

阶段 `tools` 只接受 study 分组。主助手默认清单有 `write_file`、排除了 `write_page`，因此梳理任务指定写事项所在空间的 `work/studies/<事项 id>/capabilities.md`，`stage_report.evidence` 交返回的 `src:` 引用。定方向任务不复用含历史运行入口的事项材料清单，只给事项说明、功能清单位置、覆盖次数与日期、会话位置和最近提交；运行移除台账和历史运行阅读工具，`read_ledger` 本身仍按阶段副本检查，即使误授也拒绝。试验任务只含方向、本人的话、本试验和 prior，不带别的试验结果。

试验一次只跑一个，`trial_report` 只认当前试验自己的运行。`evidence` 的文件只能在该运行的 `$OMEM_ARTIFACTS` 下，复用现有产物保存；`src:` 经过空间校验。findings 是候选，只有小结调用 `record_finding` 才进正式表。依据至少一个本课题有结果的试验；标题按英文词、中文二元组重合提示相近项，必须明确 same_as 或 distinct_from。same_as 只合并依据，不重置本人的 rejected / later 判定。

没交结果或 unclear + unsure 可对这个试验升档一次，且受本轮升档次数、分钟预算限制；后端失败重试一次，再失败 blocked。试验数按最终完成的不同试验计，重试的运行时间也计入分钟。预算用满时完成本轮试验阶段，没做的保留 queued；分钟预算由既有巡检取消当前运行，取消有巡检间隔的延迟。窗口只限制开始，不中断已运行的试验；worker 真正开始前再检查窗口和额度，额度只等待原模型。队列做完方向仍 active，由小结决定 close_direction；结束方向跳过未做的试验，正在运行的取消。停止流程取消当前试验并放回队列，已经交的结果保留。

接口返回的数据和事项的其他视图一样用驼峰字段名（`directionId`、`runId`、`stateReason`、`updatedAt`）：

- `GET /api/items/:id/study` → `{ directions, trials, findings, coverage, idleRounds }`。directions 带解析后的 plan / removed，以及 counts（queued / running / skipped / passed / failed / blocked / unclear）；trials 为最近更新的 200 条，带 evidence、候选 findings 和 artifacts；正式 findings 的 trials 展开为依据试验（含产物）。coverage 是 `{ path, ref, features: [{ title, trials, lastAt }] }`，按对象文字包含功能标题粗略统计，不含结果。
- `POST /api/items/:id/study/findings/:finding` 收 `{ state: confirmed / rejected / later, reason? }`，只改这一条；`POST /api/items/:id/study/directions/:direction/close` 收 `{ state: done / dropped, conclusion }`。均返回课题视图，写限事项本人和可写空间。
- `POST /api/items/:id/study/choose` 收 `{ direction: 方向 id 或 null, note? }`：本人在事项页选这一轮的方向（`null` 是这一轮不跑），和在卡片上回答是同一个提问、同一套校验；没有等选的方向时 409。
- `flowView.flow.study` 标出这是一份课题流程；定方向阶段等本人选时，它在 `flowView.stages[]` 里带 `asking: "direction"`，事项页据此把选择放进台账里。
- `flowView.flow.idleRounds` 为连续完成且无新发现的轮数。`flows.idleRounds` 默认 3；非 manual 达到时清空 nextRoundAt，仅发一次 later 通知，把下一步留给本人。manual 只显示计数，不通知。

与旧设计稿的差异：功能清单是工作文件，方向结论只存台账，不写 Wiki。env 本期只是文字，不代表执行环境授权或远端调度。预算列在方向提问中，本人确认后采用；调整走第一期已有的阶段预算接口，本期没有新做卡片预算表单。没有给任何内置角色默认加入 study 工具；同伴设备的外部工具入口也不开放这组工具。真实模型与真实渠道未跑，按本期任务用假运行验证。

试验的运行不挂进事项材料（一个课题会有几百个，台账里每个试验带着它的运行）。

事项页的“课题的台账”（`web/src/components/ItemStudy.vue`）：顶上是在做的方向和一条试验进度；下面分四块——发现（没判定的在前，认可 / 不算 / 以后再说）、试验（没做好的在前，展开看摘要、依据和产物）、方向（等选时在这里选，在做的可以结束并写结论）、覆盖（各功能试过几次、哪些没碰过）。

未做：试验内编码交办、持续推送授权、执行环境登记、另一台设备执行、课题简报与数据页。验证命令和实际数字见 `acceptance.md` 的“课题第二期服务端”。

## 第四期的一部分：数据页、简报、coach

本期只改服务端、角色说明、测试和文档，没有改网页，没有新增表、设置、接口、定时任务或触发器。

- 数据页在编码交付后增加“课题”。所选期间有已交结果的试验才出现，按事项的可读空间限定。试验按交结果的 `updated_at`、发现按 `created_at`、结束方向按 `updated_at` 计数。试验结果按事项标题列通过、没通过、跑不了、说不清；发现列总数、认可、不算、未判定（new / later），duplicate 只在总数中；方向列结束总数、做完、放下。发现的判定是当前状态，不是历史快照。发现多少不代表做得好坏，不排名、不计算发现率。
- 试验运行沿用日期范围内的 `runs_insights` 取数，再按主键核对事项归属，含重试与升档。档位解析后只保存后端、模型、强度，没有档位名，故按运行 `ai.model` 计数，未记下的单列。运行按创建时间，与按交结果时间的试验数不是同一口径。三个台账查询都从可读事项出发走事项索引；试验关联运行用主键取，不扫描大运行表。
- 每个数字都能回到记录。`RecordRef` 已支持任意记录的 id、label、at、link，无需改结构：有可读运行的试验链接到运行，其他试验、发现和方向链接到事项。Markdown / CSV 导出沿用通用板块输出。按人、场景、模型等运行维度筛选时，试验按交结果的运行匹配；发现和方向没有运行归属，此时省略并说明。
- 每日简报是 `src/agents/jobs.ts` 的 `brief`；`digest` 是存量原件整理。宿主用原有 `brief_at` 和本次开始时刻圈定已结束轮次，按 `isStudy` 判断课题，拼“上一轮的探索”：事项链接与轮次、方向目标、四种试验结果计数、本轮发现标题最多五条及余数、当前未判定发现数与待选方向。无结束轮次不加这一节。生成成功后推进原有边界，失败不推进；生成期间结束的轮次留给下一份。只取当前流程副本起点对应的轮次，避免流程重启后把不同流程的同号轮次混在一起。
- `roles/brief.md` 要求探索节照材料写、不评价、不补充，没有材料就不提课题；简报角色没有 `read_ledger`。coach 的精确清单增加 `read_ledger`，课题技能或课题阶段触发读台账，依据反复 unclear / blocked、rejected 发现及原因提出技能建议，不替本人判定。现有处理函数对无流程阶段的 `profile-review` 运行可用，空间校验保留；没有改 `src/studies/` 已有行为。本人自定义过、未跟随源码的 coach 不会自动得到新工具。

尚未做：另一台设备执行试验、有改动的发现计数、真实模型和真实通知验证。台账没有完整历史快照，简报按当前保留的轮次事实汇总，不推断旧结果。检查命令与实际数字记在 `acceptance.md`。
