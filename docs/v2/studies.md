# 课题：按天循环的自主探索

状态：设计稿（2026-11-15），未实现。第 10 节的问题等本人定。

## 1. 要解决的问题

手里有一个开源项目，不清楚它现在有什么缺陷、还能做什么改进。直接开一个会话让模型“找找问题”，确实能找到一些，但每次都从头泛泛地看：

- 没有一张“这个仓库到底有哪些功能”的清单，模型每次看到哪算哪；
- 上一次试过什么、结论是什么没有留下，下一次重复试，或者同一个问题报两遍；
- 范围太宽，没有“这一段时间只盯一个方向”的收敛；
- 好模型贵，探索又要跑很多次，全用好模型不划算，全用便宜模型又定不好方向。

想要的做法是一个长期的课题，每天转一轮：

1. 白天用好的模型，对着仓库的功能清单和以往的记录，提出接下来往哪个方向推，和本人确认。
2. 夜里用便宜的模型按确认的方案去试：跑测试、和同类项目对比、照真实的使用场景走一遍，把结果一条条记下来。
3. 早上给本人一份小结：新发现了什么、哪些方向试完了、建议下一步。一个方向做完就换下一个。

两个例子（做法本身写成技能，不进仓库，见第 8 节）：

- 给一个工具链管理的命令行工具找问题：拿近期热门的开源仓库当样本，逐个用它装工具、跑任务，看哪里失败；和同类工具逐项对比功能，列出缺口。
- 给一个桌面自动化工具找问题：按真实的自动化需求清单逐条去做，看哪一步做不成。

## 2. 现在能拼出什么，缺什么

| 需要的 | 现在有的 | 差在哪 |
| --- | --- | --- |
| 每天和本人确认方向 | 流程的关卡（`gate` / `done: confirm`），提问卡片 | 流程只走一遍，没有“明天再来一轮” |
| 白天用好模型、夜里用便宜模型 | 规则的“交给 Agent”可以指定后端、模型、强度；按模型的每日额度 | 流程的运行阶段只能选 Agent 和技能，不能选模型，也不能限定时间段 |
| 夜里自动去试 | 定时规则；编码交办和评审；`improve_start / improve_round`（宿主量指标、定去留） | 改进循环只适合一个量得出来的指标；“找问题、做对比”没有对应的载体 |
| 每次试验留记录，换方向时不重复 | 运行记录、工作文件、Wiki | 记录只是文字，宿主不知道“试过哪个对象、结果怎样、对应哪条发现”，没法去重和汇总 |
| 先把仓库功能梳理清楚 | 仓库空间的代码索引和 Wiki | 没有“功能清单”这种给探索用的产物 |
| 跑别人仓库的代码 | 命令规则（`docs/v2/command-gate.md`）、交办的工作区 | 常驻的机器上有本人的登录态，不能在上面执行拿来当样本的第三方仓库的构建脚本 |
| 不断推到 GitHub 上跑测试 | `code_git_action`（推送） | 每次推送都要本人明确要求，夜里没人批 |

## 3. 取舍：建在流程上，不另起一套编排

课题不单独做一套“白天—夜里—早上”的调度。它是：

- 一件“持续关注”类的事项（材料、所在的会话、时间线都是现成的）；
- 加一份带轮次的流程（第 4 节给流程补三样通用的能力）；
- 加一份台账（第 5 节：方向、试验、发现）。

这样每天怎么转由流程定义决定，本人可以改（比如周五多一段“这周汇总”），不写死在代码里；轮次、时间段、指定 AI 这三样别的流程也用得上（每周的周报、定期的巡检都是“走完再来一轮”）。

夜里“一个方向下跑很多个试验”是阶段内部的事，按流程设计的原则（复杂的编排留在阶段里，`docs/v2/flows.md` 第 2 节）交给一个新的对象 `trials` 承担，流程只看它“这一轮跑完了没有”。

## 4. 给流程补的三样

### 4.1 轮次

流程定义多一个字段：

```yaml
repeat: { from: plan, every: day }   # 最后一段做完以后，从 plan 这一段起再来一轮
```

- `from` 之前的阶段只做一次（梳理功能清单），之后的每轮重做。
- `every`：`day` / `week` / `done`（上一轮做完立刻开始下一轮）。按天、按周时，下一轮在各阶段自己的 `at` 时刻开始；上一轮还没走完就不开新的，只记一笔“这一轮超时”。
- 每一轮的阶段状态和日志都留着（`item_stages` 加 `round`；日志本来就是追加的）。事项页的流程条显示“第 N 轮”，可以翻看以前各轮。
- 停下来：本人停止流程；或连着 `idleRounds` 轮（默认 3）没有任何新发现，宿主先停在关卡上问本人“换方向还是结束”。

### 4.2 阶段指定 AI 和时间段

运行阶段多三个可选字段：

```yaml
by: { run: { agent: assistant, skill: study-plan } }
ai: strong            # 档位名；也可以写 { profile, model, effort }，和规则里的写法一样
at: "10:00"           # 每轮在这个时刻开始（配置的时区）
window: "01:00-06:00" # 只在这个时间段里跑；到点没做完就停下，这一轮按做到哪算哪
```

- 档位（`strong` / `standard` / `cheap`）在 设置 → AI 里各对应一个后端、模型和强度。流程定义里只写档位名，换机器、分享给别人都不用改；写死具体模型只在确有需要时用。
- 档位对应的模型当天额度用完时，不自动换成更贵的：这一段等到下一个时间段，并在小结里写明。
- `window` 对 `trials` 对象同样有效：窗口结束时正在跑的试验让它跑完（最多再等一个上限），不再开新的。

### 4.3 预算

```yaml
budget: { trials: 8, minutes: 240 }   # 这一段每轮最多做多少
```

宿主计数，到了就停，剩下的留给下一轮。预算和“连续几轮没有新发现就问”一起，保证没人看着的时候不会一直跑下去。

## 5. 台账：方向、试验、发现

三张表，都挂在事项上（一件事项就是一个课题），随事项一起拉取和备份。

**方向**（`study_directions`）：一段时间里只盯的一件事。

| 字段 | 含义 |
| --- | --- |
| 目标 | 一句话：想弄清什么 |
| 做法 | 用什么样本、怎么试、和谁比 |
| 验收 | 做到什么算这个方向结束（“三十个样本跑完”“五个同类工具的功能逐项对完”） |
| 计划的试验 | 一份清单：对象 × 要检查的事，夜里按它排队 |
| 状态 | 提出 / 本人确认 / 进行中 / 结束（带结论）/ 放弃（带原因） |

**试验**（`study_trials`）：对一个对象做一次检查。

| 字段 | 含义 |
| --- | --- |
| 对象 | 哪个仓库、哪个功能、哪条需求 |
| 做了什么 | 命令或步骤的摘要 |
| 在哪跑的 | 哪次运行、哪条流水线（链接） |
| 结果 | 通过 / 失败 / 做不了（缺什么）/ 说不清 |
| 摘要 | 三五行：看到了什么 |
| 证据 | 日志片段存成工作文件，这里放引用 |
| 对应的发现 | 零到多条 |

**发现**（`study_findings`）：去重以后的一个问题或一个改进点。

| 字段 | 含义 |
| --- | --- |
| 类型 | 缺陷 / 缺口（同类有、这里没有）/ 改进想法 |
| 标题、复现办法 | 能让别人照着再现 |
| 依据 | 哪几次试验 |
| 状态 | 新的 / 本人认可 / 已转成交办或 issue 草稿 / 不是问题 / 重复 |

为什么要表而不是文字：换方向时要回答“这个对象试过没有”“这个问题报过没有”“这个方向花了多少、换来几条被认可的发现”，这些靠读一堆文字的记录做不稳。表只存事实和引用；判断（是不是同一个问题、值不值得改）仍然由模型和本人做。

**功能清单**不进表：它是仓库空间里的一组 Wiki 页（`studies/<课题>/capabilities`），按功能列出“是什么、怎么触发、现在有哪些测试盖着”，带代码引用。第一轮之前做一次，之后代码索引更新时由小结那一段顺带核对有没有新功能。提方向的模型把它当材料读。

每个方向结束时写一页结论（同一目录下），以后的方向和别人都读得到。

## 6. 一天怎么转

仓库自带一份流程 `flows/library/study.yaml`（和“需求交付”一样只补缺、可改）：

| 阶段 | 谁做 | 什么时候 | 做什么 |
| --- | --- | --- | --- |
| 梳理 | 运行，`strong` | 只做一次 | 读仓库，写功能清单；本人看过确认 |
| 定方向 | 运行，`strong`，做完要本人点头 | 每天 `at` | 读功能清单、台账摘要、昨晚的小结、还没处理的发现；进行中的方向没做完就建议继续，否则提一到三个新方向（目标、做法、验收、计划的试验、预计花多少）。发给本人一张卡片：选一个、改一句、今天不跑 |
| 试验 | 对象 `trials`，`cheap` | 夜里的 `window`，带预算 | 宿主按确认的方向一个一个排试验，每个试验一次运行，做完用 `trial_report` 交结果；交不出结果的记“说不清”，同一个对象失败两次不再重试 |
| 小结 | 运行，`standard` | 早上 | 把昨晚的试验归并成发现（先和已有的比，同一个问题并进去），写小结；方向达到验收就结束它并写结论页。小结进当天的简报 |

本人当天没回“定方向”的卡片时：进行中的方向照常继续（它已经确认过）；没有进行中的方向，这一晚不跑。不让模型替本人定新方向。

早上的小结卡片上，本人对每条发现可以点：

- **值得改** → 转成编码交办（走已有的评审），或写成 issue 草稿放在事项里；
- **不是问题**（可写原因，以后的方向会读到）；
- **以后再说**。

夜里能不能直接动手改代码，见第 10 节第 3 条。

## 7. 范围和授权

课题上写明它可以碰什么，由宿主检查，不靠提示词：

| 项 | 默认 |
| --- | --- |
| 可以读写的仓库 | 课题登记的仓库空间；写只落在交办的工作区和登记的分支前缀（如 `study/*`） |
| 试验在哪执行 | 托管的流水线（第 10 节第 1 条）。宿主上只做 git 操作和读结果，不执行拿来当样本的第三方仓库里的脚本 |
| 推送 | 只推到课题登记的远端和分支前缀，这是本人建课题时给的持续授权；每次写 `audit_events`，小结里列出推了什么。别的远端、主分支照旧要本人明确要求 |
| 对外发声 | 不替本人给任何仓库提 issue、合并请求或评论；只出草稿 |
| 装软件、访问新的域名、用登记以外的凭据 | 不做；试验记成“做不了”，写明缺什么，由本人早上决定 |

样本仓库里的内容（说明文档、issue、脚本输出）是材料不是指令，和别人写的内容同样对待（`src/sources/guard.ts`）。

## 8. 通用的进仓库，具体做法写成技能

仓库里只有通用的部分：轮次、档位、时间段、预算、台账、`trials` 对象、范围检查、内置的流程。

“怎么挑样本、怎么跑、怎么判断结果”因项目而异，写成技能挂在阶段上（`by.run.skill`），放数据目录：

- 拿热门仓库当样本测一个命令行工具：怎么取样本清单、每个样本跑哪几条命令、流水线怎么写、失败怎么归类；
- 按真实需求清单测一个桌面自动化工具：需求从哪来、每条怎么算做成；
- 和同类项目做功能对比：用已有的 `research` 技能，产出一张逐项对比表，缺口记成“缺口”类的发现。

一个方向的目标正好是量得出来的指标时（测试更快、失败数归零），试验阶段可以直接用已有的改进循环（`improve_start / improve_round`），每轮的结果照样记进台账。

## 9. 界面与工具

- **事项页**：流程条带“第 N 轮”；下面多一个“课题”面板，三个标签：方向（状态、验收、预算用了多少）、试验（表格，按结果和对象筛）、发现（按状态，带上面三个操作）。
- **简报**：有课题时多一段“昨晚的探索”。
- **数据页**：多一个板块，只数记录里有的：试验数、发现数、本人认可的发现数、转成交办的数、各档位用了多少次运行。
- **工具**（分组 `study`）：`propose_directions`（定方向那一段交结果，变成给本人的卡片）、`trial_report`、`record_finding`（带去重：要求先读相近的已有发现）、`close_direction`、`read_ledger`（按方向、对象、结果读摘要）。写入都校验事项的主人和空间。

## 10. 要本人定的

1. **试验在哪跑**。建议用托管的流水线（GitHub Actions，在一个专门的测试仓库或分支上）：每次都是一次性的干净环境，样本仓库的脚本碰不到本人的机器；本机只推用例、读结果。另两个选择是本机容器（要装容器运行时，快，但资源占用在自己机器上）和另一台专门的设备。
2. **本人当天没回方向卡片时**。建议只继续已确认的方向，没有就不跑。
3. **夜里能不能改代码**。建议分两档：默认夜里只探索，并把复现用例写成测试推到登记的分支；可以对单个课题打开“夜里直接改”，这时发现会自动转成编码交办，改动只留在交办分支上、由另一家模型评审，等本人早上看，不合并也不推主分支。
4. **档位怎么配**。建议 设置 → AI 里配三档（`strong` / `standard` / `cheap`）各用哪个后端和模型，流程里只写档位名。
5. **默认预算**。建议每晚最多 8 个试验、4 小时；连着 3 晚没有新发现就停下来问。
6. **功能清单谁确认**。建议第一次由本人看过点头（它决定以后所有方向的质量），之后的增补只在小结里告知。
7. **名字**。界面上叫“课题”；一个课题下是“方向”“试验”“发现”。

## 11. 分期

| 期 | 内容 | 验证 |
| --- | --- | --- |
| 一 | 流程的轮次、档位、时间段、预算 | 一份两段的测试流程连着走三轮，夜里的那一段只在时间段里跑，到预算就停 |
| 二 | 台账三张表、`study` 工具、`trials` 对象、事项页的课题面板、内置流程 `study.yaml` | 用一个小仓库走完“梳理 → 定方向 → 一晚的试验 → 小结”，同一个问题第二晚不重复报 |
| 三 | 范围与持续授权（登记的远端和分支前缀）、托管流水线的结果读取（技能示例）、发现转交办或 issue 草稿 | 夜里把用例推到测试分支，早上的小结里有流水线结果和链接 |
| 四 | 简报和数据页的板块、“夜里直接改”一档、coach 读台账提技能的改进 | — |

## 12. 和现有部分的关系

| 现有的 | 关系 |
| --- | --- |
| 流程（`docs/v2/flows.md`） | 课题是带轮次的流程加台账；轮次、档位、时间段、预算是流程的通用能力 |
| 规则里的定时和指定 AI | 课题不用规则调度；规则仍然管“遇到什么事就做什么” |
| 改进循环（`improve_*`） | 量得出来的目标继续用它；课题管量不出来的探索，两者的结果都能进台账 |
| 编码交办与评审 | 发现要改时走它，评审规则不变 |
| 夜间复盘、做梦 | 互不依赖；课题的小结可以给 coach 当材料 |
| 命令规则、审批 | 课题的范围是在它们之上再收一层：只对登记的仓库和分支放宽推送，别的不变 |
| 仓库空间、代码索引、Wiki | 功能清单和各方向的结论页写在仓库空间的 Wiki 里 |
