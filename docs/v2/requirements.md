# 需求树：需求点与测试点

一个业务空间里“系统应该做什么”的长期记录。交办编码按它开发，评审按它核对，以后有人问“这个功能当初为什么这么做”也查它。实现在 `src/items/requirements.ts`，网页是“需求”页（`web/src/views/Requirements.vue`）。

## 为什么不是 Wiki

Wiki 页面是成段的文字，写作角色会整页重写。需求点要的是：固定的编号、按节点记录的每次变更、每轮编码和评审在每个点上的状态、交办和评审能指向某一个点。所以需求树是结构化数据，Wiki 可以引用它，但不承载它。

## 结构

- 每个空间一棵树。节点类型：系统、模块、页面、功能（需求点）、测试点。空间本身就是一个产品，系统按端分（PC端、移动端，必要时 C 端展示、服务端接口）；模块是业务模块或一级菜单下的能力；页面是一个界面或一段独立流程，跨页面的公共规则单独一个页面，各处 `link` 过去而不是抄。层级不要求每层都有，测试点只能挂在功能或测试点下（`PARENTS`）。功能点、测试点怎么写见 `roles/req-splitter.md`。
- 节点字段：标题、需求原文（`body`，带 `src:` 引用回到原件）、验收、依据（`refs`）、测试点对应的测试（文件 › 用例名）。
- 树跟着业务空间走，不属于某个事项。事项用材料 `kind: req` 圈出这次要做的节点（连同它下面的全部）。
- 跨业务：节点之间可以关联（`req_links`，可以跨空间），一边改动时另一边的交办能看到关系；不在两边各复制一份。读对方要能访问对方的空间。

## 变更与历史

每次修改是一个版本（`req_versions`，存修改后的样子），分两种：

| 修改 | 含义 | 要求 |
| --- | --- | --- |
| 更正 `correct` | 写错了、拆错了，没有业务含义 | 无 |
| 业务变更 `change` | 规则本身变了 | 必须写原因，最好带依据（群聊、会议、文档的 `src:` 引用） |

删除也分两种：`delete`（写错了，删掉）和 `remove`（业务不要了，要写原因）；都连同下级，都能恢复，历史都在。节点页的时间线按版本列出，业务变更单独标出，留给以后决策时回溯。

Agent 写的节点（拆需求、助手按本人的话改）标为“待本人确认”，本人在需求页确认（含下级）；本人自己改的直接算确认。交办和评审的说明里会标出待确认的点。

## 检索

功能、页面、模块、系统进全文检索（`reqs_fts`，标题是树里的路径，正文是需求和验收），`search` 的 `scope: "requirements"` 只查它们；测试点不进检索。检索结果的类型是 `requirement`。

## 和交办、评审接起来

1. **拆**：事项页“拆需求点”或 `split_requirements` 起一个 `req-split` 运行，内置角色 `req-splitter` 读事项的材料和空间里已有的树，用 `save_requirements` 写进去。运行结束后，它这次新建或改动的最上层节点自动挂到事项上。
2. **编码**：交办带上事项时，编码 Agent 的任务里有“需求点”一节（`reqBrief`）：圈定的节点和下级、验收、测试点、待确认标记、跨业务的关联；续轮还列出交办开始以后的业务变更。
3. **评审**：需求拆分（`submit_change_points`）按需求点逐个给变更点，`req` 填需求点 id；每个需求点在这一轮的状态和代码位置记进 `req_status`，需求页和事项上显示“最近一次评审：已实现 / 部分实现 / 没实现”。需求外的改动是不带 `req` 的 extra。
4. **之后修改或补充**：在需求页改（选更正或业务变更），或对助手说；下一轮交办和评审读到的是改过的树。

## 拆分怎么越拆越准

本人在需求页对 Agent 写的节点做的更正和删除（`req_versions` 里 `by = 本人`、`correct` / `delete`）就是反馈，`ownerCorrections` 取出来用在两处：

- 下一次在同一个空间拆需求时，任务里列出本人最近的修改，同类问题直接避免；
- 教练复盘 `req-splitter` 时，每次拆分运行的证据里带上本人之后确认了多少、改了什么、删了什么，复盘据此提出改说明、挂技能或记经验的建议，由本人确认。

需求点本身不复制进记忆：它们已经可检索，业务上的变化有版本和原因；记忆只记拆分的做法（经验、偏好），不记具体规则。

## 页面

为事项做的编码也在需求页看（`src/items/work.ts`）：事项的 `req` 材料圈定它在树上的范围，`run` 材料是为它做的交办和分支评审。选中这个范围里的节点（或它们的上级），详情里“编码与评审”列出这些工作，一次交办连同各轮算一项，标出阶段（编码中、评审中、等外部 Agent、等你处理、已评审、已应用、已丢弃）、等你做什么、几个问题还没定。点开后右栏换成这次交办的评审概览（和运行页的概览同一个组件），定问题、开始下一轮、应用或丢弃都在这里；差异、活动和工作分支的推送去运行页。树上事项挂着的节点标“等你 N”，可以只看等你处理的。带事项的交办和分支评审放在事项的空间，运行记录按这个业务空间能找到。

需求页左侧的树可以折叠（每个空间记住折叠状态，第一次打开只展开到模块），“全部展开 / 收起”，可以隐藏测试点；搜索按标题、需求、验收和 id 过滤，匹配项连同上级路径一起显示。

## 可以定制

拆需求这一步是内置角色 `req-splitter`（`roles/req-splitter.md`），本人在 Agent 页可以：

- 改它的说明（拆到多细、按什么模板写测试点）；
- 给它选模型；
- 挂技能：比如内部测试平台的技能，拆完后照技能在平台上同步生成测试用例，把用例链接或编号写回测试点。内部平台的命令和字段只写在数据目录的技能里，不进仓库。

技能要跑命令时，角色的 `modes` 要允许（默认先用只读模式）；在 Agent 页的角色设置里改。

## 工具与接口

- 工具（分组 `items`）：`req_tree`、`req_read`、`save_requirements`（一批操作，原子执行；`add` 可用 `key` 起名，后面用 `$key` 引用）、`split_requirements`。编码和评审角色有 `req_tree`、`req_read`。
- HTTP：`GET /api/requirements?space=`、`GET /api/requirements/:id`、`POST /api/requirements`（`{space, ops}`，本人写入）、`POST /api/items/:id/split-requirements`。
- 设备之间拉取（`omem peer pull`）带上四张表，拉过来的节点重建检索。
