# 日志能解释到哪一步

统一运行日志现在覆盖后台任务、Agent 调用与检索决策，并记录 API 异常。默认 info 可看任务完成、失败与降级；debug 才保留逐条材料判断。用户从 `omem service status --json` 确认服务与日志位置，再用 `omem service logs` 按任务、来源或消息筛选。完整参数和保留策略见[日志使用指引](../../skills/omem-cli/references/logging.md)。

例如知识生成失败，先找到对应 jobId。`job.failed` 说明任务是否进入重试；同一上下文中的 `acp.failed` 继续给出 Agent profile、initialize/session/prompt 阶段和错误类别。acpCallId 区分同一个任务内的多次模型调用。没有 stderr 原文，只有长度、摘要与认证提示。这样能区分 Agent 没连上、已经开始输出后超时和任务校验失败，也避免把模型回复写入常规日志。

检索问题需要 debug 日志。`retrieval.passage_decision` 对每个已判断候选保存分类结果和过滤理由，保留 hitId 及可取得的 sourceId；问题只保存 queryDigest。`retrieval.selection` 汇总保留、移除和未判断的数量。模型未就绪或超过决策等待范围时，`retrieval.decision_skipped` 记录跳过原因。全被过滤后弃权会保留原候选，日志明确标记，不能把它理解成相关性已经通过。

## 运行日志与正式记录

运行日志使用 [Pino](https://github.com/pinojs/pino)，JSON 每行一条。AsyncLocalStorage 传递任务及消息上下文；Fastify 的安全日志控制器保留异常，关闭普通请求成功日志。原始材料、请求正文和工具输出不进入这些事件，错误消息也不会整段复制。常见凭据格式和敏感字段统一脱敏。stdout 继续留给 CLI 的结果，日志写到 stderr。

这些记录帮助排查某次运行。个人库继续保存正式任务状态与固定材料版本，也保存模型结构化输出和事实应用；关闭日志等级不改变它们。调查工作区中的 research.jsonl 与角色产物是另一类个人数据，按数据生命周期管理。需要复查模型读过什么时继续查调查记录，不能仅凭运行日志判断模型已经理解。

## 常驻服务的保留

PM2 与 pm2-logrotate 随 npm 包安装，版本由项目依赖锁定。轮换模块从本地包目录加载，服务启动不隐式安装全局模块。PM2_HOME 位于当前个人目录，日志在 `service/pm2/logs/`，不会管理机器上其他 PM2 项目。

默认阈值为每个文件 10 MiB，每 10 秒检查；每天本机零点也轮换，最多保留 7 份压缩归档及当前文件。PM2 的 daemon 日志也覆盖在内。配置 `logging.maxSizeMB` 和 `logging.retain` 可调整，重启后应用。轮换加载失败使启动命令失败；状态单独报告模块是否在线，配置本身不能证明轮换正在运行。

当前日志查询只读现行文件末尾，不检索压缩历史，也不提供持续跟随或全库日志搜索。旧普通文本会被跳过，升级不会替用户擦除历史文件。轮换按时间检查，突发输出可能越过大小阈值；磁盘占用仍需通过数据目录和系统工具检查。

## 本轮验证范围

日志与已有任务/Agent 协议测试检查了脱敏、并行上下文和超时/取消的真实退出码。Fastify 使用实际请求执行异常路线。PM2 的隔离轮换验收使用临时合成日志，核对安装包的本地模块加载、关闭 watch 与压缩归档份数；这不代表真实用户材料的阅读质量或外部 Agent 调用通过。
