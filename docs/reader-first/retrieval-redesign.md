# 统一检索与材料理解

这轮把三项作为同一条用户流程验收：先找到解释，再读实现和原件；按查找目的组织结果。不能分别通过几个排序测试就声称整体有效。

## 一、讲解本身成为结果

原来的 `knowledge/retrieval.ts` 虽然搜索文章段落，但返回的是引用对应的原始 Fragment。顶部搜索和助手因此失去已整理的解释。现在使用统一的 `RetrievalHit`：讲解命中保留原文段落、文章、章节、固定文章版本与原件引用；原件、记忆和事项分别保留自己的类型和入口。讲解是派生背景，不冒充第二份事实。

正式文章、参考页和内部笔记已在发布时区分，内部笔记不进入默认知识召回。调查读取用于保留研究轨迹，不再一律成为过期依赖。实际引用和作者登记的章节 `reviewSources` 决定哪些内容需要重新核对；原件身份、时间等元数据变化也参与判断。

文章按节判断可用性：原文预算变化后，引用预算或把它登记为背景前提的章节暂时退出当前召回，仍有依据的集合说明可以继续参与。判断比较的是固定原件中的完整 Markdown 章节或代码结构；结构唯一且内容相同可承认移动行号或其他章节修改无关。原件换版不会修改旧文章引用的固定版本。定位不可靠、原件不可用或前提变化时明确待核对，不能把局部结构比较当作完整语义不变。实现与限制见[发布和维护](publication-lifecycle.md)。

文章链接仍沿保存时的子文章修订回溯。可见性检查保留在候选和补读边界，派生解释不取得事实直接写入权限。

阅读列表按文章修订和章节去重，同一节先返回分数最高的段落与该节入口；其他章节仍可入选。不再让同一节的两段消耗整篇文章的名额，也不把正文合并成脱离固定范围的新文本。显式 `diversify=false` 关闭这些阅读分组限制，排序及来源过滤仍生效。这个边界借鉴 [LlamaIndex 的节点引用检索](https://developers.llamaindex.ai/python/framework/integrations/retrievers/recursive_retriever_nodes/)中“细块用于命中、父级用于理解”的分工；引用适用性判断是 omem 自身的版本规则，不是该库提供的语义正确性保证。

助手对同一原始 Fragment 中不同函数或段落使用各自的引用别名，保存准确来源版本和行范围。模型返回的别名在事项应用时还原成原件锚点，在阅读时转为章节或函数名称；Markdown 正文与固定范围引用使用同一套阅读组件。旧会话仍能打开原来的片段，没有准确范围时不假造行号。

### 候选、回答上下文与阅读列表分开

助手首轮召回、原始材料 MCP 搜索和知识 MCP 搜索使用 `diversify=false`。同一文件的第三个必要事实不再因阅读列表的两段上限被跳过；同一知识章节的多个相关段落也可以返回。界面搜索仍按来源/章节去重。当前候选总数仍有限，尚未实现完整答案要点覆盖选择。

`retrieval/context.ts:sourceContextRange` 在候选选出后，把原文命中恢复为包含该范围的最小完整 Markdown 章节或代码结构，助手按恢复后的固定范围去重。这样，“必须提前预订”的命中能同时带上同节“周三18点截止”的条件；不需要让截止时间碰巧也匹配查询词。扩展只能读取同一修订、通过可见性检查的范围；无明确结构时保留原命中，不默认附整份文件。派生文章的引用仍按原来的固定范围读取，不把自动补读改写成文章自己的引用。

父关系现在独立保存在 `retrieval_contexts`：每个原文版本有文档根节点、章节/符号节点、父子 ID，以及检索段落到最小完整上下文的归属。复用已有 marked 和 TypeScript 结构解析，不把父章节复制成一批额外排名结果。补建关系不改变现有检索单元或向量身份；原文换版只更新该来源的投影，旧引用仍按旧版本恢复上下文。

`sourceContextRanges` 同时提供命中章节及其上级章节开头的说明，分别保留固定行范围和引用。例如“渡轮预订”除了带上截止时间，还会带上上级的“仅适用于提前报名的参加者”；不会把其他交通章节整个塞进答案。这个规则只补结构中明确写出的前提，不能识别藏在任意后文或其他文件里的全部条件。

`assistant/context.ts` 现在独立装配回答材料。派生文章命中后读取同一固定文章版本的完整相关章节，合并该节各段引用的原件；同一章只交付一次，其他章节不会因为相邻就附带进入。只有仍获准召回、全部背景和固定引用可见的章节才展开；外部适配器没有本库章节投影时保留原命中。原文仍按自身章节/函数恢复，派生解释与原件分别传给模型。

首轮先取 48 条候选，再按原排名选择最多 16 个不同阅读上下文，替代直接截取 16 个检索段落。数量是候选和阅读入口的范围，不是模型输入输出 token 限制。已选章节的引用一起保留，不再最后截断到 28 条原件而丢掉条件；追加搜索合并相同背景及固定引用。它不判断哪段一定回答问题，也不改变底层排名。完整章节可能增加无关文字和阅读成本，需用同快照实际回答比较；不能把补读更多当成质量提高。

同快照的三题真实 Traex / Sol medium 阅读对照已完成，每题各读旧、新两种输入，不允许额外搜索，以隔离材料组织的影响。补材料问题由 14 段背景（6 章）变为 8 个完整章节，原件范围 18→38，序列化输入约 4.34 万→8.82 万字符；新旧都能给出“调整材料与目标→补选→保存并重新整理”及旧文保留规则。模型失败是否保留知识的问题，两边均能区分已有文章与首次生成；英语复习问题输入完全相同，两次回答仍有措辞差异，均未声称已实现间隔重复。这三题没有证明质量净收益，也不能评估完整自主调查；这次直接阅读的约 16～19 秒不代表 Agent 调查延迟。原始输入、答案与 trace 覆盖同一份 ignored `runtime/research/answer-context-comparison.json`，不持续发布整库副本。

完整自主调查另跑了“补充背景为什么未更新正文→怎样补选另一份材料、失败是否丢旧文”的同会话两轮。Sol 使用 `read_section`、`read_material` 补读，第二轮给出了取消“只看已选”后搜索新材料的具体步骤，以及旧正文和新计划保留的结果；实际约 119/126 秒，无降级。运行前后语料身份相同，问答不进入原件索引，复制数据库在结束后释放；结果保存在 `runtime/assistant-compare/context-follow-up/report.json`。这证明新装配仍接通原生工具和连续咨询，不证明跨轮对象解析已普遍可靠，也不是新旧 Agent 的受控质量对照。

连续追问还修复了一个实际材料丢失点：上轮引用横跨多个保存片段时，`priorWorkingContext` 原先要求整段文字包含在第一个 Fragment 内，失败便退回第一片段。例如一章依次说明“预算八十元”“不含交通费”“周三十八点前确认”，追问只会收到第一句。现在从同一固定原件版本和行范围重新读取完整章节，恢复材料 key、章节名称、行范围和材料说明；范围内所有片段都必须仍可见。原件已换版时不把旧范围偷偷改指新版本，仍由当前搜索和 Agent 补查。回归先复现丢失，修复后确认完整条件进入第二轮，隐藏其中一个片段后不再传递整段。它修复上下文交付，不等于解决所有指代与时间理解。

Agent 的搜索结果与目录返回节点 `id/parentId/children`；`read_section` 可按 `contextId` 补读父章节或子话题，也保留标题、行号入口。调查快照只复制获准原件的层级，命中可见不代表父章节也可见。跨文件关系、跨轮对象解析和回答材料的完整性选择仍待后续改造；这些变化改善上下文交付，不代表整体排序已经改善。

词法候选现在直接使用 BM25，删除额外的最少匹配词数门槛：长问题中的代码、报错和叙述不应让一段简短而有效的接口说明失去候选资格。精确标识符查询仍要求实际出现对应标识符。自动调用者导航只检查请求首行的明确询问；没有可定位调用时回到普通召回，显式指定 `codeIntent=callers` 则仍只返回调用位置。这样，材料或语言尚无 AST 支持不会让普通问题直接得到空结果。

候选读取先在 SQLite 中对 ID/分数排序，再逐个读取必要原文；用途偏好仍只取 0～1。满足可见性和明确范围的候选达到上限后，只有当剩余 BM25 分数上界不可能超过已保留候选，才停止读取。这保留分类和范围条件，不再把全部命中原文搬入排序缓存和 JavaScript 内存。

融合现在使用标准 RRF：每条路线只贡献 `1 / (60 + 一基排名)`，不再混入 BM25 最大值归一化或 cosine 分数变换。采用 [Elastic 的 RRF 定义](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)，复用已有候选和固定引用，不引入新的搜索服务。用途与材料状态偏好仍在各自阶段生效，向量候选门槛、重排和回答要点选择没有因此自动解决；没有语义或符号分支的普通词法查询仍走原有 BM25 路线。

同一只读材料快照、同一 BGE、实际 dev 来源可见范围下的 12 个中文问题，第一条命中全部相同，后续名次发生变化。补充背景后为何正文未变的直接解释从第三升到第二；模型失败是否保留旧文的问题，两种方法前五条仍未直接回答；英语学习能力的问题仍先命中测试样例。这个对照支持去掉分数混合以简化基线，没有证明整体质量提升，不能代替公开中文/代码检索与实际答案验收。更完整的答案要点选择仍待改造。

## 二、结构化原件检索单位

新增可重建的 SQLite 检索投影，不改 Capture、Revision 和历史 Fragment。Markdown 使用现有 marked，保留章节路径、段落、列表和表格；代码使用现有 TS/Vue AST，按符号范围组织，附签名、注释和模块背景；聊天保留参与者、事件时间及会话/回复关系。长单位可以向量化为多个窗口，但窗口不变成阅读目录。

先使用解析得到的背景和现有讲解；没有理解过的函数不凭空添加 AI 意图。跨文件调用和业务背景仍需 Agent 补查。

全文排序复用 SQLite FTS5 的 BM25，对中文先用 ICU 分词。语义检索沿用 osdk 管理的中文 BGE，结构预处理版本进入向量身份，与旧 Fragment 向量隔离。来源或文章当前版本变化时只替换对应投影；原始历史和固定引用保留。

## 三、用途驱动的共享策略

用途有综合、概念、实现、背景、事项跟进。读者和 Agent 可以明确指定；未指定时保留综合检索，不用仓库名称、目录和题集问法猜结果。概念/背景优先提供连贯说明，实现兼顾符号与原文，事项跟进纳入当前事项和事件时间。用途是结果组合的偏好，不用它排掉仍可能需要的其他材料。

`/api/search`、知识页搜索、Agent 的材料/知识工具、助手使用同一条 `RetrievalPort.search`。旧 `searchSources` 保留为需要固定原件锚点的兼容接口，不再作为解释的唯一表示。

## 四、正式材料用途与段落概念

`MaterialDescriptions` 为每版原件保存主要用途、状态、主题、适用范围和明确的有效期。原生 `material-cataloger` 阅读材料并提交候选，读者能在原文旁查看和修正。检索先按明确用途/时间过滤，再对计划、调研、示例与历史内容施加默认排序偏好；概念别称仅附到对应原文范围的检索单位，进入 BM25 和中文 BGE。数据、界面、Agent 工具共享同一说明，目录名称不参与通用排序。

这借鉴片段上下文检索和元数据过滤，尚不是逐块完整语境生成，也不解决跨文件业务链。当前预处理身份为 `structure-icu-v6`，需要补建向量。原文换版后不沿用旧版分类；人工修正保留。具体流程与适用限制见 [材料用途与概念入口](material-understanding.md)。

## 如何判断是否做好

明确操作名现有独立定义候选，不再依赖整句话的词法/向量排名；同名定义仍按原件范围过滤。普通大写名词不自动当成操作名。可显式区分找定义与找调用者；调用仍是名称级 AST 候选，不能保证类型解析、别名或动态调用完整，也不能保证拒绝长句里的不存在符号。可选重排新增锁定的 BGE v2-m3；默认是否启用及成熟方案的具体取舍见[检索评估](retrieval-evaluation.md)。

全部实现后，用真实中文问题检查：能否找到完整机制，能否定位到正确实现和对应行，旧材料是否误当当前状态，助手是否保留解释并能继续补读。比较原始结果与新结果，不把路径命中、独立复核通过或自动测试数当成理解质量。实际 HTTP、中文模型、阅读页面和受影响 `.repo-review` 产物一起验收。

借鉴方法来自 [Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)、[LlamaIndex Recursive Retriever](https://developers.llamaindex.ai/python/framework/integrations/retrievers/recursive_retriever_nodes/) 与 [SQLite FTS5](https://www.sqlite.org/fts5.html)。这里复用它们的上下文、父子回读和成熟排序思路；效果必须在本项目材料上重新验证。
