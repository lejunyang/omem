# 围绕问题调查，再检查答案是否有用

2026-10-03。后续问答与验收统一使用 Traex ACP / GPT-5.6-sol，停止 Luna 对照。保留可配置 profile，不做快慢模型路由。本文说明本轮实现，实际效果另写验证报告。

## 问题与目标

“关键前提遗漏”可能发生在没有找到必要条件、命中后没读上下文、读到后没写进结论三个环节。“资料相关却答非所问”则常发生在把术语介绍、问题清单或计划当成已经回答问题。schema 和引用正确都不能发现这些语义缺口。

目标是让用户得到可用判断。例如询问服务是否自动运行，需要解释触发点、启用条件和用户要做什么；询问普通约定，则需要保留会改变结果的适用对象、时间和例外。

## 当前实际流程

助手沿用原生 Traex 工具循环。复杂问题用 `investigation_notes` 保存简短事实笔记：用户需要的结果、材料已回答的问题、具体未解缺口。笔记写在本次临时工作区，不是个人记忆，也不是内部思考过程。简单查询可以直接读原文回答。

调查使用原有搜索、完整章节、历史、记忆、图片和代码导航。每次补查围绕一个缺口，使用材料里发现的术语和定位。初始命中仍只是线索；相关性分数不等于能够回答。`code_navigation` 增加导入别名、调用表达式、接收者、构造调用、外围条件及完整方法的定位，便于继续核对真实入口。它仍是候选导航，不解析完整接收者类型、变量传播或跨文件调用图；提前返回及其他上下文仍须读完整方法。按导入别名寻找调用目前用于此调查工具，不等于所有 HTTP 搜索都已支持别名解析。

多部分问题现在可以用 `search_contexts` 一次分别检索。例如用户同时问“哪些材料变化会更新文章”“失败后能否继续读”“重启是否继续”，Agent 为每部分选择查询词与用途；每部分保留自己的完整章节，不把三组结果再次压成一份全局排名。原件补回同版章节及上级引言，已有讲解返回完整章节及固定依赖，记忆与事项保留已应用状态；共享上下文只返回一次，并按问题记录定位。具体范围、材料用途、有效时间和代码定位仍可显式指定。

这复用 [LlamaIndex SubQuestionQueryEngine](https://developers.llamaindex.ai/python/examples/query_engine/sub_question_query_engine/) 的按子问题调查方法，但不另起一个规划模型或 Python 服务：当前 Sol 的原生工具循环负责拆分、读懂、补查和回答，omem 负责同一快照里的分组检索。工具不会声称某个问题已被覆盖，命中数量也不是质量分；拆错问题、基础召回弱或读完仍遗漏都可能发生。简单查找保留原工具，不强制拆解或复核。

作者对复杂机制、冲突、当前行为的关键前提选择 `review_answer`。新 Sol 会话读取原问题、候选答案和相同固定材料快照，可自主补查；不接收作者调查笔记，不提供递归复核工具。原文、历史、记忆、文章和材料说明来自作者的封存数据库，新产生的实时变化不混入同一道问题。原生 CLI 仍不具备完整文件系统隔离。

独立读者集中返回会改变结论或行动的错误、遗漏和偏题问题，包含影响、原文位置及简短建议。作者补读后修改答案；无新增实质疑问时不再例行复核。普通短查询不强制增加模型调用。角色会话沿用可配置 ACP profile，当前使用 Sol，没有新增宿主 token 或工具次数上限。

## 宿主究竟检查什么

`assistant/answer-review.ts` 提供笔记和复核工具，`assistant/acp-model.ts` 接入独立 ACP 会话，`assistant/research.ts` 仍校验来源与事项候选。作者标记需要复核后，未完成复核不能提交；有重要意见的原样草稿也不能直接提交。修订稿由作者负责吸收反馈，宿主不能用“字符串变了”证明语义已经改好。是否需要复核仍由模型判断，可能漏判；复核者也可能遗漏。

复核以本次调查内的后台任务执行：`review_answer` 立即返回任务 ID，相同草稿重复调用复用结果；运行中提交另一稿也不会悄悄启动第二个模型。`read_answer_review` 每次最多等 20 秒，返回运行中、完成、失败或取消及实际意见。20 秒是单次工具等待时间，不是模型生成上限。作者取得意见后才能提交，不用 shell sleep，也无需重新发起复核。失败需明确 retry 才重试。结束作者调查会取消并等待其复核退出，再释放封存快照。

候选、状态与意见更新在同一份 `answer-review.json`，不为每次轮询追加一份快照。意见通过检查并保存后立即可取回，不必等待 CLI 说完结束语或关闭会话；后续取消不抹掉已经保存的复核意见。但这仍不等于最终答案已交付。复核无个人事实或事项写入权限，最终行动仍由原有 MemoryService/事项应用流程处理。沿用配置中的整次问答超时，新增状态读取不会自动延长它，也不代表复杂问答的耗时已解决。

助手与独立复核现已接入知识角色使用的最终提交信号：宿主校验并保存完整结果后即可收束 ACP 会话，避免结果已保存却还在等待 CLI 结束语而超时。提交被拒绝时继续留在原会话修正，用户取消与事实应用检查仍独立生效。

## 检索用途实验及撤回

本轮试过只在 `purpose=implementation` 时降低计划、调研等材料的偏好。同一最终语料和就绪索引上的对照发现，仓库搜索的公开回归从 3/6 退到 2/6，普通 HTTP 搜索也没有显示明确收益，因此撤回了这项改变。默认用途偏好沿用原策略；明确材料用途或 `purpose=background` 可以检索计划和历史。分类仍来自版本化正式标注，不按目录或题目猜测。

这不是最终的相关性解法。整篇文档的一种用途仍可能误伤其中有价值的段落；题目字面吻合也可能把题集排在答案前。需要继续区分“提到了问题”和“能回答问题”，不能用取消全局惩罚或独立复核成功代替真实检索效果。

## 验收方法

2026-10-05 的实际连续咨询已完成。第一轮同时问已选材料换版、新增聊天、失败和重启，Sol 使用按问题检索并补读实现，再由独立会话复核；约 323 秒，答案区分了已选来源自动维护与新聊天需要加入选材，也保留失败可读旧文、重启恢复队列和失败不无限重试的条件。追问如何增删材料及旧引用怎样处理，约 127 秒，回答给出“调整材料与目标”、退出“只看已选”过滤、保存并重新整理的入口，并说明移除选材不删除原文，历史正文和固定引用保留。两轮均未降级，封存语料未改变。

这次没有有效的改造前同题结果，不能声称净收益。第一轮独立复核约 160 秒，答案仍重复解释历史与维护状态；第二轮追加了未问的物理删除和另一条补充背景路径。下一步应改善直接结论、必要条件和操作步骤的取舍，并检查重复调查的耗时，不能靠继续加工具或复核次数解决。实验简报和 trace 保留在同一个 `answer-coverage` 目录，完成后释放约 1.6 GB 输入副本；它是一次仓库咨询，不是通用检索或最终答案质量的整体成绩。

真实 Sol 验收看最终回答是否保留必要条件、直接回应问题、给出需要的操作入口；普通文档与代码都要读实际正文。结合初始命中、MCP/原生读取记录、笔记、草稿、复核意见和最终回答，定位是没找到、没有补读还是最后遗漏。工具记录只能证明读取请求发生，不能证明模型已经理解。

问题文件放在未采集的 runtime，区分已有回归问题和新问题。不按某道题的路径调排序；不以工具次数、引用数或复核通过作为阅读质量分数。实现检查通过后更新受影响指南，实际成功、失败、耗时及未验证项记在本轮报告。

## 与先读材料作答配合

配置 `assistant.readingProfileId` 后，先读写作者也能直接使用这里的独立复核：复核使用 `assistant.profileId`，意见返回原写作会话，写作者补读并修正后提交。需要深入调查或执行事项才交接主 profile，不再因为请求复核额外启动一位作者。复核先从 `review-question.json` 理解用户对象、范围和所需结果，再读 `review-draft.json` 并对照来源；不提供作者调查笔记，以减少沿用作者假设。这个顺序由原生技能指导，不宣称消除了模型偏见或保证答案正确。真实对照与失败仍见[快速决策简报](../../.repo-review/knowledge/verification/fast-decisions.md)。
