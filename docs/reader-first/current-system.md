# 当前实现、不足与解法

审查基线：2026-10-02，本轮代码改造之前。本文描述实际代码，后续交付见 progress.md。早先“全局搜索还是 LIKE”“角色完全不能补读”的结论属于 10 月 1 日基线，不能直接当今天状态。

## 先区分质量的四个问题

事实是否成立、读者是否理解、问题是否得到完整回答、内容是否帮助行动，是四种不同质量。引用位置与 schema 检查只覆盖其中很小一部分。独立 verifier 对事实支持性有帮助，但同一模型分开会话仍可能有共同盲点；它不能代替实际读者。

此前的偏差是把证据保存和局部检查当主要交付，逐次修复用户反馈，却没有围绕“第一次认识系统、带问题找回信息、利用经验行动”形成统一流程。正确的修正是改变调查与讲解方法，而不是再加一句通俗提示或更多边界测试。

## 材料接入与清洗

`store.ts` 保存 Capture、Source、Revision、Fragment。相同输入可去重，内容变化保留旧版。文本、链接、图片和来源元数据进入共同体系。仓库适配器过滤二进制、依赖和生成文件等，原文基本按原样保存。

这主要是接入、过滤和保存。它不等于完整清洗：历史方案与当前状态、正文与噪声、表格与段落、对话回复与转发还未形成统一结构。通用片段主要按空行切；中文向量对片段再用 400 字符窗口、80 字符重叠。已新增 marked/TS/Vue 的阅读结构投影，助手可补父章节与相邻片段，但结构尚未充分进入索引。

解法：原件不可变，另建解析与检索投影。Markdown 使用 marked 保留标题、列表、围栏和表格；代码保留符号与所在模块；会话保留参与者、回复链及事件背景。复杂 PDF/DOCX 用 Docling 适配，不让通用 Capture 接管外部解析器的数据库或 UI。图像可进入视觉分析，但当前没有通用 OCR/布局定位和视觉索引闭环。

## 检索与 RAG

当前 `KeywordRetrieval` 使用 FTS5 trigram/BM25，中文短词使用二元组和 LIKE，另有精确符号、已应用记忆、知识正文回溯原文分支。`SemanticRetrieval` 使用 osdk 锁定的 BGE-small-zh-v1.5、CPU ONNX、SQLite 向量精确比较；RRF 融合和 MMR 调整重复。顶部、知识、助手已共用基础，入口合流不代表相关性好。

当前相关性问题有具体来源：

1. 两字中文泛词触发大量 OR 命中，较新材料可能排在更相关材料前；按标题匹配会让同一来源大量片段都成为候选。
2. 知识分支搜索整个 artifact JSON，引用理由、元数据、运行记录也可能命中。标题命中后沿所有章节引用扩散，一篇文章的几十个来源被当成同等相关。
3. 全文/短词/知识/记忆先 RRF，再与 dense 结果 RRF，失去原始相关性差距。低相似度的向量尾部候选也参加融合。
4. MMR 负责减少冗余，不能判断“这个片段回答了问题吗”。目前没有专用语义重排器，不能把多样性称为相关性保障。

`assistant/runtime.ts` 检索后补结构上下文，模型可提出有限改写再检索。当前仍缺完整意图路由、跨文件功能链、业务时间/as-of 和对回答完整性的可靠检查。长期会话有历史预算和用户纠正，但不是持续维护的项目理解。

解法先治理候选：只索引读者正文，按命中章节回溯引用；限制单来源泛匹配；保留 query coverage、精确名称、词频和原始相似度；弱匹配允许为空；所有分支只融合一次，再重排、去重和补上下文。随后对照中文 reranker，不用对 omem 题目或 archive 路径加特判。派生知识可同时提供整体解释和原文锚点，不能为了来源严格把解释再次丢掉。

## 代码理解

`code/parse.ts` 使用 TypeScript 单文件语法树与 Vue SFC 脚本，不是完整 Program/TypeChecker。相对 import 能定位；calls 仍有单文件名称级 candidate；跨 revision 身份续接有限。显式设计/测试关联来自 associations.json，结构候选不是已确认业务关系。

AST 回答“定义在哪里、有哪些结构”，业务意义需要调查调用者、类型、配置、测试、设计记录及输入输出。一条真实功能链通常跨页面、请求入口、保存、任务、模型和展示。不能按文件各写几百字，再期待目录汇总自动解释因果。

仓库原材料说明路径仍会补几个 import 文件前 70 行。新读者路径允许按问题搜索与补读，但以 JSON 请求、宿主执行和新会话重启实现。解法是把 AST 导航暴露为 Agent 工具，与原生 Read/Grep/Glob 和知识搜索一起用；优先完成自主调查，不把完整调用图当写好 Wiki 的前置条件。

## Wiki 与 harness

原路径 analyze → 单材料说明 → synthesize → plan → 上层文章，仍有超过 12 子项按数量分组的兼容流程。新路径 writePage 使用读者目的、案例、问题和最多三轮调查，之后 writer/verifier/refresher 最多四次写作复核。两条路径并存，不能把新路径能力写成所有材料总结都会具备。

当前 skills 多为 inline，知识角色 tool_policy=none、reuse=never。底层已预留 MCP 注入和原生 skill 支持，但知识任务没有使用。每次 ACP 新会话只有一次 prompt；一次 prompt 本身可包含 Agent 内部多次模型与工具交互，不能从协议请求数推断其推理次数。

现有网关把所有文本拼成 JSON，格式修复与内容复核虽有循环，但不能代替调查。工具更新主要显示标题，计划、完整工具生命周期与最终产物没有充分分开。解法见 agent-research.md：同一研究会话原生工具调查，最终 schema/产物提交，独立新会话自行补查。

Traex 已实际用于 ACP。Codex/Claude 有 CLI 输出适配与示例 profile，但当前助手只接受 ACP；Claude CLI 参数关闭工具。角色 profile_ref 和 native skill 路径还带 traex 偏好，多提供方对等接入未完成，不宣称均已实测。

## 长期记忆与主动事项

claim 表达事实与归属/有效期；episode 记录触发、行动与结果；procedure 记录步骤、前提和反例；task 用于交办和跟进。抽取 → 独立复核 → MemoryService 应用有实际链路，来源更新能重核验并保存历史。模型没有直接事实写入权限。

这些记录还没有稳定形成“这个项目现在是什么情况、这个人有什么背景、我过去哪些做法有效”的综合理解。事件时间不等于捕获时间；有效期字段不等于完整时态检索。每个配置文件自动抽取也会制造低价值条目和任务负担。

应按价值和目的选择记忆，再形成经历、当前事实/偏好/经验、持续维护的人物/项目/主题理解，最后用于行动。比较 Hindsight 的整合与 mental models、Graphiti 的时间关系，先做原件适配与同题对照，能减少自研就使用组件。任务已有等待、改期、完成和站内提醒；自动监听回复、周期回顾、英语卡片仍待实现。

## 人如何认识陌生系统

以一个实际场景建立问题，再跟完输入到结果的旅程，途中认识最少术语，随后看整体地图、关键机制和取舍，最后尝试修改或排障。初学者不是先背 Source/Revision/Fragment；先看到“同一规则变了，为什么旧回答还能打开旧原文”，再认识来源和版本。

教程、概念解释、操作指南、机制、决策和参考各有目的。入门主线不讨论 200 层 URL、JSON 修复、测试计数。原文章中出现“此前引用已被新范围替代”等编辑过程属于质量失败，即使每句话有出处也不能发布为系统解释。

验收用真实问题和读者操作：是否能解释主流程、找到必要背景、定位修改入口。给齐材料仍答不好属于生成失败；给齐能答好而检索后答不好属于召回或上下文失败。先做可读页面和任务，不先追求全库覆盖率。
