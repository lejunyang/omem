# 材料用途、适用范围与概念入口

这项改造解决一个具体问题：问“现在怎么工作”，搜索却排出一份未来方案；问某个行为，正文用的是另一个术语，结果找不到。先让每份材料说明自己能回答什么、是什么性质，再把具体概念接到对应段落。它是检索辅助，不能把模型分类变成当前事实。

## 使用流程

在“原始材料”打开一份原文，展开“材料用途与适用范围”，点击“让 AI 分析用途”。Agent 阅读该固定版本，可搜索和补读，再保存主要用途、状态、概要、主题、适用对象、明确注明的生效时间，以及概念别称对应的原文行。完成后可以人工修正。原件和旧引用不改变；人工修正不会被下一次模型分析覆盖。

例如，一份文档写“建议以后给借阅登记增加重复请求保护”，它是拟议方案；“重复归还”“幂等归还”可以指向说明这个建议的段落，但不能因此说系统已经支持它。保存于今天，不等于今天生效。没有明确适用时间就留空。

目前由页面按钮或明确的批量任务触发，**不是每次捕获后都自动分析**。原文换版后，新版本需要重新分析；旧版本的分类保留，不能静默迁移成新版本的事实。文章分类 `topicPath` 仍负责阅读目录，与材料用途、检索目的各有职责。

## 怎样影响搜索

1. **先检查正式范围，再排候选。** 选择“说明与规范”“实现”等用途时，从已保存的分类筛选；未分类的材料仍可在默认搜索中出现。`effectiveAt` 仅检查材料明确的适用起止时间，不用捕获时间代替。
2. **默认排序减少不适合作当前说明的材料。** 历史、拟议、被替代的内容，以及计划、调研、示例获得较低的排序偏好。它们仍可被找到；明确选择用途或查历史背景时不施加这层默认偏好。这是可改的产品策略，既不证明材料正确，也不能保证第一名能回答问题。
3. **概念按段落进入全文和向量索引。** “重复请求保护”的别称只加入与所标原文范围重叠的检索单位，不给整篇文档的每个段落附上同一个摘要。返回的正文仍是原文；分类和概念作为派生说明单独展示。
4. **让读者看到选择依据。** 搜索页的“筛选命中材料”作用于实际搜索结果，显示用途、状态和适用范围；综合回答仍沿自己选择的调查范围工作，该筛选不偷偷变成会话权限。

同一材料的模型讲解可沿用该材料的用途；跨多份材料的指南不直接继承其中一份来源的分类。知识讲解始终是派生背景，不能重复算作第二份独立事实。

## 采用的方法与改造位置

采用 [Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) 的一个核心做法：把与片段有关的背景同时放入全文和向量检索，而不是只加文档总摘要。本轮实现的是有固定行范围的概念及别称；还没有为每个检索单位生成完整上下文说明，不能称为完整复现，也不能套用上游的收益数字。

[Haystack 的元数据筛选](https://docs.haystack.deepset.ai/docs/metadata-filtering) 将内容检索与正式属性过滤分开。这里复用这个划分，在现有 SQLite 投影和共享检索接口实现，不另建一套向量库或 Agent 循环。类型、状态、时间必须是保存的数据；目录名称和题集问法不进入通用排序规则。

| 位置 | 负责什么 |
| --- | --- |
| `packages/contracts/src/material-description.ts` | 材料用途、状态、适用时间、概念和依据的共享结构 |
| `source-profile/descriptions.ts`、迁移 20 | 按固定 revision 保存分类版本；检查原文范围，保留人工修正和并发修改 |
| `knowledge/pipeline.ts`、`material-cataloger` 原生角色 | 重用已有 Traex 原生工具、skill、只读 MCP、固定材料工作区，提交候选说明 |
| `retrieval/units.ts` | 概念与原文范围相交后进入检索投影；Markdown 引导句连同紧随的表格、列表或代码保留 |
| `retrieval/unified.ts` | 在候选截断前执行用途/时间过滤及适用性偏好，全文和中文向量共享 |
| `knowledge/agent-research.ts`、`knowledge/research-snapshot.ts` | 给 Agent 固定的材料目录、说明、搜索过滤及补读结果，不读取超出选材范围的分类 |
| `MaterialDescription.vue` | 查看、AI 分析、人工修正和加载态；正文不被编辑表单取代 |
| `scripts/review-catalog.ts`、`knowledge/material-descriptions.ts` | 仓库输入适配、真实模型产物发布、按材料 digest 恢复；这部分不决定通用排序 |

索引预处理身份是 `structure-icu-v5`。分类版本参与投影身份；修改概念会让相关材料重新索引，不能继续使用旧预处理的向量。中文 embedding 仍用 osdk 管理的 BGE，运行不隐式下载。

## 运行与检查

```bash
osdk run review:catalog docs --documents
osdk run review:catalog apps/server/src/memory/service.ts
osdk run retrieval:index --review
```

第一个命令只选择 Markdown，第二个可处理代码；默认跳过已有说明，`--retry` 重新分析未人工修正的材料。真实模型设置仍来自 `config/review-code-model.json`，使用 traex ACP / `gpt-5.6-sol`。任务按批保存成果，失败保留已完成记录与 trace；重跑不会从零覆盖人工结果。

发布的材料说明在 `.repo-review/knowledge/material-descriptions/`；数据库、完整原件工作区和运行记录在 gitignored runtime。开发入口仍是 `osdk run dev`，会恢复已发布且匹配原件 digest 的说明，保留个人数据。

检查不能只看分类数。要在**同一份冻结材料库**关闭/启用这些说明，保存完整 HTTP 排序和原文，逐题判断：前排是否真能回答、是否混入旧方案、是否找到了实现、无答案时有没有误导。测试问题不提供给分类 Agent，也不写成固定别称来优化命中。实际结果见 [实施进度](progress.md) 与当轮报告。

## 仍然欠缺什么

- 一份混合文档目前只有一个主要用途；同页中已实现部分和计划部分可能仍需按章节标注。
- 概念别称可能过宽或错分范围；独立写作复核和用户阅读仍需回原文判断，分类任务本身不等于事实复核。
- 适用对象是文字说明，还不是可靠的项目/人物实体，也不是团队隔离或权限。
- 长问题可能在融合前丢掉明确函数定义；跨文件业务链、递归补父块和完整意图路由没有被本轮分类自动解决。
- 当前材料说明不会自动触发记忆写入或事项执行。持续主题理解、周期回顾、学习卡仍是另外的完整流程。
