# 从搜到材料，到读懂答案：助手与知识检索调研

调研日期：2026-10-02。本页由独立子 Agent 阅读实现、查阅一手资料并在冻结库上做只读实验。它记录本轮改造的起点和建议；没有把别的项目的宣传数字、人工拆词或模型复核当成 omem 已有能力。后续实现和真实流程验收见 [progress.md](progress.md)。

**眼前最值得改的是“找到入口后继续读”，以及让网页同时展示答案和真正的命中。** 当前库里已经有一些足以解释问题的指南，也能精确查完整方法；用户的自然问法却常先命中保存说明、旧计划或话题相近的界面代码。只调整融合权重或换一个更大的向量模型，不能直接解决“缺了哪段机制、应该继续查哪里”。

## 一、本轮改造前的实际链路

下表记录调查开始时的基线。普通助手现已接入原生自主补读，网页首题与追问也完成了真实模型运行；个人流程的实际结果见 [assistant-memory-flow.md](assistant-memory-flow.md)，提交和验收状态见 [progress.md](progress.md)。下面的旧缺口用于解释改造原因，不能读成当前仍只有一次补查。

| 环节 | 调研起点已有实现 | 不能据此推断的能力 |
| --- | --- | --- |
| 保存和组织 | Capture/Source/Revision 保留固定版本；原件、讲解、记忆、事项共用库；文章 `topicPath` 持久保存 | 材料尚未全部具有可管理的主题、内容角色和有效时间；目录不是权限边界 |
| 检索单位 | `retrieval/units.ts` 生成 Markdown 块、TS/Vue 完整操作、聊天背景、知识段落和当前状态 | 完整函数不等于完整功能；匹配案例开头不等于返回了处理机制 |
| 排序 | SQLite FTS5/ICU BM25、中文 BGE、融合、去重和用途偏好；中文 reranker 是可选配置 | 相似度不是“能回答”；`purpose` 主要偏好结果类型，不能可靠识别当前机制、旧方案和实验记录 |
| 知识调查 | `knowledge/agent-research.ts` 提供固定快照、原生文件读取、MCP 搜索/章节/符号/文章/记忆工具；作者和独立复核者能继续调查 | 这套调查能力当时还没有完整进入普通日常助手 |
| 普通助手 | `assistant/runtime.ts` 先召回，模型最多请求一次、三个补查问题；回答和来源已经可读 | 一次补查无法保证发现和解决缺口，也不保证方法本体、调用方和下游服务一起进入上下文 |
| Web 搜索 | `App.vue` 调 `/api/search`，显示实际 RetrievalHit，能打开讲解或固定原件 | 这里还没有 AI 综合答案；用户必须自己把几个命中拼成答案 |

用途、范围和来源可见性都应经过共享 `RetrievalPort`。不能另做一个 Web 专用排序器，或者把查询题目、某个仓库目录、某篇指南标题写进通用规则。

## 二、真正搜出来的文字是什么

本次使用上一轮生产 HTTP 验收保存的一致语料快照：2026-10-02 19:41（北京时间），语料对应 `68677fa`。数据库以只读方式打开，中文 BGE 就绪，12,679 个单位已索引，未启用重排。执行时代码版本为 `fed27f3`，该实验使用的共享检索与 v4 投影没有改变。没有导入这些问题，没有改来源、模型或索引，也没有接触个人库。

六个新问题每题保留完整原始结果、手工选择的诊断查询、联合结果和固定父章节。诊断只是为了判断“材料不存在”还是“问法找不到”；它不是生产环境的自动拆问，也不是无偏的效果测量。

- [实际召回阅读页](../../.repo-review/runtime/research/assistant-search-probe/index.html)：可以切问题、看原始文字、看人工拆词诊断，并展开固定父章节。页面没有 AI 综合答案，不把人工归纳伪装成模型结果。
- [完整结果](../../.repo-review/runtime/research/assistant-search-probe/results.json)：包括检索器返回的文字、顺序、版本、行范围、来源与各诊断分支。
- [实验脚本](../../.repo-review/runtime/research/assistant-search-probe.ts)：只读运行，不执行写入或重新建索引。runtime 是本地验收产物，不保证另一台机器存在；下面保留关键结果便于长期阅读。

这个展示页保留原始 Markdown 和引用标记，目的是看检索器究竟返回了什么，不是产品阅读界面的样板。切题、诊断与固定父节展开在 1440/768/390px 检查，并抽看桌面与手机截图，无页面异常或整体横向溢出；它不能替代实际 `dev` 的 AI 答案、引用跳转与使用流程验收。

### 例子 1：问题带了代码名，也不一定拿到代码

问题：**“MemoryService.apply 如何把模型提案变成有效记忆？若要修改这条处理链，入口和后面的写入分别在哪里？”**

第一项是《规则变了以后：原文、记忆与待办如何更新》的修改入口段：

> 若要修改机制，主要入口分别是：捕获与失效在 `store.ts`，重核验编排在 `learning/pipeline.ts` 与 `learning/refresh.ts`，应用策略在 `memory/service.ts`，事项时间与提醒在 `tasks/follow-up.ts`，Wiki 新鲜度与发布在 `knowledge/repository.ts` 和 `knowledge/pipeline.ts`。

第二项讲整批提案治理；第三项讲反馈数据与存储边界。它们能提供背景，仍没有直接给出所问方法。单独查询 `MemoryService.apply` 返回完整 1176–1280 行；查询 `applyMemory` 返回 `ApplicationRepository.applyMemory` 的 402–530 行。把这些诊断查询与原问题合并，两个方法排到第四、第五项，仍没有自动成为完整答案。

这支持两项改造：在长问句中独立保留精确名称的查找入口；得到方法后，允许 Agent 继续读下游方法。泛化成“所有问题都先查调用链”则不合适，生活约定和英语学习并没有同样的调用链。

### 例子 2：旧内容怎样更新，原始问题先找到保存说明

问题：**“我上周存的约定今天改了，助手会怎样处理已经记住的旧内容？”**

第一项说明“材料已保存”与“个人记忆已生效”不同；第二、第三项来自旧的处理政策与会话路由。这些文字没有直接回答旧记忆如何更新。

诊断查询“来源变化 记忆重核验”“旧记忆 冻结 重新应用”找到了《规则变了以后》的“规则改版后，旧结论先冻结再重核验”。其中一个直接命中只说明最终状态；读取它所属的固定章节后，可以看见连续的机制：

> 当同一来源出现“重试五次”的新版本，系统会提高来源有效性版本，把仍依赖旧版的记忆依赖标为过期，并立即把这些记忆设为 `invalidated`；随后记录受影响集合并排入刷新作业。

该节接着解释确认当前来源、复用提取流程、更新同一条记忆以及被后续版本取代。这里“小段匹配→完整节补读”有效，因为目标解释已经存在；如果目标章节没有被找到，单纯扩大原始第一项仍然只会得到更多保存说明。

### 例子 3：相关词能把无关代码推到第一项

问题：**“一个文档不断改版，为什么还要留旧稿？什么时候真的会用到旧稿？”**

第一项来自 1–1637 行的旧 JSX 原型，显示的摘录是：

> `["MCP", "检索、读取证据、记录经历"]`、`["Skills", "什么时候记，什么时候用"]`、`["API / SDK", "连接已有工作流"]`

它包含近似词，却没有解释保留旧稿的理由。第二项是文章发布和刷新说明。当前捕获指南的历史引用段也在候选中，但没有排在前面。诊断查询“固定引用 旧版本 追溯”“原文 历史版本”让该指南排到联合结果第一项，能读到：

> 因此，v1 中“至少一人批准”的引用不会被 v2 的“两人批准”静默替换。阅读界面会明确显示“历史版本”，并仍可按原行范围展开原文。

不能据此写一条“prototype 目录一律降权”的规则。正式的材料角色能告诉系统这是演示实现；“旧稿→历史版本→固定引用”的语义入口应来自内容理解和检索表示。只有这些数据可迁移到陌生仓库和其他领域。

### 其余三题，没有用一个通过数掩盖差异

| 问题 | 原始命中与诊断结果 | 后续动作 |
| --- | --- | --- |
| 知识文章核对不通过，是删旧文章还是继续修改？ | 第一项讲 UI 的“待核对问题”，容易混淆用户补背景与独立 verifier 返修；手工拆词仍没直接返回 `writeAndVerify` 的循环 | 必须继续查写作/复核入口并读实际处理，不能靠“独立复核”关键词直接生成结论 |
| 只是记下朋友一句话，会自动变成我的待办吗？ | 第一项当前指南明确区分背景、他人承诺与本人交办，足以开始回答；诊断增加了实例和服务端入口 | 这类问题直接回答即可，不需要强制走代码研究；如果用户追问实现再导航 |
| 怎样让 AI 先自己查资料再回答，而不是只看片段？ | 原问题先给旧概览和原型阅读边界；诊断找到了研究工作区、工具表和当前调查指南 | 问法需要连接到系统概念；找到工具表后应补读工作区准备和 Agent turn，确认普通助手与知识角色的区别 |

联合结果仍保留噪声，多问几次不自动解决排序。有些旧模块说明虽然已复核，正文还夹着“缺端到端测试所以不能说明已验证”等审计语言，甚至有不够准确的索引时机说明。扩大父节也会扩大这些写作问题。因此，召回、扩读和内容质量需要分别看。

## 三、成熟方案值得拿什么，怎样接进来

### 1. 父块、递归引用与相邻窗口：为回答补足语境

[LlamaIndex recursive node 示例](https://developers.llamaindex.ai/python/framework/integrations/retrievers/recursive_retriever_nodes/) 把较小块、摘要和可回答问题作为检索入口，再沿节点引用读较大原块。[Haystack AutoMergingRetriever](https://docs.haystack.deepset.ai/docs/automergingretriever) 根据同一父节点下的子命中比例合并父内容；[SentenceWindowRetriever](https://docs.haystack.deepset.ai/docs/3.1/sentencewindowretriever) 依据来源与顺序补相邻句段。它们解决匹配粒度和回答粒度不同的问题，不能保证最初选中的父节点就是正确材料。

**接入 omem：** `RetrievalUnit` 保留匹配段；另外给出固定 parent/section 与邻接入口，不覆盖命中 text。Agent 通过 `read_section`/`read_knowledge` 读取完整节或操作；自动扩展同一 SourceAnchor 时先合并重叠范围，保留真正相关段与扩展背景的区别。长代码沿符号边界读取，聊天沿回复和会话读取，文档沿章节读取。当前结构解析和固定锚点足以做第一片，不要求先换保存库。

这些官方完整组件主要在 Python 框架中，不能直接当作 Bun 包导入。若要用 Haystack 做独立对照，应通过一个可替换检索适配器运行其 splitter/retriever，并保留 revision、范围和可见性；不把来源写入第二个事实产品。当前最小改造复用方法和既有解析器，不能宣称已安装或验收了外部组件。

### 2. 多种检索表示：让人类问法找到系统概念

[Dify 文档维护](https://docs.dify.ai/en/cloud/use-dify/knowledge/manage-knowledge/maintain-knowledge-documents) 将子块作为检索钩子，返回父块；摘要命中也能返回对应正文。它还允许用摘要、关键词和常见问法帮助父内容被找到。[Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) 给每块补独有背景，并把背景同时用于向量和 BM25；给每块重复同一份泛化摘要不是同样的方法。

**接入 omem：** 原始文本不变，把概念、背景和可回答的问题作为可重建表示，指向固定原件/文章版本。已有独立复核的讲解已经是重要表示；还可在知识生成时产出少量术语别称、问题范围和对应实现符号，供 `units.ts` 建索引及 Agent 发现入口。例如“旧稿”与“固定历史引用”可以连接到同一真实章节。它们是检索假设，不是额外事实，也不是人工维护的测试问句。

不要让生成的假想问题进入原文正文，或者给每段灌十个同样的问题。应抽查别称是否指向真正能回答的段落，观察新问法、不同领域和无答案问题；一份资料缺少对应机制时，提示缺口比相似段落拼答案更好。

### 3. 内容 metadata：分类、时效与角色要能看见和修正

[Dify metadata](https://docs.dify.ai/en/cloud/use-dify/knowledge/metadata) 区分系统字段与可编辑自定义字段，并提供批量维护；[RAGFlow metadata 管理](https://ragflow.io/docs/v1.0.0-rc1/metadata_management) 让来源、类别、时间等结构信息参与管理与检索，也提醒过严或错误字段会排掉相关内容。RAGFlow 此页对应候选版本，本次只借鉴数据管理方式，不将它当 omem 实际依赖或成熟度结论。

**接入 omem：** 扩展 Capture/Source 的正式资料描述，`units.ts` 复制进入索引，`port.ts` 接受过滤与偏好，`unified.ts` 在可见性检查后使用。第一片至少分清下面三个维度；未知字段应允许为空。

| 维度 | 示例 | 使用方式 |
| --- | --- | --- |
| 主题与适用范围 | 英语/表达、摄影/曝光、某项目/发布流程；主体或所谈版本 | 浏览目录和用户明确限定；模型提议、用户可改；跨主题背景仍可检索 |
| 内容角色 | 当前说明、原始事件、决策、计划、参考、教程、验证记录、演示材料 | 回答“现在怎样做”时优先适用机制，问“为什么这样决定”时读历史；不按文件目录猜角色 |
| 时间与有效性 | 捕获时间、事件时间、生效/结束时间、来源版本、被取代关系 | “今天”“当时”“上周”使用不同时间；新上传旧文件不能自动成为最新事实 |

`reading.kind` 是文章的阅读体裁，`topicPath` 是主题目录；它们与“该内容现在是否适用”不同。源材料也可能同时有多个角色，不能把整个文件永久判成计划或事实。第一片可以先存可解释、可纠正的字段，不要做一个复杂的全库自动标签治理系统来阻塞问答。

低把握的自动分类用于排序线索，不能作为硬过滤或权限。正式可见性沿来源和宿主策略；当前仍是单用户，不能由 metadata 推出已实现团队权限。

### 4. 分阶段检索与重排：复用组件，先证明收益

[Qdrant Hybrid Queries](https://qdrant.tech/documentation/search/hybrid-queries/) 将多路 prefetch、RRF/DBSF、后续重排和按文档分组组合起来，也能用正式 payload 数据加入时效信号。它提供的是可配置检索机制，不会替系统判断“旧计划为何不该回答当前行为”。

**接入 omem：** 保留 `RetrievalPort` 和 SQLite 保存合同。词法、精确符号和语义分别提供候选，沿稳定锚点去重后重排，随后按需要扩读；同一方法被几个存储 Fragment 覆盖，不应在上下文里重复占位。当前已安装的中文 cross-encoder 可做对照，仍需比较实际文字而不是只看模型加载成功。

当前 `unified.ts` 在进程里遍历 eligible 向量。材料规模扩大后，应测延迟与内存，再决定接 Qdrant 等成熟索引作为 RetrievalPort 的适配器；导入必须带 unit/revision/metadata/visibility 身份，删除与换模型要有对应索引生命周期。不要先引入一个完整服务栈来掩盖当下的语义问题，也不要把全部候选截断到同一无关主题后期待 reranker 找到根本没进入池的答案。

### 5. 自主检索是按缺口调查，不是每题都跑固定流水线

[Self-RAG 原论文](https://arxiv.org/abs/2310.11511) 强调按需检索与对内容的反思；它采用专门训练的 reflection tokens。这不是给现有 Agent 多加一句“反思一下”就复现了论文方法。omem 更直接的选择是利用 Traex 原生工具循环，提供真实读取与检索能力，由 Agent 决定下一步调查。

**接入 omem：** 从 `knowledge/agent-research.ts` 抽共享只读研究能力，普通助手得到目录、全文、章节、图片、已有解释、记忆、事项及按需代码导航。`assistant/acp-model.ts` 将最终候选提交与过程说明分开；`runtime.ts` 接受实际补读的固定范围，不因为模型结束一轮就只取前 28 个重复 Fragment。宿主保留取消、状态、范围与写入权限，原生 CLI 管理工具回合及上下文。

研究目标取决于问题：

| 场景 | 足够好的调查与回答 | 不应强制的步骤 |
| --- | --- | --- |
| 代码机制 | 问题→入口→必要调用/配置/背景→例子→修改位置 | 每题输出完整调用图、审计边界与所有测试 |
| 个人约定变化 | 旧/新事件和相关记忆→当前规则及差异→是否需要行动 | 先找代码函数或先写 Wiki |
| 学习英语 | 知识点与已有练习→对比例句→当前误解及练习 | 所有输入都立即制成卡片、套代码章节 |
| 普通查找 | 找到并读出所要资料，必要时一两句归纳 | 固定研究者/作者/复核者三角色全跑 |

回答有关键缺口就继续调查；检索错误或无材料时说明目前找到什么、缺什么，不用主体相似的段落兜底。提供工具自由不等于事实直接写入自由，记忆和事项仍交给受管理应用服务。

## 四、Web 同时给答案与材料，而不是再建一种助手

[Dify Knowledge Retrieval 节点](https://docs.dify.ai/en/cloud/use-dify/nodes/knowledge-retrieval) 将检索结果交给生成节点，再返回引用答案；[RAGFlow retrieval testing](https://ragflow.io/docs/v1.0.0-rc1/retrieval_testing) 则直接展示块、排序与来源，区分“正确材料没有召回”和“材料齐了仍答不好”。omem 应把这两种可见性放在同一个搜索体验中。它们是这里的设计借鉴，没有运行这两个完整平台作横向评分。

建议交互：输入问题后先显示材料命中，读者可以立即打开原文；明确发起“根据资料回答”后，同页新增 AI 综合答案和可取消的调查状态。不要每敲一个字调用模型。用户在现有答案下继续追问，可以进入同一助手会话；原始搜索顺序和内容始终可查看，不能被模型挑选结果覆盖。

答案至少包括直接结论、需要的解释或例子、对应固定来源。按问题适配体裁，不强制每次都写三个标题。资料冲突或时间不明确时说明适用条件；实现名、来源行段留在引用和必要修改入口中。引用复用 `OmMarkdown` 与 `useEvidenceTrail`，而不是另做弹窗。

搜索问答应使用只读咨询模式：不得因为问题里出现“待办”“记住”或引用材料里的命令就写事实。读者从答案明确交办后，才转入普通助理的授权意图与应用流程。这样 Web 不只是一个去日常助手页面的跳转按钮，也不会新建另一套没有持续会话的 RAG。

## 五、具体改造入口与验证方式

| 文件/接口 | 最小可实施改造 | 真实检查 |
| --- | --- | --- |
| `retrieval/port.ts`、`units.ts` | 匹配单位保留 fixed parent/section；正式材料角色与时间信息；检索别称与原文分别表示 | 换成生活约定、英语、陌生代码，分类/时效不能依赖仓库路径 |
| `retrieval/unified.ts` | 独立符号线索与语义候选，范围先过滤；锚点合并；重排后再按需补父内容 | 展示每题实际前列文字、遗漏机制和噪声，不只检查预期路径 |
| `knowledge/agent-research.ts` | 可共享的只读材料、文章、记忆与代码调查工具；全节补读保留固定版本 | Traex 真正搜索、读原件、跨材料补查，记录工具读取而非 fixture |
| `assistant/acp-model.ts`、`runtime.ts` | 原生 Agent 调查，允许按缺口持续读；结果与调查过程分开；保留最终所用来源 | 用户长问题确实读到方法和下游；非代码问题不被迫套代码流程 |
| 搜索 API 与 `App.vue` | 同页综合答案、取消/继续追问、实际命中；回答复用已有会话与引用读者 | 实际 dev 浏览器看到答案与原始内容，点击固定来源，390/768/1440px 检查 |
| Capture/learning/memory/tasks | 串起来源改版、旧记忆冻结、实际重核验、有效记忆应用与明确跟进 | 一次真实保存→提问→修改→更新→提醒；验证具体内容/状态，而非只看 job done |

本轮建议先交付助手自主补读和 Web 综合答案，让调查能力与真实命中可见；随后在同一流程中补正式角色与时间、概念表示和上下文扩展。把资料准备充分却仍讲不清的回答单列为生成问题；把材料根本没进候选的情况单列为检索问题；不要用更多 schema 和流程阶段掩盖这两种缺口。

调研不建议这一轮为每种输入建设一套固定流程，也不建议马上迁移全部存储或上图数据库。保留可替换检索接口，优先接成熟组件能解决的具体环节，并用不同场景的实际阅读与使用结果决定是否扩大。
