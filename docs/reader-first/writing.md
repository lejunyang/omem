# 让人读懂、找到、开始行动

首要读者：能编程但不熟悉当前系统的人。默认阅读路线：场景 → 一个完整例子 → 必要概念 → 整体地图 → 关键机制与取舍 → 修改或排障 → 参考。

## 页面模板

| 类型 | 组织方式 |
| --- | --- |
| 入门教程 | 目标、准备条件、步骤、预期结果、解释 |
| 概念解释 | 问题、概念、具体例子、关系 |
| 功能机制 | 输入输出、主流程、关键步骤、实现位置、重要分支 |
| 设计决策 | 当时背景、备选方案、选择理由、代价与适用条件 |
| 修改/排障 | 目标或现象、调查路径、改动位置、如何确认效果 |
| 参考 | 便于检索的接口、字段、配置 |

模板指导结构，不机械凑满栏目。长度服从讲清楚问题；避免每个文件一篇相同摘要。每节应推进理解，不重复“统一、保证一致、可扩展”等空泛结论。

正式 `knowledge-writer` / `knowledge-refresher` 已移除默认字数和章节配额，主提示只指定任务，具体方法集中在角色 skill。先读页面目标，再决定需要例子、概念、图表还是直接给步骤；简单约定可以只有一节，复杂机制仍须交代因果与关键前提。无关的“不能推出”、调查日志、修订经过和测试覆盖清单应删掉，不用它们填充文章。

返修从上一稿和具体复核问题开始，只补读受影响的原文；准确且不受影响的解释保留，发现新的矛盾再扩大调查。输出仍是可独立阅读的完整文章。复核者先尝试用草稿回答页面问题，再独立检查关键事实；没有默认篇幅门槛，不为文风偏好返修，也不接受正确但无法完成读者目的的空泛概述。

维护已发布文章与修复一份新草稿现在分开处理。调查者先阅读旧正文及变化，给出 `composition`：旧路线仍好用时局部维护；结构已经妨碍阅读或目标改变时重新组织。选择重新组织后，写作者收到调查结论、讲解路线与当前原件，不再默认进入旧稿补丁模式；后续若事实复核失败，仍从这份新稿局部修正。文章身份和历史不变。决策理由与讲解路线留在生成记录中，不进入读者正文，也不作为质量分数。

这项机制针对一个实际问题：检索指南即使目标明确排除测试报告，维护时仍把旧实验数字、边界条件和本轮新增工具不断累加。真实 Sol 更新中，调查者选择重组检索页，保留同一个提问案例，去掉实验时长、字符统计和大部分参数列表；记忆与生成页选择维护旧结构。检索页的主线更集中，另两页仍有偏多的实现术语和边界说明。不能由 mode、引用或复核通过推断讲解质量；最新交付与未完成项见[进度页](progress.md)。

维护机制还不能替代明确的编辑目标。项目身份贯通后的记忆稿继续扩写状态字段和测试经过，事实复核没有阻止这种偏题。本轮将该页计划改成个人用户的一次活动流程：保存、问回、约定换版、交办提醒和完成；用中文可见结果帮助读者选择动作，把状态码和实现审计留给引用中的源码。这里调整的是本仓库实验页的读者计划，不给通用写作增加固定案例、篇幅或章节配额。新稿仍须实际抽读，不能因选择了 rewrite 就宣称更好。

自动归属改动后的两篇稿再次暴露偏差：调查者认为“已有标题覆盖了问题”就适合局部维护，继而把新分支的全部条件加进正文。现在维护先按读者已有知识试读，再调查变更；研究笔记可以详细，讲解路线只保留影响使用或理解的内容。具体抽读仍发现材料篇夹入 Sol 实验、记忆篇第二次保存要求复用一个第一次没有设置的来源标识；事实复核未拦下这两处问题。将这两条明确反馈写进页面计划后，真实 Sol 定向返修删除实验段落，补齐首次来源类型与标识，保留已讲清的路线。三篇最新正文已做实际页面检查，但检索页仍有偏多的参数与校验说明；不把模式、标题覆盖或复核通过当成人类已经读懂。

这一策略已用同一份合成活动材料和阅读计划实跑 Traex/Sol：旧产物五节、977 个正文字符，新产物一节、357 个字符，仍包含预算、集合、交接顺序和必要的清单未知，三处引用可回读。长度只是观察；这不是质量分数。复杂机制页的因果、案例和修改入口仍在真实生成与抽读中检查。

## 讲解与证据

第一次用术语时结合场景解释。例如文档的稳定身份叫 Source，每次保存的内容叫 Revision；先说明为什么需要保留旧回答引用，再给术语。

案例可为教学构造，但要标明示例，不冒充真实事件。描述代码事实引用实现；描述历史动机引用决策；合理解释可标明推断，不因没有作者原话就禁止解释。不要把修订过程、测试计数、内部 ID、无关极限条件写进入门主线。

正文去掉引用仍应通顺。支持句子语义的短链接融入句子，独立来源放句段末“参考”，背景放弱化的“延伸阅读”。同一文件可以引用不同行；同一目标在同一段不重复堆放。代码只展示所引范围，上下展开有明确间距。

图服务问题：架构图说明分工，时序图说明一次运行，状态图说明阶段，表格说明差异。图与正文必须互相解释，不为丰富格式而凑图。

## 阅读检查

事实检查判断关键论断、范围、时代是否成立；读者检查判断页面是否回答计划中的问题、必要术语是否解释、案例是否贯穿、能否找到下一步。没有实质内容价值的页面不能靠引用齐全获得好评。独立模型判断是辅助，不冒充用户已验收。

## 成稿表达检查

仓库通过 osdk 引入 [lieflat-less-ai-tone](https://github.com/larashero3-dotcom/lieflat-less-ai-tone)，源码固定在 `osdk.lock` 的提交 `27d29232f101`。上游原件、MIT 许可证和辅助材料保留在 `.agents/skills/lieflat-less-ai-tone/`，并随 npm 包提供；它不会自动进入用户的全局 skills。

文档、代码、图片和会话分析，正式文章写作与维护、需求实现计划的角色都加载这份共享技能。Traex 自主调查时，运行时核验摘要并复制完整包到隔离工作目录的 `.trae/skills/`；其他现有传输按角色规则内联主技能。独立 `knowledge-verifier` 也读取同一份规则，从自己的会话检查成稿。

先按读者目的调查和写作，再检查成稿表达。此技能只按明确规则做最小改写，保留事实、限定条件、引用、代码和结构；不靠替换词语补救缺失案例或错误解释。复核报告指出原句和规则编号，轻微措辞放入建议，不反复重写全文。JSON 合同与引用仍由原流程校验。手工更新项目文档也按这些规则检查。

升级时用 osdk 更新来源和锁定记录，再更新引用它的角色摘要。安装成功、摘要检查和模型读取记录证明技能已装配，不能证明每篇文章已经让人读懂；仍需抽读页面目标、案例和修改入口。

## 视觉与操作

继续使用根 design.md 的黑白灰与 packages/ui。主菜单保持稳定，学习目录放页面内，正文适当限制行宽，页内目录可定位。标题、段落、图、表、代码和按钮组都要有明确的垂直间距；卡片中的正文不能贴边，按钮换行仍保留行列间距。

桌面与 768/390px 真浏览器检查。引用沿用一个 trail dialog：返回恢复每层滚动、展开状态与焦点。产品默认强调解释与任务，不把内部处理状态作为阅读主线。
