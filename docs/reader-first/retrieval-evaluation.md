# 中文重排应该放在哪里，怎样决定是否采用

本轮对应材料理解报告的第三项后续工作。先把明确方法名的漏召回修好，再比较成熟融合和中文重排。**是否值得启用，要看同一批材料上哪些问题变好了、哪些退步了、增加多少等待时间。**模型较新、模型分数较高和模型复核通过都不是采用理由。

## 一次搜索其实有四次不同的选择

以“这个方法如何保存一次修改”为例：

1. **召回材料**：全文、向量和明确符号各自提供候选。正确方法没有进入候选时，后面的重排看不到它。
2. **判断能否回答**：问的是保存机制，提到“修改”或“记忆”的页面不一定有帮助。还要区分现行实现、旧计划，以及问定义还是调用方。
3. **补成完整说明**：方法调用了别的服务，或设计理由在另一篇文档里，需要沿原文继续读。重排一段文字不能自动补齐整条业务链。
4. **写给人看**：先回答问题，用一个例子解释状态如何变化，再给必要概念与修改入口。若派生文章只有职责套话，把它排到第一也不能让人理解。

这四步应分别记录失败原因。程序检查只负责接口、范围与行为没有破坏；真实问题的全文命中和阅读判断负责选择方案。

## 本轮已改的代码

`retrieval/relevance.ts` 从问题中提取明确的操作名；单独查找、引号、驼峰、下划线或限定名都可以提供符号入口。普通首字母大写单词和缩写不会仅凭大小写变成方法名。这个启发式仍不能理解所有自然语言查找意图。

`retrieval/unified.ts` 从 AST 派生的检索单位中独立查定义，按正式范围过滤，再与全文、向量融合。同一方法不再依赖长问题的 BM25 排名存活到前 100 名；进入可选重排的 40 个候选时也保留定义入口。同名定义均可参与，提到一个名字的文档不会因此被标成定义。定位仍指向固定原件版本与行范围。

这解决的是候选遗漏。现有最终排序仍有定义偏好，**问调用方时可能优先给定义**；长句中出现不存在的操作名时，也仍可能返回其他主题相关内容。不能将“查到名字”宣称为“理解了问题”。

## 借鉴哪些成熟方法，融入哪个位置

| 方法 | 对本项目有用的部分 | 如何进入现有代码 | 本轮状态 |
| --- | --- | --- | --- |
| Qdrant 多阶段检索 | 多路候选先独立产生，再融合、重排，避免一条路线提前丢掉所有材料 | 在 `UnifiedRetrieval` 分开 `lexical`、向量和 `symbols`，通过 `fuse` 汇合；保持 `RetrievalHit` 和原件版本 | 已采用分路原则；对照 RRF 融合，没有安装 Qdrant |
| BGE cross-encoder | 把问题和候选段落成对阅读，补向量相似度的不足 | `reranker.ts` 实现现有 `RerankerModel`；`factory.ts` 只负责显式配置，Agent 共用同一入口 | base 与 v2-m3 均用实际 q8 CPU 推理对照，默认仍关闭 |
| Qwen3 reranker | 使用任务指令判断段落是否满足问题，可单独比较查机制和查背景 | 应新增独立评分适配器；不能把 causal LM 当现有序列分类器加载 | 未运行；所查 ONNX 版本面向 Transformers.js v4，仓库为 3.8.1，先隔离验证 |
| Zoekt 代码搜索 | 成熟的 trigram 文本查找适合大代码库的精确内容搜索 | 以后作为代码候选适配器，结果按被索引快照映射到 Source/Revision/行号；不能直接跳到最新工作区文件 | 只调研；不是业务含义或类型调用关系的替代品 |
| Contextual Retrieval | 每段知道自己处于什么文档、章节和场景 | 继续完善 `units.ts` 的背景与原文范围，章节用途进入正式描述；同一文本供全文与向量使用 | 已有结构背景和段落概念，未逐段生成完整语境 |

以上依据分别见 [Qdrant](https://qdrant.tech/documentation/search/hybrid-queries/)、[BGE 作者模型说明](https://huggingface.co/BAAI/bge-reranker-v2-m3)、[Qwen3 ONNX 适配说明](https://huggingface.co/onnx-community/Qwen3-Reranker-0.6B-ONNX/blob/main/README.md)、[Zoekt](https://github.com/sourcegraph/zoekt) 和 [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)。方法适配与平台迁移是不同决定；当前问题没有证据表明必须先换 SQLite。

## 对照怎样避免自欺

固定 12,507 个检索单位的数据库快照，五组共用同一原件、知识、材料说明、中文 embedding 和开发入口的旧来源过滤。比较旧实现、新符号入口、候选融合改为 RRF、BGE base、BGE v2-m3。RRF 组只替换融合公式，最终用途与材料状态偏好仍在，不能说成“纯 RRF 系统”。

16 个问题中，前 10 个是已经出现在材料库中的回归问题，不能当未知题；后 6 个在冻结之后提出，包含方法长问法、调用方、日常延后和不存在的符号。没有将题目、预期路径或答案交给材料分类模型，也没有按题调权重。保留每题前 30 个结果、前 5 个完整单位和重排实际输入，不只保留好看的截图或平均数。

现有重排路径使用前 40 个候选，背景加正文摘录，最多 512 个模型 token；分数经过现有温度变换并与融合分数混合。这些是宿主现有策略，**不是 BGE 官方建议配方，也不是答案正确概率**。本轮保持它们一致来比较替换模型的实际结果；不能据此断言某个模型在最佳配置下的上限。输入截断、候选缺失、最终用途偏好都会影响结果。

查询向量预热后计时，模型首次加载、材料读取和真实入口过滤仍可能影响单次延迟。这是一台本机的顺序实验，不能当生产吞吐或严格性能基准。首次实验发现旧实现打包时机错误且漏掉开发入口的历史来源过滤，已废弃为效果证据，保留诊断记录后按一致规则重新测量。

本轮逐题结果、退步与耗时保存在[检索对照报告](../../.repo-review/knowledge/verification/symbol-reranking.md)，不继承上一轮通过率。

## 下一步怎么做比较合适

**先完善“这个问题需要哪类材料”，再决定更换重排器。**代码问题应能表达定义、引用位置、机制和设计背景等查找意图；复用现有代码导航和 Agent 调查，不给每种中文问法写路径规则。若一个方法不存在，要明确缺口，不能用几个泛化段落填满答案。

在离线实验中进一步分离三层：候选池是否含可回答材料；只看模型输出时如何排序；叠加现有用途与状态偏好后如何排序。这样才能知道错误来自模型、输入摘录还是宿主公式。截取正文要围绕实际命中段落，必要时带相邻章节；对长方法先验证关键逻辑是否被截掉。保留足够原件由 Agent 补读，不把重排窗口当写作材料的上限。

Qwen3 可作为下一项隔离实验，以同一批候选和任务指令比较中文机制理解与否定意图，同时记录冷启动、常态延迟及内存。先使用上游推荐的输入与评分方式，确认推理适配可用，再讨论共享接口或依赖升级。若没有稳定收益，保留现有默认；若只对某类查询有收益，应把用途选择做成明确策略，而非全局开启。

知识文章按问题检查内容本身：读者是否能复述一条实际流程、说清关键名词、用案例区分成功与失败、找到下一处代码。命中了一篇宽泛说明就标为“部分帮助”，不能因标题正确判为有效。补写对应机制和案例由实际 writer/独立 verifier 调查完成，不能手改模型文章来迎合题集。
