# 外部测试集与本轮检索诊断

更新：2026-10-04。目的在于判断设计和上下文是否真的有效，不再用本仓库几个预期路径或模型复核 accepted 代表质量。MTRAG Cloud、FreshStack Godot 和改造后 T2Retrieval 的完整词法检索对照已运行。其他数据集仅调研/抽查格式，尚未得到 omem 分数。

## 已运行：MTRAG Cloud

使用 [IBM MTRAG 官方数据](https://github.com/IBM/mt-rag-benchmark/tree/2c618bb98db3c8526433e22d8a2f7320f10a7470/mtrag-human/retrieval_tasks)，固定提交 `2c618bb98db3c8526433e22d8a2f7320f10a7470`。Cloud 实际文件有 **72,442 个段落、188 个问题**；不能沿用旧 README 的语料计数。lastturn 和 rewrite 是同一批问题的两种输入，不是 376 个独立样本。

基线实现提交 `315915f`。两侧共享官方段落边界、标题、ICU 分词、查询词提取、FTS5 字段权重和正例标注：

- BM25：直接取 FTS5 排名前 20。
- omem 词法链：调用实际 `UnifiedRetrieval.search`，包括其词面过滤、排名和每个原始文档最多两段的规则。

没有重新切片、向量、材料分类、派生文章、reranker、ACP 或答案生成。本实验既不是论文 BM25 复现，也不是中文混合检索或完整 Agent 评测。官方 rewrite 是提供的独立问句对照，不能当作 omem 已完成追问消解。

| 问题形式 | 方法 | Recall@5 | Recall@10 | Recall@20 | nDCG@10 | Hit@5 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 最后一轮原问句 | BM25 | 19.97% | 26.70% | **33.30%** | **0.2062** | 31.38% |
| 最后一轮原问句 | omem 词法链 | 19.35% | 25.42% | 31.24% | 0.2004 | **31.91%** |
| 官方改写问句 | BM25 | 22.69% | 28.66% | **34.03%** | **0.2242** | 34.04% |
| 官方改写问句 | omem 词法链 | **22.91%** | 27.79% | 32.13% | 0.2205 | **35.64%** |

Recall 是每题标注正例的覆盖率再平均；Hit 是是否至少找到一个正例。nDCG 此处使用二值正例，不把它叫答案正确率。未标注段落不等于已经证明无关。

原问句中，现行规则的 Recall@20 有 10 题改善、16 题退步；3 题从有正例变为一个正例都没有。改写问句有 6 题改善、16 题退步，也有 3 题丢掉全部正例。前五条是否命中略有改善，而需要的材料总覆盖下降；这是取舍，并非所有指标都失败。

**可以得出的结论**：当前词法附加规则没有稳定胜过简单基线，应拆开召回、回答材料选择与界面去重。**不能得出的结论**：不能指定某一权重为唯一原因，不能据此关闭中文向量、宣布 BM25 全面更好，不能声称已经提升生产体验。未做显著性分析，也没有测量回答耗时。

### 复现与数据保留

```bash
osdk run benchmark:mtrag
# 可选指定忽略的缓存目录
osdk run benchmark:mtrag .repo-review/runtime/design-audit
```

入口是 `scripts/benchmark-mtrag.ts`；`config/benchmarks/mtrag-cloud.json` 固定公共文件 URL、版本、大小和 SHA-256。首次会下载公共语料，不下载模型、不调用模型。原件按官方 ID 建临时索引，问题与答案标注不进入材料；结束删除临时数据库和解压文本。缓存和逐题排名留在指定 runtime 目录，`ranking-report.json` 覆盖同一文件。本轮实际报告位于 `.repo-review/runtime/design-audit/ranking-report.json`，不提交外部原文、题目或整库数据库。

脚本核对所有正例都存在于完整语料，问题集合与标注分母一致。它绕过 Capture，使用官方段落定位，因此不证明我们的材料清洗、版本引用或摄取流程正确。公开数据的权利与引用说明仍以上游为准。

## 已运行：完整中文 T2Retrieval 词法对照

`osdk run benchmark:t2` 使用 [C-MTEB/T2Retrieval](https://huggingface.co/datasets/C-MTEB/T2Retrieval) 的完整 corpus/queries 和独立 qrels：118,605 份材料、22,812 个问题、118,932 条正例关联。版本、下载地址、文件大小和 SHA-256 固定在 `config/benchmarks/t2-retrieval.json`。使用成熟的 `hyparquet` 读取官方 Parquet，不自行转换标注或挑掉长材料。

这一轮只比较相同 ICU 分词与 FTS5 字段权重下的 BM25 和当前生产词法链，不调用 ACP、向量或重排，不代表完整中文 RAG。官方语料未提供上层原文关系，因此每条官方材料独立作为 owner；它不能评估父章节补读或同文件多个答案点的覆盖。材料原文保留官方格式；查询、qrels 和评分只在评估侧，绝不进入索引或个人库。

实现 `4848871` 的完整对照已于 `2026-10-04T12:27:02.355Z` 结束，22,812 题全部完成，进程退出 0，临时数据库已释放。结果在 `.repo-review/runtime/benchmarks/t2-bounded`，运行身份为 `aee44cc049404e6dbcec5976ef8e25ce82d02c864dcd347e6744f3f7f94b27aa`。

| 方法 | Recall@5 | Recall@10 | Recall@20 | nDCG@10 | Hit@5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 透明 BM25 | 38.0386% | 47.0236% | 54.2599% | 0.475933 | 70.0640% |
| 改造后词法阅读结果 | 38.0386% | 47.0233% | 54.2596% | 0.475930 | 70.0640% |

只有六题的前二十条 ID 排列不同，Recall@20 无改善、一题退步，没有题目从有正例变成完全丢失正例。该退步发生在阅读结果的相同正文去重：官方不同 ID 的相似材料分别有正例标注，指标仍照官方 ID 计算，没有合并标注来修饰结果。助手关闭阅读分组的路径不在这次 T2 的独立测量范围中。每题两条链合计耗时中位数为 87ms，不是生成答案的延迟。

结论是删除额外词面门槛后，这条中文词法路线基本回到透明 BM25；没有证据说它超越基线。约一半标注材料仍未进入前二十，下一步收益应来自中文语义、完整上下文与回答材料选择，而不是继续叠词面权重。改造前旧进程仍在跑，不能用它的部分结果计算本轮改善幅度。

脚本已验证完整语料导入、逐题比较、正常中断时保存进度与释放临时数据库。结果覆盖同一 runtime 目录的 `ranking-report.json` 和 `rankings.ndjson`；实现与数据身份相同才可续跑，变化后用 `--reset` 替换旧对照。完整跑完前标记 `complete: false`，按原始顺序得到的前几百题不作为整体分数发布。

## 已运行：FreshStack Godot 的答案要点覆盖

`osdk run benchmark:freshstack` 使用完整 Godot topic：99 个问题，25,482 行官方语料，按上游 DataLoader 的字典覆盖语义保留 25,477 个唯一段落（五个重复 ID 中有两个内容不同）。数据版本、校验和及官方指标代码的提交和校验和固定在 `config/benchmarks/freshstack-godot.json`；查询使用官方标题加正文。答案与 nuggets 只进入评分侧，来源 URL 用于同文件分组，byte offset 保留在原始数据里。

指标直接调用 [FreshStack 官方实现](https://github.com/fresh-stack/freshstack/blob/f1c4ec96477f5100f10c83798d33b3101db727fa/freshstack/retrieval/metrics.py)。Python 与指标依赖由 osdk/隔离环境准备，不成为应用运行依赖。上游 alpha-nDCG 对空结果会抛异常，适配器跳过该空运行的计算，但保留全部 99 题的分母，空结果仍计零分。可用 `--evaluate-only` 对已保存排名重新评分，不重跑检索。

| 方法 | alpha-nDCG@10 | 要点覆盖@20 | Recall@20 |
| --- | ---: | ---: | ---: |
| 普通 BM25 | 0.1156 | 22.37% | 12.68% |
| 改造前助手词法候选 | 0.1076 | 21.36% | 12.40% |
| 改造后助手词法候选 | 0.1156 | 22.37% | 12.68% |
| 改造后界面分组结果 | 0.1149 | 21.70% | 12.17% |

一次真实报错问题被“调用者”自动识别错误地分流，得到零条候选。现已收窄首行请求判断，缺少 AST 调用位置时普通请求回到文本召回；显式调用者过滤不变。同时删除会排除简短接口说明的最少匹配词数门槛。完整重跑后，助手词法候选恢复到 BM25 的上述指标；这一结果证明修复了本轮损失，不证明超过 BM25 或已做好中文混合检索。

同文件分组仍损失少量要点，继续只用于阅读列表，不用于助手装配材料。上述覆盖率本身仍低；下一步需要处理语义召回、问题范围和完整答案上下文，不能把这一分数写成系统已能准确回答八成问题。此实验未运行 AST 解析、中文向量、重排、材料分类、ACP 或回答生成。

候选读取的纯性能中间版本在 99 题的三条排名链上与原实现完全一致；每题三条链的合计中位耗时从 3,892ms 降到 1,667ms。它证明可以不改变排名就减少全量原文处理；并发后台任务、缓存和后续导航改动会影响耗时，不把这一组数字当单次用户搜索的固定延迟。

原始基线保留在 `.repo-review/runtime/benchmarks/freshstack-godot`，最终实现对照在 `freshstack-bounded`；运行临时数据库已释放。只发布本节简报，不提交题目、答案、整库原文或重复数据库。报告中的源码指纹用于区分实际实现；当时 HEAD 只是运行起点，不能据此把未提交的改动算到旧提交里。

## LongMemEval：给足相关会话后的七类诊断

2026-10-04 已完成真实 Traex ACP / gpt-5.6-sol 对照。使用官方 cleaned 数据的 oracle 文件，固定修订 `98d7416c24c778c2fee6e6f3006e7a073259d48f`；500 题中按类别各选 SHA256(question_id) 最小的一题，在运行前固定七题和 12 段相关会话。没有把长历史压缩成人工摘要，也没有运行完整 s/m 历史、官方裁判或排行榜总分。

两条路线使用同一批原始 user/assistant 会话和相同 Sol/medium：一条直接阅读全部相关会话作答；另一条用 Hindsight 0.10.2 逐题独立 bank，按日期 retain 后 reflect。问题与标准答案不参与记忆整理，has_answer 标记剔除；原始会话 ID 只作不透明文档身份，不提供答案会话列表。问题日期随回答请求提供。这是相关会话已给足时的整合诊断，不能算长历史召回能力。

| 类别 | 人工抽读结果 |
| --- | --- |
| 缺失信息 | 两条路线都指出没有十二月参观记录、无法确定数量；Hindsight 另列一二月记录，增加了无关篇幅 |
| 知识更新 | 直接 Sol 回答衣橱鞋架，符合标注；Hindsight 回答最后确认在床下、鞋架尚为计划。原会话同时含鞋架位置线索和未来存放措辞，需单列为原文含糊/标注分歧，不能简单判定哪条路线理解更好 |
| 跨会话合并 | 两者均合并看诊 50 与药物 25，得到 75 |
| 找回助手建议 | 两者均找到 Miss Bee Providore；Hindsight 增加日期与地点限定 |
| 个人偏好 | 两者都给远程同事虚拟咖啡交流建议；Hindsight 更明确关联先前讨论及共同决定形式，但输出冗长 |
| 找回用户经历 | 两者均找到 The Glass Menagerie；Hindsight 额外补了演员与朋友的背景，问题并不需要 |
| 时间先后 | 两者均判断美西家庭旅行在欧洲独行前。原文只说“几年前”和“去年夏天”，Hindsight 额外细化为约 2020 年；相对顺序有依据，具体年份不是原文明确事实 |

Hindsight 七题均完成，无 case 级失败；回答 109.46～138.21 秒，中位 124.60 秒。12 次 retain 各 144.67～258.87 秒，累计 2309.55 秒，不能从总成本中省略。直接阅读回答为 10.01～18.90 秒，中位 12.45 秒；它无需先整理记忆，但已经拿到全部相关会话，不能据此声称能在任意长历史中这样回答。

这批结果没有证明引入整个 Hindsight 问答循环有净收益。它是当前 ACP 适配器、Sol 与 BGE-small-zh 的实际组合，不是上游服务的固有速度；公开样本是英语，中文 BGE 也不能用来推断其最佳检索效果。时间题元数据还有晚于 question_date 的同日会话，双方均沿用官方 oracle 范围，故不当作严格 as-of 测试。

下一步保留 Hindsight 作为可选持续主题视图候选，先解决原件定位与事件时间映射，并比较“后台整理 → 快速读取视图/原件 → 必要时调查”。不要让每次简单查值都进入完整 reflect。现有 MemoryService 保持事实和事项应用职责，生产暂不接入。

数据、选题、逐题输出和人工备注在 `.repo-review/runtime/benchmarks/longmemeval`；原始文件 SHA256 为 `821a2034d219ab45846873dd14c14f12cfe7776e73527a483f9dac095d38620c`。实验数据库及专用适配服务已停止，结果只更新本简报，不提交整库会话或新建一套历史报告。

## 别人的测试是否就能直接照搬

[Hindsight 的 benchmark 仓库](https://github.com/vectorize-io/hindsight-benchmarks) 区分速度/结构可靠性与 LoCoMo/LongMemEval 质量，还给出逐题结果和模型条件；[Mem0 的 memory-benchmarks](https://github.com/mem0ai/memory-benchmarks) 把摄取、搜索、答案生成和评分分开。可借用适配与结果格式，但排行榜常混合不同模型、上下文长度和成本，不是换一个组件就能得到同样分数。下一步比较应保持回答模型、历史可见范围一致，同时记录后台整理成本和回答时间。

[deepwiki-open 的所抽查页面测试](https://github.com/AsyncFuncAI/deepwiki-open/blob/d92819a9c9f3b99416e3580ff235fc9d3adf8b89/tests/backend/services/test_wiki_content.py) 主要检查引用/链接处理；不能以这些测试通过证明陌生读者能看懂。这里只描述已抽查的测试，不推断项目不存在其他评价。[RAGFlow benchmark CLI](https://github.com/infiniflow/ragflow/blob/main/test/benchmark/README.md) 也明确区分协议成功与内容质量：空搜索结果仍可能是成功请求。这与 omem 应把工程检查和用户效果分开是同一个问题。

公开测试集也有语言、领域、标注完整性和模型污染限制。采用它们是为了脱离本仓库题目循环，不是用另一个总分替代阅读判断。

## 后续评价怎样减少重复劳动

1. 每个改造只运行它影响的层：内容与发布改动看阅读任务和更新过程；召回改动看公开检索子集；记忆改动看跨会话更新。保留正常工程检查，但不每轮重跑所有昂贵模型流程。
2. 固定数据版本、完整选定子集、模型/effort 和预处理；开发集用于选择，其他领域或保留集报告退步。不能根据答案路径写规则，也不能看完公开题后称其为未见测试。
3. 给足正确原件与真实检索共用回答条件。前者仍失败就先改讲解/问题理解；前者成功、后者失败才继续改检索。完整答案必须覆盖关键前提，不能只评引用和关键词。
4. Wiki 不另造庞大的合成题库。每个主题检查读者能否解释一个完整过程、定位一个实现并开始一次真实操作；记录完成与困惑的具体位置。内容验收不等于强制图表数、字数或章节数。
