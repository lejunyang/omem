# 整体复审：基础设施已有，解释与使用链路不足

日期：2026-10-01。本文记录重构前的代码审查与用户反馈；后续实现以 progress.md 为准。

## 核心判断

此前把原文保存、固定引用、独立复核与形式化检查放在主要位置，却没有同等重视读懂、找全答案、用于下一次行动。每句话有依据不等于文章有帮助。需要改变选题、调查上下文、讲解结构与实际验收方式，而不仅增加“写得通俗”的提示。

## 审查时的实际能力

| 环节 | 已有 | 主要问题 |
| --- | --- | --- |
| 输入 | 文本、图片、链接、来源与固定修订；仓库排除部分非材料文件 | 接入和保存多于内容清洗；历史方案与当前状态混杂 |
| 切片 | 通用文本按空行形成 Fragment；向量以 400 字符窗口、80 字符重叠索引 | 存储单位被误当作检索和讲解单位；缺少父章节、表头、完整函数与对话上下文 |
| 代码 | TS 单文件 AST、Vue 脚本、符号、相对 import、部分候选调用 | 没有完整类型解析；结构定位不能代替功能、业务与设计理解 |
| 检索 | FTS5/BM25、中文短词、符号、记忆和知识召回；BGE-small-zh-v1.5、RRF、MMR | 顶部搜索仍是 LIKE，文章搜索又是简单匹配；没有统一问题上下文或专用 reranker |
| 问答 | 原片段入模型、有限改写补搜、会话和事项上下文 | 不会稳定补齐跨模块流程、设计记录和历史时间信息 |
| 记忆 | claim/episode/procedure/task、抽取/复核/应用、来源变化重核验 | 条目很多，缺少持续整理的人物、项目与主题理解；重要性与主动使用不足 |
| Wiki | 分析、规划、写作、独立复核、修订、发布 | 文件逐份说明、按目录汇总；计算分组替代概念组织，摘要再摘要丢失具体性 |

自动抽取记忆与维护 Wiki 不是一条完整用户流程。通用 analyze 处理材料，仓库脚本另做章节；复用运行时不等于端到端体验已经相同。

## 为什么 Wiki 会变成正确的废话

当前分析器只看到目标材料及少量补充。仓库脚本补充最多四个 import 文件的前 70 行，角色不能自行读取其他文件。发现背景缺失时，流程更擅长删掉未支持结论，而不是继续调查。

文件先生成短说明，再按目录综合；超过 12 个子项时按数量分组。上层越来越多依赖摘要，具体例子、因果关系与功能链容易消失。通用的 2–4 节、300–700 字建议也不能同时满足教程、机制解释和参考文档。

实际抽查发现：入门文章较早引入 Source/Revision/Fragment 与证明责任，正文又讨论 200 层深链和开发恢复；检索文章写入“此前引用已被更精确范围替代”。这些可能事实正确，但混淆了阅读层次，甚至把编辑过程发布成知识。

当前独立 verifier 主要检查事实、时代、范围、前提及引用支持性。它没有评价页面是否完成读者任务。生成和复核均使用真实 traex ACP 的 gpt-5.6-sol，分开会话不消除共同盲点。检查通过只证明对应机制运行，不证明人能理解或检索有效。

## 需要借鉴的成熟做法

| 来源 | 借鉴内容 | 取舍 |
| --- | --- | --- |
| [Docling](https://docling-project.github.io/docling/concepts/chunking/) | 按结构与长度预算切分，保留标题上下文 | Markdown/代码先用已有解析能力；复杂 PDF/Office 适配成熟解析器 |
| [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) | 给片段补足文档内具体背景，再索引 | 背景是派生解释，与原文分开；外部实验数字不是本库收益 |
| [Aider repo map](https://aider.chat/docs/repomap.html) | 用符号和依赖在预算内选上下文 | 用地图引导进一步阅读，不等待完整运行时调用图 |
| [DeepWiki](https://docs.devin.ai/work-with-devin/deepwiki) | 每页明确 purpose、层级、重点，并结合代码搜索 | 借鉴页面规划；公开文档不代表已知其闭源内部实现 |
| [Diátaxis](https://diataxis.fr/start-here/) | 教程、操作指南、解释、参考分开 | 不给所有页面套同一个模板 |
| [C4](https://c4model.com/diagrams) | 从整体到局部逐层解释系统 | 只画有助于回答问题的层级 |
| [GraphRAG](https://microsoft.github.io/graphrag/query/overview/) | 局部与全局问题采用不同上下文 | 不默认给所有问题建立图数据库 |
| [Hindsight](https://hindsight.vectorize.io/developer/mental-models) | 持续维护项目、人物、主题的综合理解 | 后续用真实材料对照适配，能减少自研就采用 |
| [Graphiti](https://github.com/getzep/graphiti) | 随时间演变的事实与关系 | 区分事件时间、获知时间、当前有效状态 |

此前 research 与 2026-10-01 文档已研究多项方案，但没有充分转化成内容样板和实际流程。不能仅因外部组件没有本项目的 Fragment 合同而否决；先评估来源元数据映射、更新与删除语义。deepwiki-open 是独立开源项目，不能当成商业 DeepWiki 的源码。

## 检索和记忆的判断

先统一入口，再补充结构和上下文，然后才对照 embedding/reranker。当前 SQLite 精确向量计算对个人规模未必是主要问题。精确符号、整体机制、历史原因、个人经历、近期变化需要不同上下文；一套 top-k 不能概括所有需求。

综合知识应能作为回答背景，原始来源继续承担追溯。不能为了“不把摘要当新证据”就把所有已整理的理解再次丢掉；同一事实通过多个摘要命中时也不能算成多份独立支持。

记忆应从原始记录形成经历、当前事实、经验和持续理解，再用于行动。不是所有仓库配置都与用户承诺同等重要。英语学习中，公共知识、个人易错点和复习任务不同，但可共享来源。卡片排程与自动监听仍是后续能力。

## 判断改进是否有效

以五篇页面和一小组真实问题开始，检查读懂、定位、修改、找全、时间正确和可行动。给足正确材料仍答不好是生成问题；给足能答好而检索后答不好是检索问题。参考 [LongMemEval](https://github.com/xiaowu0162/LongMemEval) 的问题类型，不用其基准替代用户任务。保留必要回归检查，避免重新搭庞大评分框架。
