# 整体复审：为什么流程接通，内容仍不好用

更新：2026-10-04。审查基线为 `315915f` 的实现、已提交模型正文和隔离运行库；这一轮没有改变生产排序、知识发布或助手行为。此前的复审已经提出不少正确原则，问题是这些原则还没有成为产品的主要组织方式。

## 结论与取舍

**优先重构文章的发布与维护，再简化检索，随后接持续主题记忆。** 暂停继续筛小模型和围绕少量仓库题调权重。保留统一原件、固定引用、Traex 原生调查和 MemoryService；不要再为每个文件自动制造一篇面向读者的 Wiki。

系统已经有自主搜索、文件补读、工具调用、写作和独立补查，并非只有一次 prompt/schema 输入输出。真正缺的是：哪些内容值得成为文章、目录如何保持完整、已有理解如何随变化维护，以及当前问题究竟缺哪一块答案。更多工具、复核次数或引用不能自动补上这些设计。

## 本轮直接查到的问题

### 1. 文件说明与正式文章仍混在同一层

`.repo-review/knowledge/articles` 有 512 份 JSON 资产，其中只有 6 份带读者页面计划 `reading`。隔离库有 494 个文章 head、133 个 current head；导出的 `.repo-review/wiki.md` 当前目录中，104/133 项在“未分类”。这些是不同口径，不能把文件数当成可阅读页面数。

`KnowledgePipeline.analyze()` 仍给每份材料生成说明；`synthesize()` 仍在子项超过 12 个时按批次生成“专题”。新的 `writePage(brief)` 可以跨材料调查并围绕读者任务写作，但它与旧产物共享发布、列表和检索地位。仅增加六篇指南，不能改变整个库的阅读体验。

这不是 AST 不够聪明，而是**内部整理结果被直接当成最终知识产品**。一行重新导出、配置字段或测试文件常常只需要属于某个概念的参考信息，不需要独立文章。判断依据应是持久化的内容用途和读者任务，不能在通用代码里按路径、仓库名或 `guide:` 前缀特判。

### 2. 综合解释比小文件说明更容易整体过期

六篇指南在当前隔离库中全部为待更新。每篇依赖 14～41 份材料；其中 2～19 份是调查读过但没有直接引用的材料。`knowledge/pipeline.ts` 把写作者和复核者的读取记录加入依赖；`knowledge/repository.ts:refresh()` 对整份材料 digest 比较，只要任一依赖变化就让整篇失去 current 状态，并向父文章传播。

探索得越充分，页面越容易被无关修订牵连。即使引用附近的结论没变，另一个章节或进度说明改变也可能使文章过期。`retrieval/units.ts` 已经能保留仍有依据的章节，但原材料支持性仍按整份 digest 核对。本次六篇指南的 41 个章节仅有 17 个留在检索投影中，概览和修改指南没有章节留下。

需要区分三个事实：导出的当前目录只收 current，因此没有六篇指南；开发适配器会恢复历史，文章 API 也返回待更新文章，**不能据此说 dev 页面已看不到指南**；检索只保留符合现有依据检查的部分章节。本轮未重新浏览 dev 页面。

解法不是忽略版本或偷偷改指向最新原文。旧正文和固定引用继续存在；把“调查轨迹”“影响复查的依赖”“直接支持某段结论的来源”分开，原文变化先定位影响范围，再决定哪些章节要调查、修改或停止作为当前答案。目录与已发布页面身份不应随一次依赖变化消失。未引用的背景也可能重要，不能简单删除所有未引用依赖。

抽读是内容判断，不是全部文章的统计评分。新指南不是全无价值；问题在于好的写作方式还没有成为默认发布和维护方式。

### 4. 检索把过多职责压进一套排序

共享 `RetrievalPort` 和原始依据应保留。但“数据统一”不意味着找符号、解释机制、查约定、查历史都使用同一套排名规则。

当前 `retrieval/unified.ts` 同时包含词面覆盖门槛、标识符约束、用途偏好、向量尾部阈值、按原始分数调制的 RRF、定义偏好、文章和来源去重。部分规则在截断前后共同起作用。长期维护的成本是很难判断：是没召回、被门槛删掉、被别的来源挤掉，还是答案本来就不在一个段落中。

新跑的 [MTRAG 外部对照](external-evaluation.md) 使用完整 Cloud 子集：188 个问题、72,442 个官方段落。只看最后一轮问题时，普通 FTS5 BM25 的平均 Recall@20 为 33.30%，现行词法链为 31.24%；现行 Hit@5 略高，31.91% 对 31.38%。说明它是有得有失，不能笼统宣称现有附加规则改善了检索。此次未启用向量、重排、材料分类或 Agent，不能归因于某一个权重，更不能代表中文完整 RAG。

下一步应把“候选召回”“选取回答上下文”“阅读界面分组”分开。例如每文件最多两段有利于首屏多样性，却可能妨碍同一文件里多个必要事实的覆盖。词法用透明基线，精确符号走定位，语义问题补父章节和相关原件；显式时间/范围条件仍在边界处执行。跨轮追问先利用会话解释对象，必要时澄清；不要让无上下文的小模型强猜。

### 5. 现有评测容易回答错问题

六个预期路径命中、四份短材料的语义冒烟和协议 fixture 都有工程价值，但不能证明长问题找全了答案，或人读懂了 Wiki。回归问法后来进入被索引文档，更不能当成独立泛化结果。

`quality/evaluator.ts` 的词汇、数字和否定词规则也不是语义裁判。本轮实际调用发现，主体互换、改期方向互换的短句仍可能判 supported。它属于离线规则评估，不是生产知识 verifier；应保留作确定性检查，停止以它的分数代表意义正确。

外部测试要分别检查中文检索、代码与文档的答案覆盖、多轮问题、长期更新。提供正确材料仍答不好时修写作；材料根本没找全时修召回。详情和已运行/未运行边界见[外部评测](external-evaluation.md)。

## 一个读者真正需要怎样学习

不要先让人背对象名或读保护机制。先看到一个真实问题，再沿着同一个对象观察变化，随后理解概念、因果、取舍和修改入口。

例如讲“原材料更新后怎么办”，应先展示一条约定、一次修改和用户看到的变化；再解释原文历史、当前记忆和知识文章为什么分别更新；最后指出用户在哪里确认结果、开发者从哪些入口修改。这只是讲解顺序，不应把示例写成系统已经自动具备的能力。

建议给页面选择一种主要用途：

- 入门：完成一次任务，过程中介绍必要概念；读完能开始使用。
- 机制解释：同一个输入经过哪些处理，为什么这样分工，何处会失败；读完能预测行为。
- 操作指南：触发条件、步骤、可见结果和排障入口；读完能完成操作。
- 参考：符号、字段、约束、版本，便于定位；不强行扩写成教程。

图解释分工、顺序或状态；表格比较容易混淆的概念；代码展示关键行为；引用贴近需要追溯的结论。是否有帮助取决于内容，不取决于有没有凑齐图、表、三段标题。复核除了核事实，还要实际尝试用文章回答页面原定的问题；读者评价与事实评价应分别记录。

## 成熟方案如何改变这次实施

- **DeepWiki 的页面规划**：先定整套功能地图、页面目的和相关原件，再写各页。omem 已有 brief，但要把它变成发布主流程。独立开源的 deepwiki-open 也采用结构规划与页面写作分离；不照搬其来源数量或图表配额，不声称它是商业 DeepWiki 的源码。具体代码和抽查测试见[组件接入](component-integration.md)。
- **Docling + Haystack**：复杂原件由成熟解析器恢复结构，保留父子章节、表头和定位；检索命中小段后按需要恢复完整父语境。先接解析/检索组件，不先替换全部应用与原件存储。
- **Contextual Retrieval**：为检索片段补它在原文中的具体对象、版本和指代。当前标题路径与概念别称只是部分背景，不等于已经实现逐块语境生成；不应给所有段落复制一份泛化摘要。
- **Hindsight**：持续维护一个项目或主题的综合理解，变化后更新相关内容；旧视图可见，但过期时不作为直接回答捷径。这很适合补 omem 只有分散记忆条目的缺口。先适配来源与时间，使用相同问答模型作对照，再决定替换哪些记忆机制；外部组件不取得事项和事实直接写入权。

这些是本轮决策，尚未安装或接入相应新组件。来源、代码接点、运行代价和测试集写在[成熟组件与改造](component-integration.md)。

## 下一步按三个完整切片交付

### 第一片：让知识库成为可持续阅读的知识库

在 `packages/contracts/src/knowledge.ts` 和知识存储中明确内部笔记、参考材料、正式读者页的用途；页面计划和发布身份独立持久化。`analyze/synthesize` 默认产内部笔记，`writePage` 完成正式页面。老资产保留，按已保存计划和迁移结果赋用途，不靠 key/目录猜测。

改 `knowledge/pipeline.ts`、`repository.ts`、`artifacts.ts` 的依赖与更新：读取轨迹保留审计，支持来源关联到章节，变更先定位影响后复查。旧页仍能打开旧引用，受影响内容明确标注，失效与删除不同。API、知识目录和检索使用同一发布用途，查参考时仍可查到文件说明。

用真实 Traex/Sol 重写并维护一个完整主题：从概览到机制、使用/修改入口和参考。验收是陌生读者能解释和操作，以及一次无关改动不再让整条阅读路线失效；不是再把所有材料逐文件生成一遍。

### 第二片：把检索还原为可解释的几步

保留原件和 `RetrievalPort`，加入正式父章节关系及独立的回答上下文装配。先保留简单 BM25/标准 RRF 基线，让每个额外过滤都能说明丢了哪些必要材料；定位与综合问答不共用强制两段上限。跨轮对象解析使用会话和已有材料，无法判断再问用户。

用公开完整子集验证，而非继续扩 omem 路径题。优先中文 T2Retrieval 与代码/文档 FreshStack；每次实现只跑对应层，模型与界面未改就不重复昂贵 ACP/浏览器流程。给足材料和真实召回两条回答路线共用 Sol，判断瓶颈在找还是在讲。

### 第三片：持续项目理解与行动

先用一个跨时间主题接 Hindsight 的 retain/recall/reflect 和综合视图，映射到原件版本、实体和事件时间。用 LongMemEval 的更新、时间、跨会话和信息缺失任务比较；相同模型、可见历史及回答条件下决定保留/替换。外部反馈监听、间隔重复学习等在这个持续理解层上扩展，不继续围绕每个功能造一套临时记忆规则。

这一顺序把主要投入从局部规则和形式通过率，转向可读且能持续维护的内容，以及真正覆盖问题的上下文。不能把本次诊断和方案当作上述三片已经交付。
