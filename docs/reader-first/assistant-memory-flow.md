# 个人约定如何变成可查询、能跟进的记忆

本轮要检验的是一条普通生活流程：我保存周末读书会的费用约定，之后询问预算；约定改变后，助手使用新版本；我明确要求跟进报名确认，助手在约定时间提醒我。它不要求用户的每份材料都经过代码定义、调用链和修改入口等步骤。

## 场景与目前状态

**当前状态：第四轮真实全链验收通过，退出码 0。** 2026-10-02 使用真实 Traex ACP / `gpt-5.6-sol` 完成六轮助手交互，以及持续启用的材料提取和独立核验。预算从 80 元更新到 120 元时更新同一记忆；明确委托后只保留一条等待事项；延后提醒正确应用，完成后停止提醒。前三轮失败保留在文末，第四轮没有继承它们的通过状态。

普通个人笔记中写明每次参加读书会的费用上限为 80 元，再将同一笔记改成 120 元。预算是已确认的个人约定，保存它不代表让我自动报名，也不授权创建报名任务。后续跟进必须来自我自己的明确请求。

| 操作                   | 应当出现的行为                                           | 验收读取的位置                                    |
| ---------------------- | -------------------------------------------------------- | ------------------------------------------------- |
| 保存 80 元约定         | 保留原件、独立提取和核验，形成已应用记忆；没有报名事项   | 捕获 HTTP 响应、角色输出、MemoryService 回执      |
| 提问原预算             | 解释当前上限与适用范围，可读回原件；查询不产生事项       | 实际助手 HTTP 答案、引用与事项列表                |
| 将同一笔记改成 120 元  | 保存新版本，暂停依赖旧原件的记忆；补查后更新同一记忆 ID  | 原件历史、memory version/dependency、refresh 记录 |
| 再次提问               | 使用 120 元，并解释和原约定的差别；80 元仍可沿旧版本追溯 | 实际答案、固定旧原件、新记忆正文                  |
| 明确委托等待组织者回复 | 创建一条等待事项，记录检查时间；不把跟进时间变成截止时间 | 原始用户指令、事项回执与 follow-up 状态           |
| 到约定检查时间         | 生成一次站内提醒，服务重启后仍能补发；重复轮询不重发     | 真实 Store.remind 时钟入口、提醒回执与通知 HTTP   |
| 改期及确认完成         | 依照新检查时间提醒；完成后停止；后台学习不重复建任务     | 事项版本、后台角色输出、去重和完成状态            |

## 如何运行与查看

执行 `osdk run assistant:memory-flow`，由 osdk 管理的 Bun 运行 `scripts/assistant-memory-flow.ts`。脚本使用 `config/review-code-model.json`，动态探测实际可用模型，要求真实 `traex` ACP 和 `gpt-5.6-sol`；不接受协议 fixture 作为模型运行。它启动仅监听本机的真实 HTTP 服务，使用同一自动 LearningPipeline 和 MemoryService，关闭飞书与外部发送，也不导入本仓库材料。

默认每次运行建立独立的 `.repo-review/runtime/assistant-memory-flow/<时间与运行编号>/`。其中保留原始 Markdown 文件、应用数据库、Agent 工作区中的输出与调查记录，以及逐步 `report.json`，成功或失败都不会删除整轮记录。会话用的临时只读快照在关闭后清理；固定原件和版本保留在应用数据库中。报告包含完整模型答案、实际任务变更、extractor/verifier 输出与 trace、来源换版、应用和提醒回执，不只记录布尔通过值。运行数据不进入 Git。

提醒时刻通过现有 `Store.remind(ISO时刻)` 推进，而不是等待墙钟到 2030 年。早到不提醒、重启后恰好一次、改期后恰好一次、完成后停止是四个独立检查。它验证的是实际提醒调度器和持久数据，没有伪造任务或通知。

## 已有机制与需要检查的缺口

新建“到某时提醒我检查”的事项使用 `follow_up.next_check_at`，没有明确完成期限就保持 `due_at=null`；它既不要求已有等待对象，也不需要先创建一个到期任务再延后。完成期限与提醒可分别存在，回执分别显示“截止时间”和“下次跟进”。2026-10-05 的同名项目三轮实测曾发现提醒被错存为期限，修正字段说明后重放已保存为跟进，并实际检查到点一次通知；具体结果见[项目材料](project-contexts.md#验证)。这不追溯修改旧事项，也不继承为全部时间表达已正确。

捕获换版会立即暂停依赖旧原件的记忆，并排入重查。LearningPipeline 将旧记忆 ID、版本和新原件给 extractor，要求支持时更新同一 ID；独立 verifier 对新原件复查，MemoryService 自主应用清晰、有限的变化。排入队列或模型输出成功不能代表记忆已更新，refresh 状态以应用结果核对。

记忆应用通知现在直接显示具体内容，例如“记忆已更新：周末读书会每次费用上限为 120 元”，详情显示之前和现在的正文，并把模型给出的理由作为补充说明。不再以“应用 claim：新记忆”作为更新通知。本轮已检查通知确实带有 80 元与 120 元的变化，而不只检查通知数量。

事项即时应用和后台学习原本分别有验收脚本，但普通用户会同时启用它们。助手保存的原始委托也会进入后台提取。现在 LearningPipeline 把这条原始指令的已有应用回执和当前事项状态交给提取者，并按固定片段与任务历史过滤已经生效的重复事项候选；名称相似度不决定是否重复。原始指令、模型候选、观察和其他记忆仍保留，即使该事项后来已完成或取消，也不会重新执行旧指令。迟到后台提取的行为回归已检查“前台应用→用户完成→后台仍提交创建候选”不会重建任务；协议 fixture 只验证这个行为合同，不作为外部模型成果。

本轮真实流程等待每次事项操作的后台处理结束：创建、延后提醒和完成之后，始终是同一个事项 ID，版本依次为 1、2、3；没有因后台提取另建任务，也没有重建已经完成的任务。完成后，用户报告的“报名成功”还被提取、独立核验并保存为另一条普通记忆，保留其“用户转述组织者回复”的来源说明。已应用事项的防重复处理没有丢掉这条新的生活事实。

## 这轮实际读到了什么、答出了什么

第一次提问得到：“你每次参加周末读书会，费用最多 **80 元**……它是**单次预算上限**，不是报名任务。”换版后得到：“现在每次参加周末读书会最多可以花 **120 元**……上限从 **80 元** 调高到 **120 元**：增加 **40 元**，增幅 **50%**。”这两轮均未创建事项。这里的阅读要求是解释适用范围和变化，而不只是匹配一个数字。

当前预算答案引用新原件的第 3–4 行；变化说明同时引用旧 80 元原件与新 120 元原件。Agent 自主调用 `material_history` 列出历史，再指定旧 revision 补读；HTTP 响应返回两个各自固定的原版本、digest 和范围。脚本逐项核对引用文字等于对应原件的实际行内容，旧引用没有跳到 120 元。

委托后的实际回执是：“已创建任务：跟进周末读书会报名确认；等待：组织者回复；下次跟进：2030年10月2日……09:00。”纯查询能解释“这是下次跟进检查时间，不是报名截止时间”；随后“稍后再提醒”实际提交为 `snooze`，由 MemoryService 应用并回复新的检查时间，最终确认完成得到“已完成：跟进周末读书会报名确认。”模型只提出行动候选，成功回执来自宿主。

两个约定时刻都验证了提前不提醒、到点生成一次、重复检查不重发。第一次提醒还经过真实服务关闭与重启。完成后的 2040 年时钟检查没有再生成提醒；持久提醒回执恰好两条，分别属于事项第 1 版和第 2 版。

六个 Agent 工作区的调查日志合计有 10 次成功 MCP 调用，包括中文 `search_materials`、列出材料、补读当前原件、列历史和补读指定旧版；没有 MCP 错误。不同提问采用不同补读路线：简单预算直接读原件，比较变化查历史，跟进问题搜索原始委托，纯事项回顾使用宿主提供的当前状态。没有强迫所有材料走代码导航。原生 shell 记录只读取各自工作区中的技能、目录和问题上下文，未再读取祖先仓库的 README 或进度文件。

完整报告在 `.repo-review/runtime/assistant-memory-flow/2026-10-02T13-22-55-776Z-670f40a8/report.json`，调查审计在同目录的 `research-audit.json`，日志为 `.repo-review/runtime/research/assistant-memory-flow-live-4.log`。运行从 13:22:55 UTC 到 13:32:12 UTC。运行开始时实现还未提交，报告中的 `implementationCommit` 是当时 HEAD；全程采用被冻结的工作区源码，对应实现现已提交为 `64824a6`。

独立人工复审随后发现：第二条提醒虽然按10月3日触发，正文却复制了原委托中的10月2日时间。当前提醒已改为显示持久保存的检查时间、时区、等待方与检查事项进展；原委托保留在事项详情，不再复制到主提醒。修复后用实际数据库改期、关闭并重开服务、触发提醒及再次轮询检查新日期和防重复。没有重跑六轮模型，也没有改写上述原始报告；状态通过不代表原提醒文案已经合格。

## 这轮仍不能代表什么

这份单一生活样例不能代表所有输入、检索问法和持续理解已经可靠。它没有加载内嵌 embedding/reranker；成功的材料搜索也不能替代较大、多主题个人库中的召回质量验收。没有添加竞争事实、多来源冲突、否定和含糊时间等扩展案例；下一步应围绕真实使用失败扩充，而不以更多形式化断言代替阅读与行动效果。

组织者是否回复由用户明确报告，此流程没有自动监听群聊或联系他人。提醒验证的是站内通知与调度器，外部渠道尚未接通；时钟入口用指定 ISO 时刻推进，没有等待墙钟到 2030 年。真实 HTTP 检查也没有代替完整浏览器交互与阅读体验验收。
