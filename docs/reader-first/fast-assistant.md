# 用快模型调查材料并回答

2026-10-03 决定：停止 Luna 对照，后续统一使用 Sol。本页保留既有实验和配置说明；新的质量改造见[按问题调查与答案复核](answer-investigation.md)。

## 当前改进：先读对位置，再决定是否继续查

真实问答日志显示，时间不全花在模型推理：初始命中的 `materialKey` 曾按存储命名空间重建，而引用与调查目录沿用输入适配器的正式别名，模型照抄也会读不到。现在 `assistant/runtime.ts` 保留检索返回的同一 key，历史引用也保留材料的公开定位，不在通用代码里解释某个仓库名前缀。

调查工具也有两个具体改动。`search_materials.keys` 和 `read_material` 共用定位解析，均接受返回的 key、材料路径或导出路径；未知或有歧义的路径明确报错，不再伪装成“没有相关材料”。`read_section` 可接收 `atLine`，读取命中所在的最内层完整章节或代码方法，避免猜章节名或从长文件第一行读起。搜索返回的目录范围按实际命中行筛选。原件、行号、授权范围与固定版本没有改变。

问答入口直接提供当前问题、准确 skill 路径和初始定位；完整摘录、旧会话、事项与解释仍在 `question-context.json`，追问和事项操作要求核对它。native skill 要求先判断结论、前提和操作入口是否已查清；材料足够便回答，有矛盾、缺条件或需跨文件解释则继续调查。询问自动行为时必须核对启用条件与触发点。没有新增 token、工具次数或研究轮数限制；没有用替换转义字符的规则掩盖模型格式问题。

ACP trace 新增启动初始化、会话准备、prompt 完成时间、首个工具等待及原生工具总数/失败数。prompt 时间包含模型、工具和服务等待，不是纯推理时间；总时间还包含初始检索、材料快照及会话清理。记录这些是为了定位开销，不能拿调用次数少替代答案有效。

这一轮不再调融合权重。初始排序把“问题计划”当答案的缺陷仍存在：尚未分类材料没有用途信息，混合用途的验证文章又可能整体受调研分类影响。下一步应补全正常材料说明并比较实际命中，再决定段落级用途与回答性判断如何进入召回；不能把问题集或某个文件名写进通用排序。当前真实答案、同库对照、失败及模型知识刷新见[补读与定位报告](../../.repo-review/knowledge/verification/assistant-reading.md)。

## 上一轮：快模型选择与快照准备

这轮尝试把日常回答交给 Traex ACP 的 `gpt-5.6-luna`，材料、中文搜索、代码导航、历史和记忆仍由 omem 提供。模型可以选择线索、继续读原文、修正答案，再提交带固定引用的结果。它与 Sol 使用同一套原生调查环境，没有额外的宿主 token 上限或固定调查轮数。

目标是让人更快拿到有用答案。换模型本身不等于完成优化：本轮基线中，同一个记忆更新问题，Luna 用了 136 秒、Sol 用了 148 秒；其中仅准备材料就约 37 秒。Luna 还因错误填写历史引用版本修正了两次。回答是否正确、是否遗漏条件、是否真的能指导使用，需要逐条读；工具调用成功不能替代这个判断。

## 现在如何选择

`config/omem.example.json` 保留 `traex`（Sol）与 `traex-fast`（Luna）两个 ACP profile。在个人配置 `omem.local.json` 中设 `"assistant": {"profileId": "traex-fast"}` 后重启，即用于网页与日常助手问答。已有配置不写 `assistant` 时继续使用首个 ACP profile。没有该 profile 或选到非 ACP transport 会明确报错，不悄悄退回另一模型。

问答选择独立于知识写作、材料整理与后台学习：它们仍使用各自既有配置；仓库文章生成仍由 `config/review-code-model.json` 的 Sol 执行。没有自动把复杂问题转交 Sol，也没有暗中同时调用两个模型。实际模型与推理强度由 ACP 发现、校验并回读，不依赖 UI 名称猜测。

## 本轮对代码的改造

| 问题 | 改造与位置 | 保留的限制 |
| --- | --- | --- |
| 想试快模型却同时改变写作模型 | `config.ts` 增加 `assistant.profileId`；`app.ts` 分开选择问答与知识配置 | profile 仍需配置可用的 ACP CLI |
| 原始检索结果缺用途与适用时间 | `assistant/runtime.ts` 把固定版本的材料说明传给 Agent，派生讲解也保留说明；`assistant/research.ts` 在最终引用中保留同版本说明 | 说明是派生标注，可能缺失或判断错误；不是事实证明 |
| 模型为定位初始结果再次翻全库目录 | 原文结果带 `materialKey`、路径、固定行范围；目录可按需搜索，不再要求先读完整 catalog | 仍需根据问题补查，不能把初始命中当成答案 |
| 同一库每次提问重新解析 AST、切词建索引 | `research-snapshot.ts` 复用授权范围内完整来源的索引和 FTS；再由原有投影逻辑检查版本、说明和索引身份，过期的重建 | 不是复制整个私人数据库；讲解与状态仍按快照可见依赖生成；快照准备仍有成本 |
| 每次读取一个原件版本都扫描全部片段 | 迁移 21 增加 `fragments(revision_id, ordinal)` 索引，服务原文读取、历史展开和调查快照 | 不改变材料或向量身份；首次启动会建索引 |
| 很难判断时间花在哪 | `acp-model.ts` 留下材料准备、Agent 调查和总时间；比较脚本另计初始检索 | Agent 时间含启动、工具和提交，不等于纯模型推理时间；不是首字延迟 |

这轮没有调融合权重，也没有默认开启中文重排。底层候选中的无关内容仍存在；Agent 通过检索改写和补读找到答案，说明调查能力有用，不能据此宣称原始排序已经准确。

## 如何复现比较

准备 JSON 问题文件，例如 `[{"id":"policy","turns":["目前的费用约定是什么？","旧版本有什么不同？"]}]`。题目只交给评估脚本，不能作为材料导入后再宣称新题命中。

```bash
osdk run assistant:compare --questions /absolute/path/questions.json --review
```

`--models` 默认 `gpt-5.6-sol`，`--effort` 默认 `medium`；可用 `--data` 指定输入数据目录，`--output` 指定一个新的结果目录。不带 `--review` 时使用个人材料适配器。运行会真实消耗模型调用；先对输入数据库做一致副本，模型只能在副本的授权材料中调查，不修改个人材料。报告默认在被 Git 忽略的 runtime 中，包含完整答案、原文引用、工具活动和耗时；含私人材料的报告不要提交。

每题为两个模型各开独立会话；同题的后续问题沿用各自历史。题间交替模型执行顺序，复用同一中文 embedding，不启用重排。报告记录固定原件和知识版本摘要并检查未变化，模型服务负载仍不可控制。题量小、有些问法此前已出现在库中，不能给出普遍准确率或可靠速度倍数。

人工比较应先读这四件事：是否直接回答；关键条件是否正确；需要使用或修改时是否给出真正入口；没有功能或信息时是否承认缺口。其次再看篇幅、冗余、引用是否帮助阅读、失败次数和耗时。最终实测与失败保留在[本轮报告](../../.repo-review/knowledge/verification/fast-assistant.md)。
