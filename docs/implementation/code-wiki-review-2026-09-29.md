## 可提交的 Wiki 与本地缓存

- `.repo-review/wiki.md`：本仓库的可读目录与已有模块说明，直接在 Git 中阅读。
- `.repo-review/knowledge/generated/*.json`：真实模型产物、原始生成时间/模型/input digest、依赖文件 hash，以及 path + qualifiedName + kind 引用定位信息。来源变化后过期，错误 locator 拒绝；恢复不是再次模型调用，也不是语义验证。
- `.repo-review/knowledge/understandings/*.seed.json`：既有人工说明。仍是 seed，不改造成模型成果。
- `.repo-review/runtime/`：可重建 SQLite、索引、临时模型工作目录、构建暂存。启动只写这里；明确执行 build/generate 才发布可提交的知识资产。
- `.repo-review/data/` 和根级历史同步文件：保留的冻结旧资产。它们不是当前 Wiki 的更新入口；新机器不必依赖其最新状态，代码与 committed 知识可以重建当前视图。

“跟代码提交走”不等于提交会不断变化的 SQLite WAL。源码、人工关系及派生 Wiki 共同进入 Git，本地索引用它们重建。首启需要本地索引构建，但不需要手动点击同步或重新调用模型。默认启动不自动消耗模型调用。

## 仍然存在的架构边界

1. 当前接入范围是本仓库与单用户 SQLite。代码源枚举和关系仍有 review 适配逻辑、默认仓库标识仍为 omem；不能把这次改造说成任意多仓库/多租户均已接入。
2. 个人助手的自动材料学习与 CodeUnderstanding 角色运行尚未完全统一编排。代码角色有单独的严格输出合同及 registry，复用 ACP 传输；尚未统一进入所有输入渠道的持久任务/复核流水线。后续应接统一材料处理端口，不能再增加第二套 Capture 或 memory authority。
3. 模型说明是派生资料，结构与引用存在性校验不证明每句解释正确。此次没有独立 verifier 语义复核，也没有把说明作为已验证记忆自动应用。
4. imports 是解析器关系；跨文件 calls、类型解析、跨 revision 语义身份续接仍未实现。名称级调用只作候选；评审意图边继续仅来自 associations.json。
5. 检索仍是关键词检索；下游 refresh_dependents 自动重核验仍未完成。没有将这些限制改写成“已通过完整验收”。

## 预算调整

用户明确允许较高预算后，将本机示例设为 96000 输入 tokens、24000 输出 tokens、16000 Agent 上下文预留，模型为已发现的 GPT-5.6-Sol（272000 tokens 窗口）。这是本地估算预算，非精确 tokenizer 计量；估计输入/输出均计入 25% 余量，未知模型窗口不捏造数值。此前 MemoryService 因 80000 字符门失败的记录保留，新的结果另记，不覆盖失败历史。已有五份模型说明的依赖摘要通过原生成快照逐项核对后细化到实际提供的规则片段，保留原模型输出、时间与 input digest，避免未提供给模型的文件其他部分变更造成重复调用。

记忆治理模块最终成功：110183 字符 / 111585 UTF-8 字节，估算 37195 tokens，计入余量为 46494；扩大输出预算后按完整材料生成，没有截断源代码。
