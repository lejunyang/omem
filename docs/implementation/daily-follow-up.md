# 日常消息与事项跟进

当前可用的主线是：本人交办 → 保存指令原文 → 模型提出结构化任务操作 → MemoryService 检查并应用 → 真实回执回复 → 约定时间站内提醒 → 本人完成、取消或稍后。

`assistant/message-workflows.ts` 定义随手交办、讨论归并、等待跟进、事项回顾四类模板，进入 AcpAssistantModel 的真实提示词。它们不另建 Agent 框架；后台 LearningPipeline 的 extractor/verifier 仍使用统一原始材料和归属规则。模板不会授予捕获内容写权限。

事项状态为 open / waiting / done / cancelled。`follow_up` 单独保存等待对象、下次检查、暂缓截止、原始时间表达与 IANA 时区；不占用业务截止时间 `due_at`。数据和历次版本在 schema 18 中迁移保存。数据库应用层统一转换时间为 UTC，界面和助手按用户时区显示。

- “等张三回复，明天上午9点提醒我检查”：等待对象来自当前本人指令，下次跟进为明确时间，截止时间仍可为空。
- “后天上午10点再提醒”：保留等待对象和业务截止时间，暂缓期间不提醒，到指定时间重新检查。
- “取消”或“完成”：清除跟进安排并停止后续提醒；原件和历史版本仍保留。
- “回顾进展”：读取当前事项和原文，不修改状态，不把通知已读或他人的承诺当作完成。

`POST /api/tasks/:id/commands` 与助手结构化调用复用 MemoryService 的版本、证据和应用回执。网页操作作为可读的本人操作原件保存，不把内部 JSON/ID 渲染成通知。Web 对话可以携带 requestId，网络重试复用同一个 transport event。

调度复用 Store.remind 的现有30秒轮询。事务内检查当前状态和暂缓时间，写通知与 `task_reminder_receipts`；按事项版本、类型和发生时间去重。同时到期的截止与检查合为一次通知，后续独立截止仍会提醒。重启后迟到发生补发一次，不周期性刷屏。

真实验证：`osdk run live-daily` 使用 config/review-code-model.json 的 traex ACP / gpt-5.6-sol，隔离临时数据库和合成消息，验证等待创建、稍后、重开数据库后一次补发、回顾不修改、取消停止。报告在忽略提交的 `.omem/verification/live-daily.json`。测试使用注入模型，浏览器使用协议 fixture；它们不冒充真实模型或外部飞书验收。

尚未实现：自动监听对方回复、自动认定完成、重复安排、会前准备、定期回顾和外部到期投递。当前站内提醒不主动联系等待对象。新的网页入口与控件另行提交。
