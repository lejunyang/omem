# 通用知识整理流程

本轮按功能切片实现。仓库是输入适配器；正文、引用、疑问、角色运行和任务记录供各类 Capture 材料共用。

## 已完成：正文与固定引用合同

`KnowledgeDocument` 用具名章节组织 Markdown 正文，`[[c1]]` 引用贴在对应文字旁。引用有可读名称、理由、关系和材料行范围或知识章节目标。模型选择位置，宿主从固定版本复制引文；语义支持性另由独立角色复核，位置存在不能替代语义复核。

`KnowledgeRepository` 保存不可变知识修订和当前指针。原始材料仍来自 Capture / Source / Revision / Fragment，派生知识不会再次作为独立原件采集。来源变化会使对应知识及依赖它的章节过期，旧引用仍可读取原始固定版本。JSON 和 Markdown 可作为可移植产物保存和重建。

疑问可保留为后续调查项；用户明确选择后才加入现有待办。用户回答被保存为带来源的原始材料，不改写原证据。

验证：`knowledge-repository.test.ts` 3 个行为用例通过，覆盖内联引用/范围校验、来源变更后的级联失效与历史保留、全新库恢复、问题回答和待办幂等。角色编排、仓库接入和阅读界面在后续独立提交中交付。

## 已完成：共用 Agent 运行时

材料、代码、对话、图像分析，以及章节规划、写作、复核和刷新这八个角色都使用既有 `RoleRuntimeGateway`、版本化 manifest/prompt/schema 和内嵌 skill。没有新增另一套模型进程或任务存储。宿主可以规范化引用后再交给独立复核角色，角色的原始范围和运行 trace 保留。

持久 worker 增加按 kind/job id 领取的过滤条件，知识整理不会抢走学习或通知任务。预算使用共用实现；正式 review 配置为 192000 输入 / 24000 输出 / 16000 预留 tokens，仍需通过当前模型声明窗口校验。角色默认预算是 96000 / 24000，配置覆盖会进入运行记录。

验证：jobs 与 role-runtime 两组 17 个用例通过，包含任务隔离、技能实际载入、知识输出合同和宿主绑定引用。八个 skill 均经过结构校验。具体仓库分析与页面功能在后续提交中接入。

## 已完成：通用分析、复核与服务接口

`KnowledgePipeline` 先运行材料角色，再使用独立会话复核。只有通过的正文才发布；同批已通过内容可以先保存，未通过内容继续修订。模型选择引用行范围，宿主复制精确短引文，复核角色判断其是否支持正文。持久任务和角色输出支持重建投影后复用，分析期间来源变化会拒绝当前发布。

个人服务已提供 `/api/knowledge`：正文、固定引用、原始材料、搜索、问题、回答和显式待办动作。它直接处理手工材料等通用 Capture 输入。回答保留为原始材料，并使对应知识进入重核对；下一轮处理会把回答提供给 Agent。代码关系只作为材料类型适配，不构成新的事实或记忆 authority。

验证：知识仓储、流程和 API 三组 6 个用例通过；主服务与 review dev 接入回归 15 个用例通过。协议 fixture 仅证明流程，真实模型全仓处理的覆盖与失败另行记录。

## 已完成：仓库材料适配与可提交产物

`review:analyze` 使用统一流程处理全部 Git 可见材料（含源码、文档、部署配置、技能和图像），记录明确的排除/失败原因。运行数据、旧历史库、私有环境与派生知识不重新作为独立证据。每份通过独立复核的正文立即保存为 JSON + 带内联链接的 Markdown；后续按模块、主题和概览逐层组合，仍保留固定引用。

`review:generate -- --target=<path>` 是同一流程的局部入口；`review:build` 只重建当前知识索引，不重新调用模型。启动与手动同步均接入材料和知识恢复。review 中用户明确保存的回答写为原始 user-notes 材料，可在新机器恢复后继续被引用；旧 data 仍不是启动依赖。

验证：仓库材料、知识恢复与 dev 生命周期 10 个用例通过，覆盖普通文件、部署配置、图片、私有配置排除、幂等捕获和无旧数据库的用户回答恢复。全仓模型处理的完成数以 coverage.json 为准，失败条目不冒充已生成。

## 已修正：仍在使用旧预算的历史角色

extractor/verifier/planner/feedback-curator 与早期四个代码角色的实际 manifest 预算也已统一到 96000 输入 / 24000 输出，避免只有新角色或 example 文件生效。review 的正式配置仍可覆盖到 192000 输入。更严格的 token 估算曾使旧批量提案 fixture 触到旧输出预算，已通过实际角色预算修正；输出洪泛测试仍验证硬性拒绝。

验证：learning-pipeline、role-runtime、code-understanding 共 31 用例通过。

## 已完成：正文内联引用阅读

个人“知识整理”和仓库“仓库知识”使用同一组阅读组件；代码结构视图作为补充入口。正文中的引用带可读名称，打开后先展示引用理由，再进入固定知识章节或原始材料；代码 import 行旁也能进入目标模块知识。帧栈行为已集中到 `packages/ui/useEvidenceTrail`，知识、材料与旧代码视图使用同一 dialog 合同，支持逐层返回、循环跳回、滚动与焦点恢复以及深链。

验证：完整 `osdk run check` 通过；`knowledge-browser.ts` 用真实 Vue/API/SQLite 验证正文→章节→三个模块→固定代码的五层链、理由、import 跳转、Esc、深链、焦点、1440/768/390 和显式待办；规定的 `dev:review` + `code-wiki-viewport.ts`（本仓库材料镜像）及个人 `osdk run browser` 均通过。fixture 知识与真实模型产物在验证记录中保持区分。

## 已修正：个人学习与知识整理并存

个人学习 worker 同样限定只领取 extract_claims / verify_proposals / refresh_dependents，避免它把知识角色任务误判为未知任务。两种流程共用一张持久任务表，互不抢占。验证：学习与知识流程 8 用例通过。

## 已完成：知识引导个人助手召回

关键词检索可以命中已整理的正文，再沿固定引用找到原始 Fragment 作为候选。派生正文只用于导航，不作为新的独立证据送入助手；原有会话可见性过滤继续生效。召回时重新核对当前材料摘要，即使知识投影尚未刷新，也不会将旧来源当成当前依据。

验证：知识仓储/召回与 AssistantRuntime 28 用例通过，含“原文无关键词、知识正文有关键词”的真实原片段召回及来源变化后拒绝旧依据。

## 已完善：语义退回后的定向修订

独立复核退回后切换到专门的 knowledge-refresher，依据具体反馈局部修改，不再让初始分析角色反复重写整篇。有限轮次的最后一步要求只保留直接有依据的陈述，把剩余问题明确记录；仍必须重新通过独立复核，不绕过拒绝结果。输入材料的真实来源类型与转述状态进入上下文。

验证：知识流程与角色运行时 11 用例通过，包括持续拒绝时不发布的反例。

## 已修正：输入载体身份

只有仓库文件可使用简写 omem:path；其他载体始终保留 namespace，即使用户给出相同 externalId，也不会把手工材料与仓库文件合并。验证：知识与关键词检索用例通过。

## 已完善：疑问随知识演进

新正文不再提出的开放调查项标为 superseded，已回答或已由用户加入待办的记录保留。新知识修订形成应用内通知，幂等恢复不重复通知。重新导入用户补充后，若当前正文尚未使用该回答，仍保持待重核对。相关生命周期回归通过。

知识读取会核对当前来源；历史图片按固定 revision 中的 asset 引用读取，不因来源 head 已变化而丢失。知识 API 的历史图片回归通过。

非 Markdown 文件统一按原始文本/代码展示，包括 HTML 原型、部署样例和配置，避免被当作网页渲染而丢失内容。真实浏览器验证 HTML 代码可见且未执行，原有五层引用链、import 跳转、视口和待办流程仍通过。

## 已完善：专用 skill 职责

规划和复核 skill 已拆除不适用的通用正文写作要求。复核明确依据完整固定范围判断，宿主短引文只是预览；错误、遗漏重要条件仍会拒绝，不以措辞偏好反复重写。真实 GPT-5.6 小样本校准：原文导出 42，草稿写 42 时 accepted，草稿写 43 时 needs_revision；这只是角色校准，不替代全仓验收。
