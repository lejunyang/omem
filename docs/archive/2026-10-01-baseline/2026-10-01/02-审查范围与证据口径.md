# 二、审查范围与证据口径

## 2.1 本次事实与未验证边界

本次核对了仓库说明/决策/状态、evidence-model 和 assistant-v3 策略、通用 knowledge 管线与相关角色、存储和迁移、助手 runtime、检索、输入、MemoryService、学习/通知与飞书路径、AST/Code Wiki 与共享阅读组件，以及既有研究材料。重点是生产装配与跨模块关键路径的深入审查，不宣称逐行形式化验证了整个仓库。重要结论以基线代码为准，固定commit链接与本轮验证范围见本文证据附录。

明确四种标签：

- **实码事实**：在当前基线实际存在的合同、分支、调用路径与SQL
- **本轮行为验证**：针对性离线临时数据库/纯函数复现，注明命令、输入与结果；不代表完整产品验收
- **文档历史**：过去的测试、模型调用、浏览器或飞书live记录，不能当本次新验证
- **推断/建议**：据代码路径判断的风险或拟议设计，不写成已发生事故/现有能力

本次没有修改产品源码，没有部署、推送或扩大采集权限，没有调用真实模型批量重生成，也没有重新完成真实飞书网络收发/图片下载/服务重启/完整浏览器与全量check。旧的测试通过数、旧主助手失败记录和不同机器的ACP能力不能混为一个“生产已验证”的状态。

## 2.2 应保留的底座

1. Source→Revision→Fragment 与固定版本原件：已经提供可追溯基础
2. Capture 与派生知识分离：`producerKind=derived` 不应再次作为独立学习证据
3. 统一 RoleRuntimeGateway、版本化 prompt/schema/skill、任务租约和输出 trace：不再另造 code-only 模型进程
4. KnowledgePipeline 的分析→宿主绑定原文→独立会话复核→定向修订→发布：这个方向正确，应细化评测和主张级证据
5. MemoryService 的提案/评估/治理/原子应用及 application_receipts、outbox：继续扩展，不旁路写表
6. 原件更新后的显式失效、保留历史版本，以及模型不可用时保留 pending：安全降级比假完成好
7. PersonalKnowledge/CodeWiki已共用 EvidenceTrail 的逐层返回、循环跳回、滚动/焦点恢复；旧EvidenceReader仍有独立frames，需要兼容迁移其局部追问/草稿能力，不再造第三套阅读器
8. 明确 personal-first/shared-token 的现实边界：保留团队扩展点，不把当前运行当多租户产品

## 2.3 关键现状与缺口

以下实码依据包括[当前依赖](https://github.com/lejunyang/omem/blob/94aafe934c6734aab346c6d73cf51dcec0c78d26/package.json#L1-L48)、[检索实现](https://github.com/lejunyang/omem/blob/94aafe934c6734aab346c6d73cf51dcec0c78d26/apps/server/src/retrieval/keyword.ts#L15-L171)、[主助手实际工具合同](https://github.com/lejunyang/omem/blob/94aafe934c6734aab346c6d73cf51dcec0c78d26/apps/server/src/assistant/runtime.ts#L21-L77)和[知识写作/独立复核](https://github.com/lejunyang/omem/blob/94aafe934c6734aab346c6d73cf51dcec0c78d26/apps/server/src/knowledge/pipeline.ts#L96-L143)；完整索引在附录。

| 领域 | 当前可确认事实 | 对用户目标的缺口 |
|---|---|---|
| 技术栈 | TS/Fastify/node:sqlite/Vue；通用运行时支持配置的CLI/ACP，当前主助手AcpAssistantModel只接受ACP并拒绝CLI transport | Python/React/PG是历史方向，不能反推当前实现 |
| 原件与切片 | 固定revision、空行文本切片、图片资产与provenance | 结构化表格/消息/代码/图像区域的统一selector仍不足；跨revision身份续接缺失 |
| 检索 | LIKE+中文2gram，来源head，知识正文可导航至原片段 | 没有embedding/重排；时间参数未实际执行；统一权限/时态/项目检索不足；存在引用跨片段召回缺口 |
| AST | TS单文件AST+Vue SFC，imports等确定性结构，calls保守candidate | 调用归属有复现问题；没有完整Program/跨文件符号解析；不应将calls当可靠事实 |
| 知识正文 | 共用分析/独立verifier/修订/固定引用/依赖失效 | 文章级通过不等于每项主张有独立支持；复核模型共享盲点；自动源变化触发与恢复需完善 |
| 长期记忆 | claim/episode/procedure、证据评估、冲突/等价、AttentionGate | refresh_dependents明确NOT_IMPLEMENTED；助手主问答未完整利用长期memory召回 |
| 日常交办 | owner意图门控、create_task、幂等receipt | 主助手工具不具备日期、更新、完成、取消、提醒调度的完整闭环 |
| 通知 | outbox、重试、合并和定时汇总已有基础 | “通知何时投递”不等于“任务到期触发提醒”；真实网络故障恢复仍需验收 |
| 图片 | 保存图片、visual-analyst、知识页面图像入口 | 输入生产媒体下载/所有路径多模态保真需实测；图像语义检索/OCR区域锚点尚缺 |
| 学习 | 当前learning主要是提取事实/经验的流水线 | 不是面向用户英语学习的课程/卡片/复习系统 |
| 评测 | 六维指标/空分母null/规则baseline | 规则支持判断不等于语义正确率；未建立足够真实中文跨材料holdout |

细节不能被“已有八种/多种角色”概括掉。角色文件存在只证明能力声明；真正闭环还需生产装配、触发、持久状态、失败恢复、权限及用户可验收结果。
