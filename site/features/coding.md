# 编码

在飞书或网页里说一句“在 shop 仓库实现……”，omem 把它交给编码 Agent，在独立的工作分支里改，跑检查，再交给几个评审项从不同角度审。需求和评审问题都拆成一个个修改项，逐项改、逐项验证，改坏了自动回退重做；只有业务上的取舍才问你，问的时候别的项照做。你看结果、回答问题、确认推送。

## 在常驻机器上编码

omem 可以跑在一台常驻的机器（服务器、家里的台式机）上，编码就在那里进行，你的笔记本可以合上：

- **从哪都能交办**：飞书里发一句，或网页上点“交办”，或 `omem delegate`。前端和后端一起改也是一次交办，每个仓库一条工作分支。
- **飞书里看进度**：每次交办一张卡片，持续更新当前在做什么、每轮评审的摘要；评审结束带着按钮决定改哪些。
- **浏览器里看代码**：运行页“在 VS Code 中打开”选“网页版 VS Code”，新标签页里就是那台机器上的工作区，带终端，omem 插件已经装好；不用本地装 VS Code，也不用配 SSH。见 [VS Code](./ide)。
- **不用每次装依赖**：omem 在数据目录里按需建工作区，每个仓库最多 4 个轮流借用，`node_modules` 一直留着；准备命令只在锁文件变了时才跑。
- **机器之间**：从另一台电脑用 `omem peer open` 打开那台机器的网页，交办、评审、网页版 VS Code 都能用，经中间机器转发也行。见 [多台设备](./devices)。

## 一次交办怎么走

1. **先查影响面**：新交办开始编码前，另一个 Agent 只读地查一遍：改动会碰到哪些现有功能、调用方和共用的接口，这些文件以前出过什么问题（omem 记下的需求点、交办、评审问题和仓库提交），改完要回归什么（有测试的写命令，没有的写人工步骤）。结果在交办视图“概览”里，编码 Agent 和评审都拿到它。改个文案这类小事助手会跳过；不想要可以在设置 → Agent → 自动推进里关掉。
2. **拆成修改项**：编码 Agent 先把需求拆成几项（T1、T2…），把上一步查出的要顾及的点写进完成标准，估一下要推进几轮；你交办时说了“最多推进 3 轮”就按你的。
3. **逐项编码**：一项做完提交一次，提交里写明是哪一项，所以每一项都能单独看、单独回退。项多而且有几组互不相干时，编码 Agent 把它们分给编码助手同时做，这一轮结束时合进工作分支，改到同一处的冲突由它解决。做完的项在它接着做别的项时就被验证，没改好的在同一轮里交回给它。
4. **评审看什么由 AI 定**：待做的项做完后，评审负责人看这段改的是什么（业务逻辑、接口、样式、测试、搬动的资源……），决定这次让功能、业务、架构、历史、规范、精简里哪几个评审项看、各看什么，只看上次评审以后的改动；你交办时说“完整评审”“加上安全评审”它照做。
5. **问题变成修改项**：先看问题和需求、和代码现在实际怎么被用有没有关系。有关系、说得清、好改好回退的直接改；业务或功能上的取舍（需求没说清、几种做法都说得通、改动大）放进“等你决定”；问题成立但现在的用法碰不到的（假想的并发、极少见的时序、需求没要求的加固）记成“以后再做”，不挡这次交付，同一分支下次交办时接上。同一处修了几层还在报问题时，交给助手判断还值不值得改。之后的评审又提到已有的修改项（比如还在等你决定的那项）时并到那一项，不会多出一个重复的项；评审结论里每条问题都标着它对应的 T 编号。
6. **谁提的谁验证**：修好的项交回提出问题的评审项，它接着自己的会话看；没改好就再改，改出了新问题就先回退再重做。编码 Agent 拿不准时可以直接问它（它记得当初为什么提），认为问题不成立时把理由交回给它，它可以撤回；它坚持、编码 Agent 仍不同意时，由评审负责人裁决，裁决后还有分歧才问你。
7. **停下的时候**：做完了等你确认推送；轮数用完、修改不收敛、你点了暂停时停下来说明；“等你决定”的项不挡别的，你回答后马上接着做。编码 Agent 和评审负责人拿不准、想问你的事先交给发起交办的助手：需求或你之前说过的话已经定了的，助手直接定；评审提的改动超出需求或只是偏好的，助手驳回或记成以后再做；需求要求了却没人做的，助手补成新的修改项。这些在汇报时各交代一句。助手定不了的才问你，问了就等你回答，不会在你回答之前替你处理掉；同一处助手放下两次、评审还在提的，也直接问你。需求本身做完、改完第一次评审的问题后评审还在提问题时，收到一张“需求做完了”卡片：可以先把评审过的版本推上去实际试，评审的问题接着改，或者把剩下的记成以后再做；不回复就照常改。需求做完之后评审还一轮轮提问题（连着三次），交办停下，助手对照你原来要的说明能用什么、建议先交付还是再改几项。
8. **推送后接着改**：对助手说“先推上去我试试”，只推送、交办不结束，试出的问题接着在同一次交办里改；已经确认的交办，在同一分支上再交办时，上一次没做完和记成以后再做的项会自动接上。

编码 Agent 被挡住（权限、环境、缺别的团队给的字段）、一项修了三次仍没通过、几轮都没轮到时，这一项显示“等助手处理”，不算你要决定的事：发起交办的助手马上被叫醒去查、写明怎么重做，或记成在等外部，交办的其他项照常推进；它只把业务上的取舍带着选项交给你。已有需求或授权已确定的事可以在后台恢复，不用重复点确认。确需你决定时，飞书卡片先显示问题和按钮，完整评审与修复记录默认折叠。

旧的按轮方式（档位、计划确认、每轮选改哪些）还在：设置里关掉 `agents.autoAdvance.taskLoop` 即可。详见 [交办与评审](./review)。

## 在哪看

运行页顶部切到“编码”：每次交办和分支评审一行，按等谁分组（等你、进行中、助手在处理、搁着、已结束），写着进度（需求做了几项、评审修改几项、几轮）、仓库和分支、所属的事项和需求；停了两天没人动的放进“搁着”。点开是这次交办：

- **现在**：在做什么、做到哪；**下一步**：要你做的事和按钮（确认并推送、重试这一轮、丢弃、改用这台机器的 AI……）；**分支**：每个仓库从哪个分支的哪个提交切出、工作分支有几个提交、origin 上是什么状态、确认后推到哪。
- 下面的“概览 / 需求点 / 变更 / 评审 / 活动 / 分支”编码中也都能看；各轮在“活动”里，点一轮看它的过程。
- 需求页里点需求点下的“编码”，打开的是同一个视图；“全部运行”只列问答、整理这些别的运行。
- 页头的“预览”在这次交办的工作区里起服务，在你的电脑上按原端口号打开页面看效果（设置和用法见“VS Code”页的“预览”一节）。
- **产物**：编码 Agent 和检查命令留下的截图、录屏、测试报告和日志，按修改项分组；图片、视频、报告都在页面里打开（报告在沙箱里，读不到 omem）。修改项展开后“看截图和报告”只看那一项。要让交办留下这些，在仓库的测试脚本或技能里把文件写到环境变量 `OMEM_ARTIFACTS` 指的目录：放在 `T<编号>/` 下就归到那一项，其他子目录（如 `改前/`、`改后/`）是分组，带 index.html 的目录算一份报告。评审和逐项验证也会看到这些文件。

## 中途插手

- 运行页“修改项”：加一项、暂停 / 继续、把某项重做、改成不做、回退或回退并重做；“看改动”可以只看某一项、全部、“我上次看过之后”，或“和分支比较…”（整条分支和上线分支比，合进去之前整体看一遍，选中代码提问或要改）；在“检查点”里回到某一步，看改动时把一个文件恢复成改动前，或只回退其中一段。VS Code 侧栏有同样的“修改项”视图。
- 自己在工作区里改了代码也没关系：下一轮开始前记成你的检查点，不算进任何一项，编码 Agent 会保留它。
- 编码时补要求：运行页“补充给编码 Agent”，或对助手说，编码 Agent 这一轮就收到；不在编码时说的话变成一个修改项。
- “后面评审从简”“别再拆需求”从还没开始评审的那一轮生效。
- 在差异、评审里选中几段文字，编号后一起提问，或攒成下一轮的修改点（见 [引用与修改点](./quotes)）。
- “停止”停下这一轮，工作区保留。

## 其他用法

- **评审同事的分支**：“帮我评审 shop-api 的 feature/refund”，只出意见不改代码；要改时选好问题点“开始修改”。
- **同步分支**：“把 main 合并到 feature/refund，冲突你先解决”，可以只同步不编码（见 [工作分支与同步](./git)）。
- **按分支问代码**：“feature/refund 上退款金额怎么算的？”
- **读懂陌生仓库**：建代码仓库空间，生成 [Wiki](./wiki)，或直接问。
