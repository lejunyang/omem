# 编码：常驻机器交办与多维评审

在飞书或网页里说一句**“在 shop 仓库实现……”**（或“前端和订单服务一起改……”），omem 就会把任务交给常驻机器上的编码 Agent：在独立的 Git 工作分支里先查影响面、按需出方案、拆成修改项（`T1`、`T2`…）逐项提交并跑测试，再交给**六个维度的独立评审角色**交叉把关。

**你的笔记本电脑可以合上**：在飞书卡片上看实时进度、回答业务取舍问题；改好并验证通过后，点一下**“确认并推送”**即可交付。

## 1. 和普通 AI 写代码工具哪里不一样？

| 维度 | 传统 IDE 编程助手 | omem 云端交办编码 |
| --- | --- | --- |
| **运行在哪、占不占电脑** | 跑在你本地编辑器里，改代码时你没法切分支干别的，合上电脑就断 | **跑在常驻机器的独立工作区池里**（自动保留 `node_modules` 免重装依赖），不碰你正在开发的目录；一次可跨前后端多个仓库同时改 |
| **怎么写、怎么防改乱** | 往往把所有改动混在一起改，改坏了很难局部回退 | **先查影响面 → 大改动先确认方案 → 拆成修改项（T1、T2…）逐项提交**。每一项有独立 commit，可单独看 diff、单独回退或先推送已改好的部分去测试 |
| **谁来审、怎么收敛** | 写代码的模型自己说“改好了”，或者需要你逐行人工看全量 diff | **六维独立评审 + 谁提问题谁验收**：功能、业务、架构、历史、规范、精简六个角色（默认尽量换不同家族的模型）按改动按需介入；问题转成修改项自动修，改坏自动回退；无关紧要的边界问题记为“以后再做”，不让交办在细枝末节里死循环 |
| **怎么看代码、怎么验页面** | 必须拉到本地跑 | 浏览器一键打开**网页版 VS Code**（评审问题直接挂在代码行上），点**“预览”**自动起服务并把端口按原号转发到你电脑上；测试留下的截图、录屏和 HTML 报告直接附在修改项下 |

## 2. 一次编码交办的完整闭环（8 步自动推进）

当你发起一次交办（通过问答、左侧 **编码 → 交办** 按钮，或 `omem delegate`），系统按修改项循环自动推进：

1. **先查影响面（`pre-check`）**：正式写代码前，先由另一个 Agent 只读排查：这次改动会碰到哪些现有功能与共用接口、这些文件以前出过什么历史缺陷（查库内需求点、以往交办与 Git 历史）、有哪些**现成实现可以直接复用**，并列出回归测试清单。（改文案等极小改动自动跳过）。
2. **大改动先出结构化方案（可选）**：当改动涉及接口或分工调整、有多种可选做法时，先生成一份包含若干**决定（新增 / 修改 / 删除 / 重构）**的方案卡片等你点头（详见下文“方案与变更说明”）。
3. **拆成修改项（`T1`、`T2`…）**：编码 Agent 将需求拆解为独立的修改项，把第 1 步查出的注意事项写入各修改项的完成标准。
4. **逐项编码、并行提速与边写边验**：每做完一项单独提交一次（多组互不重叠的修改项还会自动分给多个编码助手并行开发，轮末自动合并）。做完的项在它继续写下一项时就已经由评审项同步开始验证，没过关的在同一轮内立刻交回重修。
5. **评审负责人（`review-lead`）按改动动态点将**：待做项完成后，评审负责人根据实际改动性质（业务逻辑、接口、样式、测试），从**功能、业务、架构、历史、规范、精简**（以及你挂载的安全等专项评审）中挑出本轮需要出场的评审项（改满 40 行源码时“精简”必出场，专门检查哪些代码能删、能合并、能改用第 1 步找到的已有实现）。
6. **评审问题分级分流，绝不死循环**：
   - **和需求及实际用法直接相关、好改好回退的** → 直接转成新修改项自动修；
   - **业务或功能上的真取舍** → 先交给发起交办的主助手对照需求和你说过的话拍板，主助手定不了的才放进**“等你决定”**卡片问你（问你的时候其他修改项照常往前走，不干等）；
   - **假想的极端并发、当前用法根本碰不到的加固建议** → 记为**“以后再做”**，不阻塞本次交付（下次在同一分支交办时会自动接上）；
   - **同一位置连续修到第 3 次仍未过** → 负责人直接调出完整修改链，优先采用精简或架构提出的“换结构”方案，或升级请你拍板。
7. **谁提的问题谁验收，分歧由负责人裁决**：修好的项交回原提出问题的评审项复核，改出新毛病自动回退重做；若编码 Agent 认为问题不成立可附上理由申诉，双方僵持时由评审负责人裁决。
8. **分段推送或一键确认交付**：你可以中途对助手说“先把 T2 推上去我验”，也可以在需求主体做完时先推送评审过的版本去试，剩下的小问题继续在同一次交办里改；全部满意后点**“确认并推送”**，代码自动推上远端同名分支并归还工作区。

## 3. 技术方案（Designs）：写自己的方案、跟进并评审同事的方案

在左侧 **编码 → 方案** 标签页（以及交办视图或事项页的“方案”栏），omem 把技术方案拆解为一个个结构化的**决定（Decisions）**：

<Shot src="design-own" caption="自己的技术方案等你确认：每个决定按新增 / 修改 / 删除清晰列出行为对照表，待你拍板的问题（如 D2）直接在卡上点选" />

<Shot src="design-external" caption="跟进同事的技术方案并对照评审分支：自动核对代码指出方案漏洞，分支出来后把代码改动归到每个决定下，直观显示偏差与方案外改动" />

- **交办前先确认自己的方案**：在 **设置 → 推进工作 → 方案先行** 中可设为“自动”（由编码前检查判断）、“总是”或“从不”。每个决定按类型写清要点（如“修改”必写**改前 vs 改后行为对照表、影响面与数据过渡**；“删除”必写**删什么、谁还在用**）。你在飞书卡片或网页上选好待定问题并点**“通过”**（也可“提意见”让它改出下一版，或“换个思路”重写）后，编码 Agent 严格照方案执行，每个修改项和改动文件都挂在对应决定下；没走方案的普通交办结束时也会自动生成一份简短的**变更说明**。
- **替你核对同事写的技术方案**：把同事写的方案文档发给助手说“跟进一下这个方案”。助手会提取作者的每个决定，**回到真实代码库里逐一核对事实**，列出**问题（照着做会出错）、风险、改进建议和要问作者的问题**，并标出哪些关键决定“文档没写，是推断出来的”。文档更新后点“重新评估”，会自动标出上一版每条意见的最新状态。
- **对照方案评审同事的代码分支**：当同事把分支写出来后，对助手说“评审一下 `<分支>`，对照小王的方案”。系统会把分支里所有改动的文件自动归入方案的各个决定下，逐个决定展示**“方案怎么写的 vs 代码怎么做的、有没有漏做或偏差”**，并把归不到任何决定的改动单独拎出来列为**“方案之外的改动”**。

## 4. 怎么看进度、看产物、中途插手与分享结论

左侧菜单的**“编码”**统一收拢了三个标签：**交办**（所有交办与分支评审，按“等你 / 进行中 / 助手在处理 / 搁着 / 已结束”分组）、**方案**、**需求**（空间的需求树与测试点）。

- **测试截图、录屏与 HTML 报告直接挂在修改项上（产物）**：编码 Agent 和测试脚本把生成的文件写入环境变量 `$OMEM_ARTIFACTS`（按 `T<编号>/` 归属到对应修改项，带 `index.html` 的目录自动识别为测试报告）。在修改项下方点**“看截图和报告”**或切到**“产物”**标签页，即可直接在网页里看截图、拖放录屏视频、在隔离沙箱里打开 HTML 报告。
- **中途随时插手、回退检查点或自己改两行**：
  - 编码进行中可随时在交办页顶部“补充给编码 Agent”发新要求（当轮即收到），或说“先把 `integration` 分支合进来”“后面评审从简”；
  - 在“修改项”列表里，可随时新增一项、暂停/继续、让某项重做、标为不做，或在**“检查点”**里把整个工作区或单个文件/代码段一键恢复到改动前；**即使你自己在工作区里手动改了几行代码，下一轮启动前也会自动记为你的检查点并被编码 Agent 完整保留**。
- **仓库从评审中自动“学到约定”**：当同一类评审问题在该仓库的**两次不同交办**中被你采纳修改后，omem 会自动将其提炼为该仓库的**学到的约定**——能写成正则模式的由宿主在每轮直接扫描新增代码行，其余自动注入编码与评审角色的上下文（可在仓库空间设置里查看来源、编辑或启停）。
- **固定度量指标的夜间自动调优循环**：对于性能优化、包体积缩减等有明确数字指标的任务，挂上改进目标后，宿主会先跑度量命令测出基线，每轮改动后重测，**只有达到最小增益才保留提交，否则自动回退**，直到达标或连续四轮无进展后停下并输出前后对比报告。
- **一键生成免登录只读评审分享链接**：点评审概览上的**“分享结论”**（或让助手调用 `share_review`），即可生成一个免登录只读链接发给写分支的同事——里面包含评审结论、问题目录、每条问题的级别与你的决定（改 / 暂不改 / 不改），**正文引用的代码行、原件和记忆一并打包在侧栏可点开查看**，不含内部评审过程，随时可在 **设置 → 分享** 中撤销。
