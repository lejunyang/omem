# Git 同步、应用与推送

## 工作区与依赖

每次交办默认新建一个 worktree，里面没有被 Git 忽略的文件，依赖要重新装。仓库空间的设置（设置 → 空间 → 编辑）里可以换成复用：

- **准备命令**：比如 `pnpm install --frozen-lockfile`。编码前在工作区里检查，命令和锁文件跟上次成功时一样就跳过，变了才跑；失败不中止，编码 Agent 会看到输出。
- **复用工作区**：omem 自建几个（放在数据目录的 `workspaces/` 下），或者列出你已经装好依赖的目录（这个仓库 `git worktree add` 出来的）。交办借一个空闲的用，用完重置：改过的和新加的文件清掉，`node_modules` 这类忽略的文件留着。你的目录有未提交改动时不借，用完回到原来的分支。都在用时照旧新建。

设置里能看到每个工作区现在是空闲、被哪个运行占着，还是不可用及原因。

## 在 VS Code 里看

编码运行的页头有“在 VS Code 中打开”：工作区还在时打开工作区（改动相对基线暂存着，VS Code 的源代码管理面板直接就是这次的 diff），应用后打开接收位置。

网页在 omem 所在的机器上时直接打开本地目录。从别的电脑看（局域网链接、`omem peer open`）时用 Remote-SSH：第一次点会让你填这台机器在你电脑上的 SSH 主机名（`~/.ssh/config` 里的 Host），记在你的浏览器里。旁边的齿轮可以换成 VS Code Insiders 或 Cursor。

在“设置 → 外观与说明”打开“网页版 VS Code”后，齿轮里还能选“网页版 VS Code”：在新标签页里打开 omem 所在机器上的工作区，不用本地装 VS Code，也不用配 SSH。它用的是这台机器上官方的 `code serve-web`（第一次打开会先下载服务端），由 omem 代理和鉴权，只对你开放；它带终端，等于这台机器的命令行。经 `omem peer open` 打开的网页也能用，包括经中间机器才能访问的设备。

## VS Code 插件

仓库的 `vscode/` 里有插件（`pnpm run package` 打出 .vsix 安装）。打开交办的工作区后：

- 评审问题挂在对应代码行上，线程标题上点“改 / 暂不改 / 不改”，“不改”写一句理由；侧栏“修改单”列出全部问题。
- 选中代码按 `Ctrl+Alt+A`（或右键“问 omem”），在这段代码上开一个线程：输入后点“提问”，回答写回线程；点“记为修改点”留给下一轮。
- “修改单”的“开始修改”把标了“改”的问题和修改点一起交给编码 Agent，状态栏显示轮次，点开看过程。
- 侧栏“交办”的 ＋ 选仓库后在临时文档里写任务，右键“引用到交办任务”可以把选中代码带进去，点文档顶部的“提交交办”。

点状态栏左下的 omem（或命令“omem：连接 omem…”）选 omem 在哪里：这台机器上（含 Remote-SSH 连到的那台，一般什么都不用填）、另一台机器（粘贴 `omem link` 的链接或 `omem peer invite` 的配对码，或填地址和令牌）、经本机 omem 转发到配对的设备（从列表里选）。连别的机器时，要从评审跳到代码还得填那台机器的 SSH 主机名。

## 编码前先同步

<Shot src="delegate-sync" caption="交办时可以先拉取目标分支、再合并或变基到另一个分支，也可以只同步不编码" />

交办时可以选：

- **拉取目标分支在 origin 上的新提交**：能快进就快进，分叉了按选的方式合并或变基；
- **再合并或变基到另一个分支**（如 main）：本地落后 origin 时用 origin 的；
- **只同步，不再编码**：这次的任务就是“把 main 合并进来、解决冲突”。

对助理说也一样：“把 main 合并到 feature/refund，冲突你先解决”。工具上是 `delegate_code` 的 `sync` / `sync_only`，后续轮次是 `continue_code_run` 的 `sync`。

## 冲突

1. 合并或变基停在冲突上时，冲突文件交给**编码 Agent**：它读两边的改动按意图合并，业务上拿不准的取舍用卡片问你。
2. 它解决不了的，运行停下来，给你一张卡片：列出冲突文件和工作区路径。在工作区里解决、`git add` 之后点“已解决，继续”，新的一轮接着完成；或者“放弃这次同步”，工作区回到同步前的样子。
3. 解决过的冲突写进运行说明：每个文件相对同步前变成了什么，评审者也会读到。

后续轮次里同步时，工作区里还没应用的改动先收起，同步后再放回；放回时的冲突同样先交给编码 Agent。

## 应用

“应用到原分支”把改动应用到交办时的目标分支：

- 目标分支已有工作区就用它，没有就自动建一个接收工作区，不切换你的仓库主目录；
- 同步产生的提交（合并、拉取）先**快进**到目标分支，编码改动再作为**未提交的修改**应用；
- 目标分支在交办后又有了新提交、应用不上时，点“**移到目标分支最新提交**”：新的一轮把改动变基到最新提交上，冲突照样先交给编码 Agent；改动没变就沿用上一轮的评审。

## 提交与推送

应用后，运行页“接收位置与提交”里：

- 填提交信息，选“提交”“提交并推送”或“仅推送已有提交”。只提交暂存区，没暂存的修改保留。
- 默认推送到 origin 上的原分支，也可以填别的分支名（比如给合并请求用的新分支）。
- 变基过的分支和远端分叉时勾“**强制推送**”：带 lease，只有远端仍是上次拉取时的状态才替换，别人新推的提交不会被覆盖。
- 推送失败保留本地提交，刷新后可以只重试推送。

也可以让主助手做：先 `code_git_status` 看状态和待提交的差异，再 `code_git_action`；强制推送只在你明确同意时用。
