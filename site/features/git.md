# 工作分支、同步与推送

## 工作分支

每次交办在每个仓库有一条自己的分支，改动按提交留在上面：

- **从哪里开始**：不指定时从仓库目录当前的提交切出一条临时分支 `omem/<运行id>`，编码 Agent 按功能改成合适的名字；指定已有分支（`from_branch`）就在那条分支上接着提交；也可以直接给新分支起名。起点是本地的提交，没推送的也算。
- **怎么提交**：编码 Agent 按功能分几次提交，遵守仓库的提交规范；一轮结束时还没提交的（包括检查命令改出来的）由 omem 提交成“第 N 轮没提交的改动”。每轮都有提交，出了问题下一轮再改，回头看提交历史就知道每轮做了什么。
- **在仓库目录里验证**：运行页“工作分支”里点“在仓库目录检出”，你的仓库目录就切到这条分支。之后每轮结束，新提交自动快进到那里，直接在仓库目录启动服务验证，不用自己拉。你在那里也提交了的，下一轮先把分支合并进来再改。
- **几个需求同时做**：每个交办一条分支、一个工作区。编码 Agent 知道同一仓库里还有哪些没确认的交办和它们的分支，需要别的交办的改动时可以 cherry-pick。
- **确认**：最后只有一个动作，“确认并推送”：可以先勾“压缩成一个提交”，然后推到 origin 的同名分支并设为上游，归还工作区，分支保留。远端有本地没有的提交时会拦下来，你同意覆盖才勾“覆盖远端”（带 lease）。
- 确认前还可以：改分支名、压缩、合并或变基到另一个分支（排一轮同步，冲突先交给编码 Agent）、丢弃（这次新建、没推送的分支一起删）。

## 工作区与依赖

不用设置。omem 在数据目录的 `workspaces/` 下按需建工作区，每个仓库最多 4 个，都在用时收回一个闲着的（它的分支和提交都在，下一轮再借）。用完重置：改过的和新加的文件清掉，`node_modules` 这类忽略的文件留着。

- **准备命令**：不填时按锁文件自动选（`pnpm install --frozen-lockfile --prefer-offline`、`yarn install --frozen-lockfile`、`npm ci`、`bun install`），命令和锁文件跟上次成功时一样就跳过；要换就在空间设置里填，填 `none` 不准备。失败不中止，编码 Agent 会看到输出。
- **换仓库目录**：空间关联的是 omem 克隆的目录、你平时在另一份克隆里开发时，在空间设置里点“换目录”，之后交办从你的目录切出分支。两边 git remote 相同即可。
- 事项结束时，它的交办占着的工作区自动归还，分支保留。

这些也可以跟助手说。没确认的交办，让助手“清理一下”：它先列清单，你同意哪些就丢弃哪些。把另一份本地仓库路径给助手时，同一个仓库（remote 相同）已有空间就不会重复建，要改用这份目录跟它说一声。

## 在 VS Code 里看

编码运行的页头有“在 VS Code 中打开”：工作区还在时打开工作区，工作区归还了就打开检出这条分支的目录。

网页在 omem 所在的机器上时直接打开本地目录。从别的电脑看（局域网链接、`omem peer open`）时用 Remote-SSH：第一次点会让你填这台机器在你电脑上的 SSH 主机名（`~/.ssh/config` 里的 Host），记在你的浏览器里。旁边的齿轮可以换成 VS Code Insiders 或 Cursor。

齿轮里还能选“网页版 VS Code”：在新标签页里打开 omem 所在机器上的工作区，不用本地装 VS Code，也不用配 SSH。它用的是这台机器上官方的 `code serve-web`（第一次打开会先下载服务端），由 omem 代理和鉴权，只对你开放；它带终端，等于这台机器的命令行。经 `omem peer open` 打开的网页也能用，包括经中间机器才能访问的设备。选它时齿轮里会显示用的是那台机器上哪个 VS Code 命令行；找不到就在那里填路径。

浏览器是中文时，界面用那台机器上装的中文语言包翻译；语言包比 VS Code 旧时，新加的几处显示英文，菜单不会错位。omem 自己的 VS Code 插件已经装在里面，直接连着这台 omem，不用设置。网页版第一次启动时，会拿那台机器上 Remote-SSH（或桌面 VS Code）的设置当初始值；那边装过的扩展默认不复制，设置 `ide.web.reuseExtensions: true` 后会把适合这台机器和这一版的各复制一份。快捷键、主题这些存在浏览器里，要和桌面一样，在网页版里登录账号打开“设置同步”。

## VS Code 插件

仓库的 `vscode/` 里有插件（`pnpm run package` 打出 .vsix 安装）。打开交办的工作区后：

- 评审问题挂在对应代码行上，线程标题上点“改 / 暂不改 / 不改”，“不改”写一句理由；侧栏“修改单”列出全部问题。
- 选中代码按 `Ctrl+Alt+A`（或右键“问 omem”），在这段代码上开一个线程：输入后点“提问”，回答写回线程；点“记为修改点”留给下一轮。
- “修改单”的“开始修改”把标了“改”的问题和修改点一起交给编码 Agent，状态栏显示轮次，点开看过程。
- 侧栏“交办”的 ＋ 选仓库后在临时文档里写任务，右键“引用到交办任务”可以把选中代码带进去，点文档顶部的“提交交办”。

点状态栏左下的 omem（或命令“omem：连接 omem…”）选 omem 在哪里：这台机器上（含 Remote-SSH 连到的那台，一般什么都不用填）、另一台机器（粘贴 `omem link` 的链接或 `omem peer invite` 的配对码，或填地址和令牌）、本机 `omem peer add` 配好的设备（从列表里选，本机 omem 服务不用开）。连别的机器时，要从评审跳到代码还得填那台机器的 SSH 主机名。

## 编码前先同步

<Shot src="delegate-sync" caption="交办时可以先拉取目标分支、再合并或变基到另一个分支，也可以只同步不编码" />

交办时可以选：

- **拉取目标分支在 origin 上的新提交**：能快进就快进，分叉了按选的方式合并或变基；
- **再合并或变基到另一个分支**（如 main）：本地落后 origin 时用 origin 的；
- **只同步，不再编码**：这次的任务就是“把 main 合并进来、解决冲突”。

对助理说也一样：“把 main 合并到 feature/refund，冲突你先解决”。工具上是 `delegate_code` 的 `sync` / `sync_only`，后续轮次是 `continue_code_run` 的 `sync`。

## 冲突

1. 合并或变基停在冲突上时，冲突文件交给**编码 Agent**：它读两边的改动按意图合并，业务上拿不准的取舍用卡片问你。
2. 它解决不了的，运行停下来，给你一张卡片：列出冲突文件和工作区路径。在工作区里解决、`git add` 之后点“已解决，继续”，新的一轮接着完成；或者“放弃这次同步”，工作区回到同步前的样子。
3. 解决过的冲突写进运行说明：每个文件相对同步前变成了什么，评审者也会读到。

后续轮次里同步时，工作区里还没应用的改动先收起，同步后再放回；放回时的冲突同样先交给编码 Agent。

## 以前的交办：应用与提交

改成工作分支之前开始的交办（工作区里是未提交的改动）照旧：“应用到原分支”把改动作为未提交的修改放到目标分支的工作区（没有就建一个接收工作区），之后在“接收位置与提交”里填提交信息提交或推送；目标分支变了应用不上时点“移到目标分支最新提交”。主助手用 `code_git_status` / `code_git_action` 做同样的事，强制推送只在你明确同意时用。
