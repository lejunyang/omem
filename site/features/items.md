# 事项

<Shot src="items" caption="事项：待办、等待回复和持续关注，详情里有材料、相关依据和时间线" />

事项是要跟进的事：待办、提醒、待决定、等待回复和持续关注。它和记忆的区别是会结束：做完、过期，或者被新消息重新打开。

你直接在仓库里提交代码后，助手会核对它属于哪件事，在卡片上请你选择挂到已有事项、新建或不用管。确认挂到已有事项时，还没开始的编码阶段会补记完成；第一次接入不翻以前的提交。

把 GitHub 合并请求链接发给助手，就能挂到事项上跟进；流程可以等它合并或关闭后继续。需要启用对应插件并连接账号。事项页的“外部状态”里也能直接贴链接挂上，那里显示它现在的状态和几个要紧的字段。

卡片上还有插件给的按钮，比如合并请求开着时的“合并”：点了先确认一次，然后用你在平台上的身份去做，做完马上再读一次状态，流程和规则跟着走；平台拒绝（检查没过、缺评审）时原因写在卡片下面。助手也能做同样的事，默认每次先问你，在 设置 → 安全 → 工具审批 里可以改成“做完告诉我”或“不用问”。每次执行都记在审计里。

打开一件事项，材料上方会提示适用的流程，点“开始”先看各段做什么，再确认；没有适用建议时，点“用流程推进…”从全部定义中选。阶段条显示每段的进度、用时和尝试次数，点一段能看承担者、方案或交办、原件依据和最近进展。验证这类阶段交给助手做时，它按需求点逐条去试，每条的结果、做了什么、截图和录屏都列在这一段下面的“逐条的结果”里，你照着看完再确认；你给的测试账号它可以自己在测试环境登录，账号不够时会来问你。需要你确认、轮到你做或卡住时，条下直接显示操作卡片；跳过、重开或手动完成要写明原因。经过可以展开查看，流程走完后仍由你决定是否关闭事项。

在“规则 → 流程”编写或修改流程定义：左边选一份，右边是“它会怎么走”的清单（逐段写明谁来做、怎么开始、做到什么算完、要等谁）和 YAML 原文，边改边更新；读得通才可保存。没有人参与时连着自己开始几段后先问你、停在等你的阶段过几天提醒一次，在 设置 → AI → 自动推进 里改。修改定义不影响已经开始的事项，也可以先请助手按你的描述起草。

流程进行中，关联的群、会话和文档有了新内容，助手会攒一批看看这件事变了什么。新要求影响已经在做或做完的部分时，先问你要并进、另开还是不用管，不替你答应。事项页把等你定的变化放在流程条下面，写明影响哪几段、并进来会重开哪一段；下面是全部变化的记录和正在跟的群、文档。文档更新时只看新增或改过的行。

<Shot src="item-flow" caption="事项流程：评审通过，轮到你推送" />

已经做过的阶段可以补记完成，验证结果可以逐条签字；同一开始关卡连着直接同意后，会先问你是否以后直接开始，重开或暂停时改回每次问。新内容每天默认最多看 12 批，多的留到明天；事项页的阶段上有“这一段已经做过了”，验证结果每条可以点“看过，对”或“不对”；事项页的“按流程看”打开流程看板，在走流程的事项按阶段分列，今日页列出流程里等你的；这几个数和开关在 设置 → AI 里。

流程结束时（走完、你停下或事项关闭），事项页上多一块“这一次走得怎样”：各段用了多久、其中等你多久、卡在哪、返工几次、哪些关卡你每次都直接同意。同一份流程又结束满三件，助手会对照这几份回顾看定义要不要改，有站得住的修改就起草一份新定义等你点“启用”，不会直接改。重开前面的阶段时，后面正在做的阶段不会被悄悄停掉，会问你要停下还是继续做。

持续探索一个项目可用内置“课题”流程：梳理功能清单 → 提方向由你选 → 按预算逐个试验 → 小结归并发现。功能清单存事项空间的工作文件；提方向先不看旧结论，提交后宿主才去掉完全重复的试验。预算用满后剩下的留到下一轮，默认由你说何时继续；没有方向、没有新发现都是正常结果。事项页的“课题的台账”分四块：发现（没判定的在前，可以认可、不算或以后再说）、试验（没做好的在前，展开看摘要和依据）、方向（等你选时在这里选，在做的可以结束并写结论）、覆盖（各功能试过几次、哪些没碰过）。完整字段见仓库的 `docs/v2/studies.md`“第二期的实现”。

课题可限定仓库、选择登记的执行环境，试验在自己的副本里按确认时的版本运行，不改你的检出目录。允许改代码后，你可以从发现发起编码交办，改动留在交办分支上等你确认。范围在事项页“课题的台账”顶上改，发现上有“去改”，执行环境在 设置 → AI 里登记。

执行环境可以选“派给设备”：试验交给你配对过的另一台设备跑（比如要那台的系统或装好的工具）。那台按仓库的远端地址找到自己的那份仓库，缺方向确认时的提交就自己取一次，在它自己的工作区里跑，用它自己的模型和技能；本人在那台的检出目录不动。结果和证据文件送回这里的台账，试验上写着在哪台跑的、那边的运行是哪一条；单个证据文件超过 2 MB 的文本只带回开头。那台没有这个仓库时试验记“跑不了”；离线或出错时过 10 分钟再派一次，还不行记“跑不了”。停止流程、重开或预算用完时会请那台停下。只对你自己的设备开放，别人的服务不能接。

含“改”阶段的流程可按你允许的方向逐条改缺陷，评审通过后重跑失败试验，改动留在交办分支上等你应用；没改成的留给你看。通过范围接口登记远端和分支前缀后，试验与改后重跑可在授权范围内推送，每次有记录；已有流程需自行补上“改”阶段。

由你来做或只等进展的阶段可以写 `done: { signal: git.pushed }` 或 `done: { signal: git.merged }`。关联交办的改动应用到仓库后，所有仓库的提交都已在远端（合并信号则在目标分支的远端）时，这一段会自己完成，后面的阶段接着走；你也可以照旧手动点做完。内置需求交付模板的推送段已采用推送信号；已有模板只在你修改后生效，进行中的事项保留启动时的副本。

流程定义也支持重复轮次：`repeat: { from: plan, every: manual }` 从指定阶段起重做，默认等你说“再来一轮”；也可写 `done`、`day` 或 `[tue, fri]`。上一轮没做完不开新的，连续自动开始到上限先问你。

运行阶段可用 `ai: strong / standard / cheap`，在配置的 `agents.tiers` 把档位映射为 `{ profile, model?, effort? }`；未配置沿用默认 AI，额度用完等恢复。`at: "10:00"` 与 `window: "23:00-05:00"` 按配置时区限制开始；普通运行用满分钟预算会停止并等你，trials 阶段的 `budget: { minutes: 240, trials: 8 }` 用满任一上限则完成本轮阶段、保留剩余队列。写了 `ai` 的运行或 trials 阶段可加 `escalate: { to: strong, max: 2 }`，交不出结果或拿不准时带反馈换档重做，trials 每个试验最多升档一次。事项页上能看到现在第几轮、点“再来一轮”、改这一轮的预算。

## 不用专门去记

- 对话里说“周五前把方案发给小王”“等财务回复报销口径”，助理回答时顺手记成事项，并在回答末尾列出。
- 群聊和文档整理时，和你有关的承诺、请求、待决定的事会被提出来。
- 也可以在“事项”页右上角“新建事项”写一句话，交给助理理解时间和对象。

## 跟到收尾

- **时间线**：每次变化（改期、完成、新消息）都记一条，带来源。通知只带这次变化的来源，错的来源可以撤回并留历史。
- **期限**：待办 14 天、待决定和关注 7 天、等待回复 14 天没有新进展就自动“过期”（不算完成，有新进展会重新打开）。期限在 设置 → 定时任务 里改。
- **自己判断办没办**：你在来源群里回过话、回了表情的，由助理判断是否已经办了并关掉；回 DONE 表情直接关。
- **每日清点**：每天一张卡片，列出自动收尾的和明天过期的，要留下的点“保留”或“恢复”。
- **唤醒**：说“半小时后看看 CI 结果”“小王发了发布单就检查回滚方案”，它设一个定时或等消息的唤醒，到时候在原会话里接着做，没变化不打扰你。

## 拿不准先问你

<Shot src="ask-question" caption="拿不准的取舍先问你：选一个，或写一句自己的回答" />

做事项的过程中遇到非你决定不可的事，助理发一张卡片问你：选一个按钮，或在对话里回一句。你答完它在同一轮接着做。还没答的问题都在“今天”页的“等你回答”里。

设置 → 安全 → 工具审批 可以逐个选“每次问我 / 做完告诉我 / 不用问”。默认连续批准 10 次会问一次要不要改成“直接做，做完告诉我”，你同意才改；次数可调，0 不提议。做完告知会放进不急的通知里。随时能改回每次问，机器点击、输入类插件工具始终要批准；拒绝理由会回给 Agent。

## 大事项

- **材料**：大型需求可以建一个事项，把文档、群聊、代码分支、要对照的仓库挂上去；之后的交办和评审会读这些材料，结果也挂回事项。
- **工作文件**：要做好几天的事（逐个回溯一批群、清点一批文档），助理把当前成果写成工作文件挂在事项上：做了哪些、得到什么、下一步。下次接着做先读它。
- **周报**：建一条定时规则（工作日 18:00）让某个 Agent 往 `weekly/<周>` 工作文件里追加当天进展，周五整理成稿。
- **在这些会话里进行**：助理在哪个会话或群里记了、更新了这件事，事项就和那里关联上；详情里列出这些会话（最近活动和最后一句话）和正在为它跑的运行。在任一会话里再谈这件事，助理都知道别处说到哪了（见 [多 Agent 协作与会话](./collaboration)）。

## 需求点与测试点

一个需求要开发、评审好几轮时，把它拆成需求点放进业务空间的“需求”树：系统 → 模块 → 页面 → 功能，功能下面挂测试点。在事项的材料里点“拆需求点”，AI 读需求文档和讨论拆好，你在需求页确认或修改。

- 切换需求点时先显示新标题和加载骨架，返回后再显示详情；编码列表只读状态摘要，交办轮次多也不用搬回完整补丁。
- 切换空间后显示该空间的需求树，并退出原来的需求详情和编码与评审；打开跨空间的需求链接时，会切到它所属的空间。
- 交办这个事项时，编码 Agent 按需求点开发；评审逐个核对，需求页上每个点显示最近一次评审的结果（已实现、部分实现、没实现）。
- 为这个事项做的交办和分支评审列在需求点下的“编码”里，和运行页“编码”的写法一样：在等谁、进度、分支；点开就在需求页里看这次交办（和运行页同一个视图），定要改的问题、回答等你决定的项、确认并推送。树上等你处理的节点标“等你 N”。打开一次交办后，左边的树标出每个需求点这一轮实现到什么程度，点一个需求点就只看它对应的代码改动。
- 编码 Agent 跑完测试后把每个用例的结果交上来，写明它对应哪个测试点；需求页树上标“测试通过 / 测试失败 N”，点开测试点能看到每个测试最近一次的结果、失败原因和截图、录屏，更早的结果折叠起来。同一个测试只留最近 3 次结果的截图和录屏，不会越积越多。
- 每个仓库的测试怎么跑、用例里怎么写测试点 id，写成技能挂在这个仓库的空间上（设置 → 空间 → 这个空间的技能）：技能放在 omem 的数据目录，不用放进代码仓库，只有这个仓库的编码和评审会用到。
- 改需求分两种：写错了选“更正”；规则变了选“业务变更”，写清原因和依据，以后翻时间线能看到当时为什么改。
- 需求跨业务时，在两边的需求点之间加“关联”，不复制。
- 需求点能被搜索到，测试点不进搜索。
- 拆需求的角色可以在 Agent 页改：改说明、换模型、挂技能（比如在团队的测试平台上同步生成用例）。
