# 事项与流程

**事项（Items）是需要跟进到收尾的具体工作：待办、提醒、待决定、等待回复和持续关注。** 几周推进的大事可以建成[工作线](./work-lines)，把相关事项挂在下面；而单件需要分步推进的事项，则可以挂上**流程（Flows）**、拆解**需求点与测试点**，或者开启持续探索项目的**研究（Studies）**。

## 1. 怎么建事项、怎么自动收尾

### 不用专门说“记住”，但绝不乱建噪音事项

- **对话与群聊顺手记**：你在对话里说“周五前把方案发给小王”“等财务回复报销口径”，助理回答时顺手记成事项并列在回复末尾；采集群聊和文档时，与你有关的承诺、请求和待拍板事项也会自动提炼出来。
- **后台自动建事项有严格门槛**：不是你亲口交代、而是助手从群聊或巡检里自己看出来的事，它必须先交代清楚**“你为什么会需要这件事”**（关联你说过的话、你盯的关注或你的工作线）。说不清的不建；把握不大的先放进**“可能要跟的”候选池**——不发通知打扰你，只在每天早上的“今天”卡片和事项页顶部让你点“留下”或“不要”（3 天不理自动放下，你的选择还会教会决策模型以后少提你不关心的事）。

### 自动判断已办与到期收尾

你不需要每次办完事都回到网页点“已完成”：
- **从群回复和表情自动结项**：你在来源飞书群或话题里已经回复了对方，或者对提醒卡片贴了表情，后台的 `item-keeper` 会结合上下文判断这件事是否已经办完并自动关掉；贴 `DONE` 表情则直接关掉。
- **无进展自动过期，有新消息自动重开**：默认待办 14 天、待决定与关注 7 天、等待回复 14 天没有新进展就自动标为“过期”（不算完成，也不会删；之后群里一有新进展会自动重新打开）。每天早上的“今天”卡片会列出自动收尾和次日即将过期的事项，想留下的点一下“恢复”或“保留”即可。

## 2. 事项按流程推进（Flows）

当一件事项需要走过“澄清 → 方案 → 编码 → 验证 → 推送”等多个阶段时，可以在事项上开启一份**流程**（甚至没有现成模板时，直接口头交代多步工作，助理也会为这件事生成一份一次性阶段清单，走完可一键存为模板）。

<Shot src="item-flow" caption="事项流程：阶段条清晰展示各段耗时与状态，评审已通过，当前停在推送阶段等你确认" />

### 流程是怎么自动往前走的？

1. **一句话让助理起草流程定义**：在 **工作 → 按阶段 → 流程定义** 里，用自然语言讲讲这类事平时分几步、每步谁做、哪里要你拍板、做到什么算完，助理起草好 YAML 定义发给你确认启用。
2. **你在外面做完的事，不用回来手动打勾**：
   - **代码提交与推送自动过关**：你在仓库里直接提交了代码，助手会主动发卡问你是否挂到该事项并补记编码阶段完成；推送阶段若设为等待 `git.pushed` / `git.merged` 信号，你把代码推上远端或合并后，该阶段自动完成并启动下游。
   - **群里说的话自动核实对账**：轮到你做的普通阶段，助手会从你随后的发言、关联群聊消息和挂载的外部对象（如 GitHub PR 状态）里核实进展，查实了就直接带依据推进；发现整件事项的目标已经达成或不再成立时，还会带依据直接收口。
3. **能自己补的材料不麻烦你，真卡住了给齐依据**：接口暂时不可用时助手会定时重试；能自己补的文档、字段或回归验证交回原 Agent 补齐；确实需要你拍板或找同事要材料时，网页和飞书显示同一张阶段卡（若机器人在关联群里，卡上点一下就能直接把催要材料的草稿发到群里）。
4. **验证阶段逐条截图签字**：测试验证阶段交给助手时，它会按需求点逐条去试，把每条用例的通过状态、操作步骤、截图和录屏列在“逐条的结果”里，你可以逐条点“看过，对”或“不对”（同一次推送修好的几件事项还能配置 `together: push` 合并跑一次回归验证）。
5. **走完自动复盘流程定义**：每件事项走完流程后，页面会统计各段耗时、等待时长、卡点与返工次数；同一份流程累计走完 3 件，助手会对照回顾看看流程定义本身有没有可以简化的地方（比如某个开始关卡你每次都直接点同意），有站得住的改进就起草新定义供你启用。

## 3. 持续探索项目：内置“研究”流程（Studies）

对于没有现成固定需求、需要持续寻找问题或优化空间的项目（如全面排查某系统的边界缺陷、专项性能优化），可以开启内置的**“研究”**流程：

1. **梳理功能清单 → 提方向由你选**：助手先通盘梳理功能清单，结合以前各轮试过的方向和发现（自动避开重复试验），提出几个探索方向供你勾选。
2. **在独立副本或另一台设备上跑试验**：在限定的仓库范围与登记的执行环境中，按分钟预算或试验次数逐个跑试验（支持选**“派给设备”**，把试验派给你配对的另一台机器用那台的环境和模型跑，结果和截图证据自动传回本机，绝不改动你的本地检出目录）。
3. **归并有复现依据的发现，一键“交给改”**：所有有复现证据的问题按“条件 / 现象 / 为什么是问题 / 建议”归并在事项页的**“研究记录”**里。你勾选认可的几条发现点**“交给改”**，omem 就会按顺序逐条发起编码交办与独立评审（续轮评审严格按最初的复现步骤验收），改好并通过重跑试验的自动标为“已改好”，改动留在交办分支上等你确认。

## 4. 拆解需求点与测试点：让编码和评审逐条对齐

面对大型需求，把文档、群聊和代码分支挂到事项的“材料”区后，点一下**“拆需求点”**：

<Shot src="requirements-loading" caption="需求树视图：按系统 → 模块 → 页面 → 功能拆解需求点与测试点，实时联动编码与评审状态" />

- **四级需求树 + 测试点**：AI 自动把需求文档和讨论拆成 **系统 → 模块 → 页面 → 功能** 四级需求树（出现在左侧 **编码 → 需求** 标签页），每个功能点下挂具体的**测试点**。
- **编码与评审逐点核销**：交办该事项时，编码 Agent 按需求点开发并提交每个测试点的运行结果（含截图与录屏）；评审角色逐个需求点核对并标出**“已实现 / 部分实现 / 没实现”**。规则变了可在需求树上选“业务变更”并记录原因，跨业务空间的需求点支持互相建立关联而不重复复制。

## 5. 挂载外部平台对象、同步 Issue 与临期预查

<Shot src="item-sync" caption="设置 → 推进工作 → 事项同步：订阅 GitHub 等外部项目，支持新条目先当候选、本地改状态后询问是否写回" />

<Shot src="item-external" caption="来自外部平台的事项：实时展示远端编号、状态与负责人，本地关闭后可一键写回远端" />

- **挂载 GitHub 合并请求（PR）**：把 PR 链接发给助手或贴进事项的“外部状态”，即可实时跟进其状态、新提交与评论；流程阶段可设为等它合并后自动继续，你还可以在事项卡片上直接点**“合并”**按钮（经确认后以你的平台身份合并）。
- **双向同步外部 Issue / 需求**：在 **设置 → 推进工作 → 事项同步** 中订阅插件提供的外部项目（如 GitHub Issues）。新条目可设为先进入“可能要跟的”候选池或直接建为事项；你在 omem 里关闭事项时，会询问你是否把完成状态同步写回外部平台。
- **工作日指派清点与 48 小时临期预查**：
  - 在规则页开启**“清点指派给我的事”**（`assigned-sweep`），工作日早上 `09:00` 主助手会按你在工作近况里写的平台和查询技能，主动清点外部系统指派给你且有时限的单据，3 天内到期的合成一条通知提醒你。
  - 凡是**距离截止不到 48 小时、近一天无进展且没在走流程**的事项，定时巡检会先自动做一次**只读预查**（核对最新材料和外部链接），把现状、依据和建议的下一步放进“需要你处理”，你点“按这个开始”即可在事项会话里直接推进。
