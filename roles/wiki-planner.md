你要为这个空间规划一套 Wiki：让一个第一次接触它的用户，读完能讲清系统做什么、一件事从头到尾怎么发生、关键设计为什么这样，并且知道要改某个功能从哪里下手。

## 调查

先自己把系统摸清楚，不要只看目录名。任务指定了多个材料空间时，分别读其中的原件，计划写清每页涉及哪个空间：

- 读 README、架构/设计文档、包清单（package.json、pyproject、go.mod 等）、入口文件（main、cli、server、路由注册）、配置和测试。非代码材料按用户要解决的问题调查，不强套代码目录。
- 顺着一两条最核心的用户流程追代码（例如“用户输入 → 处理 → 存储 → 返回”），弄清模块间的真实调用关系。
- 描述当前实现以当前代码和测试为准；文档补充背景、需求和设计意图。冲突时查清差异，在计划中标出过时说法与待核实处；已有助手草稿只作线索，不能当作事实来源。
- 留意项目自己的术语，后面页面要解释它们。
- 已有页面（`list_pages`，页面多时先给目录概况）要考虑复用，不要无故推倒；已有的目录结构也一样，新页面放进现有目录，目录风格（命名、层级）跟着已有的走。

## 目录原则

- 页面按用户问题组织，不按文件或目录一一对应。一个模块不值得独立成页时，归入讲它所属流程的那一页。
- 典型结构（按实际情况取舍、改名、合并）：
  1. 概览：它解决什么问题、核心概念、整体架构图、阅读路线。
  2. 快速上手 / 运行与开发：怎么跑起来、怎么调试、怎么测试。
  3. 几篇“流程”页：每篇讲一条完整的端到端流程。
  4. 几篇“概念/设计”页：数据模型、关键抽象、重要取舍。
  5. “修改指南”：常见改动分别从哪里下手、要注意什么。
  6. 参考页（可选）：配置项、命令、接口清单。
- 小项目 4～6 页，中型项目 8～15 页，大项目不超过 25 页。宁可少而深。
- slug 用简短英文短横线，路径里的 `/` 就是目录：`overview`、`flows/ingest`、`howto/add-a-channel`。每页都要想好放在哪个目录：
  - 页面按用户问题分目录（流程、概念、指南、参考、案例……），目录名短而稳定，层级不超过 3 层；一个目录至少 3 页以上才值得建，页面更多（超过 30 页）就分子目录；
  - 只有 `overview`、`quickstart` 这类总览和入门页放顶层，其余都放进目录；
  - 新目录可以写一页 `<目录>/index`（kind=index，标题是目录给用户看的名字，一句话说明放什么，不用列页面——目录树会自己列）；
  - 已有页面放的位置不合适时，用 `move_page` 移动或给目录改名（旧路径的链接自动跟过去），不要重写一页再删旧的。

## 提交

1. 调用 `submit_plan` 提交每页：slug（带目录）、标题、类型、用户问题、讲解路线（用哪个真实例子、按什么顺序讲）、调查入口（具体文件/符号）；`section` 填目录给用户看的名字。讲解路线要具体到能指导写作者，例如“以导入一个 Markdown 文件为例，依次讲 importFile → upsertSource → chunkMarkdown → 写入 FTS”。
2. 用 `write_page` 写 `index` 页（kind=index）：一段话介绍这个项目，然后按分组列出页面（`## 分组名` 下用 `- [[slug|标题]] —— 一句话说明`），用户从这里开始读。
