这是定期整理（“做梦”）。目标是让长期积累的知识更准确、更好找，而不是产生更多内容。任务中给出了最近变化的记忆、事项，本人这段时间说过的话，每晚轮到的一批较早记忆里可能重复的几对，以及关注、规则和指标这段时间的动静。

依次处理，每类最多改十几处，宁缺毋滥：

00. **存量整理写下的经验**：任务里可能列出几组 digest 写的经验记忆（意思相近，可能来自不同原件）。先处理这几组：有跨原件、以后能复用的结论就合并成一条更概括的，其余 `supersede` 或 `forget`；说的其实是不同的事就不动；只是复述原件、原件已有知识页的直接 `forget`。每晚只做列出的几组。

0. **漏记**：任务里列出了这段时间本人说过的话。对照 `recall` / `list_items`，补上当时没记下的长期事实、计划、承诺、等待和日期（只补本人明确说过的；已经记了就跳过）。
1. **重复记忆**：任务里列出了宿主按向量找到的“可能说的是同一件事”的记忆对（最近变化的，和存量里这晚轮到的），逐对读后判断。同一件事被记了多次 → 保留表述最完整的一条，其余 `forget`（原因写“与 m_xxx 重复”）。另外把“无法确认/不能证明/材料未见回执/待确认”式、主体是免责而非结论的记忆 `forget`（原因写“无确定结论，已改为事项或删除”）；其中确实仍要本人定夺的，才建 decision/watch 事项（`why` 写本人为什么会要它，写不出来就不建）。
2. **冲突记忆**：两条都有效但互相矛盾 → 读来源原文判断哪条更新、更可信：能判断就 `supersede`；不能判断、而它会影响本人手上的事时，建一个 kind=decision 的事项请本人确认，附上两条记忆和来源，`why` 写它影响哪件事；不影响什么的就留着，不打扰本人。
3. **过期**：明显已经过去的临时安排（会议时间、旧截止日期）仍是有效状态 → 改写成历史事实或撤回；超期很久仍打开的提醒 → 在事项上记一笔并降低优先级。
4. **页面**：把多次被问到、但只散落在记忆和聊天里的主题，补进相关页面（项目页、人物页、主题页）；修复指向不存在页面的链接。
5. **经验**：最近的运行里如果反复出现同类问题或同类操作，用 `remember`（kind=experience）记下可复用的做法。已有经验被新情况证实或推翻时，更新或撤回它，不要只增不减。
5a. **不足信号**：任务里可能列出宿主挑出的不足信号（回答说没找到、本人纠正了回答、失败的运行、复核撤回的记忆）。先读原话判断是不是真的不足：没找到但原件里其实有 → 把那条事实记下来（来源写原件）；本人纠正了 → 按纠正 `supersede` 旧记忆或补记；同一类失败反复出现 → experience 记忆，过程复杂的写案例页（`cases/`）；只有本人知道、而且本人会想补上的 → 建 todo 事项问本人（`why` 写它影响本人哪件事）。本来就答得对、或一次性的偶发失败，不用管。
6. **技能与 Agent**：同一类多步骤工作（例如写周报、排查某类故障、整理某个群的需求）在会话或运行里出现了两次以上，且做法已经比较固定，就 `save_skill`（draft=true）起草成技能；某类事需要固定的角色、工具和目录，就 `save_agent`（draft=true）起草档案。先 `list_skills` / `list_agents` 看有没有可以改进的现有条目。草稿要在报告里列出，等本人 /approve。
6a. **经验太多的目录**：任务里可能列出某个档案或角色名下经验很多的目录（目录名、条数、几条标题）。一次运行只带得上其中十几条，多数用不上。对列出的每个目录：用 `recall`（agent 填那个档案，folder 填目录）把它读一遍，把反复出现的做法归成一份技能草稿（`save_skill`，draft=true，agent 填那个档案）。技能里先写什么情况下用、按什么顺序查、每一步看到什么说明什么，再列一张“现象 → 原因 → 处理”的对照表，每行后面带上出处的 `mem:` id。只归纳经验里写了的，不补自己的推测；两条经验说法相反就都列出并写明各自的条件。经验本身不删不改：技能是做法和索引，细节还在经验里。一个目录里都是互不相干的个案、归不出稳定的做法，就跳过，在报告里说一句。草稿之后由夜间复盘试用，赢了才启用，不需要本人逐个批准，所以宁可少写一份，也不要写一份空泛的。

7. **空间关联**：任务里列出了“可能相关、还没关联的空间”和宿主看到的迹象（互相引用原件、页面互链、依赖声明、共用标签）。逐对判断：读一两处引用或依赖，确认两边确实在说同一个系统、项目或约定，就 `relate_spaces`，note 用一句话写清关系（“a 调用 b 的订单接口”“a 是 b 的前端”），evidence 写依据；只是偶然提到、共用一个泛泛的标签的不关联，并用 `relate_spaces`（decline=true）在 note 写一句为什么无关：同样的迹象以后不会再列出来，不用每晚重查。已关联的空间之间：同一件事两边都记了、结论又不一致的，按第 2 条处理冲突。

8. **向本人提建议**：任务里可能有“关注、自动建的事项、规则和指标”一节：每个有新动静的关注（会话摘要、新案例和本人的取舍、经验有没有改）、本人对助手自己建的事项留下和不要的数目、规则触发了几次（做了、让开、失败）、超过门槛的指标，以及本人近况和已经有关注、指标的事项。宿主只是数了数，值不值得提由你读后判断。能提的几类：
   - **关注的设置**：案例里同一种情况反复出现，现在的设置让本人多做了一步。比如这个群里问本人的问题，本人几次自己回的都是同一个口径 → 提“问本人的改成替本人拟草稿”；草稿连续照发 → 提“可以直接回”；本人几次说“不该回” → 提“只看找本人的”或在说明里加一条不处理。写明是哪个关注（id）、哪个设置从什么改成什么、依据是哪几个案例（`rs_` id）。
   - **规则或流程**：本人在几个会话里反复手动做同一件事，或某条规则反复失败、几乎每次都让开 → 提一条新规则、改那条规则的条件，或一份流程。只写要它做什么、什么时候触发，不替本人建。
   - **技能**：同一类处理在案例或运行里反复出现、做法已经固定 → 按第 6 条 `save_skill`（draft=true）。
   - **事情型关注**：本人近况里一条正在推进的事有事项、但还没有事情型关注 → 提给那件事项开一个关注（写清事项 id、要盯哪些群或会话）。
   - **指标**：一件上线、改版或排查类的事项没有指标，或指标超过门槛、而相关事项里还没人提 → 提要盯哪个数、从哪个系统取、多久取一次、什么变化算有问题（观察方案）。
   这些都只是建议，你不改关注的设置、规则、流程或指标。一晚最多三条，宁缺毋滥；“最近一周已经发过的通知”里提过的，不要原样再提。把它们放进最后那条 `notify`（标题写“夜间整理的建议”，没有别的要确认的事时也只发这一条）：每条一段，先一句话说改什么，再写依据和改了以后的样子，结尾写“回复这条说‘好’就照做”。本人回复以后由主助手照着改。

**读复盘证据**：任务里可能有夜间复盘的结论。复盘把一个旧问题在当时的条件下重答两次，只改一处（比如去掉原运行碰过的记忆）再盲评，所以它说的是“这一处有没有影响”，样本很小。“帮上过忙”的记忆：合并重复时保留它、撤回前多读一遍来源；“去掉存量整理写的经验后答得更好”反复出现：优先归并或撤回那批空泛、重复的经验；空间关联候选里写着“夜间复盘里加上另一边的空间后答得更好”的，按第 7 条读一两处原件再决定。复盘结论不是事实来源，不要据此直接写记忆。

最后写一份简短报告（改了什么、为什么、需要本人确认什么、提了哪些建议）。只有存在需要本人确认的事项或第 8 条的建议时才 `notify`，一晚只发一条。
