## 实际改变

复杂问题的独立复核改为后台任务：启动立即返回 ID，作者按 ID 等待和取回意见；重复启动复用同一任务，失败需明确重试。运行中不能提交，取得意见后仍要核对原文并修正重要问题。取消问题会结束所属复核并等待资源释放。

真实验收又发现一个交付问题：复核者已经通过 `submit_result` 保存了意见，宿主仍等待 CLI 的结束消息，结果在整次问答超时时被记为取消。现在意见通过检查并保存后就立即可取回；CLI 收尾与意见交付分开，后续取消不抹掉已保存意见。这不等于作者最终答案已交付，二者分别记录。

没有更换模型、修改排序权重或延长 480 秒超时。简单直接查询仍可不使用独立复核。

## 同一道问题的实际结果

问题是“原始资料修改后，已保存的记忆会自动跟着更新吗？需要我做什么？”。两次调用都使用上轮封存的 611 份材料，语料指纹相同且运行中未变。这是一道已公开回归问题，不是盲测，也不是严格速度基准。

| 运行 | 结果 | 实际观察 |
| --- | --- | --- |
| 首次：状态工具接入后 | 480 秒超时，无最终答案 | 没有重复启动或提前提交；复核已保存“外部原件修改后需要重新导入同一来源新版”的关键遗漏，但当时等待 CLI 收尾，作者没有取回意见 |
| 修复意见交付后 | 331 秒完成，无降级 | 启动一次复核，六次等待/取回；作者补读后修订，提交完整答案，调查中的 MCP 调用没有失败 |

最终答案保留了三个对使用者重要的前提：

1. 外部改动必须再次被捕获为同一来源的新版本，不能只改外部文件然后等待。
2. 自动处理需要启用、可用 Agent 和后台运行；排队不代表执行完成。
3. 某个依赖检查任务完成或某条候选已生效，不代表所有受影响记忆都已更新；需要裁决时去“待判断”页，失败任务在“材料处理”重试。

最终候选在复核前本来就已写出重新导入前提，不能把这项差异归因于宿主回调。此次独立复核主要纠正第三点的完成判断和页面入口。程序检查仍不能证明语义已改好；以上结论来自实际阅读草稿、反馈、补读来源与最终回答。

**仍未解决：**五分多钟很慢，答案仍有重复总结和 `memory_id`、`applied` 等内部术语。一个完成的回归问题不能代表总体质量或稳定提速。此前普通 HTTP 搜索噪声仍在，不能把作者补查成功当作召回已修好。
