# 检索排序验收

更新：2026-10-09。实现已本地提交；程序检查通过，整库六题仍只命中 2/6，检索有效性尚未通过。详细输入、返回摘要和两轮检查见[结构化结果](retrieval-ranking.json)，本轮完整报告见[verification.json](../verification.json)。

## Decision 判断原先接在哪里

原有 StartLux 六维判断只接助手初始选材和单独诊断接口，普通搜索与 Agent 的后续调查没有共用它。独立 cross-encoder 端口也已有实现，当前配置没有启用 reranker。

现在正常应用的共享异步检索调用同一个 DecisionService。它分别判断相关性和回答覆盖，也判断证据支持、前提冲突，以及注入迹象和父级背景需求；阅读分取答案相关性与前提冲突的较高值，再加 0.35 倍背景分。原检索 score 保留，assessment 单独记录模型、priority 和各维度分布；概率未经大样本校准。

候选池默认至少取 40 条，模型只评估前 12 段，增加的等待最多八秒。浏览去重和数量截断在判断后进行；未评估项仍保留。冷启动后台预热，当前请求继续原检索；精确名称和显式代码导航走 AST。普通搜索、初始选材与调查工具共用判断，助手和诊断接口不重复评分。

## 同时修正的检索问题

- 类/组件原先常被拆成方法和内部声明，缺少可直接命中的类入口。现在保留首个操作前的声明与字段，方法保留完整控制流和父级背景，预处理身份为 structure-icu-v8。
- 一个结构段落回到存储片段时，重叠片段曾重复占据结果名额。现在每处来源引用只选一个可读、可定位的片段。
- 先做浏览数量限制会丢掉同一来源的后续事实。现在先判断候选，再应用浏览限制；未就绪或判断失败仍使用原有排序。
- 更新索引时，旧 FTS 按每个片段执行全表扫描删除。现在在原事务内按 owner 一次删除，失败仍回滚。

FTS 合成对照保持相同的 12,000 行与 200 个变更单位，交换测量顺序，两次逐片段删除分别为 310.26 / 301.41 ms，批量删除为 4.97 / 4.99 ms。每次均剩 11,800 行且变更旧条目为零；约 60 倍仅指该删除步骤。首轮慢索引被中断，已完成事务保留；修正后 18,214 单元全部索引，pending 为零。

## 剩余影响与下一步

`KnowledgePipeline` 排第一，`searchSourcesAsync` 排第二；其余四题未达标。长代码问题的前排包含旧原型说明，记忆更新实现排第 17，历史原型预期路径排第六。禁止按仓库名或目录写通用加分，仍需正式保存材料用途和适用状态，并用真实问题核对这些元数据的作用。

“启动不下载”问题的预期路径未进入 top-5，但第三条 docs/cli.md 确有“普通服务启动不会隐式下载”的说明。固定路径指标覆盖不全，继续保留原题结果，另做答案证据标注；不能通过调整预期路径宣称本轮通过。

下一步先建立有答案依据的候选评测，分开统计召回遗漏与已召回后错排，再对共享入口进行真实 Decision / reranker 对照。先核对候选是否包含答案，再校准判断分和候选预算；模型无法找回未召回材料，当前前 12 段判断也覆盖不到排第 17 的实现。当前仓库验收应用未注入 DecisionService，不能把六题报告解释为小模型排序效果。本轮没有生成答案质量实验，无 UI 修改，未重跑浏览器验收；临时 HTTP 数据库已释放，个人库保留，未推送或发布。
