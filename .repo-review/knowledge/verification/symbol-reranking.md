# 明确方法的召回修复，与中文重排的采用决定

2026-10-03。保留独立符号候选，默认不启用重排。本轮证明了一个具体召回修复有用，没有证明整体搜索已经好用。逐题展开看[五组实际正文](symbol-reranking.html)，完整排名、固定版本、实际重排输入及分数在[JSON](symbol-reranking.json)。成熟方案和下一步代码改造见[检索评估](../../../docs/reader-first/retrieval-evaluation.md)。

## 做了什么、解决了什么

修改前，整句话的词法匹配和向量候选会在融合前截断。即便问题写出准确方法名，该方法也可能没有进入候选。现在 AST 定义单独召回，经过正式可见范围过滤后再融合，并保留进入可选重排的入口。普通文档提到名字不算定义；普通大写词不自动当方法名。

在同库比较中，下列四条**长问题**的对应方法都从前 30 未出现变为第 1：

| 方法 | 固定源码范围 | 读者现在得到什么 | 仍缺什么 |
| --- | --- | --- | --- |
| MemoryService.apply | memory/service.ts 1192–1313 | 模型提案被应用的入口 | 保存事务和后续调用仍需补读 |
| AssistantRuntime.turn | assistant/runtime.ts 297–364 | 一次用户请求的入口 | 是否允许事项操作的完整链路 |
| KnowledgePipeline.writeAndVerify | knowledge/pipeline.ts 157–192 | 写作、修订、accepted 后发布的控制流程 | 失败如何保持旧正文的关联代码 |
| sourceUnits | retrieval/units.ts 265–422 | 代码与 Markdown 结构单位的选择入口 | 具体解析函数和上下文生成 |

16 题中，11 题前五项与旧实现完全相同；上述 4 题恢复定义；另 1 题“找调用方，不要定义”把定义推到第 1，是退步。**不能把 5 次排序变化全部称作收益。**单独查询 MemoryService.apply 原本就能命中，不算新增效果。

## 五组方案的真实取舍

| 方案 | 本机单次查询中位耗时 | 观察与决定 |
| --- | ---: | --- |
| 修改前 | 3.72 秒 | 对照基线，明确长方法漏召回 |
| 独立符号候选 | 3.78 秒 | 四条长方法问题恢复入口；采用，保留调用方意图缺口 |
| 符号 + RRF 融合 | 3.97 秒 | 未得到稳定收益；图片问题把旧原型代码推到第一，不替换默认融合 |
| 符号 + BGE base | 8.53 秒 | 老版本阅读说明从第 4 到第 2；英语卡问题却把旧计划放到当前进度前，继续可选 |
| 符号 + BGE v2-m3 | 17.08 秒 | 有局部帮助，但同样保留无关界面和旧计划；未证明值得额外等待，继续可选 |

这些时间包括真实开发入口过滤，查询向量已预热；有首次模型加载和本机其他工作影响。精确符号、空结果不会执行重排，因此全题中位数不等于模型一次推理延迟。没有做吞吐量或并发性能基准。

base 与 v2-m3 均由 osdk 固定下载、校验，实际在 CPU 上运行 q8 推理。v2 的快照是 `6f5ff65298512715a1e669753bc754d2bc8f367b`；默认配置仍没有 reranker。实验保持现有 40 个候选、512 token 成对截断、温度 3 和混合公式，因此比较的是**在现有宿主路径里替换模型**，不是两个模型的最优能力。Qwen3、Zoekt、Qdrant 平台未接入；不能把调研写成运行验证。

## 看正文之后的逐题判断

| 题号 | 要找的内容 | 结果判断 |
| --- | --- | --- |
| 1 | 取消后，旧聊天会否重建事项 | 仍偏向取消对话框和通知说明；未找到核心防重复机制 |
| 2 | 新增自主调查角色需登记什么 | 角色交接、工具提交有背景，登记清单不完整 |
| 3 | 原件换版后读旧引用 | 默认第 4 项有直接说明；BGE 提到第 2，有局部收益 |
| 4 | 图片能否用于回答 | 仍是界面补充背景和展示组件；所有方案均不够 |
| 5 | 英语间隔重复是否可用 | 默认与 RRF 第 1 项明确未实现；两个 BGE 将旧计划排在当前状态前 |
| 6 | 长问法中的 MemoryService.apply | 找回完整方法；调用链需进一步补读 |
| 7 | 单独方法名 | 原先就成功，保持成功，未执行重排 |
| 8 | 记忆类型的历史取舍 | 混入产品四类内容，历史设计有部分帮助；因果说明不足 |
| 9 | 无答案时继续补读 | 找到自主调查章节，可继续读；首项仍偏引用约束 |
| 10 | 不存在的独立符号 | 五组均为空，已有行为 |
| 11 | 只问资料为何不新建事项 | 恢复 turn 入口；v2 另找到只回答的流程图，完整控制链仍需补读 |
| 12 | 独立复核不通过会怎样 | 恢复 writeAndVerify；base/RRF 配套解释比 v2 更直接 |
| 13 | sourceUnits 的章节与代码上下文 | 恢复函数，与结构讲解组合后有帮助 |
| 14 | 明确要调用方而非定义 | 新默认把定义推到第 1，违背查找目的；BGE 后续能找到部分调用位置 |
| 15 | 延后提醒会否另建事项 | 方法、时间解释和工具动作提供部分帮助，第一项仍不直接 |
| 16 | 长句中的不存在方法 | 五组均返回泛化的参数/实现说明，没有正确报告缺口 |

这些是阅读实际结果后的人工判断，没有用模型分数作真值。没有制造一个“总体通过率”掩盖不同问题；也没有生成答案后把 Agent 补查的收益算给首次搜索。

## 对照可比性与修正记录

- 旧类取自提交 `d30b99e`，源码 SHA-256 为 `0cf4545567a19dfe8871212a799f196a9d014b8fa3bd434e68753e265c8fd365`。新实现为 `4bd891c` 与 `2dfb6fb`；可选模型适配单独提交。
- 全部方案使用同一冻结 SQLite 中的 12,507 个检索单位、v5 投影、BGE-small-zh 向量、材料说明和原件/知识版本。每题之后检查材料头、知识头和单位 ID 摘要不变。
- 所有方案使用实际 `developmentRetrieval` 的旧来源过滤。RRF 仅替换候选融合，仍保留现有最终用途/适用性偏好；与默认相同的硬性定义偏好也未拿掉。
- 前 10 题是已进入库的回归问法；后 6 题在冻结后提出。新问法数量有限，也不代表通用基准。题目不进入材料生成或分类，不按预期路径调排序。
- 初始实验的基线构建时机错误，且直接接口绕过旧来源过滤，已废弃为效果证据；原始日志仍在 runtime。随后从已提交旧源码重建基线，全部五组按生产入口规则重跑。
- 第二批发现 “Markdown” 被当成方法名，修正通用识别规则。自动比较全部题目的新旧符号提取，仅第 13 题改变，因此五组全部重测该题；其他题保留相同输入与代码路径的结果。修正前结果、重测时间和提交在 runtime/JSON 中记录。
- 同库对照在本轮新指南发布前完成。实际 dev HTTP 另作验收，不与冻结库排名混算。

## 本轮交付验证

实现已通过 `osdk deps --frozen`、全量类型/391 项测试/构建以及修正后的 12 项检索行为检查。真实中文 `retrieval:verify` 已退出 0；`retrieval:index --review` 更新到 12,438 个单位且 pending=0。这与对照冻结库的 12,507 个单位是不同时间的库，不能混用。

实际 `osdk run dev` 的 HTTP 已检查四条长方法问题和一条长句无答案问题，全部 HTTP 200；四条方法首项为对应定义，范围与原件一致。无答案题仍返回无关内容，如实保留在 JSON 的 actualDevHttp。浏览器中同一长问法首项可打开 MemoryService.apply 的 1192–1313 行，上下展开按钮仍在；未改 UI，本轮未重复全套三档视觉检查。
