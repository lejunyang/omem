# 明确方法的召回修复，与中文重排的采用决定

2026-10-03。保留独立符号候选，默认不启用重排。本轮证明了一个具体召回修复有用，没有证明整体搜索已经好用。逐题展开看[五组实际正文](symbol-reranking.html)，完整排名、固定版本、实际重排输入及分数在[JSON](symbol-reranking.json)。成熟方案和下一步代码改造见[检索评估](../../../docs/reader-first/retrieval-evaluation.md)。

## 做了什么、解决了什么

修改前，整句话的词法匹配和向量候选会在融合前截断。即便问题写出准确方法名，该方法也可能没有进入候选。现在 AST 定义单独召回，经过正式可见范围过滤后再融合，并保留进入可选重排的入口。普通文档提到名字不算定义；普通大写词不自动当方法名。

在同库比较中，下列四条**长问题**的对应方法都从前 30 未出现变为第 1：

| 方法 | 固定源码范围 | 读者现在得到什么 | 仍缺什么 |
| --- | --- | --- | --- |
| MemoryService.apply | memory/service.ts 1192–1313 | 模型提案被应用的入口 | 保存事务和后续调用仍需补读 |
| AssistantRuntime.turn | assistant/runtime.ts 297–364 | 一次用户请求的入口 | 是否允许事项操作的完整链路 |
| KnowledgePipeline.writeAndVerify | knowledge/pipeline.ts 157–192 | 写作、修订、accepted 后发布的控制流程 | 失败如何保持旧正文的关联代码 |
| sourceUnits | retrieval/units.ts 265–422 | 代码与 Markdown 结构单位的选择入口 | 具体解析函数和上下文生成 |

16 题中，11 题前五项与旧实现完全相同；上述 4 题恢复定义；另 1 题“找调用方，不要定义”把定义推到第 1，是退步。**不能把 5 次排序变化全部称作收益。**单独查询 MemoryService.apply 原本就能命中，不算新增效果。

## 五组方案的真实取舍

| 方案 | 本机单次查询中位耗时 | 观察与决定 |
| --- | ---: | --- |
| 修改前 | 3.72 秒 | 对照基线，明确长方法漏召回 |
| 独立符号候选 | 3.78 秒 | 四条长方法问题恢复入口；采用，保留调用方意图缺口 |
| 符号 + RRF 融合 | 3.97 秒 | 未得到稳定收益；图片问题把旧原型代码推到第一，不替换默认融合 |
| 符号 + BGE base | 8.53 秒 | 老版本阅读说明从第 4 到第 2；英语卡问题却把旧计划放到当前进度前，继续可选 |
| 符号 + BGE v2-m3 | 17.08 秒 | 有局部帮助，但同样保留无关界面和旧计划；未证明值得额外等待，继续可选 |

这些时间包括真实开发入口过滤，查询向量已预热；有首次模型加载和本机其他工作影响。精确符号、空结果不会执行重排，因此全题中位数不等于模型一次推理延迟。没有做吞吐量或并发性能基准。

base 与 v2-m3 均由 osdk 固定下载、校验，实际在 CPU 上运行 q8 推理。v2 的快照是 `6f5ff65298512715a1e669753bc754d2bc8f367b`；默认配置仍没有 reranker。实验保持现有 40 个候选、512 token 成对截断、温度 3 和混合公式，因此比较的是**在现有宿主路径里替换模型**，不是两个模型的最优能力。Qwen3、Zoekt、Qdrant 平台未接入；不能把调研写成运行验证。

## 模型判断错，还是宿主把好结果压下去了

进一步复用本轮实际评分，把“只按模型分数排序”和最终排序分开观察，没有新推理或重新调参。模型输入逐字匹配冻结库的单位前缀或向量窗口；同文多处位置保留歧义。结果见[分层诊断](symbol-reranking-diagnostics.json)。

| 现象 | 只看模型评分 | 最终排序 | 改进指向 |
| --- | --- | --- | --- |
| 明确要 runReviewSync 调用方 | v2-m3 的前两项是调用位置，定义第 3 | 定义被推回第 1 | 宿主的定义/融合偏好确实抵消了模型的部分收益，应先表达查找意图 |
| 英语卡是否已经可用 | 两个模型都偏好旧计划 | 旧计划仍在当前进度前 | 不能只怪最终融合；应检查是否把状态问题和正式适用性提供给评分 |
| 长问法中的 MemoryService.apply | 两个模型都把复述问题的调研段排第 1 | 定义被宿主推到第 1 | 模型有“文字吻合但不回答”的问题，不能把这一题的最终成功归功于模型 |
| AssistantRuntime.turn | 两个模型都把方法排第 1 | 第 1 保持；base 的后续结果又混入原型内容 | 方法召回和模型都有作用，宿主后排混合仍需检查 |
| 不存在的长方法问题 | 两个模型仍给泛化的参数说明高位 | 继续返回无关说明 | 需要缺口判断，不是再调几项分数就有答案 |

因此下一步优先拆清定义/调用方/机制的查找目的，以及状态问题的评分输入；对已有模型按正常任务输入做受控比较。Qwen3 可以另做隔离实验，但仅换更大的模型无法解决候选缺失、问题复述和宿主偏好覆盖三个不同问题。

输入窗口也有具体缺口：MemoryService.apply 给两个模型的正文都只到开头的通知标题准备，实际 applyTask/applyMemory 调用在窗口外；前置概念说明虽提到这两个名字，却没有调用逻辑。不能据此断言“给齐实现后模型仍不理解”。后续应该围绕问题保留关键逻辑和必要上下文，再比较评分，而非只增加模型大小。

## 本轮交付验证

### 新文章是否更容易读

抽读了真实模型更新的[材料处理指南](../articles/08e8de8e7788195db049c6fb0184ebc7888d9ec16a991ed19523deb074181035.md)、[检索指南](../articles/c7ef9ab86227b21952d1f3567bf0ff43a7d5e858dd8fb114a0775b4a78d08de5.md)和符号/重排说明。前两篇都有贯穿案例、必要概念、表格、流程图及修改入口：同一项目规则两次导入；一条群消息从实际命中走到助手补查。检索指南也区分首次命中与 Agent 后续调查，明确默认没有启用重排。这些比逐文件列职责更适合建立整体认识。

仍不能判为读者验收通过。材料指南的指纹和去重段较密，部分实现边界占据过多篇幅；重排说明的假想例子没有展示两段候选为什么一段更能回答问题。指南中的案例用于教学，不是已运行的消息场景验收。下一轮要按读者任务补上可观察的前后结果和反例，并把深入实现放到后续章节；不能用本轮独立模型复核代替这项阅读判断。

另一次代码对照抽读发现了复核已接受的实质错误：统一检索说明用 `text: "UnifiedRetrieval"` 演示完整混合路线，但 `exactLookup` 会让它提前返回，根本不进入向量与重排。本轮把这个反例交回真实模型修订。后续复核又发现改写丢掉了“默认”限定，以及把只针对特定 memory 的项目过滤说得过宽；这说明整篇重新输出也会引入新的误读。`KnowledgePipeline.writeAndVerify` 后续应支持对指定章节进行修订，并比较改动前后的含义；复核应尽量一次列出实质问题。增加重复复核次数并不能替代清楚、正确的教学案例。

### 运行检查

实现已通过 `osdk deps --frozen`、全量类型/391 项测试/构建以及修正后的 12 项检索行为检查。真实中文 `retrieval:verify` 已退出 0；`retrieval:index --review` 更新到 12,438 个单位且 pending=0。这与对照冻结库的 12,507 个单位是不同时间的库，不能混用。

实际 `osdk run dev` 的 HTTP 已检查四条长方法问题和一条长句无答案问题，全部 HTTP 200；四条方法首项为对应定义，范围与原件一致。无答案题仍返回无关内容，如实保留在 JSON 的 actualDevHttp。浏览器中同一长问法首项可打开 MemoryService.apply 的 1192–1313 行，上下展开按钮仍在；未改 UI，本轮未重复全套三档视觉检查。

### 真实知识刷新

实际 Traex ACP / `gpt-5.6-sol` 已更新 6 篇读者指南和 10 篇受影响材料说明，最终 16 篇均为 current，生成与独立复核记录见[本轮刷新记录](symbol-knowledge-refresh.json)。正文、工具与运行记录来自真实调用，没有手改模型文章。统一检索的精确查询教学错误也经过模型修订与再次独立复核，最后发布的版本把自然语言混合路线和精确名称提前返回分开解释。

这不是全库重建。旧批次的保守依赖让 3 个修改文件扩展为 10 篇材料说明；其中总览和统一检索曾超时，重试后成功。旧模块汇总仍因未覆盖子材料跳过，历史没有删除。模型刷新从首个调查到最后发布约 75 分钟，其中包含多轮修订，耗时本身也暴露了局部修订和复核覆盖需要改善。中间失败、主动调整并发的中断和最终成功分别保留，不能只看最后一个进程退出码，也不能把排队算作应用成功。

### 最终 dev 入口
