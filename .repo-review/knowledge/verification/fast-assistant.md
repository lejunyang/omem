# 快模型问答与材料准备：本轮实测

日期：2026-10-03。实现切片：`5ea1e2c`。结论先行：**Luna 已通过真实 Traex ACP、原生读取和 omem MCP 回答问题，但 medium 下尚未表现出稳定的明显速度优势。先保留为可选问答配置，不更换默认模型。材料准备的性能缺口则已定位并修复。**

## 比较方式

从 `.repo-review/runtime/data` 做一致副本，同一固定材料、知识、中文 embedding 和工具集用于不同模型。每题独立会话，同题追问保留历史；不写事项、不发外部通知。问题不导入材料库；记忆更新、实现入口等问法与既有调研相近，不是无偏新题集。按实际答案阅读，没有把 schema 接受或引用数量折成“正确率”。

基线为一题，使用 `3ab38e3` 的原生助手。第二组在本轮索引复用、元数据传递、引用定位改造后启动，当时迁移 21 尚未加入该进程；第三组用最终实现与 `low`。因此第三组端到端耗时同时包含数据库优化与推理强度变化，不能把差额全算成 Luna/low 的功劳。比较期间还运行了模型知识更新，服务与机器负载无法控制；不报告可靠速度倍数。

## 确定有效的准备优化

原件库含 698 个 source、1,667 个 revision、38,304 个 fragment。旧查询 `WHERE revision_id=?` 走整表扫描：同库单独测量中，读取当前材料目录耗时约 4.5 秒；迁移 21 增加版本/顺序索引后约 0.2 秒。

在**同一 schema 21、同一材料副本**上单独比较快照构造：

| 方式 | 快照构造时间 | 检索单位 |
| --- | ---: | ---: |
| 全部重新生成源检索投影 | 23.66 秒 | 10,976 |
| 复用授权范围内源投影，按身份重建过期项 | 9.53 秒 | 10,976 |

两边全部检索单位、FTS 内容、向量 head 的摘要一致。复用没有改排序权重或向量身份。完整记录见 [snapshot-equivalence.json](fast-assistant-snapshot.json)。在最终实际 HTTP 问答中，包含目录和文件导出的准备阶段为 8.85 秒。

## 完整逐题结果

同一冻结库的 medium 组已完成，两个模型各回答四个问题和一次连续追问。以下是端到端秒数，包含初始检索、材料准备和 Agent 调查，不是首字时间。

| 问题 | Luna / medium | Sol / medium | Luna / low（最终数据库优化） |
| --- | ---: | ---: | ---: |
| 原文变了，已有记忆会怎样 | 127.4 | 130.8 | 89.7 |
| 新电脑是否自动下载向量模型 | 110.0 | 107.8 | 79.8 |
| 修改记忆实际写入逻辑的入口 | 150.6 | 181.1 | 未测 |
| 连续追问：写入是否同时发飞书 | 161.4 | 130.9 | 未测 |
| 是否已有英语遗忘曲线复习 | 93.3 | 87.2 | 112.4 |

medium 组十次均完成且未降级，引用提交没有被拒绝；这只说明流程走通。Luna 在实现入口题上较快，在后续追问、启动步骤和缺失功能题上较慢。low 的前三项准备时间为 9.5–12.1 秒，但英语复习题整体反而更慢。还不能据这些样本把 Luna 当成稳定的低延迟替代。

完整原始答案、引用、MCP 调用与耗时见 [fast-assistant.json](fast-assistant.json)，包含两次初始基线、十次 medium、三次 low 和一次实际 HTTP 问答。原生文件/命令活动另留在被 Git 忽略的运行 trace，不能仅按报告的 MCP 数量比较全部调查量。所有原始失败保留；medium / low 两次运行都确认材料与知识版本摘要未变。问题文件见 [questions.json](experiments/fast-assistant/questions.json)。

## 回答收益与退步

- **材料更新与个人记忆：** 两个模型都能解释同来源换版、旧记忆失效、后台重核验和同 ID 更新，并给出 80→120 元的例子。优化后的回答仍容易漏掉“后台学习必须开启并有可用 Agent”这个实际使用条件。初始基线的 Sol 回答明确提到了它；因此不能声称这题质量单调提升。
- **新电脑启动：** 都回答不会自动下载向量模型，给出 osdk 下载和校验步骤；Luna 的 medium 回答也区分了 Agent CLI 与向量模型。这题 medium 实测 Luna 110 秒、Sol 108 秒，没有速度优势。
- **代码修改入口：** 两个模型都找到了 `MemoryService.apply → ApplicationRepository.applyMemory → commitApplication`，能指出真实存储位置。但 Luna 约 3,600 字符、Sol 约 4,600 字符，都用较大的伪代码对象讲“小例子”，篇幅和阅读效率仍不足。
- **连续追问：** 两者都能区分“事务中登记飞书待投递记录”和“后台真正调用飞书接口”，说明实际发送还取决于有效目标和 worker。没有把排队当成送达；Luna 将步骤挤成一段，Sol 的编号列表更好读。
- **不存在的英语间隔重复：** 两个模型都明确说尚未接入，没有虚构入口。Luna 区分材料处理和语言复习；Sol 还识别了搜索测试里的示例文本，没有把示例当成功能。
- **格式和定位退步：** Luna/low 的记忆更新回答把段落换行写成字面的 `\n`；启动步骤题还曾把材料 key 错加 `file:` 前缀，工具拒绝后自行改正。本轮保留原输出，没有悄悄修成正常 Markdown。低推理强度尚不能默认推荐。

这组问题覆盖机制、操作、代码修改、连续追问和无答案情形，但仍不是全库质量验收。

## 仓库知识更新与阅读观察

真实 Traex ACP / Sol 完成并独立复核了[提问与检索指南](../articles/c7ef9ab86227b21952d1f3567bf0ff43a7d5e858dd8fb114a0775b4a78d08de5.md)和[自主调查、写作与发布指南](../articles/8a78e7c7634bdf870e9fc4ddcb0670e345ae0a629b2af3c08bd864ef0f1482aa.md)。最终两篇均为 current。后者把教学例子从“发现缺背景”继续写到作者组织正文和 verifier 独立核对因果；两篇都有流程图、概念分工与修改入口，不再用源文件清单代替完整流程。

人工阅读仍看到不足：技术字段和引用较密，部分底层 MCP 细节可以进一步后移；检索指南的速度举例仍引用初始基线，最新完整比较应看本报告，不能把其中的 37 秒当成优化后的准备时间。独立复核通过不代表用户已接受篇幅与解释方式。

此前逐文件刷新完成了 `assistant/acp-model.ts` 与 `assistant/research.ts` 两篇，随后因反复扩写审校边界而主动停止其余任务，转向以上端到端指南。两篇文件说明后来都因本轮 `progress.md` 更新而变为 stale，**并非源码再次改变**；它们把阅读过的进度页也作为了依赖。这暴露了目前“读取集合即依赖”过宽的问题。产物和旧历史保留，未完成的八个文件说明没有算作已更新。

同时也存在另一方向的遗漏：研究者单独读过、但正文未引用且作者/复核者没有再次读取的材料，不会自动进入发布依赖。后续应让研究交接明确哪些发现依赖哪些材料，再区分背景阅读、事实支撑和更新触发条件；不能简单删除所有读取依赖，也不能靠进度页变更触发大面积重写。完整发布、修订、中断和过期原因见[模型刷新记录](fast-assistant-knowledge-refresh.json)。

逐条看失败比一个通过率更有用：

- “不在启动时联网下载”首先找到操作文档，确实能回答准备方法；预期的实现路径在第八名。这是路径排名检查失败，不能直接算作内容完全无用。
- “原始资料修改后怎样重新验证记忆”首先找到页面计划，预期实现未出现。这仍是重要的召回/排序失败；本轮 Agent 能补查到答案，不代表首轮搜索已改好。
- 历史原型的明确路径查询，目标位于第六名；路径导航仍有改善空间。

保留原来的问题和失败结果，没有为本轮修改题集、预期路径或融合权重。

## 本轮选择

保留 Sol 默认，允许在个人配置中把 `assistant.profileId` 设为 `traex-fast` 单独试用 Luna。知识写作、独立复核和后台学习各自保留原来的模型配置；没有自动双模型接力。新增 `osdk run assistant:compare`，之后可以继续用相同问题和原件比较，而不用反复临时搭脚本。

下一步应先改简单问题的调查策略与回答长度：先根据问题决定必须核实什么，已有足够材料时停止重复调查；复杂问题继续沿业务链补读。操作问题先给可执行步骤和必要开关，代码问题先给调用路线和一个最小例子，细节留给追问。简单否定题核实缺口后直接回答，不再为了凑完整性遍历所有材料。它应是 Agent 的写作与调查指导，不是宿主强制限制工具次数。

同步检查关键条件、最小例子和 Markdown 可读性。还需要记录 ACP 启动、工具等待与模型阶段的细分耗时，不能把目前整个 Agent 时间当作纯推理时间。底层检索仍有无关候选，不能用模型最终答出内容遮盖它。
