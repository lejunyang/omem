# 三项检索改造后的统一效果评审

评审时间：2026-10-02。对应实现与模型资产：`68677fa`。详细响应、固定行范围、历史对照与人工判断见 [结构化报告](unified-retrieval.json)；自动检查见 [本轮完整验证](../verification.json)。

**三项基础改造已交付，阅读和检索质量尚未整体验收。** 现在更容易找到已有讲解，也能定位完整方法；但系统仍会把“相关”当成“能回答”，案例开头、旧规划和验证记录会挤掉真正的处理流程。不能仅凭项目检查、引用完整或模型复核就称它已经好用。

## 本轮到底改了什么

| 改造 | 已实现的行为 | 仍然欠缺的效果 |
| --- | --- | --- |
| 让已有讲解参与检索 | 原文之外，已接受的讲解段落、个人记忆和事项进入共享检索；助手保留解释背景，再以固定原件引用定位依据 | 找到文章开头不等于召回问题的处理机制；讲解适用性与原件整份摘要变化仍耦合 |
| 按可理解的结构搜索 | Markdown 保留连贯章节/块；TS/Vue 返回完整函数、方法及必要背景；聊天保留参与者、回复与事件上下文。保存单位仍是固定原件版本 | 某个完整方法可命中，但调用方、下游应用服务和业务背景还不一定一起进入助手上下文 |
| 按提问用途搜索 | 阅读界面、知识调查工具和普通助手共享概念、实现、背景、跟进等用途；固定行引用与人可读引用贯通 | 用途只是一项信号，不能自动区分当前机制、未来计划和测试记录，也不能解决所有多意图问题 |

知识角色已有 Traex 自主工具循环；普通日常助手仍只有一次、最多三个补查问题。两者不能混称为已经具备同等调查能力。本轮没有改变 MemoryService 的事实应用权限，也没有把派生文章变成另一份独立事实。

## 用十个真实问题看效果

在同一隔离库上通过生产 HTTP 搜索，比较新结构检索和旧 Fragment 算法。中文 BGE 索引就绪，12,679 个单位全部建索引；本轮没有启用重排器。问题没有作为原件写入可检索语料。

人工逐条阅读前五项，以“是否足以开始回答或定位”判断。结果为 **5 条可用、4 条部分可用、1 条未命中核心问题**。这只是十题抽查，不是全库通过率，更不是用户验收。

| 用户问题 | 判断 | 实际情况 |
| --- | --- | --- |
| 笔记的规则改了，原来的记忆会不会自动改？ | 部分可用 | 找到当前记忆指南及学习条件，但没把冻结、重核验和更新流程一起召回；第一项是案例开头 |
| 哪里判断消息是交办还是背景？ | 可用，有噪声 | 第二项说明交办、他人承诺和背景的区别，第四项给出治理入口；第一项预算说明无助于回答 |
| 为什么保留旧版本，不能直接覆盖？ | 未命中核心 | 搜到投影说明、旧风险矩阵和实验记录，没有返回当前捕获指南的完整解释 |
| `MemoryService.apply` 在哪里？ | 可用 | 首项完整方法为 1176–1280 行，可打开固定版本；旧算法只返回方法签名片段 |
| 模型写的文章谁检查，没通过怎么办？ | 部分可用 | 第五项才找到独立复核说明，返修循环和保留旧文章没有一起返回 |
| 原文、讲解和个人记忆是什么关系？ | 部分可用 | 找到结果类型与解释背景说明，但对象责任分工没有直接返回，夹杂 UI 和旧设计 |
| 函数后半段怎样预览和展开？ | 部分可用 | 找到固定行范围的传递路径，没返回完整的界面预览与展开调用链 |
| 怎样给 Agent 自主补查的资料工作区？ | 可用 | 首项给出环境准备入口，当前指南补充只读快照和工具说明 |
| 等别人回复时，什么时候提醒我？ | 可用 | 当前指南清楚区分下次检查、期限和稍后提醒，并说明站内通知和显式时间 |
| 中文表述和代码名不一致怎样搜？ | 可用，限于机制解释 | 能理解关键词、标识符与向量的互补及回退；不代表任意概念到代码名的实际映射已经准确 |

HTTP 报告的耗时包含新搜索、旧算法对照和知识搜索等多次请求，不能拿来当单次搜索延迟。此前重排实验与失败记录保存在历史报告，不继承为本轮结论。

## 搜索结果交给真实助手后怎样

在隔离的实际 `dev` 中，用 Traex ACP / `gpt-5.6-sol` 提问三次，全部正常完成，没有降级，也没有创建事项。

1. **“MemoryService.apply 如何把提案变成有效记忆，修改从哪里开始？”** 最新回答选入完整方法，按评估、版本检查、交给应用服务、更新状态和修改入口说明；也明确没有 `applyMemory` 内部材料，不能继续解释底层事务。此前同一长问句的运行却漏掉 `apply` 本体，只找到 `evaluateCore` 和 `commitApplication`。两次都保留，不能由一次成功推断已经稳定解决长问句召回。
2. **“怎样提供 Agent 自主补查工作区？”** 最新回答讲清固定快照、目录、只读检索、MCP 工具、候选提交与宿主发布，也说明候选调用图、时效和可读性限制。此前回答混入“已有解释尚需参与检索”的旧计划，最新回答未再重复。
3. **“等别人回复时什么时候提醒？”** 回答直接说明要指定下次检查时间，它与期限分开；到点站内提醒，不自动联系他人，也不假称已经收到回复。

这说明提供更完整的当前讲解确实有助于理解；但语料更新和模型重跑同时发生，尚不能确定改善来自哪个环节，也不能用三题成功证明整体质量。

## “下一步”具体做什么

### 1. 先让助手拿到能回答问题的完整上下文

例如用户问 `MemoryService.apply` 的完整流程，应同时拿到获准应用的入口、方法本体、下游应用服务和修改位置，而不是多个重复签名片段。

改造 `retrieval/unified.ts`、`retrieval/units.ts` 与 `assistant/runtime.ts`：从长问题中独立保留精确符号线索，再与自然语言召回合并；按固定 SourceAnchor 合并同一操作，给必要调用方和背景留位置。补读依据问题缺口进行，不能只受一次补查限制。用多种自然中文问法和实际点击行段检查，不按题目特殊加分。

### 2. 让相关材料中的“当前答案”排到前面

例如“规则变了，记忆怎么办”应先给冻结、重核验与应用机制，案例只负责解释；“保留旧版本”应先给追溯和固定引用的理由。

在材料正式数据中表达角色、时间和适用范围，再通过共享检索使用这些信息；补足父章节与相邻必要机制，连接概念讲解与实际符号。对应 `retrieval/units.ts`、`retrieval/unified.ts`、`retrieval/port.ts`。不能简单按本仓库目录降权或给某篇实验文章加分，否则换输入就失效。

### 3. 最后串起一条持续使用流程

保存一份约定 → 自然语言提问 → 打开讲解并定位实现 → 修改约定 → 说明旧记忆为何需更新 → 安排明确的下次检查。用这一条流程检查捕获、检索、补读、记忆更新和提醒是否通畅。

为此，需要分开固定历史引用与文章的语义适用性：原件整份摘要变化不应成为唯一适用性判断，但历史引用也不能偷偷跳到新版本。普通助手可复用现有研究工具，持续搜索和补读直到足以回答；缺背景要继续调查或说明未知。对应知识仓储、`knowledge/agent-research.ts` 和 `assistant/runtime.ts`。

这些是本轮评审得出的下一轮优先级，尚未实现。应先完成第一条可用流程，再决定扩大材料覆盖、重排模型或其他学习功能。
