# 代码知识侧表迁移的历史数据保留测试

该测试构造采用单列主键的旧版代码知识侧表，执行迁移后验证快照、符号和边仍可读取，并明确检查 `code_symbols_legacy` 已被删除；当前覆盖的是单快照成功路径。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 保护可追溯的历史代码图

这项测试防止代码知识侧表升级时丢失既有历史。代码图是已捕获材料之上的确定性投影，不另存文件正文；符号从当前版本消失后仍保留在旧快照中，未再次生成的边则转为过期而非删除。因此，迁移验收既要确认数据库行仍在，也要确认旧快照仍能通过图查询读取。参考 [代码图历史保留规则 ↗](../../../apps/server/src/code/store.ts#L1 "说明代码图是捕获材料的派生投影，以及旧快照符号和未再生成的边如何保留。")

测试在独立临时目录中创建真实 `Store`，结束后关闭数据库并删除目录，以隔离不同用例的状态。参考 [临时数据库隔离与清理 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L8 "支持测试创建独立 Store，并在用例结束后关闭数据库和清理临时目录的说明。")

<a id="migration-flow"></a>
## 模拟旧库并执行结构升级

测试手工建立旧版仓库、快照、文件、符号和边表，其中 `symbol_id` 与 `edge_id` 分别是单列主键；随后插入一个快照、一项符号和一条 `defines` 边，再调用 `ensureCodeTables` 触发迁移。参考 [旧版侧表与迁移触发 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L22 "支持旧符号表和边表采用单列主键、插入单快照样本并调用迁移函数的流程，也说明该旧结构无法容纳跨快照重复 ID。")

```mermaid
flowchart LR
  A[旧版单列主键侧表] --> B[执行 ensureCodeTables]
  B --> C[检查历史行]
  C --> D[按旧快照读取代码图]
```

`Store` 创建时还会先打开 SQLite 并执行通用数据库迁移，所以该用例同时依赖基础存储初始化成功。参考 [Store 初始化流程 ↗](../../../apps/server/src/store.ts#L45 "说明测试创建 Store 时会打开 SQLite 并先执行通用数据库迁移。")

<a id="coverage"></a>
## 已验证结果与测试边界

迁移后，用例确认旧快照仍在列表中，符号表和边表各保留一行；它还明确验证 `code_symbols_legacy` 无法再查询，并通过 `graphView` 从旧快照取回原符号和原边。参考 [迁移结果与历史图查询 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L53 "支持旧快照、符号和边得以保留，`code_symbols_legacy` 被删除，以及旧快照图仍能返回原节点和关系。")

当前样本只覆盖单仓库、单快照和成功迁移。由于旧表把符号与边 ID 设为单列主键，迁移前无法插入跨快照重复 ID；若要验证新版复合键，应在迁移完成后写入第二快照的同 ID 记录，或单独针对新版结构测试。若只关注旧数据搬迁，则可增加多个快照、不同 ID 的记录来检查是否全部保留。参考 [旧版侧表与迁移触发 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L22 "支持旧符号表和边表采用单列主键、插入单快照样本并调用迁移函数的流程，也说明该旧结构无法容纳跨快照重复 ID。")
