# 代码知识侧表迁移的历史保留测试

该测试构造旧版单主键代码图表，调用正式迁移入口后验证快照、符号和边均被保留，临时遗留表已清除，并且旧快照仍可通过图查询读取。它覆盖迁移结果与历史可用性，但未覆盖复合主键细节、重复迁移、失败回滚及多快照冲突。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-fixture"></a>
## 问题与测试夹具

测试针对代码知识侧表从“仅以 ID 为主键”的旧结构升级时可能丢失历史数据的问题。每个用例在独立临时目录创建 `Store`，结束后关闭数据库并递归清理目录，从而隔离 SQLite 状态。[临时数据库创建与清理 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L8 "支持测试为每次运行创建隔离 Store，并在用例后关闭数据库、清理临时目录的说明。") `Store` 构造时会创建数据目录、打开 `omem.sqlite` 并执行通用数据库迁移；初始化失败则关闭连接后重新抛错。[Store 的 SQLite 初始化流程 ↗](../../../apps/server/src/store.ts#L45 "说明测试所用 Store 如何打开数据库、执行通用迁移以及处理初始化失败。")

<a id="migration-flow"></a>
## 迁移流程与核心断言

用例直接创建旧形态的仓库、快照、文件、符号与边表，并插入一个相互关联的历史快照、符号和 `defines` 边，随后显式调用 `ensureCodeTables`。[旧版代码图表构造与迁移入口 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L22 "支持用例模拟旧单主键表、插入历史数据并调用 ensureCodeTables 的核心流程。") 迁移后先通过 `listSnapshots` 确认旧快照仍存在，再查询新表行数，断言符号和边各保留一行；同时访问临时表 `code_symbols_legacy` 必须抛错，证明迁移暂存表已被删除。[历史行保留与临时表清除断言 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L53 "支持迁移后快照、符号、边仍存在且符号遗留临时表已删除的结论。") 最后按旧快照调用 `graphView`，确认返回的符号与边仍具原 ID，验证的不只是行数保存，还包括历史图查询可用。[旧快照图查询断言 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L62 "支持迁移后的 graphView 仍能按旧快照返回历史符号和边。")

<a id="relations-and-limits"></a>
## 模块关系与覆盖边界

测试通过 `Store.db` 准备旧数据库状态，并直接依赖代码知识存储模块的建表、快照列表和图视图接口，属于通用 SQLite 存储与代码图派生层之间的集成测试。代码图侧表被设计为同一评审数据库中的附加投影，不保存文件正文，旧解析结果失效时也倾向标记而非删除。[代码知识侧表的定位与历史策略 ↗](../../../apps/server/src/code/store.ts#L1 "解释代码图是同库附加投影、不保存文件正文，并保留旧快照数据而非直接删除的设计背景。") 当前断言没有检查新复合主键的具体列定义、多个快照中相同符号或边 ID 的共存、重复执行迁移的幂等性、事务失败回滚、其他临时表是否清除，以及迁移后新增当前快照的读写行为；因此不能据此推断这些场景均已受保障。
