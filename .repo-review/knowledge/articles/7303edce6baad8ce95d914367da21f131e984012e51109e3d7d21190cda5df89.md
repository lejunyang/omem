# 代码侧表历史保留迁移测试

该测试模拟旧版单主键符号与图边表，验证迁移到支持快照历史的新结构时不会丢失旧快照、符号或关系，并清理临时遗留表。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="legacy-fixture"></a>
## 旧结构与迁移背景

测试手工建立迁移前数据库：仓库、快照和文件表包含一份旧快照，符号与图边分别仅以 symbol_id、edge_id 为主键，同时记录所属 snapshot。该夹具刻意复现“一种标识只能有一行”的旧结构，为迁移到复合快照结构提供输入。[迁移前单主键数据库夹具 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L22 "支持旧符号和图边结构以单独 ID 为主键并携带 snapshot 字段的背景说明。")

随后直接调用 `ensureCodeTables`，因此可以确认被测迁移入口；不过材料没有展示该函数实现，不能据此断言事务、锁策略或每个中间 SQL 步骤。

<a id="preservation"></a>
## 保留历史并移除临时表

迁移后，旧快照仍可由 `listSnapshots` 列出，符号与边的计数各为一；临时 `code_symbols_legacy` 表应已删除。更关键的是，以旧 snapshotId 调用 `graphView` 仍返回原符号和图边，说明验证目标不仅是行数不变，还包括历史查询可用。[迁移后历史查询断言 ↗](../../../apps/server/tests/code-knowledge-migration.test.ts#L50 "支持旧行未丢失、临时表已清理且旧快照图仍可读取的论断。")

该测试只包含单仓库、单快照、单符号和单边，未覆盖重复 ID 跨快照、空字段、半迁移数据库、迁移失败回滚、索引与外键是否正确，也未验证迁移后继续同步新快照。
