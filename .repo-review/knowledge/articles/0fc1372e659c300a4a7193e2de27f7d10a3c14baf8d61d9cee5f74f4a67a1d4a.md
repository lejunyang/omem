# 改一条完整功能链：让搜索结果说清所属章节

以顶部搜索结果已有的章节路径为贯穿案例，从开发启动、仓库材料恢复、Vue 输入、搜索 API、统一检索和结构投影一路定位到结果卡；再按显示、合同和章节语义三种改动范围选择入口，并区分索引补建、模型小样例、仓库 HTTP 报告与真实页面阅读验收。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先看见现状，再选择一个小改动

第一次修改 omem，可以从一个用户立刻看得到、又能穿过前后端的小行为开始：在顶部搜索一个已知 Markdown 主题或代码方法，结果卡会先显示“原始材料 / 讲解”等种类，再显示由 `headingPath` 连接成的章节或符号路径；原始材料还带固定行范围。**这项能力当前已经存在**，不是待从零实现的功能。参考 [结果卡的章节提示 ↗](../../../apps/web/src/App.vue#L717 "支持顶部搜索结果显示种类、headingPath、固定行范围与阅读动作。")

本页的贯穿练习是：把这段元信息改得更清楚，例如增加“所属章节”标签、调整分隔符，或为空路径提供诚实提示。这只是教学示例，不表示仓库已有缺陷或改动已经完成。完成后，你应能回答三个问题：显示文字在哪里改，章节路径在哪里产生，怎样在真实页面确认结果。

## 启动同一套个人开发环境

运行 `osdk install`、`osdk deps --frozen`、`osdk run dev`，再打开终端打印的 Web 地址。默认 API/Web 端口是 4317/5173，占用时会选择空闲端口；开发模式载入仓库材料和已发布知识，但不会在启动时生成整库 Wiki。参考 [开发启动方式 ↗](../../../docs/reader-first/operations.md#L3 "说明 osdk 启动命令、动态端口、开发知识接入及启动不自动生成整库知识。")

入口脚本把当前目录声明为仓库根并启用 personal 模式。编排器选择端口，启动带 watch 的服务端和 Vite，健康检查成功后才打印真实地址；Vite 的 `/api` 代理指向同次选出的 API 端口。参考 [个人开发入口 ↗](../../../scripts/dev.ts#L1 "证明入口设置仓库根和 personal 模式后载入共用编排器。") [开发进程启动 ↗](../../../scripts/dev-review.ts#L81 "支持端口选择以及服务端和 Vite 子进程的启动方式。") [健康检查与实际地址 ↗](../../../scripts/dev-review.ts#L131 "支持等待 API 健康后打印实际 API、Web 与代理端口。")

服务端发现仓库根后运行开发导入器，再把同一个检索服务经开发可见性适配交给知识路由和助手。参考 [服务端开发装配 ↗](../../../apps/server/src/app.ts#L67 "说明开发导入器、共享检索服务及其在知识路由和助手中的装配。") 导入器从已发布文章收集固定依赖，必要时从隔离 review 数据库补入历史原件，随后恢复当前材料和文章；它操作传入的个人 Store，并明确不替换个人数据库。参考 [个人数据库边界 ↗](../../../apps/server/src/review/development.ts#L1 "明确开发输入加入个人 Store，但不会替换个人数据库。") [知识与历史材料恢复 ↗](../../../apps/server/src/review/development.ts#L37 "支持读取已发布文章、补入固定历史依赖并恢复当前材料和文章。") 开发适配只隐藏已移除或旧别名副本，内容排名仍由共享检索实现负责。参考 [开发可见性适配 ↗](../../../apps/server/src/review/development.ts#L15 "证明开发适配只处理仓库材料可见性，内容排名仍走共享检索。")

## 从输入框跟到结果卡

用“搜索结果属于哪一节”反向追踪，主链如下：

```mermaid
flowchart LR
  A[顶部搜索输入] --> B[GET /api/search]
  B --> C[RetrievalPort.search]
  C --> D[UnifiedRetrieval 召回与整理]
  D --> E[RetrievalHit.headingPath]
  E --> F[OmPanel 结果卡]
```
参考 [搜索输入防抖 ↗](../../../apps/web/src/App.vue#L189 "证明输入、用途和角色变化会取消旧请求、递增版本并进行 250ms 防抖。") [搜索 API 参数与返回 ↗](../../../apps/server/src/app.ts#L313 "支持搜索参数校验、查询长度和数量限制，以及统一检索结果的直接返回。") [结果字段传递 ↗](../../../apps/server/src/retrieval/unified.ts#L602 "证明最终结果将检索单位的 context 与 headingPath 写入 RetrievalHit。")

输入、用途或角色变化时，页面会取消旧请求、递增版本并等待 250ms；请求返回后也只有版本仍匹配才写回结果，避免慢响应覆盖新查询。参考 [搜索输入防抖 ↗](../../../apps/web/src/App.vue#L189 "证明输入、用途和角色变化会取消旧请求、递增版本并进行 250ms 防抖。") [搜索请求竞态处理 ↗](../../../apps/web/src/App.vue#L376 "支持 AbortController 与版本号共同避免过期响应覆盖新结果。") API helper 给相对路径统一添加 `/api`，所以组件请求的 `/search` 实际到达 `/api/search`。参考 [API 前缀封装 ↗](../../../apps/web/src/api.ts#L264 "证明前端 helper 给相对路径添加 /api 并统一处理请求失败。") 服务端校验 purpose、role、effectiveAt，把查询截到 300 字并限制最多 30 条；统一检索端口可用时直接返回结果数组。参考 [搜索 API 参数与返回 ↗](../../../apps/server/src/app.ts#L313 "支持搜索参数校验、查询长度和数量限制，以及统一检索结果的直接返回。")

统一检索先同步结构投影，再组合词法、明确代码符号和可选语义候选；可选交叉编码器只重排候选池，并保留明确符号候选。参考 [统一候选召回 ↗](../../../apps/server/src/retrieval/unified.ts#L413 "说明词法、符号、语义与可选交叉编码重排如何形成候选。") `finish()` 再按查询用途、定义匹配、材料适用性与知识复核状态调整优先级，并按 owner 和正文指纹控制重复。参考 [最终结果整理 ↗](../../../apps/server/src/retrieval/unified.ts#L515 "支持按用途、定义、适用性和复核状态调整优先级并控制重复。") `RetrievalHit` 把 `headingPath`（可显示的结构路径）与 `context`（供检索使用的更宽背景）定义为不同字段，显示章节时不要混用。参考 [检索结果合同 ↗](../../../apps/server/src/retrieval/port.ts#L43 "证明 headingPath、context、固定 target 与 references 是不同的正式字段。")

<a id="change"></a>
## 按改动含义选择落点

章节路径在投影阶段产生。Markdown 解析器维护标题栈，让正文块携带所在章节，并避免把代码围栏里的 `#` 当标题；代码材料则用 AST 符号及父符号限定名形成路径，未被符号覆盖的顶层内容归入“模块定义与初始化”。参考 [Markdown 标题路径 ↗](../../../apps/server/src/retrieval/units.ts#L31 "支持 Markdown 正文块携带标题栈，并保持表格、列表和代码块结构连贯。") [代码符号路径 ↗](../../../apps/server/src/retrieval/units.ts#L90 "支持代码按 AST 操作及父符号限定名形成 headingPath，并处理顶层内容。") 原始材料单位把路径写入检索 `context` 和独立的 `headingPath`，同时保留固定行范围；最终结果只是复制该字段，不会在返回前重新猜章节。参考 [原件检索单位 ↗](../../../apps/server/src/retrieval/units.ts#L363 "证明原件 passage 的路径写入 context 和 headingPath，并保留固定来源锚点。") [章节路径原样输出 ↗](../../../apps/server/src/retrieval/unified.ts#L602 "证明最终结果直接复制检索单位的 headingPath，而非在输出时重新推断。")

| 想改变什么 | 首要落点 | 同步考虑 |
| --- | --- | --- |
| “所属章节”的文案、分隔符、空态或顺序 | `apps/web/src/App.vue` 的结果卡模板 | 搜索专用样式与三档宽度 |
| 新增一个跨 API 字段 | `retrieval/port.ts` 的 `RetrievalHit` | 投影或 `finish()` 赋值、前端消费与测试 |
| 改“什么算章节” | `retrieval/units.ts` 的 Markdown、代码或知识投影 | 提升 `UNIT_VERSION`，重建结构单位并更新行为断言 |

当前模板直接消费 `RetrievalHit`，用 `OmPanel` 展示路径、行号、摘要和阅读动作。参考 [结果卡的章节提示 ↗](../../../apps/web/src/App.vue#L717 "支持顶部搜索结果显示种类、headingPath、固定行范围与阅读动作。") [检索结果合同 ↗](../../../apps/server/src/retrieval/port.ts#L43 "证明 headingPath、context、固定 target 与 references 是不同的正式字段。") 因而本例若只增加“所属章节”标签，应停在模板层；只有章节语义真的变化，才进入检索单位。`UNIT_VERSION` 参与单位 ID，结构语义变化时应同步提升版本。参考 [检索单位版本身份 ↗](../../../apps/server/src/retrieval/units.ts#L16 "说明 UNIT_VERSION 与结构字段，支持结构语义变化时提升投影版本。")

## 复用组件，并在真实页面看间距

结果卡已经复用 `@omem/ui` 的 `OmPanel`。共享组件负责卡片边框、圆角、桌面 24px 内边距、标题下方 16px 间距，以及手机 20px/16px 内边距；它还提供可选的 `actions` slot，使用该 slot 时 footer 是 20px 上距、12px 按钮间距。参考 [共享面板结构与间距 ↗](../../../packages/ui/src/components/OmPanel.vue#L4 "支持 OmPanel 的边框、内边距、标题间距、可选 actions footer 间距和移动端内边距。")

**当前搜索结果卡没有使用这个 actions slot。** 两个按钮位于默认 slot 内的 `.search-actions`，其 16px 上距和 8px 间距由 `App.vue` 自己控制。若要让它采用共享 footer 的间距，需要把按钮移入 `#actions`；这是可选重构，不是现状描述。参考 [搜索卡局部动作区 ↗](../../../apps/web/src/App.vue#L735 "证明结果按钮位于默认 slot 的 search-actions 容器，且局部样式使用 16px 上距和 8px 间距。") 视觉调整仍应沿用现有黑白灰 token、可见文字状态和既定间距节奏，通用行为才进入共享组件。参考 [界面设计约束 ↗](../../../.agents/skills/omem-design/SKILL.md#L8 "说明复用 packages/ui、沿用黑白灰 token、检查三档宽度与真实页面。")

页面最大宽度为 950px；相邻结果卡由 `.stack` 留出 22px；`.search-section` 使用 13px 次要文字并留 12px 下距。700px 以下页面改为 20px 水平内边距。参考 [页面宽度 ↗](../../../apps/web/src/styles.css#L99 "支持页面最大宽度 950px 及桌面内边距。") [结果卡与章节间距 ↗](../../../apps/web/src/styles.css#L167 "支持结果卡 22px 间距和章节元信息的字号、颜色与下边距。") [移动页面留白 ↗](../../../apps/web/src/styles.css#L213 "支持 700px 以下页面使用 20px 水平内边距。") 因此本例优先调整现有模板与 `.search-section`，同时留意局部 `.search-actions`，保持标题、路径、行号和按钮的层级。

启动后，用能命中已知标题或方法的查询确认路径出现，再运行 `osdk run browser`，并在 1440、768、390px 查看长路径换行、横向溢出和 loading/error/empty 状态。现有搜索浏览器检查覆盖加载、空态、失败和过期请求；三档视口脚本当前检查的是知识阅读页，所以顶部结果卡仍需在本次改动中实际查看。参考 [页面检查要求 ↗](../../../docs/reader-first/operations.md#L17 "说明 UI 要运行浏览器和视口脚本检查实际页面，机器报告不能代替阅读验收。") [三档视口脚本 ↗](../../../scripts/code-wiki-viewport.ts#L168 "证明现有脚本在 1440、768、390px 检查知识阅读页及横向溢出。") [搜索浏览器状态 ↗](../../../scripts/browser-smoke.ts#L299 "证明现有浏览器检查覆盖搜索加载、空态、失败和过期请求。")

<a id="verify"></a>
## 把“检查通过”和“读者可用”分开

实现完成后，先运行 `osdk deps --frozen` 与 `osdk run check`；`check` 依次执行类型检查、测试和构建。参考 [项目检查任务 ↗](../../../osdk.toml#L41 "支持 check 由类型检查、测试和构建组成，并给出本地模型检查入口。") 然后按改动范围分清下面几类检索动作：

1. **补建仓库索引**：章节投影、分类或检索单位变化后，运行 `osdk run retrieval:index --review`。脚本先同步隔离 review 数据、已发布知识和代码，再分批补齐检索单位；它不发 HTTP 请求。参考 [检索维护任务 ↗](../../../osdk.toml#L91 "支持 retrieval:index 的 review 标志和 review:verify 的 full 标志。") [仓库索引补建实现 ↗](../../../scripts/retrieval-index.ts#L13 "证明 review 索引任务同步仓库数据后分批建立检索单位，不执行 HTTP 搜索。")
2. **本地模型小样例**：`osdk run retrieval:verify` 在临时 Store 中写入四条合成材料，加载真实本地 embedding，直接调用 `UnifiedRetrieval` 检查语义命中、可见范围和无答案标识符；它不是仓库 HTTP 验收。参考 [本地模型检索小样例 ↗](../../../scripts/live-retrieval-smoke.ts#L11 "证明 retrieval:verify 使用临时 Store、四条合成材料和直接检索调用，而非仓库 HTTP。")
3. **仓库自动报告**：`osdk run review:verify --full` 才会运行依赖、完整项目检查和上述模型小样例，并在恢复仓库材料与知识后启动 review app，请求 `/api/review/search`，记录公开问题的 top-5。报告不继承旧结果，而且 top-5 命中不等于回答正确。参考 [完整验证模式 ↗](../../../scripts/review-verify.ts#L47 "证明 full 模式才执行依赖、项目和本地模型小样例，且不继承旧结果。") [仓库 HTTP 检索报告 ↗](../../../scripts/review-verify.ts#L78 "证明验证脚本启动 review app 的 HTTP 搜索、记录 top-5，并声明命中不代表回答正确。")
4. **人工页面验收**：另外在真实 dev 页面用贯穿案例搜索，确认用户能分辨结果种类、所属章节和固定行号；必要时单独检查真实 HTTP 返回。再在三档宽度观察层级与换行。DOM 中出现字符串只能证明元素存在，不能代替实际阅读。参考 [界面设计约束 ↗](../../../.agents/skills/omem-design/SKILL.md#L8 "说明复用 packages/ui、沿用黑白灰 token、检查三档宽度与真实页面。") [页面检查要求 ↗](../../../docs/reader-first/operations.md#L17 "说明 UI 要运行浏览器和视口脚本检查实际页面，机器报告不能代替阅读验收。") [检索修改验收流程 ↗](../../../AGENTS.md#L37 "说明检索改动应分别运行模型检查、补建索引、检查真实 HTTP 结果并生成本轮报告。")

实现与页面验证完成后，运行 `osdk run review:guides contributing` 更新本指南。脚本按页面 key 选择目标，经知识流水线生成、复核和发布；失败会记为 `failed`，不能把脚本开始或排队当成成功。参考 [读者指南流水线 ↗](../../../scripts/review-guides.ts#L17 "说明按页面 key 选择目标，经 KnowledgePipeline 处理并记录 reviewed 或 failed 状态。")

真正的阅读验收是：另一位第一次接触项目的开发者能从结果卡找到 App、API、检索单位与相关断言，解释 `headingPath` 和 `context` 的区别，并独立完成同类小改动。当前跨文件业务链与基础排序仍有限，自动检查和独立模型复核都不能替代这个判断。参考 [当前阅读与检索边界 ↗](../../../docs/reader-first/progress.md#L39 "支持跨文件业务链与排序仍有限，以及独立复核不等于用户验收。")
