# 改一条完整功能链：让搜索结果说清所在位置

以“把搜索结果中的章节或符号提示写清楚”为小改动，带第一次参与 omem 的开发者走过开发启动、仓库材料导入、顶部搜索、结构化检索、Vue 展示、组件复用、真实页面验收与知识更新。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="start-from-visible-result"></a>
## 从一个可见的小改动开始

假设你想把结果卡中的“原始材料 · 运行与维护 / 启动 · 第 5–7 行”改得更明确，例如“原始材料 · **所在章节：运行与维护 / 启动** · 第 5–7 行”。这是本文的教学示例，不是既定产品需求。

先注意一个关键事实：omem 已经在搜索结果中显示 `headingPath`，并按结果类型提供“阅读讲解”“查看事项”“查看原始依据”或“阅读原文”。因此这次工作不是从零增加“章节”字段，而是理解现有数据从哪里来，再决定只改文案，还是修正结构提取。参考 [搜索结果现有呈现 ↗](../../../apps/web/src/App.vue#L682 "支持结果卡已经展示类型、标题或符号路径、固定行号，并提供继续阅读动作。")

<a id="boot-and-import"></a>
## 启动开发环境，并理解材料怎样进入搜索

在仓库根目录依次运行：

```bash
osdk install
osdk deps --frozen
osdk run dev
```

打开终端实际打印的 Web 地址；默认 API 与 Web 端口是 4317 和 5173，冲突时会另选端口。开发模式保留个人库，并接入当前仓库材料和已发布知识，但**不会因为源码变化自动重写整库 Wiki**。参考 [开发启动方式 ↗](../../../docs/reader-first/operations.md#L3 "支持标准启动命令、端口行为、个人数据保留以及启动不自动生成 Wiki。")

`osdk run dev` 最终执行 Bun 脚本：它把当前仓库写入 `OMEM_REPO_ROOT`，以 personal 模式启动编排器；编排器启动带 watch 的 API 和 Vite，等健康端点可用后才打印地址。参考 [个人开发入口 ↗](../../../scripts/dev.ts#L1 "说明 dev 脚本怎样设置仓库根和 personal 模式，并复用开发编排器。") [开发进程编排 ↗](../../../scripts/dev-review.ts#L81 "说明端口选择、API watch、Vite 启动、健康检查和实际地址输出。")

服务端看到 `OMEM_REPO_ROOT` 后恢复开发知识，并让知识 API、助手和顶部搜索使用同一个开发检索入口。仓库适配器优先枚举 Git 已跟踪及未忽略文件，排除运行产物、依赖和私有配置，再把文本或受支持图片保存为稳定的 `omem:<path>` 来源。也就是说，dev 扫描负责**捕获输入**，真正参与搜索的仍是 Source/Revision 及其检索投影。参考 [开发知识装配 ↗](../../../apps/server/src/app.ts#L60 "支持服务端在开发模式导入仓库知识，并让知识 API、助手和搜索复用开发检索。") [仓库材料捕获 ↗](../../../apps/server/src/review/materials.ts#L16 "解释 Git 文件枚举、私有和派生目录排除、稳定来源键及文本图片捕获。")

<a id="trace-search"></a>
## 沿一次搜索穿过 UI、API 与检索

启动后，可在顶部输入一段仓库中存在的短语，例如“启动不会自动生成整库知识”，并选择“定位实现”或“综合查找”。输入框同时监听查询和用途：变化后等待 250 ms，取消旧请求，并用版本号阻止迟到响应覆盖新结果。参考 [搜索防抖与取消 ↗](../../../apps/web/src/App.vue#L186 "支持查询和用途变化后的防抖、取消旧请求及版本保护行为。")

```mermaid
flowchart LR
  A[顶部搜索框] --> B[App.vue 防抖与取消]
  B --> C[api() 添加 /api 前缀]
  C --> D[GET /api/search]
  D --> E[共享 RetrievalPort]
  E --> F[RetrievalHit]
  F --> G[结果卡与固定原文]
```

客户端请求写成相对的 `/search`，公共 `api()` 将它变成 `/api/search`，附加可选令牌并把非 2xx 响应转成错误。Fastify 路由校验五种用途、限制查询与结果数量，然后优先调用共享的 `assistantRetrieval.search`。参考 [前端 API 封装 ↗](../../../apps/web/src/api.ts#L260 "说明相对搜索路径如何获得 /api 前缀、认证头和错误处理。") [搜索 HTTP 路由 ↗](../../../apps/server/src/app.ts#L303 "支持用途校验、查询限制和共享 assistantRetrieval 调用。")

返回值不是只有一段摘要；`RetrievalHit` 同时携带正文、上下文、`headingPath`、固定目标、原始引用和来源信息。这个合同供读者界面、助手与 Agent 共用，所以新增跨层字段会影响的不只是顶部搜索。参考 [统一检索结果合同 ↗](../../../apps/server/src/retrieval/port.ts#L1 "支持 RetrievalHit 面向读者、助手和 Agent 共用，并携带 headingPath、固定目标与引用。")

<a id="where-heading-comes-from"></a>
## 章节与符号路径从哪里来

“所在位置”来自材料结构，而不是由前端根据目录名猜测：

| 材料 | 路径来源 | 可观察结果 |
| --- | --- | --- |
| Markdown | `marked` 的真实标题栈；列表、表格、代码围栏保持为完整块 | 如“运行与维护 / 启动” |
| TypeScript / Vue | AST 符号及其父符号的 `qualifiedName` | 如“UnifiedRetrieval / finish” |
| 无法提取符号的代码 | 空路径；未被符号覆盖的顶层内容另标“模块定义与初始化” | UI 应诚实处理空值 |

Markdown 块保存自己的起止行和标题链；代码块优先保留完整函数或方法，局部变量不会取代所属操作。参考 [Markdown 章节投影 ↗](../../../apps/server/src/retrieval/units.ts#L22 "说明 Markdown 块如何保留标题栈、块结构和真实行范围。") [代码符号投影 ↗](../../../apps/server/src/retrieval/units.ts#L68 "说明代码如何按完整操作和父符号生成路径，以及无法解析时的空路径行为。")

生成检索单元时，这条路径既进入可搜索的 `context`，也原样写入返回字段，并与固定行范围一起保存。词面召回会用路径参与相关性判断；最后的用途偏好只调整不同结果类型的优先级，去重并选择摘要后仍原样返回路径。因此“定位实现”不是另一套索引，“所在章节”也不是展示层临时拼出的语义分类。参考 [检索单元上下文 ↗](../../../apps/server/src/retrieval/units.ts#L336 "支持标题或符号路径同时进入搜索上下文和返回字段，并绑定固定目标。") [用途偏好与结果输出 ↗](../../../apps/server/src/retrieval/unified.ts#L423 "说明用途如何调整优先级，以及去重、摘要选择后 headingPath 仍原样输出。")

<a id="choose-change-layer"></a>
## 把改动放在最小而正确的一层

回到贯穿示例，先按症状选择落点：

| 你看到的问题 | 修改位置 | 判断 |
| --- | --- | --- |
| 路径正确，只是读者看不懂 | `apps/web/src/App.vue` 的结果元信息；必要时调整 `styles.css` | 本例首选，只改“所在章节/所在符号/位置”等呈现 |
| Markdown 标题链或代码符号本身错误 | `apps/server/src/retrieval/units.ts` | 修正结构投影，并保留固定行范围 |
| 确实需要所有消费者共享的新语义 | `retrieval/port.ts` | 才扩展 `RetrievalHit`；不要为已有 `headingPath` 再造重复字段 |
| 希望改变“搜到什么、排在何处” | `retrieval/unified.ts` | 这是检索行为变化，会影响搜索、助手和 Agent |

当前结果卡已经在类型后拼接 `headingPath.join(" / ")` 和源码行号，所以只把提示改清楚时，无需触碰 API 或排序。参考 [章节提示模板 ↗](../../../apps/web/src/App.vue#L713 "直接支持当前页面拼接结果类型、headingPath 和固定行号的位置。")

如果路径为空，不要从文件夹名补一个貌似合理的章节；空路径是代码解析无法得到符号时的合法结果。可以隐藏分隔符，或显示不误导的“未识别结构”。如果要按 Markdown 写“所在章节”、按代码写“所在符号”，这是基于现有类型和路径语义的实现选择，应作为本次变更明确评审，而不是冒充已有需求。

<a id="reuse-ui"></a>
## 复用组件，并在真实页面检查间距

搜索页已经复用 `OmPanel`、`OmButton`、`OmMarkdown` 和 `OmEmpty`。网络和搜索状态继续留在 `apps/web`；一行局部元信息可以留在页面中，只有跨页面复用的通用交互才下沉到 `packages/ui`。参考 [搜索页组件复用 ↗](../../../apps/web/src/App.vue#L1 "支持当前页面从 @omem/ui 引入并复用公共阅读与交互组件。") [公共组件边界 ↗](../../../.agents/skills/omem-design/SKILL.md#L8 "解释业务网络和状态留在 apps/web、通用组件下沉 packages/ui 的边界。")

保持黑白灰阅读样式，不为章节提示增加品牌色。沿用 4/8/12/16/24/32/48 px 的间距节奏；关键文字不能只靠低对比小字表达。如果把路径做成可点击导航，应使用真实按钮或公共组件，保留键盘焦点和至少 44×44 px 的普通点击区域。参考 [视觉与交互规范 ↗](../../../design.md#L18 "支持中性色、间距节奏、公共组件和可访问交互要求。")

长标题最容易暴露问题。请在 1440、768、390 px 下实际看路径换行、卡片间距和根页面横向滚动；静态元素存在、类型检查通过，都不能替代这一步。参考 [响应式验收要求 ↗](../../../design.md#L44 "支持三种目标宽度、无横向滚动、焦点和实际查看页面的要求。")

<a id="verify-and-refresh"></a>
## 验证行为，再更新相关知识

完成改动后，把“通过”分成四层：

1. **代码合同**：运行 `osdk deps --frozen` 与 `osdk run check`；项目的 `check` 实际包含类型检查、测试和构建。参考 [项目检查任务 ↗](../../../osdk.toml#L30 "支持 check 由类型检查、测试和构建组成。")
2. **真实页面**：用 `osdk run dev` 搜索能命中 Markdown 和代码的真实问题，确认提示、固定行范围与“阅读原文”一致；再运行 `osdk run browser` 并查看三种宽度的截图。现有浏览器流程覆盖加载、空态、失败和旧请求取消，新提示仍应在本次变更中实际观察。参考 [真实页面检查 ↗](../../../docs/reader-first/operations.md#L15 "支持 UI、检索和完整报告各自的运行入口，并强调机器报告不替代阅读验收。") [搜索异步浏览器流程 ↗](../../../scripts/browser-smoke.ts#L299 "说明现有浏览器检查覆盖加载、空态、失败和迟到请求，不等同于新提示的视觉验收。")
3. **检索效果**：若只改文案，不要宣称相关性提升；若修改 `units.ts` 或 `unified.ts`，再运行 `osdk run retrieval:verify`、`osdk run retrieval:index --review`，用真实 HTTP 中文问题抽查，并执行 `osdk run review:verify --full`。当前记录仍明确指出旧计划可能排在实现前，Agent 补查成功不能替代基础检索质量。参考 [检索验收顺序 ↗](../../../docs/reader-first/progress.md#L56 "支持检索变更后运行索引、真实问题、完整报告和三种宽度检查。") [当前检索限制 ↗](../../../docs/reader-first/progress.md#L43 "支持旧计划可能排在实现前，以及 Agent 调查不能掩盖基础检索问题。")
4. **读者知识**：实现检查通过后，单独运行 `osdk run review:guides contributing` 更新这篇指南；材料说明则使用 `osdk run review:generate <路径> --modules`。生成成功只表示产物通过流程，最终还要由读者确认：能否从界面现象找到正确层、完成修改并看懂结果。参考 [指南局部生成任务 ↗](../../../osdk.toml#L137 "支持 contributing 是 review:guides 的合法局部目标。") [知识生成与阅读验收 ↗](../../../docs/reader-first/operations.md#L9 "区分材料说明、读者指南、运行产物和发布文章，并强调生成流程不替代阅读判断。")

这样，一个很小的章节提示改动就形成了完整闭环：可见问题决定入口，结构合同决定修改层，真实页面确认体验，知识更新记录新的使用方式。
