# 改一条完整功能链：让搜索结果说明所属章节

以顶部搜索结果中的章节提示为贯穿例子，从开发环境、前端请求、搜索 API、章节推导到页面展示，说明第一次修改 omem 时如何定位改动边界、补充测试，并在真实页面中确认结果。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先看清要改变的用户体验

假设读者搜索“消息 后台”，希望每条结果不仅显示命中的原文，还明确告诉他“这段内容属于哪一节”。当前页面已经具备这一体验：结果面板先显示材料标题，再显示章节标题与起止行，随后才是原文摘要和“查看固定片段”的入口。你可以把第一次改动限定为调整这条章节提示的文案、排版或显示条件，而不必重构整套搜索。参考 [搜索结果章节展示 ↗](../../../apps/web/src/App.vue#L530 "支持当前结果面板会显示章节标题、行范围、摘要和固定片段入口。")

在代码中，搜索结果的 `section` 已声明为可空对象，包含标题和起止行；实际模板位于顶部搜索结果的 `OmPanel` 内。若需求只是把“章节标题 · 第 10–20 行”改得更易读，主要入口就是这里。参考 [搜索结果数据合同 ↗](../../../apps/web/src/App.vue#L84 "支持前端结果类型已经包含可空的章节标题和行范围。")

<a id="start"></a>
## 启动开发环境并理解材料从哪里来

先在仓库根目录运行 `osdk install`、`osdk deps --frozen` 和 `osdk run dev`。开发入口会把当前目录设为仓库根，并以个人模式加载共享启动器；启动器分别运行带监听的服务端和 Vite，默认使用 API 4317、Web 5173，端口冲突时会选择空闲端口，因此应以终端打印的实际地址为准。参考 [开发运行方式 ↗](../../../docs/reader-first/operations.md#L3 "说明 osdk 启动命令、默认端口、开发材料接入及不会自动生成整库知识。") [开发进程启动器 ↗](../../../scripts/dev-review.ts#L81 "支持个人模式下 API、Vite、动态端口和子进程的启动方式。")

这不是一套只展示静态文档的演示环境。服务端检测到仓库根后，会导入当前仓库材料、已发布知识以及固定引用仍需要的历史材料，再用仓库检索策略包装原有个人检索；实时文件最后导入，避免历史版本覆盖当前内容。启动本身不会自动重新生成整库知识。参考 [开发知识导入 ↗](../../../apps/server/src/knowledge/development.ts#L40 "解释当前材料、发布知识、引用依赖的历史材料及实时文件的恢复顺序。") [仓库检索接入 ↗](../../../apps/server/src/app.ts#L61 "支持服务端在开发模式导入仓库知识，并让知识 API 与助手使用包装后的共享检索。")

<a id="request-flow"></a>
## 从输入框追到搜索 API

用户提交搜索后，`App.vue` 会递增 `searchVersion`，把查询编码后交给通用 `api()`；只有最后一次请求的版本仍匹配时才更新结果，因此较慢的旧响应不会盖掉新搜索。请求失败会写入页面已有的错误状态。通用请求函数统一补上 `/api` 前缀、访问令牌和 JSON 处理，所以这里传入的 `/search?q=...` 最终对应 `GET /api/search`。参考 [前端搜索竞态处理 ↗](../../../apps/web/src/App.vue#L249 "支持查询编码、最后请求生效和错误状态写入的行为。") [通用 API 请求 ↗](../../../apps/web/src/api.ts#L245 "支持统一添加 API 前缀、认证头、JSON 请求和错误处理。")

```mermaid
flowchart LR
  A[顶部搜索输入] --> B[App.vue search]
  B --> C[GET /api/search]
  C --> D[共享检索服务]
  D --> E[计算命中所属章节]
  E --> F[结果面板显示章节与原文]
```

服务端会把查询限制在 300 字符内，最多取得 30 个命中；每个命中再结合固定 fragment 找到材料标题、版本、摘要、召回信息和章节信息，最后返回前端。参考 [搜索路由响应 ↗](../../../apps/server/src/app.ts#L273 "支持查询长度、结果上限、共享检索调用及章节字段的响应组装。")

<a id="section-projection"></a>
## 章节信息如何从原文中推导

`section` 不是额外维护的一份事实，而是命中原文的**阅读结构投影**。服务端先把 fragment 映射回完整材料，找出它在原文中的起始行，再选择覆盖该行且范围最小的章节。Markdown 通过标题层级形成章节范围；TypeScript、JavaScript、TSX、Vue 等代码则复用解析器得到符号范围；没有可识别结构时，整份材料作为一个 document。参考 [材料阅读结构 ↗](../../../apps/server/src/knowledge/structure.ts#L8 "解释 Markdown 标题、代码符号和整篇文档如何形成可供章节投影使用的结构。")

章节标题本身也属于内容。材料不存在、fragment 无法定位，或同一材料包含当前调用者不可见的 fragment 时，`evidenceSection` 会返回 `null`，避免章节标签泄露隐藏内容。前端因此必须保留 `v-if="r.section"` 一类的空值处理，不能假定每条结果都有章节。参考 [章节可见性保护 ↗](../../../apps/server/src/retrieval/context.ts#L21 "支持从 fragment 定位章节以及不可见材料返回空章节的限制。")

这套投影还被助手复用，用来为检索证据补充 `sectionTitle` 和相邻原文。因此，若你改变的是“哪一节”的判定算法，影响面不只包括顶部搜索，也包括助手得到的阅读上下文。参考 [助手复用章节上下文 ↗](../../../apps/server/src/assistant/runtime.ts#L684 "支持助手也使用相同章节投影，并补充相邻原文证据。")

<a id="change-boundaries"></a>
## 按改动性质选择入口

可以用下面的边界快速判断该改哪里：

| 想改变的行为 | 主要入口 | 需要同步关注 |
| --- | --- | --- |
| 章节提示的文字、顺序或布局 | `apps/web/src/App.vue` 的搜索结果面板 | 空章节、长标题、窄屏换行 |
| 搜索响应增加或调整字段 | `apps/server/src/app.ts` 的 `/api/search` | 前端结果类型、HTTP 测试 |
| 改变章节归属算法 | `retrieval/context.ts`、`knowledge/structure.ts` | Markdown、代码符号、可见性、助手上下文 |
| 改变仓库材料的召回资格或排序 | `knowledge/development.ts` | 个人材料仍保持原策略 |

前端应继续复用 `@omem/ui` 的 `OmPanel`、`OmCitation` 等组件。通用交互行为放入公共 UI，业务请求和状态留在 `apps/web`；视觉上沿用黑白灰 token、统一间距和可辨识的辅助文字，不为这一条提示另造一套按钮或面板。参考 [界面组件合同 ↗](../../../design.md#L28 "支持复用公共 UI 组件，并将业务数据和网络状态留在业务页面。")

<a id="verification"></a>
## 先验证行为，再查看真实页面

若只改展示，至少运行 `osdk deps --frozen` 和 `osdk run check`，然后启动真实服务检查搜索结果。若改了搜索或章节算法，应补两层验证：一层通过真实 Fastify handler 请求 `/api/search`，确认返回合同；另一层用结构测试确认 Markdown 标题、相邻片段和可见性仍按预期工作。现有测试已经展示了中文多词查询与章节内上下文的写法，可在相邻用例中扩展章节字段断言。参考 [搜索与章节上下文测试 ↗](../../../apps/server/tests/reading-context.test.ts#L33 "展示真实 HTTP 搜索以及 Markdown 章节、相邻片段和可见性测试的现有入口。")

程序检查通过只说明回归、类型和构建没有失败，不能证明提示真的易读。页面验收要使用 `osdk run browser`，并在真实服务中检查桌面、768px 和 390px：章节标题是否与摘要拉开层次、长中文是否自然换行、是否出现横向滚动、固定片段入口是否仍可操作。现有视口脚本会切换三个宽度、检查横向溢出并保存截图和报告，可作为扩展搜索场景的落点。参考 [分层检查要求 ↗](../../../docs/reader-first/operations.md#L15 "支持代码检查、真实浏览器检查与阅读验收需要分开判断。") [三档视口检查 ↗](../../../scripts/code-wiki-viewport.ts#L123 "支持在 1440、768、390 像素检查横向溢出、正文可见性并保存截图报告。")

<a id="knowledge-and-limits"></a>
## 更新相关知识，并区分当前能力与后续空间

如果改动改变了这篇开发指南所描述的真实流程，可运行 `osdk run review:guides contributing` 只更新本页；发布文章位于 `.repo-review/knowledge/`，研究、角色输出和 trace 留在 `.repo-review/runtime/`。启动开发环境不会替你自动生成这些知识。参考 [单页指南生成任务 ↗](../../../osdk.toml#L116 "支持按 contributing 页面键单独运行读者指南生成。") [知识生成与存放位置 ↗](../../../docs/reader-first/operations.md#L9 "说明读者指南命令以及运行 trace、发布文章各自的保存位置。")

当前统一搜索与上下文已经实现首个可用切片：顶部搜索、知识搜索和助手共享检索基础，助手能补章节标题与相邻片段；但完整意图路由和跨文件功能链仍是后续工作。因此，这次小改动应围绕“章节提示是否准确、可见、可读”验收，不要把单次搜索展示扩大成完整调用图或全仓库理解能力。最终判断也分两层：`check` 证明程序可运行，真实页面和实际问题则证明读者能理解、定位并开始行动。参考 [当前实现进度与验收口径 ↗](../../../docs/reader-first/progress.md#L5 "支持统一搜索与上下文仍是首个切片，并区分程序、阅读、检索和界面验收。")
