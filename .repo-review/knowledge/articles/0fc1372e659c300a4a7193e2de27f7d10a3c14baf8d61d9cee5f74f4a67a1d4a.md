# 改一条完整功能链：让搜索结果说清“它属于哪一节”

面向第一次修改 omem 的 TypeScript 开发者，以真实仓库符号 UnifiedRetrieval.search 为贯穿例子，从开发启动、材料接入、搜索 API、结构投影到 Vue 结果卡定位改动，并说明如何复用组件、检查真实页面和更新相关知识。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

## 先跑通一个真实可见的小目标

这次练习只改一条小链路：让顶部搜索结果更清楚地显示“它属于哪一节”。在仓库根目录运行：

```bash
osdk install
osdk deps --frozen
osdk run dev
```

打开终端最终打印的 Web 地址；端口被占用时会自动换端口。开发模式会载入本仓库材料与已发布知识，但启动不会自动重写整库 Wiki。参考 [开发环境启动 ↗](../../../docs/reader-first/operations.md#L3 "支持 osdk 启动命令、动态端口、开发材料接入以及启动不自动生成整库知识。")

进入顶部搜索，选择“定位实现”，输入 `UnifiedRetrieval.search`。在当前固定快照中，真实统一检索命中 `apps/server/src/retrieval/unified.ts` 的 `UnifiedRetrieval.search`，结构路径是 `UnifiedRetrieval / UnifiedRetrieval.search`，范围为第 323–422 行；结果卡会把类型、路径和行范围排在正文摘录上方。这个符号来自 dev 导入的真实仓库源码，可直接用来观察修改前后的页面。参考 [真实搜索方法 ↗](../../../apps/server/src/retrieval/unified.ts#L323 "支持真实仓库中的 UnifiedRetrieval.search 方法名称及其范围。") [代码符号路径 ↗](../../../apps/server/src/retrieval/units.ts#L68 "支持代码段落以父符号和当前限定名生成 headingPath，并保留精确方法范围。") [搜索结果卡 ↗](../../../apps/web/src/App.vue#L703 "支持结果卡显示结果类型、章节路径、原文行范围及阅读动作。")

## 理解仓库材料怎样进入开发环境

`scripts/dev.ts` 把当前目录写入 `OMEM_REPO_ROOT`，启用个人开发模式，再交给共享开发编排器。编排器选择 API 与 Web 端口，分别启动 Bun watch 服务端和 Vite，并等待健康检查成功后才打印可用地址；因此应以终端地址为准。参考 [个人开发入口 ↗](../../../scripts/dev.ts#L1 "支持开发入口设置仓库根和个人模式后载入共享编排器。") [开发服务编排 ↗](../../../scripts/dev-review.ts#L81 "支持端口选择、服务端与 Web 子进程启动、健康检查和最终地址输出。")

服务端的 `buildApp` 检测到仓库根后导入开发知识，创建共享检索，再把同一个检索入口交给知识路由、顶部搜索与助手。参考 [服务端开发装配 ↗](../../../apps/server/src/app.ts#L49 "支持服务端导入开发知识、创建共享检索并交给知识路由与助手。")

导入时先读取已发布文章，并从旧 review 库补齐这些文章缺失的固定历史材料依赖；随后 `restoreReviewKnowledge` 捕获当前仓库文件并恢复当前文章，再恢复历史文章与当前文章资产，最后刷新状态。这里“历史材料先补、当前文件后捕获”很关键：当前仓库内容会成为 live head，不会被历史修订倒退。参考 [开发知识导入顺序 ↗](../../../apps/server/src/review/development.ts#L37 "支持先补齐固定历史材料依赖、再捕获当前文件、恢复文章资产并刷新状态的整体顺序。") [当前材料与文章恢复 ↗](../../../apps/server/src/review/knowledge.ts#L9 "支持 restoreReviewKnowledge 先捕获当前仓库材料，再恢复当前文章并刷新知识状态。")

开发可见性适配只排除已移除副本和旧别名，内容排序仍由共享检索负责；仓库兼容没有变成一套专用排序器。参考 [开发检索可见性 ↗](../../../apps/server/src/review/development.ts#L15 "支持开发适配层只处理仓库副本可见性，并复用共享检索进行内容排序。")

## 沿一次搜索走完界面、API 与检索

顶部搜索状态在 `App.vue`。查询或用途变化时，页面取消旧请求、清空旧结果并等待 250ms；随后发送 `GET /api/search?q=UnifiedRetrieval.search&purpose=implementation`，并用请求版本避免慢响应覆盖新输入。参考 [搜索请求防竞态 ↗](../../../apps/web/src/App.vue#L178 "支持查询或用途变化时取消旧请求、延迟搜索并用版本防止旧响应回写。") [前端搜索调用 ↗](../../../apps/web/src/App.vue#L365 "支持前端把查询与用途发送到搜索 API，并处理取消、错误与当前版本结果。")

服务端校验用途，把查询截到 300 字、结果上限设为 30，然后优先调用统一检索。统一检索组合词法命中与可选中文向量，必要时重排；收尾阶段再按用途加权、按来源限量并去重。“定位实现”会提高代码单位的优先级，最终结果保留结构路径与固定来源目标。参考 [顶部搜索接口 ↗](../../../apps/server/src/app.ts#L274 "支持服务端校验用途、限制查询与结果数，并优先调用统一检索。") [统一检索编排 ↗](../../../apps/server/src/retrieval/unified.ts#L323 "支持检索融合、用途偏好、去重以及把 unit 字段映射为最终命中。")

## 弄清“所属章节”从哪里产生

`RetrievalHit` 把 `headingPath`、可读上下文、固定目标和引用分开保存。对 Markdown，投影器按块生成检索段落，并用标题栈记录每段所在的完整章节；对 TS/Vue，解析器按函数、方法或组件形成段落，把父符号与当前符号的限定名组成路径，未落入符号的顶层内容归为“模块定义与初始化”。参考 [统一结果合同 ↗](../../../apps/server/src/retrieval/port.ts#L19 "支持 headingPath、上下文、固定目标与引用是 RetrievalHit 中彼此分离的字段。") [Markdown 章节路径 ↗](../../../apps/server/src/retrieval/units.ts#L29 "支持 Markdown 按块投影并用标题栈保存完整章节路径。") [代码符号路径 ↗](../../../apps/server/src/retrieval/units.ts#L68 "支持代码段落以父符号和当前限定名生成 headingPath，并保留精确方法范围。")

每个段落随后获得 `SourceAnchor`：材料键、固定修订、摘要、精确行范围和片段列表负责打开原文；`sourceUnits` 把 `headingPath`、`target` 和 `references` 写入检索单位，`UnifiedRetrieval.finish` 再把这些字段映射为最终命中。因此路径是 Markdown/AST 结构，不是完整的跨文件业务调用图。参考 [固定原文锚点 ↗](../../../apps/server/src/retrieval/units.ts#L222 "支持 SourceAnchor 保留材料键、固定修订、摘要、行范围和片段列表。") [结构字段生产 ↗](../../../apps/server/src/retrieval/units.ts#L243 "支持 sourceUnits 为检索单位写入 headingPath、target、references 及可读上下文。") [统一检索编排 ↗](../../../apps/server/src/retrieval/unified.ts#L323 "支持检索融合、用途偏好、去重以及把 unit 字段映射为最终命中。")

还有另一种“上下文”：`evidenceNeighbors` 与 `evidenceSection` 在命中后补读同一章节的标题和相邻片段，供助手或兼容读取使用；它们不是结果卡路径的生成器。参考 [命中后的章节补读 ↗](../../../apps/server/src/retrieval/context.ts#L5 "支持邻近片段和章节边界用于命中后补背景，而非生成结果卡 headingPath。")

## 按想改变的行为选择修改层

| 想改变什么 | 首要修改位置 | 判断依据 |
| --- | --- | --- |
| 文案、分隔符、空路径表现、行号布局 | `apps/web/src/App.vue` 与 `styles.css` | 结果卡已经拿到路径和固定目标 |
| 新增共享来源结构字段或改变字段语义 | `retrieval/port.ts` → `retrieval/units.ts` 中对应的 unit producer → `retrieval/unified.ts` → `App.vue` | 合同、字段生产、最终映射与消费方要同步 |
| 改 Markdown 的“哪一节”判定 | `retrieval/units.ts::markdownPassages` | 标题栈在这里生成 |
| 改代码的类、方法或模块路径 | `retrieval/units.ts::codePassages` | AST 范围与父子路径在这里生成 |
| 改点击后补读的章节边界 | `retrieval/context.ts` | 这是补背景，不是结果卡字段 |

例如，只把路径润色为“位于 UnifiedRetrieval / UnifiedRetrieval.search”，改前端模板和局部样式即可；若要新增来源结构字段，则要从合同一路检查字段生产、收尾映射和前端消费；若要改变某段代码“属于哪个符号”，应修改结构投影，而不是在 Vue 中拆字符串。参考 [搜索结果卡 ↗](../../../apps/web/src/App.vue#L703 "支持结果卡显示结果类型、章节路径、原文行范围及阅读动作。") [统一结果合同 ↗](../../../apps/server/src/retrieval/port.ts#L19 "支持 headingPath、上下文、固定目标与引用是 RetrievalHit 中彼此分离的字段。") [结构字段生产 ↗](../../../apps/server/src/retrieval/units.ts#L243 "支持 sourceUnits 为检索单位写入 headingPath、target、references 及可读上下文。") [代码符号路径 ↗](../../../apps/server/src/retrieval/units.ts#L68 "支持代码段落以父符号和当前限定名生成 headingPath，并保留精确方法范围。") [命中后的章节补读 ↗](../../../apps/server/src/retrieval/context.ts#L5 "支持邻近片段和章节边界用于命中后补背景，而非生成结果卡 headingPath。")

结果卡已经使用 `OmPanel`、`OmButton`、`OmMarkdown` 和统一证据 trail。轻量元信息可以留在业务页面；只有跨页面复用的通用行为才进入 `packages/ui`，公共组件只接收 props、slots、emits，网络和业务状态仍留在 `apps/web`。样式沿用黑白灰 token 与既有间距尺度。参考 [公共组件边界 ↗](../../../.agents/skills/omem-design/SKILL.md#L8 "支持复用 packages/ui、业务网络与状态留在 apps/web，以及递归引用和响应式要求。") [视觉与交互基线 ↗](../../../design.md#L18 "支持既有间距、公共组件、响应式视口、焦点恢复和真实页面验收要求。")

## 分别确认程序、检索和阅读效果

改完先运行 `osdk deps --frozen` 与 `osdk run check`。涉及界面，再运行 `osdk run browser`，并在实际 dev 页面检查 1440、768、390px：长路径应换行而不造成根页面横向滚动，加载、错误和真正空结果应保持可辨，点击“阅读原文”后仍能沿统一 trail 返回并恢复焦点。若改变投影或排序，再运行 `osdk run retrieval:index --review`、`osdk run retrieval:verify`，并用真实 HTTP 查询复查结果。机器报告不能代替阅读验收。参考 [视觉与交互基线 ↗](../../../design.md#L18 "支持既有间距、公共组件、响应式视口、焦点恢复和真实页面验收要求。") [实现与页面检查 ↗](../../../docs/reader-first/operations.md#L13 "支持依赖、完整检查、浏览器、检索验证和机器报告的运行方式及边界。")

更新知识时，源码材料说明使用 `osdk run review:generate <路径> --modules`；本页指南使用 `osdk run review:guides contributing`。指南任务会按页面计划选择 `guide:contributing`，运行知识流水线，并刷新 coverage 与知识索引。参考 [知识生成入口 ↗](../../../docs/reader-first/operations.md#L9 "支持源码材料说明与读者指南使用不同的生成入口。") [指南目标选择 ↗](../../../scripts/review-guides.ts#L17 "支持 contributing 参数选择 guide:contributing，并由流水线写作、记录状态和刷新索引。")

最后让第一次接触这条链的人复述：输入怎样经过 API、结构投影和排序到达结果卡；只改文案与改变章节判定分别落在哪一层；怎样打开固定原文。程序检查只证明类型、测试与构建约束成立，检索抽查只说明选定问法的召回，独立模型复核也不等于新人已经读懂。当前统一搜索是可用的首片实现，完整意图路由和跨文件功能链仍未完成。参考 [阅读验收标准 ↗](../../../docs/reader-first/writing.md#L28 "支持以问题回答、必要术语、贯穿案例和下一步衡量读者理解，且模型复核不替代用户验收。") [当前能力边界 ↗](../../../docs/reader-first/progress.md#L33 "支持统一搜索与上下文仅为首片实现，完整意图路由和跨文件功能链仍未完成。")
