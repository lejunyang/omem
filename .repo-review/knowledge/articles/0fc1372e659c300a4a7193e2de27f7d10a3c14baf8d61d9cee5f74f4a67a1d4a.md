# 改一条完整功能链：从搜索结果到界面

以搜索结果卡显示所属章节为贯穿例子，从真实 dev 启动、仓库材料导入、Vue 请求、搜索 API、检索单位投影一路追到卡片渲染；说明 headingPath、检索 context 与回答上下文的区别，给出不同改动意图对应的最小入口、组件与间距约束，以及程序检查、真实页面验收和知识更新的完整收尾方法。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="outcome"></a>
## 先从要看到的结果倒推

这条功能链的目标很具体：用户在顶部搜索命中一段原文时，结果卡不仅给出摘录，还显示它属于哪一节，并能继续打开固定版本的准确行范围。对第一次修改 omem 的开发者，最短路径是从这个可见行为倒推字段，而不是先读完整套检索算法。

下面用一个**教学例子**贯穿全文：一份 Markdown《配送手册》有一级标题“配送手册”和二级标题“预约”，正文写着“团体需提前一天”。搜索“提前一天”后，希望卡片元信息类似：

```text
原始材料 · 配送手册 / 预约 · 第 6–6 行
```

仓库现有测试夹具已经验证：Markdown 分块会保留“手册 / 预约”的标题路径，表格里的“提前一天”仍留在完整表格块中，代码围栏里的 `#` 不会被误当成章节。这个例子用于解释字段流转，**不承诺该结果在当前排序中一定排第一**。参考 [章节路径与完整操作体测试 ↗](../../../apps/server/tests/retrieval-unified.test.ts#L710 "验证 Markdown 标题栈、表格与代码围栏行为，以及代码方法作为完整操作返回。") [当前检索效果边界 ↗](../../../docs/reader-first/progress.md#L39 "说明真实搜索仍可能让计划或旧说明领先，不能把教学例子写成首条排序承诺。")

完成一次小改动时，你应能回答三个问题：

1. 这是只改变卡片文案，还是改变服务端返回的结构？
2. “所属章节”来自检索单位，还是来自回答时补读的上下文？
3. 检查退出 0 之后，真实页面是否仍让人读得懂、点得准？

页面计划本身也把目标限定为从用户可见行为定位 API、检索与组件，完成小改动并在真实页面确认，不要求大规模重构。参考 [本页的读者目标与贯穿场景 ↗](../../../config/wiki-pages.json#L119 "支持本文面向首次修改者、从可见行为定位完整链且不做大规模重构的范围。")

<a id="start-dev"></a>
## 启动 dev，并理解仓库材料为何能被搜到

在仓库根目录执行：

```bash
osdk install
osdk deps --frozen
osdk run dev
```

打开终端最后打印的 web 地址。默认 API / web 端口是 4317 / 5173；端口占用时开发脚本会选择空闲端口，所以以终端输出为准。开发 API 由 nodemon 管理，前端由 Vite 热更新；脚本等到 `/api/health` 成功后才打印 ready 地址，任一子进程退出都会触发联动关闭。参考 [开发环境启动说明 ↗](../../../docs/reader-first/operations.md#L3 "给出 osdk 启动命令、端口、个人库和热重载的当前行为。") [API 与 Vite 开发编排 ↗](../../../scripts/dev-review.ts#L82 "支持端口选择、进程启动、健康检查、ready 地址和联动关闭的说明。")

这不是一套空白演示数据。`osdk run dev` 最终执行 `bun scripts/dev.ts`；该入口把 `OMEM_REPO_ROOT` 设为当前仓库并把模式设为 `personal`。服务装配看到仓库根路径后，会导入已提交知识和所需历史，再捕获当前仓库材料，同时保留个人数据库。参考 [dev 任务入口 ↗](../../../osdk.toml#L84 "证明 osdk dev 任务落到 pnpm run dev。") [个人开发模式入口 ↗](../../../scripts/dev.ts#L1 "证明 scripts/dev.ts 设置仓库根与 personal 模式并载入开发编排器。") [服务装配中的开发知识导入 ↗](../../../apps/server/src/app.ts#L54 "证明存在 OMEM_REPO_ROOT 时构建服务会导入开发知识并包装共享检索。") [已发布知识与历史恢复 ↗](../../../apps/server/src/review/development.ts#L37 "说明开发导入恢复已提交文章、所需历史和实时仓库材料，而不替换个人数据库。")

当前仓库捕获器优先使用 Git 的“已跟踪文件 + 未忽略的未跟踪文件”清单；它排除派生运行目录、依赖、构建物、私有环境配置和不安全链接。文本按 `verbatim-v1` 保存，内容 hash 未变时不会制造新版本。随后恢复材料说明、发布文章和 `config/wiki-pages.json` 中的页面计划。这里的文件筛选只是开发输入适配；进入 Store 后，仓库材料和个人材料仍共享检索实现。参考 [仓库材料捕获规则 ↗](../../../apps/server/src/review/materials.ts#L16 "支持 Git 文件清单、排除规则、内容 hash 和 verbatim 固定捕获行为。") [材料、文章与页面计划恢复 ↗](../../../apps/server/src/review/knowledge.ts#L12 "证明开发恢复会捕获仓库材料并载入材料说明、发布文章和页面计划。") [开发检索只增加输入可见性策略 ↗](../../../apps/server/src/review/development.ts#L15 "说明开发包装器只隐藏移除或旧别名仓库材料，排序仍走共享检索。")

因此，若刚改过一份可捕获的 Markdown，服务重启或热重载后它会作为新固定版本进入开发库；启动本身不会自动重新生成整库知识。

## 沿一次搜索追到结果卡

把顶部搜索框中的“提前一天”当作输入，可以沿一条清晰的数据链定位：

1. **Vue 状态与并发保护。** `App.vue` 中的 `query`、用途和材料角色发生变化时，旧结果会立即清空，上一请求被 `AbortController` 取消，并在 250 ms 后发起新搜索；递增的 version 还会阻止较慢的旧响应覆盖新查询。参考 [搜索防抖与旧请求取消 ↗](../../../apps/web/src/App.vue#L198 "支持查询变化后清空结果、取消请求、递增版本并延迟搜索的 UI 行为。")
2. **浏览器请求。** `search()` 请求 `/search?q=...&purpose=...`，有角色筛选时再带 `role`。`api.ts` 统一补上 `/api` 前缀、连接令牌和错误处理，所以实际入口是 `/api/search`。参考 [Vue 搜索请求 ↗](../../../apps/web/src/App.vue#L380 "证明 search 函数组织查询参数、传递 AbortSignal 并用版本号防止旧响应覆盖。") [浏览器 API 封装 ↗](../../../apps/web/src/api.ts#L260 "支持统一 /api 前缀、令牌、JSON 与非成功错误处理。")
3. **HTTP 合同。** 路由校验 `purpose`、`codeIntent`、`role` 与 `effectiveAt`，把查询截到 300 字并把 limit 设为 30，然后优先调用共享 `RetrievalPort.search`。开发模式只在它外面包一层可见性策略，用于隐藏已移除或旧别名的仓库副本。参考 [搜索 HTTP 入口 ↗](../../../apps/server/src/app.ts#L313 "支持查询校验、长度和数量限制，以及调用共享搜索接口的说明。") [开发检索只增加输入可见性策略 ↗](../../../apps/server/src/review/development.ts#L15 "说明开发包装器只隐藏移除或旧别名仓库材料，排序仍走共享检索。")
4. **候选到返回值。** `UnifiedRetrieval.search` 同步投影后组合词法、可用时的向量和符号候选，也可能走代码导航或重排；`finish` 才应用用途偏好、适用性、去重和数量限制。对本例最重要的是：它把检索单位的 `headingPath` 原样放入 `RetrievalHit`。参考 [统一检索候选组合 ↗](../../../apps/server/src/retrieval/unified.ts#L480 "支持同步投影、导航、词法、向量、符号、融合和可选重排的概括。") [最终结果装配 ↗](../../../apps/server/src/retrieval/unified.ts#L606 "证明用途偏好、去重和数量限制在 finish 中应用，并原样返回 headingPath。")
5. **卡片渲染。** `RetrievalHit` 的稳定合同同时包含 `title`、`text`、`context`、`headingPath`、`target` 和 `references`。`App.vue` 用 `OmPanel` 渲染每条结果，把非空 `headingPath` 用“ / ”连接；原始材料再显示固定起止行，按钮继续打开原文或讲解。参考 [RetrievalHit 共享合同 ↗](../../../apps/server/src/retrieval/port.ts#L45 "列出 UI 使用的结果种类、文本、上下文、章节路径、目标和引用字段。") [搜索结果卡渲染 ↗](../../../apps/web/src/App.vue#L724 "证明卡片用共享组件展示种类、章节路径、固定行范围、正文和打开动作。")

这条链也给出一个实用排障顺序：

- 网络响应已有正确 `headingPath`，页面没显示：先看 `App.vue` 模板和样式。
- 响应里的路径为空或层级错误：查 `units.ts` 如何生成检索单位。
- 命中正确但排序差：再进入 `unified.ts` 的候选和排序；不要把章节显示问题误判为排序问题。

当前实际 HTTP 搜索仍可能让计划或旧说明排在更有效的实现前，所以调试时应检查目标结果是否存在、字段是否正确，不要只看第一条。参考 [当前检索效果边界 ↗](../../../docs/reader-first/progress.md#L39 "说明真实搜索仍可能让计划或旧说明领先，不能把教学例子写成首条排序承诺。")

<a id="section-origin"></a>
## 分清章节路径、检索上下文与回答上下文

“所属章节”并不是 Vue 从摘录文本里猜出来的。它在材料变成检索单位时生成，不同材料类型有不同来源：

- **原始 Markdown：** `markdownPassages` 用解析器维护标题深度栈，每个非标题块得到当时的完整 `headingPath`；表格、列表或代码块可与前置引导句合并，同时保留原始行范围。参考 [Markdown 检索分块 ↗](../../../apps/server/src/retrieval/units.ts#L33 "解释标题栈、块边界、完整表格列表代码块和原始行范围的生成。")
- **原始代码：** `codePassages` 使用 AST 符号范围。函数或方法保留完整操作体，路径由父符号与当前 qualified name 组成；未被符号覆盖的顶层导入和初始化归到“模块定义与初始化”。参考 [代码检索分块 ↗](../../../apps/server/src/retrieval/units.ts#L92 "解释 AST 符号路径、完整函数方法体及顶层初始化单位。")
- **知识文章：** 每个正式 section 的正文再次按 Markdown 分块，路径以 section 标题开头，再接节内标题。参考 [知识文章章节单位 ↗](../../../apps/server/src/retrieval/units.ts#L670 "证明知识正文按正式 section 分块，headingPath 由 section 标题与节内路径组成。")
- **事项与记忆：** 当前不会伪造章节路径；没有结构路径时，卡片只显示种类。

最容易混淆的是下面三项：

| 名称 | 作用 | 本例中的表现 |
| --- | --- | --- |
| `headingPath` | 给调用方导航和显示 | 卡片上的“配送手册 / 预约” |
| `RetrievalUnit.context` | 给词法、向量或重排提供材料标题、章节、概念等输入 | 服务端检索使用，卡片当前不直接展示 |
| `ContextHierarchy` 与回答上下文 | 命中后在同一固定 revision 内补读最小章节或函数，必要时补父章节引言 | 助手回答时读更完整材料，不等于多返回一条搜索结果 |

原始材料单位会同时把标题和章节拼入 `context`，又把同一 `headingPath` 单独保存；两者相邻但职责不同。参考 [原始材料单位字段 ↗](../../../apps/server/src/retrieval/units.ts#L369 "证明 context 与 headingPath 分别保存，target 仍指向固定原文范围。") 层级投影则保存父子结构，回答装配只在相同固定版本、既有可见性允许的范围内扩展，不会因为命中一个子块就自动拼入所有兄弟章节。参考 [独立的阅读层级投影 ↗](../../../apps/server/src/retrieval/hierarchy.ts#L1 "支持章节父子结构与检索命中相互独立，并绑定固定 revision 的说明。") [固定版本内的上下文扩展 ↗](../../../apps/server/src/retrieval/context.ts#L13 "说明命中如何扩到最小章节、可见性如何约束，以及父引言和兄弟章节边界。") [助手回答上下文装配 ↗](../../../apps/server/src/assistant/context.ts#L10 "证明回答按固定文章章节或原始层级补读，并限制不同上下文而非拆散引用。")

所以：

- 只换卡片文案或布局，改 Vue。
- 想让卡片包含不同的章节或符号层级，改检索单位投影。
- 想改变助手点开或回答时补读多大范围，才改 hierarchy/context/assistant context。

这三个入口都和“章节”有关，但改错层会产生完全不同的行为。

## 按改动意图选择最小入口

以“把章节提示改成更轻的 badge，并保留长路径可读性”为例，先把范围限定在结果卡：

1. 在 `apps/web/src/App.vue` 的结果卡元信息处调整 `r.headingPath` 的展示；不要从 `r.text` 重新解析标题。
2. 优先复用 `@omem/ui` 已导出的 `OmBadge`、`OmPanel`、`OmButton`、`OmEmpty` 和 `OmMarkdown`。网络请求和业务状态继续留在 `apps/web`；只有一种行为或视觉会在多处复用时，才下沉到 `packages/ui`。参考 [omem 界面复用与验收约定 ↗](../../../.agents/skills/omem-design/SKILL.md#L8 "支持复用 packages/ui、业务状态边界、黑白灰风格、响应式宽度和真实页面检查。") [现有公共组件导出 ↗](../../../packages/ui/src/index.ts#L1 "证明 OmBadge、OmPanel、OmButton、OmEmpty、OmMarkdown 等组件已经可复用。")
3. 沿用黑白灰 token、可见焦点和 reduced-motion 规则。现有页面已用 `.stack` 给卡片留 22 px 间距，`.search-section` 给元信息留 12 px 下边距；`OmPanel` 自带面板内边距、标题与操作区间距。不要靠空格字符或散落的内联样式造布局。参考 [全局视觉与无障碍 token ↗](../../../packages/ui/src/tokens.css#L1 "支持黑白灰变量、字体、焦点样式和 reduced-motion 约束。") [页面卡片与章节元信息间距 ↗](../../../apps/web/src/styles.css#L99 "支持页面宽度、stack 卡片间距和 search-section 元信息间距的当前值。") [OmPanel 面板间距 ↗](../../../packages/ui/src/components/OmPanel.vue#L14 "支持面板内边距、标题、操作区和移动端内边距的说明。")

如果需求不是纯显示，可按下表扩展：

| 需求 | 主要入口 | 需要同步检查 |
| --- | --- | --- |
| 改分隔符、文案、颜色或换行 | `App.vue`、必要时 `styles.css` | 长路径、空路径、390/768/1440 px |
| 给所有调用方增加新结构字段 | `retrieval/port.ts` | `units.ts` 生产、`unified.ts` 传递、Vue 和助手消费 |
| 改 Markdown 标题提取 | `markdownPassages` | 表格、列表、代码围栏、固定行范围 |
| 改代码所属操作 | `codePassages` / AST 解析 | 完整方法体、父符号路径、顶层初始化 |
| 改知识文章的首层章节 | 知识单位生成段 | 正式 section 与节内标题组合 |
| 改回答补读范围 | `hierarchy.ts`、`context.ts`、助手上下文 | 固定 revision、可见性、父引言与兄弟章节 |

还有一个需要明确标成**实现推断**的版本规则：`UNIT_VERSION` 同时参与单位 ID，而投影 head 的 identity 也包含该版本。由此可推断，只要你改变了持久检索单位的 `headingPath` 或 `context` 生成方式，就应同步提升 `UNIT_VERSION`，让旧单位和向量不被误认为仍有效；如果只改变独立层级树，则检查是否应提升 `CONTEXT_VERSION`。这不是文档逐字规定的操作命令，而是从 identity 与回填逻辑得出的维护结论。参考 [检索单位版本常量 ↗](../../../apps/server/src/retrieval/units.ts#L18 "支持 UNIT_VERSION 是检索单位结构身份一部分的实现推断。") [单位 ID 与投影 identity ↗](../../../apps/server/src/retrieval/units.ts#L369 "证明 UNIT_VERSION 参与单位 ID 和投影 head identity，从而支持结构变化时提升版本的推断。") [上下文投影版本与回填 ↗](../../../apps/server/src/retrieval/units.ts#L520 "证明独立 CONTEXT_VERSION 可在不改单位和向量 ID 时触发层级投影回填。")

若投影或预处理变化需要显式补建开发索引，运行 `osdk run retrieval:index --review`；应用运行时不会隐式下载模型。参考 [显式索引维护 ↗](../../../docs/reader-first/operations.md#L13 "支持模型不隐式下载和 review 索引补建命令。")

<a id="verify"></a>
## 分层确认结果，再更新相关知识

验证要与改动风险匹配。纯 UI 文案不需要重测整套检索算法；改变单位生成或共享合同时，则应逐层确认：

1. **单元与服务。** 扩充 `retrieval-unified.test.ts`，覆盖 Markdown、代码和知识文章的 `headingPath`，并断言原始材料固定行范围。现有测试已经覆盖完整方法体和 Markdown 标题/表格行为，可作为落点。参考 [章节路径与完整操作体测试 ↗](../../../apps/server/tests/retrieval-unified.test.ts#L710 "验证 Markdown 标题栈、表格与代码围栏行为，以及代码方法作为完整操作返回。")
2. **真实 API。** 在 dev 中请求 `/api/search`，确认 `headingPath` 没在路由或 `finish` 中丢失，并打开结果核对固定原文。
3. **工程检查。** 先运行 `osdk deps --frozen`，再运行 `osdk run check`；check 包含 typecheck、测试和构建。参考 [工程检查任务内容 ↗](../../../osdk.toml#L128 "证明 osdk run check 顺序执行 typecheck、测试和构建。")
4. **真实页面。** 运行 `osdk run dev` 后用真实仓库词搜索，查看长章节路径换行、空路径、无结果、失败、快速改词时旧响应取消，以及点击后是否落到正确原文。页面改动还应运行 `osdk run browser`，在 1440、768、390 px 检查横向溢出与实际间距。现有 browser smoke 已覆盖 loading、empty、failure 和 superseded request，但没有显式断言结果卡的 `headingPath` 文案；本次若改变它，应补目标断言，或至少保存并抽查三种宽度的真实截图。参考 [搜索页浏览器状态覆盖 ↗](../../../scripts/browser-smoke.ts#L299 "证明现有浏览器检查覆盖加载、空态、失败和旧请求被后续查询取代。") [三种真实页面宽度检查 ↗](../../../scripts/code-wiki-viewport.ts#L191 "支持 1440、768、390 像素的无横向溢出和截图检查入口，同时表明当前脚本主对象是知识阅读页。") [当前检查与阅读验收入口 ↗](../../../docs/reader-first/operations.md#L21 "给出 check、browser、retrieval verify 与 full review verify，并说明机器报告不能代替阅读验收。")

**检查通过不等于阅读可用。** 当前项目明确把程序检查、模型复核与读者验收分开；最近一份完整报告甚至出现项目检查通过、仓库 HTTP 搜索总体失败。最终还要用人的问题验收：章节提示能否帮助定位？长路径是否一眼能懂？打开后是否仍是那一版原文的准确范围？参考 [验证与交付边界 ↗](../../../docs/reader-first/progress.md#L57 "支持程序检查、真实页面、完整报告、模型复核与用户验收必须区分。")

实现切片通过相关检查后先单独提交。若改动影响本页解释或它引用的行为，再用真实知识流程更新页面：

```bash
osdk run review:guides contributing
```

该任务也接受完整键 `guide:contributing`。`review:generate` 只生成内部分析笔记，不用于更新这篇正式指南；如果读者、目标、问题或场景本身变化，应先改 `config/wiki-pages.json` 的页面计划。参考 [正式指南更新命令 ↗](../../../docs/reader-first/operations.md#L11 "区分 review:guides 与内部 review:generate，并给出单页更新方式。") [contributing 页面选择与报告 ↗](../../../scripts/review-guides.ts#L17 "证明脚本接受短键或完整键，恢复知识后运行页面管线并记录 reviewed/failed 等状态。") [读者页面调查、写作与失败状态 ↗](../../../apps/server/src/knowledge/pipeline.ts#L251 "证明页面计划会保存，原生调查完成后进入写作复核，失败记录为 failed。")

知识更新成功后，再按风险运行 `osdk run retrieval:verify`、真实 HTTP 搜索和 `osdk run review:verify --full`，并回到实际 dev 阅读新文章。模型派生资产与实现分别提交；发布成功、引用可解析或独立复核通过，都不能代替真实读者沿这个例子找到修改入口。参考 [当前检查与阅读验收入口 ↗](../../../docs/reader-first/operations.md#L21 "给出 check、browser、retrieval verify 与 full review verify，并说明机器报告不能代替阅读验收。") [事实检查与读者检查 ↗](../../../docs/reader-first/writing.md#L34 "支持页面是否回答目标、案例是否贯穿、能否行动不能由独立模型判断替代。")
