# tasks · 模块理解

tasks 模块分别实现跟进配置校验与到期提醒派发：前者保留用户原文中的等待对象和时间措辞并规范化时间戳，后者扫描开放或等待中的任务并生成站内通知。现有材料不能证明两者已形成端到端调用链，也不能证明时间措辞与时间戳语义一致；事务、并发安全、调度方式及通知动作闭环仍待核验。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 职责与授权边界

本模块分别提供跟进配置校验和提醒派发能力，但现有材料没有展示两者的调用方，因此不能断言已经形成端到端串联。`validateFollowUp` 按共享合同解析配置；等待对象必须原样出现于当前用户文本，设置下次检查或暂缓时间时，也必须保留当前指令中的原始时间表达，随后时间戳会被规范化为 ISO 字符串。[跟进配置的原文校验与时间规范化 ↗](../../../apps/server/src/tasks/follow-up.ts#L5 "支持校验函数解析共享合同、检查等待对象与时间措辞是否出现在当前用户文本中，并将两个时间字段规范化为 ISO；也界定该实现没有校验措辞与时间戳的语义一致性。")

这套校验只能证明相关措辞来自当前文本，不能证明 `time_expression` 与提交的具体时间戳在语义上相符。共享合同还定义四种任务状态，并严格约束等待对象、带偏移的日期时间、原始表达、IANA 时区及对象字段范围。[任务状态与跟进字段共享合同 ↗](../../../packages/contracts/src/task-flow.ts#L3 "支持四种任务状态，以及等待对象、带偏移日期时间、原始时间表达、IANA 时区和严格对象结构的统一约束。")

<a id="flow"></a>
## 扫描、触发与通知流程

`dispatchTaskReminders` 扫描 `open` 或 `waiting` 状态的任务，并跳过仍处于暂缓窗口的记录。它分别判断截止时间与下次检查时间是否到达，再按任务、版本、触发类型和 occurrence 查询收据，排除已经处理的触发。[任务扫描与新触发筛选 ↗](../../../apps/server/src/tasks/follow-up.ts#L20 "支持扫描开放或等待状态、暂缓过滤、截止与跟进触发判断，以及按任务版本和 occurrence 收据排除已处理触发。")

同一任务若同时命中截止与跟进，只创建一条通知，但会为每个新触发分别写入收据。通知正文组合下一步或详情、等待对象和到期原因，提示完成、稍后提醒或取消，并明确不会自动联系他人；函数最终返回本轮创建的通知数量。[通知生成与逐触发收据 ↗](../../../apps/server/src/tasks/follow-up.ts#L35 "支持多种触发合并为单条通知、通知正文组成、不会自动联系他人的声明、逐触发收据写入和交付计数。")

<a id="relations"></a>
## 共享合同与一致性设计

模块直接依赖共享的 `task-flow` 合同：状态与跟进字段供提醒扫描和解析使用；合同还定义完成、重开、改期、等待、暂缓、取消等动作，以及包含期望版本、请求 ID、截止信息和跟进配置的严格任务命令，为其他任务入口提供统一数据边界。[任务动作与命令合同 ↗](../../../packages/contracts/src/task-flow.ts#L15 "支持任务动作集合，以及带期望版本、请求 ID、截止信息和跟进配置的严格命令结构。")

提醒函数自身不运行模型、不发送外部消息，也不创建守护进程；注释声明它应在 Store 事务内执行，使通知和收据共同提交。[提醒派发的事务与副作用边界 ↗](../../../apps/server/src/tasks/follow-up.ts#L17 "支持函数被设计为在 Store 事务内调用，且自身不运行模型、不外发消息或创建守护进程；该注释不能证明所有实际调用方都提供了事务。") 截止通知键包含任务版本，逐触发收据也按版本与 occurrence 查询，因此任务更新后可以重新提醒，并能过滤重复轮询中的旧触发。[版本去重与触发收据查询 ↗](../../../apps/server/src/tasks/follow-up.ts#L27 "支持截止通知键包含任务版本、提醒收据按版本和 occurrence 查询，以及流程采用先查询后插入；数据库级并发保护仍缺少结构证据。") 但实现采用先查询后插入，而材料没有数据库唯一约束或调用方事务代码，尚不能确认并发互斥与失败回滚。

<a id="progress"></a>
## 当前进展、替代结论与限制

当前材料表明，本模块**分别实现**了两组能力：一组是合同解析、原文子串校验和时间规范化；另一组是暂缓过滤、两类到期判断、合并通知、逐触发收据写入与交付计数。前一组由校验函数体现，[跟进配置的原文校验与时间规范化 ↗](../../../apps/server/src/tasks/follow-up.ts#L5 "支持校验函数解析共享合同、检查等待对象与时间措辞是否出现在当前用户文本中，并将两个时间字段规范化为 ISO；也界定该实现没有校验措辞与时间戳的语义一致性。") 后一组由提醒扫描函数体现；[提醒扫描核心流程 ↗](../../../apps/server/src/tasks/follow-up.ts#L20 "仅支持提醒派发函数内部的任务扫描、暂缓过滤、触发判断、通知生成、收据写入和交付计数；不用于证明配置校验与派发已经串联。") 尚无调用链证据证明两组能力已经串联。

被替代的结论是“已确认提醒时间确实来自用户且未被推断”。更准确地说，实现仅要求保存一段出现在当前指令中的时间措辞，未验证该措辞与 `next_check_at` 或 `snoozed_until` 的语义一致。离线补扫和重复轮询不重放也是源码注释表达的设计目标，[离线补扫与重复轮询设计目标 ↗](../../../apps/server/src/tasks/follow-up.ts#L17 "支持通知与收据共同提交、避免同一任务版本和 occurrence 被重复处理的设计意图，并明确函数自身不负责创建守护调度。") 但当前材料未呈现调度器、启动恢复、数据库索引、通知动作处理器或相关行为测试，不能据此确认完整运行闭环。
