# 学习刷新与来源追踪的集成测试

验证捕获材料的片段级来源信息能够进入学习流程，并覆盖来源修订后两种关键结果：证据不足时保留人工复核状态，重新验证通过时更新原有记忆且保留历史证据。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 测试解决的核心风险

该文件把捕获合同、SQLite Store、记忆与反馈服务、学习流水线组合起来，验证“捕获材料 → 模型处理 → 记忆刷新”的完整行为，而非只测试单个函数。重点防止两类问题：多人或图片材料的来源信息在送入模型前丢失，以及来源更新后旧记忆被错误覆盖或重复创建。参考 [学习刷新测试依赖 ↗](../../../apps/server/tests/learning-refresh.test.ts#L5 "说明测试直接组合捕获合同、Store、记忆服务、反馈服务与学习流水线。")

<a id="provenance"></a>
## 片段来源信息如何到达模型

合同允许每个文本、图片或链接片段携带独立的参与者、事件、时间、回复关系及转发状态；这些字段保持可选，以兼容缺少元数据的历史材料。参考 [片段级来源合同 ↗](../../../packages/contracts/src/index.ts#L4 "支持片段来源字段及其兼容历史材料的可选设计。")

测试捕获 Alice、Bob 两段文本和一张图片，运行一次学习任务后检查任务成功且类型为声明提取；夹具模型返回的详情必须同时出现两位参与者、一个图片资源引用，并明确会话标识没有被提升为可信项目。这证明的是上下文清单的传递结果，不代表模型已正确理解其语义。参考 [上下文传递断言 ↗](../../../apps/server/tests/learning-refresh.test.ts#L131 "支持参与者、图片资源引用和项目可信状态进入模型输出的断言。")

<a id="abstention"></a>
## 证据不足时保留待复核状态

测试先让一条记忆依赖来源 v1，再以同一外部来源捕获内容完全不同的 v2；新修订会产生 `refresh_dependents` 作业。参考 [来源更新触发刷新 ↗](../../../apps/server/tests/learning-refresh.test.ts#L196 "支持捕获 v2 后产生依赖刷新作业的流程。")

随后流水线可以成功分派刷新并复用声明提取流程，但当模型不支持修复时，刷新记录仍为 `needs_review`，受影响数量为 1，且记录保留原记忆标识。这里区分了“刷新作业已成功执行”和“记忆已经成功修复”，避免把入队或调度成功误算为应用成功。参考 [拒绝修复后的状态 ↗](../../../apps/server/tests/learning-refresh.test.ts#L221 "支持作业成功但刷新记录仍需复核，并保留受影响记忆标识的结论。")

<a id="successful-refresh"></a>
## 重新验证通过后原位更新记忆

另一场景先从“重试上限为 3”生成活跃记忆，再捕获“上限为 5”。新来源出现后，同一记忆先变为失效状态；流水线完成独立验证后，数据库中仍只有这一条记忆，其标识不变、版本升至 2、状态恢复为活跃，正文包含新值。同时旧来源片段仍可读取，刷新记录变为 `applied`。参考 [原位更新与历史保留 ↗](../../../apps/server/tests/learning-refresh.test.ts#L261 "支持记忆失效、同标识升版恢复、旧片段保留及刷新应用成功等断言。")

这些断言覆盖单来源、单依赖记忆的成功与拒绝修复路径，但使用的是 Node 启动的角色夹具，不能证明真实外部 Agent CLI 的认证、超时和模型兼容性。参考 [角色运行夹具 ↗](../../../apps/server/tests/learning-refresh.test.ts#L26 "说明测试通过本地 Node 夹具模拟 ACP 角色，界定其并非真实外部 CLI 验证。")
