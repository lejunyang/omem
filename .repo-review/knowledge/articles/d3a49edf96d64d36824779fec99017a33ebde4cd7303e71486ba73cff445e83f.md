# 代码分析结果的结构化输出合同

该文件定义 KnowledgeBatch.v1 的 JSON Schema，以统一结构承载代码分析形成的文章、章节、证据引用与待确认问题。它约束字段、数量、长度和枚举值，但不能单独证明宿主的引用抽取、目标校验或独立语义复核已经实现。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 统一批次与文档结构

该合同定义统一的批次输出结构：版本固定为 1，每批包含一至十六篇文档，适合一次交付一个或多个相关主题。参考 [批次版本与数量 ↗](../../../packages/agent-runtime/roles/code-analyst/1/output.schema.json#L5 "支持顶层版本固定为 1，以及每批包含一至十六篇文档。")

每篇文档必须提供键、标题、摘要、类别、章节、引用和问题，且不接受合同之外的额外字段。类别限定为概览、架构、背景、需求、进展、实现、测试、配置、流程、研究、对话和视觉等类型，使不同主题沿用一致的外层组织方式。参考 [文档类别范围 ↗](../../../packages/agent-runtime/roles/code-analyst/1/output.schema.json#L31 "支持文档类别的完整枚举范围及其统一分类方式。")、[文档必填字段 ↗](../../../packages/agent-runtime/roles/code-analyst/1/output.schema.json#L209 "支持每篇文档的必填字段以及禁止额外字段的结构约束。")

<a id="content"></a>
## 组织正文与定位证据

每篇文档包含一至二十个章节。章节由格式受约束的键、标题和字符串正文组成，并设有长度边界；该 Schema 本身没有规定正文必须采用 Markdown，也没有说明章节键是否用于路由。参考 [章节结构约束 ↗](../../../packages/agent-runtime/roles/code-analyst/1/output.schema.json#L48 "支持章节数量、键格式、标题与正文长度及章节必填字段的说明。")

引用集合至少包含一项。每项记录人读标签、引用理由、关系类型和目标；目标可携带材料行号或文章章节，但结构上只强制 `kind` 与 `key`，未按目标类型分别要求行号或章节。`quote` 的描述约定是由宿主从固定行范围抽取原文，这里只能确认合同中的声明。参考 [引用与目标结构 ↗](../../../packages/agent-runtime/roles/code-analyst/1/output.schema.json#L78 "支持引用关系、目标定位字段、必填项和 quote 的宿主抽取约定，也表明目标字段未设置按类型区分的条件约束。")

<a id="limits"></a>
## 保留疑问与识别运行边界

文档可携带最多二十个待确认问题，每项记录问题、原因、下一步、是否阻塞及关联引用键，使证据不足的事项能够显式保留。参考 [待确认问题结构 ↗](../../../packages/agent-runtime/roles/code-analyst/1/output.schema.json#L166 "支持问题可记录原因、下一步、阻塞状态和关联引用键。")

该文件只定义静态 JSON 结构，未展示实际由谁执行校验、目标及行范围是否存在、原文如何抽取，也不能证明独立角色会核对引用对论断的语义支持性；这些运行行为仍需结合宿主实现和行为测试确认。延伸阅读：[引用与目标结构 ↗](../../../packages/agent-runtime/roles/code-analyst/1/output.schema.json#L78 "支持引用关系、目标定位字段、必填项和 quote 的宿主抽取约定，也表明目标字段未设置按类型区分的条件约束。")
