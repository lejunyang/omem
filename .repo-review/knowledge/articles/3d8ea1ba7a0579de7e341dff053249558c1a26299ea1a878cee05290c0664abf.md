# 仓库评审数据迁移与关系失效测试

该测试验证仓库评审数据从内容哈希身份迁移到稳定路径身份时保留历史证据，并验证代码来源产生新修订后，显式执行关系失效处理会将旧片段关系标为过期并移出默认查询。覆盖范围包括同路径冲突、同内容不同路径、历史可读性、同一数据库状态上的重复迁移、片段保留及关系失效。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 防止身份迁移破坏历史证据

repo-review 要把旧的“内容哈希即来源身份”迁移为稳定的 `omem:<仓库相对路径>` 身份，使同一文件修改后累积修订，而内容相同但路径不同的文件仍保持独立。测试直接写入旧式 source、revision 和 fragment，构造迁移前状态。参考 [旧式来源构造 ↗](../../../apps/server/tests/review-migration.test.ts#L40 "支持测试直接构造旧哈希来源、修订和片段以模拟迁移前状态。")

每个用例使用独立临时目录和真实 `Store`，结束后关闭数据库并递归清理目录，避免用例相互污染。参考 [测试存储隔离与清理 ↗](../../../apps/server/tests/review-migration.test.ts#L22 "支持每个用例创建独立临时 Store，并在结束后关闭数据库和删除目录。") `Store` 构造时会创建 SQLite、执行数据库迁移并初始化仓储服务，因此这些断言检验的是实际存储行为。参考 [共享存储初始化 ↗](../../../apps/server/src/store.ts#L45 "说明真实 Store 会创建数据库、执行迁移并初始化相关仓储服务。")

<a id="migration-cases"></a>
## 同路径归并并保留旧历史

同一路径存在两个旧哈希来源时，用例中的较新来源取得路径身份并继续持有当前 head；旧来源保留原 external id，但解除 head、登记为历史别名。当前浏览只留下一个路径来源，迁移前后片段总数不变。参考 [同路径冲突迁移 ↗](../../../apps/server/tests/review-migration.test.ts#L111 "支持较新来源取得路径身份、旧来源成为历史别名且片段数量保持不变。")

路径才是新身份边界：正文完全相同但路径不同的文件会成为两个独立当前来源。被降级的旧来源仍能按旧 external id 找到，其修订、片段和历史记录继续可读，只是不再属于当前视图。参考 [相同内容不同路径 ↗](../../../apps/server/tests/review-migration.test.ts#L158 "支持相同正文位于不同路径时仍形成两个独立的当前来源。") [历史来源仍可读取 ↗](../../../apps/server/tests/review-migration.test.ts#L189 "支持被降级来源继续通过旧身份访问修订、片段与历史记录。")

<a id="idempotence"></a>
## 重复迁移保持已稳定状态

首次迁移后，测试记录文件来源的 external id、head 与别名；在同一个 `Store` 和 stateDir 上再次调用迁移时，返回值为零且状态快照不变。这证明的是**同一数据库状态上的第二次执行**不会继续改写结果，并未模拟关闭后重新启动服务。参考 [同一状态重复迁移 ↗](../../../apps/server/tests/review-migration.test.ts#L238 "支持在同一个 Store 和 stateDir 上第二次迁移返回零且快照不变。")

另一个用例单独比较迁移前后的 fragment 总数，确认身份调整不会删除片段行；但它没有逐字段验证正文、时间戳及全部修订属性。参考 [片段数量保持 ↗](../../../apps/server/tests/review-migration.test.ts#L262 "支持迁移前后 fragment 总数一致，并界定该断言只检查数量。")

<a id="relation-lifecycle"></a>
## 显式失效处理让旧片段关系退出默认视图

测试先通过共享捕获接口让同一代码路径从 v1 前进到 v2，再创建当前的决策材料，并为 v1 片段与决策片段写入已确认的 `implements` 关系。参考 [旧片段关系建立 ↗](../../../apps/server/tests/review-migration.test.ts#L291 "支持通过捕获接口产生两个代码修订，并为旧代码片段写入已确认关系的测试流程。")

v2 已产生时，旧关系仍保持 `confirmed`；只有显式调用关系失效处理后，它才变为 `stale`。此后默认片段查询和当前路径追踪不再展示旧关系，而启用 stale 与 historical 选项仍可读取它。测试确认 v2 是当前修订，但没有证明系统会自动为 v2 建立新关系。参考 [显式关系失效行为 ↗](../../../apps/server/tests/review-migration.test.ts#L343 "支持新修订产生后旧关系仍暂为 confirmed，以及显式失效后默认隐藏、历史模式仍可读取的结论。")
