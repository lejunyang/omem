# 评审数据迁移与关系显式失效测试

该测试文件验证 repo-review 从内容哈希身份迁移到稳定路径身份时的冲突处理、历史保留与幂等性，并覆盖已过期 fragment 关系的显式失效。被替代的旧结论是“新修订会自动把既有旧关系标为 stale”；现有用例仅证明：在 v2 已产生后新建一条指向 v1 fragment 的 confirmed 关系，该关系会保持 confirmed，直至显式调用失效处理。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="migration-purpose"></a>
## 迁移目标与路径身份

旧评审数据以内容哈希作为 source external id；测试直接插入 source、head revision 与 fragment，并将文件路径写入 revision，复现迁移前结构。[旧内容哈希数据构造 ↗](../../../apps/server/tests/review-migration.test.ts#L40 "说明测试如何手工构造带文件路径、head revision 与 fragment 的迁移前 source。") 新身份改用 `omem:<仓库相对路径>`，使同一路径的内容修改累积为修订，而相同字节但路径不同的文件仍保持独立。[稳定路径身份设计 ↗](../../../apps/server/src/review/store.ts#L29 "支持同一路径跨内容修改累积修订、相同内容不同路径保持独立的身份设计。")

同一路径冲突时，用例断言版本与时间较新的旧 source 接管路径身份，较旧者保留原 external id、解除 head，并登记为历史别名；fragment 总数不变。[同路径迁移冲突断言 ↗](../../../apps/server/tests/review-migration.test.ts#L111 "支持较新 source 接管路径身份、落选 source 降级为历史别名且 fragment 不被删除。") 不同路径即使正文相同，迁移后也仍是两个具有当前 head 的 source。[相同内容不同路径测试 ↗](../../../apps/server/tests/review-migration.test.ts#L158 "支持内容相同但路径不同的文件迁移后仍为两个独立当前 source。")

<a id="migration-properties"></a>
## 历史保留、隔离与幂等性

落选 source 不会被删除：仍可用旧 external id 定位，其 revision、fragment 与 history 均可读取，只是不再是当前 head。[降级 source 的历史可读性 ↗](../../../apps/server/tests/review-migration.test.ts#L189 "支持落选 source 的旧 external id、revision、fragment 与 history 在迁移后继续可读。") repo-review 的元数据位于隔离的运行目录和 SQLite 中，不触碰个人工作区存储。[评审存储隔离边界 ↗](../../../apps/server/src/review/store.ts#L1 "说明 repo-review 使用隔离数据目录和 SQLite，不修改个人工作区存储。")

在同一 stateDir 上再次执行迁移会返回零，且 external id、head 与 alias 快照保持一致。[重复迁移幂等测试 ↗](../../../apps/server/tests/review-migration.test.ts#L220 "支持第二次迁移返回零，且 source 身份、head 与 alias 快照保持不变。") 这证明所覆盖场景具有重复执行的幂等性；材料仍未说明版本号和创建时间完全并列时的稳定胜者规则，也未验证迁移中途失败后的恢复。

<a id="relation-lifecycle"></a>
## 已过期片段关系的显式失效

关系用例先将代码源从 v1 捕获为 v2，之后才为 v1 fragment 与仍为 current 的决策 fragment 新建 confirmed 的 `implements` 关系；查询随即仍返回 confirmed。[先推进 head 后创建旧片段关系 ↗](../../../apps/server/tests/review-migration.test.ts#L306 "明确测试时序为先产生 v2、再为 v1 fragment 创建 confirmed 关系，并支持该新建关系在显式失效前仍按 confirmed 查询；同时限定了可推出结论的范围。") 因此，材料只能证明“对已过期 fragment 后建的 confirmed 关系，在显式失效前仍按 confirmed 查询”。此前“head 更新不会自动使既有关系 stale”的更强结论缺少先建关系、再推进 head 的时序证据，现已被替代。

调用 `invalidateStaleRelations` 后，测试断言一条关系变为 stale；默认 fragment 查询隐藏它，启用 `includeStale` 则仍可追溯。[显式失效与 stale 过滤 ↗](../../../apps/server/tests/review-migration.test.ts#L349 "支持显式失效更新一条关系，以及默认隐藏、includeStale 保留历史关系的查询行为。") 按代码路径查询时，新 head 没有替代关系，默认结果为空；同时启用历史和 stale 选项才返回旧关系，并确认 v2 仍是当前 revision。[代码路径历史查询断言 ↗](../../../apps/server/tests/review-migration.test.ts#L361 "支持新 head 默认没有替代关系、历史模式可返回旧关系，并确认 v2 为当前 revision。") 当前材料仅覆盖 source 端旧 fragment，尚不能确认目标端换 head、两端同时过期或批量关系的对称行为。
