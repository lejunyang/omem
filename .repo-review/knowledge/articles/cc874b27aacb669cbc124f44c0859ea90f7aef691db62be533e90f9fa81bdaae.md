# docs-implementation · 模块理解

该模块记录 omem 从 Batch 2 工程底座走向个人主助手、渐进记忆、统一知识流程和 Code Wiki 的设计与实施状态。其共同主线是保真保存原始材料，以固定修订和内联引用支撑检索、提炼、复核与行动；现有材料证明部分学习、飞书、知识阅读和中文检索链路已经落地，但持久主助手入口、完整质量发布门、多租户能力及若干跨版本和真实平台场景仍需进一步验收。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 模块职责与设计演进

本模块既保存设计目标，也记录实现切片、迁移规则和验收边界。v3 将飞书定位为主要对话入口、Web 定位为管理与第二入口，并替代“普通材料全部深度提炼、非自动通过就询问用户”的旧默认路径；既有数据、事务、任务、ACP、飞书和 UI 基础设施继续复用。[主助手 v3 定位与路径替换 ↗](../../../docs/implementation/assistant-v3/README.md#L3 "支持飞书与 Web 的入口定位、旧默认确认路径被替换以及既有基础设施继续复用。")

其核心原则是先找回原材料并保留上下文，再按实际任务、反复使用、纠正和来源变化渐进整理。低置信内容先作为来源保存，只有会影响用户行动且确需选择的问题才应打扰用户。[渐进记忆核心原则 ↗](../../../docs/implementation/assistant-v3/README.md#L7 "支持优先保存原材料、渐进整理、按需补证以及减少无效用户打扰的设计原则。") 子专题进一步把这些原则放入 Batch 2、知识流水线和当前状态的演进脉络中；这些派生章节只提供下钻入口，事实仍须沿其引用回到固定原文。[统一证据链与代码投影 ↗](f8c11c2b83ccb5d68da4c592f7ea00d013ca3a6aaa4702d6f2e383595e9b2eb6.md#purpose "支持实现文档以统一捕获和不可变证据链为主线，并说明 Code Wiki 不是独立事实源。")

<a id="architecture"></a>
## 主助手、证据与治理流程

设计中的持久 AssistantRuntime 连接飞书与 Web，会先构建当前事项、原件、记忆和纠正上下文，再经检索端口与受管理工具提出回答或变更；确定性授权、版本和证据策略控制写入，正式回复与变更通知经 outbox 投递。被动群聊、屏幕、Git 和文档则进入保真采集及后台整理，并由 Attention Gate 决定自动处理、推迟或转入交流。[主助手职责与总体流程 ↗](../../../docs/implementation/assistant-v3/README.md#L15 "支持 AssistantRuntime、上下文构建、检索、治理工具、策略控制、outbox 和后台 Attention Gate 的关系。")

Batch 2 子专题补充了这一底座的可靠性合同：固定材料由持久任务驱动角色化提炼和独立复核，租约、输入版本及取消状态共同阻止迟到结果覆盖新状态。[批次二端到端可靠性流程 ↗](b26b2801da1ba59559f15d4a295604f7de76247ed1018609fce4d74427fd36cc.md#purpose_flow "提供固定材料、持久任务、角色提炼、独立复核及迟到提交保护的子章节下钻入口。") Proposal、证据、不确定性和预期版本有统一结构，Extractor 与 Verifier 职责分离，角色本身无权绕过领域服务直接应用变更。[候选合同与角色边界 ↗](b26b2801da1ba59559f15d4a295604f7de76247ed1018609fce4d74427fd36cc.md#contracts_roles "提供 Proposal 结构、固定证据、Extractor 与 Verifier 分工及角色权限边界的子章节入口。")

<a id="relationships"></a>
## 跨入口路由与统一知识链

交互与采集必须分流：绑定 owner 私聊和明确提及进入助手会话，群背景消息、截图及应用切换默认只采集和索引；群内回答不得泄漏私人记忆。会话按主体、渠道、聊天和线程区分，Web 与飞书只有在用户明确关联时才共享同一 conversation；重启、取消和已投递状态也必须持久恢复。[消息与会话路由规则 ↗](../../../docs/implementation/assistant-v3/README.md#L43 "支持交互和采集分流、群聊隐私边界、跨入口会话关联、持久恢复及取消语义。")

更广的实现文档把手工、文件、Git、飞书和代码都归入 Capture→Source／Revision／Fragment 证据链。知识正文是不可变派生视图，Code Wiki 是可重建的代码投影，而非第二事实源。[统一证据链与代码投影 ↗](f8c11c2b83ccb5d68da4c592f7ea00d013ca3a6aaa4702d6f2e383595e9b2eb6.md#purpose "支持实现文档以统一捕获和不可变证据链为主线，并说明 Code Wiki 不是独立事实源。") KnowledgePipeline 负责分析、独立复核和发布，共享 Evidence Trail 再把正文内联引用逐层带回知识章节、原始材料或代码目标。[知识发布与共享阅读流程 ↗](f8c11c2b83ccb5d68da4c592f7ea00d013ca3a6aaa4702d6f2e383595e9b2eb6.md#flow "提供从捕获、分析、独立复核到 Evidence Trail 追溯阅读的子章节入口。")

<a id="progress_limits"></a>
## 当前进展、验证边界与未决事项

历史专题显示受控学习、生产飞书 Host、即时通知和部分真实 ACP／飞书路径已经接通，但设计当时仍明确指出普通 owner 私聊未进入可用主助手，跨入口话题续接也缺少当前实现证据。[主助手入口的历史缺口 ↗](3d8bcd6d032e82be0c09f76762de7b216dd197fd8e859d1d4d828cbee0f41987.md#progress "支持区分已实现的 Batch 2 基础设施与当时尚未接通的持久主助手、owner 私聊及会话续接。") 质量方面，开发样本仍曾处于未确认草稿状态，冻结 holdout、短窗合并、定时摘要以及若干真实故障场景没有达到完整发布门。[质量门与平台能力限制 ↗](b26b2801da1ba59559f15d4a295604f7de76247ed1018609fce4d74427fd36cc.md#progress_limits "支持开发草稿、冻结 holdout、通知聚合、真实平台场景和单用户边界仍不完整的判断。")

较新的状态专题记录了中文向量检索和来源更新重核验闭环等进展，说明部分旧限制已被替代；小样本检索结果和行为测试仍不能外推为整体质量或真实外部网络验收。[最新能力闭环 ↗](8cacd4aed1115e3d8ab47054816bd07d2ac3d155756ba0127a3028ac0c880fd6.md#current-capabilities "支持中文语义检索和来源更新重核验已经形成新闭环，同时限定小样本结果的解释范围。")[验收结果与历史替代关系 ↗](8cacd4aed1115e3d8ab47054816bd07d2ac3d155756ba0127a3028ac0c880fd6.md#verification-boundaries "支持区分真实模型、fixture、模拟恢复等不同证据强度，并说明旧限制可能已被后续实现替代。") 当前架构仍以个人单用户 SQLite 为边界，跨文件调用和跨修订符号或片段身份续接尚未完成，代码变化后仍需重新同步定位。[仍有效的架构边界 ↗](8cacd4aed1115e3d8ab47054816bd07d2ac3d155756ba0127a3028ac0c880fd6.md#architecture-limits "支持单用户实现、跨文件调用和跨修订身份续接等当前仍有效的限制。")
