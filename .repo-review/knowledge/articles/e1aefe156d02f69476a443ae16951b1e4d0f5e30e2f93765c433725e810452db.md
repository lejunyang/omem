# 统一检索端口：连接原文、知识与已应用状态

RetrievalPort 是读者界面、助手和 Agent 共用的服务端检索合同。它统一描述查询意图、可见范围、返回目标和证据锚点，同时保留面向旧处理流程的原文候选、记忆检索与固定证据回读接口；具体的词法、符号、向量和重排策略由实现模块承担。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 为什么需要统一端口

`RetrievalPort` 解决的是多个入口各自搜索、结果语义不一致的问题：读者、助手与 Agent 可以共享同一套查询合同，但原文、知识讲解、记忆和事项仍是不同类型的结果；面向旧处理器的原文专用方法也继续保留。参考 [共享检索职责 ↗](../../../apps/server/src/retrieval/port.ts#L1 "支持端口服务读者、助手和 Agent，同时区分不同检索单位并保留原文兼容方法的论断。")

一个命中不是“引用的别名”。`RetrievalHit` 自带可读正文、上下文、标题路径、分数和召回路线，并用 `target` 指明真正可打开的对象；`references` 则把派生讲解继续连回固定原文。目标类型覆盖固定原文锚点、知识章节、记忆与事项。参考 [检索目标类型 ↗](../../../apps/server/src/retrieval/port.ts#L23 "说明统一目标如何分别表示固定原文、知识章节、记忆和事项。")、[可读命中结构 ↗](../../../apps/server/src/retrieval/port.ts#L43 "支持命中包含可读内容、上下文、召回路线、目标、原文引用和来源信息，而非仅是引用别名。")

<a id="flow"></a>
## 一次材料搜索怎样经过端口

以 Agent 搜索材料为例：调用方把问题、数量、可见性、用途、材料角色和有效时间组成 `SearchQuery`，并限定 `kinds: ["source"]`；调用 `search` 后，只把原文目标转换为带路径、行号、摘要和召回路线的结果。参考 [Agent 材料搜索调用 ↗](../../../apps/server/src/knowledge/agent-research.ts#L442 "给出代表性跨文件调用：构造 SearchQuery、调用 retrieval.search，并把原文命中转为带行号的工具结果。")

```mermaid
flowchart LR
  A[搜索问题与用途] --> B[RetrievalPort.search]
  B --> C[词法与符号候选]
  C --> D[可选语义检索与重排]
  D --> E[用途加权、去重与限量]
  E --> F[可读命中与固定目标]
```

当前 `UnifiedRetrieval` 先同步索引并生成词法、符号候选；空查询、精确查找或未加载向量模型时直接走词法分支。否则加入语义候选，语义失败也回退到词法结果；配置了重排器时再处理有限候选池。参考 [词法与符号入口 ↗](../../../apps/server/src/retrieval/unified.ts#L413 "支持统一实现先同步索引、生成词法和符号候选，并在空查询、精确查找或无向量模型时直接完成结果。")、[语义融合与降级 ↗](../../../apps/server/src/retrieval/unified.ts#L461 "支持语义检索失败回退、候选融合和可选交叉编码器重排的当前实现流程。") 最终阶段按 `purpose` 调整知识、代码、记忆或事项的偏好，默认限制同一所有者的重复结果，组装 `RetrievalHit` 并执行 `limit`。参考 [用途加权与结果组装 ↗](../../../apps/server/src/retrieval/unified.ts#L515 "支持按查询用途加权、去重、生成可读命中并执行数量限制的输出阶段。")

<a id="boundaries"></a>
## 边界、兼容接口与修改入口

项目范围不能从应用名、会话或运行上下文猜测；只有已确认的项目关系才能令 `project_trusted=true`，否则实现必须保持工作区级召回。这是防止错误缩小搜索范围的硬边界。参考 [可信项目范围 ↗](../../../apps/server/src/retrieval/port.ts#L79 "支持只有确认项目关系才能启用项目过滤，未知或不可信关系必须保持工作区召回的边界。") 时间也分两类：`timeRange` 过滤捕获版本时间，`effectiveAt` 才表示读者询问的生效时间；`visible`、`kinds`、正式主题路径和材料角色都是调用方显式传入的约束。参考 [显式查询约束 ↗](../../../apps/server/src/retrieval/port.ts#L97 "说明捕获时间、可见性、去重、用途、结果类型、主题、材料角色和生效时间等查询字段的含义。")

兼容方法各有职责：`searchSources`/`searchSourcesAsync` 只投影原文 Fragment 候选，`searchMemories` 查已应用记忆，`readEvidence` 按版本与片段回读不可变证据，`health` 报告后端状态。当前统一实现会把结果中的原文引用去重并投影回 Fragment，因此旧处理器仍可使用固定锚点。参考 [兼容端口方法 ↗](../../../apps/server/src/retrieval/port.ts#L154 "说明原文同步与异步搜索、记忆搜索、固定证据回读和健康检查的接口职责。")、[原文候选投影 ↗](../../../apps/server/src/retrieval/unified.ts#L624 "支持当前实现将统一命中的原文引用去重并投影为旧处理器需要的 Fragment 候选。") 若要改“允许查询什么、返回什么”，修改本端口；若要改召回融合、用途加权或重排，应进入 `UnifiedRetrieval`，不要把算法细节塞回接口类型。
