# 统一检索端口：让原件、知识与状态共享一种查询语言

RetrievalPort 是阅读器、助手与 Agent 工具之间的检索边界：它统一查询意图、可见性和结果形态，同时保留原始证据锚点；实际排序由 UnifiedRetrieval 等实现完成，旧处理器仍可通过 Fragment 兼容接口取回不可变原文。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-model"></a>
## 为什么需要统一检索合同

`RetrievalPort` 解决的是“不同消费者如何搜索同一知识空间”的问题：阅读页面、助手和 Agent 工具不必各自理解存储结构，且原件、派生讲解、已应用记忆与事项仍作为不同结果存在。面向旧处理器的原件接口继续保留 Fragment 锚点。参考 [统一检索职责 ↗](../../../apps/server/src/retrieval/port.ts#L1 "支持端口服务多类消费者、区分结果类型并保留原件锚点的定位。")

结果目标用联合类型区分 `source`、`knowledge`、`memory`、`task`：原件锚点带修订、摘要、行号和 Fragment；知识命中指向文章修订与章节；记忆和事项指向有版本的实体。参考 [检索目标类型 ↗](../../../apps/server/src/retrieval/port.ts#L19 "支持 source、knowledge、memory、task 四类目标及其定位字段。") `RetrievalHit` 则同时返回可读正文、上下文、标题路径、分数、命中路线和精确目标；`references` 让讲解或状态仍能回到原始证据，知识结果还可携带可操作引用。参考 [统一命中结构 ↗](../../../apps/server/src/retrieval/port.ts#L33 "支持命中正文、上下文、目标、原始引用、知识引用和来源字段的说明。")

<a id="representative-call"></a>
## 一条代表性调用如何流动

以知识库搜索“证据排序”为例：HTTP 层清理查询，默认选择 `concept`，并把 `kinds=["knowledge"]`、分类路径和上限 50 交给 `search`；返回后只接受当前文章修订，并把命中章节、摘录、分数和路线交给页面。参考 [知识搜索调用 ↗](../../../apps/server/src/knowledge/api.ts#L100 "证明知识 API 如何构造 SearchQuery，并把 RetrievalHit 转成文章章节搜索结果。")

```mermaid
flowchart LR
  A[知识搜索请求] --> B[SearchQuery]
  B --> C[RetrievalPort.search]
  C --> D[UnifiedRetrieval]
  D --> E[RetrievalHit 列表]
  E --> F[章节搜索结果]
```

运行时工厂实际创建 `UnifiedRetrieval`，按配置注入中文向量模型与可选重排器，并启动后台同步。参考 [检索实现装配 ↗](../../../apps/server/src/retrieval/factory.ts#L14 "证明工厂创建 UnifiedRetrieval、注入向量与重排模型并启动后台工作。") 实现先生成词法候选；空查询、精确查找或模型未就绪时直接完成词法结果。否则它计算查询向量，筛选合格单位；向量异常时降级回词法结果。参考 [词法与语义分支 ↗](../../../apps/server/src/retrieval/unified.ts#L323 "支持词法优先、向量检索及异常时回退词法结果的流程。") 随后语义候选经过动态门槛，与词法分支融合；若配置了重排器，再对候选池评分，失败只记录降级状态，最终仍进入统一收尾。参考 [融合与重排 ↗](../../../apps/server/src/retrieval/unified.ts#L372 "支持语义门槛、词法语义融合和可选交叉编码器重排的说明。")

收尾阶段按 `purpose` 调整知识、代码、记忆或事项的偏好，默认限制同一所有者的重复结果，并构造带目标、原始引用、来源和命中路线的 `RetrievalHit`。参考 [用途权重 ↗](../../../apps/server/src/retrieval/unified.ts#L423 "支持 concept、implementation、background、follow-up 对不同结果类型的偏好。") [结果收尾 ↗](../../../apps/server/src/retrieval/unified.ts#L461 "支持多样化、摘录、知识引用恢复和 RetrievalHit 输出字段的说明。") 助手消费同一结果时，会沿 `references` 恢复可见的原文片段，把非原件命中作为背景，因而“讲解”不会取代它依赖的证据。参考 [助手消费检索结果 ↗](../../../apps/server/src/assistant/runtime.ts#L816 "证明助手沿命中引用恢复原文，并把非原件命中作为背景。")

<a id="boundaries-and-change-points"></a>
## 边界条件与修改入口

查询合同把几个容易混淆的边界写死：项目过滤只能基于已确认的项目关系；不可信时必须保持工作区召回。`timeRange` 指捕获修订时间，不是事件时间或历史时点；`visible` 要在最终排序和截断前生效；`purpose` 由读者或 Agent 明示，分类路径也独立于引用目录；`diversify=false` 才保留未多样化的融合顺序。参考 [查询边界 ↗](../../../apps/server/src/retrieval/port.ts#L68 "支持可信项目、时间、可见性、多样化、用途、种类和分类路径的合同语义。")

修改时应按职责落点：新增查询字段或结果保证改端口；调整词法、语义融合、重排和用途权重改统一实现；切换模型装配改工厂。端口中的 `search` 与异步原件搜索是可选能力，调用者必须允许回退；同步原件搜索、记忆搜索、证据读取和健康状态则是必需能力。参考 [端口方法 ↗](../../../apps/server/src/retrieval/port.ts#L139 "支持可选统一搜索、兼容原件搜索以及必需证据读取与健康检查的职责划分。") 当前实现已对种类、分类、可见性、时间及可信项目记忆做资格过滤，但未在该过滤流程中读取 `scope`，所以不能仅凭类型名断言三种 scope 已具有不同运行语义。参考 [实现资格过滤 ↗](../../../apps/server/src/retrieval/unified.ts#L218 "显示当前统一实现检查的实际过滤项，并支持 scope 运行语义仍不明确的判断。")
