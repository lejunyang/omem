# 飞书通知投递的持久化、重试与绑定安全验收

这组验收测试验证应用变更进入飞书通知后，在进程重启、发送结果不确定、限流、鉴权失败、聚合发送、定时摘要和连接换绑等场景中的持久化与安全边界。测试通过真实 SQLite 仓储和加密密钥存储运行，但以 FakeMessages 替代飞书网络接口，因此证明的是本地投递状态机及数据映射，不代表真实飞书 API 已完成联调。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-boundary"></a>
## 解决通知不可靠与重复执行问题

业务变更不能因服务重启而丢失，也不能为了补发通知重新执行任务。测试先应用一次任务，确认生成待投递记录；关闭并重新打开 Store 后，worker 继续处理同一 outbox，最终只发送一条消息、任务仍只有一条，并保存平台消息号。参考 [重启后继续投递 ↗](../../../apps/server/tests/lark-delivery.test.ts#L172 "支持 outbox 跨进程重启保留、任务不重放且投递结果被持久化的断言。")

这与 Store 所声明的单用户 SQLite 基础一致：不可变修订、变更和通知 outbox 被设计为共同提交，团队级数据库与租户约束仍是后续迁移事项。参考 [SQLite 持久化边界 ↗](../../../apps/server/src/store.ts#L4 "说明 Store 当前以单用户 SQLite 为基础，并将变更与通知 outbox 共同提交。")

<a id="retry-and-failure"></a>
## 按错误性质收敛投递状态

投递器把外部失败区分为限流、鉴权、永久失败和结果不确定，并通过适配器携带稳定 UUID 发送卡片。参考 [投递错误与消息适配器 ↗](../../../apps/server/src/integrations/lark/delivery.ts#L24 "定义错误分类以及发送、更新消息时使用的适配器合同。")

当响应丢失时，一小时内的重试沿用同一 UUID，以降低重复消息风险；超过窗口的悬挂发送被标为 `unknown`，且不再盲目重发。参考 [不确定发送的重试窗口 ↗](../../../apps/server/tests/lark-delivery.test.ts#L212 "支持同一 UUID 重试及超时后转为 unknown、不继续发送的行为。") 限流错误遵循返回的等待时间，随后若遇到鉴权错误则投递失败、连接失效、目标禁用，同时断言错误记录不会泄露密钥。参考 [限流、鉴权与脱敏 ↗](../../../apps/server/tests/lark-delivery.test.ts#L260 "支持限流延迟、鉴权失败禁用连接和目标，以及错误信息不泄露密钥的断言。")

这些断言覆盖状态迁移和脱敏结果，但没有证明真实飞书服务是否按 UUID 幂等，也没有覆盖 worker 并发竞争、网络超时组合及消息更新接口的实际行为。

<a id="aggregation-and-binding"></a>
## 聚合通知仍保留逐项追踪

即时模式为每项变更建立独立 intent、摘要指纹、平台 UUID 和变更映射，确保通知可追溯。参考 [即时通知逐项映射 ↗](../../../apps/server/tests/lark-delivery.test.ts#L300 "支持每个变更拥有独立 intent、UUID、摘要和追踪映射。") 窗口模式则在截止后把五项变更合成一条摘要，将其余 intent 标为已被取代，但仍保留全部 change 映射；worker 最终只发送一次。参考 [窗口聚合与发送 ↗](../../../apps/server/tests/lark-delivery.test.ts#L330 "支持窗口内多项变更合并、旧 intent 取消但映射保留，以及最终单次发送。") 定时模式还验证上海时区的下一次摘要边界，并在到期后形成一条即时可发送摘要。参考 [定时摘要边界 ↗](../../../apps/server/tests/lark-delivery.test.ts#L415 "支持按上海本地时间计算下一次发送边界并聚合到单条摘要。")

换绑是明确的安全边界：旧绑定产生的 intent 不会被转发到新会话，而是取消；记忆恢复产生的新通知使用新绑定，卡片中也不得出现 localhost 或回环地址。参考 [换绑与恢复通知隔离 ↗](../../../apps/server/tests/lark-delivery.test.ts#L471 "支持旧绑定消息取消、新通知使用新绑定，以及卡片不包含本地地址的安全边界。") 该测试由 `ApplicationRepository` 产生变更与投递记录，并通过 `MemoryService.restoreMemory` 验证恢复流程，但提供材料未展示这些模块内部如何原子写入或构造卡片，因此这里只确认可观察结果。
