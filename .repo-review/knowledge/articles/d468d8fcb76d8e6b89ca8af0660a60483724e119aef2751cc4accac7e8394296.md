# Lark 外部通知投递验收测试

该测试以临时 SQLite、加密密钥存储和可编程消息适配器验证 Lark 通知的持久化投递语义，覆盖进程重启、模糊失败重试、限流与鉴权失败、窗口及定时聚合、绑定替换和恢复通知安全；它验证的是应用、存储与投递模块的本地集成合同，并不等同于真实飞书网络联调。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_fixture"></a>
## 问题与测试夹具

这组验收测试解决“业务变更已落库，但外部通知是否可靠、可追踪且不会错投”的问题。夹具为每个用例创建临时 `Store` 与独立加密密钥目录，并在结束后关闭数据库、删除目录；连接、版本、绑定和通知目标则直接写入 SQLite，以构造明确的投递前置状态。[临时存储与连接种子夹具 ↗](../../../apps/server/tests/lark-delivery.test.ts#L21 "支持测试创建并清理临时存储资源，以及构造独立 Store、密钥目录和连接前置状态的说明。")

`FakeMessages` 记录 send/update 参数，并可按顺序返回消息 ID 或抛出错误，因此测试能够精确控制模糊响应、限流和鉴权失败；这也意味着覆盖的是 `LarkMessageAdapter` 合同及 worker 状态机，而非真实 SDK、网络或飞书租户行为。[可编程消息适配器 ↗](../../../apps/server/tests/lark-delivery.test.ts#L40 "说明测试替身如何记录调用并注入发送或更新结果，也界定其不是真实网络联调。")

<a id="durability_retry"></a>
## 持久化、重试与失败隔离

重启用例先应用任务并确认 outbox 为 pending，再关闭、重开同一数据目录，只运行投递 worker；断言任务仍只有一条、消息仅发送一次，intent 最终保存 delivered 与平台 message ID，证明恢复投递不需要重放业务应用。[进程重启后的 outbox 投递 ↗](../../../apps/server/tests/lark-delivery.test.ts#L172 "支持重开数据库后无需重放应用即可完成投递，并保持任务唯一和记录消息 ID 的断言。")

模糊发送失败在一小时内进入 retry_wait，重试复用同一个 provider UUID；超过窗口的遗留 sending intent 被标为 unknown，且不再次发送。[模糊发送的 UUID 重用与超时终止 ↗](../../../apps/server/tests/lark-delivery.test.ts#L212 "支持一小时内复用 UUID 重试、超时后转为 unknown 且不继续发送的状态合同。") 限流错误遵循 retry-after 设置下次尝试时间；随后鉴权失败会令 intent 失败、连接失败、目标禁用，并断言持久化错误不泄漏 client secret。[限流与鉴权失败处理 ↗](../../../apps/server/tests/lark-delivery.test.ts#L260 "支持 retry-after、连接失效、目标禁用以及错误信息脱敏的断言。")

<a id="aggregation_traceability"></a>
## 聚合策略与逐变更追踪

即时模式为五次变更建立五个独立 intent、五个唯一 provider UUID 和五条 change 映射，并要求 payload digest 为固定长度，从而保持每次变化可追踪。[即时通知逐变更映射 ↗](../../../apps/server/tests/lark-delivery.test.ts#L300 "支持每个即时变更具有独立 intent、UUID、摘要和映射记录的追踪性说明。") 窗口模式最初存在五个待处理 intent；到期合并后只保留一个关联全部五项 change 的摘要 intent，其余四个 intent 被标记为 cancelled，且 `superseded_by` 指向该活动项，最终仅调用一次发送。测试只保证映射集合完整，不保证毫秒时间戳相同时的插入顺序。[窗口通知聚合 ↗](../../../apps/server/tests/lark-delivery.test.ts#L330 "支持合并前存在五个 pending intent，合并后保留一个关联全部 change 的活动摘要、四个取消项指向该活动项，并仅发送一次；同时限定不能断言活动项必为新建或全部原 intent 均被取消。") 这替代了“新 intent 关联全部 change、全部旧 intent 均被取消”的过度概括：材料既未证明活动项一定是新建记录，也明确只断言四项被取消。

定时模式还验证上海时区 09:00 的下一边界：边界前安排当天发送，错过后安排次日；到期聚合后生成一个 instant 摘要，并保留所有 change 映射。[本地时间定时摘要 ↗](../../../apps/server/tests/lark-delivery.test.ts#L415 "支持上海时区下一投递边界以及到期后聚合全部变更的断言。")

<a id="binding_boundary"></a>
## 绑定边界、模块关系与未覆盖行为

绑定替换场景先让旧绑定 superseded、旧目标 disabled，再建立新绑定。worker 不会把旧 intent 转发到新会话，而是取消旧目标上的待投递项；随后 `MemoryService.restoreMemory` 产生的新变更会使用新绑定，且卡片负载不得包含 localhost 或 127.0.0.1。[绑定替换与恢复通知 ↗](../../../apps/server/tests/lark-delivery.test.ts#L471 "支持旧 intent 不跨绑定转发、恢复操作使用新绑定及卡片排除本机地址的结论。")

现有断言未覆盖真实 Lark SDK 请求、update 路径、并发 worker 的租约竞争、数据库写入中途崩溃，以及夏令时地区的定时边界；测试通过可控适配器顺序驱动发送，因此它是本地集成验收，不应被解释为端到端线上可用性证明。[消息替身暴露的测试边界 ↗](../../../apps/server/tests/lark-delivery.test.ts#L40 "测试仅实例化可控适配器并记录 send/update，支持真实 SDK、并发和崩溃行为尚未由本文件验证的边界判断。")
