# Lark 通知投递验收测试

该测试以临时 SQLite、加密凭据仓库和可编程消息替身覆盖 Lark 通知的持久化、重试、即时映射、聚合、定时调度、绑定隔离及恢复通知。它验证的是组件状态机和数据库结果，并不等同于真实 Lark SDK、网络故障或并发 worker 的端到端验收。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_fixture"></a>
## 测试目标与隔离夹具

本文件验证业务变更落库后，外部通知在延迟、失败和进程重启条件下仍可追踪。每个用例创建临时 `Store`、SQLite 文件和加密 secret，种入连接、绑定及通知目标，结束后关闭数据库并删除目录。[临时存储与连接夹具 ↗](../../../apps/server/tests/lark-delivery.test.ts#L62 "支持每个测试创建临时 Store、加密凭据、连接、绑定和通知目标，并在结束后清理资源的说明。") `FakeMessages` 记录 `send`、`update` 参数并按序返回成功或错误，因此测试可以精确观察投递状态机，但不会访问真实飞书服务。[可编程消息替身 ↗](../../../apps/server/tests/lark-delivery.test.ts#L40 "支持测试记录发送与更新调用、注入结果且不访问真实 Lark 网络的说明。")

任务入口通过 `Store.applications.applyTask` 制造业务变更，随后按 `change_id` 查询 Lark intent；这证明该测试如何把应用结果与投递记录关联起来，而不只是依赖模块导入。[任务应用与投递记录关联 ↗](../../../apps/server/tests/lark-delivery.test.ts#L141 "支持 applyTask 通过应用仓库创建任务变更，并按 change ID 查询对应 Lark intent 的测试流程。")

<a id="delivery_states"></a>
## 持久化、重试与失败状态

重启用例先写入任务和 pending intent，再关闭并重开同一数据目录，由单个 `LarkDeliveryWorker` 继续处理；最终 intent 为 delivered、保存消息 ID，任务数仍为一，说明恢复投递没有重放业务应用。[重启后继续投递 ↗](../../../apps/server/tests/lark-delivery.test.ts#L173 "支持数据库重开后由 repository 和单个 worker 完成投递、保存消息 ID且不重复创建任务的结论。") 模糊发送在一小时窗口内复用同一 provider UUID 重试，超过窗口的 sending 记录转为 unknown，且不产生额外发送。[模糊发送重试窗口 ↗](../../../apps/server/tests/lark-delivery.test.ts#L212 "支持一小时内复用 UUID 重试以及超时后转为 unknown、不再发送的状态边界。")

限流错误按照 `retryAfterMs` 推迟下一次尝试；后续认证失败会使 intent 失败、连接转为 failed、目标被禁用，同时持久化错误不得泄露 secret。[限流、认证失败与脱敏 ↗](../../../apps/server/tests/lark-delivery.test.ts#L260 "支持限流退避、认证失败禁用连接和目标，以及持久化错误隐藏 secret 的断言。") 这些断言验证的是已分类错误进入 worker 后的状态迁移，不能直接证明真实 SDK 错误一定会被正确分类。

<a id="aggregation_binding"></a>
## 即时映射、聚合策略与绑定隔离

即时模式为五次变更保留五个独立 intent：每条拥有对应 change、唯一 provider UUID、64 位 payload digest，并各有一条映射记录。[即时通知独立映射 ↗](../../../apps/server/tests/lark-delivery.test.ts#L300 "直接支持即时模式生成五个独立 intent、唯一 provider UUID、64 位摘要及逐变更映射的结论。") 这项契约与窗口聚合相互独立；窗口模式到期后才把五个待处理项合成一个摘要 intent、取消四个被替代项、保留全部 change 映射，并只发送一次。[窗口聚合与变更保留 ↗](../../../apps/server/tests/lark-delivery.test.ts#L330 "支持 batcher 将到期通知合成单个摘要、取消被替代 intent、保留全部映射并只发送一次。") 定时模式另行验证上海时区下一次 09:00 边界，以及摘要生成后恢复为可立即投递的 instant 状态。[本地时间定时摘要 ↗](../../../apps/server/tests/lark-delivery.test.ts#L415 "支持上海时区调度边界、定时 intent 属性及到期聚合后恢复即时投递状态的说明。")

绑定替换后，旧目标上的 intent 被取消且不会转发到新会话；`MemoryService.restoreMemory` 产生的新变更则使用当前绑定，卡片载荷也不得含 localhost 或回环地址。[替换绑定与记忆恢复 ↗](../../../apps/server/tests/lark-delivery.test.ts#L471 "支持旧 intent 不跨绑定转发，以及 restoreMemory 产生的新 intent 使用当前绑定且载荷无本地地址。")

<a id="relations_limits"></a>
## 模块协作与未覆盖边界

测试中的职责由实际调用分别体现：`Store` 初始化 `ApplicationRepository`，为应用入口提供数据库依赖；[Store 的应用仓库装配 ↗](../../../apps/server/src/store.ts#L38 "支持 Store 创建 SQLite 数据库并初始化 ApplicationRepository 等运行组件的职责说明。") `applyTask` 产生可查询的变更与 intent，[任务应用与投递记录关联 ↗](../../../apps/server/tests/lark-delivery.test.ts#L141 "支持 applyTask 通过应用仓库创建任务变更，并按 change ID 查询对应 Lark intent 的测试流程。") repository 和 worker 领取并完成投递，[重启后继续投递 ↗](../../../apps/server/tests/lark-delivery.test.ts#L173 "支持数据库重开后由 repository 和单个 worker 完成投递、保存消息 ID且不重复创建任务的结论。") batcher 合并到期通知，[窗口聚合与变更保留 ↗](../../../apps/server/tests/lark-delivery.test.ts#L330 "支持 batcher 将到期通知合成单个摘要、取消被替代 intent、保留全部映射并只发送一次。") 而 `restoreMemory` 触发恢复版本后的新投递记录。[替换绑定与记忆恢复 ↗](../../../apps/server/tests/lark-delivery.test.ts#L471 "支持旧 intent 不跨绑定转发，以及 restoreMemory 产生的新 intent 使用当前绑定且载荷无本地地址。") 这取代了仅凭导入列表推断全部模块职责的旧结论。

边界上，生产适配器合同同时声明 `send` 与 `update`，[Lark 消息适配器合同 ↗](../../../apps/server/src/integrations/lark/delivery.ts#L35 "支持生产适配器同时具有 send 与 update 方法，并界定测试尚需验证更新行为的背景。") 但当前夹具只是记录两类调用，现有验收路径主要断言发送结果。[可编程消息替身 ↗](../../../apps/server/tests/lark-delivery.test.ts#L40 "支持测试记录发送与更新调用、注入结果且不访问真实 Lark 网络的说明。") 各可靠性用例展示的也是单 worker 顺序执行，[重启后继续投递 ↗](../../../apps/server/tests/lark-delivery.test.ts#L173 "支持数据库重开后由 repository 和单个 worker 完成投递、保存消息 ID且不重复创建任务的结论。")[模糊发送重试窗口 ↗](../../../apps/server/tests/lark-delivery.test.ts#L212 "支持一小时内复用 UUID 重试以及超时后转为 unknown、不再发送的状态边界。") 因而尚不能据此确认真实 SDK 鉴权与 HTTP 错误映射、消息更新失败策略、多个 worker 的租约竞争，或远端成功而本地确认前崩溃时的端到端结果。
