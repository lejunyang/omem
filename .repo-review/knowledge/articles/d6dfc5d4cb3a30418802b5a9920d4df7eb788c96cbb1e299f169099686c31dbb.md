# 消息纠正的保存、作用域与重新处理

该模块把用户对已保存消息的纠正保存为独立原始材料，并提供消息级或会话级生效查询、完整历史查询、幂等保存、撤销和重试。新增、撤销或重试会为原 source 排入 extract_claims 作业；本模块本身不直接改写推断事实。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_and_interface"></a>
## 模块把纠正保存为独立材料

当用户需要纠正系统对一条消息的理解时，本模块接收 `requestId`、纠正文案和作用域。`requestId` 必须是 UUID；文案会去除首尾空白，长度为 1–2000；作用域只能是 `message` 或 `conversation`，省略时默认 `message`。设计意图是把本人纠正保存成新的原始材料，而不是直接写入推断事实。参考 [纠正输入与设计意图 ↗](../../../apps/server/src/messages/feedback.ts#L5 "支持 requestId、正文长度、作用域默认值，以及纠正保存为原始材料而非直接写入推断事实。")

`MessageFeedback` 对外提供两种彼此独立的读取能力：`forSource(sourceId)` 只查仍处于 active 状态、对该 source 生效的反馈；`history(sourceId)` 则查直接属于该 source 的全部反馈，并保留每条记录的 active 状态。前者适合取得当前有效输入，后者适合回看提交历史；仅凭本模块不能断言调用方会把两者合并成同一个输出或如何展示。参考 [有效反馈与历史查询 ↗](../../../apps/server/src/messages/feedback.ts#L23 "支持 forSource 的 active 与会话作用域规则，以及 history 按 source 返回完整状态历史的差异。")

<a id="save_flow"></a>
## 保存如何形成可追溯材料并触发重处理

`save(messageId, input)` 会再次校验输入，并在事务中按消息 ID 查找已保存的原 revision；找不到时以“请先保存原消息，再补充理解”终止。`requestId` 同时充当幂等键：若已有记录的 source、正文和作用域都一致，返回 `duplicate: true`；同一 ID 对应不同反馈则报错。参考 [保存前置条件与幂等检查 ↗](../../../apps/server/src/messages/feedback.ts#L45 "支持保存前查找原 revision、原消息未保存时的错误，以及 requestId 重复和冲突处理。")

首次保存时，模块创建一个 `manual` 来源的捕获材料。材料正文同时包含原消息片段和“我的纠正”，上下文记录会话 ID 与 `message-feedback` 事件，provenance 标记 owner 身份；这次 capture 自身关闭 `learning` 与 `notify`。随后反馈表记录 request ID、原 source、会话、作用域、正文和纠正 revision，并调用 `reconsider`。成功结果返回反馈 ID、纠正材料的 `revisionId`、重新处理的 `jobId` 以及 `duplicate: false`。参考 [纠正材料捕获与落库 ↗](../../../apps/server/src/messages/feedback.ts#L67 "支持纠正材料的正文、上下文、provenance、capture 选项、反馈落库及保存返回值。")

`reconsider` 不直接改写任何推断结果，而是读取原 source 的当前 head 与有效性 epoch，排入一个 `extract_claims` 作业；输入还带有 `feedbackId`，作业原因是 `owner_correction`。因此本文件能确认的后续边界是“触发重新提取”，至于下游如何把反馈组织进提示上下文、怎样解释或刷新其他页面，需要由相应实现另行证明。参考 [重新提取作业 ↗](../../../apps/server/src/messages/feedback.ts#L142 "支持重新处理读取 source head 和 validity epoch，并以 owner_correction 原因排入 extract_claims 作业。")

<a id="scope_revoke_retry"></a>
## 作用域、撤销与重试的边界

`forSource` 先从目标 source 当前 revision 的上下文读取 `conversationId`，再返回 active 反馈：直接属于目标 source 的记录会命中；此外，`scope='conversation'` 且会话 ID 相同的记录也会命中。结果按创建时间和 ID 排序，并为每项生成对应的纠正材料 key。相比之下，`history` 只按原始 `source_id` 查询，不过滤 active，因此撤销记录仍留在历史中。参考 [有效反馈与历史查询 ↗](../../../apps/server/src/messages/feedback.ts#L23 "支持 forSource 的 active 与会话作用域规则，以及 history 按 source 返回完整状态历史的差异。")

`revoke(id)` 只接受仍 active 的记录，将其更新为非活动状态，然后以新的随机反馈 ID 对原 source 再次调用 `reconsider`；已撤销或不存在的 ID 会报错。`retry(messageId)` 不新建反馈，而是重新找到该消息的原 revision，并为其 source 再次排入处理；原消息尚未保存时会报错。这两条路径都复用同一重新提取机制。参考 [撤销与手动重试 ↗](../../../apps/server/src/messages/feedback.ts#L119 "支持软撤销、撤销后重新处理，以及按消息 revision 手动重试的条件与行为。") [重新提取作业 ↗](../../../apps/server/src/messages/feedback.ts#L142 "支持重新处理读取 source head 和 validity epoch，并以 owner_correction 原因排入 extract_claims 作业。")
