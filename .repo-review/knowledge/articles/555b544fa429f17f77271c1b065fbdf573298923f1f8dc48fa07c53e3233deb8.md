# storage · 模块理解

storage 模块以 SQLite 迁移建立持久化边界，并通过规范摘要、事务、幂等回执和乐观锁，原子应用记忆与任务变更，同时记录修订、证据依赖、通知及外部投递意图。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="responsibility"></a>
## 职责与背景

storage 是服务端的持久化基础：顺序迁移逐步承载来源、修订、片段、作业、受治理记忆、通知、会话与质量标注等数据，当前支持到模式版本 14。它把原始证据、派生知识和应用结果纳入同一 SQLite 数据边界，但表结构存在并不代表上层治理流程已经执行。[SQLite 模式迁移与历史校验 ↗](70d45111240700f09d248181bee2b36040dcc48e7938c056ed4482bae200e20d.md#purpose "概括迁移模块覆盖的数据能力、当前版本和持久化边界。")[模式版本与迁移清单 ↗](../../../apps/server/src/storage/migrations.ts#L920 "迁移清单支持当前最高版本为 14，并展示各功能切片的顺序演进。")

<a id="schema_flow"></a>
## 模式演进与一致性

启动时先启用外键并检查磁盘版本；数据库版本高于程序支持范围时拒绝写入。迁移历史按版本确认记录未超前、版本已知且应有记录齐全，并比较 SQL 清单校验和；代码虽读取迁移名称，却没有比较名称，因此此前“名称也会被核对”的结论已被替代。[迁移历史核验 ↗](../../../apps/server/src/storage/migrations.ts#L1024 "支持历史超前、未知版本、缺失记录及校验和不匹配检查，也表明读取的名称未参与比较。") 每版迁移在 `BEGIN IMMEDIATE` 事务中顺序执行，写入历史并更新 `user_version` 后提交，失败整体回滚，全部完成后启用 WAL。[原子迁移执行 ↗](../../../apps/server/src/storage/migrations.ts#L1057 "支持迁移顺序约束、事务提交与回滚、新版数据库拒写以及完成后启用 WAL 的流程。")

<a id="application_flow"></a>
## 业务写入主线

应用仓储先按应用标识或“提案摘要＋代次”查找回执：相同请求重复提交返回既有结果，幂等键相同但内容不同则报冲突。首次提交在同一事务内更新记忆或任务、追加修订，并记录变化、站内通知、投递意图和应用回执。[原子应用仓储 ↗](a32a56bc799cdb1495e273272a498cc90f84e8f718550b486e3aa8feb0c59d5a.md#purpose "概括应用事务、幂等回执以及变化和通知记录之间的关系。") 记忆与任务更新均以 `expectedVersion` 乐观锁防止覆盖并发修改；记忆还会把格式完整的来源引用登记为依赖。[记忆与任务版本化写入 ↗](../../../apps/server/src/storage/repository.ts#L400 "支持记忆和任务的乐观锁、修订追加，以及记忆来源依赖登记。")

<a id="relations_limits"></a>
## 跨模块关系与限制

飞书卡片载荷使用规范化 JSON 的 SHA-256 指纹：普通对象键顺序不影响结果，对象属性中的 `undefined` 会被移除，但特殊值和循环输入没有独立合同。[规范化摘要 ↗](../../../apps/server/src/storage/digest.ts#L3 "支持对象键排序、undefined 属性过滤和 SHA-256 稳定摘要，并揭示输入类型边界。") 通知排程支持即时、延迟窗口和按时区定时。[通知排程策略 ↗](../../../apps/server/src/storage/repository.ts#L125 "支持即时、窗口延迟和按时区定时三种投递时间计算方式。") 本模块只创建投递意图，不能证明发送、重试与聚合 worker 的完整行为；公共应用入口也未读取审批状态，所以“批准后才能应用”仍须由上层编排保证。[投递意图与应用回执 ↗](../../../apps/server/src/storage/repository.ts#L294 "支持仓储创建飞书投递意图和应用回执，同时表明该事务未读取提案审批状态。")
