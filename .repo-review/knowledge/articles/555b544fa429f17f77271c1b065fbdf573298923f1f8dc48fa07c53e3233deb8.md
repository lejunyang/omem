# storage · 模块理解

storage 模块以 SQLite 模式迁移、原子应用仓储和结构化摘要为核心，把来源证据、版本化记忆与任务、变更通知、投递意图、作业记录及检索投影纳入同一持久化边界；当前模式演进至版本 17，但应用摘要一致性、时区边界及历史迁移测试覆盖仍待确认。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="role-and-scope"></a>
## 职责与设计背景

storage 是服务器状态的持久化底座：模式从来源、修订、片段、变更、通知和任务起步，逐步加入作业、提案与复核、版本化记忆、飞书集成、对话、争议处理及检索索引，当前支持到 schema 17。[基础持久化结构与迁移历史表 ↗](../../../apps/server/src/storage/migrations.ts#L30 "支持模块初始覆盖的来源、修订、片段、变更、通知和任务结构，并说明迁移表保存的字段。") [迁移版本清单 ↗](../../../apps/server/src/storage/migrations.ts#L959 "支持数据库能力按迁移逐步演进至版本 17。") 这些结构让捕获证据、知识治理、应用结果与检索投影共享同一数据库关系。

全文检索被明确设计为固定片段的可重建投影，并通过触发器跟随片段写入、删除和更新；语义向量则按模型、片段及分片保存，使模型身份参与索引隔离。[全文检索投影 ↗](../../../apps/server/src/storage/migrations.ts#L915 "支持 FTS5 被定义为可重建的片段投影，并由触发器维护片段变化。") [语义向量存储结构 ↗](../../../apps/server/src/storage/migrations.ts#L948 "支持向量按模型、片段和分片保存，模型身份参与主键约束。") 当前材料只明确说明全文投影可重建，不能把这一结论自动扩展到向量索引的运行流程。

<a id="migration-lifecycle"></a>
## 模式如何安全演进

每项迁移在代码中包含版本、名称、SQL 语句集合及其校验和；校验和由语句按固定分隔符拼接后计算 SHA-256。[迁移校验和生成 ↗](../../../apps/server/src/storage/migrations.ts#L943 "支持迁移 SQL 语句按固定分隔符拼接后计算 SHA-256。") 数据库迁移表只保存版本、名称、校验和与应用时间，并不保存 SQL 正文，这替代了“数据库为每个版本保存完整迁移语句”的旧结论。[基础持久化结构与迁移历史表 ↗](../../../apps/server/src/storage/migrations.ts#L30 "支持模块初始覆盖的来源、修订、片段、变更、通知和任务结构，并说明迁移表保存的字段。")

历史校验会拒绝记录超前、未知版本、校验和不匹配以及当前 schema 所需迁移缺失，但存在兼容例外：schema 为 0 或 1 且尚无迁移表时允许继续，版本 1 也接受旧版校验和。[迁移历史校验与旧版兼容 ↗](../../../apps/server/src/storage/migrations.ts#L1054 "支持历史完整性检查，并明确 schema 0 或 1 无迁移表及版本 1 旧校验和的兼容例外。") 因而“任何迁移历史缺失都会被拒绝”的旧结论已被替代。实际升级逐版本使用 `BEGIN IMMEDIATE`，要求从相邻版本推进；SQL、历史记录与 `user_version` 同事务提交，失败整体回滚。[单版本事务迁移 ↗](../../../apps/server/src/storage/migrations.ts#L1104 "支持相邻版本推进、执行 SQL、登记历史、更新 user_version 和失败回滚的流程。") 入口还会拒绝高于程序支持版本的数据库，完成迁移并再次校验历史后才启用 WAL。[数据库迁移入口 ↗](../../../apps/server/src/storage/migrations.ts#L1143 "支持拒绝过新 schema、迁移前后校验历史、顺序执行迁移及完成后启用 WAL。")

<a id="application-flow"></a>
## 记忆、任务与通知的应用流程

`ApplicationRepository` 把一次获准应用视为原子事务：先按应用标识或“提案摘要 + generation”查找收据；请求摘要一致时返回 duplicate，不一致时报告幂等冲突。首次执行会共同写入实体版本、变更、站内通知、投递意图和应用收据。[统一应用事务与幂等收据 ↗](../../../apps/server/src/storage/repository.ts#L176 "支持应用查重，以及实体、变更、通知、投递意图和收据在同一事务内提交。")

记忆和任务更新都以期望版本阻止并发覆盖。记忆会新增修订、推进 head，并仅把字段完整的来源修订登记为依赖；任务会更新当前记录并追加历史修订。[记忆版本与证据依赖 ↗](../../../apps/server/src/storage/repository.ts#L400 "支持记忆的乐观并发、新修订、head 推进及来源依赖持久化。") [任务版本应用 ↗](../../../apps/server/src/storage/repository.ts#L530 "支持任务以期望版本更新当前状态并追加历史修订。") 活跃飞书目标会产生待投递卡片意图，保存调度时间、负载和稳定 payload 摘要；这证明的是投递意图可靠入库，并不证明外部消息已经送达。[飞书投递意图构建 ↗](../../../apps/server/src/storage/repository.ts#L294 "支持活跃目标筛选、卡片大小限制、稳定 payload 摘要、调度字段及待投递状态入库。")

<a id="constraints-and-open-edges"></a>
## 一致性边界与当前限制

稳定摘要工具递归排序对象键、过滤对象中的 `undefined`、保留数组顺序，再对规范 JSON 计算 SHA-256。[规范 JSON 与稳定摘要 ↗](../../../apps/server/src/storage/digest.ts#L3 "支持对象键排序、undefined 过滤、数组顺序保留及 SHA-256 摘要规则。") 它用于飞书卡片 payload；记忆与任务的应用请求仍直接哈希 `JSON.stringify`，所以键插入顺序不同但语义相同的重试可能得到不同摘要。[应用请求摘要实现 ↗](../../../apps/server/src/storage/repository.ts#L83 "支持记忆与任务应用摘要直接依赖 JSON.stringify，说明其与稳定摘要算法不同。") 这替代了“所有仓储摘要都具备键序稳定性”的旧结论。

通知支持即时、延迟窗口和指定时区的每日时刻，若当天目标已错过则顺延一天。[外部通知时间策略 ↗](../../../apps/server/src/storage/repository.ts#L125 "支持即时、延迟窗口和按时区每日调度，以及错过当天目标后顺延的规则。") 材料没有定义夏令时跳变、无效时区或非法本地时间的合同，也没有提供从所有历史 schema 升级到 17 的实际测试结果。迁移钩子只说明实现提供了提交前抛错以检验整体回滚的测试接缝，不能代替真实测试矩阵。[迁移回滚测试接缝 ↗](../../../apps/server/src/storage/migrations.ts#L25 "支持实现提供提交前钩子以检验整次迁移回滚，但不能证明历史升级组合已实际覆盖。")
