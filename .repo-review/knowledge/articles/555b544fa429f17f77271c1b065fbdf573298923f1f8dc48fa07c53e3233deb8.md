# storage · 模块理解

storage 模块以 SQLite 模式迁移、事务化应用仓库和稳定摘要工具为核心，承接来源证据、受治理记忆、任务、通知、外部接入、助手会话及检索索引的持久化。当前模式已演进至版本 17；应用流程具备幂等回执、乐观锁和追加修订，但全局不可变性、外部副作用一致性及跨运行环境兼容性仍需额外验证。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="responsibility"></a>
## 为什么需要这一层

storage 是业务流程与 SQLite 之间的持久化边界：迁移文件定义数据结构怎样随能力增长而演进，应用仓库把已确认的记忆或任务变更连同修订、变更记录、通知意图和回执一起落库，摘要工具则为部分载荷提供可复现标识。[应用仓库职责 ↗](a32a56bc799cdb1495e273272a498cc90f84e8f718550b486e3aa8feb0c59d5a.md#purpose-and-contract "子知识概括了记忆或任务应用时同时保存修订、变更、通知、投递意图与回执的模块职责；附近论断另由原始实现支持。")[应用输入与回执合同 ↗](../../../apps/server/src/storage/repository.ts#L7 "原始类型定义展示应用元数据、记忆与任务输入、回执以及钩子，支持 storage 作为业务应用持久化边界的说明。")

它保存的不只是最终实体，还包括来源修订、证据依赖、作业尝试、治理判断和投递状态，使后续追溯、重核验与重试有结构化依据。基础表从来源、修订、片段和关系开始，随后扩展到任务及通知；但这些 DDL 本身没有禁止修改旧修订，因此“不可变”仍主要依赖上层写入纪律。[基础持久化结构 ↗](../../../apps/server/src/storage/migrations.ts#L30 "基础迁移直接定义来源、修订、片段、关系、变更、通知和任务表，同时可见其中没有禁止历史行更新的约束。")

<a id="schema-flow"></a>
## 模式演进与当前进展

数据库目前声明支持模式版本 17，迁移注册表覆盖治理记忆、角色运行时、飞书接入、质量标注、助手会话、全文检索和语义向量等能力；每组 SQL 都计算校验和，用于识别已应用历史是否与当前构建一致。[迁移版本注册表 ↗](../../../apps/server/src/storage/migrations.ts#L943 "迁移校验和函数及版本 1 至 17 的注册项支持当前模式进展和历史校验基础的说明。") 启动迁移时先开启外键，拒绝比程序更新的数据库，校验历史后按顺序补齐版本，最终启用 WAL。[数据库迁移入口 ↗](../../../apps/server/src/storage/migrations.ts#L1143 "迁移入口展示外键启用、未来版本拒写、历史校验、顺序升级和 WAL 设置流程。")

每个版本在 `BEGIN IMMEDIATE` 事务中执行，并要求只从紧邻的上一版本升级；迁移语句、历史记录、测试钩子和 `user_version` 任一环节失败都会回滚。[单版本事务升级 ↗](../../../apps/server/src/storage/migrations.ts#L1104 "该实现支持连续版本要求、迁移历史写入、提交前钩子、版本更新及异常回滚的原子升级说明。") 检索方面已建立 trigram FTS5 投影及同步触发器，向量则按模型、片段和分片分别存储，从结构上避免不同模型身份直接混写。[全文与向量索引结构 ↗](../../../apps/server/src/storage/migrations.ts#L915 "FTS5 投影、同步触发器及按模型区分的向量表支持检索持久化已经落地到模式版本中的论断。")

<a id="application-flow"></a>
## 记忆、任务与通知如何落库

一次应用先依据应用标识，或提案摘要与代次查找既有回执；相同身份但请求摘要不同会被判定为幂等冲突。数据库同时为这两种身份建立工作区内唯一约束，使正常并发写入也由存储层仲裁。[应用回执身份与唯一约束 ↗](../../../apps/server/src/storage/migrations.ts#L256 "回执表为应用标识及提案摘要与代次分别建立工作区唯一约束，支持幂等查询身份与数据库仲裁相一致的说明。") 随后事务创建或更新实体、追加修订，记录变更与站内通知，并为站内及有效飞书目标写入待发送意图；实际发送和送达确认不在这个仓库中完成。[事务化应用与投递意图 ↗](../../../apps/server/src/storage/repository.ts#L217 "应用主体展示重复检查、实体写入、变更和通知创建、飞书投递意图、回执保存及钩子调用的实际顺序。")

记忆更新通过预期版本执行乐观锁，插入新修订并推进 head；完整证据集合写入修订，其中具备来源、来源修订和有效性代次的条目还会展开为依赖关系。任务也按版本更新并追加任务修订。[记忆修订与证据依赖 ↗](../../../apps/server/src/storage/repository.ts#L419 "该段展示记忆版本检查、新修订插入、head 条件推进以及合格证据依赖的结构化写入。") 这让应用结果可追踪，但只能证明当前入口采用追加写入，不能证明其他代码路径绝不会修改历史行。

<a id="limits"></a>
## 约束、差异与风险

模块存在两种摘要语义：通用稳定摘要会递归排序对象键并过滤对象中的 `undefined`，而应用请求摘要直接对输入执行 `JSON.stringify`。[稳定摘要规范化 ↗](../../../apps/server/src/storage/digest.ts#L3 "原始摘要工具展示数组递归、对象键排序、undefined 属性过滤、JSON 序列化和 SHA-256 计算，支持其语义与边界说明。")[应用请求摘要 ↗](../../../apps/server/src/storage/repository.ts#L83 "应用仓库直接对 JSON.stringify 结果计算 SHA-256，支持其与稳定摘要采用不同规范化规则的论断。") 因此逻辑内容相同但键插入顺序不同的应用请求，可能产生不同摘要；稳定摘要面对根级 `undefined`、函数、Symbol、循环、BigInt 或特殊对象时也没有完整防护。

应用的 `after` 钩子仍在数据库提交前执行；若钩子产生不可回滚的外部副作用，之后失败只能回滚数据库，不能撤销外部状态。[事务及钩子执行位置 ↗](../../../apps/server/src/storage/repository.ts#L176 "事务包装器与应用主体共同表明 after 钩子在事务函数完成及 COMMIT 之前执行，支持外部副作用一致性风险的说明。") 此外，现有材料没有提供迁移测试、SQLite 编译能力或通知时区测试，尚不能确认真实旧库逐版升级、所有环境的 FTS5 trigram 支持，以及夏令时跳变日的每日排程行为。
