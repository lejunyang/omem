# storage · 模块理解

storage 模块以 SQLite 为统一持久化核心：迁移层定义并校验 schema 1—18，仓库层把传入的记忆或任务原子地写为当前态、不可变修订、变更、通知、投递意图与幂等回执，摘要工具为部分载荷提供稳定指纹。此前关于提案已确认、迁移名称校验和后续 worker 发送的结论均已收窄。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="responsibility"></a>
## 职责与设计背景

storage 承担“原始证据—治理记录—应用结果”的持久化边界：迁移从来源、修订、片段和任务起步，继续纳入作业、提案、记忆、决策、通知、会话与检索等数据域，使各阶段能在同一 SQLite 中追溯。[SQLite 持久化模型 ↗](70d45111240700f09d248181bee2b36040dcc48e7938c056ed4482bae200e20d.md#purpose-and-schema "支持 storage 将来源、修订、治理记录、应用结果和检索结构纳入同一 SQLite 的模块定位。")[基础来源与任务表 ↗](../../../apps/server/src/storage/migrations.ts#L30 "以基础迁移中的来源、修订、片段、变更、通知和任务表支持统一持久化边界的说明。")

仓库层负责应用**传入的**记忆和任务，保存当前状态、历史修订、变更、通知及投递意图；此前“只应用已经确认的记忆和任务”这一结论被替代，因为现有材料没有展示批准状态校验，该前置条件即使存在也只能由未提供的上游保证。任务状态和随访字段则依赖共享合同约束时间格式、IANA 时区和严格字段集合。[任务状态与随访合同 ↗](../../../packages/contracts/src/task-flow.ts#L3 "支持任务状态、带偏移日期时间、IANA 时区及严格随访字段由共享合同约束。")

<a id="flow"></a>
## 迁移与业务应用流程

启动时迁移器读取 `user_version`，拒绝高于支持版本的数据库，并检查迁移版本是否已知、历史记录是否缺失、校验和是否匹配；虽然查询读取了名称，但没有将已存名称与预期名称比较，因此此前“核对迁移名称并发现名称篡改”的说法被替代。待执行版本必须逐版在 `BEGIN IMMEDIATE` 事务中运行，失败回滚，完成后再次校验历史并启用 WAL。[迁移历史校验与执行入口 ↗](../../../apps/server/src/storage/migrations.ts#L1092 "支持迁移按版本检查未知、缺失和校验和异常，但不比较名称；同时支持逐版事务、回滚、最终复核和 WAL 设置。")

业务应用也在立即事务中先检查幂等回执：同一标识且摘要相同会返回旧回执，摘要不同则报冲突；首次应用随后创建实体，并写入修订、变更、通知、投递意图和回执。[统一应用事务与幂等边界 ↗](a32a56bc799cdb1495e273272a498cc90f84e8f718550b486e3aa8feb0c59d5a.md#application-transaction "支持仓库先检查既有回执，再于同一事务内创建实体并写入变更、通知和回执。") 记忆通过期望版本推进不可变修订链，并将结构合格的证据引用投影为依赖关系；任务同样采用乐观锁，更新当前态并追加含状态、证据与随访信息的历史快照。[记忆与任务版本化写入 ↗](../../../apps/server/src/storage/repository.ts#L402 "证明记忆和任务应用接收传入数据，使用期望版本控制，并分别追加不可变修订或任务历史快照；这些代码未校验提案批准状态。")

<a id="progress-limits"></a>
## 进展、跨模块关系与限制

当前 schema 已包含由触发器维护的片段全文索引、按模型身份隔离的向量记录，以及等待、取消、随访和提醒去重等任务生命周期结构，说明检索与主动跟进已进入持久化模型。[检索与任务跟进结构 ↗](../../../apps/server/src/storage/migrations.ts#L915 "支持全文索引由触发器维护、向量按模型身份隔离，以及 schema 18 扩展任务跟进生命周期。") 通知方面，仓库会按应用元数据创建 `pending` 意图，并为有效飞书目标追加意图；材料只能证明发送不在该仓库层完成，不能再断言一定由某个后续 worker 承担。[投递意图的仓库边界 ↗](a32a56bc799cdb1495e273272a498cc90f84e8f718550b486e3aa8feb0c59d5a.md#delivery-boundaries "支持通用渠道来自应用元数据、飞书意图仅面向有效目标，且该仓库代码只创建待投递记录，未展示实际发送者。")

摘要规则仍不统一：应用请求直接哈希 `JSON.stringify`，而飞书载荷使用会递归排序对象键并过滤 `undefined` 的稳定摘要；语义相同但键插入顺序不同的应用输入可能得到不同幂等摘要。[应用请求摘要实现 ↗](../../../apps/server/src/storage/repository.ts#L85 "证明记忆与任务应用的幂等请求摘要直接基于 JSON.stringify，可能受对象键插入顺序影响。")[稳定摘要规范化规则 ↗](../../../apps/server/src/storage/digest.ts#L3 "作为对照，证明稳定摘要会递归排序对象键、过滤 undefined 后再计算 SHA-256。") 现有材料也未给出迁移回滚、表重建数据保持、FTS5 trigram 可用性或事务内钩子副作用的真实测试结果。
