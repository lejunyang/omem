# 每日消息跟进的生命周期与提醒语义测试

该测试以真实临时 SQLite Store、AssistantRuntime 和 MemoryService 验证个人跟进事项的创建、稍后提醒、重启恢复、一次性通知、取消、归属约束及多提醒去重；模型为可控桩，未覆盖真实 ACP 传输、并发更新和通知投递失败。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_and_setup"></a>
## 测试目的与协作模块

测试把 `Store`、`MemoryService`、`AssistantRuntime` 与回复解析器组合起来，用临时目录中的真实数据库运行，而非只断言协议对象。[测试依赖与模型桩 ↗](../../../apps/server/tests/task-follow-up.test.ts#L1 "支持该文件使用真实 Store、MemoryService、AssistantRuntime 和回复解析器，并通过受控模型返回结构化任务操作。") 模型桩根据当前任务和用户是否说“取消”返回创建、稍后或取消操作，因此重点是验证运行时如何治理模型提出的结构化写入，以及存储层如何持久化任务、修订和提醒回执；它不证明真实 ACP 模型能够稳定生成同样的调用。

<a id="lifecycle"></a>
## 跟进事项的完整生命周期

首个场景从“等待张三回复”创建 `waiting` 事项，明确断言普通截止时间为空、跟进结构完整，且检查时间到达前不会提醒。[等待事项创建断言 ↗](../../../apps/server/tests/task-follow-up.test.ts#L27 "支持事项创建后处于 waiting、没有普通截止时间、保存跟进结构且提前扫描不提醒。") 用户要求稍后提醒后，事项保持原 ID 和等待状态、版本升至 2，并保留等待对象，同时更新延后时间。关闭并重新打开 Store 后，逾期检查只补发一次通知，随后再次扫描不重复发送，说明一次性回执可跨进程恢复。[延后与重启补发断言 ↗](../../../apps/server/tests/task-follow-up.test.ts#L33 "支持延后操作保留事项身份与等待对象，并验证数据库重开后只补发一次跟进通知。") 最后取消事项会清空跟进信息、将版本升至 3，并留下三条任务修订；即使扫描到更远未来也不会再通知。[取消与修订历史断言 ↗](../../../apps/server/tests/task-follow-up.test.ts#L42 "支持取消后状态、版本、跟进清理、停止未来提醒以及三次不可变修订记录。")

<a id="ownership_and_receipts"></a>
## 归属边界与提醒合并

第二个场景刻意让模型把“张三承诺回复”的讨论转换成创建任务调用，但运行时最终没有落库，验证第三方承诺不会自动变成用户个人事项；这里断言的是最终拒绝效果，没有揭示具体拒绝分支。[第三方承诺不落为个人任务 ↗](../../../apps/server/tests/task-follow-up.test.ts#L52 "支持即使模型请求创建任务，关于他人承诺的解释性讨论也不会产生用户任务。") 第三个场景直接写入两个等待事项：同一时刻触发的检查提醒与截止提醒不会在后续扫描中重复，而较晚截止时间仍会产生自己的回执；最终四条回执用于约束不同触发维度的幂等性。[多提醒与回执幂等断言 ↗](../../../apps/server/tests/task-follow-up.test.ts#L64 "支持同时检查与截止提醒的处理、重复扫描抑制、较晚截止独立触发及最终回执数量。") 该场景只检查计数，没有逐条核对通知标题、正文与每条回执对应的任务及触发类型。
