# 待跟进事项的创建、提醒与取消验证

该测试以临时 SQLite 存储和可控模型替身验证个人待跟进事项的生命周期：从自然语言建项、暂缓和重开存储后的逾期补发，到取消、归属保护及双通道提醒合并。它验证运行时处理结构化任务调用的结果，但不代表真实 ACP 模型抽取能力，也未覆盖写入提醒回执后再次重启的去重行为。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="follow-up-lifecycle"></a>
## 从委托建立等待事项

用户要求跟进“张三的评审回复”后，模型替身给出结构化建项请求，助理将其保存为 `waiting` 事项。事项记录等待对象、下次检查时间、原始时间表达和时区，而普通截止时间保持为空；检查时间到达前不会通知。参考 [等待事项创建流程 ↗](../../../apps/server/tests/task-follow-up.test.ts#L17 "支持自然语言委托被保存为 waiting 事项、保留跟进字段并在检查时间前不提醒的结论。")

这里的模型是可控测试替身，因此用例验证的是运行时如何接收并落实任务调用，不证明生产模型能够稳定提取相同字段。生产适配器只接受已配置的 ACP 传输，缺少配置或使用 CLI 传输时会明确报不可用，也不会用伪造答案回退。参考 [生产模型传输限制 ↗](../../../apps/server/src/assistant/acp-model.ts#L12 "说明生产模型适配器要求 ACP 配置、拒绝 CLI 传输且不提供伪造回退，用于界定模型替身测试的适用范围。")

<a id="state-transitions"></a>
## 暂缓、补发与取消

暂缓会把下一次检查移到用户指定的新时间，同时保持 `waiting` 状态、原等待对象和空截止时间。测试随后在首次提醒产生前关闭并重开存储；新实例对已经到期的检查补发一次，同一实例再次扫描不再发送。它尚未验证提醒回执写入后再次重启是否仍能去重。参考 [暂缓与重开后补发 ↗](../../../apps/server/tests/task-follow-up.test.ts#L33 "支持暂缓后保持等待语义、首次提醒前重开存储、补发一次及同一实例后续扫描去重，并据此界定未覆盖的再次重启边界。")

恢复助理运行时后，取消请求把事项改为 `cancelled`、清空跟进配置并停止未来提醒。创建、暂缓和取消分别留下修订记录，使状态变化可追溯。参考 [取消与修订记录 ↗](../../../apps/server/tests/task-follow-up.test.ts#L42 "支持取消后清空跟进配置、停止未来提醒并保留三次状态修订。")

<a id="ownership-and-reminders"></a>
## 归属保护与提醒合并

系统不会仅因模型提出建项，就把群聊中他人的承诺变成用户自己的任务：当用户只是询问“张三会回复”这段讨论的含义时，最终没有任务落库。该用例验证归属保护结果，但未检查拒绝建项时向用户展示的具体解释。参考 [非本人承诺不建项 ↗](../../../apps/server/tests/task-follow-up.test.ts#L52 "支持讨论他人承诺时，即使模型提出建项调用，系统最终也不创建个人任务。")

双通道场景创建“同时”和“稍晚”两个等待事项。首次扫描为两个事项产生两条通知，其中“同时”事项在同一时刻到达的检查提醒与截止提醒被合并；重复扫描不再发送。“稍晚”事项到达截止时间后仍产生一条独立通知，最终四条底层回执对应各自已处理的提醒事件。用例未覆盖真正并发调用扫描时的竞争条件。参考 [双通道提醒合并 ↗](../../../apps/server/tests/task-follow-up.test.ts#L64 "支持首次扫描对两个事项产生两条通知、同一事项的同时检查与截止提醒被合并、后续截止独立发送以及最终回执数量。")
