# SQLite 数据库如何安全演进到当前结构

这套迁移器把单用户 SQLite 从空库或受支持的旧版本线性升级到版本 19；迁移历史与 SQL 校验和用于发现历史缺口、错序或迁移定义与当前构建不一致，逐版本事务则避免留下半完成升级。它同时兼容已有 legacy v1 记录，以及没有迁移表的旧 v1 数据库。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 为什么需要统一迁移入口

服务启动时面对的可能是空库，也可能是保留已有材料的旧库。迁移器把每一版定义为版本号、名称、SQL 语句集和校验和，当前支持的结构版本为 19；版本 1 先建立迁移历史、来源、修订、片段、变更、通知和任务等基础结构。参考 [迁移版本模型 ↗](../../../apps/server/src/storage/migrations.ts#L4 "支持当前结构版本为 19，以及每个迁移由版本、名称、语句集和校验和组成的说明。")、[基础持久结构 ↗](../../../apps/server/src/storage/migrations.ts#L30 "支持版本 1 建立迁移历史及来源、修订、片段、变更、通知和任务基础表的说明。")

<a id="upgrade-flow"></a>
## 一次升级如何完成

以版本 0 的新库为例：入口开启外键，确认数据库没有超出程序支持范围并校验历史，再按清单依次应用后续版本；全部完成后复核版本 19 的历史、启用 WAL，并返回当前版本。参考 [迁移入口流程 ↗](../../../apps/server/src/storage/migrations.ts#L1187 "支持入口开启外键、拒绝超前版本、校验历史、逐版升级、启用 WAL 并返回版本 19 的流程。")

每一版都在 `BEGIN IMMEDIATE` 事务中执行，只允许从紧邻的前一版进入。SQL、迁移记录和 `user_version` 一起提交；任一步骤或提交前钩子抛错，本版整体回滚，下次启动仍从上一个完整版本继续。参考 [逐版本事务 ↗](../../../apps/server/src/storage/migrations.ts#L1148 "支持连续版本约束、SQL 与历史记录提交、user_version 更新及异常回滚的说明。")

<a id="guards"></a>
## 历史一致性、v1 兼容与数据边界

历史校验会拒绝高于结构版本的记录、未知版本、应有版本缺失，以及记录校验和与当前构建中迁移 SQL 不一致的情况；v1 记录还接受明确的 legacy 校验和。它检查的是迁移历史与当前迁移定义的一致性，不会据此验证实际 SQLite 表结构或业务数据是否被改动。参考 [迁移历史一致性 ↗](../../../apps/server/src/storage/migrations.ts#L1120 "支持历史超前、未知或缺失版本、校验和不符的拒绝规则和 legacy v1 例外；该范围也表明校验对象是历史记录与迁移定义，而非实际表结构或业务数据。")

若数据库没有 `migrations` 表，结构版本 0 或 1 会被放行，版本 2 及以上则拒绝继续。这个无历史表的旧 v1 库进入版本 2 后，会以 `INSERT OR IGNORE` 补入 legacy v1 记录；已有版本 1 记录会保留，不会被改写校验和。参考 [无历史表兼容范围 ↗](../../../apps/server/src/storage/migrations.ts#L1115 "支持迁移表缺失时只放行结构版本 0 或 1、版本 2 及以上拒绝继续的说明。")、[补入 legacy v1 记录 ↗](../../../apps/server/src/storage/migrations.ts#L1164 "支持应用版本 2 时用 INSERT OR IGNORE 补入版本 1 legacy 记录、而不覆盖已有版本 1 记录的说明。")

该文件负责结构演进，而不是各领域业务。检索单元、全文索引和向量表被明确建模为可替换投影，原始修订仍是权威来源。参考 [可重建检索投影 ↗](../../../apps/server/src/storage/migrations.ts#L979 "支持检索单元、全文与向量结构属于可替换投影，而不可变修订保持权威的说明。")
