# 固定快照研究环境的生命周期与调用方导航

这组集成测试验证 Agent 能在隔离的固定材料快照上读取原文、提交结构化结果，并在结束后安全回收可重建副本；同时验证调用方搜索会返回带候选标记的 AST 名称匹配，并允许继续补读包围该调用的完整操作。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 它防止什么问题

该测试覆盖自主研究环境最关键的两类回归：一是 Agent 读到的必须是任务创建时选定的固定原件，提交结果后又不能让临时副本长期占用空间；二是“谁调用某函数”必须返回调用位置，而非把函数定义误当答案。测试通过 `Store` 捕获原件，经 `KnowledgeRepository` 选材，再把材料、输出 schema 与工作区交给 `prepareAgentResearch`，因此同时串起存储、知识仓储和 Agent 研究运行时。参考 [研究环境装配 ↗](../../../apps/server/tests/agent-research.test.ts#L19 "支持测试如何从捕获材料、知识仓储、输出 schema 和工作区装配 prepareAgentResearch，并说明相关模块关系。")

研究环境内部会建立任务快照，并用 `UnifiedRetrieval` 提供检索；关闭时只删除可重建的原件导出、图片和 SQLite 快照。参考 [快照与资源回收 ↗](../../../apps/server/src/knowledge/agent-research.ts#L81 "说明研究环境创建固定 SQLite 快照，并在关闭时仅清理可重建的任务导出与快照文件。")

<a id="lifecycle"></a>
## 一次渡轮笔记如何完成研究闭环

代表性输入是一条“周五乘渡轮，提前预订船票”的手工材料，期望输出是符合 `{ summary: string }` 的摘要。流程如下：

```mermaid
flowchart LR
  A[捕获渡轮笔记] --> B[准备固定研究工作区]
  B --> C[通过本地 MCP 读取原文]
  C --> D[提交摘要候选]
  D --> E[关闭并回收任务副本]
```

客户端先调用 `read_material` 并确认原句可见，再调用 `submit_result`；`env.result()` 随即返回已校验摘要。关闭后，`originals/` 与 `snapshot.sqlite` 消失，但 `research.jsonl`、`result.json` 和正式 Store 中的证据仍存在，这些断言把“临时副本”和“长期证据/审计”明确分开。参考 [生命周期关键断言 ↗](../../../apps/server/tests/agent-research.test.ts#L43 "直接体现读取、提交、结果返回、任务副本清理以及审计和正式证据保留的预期行为。")

实现中的提交工具先调用宿主提供的校验函数，成功后记录 submission 并写入 `result.json`；失败则把错误留在当前工具响应中供修正。参考 [提交与校验实现 ↗](../../../apps/server/src/knowledge/agent-research.ts#L794 "说明 submit_result 如何校验候选、记录 submission、持久化 result.json，并在失败时返回可修正错误。")

<a id="caller_navigation"></a>
## 调用方候选如何被验证

第二个场景捕获一个教学用 `shipping.ts`：`checkout` 调用 `reserveParcel`。即使关闭语义检索，Agent 仍可显式发送 `codeIntent: "callers"`；测试要求只返回一个位于第 2 行、状态为 `candidate` 的调用匹配，然后用 `read_section("checkout")` 读回完整包围函数并看到真实调用语句。参考 [调用方导航断言 ↗](../../../apps/server/tests/agent-research.test.ts#L78 "支持教学代码输入、显式 callers 意图、候选行号以及继续读取 checkout 完整操作的测试行为。")

这条链由研究工具把 `codeIntent` 传给统一检索，再由调用方分支挑选包含调用的最小代码单位并附上行号。参考 [调用方检索分支 ↗](../../../apps/server/src/retrieval/unified.ts#L346 "说明统一检索如何从符号名称筛选代码单位、保留最小包围操作并返回调用候选与附近正文。") 其边界也很重要：解析器只比较调用的末级名称，不解析接收者类型或 import 别名，所以结果刻意标为候选；同名方法可能混入，动态或别名调用也可能漏掉，读者应继续核对所在函数与 import，不能把它当成完整调用图。参考 [名称匹配的边界 ↗](../../../apps/server/src/retrieval/code-navigation.ts#L17 "支持调用导航只按末级名称匹配、缺少接收者类型和别名解析，因此必须保留 candidate 状态的限制。")
