# 任务跟进校验与提醒派发

该模块把用户授权的等待对象和时间表达校验为规范化跟进配置，并扫描开放或等待中的任务生成站内通知。它通过任务版本、触发类型和发生时间收据实现幂等，明确不调用模型、不联系外部人员；其原子性依赖调用方提供数据库事务。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="validation"></a>
## 跟进配置的授权边界

`validateFollowUp` 先用共享合同严格解析配置，再要求 `waiting_on` 必须原样出现于当前用户文本；只要设置下次检查或暂缓时间，也必须保留当前指令中的原始时间表达。这样避免系统自行推断等待对象或提醒时机。通过后，两个时间字段统一转换为 ISO 字符串，便于持久化和比较。[跟进配置校验与时间规范化 ↗](../../../apps/server/src/tasks/follow-up.ts#L5 "支持等待对象和时间表达必须来自当前指令，以及日期字段会被规范化为 ISO 字符串的说明。")

字段形状、长度、带偏移的日期时间以及 IANA 时区合法性由 `taskFollowUpSchema` 统一约束；服务端因此与其他任务入口共享同一合同，而不是维护一套局部格式。[任务跟进共享合同 ↗](../../../packages/contracts/src/task-flow.ts#L3 "说明跟进字段的严格结构、日期偏移格式和 IANA 时区校验，以及服务端依赖共享合同。")

<a id="dispatch"></a>
## 到期扫描与通知生成

`dispatchTaskReminders` 仅扫描 `open`、`waiting` 任务；尚处于 snooze 窗口的记录直接跳过。随后分别识别截止到期和跟进到期，并以任务 ID、版本、触发类型及 occurrence 查询收据，过滤已经处理过的触发。[任务扫描与触发去重 ↗](../../../apps/server/src/tasks/follow-up.ts#L20 "支持任务状态筛选、暂缓判断、到期触发构造及按收据过滤已处理触发的流程。")

同一轮若同时命中两类触发，只创建一条通知，但会为每个新触发分别写入收据。标题优先显示“事项待跟进”，正文组合下一步或详情、等待对象、到期说明及可执行动作，并明确不会自动联系他人。函数最终返回本轮创建的通知数量。[提醒通知正文与收据写入 ↗](../../../apps/server/src/tasks/follow-up.ts#L35 "支持单条通知合并多种触发、正文组成、禁止自动联系他人和返回创建数量的说明。")

<a id="boundaries"></a>
## 幂等性、事务与模块关系

截止提醒还会先查询通知的 `dedupe_key`，跟进提醒则主要依赖收据表；通知键包含任务版本，旧版本已提醒不会阻止新版本再次提醒。通知和全部触发收据使用同一个通知 ID 写入，使离线补扫或重复轮询不会重放同一任务版本的同一 occurrence。[通知键与逐触发收据 ↗](../../../apps/server/src/tasks/follow-up.ts#L27 "支持通知去重键包含任务版本，以及每个新触发分别写入收据实现重复轮询幂等的论断。")

源码声明该函数应运行在 Store 的事务内，且自身不启动模型、外发消息或守护进程；但所给材料没有展示调用方，因此无法确认事务是否在所有入口都被强制执行。模块与共享 `task-flow` 合同存在直接导入关系；未提供测试文件，因而只能说明实现意图，不能据此确认并发轮询、数据库失败回滚或混合触发场景已有自动化覆盖。[事务与外部副作用边界 ↗](../../../apps/server/src/tasks/follow-up.ts#L17 "说明函数被设计为在 Store 事务内调用，并明确不运行模型、不发送外部消息或创建守护进程；同时界定材料未展示调用方。")
