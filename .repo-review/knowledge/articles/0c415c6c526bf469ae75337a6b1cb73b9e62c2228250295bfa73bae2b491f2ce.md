# 角色提取、复核与记忆应用实时验证

在临时 Store 中构造带可信来源信息的任务材料，依次调用 extractor 与 verifier 真实角色，再由 MemoryService 应用策略；脚本硬性验证单提案、复核结果及 auto_apply receipt，并报告任务列表，但不要求任务必然存在或字段语义正确。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="setup"></a>
## 隔离样本与角色上下文

脚本要求配置中存在 `traex` profile，经实时能力探测选定模型后，在系统临时目录建立独立 Store。它捕获一条“支付重试方案”文本，并记录 owner、事件时间、时区及 original producer 等 provenance；随后取首个 fragment，构造并校验 extractor 的 context manifest。[临时捕获与上下文清单 ↗](../../../scripts/live-learning-smoke.ts#L13 "支持临时 Store、样本 provenance、固定 fragment 和经 schema 校验的角色上下文构造；同时显示后续 gateway 使用的工作目录来自配置。") 这里能够确认的是：脚本向角色提供了固定材料和可信上下文；由于 gateway 同时接收 `agentCwd`，现有材料不能进一步证明 Agent 无法读取工作区或业务数据库。

<a id="roles"></a>
## 提取、独立复核与应用策略

`RoleRuntimeGateway` 先运行 extractor，脚本断言输出恰好包含一个 proposal，并计算稳定摘要；然后将提案与摘要放入 verifier 的 candidates，以新 job id 发起独立复核，缺少 assessment 即失败。[提取与独立复核调用 ↗](../../../scripts/live-learning-smoke.ts#L73 "支持单提案数量断言、稳定摘要计算、verifier candidates 构造及 assessment 必须存在的流程。")

复核的语义结论、原因码、说明及角色版本被交给 `MemoryService.evaluate`。成功条件仅是策略为 `auto_apply` 且 receipt 存在。[记忆策略评估与应用断言 ↗](../../../scripts/live-learning-smoke.ts#L104 "支持复核信息进入 MemoryService，且脚本硬性成功条件仅为 auto_apply 策略和 receipt 存在。") 因而该检查证明提案被策略层安全应用，但 `store.tasks()` 只是随后被读取和报告，不能据此断言一定生成了任务。

<a id="reporting"></a>
## 审计输出、清理与覆盖边界

脚本把 extraction、verification 的结果与 trace、evaluation 以及当前任务列表写入可配置报告路径，并以受限目录和文件权限保存；控制台输出模型、effort、提案数、复核结论、策略、任务数和 receipt。[实时学习审计报告 ↗](../../../scripts/live-learning-smoke.ts#L114 "支持报告包含角色结果、trace、evaluation 与任务列表，以及任务数仅作为控制台报告字段。") `finally` 会关闭 Store 并删除临时运行目录，因此持久证据主要是外部报告。[临时 Store 清理 ↗](../../../scripts/live-learning-smoke.ts#L145 "支持执行结束时关闭 Store 并递归删除临时目录的资源清理行为。")

覆盖范围限于一个固定措辞、预期高置信的样本。它没有断言任务数量、标题、截止时间、责任人或来源引用，也未覆盖拒绝、需确认、多提案、非法模型输出、重复材料幂等及失败恢复。
