# 模块归类、依赖聚合与理解匹配测试

验证仓库路径映射为架构模块、文件与符号汇总为模块图，以及模块说明按最具体目录前缀匹配。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="bucket"></a>
## 路径归类

测试确认服务端 assistant、memory、retrieval、Lark 集成路径以及 Web 应用路径分别进入预期模块。[模块路径断言 ↗](../../../apps/web/src/codewiki/modules.test.ts#L6 "支持核心服务端目录和 Web 路径的模块归类结果。") 实际归类规则由 contracts 包共享：Web、UI、contracts、agent-runtime 和 Lark 有显式前缀，其他 `apps/server/src` 文件取路径第四段，脚本和未知路径另行归类。[共享模块归类规则 ↗](../../../packages/contracts/src/code-modules.ts#L1 "解释显式包前缀、服务端目录段和兜底模块的来源。") 因而测试中的 assistant 等并非逐个硬编码，而是服务端目录结构自然生成的模块名；尚未覆盖 server-root、packages 和 other 分支。

<a id="aggregate"></a>
## 模块图聚合

测试构造三个文件、三个符号及两条导入边，断言模块节点具有正确文件数与符号数，并只生成 assistant→memory 的仓库内依赖；没有目标文件的 React 外部导入被排除。[模块聚合断言 ↗](../../../apps/web/src/codewiki/modules.test.ts#L16 "支持节点计数及仅保留可解析跨模块导入的测试结论。") 这覆盖了基本计数、跨模块聚合和 unresolved 边过滤，但没有覆盖已删除文件、同模块导入、重复边计数、候选或 missing 且仍有 `toFileId` 的情形。

<a id="matching"></a>
## 最具体理解记录

模块理解匹配不能只看最短的代表文件：测试把 package.json 与 `apps/web/src` 文件放在同一模块，要求从 `apps/web` 和更深的 `apps/web/src` 中选择后者，并拒绝 stale 行。[理解匹配断言 ↗](../../../apps/web/src/codewiki/modules.test.ts#L66 "支持任意文件覆盖、最长前缀优先和 stale 排除行为。") 这回归了短路径遮蔽更具体 curated target 的问题。测试名称称“non-curated”也会被删除，但具体用例只构造 stale 的 curated 行，未直接验证其他 source。
