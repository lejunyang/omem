# 日常消息与事项跟进

文档记录了日常交办与事项跟进的当前可用链路：保存本人指令原文，由模型提出结构化操作，经 MemoryService 校验应用并返回真实回执，再由站内调度提醒。它同时说明了状态与时间模型、接口幂等和提醒去重、真实模型验证范围，以及自动监听回复、重复安排和外部投递等尚未实现能力。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="workflow"></a>
## 交办主线与职责边界

当前主线从本人交办开始：系统保存指令原文，模型只负责提出结构化任务操作，MemoryService 检查并应用，随后返回真实回执，并在约定时间提供站内提醒。随手交办、讨论归并、等待跟进和事项回顾被实现为进入真实 ACP 提示词的模板，而非另建 Agent 框架；捕获内容本身也不会因此获得写权限。[当前交办主线与模板边界 ↗](../../../docs/implementation/daily-follow-up.md#L3 "支持当前可用流程、四类消息模板及其不另建 Agent 框架、不授予捕获内容写权限的说明。")

<a id="state-and-commands"></a>
## 状态、时间与操作语义

事项使用 `open / waiting / done / cancelled` 四种状态。等待对象、下次检查、暂缓截止、原始时间表达和 IANA 时区存入独立的 `follow_up`，不会挤占业务截止时间；存储层统一使用 UTC，展示时再按用户时区转换。完成或取消会停止后续提醒但保留原件与版本历史，回顾操作只读不改状态。网页命令与助手调用复用 MemoryService 的版本、证据及应用回执，并可通过 `requestId` 复用同一传输事件以应对网络重试。[事项状态、跟进时间与命令接口 ↗](../../../docs/implementation/daily-follow-up.md#L7 "解释 follow_up 与业务截止时间的分离、状态操作语义、历史保留，以及网页命令和助手调用的复用与幂等设计。")

<a id="scheduling-and-limits"></a>
## 提醒调度、验证与未实现范围

提醒调度复用现有 30 秒轮询，在事务内核对状态与暂缓时间，并按事项版本、类型和发生时间去重；同一时刻的截止与检查可合并通知，重启后的迟到提醒只补发一次。真实验证使用配置中的 traex ACP 与 `gpt-5.6-sol`，覆盖等待创建、稍后、重开数据库补发、只读回顾和取消停止；注入模型测试与协议 fixture 不被当作真实模型或飞书验收。[提醒调度与真实验证范围 ↗](../../../docs/implementation/daily-follow-up.md#L16 "支持轮询、事务检查、提醒去重和重启补发行为，并界定真实 ACP 验证与 fixture 测试的证据边界。") 自动监听对方回复、自动完成、重复安排、会前准备、定期回顾和外部到期投递仍明确属于未实现范围，当前提醒也不会主动联系等待对象。[尚未实现的跟进能力 ↗](../../../docs/implementation/daily-follow-up.md#L20 "证明自动监听回复、自动完成、重复安排、定期回顾及外部投递等能力仍未实现，避免把规划误写为现状。")
