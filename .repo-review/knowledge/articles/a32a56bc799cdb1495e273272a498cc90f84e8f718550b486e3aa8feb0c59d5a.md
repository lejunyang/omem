# 记忆与任务的原子应用仓储

将记忆或任务的版本化变更、审计记录、站内及飞书投递意图和幂等收据放在同一事务中提交，并以期望版本防止并发覆盖。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="application-transaction"></a>
## 统一应用事务与幂等

`ApplicationRepository` 负责已核准提案落库时的原子性与重试。事务先按 application id，或“提案摘要 + generation”查找收据；同一键且请求摘要一致时返回 duplicate，不一致则报幂等冲突。[应用收据幂等检查 ↗](../../../apps/server/src/storage/repository.ts#L176 "支持按应用键或提案代次重放、请求摘要冲突及 duplicate 收据语义。")

首次应用在同一事务中创建实体版本、change、站内 notification、投递意图、关联记录和 application receipt，事务内钩子或任一写入失败都会回滚整批变更。[应用事务编排 ↗](../../../apps/server/src/storage/repository.ts#L217 "支持实体、变更、通知、投递关联与收据在同一事务中提交和回滚。")

<a id="memory-and-task"></a>
## 记忆与任务版本化

记忆更新必须命中同一 workspace，kind 不得改变，且期望版本必须等于当前版本。每次应用都新增 `memory_revisions`，再以旧版本为条件推进 head；证据项同时具备来源、固定修订和有效性代次时，才记录为当前依赖。[记忆版本与证据依赖 ↗](../../../apps/server/src/storage/repository.ts#L400 "支持记忆乐观并发、新修订、head 推进及来源依赖持久化流程。")

任务也使用期望版本做乐观并发控制，更新当前行后追加历史修订。更新已有任务时，change 的 beforeId 与 afterId 都是任务 id；新建任务时 beforeId 为 `null`，afterId 才是任务 id。[任务版本应用 ↗](../../../apps/server/src/storage/repository.ts#L530 "支持任务更新、新建、历史修订及创建与更新场景不同的 beforeId 语义。")

<a id="delivery-policy"></a>
## 通知投递与边界

外部通知支持即时、延迟窗口和每日本地时间三种策略；定时模式以配置时区构造当天目标时刻，已错过则顺延一天。[外部通知时间策略 ↗](../../../apps/server/src/storage/repository.ts#L125 "支持即时、窗口和按时区定时投递的计算规则。") 活跃的飞书通知目标会各自产生卡片意图，正文截断至 8000 字符，序列化负载超过 30000 字节会使事务失败；飞书 payload 使用规范化的稳定摘要。[飞书投递意图构建 ↗](../../../apps/server/src/storage/repository.ts#L294 "支持活跃目标筛选、卡片长度限制、稳定摘要和调度字段入库。")

被替代的结论是“所有请求摘要都稳定”：记忆和任务应用仍对输入直接 `JSON.stringify` 后哈希，而稳定摘要工具会递归排序对象键并忽略 `undefined`。因此键插入顺序不同但语义相同的请求仍可能得到不同摘要；材料也只证明投递意图入库，未证明外部消息最终送达。[应用请求摘要实现 ↗](../../../apps/server/src/storage/repository.ts#L83 "支持记忆与任务请求摘要仍直接基于 JSON.stringify，而非规范化 JSON。") [规范化稳定摘要 ↗](../../../apps/server/src/storage/digest.ts#L3 "解释稳定摘要会递归排序对象键、忽略 undefined，再对规范化 JSON 计算 SHA-256。")
