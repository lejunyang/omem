# 应用结果原子落库与通知投递仓库

该仓库将已确认的记忆或任务变更作为一次事务应用：检查请求幂等性和实体版本，追加修订，记录变更、通知、投递意图与应用回执。此前“不可变修订”的表述已收窄为“追加修订”：本文件只证明当前流程插入新修订，不能证明数据库或全系统禁止修改既有修订。仓库负责编排持久化与通知排程，不负责实际发送、证据真实性验证或投递重试。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-contract"></a>
## 职责与应用合同

`ApplicationRepository` 统一接收记忆和任务的应用结果。输入包含工作区、应用标识、提案摘要与代次、实体内容及投递绑定；回执返回实体类型、版本、变更记录和重复命中状态。[应用输入、回执与钩子合同 ↗](../../../apps/server/src/storage/repository.ts#L7 "说明仓库接收的应用元数据、记忆与任务内容，以及返回回执和可用钩子的结构。") 因而一次“应用”不仅修改业务实体，还留下可追踪的修订、变更、通知和投递记录。

幂等查询接受相同 `applicationId`，或相同 `proposalDigest + generation`；若查到回执但请求摘要不同，则报 `APPLICATION_IDEMPOTENCY_CONFLICT`。[应用幂等回执检查 ↗](../../../apps/server/src/storage/repository.ts#L188 "支持按应用标识或提案摘要与代次查询回执，以及请求摘要不一致时报冲突的论断。") 请求摘要直接使用 `JSON.stringify` 后计算 SHA-256，键插入顺序可能改变结果，与 Lark 载荷使用的规范化摘要并非同一算法。[请求摘要计算 ↗](../../../apps/server/src/storage/repository.ts#L83 "证明应用请求摘要直接基于 JSON.stringify 和 SHA-256，支持键顺序边界的说明。")

<a id="transaction-flow"></a>
## 事务提交与通知意图

公共提交由 `BEGIN IMMEDIATE`、`COMMIT` 和异常时的 `ROLLBACK` 包裹。[数据库事务包装器 ↗](../../../apps/server/src/storage/repository.ts#L176 "支持提交使用 BEGIN IMMEDIATE，并在成功时提交、异常时回滚。") 事务主体依次检查既有回执、执行 `before` 钩子和实体写入，再创建变更、站内通知及站内投递意图。[应用提交前半流程 ↗](../../../apps/server/src/storage/repository.ts#L229 "支持事务内依次执行重复检查、钩子、实体写入、变更记录和站内投递意图的说明。") 随后它为有效的 Lark owner notification 目标构造卡片、校验 30,000 字节上限、写入待发送意图，最终保存应用回执并调用 `after` 钩子。[Lark 意图、回执与提交后钩子 ↗](../../../apps/server/src/storage/repository.ts#L294 "支持 Lark 卡片生成、载荷限制、投递意图、应用回执以及 after 钩子执行位置的说明。") 因此这些数据库写入及钩子异常会影响整笔提交；但若钩子执行不可回滚的外部 I/O，数据库回滚不能撤销外部副作用。

Lark 载荷摘要依赖 `stableDigest`，其递归过滤 `undefined`、排序对象键并生成 SHA-256，使等价对象较少受键插入顺序影响。[规范化载荷摘要 ↗](../../../apps/server/src/storage/digest.ts#L3 "解释 stableDigest 如何递归规范化对象后生成稳定摘要。") 本文件只生成 `pending` 投递意图和下次尝试时间，没有展示发送、重试或送达确认。

<a id="entities-and-boundaries"></a>
## 修订追加、证据依赖与边界

记忆更新先核对 kind 和 `expectedVersion`，然后插入新 `memory_revisions`，令其指向旧 head，并以旧版本为条件推进主表 head。[记忆版本检查与修订追加 ↗](../../../apps/server/src/storage/repository.ts#L419 "支持 kind 校验、乐观锁、插入新修订、关联旧 head 和条件推进新 head；同时限定只能证明当前流程采用追加写入。") 此处将先前的“不可变修订”结论替换为“追加修订”：材料证明当前路径不更新旧修订，但未提供表约束或其他写入路径，不能据此断言全局不可变。

完整 `evidenceSet` 会经 JSON 序列化写入新修订。[完整证据集合写入修订 ↗](../../../apps/server/src/storage/repository.ts#L452 "证明 evidenceSet 在插入 memory_revisions 时被完整 JSON 序列化保存。") 之后只有同时含字符串 `sourceId`、字符串 `sourceRevisionId` 和整数 `validityEpoch` 的条目才写入 `memory_dependencies`；其他条目被跳过，本流程也不验证目标来源是否存在。[结构化证据依赖提取 ↗](../../../apps/server/src/storage/repository.ts#L497 "支持证据依赖字段筛选、合格条目写入依赖表及不合格条目被跳过的边界。")

任务更新同样使用版本条件，并在新建或更新后追加 `task_revisions`；截止时间会规范化为 ISO 时间。[任务更新与修订追加 ↗](../../../apps/server/src/storage/repository.ts#L540 "支持任务截止时间规范化、乐观锁更新以及追加任务修订的说明。") 外部通知支持即时、延迟窗口和指定时区的每日时间，若当天目标已过则排至次日。[外部通知排程算法 ↗](../../../apps/server/src/storage/repository.ts#L125 "支持即时、窗口和每日定时三种排程模式，以及当天时间已过时顺延的说明。") 表结构唯一约束、投递 worker 以及夏令时异常时刻的产品规则均不在现有材料中。
