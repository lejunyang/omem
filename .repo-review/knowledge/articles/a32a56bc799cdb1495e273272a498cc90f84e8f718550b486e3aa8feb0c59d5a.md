# 应用结果持久化与通知意图仓库

该仓库把已确认的记忆或任务应用转换为带版本的实体、修订记录、变更、通知、按应用元数据创建的投递意图、可用飞书目标的附加投递意图及幂等回执，并以 SQLite 事务保证写入共同成功或回滚。此前将应用元数据对应意图限定为“站内投递”的结论已被替代：其渠道和目标由调用方元数据决定。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="application-transaction"></a>
## 统一提交与幂等边界

`ApplicationRepository` 用 `BEGIN IMMEDIATE` 包裹应用过程，异常时回滚。提交前按“工作区 + applicationId”或“提案摘要 + generation”查找既有回执；请求摘要相同则返回标记为重复的原回执，摘要不同则抛出幂等冲突。[事务与幂等回执查询 ↗](../../../apps/server/src/storage/repository.ts#L178 "支持事务提交回滚、重复回执返回以及摘要冲突处理的说明。")

首次提交先执行 `before` 钩子并创建实体，再写入 change 与通知。[应用实体与变更写入 ↗](../../../apps/server/src/storage/repository.ts#L231 "支持首次提交在事务中执行前置钩子、创建实体并记录变更和通知。") 随后生成应用回执并执行 `after` 钩子，而真正的数据库 `COMMIT` 要等整个回调返回后才发生。[应用回执与后置钩子 ↗](../../../apps/server/src/storage/repository.ts#L366 "支持回执写入及 after 钩子位于事务提交之前的判断。") 因而这些数据库写入共享事务边界，但材料未证明钩子只包含可回滚操作。

<a id="memory-flow"></a>
## 记忆修订流程

记忆同时维护当前头部和不可变修订。新建时写入 `memories` 与首个 `memory_revisions`；更新时要求 kind 不变且 `expectedVersion` 精确匹配，再以旧版本为条件推进 head、scope、状态和版本。新修订通过 `supersedes_revision_id` 指向旧 head，统一提交层据此记录变更前后的修订。[记忆版本与不可变修订 ↗](../../../apps/server/src/storage/repository.ts#L402 "支持记忆新建、kind 检查、乐观锁、修订链和 head 更新流程。")

证据依赖仅从结构完整的 evidence 项生成：必须具有字符串 `sourceId`、`sourceRevisionId` 和整数 `validityEpoch`。不合格项仍存在于修订保存的原始 evidence JSON 中，但不会进入 `memory_dependencies`，所以依赖表是最低结构校验后的派生索引，而非 evidenceSet 的完整镜像。[记忆证据依赖写入 ↗](../../../apps/server/src/storage/repository.ts#L499 "支持 evidenceSet 的结构筛选规则以及依赖表只记录合格引用的边界。")

<a id="task-flow"></a>
## 任务更新、随访与历史

任务应用同样采用乐观版本控制：已有任务缺少或错用 `expectedVersion` 会失败，新任务默认状态为 `open`。截止时间被规范化为 ISO 字符串；当前任务行完成插入或更新后，还会追加 `task_revisions`，保存标题、详情、状态、下一步、证据和随访快照。[任务当前态与修订写入 ↗](../../../apps/server/src/storage/repository.ts#L532 "支持任务日期规范化、乐观版本更新、新建默认值及历史修订追加流程。")

随访对象由共享合同校验，合同约束等待对象、带偏移量的日期时间、IANA 时区及严格字段集合。[任务随访共享合同 ↗](../../../packages/contracts/src/task-flow.ts#L3 "说明任务随访日期、时区及严格字段校验来自共享合同。") 未提供 `followUp` 时沿用旧值，显式传入 `null` 时清除；但现有材料不包含上层入口，不能据此断言所有任务输入都经过完整的命令合同校验。

<a id="delivery-boundaries"></a>
## 通知调度与投递边界

每次首次应用都会按 `metadata.delivery` 创建一个 `pending` 投递意图，其 `channelBindingVersion`、`channel`、`target` 和可选 payload 摘要均来自应用元数据。[应用投递元数据合同 ↗](../../../apps/server/src/storage/repository.ts#L8 "证明通用投递意图的渠道和目标由应用元数据提供，没有类型级的站内渠道限制。")[按元数据创建投递意图 ↗](../../../apps/server/src/storage/repository.ts#L261 "支持应用时创建 pending 意图，并直接写入 metadata.delivery 的渠道、目标和绑定版本。") 因此此前称其为“站内投递意图”的结论已被替代：局部变量名虽然是 `inAppIntentId`，实际存储逻辑并未限定渠道为站内。

除此之外，只有工作区下连接、绑定和目标均为 active 的 owner notification 才会产生飞书意图；卡片内容会截断并检查序列化大小，仓库只写入待投递记录，不负责实际发送。[飞书投递意图创建 ↗](../../../apps/server/src/storage/repository.ts#L296 "支持 active 目标筛选、卡片内容限制、pending 状态以及本层只形成投递意图的说明。") 飞书调度支持立即、延迟窗口及指定时区的每日时间，已错过当天时间时顺延至次日。[外部通知时间计算 ↗](../../../apps/server/src/storage/repository.ts#L127 "支持立即、窗口和按本地时区定时三种调度语义。")

飞书 payload 使用递归排序对象键并过滤 `undefined` 的稳定摘要，而记忆和任务应用请求直接对 `JSON.stringify` 结果哈希。[应用请求摘要实现 ↗](../../../apps/server/src/storage/repository.ts#L85 "支持应用请求摘要直接依赖 JSON.stringify、可能受对象键顺序影响的判断。")[规范化稳定摘要 ↗](../../../apps/server/src/storage/digest.ts#L3 "对照说明稳定摘要会递归排序对象键并过滤 undefined。") 因而键顺序不同但语义相同的应用输入可能得到不同请求摘要。
