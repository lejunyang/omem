# 受控学习流水线的集成与恢复测试

该测试以临时 SQLite 数据目录和受控 ACP fixture 验证捕获内容经过独立提取、复核与原子应用后形成任务，并覆盖 Store 与流水线重建后的恢复、重复回放、输入过期、优雅停机、批量变更门控及 worker 类型隔离。此前“进程重启”的表述由材料无法支持，现已替换为组件和存储重开后的持久化恢复；测试也不等同于真实外部 Agent CLI 的在线兼容性检查。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 验证范围与测试边界

这组测试验证学习任务在异步执行中能否自动落地，并避免恢复、重复消费或批量输出造成重复副作用。每个用例使用临时目录隔离数据库，结束后统一清理；Agent profile 实际调用本地 Node fixture，因此结果可重复，但不代表真实外部 CLI 已通过认证和兼容性检查。参考 [临时环境与受控 ACP 配置 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L11 "支持测试使用临时目录、自动清理和 Node fixture profile，并界定其不是实际外部 CLI 验证。")

测试直接组合应用构建、存储、记忆服务与学习流水线，覆盖 HTTP 接入、持久化、角色运行和应用结果之间的集成边界，而不是单个函数的孤立单元测试。参考 [学习流水线集成模块入口 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L5 "支持测试直接组合合同、应用、记忆服务、学习流水线与存储层的集成测试定位。")

<a id="happy_path"></a>
## 从 HTTP 捕获到原子应用

成功路径明确启用 learning worker、注册受控 ACP profile，并向 `/api/captures` 提交带来源信息的手工捕获。参考 [HTTP 捕获与 learning worker 配置 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L66 "支持成功路径启用 learning worker、选择受控 ACP profile，并通过 HTTP 提交捕获的论断。") 随后应出现 `extract_claims` 与 `verify_proposals` 两个成功 job；两阶段使用不同 session，复核后的 proposal 才进入 `applied`，策略结果为自动应用。参考 [独立提取复核与自动应用断言 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L104 "支持两个 job 成功、阶段使用不同 session，以及 proposal 经复核后自动应用的结果。")

最终只允许生成一条应用回执，健康接口还应显示 worker 正在运行且没有遗留错误。这从结果侧区分了“已入列”“角色执行成功”和“副作用已经原子落地”。参考 [应用回执与健康状态 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L133 "支持成功路径只生成一条应用回执，并保持 learning worker 健康运行。")

<a id="recovery"></a>
## 持久化恢复、幂等与失败状态

恢复用例先完成提取，再停止流水线、关闭 Store，并从同一目录重新创建 Store 与流水线；持久化的 verifier job 随后继续执行，只产生一个任务和一条回执。参考 [Store 与流水线重建后的恢复 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L150 "支持关闭并重新创建 Store 和流水线后继续持久化 verifier job；该范围不证明操作系统级进程重启。") 这证明的是组件与存储重开后的恢复，替代此前证据不足的“实际进程重启”结论。再次入列同一提取结果后，任务和回执数量仍不增加，说明回放具备幂等约束。参考 [验证任务重复回放幂等性 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L179 "支持再次入列同一提取结果后任务数和应用回执数仍保持不变。")

若同一来源已产生新 revision，旧 job 会以 `STALE_JOB_INPUT` 失败，而当前版本仍可继续处理。参考 [过期 revision 拒绝 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L214 "支持旧 revision 对应 job 以 STALE_JOB_INPUT 失败，而流水线继续处理当前来源版本。") worker 执行超时任务时被停止，则 job 回到 `retry_wait` 并标记为 `transient`，为后续恢复保留状态。参考 [优雅停机后的重试状态 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L252 "支持运行中任务在停止后进入 retry_wait，并被归类为 transient。")

<a id="batch_and_boundaries"></a>
## 批量门控与 worker 隔离

批量策略按去重后的整体影响决策：十二个不同实体的创建请求全部停在 `awaiting_decision`，合并为一个 AttentionCase，且不生成记忆或应用回执。参考 [不同实体批量门控 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L308 "支持超预算批次整体停放、合并为一个 AttentionCase，且不产生应用副作用。") 十二个相同实体的创建则只应用一次，其余十一条保留为重复项，也不会产生决策卡。参考 [同实体批量去重 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L365 "支持相同实体批次按一次影响处理，仅应用一条、保留其余重复项且不创建决策卡。")

learning worker 不领取 `knowledge:code-analyst` 工作，该 job 保持排队且没有 attempt，证明当前方向的类型隔离。参考 [learning worker 类型隔离 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L407 "支持 learning worker 不领取知识角色 job，且该 job 没有产生执行 attempt。") 实现还区分 `bad_output`、`auth`、`transient`、`config` 与 `permanent` 错误，但本文件仅直接覆盖部分失败路径，其余分类仍需补充集成或 live check。参考 [流水线错误分类 ↗](../../../apps/server/src/learning/pipeline.ts#L40 "说明实现包含多类错误归因，支持识别当前测试材料尚未覆盖的分类分支。")
