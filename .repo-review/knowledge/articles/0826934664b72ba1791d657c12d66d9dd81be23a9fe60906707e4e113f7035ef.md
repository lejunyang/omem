# 受控学习流水线的集成、恢复与批量门控测试

该测试以临时 SQLite 数据目录和 ACP 角色夹具验证学习流水线的持久化路径：捕获经过独立提取与复核会话后，在成功路径中产生已应用提案、待办和唯一应用回执；重启及重复投递不重复产生已断言的副作用；过期输入被拒绝，停机中的作业转为可重试；批量变更按去重后的影响规模整体门控；学习 worker 不消费知识角色作业。此前将成功路径概括为“原子应用”的结论已被更精确的表述替代，因为现有用例没有注入应用阶段故障或断言事务回滚。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_setup"></a>
## 测试目标与受控环境

该文件验证捕获入口、持久化作业、独立角色会话、策略判断和最终副作用能否组成可恢复、可观察的学习闭环。每个用例使用独立临时目录，并在结束后清理，降低数据库状态串扰；ACP profile 由当前 Node 进程启动固定角色夹具，超时为三秒，因此结论限定于受控协议和宿主接线。[临时目录与 ACP 测试配置 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L11 "支持测试隔离方式以及由 Node 启动固定 ACP 夹具、设置三秒超时的结论。")

辅助构造会写入来源、操作者验证、事件时间及 producerKind，并组合 Store、MemoryService、FeedbackService 与 LearningPipeline；较短轮询间隔用于加快异步集成测试。[捕获与流水线辅助构造 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L33 "支持捕获 provenance 字段以及 Store、记忆、反馈和学习流水线的组合方式。") 这说明测试跨越 HTTP 装配、作业处理和持久状态，但不能仅凭模块组合推断未被断言的事务性质。

<a id="successful_path"></a>
## 成功路径、独立会话与幂等恢复

首个场景从 `/api/captures` 发起请求，最终断言生成预期待办，提取与复核两类作业均成功且使用不同 session；提案状态为 `applied`、策略结果为 `auto_apply`，数据库中应用回执数量为一，健康接口报告流水线运行且无错误。[HTTP 捕获成功路径断言 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L65 "支持独立提取与复核 session、已应用提案、唯一回执和健康状态；引用范围没有应用故障注入，因而也限定了结论边界。") 这些断言支持“成功路径完成应用且只产生一个回执”，但没有应用中途故障注入或回滚检查，因此此前“证明原子应用”的结论被替代。

恢复场景先完成提取，再关闭并重开同一数据目录，由新流水线处理持久化的复核作业；随后重放同一复核输入，任务数和回执数仍保持为一。[重启恢复与重复复核幂等 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L150 "支持持久化复核作业在重启后恢复，并且重放不重复增加任务或应用回执。") 这直接证明所覆盖结果的跨重启恢复与重复投递幂等，但不等同于证明任意副作用组合都具备事务原子性。

<a id="failure_batch_isolation"></a>
## 失败边界、批量门控与 worker 隔离

过期场景通过同一 externalId 写入新修订，使旧作业以 `STALE_JOB_INPUT` 失败，同时当前输入仍可继续形成任务；长运行夹具在停机时被中断后，作业进入 `retry_wait` 并标记为 transient。[过期输入与优雅停机 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L214 "支持旧修订作业失败、当前输入继续处理，以及停机中的作业转为可重试状态。") 用例未覆盖实际退避时长、最大重试次数或最终死信结果。

批量策略按整个 ChangeSet 的去重影响执行：十二个不同实体的 create 全部停放为 `awaiting_decision`，合并成一个 AttentionCase，且没有应用回执或 active memory。[不同实体批量变更门控 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L308 "支持十二条不同 create 整批停放、只生成一个 AttentionCase，且不产生回执或 active memory。") 十二个相同实体、相同陈述的 create 则折算为影响一，仅一条 applied，其余十一条 retained，也不生成决策卡。[同实体批量创建去重 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L365 "支持十二条相同实体提案按影响一处理，仅应用一条并保留十一条重复项。") 两端用例尚未说明部分重复、create/update/delete 混合或应用阶段异常时的整体一致性。

此外，学习流水线面对 `knowledge:code-analyst` 作业时不领取、不创建 attempt，使作业继续保持 queued，明确了学习 worker 与知识 worker 的 kind 隔离。[知识角色作业隔离 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L407 "支持学习流水线不领取知识角色作业的 worker kind 边界。")

<a id="coverage_limits"></a>
## 证据边界与现场验证缺口

这些测试使用真实 Store、Fastify 注入和子进程角色夹具，能够支持应用进程内路由接线、作业状态变化以及被明确查询的数据库结果。MemoryService 的结果类型也区分策略结果、可选应用回执和批量延后标记，说明“是否应用”和“批量门控”是可单独观察的结果。[学习策略结果结构 ↗](../../../apps/server/src/memory/service.ts#L45 "说明评估结果分别记录策略、应用回执和批量延后状态，支持对应用结果与门控结果分别观察。")

不过测试 profile 的 command 是当前 Node 可执行文件，参数指向固定夹具。[临时目录与 ACP 测试配置 ↗](../../../apps/server/tests/learning-pipeline.test.ts#L11 "支持测试隔离方式以及由 Node 启动固定 ACP 夹具、设置三秒超时的结论。") 因此测试通过不能外推为生产 ACP CLI 已安装、认证有效、指定模型与 effort 受支持，也不能覆盖真实模型在超时、长上下文或非规范输出下的表现。现场能力验证应与这组夹具集成测试分别记录。
