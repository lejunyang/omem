# assistant · 模块理解

assistant 模块是 Web 与飞书共用的会话执行层：它串联持久化轮次、受可见性约束的原始证据检索、ACP 模型调用、取消恢复及受治理的事项写入，并明确区分生产模型与测试替身。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="role-and-boundary"></a>
## 职责与生产边界

`AssistantRuntime` 是 Web 与飞书共享的主执行面，集中负责上下文组装、只读检索、轮次持久化、事项治理与降级；模型只通过受限端口接收证据和工具合同，不能自行扩大读取或写入权限。[主助手运行时职责 ↗](../../../apps/server/src/assistant/runtime.ts#L185 "界定 Web 与飞书共用执行面，以及上下文、检索、治理、持久化和模型注入的职责边界。")

生产适配器只接受已配置的 ACP profile；缺少配置或使用 CLI transport 时明确报模型不可用，不生成伪回答。[ACP 传输限制 ↗](../../../apps/server/src/assistant/acp-model.ts#L10 "支持生产适配器仅接受 ACP profile，并在配置缺失或 transport 不受支持时如实失败。") `DeterministicAssistantModel` 仅供测试稳定展示运行时已经检索的证据，不能代表真实传输、推理或工具调用已验证。[测试模型边界 ↗](../../../apps/server/src/assistant/default-model.ts#L7 "说明确定性模型只用于测试，生产缺少真实模型时不得以固定答案替代。")

<a id="turn-flow"></a>
## 对话、检索与引用流程

请求会先持久化并按外部事件标识去重；同一会话的新消息取消旧轮次，随后沿 promise 链串行执行。[轮次入队与串行执行 ↗](../../../apps/server/src/assistant/runtime.ts#L224 "支持模型调用前持久化、外部事件去重、新消息取消旧轮次及同会话串行化。") 执行阶段只读取当前会话已完成历史，并把上一轮选中证据与本轮检索结果合并；模型最多提出三条检索词，宿主只追加一轮检索。[历史上下文与补充检索 ↗](../../../apps/server/src/assistant/runtime.ts#L447 "支持当前会话历史、上一轮工作证据和最多一轮补充检索的流程说明。")

ACP 提示对历史和证据正文设定预算，同时加入可信上下文、事项、时区和证据标识，要求返回单一 JSON。[结构化模型提示 ↗](../../../apps/server/src/assistant/acp-model.ts#L45 "说明历史与证据预算、可信上下文、事项、时区、检索预算及单一 JSON 输出合同。") 最终引用还会与运行时实际提供的 fragment 集合求交集，模型无法凭空引用未暴露材料。[引用集合过滤 ↗](../../../apps/server/src/assistant/runtime.ts#L593 "证明最终引用只保留运行时实际提供过的证据标识。")

<a id="governed-actions"></a>
## 证据边界与受治理写入

检索候选会补全为当前 head 的原始片段，并再次检查会话可见性；派生材料和旧版本被排除，群聊未注入策略时默认拒绝全部证据。[证据读取与可见性边界 ↗](../../../apps/server/src/assistant/runtime.ts#L654 "支持证据补全、当前 head 与非派生限制，以及群聊未注入策略时缺省拒绝的结论。") 创建事项须先由运行时识别明确记录意图，模型请求本身不构成授权。直接委派时会尽力捕获 owner 原话，再交给 `MemoryService` 评估并尝试应用；只有返回任务 receipt 才算成功，未自动应用或治理异常都会作为拒绝结果返回。[受治理的事项创建 ↗](../../../apps/server/src/assistant/runtime.ts#L784 "支持 owner 原话捕获是尽力而为操作，并证明只有治理成功返回任务 receipt 才视为应用成功，否则返回未自动应用或治理错误。")

完成、重开和改期还须匹配用户原文中的明确动作及可见事项版本，只有改期额外校验原文时间表达和带时区的有效时间。[事项变更校验 ↗](../../../apps/server/src/assistant/runtime.ts#L697 "证明事项变更要求明确动作和匹配版本，且只有改期必须验证原文时间表达。") 模型一旦请求变更，其推测性成功文本会被丢弃，最终反馈依据治理动作及重新读取的持久化事项生成。[持久化结果反馈 ↗](../../../apps/server/src/assistant/runtime.ts#L581 "支持丢弃模型推测性成功文本，并依据治理动作和持久化事项构造最终反馈。")

<a id="progress-and-limits"></a>
## 恢复能力与现有限制

取消来源会合并为统一信号，运行时另以独立计时器和 `Promise.race` 实施硬超时，避免模型忽略中止后无限等待。[统一取消信号 ↗](../../../apps/server/src/assistant/runtime.ts#L419 "支持外部取消、新消息抢占及运行时计时器合并为统一中止信号。")[独立硬超时 ↗](../../../apps/server/src/assistant/runtime.ts#L626 "证明模型调用以独立计时器参与竞争，即使模型忽略中止也不会无限等待。") 模型明确不可用时，轮次被标回待处理状态，供人工重试或重启恢复。[模型不可用后的待处理状态 ↗](../../../apps/server/src/assistant/runtime.ts#L515 "证明 ModelUnavailableError 会把轮次标记为 pending，以便后续重试，而非伪造回答。") 恢复流程会查询真实 application receipt，避免已提交的创建事项重复执行。[Receipt 查询与恢复 ↗](../../../apps/server/src/assistant/runtime.ts#L301 "说明人工重试和重启恢复会查询真实 application receipt，同时揭示匹配依赖外部事件标识和创建事项提案前缀。")

被替代的结论是“所有写操作都会产生 receipt，且具备同等恢复防重能力”：创建事项只有成功应用才产生 receipt，现有恢复匹配也依赖外部事件标识及创建事项提案前缀。解析器还未显式拒绝同时出现创建与更新；合法更新会覆盖先前解析出的创建调用。[模型回复解析边界 ↗](../../../apps/server/src/assistant/acp-model.ts#L121 "支持 JSON 字段解析以及创建、更新同时出现时更新调用覆盖创建调用这一限制。") 群聊策略的实际装配点同样未出现在当前材料中，因此只能确认缺省拒绝，不能确认飞书端已完成来源、成员和 scope 的端到端放行。[证据读取与可见性边界 ↗](../../../apps/server/src/assistant/runtime.ts#L654 "支持证据补全、当前 head 与非派生限制，以及群聊未注入策略时缺省拒绝的结论。")
