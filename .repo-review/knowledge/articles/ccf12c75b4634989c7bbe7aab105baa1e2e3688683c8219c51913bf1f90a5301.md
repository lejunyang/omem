# 关键词检索的项目边界与有效记忆测试

该测试验证关键词检索不会把未经确认的会话或应用上下文误当作项目权限边界，同时确认只有可信项目标识才能限定项目记忆，并排除已失效记忆。测试使用临时 SQLite 存储执行真实写入和查询，但未覆盖可信项目对原始材料检索的行为、排序质量及其他查询条件。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 防止上下文被误用为项目过滤器

这组测试解决的核心风险是：`conversationId`、`application` 等上下文携带字段可能看起来像项目归属，却不具备可信的权限或作用域含义。测试把两份材料放入不同会话和应用，再以不可信的 `project_id` 查询，仍要求工作区范围内召回目标材料；无项目条件时也应同时找到两份材料。参考 [会话上下文检索边界 ↗](../../../apps/server/tests/retrieval-keyword.test.ts#L38 "支持不同会话材料的构造、不可信项目不得过滤以及工作区范围召回的断言。")

测试通过 `Store` 写入材料、由 `captureSchema` 校验输入，并直接构造 `KeywordRetrieval` 查询，说明这里验证的是存储到检索的集成行为，而非孤立的模拟接口。参考 [真实存储与检索接线 ↗](../../../apps/server/tests/retrieval-keyword.test.ts#L6 "说明测试使用 Store、KeywordRetrieval 和 captureSchema，并创建及清理临时存储。")

<a id="memory_scope"></a>
## 可信项目才约束记忆范围

对记忆检索，测试先写入一条作用域为 `payments` 的有效记忆，然后对同一关键词执行三种查询：不可信且不匹配的项目仍能召回；可信但错误的项目必须排除；可信且匹配的项目应召回。由此固定了 **项目标识与可信度必须同时成立才可过滤** 的合同，避免外部上下文意外缩窄个人记忆召回。参考 [可信项目过滤断言 ↗](../../../apps/server/tests/retrieval-keyword.test.ts#L81 "支持不可信项目、可信错误项目和可信匹配项目三种记忆查询结果。")

测试数据通过应用仓储写入，而 `Store` 将 SQLite、应用仓储及其他运行时仓储集中初始化，因此这些断言依赖真实数据库结构和应用写入路径。参考 [SQLite 存储初始化 ↗](../../../apps/server/src/store.ts#L38 "说明 Store 初始化 SQLite 数据库、迁移及应用仓储，支持测试所依赖的真实持久化路径。")

<a id="status_and_limits"></a>
## 失效记忆不得作为证据

第三个场景写入两条命中相同关键词的记忆，再直接把其中一条标为 `invalidated`。查询结果必须全部为 `active`，包含有效记录且排除失效记录，最终只剩一个命中。这验证了失效内容不会继续作为可召回证据。参考 [有效记忆过滤断言 ↗](../../../apps/server/tests/retrieval-keyword.test.ts#L137 "支持将一条记忆置为失效后，查询只返回 active 记忆的结论。")

当前测试主要断言结果数量、状态和成员关系，没有检查相关性顺序、分数、分页或时间与可见性过滤。检索实现确实对数量上限、空分词、时间范围和可见性回调设置了入口条件，但这些行为不在本文件的断言范围内。参考 [原始材料查询入口条件 ↗](../../../apps/server/src/retrieval/keyword.ts#L53 "说明检索实现还处理查询上限、分词、时间范围和可见性，而目标测试未覆盖这些条件。")
