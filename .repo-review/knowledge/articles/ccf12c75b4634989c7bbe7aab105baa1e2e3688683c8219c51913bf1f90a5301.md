# 关键词检索的项目边界与有效记忆测试

该测试以临时 SQLite Store 构造真实捕获与记忆数据，验证关键词检索不会把未受信的项目上下文误当成权限过滤条件，同时只返回 active 记忆。它覆盖项目过滤和失效记忆排除，但未覆盖排序、时间与可见性过滤、中文分词、派生证据排除及知识检索。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_and_fixture"></a>
## 测试目标与真实存储夹具

这组测试针对 `KeywordRetrieval` 的两个关键安全边界：项目上下文只有在明确受信时才能缩小记忆召回范围，失效记忆也不能继续作为证据返回。测试不是纯协议桩，而是为每个用例创建临时目录和真实 `Store`，结束后关闭数据库并递归清理目录，从而隔离状态。[临时 Store 的建立与清理 ↗](../../../apps/server/tests/retrieval-keyword.test.ts#L10 "支持测试使用独立临时数据库并在每个用例后释放资源的说明。")

`Store` 构造时创建 SQLite 文件、执行迁移并初始化 application 等仓储，因此测试中的捕获与记忆写入会经过实际持久化层。[Store 的 SQLite 初始化 ↗](../../../apps/server/src/store.ts#L38 "支持测试实际经过数据库迁移和仓储初始化，而非只使用内存协议桩。") 捕获输入还通过共享的 `captureSchema` 校验 provenance 等字段，说明来源数据结构与应用合同保持一致。[捕获来源合同 ↗](../../../packages/contracts/src/index.ts#L49 "说明测试依赖共享捕获合同校验 provenance，并关联测试导入的 captureSchema。")

<a id="project_trust_flow"></a>
## 项目可信度的断言流程

第一个用例把两份来源放进不同 conversation/application 上下文，再携带 `project_id="conv-B"`、`project_trusted=false` 搜索 A 的独有词；仍命中 A，证明 conversationId 只是上下文载体，不能冒充可信项目边界。无项目条件搜索公共标记时，两份来源均应召回。[来源检索不信任会话项目 ↗](../../../apps/server/tests/retrieval-keyword.test.ts#L38 "支持不同会话来源仍可在未受信项目参数下进行工作区级召回的断言。")

第二个用例写入一条属于 `payments` 的 active claim：未受信的错误项目仍能搜到；受信但不匹配的项目必须排除；受信且匹配时重新命中。[受信项目的记忆过滤 ↗](../../../apps/server/tests/retrieval-keyword.test.ts#L81 "支持未受信项目不缩小召回，而受信项目必须匹配记忆 scope 的三组对照断言。") 这精确验证了“是否过滤”由 `project_trusted` 与 `project_id` 联合决定，但没有证明项目权限或多租户隔离已经实现。

<a id="active_only_and_limits"></a>
## 有效状态约束与未覆盖行为

第三个用例创建两条含相同关键词的记忆，随后直接把其中一条数据库状态改为 `invalidated`。搜索结果必须全部为 `active`，包含有效实体、排除失效实体，且总数为一，因此同时检查了状态字段和实体集合。[失效记忆排除断言 ↗](../../../apps/server/tests/retrieval-keyword.test.ts#L137 "支持检索只返回 active 记忆，并明确排除被标记为 invalidated 的实体。")

从提供的实现片段只能确认来源检索会限制结果数量、分词、处理时间范围与可见性回调，并为较长词项准备 FTS 查询。[来源关键词检索入口 ↗](../../../apps/server/src/retrieval/keyword.ts#L53 "界定实现片段可确认的 limit、分词、时间范围、可见性与长词 FTS 行为，并据此指出本测试未覆盖的分支。") 当前测试没有断言这些分支，也没有覆盖空查询、limit 上下界、排序稳定性、中文二字词的 LIKE 路径、原始/派生证据过滤、`readEvidence` 或 knowledge retrieval；这些能力不能由本文件的通过结果推出。
