# 统一知识流水线、Code Wiki 与验证边界

本专题串联实现文档中从历史 Code Knowledge 设计到当前通用知识流水线的演进：代码知识不是第二套知识库，而是统一不可变证据链上的可重建投影；材料经共用角色分析、独立复核后发布，并通过 Evidence Trail、检索和助手回到原始片段。当前已具备中文语义检索、来源更新重核验和多视口浏览器流程，但跨文件调用、跨版本符号身份、全库知识覆盖及若干外部集成仍有明确限制。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_and_evolution"></a>
## 为什么要统一证据与知识模型

早期 repo-review 已能把仓库保存为不可变版本和固定片段，并用人工关系连接代码、需求、决策与测试，但代码侧缺少精确符号和结构关系，因此历史方案提出以确定性 TS/Vue 解析补充文件、符号与结构边，模型理解只作为可选增强。[历史设计的定位与目标 ↗](75e01b37461410c9d406f94ae6fbe9291a362bf8674762b4d74d32c807364a52.md#positioning "说明 Code Knowledge 文档是历史提案，并概括早期弱代码建模与确定性解析目标。")[早期代码知识问题与分层方案 ↗](../../../docs/implementation/code-knowledge-design.md#L14 "以原始设计材料支持固定片段、弱符号建模以及确定性结构层先行的具体背景。")

这条路线的关键不是建设独立 Code Wiki，而是让代码、文档、对话和图片都服从同一事实边界：原始权威始终是 Capture→Source→Revision→Fragment，代码图和知识正文只是可重建投影。这样既能提供面向人的解释，又能在来源变化、模型失败或定位缺失时保留旧证据并诚实标记状态。

<a id="pipeline_and_connections"></a>
## 如何生成、复核、阅读与召回

当前通用流程先由材料角色组织正文和内联引用，再用独立会话检查引用是否真正支持附近论断；只有通过复核的修订才能发布，分析期间来源改变也会阻止旧结果落地。用户回答则作为新的原始材料进入下一轮，而不是直接改写既有证据。[共用运行时与发布门槛 ↗](277c8acc89c393a5373ca36d829cc4939bc43481c0b909f82600c4abe65e3ee7.md#runtime-pipeline "引用子知识对共用角色运行时、独立复核和发布条件的组织性解释。")[分析、复核与仓库适配原始说明 ↗](../../../docs/implementation/knowledge-pipeline.md#L23 "支持只有通过复核的正文才发布、来源变化拒绝发布、用户回答作为原始材料及可提交产物等流程。")

仓库只是输入适配器：通过的知识可保存为 JSON 与 Markdown，索引重建不触发模型。个人知识和仓库知识共用 Evidence Trail，可从正文逐层进入章节、原始材料或代码，并恢复返回路径、滚动、焦点与深链；助手即使命中派生正文，最终仍沿固定引用返回原始 Fragment。[共用阅读与原始证据召回 ↗](277c8acc89c393a5373ca36d829cc4939bc43481c0b909f82600c4abe65e3ee7.md#repository-and-reader "支持个人知识与仓库知识共用 Evidence Trail，并说明派生正文只负责导航到原始 Fragment。") 这也与日常助理相连：交办、任务应用、真实回执和提醒复用既有 MemoryService 与证据规则，不另建 Agent 或事实来源。[日常交办与证据治理主线 ↗](../../../docs/implementation/daily-follow-up.md#L3 "说明日常助理复用现有模型、MemoryService 和原始材料规则，并界定其与知识流程的关系。")

<a id="progress"></a>
## 当前进展与可验证能力

截至 2026-10-01，知识流程已接入共用合同、八种角色、持久分析、独立复核、仓库全材料适配和知识引导召回；检索又增加固定版中文向量模型、按模型身份隔离的向量索引、混合召回与来源更新后的 extractor／verifier／apply 闭环。全库是否完成仍以实时 coverage 和 verification 记录为准，不能沿用旧统计。[检索、重核验与知识流程最新状态 ↗](../../../docs/implementation/status.md#L5 "支持中文向量检索、来源更新闭环、共用知识角色已经落地，同时限定全库覆盖仍应读取当前报告。")

代码域已有无需模型的 TS/Vue 结构图、关系视图和多层 trail，但跨文件调用仍不解析，名称级调用只是候选，跨 revision 的符号与片段身份也尚未续接。[Code Wiki 实测能力与结构限制 ↗](../../../docs/implementation/status.md#L46 "支持确定性代码图已经实现，并说明跨文件调用和跨版本身份续接仍受限制。") 因而 Code Wiki 的价值主要是把结构、派生解释和固定证据放进同一阅读路径，而不是宣称已具备完整的跨仓语义代码分析。

<a id="verification_and_limits"></a>
## 验证证据与剩余限制

浏览器记录覆盖材料捕获、递归证据、版本不可变、日常跟进、授权配对、桌面与移动布局、百节点渲染及故障呈现；后端是真实 Fastify 与 SQLite，但 Agent 使用确定性 ACP 协议夹具，所以该记录不能替代真实外部 CLI 或模型验收。[浏览器流程与协议夹具边界 ↗](../../../docs/implementation/browser-verification.json#L2 "支持浏览器覆盖范围、真实后端以及确定性 ACP 夹具不能代表真实外部模型验收的判断。")

另一份实现验证记录给出了依赖冻结、全量测试、构建和三套浏览器流程的退出码，并包含一次真实模型的小样本复核校准；它同时明确排除了全量语义正确性、真实飞书 WebSocket、外部观察器和多租户隔离等外推。[实现检查、浏览器验证与剩余限制 ↗](../../../docs/implementation/knowledge-verification.json#L2 "支持依赖、测试、构建和浏览器检查的实际退出结果，并限定 live 校准及外部集成的证据范围。") 因此当前应区分三层证据：确定性测试证明合同与状态机，真实浏览器证明可消费流程，小规模 live check 证明特定配置可连通；任何一层都不能单独代表全库知识质量或全部外部集成已经完成。
