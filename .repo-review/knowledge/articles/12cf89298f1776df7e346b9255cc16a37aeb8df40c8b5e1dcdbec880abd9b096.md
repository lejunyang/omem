# Code Wiki 哈希路由与阅读轨迹深链

该文件用轻量哈希协议承载 Code Wiki 主视图、源码行号和阅读轨迹。解析器提供有限容错并按共享预算截取轨迹；序列化仅保存帧的 kind 与 id，不保存完整展示和加载上下文。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 路由状态与轨迹合同

该模块不依赖完整路由器，而以判别联合表示概览、结构、关系图、模块和文件五类主视图；`WikiRoute` 再把主视图与阅读轨迹合并为统一状态，文件页可附带源码行号。[Wiki 主视图与路由状态 ↗](../../../packages/ui/src/OmHashRoute.ts#L7 "支持五类主视图、文件行号以及主视图与轨迹共同组成路由状态的说明。")

完整轨迹帧包含 kind、稳定 id、标题、滚动位置以及若干数据定位字段；其中循环检测明确以 `kind + id` 识别同一帧。[共享轨迹帧字段 ↗](../../../packages/ui/src/trail.ts#L16 "支持完整轨迹帧包含标题、滚动位置和数据定位字段，并说明 id 被定义为稳定身份。")[轨迹循环身份判断 ↗](../../../packages/ui/src/trail.ts#L44 "直接支持循环检测使用 kind 与 id 的组合，而不是仅凭单个字段。") 哈希协议只编码 kind 与 id，解析后暂以 id 充当标题，因此不能保证完整 `TrailFrame` 往返等价，其他展示和加载信息需要上层恢复。[轨迹帧哈希序列化字段 ↗](../../../packages/ui/src/trail.ts#L32 "支持哈希路径只序列化 kind 和 id，因而无法恢复完整 TrailFrame 的结论。")

<a id="parse-flow"></a>
## 解析流程与实际容错边界

`parseHash` 会移除哈希前缀，从查询部分提取数字行号，并在出现 `/trail/` 后缀时按 kind/id 成对解码轨迹；缺少配对项的尾段不会形成帧，解码失败则保留原字符串。轨迹最终仅保留前 `MAX_TRAIL` 帧，但 kind 只是类型断言，并无运行时枚举校验。[轨迹后缀解析与解码容错 ↗](../../../packages/ui/src/OmHashRoute.ts#L19 "支持行号提取、轨迹成对解析、无效编码容错、未知 kind 风险及解析深度截取的说明。")

主路径根据首段判断视图：模块或文件缺少必要参数、首段无法识别时回退概览；任何首段为 `trail` 的路径都回退关系图，并不限于孤立的 `trail`。解析器不会要求路径恰好耗尽，所以 `module/x/extra`、`file/id/extra` 仍分别解析为模块页和文件页。[主视图选择与回退规则 ↗](../../../packages/ui/src/OmHashRoute.ts#L50 "支持按首段选择视图、缺少必要参数或未知首段回退、trail 首段进入关系图以及多余段未被校验的结论。")

<a id="serialization"></a>
## 序列化、深度预算与限制

`writeHash` 将各主视图写成确定路径，对模块名、文件 id 以及每个轨迹帧的 kind/id 做 URI 编码；文件行号以查询参数保存，轨迹则追加为 `/trail/<kind>/<id>` 成对路径。它在序列化前执行 `.slice(0, MAX_TRAIL)`，所以长度恰为 200 时仍完整保留，只有第 201 帧及以后才会被舍弃。[路由哈希写入实现 ↗](../../../packages/ui/src/OmHashRoute.ts#L67 "支持各视图、行号和轨迹的编码方式，并直接证明仅超过 MAX_TRAIL 的部分会被截去。")

共享模块把 `MAX_TRAIL = 200` 定义为 URL 深链预算，并声明渲染栈本身不受此限制、触及预算时应由调用方显式提示。当前材料只显示解析和写入时的截取，没有显示提示由谁实现；同时 `pushFrame` 实际直接追加帧，并未自行截断。[轨迹 URL 预算与入栈行为 ↗](../../../packages/ui/src/trail.ts#L37 "支持 200 帧上限只约束深链、调用方应显式提示，以及共享 pushFrame 不截断渲染栈的说明。")
