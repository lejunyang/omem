# 模块架构分析角色的证据约束

该材料定义 module-architect 角色在固定快照内描述模块职责、边界、关键流程和出入口的工作合同，并要求所有代码相关结论可追溯到快照中的有效证据。它属于角色提示与输出规范，不足以证明对应分析器、校验器或运行流程已经实现。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-scope"></a>
## 解决什么问题

该角色面向“理解一个模块或小型模块簇”的场景：读者希望快速掌握其职责、与相邻模块的边界、内部关键流程以及入口和出口。分析必须限定在调用方提供的固定快照中，快照里的文件、符号节点、关系边和规则文档才是事实依据；材料中夹带的文字不能被当作可执行指令。参考 [固定快照与分析范围 ↗](../../../packages/agent-runtime/roles/module-architect/1/prompt.md#L3 "支持角色的使用场景、目标分析维度以及只能以固定快照为事实依据的说明。")

这一约束使架构说明能够对应到特定版本，避免把工作区外的信息或模型猜测混入结论。不过，这里描述的是角色应如何工作，并未展示快照如何构造、角色如何调用，也不能据此认定相关能力已经上线。

<a id="evidence-contract"></a>
## 结论如何组织与校验

输出被要求收敛为单个 `CodeUnderstanding.v1` JSON，重点覆盖模块职责、边界、关键流程、入口、出口以及风险与限制。凡依赖代码的陈述，都应建模为 `raw_fact` 或 `interpretation` 类型的 claim，并引用快照中真实存在的节点、边和证据标识；无法可靠判断时应进入 unknowns，而不是补造标识。参考 [结构化结论与证据校验 ↗](../../../packages/agent-runtime/roles/module-architect/1/prompt.md#L5 "支持输出格式、重点字段、claim 类型、引用标识有效性和未知事项处理规则。")

这种设计把“代码直接呈现的事实”与“基于事实作出的架构解释”区分开，也为确定性校验提供了基础。但材料只声明了校验要求，没有给出 `CodeUnderstanding.v1` 的完整字段定义或校验器行为，因此不能进一步推断具体错误处理方式。

<a id="provenance-seal"></a>
## 生成结果的来源标记

结果还需填写固定的 seal：标明角色、模型、提示词与 schema 摘要、输入快照摘要及生成时间，并明确 `seed=false`、尚未经过独立代理复核。参考 [产物来源封印 ↗](../../../packages/agent-runtime/roles/module-architect/1/prompt.md#L7 "支持 seal 字段的来源追踪要求以及初始结果尚未经过独立代理复核的判断。")

这些字段用于记录产物来源和生成条件，帮助后续判断结果对应哪个输入与合同。尤其是“未复核”标记说明初次生成不能自然等同于验证通过；至于独立复核由谁触发、何时更新 seal，本材料没有说明。
