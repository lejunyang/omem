# 来源更新影响范围记录

记录来源 revision 更新波及的记忆及审计状态，但明确不执行重新复核，也不允许调用方把记录影响范围误报为刷新成功。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="blast-radius"></a>
## 解决的问题与执行流程

该模块为来源更新提供可审计的“爆炸半径”记录。调用方必须提供首个 input ref 的 `sourceId` 与新 `revisionId`，旧 revision 可缺省；随后通过 `memory_dependencies` 与当前 head memory revision 的连接，找出依赖该来源的全部记忆。[依赖记忆查询 ↗](../../../apps/server/src/learning/refresh.ts#L33 "支持参数约束及通过依赖表计算受影响记忆集合的说明。") 查询结果会写入 `refresh_records`，保存 workspace、旧/新 revision、受影响数量和 ID 列表；有受影响项时状态为 `needs_review`，空集合则为 `no_effect`。[刷新审计记录写入 ↗](../../../apps/server/src/learning/refresh.ts#L53 "说明 needs_review、no_effect 的选择及 refresh_records 的持久化字段。")

<a id="honest-boundary"></a>
## 边界与管线关系

这里不负责让记忆失效：注释明确说明确定性失效已发生在捕获流程中，关键词检索也只返回 active memory；本函数只补充刷新审计记录。更重要的是，它没有重新运行 verifier，也没有把任何记忆标成已复核，因此返回值始终是 `blocked/not_implemented`，即使影响数量为零也不能解释为“完成了复核”。[未重新复核的明确边界 ↗](../../../apps/server/src/learning/refresh.ts#L25 "支持该函数只记录影响范围且始终返回 blocked/not_implemented 的论断。")

`LearningPipeline.refreshDependents` 直接调用本函数，然后依据返回的数量和 ID 抛出配置类 `JobExecutionError`，确保作业不会伪装成功。[学习管线的失败处理 ↗](../../../apps/server/src/learning/pipeline.ts#L126 "证明调用方记录影响范围后会主动失败，避免报告刷新成功。") 材料没有并发、重复调用或事务边界的实现，也未提供测试文件；因此无法从现有代码确认重复 refresh job 是否会生成多条预期的审计记录。
