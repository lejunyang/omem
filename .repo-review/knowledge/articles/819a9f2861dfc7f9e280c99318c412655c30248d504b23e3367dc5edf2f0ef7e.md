# 来源更新后的记忆重核验记录

冻结来源修订变更所影响的失效记忆，并在后续处理后依据当前依赖和实际应用状态判定已应用、仍需复核或已被更新版本取代。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决的问题与记录方式

来源产生新修订时，已有记忆可能因依赖旧证据而失效。`recordSourceRefresh` 要求输入中至少有一组来源与新修订标识，并以工作区、来源和修订的稳定摘要生成幂等记录键；首次处理时查询该来源下已经标为 stale 且记忆状态为 invalidated 的对象，把受影响 ID 集合冻结到记录中。这样重复投递不会因为部分记忆已修复而缩小最初影响范围。没有受影响对象时记为 `no_effect`，否则进入 `needs_review`。[冻结来源刷新影响集合 ↗](../../../apps/server/src/learning/refresh.ts#L6 "支持刷新记录采用稳定键、首次查询并冻结失效记忆集合以及初始状态的说明。")

<a id="reconciliation"></a>
## 重核验流程与边界

调度成功只代表进入队列，不能视为修复完成。`reconcileSourceRefresh` 针对新修订查找刷新记录，逐一确认受影响记忆是否已恢复 active、依赖是否指向该修订且为 current，同时要求来源 head 与依赖修订一致；全部满足才标为 `applied`。如果来源 head 已继续前进，旧刷新记录标为 `superseded`，否则保留 `needs_review` 并记录 repaired 与 unresolved。[依据当前依赖核对刷新结果 ↗](../../../apps/server/src/learning/refresh.ts#L27 "支持队列成功不等于应用成功，以及 applied、superseded、needs_review 的判定条件。") 当前实现只取输入中第一组同时含 `sourceId` 和 `revisionId` 的引用，因此一次调用并不处理多来源刷新；记录键依赖公共稳定摘要实现。[稳定摘要实现 ↗](../../../apps/server/src/storage/digest.ts#L3 "说明刷新记录键所依赖的摘要会递归规范化对象键并计算 SHA-256。")
