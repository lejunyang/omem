# 来源更新的记忆失效快照与重核验对账

该模块为来源新修订建立稳定的刷新记录，冻结首次发现的失效记忆集合，再根据当前记忆、依赖和来源 head 的数据库状态进行对账。需注意，修复查询未显式限定刷新记录中的来源，因此不能仅凭现有实现断言命中的是指定来源。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-snapshot"></a>
## 失效集合冻结与幂等记录

来源内容更新后，`recordSourceRefresh` 从输入中选取第一个同时具有 `sourceId` 和 `revisionId` 的引用；缺少完整引用时直接报错。它以工作区、来源和新修订生成稳定记录 ID，并优先复用已有记录，使重复投递不会重新缩小已经冻结的影响范围。[刷新引用选择与稳定记录键 ↗](../../../apps/server/src/learning/refresh.ts#L6 "支持首个完整引用的选择、缺失引用报错，以及记录键仅由工作区、来源和新修订生成的说明。")

首次建档时，查询当前 head 依赖该来源、依赖状态为 `stale` 且记忆状态为 `invalidated` 的记忆，去重后把 ID 列表、影响数量及初始状态写入数据库：存在受影响项时为 `needs_review`，否则为 `no_effect`。随后返回记录状态和冻结的记忆列表。[受影响记忆快照与初始状态 ↗](../../../apps/server/src/learning/refresh.ts#L13 "支持首次查询失效记忆、冻结 ID 集合、保存 previousRevisionId，并设置 needs_review 或 no_effect 的说明。")

<a id="reconciliation-flow"></a>
## 对账流程与成功语义

调度成功只表示任务已入队；`reconcileSourceRefresh` 仅选取新修订匹配且 `affected_count>0` 的刷新记录，再逐项检查冻结列表中的记忆。修复存在性查询要求记忆为 `active`、其 head 修订存在 `source_revision_id` 等于目标修订且状态为 `current` 的依赖，并要求该依赖所连来源的 head 等于同一修订。[修复存在性查询 ↗](../../../apps/server/src/learning/refresh.ts#L27 "支持对账记录筛选以及 active、目标修订依赖、current 状态和依赖来源 head 条件；同时显示查询未以刷新记录的 source_id 限定依赖来源。")

这里替代此前“依赖已核验为刷新记录指定来源”的结论：查询没有用 `row.source_id` 约束 `md.source_id`，因此现有材料只能证明存在满足条件的依赖，不能证明它必然属于该刷新记录的来源。刷新记录自身的来源 head 则由另一条查询核对；若不再指向该修订，状态为 `superseded`，否则全量修复为 `applied`，未全量修复仍为 `needs_review`，并保存 `repaired` 与 `unresolved` 明细。[来源 head 与最终状态更新 ↗](../../../apps/server/src/learning/refresh.ts#L37 "支持使用刷新记录的来源核对 head，并据此区分 superseded、applied、needs_review 及保存修复明细。")

<a id="boundaries-and-dependencies"></a>
## 输入边界与摘要依赖

一次调用只处理首个完整引用，其余来源或修订不会分别建档。`previousRevisionId` 仅在插入刷新记录时作为可空字段保存，稳定记录键只包含工作区、来源和新修订；结合对账函数的参数与查询也可见，该字段不参与当前修复判定。[刷新引用选择与稳定记录键 ↗](../../../apps/server/src/learning/refresh.ts#L6 "支持首个完整引用的选择、缺失引用报错，以及记录键仅由工作区、来源和新修订生成的说明。")[受影响记忆快照与初始状态 ↗](../../../apps/server/src/learning/refresh.ts#L13 "支持首次查询失效记忆、冻结 ID 集合、保存 previousRevisionId，并设置 needs_review 或 no_effect 的说明。")[对账范围与使用字段 ↗](../../../apps/server/src/learning/refresh.ts#L29 "支持对账仅处理 affected_count 大于零的记录，并展示后续修复判定只接收 revisionId 和记录明细。") `no_effect` 记录因对账查询要求 `affected_count>0`，不会进入后续状态更新循环。[对账范围与使用字段 ↗](../../../apps/server/src/learning/refresh.ts#L29 "支持对账仅处理 affected_count 大于零的记录，并展示后续修复判定只接收 revisionId 和记录明细。")

记录键依赖存储层的 `stableDigest`：输入会递归规范化，对象属性按键排序并忽略值为 `undefined` 的字段，之后将规范 JSON 计算为 SHA-256 十六进制摘要。因此对象字段顺序不会改变刷新 ID。[稳定摘要规范化实现 ↗](../../../apps/server/src/storage/digest.ts#L3 "说明刷新记录键所依赖的摘要会递归排序对象键、忽略 undefined，并使用 SHA-256。") 当前材料未展示表约束、事务边界、调用方及重试机制，也未说明输入是否允许多个独立来源，这些仍需结合迁移与运行流程确认。
