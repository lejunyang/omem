# Hook 捕获输入的本地磁盘队列

`HookSpool` 为 `CaptureInput` 提供带容量约束的本地 JSON 队列：以生产者和事件标识确定文件身份，以稳定摘要识别重复与冲突，并在回执关键字段匹配后删除记录。本次修订替代“仅在平台不支持目录同步时忽略错误”的旧结论：实现实际会忽略目录同步过程中的任何异常，代码注释只将部分平台不支持目录 fsync 作为预期场景。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="identity-and-enqueue"></a>
## 记录身份与入列语义

队列记录保存生产者、事件标识、载荷摘要、完整捕获内容和创建时间；服务端回执另含 `revisionId`。[队列记录与捕获回执 ↗](../../../apps/server/src/inputs/spool.ts#L20 "支持队列持久化字段以及回执包含 revisionId 的说明。") 入列要求来源中同时存在 `collectorId` 与 `eventId`，否则抛出 `HOOK_EVENT_ID_REQUIRED`；同一身份且摘要相同会复用旧记录，摘要不同则报告事件冲突。[事件校验、重复与冲突处理 ↗](../../../apps/server/src/inputs/spool.ts#L126 "支持队列要求生产者和事件标识，并区分相同载荷重复与不同载荷冲突。") 共享来源合同允许 `eventId` 为 `null`，所以事件标识必填是队列层附加约束。[捕获来源字段合同 ↗](../../../packages/contracts/src/index.ts#L49 "说明共享来源合同要求 collectorId，但允许 eventId 为空，从而界定队列附加约束。") 这些事实能证明磁盘入列与幂等语义，但不能单独确定该类在整体架构中的调用时机。

<a id="path-and-durability"></a>
## 路径、摘要与耐久写入

目标文件路径由生产者与事件标识的稳定摘要生成，而非由载荷摘要直接命名。[队列文件路径构造 ↗](../../../apps/server/src/inputs/spool.ts#L69 "直接证明文件名由 producer 与 eventId 的摘要生成。") 摘要函数递归排序对象键、忽略值为 `undefined` 的属性，再以规范化 JSON 计算 SHA-256，降低键顺序导致伪冲突的风险。[稳定摘要规范化 ↗](../../../apps/server/src/storage/digest.ts#L3 "支持对象键排序、忽略 undefined、规范化 JSON 和 SHA-256 摘要的说明。")

构造时会创建队列目录并将权限收紧为 `0700`。[队列目录权限 ↗](../../../apps/server/src/inputs/spool.ts#L51 "直接支持队列目录创建后设置为 0700 权限。") 记录写入使用同目录排他创建的隐藏临时文件，完成文件同步后重命名，目标权限为 `0600`，最后尝试同步目录。目录同步过程中的任何异常——包括打开目录、执行 fsync 或关闭描述符失败——都会被无条件忽略；代码注释仅将部分平台不支持目录 fsync 描述为预期场景。因此，先前“只忽略平台不支持目录同步错误”的较窄结论已被替代。[原子写入与目录同步异常处理 ↗](../../../apps/server/src/inputs/spool.ts#L80 "支持临时文件写入、文件 fsync、重命名和目录同步流程，并证明目录同步代码的无条件 catch 会忽略该过程中的任何异常。")

<a id="capacity-and-retention"></a>
## 容量与保留期边界

入列前统计可见 JSON 文件的数量和字节数：默认最多 1000 条、50 MB；条数达到上限即拒绝，而字节总量仅在加入新记录后严格超过上限时拒绝。超限路径先写告警，只有告警成功后才抛出 `SpoolCapacityError`；若告警文件的打开、写入或同步失败，底层文件异常会直接传播。[告警文件写入实现 ↗](../../../apps/server/src/inputs/spool.ts#L107 "证明告警写入会执行可能失败的文件操作，且这些操作没有由 warn 捕获。")[容量检查与异常顺序 ↗](../../../apps/server/src/inputs/spool.ts#L139 "支持精确容量条件，并证明超限时先写告警、告警成功后才抛出专用容量异常。")

默认保留期为七天，但过期记录只追加 `retention_exceeded` 告警，随后仍按创建时间排序返回，因此当前 `retentionMs` 是告警阈值，并非自动清理或隔离策略。[过期告警与待处理排序 ↗](../../../apps/server/src/inputs/spool.ts#L174 "证明过期记录仍会返回并参与排序，同时支持损坏 JSON 可能中断读取的边界判断。")

<a id="delivery-and-boundaries"></a>
## 投递、删除与已知限制

`flush` 最多按 `limit` 顺序发送记录。只有回执存在且 producer、eventId、payloadDigest 全部匹配时才删除文件；首次发送异常或回执不匹配会记录失败并终止本轮，可能形成头部阻塞。回执中的 `revisionId` 当前既不参与匹配，也未写入结果。[顺序投递与回执校验 ↗](../../../apps/server/src/inputs/spool.ts#L197 "支持投递上限、回执字段匹配、成功删除、首次失败停止以及 revisionId 未被使用的说明。")

现有材料还不能确认调度、退避、多进程协调与故障恢复策略。`pending()` 会直接解析全部可见 JSON，损坏记录可能阻断读取；原子写入没有展示失败后的临时文件清理。告警写入会传播自身文件错误，而目录同步阶段的全部异常又会被吞掉，两类失败具有不同的可见性。[原子写入与目录同步异常处理 ↗](../../../apps/server/src/inputs/spool.ts#L80 "支持临时文件写入、文件 fsync、重命名和目录同步流程，并证明目录同步代码的无条件 catch 会忽略该过程中的任何异常。")[告警文件写入实现 ↗](../../../apps/server/src/inputs/spool.ts#L107 "证明告警写入会执行可能失败的文件操作，且这些操作没有由 warn 捕获。")[过期告警与待处理排序 ↗](../../../apps/server/src/inputs/spool.ts#L174 "证明过期记录仍会返回并参与排序，同时支持损坏 JSON 可能中断读取的边界判断。")
