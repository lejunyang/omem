# 项目检查结果的安全复用与并发协调

ProjectChecks 为开发流程中的 setup、test、build 等登记命令提供结果缓存、有效性判定和同请求并发合并；它按命令名分别选择仍对应当前源码、命令配置和运行环境的最后结果，并且只复用日志仍存在的成功结果。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决什么问题

`ProjectChecks` 位于项目配置与真实命令执行之间，避免编码代理、宿主检查和评审对未变化的项目反复运行同一条昂贵命令。一个实例代表一套共享执行环境：随机 ID 区分进程内实例，`generation` 区分 setup 前后的依赖状态；重启或环境代次变化后，旧结果不会被误认为可复用。它从项目回调读取最新命令配置，并依赖 `workspace` 提供源码指纹与实际执行能力、依赖摘要模块比较命令配置。参考 [共享执行环境 ↗](../../../apps/server/src/development/checks.ts#L3 "支持类的职责、构造依赖、随机环境身份、代次以及跨模块依赖的说明。")

<a id="run-flow"></a>
## 一次检查如何执行

以 `run("test")` 为例：先确认名称已登记并计算当前源码指纹；没有 `forceReason` 时，查找同名、同源码指纹、同命令摘要、同环境的最后结果，只有退出码为 0、执行前后源码均未变化且日志仍存在才直接返回，并标记 `reused`。否则以名称、配置、源码和环境生成键；同键任务正在运行时共享其 Promise，避免并发重复执行。参考 [历史结果匹配 ↗](../../../apps/server/src/development/checks.ts#L24 "支持按名称、源码、命令摘要和环境查找最后结果，以及成功、源码未变、日志存在等复用条件。") [检查入口与并发合并 ↗](../../../apps/server/src/development/checks.ts#L62 "支持未知命令校验、强制执行分支、历史复用及相同执行键共享在途任务的流程。")

真正执行由 `runCommand` 完成，结果随后追加到共享结果数组并触发 `onResult` 回调，最后无论成功或异常都清除 pending 项。

```mermaid
flowchart LR
  A[run(name)] --> B{可复用的最后结果?}
  B -- 是 --> C[返回 reused]
  B -- 否 --> D{同键正在执行?}
  D -- 是 --> C
  D -- 否 --> E[runCommand]
  E --> F[记录结果并触发回调]
```
参考 [执行、记录与结果回调 ↗](../../../apps/server/src/development/checks.ts#L79 "支持委托 runCommand、推进 setup 环境代次、追加结果、调用 onResult 回调并清理 pending 的流程图。")

<a id="boundaries"></a>
## 失效规则与使用边界

`status()` 不执行命令，只给全部历史结果补充当前的 `reusable` 标记。这个“最后一条”是**按命令名分别计算**的：对每条结果，代码用它自己的 `r.name` 查找同名、同源码指纹、同命令摘要、同环境的最后候选。因此，示例中的 `test` 与 `build` 可以各自有一条结果同时标为可复用；只有同一候选集合内，更晚的记录才会覆盖更早记录。相应地，若同名且上述匹配维度相同的较晚重跑失败，它会成为该命令的最后候选，使更早的成功记录不再可复用。参考 [按命令分别标记可复用性 ↗](../../../apps/server/src/development/checks.ts#L24 "支持 latest 按命令名及其他匹配维度选择最后候选，并支持 status 对每条结果以其自身命令名计算 reusable。")

源码变化、命令配置变化、执行期间改写源码、环境变化或日志文件丢失都会使结果失效。传入 `forceReason` 会跳过历史结果复用，但仍会加入同键的在途任务。`setup` 命令只要返回结果就递增环境代次（代码未以退出码为条件），从而使此前环境中的结果失效；新建实例也会因随机环境 ID 而拒绝沿用旧实例结果。未知命令会立即报错。参考 [环境推进与未知命令 ↗](../../../apps/server/src/development/checks.ts#L62 "支持未知命令报错、forceReason 跳过历史复用、setup 返回后无条件递增代次及结果记录的边界说明。")
