# 仓库评审关系的同步与查询测试

该测试以临时 Git 仓库和隔离 SQLite Store 验证人工关联 seed 的关系同步：明确覆盖独立意图片段、confirmed implements、完整 requirementRefs 生成的 requires、重复同步 ID 幂等、未登记同名文件不误连、无法解析引用的 missing 独立性、seed 删除后的有限 stale 现象，以及 implements、implemented_by、requires 的 HTTP 查询和列表筛选。正常 decided_by、tested_by 的目标正确性尚未被断言。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_and_fixture"></a>
## 测试目标与夹具设计

该文件为关系同步中的覆盖、误连和错误成功状态提供回归保护。每个用例使用独立 `Store`，结束后关闭数据库并删除临时目录；夹具另建真实 Git 仓库，使提交状态、文件内容和持久化关系共同参与同步。[隔离存储与清理 ↗](../../../apps/server/tests/review-relations.test.ts#L15 "支持测试为每个用例创建独立 Store，并在结束后关闭数据库、删除临时目录。")

夹具安排两个共享 G08 需求、但定位到不同函数的 association seed，其中一个 seed 同时引用 G08、G09；还创建未登记的同名函数文件，以及需求、决策和测试材料。这样的布局用于检验同步是否服从明确路径、符号与引用，而不会因共享需求或同名符号合并。[双 seed 与同名诱饵夹具 ↗](../../../apps/server/tests/review-relations.test.ts#L69 "支持夹具包含共享需求、不同符号、多需求引用及未登记同名文件的设计。")

<a id="sync_invariants"></a>
## 已验证的同步不变量

首次同步产生两个彼此独立的意图片段，各自包含关联标识和对应 seed 文本，且不包含需求文档中的共享 G01、G02 表格。测试还确认生成两条源、目标均非空且状态为 `confirmed` 的 `implements` 关系。[独立意图片段与 implements 断言 ↗](../../../apps/server/tests/review-relations.test.ts#L208 "支持两个意图片段互不覆盖、不含共享表格，以及两条 implements 关系端点非空且状态为 confirmed。") 但断言没有逐条比对每条边与具体 seed 意图的对应关系，也没有验证正常 `decided_by` 或 `tested_by` 的目标，因此不能把覆盖范围概括为所有代码、决策和测试关系均已正确连通。

对需求引用，测试确认完整遍历 `requirementRefs`，生成三条从意图片段出发的 `requires` 边；相同仓库重复同步后关系 ID 集合保持不变，未登记的同名文件也不会产生关系。[多需求、幂等与精确路径 ↗](../../../apps/server/tests/review-relations.test.ts#L245 "支持为每个 requirementRef 生成 requires、重复同步复用关系 ID，以及未登记同名文件不产生关系。")

<a id="missing_stale_and_api"></a>
## 缺失、失效与查询方向

当决策或测试引用无法解析时，各 seed 仍产生独立的 `missing` 关系，并以不同 seed identity 避免空端点碰撞。删除第二个 seed 后，测试只证明出现至少一条 `stale` 关系，并找到一条 identity 以 `assoc_` 开头的 stale `implements` 行；它没有保存删除前的具体 identity 来做精确归属比对。[missing 独立性与有限 stale 断言 ↗](../../../apps/server/tests/review-relations.test.ts#L294 "支持无法解析引用保持为不同 missing 行，并界定删除 seed 后 stale 断言只能确认有限事实。")

HTTP 用例确认代码片段可查询向外的 `implements`，意图片段可看到反向派生的 `implemented_by` 和向外的 `requires`；列表接口可按状态、类型筛选，汇总接口报告 seed 数量。[关系查询与汇总接口 ↗](../../../apps/server/tests/review-relations.test.ts#L338 "支持 implements、implemented_by、requires 的查询方向，以及状态和类型筛选与 seed 数量汇总。") Review 应用本身复用隔离 Store，并把职责限定在评审所需的读取、浏览和同步接口。[Review HTTP 应用边界 ↗](../../../apps/server/src/review/app.ts#L6 "说明评审应用复用隔离 Store，并聚焦读取、浏览和同步能力。")

<a id="coverage_limits"></a>
## 覆盖边界与后续验证

现有断言覆盖关系数量、方向、多需求引用、幂等、missing 独立性和有限 stale 行为，但没有证明复杂符号定位、重命名、跨 revision 身份续接或数据库故障策略。夹具中的 G08、G09 测试仅执行恒真断言，不能作为真实助手行为通过的证据。[恒真运行时测试夹具 ↗](../../../apps/server/tests/review-relations.test.ts#L120 "支持夹具中的 G08、G09 用例只做恒真断言，不能证明真实运行时行为。")

API 注入请求只使用本机 Host/Origin，尚未覆盖无效 Host、跨 Origin、有效或无效 token 及静态资源分支，而应用明确区分无 token 时的 loopback、same-origin 限制与设置 token 后的全 API 门禁。[本机与令牌访问边界 ↗](../../../apps/server/src/review/app.ts#L12 "支持应用存在 loopback、same-origin 与 REVIEW_TOKEN 的不同安全分支，并说明当前测试未覆盖这些分支。") 同步模块还声明 Git 失败转为全量扫描、非法文件逐个拒绝，并通过 `failed` 返回无法读取、解码或导入的文件；这些是源码合同，尚非本测试已经验证的故障行为。[同步扫描故障降级 ↗](../../../apps/server/src/review/sync.ts#L7 "支持 Git 失败转为全量扫描，以及非法、非 UTF-8 或过大文件按文件拒绝而不中止整体同步。")[逐文件失败结果合同 ↗](../../../apps/server/src/review/sync.ts#L60 "支持同步结果通过 failed 单独记录无法读取、解码或导入的文件，并声明其余同步不受影响。")
