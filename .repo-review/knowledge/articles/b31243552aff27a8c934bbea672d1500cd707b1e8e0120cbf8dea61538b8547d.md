# 仓库评审关系的同步与查询测试

该测试以临时 Git 仓库和隔离 SQLite Store 验证人工 association seed 如何形成代码、意图、需求、决策与测试之间的关系，并覆盖多引用、幂等、缺失目标、删除失效以及 HTTP 双向查询。它重点防止同名文件误连、共享需求覆盖不同 seed、空端点关系碰撞，以及把整张需求总表错误展示为意图。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-fixture"></a>
## 问题与测试夹具

测试为每个用例建立临时 Git 仓库和独立 Store，并在结束后关闭数据库、递归清理目录；仓库夹具包含目标源码、同名诱饵文件、需求/决策/测试文档及人工 associations，从而在接近真实同步输入的环境中检验关系构建。[临时仓库与清理夹具 ↗](../../../apps/server/tests/review-relations.test.ts#L15 "支持测试使用隔离 Store、临时 Git 仓库并在用例后清理资源的说明。") 两条默认 seed 刻意共享 G08，但定位到不同符号，第二条还同时引用 G08、G09，用于发现按需求键覆盖 seed 或只处理首个引用的问题。[共享需求的默认关系种子 ↗](../../../apps/server/tests/review-relations.test.ts#L141 "支持两条 seed 共享 G08、定位不同符号且包含多需求引用的夹具设计。")

测试通过 `runReviewSync` 驱动同步，通过 Store 直接读取关系和虚拟意图索引；HTTP 场景再用 `buildReviewApp` 注入请求。由导入关系可确认该文件同时连接通用存储、评审同步和评审 HTTP 层，但材料没有展示被调函数完整实现，不能据此断言其内部调用链。[测试连接的服务模块 ↗](../../../apps/server/tests/review-relations.test.ts#L10 "说明测试直接使用 Store、评审同步入口与评审 HTTP 应用，但不能单凭导入推断更深调用链。")

<a id="sync-invariants"></a>
## 同步关系的核心断言

首组断言要求“一条 seed 对应一个短意图片段”：两个 seed 生成两个不同 fragment，文本只包含各自意图与关联标识，不得混入 G01–G20 总表；代码片段以 `implements` 指向该意图，端点非空且状态为 confirmed。[每种子意图与 implements 断言 ↗](../../../apps/server/tests/review-relations.test.ts#L207 "支持独立短意图片段、避免共享总表污染以及 confirmed implements 端点的核心断言。") `requires` 则从意图片段出发，并为每个 requirementRef 独立建边，因此样例总数应为三条。[多需求引用建边断言 ↗](../../../apps/server/tests/review-relations.test.ts#L245 "支持每个 requirementRef 分别生成 requires 边，且关系源是意图片段而非代码片段。")

重复同步后关系 ID 必须完全复用，说明测试把幂等性定义为稳定身份而非仅数量相同；未列入 seed 的同名文件不得产生关系，强调路径与显式 association 才是定位依据。[幂等与同名文件隔离 ↗](../../../apps/server/tests/review-relations.test.ts#L263 "支持重复同步复用关系 ID，并排除未列入 association 的同名文件。") 对无法解析的决策或测试引用，每个 seed 的 missing 边仍须独立存在，避免空端点导致覆盖；从列表删除 seed 后，其旧边应转为 stale，而不是继续显示为有效。[缺失边与删除 seed 失效 ↗](../../../apps/server/tests/review-relations.test.ts#L294 "支持 missing 边按 seed 独立保留，以及移除 seed 后旧关系转为 stale。")

<a id="api-api-limits"></a>
## 查询行为、模块关系与未覆盖边界

API 测试确认从代码 fragment 查询可得到外向 `implements`，从意图 fragment 查询可同时看到反向 `implemented_by` 与外向 `requires`；用户看到的关联对象仍是短意图，而非共享需求表。另一个用例验证关系列表可按 status/type 过滤，association 摘要返回 seed 数量。[关系双向查询与列表过滤 ↗](../../../apps/server/tests/review-relations.test.ts#L338 "支持 fragment 关系的正反向类型映射、状态确认、筛选和 association 数量摘要。") 这表明评审应用复用隔离 Store，并公开浏览、同步所需的有限 HTTP 面；应用注释还限定其默认只绑定本机，并不承载业务 worker 或业务状态。[评审应用职责与安全边界 ↗](../../../apps/server/src/review/app.ts#L6 "解释 HTTP 测试所连接应用的隔离 Store、有限路由、本机绑定和非业务运行时定位。")

这些是进程内 fixture 测试：它们未断言 `decided_by`、`researched_by`、`tested_by` 的成功目标内容，也未覆盖非法筛选参数、鉴权失败、并发同步、事务中断、Git 命令失败、非 UTF-8/超大文件或真实网络监听。同步材料声明扫描失败会降级、逐文件拒绝不安全输入，但本文件没有对这些边界作行为验证。[同步扫描声明的容错边界 ↗](../../../apps/server/src/review/sync.ts#L7 "列出同步模块声称处理的 Git 降级、安全路径、编码和文件大小边界，用于指出本测试未覆盖之处。")

<a id="assertion-scope"></a>
## 测试结论的证据边界

测试中的需求和测试文档是人为构造的最小文本，甚至下游测试内容仅为恒真断言；因此这里证明的是 locator、关系状态、身份稳定性和 API 映射规则，而不是 G08 多轮回指或 G09 恢复功能本身正确。[最小下游测试夹具 ↗](../../../apps/server/tests/review-relations.test.ts#L100 "支持夹具中的所谓 G08/G09 测试仅作文本定位且断言恒真的判断，限制对业务正确性的外推。") 同理，直接查询 SQLite 表会精确验证持久化结果，却可能绕过更上层 DTO 展示约束；当前 HTTP 断言只检查关系类型、状态和关联文本，没有验证 label、actionable、reason、排序、分页或内部 ID 是否泄露。[HTTP 响应断言范围 ↗](../../../apps/server/tests/review-relations.test.ts#L349 "支持现有 API 用例仅检查关系类型、状态、文本和数量，未覆盖完整展示合同。")
