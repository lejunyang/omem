# repo-review 服务启动与生命周期入口

按固定顺序完成仓库材料同步、知识恢复、代码投影和可选模型配置，然后在回环地址启动评审 API，并将正常关闭交给应用钩子收尾。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="startup"></a>
## 启动顺序

入口从 `REVIEW_REPO_ROOT` 或当前目录确定仓库根并创建独立评审 Store，随后先执行增量材料同步，再恢复已发布知识，最后将代码图投影到当前固定材料。服务在这些步骤完成后才进入应用构建与监听，因此初次请求看到的是已初始化的来源、知识和代码图；启动阶段任一步抛错都会进入失败分支关闭 Store。[评审服务初始化序列 ↗](../../../apps/server/src/review/main.ts#L15 "支持材料同步、知识恢复和代码投影先于应用监听的启动流程。")

<a id="configuration"></a>
## 显式模型与检索配置

代码理解模型只从评审专用配置加载，默认允许为空，并随其他依赖传给 `buildReviewApp`。检索配置优先采用环境变量指定路径；否则仅在仓库内 `config/retrieval.json` 存在时读取，缺失时交给应用工厂使用默认值。API 与 Web 端口可由环境变量覆盖，但监听地址固定为 `127.0.0.1`，与本地评审边界一致。[模型、检索与端口配置 ↗](../../../apps/server/src/review/main.ts#L29 "说明评审专用模型配置、检索配置选择、端口参数和应用构建依赖。")

<a id="lifecycle"></a>
## 监听与关闭边界

应用构建完成后才调用 Fastify `listen`。进程收到 SIGINT 或 SIGTERM 时调用 `app.close()`，成功后以状态 0 退出；入口代码本身没有展示关闭超时、拒绝处理或重复信号策略。启动异常路径则直接关闭 Store 并重新抛出错误。[监听、信号与启动失败清理 ↗](../../../apps/server/src/review/main.ts#L46 "支持回环监听、信号触发 app.close、成功退出及启动失败关闭 Store 的入口行为。")

正常的 `app.close()` 还会触发应用注册的关闭钩子，由该钩子等待检索服务停止并关闭 Store。此前仅以入口信号代码支持这一内部行为的引用不充分，现已由应用关闭钩子的固定材料补足。[应用资源关闭钩子 ↗](../../../apps/server/src/review/app.ts#L621 "补充证明 app.close 会通过应用钩子关闭检索服务和 Store。")
