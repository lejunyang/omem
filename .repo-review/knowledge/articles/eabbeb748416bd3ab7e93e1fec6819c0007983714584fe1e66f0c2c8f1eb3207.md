# repo-review 服务启动编排

作为隔离评审服务入口，依次同步仓库、恢复知识、建立代码投影、装配可选模型和 HTTP 应用，并仅监听本机回环地址。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="startup"></a>
## 启动顺序与隔离边界

入口从环境变量取得仓库根目录和 API 端口，主机固定为 `127.0.0.1`；注释明确该进程不会装配个人工作区服务。[评审入口与网络配置 ↗](../../../apps/server/src/review/main.ts#L5 "支持服务隔离声明、仓库根目录、端口和回环监听地址。") 创建评审 Store 后，流程先运行评审增量同步，再恢复评审知识，之后执行代码投影并汇总输出知识恢复状态。这个顺序意味着知识材料建立在同步后的仓库输入上，而代码结构投影在知识恢复之后更新。[同步和知识恢复序列 ↗](../../../apps/server/src/review/main.ts#L17 "支持启动阶段各步骤的实际执行先后关系。")

<a id="model-server"></a>
## 模型与服务装配

代码读取评审代码模型配置，同时构建模型端口用于记录实际 transport；随后把 Store、仓库根目录、API/Web 端口和配置传给 `buildReviewApp`，再启动 Fastify 服务。[模型与应用构建 ↗](../../../apps/server/src/review/main.ts#L26 "支持可选模型配置、transport 日志及应用参数装配的说明。") 从本材料只能确认配置对象传入应用，无法确认 `buildReviewCodeModel` 创建的端口是否由应用复用，因为其返回值仅在本文件中用于日志。

<a id="shutdown"></a>
## 关闭与失败处理

服务监听成功后注册 `SIGINT`、`SIGTERM`，收到信号时先关闭应用再退出。启动过程若抛错则关闭 Store 并继续抛出错误。[信号与异常清理 ↗](../../../apps/server/src/review/main.ts#L42 "直接说明信号关闭应用和启动异常关闭 Store 的行为。") 材料没有展示 `buildReviewApp` 内部是否负责在正常关停时关闭 Store，也没有展示监听已建立后非信号异常的统一资源回收策略。
