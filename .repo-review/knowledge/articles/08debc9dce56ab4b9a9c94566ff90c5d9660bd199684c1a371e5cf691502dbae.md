# 知识文章的状态、来源与修改入口

面向排查知识更新行为的开发者：先区分发布用途、页面生成、逐节适用性与后台维护四套状态，再拆开项目归属、阅读目录、调查范围和固定依据。说明动态文章如何选择维护或重组、如何阻止过期结果覆盖新范围，并按知识页面、私人助手、后台记忆和导入资产四条链路给出定位入口。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="status-axes"></a>
## 先分清四套状态

同一篇文章可以**仍在目录、旧正文可读、某一节待核对，同时后台更新已经排队**。这不是冲突，而是四套状态在回答不同问题。

| 查询对象 | 可能值 | 回答的问题 |
| --- | --- | --- |
| 发布用途 `role` | `article` / `reference` / `note` | 内容面向连续阅读、参考查询，还是内部分析？显式 `publication.role` 优先；旧资产才按保存的 `reading.kind` 回退。参考 [发布用途优先级与旧资产回退 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L10 "实现显式 publication.role 优先，并按保存的 reading.kind 为旧资产回退用途。") |
| 页面生成 `state` | `planned` / `writing` / `published` / `failed` / `retired` | 正文生产走到哪一步，以及页面是否退出目录。 |
| 章节适用 `SectionStatus` | `current` / `needs-review` / `unavailable` | 这一节的固定依据现在是否仍可采用。 |
| 维护任务 `maintenance.state` | `idle` / `queued` / `writing` / `published` / `failed` | 最近一次手动整理或自动维护请求走到哪一步。 |

这些字段的合同彼此独立：阅读计划定义页面用途，产物另存 publication、selection、dependencies 与 investigation；维护状态则是另一套持久任务视图。参考 [用途、维护状态与产物字段 ↗](../../../packages/contracts/src/knowledge.ts#L64 "定义阅读计划用途、维护状态以及 publication、selection、dependencies、investigation 的不同职责。") [维护任务状态映射 ↗](../../../apps/server/src/knowledge/page-worker.ts#L116 "说明持久任务如何映射成 idle、queued、writing、published 或 failed。")

已有正文的计划变化会写入 invalidation 并刷新适用性，不会先删掉 head。目录查询排除 note 与 retired，published 集合再排除 planned；所以首次生成失败可能只有计划而没有正文，而已有页面重写失败时旧正文仍可能可读。整篇 `current` 只是逐节结果的聚合：所有章节都 current 时 head 才 current。参考 [页面计划与发布过滤 ↗](../../../apps/server/src/knowledge/repository.ts#L137 "说明计划变化失效、页面 state 以及目录和 published 的过滤条件。") [整篇 current 聚合 ↗](../../../apps/server/src/knowledge/repository.ts#L297 "证明 head 的 current 由所有章节状态聚合，而页面身份和计划保持稳定。")

逐节判断从该节正文中的 citation、`reviewSources` 和递归文章依赖出发。固定来源缺失会变成 unavailable；来源仍可读但引用上下文、背景前提或所引文章解释变化，则进入 needs-review。一个章节变化不会自动抹掉其他章节。参考 [逐节适用性计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L112 "说明 citation、reviewSources、材料版本和递归文章依赖如何决定 current、needs-review 与 unavailable。")

当前 Markdown 还有一个重要边界：若文档只有一个一级标题，而引用范围横跨导言和多个二级章节，系统把它拆成“导言 + 直接子章节”，只比较与引用范围相交的完整块；嵌套条件仍随父章节比较。所选块必须在新版中唯一、连续、顺序不变且全文相同。引用范围之后的报告变化不会连带失效，但在跨度内新增或重排章节会要求复核；固定引用仍指旧版本，不会被语义迁移到新版。参考 [单一级标题引用上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "说明跨导言和子章节的引用只比较相交完整块、保留嵌套条件，并要求唯一连续且内容不变。")

**教学示例：**测试中的活动文档引用导言、预算和地点。只改后面的“筹备记录”时预算节仍可检索；改预算下的费用条件，或在引用跨度中插入参加条件时，预算节进入 needs-review。它说明比较规则，不是现实活动事实。参考 [跨章节引用适用性测试 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L137 "用后置报告、嵌套条件和跨度内新增章节验证新的适用性边界。")

排障时不要只看一个“已发布”：页面 state 说明生产结果，maintenance state 说明队列结果，section status 才说明当前依据是否仍适用。

<a id="scope-classification"></a>
## 拆开归属、目录、选材与固定依据

项目能力把几种“关联”放到了同一界面附近，但它们仍不能互相替代。

| 关系 | 保存位置 | 决定什么 |
| --- | --- | --- |
| 项目/主题材料归属 | `material_contexts` 与 `material_context_sources`，按稳定 `source_id` 多对多关联 | 哪些原件属于一个持续范围。归属是显式输入，不从文件名、会话 ID 或正文推断。 |
| 文章用途与阅读目录 | `publication.role`、`category`、`topicPath` | 内容如何发布、读者从哪个主题路径找到它；不是项目成员或权限。 |
| 页面调查范围 | 计划中的 `materialKeys` 与 `contextIds` | 固定材料和 context 当前成员的并集；两者都省略时才使用全部可用原件。`entryPaths` 只是调查起点。 |
| 固定依据与调查轨迹 | `citations`、`reviewSources`、dependencies、investigation | 正文依据哪个固定版本，以及本轮还读过哪些材料；不会随目录或成员关系静默改指新版。 |

MaterialContexts 会验证 context 与 source；`setForSource` 替换一个 source 的整组归属。捕获时若传入 `contextIds`，系统在创建或复用稳定 source 的同一事务里写 membership；没有再次传入时不会主动清掉原归属。参考 [显式项目与主题归属 ↗](../../../apps/server/src/contexts/repository.ts#L5 "说明 context 与稳定 source 的显式多对多关联、校验、整体替换和并集解析。") [捕获事务中的归属写入 ↗](../../../apps/server/src/store.ts#L108 "说明捕获先验证 context，并在复用 receipt 或稳定 source 时按显式输入更新 membership。")

页面计划的范围合同把 `materialKeys` 定义为固定调查范围，把 `contextIds` 定义为会跟随未来成员变化的项目/主题范围。解析时两者取并集，并使用这些 source 的当前 revision。文章产物另存直接依赖、动态 selection 快照和实际调查轨迹，三者用途不同。参考 [固定材料与动态 context 合同 ↗](../../../packages/contracts/src/knowledge.ts#L64 "定义 materialKeys、contextIds 和 entryPaths 的调查范围语义。") [页面计划材料解析 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "说明固定材料 key 与 context 当前 source 成员取并集。") [固定依赖、选择与调查轨迹 ↗](../../../packages/contracts/src/knowledge.ts#L115 "定义 dependencies、selection、publication 和 investigation 的职责。")

原生调查又增加了一层**固定工作区快照**。只有本轮已经获准的 personal 原件涉及的 context 与 membership 会被复制；项目名称和说明不会仅因一个共享片段暴露给非个人调查。工作区的 catalog 为每份材料附 `groupIds`，并生成只含已获准成员的 groups 目录。参考 [项目目录的固定研究快照 ↗](../../../apps/server/src/knowledge/research-snapshot.ts#L90 "说明只复制本轮获准 personal 原件涉及的 context 和 membership。") [工作区 groups 与材料目录 ↗](../../../apps/server/src/knowledge/agent-research.ts#L183 "说明 catalog 的 groupIds、获准 groups 和 groups.json 如何从固定快照形成。")

共享选择器规定：多个 group 取成员并集；同时给材料 keys 时再取交集；显式空数组选择空集；未知 group 报错而不是静默放宽。参考 [groupIds 筛选语义 ↗](../../../apps/server/src/knowledge/agent-research.ts#L349 "说明多个 group 取并集、与 keys 取交集、空数组选择空集以及未知 ID 报错。")

`list_materials`、`search_materials` 与 `search_contexts` 的处理器都接收 `groupIds` 并调用该选择器；`search_knowledge`、`search_memories` 和代码导航也把选择结果用于可见性或候选过滤。group 只缩小本次读取集合，不授予写权限，也不证明其中哪条约定仍有效。参考 [材料列表接入 group 选择器 ↗](../../../apps/server/src/knowledge/agent-research.ts#L471 "说明 list_materials 接收 groupIds，并以共享 selection 过滤目录候选。") [材料搜索接入 group 选择器 ↗](../../../apps/server/src/knowledge/agent-research.ts#L582 "说明 search_materials 接收 keys 与 groupIds，并在检索前解析共享选择范围。") [上下文搜索接入 group 选择器 ↗](../../../apps/server/src/knowledge/agent-research.ts#L682 "说明 search_contexts 为每个问题解析 keys/groupIds 范围，并用它过滤可见 fragment。") [知识搜索接入 group 选择器 ↗](../../../apps/server/src/knowledge/agent-research.ts#L765 "说明 search_knowledge 接收 groupIds，并把选择结果用于知识检索可见性。") [记忆搜索接入 group 选择器 ↗](../../../apps/server/src/knowledge/agent-research.ts#L877 "说明 search_memories 接收 groupIds，并把选择结果用于记忆检索可见性。") [代码导航接入 group 选择器 ↗](../../../apps/server/src/knowledge/agent-research.ts#L917 "说明 code_navigation 将 key 与 groupIds 一同解析，并过滤代码材料候选。")

**教学示例：**合成测试创建两个同名“周末活动”，用杭州/上海说明区分。杭州 project 与“出行”topic 的并集只返回杭州两份已关联材料；同名未关联材料被排除。快照建立后再改归属或新增材料，也不会改变正在运行的调查。这个例子验证快照与筛选语义，不保证模型能自动识别任意同名项目。参考 [同名项目隔离与快照测试 ↗](../../../apps/server/tests/project-research.test.ts#L12 "用杭州和上海同名项目、topic 并集、未关联材料和运行中归属变化验证筛选边界。")

因此可记成一句话：**context 是显式材料归属，topicPath 是阅读目录，groupIds 是固定调查快照中的过滤器，dependency 是固定证据和更新关系。**

<a id="dynamic-lifecycle"></a>
## 动态文章从选材到发布

跟踪项目或主题的文章，可以沿下面六步定位。

1. 用户把稳定 source 明确关联到 project/topic；source 换版仍沿用 membership。
2. 页面计划保存 `contextIds`、额外 `materialKeys`、阅读目标和可选 topicPath。每次写作前重新解析“固定 key ∪ context 当前成员”。
3. 手动请求或 worker 入队。`scopeDigest` 包含完整 plan 与解析出的材料 key、digest；新增、移出、换版或计划变化都会改变它。观察循环只比较并排队；同页已有活动任务时推进目标 digest，不另开并行任务。参考 [动态范围观察与任务合并 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "说明 scopeDigest 覆盖 plan 和当前材料版本，观察循环独立排队并合并活动任务。")
4. 维护上下文用旧 investigation、材料 dependency、递归文章 dependency 判断旧稿能否在新范围内复用，再提供 changedFields、materialChanges、hunks、newlySelected 和逐节状态。hunks 只是补读起点，不是语义结论或引用迁移。参考 [旧稿复用与维护变化输入 ↗](../../../apps/server/src/knowledge/maintenance.ts#L9 "说明旧稿不得扩大新范围，以及 changedFields、hunks、newlySelected 和逐节状态如何形成。")
5. 研究完成后可给出 `composition.mode`：`maintain` 表示旧阅读路线仍清楚，局部维护；`rewrite` 表示旧组织妨碍当前目的，需要重新组织。这是写作路线，不是事实结论或质量分数。参考 [维护或重组的 composition 合同 ↗](../../../packages/contracts/src/knowledge.ts#L82 "定义 maintain/rewrite 是调查后的写作路线而非事实结论。")
6. 写作、独立复核和发布都使用当前 offers。新产物记录固定 dependencies、实际 investigation；动态 context 页面还记录实际成员的 selection 快照。参考 [发布产物形成 ↗](../../../apps/server/src/knowledge/pipeline.ts#L192 "说明 citations/reviewSources 形成 dependencies、实际读取形成 investigation，动态计划形成 selection。")

`maintain` 时，存在可复用旧稿就交给 refresher 保留有效解释；`rewrite` 时，researcher 仍可用旧稿判断问题，但 writer 与 verifier 不再收到旧 sections，而是沿当前原件和 outline 重组。两条分支都保持同一 document key 与历史 revision，并都经过独立 verifier。参考 [composition 写作分支 ↗](../../../apps/server/src/knowledge/pipeline.ts#L165 "说明 rewrite 移除旧稿结构、maintain 继续局部维护，并让两者都经过独立复核。") [计划写作与研究结果接续 ↗](../../../apps/server/src/knowledge/pipeline.ts#L285 "说明写作前重新解析材料、形成维护上下文，并将 composition 交给写作和复核。")

替换 head 前还有三类竞态检查：保存的计划必须仍等于任务开始时的计划；动态范围当前 key 集合必须仍等于 selection；正文 dependencies 的材料 digest 或文章 revision 必须仍是当前值。任一失败都拒绝旧结果覆盖新范围，保留旧文和最新计划。参考 [发布前竞态检查 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "说明计划、动态成员集合和 dependency 版本变化都会在替换 head 前拒绝旧结果。")

这里要区分两个快照。**selection 快照**防止旧项目成员集合覆盖新范围；**dependency 快照**防止正文直接依据或背景前提在生成途中换版后仍发布。worker 的 scopeDigest 还覆盖全部选材，用来触发下一轮维护；不能据此推断所有 investigation 材料变化都会在同一个发布检查里被当作 dependency。

当前边界是：系统不会从内容自动判断项目归属。动态 context 会吸收后来被明确关联的 source，但它不是安全隔离边界，也不等于一套完整项目助理。

<a id="evidence-visibility"></a>
## 按证据、搜索与项目链路定位

先把发布资产中的四类来源关系分开：citation 是正文内联固定依据；`reviewSources` 是会改变本节解释的背景前提；investigation 是实际读取轨迹，不断言每份材料都直接支持正文；维护上下文只帮助下一轮定位变化。产物字段与逐节适用性分别定义了这些职责。参考 [固定依赖、选择与调查轨迹 ↗](../../../packages/contracts/src/knowledge.ts#L115 "定义 dependencies、selection、publication 和 investigation 的职责。") [逐节适用性计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L112 "说明 citation、reviewSources、材料版本和递归文章依赖如何决定 current、needs-review 与 unavailable。")

知识检索要求整篇 investigation 和递归 dependencies 都仍在可见范围，并只投影 current 章节。因此旧文可读、某节待核对、另一节仍可搜可以同时成立；检索单元会携带整篇 needs-review 标记与固定引用。参考 [知识检索准入 ↗](../../../apps/server/src/retrieval/units.ts#L587 "说明 investigation 与递归依赖必须可见，且至少一个 current 章节才建立知识投影。") [按 current 章节投影 ↗](../../../apps/server/src/retrieval/units.ts#L670 "说明检索单元只来自 supported sections，并携带整篇 reviewState、固定引用和可见性。")

| 现象 | 首先检查 |
| --- | --- |
| 页面不在目录 | `knowledge/repository.ts` 的 role、pages、published：是否为 note、planned 或 retired，是否已有 head。 |
| 页面可读但某节提示待核对 | `knowledge/lifecycle.ts` 的 `knowledgeStatus`、固定 dependency 和 invalidation。 |
| queued / writing / failed 与旧文同时出现 | `page-worker.ts` 的维护任务状态与页面生成 state 分开看。 |
| 引用打开旧内容 | 这是固定引用的预期行为；另看 current/actionable 判断周边解释是否仍适用。 |
| 正文可读但某节搜不到 | 检查整篇可见性门槛和该节是否 current。 |
| 网页知识搜索结果异常 | `/knowledge/search` 只接受文本、topicPath 前缀和 purpose，并只回退遍历 current 节；当前没有 project/group 参数。参考 [网页知识搜索入口 ↗](../../../apps/server/src/knowledge/api.ts#L142 "说明搜索参数、topicPath 前缀过滤与只遍历 current 章节的词法回退。") |
| 原生调查项目结果异常 | 检查本轮 groups 快照、groupIds 的并集/交集和调用者获准原件；group 不是权限。 |

私人助手是另一条链路。模型可返回 `project_selection`，但只能选择本轮提供的正式 project ID；无关、跨项目比较或仍有歧义时应为 null。它是 reading scope，不是权限或事实更新。研究环境先按基础可见性建立材料集合，再校验选择与引用的当前/同源历史版本。参考 [会话项目选择合同 ↗](../../../packages/contracts/src/assistant.ts#L11 "定义 project_selection 必须来自正式项目，null 用于无关、比较或歧义，并强调它不是权限或事实更新。") [助手研究环境与选择校验 ↗](../../../apps/server/src/assistant/research.ts#L49 "说明按基础可见性建立研究材料，并校验真实项目 ID 与同源历史引用。")

只有 private conversation 获得 personal projects。成功且非降级的回答会把选择与 completed turn 放在同一事务保存；失败或取消不改变项目。保存的 project 作用于**下一轮初始召回**：在排序和截断前限制到该项目的 source members，上轮工作上下文也重新过同一范围；原生工具仍能搜索其他已授权材料以识别换项目或补背景。参考 [私人项目上下文供给 ↗](../../../apps/server/src/assistant/runtime.ts#L617 "说明只有私人会话获得 personal projects，并从已存 conversation.projectId 找 workingProject。") [项目选择与回答原子保存 ↗](../../../apps/server/src/assistant/runtime.ts#L918 "说明完成 turn 与非降级项目选择在同一事务保存；取消或失败走事务后的异常分支。") [下一轮初始召回范围 ↗](../../../apps/server/src/assistant/runtime.ts#L974 "说明保存的项目在排序前限制初始召回，但仍叠加基础 visibility，原生工具可调查其他授权背景。")

新事项使用本轮 project，并把当前 owner 指令保存为同项目原件；更新已有事项时，变更指令按事项自己的 project 保存，不随当前聊天主题迁移。参考 [事项变更沿用事项项目 ↗](../../../apps/server/src/assistant/runtime.ts#L1141 "说明更新已有事项时按任务自己的 project 保存变更指令。") [新事项保存当前项目 ↗](../../../apps/server/src/assistant/runtime.ts#L1387 "说明当前 owner 指令按本轮 project 捕获，并将 project_id 写入事项 proposal scope。")

**教学示例：**测试让私人会话在重启后继续 Web 项目，初始召回排除同名移动端材料；聊天后来切到移动端，先前创建的 Web 事项仍保留 Web project；无关的“买牛奶”会清空会话项目并创建无项目事项。这验证持久化与范围边界，不保证所有自然语言歧义都能自动解决。参考 [会话与事项项目持久化测试 ↗](../../../apps/server/tests/assistant-runtime.test.ts#L75 "用重启、同名项目、聊天切换和无关事项验证初始召回与事项归属边界。")

后台记忆又是第三条链路。只有所有输入 source 共同属于唯一一个正式 project 时，LearningPipeline 才把它当可信 project；topic、名称、路径和 conversation carrier 都不能替代。旧记忆初始召回按这个 scope 过滤，模型输出必须沿用 supplied workspace/project，更新不能把既有 memory 移到另一项目。参考 [后台记忆的可信项目范围 ↗](../../../apps/server/src/learning/pipeline.ts#L295 "说明仅唯一共同正式项目成为 trusted project，并把各输入片段的 provenance 保留给模型。")

抽取和复核阶段都会记录输入 source 的 membership stamp；归属在调查途中或阶段之间变化时以 `STALE_JOB_INPUT` 拒绝旧结果。创建 claim 的等价/冲突候选也硬性限制在同 workspace、同 project。参考 [记忆召回、范围校验与 membership stamp ↗](../../../apps/server/src/learning/pipeline.ts#L428 "说明旧记忆按 trusted project 召回，模型输出不能跨项目，并在阶段前后校验归属版本。") [同项目记忆候选匹配 ↗](../../../apps/server/src/memory/service.ts#L477 "说明 claim 的等价或冲突候选硬性限制在同 workspace 和同 project。")

跨来源更新并非一律冲突。只有 verifier 判定 `amends`、语义 supported、目标版本匹配且 workspace/project 相同，才是 reviewed amendment；否则新增 source 的更新仍形成 cross-source conflict，再按是否影响活跃知识或当前任务进入 awaiting_decision 或 defer_until_use。未经验证的他人职责不能直接成为 owner task。参考 [复核后的跨来源修订 ↗](../../../apps/server/src/memory/service.ts#L353 "说明 reviewed amendment 需要 amends、supported、正确目标版本与相同 workspace/project。") [跨来源冲突处置 ↗](../../../apps/server/src/memory/service.ts#L780 "说明未满足修订条件的跨来源变化何时询问、内部延后或仅保留为来源。")

**教学示例：**合成测试中 Web 的后续 source 把 retry limit 从 3 修订为 5，Mobile 的 8 保持独立；抽取后把“9”的 source 改到 Mobile，会因 membership stamp 变化而不应用。它验证项目隔离、明确修订与过期任务拒绝，不是复杂时间或实体消歧保证。参考 [项目记忆修订与过期归属测试 ↗](../../../apps/server/tests/learning-projects.test.ts#L10 "用 Web/Mobile 隔离、后续来源修订和途中归属变化验证记忆范围与拒绝机制。")

综合来看，project 身份贯穿动态文章、私人助手、事项和后台记忆，但没有合并成“项目权限”。排障时先问观察的是 article plan、research group filter、conversation.project_id、task.project_id 还是 memory scope，再沿对应入口查。

<a id="asset-removal"></a>
## 导入资产移除后，目录退出但历史保留

导入目录中的文章资产消失时，默认动作是**撤销该导入方的发布归属**，不是删除知识 revision 或固定证据历史。

恢复流程以导入目录绝对路径作为 owner，先解析全部 JSON。只要存在无法解析的文件，本轮就不执行 reconcile，避免把临时损坏误判为删除；其他有效资产仍可恢复。只有实际可应用的 revision 才会推进当前 head。参考 [导入资产恢复 ↗](../../../apps/server/src/knowledge/artifacts.ts#L32 "说明解析失败保护、依赖顺序恢复以及只在目录完全可解析时 reconcile。")

reconcile 时，缺失 key 先移除这个 owner 的 membership。只有同时满足“没有其他 owner”与“当前 head 仍等于该 membership 记录的 imported revision”，页面才进入 retired；另一个 owner 仍持有它，或用户后来发布了个人 revision，都不会退休当前正文。相同资产重新成为 head 时可从 retired 恢复为 published。参考 [导入归属与退休条件 ↗](../../../apps/server/src/knowledge/repository.ts#L163 "说明仅撤销当前 owner membership，且只有无其他 owner、head 未被替换时才 retired。")

retired 让页面退出目录、published 集合和检索投影，但不会物理删除 `knowledge_revisions`。集成测试确认导入资产移除后，旧文章 revision 和固定旧原件仍可读取，个人捕获仍存在；另一项测试确认个人发布的新 head 不会因导入目录移除而退休。参考 [资产移除后的固定历史 ↗](../../../apps/server/tests/development-knowledge.test.ts#L11 "测试确认退出 published 后旧文章 revision、固定旧原件与个人捕获仍可读取。") [个人 head 不随导入移除退休 ↗](../../../apps/server/tests/knowledge-repository.test.ts#L113 "测试确认个人发布的新 head 在导入资产移除后继续发布，旧 imported revision 仍可读。")

所以遇到“资产删了，历史链接为什么还能打开”，先确认它是否只是 retired。若目标是物理清理历史，需要另行设计引用占用与删除策略，不能把退出目录等同于安全删除。
