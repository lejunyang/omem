# 知识文章的状态、来源与修改入口

面向需要定位知识更新行为的开发者，区分发布用途、页面生成状态与章节适用状态；说明直接引用、背景前提、调查轨迹和维护上下文各自负责什么，并给出目录、API、搜索、助手、重写与导入资产移除的主要排查入口。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="status-axes"></a>
## 先分清三套状态

同一篇文章可以**仍在目录、整篇显示待更新，同时只有部分章节能被搜索**。定位这类现象时，先分别检查发布用途、页面生成状态和章节适用状态；它们回答的是三个不同问题。

| 查询对象 | 值 | 它回答的问题 |
| --- | --- | --- |
| 发布用途 `role` | `article` / `reference` / `note` | 内容面向文章阅读、参考查询，还是仅作内部分析？显式 `publication.role` 优先；旧产物才按保存的 `reading.kind` 回退，不能根据路径或 key 猜用途。参考 [知识用途与产物字段 ↗](../../../packages/contracts/src/knowledge.ts#L92 "定义发布用途、章节状态，以及 dependencies、publication、investigation 等产物字段。") [发布用途回退规则 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L10 "说明显式 publication.role 优先，旧产物才按保存的 reading 目标回退。") |
| 页面 `state` | `planned` / `writing` / `published` / `failed` / `retired` | 本次生成走到哪一步？新计划从 planned 开始，实际写作时进入 writing，成功或失败分别落为 published / failed。参考 [计划、页面状态与发布过滤 ↗](../../../apps/server/src/knowledge/repository.ts#L128 "说明保存计划、计划变化失效、状态更新，以及 published 对 note、retired、planned 的过滤。") [页面写作状态流转 ↗](../../../apps/server/src/knowledge/pipeline.ts#L258 "说明 writePage 从 writing 到 published 或 failed 的状态流转。") |
| 章节 `state` | `current` / `needs-review` / `unavailable` | 这一节现在能否继续使用？current 表示固定依据仍适用；needs-review 表示上下文、前提或所引知识发生变化；unavailable 表示固定来源或固定知识版本不完整、已移除或无法读取。参考 [章节材料来源状态计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "说明直接引用与 reviewSources 如何组成章节来源，以及材料来源缺失、变化时的状态。") [所引知识的状态传播 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L152 "说明固定知识版本缺失、子章节待更新或出现新解释时，父章节如何变为 unavailable 或 needs-review。") |

页面状态描述**生成过程**，章节状态描述**内容适用性**。修改已有页面计划不会一律把它重置为 planned：若已有正文且计划变化，会写入失效原因并刷新；只有 retired 在重新保存计划时恢复 planned。`published()` 排除 note、retired 和 planned，却不因 failed 自动排除已有 head。因此首次生成失败只有计划，没有正文；已有页面重写失败时，旧正文仍可发布和阅读。参考 [计划、页面状态与发布过滤 ↗](../../../apps/server/src/knowledge/repository.ts#L128 "说明保存计划、计划变化失效、状态更新，以及 published 对 note、retired、planned 的过滤。")

整篇的 `current` 是逐节状态的聚合：只有所有章节都是 current，head 才为 current。阅读界面遇到非 current 文章会提示“部分内容需要核对”，但仍展示每节旧解释，并在对应章节给出原因。参考 [整篇 current 聚合 ↗](../../../apps/server/src/knowledge/repository.ts#L286 "证明只有所有章节 current 时，文章 head 才标为 current。") [待核对章节仍展示 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L87 "证明阅读界面保留旧正文，并逐节显示待核对原因。")

<a id="source-relations"></a>
## 区分证据、背景前提、调查轨迹与维护输入

发布后的知识资产有三类来源记录；维护旧页面时还会临时提供一组重写线索。前三类决定证据、复核或可见范围，第四类只帮助本轮从正确位置开始调查。

| 关系 | 保存内容 | 作用 |
| --- | --- | --- |
| **直接引用 `citations`** | 正文引用标记指向材料行范围或另一篇文章的 section | 它说明某项论断写作时依据什么。发布资产保存对应材料 digest 或文章 revision；读取引用时按这个固定版本解析，不会静默改指当前正文。参考 [直接引用合同 ↗](../../../packages/contracts/src/knowledge.ts#L4 "定义引用键、关系，以及材料行范围或文章 section 目标。") [固定引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L45 "说明 API 依赖保存的 digest 或 revision 解析固定材料与文章版本。") |
| **背景前提 `reviewSources`** | 章节级材料 key、行范围，以及“该前提为何影响本节” | 未直接写进论断的配置、约定或调用条件变化时，也能让相关章节进入 needs-review。它与正文引用一起形成固定材料依赖，但不能罗列所有读过内容。参考 [背景前提合同 ↗](../../../packages/contracts/src/knowledge.ts#L25 "定义章节 reviewSources 的材料范围、复核原因，并明确不能罗列全部阅读记录。") [章节材料来源状态计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "说明直接引用与 reviewSources 如何组成章节来源，以及材料来源缺失、变化时的状态。") |
| **调查轨迹 `investigation`** | 研究、写作、复核实际读过的材料 key 与 digest；细节保留在 trace | 它说明这一版调查过哪些背景，不断言每份材料的每个字节都支持正文，也不会单独使某节 needs-review；但其材料必须仍在允许的可见范围内，派生知识才能进入检索或研究快照。参考 [调查轨迹语义 ↗](../../../packages/contracts/src/knowledge.ts#L102 "说明 investigation 是调查中读过的材料记录，不断言所有内容支持正文。") [知识检索投影门禁 ↗](../../../apps/server/src/retrieval/units.ts#L587 "说明 investigation 与递归依赖必须可见、章节必须 current，页面不能是 note、retired 或 planned。") |
| **维护上下文** | `previousDraft`、旧阅读目标、`changedFields`、`materialChanges`、`newlySelected`、旧章节状态与 diff hunks | 它只决定本次优先补读哪里、哪些解释可保留；旧稿不是新事实来源，hunk 也不是语义判断或引用迁移。参考 [维护输入如何形成 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "说明材料变化、hunks、目标变化、新增选材、章节状态与旧稿复用条件。") |

旧正文只有在不越过新选材边界时才会交给模型：旧文所有 investigation key 必须仍在新材料集合中，材料 dependency 的固定版本仍须可解析，文章 dependency 也要递归满足同样条件。否则页面身份保留，但 researcher、writer、verifier 都拿不到旧正文，按新选材重新写。开放选材的旧计划没有完整目录，因此不会把整个材料库误报为“新增选材”。参考 [旧稿复用的选材边界 ↗](../../../apps/server/src/knowledge/maintenance.ts#L9 "说明旧文 investigation、材料固定版本与递归文章依赖都必须落在新选材中。") [维护输入如何形成 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "说明材料变化、hunks、目标变化、新增选材、章节状态与旧稿复用条件。") [旧稿复用与移出选材边界 ↗](../../../apps/server/tests/knowledge-pipeline.test.ts#L176 "测试覆盖旧稿可复用时三角色收到维护上下文，以及来源移出选材后改走 writer 且不带回旧背景。")

维护链路中，旧稿可用时第一次写作就由 refresher 承接；独立 verifier 同时看到变化信息并自行补读当前原件。发布时仍从**新稿**的材料 citations 与 reviewSources 形成材料 dependencies，从实际文章引用固定 article revision，并把研究、写作和复核阶段的实际 reads 汇成 investigation。维护 trace 只保留前版 revision、变化概要和是否复用旧稿，不复制整篇旧正文。参考 [维护时改写与独立复核 ↗](../../../apps/server/src/knowledge/pipeline.ts#L162 "证明有旧稿时首次写作使用 refresher，verifier 自行核查当前原件与遗漏前提。") [维护与新产物形成 ↗](../../../apps/server/src/knowledge/pipeline.ts#L162 "说明 refresher 和 verifier 的维护输入，以及新稿 dependencies、investigation 与精简 maintenance trace 的形成。")

固定引用与章节状态也不要混为一谈。引用始终指向写作时版本；生命周期只比较它所在的完整 Markdown 章节或代码符号是否仍适用。唯一同名结构的完整文本未变时允许整体移行；这只是缩小复查范围，不是语义等价证明或自动改写引用。参考 [固定引用的上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "说明固定引用不迁移，只通过唯一同名章节或符号的完整文本比较判断整体移行。")

**教学示例：**一篇活动文章有“预算”和“集合”两节。只在原文前插入导读时，两节完整上下文未变，仍为 current，引用仍打开写作时版本。预算从 80 改成 120 后，预算节变为 needs-review，集合节仍 current；搜索仍可命中集合，不再返回预算节。若集合节把旧预算登记为 reviewSources，同一次预算变化也会让集合节待核对，并显示保存的前提原因。这是测试夹具，不是现实活动事实。参考 [部分章节继续召回的教学测试 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L93 "用预算变化与地点不变验证逐节失效、固定引用与只召回 current 章节。") [背景前提影响章节的教学测试 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L166 "验证未直接引用的预算前提变化也会使集合章节待核对。")

<a id="visibility-entries"></a>
## 从现象找到可见性与修改入口

目录可见、详情可读、搜索可召回、普通助手可采用，以及知识写作可把旧文当背景，是不同门槛。排障时按现象进入对应入口。

| 现象 | 首先检查 | 主要入口 |
| --- | --- | --- |
| 页面不在目录 | `pages()` 是否因 note / retired 排除；`published()` 是否因 note / retired / planned 排除；是否已有 head | `knowledge/repository.ts` 的 `pages`、`published`、`savePlan`、`pageState` |
| 页面在目录但标“待更新” | `refresh()` 聚合的逐节 `knowledgeStatus`；若刚改过计划，再查页面 invalidation | `knowledge/lifecycle.ts` 的 `knowledgeStatus` 与 `knowledge/repository.ts` 的 `savePlan`、`refresh` |
| 正文可读，但某节搜不到 | 该节是否 current；investigation 与递归 dependencies 是否在可见范围；页面 role/state 是否允许发布 | `retrieval/units.ts` 的 `inputsAvailable`、`supported`、`validArticles` |
| 引用打开旧内容 | dependency 中保存的材料 digest 或文章 revision | `knowledge/api.ts` 的 `resolveCitation`；这是固定引用的预期行为 |
| 重新整理时没有旧稿 | 旧 investigation、材料 dependency 或递归文章 dependency 是否超出新选材 | `knowledge/maintenance.ts` 的 `articleWithinMaterials` 与 `planMaintenance` |
| 待更新旧文能被写作角色看到，但其变化章节搜不到 | 写作背景按整篇 published + 选材准入；搜索仍按 current 章节投影 | `knowledge/pipeline.ts` 的 `writePlannedPage`、`knowledge/research-snapshot.ts` 与 `retrieval/units.ts` |
| 普通助手没有采用目录中的文章 | 文章是否进入 published 集合，以及 investigation、固定材料版本和递归文章依赖是否获准进入同一快照 | `assistant/research.ts` 与 `knowledge/research-snapshot.ts` |

列表 API 会先刷新状态，再返回 published 文章、页面计划和当前材料；详情 API 可按 key 与可选 revision 读取正文，并返回逐节状态和解析后的固定引用。因此“按 revision 可读”不等于“仍在当前目录”。参考 [文章列表、详情与固定引用 ↗](../../../apps/server/src/knowledge/api.ts#L43 "说明列表刷新后返回发布内容，详情可按 revision 读取并返回逐节状态与固定引用。")

搜索先限定 published 文章和 topicPath。共享投影要求整篇的 investigation 与递归 dependencies 可见、目标章节为 current，且页面不是 note、retired 或 planned；只为满足条件的章节建立检索单元。若同文其他节待核对，current 章节的单元可携带整篇 needs-review 标记，但待核对章节本身不会进入投影。词法回退同样只遍历 current 章节。参考 [知识搜索的 current 章节筛选 ↗](../../../apps/server/src/knowledge/api.ts#L121 "说明搜索限定 published 与 topicPath，统一检索核对 revision，词法回退只遍历 current 章节。") [知识检索投影门禁 ↗](../../../apps/server/src/retrieval/units.ts#L587 "说明 investigation 与递归依赖必须可见、章节必须 current，页面不能是 note、retired 或 planned。") [只为可用章节建立检索单元 ↗](../../../apps/server/src/retrieval/units.ts#L670 "说明只投影 supported sections，并为部分待核对文章的 current 单元附整篇 reviewState。")

知识写作的背景准入更宽：刷新状态后，从 `repository.published()` 取其他文章，不预先要求整篇 current，再用 `articleWithinMaterials` 限定其调查与依赖都落在本次选材中。固定研究快照随后递归验证 investigation key、材料 dependency 的精确版本与文章 dependency；只有实际复制成功的 revision 才写进 `knowledge.json`，目录中会标整篇 current 或 needs-review。于是“可供角色直接阅读”与“某节可被共享搜索召回”可以同时给出不同结果。参考 [知识写作背景准入 ↗](../../../apps/server/src/knowledge/pipeline.ts#L273 "说明 native 写作从 published 文章中保留选材范围内的其他文章，不要求整篇 current。") [固定研究快照准入 ↗](../../../apps/server/src/knowledge/research-snapshot.ts#L98 "说明 investigation key、精确材料 dependency 与递归文章 dependency 都获准后才复制文章 revision。") [写作角色看到的知识目录 ↗](../../../apps/server/src/knowledge/agent-research.ts#L210 "说明 knowledge.json 只列实际进入快照的 revision，并标记整篇 current 或 needs-review。")

普通助手从当前可见 materials 与 `repository.published()` 建立同一类固定快照；提交答案时还会校验引用材料属于本轮授权范围、历史 revision 与当前材料同源、片段可见且行范围有效。参考 [普通助手的材料与文章入口 ↗](../../../apps/server/src/assistant/research.ts#L49 "说明助手以当前可见材料和 repository.published() 准备固定研究环境。") [答案引用最终校验 ↗](../../../apps/server/src/assistant/research.ts#L105 "说明提交时校验授权材料、历史版本同源性、片段可见性与精确范围。")

修改字段合同从 `packages/contracts/src/knowledge.ts` 开始；改章节失效规则看 `knowledge/lifecycle.ts`；改维护输入与旧稿复用边界看 `knowledge/maintenance.ts`；改写作背景、refresher/verifier 输入和新依赖形成看 `knowledge/pipeline.ts`；改目录与历史 head 看 `knowledge/repository.ts`；改搜索可用内容看 `retrieval/units.ts`；改助手与写作角色的快照授权看 `assistant/research.ts`、`knowledge/agent-research.ts` 和 `knowledge/research-snapshot.ts`。

<a id="asset-removal"></a>
## 导入资产移除后，目录退出但历史保留

导入目录中的文章资产消失时，默认动作是**撤销该导入方的发布归属**，不是删除知识 revision 或固定证据历史。

恢复流程以导入目录绝对路径作为 owner，先收集并解析 JSON。若存在无法解析的文件，本轮不会 reconcile，避免把临时损坏或未读到的资产误判为删除；其他有效资产仍可恢复。membership 只在资产 revision 真正成为当前 head 后推进，被拒绝、等待子依赖或因个人修改而仅保存为历史的版本不会提前取得归属。参考 [导入资产恢复与安全 reconcile ↗](../../../apps/server/src/knowledge/artifacts.ts#L32 "说明目录 owner、解析失败保护、依赖恢复，以及最后才执行 reconcile。") [导入归属与退休条件 ↗](../../../apps/server/src/knowledge/repository.ts#L154 "说明 membership 只跟随实际 head，移除时仅在无其他 owner 且 head 仍是 imported revision 时退休。")

reconcile 时，缺失的 key 先移除这个 owner 的 membership。只有同时满足“没有其他 owner”且“当前 head 仍等于该 membership 记录的 imported revision”，页面才进入 retired。另一个 owner 仍持有它，或用户后来发布了个人 revision，都不会退休当前正文；相同资产以后重新成为 head 时，可把 retired 恢复为 published。参考 [导入归属与退休条件 ↗](../../../apps/server/src/knowledge/repository.ts#L154 "说明 membership 只跟随实际 head，移除时仅在无其他 owner 且 head 仍是 imported revision 时退休。")

retired 会让页面退出 `pages()`、`published()` 和检索投影，但 reconcile 没有删除 `knowledge_revisions`。行为测试确认：移除 JSON 后文章不再 published，旧 revision 仍能按历史读取，个人捕获仍保留；另一组测试确认个人 revision 在后续导入与资产目录移除后继续发布。参考 [资产移除后历史仍可读 ↗](../../../apps/server/tests/development-knowledge.test.ts#L11 "测试确认退出 published 后历史 article revision 和个人原件仍保留。") [个人正文不被导入移除退休 ↗](../../../apps/server/tests/knowledge-repository.test.ts#L113 "测试确认个人 revision 在导入资产移除后继续发布，旧 imported revision 保留。")

因此遇到“资产删了，历史链接为什么还能打开”，先确认页面是否只是 retired。若目标是物理清理历史，需要另行设计引用占用检查，不能把退出目录等同于安全删除。
