# 知识文章的状态、来源与修改入口

面向需要定位知识更新行为的开发者，区分发布用途、页面生成状态与章节适用状态；说明直接引用、背景前提、调查轨迹如何影响固定证据、章节复核与可见范围，并给出目录、API、检索、助手和导入资产移除的主要修改入口。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="status-axes"></a>
## 先分清三套状态

同一篇文章可以**仍在目录、整篇显示待更新，同时只有部分章节能被搜索**。定位这类现象时，不要把所有状态都理解成“新旧”：先分别检查发布用途、页面生成状态和章节适用状态。

| 查询对象 | 值 | 它回答的问题 |
| --- | --- | --- |
| 发布用途 `role` | `article` / `reference` / `note` | 内容面向文章阅读、参考查询，还是仅作内部分析？显式 `publication.role` 优先；旧产物才根据保存的 reading 目标回退，不能按路径或 key 猜。参考 [知识用途与产物字段 ↗](../../../packages/contracts/src/knowledge.ts#L92 "定义 article、reference、note，并区分 dependencies、publication 与 investigation。") [发布用途回退规则 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L10 "说明显式 publication.role 优先，旧产物按 reading 目标回退。") |
| 页面 `state` | `planned` / `writing` / `published` / `failed` / `retired` | 这次整理走到哪一步？新建计划初始为 planned；已有页面调整计划通常保留原 state，只有 retired 会恢复为 planned。已有 head 且计划内容变化时会记录“等待重新整理”的失效原因并刷新；真正开始写作后才进入 writing，成功或失败分别落为 published / failed。参考 [计划保存与页面状态 ↗](../../../apps/server/src/knowledge/repository.ts#L128 "证明新页面初始为 planned，既有页面更新时保留原状态，retired 例外恢复 planned，并在已有正文且计划变化时写入失效原因。") [页面写作状态流转 ↗](../../../apps/server/src/knowledge/pipeline.ts#L251 "说明 writePage 保存计划后才明确进入 writing，成功为 published，异常为 failed。") |
| 章节 `state` | `current` / `needs-review` / `unavailable` | 这一节的解释现在能否继续使用？current 可用；needs-review 表示相关上下文或前提变化；unavailable 表示固定来源或固定知识版本已无法完整读取。参考 [章节适用状态计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "定义直接引用、背景前提与子文章依赖如何得到 current、needs-review 或 unavailable。") |

页面状态描述**生成过程**，章节状态描述**内容适用性**。因此，调整已有文章的计划不会无条件把页面改成 planned：旧 head 可以继续发布，但计划变化产生的 invalidation 会让其内容提示待重新整理。failed 也不一定让旧正文消失：只要已经有 head，`published()` 并不因 failed 排除它；首次整理失败则只有保留的计划，没有可返回的正文。planned 和 retired 会退出当前正文列表，note 也不会进入发布列表。参考 [计划保存与页面状态 ↗](../../../apps/server/src/knowledge/repository.ts#L128 "证明新页面初始为 planned，既有页面更新时保留原状态，retired 例外恢复 planned，并在已有正文且计划变化时写入失效原因。") [旧正文的发布资格 ↗](../../../apps/server/src/knowledge/repository.ts#L125 "证明 published 仅排除 note、retired 与 planned，不因 failed 自动移除已有 head。")

整篇的 `current` 是章节状态的聚合：刷新时只有每一节都是 current，head 才标为 current。界面遇到非 current 文章会提示“部分内容需要核对”，仍逐节展示旧解释与具体原因。参考 [整篇 current 的聚合 ↗](../../../apps/server/src/knowledge/repository.ts#L286 "证明只有所有章节都是 current 才更新 head.current 为真。") [待核对章节仍展示 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L87 "证明界面保留正文，逐节显示需要核对的原因。")

<a id="source-relations"></a>
## 直接引用、背景前提与调查轨迹

三类来源记录承担不同职责，不能互相替代。

| 关系 | 保存内容 | 何时影响章节 |
| --- | --- | --- |
| **直接引用 `citations`** | 正文中的引用标记指向材料行范围或另一篇文章的 section；发布资产另存对应材料 digest 或文章 revision | 它是正文论断的固定证据。点击引用时按 dependency 解析写作时的版本，不会因为原文更新而静默跳到新正文。参考 [直接引用合同 ↗](../../../packages/contracts/src/knowledge.ts#L4 "定义引用键、材料行范围或文章 section，以及章节正文和 reviewSources 的存储位置。") [固定引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L43 "证明 API 使用 dependency 的 digest 或 revision 解析历史材料与文章，而非改指当前正文。") |
| **背景前提 `reviewSources`** | 章节级材料 key、行范围和“为什么这个前提会影响本节” | 它不必出现在正文论断旁，但与直接引用一起形成 dependency；范围上下文变化时，本节变为 needs-review，并显示保存的原因。参考 [章节背景前提合同 ↗](../../../packages/contracts/src/knowledge.ts#L25 "定义 reviewSources 的材料范围与复核原因。") [依赖与调查轨迹形成 ↗](../../../apps/server/src/knowledge/pipeline.ts#L176 "证明直接引用和 reviewSources 形成 dependencies，实际读取记录形成 investigation。") [背景前提变化判断 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L103 "证明 reviewSources 与直接引用共同检查，并在前提变化时给出具体 needs-review 原因。") |
| **调查轨迹 `investigation`** | 研究、写作、复核实际读过的材料 key 与 digest；详细过程留在 trace | 它证明本版看过哪些背景，不表示每一份材料都直接支持正文，也不独自触发章节失效；但这些材料必须仍在当前可见范围内，派生正文才能进入检索或助手快照。参考 [调查轨迹语义 ↗](../../../packages/contracts/src/knowledge.ts#L102 "说明 investigation 是读过的材料记录，不代表每个字节都支持正文。") [依赖与调查轨迹形成 ↗](../../../apps/server/src/knowledge/pipeline.ts#L176 "证明直接引用和 reviewSources 形成 dependencies，实际读取记录形成 investigation。") |

固定引用解决“这句话写作时依据什么”，章节状态解决“这段解释今天还能不能用”。生命周期先比较来源身份与可信上下文；若 digest 不同，则尝试在新旧版本中找到唯一同名的 Markdown 章节或代码符号。完整结构文本相同可容忍整体移行，但这只是结构范围判断，不是语义等价或自动改写引用。参考 [固定引用的上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "说明引用保持固定，只用唯一同名章节或符号比较是否仍适用及是否发生整体移行。")

**教学示例：**一篇活动文章有“预算”和“集合”两节。只在原文前面插入导读时，完整章节内容没变，两节仍 current，引用仍打开写作时版本；预算从 80 改为 120 后，预算节变为 needs-review，集合节仍 current。检索“集合”仍能命中，检索“经费”不再返回预算节。若集合节把旧预算登记为 reviewSources，那么同一次预算变化也会让集合节待核对，并显示“集合方案以原预算为前提”。这是测试夹具说明的机制，不是生产活动事实。参考 [部分章节继续召回的测试场景 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L93 "用预算变化与集合不变验证按节失效、固定引用和只召回 current 章节。") [背景前提影响章节的测试场景 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L166 "验证未直接引用的预算前提变化也会使集合节待核对。")

<a id="visibility-entries"></a>
## 从现象找到可见性与修改入口

目录可见、API 可读、搜索可召回和助手可采用是逐层收紧的条件。遇到问题时按下表定位。

| 现象 | 首先检查 | 主要入口 |
| --- | --- | --- |
| 页面不在目录 | `pages()` 是否因 note / retired 排除；`published()` 是否因 note / retired / planned 排除；是否已有 head | `knowledge/repository.ts` 的 `pages`、`published`、`savePlan`、`pageState` |
| 页面在目录但标“待更新” | `refresh()` 聚合的逐节 `knowledgeStatus`；若刚调整过计划，再查 `knowledge_invalidations` | `knowledge/lifecycle.ts` 的 `knowledgeStatus` 与 `knowledge/repository.ts` 的 `savePlan`、`refresh` |
| 正文可读，但某节搜不到 | 该节是否 current；investigation 与递归 dependencies 是否仍可见；页面 role/state 是否允许发布 | `retrieval/units.ts` 的 `inputsAvailable`、`supported`、`validArticles` |
| 引用打开旧内容 | dependency 中保存的材料 digest 或文章 revision | `knowledge/api.ts` 的 `resolveCitation`；这是固定引用的预期行为 |
| 助手没有采用目录中的文章 | 文章是否进入 published 集合，以及调查材料和每一层固定依赖是否获准进入同一快照 | `assistant/research.ts` 与 `knowledge/research-snapshot.ts` |

列表 API 会先刷新状态，再同时返回 published 文章、页面计划和当前材料；详情 API 按 key 与可选 revision 直接读取正文，并返回逐节状态和已解析的固定引用。因而历史 revision 可以通过详情入口读取，但“可以按 revision 读取”不代表它仍在当前目录。参考 [文章列表、详情与历史读取 ↗](../../../apps/server/src/knowledge/api.ts#L43 "说明列表刷新后返回发布文章和页面，详情按可选 revision 返回章节状态与固定引用。")

知识搜索先限定 published 文章与 topicPath。统一检索分支只接受当前投影中同 revision 的 knowledge hit；词法回退也明确只遍历 current 章节。参考 [知识搜索的当前章节筛选 ↗](../../../apps/server/src/knowledge/api.ts#L121 "说明搜索限定 published 与 topicPath，统一检索核对 revision，词法回退只遍历 current 章节。")

检索投影是“搜索只用部分章节”的关键门禁：页面不能是 note、retired 或 planned，文章至少要有一个 supported 章节；supported 同时要求调查与依赖输入可见、该节状态为 current。生成检索单元时只投影这些章节；如果同文其他节待核对，单元可带整篇的 needs-review 提示，但待核对章节本身不会被放进去。参考 [知识检索投影门禁 ↗](../../../apps/server/src/retrieval/units.ts#L587 "证明 investigation 与递归依赖必须可见，章节必须 current，页面不能是 note、retired 或 planned。") [只为可用章节建立检索单元 ↗](../../../apps/server/src/retrieval/units.ts#L670 "证明只对 supported sections 建单元，并给部分待核对文章附 reviewState。")

助手从当前授权材料和 `repository.published()` 准备调查环境；固定快照只复制 investigation 材料仍获准、材料 dependency 的精确版本可用、文章 dependency 可递归访问的文章 revision。最终答案引用还要再次校验材料、历史版本、行范围与可见性。参考 [助手调查材料与文章入口 ↗](../../../apps/server/src/assistant/research.ts#L49 "说明助手从授权材料和 repository.published() 建立同一调查环境。") [固定调查快照准入 ↗](../../../apps/server/src/knowledge/research-snapshot.ts#L98 "证明 investigation、精确材料版本与递归文章依赖全部获准后才复制文章 revision。") [答案引用的最终校验 ↗](../../../apps/server/src/assistant/research.ts#L105 "证明提交时校验授权材料、历史 revision、可见性和精确行范围。")

若要改变字段合同，从 `packages/contracts/src/knowledge.ts` 开始；改变章节失效规则看 `knowledge/lifecycle.ts`；改变正文、依赖和调查轨迹如何形成看 `knowledge/pipeline.ts`；改变目录和历史 head 看 `knowledge/repository.ts`；改变搜索可用内容看 `retrieval/units.ts`；改变助手授权看 `assistant/research.ts` 与 `knowledge/research-snapshot.ts`。

<a id="asset-removal"></a>
## 导入资产移除后，目录退出但历史保留

导入目录中的文章资产消失时，默认动作是**撤销该导入方的发布归属**，不是删除知识 revision 或固定证据历史。

恢复流程以导入目录的绝对路径作为 owner。它先解析全部 JSON；只要目录中有不可解析资产，就不会执行 reconcile，以免把暂时损坏或未读到的文件误判为删除。有效资产仍可恢复；真正推进 membership 的只能是已经成为当前 head 的 revision，被拒绝、等待子依赖或因个人修改而只存为历史的资产不会提前取得归属。参考 [导入资产恢复与安全 reconcile ↗](../../../apps/server/src/knowledge/artifacts.ts#L32 "说明目录以 owner 管理、临时解析失败不会触发删除，并在恢复结束后才 reconcile。") [导入归属与退休条件 ↗](../../../apps/server/src/knowledge/repository.ts#L154 "说明 membership 只跟随实际 head，移除时仅在无其他 owner 且 head 仍为 imported revision 时退休。")

reconcile 时，缺失的 key 会先删除该 owner 的 membership。只有同时满足“没有其他 owner”且“当前 head 仍等于这条 membership 记录的 imported revision”，页面才变为 retired。若另一个 owner 仍持有它，或用户后来发布了个人 revision，当前正文不会被退休。相同资产以后重新成为 head 时，可以把 retired 恢复为 published。参考 [导入归属与退休条件 ↗](../../../apps/server/src/knowledge/repository.ts#L154 "说明 membership 只跟随实际 head，移除时仅在无其他 owner 且 head 仍为 imported revision 时退休。")

retired 会让页面退出 `pages()`、`published()` 和检索投影，但实现没有在 reconcile 中删除 `knowledge_revisions`。行为测试也确认：移除 JSON 后文章不再 published，按历史 revision 仍可读取，个人捕获仍保留；另一组测试确认个人 revision 在后续导入和资产目录移除后继续 published，旧 imported revision 仍可按 revision 找回。参考 [资产移除后历史仍可读 ↗](../../../apps/server/tests/development-knowledge.test.ts#L11 "测试确认退出 published 后历史 article revision 和个人原件仍保留。") [个人正文不被导入移除退休 ↗](../../../apps/server/tests/knowledge-repository.test.ts#L113 "测试确认真实个人 revision 在导入资产移除后继续发布，旧 imported revision 仍保留。")

因此排查“资产删了为什么还能按历史链接打开”时，应先确认它是否只是 retired；若目标是物理清理历史，需要另行设计引用占用检查，不能把目录退出等同于安全删除。
