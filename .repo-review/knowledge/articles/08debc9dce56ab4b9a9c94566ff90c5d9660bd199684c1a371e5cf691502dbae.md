# 知识文章的状态、来源与修改入口

面向排查知识更新行为的开发者，区分发布用途、页面生成、章节适用性与后台维护任务四套状态；说明直接引用、背景前提、调查轨迹和维护上下文的职责，并给出目录、API、搜索、助手、持续更新及导入资产移除的主要修改入口。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="status-axes"></a>
## 先分清四套状态

同一篇文章可以**仍在目录、旧正文可读、某些章节待核对，同时后台更新已经排队**。这些现象并不矛盾，因为系统分别记录四类状态：

| 查询对象 | 值 | 它回答的问题 |
| --- | --- | --- |
| 发布用途 `role` | `article` / `reference` / `note` | 内容面向连续阅读、参考查询，还是只作内部分析？显式 `publication.role` 优先；旧资产才按保存的 `reading.kind` 回退，不能根据路径或 key 猜用途。参考 [知识用途与产物字段 ↗](../../../packages/contracts/src/knowledge.ts#L99 "定义发布用途、章节状态以及 investigation 的语义。") [发布用途回退规则 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L10 "说明显式 publication.role 优先，旧资产按保存的 reading 目标回退。") |
| 页面生成 `state` | `planned` / `writing` / `published` / `failed` / `retired` | 页面生成走到哪一步？新计划从 planned 开始，管线执行时进入 writing，成功或失败分别落为 published / failed。参考 [页面计划、状态与发布过滤 ↗](../../../apps/server/src/knowledge/repository.ts#L128 "说明计划保存、计划变化失效、页面状态记录及 published 过滤。") [页面写作状态流转 ↗](../../../apps/server/src/knowledge/pipeline.ts#L258 "说明管线执行时从 writing 进入 published 或 failed。") |
| 章节适用 `state` | `current` / `needs-review` / `unavailable` | 这一节现在能否继续使用？current 表示固定依据仍适用；needs-review 表示上下文、背景前提或所引知识发生变化；unavailable 表示固定来源不完整、已移除或无法读取。参考 [章节状态合同 ↗](../../../packages/contracts/src/knowledge.ts#L99 "定义 current、needs-review 和 unavailable 三种章节状态。") [逐节适用性计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "说明引用、背景前提与递归文章依赖如何决定章节状态。") |
| 维护任务 `maintenance.state` | `idle` / `queued` / `writing` / `published` / `failed` | 最近一次持续维护或手动整理请求处于什么阶段？它还单独记录是否启用、错误和更新时间。参考 [维护任务状态合同 ↗](../../../packages/contracts/src/knowledge.ts#L74 "定义维护是否启用、任务状态、错误与更新时间字段。") [任务状态映射 ↗](../../../apps/server/src/knowledge/page-worker.ts#L128 "说明持久任务如何映射为 idle、queued、writing、published 或 failed。") |

页面生成状态描述**正文生产结果**，章节状态描述**现有正文的适用性**，维护任务状态描述**后台请求**。手动新建、重新整理或调整材料与目标会先进入持久队列并返回 queued；任务真正调用写作管线后，页面生成状态才进入 writing。列表 API 同时返回页面记录及其 maintenance 状态。参考 [页面请求进入持久队列 ↗](../../../apps/server/src/knowledge/api.ts#L190 "说明新建、刷新和调整目标如何返回 queued，并阻止同页重复活动请求。") [列表同时返回页面与维护状态 ↗](../../../apps/server/src/knowledge/api.ts#L21 "说明列表 API 附加每页 maintenance，并汇总运行状态。")

修改已有计划不会一律把页面重置成 planned：已有正文且计划变化时会写入失效原因并刷新；只有 retired 在重新保存计划时恢复 planned。published 集合排除 note、retired 和 planned，却不因 failed 自动排除已有 head。因此首次生成失败只有计划、没有正文；已有页面重写失败时，旧正文仍可发布和阅读。参考 [页面计划、状态与发布过滤 ↗](../../../apps/server/src/knowledge/repository.ts#L128 "说明计划保存、计划变化失效、页面状态记录及 published 过滤。")

整篇 `current` 是逐节状态的聚合：只有所有章节都是 current，head 才是 current。阅读界面会保留旧解释，并只在受影响章节显示原因。参考 [整篇 current 聚合 ↗](../../../apps/server/src/knowledge/repository.ts#L286 "证明只有全部章节 current 时文章 head 才为 current。") [待核对章节仍展示 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L87 "说明阅读界面保留旧正文并逐节显示待核对原因。")

**推断：**maintenance 的 published 只能说明最近一次队列任务成功，不能单独证明文章此刻仍 current；两者来自独立的任务状态映射与章节状态计算，之后的原件或计划变化仍可能使章节待核对。排障时必须同时看 maintenance、页面 state 和 sectionStatus。参考 [任务状态映射 ↗](../../../apps/server/src/knowledge/page-worker.ts#L128 "说明持久任务如何映射为 idle、queued、writing、published 或 failed。") [逐节适用性计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "说明引用、背景前提与递归文章依赖如何决定章节状态。")

<a id="source-relations"></a>
## 区分证据、背景前提、调查轨迹与维护输入

发布后的知识资产保存三类来源关系；维护旧页面时还会临时形成一组重写线索。前三类决定证据、复核或可见范围，第四类只帮助本轮从正确位置开始调查。

| 关系 | 保存内容 | 作用 |
| --- | --- | --- |
| **直接引用 `citations`** | 正文标记指向材料行范围或另一篇文章的 section | 说明一项论断写作时依据什么。发布资产保存材料 digest 或文章 revision；读取时按固定版本解析，不会静默改指当前正文。参考 [直接引用合同 ↗](../../../packages/contracts/src/knowledge.ts#L4 "定义引用键、关系以及材料行范围或文章章节目标。") [固定版本引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L66 "说明 API 按 dependency 中保存的材料 digest 或文章 revision 解析引用。") |
| **背景前提 `reviewSources`** | 章节级材料 key、行范围，以及“为何影响本节” | 配置、约定或调用条件即使没有写成正文论断，变化时仍能让相关章节进入 needs-review；它不应成为全部阅读记录清单。参考 [背景前提合同 ↗](../../../packages/contracts/src/knowledge.ts#L25 "定义 reviewSources 的材料范围、原因及选取边界。") [逐节适用性计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "说明引用、背景前提与递归文章依赖如何决定章节状态。") |
| **调查轨迹 `investigation`** | 研究、写作、复核实际读过的材料 key 与 digest | 说明这一版调查过哪些背景，不断言每份材料的每个字节都支持正文，也不单独使某节 needs-review；但这些材料仍须处于允许的可见范围，派生知识才能进入检索或研究快照。参考 [调查轨迹语义 ↗](../../../packages/contracts/src/knowledge.ts#L109 "说明 investigation 记录调查所读材料，而非逐字支持声明。") [知识检索准入门槛 ↗](../../../apps/server/src/retrieval/units.ts#L587 "说明调查材料与递归依赖必须可见，且只有 current 章节可用于投影。") |
| **维护上下文** | 旧稿、旧阅读目标、目标变化、材料 hunks、新增选材和旧章节状态 | 只决定本轮优先补读哪里、哪些解释可保留。旧稿不是新事实来源，hunk 是调查入口，不是语义结论或引用迁移。参考 [维护变化输入 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "说明材料变化、hunks、新增选材、目标变化和旧章节状态如何形成。") |

旧正文只有在不越过新选材边界时才会交给模型：旧文的 investigation key 必须都仍在新材料集合中，材料 dependency 的固定版本仍可解析，文章 dependency 也要递归满足同样条件。否则页面身份保留，但不提供旧正文，按新选材重写。开放选材的旧计划没有完整目录，因此不会把整个材料库误报为“新增选材”。参考 [旧稿复用的选材边界 ↗](../../../apps/server/src/knowledge/maintenance.ts#L9 "说明旧 investigation、材料依赖和递归文章依赖必须落在新选材中。") [维护变化输入 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "说明材料变化、hunks、新增选材、目标变化和旧章节状态如何形成。")

旧稿可用时，第一次改写由 refresher 承接，独立 verifier 同时拿到变化上下文并自行核查当前原件。发布新稿时，材料 dependencies 仍由**新稿**的 citations 与 reviewSources 形成，文章引用固定到实际 revision；investigation 则汇总研究、写作和复核阶段真正读过的材料。维护 trace 只保存前版 revision、变化概要与是否复用旧稿。参考 [改写、复核与新产物形成 ↗](../../../apps/server/src/knowledge/pipeline.ts#L162 "说明 refresher/verifier 输入及新稿 dependencies、investigation 和维护 trace 的形成。")

固定引用与章节状态也不要混为一谈。引用始终指向写作时版本；生命周期比较其所在的完整 Markdown 章节或代码符号是否仍适用。唯一同名结构的完整文本未变时允许整体移行；这只是缩小复查范围，不是语义等价证明，也不会迁移引用。参考 [固定引用的上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "说明引用不迁移，只以唯一同名完整结构比较是否整体移行。")

**教学示例：**测试夹具中的活动文章有“预算”和“集合”两节。只在原文前插入导读时，两节完整上下文未变，引用仍打开写作时版本；预算从 80 改成 120 后，预算节变为 needs-review，集合节仍 current，搜索保留集合而不再返回预算。若集合节把旧预算登记为 reviewSources，同一次变化也会让集合节待核对。这是行为测试，不是现实活动事实。参考 [局部章节继续召回的教学测试 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L93 "用预算变化与集合不变验证逐节失效、固定引用和 current 章节召回。") [背景前提变化的教学测试 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L166 "验证未直接引用的预算前提变化也会使相关章节待核对。")

<a id="visibility-entries"></a>
## 按现象定位可见性与持续维护

目录可见、历史详情可读、搜索可召回、助手可采用、写作角色可读，以及后台任务正在运行，是不同门槛。排障时按现象进入对应实现：

| 现象 | 首先检查 | 主要入口 |
| --- | --- | --- |
| 页面不在目录 | role 是否为 note，页面是否 retired；published 是否因 planned 排除；是否已有 head | `knowledge/repository.ts` 的 `pages`、`published`、`savePlan` |
| 页面在目录但标“待更新” | `knowledgeStatus` 的逐节结果；计划变化产生的 invalidation | `knowledge/lifecycle.ts` 与 repository 的 `refresh` |
| 显示 queued / writing / failed，但旧文仍可读 | maintenance job 状态与页面 state 分开检查；failed 是否仍有旧 head | `knowledge/page-worker.ts`、`knowledge/api.ts`、`ArticleMaintenance.vue` |
| 正文可读，但某节搜不到 | 该节是否 current；investigation 与递归 dependencies 是否可见；页面 role/state 是否允许发布 | `retrieval/units.ts` 的 `inputsAvailable`、`supported`、`validArticles` |
| 引用打开旧内容 | dependency 中保存的材料 digest 或文章 revision | `knowledge/api.ts` 的 `resolveCitation`；这是固定引用的预期行为 |
| 重新整理时没有旧稿 | 旧 investigation、材料 dependency 或递归文章 dependency 是否超出新选材 | `knowledge/maintenance.ts` 的 `articleWithinMaterials` |
| 待更新旧文可供写作角色读取，但变化章节搜不到 | 写作背景按 published + 选材准入；共享搜索仍按 current 章节投影 | `knowledge/pipeline.ts`、`knowledge/research-snapshot.ts`、`retrieval/units.ts` |
| 普通助手没有采用目录文章 | 文章是否 published；其调查材料、固定材料版本与递归文章依赖是否进入同一快照 | `assistant/research.ts` 与 `knowledge/research-snapshot.ts` |

详情 API 可按 key 与可选 revision 读取正文，并返回逐节状态和解析后的固定引用；所以“按 revision 可读”不等于“仍在当前目录”。搜索先限定 published 与 topicPath；共享投影还要求整篇 investigation 和递归 dependencies 可见，并只为 current 章节建立检索单元。同文其他节待核对时，current 单元可以携带整篇 needs-review 标记，但待核对章节本身不会进入投影；词法回退同样只遍历 current 章节。参考 [文章列表、详情与固定引用 ↗](../../../apps/server/src/knowledge/api.ts#L64 "说明详情可按 revision 读取并返回逐节状态与固定引用。") [搜索中的 current 章节筛选 ↗](../../../apps/server/src/knowledge/api.ts#L142 "说明搜索限定 published 和 topicPath，词法回退仅遍历 current 章节。") [知识检索准入门槛 ↗](../../../apps/server/src/retrieval/units.ts#L587 "说明调查材料与递归依赖必须可见，且只有 current 章节可用于投影。") [只投影可用章节 ↗](../../../apps/server/src/retrieval/units.ts#L670 "说明检索单元仅来自 supported sections，并为部分待核对文章附 reviewState。")

知识写作背景的门槛更宽：它从 published 文章中取候选，不先要求整篇 current，再按本次选材限制调查与依赖。固定研究快照递归验证 investigation、材料精确版本和文章依赖；只有实际获准的 revision 才写入 `knowledge.json`，并标出整篇 current 或 needs-review。普通助手也从当前可见材料与 published 文章建立同类快照，并在提交答案时再次校验授权材料、历史版本同源性、可见性和行范围。参考 [知识写作背景准入 ↗](../../../apps/server/src/knowledge/pipeline.ts#L273 "说明写作从 published 文章取候选，再按本次选材限制。") [固定研究快照准入 ↗](../../../apps/server/src/knowledge/research-snapshot.ts#L98 "说明 investigation、精确材料版本与递归文章依赖都获准后才复制知识 revision。") [写作角色的知识目录 ↗](../../../apps/server/src/knowledge/agent-research.ts#L204 "说明 knowledge.json 只列实际进入快照的文章，并标记 current 或 needs-review。") [普通助手的快照与引用校验 ↗](../../../apps/server/src/assistant/research.ts#L49 "说明助手的材料和文章入口，以及提交答案时的授权与范围校验。")

持续维护默认关闭，启用前必须有显式 `materialKeys`。它计算“完整计划 + 已选材料当前 digest”的 scope digest；后台定时观察启用的页面，GET 本身不运行模型。只跟踪明确选中的来源，不按项目名、路径或相似度自动吸收新增材料；新来源须通过“调整材料与目标”加入。参考 [持续维护的选材与观察 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "说明显式选材要求、scope digest、自动观察和活动任务合并。") [持续维护的产品边界 ↗](../../../docs/reader-first/publication-lifecycle.md#L41 "说明持久队列、连续变化、失败处理及只跟踪明确选中来源。")

同页已有 queued、retry_wait、leased 或 running 任务时，新变化只更新目标 digest，不再创建第二条活动任务；执行读取最新计划。执行中再次变化会在本轮结束后排下一轮。服务重启保留设置和任务。失败输入在 finally 中记为已处理，避免对同一输入无限自动重试；显式重试或新的材料变化可再次执行。关闭持续维护只取消自动任务，不取消用户明确发起的整理。参考 [持久任务执行与失败处理 ↗](../../../apps/server/src/knowledge/page-worker.ts#L28 "说明任务持久化、执行管线及失败输入不会无限自动重试。") [持续维护的选材与观察 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "说明显式选材要求、scope digest、自动观察和活动任务合并。") [连续变化合并与重启恢复测试 ↗](../../../apps/server/tests/knowledge-page-worker.test.ts#L33 "测试验证同页变化合并为一项任务、重启后使用最新版本且历史仍可读。") [失败、重试与运行中再变化测试 ↗](../../../apps/server/tests/knowledge-page-worker.test.ts#L61 "测试验证失败保留旧文、不循环，同一运行中的新变化会进入下一轮。") [关闭自动维护的任务边界测试 ↗](../../../apps/server/tests/knowledge-page-worker.test.ts#L89 "测试验证关闭仅取消自动任务，不取消明确手动请求。")

当前能力边界是：系统已接通明确选材的自动更新，但尚未实现新增项目来源的自动归属，也没有自动语义影响分析；是否影响某节仍由固定上下文、背景前提和独立复核共同判断。参考 [当前实现范围与未完成能力 ↗](../../../docs/reader-first/progress.md#L3 "记录明确选材自动更新已接通，而新增来源自动归属和完整项目理解尚未实现。")

<a id="asset-removal"></a>
## 导入资产移除后，目录退出但历史保留

导入目录中的文章资产消失时，默认动作是**撤销该导入方的发布归属**，不是删除知识 revision 或固定证据历史。

恢复流程以导入目录绝对路径作为 owner，先收集并解析 JSON。只要存在无法解析的文件，本轮就不做 reconcile，避免把临时损坏或未读到的资产误判为删除；其他有效资产仍可恢复。membership 只在资产 revision 真正成为当前 head 后推进，被拒绝、等待子依赖或因个人修改而仅保存为历史的版本不会提前取得归属。参考 [导入资产恢复与安全 reconcile ↗](../../../apps/server/src/knowledge/artifacts.ts#L32 "说明解析失败保护、依赖恢复以及最后才执行 reconcile。") [导入归属与退休条件 ↗](../../../apps/server/src/knowledge/repository.ts#L154 "说明 membership 只跟随实际 head，缺失时仅在无其他 owner 且 head 未被替换时退休。")

reconcile 时，缺失 key 先移除这个 owner 的 membership。只有同时满足“没有其他 owner”且“当前 head 仍等于该 membership 记录的 imported revision”，页面才进入 retired。另一个 owner 仍持有它，或用户后来发布了个人 revision，都不会退休当前正文；相同资产以后重新成为 head 时，可从 retired 恢复为 published。参考 [导入归属与退休条件 ↗](../../../apps/server/src/knowledge/repository.ts#L154 "说明 membership 只跟随实际 head，缺失时仅在无其他 owner 且 head 未被替换时退休。")

retired 会让页面退出目录、published 集合和检索投影，但 reconcile 不删除 `knowledge_revisions`。测试确认：资产移除后文章退出 published，旧 revision 仍可按历史读取，个人原件仍保留；个人发布的新 head 也不会因导入目录移除而退休。参考 [资产移除后历史仍可读 ↗](../../../apps/server/tests/development-knowledge.test.ts#L11 "测试确认退出 published 后旧 revision 和个人原件仍保留。") [个人正文不被导入移除退休 ↗](../../../apps/server/tests/knowledge-repository.test.ts#L113 "测试确认个人 revision 在资产移除后继续发布，旧 imported revision 保留。")

因此遇到“资产删了，历史链接为什么还能打开”，先确认页面是否只是 retired。若目标是物理清理历史，需要另行设计引用占用检查，不能把退出目录等同于安全删除。
