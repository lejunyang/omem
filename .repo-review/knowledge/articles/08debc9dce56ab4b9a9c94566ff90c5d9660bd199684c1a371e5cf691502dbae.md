# 知识文章的状态、来源与修改入口

面向排查知识更新行为的开发者，先区分发布用途、页面生成、章节适用性与后台维护四套状态，再拆开项目材料归属、文章分类、调查选材和固定引用四层关系。说明动态项目文章如何解析范围、合并变化并在发布前防止旧结果覆盖新计划，同时给出 API、检索、助手与导入资产移除的定位入口。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="status-axes"></a>
## 先分清四套状态

同一篇文章可以**仍在目录、旧正文可读、某一节待核对，同时后台更新已经排队**。这不是状态冲突，而是四套字段在回答不同问题。

| 查询对象 | 可能值 | 回答的问题 |
| --- | --- | --- |
| 发布用途 `role` | `article` / `reference` / `note` | 内容面向连续阅读、参考查询，还是内部分析？显式 `publication.role` 优先；旧资产才按保存的 `reading.kind` 回退，不能根据路径、key 或主题名猜用途。参考 [发布用途与产物字段 ↗](../../../packages/contracts/src/knowledge.ts#L100 "定义 role、selection、publication 与 investigation 的语义。") [发布用途回退 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L10 "说明显式 publication.role 优先，旧资产按保存的 reading.kind 回退。") |
| 页面生成 `state` | `planned` / `writing` / `published` / `failed` / `retired` | 正文生产走到哪一步？计划保存、生成成功失败和退出目录都记在页面记录上。参考 [页面计划与发布过滤 ↗](../../../apps/server/src/knowledge/repository.ts#L137 "说明页面计划、生成状态、计划变化失效与 published 的过滤条件。") |
| 章节适用 `state` | `current` / `needs-review` / `unavailable` | 这一节现在能否继续采用？它按本节内联引用、背景前提和递归文章依赖计算。参考 [逐节适用性计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "说明 invalidation、直接引用、背景前提和递归文章依赖如何决定章节状态。") |
| 维护任务 `maintenance.state` | `idle` / `queued` / `writing` / `published` / `failed` | 最近一次手动整理或自动维护请求处于什么阶段？它还单独保存是否启用、错误和更新时间。参考 [维护任务状态 ↗](../../../apps/server/src/knowledge/page-worker.ts#L130 "说明持久任务如何映射为 idle、queued、writing、published 或 failed。") |

已有正文且计划变化时，系统写入失效原因并刷新章节状态，不会简单把可读 head 抹掉；`published()` 排除 note、planned 和 retired，却不因页面 state 为 failed 自动排除已有 head。因此首次生成失败可能只有计划、没有正文；已有页面重写失败时，旧正文仍可读。整篇 `current` 只是逐节状态的聚合：所有章节都 current 时 head 才 current。界面也按节标出原因，并明确保留其他章节和写作时引用。参考 [页面计划与发布过滤 ↗](../../../apps/server/src/knowledge/repository.ts#L137 "说明页面计划、生成状态、计划变化失效与 published 的过滤条件。") [整篇 current 聚合 ↗](../../../apps/server/src/knowledge/repository.ts#L297 "证明只有所有章节 current 时文章 head 才 current。") [待核对章节仍展示 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L87 "说明阅读界面保留旧正文并逐节显示待核对原因。")

所以排障时不要只看一个“已发布”：maintenance 的 published 说明最近一次队列任务成功，页面 state 说明正文生产结果，sectionStatus 才说明当前依据是否仍适用。后续原件、计划或所引文章变化，仍可能让章节进入 needs-review。

<a id="scope-classification"></a>
## 拆开归属、分类、选材与固定引用

新增项目能力后，最容易混淆的是四种看起来都像“关联”的关系。它们不能互相替代。

| 关系 | 保存在哪里 | 它决定什么 |
| --- | --- | --- |
| **项目/主题材料归属** | `material_contexts` 与 `material_context_sources`，按稳定 `source_id` 多对多关联 | 哪些原件属于一个可持续跟踪的范围。归属是明确输入，不从文件名、会话 ID 或正文相似度推断；同一 source 可属于多个 context。参考 [项目与主题材料归属 ↗](../../../apps/server/src/contexts/repository.ts#L5 "说明 context 与稳定 source 的多对多显式关联、整体替换及并集查询。") |
| **文章分类与用途** | `publication.role`、`document.category`、`topicPath` | role 区分文章、参考页和内部笔记；category 是文章类型名；topicPath 是面向读者的宽到窄目录，不是来源目录或项目 ID。若页面计划给出 topicPath，管线在独立复核前覆盖模型建议。参考 [文章目录与背景前提合同 ↗](../../../packages/contracts/src/knowledge.ts#L25 "定义 category、topicPath、章节和 reviewSources；topicPath 按读者主题组织。") [页面计划覆盖目录位置 ↗](../../../apps/server/src/knowledge/pipeline.ts#L170 "说明显式 topicPath 是页面计划数据，并在复核前覆盖模型建议。") |
| **本轮调查选材** | 页面计划的 `materialKeys` 与 `contextIds` | 固定材料与当前 context 成员取并集；两者都省略才回退到全部可用原件。`entryPaths` 只是调查起点，不是权限或范围。参考 [固定材料与动态 context 合同 ↗](../../../packages/contracts/src/knowledge.ts#L64 "定义 materialKeys、contextIds 及 entryPaths 的范围语义。") [计划材料解析 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "说明固定 materialKeys 与 context 当前 source 成员取并集，两者省略时使用全部可用原件。") |
| **正文固定引用** | `citations`、`reviewSources` 及其 dependency digest/revision | 某句话或某节背景前提在写作时依据哪个固定版本。它不会因为当前项目成员或目录位置改变而静默改指新版。参考 [直接引用合同 ↗](../../../packages/contracts/src/knowledge.ts#L4 "定义引用关系、材料行范围与文章章节目标。") [产物依赖、选择与调查字段 ↗](../../../packages/contracts/src/knowledge.ts#L110 "说明 dependencies、selection、publication 和 investigation 的不同职责。") |

捕获原件时若传入 `contextIds`，系统先校验 context，再在创建或复用稳定 source 的同一事务中写 membership；同源换版没有再次传入 `contextIds` 时，不会清掉旧归属。调整 membership 是整体替换该 source 的 context 集合，不会改写原文 revision。参考 [捕获前校验归属 ↗](../../../apps/server/src/store.ts#L108 "说明传入 contextIds 时先验证这些 context。") [捕获事务内保存归属 ↗](../../../apps/server/src/store.ts#L151 "说明捕获在事务内复用 receipt 或稳定 source，并仅在传入 contextIds 时写 membership。") [项目与主题材料归属 ↗](../../../apps/server/src/contexts/repository.ts#L5 "说明 context 与稳定 source 的多对多显式关联、整体替换及并集查询。")

网页选择动态 context 后，会移除同一 source 的重复固定勾选；context 内材料自动选中且不能逐项取消，避免 source 日后移出 context 却仍被固定 pin 在页面上。提交时网页发送当前 revisionIds 与 contextIds；API 验证 revision 仍是当前版本，再把固定选择转换为稳定 materialKeys，并要求固定材料或 context 至少有一种。参考 [动态范围选择器 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L37 "说明 context 成员自动选中并移除重复固定选择。") [context 成员禁止逐项取消 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L193 "说明来自所选 context 的材料复选框会被禁用，不能单独取消。") [页面计划提交校验 ↗](../../../apps/server/src/knowledge/api.ts#L207 "说明 API 校验当前 revision、至少一种范围并把固定 revisionIds 转为 materialKeys。")

因此，**contextIds 是材料范围，不是文章目录；topicPath 是阅读目录，不是权限边界；dependency 是证据和更新关系，不是项目成员关系。** 想让新材料进入动态文章，必须先把它明确关联到该 context；标题相似或路径相近都不算归属。

<a id="dynamic-lifecycle"></a>
## 动态项目文章从选材到发布

一篇跟踪项目或主题的文章，主链可以按下面六步定位：

1. 用户把原件 source 明确关联到 project/topic；source 换版仍沿用稳定 sourceId，因此 membership 保留。
2. 页面计划保存 `contextIds`、额外 `materialKeys`、阅读目标和可选 topicPath。每次真正写作前，`materialsForPlan` 都重新计算“固定 key ∪ context 当前成员”，并取得这些 source 的当前 revision。参考 [计划材料解析 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "说明固定 materialKeys 与 context 当前 source 成员取并集，两者省略时使用全部可用原件。") [写作时重新解析材料 ↗](../../../apps/server/src/knowledge/pipeline.ts#L275 "说明每次 writePlannedPage 都解析当前材料集合并记录排序后的 keys。")
3. 手动请求或 worker 入队。worker 的 `scopeDigest` 包含完整 plan，以及当前解析出的每个材料 key 和 digest；新增成员、移出成员、原件换版或计划变化都会改变它。已有活动任务时只更新 target digest，不创建同页第二条活动任务；观察循环只比较并排队，不在 HTTP GET 中运行模型。参考 [动态范围观察与任务合并 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "说明 scope digest、启用条件、活动任务合并和独立观察排队。")
4. 研究、写作与独立复核使用这一轮 offers。旧稿只有在旧 investigation、固定材料 dependency 和递归文章 dependency 都仍落在新选材内时才可提供；否则保留页面身份，但按新范围重新调查。维护上下文中的 hunks 只是补读起点，不是语义变化结论或引用迁移。参考 [旧稿复用边界 ↗](../../../apps/server/src/knowledge/maintenance.ts#L9 "说明旧 investigation、材料依赖和递归文章依赖必须都落在新选材范围。") [维护变化输入 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "说明材料变化、hunks、新增选材、目标变化和旧章节状态如何形成维护上下文。")
5. 通过复核后，host 为正文材料引用绑定精确 quote；新产物把 citations 和 reviewSources 涉及的材料保存为 dependency，把文章引用固定到实际 revision。实际读过的材料另记入 investigation。只有动态 context 计划额外保存 `selection.materialKeys`，作为这一版实际成员集合快照。参考 [引用绑定与范围校验 ↗](../../../apps/server/src/knowledge/pipeline.ts#L141 "说明 host 绑定精确 quote，并校验引用与 reviewSources 都来自可读 offer。") [发布产物形成 ↗](../../../apps/server/src/knowledge/pipeline.ts#L183 "说明 dependencies、selection、publication 与 investigation 如何从本轮稿件和读取轨迹形成。")
6. 替换 head 前有三类检查：保存的计划是否仍等于任务开始时的计划；动态范围当前 key 集合是否仍等于 artifact.selection；正文 dependency 的材料 digest 或文章 revision 是否仍是当前值。任一不满足都在写入新 revision/head 前拒绝，旧文和最新计划保留。参考 [发布前竞态检查 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "说明计划、动态成员集合与 dependency 版本变化都会在替换 head 前拒绝旧结果。")

这里有两种不同快照。**selection 快照**防止旧成员集合覆盖新的项目范围；**dependency 快照**防止正文直接引用或登记为 reviewSources 的依据在途中换版后仍发布。这是基于字段用途与发布检查的推断，不要把两者合并成“所有读过的材料一变化，本轮必然拒绝”。worker 的 scopeDigest 覆盖全部本轮选材，因此未被正文引用的选材变化仍会触发后续维护；但发布时的版本检查遍历 dependencies，而不是全部 investigation。参考 [动态范围观察与任务合并 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "说明 scope digest、启用条件、活动任务合并和独立观察排队。") [发布产物形成 ↗](../../../apps/server/src/knowledge/pipeline.ts#L183 "说明 dependencies、selection、publication 与 investigation 如何从本轮稿件和读取轨迹形成。") [发布前竞态检查 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "说明计划、动态成员集合与 dependency 版本变化都会在替换 head 前拒绝旧结果。")

**教学示例：**测试构造了一个“活动”项目。未关联的同名 999 元材料不会触发维护；后来明确关联“周四下午截止”的 source 后，它进入文章。该 source 再被移出项目时，用旧 selection 发布会被拒绝，下一轮移除相应内容；旧文章 revision 和原件历史仍可读取。这是行为测试，不是现实活动事实。参考 [动态项目行为测试 ↗](../../../apps/server/tests/material-contexts.test.ts#L32 "用未关联同名材料、新增成员、移出成员和历史回读验证动态范围边界。")

当前边界也应写清：系统不会从内容自动判断项目归属。动态 context 只会吸收后来被明确关联到这个 context 的 source；它目前是文章选材和维护能力，不等于完整项目助理，也不是安全隔离边界。参考 [项目范围当前边界 ↗](../../../docs/reader-first/project-contexts.md#L15 "说明明确归属、动态选材以及尚未实现的自动归属和完整项目助理能力。")

<a id="evidence-visibility"></a>
## 按证据关系和可见性现象定位

发布资产中的几类来源关系职责不同：

| 关系 | 含义与更新作用 |
| --- | --- |
| `citations` | 正文内联标记指向材料行范围或另一篇文章章节；host 校验引用键、范围和可见 offer，并复制固定原文。参考 [引用绑定与范围校验 ↗](../../../apps/server/src/knowledge/pipeline.ts#L141 "说明 host 绑定精确 quote，并校验引用与 reviewSources 都来自可读 offer。") |
| `reviewSources` | 本节未必逐字引用、但会改变解释的背景前提；变化时让相关章节待核对，不应拿来记录全部阅读清单。参考 [文章目录与背景前提合同 ↗](../../../packages/contracts/src/knowledge.ts#L25 "定义 category、topicPath、章节和 reviewSources；topicPath 按读者主题组织。") [逐节适用性计算 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "说明 invalidation、直接引用、背景前提和递归文章依赖如何决定章节状态。") |
| `investigation` | 研究、写作和复核实际读过的材料及 digest；它说明调查轨迹，不断言每份材料都直接支持正文。参考 [产物依赖、选择与调查字段 ↗](../../../packages/contracts/src/knowledge.ts#L110 "说明 dependencies、selection、publication 和 investigation 的不同职责。") |
| 维护上下文 | 旧稿、目标变化、材料 hunks、新增选材和旧章节状态；只帮助本轮定位补读与可复用解释。参考 [维护变化输入 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "说明材料变化、hunks、新增选材、目标变化和旧章节状态如何形成维护上下文。") |

固定引用与章节状态也要分开。引用 API 按 dependency 中的 digest/revision 解析历史材料或文章版本，并另外返回 actionable、current；生命周期比较固定版本与当前版本时，只判断引用所在完整 Markdown 章节或代码符号是否仍适用。唯一同名同类型结构全文未变时允许整体移行，但引用仍指旧版，不做语义重映射。参考 [固定引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L64 "说明详情 API 按 dependency 的 digest 或 revision 解析引用并返回 current 与 actionable。") [固定引用上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "说明引用不迁移，只以完整结构比较当前适用性。")

按现象查入口：

| 现象 | 首先检查 |
| --- | --- |
| 页面不在目录 | `knowledge/repository.ts` 的 role、pages、published：是否为 note、planned 或 retired，是否已有 head。 |
| 页面可读但某节提示待核对 | `knowledge/lifecycle.ts` 的 `knowledgeStatus`，以及计划变化写入的 invalidation。 |
| queued / writing / failed 与旧文同时出现 | `page-worker.ts` 的任务状态和 `repository.ts` 的页面 state 分开看。 |
| 引用打开旧内容 | `knowledge/api.ts` 的 `resolveCitation` 与 repository 的历史材料解析；这是固定引用的预期行为。 |
| 正文可读但某节搜不到 | 检索要求整篇 investigation 与递归 dependencies 在可见范围内，并只投影 current 章节；文章其他节待核对时，current 节仍可形成单元并携带 needs-review 标记。参考 [知识检索准入 ↗](../../../apps/server/src/retrieval/units.ts#L587 "说明调查材料与递归依赖必须可见，且至少有 current 章节才建立知识投影。") [按 current 章节投影 ↗](../../../apps/server/src/retrieval/units.ts#L670 "说明检索单元只来自 supported sections，并携带可见性与整篇 reviewState。") |
| 普通助手没有采用目录文章 | 助手先按当前可见材料构造研究环境；固定快照还会递归验证 investigation、材料精确版本和文章依赖。提交答案时，引用必须属于本次授权 source，历史 revision 也必须同源且可见。参考 [固定研究快照准入 ↗](../../../apps/server/src/knowledge/research-snapshot.ts#L98 "说明 investigation、精确材料版本与递归文章依赖获准后才复制知识 revision。") [助手材料与引用校验 ↗](../../../apps/server/src/assistant/research.ts#L49 "说明助手从可见材料和 published 文章建环境，并校验授权、同源历史版本与可见性。") |
| 分类搜索结果异常 | `knowledge/api.ts` 先按 topicPath 前缀限制 published 文章；词法回退同样只遍历 current 章节。参考 [分类与章节搜索 ↗](../../../apps/server/src/knowledge/api.ts#L142 "说明搜索按 topicPath 前缀限制 published 文章，词法回退只遍历 current 章节。") |

因此“历史详情可读”“当前目录可见”“搜索可召回”“助手可采用”和“后台正在更新”是不同门槛。排障时先确定观察的是哪一层，再沿对应入口追踪。

<a id="asset-removal"></a>
## 导入资产移除后，目录退出但历史保留

导入目录中的文章资产消失时，默认动作是**撤销该导入方的发布归属**，不是删除知识 revision 或固定证据历史。

恢复流程以导入目录绝对路径作为 owner，先解析全部 JSON。只要存在无法解析的文件，本轮就不执行 reconcile，避免把临时损坏误判为删除；其他有效资产仍可恢复。只有 revision 实际成为当前 head，membership 才推进。参考 [导入资产恢复 ↗](../../../apps/server/src/knowledge/artifacts.ts#L32 "说明解析失败保护、依赖恢复以及仅在目录可解析时执行 reconcile。")

reconcile 时，缺失 key 先移除这个 owner 的 membership。只有同时满足“没有其他 owner”与“当前 head 仍等于该 membership 记录的 imported revision”，页面才进入 retired；另一个 owner 仍持有它，或用户后来发布了个人 revision，都不会退休当前正文。相同资产以后重新成为 head 时，可从 retired 恢复为 published。参考 [导入归属与退休条件 ↗](../../../apps/server/src/knowledge/repository.ts#L163 "说明仅当前 head 取得 membership，缺失时只有无其他 owner 且 head 未被替换才退休。")

retired 让页面退出目录、published 集合和检索投影，但不会删除 `knowledge_revisions`。集成测试确认资产移除后旧 revision 仍可按历史读取，个人原件继续存在；个人发布的新 head 也不会因导入目录移除而退休。参考 [资产移除后的历史 ↗](../../../apps/server/tests/development-knowledge.test.ts#L11 "测试确认退出 published 后旧 revision 与个人原件仍保留。") [个人正文不被导入移除退休 ↗](../../../apps/server/tests/knowledge-repository.test.ts#L113 "测试确认个人 revision 在导入资产移除后继续发布，旧 imported revision 仍可读。")

所以遇到“资产删了，历史链接为什么还能打开”，先确认它是否只是 retired。若目标是物理清理历史，需要另行设计引用占用与删除策略，不能把退出目录等同于安全删除。
