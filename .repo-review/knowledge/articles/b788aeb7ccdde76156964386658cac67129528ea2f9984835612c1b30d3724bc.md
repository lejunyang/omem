# 代码理解结果的统一数据合同

该 Schema 统一四类代码理解角色的输出形态，规定职责、边界、流程、证据、未知项、置信度与生成追溯字段。它描述数据结构及允许值，但不单独证明分析、状态转换或复核流程已经实现。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 统一代码理解结果

该合同让仓库画像、模块架构、符号解释和关系复核四类角色使用同一种结果对象。每份结果都必须包含职责、边界、关键流程、出入口、风险、论断、证据关联、未知项、置信度及生成追溯信息，便于下游按稳定字段读取不同角色的产物。参考 [统一结果字段与角色 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L3 "支持四类代码理解角色共用一个对象，并要求结果携带职责、流程、证据和追溯字段。")

它是一份 **JSON Schema 结构合同**：能够说明对象必须有哪些字段以及部分字段的取值约束，但不能单凭此文件确认源码分析、证据生成或独立复核如何执行。

<a id="status_trace"></a>
## 状态与生成追溯

`status` 只允许 `seed`、`generated`、`verified`、`failed` 和 `rejected` 五个值。当前 Schema 没有定义这些值的业务含义或转换顺序，因此只能把它们理解为允许写入的状态标签，不能据此断言 `seed` 必然来自人工维护，或存在固定生命周期。参考 [允许的结果状态 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L43 "支持状态字段仅允许五个枚举值，同时表明该范围没有定义各状态的语义或转换关系。")

结果还记录模型、生成时间、布尔型 `seed` 标记、是否经代理复核以及复核者；提示词、Schema 和输入摘要必须是 64 位小写十六进制字符串，可用于识别生成条件。摘要能够辅助追溯输入身份，但不证明结果正确。参考 [生成与复核追溯字段 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L58 "支持模型、摘要、生成时间、种子标记及代理复核信息的字段类型和摘要格式约束。")

<a id="evidence_limits"></a>
## 证据表达与合同边界

结果可关联节点和边，列出证据引用与未知项，并用 0 到 1 的数值表达置信度。这为架构判断回指代码结构、显式保留不确定内容提供了统一接口。参考 [证据、未知项与置信度 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L52 "支持结果关联节点、边和证据，并记录未知项及限定在零到一之间的置信度。")

合同对部分字段的约束仍较宽松：`key_flows`、`claims` 和 `evidence_refs` 仅要求为数组，没有规定数组元素结构；`generated_at` 也只要求字符串。流程步骤、论断、证据定位及时间格式能否稳定互操作，还需要结合其他 Schema 或实际生产、消费逻辑确认。参考 [宽松的数组与时间约束 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L48 "支持关键流程、论断和证据引用仅被限定为数组；结合生成时间的字符串定义，说明当前合同未规定这些内容的细化格式。")
