# 模块理解输出合同 CodeUnderstanding.v1

定义模块理解结果的顶层必填字段、角色与状态枚举、基础字段类型、摘要封印格式及不可附加属性规则；部分核心数组缺少元素级结构，因此仅凭该片段无法确认声明与证据的完整交叉引用约束。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="top_level_contract"></a>
## 顶层结构与必填信息

该合同采用 JSON Schema 2020-12，标识为 `CodeUnderstanding.v1`，要求结果是对象且禁止未声明的顶层属性。[Schema 标识与对象边界 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L1 "支持所用 JSON Schema 版本、合同标识、对象类型及禁止额外顶层属性的说明。") 必填项覆盖结果身份、角色和状态，以及模块职责、边界、关键流程、入口、出口、风险限制、声明、节点和边引用、证据、不确定项、置信度、模型信息、三个摘要、生成时间、种子和验证标志。[完整必填字段清单 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L6 "支持合同同时要求架构内容、引用追踪和生成封印字段的论断。") 这说明输出兼顾架构内容、证据追踪和生成封印。

<a id="states_content"></a>
## 状态、内容与角色范围

`role` 只能是仓库画像、模块架构、符号解释或关系核验四类，`status` 则区分种子、已生成、已验证、失败和已拒绝。[角色与状态枚举 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L35 "支持四种角色类型和五种结果生命周期状态的说明。") 多个架构字段被约束为数组，入口、出口、风险和未知项要求字符串元素；但 `key_flows`、`claims` 与 `evidence_refs` 仅声明为数组，没有在当前合同中限定元素结构。[架构数组字段约束 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L46 "支持部分数组有字符串元素约束，而关键流程、声明和证据数组缺少元素级定义的判断。") 因此该 Schema 能检查部分外形，却不足以单独证明每条声明都拥有合法证据引用。

<a id="seal_validation"></a>
## 封印字段与基础校验

置信度被限制在 0 到 1，模型允许字符串或空值；提示、Schema 和输入摘要都必须是 64 位小写十六进制字符串。[置信度与摘要格式 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L57 "支持置信度范围、可空模型及三个摘要的十六进制格式要求。") `seed` 与 `verified_by_agent` 是布尔值，`verified_by` 可为字符串或空值。[生成与验证字段 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L62 "支持生成时间、种子标志及验证者字段的基础类型说明。") 这些约束能表达生成来源和验证状态，但 `generated_at` 只是普通字符串，Schema 未要求 ISO 时间格式；同时也未在所给内容中建立状态、种子标志和验证字段之间的条件关系。
