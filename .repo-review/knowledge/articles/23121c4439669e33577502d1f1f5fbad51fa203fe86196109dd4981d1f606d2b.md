# ACP Provider 识别与开发运行安全收口

该模块把通用 AgentProfile 转换为可安全用于 ACP 会话和后台开发的 provider 策略：兼容识别 TraeX、Claude 与 Codex，生成隔离的会话元数据，验证并冻结编码/评审角色身份，并在执行前规范化启动参数或拒绝尚未验证的组合。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="identity"></a>
## 把启动命令归一为稳定的 Provider 身份

这个模块解决的是“同一种 ACP 实现可能由显式包装器或旧命令名启动”的兼容问题。`acpProvider` 先排除非 ACP profile，再优先采用 `acpProvider` 显式声明；未声明时只取命令 basename、去掉 Windows 的 `.exe`，将 `traex/traecli`、`codex-acp`、`claude-agent-acp` 映射为稳定身份，其他命令返回 `null`。因此调用方不必反复猜测可执行文件名，同时包装器可以显式保留真实 provider 身份。参考 [Provider 身份识别 ↗](../../../apps/server/src/agent-providers.ts#L4 "支持显式身份优先、旧命令名兼容及未知命令返回 null 的说明。")

`AgentProfile` 的契约本身将显式身份限定为 `traex`、`codex`、`claude`，并把传输方式、命令、参数、模型和思考强度放在同一配置对象中；本模块是在该通用契约之上增加运行策略，而不是另造配置格式。参考 [Agent Profile 契约 ↗](../../../packages/contracts/src/index.ts#L170 "说明 provider 枚举以及 transport、command、args、model、effort 等输入字段。")

<a id="development-flow"></a>
## 从角色选择到可执行 Profile

开发配置先分别按 ID 选择编码与评审 profile；若没有独立开发配置，则两种角色沿用助手 profile。被选对象必须存在且使用 ACP。参考 [开发角色配置选择 ↗](../../../apps/server/src/config.ts#L137 "支持编码与评审角色独立选择、助手 profile 回退及 ACP 校验。") 随后 `freezeDevelopmentProfiles` 对两者调用 `developmentProfile` 做前置校验，并用 `structuredClone` 保存各自原始身份快照；评审 profile 省略时默认复用编码 profile，不会为了适配角色而改名。参考 [角色 Profile 冻结 ↗](../../../apps/server/src/agent-providers.ts#L77 "支持前置验证、评审默认值、保持真实身份及结构化克隆快照的说明。")

代表性调用中，假设编码 profile 是 TraeX，参数含 `--yolo -c sandbox_mode="danger-full-access" acp serve`。冻结阶段只验证和复制；开发任务执行时再从快照生成有效 profile：删除 `--yolo`，删除已有的 `-c/--config + sandbox_mode=...` 参数对，并在最前面注入 `-c sandbox_mode="read-only"`，其他参数与 profile ID 保持不变。参考 [开发 Profile 安全规范化 ↗](../../../apps/server/src/agent-providers.ts#L43 "支持 TraeX 参数清洗与只读注入，以及 Claude、Codex、未知 provider 的拒绝边界。") 执行器会保存冻结快照、分别生成编码和评审有效 profile，再按 `coding-agent` 或评审角色把对应 profile 交给运行时网关，所以输出是“身份稳定、启动权限已收口”的会话配置。参考 [执行前生成有效 Profile ↗](../../../apps/server/src/development/runner.ts#L304 "证明执行器先保存冻结快照，再为编码和评审分别调用 developmentProfile。") [角色绑定到运行时网关 ↗](../../../apps/server/src/development/runner.ts#L419 "证明有效 profile 按编码或评审角色传入 RoleRuntimeGateway。")

<a id="provider-guards"></a>
## 按 Provider 收紧会话能力与失败边界

不同 provider 的边界是显式的：Claude 开发 profile 不允许携带启动参数；TraeX 返回一个注入只读沙箱的新对象；Codex 目前只允许能力探测，不能进入后台编码；非 ACP 或无法识别的自定义 provider 也会直接报错。参考 [开发 Profile 安全规范化 ↗](../../../apps/server/src/agent-providers.ts#L43 "支持 TraeX 参数清洗与只读注入，以及 Claude、Codex、未知 provider 的拒绝边界。")

会话元数据同样按身份分流。Claude 禁用原生工具与配置来源，只放行 `mcp__omem__*`，启用严格 MCP 配置、禁用 hooks，且不允许跳过权限；Codex 返回空元数据；兼容分支保留旧 Trae 元数据结构，但清空外部 MCP server。参考 [Provider 会话隔离元数据 ↗](../../../apps/server/src/agent-providers.ts#L15 "支持 Claude、Codex 与兼容 Trae 分支生成不同会话元数据的说明。") ACP 会话创建时，运行器把该结果写入 `newSession._meta`；它还会校验 Claude adapter 版本，并为 Claude/Codex 选择预期权限模式，说明这里生成的策略最终作用于真实会话，而非仅供展示。参考 [ACP 会话消费策略 ↗](../../../apps/server/src/agents.ts#L307 "证明 sessionMetadata 被传给真实 newSession，并说明 Claude adapter 校验和权限模式协商。")

需要注意：`sessionMetadata` 的默认分支本身不会拒绝未知 provider，真正用于后台开发时由 `developmentProfile` 负责 fail-closed；普通 ACP 会话是否可用则由更上层调用场景决定。
