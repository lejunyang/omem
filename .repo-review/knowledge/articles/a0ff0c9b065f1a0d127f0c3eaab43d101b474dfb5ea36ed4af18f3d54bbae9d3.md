# 仓库评审存储、迁移与关系视图

该模块在通用单用户 SQLite Store 之上建立隔离的 repo-review 运行时，维护稳定文件身份及删除、移动、迁移元数据，并将人工种子关系持久化为可双向查询、可识别缺失与历史失效状态的证据链。旧结论中关于播种失败清理、迁移标记和空端关系失效的过宽描述已被更精确的边界替代。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="runtime-isolation"></a>
## 隔离运行时与稳定来源身份

模块把仓库评审数据放在 `.repo-review/runtime/data`，与个人工作区数据库分离；来源使用 `omem:<仓库相对路径>` 作为稳定身份，使文件修改继续累积 revision，同时避免相同内容的不同文件被合并。默认启动直接创建隔离 Store，只有显式设置 `REVIEW_IMPORT_LEGACY=1` 才从旧快照播种。[评审运行时目录与显式旧数据导入 ↗](../../../apps/server/src/review/store.ts#L17 "支持隔离数据目录、稳定路径身份以及仅在显式环境开关下播种旧快照的论断。")

播种先复制旧 SQLite、WAL 和 SHM 到临时目录，再通过 `VACUUM INTO` 生成一致数据库快照。旧稿所称“失败会删除不完整目标”现限定为：一致快照生成抛错时删除目标数据库并保留旧快照；随后同步状态或 assets 的复制失败并没有同等的整体清理保证。[一致快照生成与局部失败清理 ↗](../../../apps/server/src/review/store.ts#L67 "精确限定只有 VACUUM INTO 抛错时删除目标数据库，并显示后续状态和资产复制不在该 catch 清理范围内。") 底层仍复用通用 `Store`，负责建目录、打开 SQLite、执行迁移并初始化资产目录和仓储服务，因此此处是隔离配置与评审扩展，而非独立事实库。[通用 Store 初始化 ↗](../../../apps/server/src/store.ts#L38 "说明评审运行时复用通用 SQLite Store 的迁移、资产目录和仓储初始化能力。")

<a id="source-migration"></a>
## 来源元数据与旧身份迁移

共享 Store 未表达的删除、移动、迁移和旧别名状态存入 `review_source_meta` 边表；元数据采用默认值与幂等 upsert，检索可取得已删除来源集合以排除失效证据。[评审来源元数据 ↗](../../../apps/server/src/review/store.ts#L115 "支持删除、移动、迁移、旧别名字段及其幂等读写和删除来源查询。")

旧内容哈希来源迁移会从最新 revision 的上下文恢复 `filePath` 并按路径分组：没有现存路径来源时，选择版本及创建时间最新的一行改为稳定路径身份，其余行降级为保留 revision/fragment 的历史别名；已有路径来源时，所有旧行都降级。无法解析正文或缺少路径的行被保留而不迁移。[旧来源按路径归并 ↗](../../../apps/server/src/review/store.ts#L282 "支持从最新 revision 提取路径、选择当前来源、降级历史别名并跳过无路径行的迁移流程。") 迁移标记只提供快速跳过：若标记存在但数据库仍有非 `omem:` 且带 live head 的来源，系统会视为疑似未完成迁移并重新扫描；仅在这类来源为零时直接返回。[迁移标记的重新扫描例外 ↗](../../../apps/server/src/review/store.ts#L269 "支持标记存在时仍检查带 live head 的旧身份，并仅在不存在疑似未完成迁移时快速返回。")

<a id="relation-lifecycle"></a>
## 关系写入、查询与失效边界

评审关系保存六类前向边，并从种子身份生成确定性 ID 后 upsert，使重复同步保持幂等；反向关系名仅在读取时派生。种子删除可将不再存在的边改为 stale，但当前有效 association 集合为空时函数直接返回，因此尚不能从此处确认“权威清空”是否会失效全部旧边。[关系幂等写入与移除种子失效 ↗](../../../apps/server/src/review/store.ts#L430 "支持确定性关系身份、upsert 以及有效 association 集合为空时不执行旧边失效的当前边界。")

片段查询以 LEFT JOIN 保留未解析关系，并区分存储状态与有效展示状态：若已解析的另一端不再位于当前 head 或来源已删除，有效状态强制为 stale；默认隐藏 stale，而 `other: null` 的 missing 边仍可见。[片段关系的有效状态与默认过滤 ↗](../../../apps/server/src/review/store.ts#L506 "支持双向关系视图、另一端当前性检查、missing 空端保留及默认隐藏 stale 的行为。") 代码路径查询进一步从当前代码片段沿 `implements` 展开到意图，再汇集需求、决策、研究和测试边；历史与 stale 是否出现由选项控制。[代码路径证据链查询 ↗](../../../apps/server/src/review/store.ts#L680 "支持从代码到意图再到需求、决策、研究和测试的一次查询，以及历史和 stale 过滤选项。")

同步前失效处理会检查关系两端：空端本身不会因为“无法解析”而触发 stale；但若该关系属于本次来源的已解析一端已不是当前 head，或另一已解析端失效、被删除，整条关系仍会标为 stale。这替代了旧稿“空端 missing 关系一律保留”的过宽结论。[关系两端的陈旧失效规则 ↗](../../../apps/server/src/review/store.ts#L753 "精确说明空端本身不触发失效，但本来源端或另一已解析端失效时关系仍会被标记 stale。") 汇总接口目前把 confirmed、candidate 单列，其余状态统一计入 missing，因此 stale 也会落入 missing 桶。[关系状态汇总 ↗](../../../apps/server/src/review/store.ts#L847 "支持汇总只单列 confirmed 与 candidate、并将包括 stale 在内的其他状态计入 missing 的当前实现。")
