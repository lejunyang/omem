# Repo-review 隔离存储与关系索引

在共享 Store 之上建立隔离的评审运行库，维护路径稳定身份、遗留数据迁移，以及代码到需求、决策、研究和测试的可追溯关系。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="isolation-migration"></a>
## 隔离运行库与身份迁移

repo-review 将数据库和资产放在 `.repo-review/runtime/data`，与个人工作区分离，但继续复用通用 `Store` 的 SQLite、捕获和事务基础。默认启动直接使用运行库；只有 `REVIEW_IMPORT_LEGACY=1` 时才调用旧快照播种，因此历史 `.repo-review/data` 不是日常启动依赖。[评审运行库创建入口 ↗](../../../apps/server/src/review/store.ts#L100 "直接支持默认使用隔离运行库，并且仅在显式环境开关开启时导入遗留历史。")[通用 SQLite Store ↗](../../../apps/server/src/store.ts#L1 "证明评审存储复用单用户 SQLite Store、数据库迁移、资产目录和事务能力。")

评审文件以 `omem:<仓库相对路径>` 作为稳定外部身份，使内容更新形成同一 source 的新 revision，而相同字节的不同路径保持独立。遗留内容哈希源迁移会按最新 revision 记录的路径分组，保留或选择当前路径源，并将其他旧行摘除 head、登记为历史别名；revision 和 fragment 不被删除。[遗留源路径身份迁移 ↗](../../../apps/server/src/review/store.ts#L229 "支持按最新 revision 的文件路径分组、选择当前源、保留 revision 与 fragment 并记录历史别名的迁移流程。")

<a id="relations"></a>
## 关系写入与双向读取

关系表保存 `implements`、`requires`、`decided_by`、`researched_by`、`tested_by` 与 `candidate_for` 等前向边，反向展示名在查询时派生。边 ID 由 seed identity 确定，重复同步通过 upsert 更新同一行。若有效 association ID 集合非空，已不在集合中的旧 seed 边会被标记 stale；集合为空时函数直接返回，不能把“全部旧边失效”视为已实现。[确定性关系写入与 seed 移除处理 ↗](../../../apps/server/src/review/store.ts#L367 "支持关系类型、确定性 ID、幂等 upsert，并明确有效 ID 集合为空时不会执行旧 seed 失效。")

读取 fragment 时合并出边和入边，并以左连接保留 unresolved 的 missing 关系。若另一端不再属于 source head 或已被移除，有效展示状态会变为 stale；默认隐藏 stale，历史查询可显式包含。按代码路径的查询还会展开“代码 → intent → 需求、决策、研究、测试”链。[关系视图与路径链查询 ↗](../../../apps/server/src/review/store.ts#L506 "支持双向关系读取、missing 保留、有效 stale 判定、默认过滤和代码路径链式展开。")

<a id="lifecycle-limits"></a>
## 生命周期与汇总限制

同步可按 source 检查关系两端是否仍位于当前 head、对端 source 是否已移除，并把失效关系改为 stale，而不是删除历史行；空字符串表示的未解析端点会被保留。[关系生命周期失效检查 ↗](../../../apps/server/src/review/store.ts#L753 "说明 source head 变化、删除和两端存活检查如何将旧关系标为 stale，同时保留未解析空端点。")

当前状态类型包含 stale，但关系汇总只公开 confirmed、candidate、missing 三个桶，循环会把 stale 与其他非前两类状态计入 missing。这会混淆“目标无法解析”和“历史关系已失效”，属于仍需确认或修正的展示语义。[关系状态汇总 ↗](../../../apps/server/src/review/store.ts#L847 "证明汇总 DTO 未单列 stale，且实现会把 confirmed、candidate 之外的状态累计到 missing。")
