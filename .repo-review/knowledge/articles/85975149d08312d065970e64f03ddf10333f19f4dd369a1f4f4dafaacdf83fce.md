# 反馈修正提案输出合同

该文件定义 CorrectionProposal.v1 的 JSON Schema 外层合同，用于约束反馈整理角色输出修正标识、作用目标与范围、停用内容、替代内容、证据、理由和来源。它能保证顶层字段齐备且禁止额外属性，但对多个嵌套对象及多数文本字段仅作基础类型声明，不能据此确认运行时已完成语义校验、证据核验或修正应用。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="contract-purpose"></a>
## 合同定位与输出边界

该材料声明一个基于 JSON Schema 2020-12 的 `CorrectionProposal.v1` 对象合同，并禁止未声明的顶层属性，说明其用途是稳定反馈整理角色与宿主之间的修正提案结构，而不是描述修正如何执行。[合同标识与顶层约束 ↗](../../../packages/agent-runtime/roles/feedback-curator/1/output.schema.json#L1 "支持附近关于 Schema 版本、CorrectionProposal.v1 标识、对象类型及禁止额外顶层属性的说明。") 文件本身只提供数据格式；是否有运行时加载、校验、持久化或应用该提案，不能由这份 Schema 单独证明。

<a id="proposal-flow"></a>
## 修正提案的表达流程

提案必须同时给出修正标识、目标、范围、应停止使用的内容、替代内容、证据、理由和来源。[修正提案必填字段 ↗](../../../packages/agent-runtime/roles/feedback-curator/1/output.schema.json#L6 "支持附近对提案信息链及全部必填组成部分的概括。") 这一组合表达了一条清晰的信息链：先定位受影响对象和边界，再陈述旧内容与替代内容，最后用证据、理由及来源支撑变更。它适合承载“建议如何纠正”的结构化结果，但队列入列、审核通过或实际覆盖旧知识仍属于合同之外的后续状态。

<a id="validation-limits"></a>
## 当前校验强度与限制

字段级约束目前较宽：`correction_id`、`stop_using`、`replacement` 和 `reason` 只要求字符串，未规定非空、长度或格式；`target`、`scope`、`origin` 仅要求对象，未定义内部必填键。[目标与文本字段类型 ↗](../../../packages/agent-runtime/roles/feedback-curator/1/output.schema.json#L18 "支持附近关于对象内部未展开、多个文本字段仅受基础字符串类型约束的判断。") `evidence` 至少包含一项，但数组元素的结构、引用目标和支持关系也未在此处限定。[证据、理由与来源字段 ↗](../../../packages/agent-runtime/roles/feedback-curator/1/output.schema.json#L24 "支持附近关于证据数组只有最小数量约束，以及理由和来源仅有基础类型声明的说明。") 因此该合同能拦截缺失顶层字段和额外顶层字段，却不足以独立保证修正可定位、证据可追溯或替换内容具备语义有效性。
