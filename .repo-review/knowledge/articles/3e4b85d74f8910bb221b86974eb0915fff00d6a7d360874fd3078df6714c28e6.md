# 仓库画像输出合同

仓库画像使用 CodeUnderstanding.v1 的共享顶层结构，必须描述职责、边界、流程、入口出口、风险、声明、图引用和证据追踪信息。该文件约束基础类型、状态和摘要格式，但复杂数组没有元素级定义；额外合同是否存在是非阻塞的后续调查项。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="shared_contract"></a>
## 共享理解结果结构

Schema 禁止未声明的顶层字段，并把模块职责、边界、流程、入口出口、风险限制、claims、节点与边引用、证据、未知项及生成追踪字段列为必填。[仓库画像必填信息 ↗](../../../packages/agent-runtime/roles/repo-profiler/1/output.schema.json#L4 "支持结果必须覆盖职责、边界、流程、风险、图引用、证据和追踪元数据。") `role` 同时允许仓库画像、模块架构、符号解释与关系核验，`status` 覆盖 seed、generated、verified、failed、rejected，说明仓库画像进入统一的代码理解结果生命周期。[共享角色与状态枚举 ↗](../../../packages/agent-runtime/roles/repo-profiler/1/output.schema.json#L35 "支持该结果合同供四种角色共享，并表达五类生命周期状态。")

<a id="traceability_limits"></a>
## 可追溯约束与结构空白

置信度限定在 0 至 1，prompt、schema 与 input 摘要必须是 64 位小写十六进制字符串，合同还记录模型、生成时间、seed 和外层验证字段。[画像结果追踪字段 ↗](../../../packages/agent-runtime/roles/repo-profiler/1/output.schema.json#L57 "支持置信度范围、摘要格式、模型及验证元数据的结构要求。") 然而 `key_flows`、`claims` 与 `evidence_refs` 仅被声明为数组，没有元素形状；所以仅通过此 Schema 不能证明流程步骤、声明类型及证据关系可被完整解析。[复杂数组的宽松约束 ↗](../../../packages/agent-runtime/roles/repo-profiler/1/output.schema.json#L46 "支持流程、声明与证据引用缺乏元素级定义这一合同限制。") 此限制已可由当前文件确认；此前把额外元素合同的缺失视为阻塞项的结论已被替代。
