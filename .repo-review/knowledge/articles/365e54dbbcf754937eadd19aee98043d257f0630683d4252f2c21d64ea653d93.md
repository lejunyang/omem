# SQLite 写锁下的知识捕获回归测试

该测试使用独立子进程制造真实的 SQLite 写锁，验证主进程在锁存在后开始重新初始化存储，并在初始化返回后仍能完成文本捕获。它覆盖从并发锁、存储初始化到捕获成功的端到端场景，但不直接证明捕获写语句本身与锁竞争，也未说明具体等待和超时策略。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 验证真实进程竞争下的端到端结果

这个回归测试关注单用户 SQLite 存储中的实际并发场景：另一个进程持有写锁时，主进程重新接入数据库并执行后续知识捕获，最终不应丢失固定材料。用例先创建临时数据库，再启动独立 Node 子进程，通过 `BEGIN IMMEDIATE` 取得写锁；子进程发出 `ready` 后延时提交，因此这里使用的是真实进程间锁，而非模拟错误。参考 [真实写锁建立过程 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L9 "支持独立子进程通过即时事务取得 SQLite 写锁、发出就绪信号并延时提交的场景说明。")

<a id="flow"></a>
## 从写锁建立到捕获成功

主进程收到 `ready` 后才开始构造新的 `Store`。构造过程同步打开同一 SQLite 文件、执行数据库迁移，并初始化应用、任务、输入、运行请求和来源配置等组件；材料没有表明构造何时返回，因此不能断言随后的捕获操作发生在子进程仍持锁期间。参考 [存储同步初始化流程 ↗](../../../apps/server/src/store.ts#L51 "说明 Store 构造时打开数据库、执行迁移并初始化运行组件，支持初始化在收到就绪信号后开始且捕获需等待构造返回的论断。")

只有 `Store` 构造返回后，用例才实例化 `KnowledgeRepository` 并调用 `store.capture`。成功标准是捕获结果中的首个片段完整保留输入文本，同时持锁子进程以退出码 0 正常结束。由此验证的是“并发锁已经存在时开始重新初始化，随后仍可完成捕获”的端到端行为，而不是直接证明捕获写语句自身等待了该锁。参考 [捕获与退出断言 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L17 "支持 Store 构造返回后才执行捕获，并以片段文本和子进程退出码作为端到端成功标准。")

<a id="boundaries"></a>
## 能够证明与尚未覆盖的边界

该测试覆盖一次约 250 毫秒写锁、一次存储重开和一次手工文本捕获，没有测量初始化或捕获分别等待了多久，也没有断言等待上限、超时错误、长期持锁、多个写入者或失败重试语义。`KnowledgeRepository` 只被构造而未调用方法，因此现有材料也不足以证明它是场景成立的必要条件。参考 [真实写锁建立过程 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L9 "支持独立子进程通过即时事务取得 SQLite 写锁、发出就绪信号并延时提交的场景说明。") [捕获与退出断言 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L17 "支持 Store 构造返回后才执行捕获，并以片段文本和子进程退出码作为端到端成功标准。")

无论用例成功还是失败，清理逻辑都会终止仍存活的子进程、关闭存储并删除临时目录，避免并发测试留下数据库或进程资源。参考 [并发测试资源清理 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L21 "支持用例最终终止残留子进程、关闭存储并删除临时目录的说明。")
