# SQLite 短暂写锁期间的 Store 初始化与捕获测试

该测试让独立子进程持有约 250 毫秒的 SQLite 写锁，并在持锁期间开始创建 Store，随后执行一次 manual capture；断言捕获返回的首个片段文本正确且子进程正常退出。现有时序不能确定等待发生在 Store 初始化还是 capture，因此它不单独证明 capture 本身的锁等待行为。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 测试目的与真实存储背景

用例在临时目录中先创建并关闭一个 `Store`，以生成后续父子进程共同访问的实际 `omem.sqlite` 文件。[临时数据库初始化 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L9 "支持用例在临时目录创建并关闭初始 Store，使父子进程随后访问同一文件数据库。") `Store` 构造过程会创建目录、打开数据库、执行迁移，并初始化应用、任务、输入、运行请求和来源配置等组件，因此测试覆盖的是真实启动路径，而非内存数据库或伪造仓储。[Store 的数据库启动流程 ↗](../../../apps/server/src/store.ts#L38 "支持 Store 构造会打开 omem.sqlite、执行迁移并初始化多个应用组件，说明等待点可能位于初始化阶段。")

<a id="flow"></a>
## 写锁、初始化与捕获流程

子进程对同一数据库执行 `BEGIN IMMEDIATE`，发出 `ready` 后约 250 毫秒提交并关闭连接。父进程收到信号时写锁已经存在，随后才执行 `new Store(dir)`、构造 `KnowledgeRepository` 并调用一次 manual capture。[并发写锁与调用顺序 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L13 "支持子进程取得写锁后，父进程依次创建 Store、构造知识仓储并执行 capture，同时表明代码缺少更细粒度时序观测。") 因为 `Store` 构造本身包含打开数据库和迁移，现有代码没有记录构造完成、进入 capture 与锁释放的先后关系；所以被替代的旧结论“capture 在锁释放前已经开始等待”证据不足。可确认的结论仅是：持锁期间开始 Store 初始化，之后 capture 成功返回。

<a id="assertions"></a>
## 断言范围与覆盖边界

测试断言返回 revision 的首个 fragment 文本等于输入文本，并等待持锁子进程以退出码 0 结束。[捕获结果与子进程断言 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L18 "支持测试直接验证的两项结果：首个片段文本正确，以及持锁子进程正常退出。") 它没有重启 Store 后查询持久化结果，也未验证标题、来源、上下文、其他片段、长时间锁定、回滚或多个竞争写者；清理阶段会终止残留子进程、关闭 Store 并删除临时目录。[单次操作与资源清理 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L15 "支持该用例仅执行一次捕获，并在 finally 中关闭或清理子进程、Store 和临时目录。")

提供的知识仓储代码展示了原始 revision 到知识材料的转换，以及对文档结构、内联引用、目标材料和引用行范围的校验；这些职责不能证明 `KnowledgeRepository` 构造会影响本测试的锁等待。[知识材料转换与引用校验 ↗](../../../apps/server/src/knowledge/repository.ts#L11 "支持知识仓储在所给范围内负责材料转换和知识文档引用校验，但未展示构造器或锁等待配置。") 同样，现有材料没有给出 SQLite busy timeout、重试次数或超时错误转换策略。
