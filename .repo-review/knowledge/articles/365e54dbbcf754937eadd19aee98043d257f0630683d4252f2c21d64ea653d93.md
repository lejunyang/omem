# 知识写入并发等待测试

该测试以子进程持有 SQLite 写事务，验证 Store.capture 面对短暂跨进程写锁时能够等待并完成捕获，同时检查写入结果、锁持有方退出状态及资源清理。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 测试目的与存储背景

该用例制造真实的 SQLite 跨进程写竞争，用于确认知识捕获遇到短暂写锁时会等待锁释放，而不会立即失败或静默丢失操作。子进程对同一数据库执行 `BEGIN IMMEDIATE`，发出就绪信号后约 250 毫秒提交，因此竞争来自实际数据库事务而非 mock。[跨进程写锁的建立与时序 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L9 "支持临时目录、初始 Store、子进程 BEGIN IMMEDIATE、延迟提交及退出监听共同构成真实并发场景的论断。") `Store` 当前以 SQLite 作为单用户存储基础；团队级约束仍属于后续迁移范围。[SQLite 单用户存储定位 ↗](../../../apps/server/src/store.ts#L2 "支持 Store 当前采用 SQLite 单用户基础、团队级 enforcement 尚待迁移的背景说明。")

<a id="flow"></a>
## 执行流程与初始化边界

测试先创建临时目录并构造、关闭一次 `Store`，随后启动子进程占有写事务，并等待其标准输出后再进行主进程写入，保证锁竞争的先后关系。[跨进程写锁的建立与时序 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L9 "支持临时目录、初始 Store、子进程 BEGIN IMMEDIATE、延迟提交及退出监听共同构成真实并发场景的论断。") `Store` 构造函数负责创建数据目录和数据库、执行迁移，并初始化应用、任务、输入、运行请求及来源配置等仓储；这替代了先前仅凭文件说明笼统推断其初始化职责的结论。[Store 构造与仓储初始化 ↗](../../../apps/server/src/store.ts#L43 "支持 Store 创建数据库、执行迁移并初始化多个应用仓储的具体职责，修正此前引用范围不足的结论。") 主进程再构造 `Store`、实例化 `KnowledgeRepository`，并调用 `store.capture` 写入固定文本。[捕获调用与结果断言 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L17 "支持主进程初始化、调用 Store.capture、检查 fragment 文本及等待子进程正常退出的流程和结果。")

<a id="assertions_limits"></a>
## 断言、清理与覆盖限制

用例断言返回 revision 的首个 fragment 保留完整文本，并等待子进程以退出码 0 结束，证明该次短锁竞争下捕获成功且持锁事务正常提交。[捕获调用与结果断言 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L17 "支持主进程初始化、调用 Store.capture、检查 fragment 文本及等待子进程正常退出的流程和结果。") `finally` 会终止仍存活的子进程、关闭数据库连接并删除临时目录，覆盖成功和异常路径的资源回收。[并发测试资源清理 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L21 "支持无论测试成功或异常都清理子进程、数据库连接和临时目录的边界说明。") 但它只覆盖一次约 250 毫秒的单写者竞争，未验证更长等待、多写者、公平性、回滚、进程崩溃或重新连接后的读取；现有材料也不足以确认未调用方法的 `KnowledgeRepository` 实例是否具有必要副作用。
