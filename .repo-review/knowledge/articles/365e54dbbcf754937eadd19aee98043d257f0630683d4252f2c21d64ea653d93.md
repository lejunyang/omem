# 知识捕获的 SQLite 写锁竞争测试

该测试证明：子进程取得 SQLite 写锁后，主进程启动 Store 初始化及后续捕获流程，最终仍返回完整片段，且竞争事务正常退出。它是端到端成功场景，但现有观测不能确认 capture 调用本身与写锁直接重叠，也不能定位等待发生在迁移、初始化还是捕获写入阶段。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 测试目的与真实数据库背景

该用例关注知识捕获遇到真实 SQLite 写竞争时是否最终成功，而不是仅验证协议桩。它先在临时目录创建并关闭一次 `Store`，使后续子进程与主进程共享同一数据库文件。[临时数据库准备 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L9 "支持测试先创建临时目录并初始化、关闭 Store，使两个进程随后操作同一数据库文件。") `Store` 构造会打开 `omem.sqlite`、执行迁移并初始化多个仓库服务，因此重新构造 Store 本身也是被测端到端流程的一部分。[Store 初始化流程 ↗](../../../apps/server/src/store.ts#L45 "说明 Store 构造包含打开 SQLite、执行迁移及初始化服务，支持初始化阶段本身可能受到写锁影响的限制判断。")

<a id="flow"></a>
## 竞争时序与被替代结论

子进程执行 `BEGIN IMMEDIATE`，发出 `ready` 后约 250 毫秒提交；主进程收到信号后才开始重新构造 `Store`，随后实例化 `KnowledgeRepository` 并调用 `store.capture`。[写锁与主流程时序 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L13 "支持子进程先取得写锁并发出 ready，主进程随后构造 Store、实例化仓库并执行捕获的实际时序。") 因而原先“竞争者持锁后主进程直接发起捕获”的结论应被替代为：**竞争者持锁后，主进程开始 Store 初始化及后续捕获流程，最终捕获成功**。由于构造阶段会执行迁移和服务初始化，材料无法证明写锁一直保持到 `capture` 真正开始，也无法判断等待具体发生在哪一步。[Store 初始化流程 ↗](../../../apps/server/src/store.ts#L45 "说明 Store 构造包含打开 SQLite、执行迁移及初始化服务，支持初始化阶段本身可能受到写锁影响的限制判断。")

<a id="coverage"></a>
## 断言、清理与覆盖边界

测试只直接断言返回 revision 的首个 fragment 保留完整输入文本，并确认子进程以退出码 0 结束；这支持端到端流程未丢失本次材料，但不等同于证明 capture 写事务自身发生过锁等待。[捕获结果与进程退出断言 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L18 "支持最终片段文本完整且竞争子进程正常退出，但不提供等待发生阶段的观测。") `finally` 会终止残留子进程、关闭 Store 并删除临时目录，覆盖成功与失败路径的资源清理。[并发测试资源清理 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L20 "支持测试在 finally 中处理残留子进程、数据库连接和临时目录。") 此外，`KnowledgeRepository` 在测试中仅被实例化，后续操作仍直接调用 `Store.capture`；给出的仓库实现片段展示材料读取与缓存逻辑，不能据此确认它参与锁等待。[KnowledgeRepository 的材料读取逻辑 ↗](../../../apps/server/src/knowledge/repository.ts#L8 "所给实现片段展示材料缓存、revision 转换和当前材料查询，结合测试调用可说明目前没有证据证明该实例参与锁等待或 capture。")

<a id="limits"></a>
## 尚未验证的机制

现有场景只有一个竞争者、一次捕获和约 250 毫秒持锁时间，未观测 Store 构造完成时刻、capture 开始时刻或 SQLite 等待配置。因此它没有覆盖锁长期不释放、超时阈值、多写者公平性，也没有区分迁移等待、初始化等待与捕获事务等待。要把结论收紧到 capture 与写锁直接重叠，需要增加锁状态和阶段时序断言。[写锁与主流程时序 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L13 "支持子进程先取得写锁并发出 ready，主进程随后构造 Store、实例化仓库并执行捕获的实际时序。")
