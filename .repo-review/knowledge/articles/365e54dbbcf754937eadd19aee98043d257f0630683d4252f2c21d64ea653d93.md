# 知识存储的 SQLite 并发写事务测试

通过子进程建立真实 SQLite 写事务，验证父进程随后完成存储初始化、知识仓库创建和材料捕获且数据未丢失；测试未单独证明捕获调用本身等待锁释放。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="lock-fixture"></a>
## 真实并发事务场景

测试先创建并关闭初始存储，再启动独立 Node 子进程，对同一数据库执行 `BEGIN IMMEDIATE`；子进程发出就绪信号后延迟约 250 毫秒提交。[并发写事务测试装置 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L9 "支持初始数据库创建、独立进程开启真实写事务，以及父进程等待就绪信号后继续操作的场景。") 父进程收到信号后才依次创建 `Store`、`KnowledgeRepository` 并执行捕获，因此测试确实覆盖了并发写事务已经出现后的完整操作序列。

<a id="observed-result"></a>
## 最终行为与可证明边界

测试断言捕获结果中的片段文本与输入一致，并确认持锁子进程正常退出；这证明在该并发场景下，存储初始化及随后捕获最终成功，材料没有静默丢失。[捕获结果与进程退出断言 ↗](../../../apps/server/tests/knowledge-concurrency.test.ts#L18 "支持材料捕获最终返回完整文本且持锁子进程正常退出，同时显示测试没有记录捕获开始时的锁状态或等待时长。") 但代码没有断言执行 `store.capture` 时写锁仍然存在，也未测量捕获耗时，因此此前“锁持有期间发起捕获”及“捕获会等待锁释放”的结论被替代。可能发生等待的位置还包括 `Store` 或知识仓库初始化，现有测试无法进一步区分。
