# 问题背景、研究取舍与历史演进

omem 从可追溯知识原型出发，逐步形成统一证据内核、渐进记忆与主助手方向。工程底座已有历史实现，但入口、上下文保真、知识一致性及代码知识能力仍需按当前版本继续验证。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="problem-origin"></a>
## 问题起点：记忆必须能够回到原件

omem 要解决的不是单纯“存下更多内容”，而是让知识、回答和行动能够回到固定版本的原始依据。早期离线原型已演示递归引用、版本比较、局部追问、异常来源和焦点恢复等交互，[离线原型的交互范围 ↗](../../../docs/prototype/README.md#L5 "支持早期原型已经覆盖递归引用、追问、版本、异常来源和响应式阅读等交互。") 但它未连接真实数据、LLM、数据库或后台任务，因此只能验证阅读方式，不能证明生产能力。[离线原型的能力边界 ↗](../../../docs/prototype/README.md#L18 "支持原型未接入真实模型、数据、数据库和后台任务，不能作为生产能力证明。") 研究由此提出“统一证据与记忆内核 + 可替换检索/学习引擎”：版本化引用、知识变更、自治风险和验证留在 omem，外围检索组件则通过统一验收后替换。[统一内核与可替换引擎 ↗](../../../docs/research.md#L9 "支持 omem 自持证据治理和自治边界、外围检索与学习引擎可替换的研究取舍。")

<a id="historical-shift"></a>
## 从批量提炼转向渐进记忆

Batch 2 曾把系统拆为迁移、持久任务、角色运行时、提炼应用、飞书、投递回调、Vue 流程和集成回归等切片，并要求每个切片形成可运行闭环。[Batch 2 工程切片 ↗](../../../docs/implementation/batch2/README.md#L20 "解释 Batch 2 的模块拆分、依赖关系以及必须形成可运行闭环的交付要求。") 随后的专项审查确认迁移、租约、幂等、事件收发等底座有真实实现，但也发现价值判断、上下文保真、知识召回和主助手入口不足，因而不能据此验收“个人超级助理”。[Batch 2 专项审查结论 ↗](../../../docs/reviews/2026-09-27-batch2/README.md#L1 "支持工程底座已有实现但仍不足以验收个人超级助理，以及产品路径需要调整的历史判断。") 旧有“全面提炼 claim、非自动通过就询问用户”的路径遂被 v3 设计替换；新方向保留数据、事务、任务、ACP、飞书和 UI 基础设施，把飞书设为主要对话入口、Web 设为管理及第二入口。[主助手 v3 的定位 ↗](../../../docs/implementation/assistant-v3/README.md#L3 "支持 v3 替换旧提炼路径、保留既有基础设施，并确定飞书和 Web 的入口分工。")

<a id="target-operation"></a>
## 目标工作方式与信息边界

v3 将 Evidence、SourceProfile/Index、WorkingContext 和 Knowledge/Commitments 视为并存层次：原件始终可检索引用，摘要与分类是可重算派生视图，临时线索不会自动变成本人承诺，只有实际选择或高影响操作才需要询问。[四层信息模型 ↗](../../../docs/implementation/assistant-v3/README.md#L77 "解释原件、派生索引、工作上下文及正式知识并存，以及不同层次的确认边界。") 交互路由也区分已绑定私聊、群内明确提及、群背景采集和卡片回调；群聊不得泄漏私人记忆，跨 Web 与飞书只有显式关联后才共享同一会话。[对话路由与隐私隔离 ↗](../../../docs/implementation/assistant-v3/README.md#L47 "支持私聊、群聊、背景采集和跨入口会话的不同处理方式及隐私约束。") 这使“材料进入系统”与“知识或任务正式生效”分离，避免把派生总结、群聊线索或模型建议误当独立事实。

<a id="current-boundaries"></a>
## 当前研究取舍、进展与限制

代码知识研究继续沿用固定 revision、固定 fragment、人工确认关系和本地隐私边界；材料记载当前检索仍以 SQLite 关键词为主，跨 revision 身份续接及 embedding 检索尚未完成。[代码知识的现有约束 ↗](../../../docs/research/code-wiki-landscape.md#L5 "支持固定版本与片段、关键词检索、人工关系治理以及跨版本身份和语义检索尚未实现的边界。") 技术取舍偏向复用 SCIP、Tree-sitter、repo-map 和本地向量模型，而不整体引入重复数据库、UI 与模型编排的平台。[代码知识组件取舍 ↗](../../../docs/research/code-wiki-landscape.md#L13 "支持复用 SCIP、Tree-sitter、repo-map 和本地 embedding，同时避免整体引入完整平台的方案。") 历史审查还发现，多说话人归因、项目身份、图片、引述和时间语义可能在进入模型前丢失，复核也可能缺少已有知识上下文；这些问题需要宿主数据合同和召回流程修正，不能只靠提示词。[输入保真与知识一致性缺口 ↗](../../../docs/reviews/2026-09-27-batch2/README.md#L49 "支持多人归因、项目身份、图片和引述语义丢失，以及复核缺少既有知识召回的历史问题。") 后续 PoC 必须以真实中文任务验证证据映射、删除过滤、离线运行和可重建性；上游指标或方案建议在通过这些硬门前都不能写成 omem 的服务保证。[检索 PoC 的采用硬门 ↗](../../../docs/research/mempalace/README.md#L92 "支持证据回查、更新删除过滤、离线运行、可重建运维及同口径中文评测等采用条件。")
