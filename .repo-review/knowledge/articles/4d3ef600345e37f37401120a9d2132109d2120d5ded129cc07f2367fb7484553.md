# 需求跟进的宿主状态快照

该模块把数据库中的真实事项和开发执行记录冻结成一份带宿主来源标记的页面输入，避免知识生成把讨论计划、模型意见、代码检查或发布状态混为一谈；同时提供只读研究工具，让生成与复核阶段读取同一版事实。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_and_entry"></a>
## 为什么要冻结真实执行状态

需求跟进页既包含讨论和计划，也会随事项、编码运行而变化。此模块把**宿主实际观察到的状态**单独捕获，明确排除生成文章本身，避免文章反过来触发自己的维护循环；对非 `requirement-followup` 页面则直接返回。参考 [状态快照职责与触发条件 ↗](../../../apps/server/src/assistant/followup-state.ts#L10 "支持快照来自宿主观察、排除生成文章，并仅处理需求跟进工作流的说明。")

页面维护计算输入摘要时会先执行 `prepare`；应用初始化注册知识路由时，将这个准备入口接到 `AssistantWork.preparePage`，后者再调用本模块。因此，新快照会先进入材料集合，再参与是否需要重跑的判断。参考 [维护前刷新输入 ↗](../../../apps/server/src/knowledge/page-worker.ts#L68 "支持页面维护在计算材料摘要前调用准备钩子的入口时序。")、[应用初始化接入准备钩子 ↗](../../../apps/server/src/app.ts#L129 "支持应用注册知识路由时把 preparePage 选项明确转发给 AssistantWork.preparePage。")、[助手准备页调用捕获 ↗](../../../apps/server/src/assistant/work.ts#L146 "支持 AssistantWork.preparePage 将 Store、仓储、计划与开发队列传给捕获函数。")

```mermaid
flowchart LR
  A[页面维护计算范围] --> B[准备需求跟进页]
  B --> C[捕获事项与开发运行]
  C --> D[挂接为页面固定输入]
  D --> E[研究阶段只读访问]
```
自主研究开启时，知识管线把读取工具注入角色运行。参考 [研究工具注入 ↗](../../../apps/server/src/knowledge/pipeline.ts#L124 "支持知识管线仅在自主研究模式下把 followup 状态工具加入研究运行。")

<a id="capture_flow"></a>
## 一次捕获如何形成快照

以一个需求跟进页为例（示意）：输入是页面计划、`Store`、知识仓储和开发队列。函数先按页面 key 查询已绑定的 task id，再从全部事项中只保留 `ownerId === "owner"`，且满足“已直接绑定”或“事项 projectId 位于页面 contextIds”之一的记录；其他人的事项和无关项目不会进入快照。参考 [关联事项筛选 ↗](../../../apps/server/src/assistant/followup-state.ts#L20 "支持按页面绑定、上下文项目和 owner 身份筛选实际事项的规则。")

随后它只选择 key 与页面一致的开发任务，投影出队列状态、运行阶段、错误、是否已应用、评审指纹、每次检查的命令结果，以及运行对应的结果材料。没有运行实例时阶段回退为 `queued`、检查为空、结果为 `null`；`published` 固定为 `false`，强调检查或应用不等于发布。参考 [开发运行投影 ↗](../../../apps/server/src/assistant/followup-state.ts#L37 "支持开发任务匹配、运行阶段、检查、错误、结果材料与发布标志的映射。")

最终 `{ tasks, development }` 被序列化进 Markdown/JSON，以稳定的 `followup-state:<pageKey>` 外部标识写成 `hook` 材料，标记为宿主执行产生的原始记录，并关闭学习与通知；其 sourceId 再以 `followup-state` 角色挂到页面输入。参考 [快照写入与挂接 ↗](../../../apps/server/src/assistant/followup-state.ts#L63 "支持状态序列化、宿主来源标记、关闭学习通知以及挂接页面输入的流程。")

<a id="reading_and_boundaries"></a>
## 后续阶段怎样读取与判断变化

`followupStateTools` 只从已提供材料中选择 `hook` 命名空间且 key 以 `hook:followup-state:` 开头的快照；没有匹配项就不注册工具。有匹配项时注册无参数、只读的 `read_followup_state`，返回每份材料的 key、revision、正文和完整行号范围，使生成与独立复核读取同一固定输入，而不是再次查询易变的实时状态。参考 [只读状态工具 ↗](../../../apps/server/src/assistant/followup-state.ts#L95 "支持工具的材料筛选、缺省行为、只读属性和返回字段。")

快照的关键语义边界是：`waiting` 仍表示等待，`next_check_at` 是检查时间而非截止日期；检查记录只证明所列命令与对应源码指纹，不能推出已经发布。状态未变化时，同一外部来源复用 revision；事项从 `open` 变为 `done` 后会产生新 revision，同时旧 revision 仍保留原状态。现有行为测试验证了这组版本语义，并确认该宿主快照不会排入 claim 提取。参考 [快照版本行为 ↗](../../../apps/server/tests/assistant-work.test.ts#L919 "支持相同状态复用 revision、状态变化创建新 revision、历史保留且不触发 claim 提取的已验证行为。")
