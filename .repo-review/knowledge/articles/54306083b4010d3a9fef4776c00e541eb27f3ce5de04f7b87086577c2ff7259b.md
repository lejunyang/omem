# 开发模式下的仓库知识接入与历史证据恢复

在不替换个人数据库的前提下，将仓库当前材料、已发布知识及其固定历史证据接入开发服务，并为搜索隐藏已删除或已迁移的仓库副本。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决什么问题

开发服务需要同时使用个人材料和本仓库的知识资产，但仓库同步中可能残留已删除文件或旧身份别名。`developmentRetrieval` 在共享检索器外加一层**可见性策略**：只对 `omem:` 文件的当前头部查元数据，排除 `removed` 与 `legacy_alias_of`，并继续遵守调用方原有的 `visible` 条件；个人材料不在该映射中，因此不受这层仓库适配影响。排序仍由原检索器完成。参考 [开发检索可见性策略 ↗](../../../apps/server/src/review/development.ts#L15 "支持仓库当前头部的筛选条件、与调用方可见性条件的合并方式，以及各检索端口的转发边界。")

<a id="flow"></a>
## 一次启动导入如何完成

代表性调用是 `importDevelopmentKnowledge(store, root)`：输入为个人 `Store` 与仓库根目录，输出包含恢复结果、可供 API 使用的知识仓库，以及历史恢复失败列表。它先读取已发布文章并按内容摘要建立历史集合；若个人库与评审运行库不是同一目录且旧库存在，还会沿文章依赖补齐非当前的子文章版本。参考 [文章与依赖历史收集 ↗](../../../apps/server/src/review/development.ts#L37 "支持导入函数的输入输出背景，以及从发布目录和旧评审库补齐被引用文章修订的前半段流程。")

```mermaid
flowchart LR
  A[已发布文章] --> B[补齐文章依赖]
  B --> C[补齐固定材料修订]
  C --> D[导入当前仓库材料]
  D --> E[恢复文章并刷新状态]
```

对缺失的材料摘要，代码从旧库逐版本匹配，连同图片数据、上下文和来源信息重新捕获；随后才调用 `restoreReviewKnowledge` 导入当前文件，避免历史修订把当前 head 倒退。参考 [固定材料与当前头部恢复 ↗](../../../apps/server/src/review/development.ts#L53 "支持按摘要匹配旧材料修订、保留图片与来源信息，并在历史材料之后恢复当前仓库内容的流程。")

<a id="boundaries"></a>
## 边界与修改入口

检索包装只改写 `search`、`searchSources` 与异步来源搜索；记忆搜索、证据读取和健康检查原样转发，因此“搜索中隐藏”不等于删除历史证据。要调整仓库副本的搜索资格，应改 `policy`；要调整导入顺序、历史追溯或失败呈现，应改 `importDevelopmentKnowledge`。历史文章恢复失败会收集并告警；发布目录中的当前文章若不可恢复则不会进入可读目录。最后一次 `refresh` 会依据实际依赖重新计算是否 current。参考 [开发检索可见性策略 ↗](../../../apps/server/src/review/development.ts#L15 "支持仓库当前头部的筛选条件、与调用方可见性条件的合并方式，以及各检索端口的转发边界。")、[文章恢复与状态刷新 ↗](../../../apps/server/src/review/development.ts#L72 "支持历史失败的记录方式、当前文章的可读目录处理，以及最终刷新知识状态和返回结果。")
