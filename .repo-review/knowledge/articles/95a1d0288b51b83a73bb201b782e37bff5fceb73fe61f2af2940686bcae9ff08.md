# 知识刷新结果的结构化输出合同

该 JSON Schema 定义知识刷新角色提交批量知识文档时必须遵守的数据形状，包括文档正文、内联引用和待确认问题。它约束的是输出格式，不能单凭此文件推断校验器、刷新流程或持久化机制已经实际接入。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 它解决什么问题

知识刷新需要把分析结果交给后续复核、展示或保存流程，因此输出不能只是自由文本。该合同把一次结果固定为版本号与文档数组：每批至少包含 1 篇、最多 16 篇文档；每篇文档必须给出键、标题、摘要、类别、章节、引用和问题列表，从而让宿主可以稳定解析。参考 [批量文档基本结构 ↗](../../../packages/agent-runtime/roles/knowledge-refresher/1/output.schema.json#L5 "支持输出由版本号和受数量约束的文档数组组成，以及文档必填字段的说明。")

文档类别限定为概览、架构、需求、进展、实现、测试、配置、工作流、研究、对话和视觉等枚举，便于下游按用途组织内容。不过，这里只描述允许的数据结构，不证明分类界面、数据库写入或刷新任务已经实现。参考 [知识文档类别 ↗](../../../packages/agent-runtime/roles/knowledge-refresher/1/output.schema.json#L31 "支持文档类别被限制为一组明确枚举值的论断。")

<a id="document_structure"></a>
## 正文与证据如何组织

每篇文档由 1 至 20 个章节组成；章节键必须以字母开头，并只能使用字母、数字、下划线或连字符。标题与正文也有长度上限，这使文章既能被稳定定位，又避免单次结果无限膨胀。参考 [章节格式约束 ↗](../../../packages/agent-runtime/roles/knowledge-refresher/1/output.schema.json#L48 "支持章节数量、键格式以及标题和正文长度均受到约束的说明。")

引用是正文论断与证据之间的结构化连接。每项引用包含人类可读标签、引用理由、关系类型和目标；目标可以指向材料或文章，并可携带材料行号或文章章节。`quote` 字段被要求保留，但说明明确建议留空，由宿主依据固定行范围提取原文。参考 [引用目标与原文提取 ↗](../../../packages/agent-runtime/roles/knowledge-refresher/1/output.schema.json#L112 "支持引用目标可指向材料或文章、可提供定位信息，并由宿主提取固定范围原文的说明。")

关系类型只允许支持、解释、实现、依赖、调用、矛盾、背景和跟踪等既定值。这一约束能减少下游对任意关系名称的猜测，但并不等同于语义支持性已经经过独立验证。参考 [引用关系类型 ↗](../../../packages/agent-runtime/roles/knowledge-refresher/1/output.schema.json#L99 "支持引用关系只能采用合同规定枚举值的论断。")

<a id="uncertainty_and_limits"></a>
## 如何保留不确定性与边界

合同为每篇文档预留最多 20 个问题。每个问题必须说明问题本身、提出原因、下一步、是否阻塞以及关联的引用键，使缺失背景或待决事项能够随结果一起传递，而不是被正文中的肯定语气掩盖。参考 [待确认问题结构 ↗](../../../packages/agent-runtime/roles/knowledge-refresher/1/output.schema.json#L166 "支持问题项的数量限制及其原因、下一步、阻塞状态和关联引用等必填信息。")

顶层及各主要对象都禁止未声明字段，并要求固定的必要字段；这有助于尽早发现拼写错误或协议漂移。参考 [严格顶层合同 ↗](../../../packages/agent-runtime/roles/knowledge-refresher/1/output.schema.json#L208 "支持文档字段必须完整、额外字段被禁止，以及顶层仅接受规定结构的说明。") 但该文件没有说明谁执行校验、校验失败如何处理、引用行范围是否会被再次核验，也没有展示知识刷新器的输入合同或运行状态，因此它应被理解为**格式规范**，而不是已完成能力的证据。
