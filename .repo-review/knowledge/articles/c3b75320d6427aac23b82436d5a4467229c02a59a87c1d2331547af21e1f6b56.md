# docs-reviews · 模块理解

docs-reviews 保存针对特定代码基线的审查叙事、可执行隔离复现和结果快照，并由当前实现状态文档说明哪些历史缺口已被修复、哪些验证边界仍然存在。它提供可追溯的反例与回归来源，但不是当前产品能力或真实外部集成验收的唯一依据。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 职责与形成背景

`docs-reviews` 是面向实现偏差的审计记录层：Batch 2 审查以 `16d3aa6` 为基线，关注提炼质量、用户打扰、输入语义和飞书主入口，并明确排除完整安全、性能及真实飞书验收。[Batch 2 审查范围与证据边界 ↗](../../../docs/reviews/2026-09-27-batch2/README.md#L1 "支持审查基线、关注主题、既有检查结果以及未调用真实模型或飞书接口的背景。") 子知识将结论组织为“底座可保留、入口与策略需调整”，但该归纳仍来自同一批审查材料，不是新的独立证据。[审查结论与历史边界 ↗](0e54ffd721ad0329b985f5fe0b31b35038ba30fc9ce5c5d661730e3d24f5a0e2.md#history-and-next "引用子知识对审查结论的组织方式；附近同时引用原始 README，避免把派生归纳视为独立事实。")

该模块把“为什么有问题”与“如何复现”分开：README 解释产品及实现偏差，`reproduce.ts` 用临时 SQLite、合成输入和注入判定构造确定性反例，结果 JSON 保存运行观察。脚本声明断言描述历史缺口而非期望行为，并登记所创建的临时 Store。[隔离复现的声明与资源登记 ↗](../../../docs/reviews/2026-09-27-batch2/reproduce.ts#L1 "支持脚本面向历史缺口、使用临时 SQLite，并通过 setup 创建和登记临时 Store；不用于证明退出清理行为。") 退出时再逐一关闭 Store、递归清理临时目录。[临时 Store 关闭与目录清理 ↗](../../../docs/reviews/2026-09-27-batch2/reproduce.ts#L462 "直接支持脚本在 finally 中关闭所有已登记 Store，并递归删除对应临时目录的断言。")

<a id="workflow"></a>
## 审查与复现如何协作

典型流程是先根据代码路径和只读数据观察提出问题，再以隔离场景验证领域层行为，最后登记为 R1～R10。旧脚本证明混合现状与规划的句子会直接成为 claim；引文包含即可得到满 evidence support；相反或重复的 create 提案可能全部自动应用，低价值不确定项则生成待决事项。[质量与记忆策略反例 ↗](../../../docs/reviews/2026-09-27-batch2/reproduce.ts#L132 "支持规则提取、证据支持指标、冲突重复提案和低价值待决事项的具体隔离断言。") 结果文件用相同编号保存关键输出，使文字结论可回查到具体断言。[R1 至 R4 结构化结果 ↗](../../../docs/reviews/2026-09-27-batch2/reproduction-results.json#L1 "说明结果快照如何按编号保存规则提取、质量指标、冲突去重和待决策略的观察值。")

这种方式适合产生回归素材，却不能证明模型质量或线上集成：语义判定由夹具注入，消息发送使用假适配器，图片和私聊场景也未连接真实飞书。子知识集中解释了临时数据库、确定性夹具和非真实外部调用的边界。[复现脚本的用途与夹具边界 ↗](4272f52c6c49269104a66ea3e2c47b94bf998e692c4115c233c2721ee6bba697.md#purpose-and-fixtures "引用子知识对临时数据库、注入判定和非真实外部调用边界的归纳。")

<a id="relations-progress"></a>
## 与当前实现状态的关系

审查资料与 `docs/implementation/status.md` 构成“历史反例—当前状态”的关系。后续 G01～G20 已记录为通过，覆盖普通导入不生成逐句标注、逐片段来源保留、身份映射、冲突与重复治理、取消未发卡、质量指标修正和诚实恢复；但 G15 仍是 fake transport，G20 的进程重启仍由同数据库的新 runtime 模拟。[G01 至 G20 后续验收状态 ↗](../../../docs/implementation/status.md#L61 "支持历史反例对应行为已由后续测试覆盖，同时说明图片链路和重启验证的证据等级限制。") 因而 R1～R10 是修复来源和防回归案例，不能直接描述当前产品仍有同样缺陷。

当前能力矩阵显示主助手、关键词检索、知识治理、输入保真、通知及质量评估已有代码与本地测试支撑，但真实 ACP、真实飞书和语义检索的证据等级不同。[当前能力矩阵 ↗](../../../docs/implementation/status.md#L45 "支持主助手、检索、治理、输入、通知和质量评估的实现进展及真实外部验证缺口。") 模块因此需要同时保存审查结论、复现方法和后续状态，不能用单一“测试通过”数字代替能力判断。

<a id="constraints"></a>
## 使用约束与剩余限制

历史报告要求保留迁移、不可变原件与片段、租约、事务回执、角色包、飞书基础设施和证据阅读组件，重点重做入口及策略层；旧缺口脚本不能直接并入常规 CI，以免把错误行为固化为长期合同。[可保留底座与回归转换原则 ↗](../../../docs/reviews/2026-09-27-batch2/README.md#L109 "支持保留基础设施、重做入口策略，以及不得让常规 CI 固化旧缺陷的约束。") 合理做法是将仍适用的反例改写成期望行为测试，同时保留原审计文件解释修复缘由。

目前仍缺少真实 ACP 主助手与飞书 WebSocket 的端到端验证、真实飞书图片下载、进程级 kill/restart，以及来源刷新后的完整 extractor/verifier 重核验；刷新任务会明确报告未实现，而非假报完成。[当前外部验证和重核验限制 ↗](../../../docs/implementation/status.md#L86 "支持真实 ACP、飞书、进程重启及 refresh_dependents 完整重核验仍未完成的结论。") 因此本模块能回答某次基线为何有缺口、如何隔离复现及后续测试声称修复了什么，却不能单独证明当前部署、外部服务和真实模型已达到产品验收标准。
