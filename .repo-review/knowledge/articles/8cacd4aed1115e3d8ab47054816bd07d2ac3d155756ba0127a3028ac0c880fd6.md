# docs-implementation：统一知识流程、运行进展与验证边界

本专题说明 omem 如何在统一证据链上组织知识、驱动助手与 Code Wiki，并区分已实现流程、历史验证结果、被替代结论和仍待补齐的外部集成及跨版本能力。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 统一知识流程的职责

该模块把仓库文件、手工材料、对话和图像都视为 Capture 输入，共用正文、引用、疑问、角色运行与任务记录，避免为代码另建事实权威。知识正文以具名章节组织，引用固定到材料行范围或知识章节目标；原始证据仍来自 Capture / Source / Revision / Fragment，派生知识不会再次作为独立原件采集。来源更新会使相关知识及依赖章节过期，但历史引用仍可读取固定版本。[正文、固定引用与不可变修订 ↗](../../../docs/implementation/knowledge-pipeline.md#L3 "支持引用可指向材料行范围或知识章节目标、原始证据链、派生知识非独立原件以及来源变化后的级联过期。")

材料、代码、对话、图像分析以及规划、写作、复核、刷新八类角色复用同一运行时与持久任务体系。正文只有经过独立会话的语义复核才能发布；引用位置有效不等于附近论断确实受证据支持。[共用角色运行时与独立复核 ↗](../../../docs/implementation/knowledge-pipeline.md#L15 "支持八类角色复用运行时、持久任务隔离及独立语义复核流程。")

<a id="workflow"></a>
## 从材料到可阅读、可召回知识

仓库适配器将 Git 可见源码、文档、配置和图像送入通用流程，同时排除运行数据、私有配置与已有派生知识。通过复核的结果保存为带内联引用的 JSON 和 Markdown，再逐层组成模块、主题与概览；局部生成负责模型处理，索引重建不会隐式调用模型。[仓库材料适配与可提交产物 ↗](../../../docs/implementation/knowledge-pipeline.md#L31 "支持仓库输入范围、排除边界、分层知识生成，以及局部生成与索引重建的职责区分。")

个人知识与仓库知识复用同一证据阅读栈，可逐层打开固定知识章节或原始材料，并支持返回、深链、滚动与焦点恢复。检索可先命中知识正文，再沿固定引用返回原始 Fragment；派生正文只用于导航，送给助手的仍是经当前来源核对的原始证据。[共享证据阅读与知识引导召回 ↗](../../../docs/implementation/knowledge-pipeline.md#L45 "支持个人与仓库知识共用阅读栈，并明确派生正文只用于导航、助手最终使用经来源核对的原始证据。") Code Wiki 因而只是统一证据链在代码域的投影，而非独立知识库。[统一知识与仓库评审 ↗](ea3b10c73196cbb2d4fbcdb64dda5f83612fc7e831d8c0ace4d3f9507a4c899b.md#knowledge-and-review "作为子知识说明 Code Wiki 与通用 Capture 证据链之间的关系。")

## 较新进展、被替代结论与证据范围

2026-10-01 的较新记录显示，系统已加入混合词法检索、固定中文向量模型、来源更新后的 extractor→verifier→原子应用闭环，以及带等待、暂缓和取消动作的日常助理；全库知识是否完成仍须查看当前 coverage 与 verification 报告。[2026-10-01 能力进展 ↗](../../../docs/implementation/status.md#L1 "支持日常助理、检索、中文向量、来源更新闭环及知识覆盖需以当前报告为准的阶段性结论。") 其中 schema 14、只有关键词检索和本机无真实 CLI 等旧说法已被较新记录替代。[被较新进展替代的历史状态 ↗](../../../docs/implementation/status.md#L33 "支持旧状态区块曾记录 schema 14、无真实 CLI 和仅关键词召回，并与较新记录形成时间性替代关系。") 第 104 行保留的“refresh_dependents 重核验未实现”也是历史口径，顶部已明确记录该闭环不再是占位实现。[被替代的重核验占位记录 ↗](../../../docs/implementation/status.md#L104 "定位历史区块中 refresh_dependents 仍被描述为未实现的旧结论，说明该结论已被顶部较新闭环记录替代。")

Review 启动竞态已有针对性处理：服务未就绪时保持连接并重试，只有 Review health 明确为 404 且个人 health 成功才切换模式；文档记录了 API 暂停后恢复及浏览器回归，但这只是当时的验证结果。[Review 启动模式修复 ↗](../../../docs/implementation/review-startup.md#L3 "支持启动竞态成因、模式探测条件、恢复行为和当时浏览器验证范围。") 飞书实机快照则只证明 `lark-cli` 取得版本 15 文档、包含 text/link 并报告 12,245 字符，不能据此推断 WebSocket、图片下载、幂等导入或固定引用精度已验收。[飞书文档导入实机摘要 ↗](../../../docs/implementation/live-lark-verification.json#L1 "支持快照仅记录连接器、文档版本、part 类型和字符规模，并据此限定可证明范围。")

<a id="limits"></a>
## 跨模块关系与仍然存在的边界

Code Wiki 已覆盖确定性代码图、人工关系 seed 和共享阅读交互，但跨文件调用尚不解析，单文件名称级调用只能标为候选；跨 revision 的符号与 Fragment 身份续接也未实现，代码变化后仍需在新 head 重新定位。[Code Wiki 实现边界 ↗](../../../docs/implementation/status.md#L46 "支持 Code Wiki 的统一证据链定位，以及跨文件调用和跨版本身份续接尚未实现的限制。")

整体实现仍以 TypeScript、SQLite 和个人单用户为边界，不具备多租户 ACL、分布式事务或 pgvector；原件与回答可追溯，也不代表每条 Claim 都已完成自动语义支持性评估。[个人单用户实现取舍 ↗](../../../docs/implementation/status.md#L138 "支持 SQLite 单用户边界、多租户与分布式能力缺失，以及可追溯不等于所有论断均完成语义验证。") 后续仍需补齐全库知识覆盖、跨版本身份、reranker/ANN、周期巡检和外部提醒投递。[全库知识覆盖仍不完整 ↗](../../../docs/implementation/status.md#L5 "支持全库知识尚未完整、覆盖及失败必须以当前验证报告为准的限制。")[Code Wiki 实现边界 ↗](../../../docs/implementation/status.md#L46 "支持 Code Wiki 的统一证据链定位，以及跨文件调用和跨版本身份续接尚未实现的限制。")[语义检索剩余缺口 ↗](../../../docs/implementation/status.md#L7 "支持 reranker、ANN 和历史时点检索尚未实现，并限定现有中文检索结果只是小样本。")[来源更新后的后续能力 ↗](../../../docs/implementation/status.md#L9 "支持周期全库巡检仍未实现，并区分已经完成的来源更新闭环与后续自动化能力。")[日常助理外部投递边界 ↗](../../../docs/implementation/status.md#L1 "支持自动监听、周期回顾、重复提醒和外部到期投递仍未接入的结论。") 进程恢复方面，目前 G20 只用同一数据库的新 runtime 实例模拟 pending turn 恢复，尚未执行真实进程 kill+restart，因此不能将测试通过表述为完整的进程级恢复验收。[进程恢复测试的实际边界 ↗](../../../docs/implementation/status.md#L96 "支持 G20 当前通过同一数据库的新 runtime 实例模拟恢复、尚未进行真实进程 kill+restart 的限制。")
