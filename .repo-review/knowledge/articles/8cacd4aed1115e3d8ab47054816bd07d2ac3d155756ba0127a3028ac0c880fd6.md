# 统一知识流程、阶段进展与验证边界

本专题说明 omem 如何在统一原始证据链上生成、复核、阅读和检索知识，并梳理仓库评审、中文语义检索、来源更新及日常助理的当前进展与仍需实证的边界。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-authority"></a>
## 为什么需要统一知识流程

知识整理的目标不是另建一个事实库，而是把不同 Capture 中的原始材料组织成可阅读、可追溯且可失效的正文。`KnowledgeDocument` 以具名章节和内联引用表达结论，宿主从固定 Revision 复制引文；派生知识只负责组织与导航，事实权威仍属于 Capture、Source、Revision 和 Fragment。来源变化会让相关知识及其上层章节过期，但旧修订及固定引用仍可追溯。[知识正文与固定引用合同 ↗](../../../docs/implementation/knowledge-pipeline.md#L3 "说明派生正文的组织职责、原始证据权威、不可变修订以及来源变化后的级联失效。")

这一约束也适用于代码域：Code Wiki 只是统一证据链上的类型化投影，repo-review 是隔离的输入适配与开发视图，并不是独立知识库。跨文件调用尚未解析，名称级调用只能作为候选；代码变化后还需重新同步，使 locator 在新 head 上重新定位。[Code Wiki 的统一证据链定位 ↗](../../../docs/implementation/status.md#L48 "支持 Code Wiki 不是独立知识库，并界定跨文件调用和跨版本身份续接限制。")

<a id="generation-and-review"></a>
## 如何生成、复核与演进

材料、代码、对话和图像分析，以及规划、写作、复核和刷新角色，共用同一角色运行时与持久任务体系。`KnowledgePipeline` 先分析材料，再以独立会话核验引用对正文的支持性；只有通过的内容才发布，未通过部分进入定向修订，分析期间若来源变化则拒绝发布旧结果。协议用例只能证明流程合同，不能替代真实模型覆盖。[共用角色运行时与独立复核 ↗](../../../docs/implementation/knowledge-pipeline.md#L15 "支持八类角色复用同一运行时，以及先分析、后独立复核、来源变化时拒绝发布的流程。")

仓库入口会处理 Git 可见材料并记录排除或失败原因，通过复核的正文保存为 JSON 与 Markdown，再逐层组成模块、主题和概览。失败项不能冒充已生成内容，实际覆盖必须以当前 `coverage.json` 和验证报告为准。复核退回后由专用刷新角色依据具体意见局部修改，有限轮次后仍无依据的内容应降为明确问题，而不能绕过复核。[仓库材料适配与覆盖记录 ↗](../../../docs/implementation/knowledge-pipeline.md#L31 "说明仓库材料如何进入统一流程、产物如何保存，以及失败项和实际覆盖的记录口径。")[复核退回后的定向修订 ↗](../../../docs/implementation/knowledge-pipeline.md#L61 "支持刷新角色按具体反馈局部修订，并要求最终结果仍通过独立复核。")

<a id="reading-and-retrieval"></a>
## 知识如何关联阅读与助手召回

个人知识入口和仓库知识入口复用同一证据阅读组件：读者可从正文中的可读引用进入固定知识章节或原始材料，并沿帧栈逐层返回、循环跳转、恢复滚动位置和焦点。代码结构图是补充入口，而不是另一套阅读合同。[统一证据阅读组件 ↗](../../../docs/implementation/knowledge-pipeline.md#L45 "支持个人知识与仓库知识共用引用阅读、帧栈、深链和焦点恢复合同。")

检索命中整理后的正文时，会继续沿固定引用返回原始 Fragment；派生正文不会作为独立证据送给助手。召回还会重新核对材料当前版本，避免知识投影尚未刷新时继续使用旧来源。当前实现进一步加入 FTS5/BM25、中文短词、知识引用和活跃记忆的融合，以及固定中文向量模型；但四条同义问法的结果只是小样本，reranker、ANN 和历史时点检索仍未完成。[知识引导原始证据召回 ↗](../../../docs/implementation/knowledge-pipeline.md#L55 "说明正文仅用于导航，助手最终获得原始 Fragment，并在召回时重新检查当前来源。")[中文混合与向量检索进展 ↗](../../../docs/implementation/status.md#L5 "支持当前混合检索、固定中文向量模型、词法降级、小样本结果及尚未完成的检索能力。")

<a id="progress-and-limits"></a>
## 当前进展、验证口径与限制

来源更新已形成 Capture 记录失效范围、extractor 重跑、独立 verifier 和原子应用的闭环；失败或缺证据时保持待复核，不能把“已入队”视为更新成功。日常助理也已验证等待创建、暂缓、重启后单次补发和取消，但自动监听回复、周期回顾、重复提醒及外部到期投递仍未接入。[来源更新重核验闭环 ↗](../../../docs/implementation/status.md#L9 "支持失效范围记录、extractor、独立 verifier、原子应用及失败时保持待复核的当前实现。")[日常消息与跟进状态 ↗](../../../docs/implementation/status.md#L1 "支持等待事项闭环的实测范围及自动监听、周期回顾、重复提醒和外部投递缺口。")

不同证据只能支持各自范围：工程检查证明构建和测试通过，真实 ACP 调用证明模型链路可用，小样本检索不代表总体质量。系统目前仍是 TypeScript 与 SQLite 的个人单用户实现，不具备多租户 ACL、分布式事务或 pgvector；可追溯也不等于每条 Claim 都已完成正式语义支持性评估。[个人单用户实现边界 ↗](../../../docs/implementation/status.md#L138 "支持 SQLite 单用户取舍、多租户与分布式能力缺失，以及可追溯不等于语义验证完成。")

飞书实机快照仅记录 `lark-cli`、文档版本、text/link 类型及文本规模；它没有给出退出码、固定 Capture/Revision、幂等重试或关键内容断言，因此不能据此宣称真实 WebSocket、图片下载或精确引用定位已经验收。[飞书文档导入摘要快照 ↗](../../../docs/implementation/live-lark-verification.json#L1 "支持快照实际包含的连接器、版本、part 类型和文本规模，并界定其无法证明的验收范围。")
