# 实时记忆刷新冒烟验证

该脚本以真实 ACP 模型运行一次端到端刷新场景：先从来源提取并应用“重试上限为 3”，再捕获同一来源的新修订“上限为 5”，验证旧记忆立即失效、复核后沿用原记忆身份生成新版本，并保留旧来源证据和刷新记录。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_setup"></a>
## 目标与运行环境

脚本解决的是“来源内容变化后，已应用记忆能否可靠重核验并更新”的真实链路验证问题。它创建隔离的临时 SQLite Store，选择 `traex` 的实时 ACP profile，并组装 `LearningPipeline`、记忆与反馈服务；因此这里验证的是多个现有模块的协作，而不是模拟单个函数。脚本还硬性断言最终模型为 `gpt-5.6-sol`，不满足便直接失败。[实时 profile 与学习流水线初始化 ↗](../../../scripts/live-refresh-smoke.ts#L10 "支持脚本创建隔离运行环境、选择真实模型并组装学习流水线，以及强制校验模型名称的说明。")

模型选择器会先探测 ACP 暴露的模型选项，环境变量指定了不可用模型时会报错；但 effort 仅由环境变量传入，当前脚本只记录它，没有断言具体值或能力支持。[ACP 模型探测与选择规则 ↗](../../../scripts/live-model.ts#L12 "解释实时 profile 如何校验可用模型，以及 effort 仅从环境变量写入 profile 的边界。")

<a id="refresh_flow"></a>
## 刷新流程与核心断言

场景用相同外部来源标识连续捕获两次声明。第一次写入“重试上限 3 次”，排空最多 8 轮流水线任务后，断言系统只产生一条已应用的活跃记忆。[初始来源提取与应用断言 ↗](../../../scripts/live-refresh-smoke.ts#L20 "支持首次捕获重试上限为 3、排空流水线并要求恰有一条活跃记忆的描述。") 第二次改为“5 次”时，脚本先验证旧记忆立即进入 `invalidated`；再次排空任务后，要求仍只有同一条 memory id，其版本升为 2、状态恢复为 `active`、正文包含 5。同时旧 revision 的 fragment 仍保留 3，且新 revision 对应的刷新记录必须为 `applied`。这共同覆盖了身份续接、不可变原始证据和刷新落地状态。[来源变化后的刷新断言 ↗](../../../scripts/live-refresh-smoke.ts#L28 "支持旧记忆失效、同一身份升至版本 2、正文更新、旧证据保留及刷新记录应用成功的论断。")

<a id="boundaries"></a>
## 边界、产物与未覆盖行为

异常会被转成失败状态并设置非零退出码；无论成功失败，脚本都会停止流水线、收集 jobs、刷新记录和 proposals，写出 `verification/live-refresh.json`，随后关闭数据库并删除临时目录。[失败处理、验证报告与清理 ↗](../../../scripts/live-refresh-smoke.ts#L38 "支持异常退出、诊断数据收集、报告写入和临时资源清理流程的说明。")

它属于单场景实时冒烟测试：只检查一个文本来源、一次从 3 到 5 的高置信更新以及最多两次 drain。材料没有证明并发更新、模型超时、歧义或拒绝策略、批量变更、超过 drain 轮数、报告写入失败等行为，也没有断言刷新期间是否产生额外通知或待决事项。

<a id="module_relations"></a>
## 与其他模块的关系

脚本直接依赖配置加载、Store、MemoryService、FeedbackService、LearningPipeline 和实时模型选择器，负责把这些模块串成可执行验收入口；具体提取、独立复核及应用规则仍由流水线和服务实现，不能仅从本文件推断其内部算法。[冒烟脚本的模块依赖 ↗](../../../scripts/live-refresh-smoke.ts#L5 "支持脚本与存储、配置、记忆服务、学习流水线及实时模型选择模块之间的显式关系。") Store 在这里既承载捕获与修订，也通过数据库查询暴露记忆和刷新状态，但跨模块调用关系仅能确认到显式导入、构造和方法调用。
