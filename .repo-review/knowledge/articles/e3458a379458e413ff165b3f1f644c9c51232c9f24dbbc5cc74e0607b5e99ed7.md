# 代码理解输出模式

定义 CodeUnderstanding.v1 的顶层结构、角色与状态范围，以及职责、引用、置信度和溯源字段；模式能约束整体形状，但复杂数组元素与生成时间仍依赖未确认的补充验证。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="contract"></a>
## 顶层合同与状态空间

该文件以 JSON Schema 2020-12 定义 `CodeUnderstanding.v1`。输出必须是对象，不允许额外顶层属性，并要求结果身份、角色、状态、职责、边界、流程、声明、引用、未知项、置信度及 provenance 字段全部存在。[CodeUnderstanding 顶层必填字段 ↗](../../../packages/agent-runtime/roles/symbol-explainer/1/output.schema.json#L1 "支持输出禁止额外顶层属性，并要求职责、流程、声明、引用、未知项和溯源信息等字段齐备的论断。")

角色枚举覆盖仓库画像、模块架构、符号解释和关系核验，状态允许 `seed`、`generated`、`verified`、`failed` 与 `rejected`。[角色与结果状态枚举 ↗](../../../packages/agent-runtime/roles/symbol-explainer/1/output.schema.json#L33 "支持合同允许的四类角色和五种结果状态。") 这些约束描述统一结果容器的合法形状，但不表示各角色会以相同粒度填写所有字段，也不能单独证明状态转换已由运行时实施。

<a id="validation"></a>
## 字段校验强度与限制

职责、边界、入口、出口及风险集合被规定为字符串数组，而 `key_flows` 与 `claims` 只被声明为数组。[职责、流程与生成时间定义 ↗](../../../packages/agent-runtime/roles/symbol-explainer/1/output.schema.json#L46 "支持职责、边界、入口、出口和风险字段的字符串元素约束，也支持复杂数组缺少元素模式及生成时间仅为字符串的限制分析。") 引用节点、引用边和未知项同样要求字符串元素；置信度限定在 0 到 1，模型与验证者可为空，三个摘要须为 64 位小写十六进制字符串。[引用、置信度与溯源字段约束 ↗](../../../packages/agent-runtime/roles/symbol-explainer/1/output.schema.json#L53 "支持引用标识与未知项采用字符串元素、置信度范围、可空字段及摘要格式的说明。") 因此模式可以拦截缺失字段、非法枚举值、越界置信度和明显错误的摘要格式。

不过，`key_flows`、`claims` 与 `evidence_refs` 没有元素结构，`generated_at` 也只要求字符串。[职责、流程与生成时间定义 ↗](../../../packages/agent-runtime/roles/symbol-explainer/1/output.schema.json#L46 "支持职责、边界、入口、出口和风险字段的字符串元素约束，也支持复杂数组缺少元素模式及生成时间仅为字符串的限制分析。") 符号解释角色则进一步要求声明区分 `raw_fact` 与 `interpretation`、引用固定快照中真实存在的标识，并填写当前 ISO 时间。[符号解释角色的声明与时间要求 ↗](../../../packages/agent-runtime/roles/symbol-explainer/1/prompt.md#L5 "支持角色要求区分事实与解释、引用真实快照标识并填写当前 ISO 时间，说明角色要求强于静态模式。") 这些语义和格式要求是否由宿主验证器补足，现有材料无法确认。
