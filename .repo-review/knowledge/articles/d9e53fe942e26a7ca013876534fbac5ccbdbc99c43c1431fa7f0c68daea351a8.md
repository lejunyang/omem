# 飞书实时连接、助手应答与可靠投递编排

LarkRuntimeHost 是服务端飞书集成的常驻编排层：同步数据库中的有效连接，先处理收件箱中的原始事件，再把消息路由到受可见性约束的助手会话，并处理通知聚合、卡片动作和回复投递；同时提供重启恢复、状态观测和有序停机。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="role_and_composition"></a>
## 解决什么问题

该运行时把飞书接入所需的组件装配成一个常驻服务。它创建回复投递 Worker 和通知批处理器，并装配卡片动作服务、质量标注服务以及可选的助手运行时。消息适配器未注入时使用官方实现；资源端口未注入且媒体端口也未注入时，才创建官方资源实现。若已注入媒体端口但未注入资源端口，资源端口保持 `undefined`。参考 [运行时组件装配 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L59 "支持投递、通知、卡片、质量、资源与收件箱服务的装配，以及消息和资源端口的回退条件、助手模型与检索器的可选配置。") 实时适配器未注入时也使用官方实现。参考 [连接同步与收件处理 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L173 "支持有效连接筛选、连接管理器启停、实时适配器的官方实现回退，以及每轮先处理收件箱任务并受 limit 限制的流程。") 没有注入检索器时使用关键词检索。若未提供 `assistantModel`，助手能力保持关闭，连接和收件流程仍可运行，卡片与投递编排也不受影响。参考 [运行时组件装配 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L59 "支持投递、通知、卡片、质量、资源与收件箱服务的装配，以及消息和资源端口的回退条件、助手模型与检索器的可选配置。")

证据可见性由服务端控制。私聊会话通过可见性检查，而群聊证据必须存在，并且来源记录中的会话 ID 要与当前群一致。飞书群内提问因此不会检索到私聊、其他群或没有对应会话来源的证据。参考 [群聊证据可见性 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L99 "支持私聊直接通过检查、群聊仅允许同一来源会话证据的可见性规则。")

<a id="message_flow"></a>
## 一条消息如何变成回复

以绑定用户在群里触发助手为例：`processOnce()` 先读取处于 `active` 或 `awaiting_pair` 状态的连接，停掉已失效的实例，并为新连接创建带租约的 `LarkConnectionManager`。连接管理器使用实时适配器接收事件，并把事件交给 `LarkEventInbox`；随后本轮会重复处理收件箱任务，直到没有待处理项或达到 `limit`。参考 [连接同步与收件处理 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L173 "支持有效连接筛选、连接管理器启停、实时适配器的官方实现回退，以及每轮先处理收件箱任务并受 limit 限制的流程。")

收件箱调用助手回调后，运行时用 `appId + bindingVersion` 生成传输线程标识，再按群聊或私聊打开对应会话。若已存会话的可见性与当前路由的群聊或私聊类型不一致，调用立即失败。随后文本和飞书事件 ID 被交给 `AssistantRuntime.turn()`。回复文本、轮次 ID 和去重状态会返回给收件箱，已有的 outbox ID 也一并返回。参考 [助手消息路由 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L140 "支持传输线程命名、会话与当前路由类型的可见性校验、助手轮次调用及回复元数据返回。")

收件箱任务处理完后，本轮生成到期通知批次，再分别处理最多 `limit` 个卡片任务和 `limit` 个投递任务。卡片协议为 `omem.quality.v1` 时直接交给质量标注服务，其余卡片进入普通队列。参考 [卡片协议分流 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L202 "支持质量标注协议与普通卡片队列的分流。") [通知、卡片与投递处理 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L219 "支持收件任务之后的通知聚合，以及卡片和投递任务各自受 limit 限制的处理顺序。")

<a id="recovery_and_lifecycle"></a>
## 恢复、错误与生命周期边界

启动方法有重复调用保护，并在进入轮询前恢复未完成轮次。已有结果但未终结的轮次会补记为完成；没有结果的陈旧轮次会被删除，使同一传输事件重投时能够重新执行。助手未启用时，恢复直接返回零计数。参考 [未完成轮次恢复 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L244 "支持有结果轮次补完成、无结果轮次删除、无助手时返回零计数及启动前恢复。")

循环默认每秒执行一次。单轮异常不会终止运行时；错误信息会移除换行，遮蔽常见密钥前缀，并截断到 1000 字符后保存，下一轮成功时清空。`status()` 暴露运行状态和正在运行的连接数，也包含累计卡片与投递处理量以及最近错误。参考 [错误信息清洗 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L39 "支持错误去换行、常见密钥前缀遮蔽与 1000 字符截断。") [轮询、状态与停止流程 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L281 "支持默认轮询间隔、异常隔离、状态统计，以及停止收件箱、连接、onboarding 并等待循环退出。")

停止时，`AbortController` 会唤醒等待，收件箱和所有连接随即停止，onboarding 服务也会关闭；运行时最后等待循环退出。参考 [轮询、状态与停止流程 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L281 "支持默认轮询间隔、异常隔离、状态统计，以及停止收件箱、连接、onboarding 并等待循环退出。")
