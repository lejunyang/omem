# agent-runtime · 模块理解 · 专题 5

本专题说明 agent-runtime 中三类已有行为规范与一个静态角色配置：材料分析整理固定证据，模块架构师生成快照限定的代码理解，planner 只提出计划；另有名为 relation-verifier 的角色清单。现有材料主要证明合同与配置已定义，尚不能证明角色间调度顺序、结果替换、预算执行或语义校验已经实现。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="role_architecture"></a>
## 角色化合同与证据边界

材料分析角色用于整理需求、设计、研究、进展和配置，并区分文档陈述、实现事实与历史状态，避免把旧计划误写成已实现能力。[材料分析职责 ↗](12afa757e074e29f09721401f866d21f151c07f353f1477f83646a83b46ecc7f.md#skill_scope "支持材料分析覆盖的内容类型及区分文档陈述、实现事实和历史状态的原则。") 它只能处理给定材料、不得调用工具，并要求把不确定事项结构化记录。[材料分析输入与输出边界 ↗](../../../packages/agent-runtime/roles/material-analyst/1/skills/omem-material-analyst/SKILL.md#L10 "支持只处理给定材料、禁止工具调用以及结构化记录不确定事项的行为边界。")

模块架构师面向固定代码快照，描述模块职责、相邻边界、内部流程和入口出口；文件、符号、边及指定文档是唯一事实来源。[模块架构师固定快照范围 ↗](../../../packages/agent-runtime/roles/module-architect/1/prompt.md#L3 "支持模块架构师的分析对象、唯一事实来源及不得越界读取的限制。") 这类拆分为派生结论的来源追踪和权限隔离提供基础，但材料没有定义结果替换、版本切换或失败保留机制，因此此前“派生理解可替换”的结论已被撤回。

<a id="contracts_and_flows"></a>
## 模块理解与规划流程

模块架构师清单绑定角色版本、提示模板、技能制品、`CodeUnderstanding.v1` 以及资源上限。[模块架构师装配清单 ↗](../../../packages/agent-runtime/roles/module-architect/1/manifest.json#L2 "支持角色版本、输出合同、技能制品和资源预算之间的静态绑定。") 分析时应沿快照已有边识别边界和关键流程，把结论区分为 `raw_fact` 与 `interpretation`，不清楚之处进入未知项。[模块边界与流程分析纪律 ↗](../../../packages/agent-runtime/roles/module-architect/1/skills/omem-code-module-architect/SKILL.md#L8 "支持沿已有边组织流程、区分事实与解释并以未知项承载不确定性的要求。") 输出合同覆盖职责、边界、流程、证据和生成封印，但 `key_flows`、`claims`、`evidence_refs` 仅被声明为数组，元素及交叉引用规则未在 Schema 中给出。[模块理解合同的结构限制 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L43 "支持核心数组、状态、摘要和验证字段的现有类型约束，并据此说明元素级及状态机规则仍未定义。")

planner 则依据固定证据提出下一步，每步需连接证据、预期产物、验证、所有者决策与停止条件；代码、部署、消息和数据变更都只可作为提案，仍需另行授权执行。[规划步骤与授权边界 ↗](../../../packages/agent-runtime/roles/planner/1/skills/omem-task-planning/SKILL.md#L8 "支持规划步骤的证据闭环、允许动作以及外部变更需独立执行和授权的限制。")

<a id="progress_limits"></a>
## 静态配置与尚未证实的关联

现有材料还确认一个名为 `relation-verifier` 的 v1 角色：它静态绑定 `CodeUnderstanding.v1`、独立提示模板、技能制品摘要，以及 96,000/24,000 token 和 150 个引用节点的上限。[关系核验角色静态清单 ↗](../../../packages/agent-runtime/roles/relation-verifier/1/manifest.json#L2 "仅支持 relation-verifier 的角色名称、输出合同、提示模板、技能制品及预算配置，不推导其职责或调度顺序。") 仅凭清单无法确定该角色的具体工作方式，也不能证明它会在模块架构师之后运行或接收其结果；此前“先生成、后复核”的确定性结论已被替代为待验证问题。

同样，清单和 Schema 不能证明技能摘要、预算及节点上限已被运行时强制，也未定义 generated、verified、failed、rejected 等状态之间的转换和覆盖策略。[模块理解合同的结构限制 ↗](../../../packages/agent-runtime/roles/module-architect/1/output.schema.json#L43 "支持核心数组、状态、摘要和验证字段的现有类型约束，并据此说明元素级及状态机规则仍未定义。") 因此目前可确认的是静态装配、固定证据纪律和结构化输出要求，而非端到端运行、语义核验或有效结果保留机制已经验收。
