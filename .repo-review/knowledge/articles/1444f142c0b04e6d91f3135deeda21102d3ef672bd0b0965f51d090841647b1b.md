# 可追溯的多路关键词检索

解释 KeywordRetrieval 如何把一次查询分发到全文、短词、代码符号、记忆和知识线索，经过可见性过滤、相关性融合与去重排序，最终仍返回可回读的原始材料片段。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决什么问题

`KeywordRetrieval` 是 SQLite 上的同步检索基线：上层只需提交查询，就能在普通材料、代码、已应用记忆和知识文章线索之间找候选，而不必理解各自的表结构。它实现统一检索端口，并公开健康状态；候选中的修订号与片段号还可交给 `readEvidence` 回读原文。参考 [统一检索实现 ↗](../../../apps/server/src/retrieval/keyword.ts#L22 "支持该类作为 RetrievalPort 实现并报告 SQLite 词法后端健康状态。") [原文回读 ↗](../../../apps/server/src/retrieval/keyword.ts#L30 "支持候选可凭修订号和片段号回读固定证据片段。")

它的关键原则是：**派生内容负责引路，原始片段负责作证**。文件定义了统一的原始材料过滤条件，排除派生修订；即使查询命中记忆，也会沿记忆的证据集合返回对应原始片段，而不是把记忆文本包装成新的独立证据。参考 [原始材料过滤 ↗](../../../apps/server/src/retrieval/keyword.ts#L17 "支持检索统一排除 derived 来源和派生上下文。") [记忆回溯原证据 ↗](../../../apps/server/src/retrieval/keyword.ts#L82 "支持记忆只用于导航，并沿证据集合取回原始片段。")

<a id="representative-flow"></a>
## 一次查询怎样变成候选

以教学示例“查找 `resolveWidget` 的重试说明”为例：`searchSources` 先把数量限制夹在 1–100，调用共享分词器得到检索词；没有有效词就直接返回空。时间范围和调用方提供的 `visible` 函数会在评分前过滤候选。参考 [查询入口与过滤 ↗](../../../apps/server/src/retrieval/keyword.ts#L54 "支持数量边界、空查询提前返回、时间范围及可见性过滤。")

```mermaid
flowchart LR
  Q[查询文本] --> T[分词]
  T --> B[多路召回]
  B --> F[可见性与时间过滤]
  F --> S[相关性评分与合并]
  S --> R[排序后的原始片段]
```

长度不少于三个字符的词走 FTS5 trigram 与 BM25；更短的词走转义后的 `LIKE`。随后代码符号、全文、短词、记忆证据和知识证据五路候选汇合。这个例子里的 `resolveWidget` 可能由符号路命中，中文说明则可由词法或知识路补充；这是机制示例，不代表仓库中一定存在该符号。参考 [长短词召回 ↗](../../../apps/server/src/retrieval/keyword.ts#L65 "支持长词使用 trigram FTS、短词使用逐词检索的分流机制。") [五路候选 ↗](../../../apps/server/src/retrieval/keyword.ts#L98 "支持代码符号、全文、短词、记忆和知识五个候选分支。")

<a id="scoring-output"></a>
## 如何合并、评分并返回

多路命中不会按“命中路线数量”累加质量。实现先按来源修订统计每个词出现在哪些来源，以文档频率给稀有、区分度高的词更大权重；再在每个片段的最佳局部窗口上计算正文覆盖度，并允许少量纯标题入口。同一片段若被多路命中，只保留最高分，同时记录所有命中路线。参考 [词频权重 ↗](../../../apps/server/src/retrieval/keyword.ts#L105 "支持按来源而非片段统计词频并生成区分度权重。") [相关性融合 ↗](../../../apps/server/src/retrieval/keyword.ts#L114 "支持局部摘要评分、有限标题入口、按片段取最高分并保留路线。")

最后，片段被转换为统一候选：包含相关性分数、命中路线、面向读者的局部摘要、固定修订与片段身份，以及作者、时间、来源等 provenance，再交给 `rankEvidence` 做最终限量和排序。调用方获得的是可展示、也可继续回读核验的证据坐标，而不是一段无来源的生成答案。参考 [候选输出结构 ↗](../../../apps/server/src/retrieval/keyword.ts#L131 "支持最终输出包含摘要、固定身份、来源信息并交由统一排序。")

<a id="boundaries"></a>
## 边界与协作关系

代码符号检索是可选投影：没有 `code_symbols` 表时直接为空；存在时只接受符合标识符形态的名称，并联结当前仓库快照、未移除文件和原始片段。因此 AST 在这里增强定位，但不会建立第二套证据库。参考 [当前符号投影 ↗](../../../apps/server/src/retrieval/keyword.ts#L140 "支持符号索引可选、仅查询当前快照未移除文件并仍返回原始片段。")

记忆检索只读取 `active` 记录。只有 `project_id` 同时被标记为可信时，项目不匹配才会排除；未知或不可信的项目上下文不会缩窄工作区召回。记忆正文按词命中计分、截断到 1–50 条，而源材料搜索的记忆分支还会继续解析证据集合，缺少片段或修订标识的引用会被跳过。参考 [可信项目过滤 ↗](../../../apps/server/src/retrieval/keyword.ts#L163 "支持只读取活动记忆，并仅在项目关联可信且不匹配时过滤。") [记忆评分输出 ↗](../../../apps/server/src/retrieval/keyword.ts#L189 "支持记忆按正文词命中计分、排序、限量并返回来源信息。")

模块关系很集中：分词、正文相关性和摘要选择委托给 `relevance`，最终排序委托给 `ranking`，知识文章命中则由知识检索模块转换回证据候选。若要改变“词怎么切”，应修改共享相关性模块；若要改变多路融合、原文过滤或记忆回溯，则修改本实现相应阶段。参考 [检索协作模块 ↗](../../../apps/server/src/retrieval/keyword.ts#L1 "支持本文件依赖知识证据、相关性和排序模块，并展示分词与摘要的委托边界。")
