# omem 项目能力、运行方式与当前边界

README 汇总 omem 的证据链、语义检索、知识整理、助手治理、部署接入与验证方式；后续实现已替代部分早期限制，但 embedding 状态和局部生成参数仍存在文档冲突。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="product_and_startup"></a>
## 产品定位、启动与检索

omem 将文本、图片、链接和上下文纳入不可变证据链，个人问答、受治理记忆、待办、通知及仓库 Wiki 都复用这条链。当前运行需要 osdk 与可登录的 Agent CLI，不要求 Docker、Redis、Python 或本地大语言模型；个人服务和 Vue 开发模式分别提供约定的本地入口。[项目定位与启动说明 ↗](../../../README.md#L1 "支持统一证据链、运行依赖、默认入口和开发启动方式的概述。")

中文语义检索已接入锁定快照的 BGE-small-zh-v1.5，与全文、记忆和 Wiki 引用召回融合，最终返回当前原始 Fragment；模型缺失时退回全文检索并报告 degraded，运行时不会隐式下载。当前四条中文问法验证仅说明小样本链路可用，不代表全面召回率。[中文语义检索现状 ↗](../../../README.md#L20 "支持 BGE 已接入、固定快照、全文降级和小样本验证边界。")

<a id="knowledge_pipeline"></a>
## 知识整理与仓库 Wiki

知识处理复用 Capture、Source、Revision、Fragment、持久任务与共用角色运行时；材料先分析，再由独立会话复核，正文引用贴近论断并指向固定原文。repo-review 使用独立 SQLite 与端口，但只是本仓库的输入适配器和阅读配置。[统一知识整理与 Wiki 入口 ↗](../../../README.md#L37 "说明知识处理链、独立复核、内联引用以及 repo-review 的隔离运行定位。")

早期复审曾记录代码角色未完全进入统一流水线、检索仍限于关键词。[早期 Code Wiki 架构边界 ↗](../../../docs/implementation/code-wiki-review-2026-09-29.md#L31 "记录角色流水线未完全统一和检索仅支持关键词的早期结论。") 后续流程已实现八类角色共用运行时、通用分析与独立复核，并让知识正文导航回原始 Fragment，因此这些早期结论已被替代。[后续统一知识流程实现 ↗](../../../docs/implementation/knowledge-pipeline.md#L15 "支持共用角色运行时、通用分析复核接口及知识引导原始证据召回已经完成，从而替代早期结论。") 不过 README 第 69 行仍称 embedding 未完成，与前文已接入 BGE 的现状冲突；跨文件调用精确类型解析、周期巡检和跨来源冲突自动修订等限制仍有明确依据。[README 检索能力冲突 ↗](../../../README.md#L67 "支持同一 README 一面声明 embedding 已接入、一面又称其未完成，并保留其他尚未交付的限制。")

<a id="assistant_and_governance"></a>
## 助手操作、记忆刷新与写入治理

来源更新后，旧记忆先停止作为有效依据，再运行提炼、独立复核与确定性应用；排队成功不等于应用完成，不能由新原文支持的结论保持 `needs_review`。[材料变更后的记忆刷新 ↗](../../../README.md#L90 "支持旧依据停用、重核验、needs_review 状态以及排队与实际应用的区别。") 主助手可查询、创建、改期、完成或重开事项，缺少明确时间时会询问；独立 reminder、重复安排、取消状态与外部到期投递仍未接通。[助手事项操作与未完成能力 ↗](../../../README.md#L96 "支持当前可执行的任务操作、时间澄清机制和提醒系统的剩余边界。")

自动学习 worker 通过 extractor、独立 verifier 与确定性策略处理持久任务，Agent 没有领域写权限，最终事实与回执只能由 MemoryService 提交。HTTP 提案评估另有固定引文、来源 head/epoch、owner、冲突范围和 CAS 等明确门禁；材料只能确认两条路径共享 MemoryService 写入边界，不能断言 worker 逐项执行与 HTTP 完全相同的门禁。[持久学习 worker 写入边界 ↗](../../../README.md#L125 "支持自动 worker 的 extractor、独立 verifier、确定性策略流程，以及 Agent 无领域写权限、仅 MemoryService 可提交结果。") [HTTP 提案评估门禁 ↗](../../../README.md#L131 "支持具体门禁明确属于 HTTP evaluate，并说明自动 worker 与 HTTP 路径最终共享 MemoryService 边界。")

<a id="deployment_and_validation"></a>
## 部署、外部接入与验证边界

默认部署只监听 loopback；开放局域网或公网时需要强 token，并建议使用 TLS 反向代理或 SSH 隧道。飞书功能默认关闭，启用后需独立主密钥加密 App Secret、完成同应用 owner pairing，并按实际授权能力运行；shared token 或 App ID 都不能充当团队权限系统。[部署与飞书安全边界 ↗](../../../README.md#L127 "支持单用户网络部署、Bearer token、飞书显式启用、主密钥保存和 pairing 要求。")

项目提供类型检查、测试、构建、浏览器及真实 Agent 流程，真实模型 smoke 会消耗调用；质量数据、原文与预测只保存在本地数据目录。[项目验证与质量数据说明 ↗](../../../README.md#L145 "支持可运行的检查、真实模型调用成本及质量数据不得提交 Git 的边界。") 协议 fixture 只能证明约定流程，不能证明所有外部 CLI 可用；提交本身也不是完整验收，结果还需记录真实退出码、知识覆盖范围和剩余限制。[验收证据要求 ↗](../../../AGENTS.md#L11 "支持 fixture 不能代表全部外部 CLI、提交不等于完整验收，以及需要记录实际退出码、覆盖和剩余限制。")

局部 Wiki 生成在 README 与知识流程中使用 `--target`，而当前实施约定要求 `--only ... --modules`。[局部生成的 target 参数 ↗](../../../docs/implementation/knowledge-pipeline.md#L31 "支持 README 和知识流程文档将 target 记作局部生成入口。") [局部生成的 only 参数 ↗](../../../AGENTS.md#L20 "支持当前实施约定要求使用 only 选择器并附带 modules，构成尚未解释的参数差异。") 现有材料未说明二者是兼容别名还是文档漂移。
