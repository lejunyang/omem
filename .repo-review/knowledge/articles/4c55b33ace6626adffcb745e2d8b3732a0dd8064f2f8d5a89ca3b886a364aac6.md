# omem：把个人材料变成可读、可找、可行动的记忆

omem 将文档、代码、聊天、图片与个人经历纳入统一知识库，通过固定版本、混合检索、问题驱动的 Wiki 和日常事项能力，帮助用户理解材料、找回答案并继续行动。项目已有可用基础，但完整意图路由、跨文件理解和主动助理仍在建设中。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决什么问题

omem 面向材料分散、事后难以找回上下文的个人用户：文档、代码、聊天、图片和经历统一进入同一个记忆系统，代码仅额外使用 AST 定位，不形成另一套知识产品。目标不只是保存信息，而是让人能够读懂来龙去脉、检索答案，并把结果转成后续行动。参考 [统一个人记忆目标 ↗](../../../README.md#L1 "支持 omem 统一组织多类材料、使用 AST 辅助代码定位，以及以读懂、找回和行动为目标的产品定位。")

项目当前处于以阅读体验和真实问题为中心的重构阶段。输入、检索、记忆、问答和事项已有基础，但高质量知识整理与主动助理尚未完整实现；程序检查或模型生成成功也不能直接证明内容对读者有用。当前进度页将“统一搜索”“问题驱动 Wiki”标为首片已实现，同时把持续记忆理解和更广接入列为后续工作。参考 [当前实施阶段 ↗](../../../docs/reader-first/progress.md#L3 "说明哪些能力仅完成首个切片，哪些仍属于后续工作，避免把重构计划写成已经完整实现。")

<a id="workflow"></a>
## 从启动到整理知识

开发模式通过 `osdk run dev` 启动统一界面，接入本仓库材料、已发布知识和既有个人数据；启动本身不会自动生成整库 Wiki。生产模式从“输入材料”开始，运行依赖已安装并登录的 Agent CLI，但不强制要求本地大模型、Docker 或 Python。参考 [启动与运行方式 ↗](../../../README.md#L7 "支持开发模式的数据接入、端口行为、不会自动生成整库 Wiki，以及生产运行的依赖边界。")

典型使用流程是：先保存带固定版本的原始材料，再用全文、中文短词、符号、记忆与知识路径进行召回；助手可以补读原始章节和相邻上下文。需要形成长篇解释时，用户在知识库选择材料、填写主题、阅读对象和问题，系统依次调查、写作并独立复核，成功后发布文章；若生成期间材料发生变化，旧结果不会发布，失败也不会覆盖已有正文。参考 [从材料整理文章 ↗](../../../docs/reader-first/operations.md#L27 "解释用户选材、填写阅读目标、经历调查写作和独立复核的流程，以及材料变化和失败结果的处理方式。")

<a id="boundaries"></a>
## 能力边界与开发入口

原件、检索片段和讲解章节承担不同用途，因此不会用同一种切分直接充当阅读目录。分类路径随文章保存，引用负责回到原文而不充当目录关系。当前检索与助手已经共享召回基础，但完整意图路由和跨文件功能链仍待扩展；日常助理支持交办、等待、改期、完成、取消与站内提醒，自动监听回复、周期回顾和学习卡片尚未提供。参考 [检索、Wiki 与助理边界 ↗](../../../README.md#L38 "支持原文、检索片段和讲解章节的职责区分，并明确检索、知识生成、事项能力及尚未实现的部分。")

实现采用 Vue 3、TypeScript 与公共 UI 组件，Bun 执行 TypeScript 脚本，工作区依赖由 pnpm 和 osdk 管理。个人数据及真实配置不得提交 Git；当前服务是 SQLite 单用户实现，飞书、外部通知和屏幕监听都属于需要单独启用并明确范围的集成，不能据此推断系统已经具备团队隔离或默认的全局监听能力。参考 [技术栈与数据边界 ↗](../../../README.md#L44 "支持前端与脚本技术栈、个人数据保护要求、单用户限制及外部集成需要显式启用等说明。")
