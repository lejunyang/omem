# 提案策略、反馈约束与知识关联验收测试

该测试以临时 SQLite Store 验证固定证据提案的自动应用、保留、延迟、拒绝和人工决策，并覆盖反馈约束、来源刷新、冲突定位及等价关系持久化。更新后的正文收窄了两项旧结论：仅确认“同时转发且身份未知”的用例会保留为来源；等价关系只确认含非空证据引用，未证明合并了两条声明各自的证据。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

## 测试目的与证据构造

测试直接使用 `Store`、`MemoryService`、`FeedbackService` 与 `Proposal` 合同，覆盖服务和持久化的真实切片。[测试使用的服务与合同 ↗](../../../apps/server/tests/proposal-policy.test.ts#L5 "支持测试直接依赖 Store、MemoryService、FeedbackService 和 Proposal 合同的说明。") 每个用例创建临时目录与 SQLite Store，结束后关闭数据库并清理；捕获辅助函数记录身份、验证方式、转发状态和时区。[临时 Store 与捕获来源设置 ↗](../../../apps/server/tests/proposal-policy.test.ts#L10 "支持临时数据库生命周期以及身份、验证方式、转发状态和时区的说明。") 提案证据绑定固定 revision、fragment、精确引文及 Unicode 码点选择器，并携带作用域和派生来源。[固定证据与提案构造 ↗](../../../apps/server/tests/proposal-policy.test.ts#L63 "支持提案绑定 revision、fragment、精确引文、Unicode 选择器和作用域的说明。") Store 当前是单用户 SQLite 底座，初始化迁移、应用仓储、作业仓储、输入聚合器、运行请求仓储和来源档案服务；此前把 `JobRepository` 称为“任务仓储”的结论已被替代。[SQLite Store 初始化组件 ↗](../../../apps/server/src/store.ts#L4 "支持当前单用户 SQLite 定位及 Store 初始化的仓储与服务组件，也用于纠正 JobRepository 的人类可读名称。")

<a id="proposal_policy"></a>
## 提案策略与证据安全边界

明确且已验证的所有者任务会自动应用，产生任务、应用回执、通知意图和首个任务修订；重复评价只明确验证回执标记重复且任务不新增。[明确任务自动应用与重复评价 ↗](../../../apps/server/tests/proposal-policy.test.ts#L160 "支持自动应用后的任务、回执、通知意图和任务修订结果，并限定重复评价实际断言的范围。") A-K02 同时设置“转发、身份未知、无验证者”，该组合只保留为来源且不创建任务或决策；此前将“转发”与“身份未知”分别概括为充分条件的结论已被替代。[转发且身份未知的来源用例 ↗](../../../apps/server/tests/proposal-policy.test.ts#L189 "支持仅对同时转发、身份未知且无验证者的具体组合确认保留为来源，避免把两个条件分别泛化。") 含糊时间会延迟使用，篡改来源 revision 会被拒绝；即使精确引文存在，语义范围被扩大也会拒绝。[语义范围泛化拒绝 ↗](../../../apps/server/tests/proposal-policy.test.ts#L245 "支持精确引文存在时，语义复核发现适用范围被扩大仍会拒绝。")

跨来源冲突保留既有 active memory 并等待决策；若评审后来源 head 改变，批准会以 `STALE_DECISION` 失败。影响超限、procedure 与仅凭图片推断的成功结果受到更保守的门控。[冲突决策、影响门槛与图片推断 ↗](../../../apps/server/tests/proposal-policy.test.ts#L259 "支持跨来源冲突、过期批准、影响上限、procedure 审核和图片推断的保守策略。") 来源刷新保留旧 revision、使依赖记忆失效并入列刷新作业，同时阻止过期版本恢复。[来源刷新与恢复保护 ↗](../../../apps/server/tests/proposal-policy.test.ts#L426 "支持不可变旧 revision、依赖失效、刷新作业入列以及恢复操作的新鲜度保护。")

<a id="feedback"></a>
## 反馈约束的权威等级与作用域

经认证、由原始证据支持且处于相同作用域的负责人纠正可形成 confirmed constraint，并把下一候选任务的负责人由 A 改为 B；应用后两个任务 revision 都被保留，说明修正通过新修订生效而非覆写历史。[认证反馈修正负责人 ↗](../../../apps/server/tests/proposal-policy.test.ts#L473 "支持 confirmed correction 修改后续候选，并以新任务 revision 保存负责人变化及证据。")

“有用”反馈属于弱信号，重复事件会去重；派生摘要形成的事实纠正仍为弱信号且不会被召回。[弱反馈、去重与派生摘要 ↗](../../../apps/server/tests/proposal-policy.test.ts#L561 "支持反馈事件去重，以及有用性反馈和派生事实摘要保持非权威、不可召回。") ACL 或自动审批类建议保持 shadow、inactive。隔离用例仅在 workspace 与 subject 不变时切换 project，因此只能证明项目作用域隔离，不能外推为所有作用域维度均已独立验证。[项目隔离与影子策略 ↗](../../../apps/server/tests/proposal-policy.test.ts#L597 "支持项目间纠正隔离及 ACL 类策略建议保持 shadow、inactive，同时限定实际变化的作用域维度。")

<a id="knowledge_matching"></a>
## 冲突、等价关系与未覆盖范围

冲突用例先写入无关记忆，再写入“服务 A 已启用重试”，最后提交相反声明；结果关联真正相关的记忆，并断言冲突 revision、匹配理由、已有陈述、共享词和提案侧证据引用。它没有断言已有一侧证据引用非空，因此不能声称双方证据链均已验证。[真实冲突记忆关联 ↗](../../../apps/server/tests/proposal-policy.test.ts#L657 "支持冲突关联到相关记忆，并准确限定已有陈述、共享词和提案侧证据引用等实际断言。")

相同文本位于不同项目时不会建立等价关系；同一作用域、不同来源的相同声明会创建第二条记忆，并持久化可从两端查询的等价关系。测试只断言 `evidenceRefs` 非空，未核对其同时包含两条声明各自的证据；此前“包含合并证据集合”的结论已被替代。[跨项目隔离与等价关系持久化 ↗](../../../apps/server/tests/proposal-policy.test.ts#L687 "支持不同项目不建立等价关系，以及同一作用域等价关系可双向查询且仅确认其证据引用非空。") 当前材料也未覆盖通知实际送达、并发评价或审批竞争、注入式数据库故障回滚、跨 workspace 权限执行及刷新 worker 的最终完成。
