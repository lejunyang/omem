# 开发知识导入与固定证据保留

这组测试验证仓库知识并入个人记忆时不会替换已有捕获，重复导入保持幂等；来源更新后文章会失去当前性，但旧版固定证据仍可追溯。父子文章场景验证同次更新最终生效，而顺序无关的等待与多轮恢复能力由恢复器实现提供。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="personal-memory-import"></a>
## 仓库知识并入个人记忆

测试先从仓库 README 生成材料和已复核文章，再在另一套个人 Store 中创建日记并导入开发知识。导入后，仓库文章处于当前状态，固定摘要能够解析，个人日记也仍然存在。这说明该流程把仓库知识加入个人库，而不是用仓库内容替换已有捕获。参考 [个人记忆与仓库知识共存 ↗](../../../apps/server/tests/development-knowledge.test.ts#L16 "支持仓库文章导入后可读取，同时个人日记仍被保留的结论。")

测试随后记录 revision 数量并重复导入，数量保持不变，验证相同输入在再次启动时不会不断制造重复修订。参考 [重复导入保持幂等 ↗](../../../apps/server/tests/development-knowledge.test.ts#L24 "支持再次执行相同导入后 revision 数量不增加。")

<a id="fixed-evidence"></a>
## 来源变化与历史证据

当 README 更新后再次导入，原文章不再被视为当前版本；但通过旧材料键和摘要仍能读取文章当时引用的内容。重新恢复这份历史文章也不会把它错误提升为当前知识。由此可见，**当前性**反映文章是否仍匹配现有来源，**可追溯性**则保留文章形成时的固定证据，两者彼此独立。参考 [旧证据保留与当前性变化 ↗](../../../apps/server/tests/development-knowledge.test.ts#L28 "支持来源更新使文章失去当前性，但旧材料仍可解析且恢复历史文章不会改变当前性的结论。")

<a id="article-dependencies"></a>
## 父子文章的同次更新

第二个场景建立两级依赖：子文章引用原始材料，父文章引用子文章的特定修订，并分别保存为子、父资产文件。参考 [父子文章依赖构造 ↗](../../../apps/server/tests/development-knowledge.test.ts#L47 "说明子文章依赖材料、父文章依赖子文章修订，并分别写入两个资产文件。")

测试先导入旧版，再发布新版父子文章并重新导入；最终父文章摘要更新，父文章与子文章都处于当前状态。因此，这个场景验证的是**相关父子新版能够在同一次启动导入中最终生效**。参考 [父子新版最终生效 ↗](../../../apps/server/tests/development-knowledge.test.ts#L55 "支持重新导入后父文章摘要更新，父子文章均处于当前状态。")

恢复器本身会把资产放入待处理集合：若父文章要求的子修订尚不可用、但对应子资产仍在等待恢复，就暂缓父文章；每轮有进展时继续扫描，直到处理完成、无进展或达到轮次上限。该实现提供了不依赖单次遍历先后顺序的恢复机制，但现有测试没有单独断言发生了等待或执行了多轮扫描。参考 [依赖等待与多轮恢复 ↗](../../../apps/server/src/knowledge/artifacts.ts#L40 "解释恢复器如何暂缓依赖未满足的父文章，并通过多轮扫描继续处理待定资产。")

<a id="test-boundary"></a>
## 测试能够证明什么

这些场景在临时目录和两套本地 Store 中执行，结束时关闭数据库并清理资源，证明的是单进程、本地存储条件下的行为。参考 [临时存储测试环境 ↗](../../../apps/server/tests/development-knowledge.test.ts#L39 "支持测试使用临时目录和两套 Store，并在结束时关闭与清理资源。") Store 也明确以 SQLite 作为单用户基础，团队级权限隔离仍属于后续迁移范围，不能从本测试外推出租户安全能力。参考 [单用户 SQLite 边界 ↗](../../../apps/server/src/store.ts#L4 "说明 Store 当前是单用户 SQLite 基础，团队权限执行仍是后续迁移事项。")

测试中的生成与复核来源是 fixture，并未实际调用外部模型或 Agent CLI；同时尚未覆盖损坏资产、缺失子文章、循环依赖、超过轮次上限以及未通过复核的产物。恢复器会把无法继续处理的待定项作为 `missing` 返回，但当前实现片段只持久化已进入处理分支的结果，不能据此断言 `missing` 一定写入导入状态表。参考 [待定资产与导入状态记录 ↗](../../../apps/server/src/knowledge/artifacts.ts#L52 "支持无进展时停止扫描、将剩余项作为 missing 返回，并区分已处理结果的数据库写入位置。")
