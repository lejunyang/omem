# memory · 模块理解

memory 模块负责提案幂等持久化、证据与来源新鲜度校验、同域知识匹配、注意力门控及经 Store application 落地；反馈约束另具有限改写能力，但现有材料未证明其已接入主提案管线。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="role-and-evidence"></a>
## 职责与可信基础

该模块是候选任务或知识进入应用阶段前的治理边界。提案以稳定摘要去重，同一标识对应不同内容会冲突；持久化时还记录证据所读来源的修订与有效性纪元。[提案去重与来源读取快照 ↗](../../../apps/server/src/memory/service.ts#L135 "支持提案按稳定摘要幂等持久化，并保存证据读取时来源修订和有效性纪元的说明。") 文本证据核对来源修订、Unicode 码点区间和精确引文，图片证据则核对修订中的资产引用及资产是否存在。[确定性证据校验 ↗](../../../apps/server/src/memory/service.ts#L201 "支持文本精确区间、来源修订和图片资产引用均需校验的论断。") 模块提供比较当前 head、纪元与读取快照的新鲜度检查能力；实际应用钩子和人工决定处理都会调用它，避免依据变化后继续应用。[来源新鲜度检查能力 ↗](../../../apps/server/src/memory/service.ts#L255 "说明模块能够比较读取快照与当前来源 head、有效性纪元，并在不一致时判为陈旧。")[Store application 与应用前检查 ↗](../../../apps/server/src/memory/service.ts#L1141 "证明应用流程调用 Store 接口，并在应用钩子中检查来源新鲜度、决定状态及 procedure 授权。")[人工决定处理 ↗](../../../apps/server/src/memory/service.ts#L1660 "支持人工决定的摘要、操作者、幂等、期限和来源检查，以及批准后应用单个绑定提案的流程。")

<a id="matching-and-policy"></a>
## 匹配与注意力治理

创建 claim 时只检查同工作区、同项目的活跃知识：规范化陈述相同时按来源是否重叠区分重复与独立等价；只有核验结果指示冲突，且候选在时间上重叠、共享内容词并具有相反极性时，才记录冲突及双方证据链。[同域知识匹配与冲突关联 ↗](../../../apps/server/src/memory/service.ts#L417 "支持工作区和项目过滤、重复与等价区分，以及按时间、共享词项和相反极性选择冲突对象。") AttentionGate 将无效或自相矛盾证据拒绝、噪声忽略。跨源分歧只要覆盖活跃目标或阻塞当前任务之一就升级请求决定；仅当两者都不满足时才延后。图片推断、procedure 和部分软不确定性通常保留或延后，而非直接应用。[AttentionGate 策略分支 ↗](../../../apps/server/src/memory/service.ts#L704 "支持各治理结果及跨源冲突仅在目标活跃或阻塞当前任务时升级的精确条件。")

<a id="application-and-batch"></a>
## 应用、决定与批量边界

应用阶段把已解析的 Proposal 交给 Store 的任务或记忆 application，并附带通知元数据和事务钩子；此处可见的是接口调用，不能据此断言 Proposal 的上游生产者或 Store 内部采用不可变修订。procedure 未获所有者批准时禁止应用。[Store application 与应用前检查 ↗](../../../apps/server/src/memory/service.ts#L1141 "证明应用流程调用 Store 接口，并在应用钩子中检查来源新鲜度、决定状态及 procedure 授权。") 人工决定校验摘要、操作者、请求幂等性、期限和来源新鲜度，批准后才应用其绑定提案。[人工决定处理 ↗](../../../apps/server/src/memory/service.ts#L1660 "支持人工决定的摘要、操作者、幂等、期限和来源检查，以及批准后应用单个绑定提案的流程。") 批量入口先按受影响记忆与新实体的去重并集计算总影响；超预算时仅停放所有原本会自动应用的提案，其他提案仍按各自策略处理。预算内也只是逐项运行单提案原子管线，并不保证每项都会应用。[批量影响门控 ↗](../../../apps/server/src/memory/service.ts#L1405 "支持去重计算整体影响、超预算时仅停放原本会自动应用的提案，以及预算内逐项运行单提案管线的边界。") 这替代了“超预算整批无差别停放、预算内全部应用”的旧结论。

<a id="feedback-and-limits"></a>
## 反馈能力与当前限制

反馈服务按工作区、生产者和事件标识保证幂等，并依据身份验证、原始生产者、证据完整性及是否涉及受保护策略，将约束分为 confirmed、weak 或 shadow。[反馈可信度分级 ↗](../../../apps/server/src/memory/service.ts#L1869 "支持反馈事件幂等、身份与证据条件，以及 confirmed、weak、shadow 强度划分。") confirmed 约束目前只会在显式调用改写方法时处理 task 的负责人分配；其他提案原样返回。[确认约束的有限应用 ↗](../../../apps/server/src/memory/service.ts#L1957 "支持 confirmed 约束按作用域召回，且当前改写仅覆盖任务负责人分配的能力边界。") 因而它具备窄范围的约束召回与改写能力，但材料没有显示主提案评估流程调用该方法，不能再表述为反馈已接入端到端治理链。冲突识别仍依赖确定性词项与极性启发式，批量汇总决定获批后的整批执行语义也尚未展示。
