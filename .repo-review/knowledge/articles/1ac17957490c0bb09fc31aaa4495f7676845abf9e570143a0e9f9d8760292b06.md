# memory · 模块理解

memory 模块是固定证据进入记忆与任务修订链前的治理层：它保存并校验提案，复查来源时效，匹配重复、等价与冲突知识，按影响预算分流，再委托 Store 应用；同时承接人工决定、任务命令、历史恢复和反馈约束。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="role_and_flow"></a>
## 职责与主流程

该模块位于原始证据与持久化记忆、任务之间。`evaluate` 先解析并保存提案，按摘要复用已有应用回执，再执行确定性证据校验、评估留档、知识匹配与策略分流；只有最终允许物化的变更才交给 Store。[提案评估主流程 ↗](../../../apps/server/src/memory/service.ts#L1282 "支持提案持久化、回执复用、证据校验、知识匹配、策略分流与最终应用的执行顺序。") 保存提案时还记录所读来源的 revision 与 validity epoch，应用或决定前重新比对当前 head 和 epoch，避免来源变化后继续采用旧结论。[来源读取与时效复查 ↗](../../../apps/server/src/memory/service.ts#L170 "支持保存来源 revision 和 validity epoch，并在后续应用或决定前与当前来源状态比较。")

提案身份依赖稳定摘要：对象键递归排序、忽略 `undefined`，再对规范 JSON 计算 SHA-256。[稳定摘要实现 ↗](../../../apps/server/src/storage/digest.ts#L3 "支持递归规范化对象键、忽略 undefined，并对规范 JSON 计算 SHA-256。") 其作用应限定为内容身份和相关去重；任务命令与人工决定仍分别使用 requestId、applicationId 等请求身份。

<a id="governance"></a>
## 知识匹配与注意力控制

新建 claim 只匹配同 workspace、同 project 的活跃知识：同陈述且来源重叠为重复，独立来源得到同一陈述为等价；冲突还要求复核标记矛盾，并满足实体词重叠、谓词极性相反和有效期相交。[新建知识匹配规则 ↗](../../../apps/server/src/memory/service.ts#L452 "支持作用域过滤以及重复、等价和冲突匹配的具体条件。") 重复项不创建新记忆；等价项可生成独立记忆并登记关系；冲突则保存争议、延后使用，不静默覆盖现行知识。[匹配结果处理 ↗](../../../apps/server/src/memory/service.ts#L1599 "支持冲突延后、等价项创建并登记关系，以及重复项保留但不新建实体的差异化处理。")

一般策略会拒绝无效或被证据反驳的提案，将噪声、图片推断、procedure、未验证任务归属及软不确定性分别忽略、保留为来源或延后，仅在影响超限或关键跨来源选择时升级。[策略与注意力门控 ↗](../../../apps/server/src/memory/service.ts#L739 "支持不同证据质量、不确定性、任务归属、procedure、跨来源变化和影响预算的分流规则。") 批量影响按受影响记忆与新实体的去重并集计算。超限时，普通 `auto_apply` 分支以及原本会创建新等价记忆的提案会被停放；不物化新实体的重复项仍保留，冲突项仍进入延后。[普通批量门控分支 ↗](../../../apps/server/src/memory/service.ts#L1380 "支持批量超限时只把普通 auto_apply 结果改为 awaiting_decision，并保持拒绝、忽略、延后和保留结果不变。")[匹配项的批量处理差异 ↗](../../../apps/server/src/memory/service.ts#L1599 "支持等价项在超限时停放、重复项仍保留且不标记 batchDeferred、冲突项继续延后的限定结论。") 这替代了“超限时停放所有原本会自动应用的提案”的过宽结论。

<a id="tasks_feedback"></a>
## 任务、恢复与反馈

显式任务命令要求证据来自经验证、未转发且非转述的所有者原始材料，并通过 Store 的任务应用入口复用修订和回执链。[所有者任务命令 ↗](../../../apps/server/src/memory/service.ts#L86 "支持所有者原始证据要求、任务状态限制以及通过 Store 应用任务的流程。") 等待对象与时间原始表达必须出现在当前用户文本中，之后才规范化时间；任务状态、动作、follow-up 字段及 IANA 时区由共享合同约束。[跟进内容校验 ↗](../../../apps/server/src/tasks/follow-up.ts#L5 "支持等待对象和时间原始表达必须来自当前用户文本，并在校验后规范化时间。")[共享任务流合同 ↗](../../../packages/contracts/src/task-flow.ts#L3 "支持任务状态、动作、follow-up 字段、时间格式和 IANA 时区约束由共享合同定义。")

历史恢复检查当前版本、目标修订和依赖状态，再通过应用入口创建新的活跃修订，保留旧历史。[历史记忆恢复 ↗](../../../apps/server/src/memory/service.ts#L1789 "支持版本和依赖检查，并通过应用入口生成新修订而保留历史版本。") 反馈按事件幂等保存并分为 weak、shadow 或 confirmed；当前自动应用 confirmed 修正只覆盖任务 owner。[反馈约束处理 ↗](../../../apps/server/src/memory/service.ts#L1906 "支持反馈事件幂等、约束强度分级，以及当前仅自动修正任务 owner 的实现范围。") 因而反馈约束、争议和策略记录属于治理数据，不能等同于已进入记忆或任务修订链的事实。

<a id="limits"></a>
## 应用边界与当前限制

`apply` 在 Store 应用前复查来源和决定状态，并在 after hook 更新 proposal 与 decision；但材料没有 Store 应用实现，尚不能确认实体修订、回执、通知及这些状态是否处于同一原子事务。[Store 应用与状态钩子 ↗](../../../apps/server/src/memory/service.ts#L1176 "支持应用前后的来源、决定及提案状态处理，同时限定当前材料无法证明 Store 内部完整事务边界。")

批量确认卡保存全部停放提案的摘要标识和聚合证据，但数据库决定行锚定代表提案。[批量确认卡与代表提案锚点 ↗](../../../apps/server/src/memory/service.ts#L1522 "支持批量卡保存全部停放提案摘要标识和聚合证据，同时决定行只锚定代表提案摘要。") `decide` 批准时也只按该行的 `proposal_digest` 重建并应用一个提案，未遍历 `batchProposalDigests`。[人工决定批准入口 ↗](../../../apps/server/src/memory/service.ts#L1697 "支持批准时仅按决定行的 proposal digest 重建并应用单个提案，未遍历批量摘要集合。") 因此“批量批准会一次应用全部停放提案”的结论已被替代：当前实现只证明卡片表达了整体应用意图，未证明其余提案已有协调、重试或失败恢复路径。
