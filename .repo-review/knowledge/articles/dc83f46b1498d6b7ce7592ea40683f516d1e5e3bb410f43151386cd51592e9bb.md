# AssessmentBatch.v1 核验输出合同

该 JSON Schema 规定 verifier 批量核验结果的顶层身份、逐提案字段、摘要格式和判定枚举，形成严格的数据交换边界，但未定义各 reason_code 的受控词表。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="batch_shape"></a>
## 批次身份与严格结构

合同采用 JSON Schema 2020-12，并将对象限制为不得出现额外属性。顶层必须包含版本、任务标识、固定为 `verifier` 的角色标识以及 assessments 数组；版本常量为 1。[AssessmentBatch 顶层结构 ↗](../../../packages/agent-runtime/roles/verifier/1/output.schema.json#L1 "支持 Schema 版本、禁止额外字段、必填顶层字段及固定角色身份的说明。") 这使宿主能够把输出绑定到具体任务和角色，并拒绝字段漂移，但材料只展示合同定义，没有展示验证器是否在持久化或消费前实际执行该 Schema。

<a id="assessment_semantics"></a>
## 单项核验的双重判定

每项 assessment 必须携带提案标识、64 位小写十六进制摘要、引文或资产判定、语义判定、原因代码、解释和缺失上下文。[逐提案核验必填字段 ↗](../../../packages/agent-runtime/roles/verifier/1/output.schema.json#L13 "支持每项 assessment 的标识、摘要、双重 verdict、原因与缺失上下文字段要求。") 引文层判定区分有效、无效和歧义；语义层仅允许“支持、矛盾、证据不足、需要限定范围”四种结果。[核验判定枚举 ↗](../../../packages/agent-runtime/roles/verifier/1/output.schema.json#L28 "支持引文或资产判定与语义判定各自允许的状态集合。")

这种分离避免把定位正确直接等同于语义支持，也允许明确记录缺失背景。限制是 `reason_code` 目前仅约束为任意字符串，`reason` 与 `missing_context` 也没有长度或词表约束，跨实现的一致性仍依赖额外约定。
