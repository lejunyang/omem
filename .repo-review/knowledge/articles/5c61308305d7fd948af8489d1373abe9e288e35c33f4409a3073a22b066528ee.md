# 服务启动与优雅关闭入口

该入口负责把配置加载、应用装配、网络监听和进程信号处理串成服务生命周期；具体业务能力由应用构建模块装配，入口本身不注册路由或创建存储。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决什么问题

该文件是服务进程的启动入口：先读取运行配置，再构建 Fastify 应用，最后按配置的主机和端口开始监听，并输出可访问地址。它把“准备应用”和“开放网络端口”明确分开，使业务路由、存储及助手能力无需堆进入口文件。参考 [服务启动顺序 ↗](../../../apps/server/src/main.ts#L1 "支持配置加载、应用构建、监听和日志输出组成串行启动流程，并显示这些步骤使用顶层 await。")

配置至少包含用户档案、通知策略、检索、捕获目录和学习开关等结构；不过现有材料只展示了校验 schema，没有展示 `loadConfig` 如何选择配置文件或环境变量，因此这里不能确认配置来源与覆盖优先级。延伸阅读：[运行配置结构 ↗](../../../apps/server/src/config.ts#L18 "说明配置包含档案、通知、检索、捕获目录和学习设置，同时限定当前证据仅覆盖 schema。")

<a id="startup-flow"></a>
## 从配置到可访问服务

启动过程是严格串行的：

```mermaid
flowchart LR
  A[加载配置] --> B[构建应用]
  B --> C[监听主机与端口]
  C --> D[输出访问地址]
```

入口通过顶层 `await` 等待应用构建和监听完成；任一步抛错都会阻止后续步骤执行，因为文件中没有本地捕获逻辑。参考 [服务启动顺序 ↗](../../../apps/server/src/main.ts#L1 "支持配置加载、应用构建、监听和日志输出组成串行启动流程，并显示这些步骤使用顶层 await。") 应用构建阶段会创建 Fastify、数据存储、运行记录和记忆服务，并选择可用的 ACP 助手档案；这说明入口只负责编排生命周期，实际能力集中在 `buildApp`。参考 [应用能力装配 ↗](../../../apps/server/src/app.ts#L47 "支持 buildApp 创建 Web 应用、存储及核心服务，并选择 ACP 助手档案的论断。")

当绑定地址不是本机回环地址时，构建器要求配置访问令牌，否则直接拒绝启动，避免无认证服务暴露到网络。参考 [非本机绑定保护 ↗](../../../apps/server/src/app.ts#L53 "支持非回环地址必须配置令牌，否则构建阶段拒绝启动的安全边界。")

<a id="shutdown-boundaries"></a>
## 关闭行为与边界

进程收到 `SIGINT` 或 `SIGTERM` 后，会调用 Fastify 的 `close()`，待关闭成功再以状态码 0 退出；这为已建立的服务资源提供了统一收尾入口。参考 [进程信号关闭流程 ↗](../../../apps/server/src/main.ts#L7 "支持 SIGINT 和 SIGTERM 触发应用关闭，并在成功后正常退出的行为。")

当前处理器只注册成功分支，没有展示关闭超时、二次信号或 `app.close()` 失败后的兜底策略。因而从材料可确认正常关闭路径，却不能确认异常关闭是否会记录错误或强制退出。入口也没有直接启动后台 worker；这些任务是否随 `buildApp` 创建、何时停止，需要结合构建函数其余未提供代码判断。
