# 数据库迁移与应用原子性验收测试

该测试以真实临时 SQLite 文件覆盖旧库升级、迁移中断恢复、未来版本拒写，以及记忆与任务应用失败后的可观察回滚和重复投递，验证数据库演进不会破坏既有证据、任务与通知链路。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-fixture"></a>
## 测试目标与历史基线

该文件针对数据库持续演进的兼容性风险：升级既要保留既有数据，也不能留下可观察的半完成状态。测试手工建立 `user_version=1` 的旧 schema，写入两代 revision、固定 fragment、引用边、任务及图片资产；每例使用独立临时目录并在结束后清理。[旧版数据库夹具与临时目录 ↗](../../../apps/server/tests/migrations.test.ts#L25 "支持测试使用独立临时目录、手工旧 schema 和固定历史数据建立迁移基线。")

被测入口并非孤立 SQL。测试直接导入迁移器、`Store`、应用构建器和应用 DTO，形成迁移、存储初始化与 HTTP 读取的集成链路。[迁移测试的模块依赖 ↗](../../../apps/server/tests/migrations.test.ts#L12 "证明测试直接连接应用构建器、Store、迁移器与 repository 类型。") `Store` 打开 SQLite 后先执行迁移，再创建各 repository；初始化失败则关闭连接并继续抛错。[Store 初始化与迁移流程 ↗](../../../apps/server/src/store.ts#L38 "证明 Store 打开数据库后先执行迁移，再初始化 repositories，并在失败时关闭连接。")

## 历史数据与旧 API 兼容

A-M01 从带历史数据的 v1 文件启动 `Store`。升级到版本 18 后，用例确认旧 revision 与 fragment 的固定身份、旧正文及原始序列化 body 未变，并检查图片资产、fragment 引用边、任务证据与版本、当前 head、补建的 `source_state` 及外键完整性。[历史数据保持断言 ↗](../../../apps/server/tests/migrations.test.ts#L162 "支持升级后对旧 revision、fragment、资产、引用、任务、当前 head、source_state 和外键的检查。") 材料没有断言 head revision 的 `previousId` 或 fragment ordinal，因此这些字段不属于已验证结论。

第一个 `Store` 关闭后，测试对同一数据目录调用 `buildApp`，再通过真实应用注入请求读取旧 revision 和旧任务。[旧 revision 与任务的 HTTP 读取 ↗](../../../apps/server/tests/migrations.test.ts#L219 "支持关闭首个 Store 后，通过应用请求读取同一数据目录中的旧 revision 和任务。") 更正此前“创建同一 `Store`”的表述：`buildApp` 实际为该数据目录创建一个新的 `Store` 实例，所以 HTTP 验证会再次经过迁移与存储初始化，但并非复用先前实例。[应用启动创建新 Store ↗](../../../apps/server/src/app.ts#L46 "证明 buildApp 根据 dataDir 新建 Store 实例，支持对先前实例身份表述的更正。")

<a id="migration-safety"></a>
## 迁移回滚、重启与版本边界

A-M02 通过 `beforeCommit` 钩子在版本提交前制造异常。v1 升 v2 失败后，版本号、迁移表和新增列保持原状；随后两次重启都能升级到版本 18，迁移记录以及表、索引数量不重复增长，覆盖单步回滚、恢复与重复启动。[迁移中断回滚与重复启动 ↗](../../../apps/server/tests/migrations.test.ts#L252 "支持提交前故障不留下部分迁移，以及后续重启完成升级且 schema 不重复增长。") 用例还显式构造 v2 至 v8、v10 等部署落点，抽查新增结构及飞书目标状态、投递关联等数据转换。[历史版本落点与数据转换 ↗](../../../apps/server/tests/migrations.test.ts#L303 "支持从 v2 至 v8、v10 等落点升级，并抽查代表性结构和数据迁移。")

A-M03 构造版本 99 的未来数据库，要求启动抛出专用错误，并确认数据库文件字节、标记数据、版本和 schema 均未改写。[未来 schema 拒写测试 ↗](../../../apps/server/tests/migrations.test.ts#L616 "支持版本 99 数据库被拒绝且文件、标记数据、版本和 schema 保持不变。") 这与迁移模块声明当前仅支持版本 18、遇到更高版本拒绝写入的合同一致。[支持版本与拒写错误 ↗](../../../apps/server/src/storage/migrations.ts#L4 "说明迁移器当前支持版本 18，并为更高版本定义拒绝写入错误。")

<a id="application-behavior"></a>
## 应用回滚、幂等结果与覆盖边界

A-M04 用 SQLite trigger 分别令 `changes` 与 `delivery_intents` 插入失败。失败后，相关实体、revision、receipt、change、notification 和 delivery intent 均无残留；移除故障后，同一任务首次应用成功，重放返回相同实体与 change 身份并标记 `duplicate`，各相关表仍只有一行。[应用失败回滚与重复投递 ↗](../../../apps/server/tests/migrations.test.ts#L647 "支持失败后没有可观察的部分记录，以及相同任务重放返回 duplicate；不用于断定内部事务实现。") 更正此前“这些写入处于同一事务”的实现性结论：现有材料只能证明这些写入**对调用方呈现原子回滚行为**，不能排除内部使用补偿清理。

输入元数据包含 workspace、application ID、proposal digest、generation 与投递目标；任务和记忆 DTO 还定义版本、证据、状态及 follow-up 等字段。[应用元数据测试输入 ↗](../../../apps/server/tests/migrations.test.ts#L650 "支持测试输入包含 workspace、application ID、摘要、generation 和投递上下文。")[Repository 应用类型合同 ↗](../../../apps/server/src/storage/repository.ts#L8 "支持元数据、记忆、任务和回执的字段语义，同时说明所给片段未展示具体幂等实现。") 但提供的 repository 片段只有类型合同，没有 `applyTask`、`applyMemory` 或回执表约束，因而不能确定实际幂等键、事务边界及跨连接并发安全性。当前测试也未覆盖进程在提交瞬间终止、磁盘损坏或全部中间 schema 的逐版本业务回填。
