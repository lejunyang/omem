# Lark 凭据加密存储

以本地文件加密保存 Lark 应用凭据，并提供受约束的引用、读取、删除和配对码摘要能力；实现强调密钥长度、文件权限、认证加密与落盘可靠性，但尚未体现密钥轮换、解密载荷结构校验及异常恢复策略。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-key"></a>
## 用途与密钥边界

该模块避免把 Lark 的 `appId` 和 `clientSecret` 直接写入业务数据：真实凭据存放在独立加密目录，调用方持有 `lark:` 引用。字符串密钥可按 64 位十六进制或 Base64 解析，最终必须恰好为 32 字节；构造时目录权限被收紧为 `0700`。[密钥解析与存储目录初始化 ↗](../../../apps/server/src/integrations/lark/secret-store.ts#L22 "支持密钥编码、32 字节长度约束以及存储目录权限边界的说明。") 环境入口要求配置 `OMEM_SECRET_KEY`，并将存储位置固定为数据目录下的 `secrets`。引用校验只保证前缀后是由十六进制字符或连字符组成的 36 字符受限字符串，并不验证标准 UUID 分组；但该字符集结合固定后缀可阻止引用直接注入路径分隔符。[环境密钥入口与引用路径校验 ↗](../../../apps/server/src/integrations/lark/secret-store.ts#L47 "支持环境变量要求、secrets 目录位置，以及引用实际只校验受限字符集和固定长度的论断。")

<a id="write-read-flow"></a>
## 写入与读取流程

`put()` 自身使用 `randomUUID()` 生成标准引用和临时文件名，以随机 12 字节 IV 执行 AES-256-GCM。版本、算法、IV、认证标签和密文先写入排他创建且权限为 `0600` 的临时文件，完成文件同步后再重命名、调整权限并尝试同步目录，以降低半写文件和目录项未持久化的风险。[凭据认证加密与原子落盘 ↗](../../../apps/server/src/integrations/lark/secret-store.ts#L72 "解释标准 UUID 引用、随机 IV、AES-256-GCM 封装、临时文件权限、文件同步和重命名组成的写入流程。") 读取端先检查版本与算法，再解码 IV、标签和密文并完成认证解密；有效形状数据发生密钥、密文或标签不匹配时通常会在认证过程中抛错，而格式畸形的数据也可能更早在解码或解密初始化阶段失败。成功解密后仅以类型断言将 JSON 视为凭据对象，没有运行时字段校验。[密文格式检查与认证解密 ↗](../../../apps/server/src/integrations/lark/secret-store.ts#L102 "支持读取端的版本与算法检查、解码和认证解密流程，并表明解密后的 JSON 仅通过类型断言成为凭据对象。")

<a id="boundaries-and-relations"></a>
## 删除、持久化限制与配对码摘要

目录同步通过打开目录并调用 `fsync` 实现，但异常被统一忽略，以兼容不支持该操作的平台，因此耐崩溃保证依赖具体文件系统与操作系统。[目录同步兼容处理 ↗](../../../apps/server/src/integrations/lark/secret-store.ts#L59 "说明目录 fsync 的实现，以及同步失败被忽略所形成的平台相关持久化限制。") 删除不存在的引用不会报错；文件存在时则删除并同步目录。配对码摘要使用同一主密钥执行 HMAC-SHA256，并在消息前加入带版本的域分隔前缀；这只隔离配对码摘要的消息域，不能证明摘要与凭据加密使用了独立派生密钥。[凭据删除与配对码摘要 ↗](../../../apps/server/src/integrations/lark/secret-store.ts#L126 "支持幂等删除、删除后的目录同步，以及复用主密钥并加入消息域分隔前缀的 HMAC-SHA256 摘要行为。") 当前材料也未展示调用层如何处理解密、JSON 解析和文件系统错误。
