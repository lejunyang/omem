# 代码材料分析与证据化写作规范

该文档定义代码分析角色的写作与引用约束：面向首次接触项目的读者解释代码用途、流程、边界和模块关系，并以固定材料行号支撑论断。它是一份角色规范，不是代码分析能力已经运行或通过测试的实现证据。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决什么问题

这份规范用于把源代码材料整理成可阅读、可追溯的中文 Wiki。分析不能停留在函数清单或数量统计，而应说明代码解决的实际问题、核心流程、边界条件及模块关系；AST 只提供定位线索，跨文件调用仍需源代码证据，无法确认时应明确标注。对于测试文件，还要区分已有断言与尚未覆盖的行为。参考 [代码分析职责 ↗](../../../packages/agent-runtime/roles/code-analyst/1/skills/omem-code-analyst/SKILL.md#L2 "支持代码分析需解释问题、流程、边界和模块关系，并区分 AST 线索、跨文件证据及测试覆盖范围的论断。")

需要注意，这些内容描述的是**分析角色应如何工作**，并不证明相关分析流程、AST 能力或跨文件关系识别已经在运行时实现。

<a id="evidence-contract"></a>
## 证据与输出合同

分析结果必须覆盖任务指定的全部目标，并保持文档键与目标键完全一致。正文采用 Markdown，每节至少嵌入一处引用；引用只能指向任务提供的材料或文章，材料引用使用真实行号并由宿主复制精确原文。遇到背景不足、歧义或需要选择的事项，应写入结构化问题，而不能用无依据的推断补齐。参考 [输出与引用规则 ↗](../../../packages/agent-runtime/roles/code-analyst/1/skills/omem-code-analyst/SKILL.md#L10 "支持目标覆盖、键一致、节内引用、固定材料行号和结构化问题等输出合同。")

这一合同把“论断—引用—待确认问题”绑定在同一输出中，便于后续独立复核，但文档本身没有给出宿主提取引文、校验 JSON 或处理失败的实现细节。

<a id="reader-oriented-writing"></a>
## 面向读者组织知识

成文应先交代使用场景与要解决的问题，再解释流程、关键概念和限制，并以功能命名标题。只有多阶段关系确实需要可视化时才使用简洁的 Mermaid 图；正文即使移除引用标签也必须保持语句通顺，证据标签应自然放在相关句段末尾。参考 [读者导向写作 ↗](../../../packages/agent-runtime/roles/code-analyst/1/skills/omem-code-analyst/SKILL.md#L18 "支持文章应从场景和问题出发、按需使用图示并让引用自然贴近论断的写作要求。")

因此，这份规范强调的是可理解性与证据贴近论断，而非展示内部标识、日志或校验计数。它约束知识文章的表达方式，却没有规定具体代码语言、解析器实现或模型配置。
