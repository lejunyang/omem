# 中文语义检索现场冒烟验证

该脚本在临时个人库中写入四类中文材料，加载锁定的本地中文向量模型、补齐向量索引并逐条检索，以行为断言验证正确的第一名结果包含语义路由，并检查可见性过滤。它是直接调用存储与检索组件的现场检查，不覆盖 HTTP 接口、服务启动或异常降级路径。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 验证真实中文语义召回链路

脚本用于回答一个实际问题：组件级测试通过后，中文模型、SQLite 数据和检索排序组合起来，能否把自然语言问题指向正确材料。它创建临时 `Store`，以人工捕获方式写入诊疗、故障处理、语言学习和报销四种文本，再持续执行批量索引，直到没有待处理片段。参考 [临时材料捕获与索引 ↗](../../../scripts/live-retrieval-smoke.ts#L9 "支持脚本创建临时存储、写入四类中文材料并循环补齐向量索引的流程说明。")

检索器并未使用伪向量：`loadChineseEmbedding` 从项目锁定的本地快照加载中文模型，校验仓库、修订和文件摘要，关闭远程模型访问，并为查询添加检索指令。因此现场检查依赖 `osdk` 模型配置与本地快照完整可用。参考 [中文向量模型加载约束 ↗](../../../apps/server/src/retrieval/embedding.ts#L17 "支持现场验证使用锁定且经过校验的本地中文模型，并禁止运行时远程下载。")

<a id="assertions"></a>
## 从捕获到排序的核心断言

对每个自然语言问题，脚本同时执行关键词检索和异步融合检索。通过条件是：融合结果第一名必须对应预期捕获片段，并且该命中的路由包含 `semantic`。这证明语义路由参与了检索且最终得到正确第一名；关键词第一名是否正确只写入报告，不参与成败判断，所以该脚本不能隔离证明语义路径相对关键词检索带来了多少排序增益。参考 [召回与语义路由断言 ↗](../../../scripts/live-retrieval-smoke.ts#L21 "支持融合检索第一名、semantic 路由和可见性过滤的断言，并表明关键词结果只被记录而非作为通过条件。")

索引阶段调用 `SemanticRetrieval.indexBatch`。该入口依据当前模型身份选择尚未建立向量索引的原始片段，将较长文本切成重叠窗口并分批生成向量。脚本循环调用它，覆盖实际 SQLite 索引写入与后续检索的协作，而不只是验证静态协议样例。参考 [向量索引批处理 ↗](../../../apps/server/src/retrieval/semantic.ts#L45 "解释脚本调用的索引入口如何选择未索引片段、切分重叠窗口并批量生成向量。")

<a id="boundaries"></a>
## 可见性、报告与未覆盖范围

脚本还通过 `visible` 回调排除指定材料，并断言返回结果不再包含该片段，覆盖检索结果层面的可见性过滤。成功后会把健康状态、查询结果摘要、关键词首名是否正确以及命中路由写入验证报告；无论成功或失败，都会关闭模型与数据库并删除临时目录。参考 [验证报告与资源清理 ↗](../../../scripts/live-retrieval-smoke.ts#L30 "支持脚本检查可见性过滤、输出健康与检索结果报告，并在结束时关闭资源和清理临时数据。")

这仍是进程内冒烟检查：它直接构造 `Store` 和 `SemanticRetrieval`，没有经过服务器路由，因此不能证明 HTTP 请求校验、鉴权或响应序列化正确；也未覆盖模型缺失或损坏、索引失败后的降级恢复、并发写入及开放域中文检索质量。参考 [召回与语义路由断言 ↗](../../../scripts/live-retrieval-smoke.ts#L21 "支持融合检索第一名、semantic 路由和可见性过滤的断言，并表明关键词结果只被记录而非作为通过条件。")
