# 持久化任务的故障恢复与幂等验收

这组验收测试验证任务从捕获入队、租约竞争、失败重试到取消和人工重试的完整生命周期，重点保证服务重启、并发 worker 与应用后崩溃不会造成数据丢失或重复业务副作用。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-recovery"></a>
## 任务入队与重启恢复

该测试解决的是后台任务在进程崩溃、重启或尚无 worker 时仍能可靠推进的问题。测试使用临时 SQLite 目录创建 `Store`，并在每例结束后关闭数据库和清理目录，使场景彼此隔离。参考 [临时数据库测试环境 ↗](../../../apps/server/tests/jobs.test.ts#L10 "支持测试通过独立 Store 和临时目录隔离持久化场景，并在结束后清理资源的说明。")

首个场景通过数据库触发器故意让入队失败，确认捕获内容、任务和通知会整体回滚；移除故障后，捕获与待处理任务一起提交。关闭并重新打开同一数据目录后，新 worker 能继续处理任务，且原始片段仍可读取，说明这里验收的是持久化恢复而非单进程内存队列。参考 [入队原子性与重启恢复 ↗](../../../apps/server/tests/jobs.test.ts#L53 "支持入队失败整体回滚、成功任务跨 Store 重启后继续处理且原始片段仍存在的论断。")

<a id="leases-and-fencing"></a>
## 并发租约与过期结果隔离

两个连接同时竞争同一任务时，只有取得租约的 worker 会进入处理器，另一方返回“未处理”；随后任务、应用回执和待办均只产生一次。该断言覆盖了并发领取与业务应用的单次性。参考 [竞争领取只应用一次 ↗](../../../apps/server/tests/jobs.test.ts#L107 "支持两个 worker 竞争时只有一个执行处理器，且业务回执与待办均只生成一次。")

租约过期后，新 worker 会取得不同的 fencing token。旧 worker 即使迟到，也不能再提交成功结果；测试要求旧 token 抛出 `STALE_JOB_LEASE`，并只接受替代租约的结果，同时保留“租约过期”和“成功”两次尝试记录。参考 [租约 fencing token ↗](../../../apps/server/tests/jobs.test.ts#L162 "支持过期租约被替换、旧 token 的迟到结果遭拒以及尝试历史被保留的说明。")

<a id="failure-cancel-idempotency"></a>
## 失败策略、取消与幂等应用

失败按类型实行不同上限：临时错误重试三次、坏输出两次、认证错误一次即停止，并验证认证消息中的令牌不会写入任务错误字段。参考 [分类重试与错误脱敏 ↗](../../../apps/server/tests/jobs.test.ts#L207 "支持不同错误类型采用有限重试次数，并避免认证令牌进入持久化错误信息。")

取消也区分生命周期：排队任务直接取消，运行任务通过 `AbortSignal` 协作终止；已成功应用的任务不能假装撤销，而是返回“需要补偿”，且既有待办仍保留。参考 [任务取消生命周期 ↗](../../../apps/server/tests/jobs.test.ts#L253 "支持排队、运行和已应用任务分别采用取消、协作中止与补偿要求的行为。")

若业务应用已经完成、但 worker 在登记任务结果前崩溃，重放处理器会得到重复回执，最终仍只有一份待办、回执、通知和投递意图。这验证了应用仓储以任务应用标识提供幂等边界。参考 [崩溃后的幂等重放 ↗](../../../apps/server/tests/jobs.test.ts#L325 "支持业务应用后崩溃再执行不会重复创建待办、回执、通知和投递意图。")

<a id="generations-and-scope"></a>
## 重试代际、执行指纹与处理范围

认证失败后由显式重试创建新 generation；相同请求重复提交保持幂等，旧尝试记录不被改写，新尝试则保存新的模型、effort 和指纹。因此运行配置变化可追溯，而不会篡改历史执行证据。参考 [重试代际与执行指纹 ↗](../../../apps/server/tests/jobs.test.ts#L377 "支持显式重试创建新 generation、保留旧尝试并记录新模型配置和指纹。")

worker 还能用任务 kind 与任务 ID 限定领取范围：知识处理 worker 完成目标任务后，与其无关的提取任务仍保持排队。参考 [限定范围的 worker ↗](../../../apps/server/tests/jobs.test.ts#L431 "支持 worker 只处理指定 kind 和任务 ID、不领取无关排队任务的断言。") 其依赖关系也可从实现中确认：`processOne` 将这些过滤条件交给仓储领取任务，并在没有可领取任务时返回未处理；已提供但没有处理器的类型会被记为配置失败。参考 [单任务领取流程 ↗](../../../apps/server/src/jobs/worker.ts#L47 "解释 worker 如何把范围、指纹和租约参数交给仓储，以及缺少处理器时如何记录配置失败。") `Store` 则负责初始化同一数据库上的任务仓储与应用仓储，为测试中的租约状态和业务副作用提供共同持久化基础。参考 [持久化仓储初始化 ↗](../../../apps/server/src/store.ts#L38 "说明测试使用的 Store 在同一 SQLite 数据库上初始化任务仓储和应用仓储。")
