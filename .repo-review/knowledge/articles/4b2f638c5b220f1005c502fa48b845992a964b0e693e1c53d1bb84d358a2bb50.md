# 飞书回复的持久投递、去重与故障恢复

该测试验证飞书消息从接收、生成回复、写入持久化发件箱到异步投递之间的关键故障语义：重复事件不会产生重复回复，不同会话轮次不会因文本相同而误去重，临时发送失败能够重试，处理中断的轮次也可恢复。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决消息处理中断造成的重复与丢失

飞书事件处理横跨数据库、模型调用和外部消息发送，任一步骤中断都可能造成“回复已生成但未发送”或“同一事件被执行两次”。测试用临时 SQLite、加密凭据、伪实时连接、可控消息适配器和伪模型组装完整运行宿主，使状态变化可被直接观察。参考 [恢复测试运行夹具 ↗](../../../apps/server/tests/lark-delivery-recovery.test.ts#L77 "支持测试通过临时存储、伪适配器、模型和运行宿主构造可控环境的说明。")

核心设计是把回复先写入持久化发件箱，再由投递循环发送；事件收件箱则记录接收和处理状态。测试模拟回复入列后、事件确认前崩溃，确认发件箱仍为待发送、收件箱仍为已接收；同一事件重投后只复用原有发件箱记录，随后由 worker 完成一次发送。参考 [入列后崩溃恢复 ↗](../../../apps/server/tests/lark-delivery-recovery.test.ts#L172 "支持发件箱先持久化、重复事件不重复入列以及 worker 最终单次发送的断言。")

<a id="scenarios"></a>
## 去重、重试与轮次身份

```mermaid
flowchart LR
  A[收到飞书事件] --> B[创建会话轮次]
  B --> C[模型生成回复]
  C --> D[写入持久化发件箱]
  D --> E[投递 worker 发送]
  E -->|临时失败| F[等待退避后重试]
```

并发测试让第一个请求停在模型调用中，再提交相同事件；第二个请求应直接结束，最终数据库中只有一个轮次和一条发件箱记录，且只发送一次。这覆盖了“重复事件正在处理”这一竞态。参考 [并发事件去重 ↗](../../../apps/server/tests/lark-delivery-recovery.test.ts#L218 "支持相同事件并发到达时只创建一个会话轮次和一条投递记录。")

去重依据不是回复文本：两个不同事件即使生成完全相同的中文回复，也会得到不同的投递标识并分别发送。临时网络错误则使原记录进入 `retry_wait`，退避结束后原记录转为 `delivered`，不会新建第二条发件箱记录。参考 [相同回复文本独立投递 ↗](../../../apps/server/tests/lark-delivery-recovery.test.ts#L241 "支持投递身份按轮次区分，而不是按回复文本错误合并。") [临时发送失败重试 ↗](../../../apps/server/tests/lark-delivery-recovery.test.ts#L256 "支持发送失败进入等待状态、退避后成功且不新增发件箱记录的流程。")

<a id="boundaries"></a>
## 恢复边界与模块协作

测试还直接构造一个已入列但未完成的会话轮次，调用宿主恢复逻辑后确认它从未完成集合中移除，并报告一次重置；这说明启动恢复允许事件重投时重新执行模型流程，但该用例没有覆盖已经生成回复的未完成轮次如何判定为可完成。参考 [未完成轮次恢复 ↗](../../../apps/server/tests/lark-delivery-recovery.test.ts#L272 "支持宿主把中断于模型处理阶段的待处理轮次重置为可重投状态。")

从依赖关系看，测试通过 `ConversationRouter` 操作轮次，通过 `Store` 检查 SQLite 状态，并把 `MemoryService`、实时适配器、消息适配器和模型端口注入 `LarkRuntimeHost`。参考 [宿主依赖装配 ↗](../../../apps/server/tests/lark-delivery-recovery.test.ts#L6 "说明测试所连接的会话路由、持久化存储、记忆服务、飞书运行宿主及各适配器之间的关系。") 实时连接接口明确把事件回调与连接状态回调交给宿主，因此伪连接能够驱动事件而无需真实网络。参考 [飞书实时连接接口 ↗](../../../apps/server/src/integrations/lark/realtime.ts#L51 "支持实时适配器通过事件和状态回调驱动宿主、测试可用伪实现替代真实网络连接的论断。")

这些断言证明的是进程内持久化、并发去重和重试状态机，不等同于真实飞书 API 的端到端“恰好一次”保证；测试没有启动真实 SDK、验证远端幂等行为，也没有覆盖长期失败、退避上限或进程在远端接收成功后再次崩溃的情形。
