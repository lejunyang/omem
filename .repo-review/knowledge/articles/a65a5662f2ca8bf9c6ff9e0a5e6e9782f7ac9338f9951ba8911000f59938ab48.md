# 让需求变成可跟进的事项和可评审的代码

用“工单完成入口”这一教学案例，说明怎样直接用自然语言让主助手持续跟进需求、纠正事实与范围、暂停或恢复调查、明确交办后台实现，并读取真实的检查与独立评审结果。文章同时给出个人行动、项目登记、ready/apply/发布状态的操作边界，以及快速决策模型、Traex、Figma 和其他提供方目前各自做到哪里。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="four_messages"></a>
## 先用四句话走完全程

下面的“工单完成入口”是**教学案例**，不是当前快照中已经实施或验收过的业务。假设现有工单服务能选择处理队列，现在要补一个“处理完成”入口：本期保留未知类别兜底，由同事负责接口，你关注阻塞，最终还要确认实现不会修改调用方传入的对象。

你可以按同一段私聊依次说：

1. **“帮我跟进工单完成入口，只看本期上线阻塞和需要我回答的事。”**
2. **“批量完成不在本期；小李只负责接口，页面由我做。”**
3. **“请在 ticket-service 实现当前这版需求。”**
4. **“现在做到哪了？把实际检查和评审结果给我。”**

第一句建立持续需求并返回“已排队”，不是假装需求已经整理完；第二句把纠正保存下来并重新调查；第三句才是编码授权；第四句只读已有任务状态，不会再次派发。这个自然语言旅程已经接入主助手，Figma 装配和需求变化后的自动重新规划仍未完成。参考 [自然语言跟进到后台实现的用户旅程 ↗](../../../docs/reader-first/assistant-orchestration.md#L19 "支持四句话的主流程及已接通和未完成能力的区分。")

这些动作不是模型说一句“已完成”就算成功。模型提交的是候选动作；宿主会核对当前用户原话、本人私聊身份、版本与请求幂等性，持久写入后才返回回执。所有需求与编码写操作都要求 owner 私聊；编码交办还必须逐字来自当前消息，并能表达明确的实现意图。参考 [工作动作与当前原话字段 ↗](../../../packages/contracts/src/work.ts#L20 "说明跟进、反馈、范围、暂停和编码交办的结构化动作及当前原话要求。") [本人私聊与明确编码交办校验 ↗](../../../apps/server/src/assistant/work.ts#L31 "支持所有写操作的会话限制和编码必须来自当前明确交办。") [动作幂等与持久回执 ↗](../../../apps/server/src/assistant/work.ts#L294 "支持动作先校验、同请求幂等、跟进入队和编码回执的行为。") [宿主应用候选工作动作 ↗](../../../apps/server/src/assistant/runtime.ts#L806 "说明模型动作在当前 turn 后由宿主带身份和原话实际应用或拒绝。") [最终回答以真实回执为准 ↗](../../../apps/server/src/assistant/runtime.ts#L865 "支持有写操作时丢弃模型猜测性成功文案并返回持久回执。")

<a id="continuous_requirement"></a>
## 第一步：建立并维护同一个需求

主助手会先看已有需求、项目和后台任务，再选择对象；只有同名项目或范围无法区分时，才需要你补充。新建跟进时保存三类信息：

| 层次 | 在案例中的内容 | 后续怎样变化 |
| --- | --- | --- |
| 需求事实 | 本期范围、验收、决定、负责人、代码与发布状态 | 由原始材料调查和复核 |
| 关注策略 | 只看上线阻塞；忽略重复提醒；重要变化才通知 | 你可以随时调整 |
| 人工反馈 | “批量完成不在本期”“页面由我做” | 保留原话，可撤销并重新调查 |

**范围有两种选法。** 选择项目或主题的 `contextIds`，会持续跟随它未来加入或移出的成员；选择 `materialKeys`，则盯住指定原件及其修订。关注策略另存 `focus`、`ignore` 和通知强度，不能混成需求事实。主助手的状态查询会同时返回当前需求、文章是否 `current`、revision、反馈、维护状态以及开发任务的检查和评审。参考 [需求与开发状态视图 ↗](../../../apps/server/src/assistant/work.ts#L102 "支持状态查询返回关注、current、revision、反馈、检查、评审和 runId。") [动态项目范围与固定原件范围 ↗](../../../packages/contracts/src/work.ts#L3 "解释 contextIds、materialKeys 和关注策略字段的区别。")

新消息、文档修订或项目成员变化不会为每条消息另建需求。维护服务根据“计划 + 当前材料摘要”计算变化；同一页已有运行任务时只更新目标摘要，连续变化合并到下一轮。保存新反馈也不会篡改正在运行的冻结输入，而是让最新计划排到后续调查。参考 [保存新计划不覆盖运行输入 ↗](../../../apps/server/src/knowledge/page-service.ts#L8 "支持调查运行中保存更新并让最新计划排到下一轮。") [持续需求的摘要观察与合并排队 ↗](../../../apps/server/src/knowledge/page-worker.ts#L96 "支持材料或成员变化由 digest 驱动，同一页连续变化合并处理。")

当你说“负责人不是小王，是小李”时，系统把这句当前原话捕获成新的人工原件，再让研究与复核判断它如何影响需求；它**不是写入瞬间就变成已验证事实**。调整关注点只改变阅读与通知策略。撤销反馈会将其置为 inactive，并恢复最后一个仍有效的关注策略；改范围时仍保留有效纠正原件。参考 [纠正、撤销、调范围与暂停恢复 ↗](../../../apps/server/src/assistant/work.ts#L350 "支持纠正捕获为原件、撤销有效性、保留纠正材料、暂停恢复和刷新回执。")

几种常用说法的结果不同：

- “先别自动跟进”是 **pause**：关闭自动维护，可取消当前自动维护任务，但不删除需求。
- “继续跟进”是 **resume**：重新启用并立即请求刷新。
- “再查一遍”是 **refresh**：只请求重新调查。
- “撤销我刚才那条纠正”是 **revoke**：保留历史记录，但不再把该反馈作为有效输入。
- “只看接口材料”是 **scope/attention**：前者改材料边界，后者改关注策略。

关注版本已经被别处修改时，旧动作会被拒绝并要求重读现状。发布新需求后，系统比较目标、非目标、验收和行动；没有实质变化时保持安静，重要变化才进入通知。参考 [需求变化通知与安静策略 ↗](../../../apps/server/src/assistant/work.ts#L484 "支持结构化比较需求变化、无变化不通知和按通知策略给摘要。")

<a id="structured_requirement"></a>
## 第二步：把讨论读成验收项和行动项

调查完成后，同一需求应出现稳定的目标、非目标、验收项和行动项。对教学案例，可以期待类似下面的结构；它展示的是写法，不代表这些业务事实已在真实材料中确认：

| 项目 | 示例内容 | 状态怎样读 |
| --- | --- | --- |
| objective | 增加单工单处理完成入口 | 说明要解决什么问题 |
| nonGoals | 本期不做批量完成 | 明确不进入本轮 |
| C1 | 未知类别仍走原兜底 | `missing / implemented / verified / released / uncertain` |
| C2 | 完成入口选择正确队列 | 同上 |
| C3 | 不修改调用方输入对象 | 同上 |
| C4 | 项目必需检查通过 | 同上 |
| A1 | 小李确认接口约定 | 另有负责人、等待对象、日期、状态和确定性 |

`implemented` 只表示已有实现证据，`verified` 表示验收证据成立，`released` 才表示已有发布证据；材料不足时通常写 `uncertain`，不能把“没看到”一律写成 `missing`。行动项还要区分 `confirmed`、`proposed` 和 `uncertain`：一句“最好顺便改 UI”不能自动变成承诺、负责人或截止时间。参考 [结构化需求状态合同 ↗](../../../packages/contracts/src/development.ts#L3 "定义验收状态、行动状态、确定性和证据字段。")

需求页的 `current=false` 表示依赖材料已经变化，开工前必须刷新。交接导出的也是固定引用原件和版本，而不是可变工作文件；这保证编码与评审针对同一版验收。参考 [固定需求交接与 current 边界 ↗](../../../apps/server/src/knowledge/requirements.ts#L28 "支持编码交接使用固定引用原件、revision 和 current 标记。")

如果你要把 A1 变成自己的日常跟进事项，目前仍要使用现有 CLI/API：

```bash
omem requirements follow REQUIREMENT_KEY A1
omem tasks list --json
omem requirements unfollow REQUIREMENT_KEY A1
```

只有当前 revision、`current=true` 且行动为 `confirmed` 时才能 follow。这里的含义是“我负责跟进”，不会把原材料中的小李改写成当前用户。后续需求更新会同步同一待办；如果你手工改过待办，自动同步会停下并保留修改，重新 follow 才恢复。行动从新稿消失或不再明确时，旧待办也不会被自动删除。参考 [confirmed 行动才能 follow ↗](../../../apps/server/src/knowledge/requirement-tasks.ts#L33 "支持 follow 要求当前 revision、current 和 confirmed，并关联同一待办。") [人工修改保护与行动失效处理 ↗](../../../apps/server/src/knowledge/requirement-tasks.ts#L64 "支持人工修改后暂停同步、缺失或不明确行动保留旧待办。")

这是当前自然语言入口的一个明确例外：需求跟进、反馈、暂停恢复和后台派发已经接通，但主助手的 `work_action` 尚未包含结构化行动的 follow/unfollow。参考 [当前接通能力总表 ↗](../../../docs/reader-first/assistant-orchestration.md#L7 "支持行动 follow 尚未接入主助手、Traex 限制及外部能力未完成。")

<a id="register_project"></a>
## 实施前：只登记一次真实项目

后台编码需要一个已登记的本地项目。用 CLI 准备配置；真实项目应替换仓库、规则和命令：

```json
{
  "name": "工单服务",
  "repository": "/absolute/path/to/ticket-service",
  "instructions": "保留未知类别兜底；兼容现有调用方。",
  "ruleFiles": ["docs/development.md"],
  "commands": [
    {
      "name": "test",
      "command": "node",
      "args": ["--test"],
      "cwd": ".",
      "purpose": "test",
      "required": true,
      "timeoutMs": 600000
    }
  ]
}
```

```bash
omem develop register ticket-service ./development-project.json
omem develop projects
```

`purpose` 可以是 `setup/test/build/browser/design`。setup 由 Agent 按需运行；所有 `required=true` 且非 setup 的命令由宿主在每轮实现后实际执行。至少要有一项这样的真实检查，否则任务不能进入 `ready`。这些命令以本机用户权限运行，独立副本不是操作系统沙箱，所以只登记你信任且项目确实需要的命令。参考 [项目配置与命令信任边界 ↗](../../../docs/reader-first/requirement-followup.md#L37 "支持项目登记格式、required 检查、本机权限和副本非沙箱。")

开工时原仓库必须干净；任务固定当前提交和需求 revision，在独立、无硬链接的 checkout 中工作。未提交文件、被忽略的凭据和本地依赖不会被复制。项目规则、`AGENTS.md/CLAUDE.md`、额外 `ruleFiles` 和仓库 skills 应已经提交到基线，才能稳定提供给编码与评审。参考 [固定代码基线与独立副本 ↗](../../../apps/server/src/development/runner.ts#L132 "支持 current 需求、干净仓库、固定提交和无硬链接 checkout。")

<a id="delegate_and_status"></a>
## 第三、四步：明确交办，然后随时读取进度

“帮我跟进”只授权维护需求，**不授权改代码**。要启动后台任务，请在本人私聊的当前消息中明确说“请在 ticket-service 实现当前这版需求”。“现在的实现机制是什么？”、“先别改代码”或材料里引用的“请修改”都不是授权。主助手还会检查：编码 Agent 已配置、项目 alias 已登记、需求跟进存在。参考 [本人私聊与明确编码交办校验 ↗](../../../apps/server/src/assistant/work.ts#L31 "支持所有写操作的会话限制和编码必须来自当前明确交办。") [后台编码入队条件与去重 ↗](../../../apps/server/src/development/queue.ts#L120 "支持编码 profile、项目、需求身份校验和 active 任务复用。")

交办成功后，系统在同一事务中写入持久任务并立即返回 `taskId` 和“等待后台执行”；同一 requestId，或同一需求与项目已经有 active 任务时，会复用已有任务，避免重复派发。后台先等待需求页处于 `current` 且已有结构化 requirement，再固定需求版本和代码基线创建 run。参考 [后台编码入队条件与去重 ↗](../../../apps/server/src/development/queue.ts#L120 "支持编码 profile、项目、需求身份校验和 active 任务复用。") [等待 current 需求后创建 run ↗](../../../apps/server/src/development/queue.ts#L36 "支持后台等待需求调查完成、复用 run 并运行编码检查评审。")

用户可以马上离开聊天。回来问“做到哪了”时，主助手读取已有任务，回答这些真实字段：

- durable job 的 `state`，例如 queued/running/succeeded/failed；
- runner 的 `phase`，例如 queued、coding、checking、reviewing、ready、blocked；
- 当前 `message` 或 `error`；
- 每条实际检查的名称与 `exitCode`；
- 独立评审结果和 `runId`。

这些状态来自持久服务，不是重新让模型猜进度；HTTP 的 `/api/work`、需求状态和开发任务接口也读取同一组对象。参考 [需求与开发状态视图 ↗](../../../apps/server/src/assistant/work.ts#L102 "支持状态查询返回关注、current、revision、反馈、检查、评审和 runId。") [统一工作状态 HTTP 入口 ↗](../../../apps/server/src/app.ts#L107 "支持 API 和主助手读取同一 work、requirement 与 development 服务。")

服务启动时会重新启动 DevelopmentQueue；已有 task 使用自己的 id 复用 run 和 checkout。若副本尚处于 created，可以安全完成准备；如果已经工作过的副本丢失，则报错并保留任务，不覆盖已有成果。因此可以承诺“进程重启后续跑同一持久任务和代码副本”，不能承诺恢复同一个模型会话；只有具体提供方支持并验证过会话恢复时才可这样做。参考 [持久 run 与 checkout 复用 ↗](../../../apps/server/src/development/runner.ts#L117 "支持宿主重启后按 task id 复用 run，副本丢失时的安全处理。") [会话恢复只在提供方验证后使用 ↗](../../../docs/reader-first/assistant-orchestration.md#L90 "支持区分持久任务恢复与模型会话恢复。")

“取消开发”只请求停止 active job，并保留已有代码和检查结果；“暂停需求跟进”则关闭需求的自动维护，两者不要混用。询问进度是只读操作，也不会再次派发。参考 [取消开发保留已有结果 ↗](../../../apps/server/src/development/queue.ts#L194 "支持取消 active job 与保留代码和检查结果的语义。")

<a id="review_and_apply"></a>
## 为什么 ready 可信，又为什么它还不是上线

每个开发 run 最多走三轮闭环：

1. 编码角色读取固定需求、原件、项目规则、真实代码和上一轮问题，逐项覆盖所有验收 ID。
2. 宿主实际运行所有 required 且非 setup 的登记命令，保存退出码与代码指纹。
3. 全新的只读 code-reviewer 会话从原需求、完整 diff、真实代码和检查结果重新判断，不读取开发者自评。
4. 若评审要求修改，则问题回到下一轮编码；前提不足、三轮耗尽或需求变化时转为 blocked，并保留副本与问题。

只有“至少一项宿主必需检查实际运行且全部成功、评审 accepted、所有验收 passed、没有中高优问题、评审前后源码指纹一致、需求 revision 仍 current”同时成立，run 才进入 `ready`。检查命令污染源码、评审期间源码变化或编码期间需求变化都会使本轮结论失效。参考 [编码检查独立评审与 ready 条件 ↗](../../../apps/server/src/development/runner.ts#L392 "支持三轮回修、宿主检查、只读新会话评审和 ready/blocked 判定。")

状态边界可以这样记：

| 状态 | 能说明什么 | 还不能说明什么 |
| --- | --- | --- |
| ready | 独立副本针对固定需求完成必需检查与独立评审 | 原仓库已修改、人工验收、发布 |
| applied | 已把评审过的补丁应用到原工作区 | 已提交、push、部署 |
| verified | 需求页已有真实验收证据 | 已发布 |
| released | 需求页已有真实发布证据 | 不自动由代码检查推导 |

`apply` 是显式后续动作。执行前会重新核对已评审代码指纹、原仓库 HEAD 与干净状态、需求 revision；再从已评审树重建 patch，先做 `git apply --check`，最后应用为未提交修改。任一边界已变化就拒绝覆盖，让你人工合并并重新验证。参考 [显式 apply 的重新校验 ↗](../../../apps/server/src/development/runner.ts#L520 "支持 apply 前核对代码、原仓库与需求版本并应用未提交补丁。")

因此，主助手说“ready”时应同时给出实际检查、评审与剩余问题，而不说“已经上线”。如果需求实质变化，当前实现会保留旧 run 的代码并要求基于新版需求重新交办/评审；“自动保留代码后重新规划”尚未接通。

<a id="decision_model"></a>
## 快速决策模型只排阅读顺序，Sol 负责结论

消息很多时，快速决策模型从四个维度给建议：

| 维度 | 可能的建议 |
| --- | --- |
| intent | 咨询、跟进、反馈、实施、停止、未知 |
| focus | 直接相关、背景、无关、未知 |
| change | 决定/范围变化、阻塞、进展、重复、未知 |
| context | 信息足够、需补读、需澄清、可能冲突 |

它只帮助选择对象、识别变化和决定先读哪里。模型未就绪时后台预热并返回空建议；已就绪时前台最多等待 2.5 秒，超时后本轮照常交给 Sol/主助手。参考 [快速决策四维度与 2.5 秒降级 ↗](../../../apps/server/src/decision/work.ts#L4 "定义快速建议类别以及冷启动和超时不阻塞本轮。")

Sol/主助手仍要消解真实对象、补读当前需求与原件、处理含糊和冲突、形成回答与结构化动作候选；宿主仍负责身份、版本、当前交办、幂等和持久写入。快速分数不能删除低分材料、覆盖用户纠正、改变负责人或截止时间、授予编码权限，也不能跳过独立评审。当前材料只证明这条分流路径已经接线，没有证明它已经降低耗时或提高准确率。参考 [快速模型与 Sol 的职责边界 ↗](../../../docs/reader-first/assistant-orchestration.md#L66 "支持快速模型只排调查顺序、不产生事实授权且效果尚未验证。")

<a id="capability_boundary"></a>
## 当前能力边界与一张操作清单

截至 2026-10-06，可以把能力分成三组：

**已经接通**

- 自然语言建立需求跟进、调整范围与关注点、保存/撤销纠正、暂停/恢复/刷新；
- 本人明确交办后，Traex 后台持久派发；
- 服务重启复用任务和代码副本；
- 宿主真实检查、独立只读评审、状态与结果查询。

**仍需 CLI/API**

- 登记项目、规则和检查命令；
- 把结构化行动 follow/unfollow 为个人待办；
- 查看详细 diff、排障以及显式 apply。

**尚未完成或不能宣称**

- 需求变化后保留旧代码并自动重新规划；
- 通用外部能力注册与登录编排；
- 内建 Figma 下载缓存、Mock runtime、Studio 或任意视觉验收；
- Codex/Claude 编码提供方适配；
- 自动提交、push、部署或发布。

当前只验证 Traex ACP。browser/design 只是项目命令类别；没有真实设计工具、skill、节点和检查结果时必须写“未验证”，普通 build 不能冒充视觉验收。参考 [当前接通能力总表 ↗](../../../docs/reader-first/assistant-orchestration.md#L7 "支持行动 follow 尚未接入主助手、Traex 限制及外部能力未完成。") [设计与提供方当前边界 ↗](../../../docs/reader-first/requirement-followup.md#L82 "支持 Figma 能力未内建、普通检查不能冒充视觉验收及当前只验证 Traex。")

实际使用时，按这张清单确认即可：

1. **跟进回执**是否只说“已排队”，并给出同一个需求 key。
2. **纠正回执**是否说明会重新调查，而不是立即宣称事实已验证。
3. **开工前**需求是否 current、项目是否已登记、原仓库是否干净、至少一个 required 非 setup 检查是否真实可跑。
4. **交办回执**是否给出 taskId，并明确“现在尚未完成”。
5. **进度回答**是否包含阶段、实际退出码、评审与错误，而不是泛泛说“正在处理”。
6. **ready 后**是否仍由你决定查看 diff、apply、提交与发布；发布证据再回到同一需求更新 `released`。
