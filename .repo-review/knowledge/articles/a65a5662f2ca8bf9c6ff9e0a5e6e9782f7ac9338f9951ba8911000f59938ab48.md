# 让需求变成可跟进的事项和可评审的代码

用“工单完成入口”教学案例说明：怎样持续补充事实、纠正范围和责任、调整关注、暂停或恢复同一需求；怎样把本人私聊中实际读取的设计或研发回执交给后台编码与独立评审；以及怎样根据真实检查、评审、差异和交付位置判断任务处于等待、失败、受阻、ready 还是 applied。外部回执是实现背景，不会静默改写固定需求与验收。个人行动的 follow/unfollow、受阻任务的 resume 和已评审补丁的 apply 当前需走本地 CLI 或对应 API，尚不是主助手动作。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="one_requirement"></a>
## 先用五句话走完一条需求

可以把同一个需求持续维护下去，也可以把刚在本人私聊中实际读取的设计或研发结果交给后台编码和独立评审。关键边界是：**需求页里的目标和验收仍是权威输入；外部回执只是本次实现的背景，不能替你改变范围、验收或授权。**

下面用“工单分派已有队列选择，现在补一个处理完成入口”贯穿全文。这是教学案例，不表示现实中的 `ticket-service`、Figma 节点或上线状态已经存在。

1. **建立跟进：**“帮我跟进工单完成入口，只看本期上线阻塞和需要我回答的事。”
2. **纠正需求：**“批量完成不在本期；小李只负责接口，页面由我做。”
3. **读取外部对象：**“读取 Figma 节点 Y，确认单工单完成态和未知类别兜底。”
4. **明确交办：**“请在 ticket-service 实现当前这版需求，使用 project-design，并把刚才节点 Y 的实际读取结果交给编码和评审。”
5. **查询结果：**“现在做到哪了？给我实际检查、独立评审、diff 和 matchesReviewed。”

第一句建立持续需求，第二句通过反馈通道修改范围和责任事实，第三句只调查并保存真实工具结果，第四句才是实施授权，第五句只读已有任务而不会重复派发。宿主要求实施原话确实出现在当前用户消息中，并拒绝把“先别实现”等否定表达当成交办。参考 [需求维护与交办操作合同 ↗](../../../packages/contracts/src/work.ts#L20 "支持主助手可提出的需求维护、编码开始和取消动作，并显示没有 follow、开发 resume 或 apply 动作。") [当前消息的实施授权校验 ↗](../../../apps/server/src/assistant/work.ts#L39 "支持本人私聊、当前原话和否定表达的实施授权边界。")

<a id="state_and_maintenance"></a>
## 分清需求事实、关注策略和外部回执

同一段对话里有三类状态，处理方式不同：

| 内容 | 在案例中的例子 | 会怎样更新 |
| --- | --- | --- |
| 需求事实、验收与行动约定 | 本期只做单工单完成；未知类别需要兜底；小李负责接口、页面由我负责 | 通过材料调查或 `correction` 反馈进入同一需求页，形成 objective、nonGoals、criteria、actions；行动可以带 owner、waitingOn、期限和确定性 |
| 关注策略 | 只提醒上线阻塞和需要我回答的事 | 通过 `attention` 独立调整“优先看什么、排除什么”，不会把责任约定隔离在 requirement 之外 |
| 对话外部回执 | 节点 Y 的设计上下文、截图、接口查询结果 | 可随开发 handoff 复制，供编码和评审读取；本身不改写 criteria |

“反馈”是保存用户补充并触发更新的通道，不等于所有反馈都只是关注设置：`correction` 会保存当前用户原话、捕获为人工原件并重建需求；`attention` 才只改变关注策略。因此“页面由我负责”应作为责任事实或行动纠正进入重新调查，而不是仅作为提醒偏好。结构化验收区分 `missing`、`implemented`、`verified`、`released` 和 `uncertain`；行动另有 `confirmed`、`proposed`、`uncertain`。参考 [纠正反馈、关注调整与需求重建 ↗](../../../apps/server/src/assistant/work.ts#L471 "支持 correction 捕获人工原件、attention 更新关注策略，以及撤销、范围、暂停恢复和刷新。") [需求状态与行动责任字段 ↗](../../../packages/contracts/src/development.ts#L4 "支持 objective、nonGoals、criteria、actions 及完成层级和行动确定性。")

第一次跟进时，助手保存标题、目标、范围和关注策略。选择项目或主题范围，会继续跟随未来加入的成员；选择固定原件，则只盯指定材料。系统先返回“已排队”，调查完成后才形成或更新需求页，不能把排队回执当成结论。后续可以直接说：

- **纠正事实或责任：**“批量完成不在本期；小李只负责接口，页面由我做。”
- **调整关注：**“只提醒阻塞和需要我回答的事。”
- **撤销反馈：**停用指定反馈，历史仍保留。
- **调整范围：**换成新的项目、主题或固定材料集合。
- **暂停 / 恢复需求维护：**暂停停止自动维护；恢复会重新刷新。取消开发任务是另一件事。
- **只刷新：**重新调查当前范围，不预先断言结论一定改变。

这些修改带当前版本检查；页面已变化时应先重读。短时间连续补充不会为每句话另建需求，活动维护任务更新目标摘要，后续一轮处理新变化。参考 [需求维护与交办操作合同 ↗](../../../packages/contracts/src/work.ts#L20 "支持主助手可提出的需求维护、编码开始和取消动作，并显示没有 follow、开发 resume 或 apply 动作。") [纠正反馈、关注调整与需求重建 ↗](../../../apps/server/src/assistant/work.ts#L471 "支持 correction 捕获人工原件、attention 更新关注策略，以及撤销、范围、暂停恢复和刷新。") [同一需求连续变化的合并处理 ↗](../../../apps/server/src/knowledge/page-worker.ts#L96 "支持活动维护任务更新目标摘要并在后续轮次处理连续变化。")

个人待办关联是另一条已有能力，但**尚未接入新主助手的需求动作**。要把一条已确认且有原文依据的行动加入个人待办，当前使用本地 CLI：

```bash
omem requirements follow REQUIREMENT_KEY ACTION_ID
omem tasks list --json
omem requirements unfollow REQUIREMENT_KEY ACTION_ID
```

也可以调用对应的 RequirementTasks HTTP API。需求更新会同步同一待办；手工改过待办后会停止自动覆盖，重新 follow 才恢复。行动消失或变得不确定时，旧待办会保留并提示核对，不会自动删除。不要仅对主助手说“帮我 follow”并假定已经执行成功，应以 CLI/API 返回和 board 状态为准。参考 [个人行动关联 CLI 入口 ↗](../../../docs/reader-first/requirement-followup.md#L25 "给出 requirements follow、tasks list 和 requirements unfollow 的可执行入口。") [个人行动关联 HTTP 入口 ↗](../../../apps/server/src/knowledge/requirement-tasks.ts#L140 "支持 follow 与 unfollow 当前可通过 RequirementTasks API 执行。") [确认行动同步个人待办 ↗](../../../apps/server/src/knowledge/requirement-tasks.ts#L33 "支持只跟进已确认行动、人工修改停止覆盖，以及行动变化时保留旧待办。") [当前接线与未完成能力 ↗](../../../docs/reader-first/assistant-orchestration.md#L7 "支持个人行动尚未接入主助手、Traex 已接通，以及需求变化重规划和多提供方仍未完成。")

<a id="prepare"></a>
## 交办前只做一次的准备

后台实现需要一个登记项目。项目配置至少说明仓库、项目说明、规则文件、默认外部能力和可运行命令；命令用途分为 setup、test、build、browser、design。setup 由 Agent 按需执行，宿主每轮真实运行所有 required 且非 setup 的命令。**没有至少一项真实必需检查，任务不能进入 ready。** 项目命令以本机用户权限运行，独立副本不是操作系统沙箱，因此只登记可信命令。参考 [开发项目配置合同 ↗](../../../packages/contracts/src/development.ts#L48 "支持仓库、规则文件、默认能力和 setup/test/build/browser/design 命令配置。") [项目命令与独立副本信任边界 ↗](../../../docs/reader-first/requirement-followup.md#L37 "支持项目登记、required 检查、无必需检查不能 ready，以及独立副本不是操作系统沙箱。")

开工前确认三件事：

1. 需求已经生成结构化 requirement，且与当前材料一致，即 `current=true`。
2. 登记仓库工作区干净；任务从当前提交创建独立 checkout。未提交文件、被忽略的凭据和依赖不会自动进入副本。
3. 项目规则和需要的 skills 已在提交基线中；Agent 修改文件前必须读取适用规则。参考 [固定需求与干净代码基线 ↗](../../../apps/server/src/development/runner.ts#L154 "支持创建前拒绝非 current 需求，以及干净仓库、固定 HEAD、需求 revision 和独立 checkout 的开工条件。") [修改前读取项目规则 ↗](../../../apps/server/src/development/workspace.ts#L230 "支持按路径读取规则、命令清单和仓库 skills，并在修改前强制读取适用规则。")

外部设计或研发上下文通过已登记的只读能力提供。正常顺序是：发现能力 → inspect 可执行文件、声明检查和 MCP 工具 → 阅读相关 skill → call → 实际查看正文或图片。CLI 用于首次登记、`check` 和排障，也承担尚未接入主助手的 follow/unfollow、开发 resume 和 apply；日常的需求跟进、纠正、明确派发和状态查询可以由助手完成。注意 `available` 只表示声明检查和工具发现通过，不证明目标节点或私有对象一定有权限；没有登录检查时，认证也没有被单独验证。参考 [外部能力检查与实际调用 ↗](../../../apps/server/src/capabilities/session.ts#L220 "支持可执行文件、声明检查、MCP 工具发现、认证边界和实际 CLI/MCP 回执。") [需求维护与交办操作合同 ↗](../../../packages/contracts/src/work.ts#L20 "支持主助手可提出的需求维护、编码开始和取消动作，并显示没有 follow、开发 resume 或 apply 动作。")

<a id="receipt_and_decisions"></a>
## 把刚读到的真实结果交给编码与评审

普通问答实际调用 CLI 或 MCP 后，会保存 receipt，其中包含能力及版本、工具、参数、时间和真实结果，图片也参与摘要。receipt 只在**本人的同一私聊**中可见：当前轮可以读取，此前轮次必须已经完成；不能跨私聊取资料，也不能让模型指定任意本机路径。参考 [外部回执的内容与摘要 ↗](../../../apps/server/src/capabilities/receipts.ts#L11 "支持回执记录能力、工具、参数、时间、真实结果以及图片摘要。") [同一本人私聊的回执范围 ↗](../../../apps/server/src/capabilities/receipts.ts#L115 "支持当前轮和已完成历史轮次的列出、解析和精读，以及会话所有权限制。")

交办前，让助手用 `conversation_inputs` 列出并精读相关记录，再选择 recordId。这样能确认对象、调用是否成功以及内容是否真与本次实现有关。`inputReceipts` 有三种语义：

- 给出 ID：只带所选结果；
- 给出空数组：一份也不带；
- 省略字段：从本次选择的 capabilities 中，带同会话最近最多 100 条结果。

默认集合不会自动筛成“必然正确”，所以涉及设计节点或私有研发对象时，优先精读后显式选 ID。入队时，系统固定当前交办原话、此前最多 20 个已完成讨论轮次和所选 receipt 身份，并在返回 taskId 前把回执及图片复制到 run 的 `external-inputs`。服务重启或临时问答目录消失后仍可恢复；没有保存会话时不能凭空交接 receipt。参考 [inputReceipts 的三种语义 ↗](../../../packages/contracts/src/work.ts#L78 "支持显式 ID、空数组和省略字段所对应的交接范围。") [讨论历史与回执选择 ↗](../../../apps/server/src/capabilities/receipts.ts#L218 "支持固定交办原话、最多 20 个已完成轮次，以及显式或默认回执选择。") [入队前持久复制外部回执 ↗](../../../apps/server/src/development/queue.ts#L132 "支持会话存在性校验，并在返回前导出回执与图片供任务恢复。")

快速决策模型只做短时建议：工作分流判断当前意图、材料变化和缺失背景；能力相关性判断某项能力是否可能有帮助；回执相关性判断某份外部结果对编码目标是直接、背景、无关还是不确定。它们都不能写事实、授权交办、证明能力可用、选择或丢弃 receipt，也不能替代阅读。主助手仍负责读取当前需求和原件、检查并调用能力、查看真实结果、选择 receipt、处理冲突，并在用户明确授权后提出 work action。参考 [材料分流只决定补读方向 ↗](../../../apps/server/src/assistant/work.ts#L307 "支持工作分流只提供相关性、变化类型和缺背景建议，不能授权或写事实。") [能力相关性只供选择建议 ↗](../../../apps/server/src/capabilities/session.ts#L458 "支持快速模型只判断能力帮助程度，可用性仍以 inspect 和实际调用为准。") [单份外部结果相关性只供建议 ↗](../../../apps/server/src/capabilities/receipts.ts#L278 "支持回执相关性模型不选择、不授权、不丢弃回执且不能替代阅读。")

执行前 runner 会再次校验每份回执摘要，并 inspect 所选能力。缺可执行文件、声明检查失败、MCP 工具发现失败或摘要不一致会直接 blocked，不消耗编码回修轮次。编码和独立评审都能读取交办、讨论、回执正文和图片；历史回答与工具输出仍是待核对背景。若节点只补充既定验收的实现上下文，可直接交接；若它改变范围、验收或责任约定，应先反馈并刷新需求。参考 [执行前校验回执与能力 ↗](../../../apps/server/src/development/runner.ts#L329 "支持摘要复核和能力预检失败直接 blocked，而不进入编码回修轮次。") [交办背景不能改写固定验收 ↗](../../../apps/server/src/development/runner.ts#L396 "支持编码与评审读取交办和回执，并将历史回答与工具输出视为待核对背景。")

<a id="run_and_status"></a>
## 后台编码、检查、独立评审，再查询真实状态

明确交办后，聊天立即得到 taskId，并明确“现在尚未完成”。后台先等待需求 current 且已有结构化 requirement，再创建或恢复同一个独立 checkout；服务重启会复用 durable task、run id 和已有副本。暂停需求维护与取消开发是两个操作。参考 [后台等待当前需求并恢复任务 ↗](../../../apps/server/src/development/queue.ts#L41 "支持 durable worker 等待结构化 current requirement、暂停时拒绝继续并复用已有 run。")

一次 `start`，或对同一 run 显式 `resume` 后触发的一次 `execute` 批次，最多进行三轮：

1. **编码：**读取固定需求、原始材料、项目规则、代码、交办背景和上一轮问题，再修改独立副本。
2. **宿主检查：**真实执行全部 required 且非 setup 的项目命令，保存退出码和日志；检查污染源码时必须先整理。
3. **独立评审：**全新、只读的评审角色从原需求、实际代码与完整 diff、检查结果和同一批外部回执重新判断，不接受开发者自评，并逐项覆盖 criteria。
4. **回修或结束：**检查失败或评审要求修改会进入本批次下一轮；环境前提不足或评审明确 blocked 会保留副本并停止。

如果本批次三轮用尽仍未通过，run 变为 blocked，保留代码与评审问题；后台队列不会据此自行无限重试。处理前提后，当前要在本机对**同一副本**显式执行：

```bash
omem develop resume RUN_ID
```

`resume` 再执行一个最多三轮的批次，`attempt` 会继续累计，所以同一 run 的累计编码轮数可能超过三轮。主助手的动作合同目前只有 `start_development` 和 `cancel_development`，没有开发任务的 resume；不能只在私聊里说“继续”并把模型回复当成恢复成功，应以 CLI 输出和随后查询到的真实 phase 为准。参考 [一次执行批次的三轮上限与状态收束 ↗](../../../apps/server/src/development/runner.ts#L484 "支持每次 execute 的三轮循环、检查评审、三轮用尽 blocked、ready 条件和异常 failed。") [恢复、查看差异与应用的本地 CLI ↗](../../../apps/server/src/cli.ts#L799 "支持 resume 复用既有 run，diff 查看差异，apply 将已评审补丁应用到原工作区。") [后台队列单次调用执行器 ↗](../../../apps/server/src/development/queue.ts#L78 "支持队列对非 ready/applied 的 run 调用一次 execute，而非三轮耗尽后自行无限循环。") [需求维护与交办操作合同 ↗](../../../packages/contracts/src/work.ts#L20 "支持主助手可提出的需求维护、编码开始和取消动作，并显示没有 follow、开发 resume 或 apply 动作。")

需求变化不能笼统理解为总会得到 blocked，要看检查时点：

- **创建新 run 前**发现需求页不是 current：直接拒绝创建，尚无新的 run phase。
- **execute 开始或恢复时**发现固定 requirement revision 已不是当前版本：抛错，外层把该 run 记为 failed，并保留已有改动。
- **编码、检查和评审结束、准备进入 ready 时**才发现需求已变化：该 run 记为 blocked，提示基于新需求重新评审。

这三个结果都意味着不能把旧需求对应的结果称为 ready，但查询状态时应按实际 `phase` 和 `error` 解释，而不要预设它一定是 blocked。参考 [固定需求与干净代码基线 ↗](../../../apps/server/src/development/runner.ts#L154 "支持创建前拒绝非 current 需求，以及干净仓库、固定 HEAD、需求 revision 和独立 checkout 的开工条件。") [执行入口的固定需求版本检查 ↗](../../../apps/server/src/development/runner.ts#L297 "支持 execute 开始或恢复时需求 revision 过期会抛错，并由外层异常路径记为 failed。") [进入 ready 前的需求变化检查 ↗](../../../apps/server/src/development/runner.ts#L550 "支持编码和评审完成后发现需求变化时将 run 记为 blocked。")

只有至少一项宿主检查存在且全部退出码为 0、独立评审 accepted、所有验收项通过、源码在评审期间未变，并且需求仍是同一 current revision，run 才能成为 ready。评审期间源码变化、无必需检查、能力预检失败或评审 blocked 会留下相应的 blocked 状态；其他未被内部转成 blocked 的异常会进入 failed。参考 [一次执行批次的三轮上限与状态收束 ↗](../../../apps/server/src/development/runner.ts#L484 "支持每次 execute 的三轮循环、检查评审、三轮用尽 blocked、ready 条件和异常 failed。")

离开聊天后直接问“现在做到哪了”，助手应读取已有任务，不重复派发。重点看：

- `state` 与 `phase`：queued/coding/checking/reviewing，还是 failed、blocked、ready、applied；
- `message` 与 `error`：当前等待什么、为何停止；
- `checks[].exitCode`：真实检查是否成功；
- `review`：独立评审及逐项验收；
- `delivery`：结果仍在 isolated checkout，还是已经 applied；
- `diff`：保存的已评审补丁；
- `matchesReviewed`：当前副本是否仍与评审时完全一致。

`matchesReviewed=false` 或 `null` 时，不能声称当前文件仍是已评审版本。ready 时登记仓库保持不变是正常现象。参考 [真实阶段、检查、评审与差异 ↗](../../../apps/server/src/assistant/work.ts#L141 "支持状态查询返回 delivery、检查退出码、review、diff 和 matchesReviewed。")

<a id="delivery_boundary"></a>
## 最后决定是否应用，以及什么才算完成

`ready` 只表示固定需求对应的独立副本通过本地必需检查和独立评审。需要把修改落到登记仓库时，当前在本机明确执行：

```bash
omem develop diff RUN_ID
omem develop apply RUN_ID
```

先看 diff，再 apply。主助手的动作合同目前没有 apply，因此不能只在私聊中说“应用”并假定登记仓库已经变化。apply 会重新核对：checkout 仍等于评审版本、登记仓库仍处于原 base HEAD 且干净、需求仍是同一 current revision，以及重新生成的补丁能通过应用检查。任一条件变化都会拒绝覆盖并保留补丁；成功后状态是 `applied`，但不会自动提交、push、部署或发布。参考 [恢复、查看差异与应用的本地 CLI ↗](../../../apps/server/src/cli.ts#L799 "支持 resume 复用既有 run，diff 查看差异，apply 将已评审补丁应用到原工作区。") [应用补丁前的重新核对 ↗](../../../apps/server/src/development/runner.ts#L613 "支持只把未变化的 ready 评审版本应用到仍处原基线且需求未变的仓库。") [需求维护与交办操作合同 ↗](../../../packages/contracts/src/work.ts#L20 "支持主助手可提出的需求维护、编码开始和取消动作，并显示没有 follow、开发 resume 或 apply 动作。")

因此不要只问“完成了吗”，而要区分：

- **implemented：**代码中已有实现；
- **ready：**独立副本的必需检查与独立评审通过；
- **applied：**已评审补丁已应用到登记仓库，尚不能由此推断提交或上线；
- **verified / released：**必须由真实验收或发布材料更新需求，不能由 ready/applied 自动写成。

当前可确认接通的是 Traex 编码流程、skill/只读 CLI/MCP 能力装配、同一私聊 receipt 的选择和持久交接，以及编码和评审共享回执。仍不能宣称真实 Figma 或私有研发服务已配置并拥有对象权限，也没有 OAuth 浏览器登录、回执自动沉淀为全库原件、需求变化后的自动重规划、Codex/Claude 已验证编码路径，或自动 commit/push/deploy/release。参考 [当前接线与未完成能力 ↗](../../../docs/reader-first/assistant-orchestration.md#L7 "支持个人行动尚未接入主助手、Traex 已接通，以及需求变化重规划和多提供方仍未完成。") [外部能力不能推出的结论 ↗](../../../skills/omem-cli/references/capabilities.md#L47 "支持对象权限、OAuth、自动知识沉淀和版本固定范围等限制。")
