# 让需求变成可跟进的事项和可评审的代码

用一条虚构的“工单处理完成入口”需求，走完材料归组、需求整理、行动跟进、项目登记、编码、宿主检查、独立评审、回修和补丁应用。重点说明每一步该运行什么命令、看到什么结果，以及需求约定、代码存在、检查通过、应用与发布的边界；同时明确 browser/design 只是可配置命令类别，omem 当前没有内置 Mock、Figma 或 Studio 验收能力。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="case-and-finish-line"></a>
## 先认清终点：一条需求要经过哪些关口

这篇指南用一条**虚构教学案例**贯穿全程：工单分派已经能按类别选择队列；会议决定新增“处理完成”入口，同时要求保留未知类别的兜底队列；一位同事负责确认状态字段，你要跟进其进展；代码还要证明路由函数不会修改传入对象。材料没有提供这个业务的真实仓库、接口或测试结果，因此这些业务名称和验收项只是演示，不是现实部署事实。

你要走完的是一条有明确关口的链路：

1. 把纪要、消息和代码等原件归入同一范围，生成持续维护的需求页。
2. 核对目标、非目标、验收项和行动项，分清建议与明确约定。
3. 把一条 confirmed 行动关注为个人待办。
4. 登记真实 Git 仓库、项目规则、skills 和允许执行的命令。
5. 在独立副本中编码，让宿主运行必需检查，再由新会话独立评审。
6. 查看差异和问题；只有任务到达 ready 才能 apply。
7. apply 后补丁只是回到原工作区的未提交修改，提交、推送和发布仍由你决定。

omem 把需求事实、个人跟进、代码实现、机器检查、独立评审、应用到工作区和上线分开；后一步的局部成功不能替代整体完成。参考 [需求到代码的总体边界 ↗](../../../docs/reader-first/requirement-followup.md#L1 "说明需求跟进、独立副本、独立评审、apply 以及不自动发布的整体流程。")

<a id="keep-one-requirement-current"></a>
## 第一步：让后续讨论进入同一需求

先保存原件，再把相关来源归到一个 context。下面的 ID 都要换成你本机实际返回的值：

```bash
omem contexts create '工单完成入口' --description '工单分派和完成状态'
omem contexts assign SOURCE_ID CONTEXT_ID
omem requirements track '工单完成入口' \
  --goal '补处理完成入口，保留未知类别兜底，并明确验收与负责人' \
  --context CONTEXT_ID --watch
omem requirements list --json
omem requirements show REQUIREMENT_KEY
omem requirements board REQUIREMENT_KEY
```

`contexts assign` 设置的是该来源的**完整归属列表**；若来源原本属于多个 context，要把仍需保留的 ID 一起传入。后续纪要或消息也要先被捕获并归入这个 context，`--watch` 才会把范围变化带回同一需求；系统不会仅凭群名相似或一条新消息猜测归属。参考 [来源完整归属列表 ↗](../../../apps/server/src/cli.ts#L509 "说明 contexts assign 设置来源的完整归属列表。")

`--context` 适合持续变化的范围：成员增减也会被跟踪。只想固定选择若干来源时，用 `--revision ID...`；它跟随所选来源的修订，但不随 context 增加成员。暂停维护用 `omem requirements watch KEY --off`，主动重查用 `omem requirements refresh KEY`。参考 [context 与 revision 的选择 ↗](../../../docs/reader-first/requirement-followup.md#L7 "说明 context、revision、watch 和 refresh 的操作差异。")

`track` 返回“已排队”只表示任务已提交。用 `list --json` 看处理状态和失败原因，成功后用 `show` 看正文、用 `board` 看结构化验收项和行动项。旧页面没有结构化 requirement 时先 refresh；`current=false` 表示材料已变化，**不要据此开工**。参考 [结构化需求与 current ↗](../../../skills/omem-cli/references/development.md#L3 "说明先看 board、旧页 refresh、current=false 不开工。")

<a id="turn-materials-into-work"></a>
## 第二步：把讨论拆成验收项和行动项

需求页要把“要求是什么”和“目前证明到哪一层”分开。针对本教学案例，board 可以整理成下面这样；ID 只是示例：

| 类型 | 示例内容 | 本快照下的初始状态 |
| --- | --- | --- |
| 目标 | 增加“处理完成”入口，不破坏现有分派行为 | 需求约定 |
| 非目标 | 不顺手重做整套工单 UI，不在本任务中发布上线 | 明确排除 |
| C1 | 存在可调用的处理完成入口 | `missing`：案例明确说这是待新增能力 |
| C2 | 已知类别仍进入对应队列 | `uncertain`：案例把它设为既有行为，但本快照没有真实代码或检查证据 |
| C3 | 未知类别继续进入兜底队列 | `uncertain`：这是要保留的行为，本快照没有实现证据 |
| C4 | 调用路由后传入对象保持不变 | `uncertain`：这是待证明的验收要求，不能假定当前实现一定违反 |
| A1 | 跟进同事确认完成状态字段 | 只有原文明确记录负责人和约定时才是 `confirmed` |

状态不是进度百分比：`missing` 表示材料确认能力尚不存在；`implemented` 表示有实际代码依据；`verified` 还需检查或验收依据；`released` 还需发布依据；`uncertain` 表示材料不足。因此“尚未核验”不能一律写成 `missing`。验收项使用稳定 ID；行动项另有负责人、等待对象、日期、状态和 `confirmed/proposed/uncertain` 确定性。参考 [验收与行动状态结构 ↗](../../../packages/contracts/src/development.ts#L3 "支持验收状态、行动确定性、负责人和等待对象字段。")

判断建议与约定时要回到原文。例如，会议明确决定“由小林确认状态字段”时，A1 才能是 `confirmed`；一句“最好顺便改 UI”应保留为 `proposed` 或 `uncertain`，不能升级为验收承诺。需求整理也要区分决定、待确认、代码存在、测试和发布。参考 [区分决定和状态 ↗](../../../apps/server/src/knowledge/requirements.ts#L17 "说明需求整理要区分明确决定、待确认、代码、测试与发布。")

<a id="follow-an-action"></a>
## 第三步：把明确行动变成个人跟进事项

先从最新 board 复制行动 ID，再关注它：

```bash
omem requirements board REQUIREMENT_KEY
omem requirements follow REQUIREMENT_KEY A1
omem tasks list --json
```

`follow` 执行时会重新读取当前 board，把本次读到的 revision 随请求提交。后端要求页面仍为 `current`、行动仍存在且是 `confirmed`。它不会校验你更早在终端复制 ACTION_ID 时看到的 revision；如果期间换版而同一 ID 仍存在，命令关注的是新版同名行动。因此执行前要重读 board，确认新版 A1 的含义、负责人和证据仍符合预期。参考 [CLI follow 读取当前 revision ↗](../../../apps/server/src/cli.ts#L624 "证明 follow 重新读取当前 board 并提交该 revision。")[follow 后端校验 ↗](../../../apps/server/src/knowledge/requirement-tasks.ts#L33 "证明后端校验 revision、current、行动存在及 confirmed。")

“关注”表示**我负责跟进**，不是把材料中的负责人改成我。生成的个人任务 owner 是当前个人库的 owner，但详情仍保留材料里的负责人、等待对象、日期表达和来源需求；本例中的含义是“我去追踪同事确认状态字段的进展”。参考 [个人跟进保留材料负责人 ↗](../../../apps/server/src/memory/service.ts#L136 "说明个人任务与材料负责人、等待对象的保留方式。")

同一 action ID 可以更新同一待办，并会保护人工修改：

- 你或其他流程人工改过待办后，自动同步暂停并保留修改；再次 `follow` 表示认可当前任务状态并恢复同步。
- `unfollow` 只关闭后续同步，已创建的任务仍保留。
- 新稿遗漏行动、certainty 不再是 confirmed 或原件证据失效时，旧待办不会被静默删除，而会保留并记录错误。

参考 [行动同步与人工修改保护 ↗](../../../apps/server/src/knowledge/requirement-tasks.ts#L64 "支持同一行动更新、人工改动保护、取消关注和失效行动保留。")

<a id="register-real-project"></a>
## 第四步：登记真实项目和验收命令

创建一个本机 JSON，并把路径和命令换成目标项目真实可用的值：

```json
{
  "name": "工单服务",
  "repository": "/absolute/path/to/ticket-service",
  "instructions": "保持现有队列选择兼容；不要修改调用方传入对象。",
  "ruleFiles": ["docs/development.md"],
  "commands": [
    {
      "name": "setup",
      "command": "npm",
      "args": ["ci"],
      "purpose": "setup",
      "required": true
    },
    {
      "name": "test",
      "command": "npm",
      "args": ["test"],
      "purpose": "test",
      "required": true,
      "timeoutMs": 600000
    }
  ]
}
```

然后登记并确认：

```bash
omem develop register ticket-service ./development-project.json
omem develop projects
```

`repository` 必须解析为 Git 仓库根目录；`instructions` 是项目级约束；`ruleFiles` 列出额外规则文件。每条命令有唯一 `name`、`command`、`args`、可选 `cwd`、`purpose`、`required` 和 `timeoutMs`；purpose 只能是 `setup/test/build/browser/design`。项目别名以字母开头，只能含字母、数字、下划线和连字符，已有别名不能原地覆盖。参考 [项目配置字段 ↗](../../../packages/contracts/src/development.ts#L48 "说明项目、仓库、规则文件、命令、purpose 和默认值。")[项目登记校验 ↗](../../../apps/server/src/development/runner.ts#L77 "支持仓库根目录、命令名唯一和别名不可覆盖等登记条件。")

编码角色会按目标文件位置读取从仓库根到子目录的 `AGENTS.md`、`CLAUDE.md`，并叠加 `ruleFiles`；还会枚举 `.agents/skills`、`.claude/skills`、`.trae/skills` 下的 `SKILL.md`，按相关性读取。因为开发副本来自已提交版本，这些规则和 skills 也要存在于该提交中。参考 [目录规则叠加 ↗](../../../apps/server/src/development/workspace.ts#L132 "支持读取根到子目录规则并叠加 ruleFiles。")[仓库 skills 发现 ↗](../../../apps/server/src/development/workspace.ts#L228 "支持枚举三类仓库 skill 入口并按相关性读取。")

`setup` 供编码 Agent 按需准备依赖；每轮实现后，宿主自动执行所有 `required=true` 且 purpose 不是 setup 的命令。至少登记一个真实可运行的必需检查，否则任务不能进入 ready。命令以本机用户权限运行，独立副本**不是操作系统沙箱**；只登记你授权且项目确实需要的命令。参考 [setup 与宿主检查边界 ↗](../../../docs/reader-first/requirement-followup.md#L51 "说明 setup、required 非 setup 检查及本机权限信任边界。")

<a id="start-implementation"></a>
## 第五步：从当前需求启动编码

启动前再看一次 `requirements board`：必须已有结构化目标和验收项，且 `current=true`。目标仓库还要停在准备作为基线的提交，并保持工作区干净。然后运行：

```bash
omem develop start REQUIREMENT_KEY --project ticket-service
```

runner 会记录当前 HEAD，在个人库的 development 目录创建无硬链接的独立 checkout，切到该基线并移除 origin。原工作区保持不动；未提交文件、被忽略的凭据和本地依赖目录不会随提交历史复制过去，缺依赖时使用已登记的 setup 命令。参考 [创建独立开发副本 ↗](../../../apps/server/src/development/runner.ts#L130 "支持 current 需求、干净仓库、固定 base、无硬链接 clone 与移除 origin。")

编码角色读取启动时固定的需求版本及其原件、项目规则和独立副本中的真实代码。它能搜索和读取代码、查看完整 diff、运行登记命令；写文件前必须读取适用规则，并带上刚读取内容的 hash，文件后来变化时会拒绝覆盖。参考 [编码读取固定需求与原件 ↗](../../../apps/server/src/development/runner.ts#L237 "说明固定需求版本、原始材料和真实代码工具的装配。")[写代码的规则与 hash 保护 ↗](../../../apps/server/src/development/workspace.ts#L391 "支持修改前读取适用规则、expectedHash 检查和评审只读。")

编码结果必须逐项覆盖原需求中的每个验收 ID，不能遗漏或新增。角色不能改需求标准，也不能提交、推送或部署。对本例而言，结果应分别对应 C1—C4，而不是只说“功能已完成”。参考 [逐项覆盖验收标准 ↗](../../../apps/server/src/development/runner.ts#L309 "说明编码和评审不能遗漏或新增验收 ID，并限制编码角色职责。")

<a id="checks-review-and-repair"></a>
## 第六步：看宿主检查、独立评审并处理失败

运行中或结束后查看状态：

```bash
omem develop list
omem develop show RUN_ID
```

一次正常循环是：编码角色修改代码 → runner 保存副本快照 → 宿主实际运行必需的非 setup 命令 → 新的 code-reviewer 会话独立评审。评审不接收开发者自评；它读取固定需求、原件、项目规则、实际代码、完整差异和宿主检查结果，使用只读代码工具，逐项给出 `passed/failed/not_run`，并记录路径、行号、问题和修改建议。参考 [宿主检查与独立评审 ↗](../../../apps/server/src/development/runner.ts#L375 "说明宿主实际检查、新会话只读评审及源码污染防护。")

按 `show` 的结果行动：

- **检查失败**：不能进入 ready，流程回到编码修复。
- **检查改变源码或产生未忽略文件**：本轮不直接送审；下一轮先整理变化再重验。
- **评审 changes_requested**：上一轮 review 会交回编码角色修复。
- **编码声明 blocker、评审 verdict=blocked、或没有任何必需宿主检查**：任务停在 `blocked`。
- **三轮仍未通过**：任务停在 `blocked`，副本和问题保留；解决前提后运行 `omem develop resume RUN_ID`。
- **Ctrl+C/SIGTERM 中断**：状态为 `interrupted`，用 resume 继续保留的副本。参考 [三轮回修与 ready 条件 ↗](../../../apps/server/src/development/runner.ts#L430 "支持失败分流、最多三轮和进入 ready 的必要条件。")
- **需求换版**：旧任务固定在启动时的 requirement revision，不能切换到新版标准。保留代码副本，先刷新并确认新版需求为 current，再用 `develop start` 新建任务；不要用旧 run 的 resume 代替新版验收。参考 [固定需求版本不能切换 ↗](../../../apps/server/src/development/runner.ts#L202 "说明旧任务固定 requirement revision，需求换版要新建任务。")

只有至少一个必需宿主检查实际执行且全部成功、独立评审 accepted、全部验收 passed 且没有 high/medium 问题，并且需求 revision 与源码指纹仍有效，任务才进入 `ready`。这仍不等于人类验收或上线。参考 [三轮回修与 ready 条件 ↗](../../../apps/server/src/development/runner.ts#L430 "支持失败分流、最多三轮和进入 ready 的必要条件。")

<a id="inspect-and-apply"></a>
## 第七步：人工检查差异，再应用补丁

先看完整差异和评审详情：

```bash
omem develop diff RUN_ID
omem develop show RUN_ID
```

在教学案例中，人工检查至少回答四个问题：是否真的增加处理完成入口；已知类别分派是否保持；未知类别是否仍走兜底；“输入对象不被修改”对应的验收项是否在 review 中 passed。还要检查是否混入无关改动。这里说明的是检查方法，不表示材料已经证明存在这些代码。相关查看命令见 [开发任务查看与应用命令 ↗](../../../apps/server/src/cli.ts#L680 "支持 list、show、diff、apply 命令及 ready/applied 操作边界。")。

确认任务为 ready 后才运行：

```bash
omem develop apply RUN_ID
```

apply 会重新核对独立副本、目标仓库和需求，而三类失效情形的恢复动作不同：

1. **评审后的独立 checkout 指纹变化**：现有评审不再覆盖当前代码，先对变化后的代码重新验证，不能直接 apply。
2. **原仓库 HEAD 已离开 base，或工作区不再干净**：系统拒绝覆盖并保留补丁；人工合并到当前工作区后，重新运行项目验证。
3. **需求 revision 已变化或页面不再 current**：旧评审不能应用。先确认新版需求，再按新版验收启动新的开发任务并重新评审；不能只把旧补丁人工合并后沿用旧结论。参考 [固定需求版本不能切换 ↗](../../../apps/server/src/development/runner.ts#L202 "说明旧任务固定 requirement revision，需求换版要新建任务。")[apply 三类失效分支 ↗](../../../apps/server/src/development/runner.ts#L492 "区分副本变化需重新验证、原仓库变化需人工合并、需求变化需按新版重新评审。")

三项都通过后，系统才从已评审 checkout 重新生成二进制 patch，先运行 `git apply --check`，再应用到原工作区。参考 [apply 三类失效分支 ↗](../../../apps/server/src/development/runner.ts#L492 "区分副本变化需重新验证、原仓库变化需人工合并、需求变化需按新版重新评审。")

最后用状态边界判断下一步：

| 状态 | 能说明什么 | 还不能说明什么 |
| --- | --- | --- |
| `created/coding/checking/reviewing` | 任务正在推进 | 不能叫完成 |
| `interrupted/failed/blocked` | 有中断、错误或前提不足 | 需处理原因后 resume；需求换版时新建任务 |
| `ready` | 固定源码指纹上的必需检查成功，独立评审接受 | 不等于人类验收、发布或上线 |
| `applied` | 已评审补丁进入原工作区 | 仍是未提交修改；没有自动 commit、push 或部署 |
| 需求页 `implemented/verified/released` | 分别表达代码存在、验证通过和已经发布 | 开发检查不会自动改写需求页状态 |

CLI 把 ready 与 apply 分开。真实实现、检查和发布若要更新需求页，应先捕获为材料，再 refresh 调查。参考 [开发任务查看与应用命令 ↗](../../../apps/server/src/cli.ts#L680 "支持 list、show、diff、apply 命令及 ready/applied 操作边界。")[检查不会自动标记上线 ↗](../../../docs/reader-first/requirement-followup.md#L94 "说明需求页发布状态需捕获真实代码或检查材料后重新调查。")

<a id="capability-boundaries"></a>
## 当前能做什么，哪些视觉能力没有内置

当前本地 CLI 覆盖两组核心能力：

- requirements：`track/list/show/refresh/watch/handoff/board/follow/unfollow`。
- develop：`register/projects/start/list/show/resume/diff/apply`。

develop 在本机个人库和仓库运行，不接受远端 `--url/OMEM_URL`；start/resume 前台执行，中断后显式 resume。当前编码权限适配只验证 Traex ACP。参考 [当前本地 develop 能力 ↗](../../../apps/server/src/cli.ts#L653 "支持本地运行、无远端 URL、前台执行、恢复和 Traex ACP 范围。")

`browser` 和 `design` 只是项目命令的 purpose 类别，用来接入项目已经具备的浏览器或设计检查；它们不表示 omem 内置了视觉验收平台。当前没有内嵌 Figma 下载缓存、静态 Mock runtime、测试包或 Studio，也不保证 Agent 能自动完成任意 Figma 验收。真实 UI 需求必须预先准备对应工具、skills 和 browser/design 命令；缺少这些前提时，评审应写“未验证”，普通 build 不能冒充完整视觉验收。参考 [Mock 与 Figma 能力边界 ↗](../../../docs/reader-first/requirement-followup.md#L80 "说明 browser/design 接入方式和当前未内置的视觉验收组件。")
