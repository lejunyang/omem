# 让需求变成可跟进的事项和可评审的代码

用“工单完成入口”这一教学案例，说明怎样通过自然语言持续跟进同一需求、纠正事实与范围、暂停或恢复调查，并在准备好项目与外部能力后明确交办 Traex 后台实现。文章重点区分普通问答中的外部能力调用与开发 run 的固定输入：设计节点等目标标识须先进入当前需求材料再交办；通用 skill/CLI/MCP 装配已经接通，但真实 Figma、OAuth、多编码提供方和需求变化后的自动重新规划仍需另行实现与验证。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="four_messages"></a>
## 先用四句话走完全程

下面的“工单完成入口”是**教学案例**，不是当前快照中已经实施或验收过的业务。假设现有工单服务已经能选择处理队列，现在要增加“处理完成”入口：本期保留未知类别兜底，小李负责接口，你关注上线阻塞，最终还要确认实现不会修改调用方传入的对象。

在本人私聊里，可以依次说：

1. **“帮我跟进工单完成入口，只看本期上线阻塞和需要我回答的事。”**
2. **“批量完成不在本期；小李只负责接口，页面由我做；设计目标是文件 X 的节点 Y，请把它纳入当前需求并重新调查。”**
3. **“请在 ticket-service 实现当前这版需求，使用已登记的 project-design 能力。”**
4. **“现在做到哪了？把实际检查、评审和可查看的差异给我。”**

第一句建立持续需求并返回“已排队”；第二句保存当前原话，并让设计目标随需求一起重新调查；第三句才授权编码并选择能力；第四句只读已有任务，不会再次派发。通用的 skill、只读 CLI 和 MCP 装配已经接通，但某个真实 Figma 服务是否可用，要以能力检查和实际节点调用结果为准。参考 [自然语言跟进与编码旅程 ↗](../../../docs/reader-first/assistant-orchestration.md#L19 "支持跟进、纠正、明确编码交办和查询结果的用户流程，以及通用能力与真实 Figma 的边界。")

这里有一个重要边界：选择 `project-design` 只会把能力的固定版本交给后台任务，**不会自动传递普通问答里临时输入的节点参数或回执**。所以节点 ID、文档 URL 或研发对象标识应先成为当前需求的反馈/原件并完成刷新；如果它只出现在此前一次普通问答中，后台编码不能据此假定自己已经收到。当前 `start_development` 合同没有单独的“节点参数/问答回执交接”字段。参考 [需求工作动作合同 ↗](../../../packages/contracts/src/work.ts#L20 "定义跟进、反馈、范围和编码交办字段；编码动作没有节点参数或问答回执字段。") [编码入队时固定能力版本 ↗](../../../apps/server/src/development/queue.ts#L125 "支持项目默认或单次能力选择、固定能力引用、任务去重，并显示队列未持久化节点参数或授权原话。") [普通问答能力会话 ↗](../../../apps/server/src/assistant/acp-model.ts#L175 "支持普通问答在本轮 workspace 创建独立 CapabilitySession，说明其目录不等于开发 run 的 external-inputs。")

模型只能提出候选动作。宿主还会核对本人私聊、当前用户原话、动作版本和请求幂等性；持久写入后才返回成功回执。尤其是编码交办，必须直接来自当前消息并表达明确实现意图。“帮我跟进”“解释一下实现”或材料里引用的“请修改”都不构成编码授权。参考 [本人私聊与明确编码交办 ↗](../../../apps/server/src/assistant/work.ts#L35 "支持需求写操作的私聊边界，以及编码必须来自当前消息的明确实现交办。") [跟进与编码的持久回执 ↗](../../../apps/server/src/assistant/work.ts#L388 "支持动作幂等、跟进只返回已排队，以及编码返回 taskId 和尚未完成。")

<a id="continuous_requirement"></a>
## 第一步：建立并维护同一个需求

主助手会先读取已有需求、项目、开发任务和可用能力，再选择当前对象；只有项目或范围确实无法区分时才需要补充。持续跟进要把三类内容分开：

| 层次 | 案例中的内容 | 后续怎样变化 |
| --- | --- | --- |
| 需求事实 | 本期范围、验收、决定、负责人、实现与发布状态 | 由原始材料调查和复核 |
| 关注策略 | 只看上线阻塞；重要变化才通知 | 你可以随时调整 |
| 人工反馈 | “批量完成不在本期”“页面由我做”“设计节点是 Y” | 保存原话，可撤销并重新调查 |

选择项目或主题的 `contextIds`，会持续跟随它未来加入或移出的成员；选择 `materialKeys`，则盯住指定原件及其修订。关注策略另存关注项、排除项和通知强度，不能混成需求事实。跟进、反馈、撤销、改范围、暂停、恢复、刷新与编码交办也是不同动作。参考 [需求工作动作合同 ↗](../../../packages/contracts/src/work.ts#L20 "定义跟进、反馈、范围和编码交办字段；编码动作没有节点参数或问答回执字段。")

新消息、文档修订或项目成员变化不会为每条消息另建一个需求。维护服务按“阅读计划 + 当前材料范围”判断是否变化；同一页已经在运行时，只更新目标摘要，让连续变化合并进入后续一轮。保存新计划也不会替换正在运行的冻结输入。参考 [变化摘要与合并排队 ↗](../../../apps/server/src/knowledge/page-worker.ts#L96 "支持同一需求的连续材料变化合并处理，不替换当前运行输入。")

当你说“负责人不是小王，是小李”时，这句原话成为新的人工原件，随后才由调查与复核判断它如何影响需求；保存瞬间不等于事实已验证。常用动作的含义是：

- **pause**：关闭自动维护，可停止当前自动维护任务，但不删除需求。
- **resume**：恢复自动维护并请求刷新。
- **refresh**：只安排重新调查。
- **revoke**：保留反馈历史，但让指定反馈不再作为有效输入。
- **scope**：改变材料边界；**attention**：改变阅读和通知策略。

旧版本动作会被拒绝并要求重读现状。反馈或撤销的回执也只承诺“重新调查”，不提前宣称结论已经改变。参考 [反馈、撤销和维护控制 ↗](../../../apps/server/src/assistant/work.ts#L456 "支持反馈原话捕获、版本检查、范围修改、暂停恢复刷新及重新调查回执。")

<a id="structured_requirement"></a>
## 第二步：把讨论读成验收项和行动项

调查完成后，同一需求应形成稳定的目标、非目标、验收项和行动项。下面仍是教学写法，不代表真实项目事实：

| 项目 | 示例内容 | 怎样读 |
| --- | --- | --- |
| objective | 增加单工单处理完成入口 | 说明要解决什么 |
| nonGoals | 本期不做批量完成 | 明确本轮不做什么 |
| C1 | 未知类别仍走原兜底 | `missing / implemented / verified / released / uncertain` |
| C2 | 完成入口选择正确队列 | 同上 |
| C3 | 不修改调用方输入对象 | 同上 |
| C4 | 项目必需检查通过 | 同上 |
| A1 | 小李确认接口约定 | 另有负责人、等待对象、日期、状态与确定性 |

`implemented` 只说明已有实现证据，`verified` 表示验收证据成立，`released` 才表示有发布证据。材料不足通常应写 `uncertain`，不能把“没看到”一律写成 `missing`。行动还要区分 `confirmed`、`proposed` 和 `uncertain`；一句“最好顺便改 UI”不能自动变成承诺、负责人或截止时间。参考 [结构化需求状态 ↗](../../../packages/contracts/src/development.ts#L3 "定义目标、非目标、验收状态、行动状态和确定性。")

需求页的 `current=false` 表示依赖材料已经变化，开工前必须刷新。编码交接导出的是固定引用原件、需求 revision 与 current 状态，而不是可变工作文件；编码与评审因此可以针对同一版验收。设计节点等外部目标只有先进入这些固定输入，后台角色才能稳定复现“本次究竟要读什么”。参考 [固定需求交接 ↗](../../../apps/server/src/knowledge/requirements.ts#L28 "支持交接固定引用原件和需求 revision，并显式暴露 current 边界。")

如果要把 A1 变成个人待办，目前仍需现有 CLI/API：

```bash
omem requirements follow REQUIREMENT_KEY A1
omem tasks list --json
omem requirements unfollow REQUIREMENT_KEY A1
```

只有当前 revision、`current=true` 且行动为 `confirmed` 时才能 follow。“我来跟进”不会把原材料里的小李改写成当前用户。需求更新会同步同一待办；若你手工改过待办，自动同步会停下并保留修改，重新 follow 才恢复。行动从新稿消失或不再明确时，旧待办也不会被自动删除。参考 [行动 follow 与人工修改保护 ↗](../../../apps/server/src/knowledge/requirement-tasks.ts#L33 "支持 confirmed/current/revision 前提，以及人工修改或行动消失时保留旧待办。")

<a id="prepare_project"></a>
## 实施前：登记项目和真实检查

后台编码需要一个已登记的本地项目。下面只是配置形状示例，真实项目要替换仓库、规则和命令：

```json
{
  "name": "工单服务",
  "repository": "/absolute/path/to/ticket-service",
  "instructions": "保留未知类别兜底；兼容现有调用方。",
  "ruleFiles": ["docs/development.md"],
  "capabilities": ["project-design"],
  "commands": [{
    "name": "test",
    "command": "node",
    "args": ["--test"],
    "cwd": ".",
    "purpose": "test",
    "required": true,
    "timeoutMs": 600000
  }]
}
```

```bash
omem develop register ticket-service ./development-project.json
omem develop projects
```

`purpose` 可以是 `setup/test/build/browser/design`。setup 由 Agent 按需运行；所有 `required=true` 且非 setup 的命令由宿主在每轮实现后真实执行。至少要有一项这样的检查，否则任务不能进入 `ready`。命令以本机用户权限运行，独立副本不是操作系统沙箱，所以只能登记你信任且项目确实需要的命令。项目合同也允许设置默认 capability 列表。参考 [项目登记与命令信任边界 ↗](../../../docs/reader-first/requirement-followup.md#L37 "解释项目配置、检查类别、必需检查、干净基线和独立副本边界。") [项目默认能力字段 ↗](../../../packages/contracts/src/development.ts#L48 "支持项目配置中的 capabilities、命令用途和 required 属性。")

开工时原仓库必须干净；任务固定当前提交、需求 revision 和引用原件，在独立 checkout 中工作。未提交文件、被忽略的凭据和本地依赖不会自动进入副本。项目规则、额外 `ruleFiles` 和仓库 skills 应先提交到基线，才能稳定提供给编码与评审；修改文件前，编码工具还要求先读取适用规则。参考 [固定代码基线与需求版本 ↗](../../../apps/server/src/development/runner.ts#L148 "支持干净仓库、固定 HEAD 与需求 revision、持久 run 和独立 checkout。") [项目规则与仓库技能 ↗](../../../apps/server/src/development/workspace.ts#L230 "支持读取项目 instructions、祖先规则、命令和仓库 skill，并要求修改前先读适用规则。")

<a id="prepare_capabilities"></a>
## 需要设计或研发上下文时，先装配能力

第一次配置或排障时，按下面的顺序做：

```bash
omem capabilities add ./capability.json --json
omem capabilities check project-design --json
omem capabilities skill project-design design-reading
omem capabilities attach ticket-service project-design
```

`add` 导入能力声明及 skill 快照；`check` 核对 CLI、运行声明的健康/登录检查，并发现 MCP 允许工具；`skill` 用于查看操作说明；`attach` 设置项目默认能力。主助手也可在单次 `start_development` 中显式覆盖默认选择；显式空列表表示本任务不用外部能力。任务入队时会固定 `{id, revision}`，之后再次 add 或 attach 不会悄悄改变已排队任务。参考 [能力配置与操作路线 ↗](../../../skills/omem-cli/references/capabilities.md#L47 "说明 add、check、skill、attach、call、单次覆盖和图片读取边界。") [能力快照与版本注册 ↗](../../../apps/server/src/capabilities/registry.ts#L32 "支持 skill 资源复制、revision 生成、current 更新和旧版本保留。") [编码入队时固定能力版本 ↗](../../../apps/server/src/development/queue.ts#L125 "支持项目默认或单次能力选择、固定能力引用、任务去重，并显示队列未持久化节点参数或授权原话。")

能力调用链可以记成：**catalog → inspect → read_skill → call → 查看文字或图片 → 保存 receipt**。

| 对象 | 作用 | 不能代替什么 |
| --- | --- | --- |
| skill | 告诉 Agent 何时、怎样读取外部上下文 | 不授予新权限 |
| 只读 CLI | 用固定可执行文件和参数槽读取信息 | `readOnly` 声明不是 OS 沙箱 |
| MCP | 只暴露配置允许且服务实际发现的工具 | 连接成功不等于每个业务对象都有权限 |
| receipt | 保存能力版本、参数、时间和真实结果 | 图片路径不等于已经看图或完成视觉验收 |

`available=true` 只证明已声明检查通过、CLI 存在、允许的 MCP 工具已发现；若没有登录检查，认证会标为未单独验证。CLI 动态输入只能填配置声明的完整参数值；MCP 也只能调用 allowlist 中的工具。每次调用都会保存真实结果，凭据值在持久 JSON 中遮蔽，图片字节落为私人文件路径。参考 [能力可用性检查 ↗](../../../apps/server/src/capabilities/session.ts#L220 "支持 CLI、声明检查、MCP 工具发现，以及 available 不代表业务对象权限。") [受限调用与结果回执 ↗](../../../apps/server/src/capabilities/session.ts#L280 "支持 CLI 参数限制、MCP allowlist、调用错误保存、图片落盘和回执字段。")

普通问答与开发任务有两套工作目录。普通问答可以当场调用能力并回答，但它的 receipt 留在本轮问答目录；开发 run 会新建自己的 `external-inputs`。因此“我刚才在聊天里看过节点”不等于编码与评审已获得该节点。正确做法是先让目标标识进入当前需求材料并刷新，再交办；开发角色随后在自己的 run 中按固定能力重新调用，编码与独立评审才会共享该 run 的回执。当前没有把普通问答 receipt 自动复制给开发 run 的能力。参考 [普通问答能力会话 ↗](../../../apps/server/src/assistant/acp-model.ts#L175 "支持普通问答在本轮 workspace 创建独立 CapabilitySession，说明其目录不等于开发 run 的 external-inputs。") [问答与开发回执目录边界 ↗](../../../docs/reader-first/assistant-orchestration.md#L115 "明确普通问答、开发任务和直接 CLI 调用使用不同回执目录，并列出仍未完成的自动入库与重规划。") [能力工具与共享回执 ↗](../../../apps/server/src/capabilities/session.ts#L381 "定义 catalog、inspect、read_skill、call 和 receipts，支持同一任务后续角色读取外部输入。") [编码与评审共享开发回执 ↗](../../../apps/server/src/development/runner.ts#L381 "支持开发和独立评审在同一 run 中使用固定能力目录、工具及 external-inputs 回执。")

后台开始编码前会对所选能力执行 `inspect`。预检能看见的缺可执行文件、声明检查失败、MCP 连接失败或允许工具未发现，会让 run 直接进入 `blocked`，不消耗编码回修轮次。若未配置登录检查，预检不能证明业务对象权限；真正调用某个节点时发生的认证或对象访问失败，会保存为失败回执，再由编码/评审据此报告阻塞或未验证，而不是由 CapabilitySession 自动改写 run 状态。参考 [能力可用性检查 ↗](../../../apps/server/src/capabilities/session.ts#L220 "支持 CLI、声明检查、MCP 工具发现，以及 available 不代表业务对象权限。") [受限调用与结果回执 ↗](../../../apps/server/src/capabilities/session.ts#L280 "支持 CLI 参数限制、MCP allowlist、调用错误保存、图片落盘和回执字段。") [能力预检失败时阻塞 ↗](../../../apps/server/src/development/runner.ts#L320 "支持编码前 inspect 所选能力，并将预检不可用转为 blocked。")

真实 Figma 不会因通用装配存在而自动出现：必须先登记并核对实际服务、登录和节点访问；拿到截图路径后仍要真正读图并执行项目的视觉验收。参考 [能力配置的安全与认证边界 ↗](../../../skills/omem-cli/references/capabilities.md#L1 "支持 skill/CLI/MCP 配置、只读声明非沙箱、OAuth 未接和示例不等于真实 Figma。")

<a id="delegate_and_status"></a>
## 第三、四步：明确交办，然后读取真实进度

“帮我跟进”只授权维护需求，**不授权改代码**。要启动后台任务，请在本人私聊的当前消息中明确说“请在 ticket-service 实现当前这版需求，使用 project-design”。节点标识应已经存在于当前需求材料，而不是只写在更早的一次闲聊中。若省略能力选择就采用项目默认值；同一 requestId，或同一需求与项目已有 active 任务时，会复用任务，避免重复派发。交办成功会立即返回 `taskId` 和“现在尚未完成”；后台等待需求 `current` 且已有结构化 requirement 后再创建 run。参考 [本人私聊与明确编码交办 ↗](../../../apps/server/src/assistant/work.ts#L35 "支持需求写操作的私聊边界，以及编码必须来自当前消息的明确实现交办。") [跟进与编码的持久回执 ↗](../../../apps/server/src/assistant/work.ts#L388 "支持动作幂等、跟进只返回已排队，以及编码返回 taskId 和尚未完成。") [编码入队时固定能力版本 ↗](../../../apps/server/src/development/queue.ts#L125 "支持项目默认或单次能力选择、固定能力引用、任务去重，并显示队列未持久化节点参数或授权原话。") [等待当前需求并复用 run ↗](../../../apps/server/src/development/queue.ts#L35 "支持后台等待 current requirement、按 task id 复用 run 并执行。")

此后可以离开聊天。回来问“做到哪了”时，应看到真实状态而非模型猜测：

- durable job 的 `state` 与 runner 的 `phase`；
- 当前 `message` 或 `error`；
- 每条真实检查及 `exitCode`；
- 独立评审与 `runId`；
- `delivery`：代码在独立副本还是已应用到登记仓库；
- 保存的已评审 patch，以及当前副本是否仍满足 `matchesReviewed`。

`matchesReviewed=false` 或 `null` 时，不能宣称当前文件仍与评审版本一致。独立副本完成了工作而登记仓库尚未变化，是 `ready` 阶段的正常现象。参考 [状态、交付位置与已评审差异 ↗](../../../apps/server/src/assistant/work.ts#L106 "支持查询 phase、检查、评审、独立副本位置、保存 patch 和 matchesReviewed。")

服务重启会复用持久 task、run id 和 checkout，但这不等于恢复同一个模型会话。“取消开发”停止 active job 并保留已有代码和检查结果；“暂停需求跟进”关闭自动维护，是另一件事。参考 [等待当前需求并复用 run ↗](../../../apps/server/src/development/queue.ts#L35 "支持后台等待 current requirement、按 task id 复用 run 并执行。") [取消开发保留结果 ↗](../../../apps/server/src/development/queue.ts#L209 "支持取消 active job 时保留已有代码与检查结果。")

<a id="review_and_apply"></a>
## 为什么 ready 可信，又为什么它还不是上线

每个开发 run 最多走三轮：

1. 编码角色读取固定需求、原件、项目规则、真实代码和上一轮问题，逐项覆盖所有验收 ID。
2. 宿主运行所有 required 且非 setup 的登记命令，保存结果和代码指纹。
3. 全新的只读 code-reviewer 会话从原需求、完整 diff、真实代码与检查结果独立判断。
4. 若评审要求修改，问题回到下一轮；前提不足、三轮耗尽或需求变化则转为 `blocked` 并保留副本。

开发与评审共享同一组固定 capability 配置及该 run 的 `external-inputs` 回执。评审可以先看开发实际读取过的外部输入，必要时再补查；共享资料不代表自动接受开发结论，评审仍要自行检查代码、差异、宿主检查和外部资料。参考 [能力工具与共享回执 ↗](../../../apps/server/src/capabilities/session.ts#L381 "定义 catalog、inspect、read_skill、call 和 receipts，支持同一任务后续角色读取外部输入。") [编码与评审共享开发回执 ↗](../../../apps/server/src/development/runner.ts#L381 "支持开发和独立评审在同一 run 中使用固定能力目录、工具及 external-inputs 回执。")

只有至少一项宿主必需检查实际运行且全部成功、评审 accepted、所有验收通过、没有中高优问题、评审前后源码指纹一致、需求 revision 仍 current，run 才进入 `ready`。检查命令污染源码、评审期间源码变化或编码期间需求变化都会使本轮结论失效。参考 [三轮编码检查与独立评审 ↗](../../../apps/server/src/development/runner.ts#L447 "支持宿主检查、全新只读评审、ready 条件和需求变化时阻塞。")

| 状态 | 能说明什么 | 还不能说明什么 |
| --- | --- | --- |
| ready | 独立副本针对固定需求通过必需检查与独立评审 | 原仓库已修改、人工验收、发布 |
| applied | 已把评审过的补丁应用到原工作区 | 已提交、push、部署 |
| verified | 需求页已有真实验收证据 | 已发布 |
| released | 需求页已有真实发布证据 | 不能由本地代码检查自动推导 |

`apply` 是显式后续动作。执行前会重新核对评审指纹、原仓库 HEAD 与干净状态、需求 revision，再从已评审树重建 patch，先检查后应用为未提交修改。任一边界变化就拒绝覆盖。参考 [显式 apply 的重新校验 ↗](../../../apps/server/src/development/runner.ts#L576 "支持应用前重新核对指纹、原仓库状态和需求版本，并只应用未提交补丁。")

因此，主助手说 `ready` 时应同时给出检查、评审、差异与剩余问题，而不能说“已经上线”。如果需求实质变化，当前流程保留旧 run 的代码并要求按新版需求重新交办或评审；自动保留代码后重新规划尚未接通。

<a id="decision_model"></a>
## 快速模型只排调查顺序

消息很多时，快速 work 决策会对意图、相关性、变化类型和是否需要补读给出建议；`capability_relevance` 则判断某个能力是需要、背景、无关还是不确定。它们都只帮助决定先读哪里、先检查哪个能力。未就绪或短时超时后，本轮仍按目录由主助手正常调查。参考 [快速建议不构成权限 ↗](../../../apps/server/src/assistant/work.ts#L297 "支持快速 work 建议只用于调查排序，不能作为事实或授权。")

主助手仍要消解真实对象、补读当前需求与原件、处理含糊和冲突，并形成动作候选；宿主仍负责当前交办、身份、版本、幂等和持久写入。快速分数不能删掉低分材料、覆盖用户纠正、改变负责人或截止时间、证明能力可用、授权工具调用或跳过独立评审。当前材料只证明这两条分流路径已接线，没有证明它们已经降低耗时或提高准确率。

<a id="capability_boundary"></a>
## 当前能力边界与操作清单

截至 2026-10-06，可以把能力分成三组。

**已经接通**

- 自然语言建立需求跟进、调整范围与关注、保存或撤销纠正、暂停、恢复与刷新；
- 本人明确交办后，Traex 后台持久派发；
- skill 快照、只读 CLI、标准 MCP 的登记、检查、按项目或任务选择、实际调用和回执保存；
- 同一开发 run 内，编码与独立评审复用固定能力配置和外部输入回执；
- 服务重启复用任务和代码副本，宿主真实检查并提供状态、评审和结果查询。参考 [当前能力总表 ↗](../../../docs/reader-first/assistant-orchestration.md#L7 "支持自然语言需求、Traex 后台流程、外部能力装配和未完成项目的当前边界。")

**仍需 CLI/API 做一次性配置或排障**

- 登记项目、规则和检查命令；
- add/check/skill/attach/disable 外部能力；
- 把结构化行动 follow/unfollow 为个人待办；
- 查看详细 diff、处理阻塞和显式 apply。

**尚未完成或不能宣称**

- 某个真实 Figma 或私有研发服务已经配置、登录并能读取指定对象；
- 把普通问答的节点参数或 receipt 自动交接给后续开发 run；
- OAuth 交互登录、能力回执自动进入全库检索以及自动过期策略；
- Codex/Claude 编码提供方适配；当前编码权限路径只验证 Traex；
- 需求变化后保留旧代码并自动重新规划；
- 自动提交、push、部署或发布。参考 [当前能力总表 ↗](../../../docs/reader-first/assistant-orchestration.md#L7 "支持自然语言需求、Traex 后台流程、外部能力装配和未完成项目的当前边界。") [能力配置的安全与认证边界 ↗](../../../skills/omem-cli/references/capabilities.md#L1 "支持 skill/CLI/MCP 配置、只读声明非沙箱、OAuth 未接和示例不等于真实 Figma。") [问答与开发回执目录边界 ↗](../../../docs/reader-first/assistant-orchestration.md#L115 "明确普通问答、开发任务和直接 CLI 调用使用不同回执目录，并列出仍未完成的自动入库与重规划。")

实际使用时检查六件事：

1. 跟进回执是否只说“已排队”，并给出同一个需求 key。
2. 纠正回执是否说明会重新调查，而非立即宣称事实已验证。
3. 外部节点或对象标识是否已进入当前需求材料并完成刷新，而非只停留在旧聊天回执。
4. 开工前需求是否 current、项目是否已登记、原仓库是否干净、必需检查是否可跑；能力预检是否通过，实际对象是否读取成功。
5. 交办回执是否给出 taskId 并明确“现在尚未完成”；进度是否包含阶段、退出码、评审、delivery 和 matchesReviewed。
6. ready 后是否仍由你决定查看 diff、apply、提交与发布；只有真实发布证据才能把需求更新为 released。
