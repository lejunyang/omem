# 先认识 omem：把材料变成能找回的工作记忆

以“保存项目约定、找回其中的决定、跟进一次评审”为贯穿示例，说明 omem 如何把原始材料、知识文章、个人记忆与事项连接成从保存、理解到行动的个人工作流程，并区分当前可用能力与尚未实现的主动能力。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="start-with-one-agreement"></a>
## 从一份项目约定开始

假设你刚收到一份“支付服务评审约定”，其中写着：“所有接口变更必须由两名维护者评审。”几周后，你需要确认这项决定，并等待张三完成一次评审。omem 要解决的正是这种日常断层：材料当时保存了，后来却难以找回上下文，也没有自然地连接到下一步行动。它把文档、代码、聊天、图片和个人经历放进同一个工作记忆中；代码会获得专门的结构定位，但不会被拆成另一套知识产品。参考 [产品定位 ↗](../../../README.md#L3 "支持 omem 将多种个人材料组织为可读、可找回、可行动的记忆，并说明代码仍共享同一知识库。")

本地开始使用时，运行 `osdk install`、`osdk deps --frozen` 和 `osdk run dev`，再打开终端给出的 Web 地址。开发模式会载入仓库材料和已经发布的知识，同时保留个人数据；启动本身不会自动整理整个知识库。正式运行也从界面的“输入材料”开始。参考 [启动与入口 ↗](../../../README.md#L7 "支持本地启动步骤、开发模式的数据行为以及正式运行从输入材料开始。")

<a id="save-and-return"></a>
## 保存原件，留下以后能返回的出处

进入“输入材料”，选择“文本＋图片＋链接”，把标题填写为“支付服务评审约定”，将约定正文粘贴进去，然后点击“保存材料与证据”。同一入口还允许附带链接或图片；飞书文档、指定 Git 文件和允许范围内的服务器文本文件则有各自的导入入口。参考 [材料输入表单 ↗](../../../apps/web/src/App.vue#L623 "支持文本、链接、图片及其他导入方式的用户操作和保存按钮。")

保存后，在“原始材料”中按标题找到它。页面会显示保存时间、当前或历史版本，并允许打开固定原文和版本历史。因此，将来搜索到“双人评审”时，你不仅能看到一句摘要，还能回到当时保存的约定。参考 [原始材料阅读 ↗](../../../apps/web/src/App.vue#L556 "支持按标题查找材料、查看当前或历史版本、打开固定原文及版本历史。")

这里的重点是**先保留原件，再在其上建立理解**。原件、用于搜索的片段和面向读者的讲解承担不同职责；整理出来的解释可以帮助检索和理解，却不会因此变成第二份独立事实。参考 [来源与讲解分工 ↗](../../../docs/reader-first/architecture.md#L5 "解释原件、检索结构和知识页面为何采用不同组织单位，以及派生解释不构成独立事实。")

<a id="four-kinds"></a>
## 材料、知识、记忆与事项有什么不同

沿用这个例子，可以把四类内容理解为：

| 类型 | 在示例中是什么 | 主要作用 |
| --- | --- | --- |
| 原始材料 | “支付服务评审约定”的固定版本 | 保留原文、版本与出处 |
| 知识文章 | “接口变更为什么要双人评审，提交前检查什么” | 围绕问题组织多份材料，帮助读懂 |
| 个人记忆 | 以后能够找回并用于回答的“该项目要求接口变更经双人评审” | 维护当前事实、偏好和经验，并连接后续使用 |
| 事项 | “等待张三的评审回复，明天上午九点检查” | 推动需要完成、等待或提醒的行动 |

个人记忆并不是把原文复制一遍。目标流程是从原始记录逐步形成经历、当前事实、偏好与经验，再汇成对人物、项目和主题的持续理解；目前已有来源变化后的重核验基础，但周期整合、事件时间检索和自动跟进仍属于后续能力。参考 [记忆形成路径 ↗](../../../docs/reader-first/architecture.md#L25 "支持个人记忆从记录、经历到当前事实和持续理解的目标流程，并界定尚未实现的后续能力。")

事项也不能由材料中的一句话自动推断出来。约定里出现“需要评审”，只说明规则；只有你明确说“帮我跟进这次评审”，才构成要记录或修改的行动。讨论材料、他人的承诺和本人明确交办需要分开处理。参考 [交办与讨论边界 ↗](../../../apps/server/src/assistant/message-workflows.ts#L3 "支持只有明确的本人交办才创建或修改事项，并区分讨论、他人承诺和等待跟进。")

<a id="find-and-understand"></a>
## 找回决定，再把原句变成可理解的知识

几周后，你可以在顶部搜索“支付接口 双人评审”。搜索会结合原文、代码名称和已有知识；启用中文语义索引时，它也会参与召回。结果提供“查看固定片段”的入口；若没有结果，页面会建议改用原文关键词或先导入材料。参考 [统一搜索界面 ↗](../../../apps/web/src/App.vue#L539 "支持搜索结合原文、代码名称、已有知识和可选语义索引，并能打开固定片段。")

如果只想确认约定原句，打开固定片段即可。如果想知道“为什么这样约定、改接口时该检查什么”，可以进入知识库的“全部分类”，点击“整理文章”，选择约定及相关材料，并填写主题、阅读对象和想弄懂的问题。系统会进行调查、写作和独立复核，成功后发布为文章；材料在生成期间变化会阻止旧结果发布，失败也不会覆盖已有正文。参考 [从材料整理文章 ↗](../../../docs/reader-first/operations.md#L27 "支持用户选择材料和阅读问题后经历调查、写作、复核与发布，以及材料变化和失败时的保护行为。")

还可以在原始材料中选择某一段，使用“和记忆一起思考”继续追问。回答保存后仍可重新打开本次提供的依据，但界面明确提示：目前不会自动逐条核验回答中每个主张是否都受到材料支持。因此，重要决定仍应回看原文，而不是只依赖生成回答。参考 [依据明确的追问 ↗](../../../apps/web/src/ChatPane.vue#L81 "支持从选定片段提问、保存回答、重新打开依据，并说明回答主张尚未逐条自动核验。")

<a id="follow-up-review"></a>
## 把评审变成可持续跟进的事项

确认“双人评审”约定后，在“日常助理”中明确输入：**“帮我跟进张三对支付接口变更的评审回复，明天上午 9 点提醒我检查。”** 日常会话会保留消息、处理状态和结果；如果处理失败或等待重试，消息不会消失，可以再次尝试。参考 [日常助理会话 ↗](../../../apps/web/src/DailyAssistant.vue#L49 "支持直接交办评审跟进、保留处理状态以及对失败消息进行重试。")

形成事项后，可以记录等待对象“张三的评审回复”和下次跟进时间。跟进时间与真正的截止时间分开：前者表示何时回来检查，后者表示事情何时必须完成。没有填写时间时，也可以只登记为等待。参考 [跟进时间设置 ↗](../../../apps/web/src/TaskFollowUpControls.vue#L25 "支持记录等待对象和下次跟进时间，并说明跟进时间不改变截止时间、不会自动联系对方。")

到期提醒会进入通知中心。若张三尚未回复，可以修改跟进安排或暂缓提醒；收到回复后，需要由你将事项标为完成。事项页还支持重新打开、取消以及查看事项来源。系统目前不会自动联系张三，也不会因为通知被阅读就判断评审已经完成。参考 [事项状态与来源 ↗](../../../apps/web/src/App.vue#L736 "支持事项的等待、提醒、完成、重新打开及查看来源等可见操作。")

<a id="code-and-other-materials"></a>
## 代码与约定如何放在同一条理解链上

代码在 omem 中仍是一种材料，只是多了 AST、符号等结构定位能力。例如，约定写着“失败请求最多重试三次”，你可以把约定文档和实现重试逻辑的代码一起选入文章，整理成“规则是什么、代码在哪里落实、修改时要检查什么”。文章生成和检索允许同一路径同时处理文档、代码和学习笔记，代码结构帮助定位定义，却不会取代业务背景和约定原文。参考 [跨材料知识整理 ↗](../../../docs/reader-first/general-knowledge.md#L11 "支持同一知识流程同时使用文档、代码和学习笔记，并保留代码 AST 定位。")

这意味着 omem 的目标不是建立一个孤立的代码百科，而是让代码和会议记录、设计说明、个人经验共同回答真实问题。不过，当前尚未完成完整的意图路由和跨文件功能链扩展，因此不能把结构定位理解为系统已经自动掌握整个项目的所有调用与设计关系。参考 [检索能力边界 ↗](../../../README.md#L31 "支持统一召回基础已经存在，同时完整意图路由和跨文件功能链仍待实现。")

<a id="current-boundaries"></a>
## 现在能做什么，还不能期待什么

当前已经具备一条基础但真实可用的链路：输入并保留固定版本、阅读原始材料、统一搜索、基于选定材料提问、整理知识文章、在来源变化后重核验记忆，以及创建、等待、改期、完成或取消事项并接收站内提醒。持续的项目、人物和主题理解仍在后续阶段；当前服务也是单用户实现，不具备团队隔离。参考 [当前实施进度 ↗](../../../docs/reader-first/progress.md#L5 "支持统一搜索、知识页面、记忆重核验和事项提醒等当前基础，并说明持续理解仍属后续且当前为单用户实现。")

尚不能期待的能力包括：自动监听他人回复、周期回顾、日历或学习卡，以及对任意跨文件功能链的完整理解。飞书、远程访问、外部通知、全局 hooks 和屏幕监听也不是默认开启的能力，而是需要单独配置并明确范围的集成。换句话说，当前最合适的使用方式是由你明确保存材料、提出问题和交办事项，让系统负责保留出处、协助找回与持续记录，而不是把它当成已经能够自行观察并完成所有工作的全自动助理。参考 [运行与主动能力限制 ↗](../../../docs/reader-first/operations.md#L19 "支持单用户运行范围、外部集成需明确启用，以及自动监听回复、周期回顾等能力尚未实现。")
