# 先认识 omem：把材料变成能找回的工作记忆

面向第一次接触 omem 的个人用户，以“保存项目评审约定、后来找回决定、再明确交办一次评审跟进”为教学示例，说明如何开始使用，以及原始材料、知识文章、个人记忆和事项各自解决什么问题。文章同时解释代码为何仍与文档共用一个知识库，并标明当前检索、提醒、外部监听与解析能力的实际边界。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="what-it-does"></a>
## 它把“保存、找回、理解、行动”接在一起

omem 面向的不是单纯“存文件”，而是这样一条日常链路：你先把文档、代码、聊天、图片或个人经历保存下来；过一段时间，用自己的问题找回其中的决定；需要推进事情时，再把决定变成可以等待、提醒和完成的事项。代码有额外的结构定位能力，但仍与其他材料共用一个知识库。参考 [omem 的产品目标 ↗](../../../README.md#L1 "支持 omem 将文档、代码、聊天、图片和个人经历组织为可读、可找回、可行动记忆，以及代码共享同一知识库的定位。")

下文使用一个**教学示例**：你保存了一份项目评审约定，后来想确认“合并前需要谁确认”，并请助手在明天上午 9 点提醒你检查张三的评审回复。这个具体项目场景用于说明操作，不代表它已经单独完成端到端验收；当前真实跑通的相邻流程是“读书会预算从 80 元改为 120 元，再创建等待报名回复的事项”。参考 [个人记忆与跟进的真实样例 ↗](../../../docs/reader-first/assistant-memory-flow.md#L3 "支持 80 元改为 120 元、更新同一记忆、明确委托后创建等待事项、改期和完成的真实验收范围。")

<a id="start-and-capture"></a>
## 先保存约定，再从原件核对

开发环境中，依次运行：

```bash
osdk install
osdk deps --frozen
osdk run dev
```

然后打开终端打印的 Web 地址。运行需要已安装并登录的 Agent CLI，但不强制本地大语言模型、Docker 或 Python；启动也不会自动生成整库 Wiki。参考 [启动与运行前提 ↗](../../../README.md#L7 "支持开发启动命令、Web 地址、Agent CLI 前提以及启动不自动生成整库知识的说明。")

进入**输入材料**，最简单的入口是“文本＋图片＋链接”：填写标题（例如“项目评审约定”）和正文后保存。也可以导入飞书文档、Git 文件或受限的服务器文本文件。以后更新同一份约定时，沿用相同的来源标识，系统会保存为新版本。参考 [输入材料与版本入口 ↗](../../../apps/web/src/App.vue#L882 "支持文本、图片、链接、飞书文档、Git 文件和服务器文本文件入口，以及相同来源标识产生新版本。")

保存后到**原始材料**检查结果。这里能看到当前版、历史版、保存时间与原文，也可以选中片段提问或打开固定来源。先做这一步，是为了确保后续答案有可回看的来路。参考 [原始材料与历史版本界面 ↗](../../../apps/web/src/App.vue#L779 "支持当前与历史版本、原文阅读、片段提问和版本历史的用户操作。")

要注意：**保存成功只表示原件已经进入资料库**。它不等于文章已经整理好、每条约定都已经成为个人记忆，也不等于系统获得了替你联系评审者或创建事项的授权。材料用途分析目前也需要页面按钮或明确任务触发，不会在每次捕获后自动运行。参考 [材料分析需要明确触发 ↗](../../../README.md#L38 "支持材料用途整理不是每次捕获后自动运行，且分类不等于事实正确的边界。")

<a id="four-objects"></a>
## 用同一个例子分清材料、知识、记忆与事项

这四类对象共享来源和搜索入口，但承担不同工作，所以不应混成一份东西：

| 对象 | 在评审示例中是什么 | 主要回答 |
| --- | --- | --- |
| **原始材料** | 你保存的“项目评审约定”原文及其历史版本 | 当时原话是什么？ |
| **知识文章** | 围绕“本项目如何完成评审”整理的讲解，可同时引用约定、会议记录和代码 | 这些材料合起来意味着什么？ |
| **个人记忆** | 经提取、核验并应用后，值得以后直接找回的当前事实，例如“当前评审需要谁确认” | 我现在应记住什么？ |
| **事项** | “等待张三回复，明天 9 点检查”的行动记录 | 接下来要推动什么？ |

这种区分来自用途，而不是文件格式：原件负责保留历史，文章围绕读者问题跨材料解释，派生解释不会变成第二份独立事实。参考 [保存、检索与讲解的用途分离 ↗](../../../docs/reader-first/architecture.md#L5 "支持原件保留历史、页面跨材料解释、派生内容不成为第二份独立事实的概念区分。")

如果你希望新人理解完整评审流程，而不只是找回一个决定，可以在**知识库**点击“整理文章”：先选择相关材料，再填写主题、阅读对象和想弄懂的问题。系统经过调查、写作和独立复核后发布；生成期间材料变化会阻止旧结果发布，失败也不会覆盖已有正文。参考 [从材料整理知识文章 ↗](../../../docs/reader-first/operations.md#L39 "支持网页选材、填写主题和阅读目标、经过调查写作复核后阅读，以及材料变化和失败时的处理。")

个人记忆比整篇原文短、比知识文章直接，但仍应保留依据。事项则有独立的状态和时间语义。真实生活样例验证了一个关键边界：保存预算和查询预算都不会创建报名事项，只有用户明确委托后才会生成等待事项。参考 [保存和查询不自动创建事项 ↗](../../../docs/reader-first/assistant-memory-flow.md#L7 "支持材料、记忆与事项具有不同授权边界，只有用户明确委托后才创建等待事项。")

<a id="retrieve-and-check"></a>
## 找回决定时，先问业务问题，再打开依据

在顶部搜索中直接输入你真正想解决的问题，例如：**“当前评审约定是什么？”**或**“合并前需要谁确认？”**。搜索会覆盖材料、讲解、已应用记忆与事项，也可以让助理补读材料后组织回答；结果旁仍保留“阅读原文”“查看原始依据”或“查看对应原文”的入口。参考 [统一搜索与回看来源 ↗](../../../apps/web/src/App.vue#L689 "支持搜索材料、讲解、记忆和事项，由助理补读回答，并从结果打开原文或依据。")

读答案时，先看它是否回答了你的业务问题，再打开引用核对版本。如果约定后来修改过，当前答案应使用新版，旧决定仍应从历史版本回读。已经真实验收的预算样例中，80 元改为 120 元后更新的是同一条记忆；再次提问使用 120 元，80 元仍可沿旧版本追溯。参考 [换版后更新同一记忆并保留历史 ↗](../../../docs/reader-first/assistant-memory-flow.md#L7 "直接支持预算从 80 元换版为 120 元后更新同一记忆 ID、使用新版回答，并让旧约定仍可沿固定旧版本追溯。")

搜索结果不是权威本身，原件才是事实来路。当前检索已经共享原文、知识、记忆和事项的候选与上下文，但实际 HTTP 搜索仍可能把计划或提示材料排在有效解释之前；看到不理想的首条结果时，应打开实际命中、换用原文关键词，或让助理继续补读，而不要把“模型最后答对”理解成排序已经可靠。参考 [当前检索效果边界 ↗](../../../docs/reader-first/progress.md#L28 "支持共享召回与完整上下文已经接通，但排序和答案要点选择仍有限、HTTP 搜索仍可能把计划材料排在有效解释之前。")

<a id="code-together"></a>
## 代码和文档仍在同一个问题里

假设评审约定写在文档里，而真正阻止合并的检查落在代码中。你可以把约定文档与 Git 文件一起保存、一起搜索，也可以把它们同时选入一篇知识文章。系统会对代码多做定义、函数和调用位置等结构定位，但引用仍回到对应版本的代码原文；它不会另造一个与个人材料分离的“代码知识库”。参考 [代码与其他材料共享来源体系 ↗](../../../docs/reader-first/architecture.md#L5 "支持代码使用专用结构解析但不建立独立知识库，并可与其他材料共同参与跨材料解释。")

实际使用时，查函数名更适合精确定位，问“评审检查如何生效”则需要补读相关上下文。界面会明确提醒：按名称找到的调用位置只是候选，同名方法可能属于不同对象，别名和动态调用也可能遗漏。当前还没有完整的跨文件调用图，因此不要据一个调用候选断言全部影响范围。参考 [代码调用位置只是候选 ↗](../../../apps/web/src/App.vue#L707 "支持界面对同名方法、别名和动态调用遗漏的提示，以及不能把名称候选当完整调用图的边界。")

<a id="follow-review"></a>
## 把“知道约定”变成一次明确的评审跟进

找到决定后，如果确实需要推进评审，请明确交办，例如：**“帮我跟进张三的评审回复，明天上午 9 点提醒我检查。”** 日常助理界面就以这类话术作为输入示例；等待对象和跟进时间会保存，完成或取消以实际操作结果为准。参考 [日常助理的评审跟进入口 ↗](../../../apps/web/src/DailyAssistant.vue#L135 "支持直接交办、保存等待与跟进时间，以及“跟进张三评审回复”的实际输入示例。")

提交后，不要只看模型文字说“会提醒”，还要检查宿主返回的成功回执；模型只负责提出行动候选，真正表示事项已经创建或改变的是宿主应用后的结果。参考 [行动候选与宿主成功回执 ↗](../../../docs/reader-first/assistant-memory-flow.md#L45 "直接支持模型只提出行动候选，成功回执来自宿主，以及应以实际创建、改期和完成结果确认操作成功。")

再到**事项与待办**确认：

1. 状态是否为“等待回复”；
2. 等待对象是否正确；
3. “下次跟进”是否为你指定的时间；
4. 它是否被误填成业务截止时间；
5. 完成或取消后，提醒是否停止。

事项页把截止时间、下次跟进和暂缓提醒分开显示；到点提醒进入通知中心，而把通知标为已读并不会完成事项或取消后续提醒。参考 [事项状态、时间与通知语义 ↗](../../../apps/web/src/App.vue#L999 "支持等待对象、下次跟进、暂缓、截止时间分开显示，完成或取消停止提醒，以及已读不等于完成事项。")

当前可依赖的是站内事项链：明确交办、等待、改期、完成、取消和到期提醒。真实预算样例验证了重启后补发一次、重复检查不重发、改期后按新时间提醒、完成后停止。参考 [提醒重启、去重、改期与完成验收 ↗](../../../docs/reader-first/assistant-memory-flow.md#L27 "直接支持真实流程分别检查重启后补发一次、重复检查不重发、改期后按新时间提醒和完成后停止。") 尚不能期待系统自动监听张三或群聊的回复，也不能期待它主动联系对方；目前需要你把回复结果告诉系统，外部通知也要另行集成。参考 [站内提醒与外部监听边界 ↗](../../../docs/reader-first/operations.md#L33 "支持没有自动监听对方回复，且外部通知需要独立显式集成的限制。")

<a id="current-boundaries"></a>
## 目前可以依赖什么，哪些仍要人工把关

目前可以实际使用的主干是：输入多种材料并保留版本；从统一入口搜索原文、讲解、记忆和事项；按读者问题选材整理文章；在持久会话中明确交办、等待、改期、完成或取消，并接收站内提醒。系统的目标是让答案能回到固定原文，而不是只给一段无法核对的总结。参考 [当前基础能力总览 ↗](../../../README.md#L27 "支持固定版本、统一检索、问题驱动知识整理、持久会话、事项和站内提醒构成当前可用主干。")

仍需保留这些预期边界：

- 启动不会自动生成整库 Wiki，材料用途分析也不是每次保存后自动执行；文章需要选材和阅读目标。
- 检索排序与答案要点选择仍有限，重要决定应打开引用核对。
- 项目评审场景是本文的教学示例；完整真实验收目前只有一个隔离的生活样例，不能代表大而杂的个人库、多来源冲突或所有问法。
- 自动监听外部回复、周期回顾、可靠的跨轮与时间理解、持续人物/项目记忆、成熟 PDF/Office/OCR 和完整跨文件调用图仍未完成。
- 当前服务是 SQLite/shared-token 的单用户实现，不应当作团队权限隔离方案。

这些限制不会妨碍你从一份项目约定开始，但会改变使用方式：**保存后核对原件，搜索后核对引用，需要行动时明确交办，收到外部结果后主动回报并完成事项。** 参考 [当前未实现能力与单用户边界 ↗](../../../docs/reader-first/progress.md#L67 "支持完整解析、跨文件调用图、跨轮时间理解、持续项目记忆、外部回复监听等仍有缺口，以及当前为单用户实现。")
