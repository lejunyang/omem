# 先认识 omem：把材料变成能找回的工作记忆

用一份项目协作约定贯穿保存、找回、理解与跟进流程，说明原始材料、知识文章、个人记忆和事项各自解决什么问题，以及当前能力的边界。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="why"></a>
## 从一个容易遗忘的决定开始

**教学示例：**你把《项目协作约定》保存进 omem，其中写着“合并前需完成评审”。几周后，你忘了这条决定为何存在；找到原文后，又想在明天上午 9 点检查小李是否回复。

omem 要解决的不是“再找一个地方存文件”，而是让文档、代码、聊天、图片和个人经历进入同一个工作记忆：之后既能回到原文，也能读到围绕问题组织的讲解，还能把下一步变成可跟进的事项。代码会多一层结构定位，但不会另建一套知识产品。参考 [产品目标 ↗](../../../README.md#L1 "支持 omem 将多种材料组织成可读、可找回、可行动的记忆，并让代码共享同一知识库的定位。")

界面把日常助理、知识库、原始材料、输入材料、事项、通知等入口放在同一个个人空间中，因此这个例子可以沿着“保存 → 找回 → 理解 → 行动”走完，而不必先学习数据库或内部模型。参考 [个人工作记忆入口 ↗](../../../apps/web/src/App.vue#L40 "支持界面把材料、知识、助理、事项和通知等能力放在同一导航中的描述。")

<a id="start"></a>
## 先保存约定，再确认它可被找回

本地开始使用时，依次运行 `osdk install`、`osdk deps --frozen` 和 `osdk run dev`，再打开终端显示的 Web 地址。启动只载入已有材料与知识，不会自动替你生成整库文章；正式运行也从“输入材料”开始，并需要已安装、已登录的 Agent CLI。参考 [启动与使用入口 ↗](../../../README.md#L7 "支持首次启动命令、Web 地址、不会自动生成整库知识以及 Agent CLI 前提。")

进入**输入材料**，为示例填写标题《项目协作约定》，粘贴正文并保存。网页也支持附带链接和一张图片，或从飞书文档、指定 Git 文件、允许目录中的服务器文本文件导入；Git 方式只读指定版本，不会拉取仓库或运行脚本。参考 [材料输入方式 ↗](../../../apps/web/src/App.vue#L623 "支持文本、图片、链接、飞书、Git 和服务器文件等输入方式及 Git 只读行为。")

保存后，到**原始材料**打开它。页面会显示当前版本、固定片段和版本历史。若以后用相同来源标识保存了不同内容，系统会新增版本并保留旧版；内容没有变化时则复用已有版本。这样，未来看到“规则已修改”时，仍能回看当初那段文字。参考 [材料版本保存 ↗](../../../apps/server/src/store.ts#L168 "支持内容不变复用版本、内容变化创建新版本并保留历史的行为。")

<a id="four-things"></a>
## 同一份约定会产生四种不同东西

这四类对象刻意分开，因为它们回答的问题不同：

| 对象 | 示例 | 回答什么 |
| --- | --- | --- |
| **原始材料** | 《项目协作约定》及其版本 | 当时到底写了什么、来自哪里 |
| **知识文章** | 《为什么合并前要评审》 | 怎样把多份材料组织成可读解释 |
| **个人记忆** | “这个项目要求合并前评审” | 以后回答时可以复用什么 |
| **事项** | “明早检查小李的评审回复” | 下一步做什么、何时再看 |

原始材料负责保真；检索片段和讲解页面按各自用途组织，派生讲解可以帮助理解，却不是第二份独立事实。参考 [材料与讲解分工 ↗](../../../docs/reader-first/architecture.md#L5 "支持原件、检索结构和围绕读者问题的讲解采用不同组织单位，派生内容不成为独立事实。")

知识文章需要你明确选择相关文档、代码或记录，再填写主题、读者和想弄懂的问题；系统调查、撰写并复核后，才会把文章放进知识库。参考 [整理知识文章 ↗](../../../docs/reader-first/architecture.md#L11 "支持用户先选材料，再填写主题、目标和读者，由系统围绕问题调查、撰写并复核。")

个人记忆则来自另一条受治理的处理链。启用自动处理和可用 Agent 后，系统才会提炼并核验候选；可靠结果可生效，需要选择的内容进入“待判断”。即使自动处理未启用，原文仍然可以阅读和检索。参考 [记忆处理条件 ↗](../../../apps/web/src/LearningView.vue#L81 "支持记忆候选需后台提炼和核验、未启用自动处理时原文仍可用的说明。")

事项也不是材料里出现一句“要评审”就自动创建。讨论、转述和他人的承诺不等于你的交办；只有你明确要求记录或修改事项，系统才应执行动作。参考 [明确交办规则 ↗](../../../apps/server/src/assistant/message-workflows.ts#L1 "支持讨论和他人承诺不会自动成为用户事项，只有明确要求才执行记录或修改。")

<a id="retrieve"></a>
## 找回决定，并在需要时整理成解释

几周后，在顶部搜索输入“合并前 评审”。搜索会结合原文、代码名称和已有知识；若已启用中文语义索引，它也会参与。结果可以直接打开固定原文片段，因此你能先确认“当时怎么写”，再决定是否需要更完整的解释。参考 [统一搜索结果 ↗](../../../apps/web/src/App.vue#L539 "支持搜索结合原文、代码名称、已有知识和可选中文语义索引，并可打开固定片段。")

若仅找回原句还不够，进入**知识库**，点击“整理文章”，选择《项目协作约定》以及相关设计说明或代码，填写“为什么合并前要评审、团队怎样执行”，并注明写给谁看。当前 Agent 配置可用时，系统会调查、写作、复核。参考 [文章生成条件 ↗](../../../apps/server/src/knowledge/api.ts#L133 "支持文章生成需要 Agent、明确阅读目标和固定选材，并启动调查写作流程。") 发布前还会重新比较文章记录的依赖摘要与当前材料；若材料在生成期间发生变化，旧选材不会被悄悄当作当前版本发布。参考 [发布前依赖校验 ↗](../../../apps/server/src/knowledge/repository.ts#L122 "直接支持发布阶段重新比较材料和文章依赖摘要，输入变化时拒绝发布旧结果。")

这里要保留一个现实预期：统一搜索入口已经可用，但复杂自然语言问题的相关性、完整意图路由和跨文件功能链仍有限。搜到结果不等于最佳答案一定排在第一位；必要时应换成原文关键词，或打开命中的上下文继续阅读。参考 [检索当前限制 ↗](../../../docs/reader-first/progress.md#L5 "支持统一搜索已实现首片，但完整意图路由、跨文件功能链和复杂相关性仍有限。")

<a id="code"></a>
## 代码与文档一起成为材料

如果这条约定还对应自动检查脚本，可以把脚本和约定文档一起选进文章。对用户而言，代码仍是一种材料；区别只是系统会额外识别函数、导入和符号，帮助定位“定义在哪里、依赖在哪里”。业务原因仍需要结合同一条流程中的说明、配置、调用者和输入输出来理解。参考 [代码材料的作用 ↗](../../../docs/reader-first/current-system.md#L34 "支持 AST 用于结构定位，而业务意义仍需结合调用者、配置、测试和设计说明调查。")

当前结构分析适合单文件 TypeScript 与 Vue 定位，也能解析确定的相对导入；它不是完整类型分析或完整调用图，跨文件调用和跨版本符号续接仍有限。因此，代码知识适合与设计说明共同阅读，不应把结构候选误当成已经确认的业务关系。参考 [代码结构边界 ↗](../../../docs/reader-first/current-system.md#L34 "支持当前代码解析针对单文件 TypeScript 与 Vue、可定位相对导入且调用和跨版本续接有限。")

<a id="follow-up"></a>
## 把评审变成真正可跟进的事项

确认约定后，可以到**日常助理**明确交办：

> 帮我跟进小李的评审回复，明天上午 9 点提醒我检查。

也可以在**事项与待办**中手工记录。事项能处于待推进、等待回复、已完成或已取消等状态；截止时间与下次跟进时间分开，适合表达“项目真正何时截止”和“我何时再检查”这两件事。参考 [事项与跟进设置 ↗](../../../apps/web/src/App.vue#L736 "支持事项状态、截止时间与跟进时间分开，以及手工记录待办的用户流程。")

到约定时间，系统会产生站内通知，提醒你检查进展，并允许完成、稍后提醒或取消。它不会自动联系小李，也不会因为通知已读就把事项判为完成；是否收到回复、是否完成，仍需你确认。参考 [站内跟进提醒 ↗](../../../apps/server/src/tasks/follow-up.ts#L17 "支持到期或跟进时只产生站内检查提醒，不自动联系他人。")

<a id="limits"></a>
## 现在能做什么，哪些仍需人工

目前可用的主链包括：统一保存多种材料并保留版本；让顶部搜索、知识检索与助手共用召回基础，检索全文、符号、记忆和知识；显式选材后整理文章；配置后台处理后提炼并重核验记忆；以及记录、等待、改期、完成、取消和站内提醒。参考 [统一召回基础 ↗](../../../README.md#L27 "支持全文、符号、记忆和知识可参与检索，以及顶部搜索、知识检索与助手共用召回基础。")

它还不是会自己接管工作的主动助理：不会自动监听评审对象的回复，不会主动联系对方，也没有周期回顾、日历或学习卡。参考 [主动提醒边界 ↗](../../../docs/reader-first/operations.md#L23 "支持没有自动监听回复、周期回顾、日历或学习卡，且通知已读不等于事项完成。")

持续维护完整的项目、人物和主题理解，以及事件时间能力，仍属于后续阶段。复杂问题也尚无完整意图路由、跨文件功能链和回答完整性保障，因此搜到内容并不等于系统已经完整理解问题。参考 [持续理解进度 ↗](../../../docs/reader-first/progress.md#L20 "支持项目、人物、主题整合和事件时间能力仍处于后续阶段。") [复杂回答边界 ↗](../../../docs/reader-first/current-system.md#L30 "支持完整意图路由、跨文件功能链和回答完整性检查仍然缺失。")

此外，当前服务以 SQLite 和共享令牌面向单用户；飞书、外部通知、全局钩子和屏幕监听都需要单独、明确地启用。把 omem 当作“保存有来处的信息、按问题找回并辅助行动”的个人工具最准确，不要把它理解成默认监控所有工作、自动替你做决定的团队系统。参考 [单用户与显式连接 ↗](../../../README.md#L55 "支持当前是单用户服务，外部通知、飞书与屏幕监听等需要独立明确启用。")
