# 先认识 omem：把材料变成能找回的工作记忆

面向服务已经启动、第一次使用 omem 的个人用户。沿“保存合并评审约定—提问找回决定—需要时整理多份材料—明确交办跟进—收到外部回复后完成事项”的单一教学示例，说明每一步的入口和页面可见结果，并区分原始材料、知识文章、个人记忆与事项。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="start-with-agreement"></a>
## 从一份约定开始

omem 把文档、代码、聊天、图片和个人经历放进同一个可检索、可回看、可继续行动的知识库。对第一次使用者，最短路径不是先整理一整套知识，而是：**保存一份材料，按问题找回其中的决定，需要推进时再明确交办。** 参考 [omem 的使用目标 ↗](../../../README.md#L1 "支持 omem 将多种材料组织为可读、可找回并可用于行动的记忆，且代码与其他材料共享知识库。")

下面只标明一次教学示例：你要保存“合并前请张三完成评审”这条项目约定，后来问“合并前要做什么？”，再交办“明天上午 9 点提醒我检查张三的回复”。服务已经启动，本文直接从页面操作开始。

<a id="save-and-read"></a>
## 保存后，先确认原文已经出现

进入 **输入材料**。本例选择“文本＋图片＋链接”，标题可填“项目合并约定”，正文填写“合并前请张三完成评审”，然后点击“保存材料与证据”。同一页面也提供飞书文档、Git 文件和服务器文本文件入口；它们适合已有材料，不是本例的必经步骤。参考 [输入材料入口 ↗](../../../apps/web/src/App.vue#L882 "支持文本、图片、链接、飞书文档、Git 文件和服务器文本文件入口，以及文本标题与正文的填写方式。")

保存成功后，页面会打开刚保存的版本，并提示“材料已保存，固定证据片段已生成”；若内容没有变化，则提示复用原版本。参考 [保存后的页面反馈 ↗](../../../apps/web/src/App.vue#L466 "支持保存后刷新并打开该版本，以及新内容和重复内容各自的可见提示。")

在 **原始材料** 页面确认三件事：

1. 标题和正文与输入一致；
2. 页面标为“当前版本”，并显示保存时间；
3. “选择原文提问或查看来源”中可以打开固定原文，“版本历史”中可以回看旧版。

这就是保存成功的可见结果，也是以后核对“当时原话”的位置。参考 [原始材料与版本历史 ↗](../../../apps/web/src/App.vue#L779 "支持当前版、历史版、保存时间、片段提问、打开原文和版本历史等可见结果。")

保存只会先把原件及版本留住。它不等于已经整理出知识文章，也不保证正文里的每句话已经成为个人记忆，更不会因为材料提到张三就自动创建跟进事项；事项需要后续明确交办。参考 [查询与交办的边界 ↗](../../../docs/reader-first/assistant-memory-flow.md#L9 "支持保存和查询不会自动创建事项，后续跟进必须来自用户明确请求。")

<a id="ask-and-check"></a>
## 直接提问，必要时打开依据

在顶部搜索框输入真正的问题：**“合并前要做什么？”** 页面会保留“实际搜索命中”；点击 **综合回答** 后，助理会围绕当前问题查找、补读材料，并整理带引用的回答。即使综合回答没有完成，原始搜索结果仍可继续阅读。参考 [综合回答与实际命中 ↗](../../../apps/web/src/SearchAnswer.vue#L205 "支持综合回答会查找、补读并生成带引用回答，同时保留实际搜索命中和失败后的原始结果。")

搜索覆盖原始材料、知识讲解、已应用记忆和事项。不同结果会提供“阅读原文”“阅读讲解”“查看原始依据”或“查看事项”等入口，所以判断答案时不要只看一句总结：打开引用，确认它指向刚才保存的约定及正确版本。参考 [统一搜索与原文入口 ↗](../../../apps/web/src/App.vue#L689 "支持搜索材料、讲解、记忆与事项，以及从各类结果阅读原文、讲解、原始依据或事项。")

提问只是找回和解释信息，不是交办。问“合并前要做什么？”不会自动生成一条跟进张三的事项。参考 [查询与交办的边界 ↗](../../../docs/reader-first/assistant-memory-flow.md#L9 "支持保存和查询不会自动创建事项，后续跟进必须来自用户明确请求。")

如果首条结果偏题或答案不够确定，先点开实际命中和引用；也可以改用原文中的词语，例如“张三”“完成评审”，再继续问。当前检索仍可能把计划或说明材料排在更有用的解释之前，因此原文入口仍是重要的核对手段。参考 [搜索效果的当前边界 ↗](../../../docs/reader-first/progress.md#L48 "支持实际搜索仍可能让计划或提示材料排在有效解释之前，回答材料选择仍需改进。")

<a id="organize-article"></a>
## 多份材料需要反复阅读时，再整理文章

只有一个明确决定时，直接提问并打开原文通常已经够用。若你还保存了会议记录、评审规范和相关代码，希望得到一份可反复阅读的“本项目如何完成评审”，再进入 **知识库** 点击 **整理文章**。这是使用建议：文章适合跨材料解释问题，并不是每次保存后都必须生成。

整理分两步：

1. 选择相关文档、代码或记录；
2. 填写文章主题、想弄懂什么以及写给谁看，然后点击“开始整理”。

界面会说明 AI 将调查、撰写并复核，完成后可在知识库阅读。参考 [整理文章的选材步骤 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L127 "支持第一步选择相关文档、代码或记录，并说明重新整理时仍是同一篇文章。") [整理文章的阅读目标 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L213 "支持第二步填写文章主题、想弄懂什么和写给谁看，以及调查、撰写、复核后在知识库阅读。")

开始后，知识库会显示“已排队整理”或“正在整理”；成功后显示“已完成”和“阅读文章”，失败则显示原因。参考 [文章整理状态 ↗](../../../apps/web/src/knowledge/KnowledgeHome.vue#L315 "支持已排队、正在整理、失败原因、已完成和阅读文章等页面可见状态。") 阅读页会展示标题、摘要、阅读目标、分节正文和可点击引用，因此文章负责回答“这些材料合起来意味着什么”，同时仍能回到对应原文。参考 [知识文章阅读页 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L83 "支持文章展示标题、摘要、阅读目标、分节正文、引用以及来源说明。")

固定材料在生成期间发生变化时，旧结果不会直接发布；失败也不会覆盖已有正文。参考 [文章生成与失败处理 ↗](../../../docs/reader-first/operations.md#L39 "支持从普通材料整理文章、材料变化阻止旧结果发布，以及失败不覆盖旧正文。")

<a id="four-objects"></a>
## 材料、知识、记忆与事项各做什么

当你需要选择入口时，可以用同一份评审约定来区分四类对象：

| 对象 | 本例中的内容 | 主要回答 |
| --- | --- | --- |
| **原始材料** | “合并前请张三完成评审”的原文及历史版本 | 当时原话是什么？ |
| **知识文章** | 综合约定、会议记录和代码形成的评审说明 | 这些材料合起来意味着什么？ |
| **个人记忆** | 经提取、独立核验并应用后，系统当前记住的评审事实 | 系统目前为我记住什么？ |
| **事项** | 等待张三回复、明天 9 点检查的行动记录 | 接下来要推动什么？ |

它们共享来源和搜索入口，但职责不同：原件保留历史，知识文章围绕读者问题跨材料解释；派生解释帮助理解，却不会取代原件成为第二份事实。参考 [一个来源体系，多种用途 ↗](../../../docs/reader-first/architecture.md#L5 "支持代码与其他材料共享来源体系，原件保留历史，文章跨材料解释且不成为第二份事实。") 个人记忆需要经过提取、独立复核和应用，并保留来源历史；事项则记录明确交办后的行动、等待和完成状态。参考 [个人记忆与事项 ↗](../../../docs/reader-first/current-system.md#L54 "支持个人记忆经过提取、独立复核和应用并保留来源历史，以及事项具备等待、改期、完成和提醒能力。")

因此，“保存”“提问”“整理文章”和“交办”会产生不同结果：保存后看原文，提问后看回答与命中，整理后在知识库读文章，交办后到事项列表核对行动记录。

<a id="documents-and-code"></a>
## 文档和代码可以解释同一个问题

代码仍属于同一个来源体系，只是多了适合代码的结构定位；它不会另建一套与文档分离的知识库。参考 [一个来源体系，多种用途 ↗](../../../docs/reader-first/architecture.md#L5 "支持代码与其他材料共享来源体系，原件保留历史，文章跨材料解释且不成为第二份事实。")

如果评审约定写在文档里，而实际检查落在代码中，可以从 **输入材料 → Git 文件** 保存指定代码文件。随后按用途选择入口：

- 想核对约定原话，打开原始文档；
- 想找具体函数，在搜索中选择“定位实现”并查函数名；
- 想理解“约定如何由代码执行”，让综合回答补读，或把文档和代码一起选入知识文章。

Git 入口只读取指定提交中的文件；知识文章的选材页也允许选择相关文档、代码或记录。参考 [Git 文件与代码选材 ↗](../../../apps/web/src/App.vue#L888 "支持从输入材料选择 Git 文件，以及整理文章时选择相关代码与文档。") [整理文章的选材步骤 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L127 "支持第一步选择相关文档、代码或记录，并说明重新整理时仍是同一篇文章。")

按名称找到的调用位置只是候选：同名方法可能属于不同对象，别名和动态调用也可能遗漏。当前还没有完整的跨文件调用图，所以应结合上下文和引用核对，不能把一个名称命中当成完整影响范围。参考 [调用位置只是候选 ↗](../../../apps/web/src/App.vue#L694 "支持定位实现用途及同名方法、别名和动态调用可能造成候选不完整的界面提示。") [跨文件调用图尚不完整 ↗](../../../docs/reader-first/progress.md#L89 "支持当前完整跨文件调用图仍有缺口，不能把名称候选当作完整影响范围。")

<a id="delegate-and-close"></a>
## 明确交办，并在外部回复后收尾

知道约定之后，如果确实要推进，请到 **日常助理** 明确输入：**“帮我跟进张三的评审回复，明天上午 9 点提醒我检查。”** 页面本身就用这类话术说明交办；等待和跟进时间会保存，完成或取消以实际操作结果为准。参考 [日常助理的交办入口 ↗](../../../apps/web/src/DailyAssistant.vue#L135 "支持直接交办、保存等待与跟进时间，以及跟进张三评审回复的具体输入示例。")

发送后，到 **需求与待办** 检查页面可见结果：

1. 出现一条对应事项；
2. 状态为“等待回复”；
3. “等待”显示张三的评审回复；
4. “下次跟进”显示明天上午 9 点，而不是被写成“到期”；
5. 到点提醒进入通知中心，完成或取消后停止提醒。

事项页明确区分等待对象、下次跟进、暂缓提醒和到期时间，并提供“标为完成”。参考 [事项状态与完成操作 ↗](../../../apps/web/src/App.vue#L999 "支持等待回复、等待对象、下次跟进、到期、完成和取消等页面状态，以及通知已读不等于完成事项。") 如果等待对象或时间不正确，可展开 **跟进设置** 手动修正；这里也明确提示跟进时间不会改变截止时间，系统不会自动联系对方。参考 [跟进设置与外部联系边界 ↗](../../../apps/web/src/TaskFollowUpControls.vue#L25 "支持手动修正等待对象和跟进时间，且跟进时间不改变截止时间、不会自动联系对方。")

omem 目前不会自动知道张三已经回复。收到外部回复后，你仍需主动告诉日常助理，例如“张三已经回复，评审完成了”，或者直接在事项卡片点击“标为完成”，然后确认状态显示“已完成”。把通知标为已读只会清除未读提醒，不等于完成事项，也不会取消后续提醒。参考 [事项状态与完成操作 ↗](../../../apps/web/src/App.vue#L999 "支持等待回复、等待对象、下次跟进、到期、完成和取消等页面状态，以及通知已读不等于完成事项。") [外部回复需要主动告知 ↗](../../../docs/reader-first/operations.md#L33 "支持日常消息的交办、等待、改期、完成和取消能力，并明确没有自动监听对方回复且通知已读不等于事项完成。")

整条使用路线可以归结为三件事：**保存后看原件，回答后可查引用，需要行动时明确交办；外部结果回来后，再主动告诉助手并确认事项已完成。**
