# 一份材料的旅程：从导入到阅读与引用

用一份两节 Markdown 项目约定的 V1→V2 案例，串起网页输入、版本保存、当前检索、后台记忆整理、知识文章与固定引用，并说明旧版保留、自动归属以及图片、代码和 PDF/DOCX 的专门处理。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="case"></a>
## 先走一遍 V1→V2

一份材料进入 omem 后，原文版本、查找索引、当前记忆和知识文章会按不同节奏工作。最容易看清这条链的方法，是连续保存同一来源的两个版本：第一次得到可核对的 V1，第二次让当前版本变成 V2，同时观察 V1 能否继续打开。

下面是教学示例。在「输入材料」里选择「主动输入」，标题填「项目约定」，来源标识填 project-rules。两次保存都要使用这个标识；界面也直接说明，相同标识会产生新版本。若留空，页面会为本次保存生成一个新标识，下一次就会成为另一个来源。参考 [网页来源标识 ↗](../../../apps/web/src/App.vue#L1050 "说明主动输入类型、相同来源标识产生新版本，以及留空会自动分配。") [网页提交与事件元数据 ↗](../../../apps/web/src/App.vue#L491 "说明网页提交 CaptureInput，并在每次提交时新建 eventId 和 eventAt。")

V1 只有两节：

~~~markdown
# 构建约定

## 检查
合并前运行 pnpm test。

## 发布
周五发布。
~~~

页面把 source 与 externalId 作为来源身份，连同 title、正文及可选链接或图片整理成 CaptureInput，POST 到 /api/captures。文件、Git 和飞书连接器也会把各自输入归一成同一种 CaptureInput。本地文件受 captureRoots 限制，普通文本上限 500 KB；Git 会先把 ref 固定到 commit，再读取单个文件。飞书连接器读取文档正文与完整响应附件，并保留远端 revision_id。参考 [统一采集契约 ↗](../../../packages/contracts/src/index.ts#L21 "说明 CaptureInput 的来源、parts、身份及上下文字段。") [文件与 Git 连接器 ↗](../../../apps/server/src/connectors.ts#L12 "支持文件读取边界、文本限制和 Git 固定 commit 后返回 CaptureInput 的说明。") [飞书连接器 ↗](../../../apps/server/src/connectors.ts#L85 "说明飞书读取正文、保留完整响应附件和远端 revision_id，并返回 CaptureInput。")

第一次保存时，服务端用 source + externalId 查找或创建来源，写入 revision，把文字按空行切成固定片段，再把来源的 head 指向这个版本。参考 [来源创建与 revision 分片 ↗](../../../apps/server/src/store.ts#L208 "支持 source 身份、revision 创建、版本递增和固定片段生成。")

版本复用要比较完整指纹。在同一来源内，只有当前 head 的版本指纹相同才会复用；该指纹覆盖标题和 parts，也包含 context、provenance、observedAt 与 upstreamVersion。网页每次点击保存都会新建 eventId 和 eventAt，它们属于 provenance，所以即使来源标识、标题和正文不变，再次点击也会创建新版。参考 [网页提交与事件元数据 ↗](../../../apps/web/src/App.vue#L491 "说明网页提交 CaptureInput，并在每次提交时新建 eventId 和 eventAt。") [版本指纹与复用条件 ↗](../../../apps/server/src/store.ts#L164 "说明版本指纹覆盖标题、parts、context、provenance、observedAt 和 upstreamVersion，且只有当前 head 指纹相同才复用。")

现在保持 project-rules 不变，只把检查规则改成：

~~~diff
- 合并前运行 pnpm test。
+ 合并前运行 pnpm test 和 pnpm lint。
~~~

第二次保存得到 V2，revision 记录前一版，source head 转到 V2。普通材料列表和查找面向当前 head，所以新规则进入当前阅读与检索；V1 是否还能打开，则由输入类型的保留策略决定。参考 [head 更新与保存后处理 ↗](../../../apps/server/src/store.ts#L289 "支持 head、validity epoch、依赖刷新、作业入队和保留压缩的时序。") [当前 head 的检索投影 ↗](../../../apps/server/src/retrieval/units.ts#L429 "说明检索投影只读取各来源当前 head，并按 revision 身份更新。")

<a id="branches"></a>
## 保存后的四条用途

保存成功说明原件版本和固定片段已经落库，后续作业也已经入队。记忆与知识文章仍有各自的处理条件。

~~~mermaid
flowchart LR
    A[CaptureInput] --> B[revision / head / history]
    B --> C[原文阅读与历史]
    B --> D[当前查找投影]
    B --> E[后台记忆整理]
    B --> F[显式知识文章]
~~~

四条分支不会同时完成。

- **原文阅读与历史**：revision、片段、head 和版本变化在 capture 事务内完成，保存结束后再执行保留策略。参考 [head 更新与保存后处理 ↗](../../../apps/server/src/store.ts#L289 "支持 head、validity epoch、依赖刷新、作业入队和保留压缩的时序。")
- **当前查找投影**：索引是从当前 head 生成的可重建投影。每次搜索会在读取候选前同步，后台服务也会持续同步；Markdown 会按标题、段落和列表组织查找单元，表格与代码块也保留为结构化块。参考 [当前 head 的检索投影 ↗](../../../apps/server/src/retrieval/units.ts#L429 "说明检索投影只读取各来源当前 head，并按 revision 身份更新。") [搜索请求先同步 ↗](../../../apps/server/src/retrieval/unified.ts#L480 "支持 search 在读取检索候选前调用 syncAsync。") [后台同步检索投影 ↗](../../../apps/server/src/retrieval/unified.ts#L84 "说明后台循环调用 syncAsync 并继续索引批次。") [Markdown 与代码检索单元 ↗](../../../apps/server/src/retrieval/units.ts#L33 "说明 Markdown 结构切分与代码 AST 切分属于可重建检索投影。")
- **后台记忆整理**：原始输入会排入 extract_claims，但 LearningPipeline 只有在 learning.enabled=true 且找到配置的 profile 时才会创建。服务启动阶段才会调用它的 start；默认配置关闭学习。参考 [学习默认关闭 ↗](../../../apps/server/src/config.ts#L87 "说明 learning.enabled 默认值和 profile 配置。") [学习流水线装配 ↗](../../../apps/server/src/app.ts#L420 "说明只有启用配置且找到 profile 时才创建 LearningPipeline。") [服务启动学习流水线 ↗](../../../apps/server/src/app.ts#L1545 "支持服务启动阶段调用 learning.start。")
- **显式知识文章**：用户需要保存页面阅读目标并选择固定材料、项目或主题，或者显式调用知识分析入口；这条流程还要求可用 Agent。写作流水线会调查、写作并独立复核，发布后文章拥有自己的 revision。参考 [知识页面与显式分析入口 ↗](../../../apps/server/src/knowledge/api.ts#L721 "说明保存阅读目标、选择材料以及显式分析都要求可用 Agent。") [知识写作与独立复核 ↗](../../../apps/server/src/knowledge/pipeline.ts#L215 "说明写作、引用依赖、独立复核和发布文章 revision 的流程。")

刚保存完就能读原文，也能等待当前索引同步。能否随后看到记忆，取决于学习开关和 Agent；能否看到一篇围绕读者问题组织的文章，则取决于是否另行发起知识整理。

<a id="layers"></a>
## 为什么原件、索引、记忆和文章要分开

这四层承担不同责任，分开后才能同时支持核对、查找和面向读者的解释。

| 层 | 在案例中的样子 | 变化方式 |
| --- | --- | --- |
| 原件版本 | V1 的「运行 pnpm test」和 V2 的「运行 pnpm test 和 pnpm lint」 | 保存同一来源的新 revision，当前 head 前移 |
| 查找索引 | 指向 V2 对应段落的检索单元 | 从当前 head 重建或替换 |
| 当前记忆 | 例如「合并前需要运行测试与 lint」 | 经提取、复核和策略处理；来源更新或归属纠正后可失效再整理 |
| 知识文章 | 例如「提交前检查同时覆盖测试和 lint」并附固定引用 | 按阅读目标写作和复核，形成独立文章 revision |

原件层保存可核对的原始内容或附件，并记录版本关系。索引把这些内容投影成适合搜索的单位：代码文件会按 AST 符号切分，普通 Markdown 按结构切分；投影损坏后可以从原件重建。参考 [来源创建与 revision 分片 ↗](../../../apps/server/src/store.ts#L208 "支持 source 身份、revision 创建、版本递增和固定片段生成。") [Markdown 与代码检索单元 ↗](../../../apps/server/src/retrieval/units.ts#L33 "说明 Markdown 结构切分与代码 AST 切分属于可重建检索投影。")

当前记忆属于派生状态。后台先解决材料归属，再由 extractor 形成 proposals 并排入 verifier。系统会先过滤已经处理的任务行动，verifier 随后覆盖本次待验证的全部提案；完整评估批次再交给记忆策略，结果分为自动应用、等待决定或拒绝。来源换成 V2 时，依赖旧 revision 的记忆会被标为失效并安排刷新，旧记忆不会被静默改写成新事实。参考 [提取并排入验证 ↗](../../../apps/server/src/learning/pipeline.ts#L612 "支持归属先于提取、extractor 形成提案批次并排入 verify_proposals。") [待验证提案的覆盖检查 ↗](../../../apps/server/src/learning/pipeline.ts#L741 "说明系统先过滤已处理任务行动，再要求 assessments 覆盖本次待验证的全部 proposals。") [整批记忆策略评估 ↗](../../../apps/server/src/learning/pipeline.ts#L786 "说明完整提案批次交给 evaluateBatch，并统计自动应用、等待决定和拒绝三类结果。") [来源更新使旧记忆失效 ↗](../../../apps/server/src/store.ts#L304 "说明新 head 会令依赖旧 revision 的记忆失效并安排刷新。")

知识文章也是派生结果，但它面向明确读者和问题组织材料。发布前，宿主会把模型选择的行范围绑定成原文 quote，并校验正文里的每个引用；文章保存自己的依赖版本和独立 revision。参考 [宿主绑定精确引用 ↗](../../../apps/server/src/knowledge/repository.ts#L46 "说明宿主按行范围复制 quote，并校验引用落在固定原文中。") [文章独立版本发布 ↗](../../../apps/server/src/knowledge/repository.ts#L254 "说明发布校验依赖并写入知识 revision 和 head。")

表中后两行是教学示例，不属于项目约定原文。原文提供证据，记忆和文章提供经过处理的陈述；读者回查时，仍然落到固定原件。

<a id="citations"></a>
## 旧引用为什么不会漂到 V2

知识引用记录材料 key 与行范围，文章依赖同时保存生成时材料的 digest。打开引用时，服务端先检查当前材料；如果 V2 的 digest 不匹配，就沿该来源的历史 revisions 查找与依赖 digest 相同的版本，并把结果标为 current=false。引用因此仍然指向 V1，不会自动改指 V2。参考 [按 digest 查找历史原件 ↗](../../../apps/server/src/knowledge/repository.ts#L347 "说明当前材料不匹配时会遍历历史 revision，并标记为非当前。") [引用解析可用性 ↗](../../../apps/server/src/knowledge/api.ts#L306 "说明引用使用依赖 digest，并显式返回 current 与 actionable；原始材料版本不可用时给出原因。")

原文变化后，文章适用性需要单独判断。生命周期检查会比较引用所在的原章节或函数；相关内容变化，章节可标为 needs-review，但原引用仍固定在生成时的材料上。参考 [引用固定与章节复核 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L72 "说明原引用保持固定，内容变化只影响章节适用性判断。")

旧版是否还有正文可读，受保留策略约束：

- manual、chat、screen、agent 等普通事件型输入默认使用 event，保留各版本。
- file 和 git 默认使用 latest；文档型飞书输入也走 latest。新 head 建立后，旧 revision 会写入 tombstone，正文和片段被清空，关联附件进入回收候选，同时保留版本身份、替代版本与移除原因。参考 [输入类型的默认保留策略 ↗](../../../apps/server/src/storage/retention.ts#L16 "说明 file、git、文档和事件型输入的默认策略。") [latest 策略选择旧版本 ↗](../../../apps/server/src/storage/retention.ts#L144 "说明 latest 策略找出非 head 的 revision 并交给原件移除流程。") [旧原件回收内容 ↗](../../../apps/server/src/storage/retention.ts#L225 "说明回收流程写入 tombstone、解除附件引用、清除检索状态，并清空片段和 revision body。")

本文用网页主动输入演示 V1→V2，因为它默认保留事件版本。若把同一案例改成文件或 Git 导入，V1 可能只剩墓碑信息。读取旧 revision 或 evidence 时，服务端会返回 410 和保留原因；知识引用会显示不可用，不会拿 V2 冒充 V1。参考 [旧原件不可用时返回 410 ↗](../../../apps/server/src/app.ts#L829 "说明 revision 和 evidence 被回收后返回保留原因。") [引用解析可用性 ↗](../../../apps/server/src/knowledge/api.ts#L306 "说明引用使用依赖 digest，并显式返回 current 与 actionable；原始材料版本不可用时给出原因。")

<a id="assignment"></a>
## 没有指定项目时会怎样

页面可以在保存时直接选择项目或主题。这个手动选择会记录为 manual，后续模型结果不能覆盖它。参考 [手动归属优先 ↗](../../../apps/server/src/contexts/repository.ts#L43 "说明手动选择被记录为 manual，模型结果不能覆盖。")

若没有手动归属，同时系统已有候选项目或主题，并且学习流程使用原生研究模式，后台会在提取事实前尝试判断归属。第一次调查给出匹配结果后，还要由第二个独立会话复核；两次对同一组 contextIds 一致，才保存自动归属。结果含糊时，系统记录补充问题并暂停这次后续整理，原文仍然保留。参考 [双重判断后自动归属 ↗](../../../apps/server/src/learning/pipeline.ts#L664 "说明两次独立判断一致才自动保存，含糊时暂停并提问。")

手动纠正始终优先。归属改变后，错误项目下依赖这份材料的活动记忆会失效，随后重新排入提取流程；系统不会把既有记忆直接搬到新项目。参考 [纠正归属后重新整理 ↗](../../../apps/server/src/store.ts#L373 "说明归属改变会使错误范围中的记忆失效并重新入队。")

这个分支会影响后续记忆放在哪个范围，却不改变原件版本。开发自动归属时，应查看 context resolver 与 ContextRepository；修改记忆如何重建，则继续追 Store 和 LearningPipeline。

<a id="special_inputs"></a>
## 图片、代码和 PDF/DOCX 仍沿用同一来源体系

图片与代码仍属于具体 source revision，只在保存、阅读或检索投影上增加专门处理。

**图片。** 网页接受 PNG、JPEG 和 WebP，单张不超过 5 MB。服务端还会校验 base64、实际文件签名和大小，再按内容哈希保存 asset；revision 保存的是 asset 引用。参考 [图片校验与哈希存储 ↗](../../../apps/server/src/store.ts#L131 "说明图片格式、大小、文件签名和 asset 身份。") 图片描述属于后续派生信息，不能替代原图。

**代码。** TS、JS 和 Vue 等文件的原文仍按普通 source revision 保存。检索层根据文件身份解析 AST，按函数、方法、类或组件形成 passage，也保留 import 和顶层初始化等未被符号覆盖的内容。调用匹配只按候选名称定位，并非类型解析后的完整调用图。参考 [代码 AST passage ↗](../../../apps/server/src/retrieval/units.ts#L92 "说明代码按符号形成查找单元并保留顶层内容。") [调用仅为候选匹配 ↗](../../../apps/server/src/retrieval/code-navigation.ts#L6 "说明调用导航按名称匹配，不提供类型解析后的完整调用图。") Markdown 里的代码围栏只按 Markdown 块处理；要得到文件级 AST 导航，材料需要带有 .ts、.js 或 .vue 等文件身份。

**PDF/DOCX。** 这类文件多一个异步停靠站。上传先按原字节的 SHA256 保存附件并建立持久导入记录，然后排 document_parse；解析成功后才生成 Capture。文件上限是 20 MB，解析器最多处理 200 页，导出的正文上限为 20 万字符。参考 [文档原字节附件 ↗](../../../apps/server/src/imports/documents.ts#L10 "说明 PDF/DOCX 原字节按 SHA256 生成 asset 标识并写入附件存储。") [文档原件先存与持久任务 ↗](../../../apps/server/src/imports/service.ts#L98 "说明上传先保存原件和导入记录，再排文档解析任务。") [文档解析后的 Capture ↗](../../../apps/server/src/imports/documents.ts#L36 "说明文件限制、Markdown 字数限制、结构和图片 asset，以及成功后形成 Capture。")

当前解析关闭 OCR；扫描件没有可读正文时会报错。成功结果包含 Markdown 与顺序 blocks，还包含表格、图片以及页码和区域信息。图片及结构分别存成 asset。阅读页按具体 revision 请求结构和原件，并按 blocks 顺序渲染；服务端只允许读取该结构列出的图片 asset。参考 [Docling 输出与 OCR 条件 ↗](../../../scripts/document-parser/convert.py#L11 "说明 200 页限制、OCR 关闭、顺序块及页码区域输出。") [文档解析后的 Capture ↗](../../../apps/server/src/imports/documents.ts#L36 "说明文件限制、Markdown 字数限制、结构和图片 asset，以及成功后形成 Capture。") [按 revision 阅读文档结构 ↗](../../../apps/web/src/DocumentReading.vue#L24 "说明阅读页按固定 revision 获取结构、下载原件并渲染块与图片。") [文档图片访问白名单 ↗](../../../apps/server/src/app.ts#L854 "说明服务端只返回当前 revision 的结构附件所列出的图片 asset。")

页码和区域已经保存，但当前检索引用仍落在派生 Markdown 的固定行或章节，尚不能从引用直接框选 PDF 原页。参考 [文档引用的当前边界 ↗](../../../docs/reader-first/document-import.md#L42 "说明当前引用仍指向派生文字，页码和区域尚未接到原页框选交互。")

## 要修改哪一层

改动应落在它实际影响的那一层。

| 想改的行为 | 入口 |
| --- | --- |
| 网页字段、来源标识与提交方式 | apps/web/src/App.vue；统一输入约束在 packages/contracts/src/index.ts |
| 文件、Git、飞书的读取边界 | apps/server/src/connectors.ts；路由装配在 apps/server/src/app.ts |
| 版本、片段、head、记忆失效与作业入队 | apps/server/src/store.ts |
| 旧原件保留或回收 | apps/server/src/storage/retention.ts |
