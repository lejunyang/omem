# 一份材料的旅程：从导入到阅读与引用

用一份两节 Markdown 项目约定贯穿网页导入、稳定来源、固定版本、当前检索、后台记忆提炼、显式知识生成与历史引用，并说明图片和代码如何共享来源体系而采用不同投影。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先看结果：同一约定的两个版本

假设你在“输入材料”页保存标题为“项目约定”的 Markdown，并把来源标识填写为 project-rules：

~~~markdown
# 合并约定
合并前至少一人复核。

# 发布约定
先部署测试环境，再部署生产环境。
~~~

第二次仍使用 project-rules，把“一人”改成“两人”。稳定标识让两次输入归到同一个 **Source**；正文变化则保证完整指纹不同，从而产生下一版 **Revision**。两段正文会成为该快照内可检索、可引用的 **Fragment**。页面也提示相同来源标识用于产生新版本；留空时会自动分配标识。参考 [网页来源标识 ↗](../../../apps/web/src/App.vue#L881 "支持稳定来源标识、留空自动分配以及段落生成固定片段的页面提示。") [完整指纹与事件去重 ↗](../../../apps/server/src/store.ts#L136 "支持事件回执冲突规则、完整 fingerprint 字段以及仅在当前 head 指纹相同时复用 Revision。") [新版本与固定片段 ↗](../../../apps/server/src/store.ts#L197 "支持 Revision 递增、previous_id、片段生成、head 更新与有效性代次递增。")

这里有一个容易忽略的细节：网页每次手动提交都会生成新的事件标识和时间，而这些 provenance 字段也参与指纹。因此，即使正文一字未改，再点一次保存通常仍会产生新 Revision；不能把去重理解成“只比较正文”。参考 [网页提交来源信息 ↗](../../../apps/web/src/App.vue#L429 "证明网页每次提交都会生成新的 eventId 和 eventAt，并把 provenance 连同正文一起发送。") [完整指纹与事件去重 ↗](../../../apps/server/src/store.ts#L136 "支持事件回执冲突规则、完整 fingerprint 字段以及仅在当前 head 指纹相同时复用 Revision。")

Source 是长期身份，Revision 是某次保存后的固定快照，Fragment 是快照内的证据位置。原件、检索单元和面向读者的知识文章用途不同，不用同一种切分替代彼此。参考 [来源与阅读分层 ↗](../../../docs/reader-first/architecture.md#L5 "解释 Source 与 Revision 的统一来源体系，以及保存、检索和讲解单位分开的设计。")

<a id="entry"></a>
## 入口统一：页面与连接器都交付 CaptureInput

页面把文本、链接和图片组成 parts，连同来源类型、稳定标识、标题、时间、上下文与 provenance 交给服务端。合同允许文本、链接和图片；图片落库后由 assetId 代替 base64 数据。参考 [捕获输入合同 ↗](../../../packages/contracts/src/index.ts#L70 "定义 CaptureInput 的来源、标识、parts、时间和上下文字段，并展示图片落库后的 StoredPart。")

普通页面经 /api/captures 进入；文件、Git、飞书等连接器先把外部内容适配成相同的 CaptureInput，随后仍调用 Store.capture。参考 [统一服务端入口 ↗](../../../apps/server/src/app.ts#L236 "证明普通捕获和各连接器最终都校验 CaptureInput 并调用同一个 Store.capture。") 文件连接器只读配置根目录内、大小受限的 UTF-8 文本；Git 先把 ref 固定为 commit SHA，再读取该提交中的文件。参考 [文件与 Git 适配 ↗](../../../apps/server/src/connectors.ts#L19 "支持受控文件读取以及 Git ref 固定到 commit 后再读取内容。") 飞书连接器保存 Markdown、文档版本、原文链接与引用元信息，不继续爬取正文中的链接。参考 [飞书文档适配 ↗](../../../apps/server/src/connectors.ts#L76 "支持保存飞书 Markdown、版本、原文链接与引用元信息且不递归抓取链接。")

~~~mermaid
flowchart LR
  A[网页或连接器] --> B[CaptureInput]
  B --> C[Store.capture]
  C --> D[Source 当前 head]
  C --> E[固定 Revision]
  E --> F[Fragment]
~~~

连接器只负责受控读取和边界适配，身份、版本和证据保存仍是一条主链。参考 [统一服务端入口 ↗](../../../apps/server/src/app.ts#L236 "证明普通捕获和各连接器最终都校验 CaptureInput 并调用同一个 Store.capture。")

<a id="versioning"></a>
## 保存事务：事件回执、完整指纹与换版

Store.capture 先处理事件回执：同一 collectorId 与 eventId 若已接收且 payload 完全相同，直接返回原 Revision；事件标识相同但 payload 不同则拒绝。没有可复用回执时，它按 (source, externalId) 找 Source，只有当前 head 的**完整指纹**相同才去重。该指纹包含标题、落库后的 parts、context、provenance、observedAt 与 upstreamVersion。参考 [完整指纹与事件去重 ↗](../../../apps/server/src/store.ts#L136 "支持事件回执冲突规则、完整 fingerprint 字段以及仅在当前 head 指纹相同时复用 Revision。")

若不能去重，就插入新 Revision：version 递增、previous_id 指向旧 head，文本按空行切片，链接与图片也形成固定 Fragment；随后才更新 Source head 和有效性代次。旧 Revision 与旧 Fragment不会被覆盖。参考 [新版本与固定片段 ↗](../../../apps/server/src/store.ts#L197 "支持 Revision 递增、previous_id、片段生成、head 更新与有效性代次递增。") 示例中的 v2 由正文改动保证产生，而不是仅凭“再次使用同一标识”。

Source 列表面向当前 head；开发者可用 /api/sources/:id/history 枚举历史，再用 /api/revisions/:id 读取指定版本。参考 [版本读取接口 ↗](../../../apps/server/src/app.ts#L284 "支持从 Source history 枚举历史并按 Revision ID 读取指定版本。")

<a id="after-save"></a>
## 保存之后：立即完成、检索追赶与可选学习

保存返回前，事务已完成 Revision、Fragment、head、变更通知、回执和持久任务入队。若来源换版，依赖旧版的记忆会立即标为失效，并排入重新核验；这是数据库状态变化，不代表新结论已经提炼完。参考 [换版后的即时处理 ↗](../../../apps/server/src/store.ts#L246 "证明来源更新会立即失效旧记忆依赖、记录刷新、排队重核并完成捕获记录。")

检索与 Agent 是两条支线。检索投影只读取各 Source 的当前 head，并按 Revision 身份替换该来源的检索单元；旧版仍可按历史读取，但不混入当前来源搜索。参考 [当前版本检索投影 ↗](../../../apps/server/src/retrieval/units.ts#L443 "支持检索投影只选择 Source head，并按 Revision 身份替换当前来源的检索单元。") 搜索会先同步投影，词法分支不依赖 Agent；有向量模型时再融合语义结果，向量异常会退回词法结果。参考 [词法与语义检索 ↗](../../../apps/server/src/retrieval/unified.ts#L323 "证明搜索先同步投影，缺少向量模型或向量异常时仍可返回词法结果。")

每个非派生捕获都会排入 extract_claims，但 learning 默认关闭。参考 [学习功能默认关闭 ↗](../../../apps/server/src/config.ts#L58 "支持 learning 默认关闭及其 profile 与轮询配置。") [学习任务入队边界 ↗](../../../apps/server/src/store.ts#L348 "证明非派生捕获会排入提取任务，而派生材料被排除以避免自循环。") 只有启用并找到指定 Agent profile 时，服务端才装配学习管线。参考 [学习管线装配 ↗](../../../apps/server/src/app.ts#L120 "支持只有启用 learning 且找到指定 profile 时才创建学习管线。") 启用后，提取器只处理仍为当前 head 的固定输入，有候选才交给核验；核验结果再整批交给 MemoryService，可能自动应用、等待判断或拒绝，模型不直接写成事实。参考 [记忆提取流程 ↗](../../../apps/server/src/learning/pipeline.ts#L550 "说明提取器读取固定输入、保存观察，并仅在有候选时排入独立核验。") [记忆核验与应用 ↗](../../../apps/server/src/learning/pipeline.ts#L672 "支持核验输出整批交给 MemoryService，并区分自动应用、等待判断与拒绝。")

<a id="derived-layers"></a>
## 原始材料、记忆与知识不是一回事

贯穿示例可以分成三层：

| 层次 | 示例结果 | 产生时机 |
| --- | --- | --- |
| 原始材料 | v1、v2 的逐字 Markdown | 保存事务内 |
| 记忆 | “合并前至少两人复核” | 可选学习 Agent 提取、核验后 |
| 知识 | 面向读者解释规则背景与执行方式的文章 | 显式选择材料并发起整理后 |

派生模型材料不会再次进入提取队列，避免摘要自我循环成独立证据。参考 [学习任务入队边界 ↗](../../../apps/server/src/store.ts#L348 "证明非派生捕获会排入提取任务，而派生材料被排除以避免自循环。") 知识页面也不会随 capture 自动出现：/pages 要求配置 Agent、选择仍可用的固定 Revision并填写阅读目标，然后异步调用 writePage。参考 [显式页面整理入口 ↗](../../../apps/server/src/knowledge/api.ts#L147 "支持知识页面必须配置 Agent、选择固定 Revision、填写阅读目标后才异步生成。")

页面生成会先调查材料，再由知识写作者成文并接受独立复核；发布前还会校验材料与文章依赖摘要没有变化。输入已变化时，基于旧输入的产物不能成为当前文章。参考 [读者页面生成流程 ↗](../../../apps/server/src/knowledge/pipeline.ts#L214 "支持原生页面先调查，再写作、复核并形成发布候选。") [发布依赖校验 ↗](../../../apps/server/src/knowledge/repository.ts#L122 "证明发布前核对固定材料与文章依赖摘要，并在写入时记录当前知识版本。")

<a id="historical-citations"></a>
## 为什么 v2 出现后仍能打开 v1 引用

知识引用不仅保存 material key 和行范围；文章依赖还封存生成时的材料摘要。打开引用时，API 先找到对应依赖，再按该摘要解析材料，并报告它是当前版还是历史版。参考 [引用固定依赖解析 ↗](../../../apps/server/src/knowledge/api.ts#L28 "支持引用先匹配文章依赖，再按固定摘要解析材料并返回 current 状态。")

若当前材料摘要不同，仓储会沿同一 Source 的 Revision 历史寻找匹配摘要。因此旧文章里“一人复核”的引用仍打开 v1，而不会静默跳到 v2 的“两人复核”。参考 [历史材料回溯 ↗](../../../apps/server/src/knowledge/repository.ts#L193 "证明当前摘要不匹配时会沿同一 Source 的历史 Revision 寻找固定材料。") 普通 Fragment 证据也由 fragmentId 反查所属 Revision，再读取那一版内容，与 Source 当前 head 无关。参考 [固定片段证据读取 ↗](../../../apps/server/src/store.ts#L422 "支持 fragmentId 先定位所属 Revision，再返回该版本而非跟随 Source head。")

<a id="specialized"></a>
## 同一来源体系上的图片与代码专门处理

图片仍是 Revision 的 part。保存时会校验 base64、5 MB 上限以及 PNG、JPEG、WebP 的实际文件头，再按内容哈希复用资产；Revision 只保留资产标识、类型和标签。参考 [图片资产保存 ↗](../../../apps/server/src/store.ts#L102 "支持图片完整性、大小、文件类型校验以及按内容哈希保存资产。") 学习管线会按 assetId 读取真实字节，把图片随固定 Revision 交给提取与核验角色。参考 [图片进入学习上下文 ↗](../../../apps/server/src/learning/pipeline.ts#L330 "证明学习管线按 assetId 读取图片字节并随固定 Revision 交给角色。")

普通检索的图片行为更窄：**纯图片材料**没有文本时，才用图片 label 建 passage；混合图文材料走文本 passages，不会把图片 label 额外并入普通文本索引。参考 [纯图片检索投影 ↗](../../../apps/server/src/retrieval/units.ts#L243 "证明只有无文本且含图片的材料才用图片标签建 passage，混合图文优先走文本 passages。") 当前也没有通用 OCR、版面定位和视觉索引闭环。参考 [图片处理边界 ↗](../../../docs/reader-first/current-system.md#L13 "说明当前尚无通用 OCR、布局定位与视觉索引闭环。")

知识侧有两条不同入口。/pages 生成读者页面：原生研究模式先运行 knowledge-researcher，再由 knowledge-writer 写作和 verifier 复核；需要看图时，研究工作区提供受范围约束的 read_image 工具。参考 [原生读者页面角色 ↗](../../../apps/server/src/knowledge/pipeline.ts#L214 "证明 /pages 的原生模式依次使用知识调查、知识写作和独立复核，而非 visual-analyst。") [原生图片读取工具 ↗](../../../apps/server/src/knowledge/agent-research.ts#L744 "支持原生研究工作区按选定范围提供 read_image，并返回实际图片字节。") 非原生模式则把所选图片字节直接放入角色上下文。参考 [非原生图片上下文 ↗](../../../apps/server/src/knowledge/pipeline.ts#L31 "证明非原生知识上下文会直接读取所选图片资产并内联字节。") /analyze 是材料说明流程，它才会对含图材料选择 visual-analyst；不能把这个角色选择套到 /pages 上。参考 [材料分析入口 ↗](../../../apps/server/src/knowledge/api.ts#L147 "区分 /analyze 材料说明入口与 /pages 读者页面入口。") [视觉分析角色选择 ↗](../../../apps/server/src/knowledge/pipeline.ts#L182 "证明 analystFor 仅在 analyze 流程选取材料分析角色，含图材料由此选择 visual-analyst。")

代码也不建立第二份权威正文。仓库适配器按代码边界组织 parts，保留文件与提交上下文，最终仍进入 Store.capture；检索和代码理解再用 TypeScript/Vue 单文件 AST 投影完整函数、组件、import 与候选调用。参考 [代码捕获适配 ↗](../../../apps/server/src/review/sync.ts#L471 "支持仓库适配器按代码边界组织 parts、保留文件与提交上下文并调用统一捕获。") [代码检索单元 ↗](../../../apps/server/src/retrieval/units.ts#L68 "支持把完整函数、方法和组件等结构投影为可搜索 Passage。") [代码结构解析 ↗](../../../apps/server/src/code/parse.ts#L236 "支持 Vue 与 TypeScript/JavaScript 的符号、import、候选调用、路由和测试解析。") 这些侧表依附固定 Revision/Fragment，不复制另一份文件正文；当前调用关系仍是单文件名称级候选，不是完整跨文件调用图。参考 [代码投影不复制正文 ↗](../../../apps/server/src/code/store.ts#L1 "证明代码侧表是固定片段上的确定性投影，不保存另一份文件正文。") [单文件解析边界 ↗](../../../apps/server/src/code/parse.ts#L1 "明确解析器没有跨文件类型解析，调用仅为名称级候选。")

修改入口依次是：输入合同 packages/contracts/src/index.ts，连接器 connectors.ts，版本事务 store.ts，检索 units.ts 与 unified.ts，记忆提炼 learning/pipeline.ts，知识入口与历史引用 knowledge/api.ts、pipeline.ts、repository.ts，代码投影 review/sync.ts、code/parse.ts 与 code/store.ts。
