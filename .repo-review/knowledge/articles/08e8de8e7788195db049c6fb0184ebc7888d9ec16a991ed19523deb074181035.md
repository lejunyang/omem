# 一份材料如何变成可检索、可追溯的知识

沿一份两节 Markdown 项目约定的两次导入，解释网页与连接器如何形成统一 Capture，Source、Revision、Fragment、检索投影、Memory 与 Knowledge 如何分工；重点区分同步保存、可重建索引、受控的 Source 归属调查、后台记忆和显式知识生成，并说明人工纠正、动态文章范围、固定历史引用、图片与代码处理边界及相应代码入口。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="example"></a>
## 先走一遍：同一份约定的两个版本

先给结论：一次导入先固定“当时收到的原件”，再从这个不可变版本建立可重建的检索、可选的记忆和知识文章。**原件、索引、归属、记忆和讲解不是同一份数据，也不会在保存按钮按下时同时完成。**

下面的 Markdown 是教学示例，不是仓库中的真实材料。假设你在“输入材料”里填写标题“项目约定”、来源类型 `manual`、来源标识 `project-rules`：

```markdown
# 提交
合并前运行检查。

# 发布
发布由值班同学执行。
```

页面把非空正文、可选 HTTP(S) 链接和图片组成 `parts`，也可以同时选择已有项目或主题；普通网页提交会生成新的 `eventId` 与 `eventAt`，保存后打开服务端返回的 Revision。参考 [网页捕获请求 ↗](../../../apps/web/src/App.vue#L423 "支持网页组装 parts、附加 contextIds、生成新的 eventId 与 eventAt 并打开返回 Revision。")

第二次仍使用 `manual + project-rules`，但把“提交”改成“合并前运行完整检查并记录结果”。相同来源类型与来源标识让系统找到同一个 Source；标识留空时页面随机分配，不会自然接到旧版本链。参考 [来源标识与输入表单 ↗](../../../apps/web/src/App.vue#L909 "支持来源标识复用或留空分配、正文、链接与图片输入的界面语义。")

| 对象 | 示例中的含义 | 作用 |
| --- | --- | --- |
| Source | `manual + project-rules` | 稳定来源身份；项目/主题归属绑定在这里 |
| Revision | V1、V2 | 不可变原件快照；V2 指向 V1 |
| Fragment | 按空行、链接或图片固定的片段 | 捕获时的证据锚点，不是文章目录 |
| 检索投影 | Markdown passage、代码符号、向量 | 可重建的查找入口，不改写原件 |
| Source 归属 | manual / automatic / ambiguous / unrelated | 描述这份来源属于哪些已有项目或主题 |
| Memory | 从原始输入提炼并复核的持续状态 | 可选后台分支 |
| Knowledge | 围绕读者目标写成的本文 | 派生讲解，不能替代原件 |

这里要区分代码事实与推导。代码事实是：fingerprint 包含标题、parts、context、provenance、观察时间和上游版本；网页普通提交每次换新的事件 ID 和时间。由此可以推导，即使正文未改，两次独立网页提交通常也会形成两个 Revision；同一采集事件重放，或完整 fingerprint 相同，才会复用已有版本。Source 复用与 Revision 去重因此是两件事。参考 [网页捕获请求 ↗](../../../apps/web/src/App.vue#L423 "支持网页组装 parts、附加 contextIds、生成新的 eventId 与 eventAt 并打开返回 Revision。") [资产、幂等、身份与片段 ↗](../../../apps/server/src/store.ts#L108 "支持图片事务前校验和内容寻址、receipt 幂等、Source 定位、人工归属写入、fingerprint、新 Revision 与 Fragment 生成。")

<a id="entry"></a>
## 网页和连接器最终交出同一种原件输入

手工页面只是 Capture 的一个生产者。统一合同要求 `source`、`externalId`、标题和 1–50 个 parts；part 只能是非空文本、HTTP(S) 链接或 PNG/JPEG/WebP 图片。顶层及逐 part provenance 可以保留采集者、参与者、事件、时间、回复关系、引用/转发及 original/derived 等信息。参考 [统一 Capture 合同 ↗](../../../packages/contracts/src/index.ts#L5 "支持文本、链接、图片、顶层及逐 part provenance 与 CaptureInput 的字段边界。")

文件、Git、飞书连接器负责**适配格式并划定读取边界**，最后仍返回 `CaptureInput`：

- 文件连接器只读取 `captureRoots` 内的真实路径，限制 500 KB，要求 UTF-8 且拒绝含 NUL 的二进制内容。
- Git 连接器校验 ref 与路径，先把 ref 固定为 commit SHA，再读取该提交中的文件，并把 SHA 写入 `upstreamVersion`。
- 飞书连接器只接受指定 HTTPS docx/wiki 地址，经外部 CLI 拉取 Markdown，以文档 ID 作为稳定标识、revision ID 作为上游版本，并保留原链接和引用 sidecar。
- 捕获正文中的 URL 只作为内容保存，不会被连接器自动爬取。参考 [有边界的连接器 ↗](../../../apps/server/src/connectors.ts#L1 "支持文件、Git、飞书的读取边界、稳定身份和上游版本，并说明正文 URL 不自动爬取。")

项目/主题不在 `CaptureInput` 正文里，而是 HTTP 入口随 Capture 传给 Store 的附加 `contextIds`；网页、文件、Git 和飞书都走同一个保存入口。参考 [Capture 路由与归属接口 ↗](../../../apps/server/src/app.ts#L240 "支持 Source 归属读写接口，以及网页和三个连接器把 contextIds 作为 Capture 之外的选择传给 Store。") 归属本身是 Source 级关系，独立于 Revision 正文、文章分类和 citation。人工保存会替换整个 membership 集合，并记录为 `manual`；显式空集合也是人工决定。未指定时，Source 可以先没有归属，之后再由受控后台调查提出 `automatic`、`ambiguous` 或 `unrelated` 状态，模型判断不能覆盖人工选择。参考 [Source 归属与判断状态 ↗](../../../apps/server/src/contexts/repository.ts#L5 "支持人工归属优先、替换 membership、保存自动或含糊判断、双判断一致条件及按 Revision 决定是否调查。") [归属提案合同 ↗](../../../packages/contracts/src/contexts.ts#L12 "支持 matched、ambiguous、unrelated 提案以及 manual、automatic、ambiguous、unrelated 持久状态。")

```mermaid
flowchart LR
  A[网页或连接器] --> B[CaptureInput]
  X[可选 contextIds] --> C[Source 归属]
  B --> D[Source]
  D --> E[不可变 Revision]
  E --> F[固定 Fragment]
  E --> G[可重建检索投影]
  E --> H[可选后台学习]
  H -.必要时先调查归属.-> C
  E -.固定材料或动态范围.-> I[知识文章任务]
```

因此入口可以不同，落库后的身份、版本与证据语义相同；差别保留在 `source`、上游版本、上下文、provenance 和独立的 Source 归属中。

<a id="commit"></a>
## 一次 Capture 真正提交了什么

`Store.capture` 先校验传入的 context IDs 并计算原始输入 payload digest。图片在数据库事务前从 base64 解码，限制真实字节不超过 5 MB，以 magic bytes 校验声明的 PNG/JPEG/WebP 类型，再按内容哈希写入私有资产文件；Revision body 只保存资产引用和元数据。随后标题、parts、context、provenance、观察时间与上游版本共同进入 fingerprint。参考 [资产、幂等、身份与片段 ↗](../../../apps/server/src/store.ts#L108 "支持图片事务前校验和内容寻址、receipt 幂等、Source 定位、人工归属写入、fingerprint、新 Revision 与 Fragment 生成。")

事务内的主顺序是：

1. 若存在 `collectorId + eventId`，先查采集收据；同事件同 payload 返回原 Revision，同事件不同 payload 报冲突。复用 Revision 时若明确传了 `contextIds`，仍可更新 Source 归属并确保学习任务存在。
2. 按 `source + externalId` 查找或创建 Source。
3. 若明确传入 `contextIds`，将其保存为人工归属；没有传入则不在 Capture 内猜测。
4. 当前 head 的 fingerprint 完全相同时复用 head；否则插入 `version + 1` 的 Revision，并记录 `previous_id`。
5. 文本按空行、链接按“标签＋URL”、图片按“[图片] 标签”生成最多 2000 个固定 Fragment。参考 [资产、幂等、身份与片段 ↗](../../../apps/server/src/store.ts#L108 "支持图片事务前校验和内容寻址、receipt 幂等、Source 定位、人工归属写入、fingerprint、新 Revision 与 Fragment 生成。")

新 Revision 建好后，系统尽力写入确定性导航画像；失败只记录画像失败，不阻止来源保存。随后切换 Source head 与 validity epoch。若这是换版，还会把旧记忆依赖标为 stale、相关记忆标为 invalidated，登记刷新并排入 `refresh_dependents`；最后记录变化、写收据，并为非 derived 输入排 `extract_claims`。参考 [换版后的确定性工作 ↗](../../../apps/server/src/store.ts#L234 "支持导航画像、切换 head、失效旧记忆、登记刷新、记录变化与后续任务。") [学习任务入队 ↗](../../../apps/server/src/store.ts#L394 "支持非 derived Capture 排入 extract_claims，并说明入队不等于后台已经消费。")

因此“保存成功”的准确边界是：原件版本、固定片段、Source head、明确提供的人工归属、变化记录和持久任务已经落下。它**不表示** embedding 已补齐、自动归属已经完成、模型已提炼记忆，或知识文章已经写完。Source membership 适用于同一来源的各版本，但它仍是可调整的元数据；测试确认换版会保留 membership，之后清空归属不会改写旧 Revision，无效 context 也不会留下半份原件。参考 [归属跨版本与原件不变测试 ↗](../../../apps/server/tests/material-contexts.test.ts#L13 "验证换版保留 Source 归属、人工清空不改写旧 Revision，并在无效 context 时不保存半份原件。")

<a id="retrieval"></a>
## 为什么保存后马上能搜，但索引又不等于原件

Revision 与 Fragment 落库后即可直接读取；搜索调用会同步可重建投影。显式代码导航意图优先返回符号或调用方候选；自然语言中识别到“谁调用某符号”时，只有确实找到候选才走捷径，否则仍回到普通召回。参考 [代码导航候选 ↗](../../../apps/server/src/retrieval/unified.ts#L345 "支持显式代码意图优先，以及自然语言调用方捷径无候选时回到普通召回。")

普通非空查询组合词法、符号和可用的语义候选。**空查询得到空结果**；精确定位、向量模型尚未加载，或向量计算失败时，使用词法与符号结果。参考 [搜索同步、空查询与回退 ↗](../../../apps/server/src/retrieval/unified.ts#L427 "支持搜索前同步投影、空查询为空，以及精确定位、无模型或向量失败时的词法和符号回退。") 检索服务创建后立即启动后台循环：首轮 tick 延迟 100 ms，随后同步投影并分批补建 embedding，正常约 1 秒继续，出错后约 30 秒重试。这个 100 ms 是调度安排，不是 HTTP listener 的就绪承诺。参考 [后台补建向量 ↗](../../../apps/server/src/retrieval/unified.ts#L84 "支持首轮延迟 100 ms 的后台循环、同步投影、分批索引与错误退避。") [检索服务创建时启动 ↗](../../../apps/server/src/retrieval/factory.ts#L14 "支持 createRetrieval 构建 UnifiedRetrieval 后立即调用 start。")

对示例 Markdown，passage 按 Markdown token 与标题路径建立并保留真实行号；以冒号结尾的引导段会尽量与紧随的表格、列表或代码块一起返回。它不会改写 Revision，也不会把捕获时按空行形成的 Fragment 当成阅读章节。参考 [Markdown passage ↗](../../../apps/server/src/retrieval/units.ts#L33 "支持按标题和语法块投影、保留行号，并合并引导段与结构块。")

代码也先作为文本进入同一 Source/Revision，只在投影层特殊处理：完整函数和方法保留控制流，函数内局部 `const` 不抢占为独立 passage；imports 与顶层初始化仍可搜索。参考 [代码 passage ↗](../../../apps/server/src/retrieval/units.ts#L92 "支持按完整操作切分代码、保留父级路径、注释、imports 与顶层初始化。") 底层解析是离线、单文件的 TypeScript AST 与 Vue SFC；calls 只是名称级候选，没有 Program 或跨文件 TypeChecker，因此适合导航调查，不能当成完整调用图。参考 [单文件 AST 边界 ↗](../../../apps/server/src/code/parse.ts#L1 "支持 TypeScript 单文件 AST、Vue SFC 与名称级调用候选的能力边界。")

<a id="branches"></a>
## 保存后的三条分支：立即、后台与显式整理

**第一条是立即可用的原件与检索。** Source、Revision、Fragment 与版本历史已经确定；词法/结构投影可以重建，embedding 再由后台补齐。Source 此时可能仍没有项目/主题归属。

**第二条是可选的后台记忆。** 配置默认 `learning.enabled=false`；只有启用并找到指定 profile，应用才创建 LearningPipeline。参考 [学习默认配置 ↗](../../../apps/server/src/config.ts#L63 "支持 learning 默认关闭及 profile 与轮询配置。") [学习管线启动条件 ↗](../../../apps/server/src/app.ts#L122 "支持仅在启用并找到指定 profile 时创建 LearningPipeline。") 非 derived Capture 即使在 learning 关闭时仍会排 `extract_claims`，只是没有 worker 消费。参考 [学习任务入队 ↗](../../../apps/server/src/store.ts#L394 "支持非 derived Capture 排入 extract_claims，并说明入队不等于后台已经消费。")

启用后台学习后，当前原生研究流程会在事实提取前处理必要的未归属 Source，但它有明确护栏：

1. 只有原生研究、库中已有项目/主题、Source 没有人工归属且当前 Revision 尚未调查时才运行；人工选择（包括空集合）优先。
2. 第一次判断若为 matched，会开启第二个独立 session；两次都 matched 且 context ID 集合完全一致，才写入 `automatic` membership。
3. 第一次判断为 unrelated 时记录“没有合适的已有项目或主题”，随后继续按无项目范围提取。
4. 判断为 ambiguous，或两次 matched 不一致时，记录候选与具体问题，并在事实提取前暂停；人工选择后会重新排队。参考 [事实提取前的归属调查 ↗](../../../apps/server/src/learning/pipeline.ts#L612 "支持 extract 先调用 resolveContexts，以及原生研究条件、双独立 session、歧义暂停和 unrelated 继续。") [归属结果落库条件 ↗](../../../apps/server/src/contexts/repository.ts#L70 "支持旧输入防护、两次 matched ID 集合一致才 automatic、候选汇总和人工决定不可覆盖。")

合成测试验证了双 session 自动归属、歧义不先新增记忆、人工选择后继续，以及人工空集合优先；这证明流程接通，不等于复杂真实材料上的模型质量已经成熟。参考 [自动与含糊归属测试 ↗](../../../apps/server/tests/learning-projects.test.ts#L47 "验证两个独立 session、automatic membership、含糊输入不新增记忆、人工选择后恢复及人工空集合优先。") 项目文档也明确把真实模糊归属效果列为仍待验证。参考 [真实归属效果边界 ↗](../../../docs/reader-first/project-contexts.md#L53 "说明未指定归属流程已接入，但真实模型效果仍待验证，并给出人工优先与不创建新项目等边界。")

归属与“可信记忆 scope”还不是一回事。一份 Source 可以属于多个 project/topic，但事实提取只有在所有输入 Source **共同且恰好有一个**显式 project 时，才把该 project 作为可信 scope；topic、名字、路径、会话载体、没有共同项目或有多个共同项目都不能代替。抽取前后还会比较 membership stamp，异步运行期间归属变化就拒绝旧结果；更新已有记忆也不能把它搬到另一个项目。参考 [唯一共同项目 scope ↗](../../../apps/server/src/learning/pipeline.ts#L296 "支持只有所有输入 Source 唯一共同显式 project 才成为可信 scope，topic、名称、路径和会话载体不能代替。") [归属戳与跨项目更新防护 ↗](../../../apps/server/src/learning/pipeline.ts#L452 "支持异步运行前后比较 membership、拒绝变更后的旧结果，并禁止更新时搬动已有记忆的项目 scope。")

人工纠正 membership 时，Store 会让依赖该 Source、但旧 project scope 已不成立的 active memory 失效并把依赖标 stale，历史仍保留；随后为非 derived 原件排 `context_correction` 的重新提炼。它不会静默搬动既有记忆或个人事项。参考 [人工纠正归属 ↗](../../../apps/server/src/store.ts#L309 "支持失效错范围 active memory、保留历史、标记依赖 stale，并按新归属排 context_correction 提炼任务。")

**第三条是显式排队的知识文章。** 整理窗口可以同时选择固定 Revision 与持续跟踪的项目/主题：动态范围中的当前成员自动包含，仍可另选固定背景材料。参考 [固定材料与动态范围界面 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L163 "支持文章同时选择持续跟踪的项目或主题和固定背景材料，并说明以后加入的成员可触发维护。") 服务端验证至少存在固定材料或动态范围、确认固定 Revision 仍为当前版本，保存 `materialKeys + contextIds` 计划并返回 202 queued。参考 [页面计划校验与排队 ↗](../../../apps/server/src/knowledge/api.ts#L207 "支持服务端验证固定 Revision 或 context 范围、保存 materialKeys 计划并以 202 queued 返回。")

两种选材语义不同：

- `materialKeys` 是固定集合；未选的新材料不会自行加入。
- `contextIds` 是动态范围。repository 每次把固定 keys 与这些 context 当前 Source 成员取并集；自动或人工归属变化都可能改变范围，但相似文本不会自动加入。参考 [计划材料并集 ↗](../../../apps/server/src/knowledge/repository.ts#L125 "支持每次把显式 materialKeys 与 contextIds 当前 Source 成员取并集。")
- 开启自动维护后，worker 把计划、实际成员和 digest 计算为 scope digest；换版、加入或移出范围都会排最新维护请求。参考 [范围摘要与自动维护 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "支持 scope digest 包含实际成员和 digest，并在动态范围变化后排最新维护请求。")

文章仍由 page worker 触发自主调查、写作、最多四轮独立复核和发布；归属 resolver 不直接改正文。accepted 文档固定实际依赖，动态范围还保存当次 selection 快照。参考 [写作、独立复核与选材快照 ↗](../../../apps/server/src/knowledge/pipeline.ts#L165 "支持最多四轮写作或维护、独立 verifier、固定实际依赖并为动态范围保存 selection 快照。") 发布前 repository 再检查阅读计划、动态成员集合与依赖 digest，防止旧调查覆盖新范围。参考 [发布竞态检查 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "支持发布前核对阅读计划、动态成员快照和依赖 digest，再保存新的知识 Revision。")

三条分支回答不同问题：原件说明“当时收到了什么”，记忆支持持续助理状态，知识文章围绕特定读者目标组织解释。

<a id="citations"></a>
## 材料更新或改归属后，旧引用为什么仍能打开

知识文章的 citation 与 dependency digest 一起固定。读者点击引用时会携带文章身份、文章 revision 和 citation key；API 从指定知识 Revision 找 citation，再按固定 dependency digest 解析材料。参考 [固定引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L66 "支持从指定文章 Revision 查 citation，并按固定 dependency digest 解析材料或文章。") 当前材料 digest 不匹配时，repository 会沿同一 Source 的历史 Revisions 找到对应版本，并返回 `current:false`。参考 [历史材料回溯 ↗](../../../apps/server/src/knowledge/repository.ts#L297 "支持当前 digest 不匹配时沿同一 Source 的历史 Revisions 查找固定材料。")

因此示例中 V2 改写“提交”规则后，写作时引用 V1 的旧句仍能打开；系统不会拿 V2 的新句冒充旧论断的依据。但“旧引用还能打开”和“这一节仍然适用”是两项独立判断。

适用性比较先检查 `actorId`、`actorVerifiedBy`、`quoted`、`forwarded`、`eventAt`；任一项变化都会进入 needs-review。只有元数据门槛通过后，系统才可能比较原引用周围唯一同名的 Markdown 章节或代码结构。存在图片、引用没有行范围、结构缺失或同名歧义时也不会沿用。这个过程只判断旧解释是否仍适用，**不会重映射或替换 citation**。参考 [结构未变与 Markdown 根范围 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持 provenance 门槛、图片与行范围限制、唯一结构比较，以及单一 H1 只比较实际相交连续章节的规则。")

这对教学示例有一个关键限定：网页 manual 的两次普通提交会产生不同 `eventAt`，所以元数据检查先失败。即使 V2 只改“提交”，依赖该材料的“提交”和“发布”知识章节都会 needs-review，而不是把“发布”继续标为 current。系统逐节合并 citation 与 `reviewSources` 的状态；文章 head 的 current 是所有章节状态的汇总，界面仍保留旧解释与写作时原文。参考 [网页捕获请求 ↗](../../../apps/web/src/App.vue#L423 "支持网页组装 parts、附加 contextIds、生成新的 eventId 与 eventAt 并打开返回 Revision。") [章节级知识状态 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L116 "支持逐节检查 citation 与 reviewSources，并区分 current、needs-review 与 unavailable。")

章节级保留要看另一个满足前提的场景，例如 file/Git 换版前后上述 provenance 字段不变。若引用位于唯一同名结构中，相关结构原文完全未变，其他章节变化可以不影响它。单一 H1 的引用横跨导读和若干直接子章时，只比较实际相交的连续部分；每个相交子章仍包含其嵌套条件。范围外后续章节变化可以不影响，范围内新增、重排、改文或定位不唯一仍需复核。参考 [结构未变与 Markdown 根范围 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持 provenance 门槛、图片与行范围限制、唯一结构比较，以及单一 H1 只比较实际相交连续章节的规则。")

Source membership 是可变的范围元数据，citation dependency 则固定到写作时原件。人工纠正归属会让错范围的 active memory 失效并触发重新提炼，也会改变跟踪该 context 的文章范围，但不会改写旧 Revision 或旧 citation；原文界面也明确说明归属适用于所有版本、调整不会删除原文或历史引用、手动保存优先。参考 [人工纠正归属 ↗](../../../apps/server/src/store.ts#L309 "支持失效错范围 active memory、保留历史、标记依赖 stale，并按新归属排 context_correction 提炼任务。") [原文归属与人工覆盖界面 ↗](../../../apps/web/src/SourceContexts.vue#L10 "支持查看 AI 判断、候选和问题，并说明归属跨版本、调整不删除原文或历史引用、人工空集合也优先。")

<a id="media-code"></a>
## 图片、代码与修改入口

图片仍属于同一 Revision，但字节按内容哈希写入私有资产目录，Revision 保存引用。KnowledgeMaterial 从该 Revision 分离 text 与 images；材料 digest 包含文本、图片身份以及部分顶层 provenance，`eventAt` 则由生命周期适用性检查另行处理。参考 [资产、幂等、身份与片段 ↗](../../../apps/server/src/store.ts#L108 "支持图片事务前校验和内容寻址、receipt 幂等、Source 定位、人工归属写入、fingerprint、新 Revision 与 Fragment 生成。") [知识材料中的图片与 digest ↗](../../../apps/server/src/knowledge/repository.ts#L13 "支持从同一 Revision 分离文本和图片，并说明材料 digest 与 eventAt 的不同职责。") 图片可以进入原生视觉调查，但当前没有通用 OCR、布局定位和视觉索引闭环；标签可搜索、模型按需看图，不等于所有图片都已结构化理解。参考 [图片理解边界 ↗](../../../docs/reader-first/current-system.md#L13 "支持当前没有通用 OCR、布局定位和视觉索引闭环这一产品边界。")

代码同样先作为普通文本进入 Source/Revision，只在检索与调查层用单文件 AST/Vue SFC 建立符号、imports、route/test 与名称级调用候选。它帮助定位阅读入口，不证明跨文件语义或完整影响范围。参考 [代码 passage ↗](../../../apps/server/src/retrieval/units.ts#L92 "支持按完整操作切分代码、保留父级路径、注释、imports 与顶层初始化。") [单文件 AST 边界 ↗](../../../apps/server/src/code/parse.ts#L1 "支持 TypeScript 单文件 AST、Vue SFC 与名称级调用候选的能力边界。")

要修改这条链，可以沿数据流找入口：

- **输入与合同**：`apps/web/src/App.vue::capture/upload`、`packages/contracts/src/index.ts::captureSchema`、`apps/server/src/app.ts` 的 capture routes。
- **Source 归属**：`contexts/repository.ts::setForSource/saveResolution`、`learning/pipeline.ts::resolveContexts`、`store.ts::setSourceContexts`、`SourceContexts.vue`。
- **连接器与固定原件**：`connectors.ts::fileInput/gitInput/larkInput`、`store.ts::capture/queueCaptureJob/revision`。
- **检索投影**：`retrieval/units.ts::markdownPassages/codePassages`、`retrieval/unified.ts::search/start`、`retrieval/factory.ts::createRetrieval`、`code/parse.ts::parseFile`。
- **后台记忆**：`config.ts` 与 `app.ts` 决定启用条件；`learning/pipeline.ts::resolveContexts/context/runRole/extract/verify` 负责归属、scope、候选和复核。
- **知识文章**：`ArticleComposer.vue`、`knowledge/api.ts`、`repository.ts::materialsForPlan/publish`、`page-worker.ts`、`pipeline.ts::writePlannedPage/writeAndVerify`。
- **固定引用与适用性**：`knowledge/api.ts::resolveCitation`、`repository.ts::resolveMaterial`、`lifecycle.ts::unchangedContext/knowledgeStatus`。

当前未知也要放在正确位置：工程与合成测试说明自动归属流程已接通，但复杂同名项目、简短含糊消息和大材料库中的真实模型效果仍在验证；这不影响原件保存与历史引用，却会影响是否应直接信任 automatic membership。参考 [真实归属效果边界 ↗](../../../docs/reader-first/project-contexts.md#L53 "说明未指定归属流程已接入，但真实模型效果仍待验证，并给出人工优先与不创建新项目等边界。")

导航画像、passage、embedding 和归属提案都可重建或纠正；需要长期保真的事实边界仍是 Source、不可变 Revision 及其固定证据。
