# Web 应用的启动与样式入口

该入口文件负责创建 Vue 应用、装载根组件，并在首屏渲染前引入共享设计令牌与应用级样式。它刻意保持轻量，把导航、状态和业务界面交给根组件及其下游模块。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决什么问题

这个文件是浏览器端应用的**启动入口**：它把根组件 `App` 交给 Vue 创建应用实例，再挂载到页面中的 `#app` 容器。实际使用时，浏览器加载该模块后，工作区界面才会进入 Vue 的渲染与响应式生命周期。参考 [Vue 应用挂载 ↗](../../../apps/web/src/main.ts#L1 "支持入口创建 Vue 应用并挂载到页面容器的核心作用。")

入口本身不承担导航或数据处理，只负责把应用“接上线”，因此启动职责清晰，也便于将复杂界面留在根组件中。参考 [根组件导入 ↗](../../../apps/web/src/main.ts#L1 "支持入口将复杂界面职责交给 App 根组件的说明。")

<a id="startup-flow"></a>
## 启动流程与模块关系

启动顺序可以概括为：导入 Vue 工厂函数 → 导入根组件 → 加载共享设计令牌和应用样式 → 创建并挂载应用。两个 CSS 导入发生在挂载语句之前；其中 `@omem/ui/tokens.css` 提供共享 UI 设计令牌，`styles.css` 则是当前 Web 应用的样式入口。参考 [全局样式加载 ↗](../../../apps/web/src/main.ts#L3 "支持共享设计令牌和应用样式在挂载前被导入的流程描述。")

`main.ts` 与 `App.vue` 的关系是直接且有源码依据的：前者导入并挂载后者；而 `App.vue` 再组合导航、证据阅读、聊天、个人知识和学习等界面组件，因此 `main.ts` 是这些功能进入浏览器的统一上游入口，但材料不足以证明它会直接调用这些子组件。参考 [根组件功能组合 ↗](../../../apps/web/src/App.vue#L32 "说明 App 根组件继续组合证据阅读、聊天、个人知识和学习等界面模块。")

<a id="boundaries"></a>
## 边界条件与失败点

挂载目标被固定为选择器 `#app`，所以宿主 HTML 必须提供匹配节点；现有材料未包含 HTML，无法确认该节点如何创建。入口也没有展示路由器、全局插件、错误处理或启动时异步初始化，不能据此断言这些能力不存在，只能确认它们不在这六行入口代码中。参考 [固定挂载容器 ↗](../../../apps/web/src/main.ts#L5 "支持挂载目标固定为 #app，并界定入口代码未展示其他初始化步骤。")

当前材料没有对应测试文件，因此无法说明启动挂载、样式加载或缺失容器时的行为是否受到自动化断言保护。根组件内部存在基于 URL hash 与会话存储的视图选择逻辑，但那属于挂载后的界面状态管理，而非入口初始化。参考 [根组件视图状态 ↗](../../../apps/web/src/App.vue#L40 "支持 hash、会话存储和视图同步由根组件管理，而不是由启动入口管理。")
