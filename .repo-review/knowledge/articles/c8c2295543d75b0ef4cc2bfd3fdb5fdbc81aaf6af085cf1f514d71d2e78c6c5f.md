# 聊天与屏幕事件的事务化聚合

将高频聊天或屏幕事件按流暂存、按说话者去重并批量封装为统一 CaptureInput，同时保留逐 part 来源、迟到关系和批次记录。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="ingest"></a>
## 事件接收与幂等身份

聚合器只接受 chat 或 screen：聊天必须提供 conversationId，屏幕流由应用名和窗口标题组成。事件还必须携带 eventId 与 collectorId；在固定 personal workspace 内，相同身份且摘要一致返回 duplicate，摘要变化则报冲突。[聚合流与事件幂等规则 ↗](../../../apps/server/src/inputs/aggregator.ts#L39 "支持 chat 和 screen 流键、provenance 必填以及重复事件冲突检查。")

新事件的完整 envelope、payload/content 摘要、观察时间和接收时间会在同一个 `BEGIN IMMEDIATE` 事务中写为 pending。该实现明确固定到 personal workspace，并未提供任意 workspace 的租户隔离。[Pending 事件事务写入 ↗](../../../apps/server/src/inputs/aggregator.ts#L53 "直接支持新事件 envelope、摘要、时间字段及 pending 状态在事务中的写入。")

<a id="selection"></a>
## 成批时机与去重规则

流在静默超过默认 15 秒、最早事件超过默认 5 分钟或数量达到阈值时进入可处理集合；单批事件上限被夹在 1–500。[流就绪条件 ↗](../../../apps/server/src/inputs/aggregator.ts#L124 "支持静默时间、最大窗口和最大事件数三个批处理触发条件。") 候选按接收时间和 ID 排序，part 总数最多 50。内容去重键由 content digest 与 actor ID 组成，因此同一说话者的重复内容只产生一份 part，不同说话者的相同文本仍作为独立证据；重复事件本身仍保留在批次追踪列表。[同说话者去重与 part 预算 ↗](../../../apps/server/src/inputs/aggregator.ts#L145 "说明按内容与 actor 联合去重、不同说话者保留及 50 part 限制。")

<a id="envelope"></a>
## 来源合并与迟到标记

批量 envelope 为每个 part 补充 actor、观察时间、event ID、转发及 producer 信息。只有批内 actor 身份、类型和验证方式全部一致时，顶层 actor 才沿用，否则降级为 unknown；批次 ID 由 workspace、source、stream 和事件 ID 列表稳定生成。[聚合 envelope 的逐 part 来源 ↗](../../../apps/server/src/inputs/aggregator.ts#L181 "支持逐 part provenance、顶层 actor 稳定性判定和确定性批次身份。")

若任一观察时间不晚于上一批的最后观察时间，新批通过 `lateForBatchId` 指向上一批，而不是回写旧批，从而保留不可变捕获历史。[迟到事件批次关联 ↗](../../../apps/server/src/inputs/aggregator.ts#L224 "说明迟到判断基于上一批最后观察时间，并以 lateForBatchId 建立关系。")

<a id="commit"></a>
## 捕获与提交边界

flush 先调用外部 capture 获得 revision 和 job，再开启数据库事务复查所选事件仍全部 pending，写入批次并将事件更新为 batched；若状态已变化则抛出 `INPUT_BATCH_CHANGED`。[批次提交与并发复查 ↗](../../../apps/server/src/inputs/aggregator.ts#L320 "支持先执行 capture、再事务复查 pending 状态、写批次并更新事件的顺序及其非原子边界。")

外部 capture 位于批次事务之前，因此这里只能保证聚合表内部提交一致。若 capture 成功而状态复查或批次写入失败，当前材料没有展示对已生成 revision/job 的回滚、补偿或重用机制，不能宣称两部分具有原子性。[批次提交与并发复查 ↗](../../../apps/server/src/inputs/aggregator.ts#L320 "支持先执行 capture、再事务复查 pending 状态、写批次并更新事件的顺序及其非原子边界。")
