# agent-runtime · 模块理解 · 专题 2

本专题梳理会话材料整理、记忆候选提取与反馈纠正三类角色。它们在职责上可形成从语境保真、候选表达至纠正建议的分层，但现有材料没有证明三者已由宿主按固定顺序编排；此前“已形成分阶段处理链”的结论已被更审慎的独立角色表述取代。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="role-boundaries"></a>
## 彼此独立的角色职责与共同边界

conversation-analyst 负责保留说话人、时间、转述及回复语境，区分请求、承诺、猜测与事实，并避免把他人的承诺误记为用户待办。[会话语境与责任归属 ↗](../../../packages/agent-runtime/roles/conversation-analyst/1/prompt.md#L1 "支持 conversation-analyst 保留会话语境、区分陈述性质并防止把他人承诺转为用户待办的职责说明。") 它只能返回指定的中文 JSON，不调用工具或读取任务之外的文件，因此其定位是受固定材料约束的会话理解，而非直接执行动作。[会话分析的输出与执行边界 ↗](../../../packages/agent-runtime/roles/conversation-analyst/1/prompt.md#L3 "支持 conversation-analyst 仅返回中文 JSON、不调用工具且不读取额外文件的边界。")

extractor 则依据固定证据生成持久记忆候选，以可信上下文确定人物、范围、时间、来源和转发状态，并把材料正文视为不可信数据；它不得执行动作、批准候选或宣称候选已经应用。[提取器的可信上下文与权限边界 ↗](../../../packages/agent-runtime/roles/extractor/1/prompt.md#L3 "支持 extractor 从固定证据生成候选、依赖可信上下文、将材料视为数据，并禁止执行、批准或宣称应用。") 两者具有相容的证据边界，但材料未展示角色间调用和执行顺序。因此，先前“conversation-analyst 完成后由 extractor 接续处理”的结论已被替代：当前只能确认两项独立职责，不能确认实际编排。

<a id="proposal-flow"></a>
## 候选批次、证据与变更语义

extractor 清单绑定内联技能和 `ProposalBatch.v1`，同时声明禁用工具、隔离会话以及资源与修复预算。[提取器装载与隔离配置 ↗](../../../packages/agent-runtime/roles/extractor/1/manifest.json#L9 "支持内联技能、ProposalBatch 输出合同、工具禁用、会话隔离及资源预算均已在清单中声明。") 该批次的顶层结果由 `observations`、`proposals` 和 `abstentions` 组成：Schema 分别定义观察与提案入口，并把三类集合都列为顶层必填字段；弃权项还记录原因、细节和证据标识。[观察与提案集合定义 ↗](../../../packages/agent-runtime/roles/extractor/1/output.schema.json#L19 "支持 ProposalBatch 顶层包含 observations 和 proposals，并展示两类集合的结构入口。")[弃权集合与批次必填字段 ↗](../../../packages/agent-runtime/roles/extractor/1/output.schema.json#L606 "支持 abstentions 的结构及 observations、proposals、abstentions 均为批次顶层必填字段的概括。") 文本证据绑定片段修订、来源修订、精确引文及 Unicode 码点范围，以便候选回到固定材料。[不可变文本证据结构 ↗](../../../packages/agent-runtime/roles/extractor/1/output.schema.json#L697 "支持文本证据绑定片段修订、来源修订、精确引文和 Unicode 码点选择范围。")

操作枚举明确包含创建、更新和取代。[候选操作枚举 ↗](../../../packages/agent-runtime/roles/extractor/1/output.schema.json#L838 "直接支持候选操作包含创建、更新和取代三种取值，修正此前引用范围不足的问题。") 提示规范进一步说明：创建时省略目标并使用空版本映射；更新时携带既有目标及当前版本、保持原作用域，并由当前原始片段重新支撑，来源失去支持时应弃权。[候选创建与更新规则 ↗](../../../packages/agent-runtime/roles/extractor/1/prompt.md#L7 "支持创建与更新的目标、版本、作用域和当前原始证据要求，以及失去支持时应弃权的语义。") 这些材料证明合同和角色要求已经定义，却不能证明宿主已实施证据语义复核、版本冲突处理或应用状态机。此前把“结构合法、语义复核、实际应用”描述为已存在三道关口的结论，也由“这三个层面仍需分别验证”取代。

<a id="feedback-loop"></a>
## 反馈纠正提案及其限制

feedback-curator 面向已认证所有者反馈，区分事实纠正、任务调整、范围约束、弱有用性信号与结果证据，并将纠正候选绑定到原始目标和证据；重复反馈或生成摘要不能升级为独立权威。它只返回 `CorrectionProposal.v1`，不得直接应用纠正，也不得改变权限、采集范围、预算或自动批准规则。[反馈纠正角色职责与禁区 ↗](../../../packages/agent-runtime/roles/feedback-curator/1/prompt.md#L3 "支持反馈分类、原始目标与证据绑定、非独立权威信号，以及不得应用纠正或改变全局控制项的边界。")

该合同要求修正标识、目标、范围、停用内容、替代内容、证据、理由和来源齐备，但目标、范围和来源仅约束为对象，证据元素也没有在该 Schema 中展开。[纠正提案外层合同 ↗](../../../packages/agent-runtime/roles/feedback-curator/1/output.schema.json#L6 "支持 CorrectionProposal 的必填信息链，并说明多个嵌套对象和证据元素目前只有宽泛类型约束。") 因此只能确认纠正提案的外层信息链，不能确认身份绑定、目标版本、证据语义及应用成功已由宿主强制保障。feedback-curator 与前两类角色在概念上可以形成职责分层，但是否由同一编排器触发、是否接收前序角色产物，仍缺少材料支持。
