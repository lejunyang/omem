# 证据 Trail 的可序列化数据模型

定义可跨模块复用的证据阅读帧、URL 片段编码、循环定位与无损压栈，并将 URL 持久化预算与渲染深度分离。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="frame-contract"></a>
## 帧合同与导航语义

Trail 被建模为单个浮动抽屉中的帧栈，目标是支持从模块逐层进入文件、符号、决策或测试，再按原路径返回；帧采用普通可序列化记录，以便整个栈经 `location.hash` 深链恢复。[Trail 栈设计目标 ↗](../../../packages/ui/src/trail.ts#L1 "支持单抽屉逐层阅读、返回及通过哈希恢复整个帧栈的架构说明。") 帧类型覆盖模块、文件、符号、评审片段、决策、知识、引用和来源。每帧以 `kind + id` 形成稳定身份，并携带人读标题；可选的滚动位置用于退栈恢复，文件、符号、片段、行号和模块字段则留给父级加载具体数据。[TrailFrame 类型合同 ↗](../../../packages/ui/src/trail.ts#L6 "支持帧种类、稳定身份、人读标题、滚动恢复和数据引用字段的说明。")

<a id="stack-utilities"></a>
## 序列化、循环与深度边界

`frameToSegment` 分别对 kind 与 id 做 URI 编码，再组合成两段哈希路径，避免标识中的保留字符直接破坏路由。[哈希路径片段编码 ↗](../../../packages/ui/src/trail.ts#L32 "支持 kind 与 id 被分别 URI 编码后组成路径片段的流程。") `findLoop` 以 kind 和 id 查找已有帧，返回索引或 `-1`，只提供纯检测，不自行决定跳转或提示。`pushFrame` 则始终返回追加后的新数组，不修改原栈。[循环查找与不可变压栈 ↗](../../../packages/ui/src/trail.ts#L44 "支持循环检测只返回索引，以及压栈通过新数组追加而不修改输入的论断。")

`MAX_TRAIL=200` 被注释为 URL 持久化预算而非渲染上限；真实链条达到预算时应由调用者显式告知，而不是静默丢帧。值得注意的是，`pushFrame` 的注释称“bounded”，实现却没有读取该常量，因此截断或拒绝序列化必须发生在未提供的路由层。[URL 深链预算说明 ↗](../../../packages/ui/src/trail.ts#L37 "支持 200 层仅限制持久化、渲染不静默截断，并揭示压栈注释与实现之间的边界。")
