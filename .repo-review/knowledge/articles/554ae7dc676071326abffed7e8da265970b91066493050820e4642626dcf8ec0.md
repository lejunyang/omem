# 证据追踪抽屉的可序列化导航栈

定义证据追踪抽屉的共享帧模型，以及深链接序列化、循环检测和入栈操作。它让用户能沿模块、文件、符号、决策、引用和来源逐层阅读，并为返回位置恢复与 URL 长度控制提供基础数据，但具体抽屉交互和持久化策略由调用方实现。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决递归阅读中的导航问题

证据阅读并非一次跳转：用户可能从模块进入文件，再深入符号、决策、测试或原始来源。这里把每一步表示成一个可序列化的栈帧，使同一个浮动抽屉能够逐层钻取并逐层返回；普通记录结构还允许调用方把整条路径写入 `location.hash`，刷新后恢复深链接。参考 [追踪栈设计目的 ↗](../../../packages/ui/src/trail.ts#L1 "支持抽屉逐层钻取、返回以及通过地址哈希恢复深链接的用途说明。")

帧类型覆盖模块、文件、符号、评审片段、决策、知识、引用和来源，说明该模型承担的是跨内容类型的统一导航，而不是某一种代码实体的专用历史。参考 [可导航内容类型 ↗](../../../packages/ui/src/trail.ts#L6 "支持该导航模型统一覆盖代码、知识、决策、引用与来源等多类内容。")

<a id="frame-data"></a>
## 帧如何保存身份与恢复线索

每个帧以 `kind + id` 构成稳定身份，`title` 用于抽屉标题或面包屑；可选的 `scroll` 保存弹出子层后应恢复的位置。`fileId`、`symbolId`、`fragmentId`、行号和模块名则是自由组合的加载线索，由上层按帧类型解释。参考 [栈帧字段定义 ↗](../../../packages/ui/src/trail.ts#L16 "说明稳定身份、展示标题、滚动恢复位置以及各类数据加载线索。")

`frameToSegment` 只把类型与身份分别进行 URI 编码后拼成路径片段，因此 URL 中不会包含标题、滚动位置或其他加载字段。仅凭当前材料无法确认这些附加字段是否另有序列化机制。参考 [深链接片段编码 ↗](../../../packages/ui/src/trail.ts#L32 "支持序列化函数仅编码帧类型与 ID 的判断。")

<a id="stack-rules"></a>
## 循环检测与深度边界

`findLoop` 以同类型且同 ID 为重复条件，返回已有帧下标，供容器在入栈前决定如何处理循环；函数本身不修改栈，也不规定是回退到旧帧、拒绝打开还是展示提示。参考 [重复帧定位 ↗](../../../packages/ui/src/trail.ts#L44 "说明循环检测采用 kind 与 id 联合匹配，并只返回已有位置供容器决策。")

持久化到 URL 的设计上限是 200 层，注释明确渲染器本身不受此限制，并要求触顶时由调用方显式提示。值得注意的是，`pushFrame` 的注释称入栈受上限约束，但实现只是复制旧数组并追加新帧，没有检查 `MAX_TRAIL`；所以实际限长只能依赖未提供的调用方，不能据此认定本文件已经执行截断或拒绝策略。参考 [URL 持久化深度 ↗](../../../packages/ui/src/trail.ts#L37 "支持 200 层限制只针对序列化深链接、渲染不受限且触顶应显式提示的边界说明。") [实际入栈行为 ↗](../../../packages/ui/src/trail.ts#L50 "显示 pushFrame 实际仅追加帧，与其受限入栈的注释存在未落实的差异。")
