# 为开发任务准备可复现的 Git 仓库快照

该模块把经校验的 Git 地址或本地绝对路径与 ref 准备成固定提交工作区：复用该别名下的裸对象缓存，按提交创建独立 worktree，持续保存准备状态，并限制交互认证、hooks、子模块和 LFS 等隐式行为。并发锁和缓存均以 alias 为边界；进入 Git 主流程后的错误恢复不覆盖锁建立前后的所有前置操作。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_and_inputs"></a>
## 解决什么问题

开发任务不能直接依赖会移动的分支，也不应在刷新仓库时覆盖正在使用的旧工作区。`RepositoryPreparer` 因此把一次准备过程记录为 `fetching`、`checkout`、`ready` 或 `failed`，并返回固定提交、目录、进度消息和已知限制。参考 [准备状态模型 ↗](../../../apps/server/src/development/repositories.ts#L12 "说明准备阶段、固定提交、输出目录、消息与限制如何作为结果返回。")

入口接受项目别名、Git 地址或本地绝对路径、ref 与 requestId。地址校验分为几层：所有输入都拒绝控制字符和前导 `-`；绝对路径随后直接规范化并返回，因此其中的空白、`?` 或 `#` 不受 URL 组件规则限制；非绝对路径拒绝空白，符合 `user@host:path` 的 scp 风格地址也会直接接受。只有经 `new URL` 解析的 HTTP(S)/SSH 地址才会拒绝查询、片段和密码，其中非 SSH 地址还拒绝用户名。认证应由既有 SSH 或 Git credential helper 提供。ref 则拒绝空值、前导 `-`、空白、`~ ^ : ? * [ \\`、`..` 和 `@{`，从而排除带目标端冒号等受检 refspec 以及多种修订表达式；但前导 `+` 未被拒绝，例如 `+main` 仍会原样成为 `git fetch origin <ref>` 的参数。参考 [仓库地址与 ref 校验 ↗](../../../apps/server/src/development/repositories.ts#L26 "支持绝对路径、scp 风格地址和标准 URL 的分层校验顺序，以及 ref 实际拒绝与仍可通过的语法边界。")

<a id="preparation_flow"></a>
## 一次代表性准备如何执行

**教学示例**：上层调用 `prepare("workshop", url, "main", "req-1")`。模块先校验输入，再由 alias 确定 `repositories/<alias>`，锁文件和对象缓存都位于这个目录下。同一 requestId 已成功且目录仍在时直接复用结果；同一 alias 若已绑定其他地址则拒绝。活跃锁阻止的是**同一 alias** 的并发准备，僵尸锁会被清理；同一 URL 若使用不同 alias，会得到不同的锁和缓存，因而仍可能并发准备。参考 [alias 目录、状态与准备锁 ↗](../../../apps/server/src/development/repositories.ts#L188 "支持 alias 到独立目录的映射、失联进程的状态解释、同请求复用、地址绑定，以及 lock.json 和对象缓存的 alias 级作用域。")

```mermaid
flowchart LR
  A[校验 alias、URL、ref] --> B[建立或复用该 alias 的裸对象缓存]
  B --> C[fetch 指定 ref]
  C --> D[解析 FETCH_HEAD 为 commit]
  D --> E[为 commit 创建 detached worktree]
  E --> F[保存 ready 状态与目录]
```

缓存首次使用时执行 bare init 并登记 `origin`，随后 fetch 目标 ref；解析出的提交会写入专用 ref，避免远端强推后失去可达性。工作区位于 `versions/<commit>`，以 detached worktree 固定到该提交，并再次校验 HEAD。参考 [固定提交工作区 ↗](../../../apps/server/src/development/repositories.ts#L255 "支持裸缓存、fetch、提交解析、保活引用和 detached worktree 的主流程。")

<a id="safety_and_limits"></a>
## 执行边界、恢复与其他模块关系

fetch 复用现有 Git/SSH 凭据，但关闭终端提示、Git hooks 和扩展协议，不递归抓取子模块，并跳过 LFS smudge。`--no-tags` 表示不自动跟随或抓取额外标签；显式 `ref` 仍可指定标签。进程输出只对实现已识别的模式做脱敏：HTTP(S) URL 中的 `user:password@`，以及带 `authorization:`、`password=`、`password:`、`token=` 或 `token:` 前缀的非空白值；处理后只保留末尾 4000 字符，这并非对任意 Git 或 SSH 凭据格式的通用清除保证。连续两分钟无输出或收到 AbortSignal 时先终止进程，三秒后仍未退出再强制结束。参考 [受控 Git fetch ↗](../../../apps/server/src/development/repositories.ts#L71 "支持关闭交互、hooks、扩展协议与递归子模块，说明 --no-tags 与显式 ref 的组合，并界定已识别输出模式的脱敏、截断、超时和中止策略。")

成功并不意味着仓库内容完整或已可直接编码：现有未提交修改会保留并写入限制；`.gitmodules` 表示子模块尚未读取；检测到 LFS 属性时文件可能仍是指针。模块只把状态置为 ready，明确不运行项目脚本。参考 [内容完整性限制 ↗](../../../apps/server/src/development/repositories.ts#L301 "说明未提交修改、子模块和 LFS 内容如何被保留或标记为限制，并明确 ready 不等于已编码或执行脚本。")

失败恢复有明确的控制流边界。建目录、读取或清理旧锁、以 `wx` 创建新锁以及首次保存 `state.json` 都发生在 `try` 之前；这些前置步骤若失败，不会进入后面的 `catch/finally`，其中首次保存失败时可能留下刚创建的锁。参考 [try 之前的锁与首次状态写入 ↗](../../../apps/server/src/development/repositories.ts#L229 "证明建目录、旧锁处理、新锁创建和首次 save 均位于 Git 主流程的 try 之前，因此不受后续 catch/finally 覆盖。") 一旦执行进入 Git 准备主流程，内部错误会被转成对已识别模式脱敏的 failed 状态并尝试保存、再向调用者抛出，`finally` 随后删除锁。参考 [主流程失败处理与锁释放 ↗](../../../apps/server/src/development/repositories.ts#L324 "支持进入 try 后的错误按已识别模式脱敏、failed 状态保存尝试、重新抛错和 finally 删除锁的行为。") 下次读取状态时，如果发现处于 fetching 或 checkout 的记录所对应进程已不存在，会把返回结果解释为可重试的 failed，但这只是读取时的解释，不会在此处重新写入状态文件。参考 [alias 目录、状态与准备锁 ↗](../../../apps/server/src/development/repositories.ts#L188 "支持 alias 到独立目录的映射、失联进程的状态解释、同请求复用、地址绑定，以及 lock.json 和对象缓存的 alias 级作用域。")

与其他模块的直接关系是：本文件从 `workspace.js` 复用 `git` 和 `saveJson`，分别执行受控 Git 子命令与持久化 `state.json`；对外导出的校验函数、状态类型和 `RepositoryPreparer` 则构成上层开发编排可调用的仓库准备接口。参考 [工作区工具依赖 ↗](../../../apps/server/src/development/repositories.ts#L1 "说明模块直接依赖 workspace.js 提供的 Git 执行与 JSON 持久化能力。")
