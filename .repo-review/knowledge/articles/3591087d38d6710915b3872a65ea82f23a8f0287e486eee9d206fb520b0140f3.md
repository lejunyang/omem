# omem 实施与仓库知识维护约定

面向实现工作的规范性约定：omem 坚持统一证据链和单用户现实边界，并要求功能实现、真实验证与仓库派生知识分别提交和记录。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="principles"></a>
## 产品目标与实施边界

omem 的目标是统一个人记忆、可追溯问答与主动事项跟进；代码 AST 只是同一证据体系中的特化输入，不能形成独立知识库。修订与片段身份保持固定，派生回答不是新原件；高置信小范围变更可以自主执行，歧义、危险或范围过大的操作仍需用户决定。[统一证据链与变更决策原则 ↗](../../../AGENTS.md#L3 "支持产品目标、AST 的从属地位、固定证据身份以及自主变更的决策边界。")

当前 SQLite/shared-token 实现明确是单用户系统，架构虽保留团队扩展空间，却不能宣称已有租户隔离。外部通知、捕获范围、系统服务和屏幕监听也都是独立的显式集成，不应因启动主服务而自动启用。[单用户与外部集成边界 ↗](../../../AGENTS.md#L8 "支持当前没有租户隔离，以及外部通知和系统监听必须显式启用的说明。")

<a id="review_workflow"></a>
## 代码修改与知识验收流程

`.repo-review` 同时是本仓库对 omem 的实际应用和验收材料。捕获、AST、知识生成、引用、检索或助手运行发生变化后，应先验证并提交实现，再通过真实模型更新受影响知识并单独提交；覆盖记录须区分 reviewed、stale、pending、failed，失败结果不得伪装成复核完成。[仓库知识更新流程 ↗](../../../AGENTS.md#L16 "说明实现提交、真实模型生成、独立复核及覆盖状态检查的先后关系。")

语义检索修改还要更新 review 索引，并通过真实搜索接口检查中文问法能否回到当前原始材料；验证记录必须写明命令、退出码、模型、快照、范围及剩余限制，因此测试通过不等于知识覆盖完整。[检索与覆盖验证要求 ↗](../../../AGENTS.md#L23 "支持语义检索的真实验证步骤以及 verification 记录不能被笼统测试结论替代。")

局部生成参数目前存在文档冲突：本约定要求 `--only=<文件或目录> --modules`，README 示例仍使用 `--target=<path>`。[README 局部生成示例 ↗](../../../README.md#L41 "支持 README 仍以 `--target` 展示局部知识生成，与 AGENTS 的 `--only` 写法形成待确认的合同冲突。") 在实现合同确认前，两者不能被默认为等价。

<a id="wiki_contract"></a>
## Code Wiki 的共用合同与已知限制

Code Wiki 是统一 Capture→Source/Revision/Fragment 证据链上的派生视图，repo-review 只提供仓库输入适配与隔离运行配置。内部 ID 可用于路由，但可见文本必须使用人类标签；missing 或 stale 目标要显示不可操作原因。知识、原文和代码阅读共同复用 `packages/ui` 的 evidence trail。[派生视图与共享阅读合同 ↗](../../../AGENTS.md#L26 "支持 Code Wiki 的系统定位、人类标签约束和共享 evidence trail 交互要求。")

评审关系只能来自人工维护且可重新解析的 locator；解析失败保留 rejected 记录，不能用语义相似度自动补边。当前明确未实现的是跨文件 calls 解析和跨 revision 符号或片段身份续接。[关系定位与明确解析边界 ↗](../../../AGENTS.md#L32 "支持关系种子必须可校验，以及跨文件调用和跨修订身份续接尚未实现。") 类型解析未完成则由 README 的现状说明另行确认，不能仅凭前述 AGENTS 范围推导。[README 中的类型解析限制 ↗](../../../README.md#L67 "直接支持跨文件调用精确类型解析尚未完成，避免把该结论错误归因于 AGENTS 的较窄范围。")
