# omem 实施与仓库知识维护约定

该文件规定 omem 的实施方向、技术边界、验证与提交纪律，以及 Code Wiki/repo-review 的数据、交互、模型和关系约束。它属于面向后续工作的规范性材料，描述目标、要求和部分当前边界，不能单独证明相应能力已经实现或通过验收。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="goals-and-boundaries"></a>
## 产品目标与实施边界

文件把 omem 定位为统一个人记忆、可追溯问答与主动事项跟进的系统，未来学习卡继续复用同一原始证据；代码分析虽需 AST 特化，但不应形成独立事实库。它还明确提醒：调研方案不能视作已实现能力，因此本文中的目标和约定主要是实施准则，而非当前功能清单。[产品目标与调研边界 ↗](../../../AGENTS.md#L1 "支持 omem 的统一记忆目标、AST 特化仍归属于统一知识体系，以及调研方案不能当作已实现能力的判断。")

技术选择上，UI 采用 Vue 3 与 TypeScript，并复用公共 UI 包；依赖与全局配置由 osdk 管理。LLM 首期通过可配置 Agent CLI/ACP 接入，本地大模型不是运行前提；中文向量模型需显式声明、下载和锁定，换模型时必须更换向量身份。当前 SQLite/shared-token 方案被明确界定为单用户实现，架构虽保留团队范围，但不能宣称已有租户隔离。捕获输入统一覆盖文本、图片、链接和上下文元数据，且捕获内容不能被当成工具指令。[技术选型与系统边界 ↗](../../../AGENTS.md#L5 "说明 UI、osdk、模型与向量配置、单用户实现、统一捕获输入和证据不可被当作指令等基础约束。")

<a id="verification-workflow"></a>
## 知识更新、验证与提交流程

`.repo-review` 被定义为 omem 在自身仓库上的实际应用及验收材料。捕获、AST、知识生成与复核、引用、检索或助手运行发生变化后，应先检查并提交实现，再单独更新受影响的知识资产；这体现了“产品实现”和“派生知识”分阶段提交、分别留痕的要求。[仓库知识验证流程 ↗](../../../AGENTS.md#L16 "支持实现提交、真实模型复核、覆盖状态、检索验证和自动化全量验证报告之间的流程关系。")

知识生成要求调用真实 ACP 模型并保留独立 verifier 与运行 trace，手写 seed、fixture 或仅同步 AST 都不能替代模型验证。覆盖记录必须区分 reviewed、stale、pending、failed，失败时保留旧历史并说明原因。检索改动还需更新 review 索引并通过真实 HTTP 搜索验证中文问题能返回当前原始材料；全量验证报告应自动记录命令、退出码、指纹、索引及引用状态，未执行项只能标为 skipped，不能手填通过率。[仓库知识验证流程 ↗](../../../AGENTS.md#L16 "支持实现提交、真实模型复核、覆盖状态、检索验证和自动化全量验证报告之间的流程关系。")

<a id="repo-review-contract"></a>
## Code Wiki 与 repo-review 合同

Code Wiki 被约束为统一 Capture→Source/Revision/Fragment 链上的派生视图，而非独立产品或事实权威；通用处理应复用既有知识流水线、角色运行网关和任务系统，repo-review 只承担本仓库输入适配与隔离运行配置。[Code Wiki 与 repo-review 维护规则 ↗](../../../AGENTS.md#L26 "解释统一派生视图、DTO 展示合同、trail 复用、seed 校验、模型触发、数据发布边界和已知代码分析限制。")

前端合同严格区分内部标识和人类可读标签：内部 ID 可用于路由与深链，却不得直接渲染；缺失或过期目标必须不可操作并展示原因。证据阅读的 trail 帧栈由公共 UI 组件承载，Code Wiki 不另建抽屉体系。人工 association 和理解 seed 必须通过稳定 locator 重新解析到当前代码图，解析失败保留 rejected 记录，禁止凭语义相似度自动建立评审边。模型生成只在显式分析、生成或用户操作时触发；运行数据进入 gitignored 目录，发布知识资产则按功能提交。当前明确限制包括不解析跨文件 calls，以及尚未实现跨 revision 的符号或 fragment 身份续接。[Code Wiki 与 repo-review 维护规则 ↗](../../../AGENTS.md#L26 "解释统一派生视图、DTO 展示合同、trail 复用、seed 校验、模型触发、数据发布边界和已知代码分析限制。")

<a id="knowledge-and-relations"></a>
## 正文知识流程与关系模型

正文知识遵循“分析原始材料—独立复核—组织模块、主题与概览”的流程，并要求代码、文档、对话和图像共享同一合同与运行时。引用必须贴近所支持的论断，带可读名称、理由、关系和固定目标；宿主负责复制精确原文，独立角色再判断语义支持性，因此位置有效不等于论断已被证据支持。无法确认的内容应保留为有依据的疑问或调查项，错误、过期或失败的结果不得覆盖有效知识。[知识正文与独立复核流程 ↗](../../../AGENTS.md#L38 "支持多阶段知识生成、内联引用、统一证据阅读、调查项处理和失败结果不得覆盖有效知识等要求。")

评审关系由 `review_relations` 表达，前向类型包括 implements、requires、decided_by、researched_by、tested_by 和 candidate_for，状态区分 confirmed、candidate、missing；无法解析的目标必须记为 missing。关系种子同步采用确定性 ID 幂等写入，新增关系需要先登记到 associations 配置，再触发 review 同步。这里描述的是规定的数据模型和同步路径，不能仅凭本文确认数据库迁移、接口或 UI 已全部落地。[评审关系类型与同步路径 ↗](../../../AGENTS.md#L47 "说明关系类型、状态语义、缺失目标处理、确定性同步以及新增关系的登记入口。")
