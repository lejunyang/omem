# 整理文章，并在原文更新后维护解释

从“预算八十元、图书馆集合”的教学材料出发，说明如何在统一知识库选材、填写阅读目标、观察调查与复核结果；也说明失败重试、章节级待核提示、同篇重新整理和固定历史引用。最后给出修改这条流程时的前后端入口。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="start"></a>
## 从一个具体整理任务开始

启动统一 dev 后进入主菜单的“知识库”；它也是没有指定地址时的默认入口。参考 [统一知识库入口 ↗](../../../apps/web/src/App.vue#L51 "支持知识库是主菜单项且默认进入该视图的说明。")

下面用一个**教学示例**贯穿全文，不代表真实活动：原始 Markdown《活动约定》有两个小节——预算是八十元，地点在图书馆；生成后的文章可把它们重组为“费用”和“集合”两节，并分别引用对应原文。参考 [活动约定教学材料 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L23 "给出八十元预算、图书馆地点及文章两节的教学夹具，支持贯穿示例。")

在知识库首页或某个分类中点击“整理文章”：

1. **选择材料**：按标题或路径筛选，勾选《活动约定》的固定版本；列表允许跨分类选择和继续展开。
2. **说明阅读目标**：文章主题可填“春游安排”，在“想弄懂什么”中写“参加者要知道带多少钱、去哪里集合”，读者填“参加者”。
3. 点击“开始整理”。从分类页发起时文章保存到该分类；从知识库根页发起时按生成内容归类。参考 [两步整理与分类提示 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L102 "支持跨分类选材、填写文章目的，以及分类页保存当前路径、根页按内容归类的界面提示。")

当前界面只有一个“想弄懂什么”输入框，它会同时成为目标、场景和一个问题；不要误以为页面还要求分别填写这三项。参考 [阅读目标与分类字段 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L58 "说明当前单个目标输入会同时写入 goal、scenario 和 questions，且只有存在分类路径时才写入 topicPath。")

<a id="submit"></a>
## 提交后怎样变成可读文章

提交时，服务端先确认已配置 Agent、当前没有另一项知识整理在运行、阅读目标格式有效，并检查所选固定版本仍然存在；如果材料已换版，页面会要求刷新后重选。通过检查后，页面计划保存稳定的材料 key，而不是只记住这次勾选的 revision id。参考 [创建页面校验 ↗](../../../apps/server/src/knowledge/api.ts#L184 "支持 Agent、并发、合同和固定材料版本校验，以及将 revision 选择转成稳定材料 key。")

```mermaid
flowchart LR
  A[保存页面计划] --> B[调查材料]
  B --> C[撰写文章]
  C --> D[独立复核]
  D -->|接受| E[发布到知识库]
  D -->|需修改| C
```

写作链先保存计划并标记为进行中，再读取计划范围内的当前材料；原生研究完成后才进入写作，接受的文档才会发布。正文引用和章节背景前提成为更新依据，调查中读过但未用于支撑论断的材料另存为调查轨迹。参考 [页面写作生命周期 ↗](../../../apps/server/src/knowledge/pipeline.ts#L251 "支持先保存计划、标记状态、失败留档，以及从当前材料启动原生研究。") [写作复核与显式分类 ↗](../../../apps/server/src/knowledge/pipeline.ts#L161 "支持写作后独立复核、仅发布接受结果，并证明只有计划带 topicPath 时才强制保持目录位置。")

知识库每五秒刷新一次状态。运行时会提示文章要在“调查、撰写与复核”完成后出现；成功后显示“已完成”，可直接点“阅读文章”。参考 [整理状态与阅读入口 ↗](../../../apps/web/src/knowledge/KnowledgeHome.vue#L180 "支持页面轮询运行状态，以及成功后提供阅读文章入口。")

<a id="failure"></a>
## 失败后保留什么，怎样重试

失败不会抹掉阅读目标。写作入口总是先保存页面计划；异常只把计划标为失败，只有通过独立复核的结果才进入发布步骤。第一次整理失败时，“准备整理”区域显示“上次整理未完成，阅读目标已保留”，按钮变为“重试整理”；已有文章重新整理失败时，原来的已发布正文仍然可读。参考 [失败计划与重试按钮 ↗](../../../apps/web/src/knowledge/KnowledgeHome.vue#L412 "支持失败时保留阅读目标、显示重试整理，以及已有文章的重新整理入口。") [失败恢复行为 ↗](../../../apps/server/tests/knowledge-pipeline.test.ts#L138 "验证失败后计划保留、未发布失败结果，并可沿精确反馈重新写作后发布。")

“重试整理”和“重新整理这篇”都调用同一个按页面 key 刷新的入口：服务端取回保存的计划并强制重跑，因此是在维护同一篇文章，而不是新建同名副本。新结果发布前，旧 head 不会被替换。参考 [同篇刷新入口 ↗](../../../apps/server/src/knowledge/api.ts#L169 "支持按原页面 key 读取保存计划并强制重跑。") [发布时替换文章 head ↗](../../../apps/server/src/knowledge/repository.ts#L192 "支持只有发布成功时才写入新 revision 并更新同一文档的 head。")

常见阻碍也能直接从界面处理：未配置 Agent 时先到“能力与连接”完成配置；已有任务运行时等待它结束；若提示所选材料已更新，则刷新材料列表后重新选择。参考 [创建页面校验 ↗](../../../apps/server/src/knowledge/api.ts#L184 "支持 Agent、并发、合同和固定材料版本校验，以及将 revision 选择转成稳定材料 key。")

<a id="changes"></a>
## 只改导读与改预算，会看到不同结果

文章引用始终钉在写作时的原文。系统另行比较旧版与当前版，只判断解释是否仍适用：对 Markdown 或代码，它寻找包住引用范围的最小完整章节或符号；新版中只有一个同名同类结构且全文未变时，即使行号移动也可继续使用。图片、无行范围、普通整篇文本或结构有歧义时不能这样豁免。参考 [结构化上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "解释固定引用不重映射，以及 Markdown 章节或代码符号在唯一且文本未变时允许移动行号。")

| 教学变化 | 页面结果 | 检索结果 |
| --- | --- | --- |
| 在两个小节前只加“这里只更新导读” | “费用”“集合”仍为当前 | 两节仍可找到 |
| 把预算改为一百二十元 | “费用”提示需核对；“集合”仍可读 | 旧“八十元”费用节不再作为当前知识命中；集合仍可找到 |
| 若“集合”明确登记了“方案以原预算为前提” | 预算变化也会使“集合”待核 | 该节在重新整理前也退出当前知识检索 |

前两种结果由同一组教学夹具验证：无关导读移动后固定引用仍指向旧 revision；预算章节变化后，只把费用节标为待核，集合节继续参与检索。参考 [导读与预算变化示例 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L92 "验证无关导读变化不使文章失效、预算变化只影响费用节，并让旧费用节退出当前知识检索。") 第三种结果说明 reviewSources 的用途：正文没直接引用、但会改变本节解释的前提，应按最小原文范围登记；不能把所有调查读取都算作依赖。参考 [背景前提变化示例 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L165 "验证明确登记的预算前提变化会使集合节也进入待核状态。")

阅读页会在文章顶部说明“部分内容需要核对”，并在对应章节上方给出原因，同时保留下方旧解释供判断。自动发生的是**状态重算与提示**，不是后台自动改写正文。参考 [逐节待核提示 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L69 "支持阅读页保留旧解释并在具体章节展示更新原因。")

<a id="history"></a>
## 重新整理同一篇，同时保留旧来源

看到待核提示后，点击页底“重新整理这篇”。刷新接口沿用原页面 key 和已保存的阅读目标；运行时用计划中的材料 key 取得当前版本，重新调查、写作和复核。成功发布后，同一页面的 head 指向新 revision，文章身份不变。参考 [同篇刷新入口 ↗](../../../apps/server/src/knowledge/api.ts#L169 "支持按原页面 key 读取保存计划并强制重跑。") [发布时替换文章 head ↗](../../../apps/server/src/knowledge/repository.ts#L192 "支持只有发布成功时才写入新 revision 并更新同一文档的 head。") [重新整理读取当前材料 ↗](../../../apps/server/src/knowledge/pipeline.ts#L266 "支持同一计划按 materialKeys 取得当前材料，并在完成研究后进入写作复核。")

目录位置取决于创建时是否保存了分类路径：从某个分类发起时，计划会显式保存 `topicPath`，写作管线每次都用它覆盖生成结果，因此重新整理后仍留在该分类；从知识库根页发起时不保存该字段，界面提示“按内容归类”，重新整理后的文章仍可能随新生成内容改变分类位置。参考 [两步整理与分类提示 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L102 "支持跨分类选材、填写文章目的，以及分类页保存当前路径、根页按内容归类的界面提示。") [阅读目标与分类字段 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L58 "说明当前单个目标输入会同时写入 goal、scenario 和 questions，且只有存在分类路径时才写入 topicPath。") [写作复核与显式分类 ↗](../../../apps/server/src/knowledge/pipeline.ts#L161 "支持写作后独立复核、仅发布接受结果，并证明只有计划带 topicPath 时才强制保持目录位置。")

重新整理不会偷偷改写旧版文章的引用。读者点击正文引用时，前端发送“文章 key + 文章 revision + 引用 key”；服务端先读取那一版文章，再用其依赖中保存的 digest 解析材料。若当前材料 digest 不匹配，仓储会遍历来源历史，找到写作时的固定版本。参考 [文章版本固定引用 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L50 "支持前端以文章 key、文章 revision 和引用 key 打开证据。") [服务端引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L45 "支持按文章依赖 digest 解析固定文章或材料版本，并返回不可用原因。")

证据抽屉随后以材料 key、digest 和行范围打开旧原文；若固定版本确实找不到，会显示“无法打开引用”的可读原因，而不是回退到新版冒充原证据。参考 [证据抽屉读取固定原文 ↗](../../../apps/web/src/knowledge/KnowledgeFrame.vue#L83 "支持用 digest 和行范围打开材料，固定目标不可用时显示人读错误。")

因此用户应把两个动作分开理解：系统会自动告诉你哪些节需要核对；正文更新必须显式点击“重新整理这篇”。应用启动也只恢复已有知识，不会自动生成或重写整库。参考 [显式更新边界 ↗](../../../docs/reader-first/publication-lifecycle.md#L27 "明确系统保留历史并要求显式重新整理，没有后台自动重写所有受影响页面。")

<a id="developer"></a>
## 开发者从哪里修改这条流程

按要改变的用户行为定位入口：

| 想改变什么 | 首要入口 |
| --- | --- |
| 两步选材、字段文案、提交内容 | ArticleComposer.vue |
| 目录状态、轮询、失败重试和“重新整理这篇” | KnowledgeHome.vue |
| 阅读目标、逐节待核提示、引用点击 | KnowledgeDocument.vue、KnowledgeFrame.vue |
| 创建/刷新页面、并发限制、固定引用解析 | 服务端 knowledge/api.ts |
| 调查—写作—复核—发布、失败状态 | knowledge/pipeline.ts |
| 页面计划、历史 head、旧材料解析 | knowledge/repository.ts |
| 无关改动与逐节状态判断 | knowledge/lifecycle.ts |
| 页面计划和引用合同 | packages/contracts/src/knowledge.ts |

当前设计文档也把发布更新、阅读操作和合同入口按这几层列出。参考 [知识维护修改入口 ↗](../../../docs/reader-first/publication-lifecycle.md#L41 "给出合同、发布更新、搜索调查和阅读操作的分层入口。")

仓库自身的读者指南走同一条 KnowledgePipeline：脚本读取页面计划和实际模型配置，最多并发处理两页，并记录每页是 reviewed、stale、pending 还是 failed。局部更新应显式指定页面目标；`--retry` 是强制重跑已有或失败目标，不代表产品已经有后台自动维护。参考 [仓库指南生成脚本 ↗](../../../scripts/review-guides.ts#L17 "支持页面计划、实际模型配置、同一管线、并发上限和结果状态记录的说明。") [运行与局部重跑 ↗](../../../docs/reader-first/operations.md#L5 "说明启动不自动生成整库，指南可按页面显式运行，retry 用于重试。")
