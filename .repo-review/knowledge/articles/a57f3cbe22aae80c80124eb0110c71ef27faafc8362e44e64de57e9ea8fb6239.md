# Repo-review 增量同步与关系重建

按固定白名单将仓库文本捕获为路径身份稳定的不可变修订，区分遍历时跳过与捕获失败，依据内容类别分片，并在完整同步中结合 Git 状态更新基线、从人工 association seed 重建关系。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scope"></a>
## 扫描范围、安全边界与分片

同步器遍历固定目录，并接纳少量根级白名单文件。目录遍历中发现的符号链接会被跳过，不安全的顶层扫描根也不会进入遍历；这两类排除不会自动生成逐文件失败记录。根级白名单文件仅凭存在性加入候选，显式 `only` 目标也直接进入候选，因此它们若是链接或越界路径，仍会在捕获阶段被拒绝并记入 `failed`。[候选扫描与链接排除 ↗](../../../apps/server/src/review/sync.ts#L172 "支持附近对目录遍历链接、不安全顶层扫描根和根级白名单文件加入候选方式的区分。")[单文件捕获的安全拒绝 ↗](../../../apps/server/src/review/sync.ts#L427 "证明已经进入捕获阶段的目标会检查链接或越界，并把拒绝原因记入逐文件失败结果。") 这限定并替代了此前“扫描阶段跳过的所有链接都不会形成失败记录”的过宽结论。

候选先按路径归类；`architecture` 类采用测试边界或代码声明边界，其余类别采用 Markdown 标题边界。[内容类别判定 ↗](../../../apps/server/src/review/sync.ts#L126 "说明应用、包、脚本及特定文档如何被归入架构或其他类别，为分片选择提供前置依据。")[按类别选择分片器 ↗](../../../apps/server/src/review/sync.ts#L468 "直接支持架构类采用测试或代码边界、其他类别采用 Markdown 标题边界的实际分支。") 所以分片策略取决于类别而非单看扩展名，架构类 Markdown 文件也不保证按标题切分。

## 固定身份、快照与增量基线

每个文件以 `omem:<仓库相对路径>` 作为稳定 source 身份，内容摘要只用于判断当前 head 是否已经捕获相同文本。新 revision 保存类别、路径、摘要、同步时间及调用方提供的快照；决策日期只从正文中的显式日期提取。[不可变修订捕获上下文 ↗](../../../apps/server/src/review/sync.ts#L460 "支持稳定路径身份、内容摘要去重、快照字段、同步时间及显式决策日期的捕获流程。")

完整同步查询 Git HEAD、工作区状态与基线，合并已提交和未提交变化；Git 失败、基线无效、数据库身份变化或上次同步为 dirty 时会扩大到全量扫描。[完整同步的 Git 增量决策 ↗](../../../apps/server/src/review/sync.ts#L881 "支持完整同步读取 HEAD、dirty 状态和基线，并在不同异常或历史状态下选择全量或增量目标。") `only` 模式则不查询 Git、不读写同步基线，其 revision 快照保持 `commit=null`、`dirty=false`。完整同步遇到 dirty 工作区或文件捕获失败时不推进基线；关系构建失败目前只形成 warning，并不属于该阻止条件。[定向模式、关系重建与基线推进 ↗](../../../apps/server/src/review/sync.ts#L997 "证明 only 模式与完整同步的差异、关系异常仅进入 warning，以及基线阻止条件只覆盖 dirty 和文件失败。")

<a id="relations"></a>
## 人工关系种子与重建限制

关系仅由人工维护的 association seed 生成，不通过语义相似度自动确认。同步为每条 seed 建立派生意图 fragment，再从当前 head 定位代码符号、需求、决策、研究与测试，写入相应关系；无法解析的端点保留为 `missing`。[人工种子关系构建 ↗](../../../apps/server/src/review/sync.ts#L699 "支持从人工 seed 建立派生意图索引、解析当前 head 端点并写入确认、候选或 missing 关系的流程。")

关系重建只在完整同步后执行，失败不会回滚已经完成的文件捕获。[定向模式、关系重建与基线推进 ↗](../../../apps/server/src/review/sync.ts#L997 "证明 only 模式与完整同步的差异、关系异常仅进入 warning，以及基线阻止条件只覆盖 dirty 和文件失败。") 删除 seed 后会调用失效处理，但当有效 association 集合为空时该处理直接返回；因此从最后一条 seed 删除到零条时，历史关系可能继续保持原状态，“空清单必然使全部旧关系 stale”的结论尚不成立。[空种子集合的失效边界 ↗](../../../apps/server/src/review/store.ts#L485 "证明有效 association 集合为空时失效函数直接返回，支持旧关系可能未被标为 stale 的限制。")
