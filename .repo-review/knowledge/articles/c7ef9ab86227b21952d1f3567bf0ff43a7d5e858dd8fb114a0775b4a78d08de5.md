# 一次提问如何找到答案：搜索、上下文与 RAG

以“飞书 消息 后台”为贯穿示例，说明顶部搜索、知识搜索和助手如何共享来源召回，又分别返回原始片段、文章章节和带引用的回答；同时给出区分召回失败、排序不佳、背景不足与模型回答失败的观察方法。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先判断是“没找到”还是“没答好”

假设用户只记得一条飞书消息会经过后台处理，却忘了实现名称，先输入“飞书 消息 后台”，再追问“具体怎么处理”。一次完整链路可以概括为：

```mermaid
flowchart LR
  Q[中文问题] --> R[来源召回]
  R --> F[融合与排序]
  F --> C[补充章节背景]
  C --> A[模型回答]
  A --> S[必要时再搜索一轮]
  S --> E[保存答案与有效引用]
```

顶部搜索、知识搜索和助手由同一个检索实例提供来源候选；助手在此基础上补背景并生成回答。参考 [统一检索装配 ↗](../../../apps/server/src/app.ts#L80 "支持顶部知识路由与助手运行时共享同一检索实例的主链说明。")

排障时先划清边界：如果相关原始片段没有进入候选或助手证据集，应检查分词、召回路线、索引、可见范围和排序，这是**召回问题**；如果关键片段已经交给模型，答案仍遗漏处理步骤、误解来源或没有留下有效引用，则是**回答或上下文问题**。

<a id="entrypoints"></a>
## 三个入口共享召回，但展示不同层级

顶部搜索直接调用统一来源检索，展示命中片段的摘要、标题、版本、召回路线和所属章节，适合确认“系统究竟找到了什么”。参考 [顶部搜索结果 ↗](../../../apps/server/src/app.ts#L273 "说明顶部搜索调用统一来源检索并返回摘要、路线和章节。")

知识搜索也调用相同的来源检索，但不会直接列出所有 fragment。它把原始片段的排名传播给引用这些片段的当前文章章节，再叠加文章标题、章节标题与正文的词面覆盖率；每篇文章最终只保留得分最高的章节。选择分类时，来源范围还会收窄到该分类文章固定依赖的材料。参考 [知识章节搜索 ↗](../../../apps/server/src/knowledge/api.ts#L97 "支持知识搜索的分类范围、来源排名传播、文章词面得分及每篇最佳章节规则。")

因此，“知识页没有匹配文章”不等于原始材料不存在：也可能是材料尚未被当前文章引用、文章不在所选分类，或文章文字与问题缺少直接覆盖。助手则继续读取候选原文、补充邻近片段，再把证据交给模型；三者共享召回内核，并不保证结果形态和数量相同。

<a id="lexical"></a>
## 中文短词、全文与代码符号怎样配合

查询先按空白和标点切开。中文连续文本既保留完整词，也会产生过滤常见停用词后的重叠二元组，使短追问仍有机会命中原文。参考 [中文查询分词 ↗](../../../apps/server/src/retrieval/keyword.ts#L210 "说明中文连续文本、二元组和停用词过滤如何形成可匹配查询词。")

以“飞书 消息 后台”为例，三个词都是二字词。当前 FTS5 trigram 不能直接匹配二字中文，因此它们走标题或正文的短关键词匹配；三字及以上中文词、较长短语和路径子串才进入全文 MATCH。参考 [短词与全文匹配 ↗](../../../apps/server/src/retrieval/keyword.ts#L53 "支持二字中文走短关键词、长词走 FTS5 trigram 的流程解释。")

如果问题中出现 `CircuitBreaker`、类名、函数名或限定名，AST 符号投影会精确匹配名称，但命中仍指回原始 fragment，并不会建立第二套代码事实库。参考 [代码符号召回 ↗](../../../apps/server/src/retrieval/keyword.ts#L123 "说明 AST 符号投影精确匹配名称并继续返回原始证据。")

词法候选来自 `code-symbol`、`fulltext`、`short-keyword`、`memory` 和 `knowledge` 五条路线。系统用倒数排名融合各路线，同一 fragment 在单条路线只贡献一次，从而不必直接比较 BM25、短词计数和派生文字分数。参考 [多路线融合 ↗](../../../apps/server/src/retrieval/keyword.ts#L97 "支持五条词法路线及倒数排名融合的规则。")

<a id="semantic"></a>
## 记忆、知识与向量分别补什么缺口

| 能力 | 主要作用 | 不应误解为 |
| --- | --- | --- |
| 记忆召回 | 用已整理的记忆文字找到其证据集 | 把记忆当成另一份独立事实 |
| 知识召回 | 用文章解释导航到引用覆盖的原始片段 | 直接以派生文章替代原文 |
| 中文向量 | 补充词面不同但语义相近的问题 | 保证所有相关结果都排在前面 |

活跃记忆命中后会沿 evidence set 回到原始 fragment；记忆正文只负责导航。参考 [记忆回到原始证据 ↗](../../../apps/server/src/retrieval/keyword.ts#L81 "说明记忆只承担导航作用，命中后沿证据集返回原始 fragment。") 知识文章也会先校验固定依赖，再递归沿文章引用定位原始材料，并限制递归深度和候选数量。参考 [知识引用回溯 ↗](../../../apps/server/src/knowledge/retrieval.ts#L35 "支持知识文章校验固定依赖并沿引用递归映射到原始片段的说明。")

启用中文向量后，系统先取词法候选，再对已经完成索引的重叠窗口计算余弦相似度，并以倒数排名融合词法与语义两支。长 fragment 使用 400 字窗口、320 字步长，语义命中可以保留窗口中的实际片段，而不是只显示长文开头。模型未就绪或推理报错时仍退回词法结果。参考 [语义窗口与词法降级 ↗](../../../apps/server/src/retrieval/semantic.ts#L81 "说明词法与向量融合、窗口摘要、时间和可见性过滤，以及模型未就绪或推理错误时返回词法结果。")

当前模型从 osdk 管理的固定 BGE-small-zh-v1.5 快照加载，校验文件哈希并禁止远程模型；查询会添加中文检索指令。参考 [本地中文向量模型 ↗](../../../apps/server/src/retrieval/embedding.ts#L17 "支持固定模型快照、哈希校验、禁止远程加载和中文查询指令的说明。")

<a id="ranking_context"></a>
## 融合之后怎样排序并补背景

当前没有独立的学习式 reranker。融合候选会经过轻量 MMR：相关性占 85%，冗余惩罚占 15%；代码符号路线获得额外权重。相同摘要、同一来源或向量相近的候选可能后移，但原始 fragment 身份、可见性和来源不会被改写。参考 [MMR 多样化排序 ↗](../../../apps/server/src/retrieval/ranking.ts#L3 "说明当前重排是相关性与冗余惩罚结合的轻量排序，并保留原始身份。")

命中一个 fragment 后，助手不会无限扩展全文，而是在它所属章节内补充标题片段、前一个片段和后一个片段，并再次检查可见性。章节标题本身也被视为内容，只有材料满足可见条件时才会暴露。参考 [章节邻居补充 ↗](../../../apps/server/src/retrieval/context.ts#L5 "支持命中后仅补同章节标题和相邻片段，并执行可见性检查。")

这种局部补充适合恢复小节标题和相邻解释，却不保证自动拼出跨文件调用链、完整设计背景或历史演变。诊断“结果看似相关但信息不够”时，应区分是目标实现排名太低，还是目标 fragment 已命中但所需背景位于其他章节或模块。

<a id="assistant"></a>
## 助手如何追问、补搜和保存引用

助手先读取同一会话最近的已完成轮次，用用户原文检索，并合并上一轮工作上下文。因此第二句“具体怎么处理”可以继续利用上一问证据，而不会借用其他会话的历史。模型第一次收到用户问题、会话历史、服务器准备的证据以及 `retrievalRound: 0`。参考 [会话历史与一轮补搜 ↗](../../../apps/server/src/assistant/runtime.ts#L465 "说明助手合并同会话上下文、首次生成、查询词限制和第二轮生成流程。")

模型可以提出最多三个去重并截断的查询词。例如第一次只找到飞书接入说明时，可以进一步请求某个处理器或符号名。运行时执行这些查询，把新增证据与原证据按 fragment 去重、限制数量，再以 `retrievalRound: 1` 调用模型一次；第二次回复不会继续递归补搜。参考 [会话历史与一轮补搜 ↗](../../../apps/server/src/assistant/runtime.ts#L465 "说明助手合并同会话上下文、首次生成、查询词限制和第二轮生成流程。")

每次来源召回后，助手保留排序命中，在证据预算允许时加入同章节邻居；语义路线命中长 fragment 尾部时，会保留实际命中窗口。参考 [助手证据构造 ↗](../../../apps/server/src/assistant/runtime.ts#L665 "支持助手保留排序命中、语义窗口和同章节邻居的证据构造过程。") 最终只有模型所报 citation ID 与运行时真实提供的 fragment 相交后，才会保存为引用和 selected evidence。参考 [引用有效性校验 ↗](../../../apps/server/src/assistant/runtime.ts#L604 "说明最终只保存模型引用与实际提供证据的交集。")

这形成了清晰观测点：补搜前后都没有关键 fragment，是检索没有给够材料；selected evidence 已含关键 fragment，但答案仍错误或残缺，则应检查模型理解、局部上下文是否足够以及第二轮查询是否有效。

<a id="limits"></a>
## 当前限制与实际排障顺序

建议按以下顺序检查同一个问题：

1. 在顶部搜索查看标题、摘要、`routes`、章节和排序；“飞书 消息 后台”应重点观察 `short-keyword`，但没有实际返回记录时不能断言它必然命中某个文件。
2. 若目标不在结果中，检查词面是否过短、是否应使用代码符号、语义索引是否仍在追赶，以及可见性或知识分类是否缩小了范围。
3. 若目标出现但靠后，检查 RRF 后的位置和 MMR 的同源冗余影响。现有真实验收曾出现长代码片段的目标实现首次排到第 14 位，说明小规模中文检查通过并不代表整个库排序可靠。参考 [真实排序限制 ↗](../../../docs/reader-first/validation.md#L17 "支持小规模中文检查的适用边界及目标实现排名靠后的实际问题。")
4. 在助手中追问处理过程，观察是否发生一次补搜，以及最终 selected evidence 是否含关键片段；有证据却答不好时，不应继续把问题归咎于召回。

时间过滤比较的是捕获 revision 的创建时间，不是飞书消息的业务事件时间，也不是“当时系统知道什么”的历史 as-of 推理。项目范围也只有在项目关系经过确认时才能收窄，否则应保持工作区级召回。参考 [时间与项目范围合同 ↗](../../../apps/server/src/retrieval/port.ts#L17 "说明时间范围是捕获时间，且项目过滤必须依赖可信项目关系。")

本地中文向量模型缺失时，应用仍保留全文检索并报告状态，而且不会在运行时隐式下载模型。参考 [模型缺失时的降级 ↗](../../../docs/reader-first/operations.md#L11 "直接支持应用不隐式下载中文向量模型，缺少模型时保留全文检索并报告状态。") 专用 reranker、稳定的跨模块背景补齐、事件时间检索和历史 as-of 能力都不能当作当前已具备功能。参考 [检索能力边界 ↗](../../../docs/reader-first/architecture.md#L19 "支持历史 as-of、事件时间检索和待验证新重排器等当前能力边界。")
