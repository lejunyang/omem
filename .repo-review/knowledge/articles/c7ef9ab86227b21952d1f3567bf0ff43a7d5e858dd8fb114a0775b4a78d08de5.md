# 一次提问如何找到答案：搜索、上下文与 RAG

沿“这次活动要准备多少钱、到哪里集合？”这一教学问题，解释整句提问如何形成全文与向量候选，候选如何在固定版本中恢复完整章节与上级条件，以及 Agent 如何只针对未解的金额、地点或活动身份继续调查。最后用召回、原文或选材、补读装配、调查、回答五类问题定位遗漏，并区分已验证的修复、输入压缩与尚不能外推的效果结论。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="example"></a>
## 先明确什么才算回答了问题

一次可用回答不是“找到一段相关文字”，而是让**用户要的每个结果和会改变结果的条件**都有合适原文支持，并把它们逐项写进答案。搜索只负责提供入口；原文是否真的包含关键前提、命中后的语境是否完整、未解部分是否继续调查，仍要分别检查。

下面是全文共用的**教学示例**，只用于解释机制，不代表一次真实运行、真实活动或固定排名：

| 已保存的材料 | 内容 |
| --- | --- |
| 当前活动说明的“费用”章 | 参加预算八十元；仅限已报名者；不含交通费；周三 18 点前确认 |
| 同一说明的“集合”章 | 在图书馆集合 |
| 旧活动记录 | 也出现“八十元” |
| 主题介绍 | 讨论活动内容，但没有金额、集合点或适用条件 |

用户问：“这次活动要准备多少钱、到哪里集合？”

可用答案至少要覆盖**金额**与**集合点**，并保留会改变行动或适用范围的条件。例如：

> 若这份当前活动说明确实对应你说的这次活动，并且你已经报名，预算为八十元，不含交通费，需在周三 18 点前确认；集合点是图书馆。

金额、报名资格、费用范围、截止时间和集合点应分别贴近对应原件引用。如果材料不能把“这次”唯一绑定到某个活动或版本，就应把活动身份或日期标为未知，而不是按相似度、捕获时间或“看起来更新”替用户决定。当前设计把语义遗漏概括为：必要条件没有找到、命中后没有读到上下文、读到后没有写进结论；相关材料和合法引用本身都不能发现这些缺口。参考 [语义遗漏与可用答案 ↗](../../../docs/reader-first/answer-investigation.md#L5 "说明必要条件可能在召回、补读或写入答案时遗漏，相关材料和合法引用不等于可用回答。")

还要多问一步：**现有原文或人工选择的范围是否真的写了必要前提？** 如果活动说明只写“八十元”，却没有说明是否含交通费，系统不能靠扩大同一段、提高排名或润色答案补出这个条件；应继续寻找别的章节或文件，仍找不到就明确未知。于是坏答案可分为五类：

1. 金额或地点没有进入任何候选：**召回遗漏**。
2. 候选或人工指定的原文本身没有关键前提：**原文或选材缺口**。
3. 原文中有报名、交通或截止条件，但没有随命中进入阅读材料：**补读装配遗漏**。
4. 地点在兄弟章，首轮没中，Agent 也没有围绕未解部分继续找：**调查遗漏**。
5. 金额、地点和条件都已读到，最终仍漏写或把旧记录当成当前安排：**回答遗漏**。

## 整句问题怎样变成候选

材料保存后不总是以整文件参加排序。Markdown 会按块形成检索段，保留真实行号和章节路径；表格、列表或代码块若由上一段的冒号引出，会与引导段保持在一起。这样，“参加预算八十元”和“图书馆集合”可以分别成为可排序线索，又不会留下一个无法独立回答问题的引导句。参考 [Markdown 检索段 ↗](../../../apps/server/src/retrieval/units.ts#L33 "支持按块形成检索段、记录章节路径，并将由冒号引出的表格、列表和代码与引导段保持完整。")

**全文路线**先把查询拆成词，再用 FTS5/BM25 找原文中直接出现的内容。中文查询使用 ICU 分词、过滤常见停用词，并为 2～8 个汉字的短查询保留完整词形；案例里的“八十元”“图书馆”“集合”等字面信息适合走这条路线。参考 [中文查询词 ↗](../../../apps/server/src/retrieval/relevance.ts#L1 "支持 ICU 中文分词、停用词过滤和短汉字查询的完整词形保留。") [BM25 全文候选 ↗](../../../apps/server/src/retrieval/unified.ts#L427 "支持用查询词构造 FTS5 OR 查询，以 BM25 排序并在可见性与范围条件后形成候选池。")

**向量路线**在 embedding 可用时比较问题与检索窗口的语义接近程度，所以“准备多少钱”也可能找到写着“参加预算”的段落。模型不存在、查询是精确标识符或向量执行失败时，搜索仍可退回全文与符号候选。全文、向量和符号分支的原始分数尺度不同，当前实现用 RRF 按各分支名次融合。参考 [向量召回与回退 ↗](../../../apps/server/src/retrieval/unified.ts#L480 "支持 embedding 语义候选，以及模型缺失、精确查询或向量失败时回退全文和符号候选。") [RRF 名次融合 ↗](../../../apps/server/src/retrieval/unified.ts#L408 "支持全文、向量和符号路线按各自名次计算 RRF，避免直接比较不同分数尺度。")

融合后的结果还会根据查询用途、代码定义、知识文章复核状态和材料适用性调整最终优先级。材料 role/status 同时参与候选适用性计算，但它们只是导航偏好，不是真伪裁决；有效时间也只有调用方显式提供时才用于过滤。参考 [用途与结果优先级 ↗](../../../apps/server/src/retrieval/unified.ts#L606 "支持融合结果按查询用途、代码定义、文章复核状态和材料适用性调整最终优先级。") [材料过滤与适用性 ↗](../../../apps/server/src/retrieval/unified.ts#L231 "支持 effectiveAt 显式过滤和材料 role/status 适用性计算，并明确这些状态是导航偏好而非真伪裁决。")

这些结果仍只是“值得读的线索”。主题介绍可能因词面或语义接近而进入清单，但它没有金额、地点或适用条件，不能支持答案。

普通助手首轮把**整句**用户问题交给共享搜索，取 48 条候选并设置 `diversify=false`，再装配最多 16 个不同阅读上下文。这里关闭的是浏览界面的来源或章节分组限制，不是自动保证“金额”和“地点”都被覆盖；界面搜索仍可为浏览体验去重，因此页面显示条数也不等于助手可读条数。参考 [助手首轮整句召回 ↗](../../../apps/server/src/assistant/runtime.ts#L940 "支持普通助手将整句问题交给搜索、取 48 条且关闭浏览去重，再装配回答上下文。") [diversify 合同 ↗](../../../apps/server/src/retrieval/port.ts#L96 "说明 diversify=false 关闭浏览分组限制，但仍保留排序、范围和可见性过滤。")

当前候选总数有限，没有“答案要点全部出现才算召回完成”的确定性选择算法。首轮也不会先把整句自动规划为金额和集合点；相关性分数提高找到材料的机会，却不等于材料已经回答问题。参考 [候选与上下文边界 ↗](../../../docs/reader-first/retrieval-redesign.md#L19 "说明候选数量有限、没有答案要点覆盖算法，分问题工具也不判断问题是否已经回答。")

<a id="context"></a>
## 命中预算后怎样补回条件

假设全文或向量先命中“参加预算八十元”。回答阶段不会只把这一小段交给模型。

对原件命中，系统只在**同一固定 revision** 内恢复所属的最小完整 Markdown 章节或代码结构。没有可靠结构时保留原命中，不默认附上整份文件；扩展范围中的所有片段必须通过可见性检查，否则退回原命中。参考 [同版完整范围与 H1 边界 ↗](../../../apps/server/src/retrieval/context.ts#L13 "支持固定版本内的结构展开、唯一外层 H1 导言边界和扩展范围可见性检查。")

这里有一个重要边界：若文档根下只有一个最外层 H1，它被视为文档标题。命中 H1 后、第一个子章节前的导言时，只恢复“标题到第一个子章节之前”，不会因为导言命中就附上整本手册。普通章节仍包含自己的子章节，所以命中预算章时，其下的报销条件仍可进入语境。回归测试同时验证了导言范围、预算包含报销子节，以及预算不越界进入后续集合章。参考 [同版完整范围与 H1 边界 ↗](../../../apps/server/src/retrieval/context.ts#L13 "支持固定版本内的结构展开、唯一外层 H1 导言边界和扩展范围可见性检查。") [层级范围回归测试 ↗](../../../apps/server/tests/retrieval-hierarchy.test.ts#L55 "验证 H1 导言只恢复 1 至 4 行，预算章包含报销子节且不进入后续集合章。")

系统还会沿父链读取各级章节在第一个子节之前的真实引言，并把每段作为独立固定范围加入。例如，“仅限已报名者”若写在费用子节的上级引言中，可以随费用章进入阅读材料。这个规则不会自动拼接兄弟章节，所以另一章的“图书馆集合”仍需要自己的候选，或由后续调查单独补查。参考 [父章节引言独立补入 ↗](../../../apps/server/src/retrieval/context.ts#L64 "支持沿父链补入各级首个子节前的真实说明，同时不自动附加兄弟章节。")

回答上下文以恢复后的 revision 和行范围选择阅读入口。知识文章命中会读取同一固定文章版本的完整相关节，并合并该节实际使用的原件引用；默认限制的是不同阅读上下文数量，而不是把已选章节再次截成零散段落。换句话说，**细段用于排序，固定完整章节用于理解**。参考 [知识文章整节恢复 ↗](../../../apps/server/src/assistant/context.ts#L10 "支持从同一固定文章版本恢复命中的完整相关节，并合并该节实际使用的原件引用。") [回答上下文装配 ↗](../../../apps/server/src/assistant/context.ts#L74 "支持原件范围展开、知识文章恢复调用、可见性检查和最多 16 个不同阅读上下文。")

装配完成后还有一次包含去重：若一个已准许的原文范围被同一 revision 的更大范围完整包含，只保留覆盖范围，并把派生背景的 citationIds 重映射到该固定引用。不同 revision 不会互相吞并，也不会把部分重叠或不相交的范围拼成原文不存在的新范围。测试验证旧版八十元与当前版一百二十元仍各自保留，旧背景引用继续指向旧版。参考 [同版包含范围去重 ↗](../../../apps/server/src/assistant/context.ts#L170 "支持保留同版覆盖范围、重映射背景引用，同时不合并不同 revision 或制造更宽原文。") [不同版本保持独立 ↗](../../../apps/server/tests/retrieval-hierarchy.test.ts#L149 "验证同版重复父引言和报销范围只出现一次，而旧版八十元、当前版一百二十元及旧背景引用保持独立。")

结构展开和去重能补回同章条件、减少同版重复，但不能发现任意兄弟章、其他文件或原文根本没写的前提，也不会证明答案要点已完整。完整章节还可能增加无关文字和阅读成本。参考 [候选与上下文边界 ↗](../../../docs/reader-first/retrieval-redesign.md#L19 "说明候选数量有限、没有答案要点覆盖算法，分问题工具也不判断问题是否已经回答。")

<a id="investigation"></a>
## 按未解部分继续查，并辨认旧记录

首轮整句召回之后，Agent 才主动把复合问题拆成具体调查部分。当前助手约定：用户同时问多个结果、比较多种情况，或缺少会改变结论的前提时，可以用 `search_contexts`；简单查值不强拆，同义关键词也不能冒充多个子问题。搜索只围绕未解缺口，优先读取完整章节、外围条件和真实入口。参考 [围绕未解问题调查 ↗](../../../packages/agent-runtime/roles/daily-assistant/1/skills/omem-assistant-research/SKILL.md#L12 "说明多结果、比较或关键前提缺失时按具体问题检索，简单查询不强拆且只补未解缺口。")

在教学案例中，一个合适的**建议性调查策略**是维护三个槽位：

1. **金额与费用条件**：预算、报名资格、是否含交通、确认截止时间。
2. **集合点**：地点以及它对应哪个活动。
3. **“这次”的身份**：活动名称、日期或版本关系。

这是 Agent 使用现有工具的策略，不是检索器内置规划。若费用槽位已经有完整语境、集合点仍为空，就围绕材料中的真实术语补搜集合地点，不必反复搜索费用。

`search_contexts` 为每个具体问题建立独立候选池，每池最多取 50 个搜索候选且使用 `diversify=false`；每题可以分别指定用途、代码意图、材料角色、有效时间、类型、材料键和项目或主题范围。原件命中会恢复同版焦点章节与父级引言，知识命中返回固定文章版本的完整节。相同固定上下文在全局 `contexts` 中只返回一次，每个问题通过自己的 `matches[{contextId, rank}]` 保留对应关系和原搜索名次，直到达到该题的上下文上限。空组只表示搜索缺口，不证明事实不存在。参考 [分问题检索与共享上下文 ↗](../../../apps/server/src/knowledge/agent-research.ts#L661 "支持每题独立搜索和范围、固定上下文全局共享、contextId 与题内 rank 映射，以及空组只表示搜索缺口。") 当前测试也验证：两个费用问题可以共享同一个 contextId，费用语境包含上级报名条件和“不含交通费”，集合点另有上下文，调查快照不会混入之后捕获的新版本；无法解析的材料键会直接报错，而不会静默扩大到全库。参考 [分问题上下文测试 ↗](../../../apps/server/tests/agent-research.test.ts#L13 "验证两个费用问题共享上下文、费用保留上级条件与费用范围、集合另有上下文、封存快照不混入新版，且无效键不会放宽范围。")

若用户或会话已明确“这次活动”属于哪个已保存项目或主题，Agent 可以先查看目录和少量成员，再把金额、集合点等每个子问题限制到该冻结 `groupId`。多个组取并集；同时给出材料键时取交集；空组不会选中任何材料，未知组会报错。这样能减少同名活动互相混入，测试也验证了杭州和上海两个同名活动可分别检索，调查开始后的归属变化和新增消息不会进入这次快照。参考 [项目范围与边界 ↗](../../../docs/reader-first/project-contexts.md#L23 "说明项目目录和 groupIds 的冻结范围、并集与交集语义，以及归属不等于有效性、首轮不按项目过滤且不会自动判断归属。") [同名项目范围测试 ↗](../../../apps/server/tests/project-research.test.ts#L12 "验证同名杭州与上海活动按组分开、成员关系冻结、未归组与后续新增材料不混入，以及空组和未知组的严格行为。")

但**归属只限定去哪里找，不裁决哪条记录有效**。目录只列本次获准原件涉及的组，缺席不证明项目不存在；首轮全库召回和网页搜索目前也不按项目过滤，调用方不会自动把对话绑定到某个项目，系统更不会按内容相似度自动认领未归组材料。即使旧记录与当前说明同组，仍要读正文判断替代关系。参考 [项目范围与边界 ↗](../../../docs/reader-first/project-contexts.md#L23 "说明项目目录和 groupIds 的冻结范围、并集与交集语义，以及归属不等于有效性、首轮不按项目过滤且不会自动判断归属。")

如果问题包含连续操作，还要核对**状态衔接**：前一步完成后，后一步是否已具备条件，还是仍需触发、等待、重启或处理既有状态。两种能力分别存在，不代表它们会自动衔接。活动案例中也不能因为材料分别写了“已报名者可参加”和“周三前确认”，就悄悄假定用户已报名、已确认；不清楚时应用条件分支表达。参考 [状态衔接与复核条件 ↗](../../../packages/agent-runtime/roles/daily-assistant/1/skills/omem-assistant-research/SKILL.md#L28 "要求给步骤前验证前后状态是否真正衔接，并只在仍有会改变结论的重要推断时启动独立复核。")

旧活动记录也出现“八十元”时，应核对：

- 正文中的活动名称、日期、适用对象和版本关系；
- 该版本材料说明中的 role、status、scope、validFrom/validUntil；
- 同一来源的历史版本身份。

`effectiveAt` 只有调用方显式提供时才按有效期过滤；role/status 默认只是排序先验。历史工具按同一 sourceId 列出版本，指定 revision 时返回那一版自己的正文和行数，因此旧事实必须保持旧 revision 身份，不能绑定到当前正文。参考 [材料过滤与适用性 ↗](../../../apps/server/src/retrieval/unified.ts#L231 "支持 effectiveAt 显式过滤和材料 role/status 适用性计算，并明确这些状态是导航偏好而非真伪裁决。") [历史版本独立身份 ↗](../../../apps/server/src/knowledge/agent-research.ts#L1005 "支持按同一来源列出版本，并在指定 revision 时返回该版正文、行数和 current 标志。")

若名称、时间和版本关系仍无法消歧，当前**未知项**就是活动身份或日期。此时应并列说明候选差异，问一个最小澄清问题，或写成“若你指的是 X 当前说明，则……”；不能凭排名、捕获先后、同组关系或 historical 标签断言旧记录错误。

## 组织答案，并按遗漏所在层修改

最后一步是把已确认的金额、报名资格、费用范围、截止时间和集合点逐项写入答案，让引用贴近它所支持的句子。提交门禁会校验材料是否在本次授权范围、历史 revision 是否同源、固定范围是否可见，以及正文引用是否有原文定位。它保证“引用来自哪里”，不保证“问题已经答全”。参考 [固定原件引用校验 ↗](../../../apps/server/src/assistant/research.ts#L105 "支持校验授权材料、同源历史版本、可见性、行范围和正文引用定位。")

复杂机制、资料冲突或仍有会改变结论的重要推断时，可以交给同一固定快照上的独立答案复核；简单的原文直接查值不必因为引用多、涉及代码或答案带条件就启动复核。一旦启动，复核运行中、意见未读取，或发现实质问题却原样提交时，运行时会阻止结束。复核仍是辅助门禁，不是完整性证明。参考 [独立答案复核 ↗](../../../apps/server/src/assistant/answer-review.ts#L107 "说明复核使用同一快照，可用于复杂解释或重要推断，简单直接查值无需启动。") [复核提交门禁 ↗](../../../apps/server/src/assistant/answer-review.ts#L204 "支持在复核运行、意见未读取或发现实质问题但答案未修改时阻止提交。") [状态衔接与复核条件 ↗](../../../packages/agent-runtime/roles/daily-assistant/1/skills/omem-assistant-research/SKILL.md#L28 "要求给步骤前验证前后状态是否真正衔接，并只在仍有会改变结论的重要推断时启动独立复核。")

发现坏答案时，应保留同一次问题的**首轮候选、人工或自动选择的原文范围、展开后的完整上下文、分问题调查结果和最终答案**，再判断修改哪一层：

| 观察 | 问题层 | 首要修改入口 |
| --- | --- | --- |
| 金额或地点没进任何候选 | 召回 | `retrieval/units.ts`（检索段）、`retrieval/relevance.ts`（查询词）、`retrieval/unified.ts`（全文、向量与融合） |
| 候选或人工指定范围本身没写关键前提 | 原文或选材 | 补另一章或文件、修正文档，或把条件明确标为未知；不能只调排名 |
| 原文中有条件，但完整章、父引言、可见范围或同版引用没正确交付 | 补读装配 | `retrieval/context.ts`（焦点章、H1 边界、父引言）、`assistant/context.ts`（选择、去重与引用重映射） |
| 地点在兄弟章或条件跨文件，Agent 没围绕未解部分继续查；或把两个步骤误认为自动衔接 | 调查 | daily-assistant 调查技能、`assistant/reading-stage.ts`、`knowledge/agent-research.ts` 的 `search_contexts` |
| 所需事实都进入材料，答案仍漏项、混淆旧版、偏题或追加未问内容 | 回答与复核 | `assistant/research.ts`（提交引用）、`assistant/answer-review.ts`（独立复核） |

实际对照说明了为什么这些层必须分开。2026-10-05 的两题四组冻结库实验中，第二题的指定原文组最终漏写“改配置后必须重启”，而实际召回组在独立复核后补上；这是回答与调查结果的差异。与此同时，所选运行说明本身没有讲清“启动时已启用但缺模型”和“现在才修改配置启用”两种状态，这是原文或选材边界。参考 [对照、重放与输入整理的边界 ↗](../../../docs/reader-first/answer-investigation.md#L65 "区分回答漏项、所选原文缺口、后续重放和输入字符减少，并说明这些结果不能支持单一指令因果或普遍速度与质量结论。")

修正调查约定后，又用仍缺重启说明的旧版运行说明重放：Agent 主动补读配置入口、检索工厂和后台加载，约 125 秒完成，正确区分了“安装后等待重试”与“从关闭改为启用后重启”，且没有调用独立复核。这能说明**已知遗漏在这次重放中被补齐**；但输入库里的其他指南版本已经变化，答案仍偏长并追加未问命令，所以不能把结果归因于单一指令，也不能外推成普遍质量或速度提升。参考 [对照、重放与输入整理的边界 ↗](../../../docs/reader-first/answer-investigation.md#L65 "区分回答漏项、所选原文缺口、后续重放和输入字符减少，并说明这些结果不能支持单一指令因果或普遍速度与质量结论。")

同一批实际候选经过根 H1 边界修正与同版包含去重后，两题原文分别从 41,554 和 39,616 字符降为 35,232 和 34,789 字符，已有背景引用仍能解析。这只证明**输入范围减少且引用保持可用**：候选没有重排，无关材料仍在，也没有测出完整问答的速度或质量收益。参考 [对照、重放与输入整理的边界 ↗](../../../docs/reader-first/answer-investigation.md#L65 "区分回答漏项、所选原文缺口、后续重放和输入字符减少，并说明这些结果不能支持单一指令因果或普遍速度与质量结论。")

因此，工具调用、引用通过和复核完成都不能证明模型已经理解并采用条件。修改后应回到同一个真实问题，依次确认：必要事实是否进入候选，所选原文是否真的包含前提，固定语境是否正确交付，未解部分是否继续调查，最终答案是否逐项回应用户。
