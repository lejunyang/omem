# 一次提问如何找到答案：搜索、上下文与 RAG

用一条群消息的教学示例说明：顶部搜索、知识搜索和助手如何共用统一召回，又如何分别承担找命中、读讲解和补查回答；同时解释中文全文、短词、符号、向量、知识与记忆的分工，以及固定引用、当前限制和分层排障入口。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="journey"></a>
## 先看一条实际阅读路线

假设群里出现一条普通消息：“报销以后用新模板，旧表不用了。”过几天，用户只记得大意，于是在顶部搜索“群里提过的报销新模板”。这是**教学示意**，用于串起流程，不承诺这句话一定排在第一名。

~~~mermaid
flowchart LR
  A[普通群消息] --> B[保存为固定原件]
  B --> C[投影为会话检索单位]
  C --> D[顶部搜索看实际命中]
  D --> E[知识页先读整体讲解]
  E --> F[展开原文或完整方法]
  F --> G[助手按缺口继续补查]
~~~

被监控的普通群消息会以聊天来源保存文本或图片、会话、发言人、事件时间和回复关系；但绑定用户在群里 @ 机器人时会先走助手分支并直接返回，不应把同一事件描述成“既提问又采集”。参考 [普通群消息采集 ↗](../../../apps/server/src/integrations/lark/realtime.ts#L602 "支持普通群消息在启用监控后以聊天来源保存文本、会话、发言人与事件时间的场景说明。") [群内助手分支 ↗](../../../apps/server/src/integrations/lark/realtime.ts#L524 "支持绑定用户私聊或在群里提及机器人时先进入助手分支并返回，不继续普通群采集。")

这里的 **RAG** 可以先理解为“先找材料，再让模型依据材料回答”。保存的原件、用于搜索的结构片段、面向读者的讲解是三种不同单位；讲解能帮助理解和导航，但事实引用仍回到固定原文。参考 [保存、检索与讲解分层 ↗](../../../docs/reader-first/architecture.md#L5 "解释原件、结构检索单位和读者页面分工，以及派生内容不成为独立事实。")

<a id="entrances"></a>
## 三个入口，一套召回基础

服务端只创建一套统一检索实例，并把它交给顶部搜索、知识路由和助手。因此三者共享全文、向量、符号及最终排序基础，但**不会返回完全相同的结果**。参考 [共享检索实例装配 ↗](../../../apps/server/src/app.ts#L93 "支持知识路由与助手复用同一个 assistantRetrieval 实例。")

| 入口 | 主要用途 | 关键范围 |
| --- | --- | --- |
| 顶部搜索 | 先看系统实际找到了什么 | 默认 balanced，可跨原件、知识、记忆和事项，并可显式选用途、材料角色或有效时间 |
| 知识搜索 | 先读围绕问题组织的整体讲解 | 默认 concept，只查当前分类范围内的 knowledge，并让一篇文章只占一个最佳章节 |
| 助手 | 把命中组织成回答，缺什么再查什么 | 初始检索受会话可见性约束；原件成为证据，知识、记忆和事项可作为背景 |

顶部 /api/search 把用途与筛选条件传给同一检索端口；知识搜索则显式限定知识类型与分类路径。参考 [顶部搜索入口 ↗](../../../apps/server/src/app.ts#L313 "支持顶部搜索将 balanced 等用途、材料角色和有效时间传给统一检索。") [知识搜索范围 ↗](../../../apps/server/src/knowledge/api.ts#L118 "支持知识搜索限定 knowledge、topicPath，并按文章只返回最佳相关章节。") 搜索页还把“查看实际命中”和“综合回答”并列保留，用户明确发起综合回答后才建立私有研究会话，所以可以直接对照“搜到了什么”和“回答用了什么”。参考 [实际命中与综合回答 ↗](../../../apps/web/src/SearchAnswer.vue#L205 "支持搜索页保留实际命中，并由用户显式启动可继续追问的研究回答。")

<a id="candidates"></a>
## 全文、短词、符号、向量、知识与记忆各做什么

统一检索不是让一种模型包办所有问题，而是让几条候选路线各自发挥长处，再按名次与质量融合：

| 表示 | 更擅长解决 | 不应误解为 |
| --- | --- | --- |
| 全文 BM25 | 正文中明确出现的业务词、路径、错误字样 | 任意词沾边就算相关；长问题仍要求一定词项覆盖 |
| 中文短词 | 保住恰好为 2–8 个汉字的领域复合词，如“重试” | 对任意长句做完整意图理解 |
| 符号 | 用 AST 单位精确找到函数、方法或限定名定义 | 完整调用图；问调用方时定义仍可能靠前 |
| 中文向量 | 找到词面不同、语义接近的描述 | 答案正确性判断；模型失败时系统会退回词法与符号 |
| 知识 | 先读按读者问题组织、仍能回到原文的讲解 | 第二份独立事实库 |
| 记忆 | 找已应用的当前事实、经历或方法 | 把每次原聊天重新猜成“当前结论” |

中文查询先经 ICU 分词，并为整条短中文词额外保留 literal；明确的代码拼写再进入独立符号候选。全文、符号与向量候选分别产生后融合，避免直接相加不可比分数。参考 [中文短词与符号识别 ↗](../../../apps/server/src/retrieval/relevance.ts#L1 "支持 ICU 分词、2 至 8 个汉字短词保留，以及明确代码拼写才形成符号候选。") [多路候选融合 ↗](../../../apps/server/src/retrieval/unified.ts#L306 "支持符号独立召回，以及全文、语义和符号候选按名次与归一化质量融合。") 默认向量模型是 osdk 锁定的本地 BGE-small-zh-v1.5，使用中文查询指令、归一化表示且禁止运行时远程取模型。参考 [本地中文向量 ↗](../../../apps/server/src/retrieval/embedding.ts#L14 "支持默认 BGE 中文模型的锁定快照、本地 q8 CPU 推理、查询指令与禁止远程模型。")

知识章节只有在复核通过、依赖仍可读且引用仍对应固定版本时才进入有效投影；记忆只投影 active 的当前 head，并继续保留原件证据。两者都能被搜索，却仍与原始 source 分开。参考 [知识章节有效投影 ↗](../../../apps/server/src/retrieval/units.ts#L589 "支持知识只有在复核、依赖和固定引用仍受支持时才进入检索，并保留递归原文 references。") [活动记忆投影 ↗](../../../apps/server/src/retrieval/units.ts#L804 "支持仅投影 active memory 当前 head，并把结构化内容与原件证据一起变成检索单位。")

<a id="context"></a>
## 命中片段后，怎样补成可读上下文

检索单位尽量保留原结构：Markdown 按块切分并携带标题路径，引导句会与紧随的列表、表格或代码块合并；TS/Vue 按 AST 保留完整函数或方法，函数内局部变量不会被拆成失去控制流的碎片；聊天片段把发言人、事件时间、会话和回复关系写入 context。参考 [文档与代码结构切分 ↗](../../../apps/server/src/retrieval/units.ts#L31 "支持 Markdown 保持块结构、代码保留完整方法及其控制流的说明。") [会话上下文投影 ↗](../../../apps/server/src/retrieval/units.ts#L265 "支持聊天检索单位携带发言人、事件时间、会话与回复关系。")

每个原件命中都带固定 revision、行范围、fragmentIds 与标题路径。助手不会只把一段自由文本交给模型，而是把这些引用重新解析成精确行段；同一个底层片段中的不同函数或行范围也得到不同 citationId。知识、记忆和事项作为背景时，其引用仍可递归回原件。参考 [统一命中与固定目标 ↗](../../../apps/server/src/retrieval/port.ts#L23 "解释 RetrievalHit 如何区分 source、knowledge、memory、task，并为 source 保存 revision 与行范围。") [助手证据组装 ↗](../../../apps/server/src/assistant/runtime.ts#L913 "支持助手把命中 references 重建为精确证据，并把非 source 结果保留为带引用背景。")

需要注意：系统确实有“补标题、前一块、后一块”的章节邻居函数，但当前正常统一搜索路径主要按命中的固定范围组装证据；直接邻居扩展用于 source-only 兼容路径。需要完整章节、完整方法或下游文件时，当前主路径是让 Agent 继续调用按章节、按行和代码导航工具补读，而不是宣称每次命中都会自动展开整个父章节。参考 [章节邻居兼容路径 ↗](../../../apps/server/src/assistant/runtime.ts#L972 "支持邻居函数补标题与前后块，同时说明它在 runtime 中属于 source-only 取证路径。")

<a id="assistant"></a>
## 助手如何使用来源并继续查询

助手先取得本轮统一召回，再把 source 命中变成可引用证据，把 knowledge、memory、task 变成带原文引用的背景。对网页私有会话，服务端固定为 private；对群会话，只允许看到同一 chatId 已采集的证据，前端不能伪造群可见性。参考 [网页私有会话 ↗](../../../apps/server/src/app.ts#L790 "支持网页调用者不能伪造 Lark 渠道或群可见性，服务端固定打开 private web 会话。") [群会话可见性 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L90 "支持群会话只能读取同一 chatId 已采集的证据。")

当前生产装配给助手提供知识仓储，因此它会进入原生自主调查：初始命中只是线索，Agent 可搜索材料或知识、读取完整章节和指定行、查看活动记忆或历史版本、用 AST 导航定义与候选调用，然后提交带精确原文范围的回答。宿主再次检查材料是否属于授权快照、历史版本是否同源、行范围和可见性是否有效。参考 [原生助手调查 ↗](../../../apps/server/src/assistant/acp-model.ts#L162 "支持当前助手创建原生调查工作区、提供初始命中，并让 Agent 自主补读后提交结果。") [补读工具与代码导航 ↗](../../../apps/server/src/knowledge/agent-research.ts#L388 "支持 Agent 可读取材料章节、搜索知识并使用只读代码导航；调用关系明确为候选而非完整调用图。")

因此，“助手回答得好”不等于“第一次搜索排得好”。Agent 可能通过后续调查找回漏掉的上下文；排查搜索质量时仍要回看初始实际命中。反过来，初始命中很多也不代表回答完整：模型还必须区分事实、条件和未知。

<a id="limits"></a>
## 当前中文排序与时间检索的边界

默认配置启用了中文 embedding，却没有配置 reranker，所以 cross-encoder 重排默认关闭。代码支持显式加载锁定的中文重排模型，只处理已有候选；现有对照同时出现收益与退步，模型分数也不是答案正确概率。参考 [默认检索模型配置 ↗](../../../config/retrieval.json#L1 "支持默认只启用 memory-zh embedding、没有 reranker 配置。") [重排采用边界 ↗](../../../docs/reader-first/retrieval-evaluation.md#L24 "支持重排默认关闭、只处理已有候选，并且对照存在收益与退步、分数不是正确率。")

时间字段目前分三层：timeRange 过滤捕获 revision 的时间，effectiveAt 检查材料声明的有效期，消息、记忆和事项的 eventAt 主要在 follow-up 排序中提供近期偏好。顶部搜索虽暴露有效时间条件，但系统尚不能把“上周当时怎样”自动变成完整的历史 as-of 查询。参考 [时间查询合同 ↗](../../../apps/server/src/retrieval/port.ts#L87 "支持捕获时间过滤与明确有效时间条件不同，并说明当前不是历史 as-of 推理。")

还要保留三条现实边界：主题相近不等于能回答；符号定义不等于调用方或跨文件业务链；结构背景已经实现，但还不是逐块生成的完整 Contextual Retrieval。用途和材料状态只是排序偏好，也不能替代事实判断。参考 [当前检索限制 ↗](../../../docs/reader-first/current-system.md#L23 "支持主题相关不等于可回答、可选重排未解决完整性，以及完整时态和跨文件链仍有限。")

<a id="diagnosis"></a>
## 从可见症状定位问题和修改入口

遇到“没找到答案”，按三层看最省时间：

1. **召回问题**：正确原件或知识章节根本不在候选里。检查消息是否已采集、当前 head 是否已投影、向量是否 ready，以及短词/符号识别、材料角色、有效期和可见性是否提前过滤。
2. **上下文问题**：候选已有正确材料，但引用范围缺关键方法、父章节、相邻回复或下游文件。检查固定 SourceAnchor、按范围取证、章节补读和代码导航。
3. **回答问题**：必要证据已完整提供，模型仍漏条件、混淆事实或讲不清。此时应改生成与表达，而不是继续调召回权重。

如果正确材料在候选里但位置靠后，应记录为“可发现但排序差”，不要与“完全未召回”混为一谈；重排只能调整已有候选，不能补出缺失原件或自动拼成跨文件功能链。参考 [四层检索判断 ↗](../../../docs/reader-first/retrieval-evaluation.md#L5 "解释召回候选、可回答性、补全说明与最终写作是不同阶段，重排不能补齐业务链。") [召回与生成验收 ↗](../../../docs/reader-first/current-system.md#L62 "支持按真实命中和材料完整性区分召回、上下文与生成失败。")

修改时从用户可见结果反向走：群消息输入看 integrations/lark/realtime.ts；三个入口的共用装配看 app.ts 与 knowledge/api.ts；切分和上下文看 retrieval/units.ts、context.ts；候选融合与用途排序看 retrieval/unified.ts；助手证据和补查看 assistant/runtime.ts、assistant/research.ts 与 knowledge/agent-research.ts。这样一次只改对应层，并用“实际命中”和“最终回答”分别观察结果。
