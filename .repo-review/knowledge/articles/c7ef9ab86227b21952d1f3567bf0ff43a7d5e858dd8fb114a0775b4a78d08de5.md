# 一次提问如何找到答案：搜索、上下文与 RAG

沿“这次活动要准备多少钱、到哪里集合？”这一教学问题，解释顶部搜索、知识搜索和助手怎样共享召回基础，又怎样在候选、补读和回答阶段分工；同时说明全文、中文短词、符号、向量、记忆与知识的作用，给出遗漏诊断和实现修改入口，并标明当前重排与时间判断的限制。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="example"></a>
## 先看一次可用答案是怎样形成的

先给结论：搜索负责**把可能有用的细段放进候选**，上下文装配负责**补回理解这段话所需的完整章节和上级说明**，助手负责**检查问题还缺什么、继续查，并把原件组织成答案**。任何一层都可能造成遗漏。

下面是贯穿全文的**教学示例**，用于说明机制，不承诺系统必然给出某个排名。假设材料已经保存：

| 项目 | 内容 |
| --- | --- |
| 用户问题 | “这次活动要准备多少钱、到哪里集合？” |
| 必要材料 | 当前活动说明中的“参加预算八十元”和“图书馆集合”；若同节或上级引言另有“仅限报名者”“周三前确认”等条件，也要带入 |
| 干扰内容 | 旧活动记录中的“八十元”、只介绍活动主题却没有地点的相似段落、讨论检索方案的文档 |
| 可用答案 | “准备八十元，在图书馆集合”，金额和地点各贴对应原文引用；必要的适用条件紧跟结论 |

“旧记录”不能只因文件较早、上传较早或排名较低就自动判为失效。在**没有显式筛选材料角色且 purpose 不是 background** 时，当前实现会把计划、调研、示例和 superseded 等正式标注作为排序先验；这只是默认导航偏好，不是真伪裁决，未分类材料仍完整参与。显式角色搜索和 background 搜索不应用这项降权。只有查询明确给出 `effectiveAt` 时，检索才按材料说明中的 `validFrom/validUntil` 过滤。若原文标题、日期、版本历史和正式说明仍不能区分“这次”，正确答案应保留不确定，并继续调查，而不是擅自选一条。参考 [默认材料用途与状态先验的守卫 ↗](../../../apps/server/src/retrieval/unified.ts#L285 "支持只有未显式筛选材料角色且 purpose 不是 background 时才按计划、调研、示例和状态降权，unknown 保持完整资格。") [有效时间按正式范围过滤 ↗](../../../apps/server/src/retrieval/unified.ts#L231 "支持 effectiveAt 仅依据材料说明中的 validFrom 和 validUntil 过滤。")

这也给出最实用的排错框架：

1. 金额或地点根本不在候选中：**召回遗漏**。
2. 候选命中了“八十元”，但漏掉同节的报名条件：**补读遗漏**。
3. 金额、地点和条件都已交给模型，答案仍只写金额：**回答遗漏**。

引用范围正确、输出 JSON 合法或复核通过，都不能单独排除这三类语义问题。参考 [遗漏发生在召回、补读或写入答案 ↗](../../../docs/reader-first/answer-investigation.md#L5 "直接说明关键前提遗漏的三个环节及格式和引用不能替代语义完整性。")

<a id="shared-entry"></a>
## 三个入口共用召回，但读取方式不同

顶部搜索、知识搜索和助手不是三套彼此独立的索引。主合同 `RetrievalPort.search` 同时容纳原件、知识、已应用记忆和事项；每个命中保留自己的固定目标，知识命中还保留回到原件的 references。旧的 `searchSources` 仍服务于必须拿 Fragment 锚点的兼容调用，不是今天解释所有搜索行为的主入口。参考 [统一检索合同与固定目标 ↗](../../../apps/server/src/retrieval/port.ts#L1 "定义共享 search、统一结果类型、固定目标与原件 references，以及兼容 source-only 接口。")

| 入口 | 怎样调用共享召回 | 命中之后怎样处理 |
| --- | --- | --- |
| 顶部搜索 | `/api/search` 默认 `balanced`、最多 30 条，可显式传 purpose、代码意图、材料角色和有效时间 | 作为阅读列表展示，沿用默认来源上限、知识同节去重和相同文本去重 [顶部搜索的共享入口 ↗](../../../apps/server/src/app.ts#L313 "支持 /api/search 调用统一 retrieval，默认 balanced、limit 30，并接收用途、代码意图、角色和有效时间。") |
| 知识搜索 | 同一 `search`，但限定 `kinds=["knowledge"]`、默认 `concept`、最多 50 条 | 页面按文章 key 只展示一次，并把命中章节作为入口 [知识搜索的限定与文章分组 ↗](../../../apps/server/src/knowledge/api.ts#L121 "支持知识页限定 knowledge、默认 concept、limit 50，并按文章 key 返回一次命中章节。") |
| 助手 | 同一 `search` 先取 48 条，明确 `diversify=false` | 再按完整阅读上下文装配，最多选 16 个不同上下文 [助手先取候选再装配上下文 ↗](../../../apps/server/src/assistant/runtime.ts#L926 "支持助手首轮取 48 条、关闭 browse diversity，并调用 assembleAnswerContext。") |
| Agent 调查工具 | `search_materials` 限原件，`search_knowledge` 限知识，均明确关闭浏览去重 | 在固定调查快照内继续读章节、历史、记忆或代码关系 [Agent 原件与知识搜索工具 ↗](../../../apps/server/src/knowledge/agent-research.ts#L505 "支持调查工具分别限定 source 和 knowledge，且两者都设置 diversify=false。") |

因此，“共用召回”指它们共享检索单位、全文/向量/符号路线、范围与用途过滤、以及统一命中结构；它不表示三处使用相同的 kinds、limit、去重策略或阅读结果。排查时先确认问题发生在哪个入口，不能拿顶部列表只显示两段，推断助手也只能看到两段。

<a id="recall-routes"></a>
## 全文、短词、符号、向量、记忆与知识各解决什么

理解这些名词前，先区分三个单位：

- **保存单位**是固定的 Source / Revision / Fragment，用来保留历史和引用。
- **检索单位**是可重建的投影，用来让相关内容容易被找到。Markdown 按块和章节路径组织，列表、表格、代码及其引导句尽量保持完整；TS/Vue 代码按函数、方法等 AST 范围组织。参考 [Markdown 与代码检索单位 ↗](../../../apps/server/src/retrieval/units.ts#L33 "支持 Markdown 保持块结构和章节路径，以及代码按 AST 符号范围形成检索段。")
- **回答单位**是命中后恢复的完整章节、代码操作及必要原件引用，不等于某个检索细段。

在教学问题中，各路线的分工如下：

| 路线 | 它帮助解决的问题 | 不应误解为 |
| --- | --- | --- |
| 全文 | SQLite FTS5 用 ICU 分词后的文本做 BM25；“八十元”“图书馆”原样出现时，这是透明、稳定的基线 [中文 FTS5 索引与 BM25 候选 ↗](../../../apps/server/src/retrieval/units.ts#L945 "支持中文索引先做 ICU 分词，以及全文路线用 FTS5 BM25 产生候选。") | 理解同义表达或判断记录是否仍适用 |
| 中文短词 | 查询也用中文 `Intl.Segmenter`，去常见停用词，并为 2～8 个汉字的完整短查询保留 literal compound；这能避免领域短词只剩错误拆分 [中文查询词与短词保留 ↗](../../../apps/server/src/retrieval/relevance.ts#L1 "支持 Intl.Segmenter、停用词和 2 至 8 个汉字短查询的 literal compound 规则。") | 通用同义词、实体或时态推理 |
| 向量 | 启用 embedding 时，将问题与单位窗口编码，按余弦相似度产生候选；例如“准备多少钱”可能靠近“参加预算” [向量候选与弱尾过滤 ↗](../../../apps/server/src/retrieval/unified.ts#L480 "支持查询 embedding、窗口余弦相似度、相对阈值过滤和最多 100 条语义候选。") | 相似就一定能回答，或相似记录一定是当前记录 |
| 符号 | 明确代码拼写会沿 AST 派生的 headingPath 独立找定义；显式 callers 返回名称级候选调用位置 [AST 符号独立路线 ↗](../../../apps/server/src/retrieval/unified.ts#L309 "支持代码定义不依赖整句 BM25，并说明 callers 路线是名称级候选。") | 类型解析后的完整跨文件调用图；它也不参与普通活动问答 |
| 记忆 | 只有 active 的记忆被投影，保留事实、经历、方法类型、版本及支撑原件范围 [仅 active 记忆进入投影 ↗](../../../apps/server/src/retrieval/units.ts#L805 "支持记忆投影只读取 active 状态，并保留类型、版本、原件引用和事件时间。") | 另一份独立事实，或所有原始聊天的替代品 |
| 知识 | 已发布且仍受支持的文章章节成为检索单位，保留文章修订、章节、状态和原件 references [知识章节作为带引用的检索单位 ↗](../../../apps/server/src/retrieval/units.ts#L670 "支持仍受支持的文章章节按固定修订进入投影，并携带 reviewState 与原件 references。") | 脱离原件的新权威事实 |

全文、向量和符号分支的原始分数不可直接比较，所以当前主实现按每条路线的名次计算标准 RRF：第 r 名按一基名次贡献 `1/(60+r)`，同一单位的贡献再相加。参考 [标准 RRF 融合 ↗](../../../apps/server/src/retrieval/unified.ts#L408 "支持全文、向量和符号路线仅按一基名次贡献 1/(60+rank)，不直接混合原始分数。")

排序先验的生效阶段要分清：**purpose 用途偏好只在融合后的 `finish` 阶段应用**；材料用途/状态的 applicability 先验还会影响词法候选池的排序与截取、向量候选的排序与截取，并在 `finish` 中再次参与最终排序。它们都帮助决定“先看哪类内容”，不是真伪裁决。参考 [材料先验影响词法候选池 ↗](../../../apps/server/src/retrieval/unified.ts#L427 "支持词法分支在最多 250 个候选的排序、提前停止和截取中使用 applicability。") [材料先验影响向量候选截取 ↗](../../../apps/server/src/retrieval/unified.ts#L534 "支持语义候选先经过相似度阈值，再按相似度乘 applicability 排序并截取前 100。") [用途偏好与材料先验进入最终排序 ↗](../../../apps/server/src/retrieval/unified.ts#L606 "支持 purpose preference 在 finish 定义并参与最终 priority，同时 applicability 和知识 freshness 也参与最终排序。")

这就是本文所说的 RAG：先 **Retrieval（检索）** 找候选，再把原件与派生背景 **Augment（补入上下文）**，最后由模型 **Generate（生成）** 回答。重点不在缩写，而在三步可分别检查。

<a id="context"></a>
## 命中一个细段后，怎样补回条件

假设全文或向量先命中“参加预算八十元”。回答不能只把这一个片段塞给模型。

对原件命中，`sourceContextRange` 会在**同一固定 revision** 中找到包住该范围的最小完整 Markdown 章节或代码操作；没有可靠结构就保留原命中，不把整份文件强行附上。扩展范围内的所有 Fragment 都必须通过可见性检查。参考 [原件命中恢复为同版完整上下文 ↗](../../../apps/server/src/retrieval/context.ts#L13 "支持原件命中只在同一固定版本扩为最小完整章节或操作，并执行可见性检查。")

`sourceContextRanges` 还会逐级查看父章节，把父级在第一个子节之前的实际引言作为独立固定范围带入。于是“仅适用于提前报名者”这类上位范围条件可以随焦点章节进入答案；兄弟章节和任意后文不会自动拼接，因此地点若在另一节，仍需要另一个候选或 Agent 继续查询。参考 [父级引言作为独立固定范围 ↗](../../../apps/server/src/retrieval/context.ts#L43 "支持补入父章节首个子节前的实际说明，同时不自动拼接兄弟章节。")

回答装配还做两件事：

1. 知识命中会在同一固定文章 revision 中查找命中章节的全部检索单位；只有整章单位及其引用都通过可见性检查，才恢复完整章节正文并合并该章实际使用的原件引用，否则退回原命中。
2. 原件命中按恢复后的 revision 与行范围去重。限制的是最多 16 个**不同阅读上下文**，不是一个已选章节可以携带多少条必要引用。参考 [知识整节与回答上下文装配 ↗](../../../apps/server/src/assistant/context.ts#L10 "覆盖 knowledgeContext 的整章可见性、完整章节恢复和引用合并，以及 assembleAnswerContext 的原件扩展、去重与 16 个上下文限制。")

这解释了为什么浏览列表的去重不能提前限制助手。默认阅读列表会让同一来源最多保留两段、同一知识章节只留一次，并去掉重复文本；`diversify=false` 才关闭这些展示限制。若助手召回时也套“两段/来源”，同一活动说明里的第三项必要事实可能在补读前已经消失。参考 [浏览去重的实际边界 ↗](../../../apps/server/src/retrieval/unified.ts#L651 "支持默认同来源两段、知识同节一次和相同文本去重，diversify=false 时关闭这些限制。")

不过，这不是“找全”保证：首轮仍只有 48 个候选，装配仍按原排名选最多 16 个上下文，并未根据“金额、地点、适用范围”做答案槽位覆盖优化；完整章节也可能带来噪声。当前实现只是把候选保留、结构补读和界面展示拆开。参考 [48 与 16 不是找全保证 ↗](../../../docs/reader-first/retrieval-redesign.md#L19 "说明候选与阅读上下文的数量、完整章节的成本，以及尚未实现答案要点覆盖选择。")

<a id="investigation"></a>
## 助手怎样继续查，并在必要时独立核对

初始召回只是线索。处理教学问题时，助手应先把答案拆成三个槽位：**金额、集合点、为什么它们适用于“这次”**。若只找到金额，就围绕“集合、地点、本次活动”补查；命中后读完整节和父级引言；遇到旧记录，再检查标题、日期、材料说明、历史版本和正式有效期。

原生调查工具允许按缺口选择动作：`search_materials` 搜原件并可限定材料类型、用途、代码意图、材料角色和有效时间；`read_section` 可按搜索返回的 contextId 读完整节点，并沿 parentId/children 补读父条件或子话题。参考 [按节点补读与搜索原件 ↗](../../../apps/server/src/knowledge/agent-research.ts#L450 "支持 read_section 按 contextId、父子节点或行号补读，以及 search_materials 的范围和代码导航边界。")

`search_knowledge` 从同一个统一检索中限定 knowledge，保留原件 references；`read_knowledge` 再按精确文章 key、可选 revision 与 section 读取固定文章和依赖版本。它们适合先取得整体解释，再回原件核对，派生解释本身不是第二份事实。参考 [知识搜索的工具定义 ↗](../../../apps/server/src/knowledge/agent-research.ts#L603 "支持 search_knowledge 限定 knowledge、关闭展示去重并返回文章修订、章节、引用和原件 references。") [固定知识文章的读取 ↗](../../../apps/server/src/knowledge/agent-research.ts#L673 "支持 read_knowledge 按文章 key、可选 revision 与 section 读取正文、依赖版本和 reviewState。")

调查不是对实时数据库的无边界浏览。宿主从允许可见的材料建立固定快照；派生文章只有在其精确依赖版本也获准时才进入。回答提交时，宿主校验材料 key、历史 revision、行范围和可见性，再把短引用 ID 还原为固定原件锚点。参考 [固定调查快照的准入 ↗](../../../apps/server/src/knowledge/research-snapshot.ts#L50 "支持只复制可见修订，并仅在精确依赖版本获准时把派生文章放入快照。") [答案引用由宿主校验 ↗](../../../apps/server/src/assistant/research.ts#L105 "支持提交时校验材料、历史版本、范围和可见性，并把短引用映射到固定证据。")

可用回答应直接写金额与地点，在各自论断旁贴精确原文引用；知识文章只负责组织背景。如果适用状态仍无法确认，就明确说“不确定哪份记录适用于这次”，并指出已核对和仍需核对的依据，不以相似度或上传时间代替事实。

独立核对适合跨来源机制、冲突、当前行为或会改变结论的重要前提；简单的原文直接查值不强制多一次模型调用。作者可保存简短事实笔记并标记 `reviewRequired`，随后 `review_answer` 在同一固定材料快照中启动独立会话；复核者看原问题和候选答案，但不接收作者的调查笔记。若作者要求复核，宿主会阻止在复核未完成、意见未读取或有实质问题却原样提交时结束。参考 [独立答案复核与提交门禁 ↗](../../../apps/server/src/assistant/answer-review.ts#L88 "支持复杂前提触发独立复核、复用同一快照，以及未完成、未读取或有问题的原样草稿不能提交。")

复核是第二次独立补查，不是正确性证明：是否触发仍由模型判断，复核者也可能遗漏。最终验收仍要看答案是否切题、必要条件是否齐全、引用是否真的支持结论。参考 [复核能力与误判边界 ↗](../../../docs/reader-first/answer-investigation.md#L17 "说明独立复核的材料隔离、职责以及模型漏判和复核遗漏仍可能发生。")

<a id="diagnosis"></a>
## 发现效果不好时，先定位哪一层

不要一看到坏答案就调排序权重。先保留同一次问题的候选、展开后的阅读上下文和最终答案，按下面的顺序定位：

| 观察 | 更可能的问题 | 首要修改入口 |
| --- | --- | --- |
| 必要的金额或地点没有进入候选 | 检索单位、分词、全文/向量/符号路线、范围过滤或排序 | `retrieval/units.ts`（单位）；`retrieval/relevance.ts`（中文短词与代码问法）；`retrieval/unified.ts`（候选、RRF、用途与去重）；`retrieval/port.ts`（查询合同） |
| 细段命中，但同节条件或父级范围没进入回答材料 | 结构层级、可见性或回答上下文装配 | `retrieval/context.ts`（完整节与父引言）；`assistant/context.ts`（知识整节、16 个上下文及引用合并） |
| 同文件第三个事实只在顶部列表缺失，助手材料里存在 | 界面阅读去重是正常差异 | `app.ts` 与知识页 API；不要据此修改助手召回 |
| 初始候选缺一个跨节或跨材料条件，Agent 没继续找 | 调查工具选择或 ACP 编排 | `knowledge/agent-research.ts`、`assistant/acp-model.ts`、`knowledge/research-snapshot.ts` |
| 金额、地点和适用条件都在模型输入中，最终答案仍遗漏 | 生成或答案核对问题，而非召回问题 | `assistant/research.ts`（引用提交）；`assistant/answer-review.ts`（独立核对） |
| 知识页搜索与顶部搜索结果形态不同 | kinds、purpose 和页面分组不同 | `knowledge/api.ts` 与 `app.ts` |

其中最容易误诊的是最后一步：工具日志只能说明模型请求过某段材料，不能证明它理解并使用了该条件。当前验收方法也明确要求把“没找到、没补读、最后遗漏”分开看。参考 [真实回答的分层验收 ↗](../../../docs/reader-first/answer-investigation.md#L35 "支持结合候选、读取、笔记、草稿、复核和最终答案区分三类遗漏，工具记录不证明理解。")

修改后，用真实问题重新比较三份产物：候选是否包含必要材料、展开上下文是否保留改变结论的条件、最终回答是否逐项覆盖问题。排序测试、引用数量或 schema 通过只能辅助定位，不能替代这次端到端检查。

<a id="limits"></a>
## 当前边界：中文模型、重排和时间

当前仓库的 `config/retrieval.json` 明确启用了检索并选择 `memory-zh`，文件中没有 reranker 配置。工厂只有在显式提供 reranker 名称时才加载中文 cross-encoder。锁文件把 `memory-zh` 固定到 `Xenova/bge-small-zh-v1.5` 的量化 ONNX 快照。参考 [当前仓库的检索模型配置 ↗](../../../config/retrieval.json#L1 "直接证明当前配置 enabled=true、osdkModel=memory-zh，且没有 reranker 字段。") [reranker 仅按显式配置加载 ↗](../../../apps/server/src/retrieval/factory.ts#L9 "支持配置 schema 中 reranker 可选，工厂只有配置该名称时才加载中文重排模型。") [锁定的中文向量模型 ↗](../../../osdk.lock#L203 "支持 memory-zh 指向固定 revision 的 Xenova/bge-small-zh-v1.5 量化 ONNX 模型。")

如果某个部署显式启用重排，当前实现只处理融合后的前 40 个单位；每个长单位最多取词法命中附近和向量命中附近两个局部窗口，cross-encoder 分数占 0.7，原融合分占 0.3。材料没进前 40，重排无法救回；局部段落很相关，也不等于问题所需条件齐全。参考 [重排只处理融合前四十 ↗](../../../apps/server/src/retrieval/unified.ts#L545 "支持重排池为前 40 个候选、局部段输入及 0.7/0.3 分数混合。") [长单位最多两个局部窗口 ↗](../../../apps/server/src/retrieval/rerank-passages.ts#L3 "支持重排对长单位最多使用词法与密集命中附近的两个局部段，而完整单位仍用于阅读。")

时间至少有三种含义，排查时不能混用：

- `timeRange` 过滤的是 revision 的**捕获时间**，合同明确说它不是事件时间，也不是历史 as-of。
- `effectiveAt` 只在调用方明确提供时，按正式材料说明的 `validFrom/validUntil` 过滤。
- `purpose=follow-up` 只对事项、记忆和会话的 `eventAt` 给轻量近期加成；它不是通用的“当前事实”判定。参考 [捕获时间与有效时间合同 ↗](../../../apps/server/src/retrieval/port.ts#L96 "支持 timeRange 是捕获时间而非事件/as-of，effectiveAt 是读者明确要求的正式有效日期。") [跟进场景的轻量近期偏好 ↗](../../../apps/server/src/retrieval/unified.ts#L630 "支持 follow-up 仅对事项、记忆和会话使用 eventAt 的衰减加成。")

因此，教学例子里的旧活动记录只是一个需要调查适用范围的干扰候选。当前系统没有可靠的跨轮时态理解，也不能把事件时间、捕获时间和有效期字段自动合成为完整时间推理。参考 [当前时态理解仍不完整 ↗](../../../docs/reader-first/current-system.md#L54 "明确事件时间不等于捕获时间，有效期字段也不等于完整时态检索。")

最后保留两个诚实边界：符号调用是名称级候选而非完整调用图；48/16 的有限候选池也尚未实现按答案要点覆盖的选择。当前实现能让新人准确判断问题发生在召回、补读还是回答，并找到相应入口，但不能保证每个复杂问题自动找全、自动判新旧、或经复核后必然正确。
