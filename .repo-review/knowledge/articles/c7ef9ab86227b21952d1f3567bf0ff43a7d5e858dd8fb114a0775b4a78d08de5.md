# 一次提问如何找到答案：搜索、上下文与 RAG

用“活动要准备多少钱、到哪里集合”的教学示例，解释 omem 如何把整句问题变成全文、向量与符号候选，如何在固定版本中补回完整章节与父级条件，如何借助会话项目与按子问题调查处理旧记录或对象歧义，以及答案遗漏时应定位到召回范围、原文、补读、调查还是回答与复核层。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="what-counts-as-an-answer"></a>
## 先定义“答全”：结果与行动条件都要有依据

假设已经保存了几份活动材料。当前活动说明的一章写“参加预算八十元”，同章或上级简介还写着“仅限已报名者”“不含交通费”“周三 18 点前确认”；另一章写“在图书馆集合”。库里另有一份旧活动记录，也提到八十元。用户问：

> 这次活动要准备多少钱、到哪里集合？

这是贯穿本文的**教学示例**，不代表一次真实检索的固定排名。对这个问题，“答全”不只是找到一段谈活动的文字，也不只是输出“八十元、图书馆”。可用答案至少要做到两件事：

1. 分别回答金额和集合点，并让每项都能回到原文；
2. 把会改变行动的资格、费用范围、截止时间等条件放在对应结论附近。

因此，“活动很适合周末参加”即使语义相关，也不足以回答金额或地点；“八十元”若来自旧记录，也还不能证明适用于“这次”。关键前提可能在召回、补读和最终表达三个环节丢失，而引用格式正确本身发现不了这些语义缺口。参考 [可用答案与关键前提 ↗](../../../docs/reader-first/answer-investigation.md#L5 "说明关键前提可能在召回、补读或表达阶段丢失，引用正确不等于语义完整。")

<a id="retrieve-candidates"></a>
## 整句问题先产生候选，而不是直接产生答案

普通助手先把用户整句问题送入检索，取一个候选池，再装配回答上下文；这一步不会当场判断“金额和地点是否都找齐”。当前检索池最多取 48 个候选，并关闭浏览用途的多样化去重。参考 [助手首轮候选入口 ↗](../../../apps/server/src/assistant/runtime.ts#L974 "说明普通助手用整句问题检索有限候选池，并关闭浏览去重后装配完整回答上下文。")

这里有一个会影响候选范围的前置条件：**个人会话若已经保存了讨论项目，首轮检索会在排序和截断前，只保留属于该项目来源的可见材料；没有已确认项目时，仍搜索整个可见库。** 这同样作用于合并进来的上轮引用。它改变“从哪里开始读”，不改变材料可见性，也不限制后续原生调查跨到其他已授权材料。参考 [会话项目限定首轮阅读 ↗](../../../apps/server/src/assistant/runtime.ts#L1061 "说明已保存个人会话项目按来源成员过滤初始候选，而原生调查仍可跨到其他已授权范围。")

Markdown 原件不是整份文件作为一个单元排序。系统按结构化 token 生成带真实行号和标题路径的检索段；如果一段话以冒号引出表格、列表或代码块，会把引导语与后面的块放在一起，避免只返回无法独立理解的引导句。参考 [Markdown 检索段 ↗](../../../apps/server/src/retrieval/units.ts#L33 "说明结构化段落、标题路径及引导语与列表、表格、代码块的合并规则。")

候选主要从三条路线汇合：

- **全文路线**把分词后的查询词组成 FTS 查询，用 BM25 找字面匹配，擅长“八十元”“图书馆”或精确名称等信号。
- **向量路线**在 embedding 可用时寻找语义相近的窗口，例如措辞不同但含义接近的“费用准备”和“参加预算”。
- **符号路线**为代码名称与导航提供补充入口。

这些路线的原始分值尺度不同，系统用各路线中的名次做 RRF 融合；没有向量模型、查询是精确标识符，或向量执行失败时，仍可沿全文与符号路线返回结果。参考 [全文检索与 RRF ↗](../../../apps/server/src/retrieval/unified.ts#L408 "说明 BM25 全文候选及不同路线按名次融合。") [向量路线与降级 ↗](../../../apps/server/src/retrieval/unified.ts#L480 "说明何时使用语义向量、如何融合，以及向量不可用或失败时如何退回全文与符号路线。")

所以同一句问题可能让费用段、集合段和一段只讲活动主题的介绍都进入候选。**相关候选只是阅读入口，不是答案覆盖证明。** 当前候选总数有限，也没有一个确定性选择器等到金额、地点等所有要点都覆盖后才停止。参考 [候选不等于覆盖 ↗](../../../docs/reader-first/retrieval-redesign.md#L19 "说明候选有限，按子问题搜索也不判断答案是否已经覆盖。")

这也解释了为何网页搜索列表与助手读到的内容不一定一一对应。浏览列表默认会限制同一来源或章节的重复展示；助手和调查工具使用不做这种浏览去重的候选池。排序、显式范围和可见性过滤仍然存在；个人助手还可能带有已保存项目范围，因此不能只按显示条数比较两个入口。参考 [浏览去重与助手候选 ↗](../../../apps/server/src/retrieval/port.ts#L109 "说明 diversify=false 关闭浏览用途的来源上限和去重，但保留排序、范围与可见性过滤。")

<a id="restore-context"></a>
## 命中细段后，在固定版本中补回可读语境

候选排序用细段，但回答不能只读命中的一句。原件候选被选中后，`sourceContextRange` 会在**同一个不可变版本**内，把命中扩为包含它的最小完整 Markdown 章节或代码结构；没有可靠结构时保留原命中，不把整份文件一股脑附上。扩展范围还必须全部通过可见性检查。参考 [最小完整章节 ↗](../../../apps/server/src/retrieval/context.ts#L13 "说明命中在同一固定版本内扩展到最小结构上下文、H1 特例及可见性回退。")

Markdown 层级决定扩展边界。普通章节包含自己的子章节，所以费用章里的“八十元”命中后，可以一起读到该章下面的报销或费用条件。文档唯一的 H1 则被视为标题：命中开篇导言时只读到第一个子章节之前，不因一个简介命中而展开整篇。参考 [最小完整章节 ↗](../../../apps/server/src/retrieval/context.ts#L13 "说明命中在同一固定版本内扩展到最小结构上下文、H1 特例及可见性回退。")

系统还会沿父链补入各级章节在第一个子节之前的引言，并把它们保留成独立的固定引用。因此，上级写的“仅限已报名者”可以随费用命中进入语境；但兄弟章节不会自动附加，另一章的“图书馆集合”需要自己的候选或后续补查。参考 [父级引言与兄弟边界 ↗](../../../apps/server/src/retrieval/context.ts#L64 "说明父级开头会作为独立固定引用加入，而兄弟章节不会自动附加。")

回答上下文限制的是不同阅读上下文的数量。选入后，原件按上述结构恢复；相同固定版本中被更大范围包含的证据会去重，但不同版本不会拼接，也不会制造原文不存在的新范围。参考 [回答上下文装配 ↗](../../../apps/server/src/assistant/context.ts#L74 "说明完整上下文的选择上限、固定版本读取与包含范围去重。") 测试覆盖了旧版“八十元”和新版“一百二十元”同时存在的情形，并确认旧背景仍指向旧版本、费用命中不会自动带入兄弟章的集合点。参考 [多版本上下文测试 ↗](../../../apps/server/tests/retrieval-hierarchy.test.ts#L149 "验证旧版和新版事实可并存、旧背景保持指向旧版且兄弟地点不被自动带入。")

可以把这一层记成一句话：**细段用于排序，固定完整章节用于理解。** 它能补回结构上明确相邻的条件，却不能保证兄弟章、其他文件或原文未写明的替代关系自动出现。

<a id="investigate-gaps"></a>
## 只补未解项，并先确认“这次”指哪个对象

第一次阅读后，可以把教学问题拆成三个槽位：

- 金额及会改变金额含义的费用条件；
- 集合点；
- “这次活动”对应的对象和版本。

若费用章已经给出八十元、报名资格和交通费条件，就不必换几个近义词反复搜索金额；应把调查资源用于仍为空的集合点或对象身份。多部分问题可以通过 `search_contexts` 分别检索，每部分保留自己的排名和完整上下文，共享的固定上下文只返回一次。工具最多提供阅读线索，不会宣布某个问题已经回答；空结果也是搜索缺口，不是事实不存在的证明。参考 [按子问题保留上下文 ↗](../../../apps/server/src/knowledge/agent-research.ts#L661 "说明 search_contexts 的独立候选池、固定上下文恢复、共享去重及空结果边界。")

**如果已经发现多个可能对象，而且本轮和会话都没选定其中一个，应先做最小澄清。** 例如问“你指春游活动，还是同名的读书会？”不要凭“通常”默认一个，也不必先把所有对象完整调查、写成答案再让用户挑。只有用户明确要求比较时，才并列调查。参考 [对象澄清与项目选择 ↗](../../../packages/agent-runtime/roles/daily-assistant/1/skills/omem-assistant-research/SKILL.md#L14 "说明多对象未选定时先最小澄清，以及会话项目的沿用、切换与清空规则。")

项目身份在这里有两种用途，但都不是事实裁决：

1. 调查时可从项目或主题目录取得 `groupIds`。多个组取并集，与明确材料键同时使用时取交集，成员关系在本次固定快照中不变。
2. 个人会话会保存已经确认的正式项目。代词追问可沿用；用户换对象时选择新项目；无关、通用、跨项目比较或歧义未解时清空。新的选择只有在本轮成功后才与答案一起保存，失败或取消不改变它。

已保存项目会影响后续首轮阅读起点，但原生调查仍可跨范围查必要背景或新对象。归属只说明“去哪里找”，不证明组内哪条记录当前有效，也不授予写入权限；网页普通搜索目前也没有项目过滤。参考 [项目范围与会话阅读起点 ↗](../../../docs/reader-first/project-contexts.md#L23 "说明 groupIds 的范围运算、会话项目持久化、首轮过滤及项目身份不裁决事实或权限。")

回到旧记录：旧文也写“八十元”时，需要核对正文中的活动名称、日期、适用对象，以及是否明确写了变更或替代关系。材料角色和状态默认只是导航先验，不是真伪裁决；有效时间也只有调用方显式提供时才成为过滤条件。参考 [材料适用性与有效时间 ↗](../../../apps/server/src/retrieval/unified.ts#L231 "说明有效时间只在显式传入时过滤，材料角色和状态默认是导航先验而非真伪裁决。") 如果这些信息仍不足以确认“这次”，可用条件分支回答——“若指春游说明，则……；若指旧活动记录，则……”——或提出一个简短澄清。不能让排名、捕获先后、已保存会话项目或同属一个项目替用户做决定。

<a id="write-the-answer"></a>
## 把结论、条件与未知组织成可行动的答案

材料足够时，答案应按用户的两个问题逐项写，而不是先长篇解释检索机制。例如：

> 这次活动按每人八十元准备，在图书馆集合。八十元仅适用于已报名者，不含交通费；请在周三 18 点前确认。［分别附金额/条件与集合点的原文引用］

这个示例只有在固定原文确实支持每一句时才成立。若“这次”尚未消歧，就应先问对象，或把结论写成清楚的条件分支；若原件根本没说明交通费或替代关系，就保留未知，不能用 RAG 补造。

提交阶段会分别校验项目选择与引用：非空项目必须是当前可用的正式个人项目；引用必须来自本次授权材料，历史版本须与当前材料同源，范围须可见且有效，正文使用的引用编号也必须有原文定位。这些门禁保证选择和来源链接合法，却不验证金额、地点和条件是否都答到了。参考 [项目选择与答案引用校验 ↗](../../../apps/server/src/assistant/research.ts#L82 "说明提交阶段对正式项目 ID、授权材料、同源历史版本、可见性及正文引用定位的校验。")

复杂机制、冲突或关键推断还可以交给独立读者复核。复核使用同一固定快照；一旦请求复核，运行中、未完成、反馈未读取，或报告有实质问题但答案仍原样未改时，都不能提交。参考 [复核提交门禁 ↗](../../../apps/server/src/assistant/answer-review.ts#L204 "说明复核运行、反馈读取和含实质问题的原样草稿会阻止提交。") 复核能发现会改变结论或行动的遗漏，但是否启动与能否发现问题仍依赖模型判断，因此它是门禁，不是完整性证明。参考 [复核的能力边界 ↗](../../../docs/reader-first/answer-investigation.md#L21 "说明复核可发现重要遗漏但仍依赖模型判断，不能证明答案完整。")

<a id="locate-failures"></a>
## 答案仍不完整时，按信息丢失的位置定位

不要先用“搜索不好”概括所有遗漏。沿问题到答案倒查，通常能落到下面一层：

| 现象 | 问题所在层 | 优先查看的实现入口 |
| --- | --- | --- |
| 金额或地点从未进入候选，或只在取消项目范围后才出现 | 召回范围：检索段、全文/向量/符号路线、融合、可见性，以及 `conversation.projectId` / `readingScope` 是否错误收窄 | `retrieval/units.ts`、`retrieval/unified.ts`、`retrieval/port.ts`、`assistant/runtime.ts` |
| 候选或人工指定的原文本身没写必要条件 | 原文或选材 | 原材料正文、材料历史、选材入口 |
| 原文有条件，但同章、父级引言或固定引用没有交给助手 | 补读装配 | `retrieval/context.ts`、`assistant/context.ts` |
| 费用已读到，但兄弟章地点、对象切换或歧义仍未补查 | 调查策略与项目选择 | `knowledge/agent-research.ts`、`omem-assistant-research/SKILL.md`、`assistant/acp-model.ts` |
| 本轮已确认新项目，后续轮次仍沿旧范围 | 项目选择的应用与持久化 | `assistant/runtime.ts`、`conversation/router.ts` |
| 金额、地点和条件都已读到，最终答案仍漏写或混用版本 | 回答与复核 | `assistant/research.ts`、`assistant/answer-review.ts` |

判定时要同时看初始命中、后续读取、草稿、复核与最终答案：工具日志只能证明发起过读取，不能证明内容已被理解。人工指定原文也可能选得不全，因此“给了材料”不能自动归因为写作问题。参考 [分层验收方法 ↗](../../../docs/reader-first/answer-investigation.md#L47 "说明需结合命中、读取、草稿与答案定位遗漏，读取发生和人工选材都不等于已理解或材料完备。")

这张表的价值在于把修复放回正确层：范围或召回不到就检查项目身份与检索；命中了却缺结构语境就改补读装配；跨章和对象身份没继续查就改调查策略；项目已切换但后续没生效就查保存链路；证据已齐却没写进结论，才主要处理回答与复核。
