# 一次提问如何找到答案：召回、补读与回答

沿“本次活动要准备多少钱、到哪里集合”的教学示例，解释顶部搜索、知识搜索与助手如何共享召回基础，又如何分别浏览、补读和组织答案；说明全文、中文向量、符号、记忆与知识的分工，并给出遗漏条件的定位方法、修改入口和当前边界。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="example"></a>
## 先看一条能回答的问题链

这是一个**教学示例**，不是对实际排名的承诺：已保存的“本次活动说明”有两节，一节写“参加预算八十元”，另一节写“图书馆集合”；另一份旧活动记录也提到八十元。用户问：“这次活动要准备多少钱、到哪里集合？”

可用答案应同时给出金额与地点，例如：“按本次活动说明，准备八十元，到图书馆集合。”但前提是原文确实说明哪份材料适用于“本次”；若没有有效期、状态或明确时间，不能仅凭文件较新、目录名称或相似度排除旧记录，应继续查看材料说明或历史，并把不确定性告诉读者。

这条链可以拆成三个检查点：必要事实是否进入候选；命中后是否补出同节的对象、时间和例外；材料齐全后答案是否保留了两项事实及其适用条件。“相关”不等于“能够回答”，引用格式正确也不能发现语义遗漏。参考 [关键前提遗漏的三个环节 ↗](../../../docs/reader-first/answer-investigation.md#L5 "支持将一次问答拆成召回、补读和回答选择三个检查点，并说明相关性不等于可回答。")

<a id="shared"></a>
## 共享召回基础，不等于返回同一列表

顶部搜索、知识搜索、助手和 Agent 工具都建立在同一个 `RetrievalPort.search` 与统一结果类型上；结果可以是固定原件、知识、记忆或事项，派生解释仍保留其原始引用。参考 [统一检索结果合同 ↗](../../../apps/server/src/retrieval/port.ts#L1 "支持读者、助手和 Agent 共用搜索，并区分原件、知识、记忆等结果类型。")

它们的消费方式不同：

| 入口 | 查询后的处理 |
| --- | --- |
| 顶部搜索 | 返回综合浏览结果，可带用途、代码意图和有效时间筛选。参考 [顶部搜索入口 ↗](../../../apps/server/src/app.ts#L313 "支持顶部搜索通过共享 retrieval.search 传递用途、代码意图和材料筛选。") |
| 知识搜索 | 只取已发布知识，并把同篇文章收束到最佳章节入口。参考 [知识搜索入口 ↗](../../../apps/server/src/knowledge/api.ts#L121 "支持知识搜索限制为 knowledge，并按文章保留最佳章节入口。") |
| 助手 | 关闭浏览去重，将原件组装为可引用 evidence，把知识、记忆和事项作为 background，再补读固定原文。参考 [助手初始上下文组装 ↗](../../../apps/server/src/assistant/runtime.ts#L927 "支持助手关闭浏览去重、扩展原文上下文，并把非原件结果作为背景。") |
| Agent 调查 | 分开搜索原件与知识，保留目录节点，允许继续读取章节。参考 [Agent 搜索与章节导航 ↗](../../../apps/server/src/knowledge/agent-research.ts#L450 "支持 Agent 搜索原件时关闭浏览去重、返回目录节点，并可按章节继续补读。") |

因此，共享的是候选、范围与排序基础，不是最终展示形态。改公共召回先看 `retrieval/port.ts` 和 `retrieval/unified.ts`；改某个入口的筛选或呈现，再看该入口代码。

<a id="routes"></a>
## 全文、向量、符号、记忆与知识各做什么

**全文**从 Markdown 的段落、列表、表格等结构建立单位，代码则按函数、方法等符号范围建立单位；中文先经 ICU 分词，再交给 FTS5/BM25。它擅长找到原文出现的“八十元”“图书馆”，透明且容易定位，但旧记录和复述问题的材料也可能命中。参考 [结构化检索单位 ↗](../../../apps/server/src/retrieval/units.ts#L34 "支持 Markdown 按结构块、代码按符号范围建立检索单位。") [中文 ICU 分词 ↗](../../../apps/server/src/retrieval/units.ts#L966 "支持中文先经 ICU 分词再进入 FTS5/BM25 索引的说明。")

**中文向量**帮助词面不同但含义相近的材料进入候选池。当前配置启用 `memory-zh`，加载器只接受锁定的 BGE-small-zh-v1.5 固定修订，并在本地 CPU 上生成归一化表示。模型未配置或推理失败时，搜索会退回全文与符号路线。参考 [当前中文向量配置 ↗](../../../config/retrieval.json#L1 "支持当前检索配置启用 memory-zh。") [锁定的中文向量模型 ↗](../../../apps/server/src/retrieval/embedding.ts#L14 "支持固定 BGE-small-zh-v1.5 修订、本地加载、CLS pooling 与归一化配置。")

**符号路线**为代码定义和名称级调用候选服务，不依赖长问题先挤进 BM25 前列；调用位置仍是候选，不是类型解析后的完整跨文件调用图。参考 [符号与调用候选路线 ↗](../../../apps/server/src/retrieval/unified.ts#L309 "支持符号定义独立召回、调用位置为名称级候选以及自动导航失败时回退普通召回。")

**记忆**只投影已应用且 active 的事实、经历或方法，并保留回到原始证据的 references；**知识**按文章章节进入索引，提供整理过的整体解释和原文引用。两者帮助理解与找回，不会把派生内容变成第二份独立事实。参考 [active 记忆投影 ↗](../../../apps/server/src/retrieval/units.ts#L805 "支持只投影 active 记忆，并保存回到固定原件的 references。") [知识按节投影 ↗](../../../apps/server/src/retrieval/units.ts#L678 "支持知识按文章章节建单位、携带固定文章版本和原始 references。")

<a id="context"></a>
## 候选、阅读列表与回答上下文必须分开

普通浏览会限制同一来源反复占位，并对同一知识节或相同文本去重；助手与研究工具传入 `diversify:false`，绕开这些**浏览层**限制，但仍受总候选数、可见性、显式范围和排序约束。这样，同一活动说明里的预算和地点不会仅因“每份材料最多展示两段”而提前丢失。参考 [浏览去重开关合同 ↗](../../../apps/server/src/retrieval/port.ts#L107 "支持 diversify=false 只关闭浏览层来源上限与去重，仍保留排序、范围和可见性过滤。") [浏览结果去重实现 ↗](../../../apps/server/src/retrieval/unified.ts#L653 "支持普通浏览按来源、章节和文本去重，而 diversify=false 跳过这些限制。")

```mermaid
flowchart LR
  Q[用户问题] --> R[全文/向量/符号召回]
  R --> C[保留回答候选]
  C --> X[恢复同 revision 的完整节或函数]
  X --> A[助手补查并组织引用答案]
```

命中原件片段后，系统只在同一个固定 revision 内恢复最小完整 Markdown 章节或代码结构；还会把上级章节在首个子节前的引言作为独立范围放在焦点前。若没有结构、范围不可见，就保留原命中；兄弟章节不会整段自动附加。参考 [固定 revision 的结构补读 ↗](../../../apps/server/src/retrieval/context.ts#L13 "支持恢复最小完整章节或操作、补上级引言，并说明可见性与兄弟章节边界。")

套回示例：若“八十元”和“仅限已报名者”在同一节，命中金额可以带回该条件；若“图书馆集合”在另一个兄弟节，它仍需自己进入候选，或由 Agent 沿 `parentId/children` 用 `read_section` 补读。另一份旧记录也不会因结构扩展而自动判为过期。参考 [Agent 搜索与章节导航 ↗](../../../apps/server/src/knowledge/agent-research.ts#L450 "支持 Agent 搜索原件时关闭浏览去重、返回目录节点，并可按章节继续补读。")

<a id="research"></a>
## 助手如何补查、引用与独立核对

助手拿到初始 evidence/background 后，可以围绕具体缺口继续查询；常规 runtime 最多接收三条后续搜索请求并合并第二轮上下文。原生 Agent 调查还可搜索材料与知识、读完整章节、历史、记忆、图片和代码导航。做法不是相信首轮最高分，而是发现“缺地点”后改查集合地点，发现“本次”不清楚后查状态、有效期或历史。参考 [助手第二轮查询 ↗](../../../apps/server/src/assistant/runtime.ts#L627 "支持常规助手接收最多三条后续搜索请求并合并第二轮证据。") [Agent 搜索与章节导航 ↗](../../../apps/server/src/knowledge/agent-research.ts#L450 "支持 Agent 搜索原件时关闭浏览去重、返回目录节点，并可按章节继续补读。")

提交前，研究层会检查每个引用是否来自本次授权材料、历史 revision 是否属于同一来源、行范围与可见性是否有效，再把模型使用的引用别名还原成固定原文锚点。关键事实应引用原件；知识和记忆用于组织理解，并沿 references 回到原文。参考 [固定引用校验 ↗](../../../apps/server/src/assistant/research.ts#L105 "支持校验授权材料、历史 revision、行范围与可见性，并映射成固定原文证据。")

复杂机制、跨来源冲突或会改变结论的关键前提，可以启动独立答案复核；简单直接查值不强制。复核者读取原问题、候选答案和**同一封存材料快照**，可自行搜索补读，但不接收作者调查笔记，也不会递归再找复核者。若作者声明需要复核，未完成、未读取意见或有实质问题却原样提交都会被拦住。参考 [独立答案复核门禁 ↗](../../../apps/server/src/assistant/answer-review.ts#L88 "支持复核适用场景、后台任务行为，以及声明复核后必须读取并吸收实质意见。") [同快照独立调查 ↗](../../../apps/server/src/assistant/answer-review.ts#L225 "支持复核者使用同一封存材料和原问题独立搜索，不接收作者调查笔记且没有递归复核。")

<a id="limits"></a>
## 当前实现能做什么，不能保证什么

当前已有统一结果合同、结构化原件单位、ICU/BM25、锁定中文向量、符号定义与名称级调用候选、浏览去重与助手候选分离、固定 revision 的整节补读、Agent 自主补查和可选独立复核。

仍不能保证：第一名一定能回答、多项答案要点都进入有限候选、跨材料自动判断“本次”与旧记录、完整跨文件调用链、可靠的跨轮对象解析或完整时态检索。当前融合是分支归一化后的排名累加；标准 RRF 和完整答案要点覆盖选择仍是后续工作。参考 [当前融合与向量回退 ↗](../../../apps/server/src/retrieval/unified.ts#L408 "支持当前分支融合公式、向量失败时回退，以及可选 reranker 只处理有限候选。") [候选与上下文的当前边界 ↗](../../../docs/reader-first/retrieval-redesign.md#L19 "支持候选、回答上下文和阅读列表分离，并列明答案要点选择、跨文件与跨轮能力仍有限。")

时间尤其容易被误解：`timeRange` 过滤的是捕获 revision 的时间，不是事件时间或历史 as-of；`effectiveAt` 也只会检查材料说明中已明确保存的 `validFrom/validUntil`。新上传的旧记录不因此成为当前事实，没有正式时间说明的材料也不会自动被排除。参考 [捕获时间过滤语义 ↗](../../../apps/server/src/retrieval/port.ts#L96 "支持 timeRange 是捕获 revision 时间而非事件时间或历史 as-of。") [明确有效期过滤 ↗](../../../apps/server/src/retrieval/unified.ts#L231 "支持 effectiveAt 只在已有材料说明时检查 validFrom 与 validUntil。")

可选 cross-encoder 只重排召回池前部的局部段落，看不到池外材料；当前默认配置只有中文 embedding，没有启用 reranker。既有对照也没有显示稳定收益，所以不能把“有重排代码”写成“默认中文排序已解决”。参考 [可选局部重排 ↗](../../../apps/server/src/retrieval/unified.ts#L547 "支持 cross-encoder 只处理融合后的前部候选，并与原融合分混合。") [重排实测边界 ↗](../../../docs/reader-first/retrieval-evaluation.md#L42 "支持重排输入与候选缺失会影响结果，且现有模型实验未显示稳定全局收益。")

<a id="diagnose"></a>
## 从遗漏现象找到修改入口

沿示例排查时，先判断问题落在哪一层：

| 现象 | 主要入口 |
| --- | --- |
| 预算或地点根本不在候选 | `retrieval/units.ts` 检查检索单位；`retrieval/unified.ts` 检查全文、向量、符号、范围过滤与融合 |
| 命中“八十元”却丢掉同节适用条件 | `retrieval/context.ts` 检查完整节、上级引言和可见性；`assistant/runtime.ts` 检查证据组装 |
| 两项材料都给齐，答案只写了一项 | 检查 Agent 的调查、事实笔记、回答选择与提交过程，不要用界面去重或重排掩盖 |
| 旧记录压过当前说明 | 先核对正式 role/status/validFrom/validUntil 与 revision/history，再检查 `unified.ts` 的适用性排序 |

这套定位与当前设计的三层判断一致：候选、回答上下文、阅读列表各负其责；上下文改进不代表整体排序已经改善，Agent 最终补查成功也不代表基础召回已经好用。参考 [候选与上下文的当前边界 ↗](../../../docs/reader-first/retrieval-redesign.md#L19 "支持候选、回答上下文和阅读列表分离，并列明答案要点选择、跨文件与跨轮能力仍有限。") [当前检索进度与限制 ↗](../../../docs/reader-first/progress.md#L41 "支持上下文补读已实现但标准融合、要点覆盖和基础排序仍未解决。")
