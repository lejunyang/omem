# 一次提问如何找到答案：召回、上下文与 RAG

用一条“从群消息寻找整体讲解，再定位原件与助手入口”的教学路线，解释顶部搜索、知识搜索和助手如何共享统一召回，又为何得到不同结果；说明全文、中文短词、符号、向量、知识与记忆各自的作用，命中后的结构上下文与固定引用，助手的自主补查方式，以及中文模型、可选重排和时间检索的现实边界。最后给出区分召回问题、上下文问题与回答问题的可操作方法和修改入口。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先走一遍：从群消息到可修改的实现

下面是**教学示意**，用于说明阅读路线，不保证某个搜索词一定得到固定排名。

假设群里先前有一条普通消息，讨论“新消息怎样进入收件箱并触发助理”。当前实现会先判断它是否是已绑定 owner 发出的助理请求；群聊还要求提及机器人。满足条件的消息直接进入助手分支，该分支的各条处理路径都会返回，因此当前这条提问不会继续落入后面的群监控采集分支。参考 [群消息进入助手并退出分支 ↗](../../../apps/server/src/integrations/lark/realtime.ts#L524 "支持已绑定 owner、群聊提及机器人，以及助手分支各处理路径返回、不继续进入群监控采集的控制流说明。")

群监控不要求用户在首条消息到达前另行预建目标：机器人加入群时，活动连接会把该群设为启用监控；对未进入助手分支、不是机器人自身、信息完整的普通群消息，如果尚无监控目标，当前路径也会补建启用目标。只有查到仍为 active 且 capture_enabled=1 的目标，消息才会被整理为文本、富文本或图片等 Capture parts，并以聊天来源保存；机器人被移出群时，该群目标会被禁用。参考 [群监控的加入与移出状态 ↗](../../../apps/server/src/integrations/lark/realtime.ts#L422 "支持机器人加入群时启用监控目标、移出群时禁用目标的生命周期。") [普通群消息自动建立监控并采集 ↗](../../../apps/server/src/integrations/lark/realtime.ts#L602 "支持普通群消息在缺少目标时补建启用监控，随后只对活动且允许采集的目标构造并保存聊天来源。")

随后，开发者在 Web 顶部搜索中用自己的说法查询“群消息如何进入助理”。页面会立即列出实际命中，并显示结果类型、章节或原文行范围；读者可以先读整体讲解，再打开对应原文。若还想得到一段围绕问题组织的说明，再明确点击“综合回答”；原始命中仍留在下方，可以与回答对照，完成后也能继续追问。参考 [搜索页的实际命中 ↗](../../../apps/web/src/App.vue#L685 "支持顶部搜索展示结果类型、章节、行范围以及阅读讲解和原文入口。") [综合回答与继续追问 ↗](../../../apps/web/src/SearchAnswer.vue#L205 "支持综合回答需明确触发、保留实际命中并允许同会话继续追问。")

这里还有一道硬边界：群会话只能看到同一 chatId 已采集的证据，不能顺手搜索 owner 的私聊材料。因此更准确的说法是：**此前已收录的同群消息可以成为证据；当前提问作为 userText 进入助手回合。**参考 [群会话证据可见性 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L90 "支持群会话只能读取同一 chatId 已采集证据的边界。")

<a id="responsibilities"></a>
## 搜索找材料，回答组织结论

**召回**负责从材料、讲解、记忆和事项中提出候选，并保留“到哪里重读原文”的固定位置；**回答**负责选择候选、补读缺失背景、组织语言并只引用真正使用的来源。RAG（检索增强生成）就是把这两步接起来：模型不是只靠参数记忆作答，而是先得到可核对的上下文。

三个入口共用一个 RetrievalPort/UnifiedRetrieval 基础。服务只创建一套 retrievalService，并把同一个 assistantRetrieval 注入知识路由和 AssistantRuntime；它们不是三套彼此独立的索引。参考 [共享召回服务装配 ↗](../../../apps/server/src/app.ts#L100 "支持同一个 retrieval 实例同时注入知识路由和助手运行时。")

| 入口 | 默认视角 | 为什么结果仍会不同 |
| --- | --- | --- |
| 顶部搜索 | 综合查找，最多 30 条 | 可混合原件、讲解、记忆和事项，也可选择“理解概念、定位实现、了解背景、跟进事项”等 purpose。参考 [顶部搜索查询范围 ↗](../../../apps/server/src/app.ts#L313 "支持顶部搜索的默认 purpose、limit 和统一 search 调用。") |
| 知识搜索 | 理解概念 | 强制只找 knowledge，可限定分类路径，并让每篇文章只保留最佳章节；它是“只看讲解”的窄视图。参考 [知识搜索的窄视图 ↗](../../../apps/server/src/knowledge/api.ts#L118 "支持知识搜索限定 knowledge、topicPath、concept purpose 和每文章最佳章节。") |
| 助手 | 围绕当前问题取最多 16 条 | 还要应用会话可见性；原件命中转为 evidence，讲解、记忆和事项转为 background，但其中的固定原文 references 仍可成为引用。参考 [助手召回与上下文组装 ↗](../../../apps/server/src/assistant/runtime.ts#L913 "支持助手的 limit、可见性过滤、固定范围 evidence 和非 source background 组装。") |

purpose 是排序偏好，不是事实判断：例如 implementation 偏代码，background 偏讲解和记忆，follow-up 偏事项、记忆与会话。最终结果还会限制同一 owner 的摘录数并合并相同正文，避免一份材料占满首屏。参考 [用途偏好、时间偏好与去重 ↗](../../../apps/server/src/retrieval/unified.ts#L477 "支持 purpose 排序偏好、follow-up 的有限新近度，以及同 owner 限制和相同正文去重。")

<a id="routes"></a>
## 六种线索各自解决什么

这些路线不是六个互斥搜索框，而是统一召回中的互补信号：

| 线索 | 最擅长的任务 | 实际机制 |
| --- | --- | --- |
| 全文 | 已知原词、标题、路径或实现词 | 结构单位进入 SQLite FTS5；标题、上下文和正文使用不同 BM25 权重，并检查查询词在同一局部段落中的覆盖。参考 [全文候选与相关性 ↗](../../../apps/server/src/retrieval/unified.ts#L305 "支持 FTS5 BM25 加权、局部词覆盖和候选截断的全文召回机制。") |
| 中文短词 | “重试”这类容易被切开的领域词 | 查询和索引都使用 ICU 中文分词；纯汉字的 2–8 字短查询还保留整句复合词。参考 [中文分词与短复合词 ↗](../../../apps/server/src/retrieval/relevance.ts#L1 "支持 ICU 查询分词和 2 到 8 字短复合词保留。") |
| 符号 | 从讲解跳到具体函数或方法 | 代码按 AST 符号范围保留完整函数/方法，局部声明不从所属操作中拆走；纯 ASCII 标识符走精确查找，要求正文或上下文真实包含该名字，命中定义名时再加权。参考 [代码结构检索单位 ↗](../../../apps/server/src/retrieval/units.ts#L90 "支持完整函数方法、所属操作内局部声明和顶层配置的结构化投影。") [精确符号召回 ↗](../../../apps/server/src/retrieval/unified.ts#L296 "支持 ASCII 标识符的 exact lookup、实际包含校验和定义名加权。") |
| 向量 | 词面不同、语义相近的中文表达 | 锁定的 BGE-small-zh-v1.5 分别编码查询与正文；长单位只为向量切重叠窗口，不改变阅读锚点。模型不可用或检索报错时，系统保留词法结果。参考 [锁定的中文向量模型 ↗](../../../apps/server/src/retrieval/embedding.ts#L14 "支持 BGE 模型锁定、本地 q8 CPU、查询指令和禁止远程下载。") [语义召回与词法降级 ↗](../../../apps/server/src/retrieval/unified.ts#L370 "支持精确查询跳过向量、语义窗口命中及异常时保留词法结果。") |
| 知识 | 先理解完整机制 | 已接受且依据可用的文章按可读段落建立 knowledge unit，返回文章章节和该段实际引用的原文范围；它是背景讲解，不是第二份独立事实。参考 [知识段落与原文引用 ↗](../../../apps/server/src/retrieval/units.ts#L630 "支持已接受文章按段落建 unit，并保留文章版本、章节和原文 references。") |
| 记忆 | 找已应用的事实、经历或方法状态 | 只有 active memory 进入统一检索，并携带 evidence set 回到原件；它适合背景和后续跟进，不能替代原始依据。参考 [记忆单位与证据集 ↗](../../../apps/server/src/retrieval/units.ts#L804 "支持仅 active memory 入索引，并通过 evidence set 保留原件 references。") |

所以在贯穿示例中，可以先用自然中文找到“群消息进入助理”的讲解；确认方向后，再查 LarkEventInbox 或 AssistantRuntime.retrieveContext 这样的符号，定位完整方法。不要把“语义相近”误当成“已经回答了问题”。

<a id="context"></a>
## 命中一个片段后，怎样补成可读上下文

系统首先通过**检索单位本身**减少断章：Markdown 保留标题路径，并把以冒号结尾的引导句与后续列表、表格或代码合在一起；代码保留完整函数/方法；聊天单位附带会话、发言人、事件时间和回复关系。参考 [文档块保持连贯 ↗](../../../apps/server/src/retrieval/units.ts#L31 "支持 Markdown 标题路径以及引导句与列表、表格、代码合并。") [会话结构上下文 ↗](../../../apps/server/src/retrieval/units.ts#L265 "支持检索单位附带会话、发言人、事件时间和回复关系。")

~~~mermaid
flowchart LR
  Q[用户问题] --> U[结构化检索单位]
  U --> H[混合候选与用途排序]
  H --> A[固定 Revision 与行范围]
  A --> E[原件证据]
  A --> B[讲解或记忆背景]
  E --> R[助手补读并回答]
  B --> R
~~~

每个原件锚点包含材料 key、固定 revision、摘要、起止行和 fragmentIds；知识结果另外保留文章版本、章节和回到原件的 references。参考 [固定目标与原文锚点 ↗](../../../apps/server/src/retrieval/port.ts#L23 "支持固定 revision、行范围及原文 references 的表达。")

助手拿到统一检索结果后，会按每个 reference 读取精确原文范围并生成 citationId。source 命中成为 evidence；knowledge、memory、task 成为 background，同时携带可回原文的 citationIds。参考 [助手召回与上下文组装 ↗](../../../apps/server/src/assistant/runtime.ts#L913 "支持助手的 limit、可见性过滤、固定范围 evidence 和非 source background 组装。")

一个容易混淆的边界是：当前 Unified search 主分支主要依靠结构单位和固定 reference，**不会无条件为每个命中自动塞入前后相邻 fragment**。同节标题、前一片、后一片的自动扩展位于旧的 source-only 兼容路径；它是在没有统一 search 时使用的回退行为。参考 [旧兼容路径的邻段扩展 ↗](../../../apps/server/src/assistant/runtime.ts#L972 "支持相邻 fragment 扩展只存在于 source-only 兼容路径，而非统一 search 主分支。")

<a id="assistant"></a>
## 助手怎样继续查，并守住引用边界

初始命中只是调查线索，不是强制阅读顺序。生产 ACP 助手会建立只读研究工作区，把当前问题、同会话历史、初始 evidence 和 background 交给调查 Agent。参考 [助手自主调查入口 ↗](../../../apps/server/src/assistant/acp-model.ts#L162 "支持把问题、历史、初始匹配和讲解背景交给只读 ACP 调查工作区。")

Agent 可以继续搜索材料和知识，也能读取完整材料或章节；需要更多背景时，还可以查活动记忆、固定历史和代码定义。参考 [读取材料与章节 ↗](../../../apps/server/src/knowledge/agent-research.ts#L388 "支持调查 Agent 按需读取完整材料范围或指定文档章节和代码符号。") [搜索原始材料 ↗](../../../apps/server/src/knowledge/agent-research.ts#L411 "支持调查 Agent 通过统一召回搜索固定快照中的原始材料。") [搜索知识讲解 ↗](../../../apps/server/src/knowledge/agent-research.ts#L485 "支持调查 Agent 搜索知识章节，并保留讲解关联的原文 references。") [记忆与代码导航 ↗](../../../apps/server/src/knowledge/agent-research.ts#L593 "支持调查 Agent 搜索或读取活动记忆，并检查代码定义、导入和候选调用。") [固定材料历史 ↗](../../../apps/server/src/knowledge/agent-research.ts#L721 "支持调查 Agent 列出或读取材料的固定历史版本。")

补读后的引用不是一段随意生成的文字。Agent 必须提交本次授权 catalog 中的材料 key 和真实行范围；服务端重新解析对应原文，检查版本、可见性和范围，再把它变成 evidence。研究模式也禁止顺带执行事项操作。参考 [补读引用的服务端校验 ↗](../../../apps/server/src/assistant/research.ts#L95 "支持对授权材料、固定版本、可见性、真实行范围和研究模式进行再次校验。")

最终 Runtime 只接受它实际供应过的 citationId，模型虚构或越界的引用会被过滤。继续追问时，同一会话会带入已完成的历史回合，并合并上一轮工作上下文，因而“按这个继续看实现”不必从零开始。参考 [最终引用白名单 ↗](../../../apps/server/src/assistant/runtime.ts#L839 "支持 Runtime 只保留实际供应过的 citationId。") [同会话历史与工作上下文 ↗](../../../apps/server/src/assistant/runtime.ts#L568 "支持继续追问时读取已完成历史回合并合并上一轮工作上下文。")

这也解释了“搜索”和“综合回答”为何并列展示：搜索结果让读者检查首次召回；综合回答允许助手越过首批候选继续补查。后者成功不能证明前者排序已经合格。

<a id="limits"></a>
## 中文模型、重排与时间问题的现实边界

仓库默认检索配置启用 memory-zh；实现只接受锁定 revision 的 BGE-small-zh-v1.5，本地 q8/CPU 运行且禁止远程下载。但“配置启用”不等于任意进程已经完成索引：健康状态仍可能是 indexing、ready、disabled 或 degraded，语义失败时会退回词法。参考 [默认中文检索配置 ↗](../../../config/retrieval.json#L1 "支持仓库默认启用 memory-zh，且默认配置没有 reranker 字段。") [语义索引健康状态 ↗](../../../apps/server/src/retrieval/unified.ts#L71 "支持索引后台推进以及 disabled、indexing、ready、degraded 等可观察状态。")

中文 cross-encoder 重排器是可选项，只有配置 reranker 才加载。当前仓库默认配置没有写该项；已有真实对照同时出现收益和退步，因此没有默认启用。重排器即使可用，也只是重新评估候选，不能找回候选截断前已经丢失的正确方法，更不能保证答案完整。参考 [可选重排的配置决定 ↗](../../../docs/reader-first/component-integration.md#L45 "支持重排器为显式选项、真实对照有收益也有退步且未默认启用。")

时间要先分清三件事：

- timeRange 过滤的是 revision 的捕获时间，不是业务事件时间，也不是“当时世界是什么样”的 as-of 查询。参考 [时间查询字段语义 ↗](../../../apps/server/src/retrieval/port.ts#L97 "支持 timeRange 过滤捕获 revision 时间，而不是事件时间或历史 as-of。")
- effectiveAt 只在读者明确提供时，按材料说明中的 validFrom/validUntil 过滤。参考 [有效期过滤 ↗](../../../apps/server/src/retrieval/unified.ts#L218 "支持 effectiveAt 仅按材料说明中的 validFrom 和 validUntil 区间过滤。")
- eventAt 会保存在会话、记忆和事项单位里，目前只在 follow-up 对这些类型提供有限的新近度偏好。参考 [用途偏好、时间偏好与去重 ↗](../../../apps/server/src/retrieval/unified.ts#L477 "支持 purpose 排序偏好、follow-up 的有限新近度，以及同 owner 限制和相同正文去重。")

这些字段尚未组成完整时态推理。类似“上周发生了什么”或“当时规则是什么”的问题，仍需要查固定历史并补读。

当前相关性也有已知边界：长自然问题可能让明确方法在候选截断前丢失；主题相似的计划或调研可能靠前；一份混合文档只有一个用途标签时会误导；跨文件业务链仍依赖 Agent 调查。参考 [当前检索质量边界 ↗](../../../docs/reader-first/current-system.md#L21 "支持长问题漏方法、主题噪声、混合用途、可选重排和跨文件调查等现实限制。")

<a id="diagnosis"></a>
## 如何判断问题在哪，并找到修改入口

先在搜索页看“实际搜索命中”的类型、route、章节和行范围，再判断层级：

1. **正确材料根本没进候选**：这是召回或索引问题。先看 relevance.ts 的分词与 exact lookup，units.ts 的结构单位和上下文，unified.ts 的过滤、融合、purpose 与截断；语义相关问题再看 embedding.ts，可选重排看 reranker.ts。
2. **顶部搜索有原件，知识搜索没有**：先确认是不是期待原文出现在“只找讲解”的入口；再看 knowledge/api.ts 的 kinds=knowledge、topicPath、当前文章版本和每篇文章去重。
3. **正确原文和引用已进入助手输入，但答案仍遗漏或组织错误**：这是回答或补读问题。看 assistant/runtime.ts 的 evidence/background 组装、assistant/acp-model.ts 的调查入口、assistant/research.ts 的引用校验，以及 SearchAnswer.vue 的 research 交互。
4. **群消息没有进入预期路径**：看 realtime.ts 的 owner/@bot 分流、群监控 Capture，再看 lark/runtime.ts 的群会话可见性和 AssistantRuntime.turn 调用。
5. **时间答案不对**：先确认问的是捕获时间、事件时间还是有效期；当前没有完整 as-of 语义，不应先调排序权重掩盖时间模型缺口。

最实用的判定规则是：**给齐材料仍答不好，属于生成/回答失败；给齐能答好，但检索后答不好，属于召回或上下文失败。**材料本身缺信息时应明确未知，而不是用主题相似段落补答案。参考 [召回与回答失败的判别 ↗](../../../docs/reader-first/current-system.md#L62 "支持用给齐材料后的表现区分生成失败与召回或上下文失败。")
