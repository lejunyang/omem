# 一次提问如何找到答案：搜索、上下文与 RAG

从一条群消息和一次中文提问出发，解释顶部搜索、知识搜索与助手如何共用统一召回，又为何返回不同结果；说明全文、符号、向量、知识、记忆和事项各自解决的问题，命中后如何补读完整上下文并形成固定引用，以及如何区分召回故障、上下文不足和回答故障。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 从一条群消息开始

**教学示意：**群里有人讨论“消息怎样进入助理”。已绑定的 owner 在群聊中提及机器人时，事件会直接交给助理；没有走这条即时问答分支的群消息，则可沿群监控路径保存成带会话、发送者和事件时间的原始聊天材料。两者作用不同：前者发起一次回答，后者让这段经历以后可以被搜索。参考 [群消息触发助理 ↗](../../../apps/server/src/integrations/lark/realtime.ts#L524 "支持已绑定 owner 在群聊提及机器人时，事件被路由给助理。") [群消息保存为原件 ↗](../../../apps/server/src/integrations/lark/realtime.ts#L602 "支持未走即时助理分支的群消息通过群监控保存为带上下文和事件来源的聊天材料。")

~~~mermaid
flowchart LR
  A[飞书群消息] --> B{已绑定 owner 且提及机器人?}
  B -->|是| C[群会话]
  C --> D[AssistantRuntime]
  B -->|否| E[聊天原件]
  E --> F[统一搜索]
  F --> G[实际命中或助手补查]
~~~

群会话的可见范围还会收紧到该群实际采集的证据，不能读取 owner 私聊或其他群材料。这个约束发生在服务端，不依赖模型自觉。参考 [群会话证据可见性 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L90 "支持群会话只允许读取该群采集的证据，并说明可见性策略注入 AssistantRuntime。")

之后，开发者可以在顶部搜索里用自己的描述找整体讲解，再从讲解落到收件箱、会话和助理入口。这里不预设某个搜索词必然排第几；示意的是一条真实可走的阅读路线，而不是排名承诺。

<a id="responsibilities"></a>
## 搜索负责找候选，助手负责形成回答

**召回**回答“哪些材料值得进入视野”，**回答或调查**回答“这些材料能否支持结论，还要补读什么”。服务启动时只构造一份统一召回实例，并把它交给知识路由、普通助手和顶部搜索接口，因此三处共享索引、候选融合与固定来源表达。参考 [统一召回装配 ↗](../../../apps/server/src/app.ts#L93 "支持应用只创建一份 assistantRetrieval，并同时交给知识路由和 AssistantRuntime。")

| 入口 | 对统一召回增加的约束 | 读者看到什么 |
| --- | --- | --- |
| 顶部搜索 | 默认综合用途，最多取 30 条；可按用途、材料角色和有效时间筛选 | 原件、讲解、记忆、事项的混合命中 |
| 知识搜索 | 只取 knowledge，默认用于理解概念，可限定分类；每篇文章只保留最相关章节 | 可直接阅读的讲解 |
| 助手 | 默认取 16 条并应用会话可见性；原件转成 evidence，其他类型作为 background | 初始线索，以及调查后的回答 |

顶部接口直接调用这份召回；知识接口则显式限定 knowledge 并按文章去重；助手把每条命中的原始引用重新读取成可用证据。参考 [顶部搜索接口 ↗](../../../apps/server/src/app.ts#L313 "支持顶部搜索使用统一召回，开放用途、代码意图、材料角色和 effectiveAt，但未开放 timeRange。") [知识搜索约束 ↗](../../../apps/server/src/knowledge/api.ts#L118 "支持知识搜索只取 knowledge、限定主题，并为每篇文章返回最佳匹配章节。") [助手上下文装配 ↗](../../../apps/server/src/assistant/runtime.ts#L913 "支持助手按可见性取统一命中，将原件引用转为 evidence，并把非原件命中转为 background。")

所以“共用召回”不等于返回完全相同的列表。搜索页还特意把“综合回答”和“实际搜索命中”并排保留：前者需要用户显式启动调查，后者可用来检查首轮召回是否真的找到了关键材料。参考 [搜索页双入口 ↗](../../../apps/web/src/App.vue#L693 "支持页面同时展示综合回答入口和实际搜索命中，并允许选择搜索用途。")

<a id="routes"></a>
## 一条中文问题会经过哪些候选路线

统一检索不是只做一次关键词匹配，而是让不同表示各司其职：

| 路线 | 适合解决的问题 | 不能替代什么 |
| --- | --- | --- |
| 全文与中文短词 | 正文确实出现业务词、文件名或正式别称 | 词面相同不代表内容能回答 |
| 符号与调用候选 | 已知函数、方法或组件名，需要找定义或调用位置 | 不是类型解析后的完整调用图 |
| 中文向量 | 用户说法与材料措辞不同，但语义接近 | 相似度不是答案正确率 |
| 知识讲解 | 先读跨材料的整体解释 | 派生讲解仍要回到原件 |
| 记忆与事项 | 找已应用的当前事实、经历和待办状态 | 不能替代原始聊天事实 |

中文全文路线把标题、上下文和正文写入 FTS，并用 ICU 中文分词后交给 BM25；代码则按 AST 得到的完整函数、方法或组件范围建立单位。参考 [中文全文索引 ↗](../../../apps/server/src/retrieval/units.ts#L918 "支持检索单位写入 FTS，并通过 ICU 中文分词形成可供 BM25 查询的索引文本。") [结构化检索单位 ↗](../../../apps/server/src/retrieval/units.ts#L31 "支持 Markdown 连贯块和 AST 完整操作范围作为检索单位，保留标题路径与完整方法。")

明确的操作名有独立符号候选，不必只靠整句全文排名；询问 callers 时返回按名称找到的调用位置。它会优先较小的包围方法并保留行号，但同名对象、别名和动态调用仍需结合上下文确认。参考 [符号与调用候选 ↗](../../../apps/server/src/retrieval/unified.ts#L312 "支持操作名独立召回，以及 callers 按名称返回带行号的候选调用位置。")

向量路线把查询和正文分别编码，选择每个单位最相近的窗口，再与全文和符号候选融合；当前中文模型使用锁定的离线 BGE-small-zh-v1.5、q8 CPU 推理，并为查询添加检索指令。参考 [全文向量符号融合 ↗](../../../apps/server/src/retrieval/unified.ts#L476 "支持查询向量、单位窗口相似度、阈值筛选与全文和符号候选融合。") [离线中文向量模型 ↗](../../../apps/server/src/retrieval/embedding.ts#L14 "支持锁定 BGE-small-zh-v1.5 快照、禁止远程模型、q8 CPU 推理和查询指令。")

事项投影当前版本和状态，记忆只投影 active 状态并保留原始证据引用；知识文章只有在已接受、依赖材料仍可用时才进入召回，正文中的引用会继续展开成固定原件范围。参考 [当前事项投影 ↗](../../../apps/server/src/retrieval/units.ts#L736 "支持事项以当前版本、状态、正文和原始证据范围进入统一检索。") [当前记忆投影 ↗](../../../apps/server/src/retrieval/units.ts#L804 "支持只投影 active 记忆，并保留其原始证据引用和有效时间。") [知识依据展开 ↗](../../../apps/server/src/retrieval/units.ts#L589 "支持只投影已接受且依赖可用的文章，并把正文引用递归展开为原件范围。")

<a id="context"></a>
## 命中片段之后，怎样补成可读上下文

保存单位、检索单位和讲解单位彼此分开。Markdown 按标题保留连贯块，并把介绍句与紧随的表格、列表或代码合在一起；代码检索单位保留完整操作，而不是只留下局部变量。这样首个命中既足够定位，也仍能打开完整章节或方法。参考 [结构化检索单位 ↗](../../../apps/server/src/retrieval/units.ts#L31 "支持 Markdown 连贯块和 AST 完整操作范围作为检索单位，保留标题路径与完整方法。")

每个原件命中携带固定的材料 key、revision、digest、起止行和 fragment 列表；讲解、记忆或事项也可以携带其原件引用。助手据此读取原文，而不是把检索摘要冒充事实。参考 [固定来源锚点 ↗](../../../apps/server/src/retrieval/port.ts#L25 "支持命中携带材料键、revision、digest、行范围和 fragment，并区分原件、讲解、记忆与事项目标。") [助手上下文装配 ↗](../../../apps/server/src/assistant/runtime.ts#L913 "支持助手按可见性取统一命中，将原件引用转为 evidence，并把非原件命中转为 background。")

如果初始候选不够，当前生产助手会创建受控研究工作区，读取初始命中后自行搜索原件、完整章节、符号线索、已有讲解、记忆或历史版本。参考 [助手自主调查 ↗](../../../apps/server/src/assistant/acp-model.ts#L162 "支持生产助手准备研究工作区，并允许围绕初始线索补读材料后提交结构化结果。")

调查回复可以不附来源引用；当助手选择提交引用时，必须给出获授权材料的 key 和精确行范围，引用历史正文时还要给出对应 revision。宿主会对这些已提交的引用检查授权材料、版本、范围和可见性；正文中若使用引用编号，也必须能映射到已提交定位。这些约束保证“实际引用”可追溯，但不表示每个回答天然都有引用，也不逐句判断所有陈述是否被覆盖。参考 [调查回复引用合同 ↗](../../../packages/contracts/src/assistant.ts#L5 "支持调查回复要求 citations 为数组但不设最小数量，因此可以为空；有引用时才需要材料定位字段。") [已提交引用的校验 ↗](../../../apps/server/src/assistant/research.ts#L95 "支持宿主只对实际提交的引用核对授权材料、历史版本、行范围和可见性，并校验正文引用编号有定位。")

兼容的 source-only 路径还会在同一章节内补标题、前一个和后一个 fragment，并逐项检查可见性。这解释了旧路径的“相邻上下文”，但不意味着统一搜索的每个结果都会自动拼接邻居。参考 [相邻原件上下文 ↗](../../../apps/server/src/retrieval/context.ts#L5 "支持兼容原件路径在同一章节内补标题和相邻 fragment，并逐项执行可见性过滤。")

<a id="limits"></a>
## 当前模型、重排与时间能力的边界

当前配置启用中文 embedding，模型别名为 `memory-zh`，没有配置 reranker，因此默认运行状态是“向量开启、交叉编码重排关闭”。模型文件由 osdk 提供锁定快照，应用只做本地校验和离线读取，不会在查询时联网下载。参考 [当前检索配置 ↗](../../../config/retrieval.json#L1 "支持当前启用 memory-zh embedding 且未配置 reranker。") [离线中文向量模型 ↗](../../../apps/server/src/retrieval/embedding.ts#L14 "支持锁定 BGE-small-zh-v1.5 快照、禁止远程模型、q8 CPU 推理和查询指令。")

若显式配置 reranker，它只处理融合后的前 40 个单位，并从长文本的词面窗口与向量窗口中选局部段落评分。它可以改善局部相关性，却不能保证整篇材料足以回答，也不能把局部高分当成机制已经理解。参考 [可选局部重排 ↗](../../../apps/server/src/retrieval/unified.ts#L545 "支持可选重排器只处理前 40 个融合候选，并以局部 passage 最高分参与最终排序。")

时间过滤要先看入口和结果类型。统一检索内部的 `timeRange` 比较每个检索单位的 `provenance.time`；这个字段并非所有类型都表示同一种时间：原件使用 revision 捕获时间，知识使用文章生成时间，事项使用事项创建时间，记忆使用记忆更新时间。参考 [统一时间与有效期过滤 ↗](../../../apps/server/src/retrieval/unified.ts#L225 "支持 effectiveAt 检查材料有效期，而 timeRange 实际比较各检索单位的 provenance.time。") [原件时间字段 ↗](../../../apps/server/src/retrieval/units.ts#L409 "支持原件检索单位把 revision 的 created_at 写入 provenance.time。") [知识时间字段 ↗](../../../apps/server/src/retrieval/units.ts#L713 "支持知识检索单位把文章生成时间写入 provenance.time。") [事项时间字段 ↗](../../../apps/server/src/retrieval/units.ts#L780 "支持事项检索单位把事项创建时间写入 provenance.time。") [记忆时间字段 ↗](../../../apps/server/src/retrieval/units.ts#L860 "支持记忆检索单位把记忆更新时间写入 provenance.time。")

当前顶部 `/api/search` 没有开放 `timeRange`，只开放 `effectiveAt`；后者依据材料说明里显式保存的有效期筛选。因此顶部搜索既不是按统一“捕获时间”过滤，也不是“回到上周还原当时全部状态”的历史 as-of 查询。参考 [顶部搜索接口 ↗](../../../apps/server/src/app.ts#L313 "支持顶部搜索使用统一召回，开放用途、代码意图、材料角色和 effectiveAt，但未开放 timeRange。") [统一时间与有效期过滤 ↗](../../../apps/server/src/retrieval/unified.ts#L225 "支持 effectiveAt 检查材料有效期，而 timeRange 实际比较各检索单位的 provenance.time。")

最后，材料用途和状态会影响导航偏好：计划、调研、示例或历史材料通常被降权，但这只是排序倾向，不是事实裁决；未知材料仍可进入候选。参考 [材料用途排序偏好 ↗](../../../apps/server/src/retrieval/unified.ts#L279 "支持计划、调研、示例和历史状态只作为降权偏好，而非事实判断。")

<a id="diagnosis"></a>
## 如何区分召回问题与回答问题

遇到“答案不对”时，按下面顺序定位：

1. **先看实际搜索命中。**关键讲解或原件完全没出现，优先检查查询用途、材料角色、有效期、会话可见性、中文向量状态，以及 `port.ts`、`units.ts`、`unified.ts` 和 `factory.ts` 的候选与排序逻辑。顶部页面保留实际命中，正是为了让这一步可观察。参考 [顶部搜索接口 ↗](../../../apps/server/src/app.ts#L313 "支持顶部搜索使用统一召回，开放用途、代码意图、材料角色和 effectiveAt，但未开放 timeRange。") [搜索页双入口 ↗](../../../apps/web/src/App.vue#L693 "支持页面同时展示综合回答入口和实际搜索命中，并允许选择搜索用途。")
2. **命中了，但摘录不够。**打开固定章节或完整方法，或让助手继续调查。若要改装配行为，先看 `assistant/runtime.ts` 的 evidence/background 转换和 `assistant/research.ts` 的范围校验；兼容邻居策略在 `retrieval/context.ts`。参考 [助手上下文装配 ↗](../../../apps/server/src/assistant/runtime.ts#L913 "支持助手按可见性取统一命中，将原件引用转为 evidence，并把非原件命中转为 background。") [已提交引用的校验 ↗](../../../apps/server/src/assistant/research.ts#L95 "支持宿主只对实际提交的引用核对授权材料、历史版本、行范围和可见性，并校验正文引用编号有定位。") [相邻原件上下文 ↗](../../../apps/server/src/retrieval/context.ts#L5 "支持兼容原件路径在同一章节内补标题和相邻 fragment，并逐项执行可见性过滤。")
3. **原件齐全，回答仍遗漏或误解。**这是材料选择、阅读或表达问题，应检查 `assistant/acp-model.ts` 的调查入口和回答合同，而不是继续盲目调整召回权重。参考 [助手自主调查 ↗](../../../apps/server/src/assistant/acp-model.ts#L162 "支持生产助手准备研究工作区，并允许围绕初始线索补读材料后提交结构化结果。")
4. **要改群消息入口。**“什么消息触发即时助理”在 `integrations/lark/realtime.ts`；“怎样建立群会话并限制可见证据”在 `integrations/lark/runtime.ts`。参考 [群消息触发助理 ↗](../../../apps/server/src/integrations/lark/realtime.ts#L524 "支持已绑定 owner 在群聊提及机器人时，事件被路由给助理。") [群会话证据可见性 ↗](../../../apps/server/src/integrations/lark/runtime.ts#L90 "支持群会话只允许读取该群采集的证据，并说明可见性策略注入 AssistantRuntime。")

简言之：候选中没有关键证据，是召回、过滤或排序问题；关键证据已在实际命中中、但还缺完整章节，是上下文扩展问题；必要原件已经提供而回答仍错，才是回答问题。
