# 一次提问如何找到答案：搜索、候选评估与上下文

用“这次活动要准备多少钱、到哪里集合”的教学示例，解释 omem 如何把整句问题变成全文、向量与符号候选，可选快速决策怎样保守调整初始候选，命中后又怎样在固定版本中补回章节和父级条件。随后说明如何只围绕金额、地点和对象版本的未解项继续调查，并按召回、候选评估、上下文装配、调查和回答分层定位遗漏。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="what-counts-as-an-answer"></a>
## 先定义“答全”：结果、条件与对象都要有依据

假设已经保存了几份活动材料。当前活动说明的一章写“参加预算八十元”，同章或上级简介还写着“仅限已报名者”“不含交通费”“周三 18 点前确认”；另一章写“在图书馆集合”。库里另有一份旧活动记录，也提到八十元。用户问：

> 这次活动要准备多少钱、到哪里集合？

这是贯穿本文的**教学示例**，不代表一次真实检索，也不预言固定排名。对这个问题，“答全”至少要满足四项：

1. 回答金额；
2. 回答集合点；
3. 把资格、费用范围和截止时间等会改变行动的条件贴近相应结论；
4. 确认“这次”对应哪场活动、哪个版本。

所以，“活动很适合周末参加”即使主题相关，也没有回答金额或地点；旧记录里的“八十元”即使字面完全命中，也不能证明适用于这次。关键前提可能在召回、补读或最终表达时丢失，而引用格式正确本身发现不了这些语义缺口。参考 [可用答案与关键前提 ↗](../../../docs/reader-first/answer-investigation.md#L5 "说明关键前提可能在召回、补读或表达阶段丢失，引用正确不等于语义完整。")

<a id="retrieve-candidates"></a>
## 整句问题先产生候选，而不是直接产生答案

普通助手先把用户整句问题交给检索，最多取得 48 个候选，再进入候选评估和回答上下文装配。首轮关闭的是浏览用途的多样化去重，排序、显式范围和可见性仍然有效；这一步也不会等到“金额、地点和条件全部找齐”才结束。参考 [普通助手的首轮主链 ↗](../../../apps/server/src/assistant/runtime.ts#L977 "说明整句问题的候选规模、检索设置、候选评估和上下文装配的调用顺序。") [候选与覆盖分开 ↗](../../../docs/reader-first/retrieval-redesign.md#L19 "说明助手候选关闭浏览去重但总数有限，尚无完整答案要点覆盖选择。")

Markdown 原件不是整份文件作为一个单元排序。系统按结构 token 生成带真实行号和标题路径的 passage。若一段引导语以中英文冒号结尾，紧随且仍在同一标题路径中的表格、列表、代码块或引用块会与它合成连续 passage；下一章节不会被一起吞入。这能避免只返回“可以这样交办：”之类无法独立理解的引导句，却不判断该例子是否回答当前问题。参考 [Markdown 检索段 ↗](../../../apps/server/src/retrieval/units.ts#L33 "说明结构化 passage、标题路径及冒号引导语与结构块的合并边界。")

候选主要从三条路线汇合：

- **全文路线**用 FTS/BM25 找字面匹配，适合“八十元”“图书馆”和精确名称；
- **向量路线**在 embedding 可用且查询不是精确标识符时寻找语义窗口，例如问题写“要带多少活动费”，原文写“参加预算”；
- **符号路线**为代码名称和导航补充入口。

这些路线的分值尺度不同，系统按各路线中的名次用 RRF 融合。没有向量模型、查询是精确标识符，或向量执行失败时，仍可沿全文和符号路线继续。这里对教学示例的路线分工只是解释各路线擅长什么，不保证某次查询一定由哪一路命中。参考 [全文、向量与 RRF ↗](../../../apps/server/src/retrieval/unified.ts#L408 "说明 BM25、向量和符号候选如何融合，以及向量不可用或失败时如何降级。")

材料说明在这一阶段提供导航信号，但不是另一份事实来源。概念及别称只投影到与标注行范围相交的 passage；用途和状态形成默认排序先验，历史、拟议、被替代、计划、调研或示例材料可能后排，但不会自动失效。只有调用方显式给出材料角色或 effectiveAt 时，才按相应角色或材料声明的有效期过滤，捕获时间不会代替有效时间。参考 [材料说明怎样影响搜索 ↗](../../../docs/reader-first/material-understanding.md#L17 "解释用途、状态、有效时间与概念别称是导航信号而非事实裁决。") [显式过滤与适用性先验 ↗](../../../apps/server/src/retrieval/unified.ts#L231 "说明材料角色和有效时间过滤，以及用途和状态的默认排序先验。")

个人私有会话如果已经保存了正式项目，首轮候选还会在排序截断前限定为该项目来源中的可见材料；没有已确认项目时，从整个可见库开始。这个项目范围只是阅读起点，不是权限边界，后续原生调查仍可查询其他已授权材料。参考 [会话项目的阅读起点 ↗](../../../docs/reader-first/project-contexts.md#L31 "说明项目成员限定后续初始召回，但不成为权限边界或事实裁决。")

因此，旧活动记录可能因“八十元”进入候选，当前活动的泛泛介绍也可能因语义接近进入候选。**候选表示值得读，不表示当前适用，更不表示答案已经覆盖。**

<a id="select-and-restore-context"></a>
## 候选可被保守评估，理解仍依赖固定完整章节

当前流程在初始候选和上下文装配之间有一层**可选的本地快速决策**。只有配置了 decisions 且模式不是 off，助手才把候选交给它；否则直接沿用原候选。参考 [快速决策的启用条件 ↗](../../../apps/server/src/app.ts#L119 "说明只有显式配置且模式不是 off 时，DecisionService 才注入助手。")

启用后，它用“整句问题 + 单个候选正文、标题、标题路径和候选 context”评估前 12 段，总等待最多 8 秒；来不及评估的候选保持原顺序。已评估候选按“回答或关键条件、明确矛盾、背景价值”等信号重新排序。只有候选同时被高概率判为无关、没有答案、没有内容支持，并且没有明显矛盾、父级背景需求或不确定性保护时，才会被省略；若所有已评估项都会消失，则退回完整原候选。参考 [候选评估与保守回退 ↗](../../../apps/server/src/decision/passages.ts#L5 "说明评估数量和时间边界、联合省略门槛、保护条件、排序及全删回退。")

这层失败时也不应截断问答：服务是可选、只读、串行的 sidecar，未准备、超时或执行失败会返回空判断；冷启动先后台预热，本轮继续使用原 hits。Agent 后续自主搜索仍能找回原候选。参考 [可选决策服务的失败语义 ↗](../../../apps/server/src/decision/service.ts#L16 "说明 sidecar 只读串行，执行失败返回空判断并保持既有流程可用。") [快速决策的能力边界 ↗](../../../docs/reader-first/fast-decisions.md#L23 "说明当前消费者、保守门槛、冷启动和失败回退，以及覆盖分数不触发自动快答。")

最重要的边界是：**这不是答案槽位检查器。** 模型虽然输出单段回答覆盖等维度，当前策略并不会因为“充分”就自动快答，也不会检查金额、地点和条件是否已经共同齐全；它只以严格联合条件保守省略明显无关项，并保护矛盾、缺背景和不确定候选。参考 [快速决策的能力边界 ↗](../../../docs/reader-first/fast-decisions.md#L23 "说明当前消费者、保守门槛、冷启动和失败回退，以及覆盖分数不触发自动快答。")

候选选择完成后才进入回答上下文装配。排序使用细 passage，但原件候选被选中后，系统会在**同一个不可变版本**内扩为包含命中的最小可靠 Markdown 章节或代码结构；没有可靠结构时保留原命中。唯一 H1 被视为文档标题，命中开篇引言不会因此展开整篇。扩展范围还必须全部通过可见性检查。参考 [固定版本的最小完整章节 ↗](../../../apps/server/src/retrieval/context.ts#L13 "说明命中扩展、H1 特例、父级引言、兄弟章节和可见性边界。")

系统还会沿父链补入各级章节在第一个子节之前的引言，并把它们保留成独立固定引用。因此，费用章命中“八十元”时，可以带回同章条件和上级写的“仅限已报名者”；兄弟章不会自动加入，另一章的“图书馆集合”仍需要自己的候选或后续补查。参考 [固定版本的最小完整章节 ↗](../../../apps/server/src/retrieval/context.ts#L13 "说明命中扩展、H1 特例、父级引言、兄弟章节和可见性边界。")

回答上下文限制的是不同阅读上下文的数量，默认最多 16 个。一个上下文选入后，其必要固定引用一起保留；同一版本中被更大范围包含的小范围会去重，不同版本不会合并，也不会拼成原文不存在的新范围。可以把这一层记成一句话：**细段用于召回和选择，固定完整章节用于理解。**参考 [回答上下文装配 ↗](../../../apps/server/src/assistant/context.ts#L74 "说明不同阅读上下文数量限制、固定引用恢复、包含去重和版本隔离。")

<a id="investigate-gaps"></a>
## 只补未解项，并先确认“这次”指哪个对象

第一次阅读后，可以把教学问题拆成三个待答槽位：

- 金额以及会改变金额含义的费用条件；
- 集合点；
- “这次活动”对应的对象和版本。

如果费用章已经给出八十元、报名资格和交通费条件，就不必换几个近义词反复搜索金额；调查资源应转向仍为空的集合点或对象身份。search_contexts 可以让每个具体问题保留自己的候选池和完整上下文，跨问题相同的完整上下文只返回一次，并可为具体缺口显式指定材料、项目、用途、角色、有效时间或代码意图。它返回的是阅读线索，不是覆盖分数；空结果只是搜索缺口，不证明事实不存在。参考 [按子问题保留完整上下文 ↗](../../../apps/server/src/knowledge/agent-research.ts#L685 "说明独立候选池、显式范围、共享上下文去重，以及空结果不是不存在证明。")

如果发现多个可能对象，而本轮和会话都没有选定其中一个，应先做最小澄清，例如“你指春游活动，还是同名的读书会？”项目或主题归属可以缩小查找范围，多个项目取并集，与明确材料键同时使用时取交集；但归属只说明“去哪里找”，不能裁决哪条记录是当前事实。已确认的个人会话项目成为后续首轮阅读起点，换对象时应改选，无关问题、跨项目比较或歧义未解时应清空。参考 [项目范围与对象选择 ↗](../../../docs/reader-first/project-contexts.md#L23 "说明项目范围运算、会话项目选择和项目归属不裁决当前事实。")

回到旧活动记录，应核对原文里的活动名称或适用对象、日期，以及是否明确写了变更或替代关系。材料角色、状态、默认排名、捕获先后和同属一个项目都只是导航信号，不能替用户决定“这次”。若证据仍不足，可以先问一句对象澄清，也可以按对象给出条件分支——“若指春游说明，则……；若指旧活动记录，则……”——并明确尚未确认的部分。原件没有说明交通费或替代关系时，应保留未知，不能用 RAG 补造。

<a id="write-the-answer"></a>
## 把结论、条件与未知组织成可行动的答案

材料足够时，答案应先按用户的两个问题逐项给结论，再把条件贴近对应结论。例如：

> 这次活动按每人八十元准备，在图书馆集合。八十元仅适用于已报名者，不含交通费；请在周三 18 点前确认。［分别附金额/条件与集合点的固定原文引用］

这仍是格式教学，只有固定原文确实支持每一句时才成立。若“这次”尚未消歧，就先问对象，或写成清楚的条件分支；若材料没有说明某项条件，则明确未知。

提交阶段会校验项目选择和引用：非空项目必须是当前可用的正式个人项目；引用必须来自本次授权材料，历史版本须与当前材料同源，范围须可见，正文使用的引用编号必须有原文定位。这些门禁保证选择与来源链接合法，却不会验证金额、地点和条件是否都答到了。参考 [项目选择与答案引用校验 ↗](../../../apps/server/src/assistant/research.ts#L82 "说明项目 ID、授权材料、历史同源性、可见范围和正文引用定位的提交校验。")

复杂机制、冲突或关键推断还可以交给独立读者复核。一旦请求复核，复核运行中、未完成、反馈未读取，或报告有实质问题但草稿仍原样未改时，都不能提交。参考 [复核提交门禁 ↗](../../../apps/server/src/assistant/answer-review.ts#L204 "说明复核运行、完成、反馈读取和含实质问题的原样草稿会阻止提交。") 独立读者能在同一固定快照中补查并指出会改变结论或行动的遗漏，但是否启动复核以及能否发现问题仍依赖模型判断；它是第二双眼睛，不是完整性证明。参考 [独立复核的能力边界 ↗](../../../docs/reader-first/answer-investigation.md#L21 "说明独立读者可补查重要遗漏，但是否启动和能否发现问题仍依赖模型判断。")

<a id="locate-failures"></a>
## 答案仍不完整时，按信息丢失的位置定位

不要先用“搜索不好”概括所有遗漏。沿问题到答案倒查，通常能落到下面一层：

| 现象 | 问题所在层 | 优先查看的实现入口 |
| --- | --- | --- |
| 金额或地点从未进入 RetrievalPort 的初始 hits，取消项目范围后才出现，或概念别称没有帮助对应段 | 召回范围与排序：passage 投影、全文/向量/符号路线、融合、显式筛选、可见性和 readingScope | retrieval/units.ts、retrieval/unified.ts、retrieval/port.ts、assistant/runtime.ts |
| 初始 hits 中已有金额或地点，但进入 assembleAnswerContext 前消失或顺序显著变化 | 可选候选评估：联合省略门槛、矛盾/父背景/不确定保护、前 12 段与 8 秒边界、服务状态和回退 | decision/passages.ts、decision/service.ts、assistant/runtime.ts |
| 候选或人工指定的原文本身没有写必要条件 | 原文或选材 | 原材料正文、材料历史、选材入口 |
| 原文有条件，但同章、父级引言或固定引用没有交给助手 | 上下文装配 | retrieval/context.ts、assistant/context.ts |
| 费用已读到，但兄弟章地点、对象切换或歧义仍未补查 | 调查策略与项目选择 | knowledge/agent-research.ts、assistant/acp-model.ts、project-contexts.md |
| 金额、地点和条件都已读到，最终答案仍漏写或混用版本 | 回答与复核 | assistant/research.ts、assistant/answer-review.ts |

判定时要同时看初始 hits、快速决策结果、装配后的固定上下文、后续读取、草稿、复核和最终答案。关闭 decisions 或 sidecar 不可用后仍缺候选，问题应回到召回；候选保留却没带回条件，检查上下文装配；金额已读但地点在兄弟章仍没查，检查调查策略；证据已齐却没有写进结论，才主要处理回答与复核。

工具日志只能证明发起过读取，不能证明内容已经被理解；人工指定原文也可能选得不全。“有引用”“快速决策保留了候选”“给过材料”或“复核完成”都不能单独证明语义完整。参考 [分层验收方法 ↗](../../../docs/reader-first/answer-investigation.md#L47 "说明需联合检查初始命中、读取、草稿、复核与最终答案，读取发生不等于理解。")
