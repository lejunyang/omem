# 一次提问如何找到答案：统一召回、上下文与 RAG

以“飞书 消息 后台”为贯穿示例，解释顶部搜索、知识搜索和助手如何共享底层召回，又如何形成不同结果；并沿分词、多路召回、融合排序、上下文补充和二轮查询定位“找不到”与“找到却答不好”。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先看一次真实提问

假设用户记得“飞书消息会经过后台处理”，却忘了文件名，于是在顶部搜索输入 **“飞书 消息 后台”**，看到若干原始片段后又向助手追问：“具体经过哪些步骤？”

这两个动作共用同一个底层检索实例：应用启动时创建检索服务，并把它同时交给知识路由和助手；顶部搜索也调用同一实例。因而三处共享原始材料、向量索引与基础排序，但用途不同：顶部搜索直接展示最多 30 个片段，助手取证据后组织回答，知识搜索则把原始证据命中与文章章节文字匹配结合起来。参考 [统一检索实例装配 ↗](../../../apps/server/src/app.ts#L80 "支持顶部搜索、知识路由和助手共享同一个检索服务实例的说明。")、[顶部搜索结果 ↗](../../../apps/server/src/app.ts#L273 "支持顶部搜索调用共享检索器并返回片段、路由和章节信息的说明。")、[知识章节搜索 ↗](../../../apps/server/src/knowledge/api.ts#L97 "支持知识搜索将文章章节文字命中与原始证据排名结合、每篇文章只返回最佳章节的说明。")

<a id="recall"></a>
## 中文问题如何进入多路召回

查询会先按空白和标点拆词；连续中文还会生成重叠二元词组，并过滤“这个”“怎么”等过于常见的组合。因此示例中的“飞书”“消息”“后台”都是二字词，主要走正文和标题的短词匹配；三字以上中文词则可进入 trigram 全文检索。若用户后来改查 `LarkRuntimeHost` 或完整函数名，符合代码名称形态的 ASCII 标识符还会进入 AST 符号精确匹配。参考 [长词与短词召回 ↗](../../../apps/server/src/retrieval/keyword.ts#L53 "支持三字以上词进入全文检索、二字词使用短词匹配路径的说明。")、[中文查询分词 ↗](../../../apps/server/src/retrieval/keyword.ts#L210 "支持连续中文保留完整词、生成二元词组并过滤常见组合的说明。")

系统并行汇集五类候选：代码符号、全文、中文短词、活动记忆和知识文章。记忆与知识只负责帮助发现材料：命中后仍要沿证据关系回到当前原始片段，不会把整理后的文字当成另一份独立事实。失效记忆不会参与；知识引用的固定版本或原文定位失效时，也不会产生原始证据候选。参考 [多路召回与融合 ↗](../../../apps/server/src/retrieval/keyword.ts#L81 "支持代码符号、全文、短词、记忆和知识五路候选，以及按路线排名融合并返回原始证据的说明。")、[知识引用回溯 ↗](../../../apps/server/src/knowledge/retrieval.ts#L35 "支持派生知识只在依赖有效且引用能定位原文时递归映射回原始片段的说明。")

<a id="routes"></a>
## 每条召回路线解决什么问题

| 路线 | 更适合的记忆线索 | 在示例中的作用 |
|---|---|---|
| 全文检索 | 较长中文短语、路径、代码子串 | 用户记得接近原文的表述时定位材料 |
| 短词匹配 | 二字中文业务词 | 让“飞书、消息、后台”不因 trigram 限制而漏掉 |
| 代码符号 | 类名、函数名、限定名 | 从业务词命中继续追到具体实现 |
| 向量检索 | 说法不同但含义相近 | 补足无法靠字面重合发现的材料 |
| 活动记忆 | 记得整理后的结论 | 沿记忆的证据集合找回原文 |
| 知识文章 | 记得文章标题或解释 | 沿有效引用递归找回原始片段 |

这些路线返回的分数含义不同，不能直接把 BM25、短词次数和派生文字分数相加。系统先在各路线内排序，再用倒数排名融合；同一片段从多条路线命中时会累积优势。参考 [多路召回与融合 ↗](../../../apps/server/src/retrieval/keyword.ts#L81 "支持代码符号、全文、短词、记忆和知识五路候选，以及按路线排名融合并返回原始证据的说明。")

<a id="ranking"></a>
## 融合、向量与去重怎样配合

融合后的候选还会经过排序：代码符号命中获得额外权重，随后以相关性为主、冗余惩罚为辅执行 MMR。摘录完全相同、来自同一材料版本或向量高度相似的结果会被降序，以免结果页被重复片段占满；片段身份、来源与可见性不会因此改变。参考 [融合结果去重排序 ↗](../../../apps/server/src/retrieval/ranking.ts#L3 "支持代码符号加权、MMR 相关性与冗余权衡，以及不改变原始身份和来源的说明。")

启用语义检索时，系统先保留最多 100 个词法候选，再计算当前模型身份下的向量窗口候选，最后进行第二次融合和排序。长片段按 400 字窗口、320 字步长重叠索引，所以位于材料尾部的关键句也有机会被召回；向量异常时则退回词法结果。参考 [词法与向量二次融合 ↗](../../../apps/server/src/retrieval/semantic.ts#L81 "支持词法候选和向量候选再次融合、语义异常时退回词法结果的说明。")、[长片段向量窗口 ↗](../../../apps/server/src/retrieval/semantic.ts#L125 "支持长片段使用重叠窗口建立向量索引的说明。")

当前配置启用本地中文模型 `memory-zh`。模型快照、文件校验、量化方式和查询指令均固定，运行时关闭远程模型；缺少权重或快照不匹配会让语义能力降级，而不是临时下载未知版本。参考 [中文检索配置 ↗](../../../config/retrieval.json#L1 "支持当前启用 memory-zh 语义检索配置的说明。")、[本地中文向量模型 ↗](../../../apps/server/src/retrieval/embedding.ts#L14 "支持固定模型快照、校验文件、关闭远程下载、CPU q8 和中文查询指令的说明。")

<a id="context"></a>
## 命中片段之后如何补足背景

单个命中往往只说明“这里提到了后台处理”，不足以解释完整过程。助手会先保留排序命中；若命中来自长片段尾部的向量窗口，也会保留实际命中的窗口文字，避免重新读取时只拿到片段开头。随后，它在总证据预算内补入同一材料、同一章节的标题片段和前后相邻片段。参考 [助手证据扩展 ↗](../../../apps/server/src/assistant/runtime.ts#L665 "支持保留语义命中窗口并在证据预算内补充标题和相邻片段的说明。")

补背景不是无限展开：邻居不会自动跨到整份文件或其他文件，而且每个片段仍须通过当前会话的可见性检查。章节标题本身也被视为内容；只要材料中存在当前会话不可见的片段，系统就不会暴露该章节的标题和行范围。参考 [章节邻居与可见性 ↗](../../../apps/server/src/retrieval/context.ts#L5 "支持邻居仅限同章节标题及前后片段，并避免通过章节标题泄露隐藏内容的说明。")

因此，首次命中不能被当成完整调用链。入口、核心处理和输出若分散在不同章节或文件，助手仍需要用命中处出现的类型名、函数名或业务词继续查询。

<a id="rag"></a>
## 助手怎样从证据生成回答

```mermaid
flowchart LR
  Q[用户问题] --> R[统一召回]
  R --> N[补章节邻居]
  N --> A1[模型首轮]
  A1 -->|背景足够| F[带引用回答]
  A1 -->|提出检索词| R2[追加一次检索]
  R2 --> A2[模型第二轮]
  A2 --> F
```
助手先用用户原文检索，并合并同一会话此前咨询轮留下的工作上下文，所以“继续说处理过程”可以承接上一轮；不同会话的历史不会混入。首轮模型只能看到运行时提供的对话、证据和受控上下文。若材料不足，它最多提出 3 个追加检索词；新证据按片段去重并置前，截取最多 24 项后，只再生成一轮回答。参考 [助手二轮检索流程 ↗](../../../apps/server/src/assistant/runtime.ts#L465 "支持合并会话历史、限制追加检索词、合并新证据并只进行一次第二轮生成的说明。")

最终引用也有白名单：只有实际传给模型的片段 ID 才能保留，虚构或越权引用会被过滤，持久化的仅是模型明确选择的证据。模型不可用时，系统不会用模板冒充有依据的答案。参考 [回答引用白名单 ↗](../../../apps/server/src/assistant/runtime.ts#L524 "支持仅保留运行时实际提供且模型明确选择的证据引用，并说明模型失败时的处理。")

<a id="diagnosis"></a>
## 区分“找不到”和“找到却答不好”

**找不到**通常发生在召回之前或召回阶段。可依次检查：分词后是否还有有效词；二字中文是否只能依赖短词匹配；目标是否属于当前原始版本；可见性是否过滤了片段；活动记忆是否具备证据集合；知识文章的固定依赖是否仍有效；语义索引是否仍在追赶或已经降级。时间范围过滤针对材料版本的捕获时间，并不是飞书事件发生时间，也不是历史时点查询。参考 [检索时间与可见性范围 ↗](../../../apps/server/src/retrieval/port.ts#L25 "支持时间条件针对捕获版本时间、可见性在最终排序前应用的诊断说明。")

**找到却答不好**则说明至少有一部分召回已经成功，应继续检查正确片段是否进入最终名额、融合和去重后是否排得过低、长片段的实际命中窗口是否被保留、相邻片段是否足以解释流程，以及助手有没有用具体符号发起追加查询。顶部搜索有结果而助手回答含糊，往往指向上下文或生成阶段；知识搜索出现文章，则还可能只是章节文字匹配较高，不能单独证明原始证据排名足够靠前。参考 [知识章节搜索 ↗](../../../apps/server/src/knowledge/api.ts#L97 "支持知识搜索将文章章节文字命中与原始证据排名结合、每篇文章只返回最佳章节的说明。")

<a id="limits"></a>
## 当前边界与稳妥使用方式

当前可观察到的“重排”主要由倒数排名融合、代码符号加权和 MMR 去冗余组成；向量用于补充语义候选及辅助判断重复。语义索引在后台分批追赶，新查询不会等待全部材料完成索引，因此 `indexing` 或 `degraded` 状态下的覆盖并不完整，但词法检索仍可继续工作。参考 [融合结果去重排序 ↗](../../../apps/server/src/retrieval/ranking.ts#L3 "支持代码符号加权、MMR 相关性与冗余权衡，以及不改变原始身份和来源的说明。")、[词法与向量二次融合 ↗](../../../apps/server/src/retrieval/semantic.ts#L81 "支持词法候选和向量候选再次融合、语义异常时退回词法结果的说明。")

上下文扩展只覆盖同章节的标题与相邻片段，不能自动拼成跨文件调用图；时间条件也只表示捕获时间。对于“飞书消息怎样经过后台处理”这类跨文件问题，稳妥路径是先用中文业务词发现入口，再用结果中的具体类型或函数名追加一次查询，并核对最终回答引用的是否真是描述处理步骤的原始片段。
