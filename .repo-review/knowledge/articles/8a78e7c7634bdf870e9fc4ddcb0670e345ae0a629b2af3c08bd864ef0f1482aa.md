# 把材料整理成一篇真正能用的文章

从一个读者问题出发，说明页面计划如何确定目标与材料范围，研究者、作者和独立复核者如何把原件变成可用解释，以及固定选材和项目/主题动态范围怎样让新聊天安全进入同一篇文章。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先回答读者的问题，而不是介绍文件

一篇能用的知识文章，核心不是把每份材料换一种说法，而是**围绕读者要解决的问题重组原始事实，并让解释仍能回到写作时的原件**。

以下只是一则教学示例：原件写着“预算是八十元”和“地点在图书馆”，文章把它们组织为参加者真正关心的“要准备多少钱”和“去哪里集合”。后来又保存了一条聊天：“场地改为东侧阅读室，小周负责签到。”如果这条聊天明确属于同一个“阅读小组”项目，它就可以在下一次整理时进入同一篇文章；仅仅标题相似或刚好提到活动，并不会自动混入。参考 [预算与地点示例 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L38 "支持预算八十元、图书馆集合被组织为费用与集合两节的教学示例。") [后来记录进入项目说明 ↗](../../../docs/reader-first/project-contexts.md#L1 "解释新消息只有明确归入同一项目后才进入文章范围，同名未关联材料不会混入。")

这背后有三种不同的单位：Source 与 Revision 保存原件身份和每次内容版本；章节、函数、对话等结构块用于检索；文章跨材料回答一个读者问题。文章能提供解释和导航，但不是另一份独立事实。参考 [保存、检索与讲解单位 ↗](../../../docs/reader-first/architecture.md#L7 "解释原件、结构块和读者文章的职责差异，以及问题驱动的生成主线。")

<a id="page-plan"></a>
## 页面计划同时定义目的和调查边界

整理从**页面计划**开始。计划说明写给谁、读完要完成什么、处于什么场景、要回答哪些问题，并给出调查入口与材料范围。`entryPaths` 只是从哪里开始读；它不会替代材料边界。当前网页把创建和编辑分为两步：先选材料或持续跟踪的项目/主题，再填写文章主题、阅读目标和读者。新建或目标改变时，界面暂时把目标同时作为场景和唯一问题，这只是默认映射，不表示底层计划只能回答一个问题。参考 [页面计划合同 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持计划字段，以及 materialKeys、contextIds、entryPaths 和 topicPath 的不同语义。") [两步编辑与目标映射 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L95 "支持网页先选择材料范围、再填写阅读目标，以及目标变化时的默认场景和问题映射。")

三种容易混淆的字段承担不同职责：

| 选择 | 表达什么 | 后来新增一条聊天时会怎样 |
| --- | --- | --- |
| `materialKeys` | 明确列举的原件范围 | 同一 source 的新版仍在范围内；新的 source 不会自动加入 |
| `contextIds` | 持续跟踪的项目或主题成员关系 | 每次整理重新解析成员；后来明确归属的新 source 会加入，移出的会离开 |
| `topicPath` | 读者看到的文章目录分类 | 只组织文章，不会把同分类材料纳入调查 |

`materialKeys` 与 `contextIds` 可以并用：用项目承载持续变化的主体材料，再固定加入少量范围外背景。两者都省略时，合同才允许在全部合格捕获材料中调查。参考 [页面计划合同 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持计划字段，以及 materialKeys、contextIds、entryPaths 和 topicPath 的不同语义。")

<a id="new-chat"></a>
## 一条新聊天怎样进入已有文章

要让新聊天进入已有文章，需要把“它属于哪个项目”变成明确关系，而不是让模型猜：

1. 在“输入材料”中创建或选择项目/主题，并写清范围；把聊天保存为原件时勾选它。已有原件也可以在“所属项目与主题”中调整。
2. 编辑文章，选择“持续跟踪项目或主题”。范围内现有材料整体加入，不能在这篇文章里逐项取消；仍可额外选择范围外背景。
3. 重新整理文章。若开启“随所选材料自动更新”，成员新增、移出或换版会自动排入维护队列；若未开启，就手动点击“重新整理这篇”。
4. 调查、写作和复核通过后，新稿才替换当前稿；仅保存聊天或建立归属，不等于正文已经更新。参考 [项目与主题使用步骤 ↗](../../../docs/reader-first/project-contexts.md#L5 "支持保存或调整原件归属、文章跟踪范围、自动或手动更新及范围内材料整体加入的操作链。")

归属连在稳定的 source 身份上，而不是某一个 revision 上，因此原件换版仍属于原项目，移出项目也不会删除原件、旧版本或旧引用。当前实现只接受明确归属，不会从文件路径、会话 ID、正文相似度或同名标题推断项目；一个 source 可以属于多个项目或主题。参考 [显式 source 归属 ↗](../../../apps/server/src/contexts/repository.ts#L5 "支持项目或主题与稳定 source 的关联、一个 source 的多重归属及不从路径、会话或正文推断归属。")

每次整理时，系统把显式 `materialKeys` 与所有 `contextIds` 当前关联的 source 求并集。动态范围发布时还保存**本次实际解析出的材料键集合**：计划保留未来应继续跟踪的范围，发布选择则记录这次模型究竟看到了哪些成员。参考 [页面材料范围解析 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "支持每次整理把固定 materialKeys 与 contextIds 当前成员求并集。") [按当前范围调查并保存发布选择 ↗](../../../apps/server/src/knowledge/pipeline.ts#L275 "支持写作前解析当前材料集合、动态范围的实际选择检查以及原生调查启动。")

<a id="workflow"></a>
## 调查、写作和独立复核各解决一个问题

一次整理的主线是：**保存计划 → 解析当下材料范围 → 调查原件与必要背景 → 写成完整解释 → 独立补查并试读 → 通过后发布**。已有文章在新结果发布前继续可读。参考 [按当前范围调查并保存发布选择 ↗](../../../apps/server/src/knowledge/pipeline.ts#L275 "支持写作前解析当前材料集合、动态范围的实际选择检查以及原生调查启动。")

**研究者**回答“背景是否读够”。原生模式把获准原件、历史以及范围内可用的既有知识和记忆放进同一只读快照；任务中主库变化不会悄悄替换它看到的版本。研究者可以按页面的不同问题搜索完整阅读上下文，再补读章节、函数、历史和候选调用位置。已有文章与记忆只是背景，新事实仍要回原件核对。参考 [只读研究快照与调查工具 ↗](../../../docs/reader-first/agent-research.md#L9 "解释固定原件快照、按需搜索阅读、历史与派生知识的背景地位，以及独立复核者可自行补查。")

**作者或 refresher**回答“怎样让目标读者理解并行动”。在前面的例子中，作者可以据当前材料写出预算、集合地点和签到安排，却不能自行补出材料未说明的时间或规则。维护同一篇时，旧稿只用于保留仍有价值的解释；若旧稿依赖的材料已经移出新范围，系统不把旧正文交给模型，而由 writer 按当前范围重写。参考 [写作与独立复核循环 ↗](../../../apps/server/src/knowledge/pipeline.ts#L162 "支持 refresher 的旧稿复用条件、独立 verifier、最多四轮返修和只发布 accepted 文档。")

**独立复核者**在新会话拿到同一材料范围和完整草稿，自行补查事实，并尝试用文章回答页面问题。被拒绝的内容携具体问题交给 refresher，最多经过四轮写作与复核；只有 accepted 的文档会发布。独立模型复核仍不等于真实用户验收，最终还要看目标读者是否能回答计划问题、理解首次出现的术语并执行下一步。参考 [写作与独立复核循环 ↗](../../../apps/server/src/knowledge/pipeline.ts#L162 "支持 refresher 的旧稿复用条件、独立 verifier、最多四轮返修和只发布 accepted 文档。") [读者目标检查 ↗](../../../docs/reader-first/writing.md#L16 "支持复核先试答页面问题，并区分事实检查、读者检查和真实用户验收。")

<a id="reader-result"></a>
## 读者得到文章，也得到继续核对的路径

发布结果按阅读意图区分：教程、解释和操作目标形成正式文章；`reference` 目标形成参考资料；对固定材料执行 `analyze` 得到内部笔记。正式文章进入主题目录、搜索和助手背景，参考资料进入单独目录且仍可检索，内部笔记不进入读者目录或默认召回。用途来自保存的阅读目标，不按路径、项目名或 key 前缀猜测。参考 [发布用途与来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L5 "支持正式文章、参考资料、内部笔记的用途差异，以及 citation、reviewSources、investigation 的分工。")

来源关系也分三种：正文 `citations` 支持附近论断；章节 `reviewSources` 登记未直接写进正文、但变化后必须复核的前提；`investigation` 记录角色实际读过什么。偶然读过一份材料不会因此变成正文更新依据。参考 [发布用途与来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L5 "支持正式文章、参考资料、内部笔记的用途差异，以及 citation、reviewSources、investigation 的分工。")

点击正文引用时，服务端按文章依赖中保存的 digest 打开写作时的固定原件或文章版本。若固定版本不存在，会明确说明不可用，不会静默跳到当前文字。这样读者既能顺着文章理解，也能回到当时支持结论的证据。参考 [固定引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L64 "支持按保存依赖解析固定原件或文章版本，并在缺失时返回明确不可用原因。")

<a id="changes"></a>
## 原文变化后，按章节判断哪些解释还能用

固定引用回答“当时依据了什么”，章节状态回答“这段解释现在是否仍适用”，两者不能混为一谈。引用始终指向写作时版本；适用性检查比较旧引用所在的完整 Markdown 章节或代码符号与当前版本。若新版只有一个同标题、同类型结构且完整文本相同，即使行号移动也可以继续使用；来源身份变化、图片、缺少行号或无法唯一定位结构时会保守地要求复核。系统不会把旧引用自动改指新文字。参考 [引用上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持引用不重映射、完整结构相同可容忍行号移动，以及无法可靠定位时保守复核。")

沿用开头的预算与地点例子：只在前面增加无关导读时，两节仍可检索，引用仍打开最初版本；把预算从八十元改为一百二十元时，费用节进入待核对并退出当前知识搜索，集合节继续可用；若集合节还把原预算登记为背景前提，那么预算变化也会让集合节待核对。参考 [局部变化保留可用章节 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L93 "支持无关导读变化后章节仍可用，以及预算变化只使费用节待核对而集合节继续可检索。") [未写入正文的背景前提 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L166 "支持 reviewSources 中的预算前提变化会使集合节进入待核对。")

这套判断用于**缩小复查范围**，不是自动证明语义不变。跨文件配置、调用者或运行环境若会改变本节解释，需要作者把对应原文登记为 `reviewSources`。整篇旧文仍留在目录并显示状态，当前搜索只返回仍适用的章节。参考 [章节适用性边界 ↗](../../../docs/reader-first/publication-lifecycle.md#L27 "解释章节级状态、当前检索过滤以及该机制不是自动语义影响证明。")

<a id="maintenance"></a>
## 动态范围变化后仍走同一条安全更新路径

手动整理与自动维护最终都进入同一种持久任务，并复用相同的调查、写作和独立复核流程。自动维护默认关闭；开启后，系统计算页面计划以及当前范围内每份材料的 key/digest。新聊天加入项目、材料移出项目或原件换版都会改变这个摘要并触发整理。连续变化会合并，运行中再次变化则留给下一轮；失败保留旧文，关闭自动维护只取消自动任务，不取消用户明确发起的整理。参考 [维护触发与历史保留 ↗](../../../docs/reader-first/publication-lifecycle.md#L39 "解释固定选材与动态范围的自动维护差异、持久队列、失败保留旧文和手动更新路径。") [范围摘要与自动排队 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "支持只有启用持续维护的页面才会被自动观察并续排，也支持范围摘要、任务合并和关闭行为。")

维护不会把差异 hunk 当成语义结论。它比较旧发布选择、依赖和调查轨迹与当前范围，告诉研究者哪些字段改变、哪些原件换版、哪些材料新加入；refresher 只在旧稿仍完全位于当前范围内时复用旧解释。参考 [维护上下文规划 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "支持比较旧输入与当前范围、识别新增材料，并只在旧文章完全落入新范围时复用旧稿。")

发布前还有最后一道保护：页面计划必须仍与任务开始时一致；动态范围文章的当前成员集合也必须仍等于新稿记录的实际选择；每个固定依赖还必须是模型读取的版本。如果整理途中又加入一条聊天或调整了目标，较早结果会被拒绝，不能覆盖最新输入。**开启持续维护时**，worker 会观察到最新范围摘要并排入下一轮；**未开启时**，旧文仍会保留，但读者需要手动点击“重新整理这篇”。参考 [范围摘要与自动排队 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "支持只有启用持续维护的页面才会被自动观察并续排，也支持范围摘要、任务合并和关闭行为。") [发布前范围与版本保护 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "支持发布前校验页面计划、动态范围实际成员及固定依赖，阻止过时结果覆盖最新输入。")

因此，“让聊天进入已有文章”的准确含义是：**先把聊天保存为原件并显式归入项目/主题，让文章跟踪同一范围，再由手动或自动维护生成并复核新稿**。当前已经实现明确归属、动态解析、持久触发、固定版本证据和并发保护；尚未实现从聊天内容自动判断归属，也不能把一次聊天检索范围或同名 `topicPath` 当成材料归属。参考 [项目与主题使用步骤 ↗](../../../docs/reader-first/project-contexts.md#L5 "支持保存或调整原件归属、文章跟踪范围、自动或手动更新及范围内材料整体加入的操作链。") [显式 source 归属 ↗](../../../apps/server/src/contexts/repository.ts#L5 "支持项目或主题与稳定 source 的关联、一个 source 的多重归属及不从路径、会话或正文推断归属。")
