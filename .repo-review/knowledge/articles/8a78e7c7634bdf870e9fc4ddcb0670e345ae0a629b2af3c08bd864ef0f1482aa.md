# 把材料写成一篇能用的文章

用一份活动约定贯穿 omem 的知识生成过程：先把读者问题和调查范围写成页面计划，再由研究者补齐背景、作者重组事实、独立复核者自行核对，最后发布带固定依据的正式文章。文章同时说明固定选材与持续跟踪项目的差别，以及原文变化后如何只复查受影响的章节。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="from-facts-to-page"></a>
## 文章不是材料的复述，而是对读者问题的回答

把材料写成知识文章，关键不是“每份文件生成一段摘要”，而是先确定读者读完要解决什么问题，再跨材料组织答案。原件负责保留当时说了什么，检索结构负责帮助找到相关段落，文章负责把这些段落变成可理解、可行动的解释；文章可以帮助理解，却不会取代原件成为另一份事实。参考 [问题驱动的知识生成 ↗](../../../docs/reader-first/architecture.md#L5 "支持原件、检索结构与文章承担不同职责，以及从阅读目的到调查、写作、检查、发布和增量更新的整体路线。")

下面全篇使用一个**教学示例**：一份活动约定写着“预算八十元、在图书馆集合”。如果只是复述原文，读者仍要自己判断该准备什么、该去哪里；面向参加者的文章则可以重组为“费用准备”和“集合安排”，说明八十元对应活动预算，集合地点是图书馆。后来又收到“改到东侧阅读室，小周负责签到”的聊天时，问题也不是把消息接在文末，而是重新回答：地点是否替代旧安排、签到人是谁、哪些费用约定仍然有效。

因此，一次完整生成可以概括为：

1. 明确读者、场景和要回答的问题；
2. 确定允许调查的材料范围；
3. 围绕问题补读必要背景；
4. 把事实重组为完整解释并绑定依据；
5. 让独立复核者自行查证、试着用草稿回答原问题；
6. 通过后发布，并在依据变化时重新检查受影响部分。

这条路线把“保存了什么”和“读者需要理解什么”分开：前者保证可追溯，后者决定页面是否真的有用。

<a id="plan-purpose-and-scope"></a>
## 页面计划同时定义阅读目的和调查范围

页面计划有两层，缺一层都会让生成偏离目标。

| 层次 | 计划中的内容 | 在活动示例中解决什么 |
| --- | --- | --- |
| 阅读目的 | 页面类型、目标读者、读完后的目标、使用场景、要回答的问题 | 明确这是给参加者看的解释，要回答“准备多少费用、去哪里、变化后怎么确认” |
| 调查范围 | 明确选择的材料、持续跟踪的项目或主题，以及起读线索 | 决定活动约定、后来聊天和哪些背景可以进入调查 |

实现中，`reader`、`goal`、`scenario` 和 `questions`描述目的；`materialKeys` 是明确选中的原件，`contextIds` 是持续跟踪的项目或主题成员，`entryPaths` 只是从哪里开始读，`topicPath` 只决定文章在人读目录中的位置。目录位置不会自动扩大调查范围，起读线索也不是只能读取的文件清单。参考 [页面计划字段 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持阅读目的字段、明确材料范围、动态项目范围、起读入口和主题目录之间的区别。")

固定选材和项目范围可以合用：运行时会取“明确材料”与“所选项目当前成员”的并集；若两者都没有，底层计划语义才是开放到所有合格材料。参考 [计划如何解析材料 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "支持显式材料与项目成员取并集，以及未指定两者时使用全部合格材料的运行时语义。") 网页把这件事呈现成两个直观步骤：先“选择材料”，再“说明阅读目标”；选择持续跟踪的项目后，其现有成员自动进入选材，还可以另加背景材料。参考 [网页中的选材与目标 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L149 "支持网页先选择材料、再说明阅读目标，以及持续跟踪项目时自动带入成员并允许另选背景材料。")

对活动说明而言，较好的页面计划不是“总结 activity.md”，而是：

- 读者：准备参加活动的人；
- 目标：能确认费用、集合地点和变更后的安排；
- 问题：要准备什么、去哪里、谁负责签到、哪条新消息替代了旧约定；
- 范围：活动约定，加上“阅读小组”项目里的后续记录；
- 入口：约定文件或活动聊天，只用于帮助研究者开始调查。

这样，文件只是证据入口，问题才是文章结构的来源。

<a id="three-roles"></a>
## 研究者、作者和独立复核者解决不同问题

生成过程故意把“找到足够依据”“写成解释”和“检查解释”分开。三者都在同一批获准材料上工作，但不会共享一个正在变化的主库视图：原生调查把原件、历史及可见的知识背景封装成固定只读快照，任务中途不会悄悄换成新版本。参考 [固定只读调查快照 ↗](../../../docs/reader-first/agent-research.md#L9 "支持研究者、作者和独立复核者的调查能力，以及任务中途不悄悄切换原件版本。")

**研究者解决“还缺什么背景”。** 它从页面计划出发，搜索和补读原件、相关章节、调用者、测试或已有解释，直到能回答页面问题。已有旧文时，它还判断是保留清楚的阅读路线、只更新局部，还是因为旧结构已经妨碍目标而重新组织。这个“维护或重组”是写作路线选择，不是事实结论或质量分数。运行时只有研究完成、没有遗留读取请求，才把调查结论交给作者。参考 [研究完成后进入写作 ↗](../../../apps/server/src/knowledge/pipeline.ts#L285 "支持按计划解析当前材料、研究者自主调查、完成调查请求后才把结论交给写作者的流程。")

在活动示例中，研究者需要查清“东侧阅读室”是否属于同一活动、它是否替代“图书馆”、小周的角色是什么，以及预算有没有同时变化。它不应因为两个活动名字相似就把另一场活动的记录混进来。

**作者解决“读者怎样理解和使用这些事实”。** 作者不按材料顺序抄写，而是围绕页面问题重组内容：把预算放进费用准备，把地点变更和签到人放进集合安排；直接论断绑定正文引用，未写进正文但会改变解释的重要前提登记为章节背景依据。

**独立复核者解决“这篇草稿是否真的答对了”。** 它在独立新会话中拿到完整草稿和同一材料范围，自行补查当前原件，并尝试用草稿回答阅读目标。若事实、必要条件或页面目的有问题，草稿进入返修；只有复核结论为 accepted 的文档才会成为新发布版本。参考 [写作、独立复核与发布门槛 ↗](../../../apps/server/src/knowledge/pipeline.ts#L165 "支持复核者在独立角色中检查完整草稿，未通过进入返修，只有 accepted 文档才发布。")

这三种职责不能互相替代：研究者读过某条消息，不代表作者表达准确；作者带了引用，不代表页面回答了参加者的问题；复核通过也只是发布门槛，不是读者已经验收。

<a id="reader-result"></a>
## 读者拿到正式讲解，仍能回到写作时的原件

发布以后，读者面对的不是调查日志，而是一篇可在主题目录中阅读、搜索、继续追证的文章。系统把三类产物分开：

| 产物 | 用途 | 是否进入读者目录与知识召回 |
| --- | --- | --- |
| 正式文章 | 围绕入门、解释或操作目标回答问题 | 是 |
| 参考页 | 按查询对象组织接口、字段或事实 | 进入独立参考目录，也可检索 |
| 内部笔记 | 对选中材料做分析，供内部复用 | 否 |

用途来自保存的阅读目标，不从文件路径、项目名或 key 猜测。正文引用说明某个论断依据哪里；章节背景依据记录“虽然没直接写进正文，但它变化后必须复查”的条件；调查轨迹只说明角色实际读过什么，偶然读到不等于正文依赖。参考 [三类产物与三种来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L5 "支持正式文章、参考页、内部笔记的用途区别，以及正文引用、章节背景前提和调查轨迹的不同作用。")

在活动文章里，“预算八十元”可以链接到原约定，“改到东侧阅读室”链接到后来的聊天。点击引用时，系统按文章依赖中保存的版本标识打开**写作当时的原件版本**；如果该版本不可用，会明确显示不可用，而不会悄悄跳到当前文字。参考 [固定版本引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L64 "支持引用按文章依赖的固定版本解析，缺失时明确不可用而不跳到当前版本。")

这里可以用场景理解两个术语：

- **Source** 是同一份原件跨换版保持不变的身份，例如那份活动约定；
- **Revision** 是某次保存下来的具体内容，例如仍写着“图书馆”的旧版，或后来写着“东侧阅读室”的新版。

固定版本让读者能回答“这篇文章当时依据什么”。至于文章现在是否仍适用，则由下一节的章节状态回答。

<a id="change-and-review"></a>
## 原文变化后，只复查真正受影响的解释

材料更新时，系统不会把旧引用改写成新引用，而是比较旧依据所在的完整结构是否仍然适用。若来源身份、转述状态或事件时间等关键属性改变，或者引用缺少可定位范围、涉及图片、无法落入明确章节或代码结构，就保守地要求复查；若引用所在的同标题、同类型完整结构在新版中唯一存在且文本相同，即使行号移动，该节仍可继续使用。参考 [章节上下文是否仍适用 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持来源属性检查、结构定位、同标题同类型完整文本比较，以及不自动重映射旧引用的规则。")

回到活动示例，可以得到三个不同结果：

1. **只在原文开头增加导读。** “费用”和“集合”所依据的完整小节都没变，文章仍可用；引用仍打开旧 revision。
2. **预算从八十元改为一百二十元。** “费用准备”需要复查，“集合安排”仍可搜索和阅读。现有测试正是用这个例子验证章节级状态，而不是让整篇文章一起失效。参考 [预算变化只影响费用节 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L93 "用活动约定的实现测试支持导读移动不使章节失效、预算变化只标记费用节而集合节继续可用。")
3. **集合方案实际上以预算为前提。** 即使“集合安排”正文没有直接引用预算，作者也应把预算登记为该节的背景依据；预算变化时，集合节同样进入待复查。这个传播关系只在作者明确登记后成立。参考 [背景前提传播到集合节 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L166 "支持作者登记 reviewSource 后，预算变化会使依赖预算的集合节进入待复查状态。")

这套机制的价值是**缩小复查范围**，不是证明新旧内容语义等价。跨文件配置、调用条件、运行环境或未登记的约定仍可能改变解释；研究者和复核者必须在具体页面中判断哪些前提重要。换句话说，结构比较负责指出“哪里值得重看”，理解和改写仍由角色完成。

<a id="new-chat-loop"></a>
## 让一条新聊天进入已有文章

仅把新聊天保存到材料库还不够。要让“场地改到东侧阅读室，小周负责签到”进入已有活动文章，需要完成三步：

1. **把聊天明确归入项目或主题。** 在“输入材料”中选择或创建“阅读小组”，保存聊天时一并保存归属；已有材料也可以在原文页面调整归属。
2. **让文章持续跟踪这个范围。** 在“调整材料与目标”中选择“持续跟踪项目或主题”。文章仍可另外选择背景材料。
3. **重新运行生成。** 开启自动更新后，新成员、成员换版或移出会进入持久队列；未开启时，手动点击重新整理。两条路径都会重新经过调查、写作和独立复核，而不是把新消息直接拼进正文。参考 [项目材料进入文章的步骤 ↗](../../../docs/reader-first/project-contexts.md#L5 "支持显式保存归属、文章持续跟踪项目、自动或手动重新整理，以及动态范围的实际选择与旧文保护。")

归属是用户明确保存到稳定原件身份上的关系，与文章分类和正文引用彼此独立；系统不会根据文件名、会话 ID 或材料正文自动猜项目。参考 [项目归属不靠内容推断 ↗](../../../apps/server/src/contexts/repository.ts#L5 "支持项目归属是与分类和引用独立的显式关系，不从文件名、会话 ID 或正文推断。") 当前也还没有实现从内容自动判断新材料归属，因此相似标题、转述或模糊代词仍需先调查并建立正确关系。参考 [尚未自动判断归属 ↗](../../../docs/reader-first/project-contexts.md#L47 "支持当前没有从内容自动判断材料项目归属，以及相似消息和模糊指代仍需后续调查。")

这也解释了“跟踪项目”和“只选几份材料”的差别：

- **跟踪项目或主题**：范围是动态的。后来明确加入该范围的聊天会在下次运行中自动成为候选；项目成员整体进入，不能只在这篇文章里排除其中一项。若文章只讨论项目的一部分，应取消整项目跟踪，改用固定选材。
- **只选固定材料**：范围只包含所选原件。后来保存的新聊天不会因为内容相似而进入文章，必须手动加入选材。
- **两者合用**：项目成员提供持续范围，额外材料提供必要背景。

自动更新默认关闭，而且只有文章已经明确选择材料或项目范围时才能开启。队列会合并连续变化，运行中再次发生的变化留到下一轮；失败时旧文章继续可读，不会被失败草稿覆盖。参考 [自动维护的条件与行为 ↗](../../../docs/reader-first/publication-lifecycle.md#L39 "支持自动更新默认关闭、要求明确范围、连续变化合并、运行中变化进入下一轮以及失败保留旧文。")

发布前还有最后一道一致性检查：页面目标是否在运行中被修改、动态项目的实际成员是否改变、每个固定依赖是否仍是调查时的版本。任一项变化都会拒绝较早结果覆盖当前输入，并保留旧文，随后按最新范围重新整理。参考 [发布前校验最新输入 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "支持发布前重新检查页面计划、动态范围实际成员和固定依赖版本，避免旧结果覆盖新输入。")

于是，一条新聊天进入已有文章的完整闭环是：**明确归属 → 动态范围变化 → 手动或自动排队 → 固定快照内重新调查 → 写作 → 独立复核 → 发布前再校验**。范围关系负责让正确材料有机会被看到，模型仍需理解哪条消息替代旧约定；这也是“材料进入范围”和“文章解释正确”必须分开的原因。
