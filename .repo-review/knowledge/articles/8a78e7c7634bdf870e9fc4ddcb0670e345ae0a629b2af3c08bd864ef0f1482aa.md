# Agent 怎样把材料讲明白：自主调查、写作与补查

以一篇功能说明的生成过程为主线，解释阅读目标如何约束选材与结构，研究者怎样在固定原件中搜索补读，作者与独立复核如何交接，以及候选文章如何记录依赖、发布并在来源变化后更新。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="goal"></a>
## 先决定读者要解决什么问题

假设要向新人解释“工单分派”。输入是一份功能设计和对应实现；期望结果不是两份文件的摘要，而是一篇能回答“请求怎样进入、为何按优先级分派、结果在哪里可见、要改规则去哪里”的文章。这个例子是教学构造，不代表一次真实运行。

页面计划把读者、目标、场景、问题和入口路径保存为正式数据；入口只是调查起点，明确选择的材料才限定范围。网页会把用户选中的当前修订转成材料 key，若选择期间材料已经更新，就要求刷新后重试。参考 [页面阅读计划 ↗](../../../packages/contracts/src/knowledge.ts#L60 "支持阅读计划保存读者、目标、场景、问题、入口和显式材料范围的说明。") [选材生成入口 ↗](../../../apps/server/src/knowledge/api.ts#L133 "支持网页按当前修订选材、拒绝过期选择并异步生成页面的流程。")

因此阅读目标首先决定调查价值和讲解顺序：面向新人时先讲可观察的输入与结果；面向改进机制的开发者时，才继续追到配置、调用链和修改入口。概念解释应从问题、例子和关系展开，而不是按文件名排目录。参考 [读者页面结构 ↗](../../../docs/reader-first/writing.md#L1 "支持按读者问题和页面类型组织内容，而非按文件机械摘要。")

<a id="workspace"></a>
## 在固定原件上建立调查地图

生成开始时，管线先刷新文章状态，再把本次页面计划和允许材料交给研究者。原生模式不会把整库正文塞进初始提示，而是让角色按需读取；研究者必须完成调查并返回可用的发现与缺口，之后才进入写作。参考 [页面调查入口 ↗](../../../apps/server/src/knowledge/pipeline.ts#L212 "支持 writePage 刷新状态、按明确材料范围运行研究者，并在调查完成后进入写作。")

研究环境把允许材料导出到任务独占的 `originals/`，尽量保留代码和文档的相对结构；`catalog.json` 记录 key、路径、修订和行数，SQLite 则通过一致快照供检索读取。这样同一次调查看到的是固定版本，不会在途中悄悄换成新的原文。参考 [固定研究工作区 ↗](../../../apps/server/src/knowledge/agent-research.ts#L90 "支持原件导出、目录记录和 SQLite 一致快照的实现说明。")

```mermaid
flowchart LR
  B[阅读目标与选材] --> R[研究者：搜索并补读]
  R --> W[作者：组织解释并继续核对]
  W --> V[独立复核：重查关键因果]
  V --> P[宿主：校验依赖并发布]
```

omem 负责目标、材料范围、固定快照、调查工具、合同与发布；Traex harness 负责在一个 Agent turn 内选择下一步、调用工具和管理上下文；模型角色分别承担调查、写作和复核。参考 [omem 与 harness 分工 ↗](../../../docs/reader-first/agent-research.md#L36 "支持 omem、Traex harness、模型角色在自主调查链中的职责划分。")

<a id="research"></a>
## 缺背景时，沿问题补读而不是猜

研究者可以用原生 Read/Grep/Glob 浏览导出文件，也可以用 omem 工具发现材料、读取任意行段或完整章节、混合搜索、定位代码定义和候选调用、查看显式关联及历史版本。已有文章和记忆只能帮助发现背景；新增事实仍要回到原件核对。代码导航给出的跨文件调用是候选，不是完整调用图。参考 [调查工具范围 ↗](../../../docs/reader-first/agent-research.md#L15 "支持材料读取、搜索、代码导航、历史与候选提交工具的用途及边界。")

继续“工单分派”的例子：研究者先读设计中的“按优先级分派”，再沿入口函数读到处理函数；此时发现优先级来自一个未解释的配置键，就用该键或函数名搜索，补读配置定义和设计理由。交给作者的应是一张研究地图：场景输入、处理主链、可见结果、关键概念的因果、出处和修改入口。若只搜“工单系统”这类宽泛标题，命中很多材料也未必回答问题。

搜索结果弱时可以为空；本地中文语义模型未安装时会降级全文检索而不会运行时下载。图像、历史读取和复杂全库调查目前也不能因为小型样例成功就视为都已完成真实模型验收。参考 [调查能力边界 ↗](../../../docs/reader-first/agent-research.md#L30 "支持语义检索降级和仍需单独验收的调查工具范围。")

<a id="handoff"></a>
## 研究、写作与复核是三次独立判断

研究笔记是给作者的路线图，不是新的事实来源。作者收到 findings 与 gaps，同时仍处在相同材料范围和研究环境里，可以再搜索、补读、核对，然后把零散发现改写成“输入—处理—结果—修改入口”的连贯解释。之后复核者在独立角色运行中拿到草稿与原件，自行检查关键因果和页面是否真正回答阅读问题；需要修改时，管线把具体问题交给修订角色重写，而不是直接发布。参考 [写作、复核与依赖组装 ↗](../../../apps/server/src/knowledge/pipeline.ts#L126 "支持作者与复核者独立运行、修订流程，以及依赖仅吸收正文引用和作者、复核者读取，研究 trace 另行保存的边界。")

这里的“一次 ACP prompt”不是一次纯文本推理。omem 先创建 session 并挂入 MCP server，再调用一次 `connection.prompt`；在结束前，客户端持续接收工具调用、计划和用量更新，直到 `end_turn`。反复的“判断—调用工具—读取结果—继续判断”由 Traex harness 在这个 turn 内编排。参考 [ACP 会话建立 ↗](../../../apps/server/src/agents.ts#L267 "支持 omem 建立 ACP session、挂入 MCP server并发现原生 skill 的说明。") [一个 Agent turn ↗](../../../apps/server/src/agents.ts#L335 "支持一次 connection.prompt 持续到 end_turn 的运行语义。")

原生角色最终必须调用 `submit_result`：提交失败会把校验错误返回同一 turn 继续修正，成功只保存候选。聊天里写出一段 JSON 并不等于已经提交，更不等于文章已经发布。参考 [原生提交要求 ↗](../../../apps/server/src/agent-runtime/gateway.ts#L473 "支持 gateway 要求原生角色通过 submit_result 交付，而非把聊天文本当最终产物。") [候选提交校验 ↗](../../../apps/server/src/knowledge/agent-research.ts#L636 "支持 submit_result 在同一 turn 内返回错误、成功保存候选但不直接发布的行为。")

<a id="publish"></a>
## 通过复核后才成为可更新的文章

作者候选先检查目标 key、引用目标与可见行范围，再由独立复核给出结论。只有通过的文档才组装为产物；材料依赖来自正文引用，以及作者和复核者实际记录到的读取。研究者的 findings 与 gaps 会交给作者，完整研究 trace 也保存在生成记录中，但研究者的读取不会单独加入依赖集合。复核要求修订时会重新写作，最终仍未通过则失败，不覆盖旧的有效文章。参考 [写作、复核与依赖组装 ↗](../../../apps/server/src/knowledge/pipeline.ts#L126 "支持作者与复核者独立运行、修订流程，以及依赖仅吸收正文引用和作者、复核者读取，研究 trace 另行保存的边界。")

发布前，仓储只对产物中已经记录的材料摘要和文章修订做比较；其中任一依赖已经变化，就拒绝把候选提升为当前版本。发布成功后会保存不可变文章修订并更新当前 head。参考 [已记录依赖的发布检查 ↗](../../../apps/server/src/knowledge/repository.ts#L122 "支持发布仅比较产物中的依赖版本、保存不可变修订并更新当前 head 的行为。")

以后材料变化时，`refresh` 同样按已记录依赖判断：直接失配的文章会变为非 current，依赖这些文章的上层页面也会继续过期传播。固定历史仍可按原摘要找回，不会静默跳到新版。再次生成页面时，阅读计划或角色版本变化也会触发重新调查、写作和复核。参考 [已记录依赖的过期传播 ↗](../../../apps/server/src/knowledge/repository.ts#L178 "支持按产物依赖判定非 current、沿文章关系传播，并按固定摘要恢复历史材料。") [页面调查入口 ↗](../../../apps/server/src/knowledge/pipeline.ts#L212 "支持 writePage 刷新状态、按明确材料范围运行研究者，并在调查完成后进入写作。")

<a id="quality"></a>
## 工具正确不等于读者已经读懂

检索能找到片段，代码导航能缩小位置，引用校验能确认来源，但它们不能替代解释顺序和跨材料因果：命中设计与代码不等于已经说清“为什么这个配置产生这个行为”。独立事实复核也不能证明陌生开发者真的能沿案例理解输入输出、找到修改点并开始行动；项目因此把事实检查与读者检查分开，模型判断只是辅助。参考 [事实检查与读者检查 ↗](../../../docs/reader-first/writing.md#L18 "支持引用完整不能替代页面用途、读者理解与真人验收的质量边界。")

改进体验时可按职责定位：调查策略和研究地图看研究者角色；文章结构、补读和引用风格看 writer/refresher；什么问题阻止发布看 verifier；材料导出、搜索导航、读取审计与提交在 `agent-research.ts`；研究—写作—复核—发布在 `pipeline.ts`；原生 skill、MCP 与候选提交接入在 `gateway.ts`；ACP session 和一个 turn 内的事件循环在 `agents.ts`。这条原生调查链当前要求 ACP，且普通助手问答的上下文策略不会因此自动改变。参考 [当前原生调查链 ↗](../../../docs/reader-first/agent-research.md#L9 "支持研究者、作者、复核者的工具能力、ACP 要求及普通助手上下文未同步改造的当前边界。")
