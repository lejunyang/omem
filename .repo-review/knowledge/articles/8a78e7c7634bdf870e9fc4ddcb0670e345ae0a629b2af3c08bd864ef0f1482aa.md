# 把材料整理成一篇真正能用的文章

从一个读者问题出发，说明页面计划如何确定目标与材料范围，研究者怎样在固定且可见的快照中补足背景，作者与独立复核者如何把原件变成可用解释，以及固定选材和项目/主题动态范围怎样让新聊天安全进入同一篇文章。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先回答读者的问题，而不是介绍文件

一篇能用的知识文章，核心不是把每份材料换一种说法，而是**围绕读者要解决的问题重组原始事实，并让解释仍能回到写作时的原件**。

以下是一则贯穿全文的教学示例：原件写着“预算是八十元”和“地点在图书馆”，文章把它们组织为参加者真正关心的“要准备多少钱”和“去哪里集合”。后来又保存一条消息：“场地改为东侧阅读室，小周负责签到。”只有这条消息被明确归入同一个“阅读小组”项目，它才会在下一次整理时进入这篇文章；标题相似或正文提到同一活动，都不会自动建立归属。参考 [预算与地点教学示例 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L38 "支持原件中的预算和地点被重组为文章费用与集合两节。") [后来消息进入项目范围 ↗](../../../docs/reader-first/project-contexts.md#L1 "解释新消息只有明确归入同一项目才进入范围，并说明范围正确不等于理解正确。")

这背后有三种不同的单位：Source 与 Revision 保存原件身份和每次内容版本；章节、函数、对话等结构块用于检索；文章跨材料回答一个读者问题。文章可以提供解释和导航，但不是另一份独立事实。参考 [保存、检索与讲解单位 ↗](../../../docs/reader-first/architecture.md#L5 "解释 Source/Revision、结构块与跨材料页面的不同职责及问题驱动生成主线。")

<a id="page-plan"></a>
## 页面计划同时定义目的和调查边界

整理从**页面计划**开始。计划说明写给谁、读完要完成什么、处于什么场景、要回答哪些问题，并给出调查入口与材料范围。当前网页分两步：先选择材料，再说明阅读目标；新建页面或目标变化时，界面暂时把目标同时写入场景和一个问题，这只是默认映射，底层计划仍可保存多个问题。参考 [页面计划合同 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持页面类型、读者、目标、问题、入口、topicPath、materialKeys 与 contextIds 的字段语义。") [两步编辑与目标默认映射 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L95 "支持模板明确显示先选择材料、再说明阅读目标，并支持目标变化时场景和问题的默认映射。")

三种容易混淆的选择承担不同职责：

| 选择 | 表达什么 | 后来新增一条聊天时会怎样 |
| --- | --- | --- |
| `materialKeys` | 明确列举的原件范围 | 同一 Source 的新版仍在范围内；新的 Source 不会自动加入 |
| `contextIds` | 持续跟踪的项目或主题成员关系 | 每次整理重新解析成员；后来明确归属的新 Source 会加入，移出的会离开 |
| `topicPath` | 读者看到的文章目录分类 | 只组织文章，不会把同分类材料纳入调查 |

`entryPaths` 只是从哪里开始读，也不替代材料边界。`materialKeys` 与 `contextIds` 可以并用：用项目承载持续变化的主体材料，再固定加入少量范围外背景；整理时两部分取并集。只有两者都省略，计划才允许在全部合格捕获材料中调查。参考 [页面计划合同 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持页面类型、读者、目标、问题、入口、topicPath、materialKeys 与 contextIds 的字段语义。") [页面材料范围解析 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "支持固定 materialKeys 与 contextIds 当前成员取并集，并说明两者都省略时的开放范围。")

<a id="new-chat"></a>
## 一条新聊天怎样进入已有文章

要让新聊天进入已有文章，需要把“它属于哪个项目”变成明确关系，而不是让模型猜：

1. 在“输入材料”中创建或选择项目/主题，并写清范围；保存聊天时同时选择归属。已有原件也可以在“所属项目与主题”中调整。
2. 编辑文章，选择“持续跟踪项目或主题”。范围内现有材料会整体加入，不能只在这篇文章中排除其中一项；仍可额外固定选择范围外背景。
3. 重新整理文章。若开启“随所选材料自动更新”，成员新增、移出或换版会自动排入维护队列；未开启时手动点击“重新整理这篇”。
4. 调查、写作和复核通过后，新稿才替换当前稿。仅保存聊天或建立归属，不等于正文已经更新。参考 [项目与主题使用步骤 ↗](../../../docs/reader-first/project-contexts.md#L5 "支持保存归属、整项目跟踪、自动或手动更新以及范围内材料整体加入的操作链。")

归属连在稳定的 Source 身份上，而不是某一个 Revision 上。因此原件换版仍属于原项目，移出项目也不会删除原件、历史版本或旧引用。一个 Source 可以属于多个项目或主题；当前实现不会从文件路径、会话 ID、正文或相似标题推断项目。参考 [显式 Source 归属 ↗](../../../apps/server/src/contexts/repository.ts#L5 "支持项目与稳定 Source 的关联、多重归属以及不从路径、会话或正文推断归属。")

每次整理时，系统把显式 `materialKeys` 与所有 `contextIds` 当前关联的 Source 求并集。动态范围的发布结果还保存**本次实际解析出的材料键集合**：计划表达未来继续跟踪什么，发布选择记录这次模型实际看到了哪些成员。参考 [页面材料范围解析 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "支持固定 materialKeys 与 contextIds 当前成员取并集，并说明两者都省略时的开放范围。") [按当前范围启动调查 ↗](../../../apps/server/src/knowledge/pipeline.ts#L275 "支持写作前刷新并解析材料集合、保存实际材料键以及在原生模式启动研究者。")

<a id="workflow"></a>
## 调查、写作和独立复核各解决一个问题

一次整理的主线是：**保存计划 → 解析当下材料范围 → 调查原件与必要背景 → 写成完整解释 → 独立补查并试读 → 通过后发布**。已有文章在新结果发布前继续可读。参考 [按当前范围启动调查 ↗](../../../apps/server/src/knowledge/pipeline.ts#L275 "支持写作前刷新并解析材料集合、保存实际材料键以及在原生模式启动研究者。")

**研究者**回答“背景是否读够”。原生模式把本次获准的固定原件、可见历史以及相关知识和记忆复制进隔离快照，封存后不随主库变化。已有文章与记忆只是背景；新增事实仍要回原件核对。研究者可以搜索完整语境、补读章节或函数，也可以先辨认快照内的项目，再用 `groupIds` 缩小材料、知识、记忆或代码检索。参考 [固定研究快照与调查工具 ↗](../../../docs/reader-first/agent-research.md#L9 "解释固定原件、隔离只读快照、派生背景地位及项目过滤可用的调查工具。") [项目调查的范围和边界 ↗](../../../docs/reader-first/project-contexts.md#L23 "解释项目目录、接受 groupIds 的搜索工具、快照冻结、共享调查边界与未实现自动归属。")

这里有一处重要区别：页面计划中的 `materialKeys + contextIds` 决定整次写作的材料范围，两者取并集；调查工具的 `groupIds` 只在已经获准的快照内缩小一次发现或搜索。工具同时收到材料键和项目时取交集，多个项目取并集；空项目数组明确选空，未知项目报错。它不会改变归属，也不会把项目字段写回页面计划。参考 [项目过滤的选择规则 ↗](../../../apps/server/src/knowledge/agent-research.ts#L348 "支持多个 groupIds 形成并集、与显式材料键取交集、空数组选择空集合以及未知项目报错。")

项目目录也不是个人全库目录：它只列本次获准原件涉及的项目，群聊调查不提供个人项目名称和范围说明；没有看到某个项目，不能据此断定它从未存在。参考 [项目调查的范围和边界 ↗](../../../docs/reader-first/project-contexts.md#L23 "解释项目目录、接受 groupIds 的搜索工具、快照冻结、共享调查边界与未实现自动归属。") [共享对话不暴露个人项目元数据 ↗](../../../apps/server/tests/assistant-research.test.ts#L153 "支持共享调查即使可读一份原件，也不会得到其个人项目名称和范围说明。")

**作者或 refresher**回答“怎样让目标读者理解并行动”。在示例中，作者可以据当前材料写预算、集合地点和签到安排，却不能自行补出未说明的时间或规则。维护同一篇时，旧稿只用于保留仍有价值的解释；如果旧文使用过当前范围之外的材料，系统不把旧稿交给模型，而按当前范围重写。

**独立复核者**在新会话拿到同一材料范围和完整草稿，自行补查事实，并尝试用文章回答页面问题。被拒绝的内容会携具体问题交回 refresher，最多经历四轮写作与复核；只有 accepted 的文档会发布。独立模型复核仍不等于真实用户验收，最终还要看目标读者是否能回答计划问题、理解首次出现的术语并执行下一步。参考 [写作与独立复核循环 ↗](../../../apps/server/src/knowledge/pipeline.ts#L162 "支持 refresher 的旧稿复用、独立 verifier、最多四轮返修和只发布 accepted 文档。") [读者目标检查 ↗](../../../docs/reader-first/writing.md#L16 "支持按页面目标组织文章、复核先试答问题并区分模型检查与真实用户验收。")

<a id="reader-result"></a>
## 读者得到文章，也得到继续核对的路径

发布结果按阅读意图区分：教程、解释和操作目标形成正式文章；`reference` 目标形成参考资料；对固定材料执行 `analyze` 得到内部笔记。正式文章进入主题目录、搜索和助手背景，参考资料进入独立参考目录且仍可检索，内部笔记不进入读者目录或默认召回。用途来自保存的阅读目标，不按路径、项目名或 key 前缀猜测。参考 [发布用途与三种来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L5 "支持正式文章、参考资料、内部笔记的用途差异，以及 citations、reviewSources、investigation 的分工。")

来源关系也分三种：正文 `citations` 支持附近论断；章节 `reviewSources` 登记未直接写进正文、但变化后必须复核的前提；`investigation` 记录角色实际读过什么。偶然读过一份材料，不会因此自动成为正文失效依据。参考 [发布用途与三种来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L5 "支持正式文章、参考资料、内部笔记的用途差异，以及 citations、reviewSources、investigation 的分工。")

点击正文引用时，服务端按文章依赖中保存的 digest 打开写作时的固定原件或文章版本。若固定版本不存在，会明确说明不可用，而不会静默跳到当前文字。这样读者既能顺着文章理解，也能回到当时支持结论的证据。参考 [固定引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L64 "支持按保存依赖打开固定原件或文章版本，并在缺失时返回明确不可用原因。")

<a id="changes"></a>
## 原文变化后，按章节判断哪些解释还能用

固定引用回答“当时依据了什么”，章节状态回答“这段解释现在是否仍适用”，两者不能混为一谈。引用始终指向写作时版本；适用性检查比较旧引用所在的完整 Markdown 章节或代码符号与当前版本。若新版只有一个同标题、同类型结构且完整文本相同，即使行号移动也可继续使用；来源身份变化、图片、缺少行号或无法唯一定位结构时，会保守地要求复核。系统不会把旧引用自动改指新文字。参考 [引用上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持引用不重映射、完整结构相同可容忍行号移动及无法可靠定位时保守复核。")

沿用开头的预算与地点示例：只在前面增加无关导读时，两节仍可检索，引用仍打开最初版本；把预算从八十元改为一百二十元时，费用节进入待核对并退出当前知识搜索，集合节继续可用。若集合节还把原预算登记为背景前提，那么预算变化也会让集合节待核对。参考 [局部变化保留可用章节 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L93 "支持无关导读变化后章节仍可用，以及预算变化只使费用节待核对。") [未写入正文的背景前提 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L166 "支持 reviewSources 中的预算前提变化会使集合节进入待核对。")

这套判断用于**缩小复查范围**，不是自动证明语义不变。跨文件配置、调用者或运行环境若会改变本节解释，需要作者把对应原文登记为 `reviewSources`。整篇旧文仍留在目录并显示状态，当前搜索只返回仍适用的章节。参考 [章节适用性边界 ↗](../../../docs/reader-first/publication-lifecycle.md#L27 "解释章节级状态、当前检索过滤以及该机制不是自动语义影响证明。")

<a id="maintenance"></a>
## 动态范围变化后仍走同一条安全更新路径

手动整理与自动维护最终都进入同一种持久任务，并复用相同的调查、写作和独立复核流程。自动维护默认关闭，而且开启前必须明确选择材料或项目/主题范围。开启后，系统计算页面计划以及当前范围内每份材料的 key/digest；新聊天加入项目、材料移出项目或原件换版都会改变摘要并触发整理。连续变化会合并，运行中再次变化留给下一轮；失败保留旧文，关闭自动维护只取消自动任务，不取消用户明确发起的整理。参考 [维护触发与历史保留 ↗](../../../docs/reader-first/publication-lifecycle.md#L39 "解释固定与动态选材的自动维护差异、持久队列、失败保留旧文和手动路径。") [范围摘要与自动排队 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "支持自动维护启用条件、范围摘要、任务合并、再次变化续排与关闭行为。")

维护不会把差异 hunk 当成语义结论。它比较旧调查与依赖、旧发布选择和当前范围，告诉研究者哪些原件换版、哪些材料新加入、哪些页面字段改变；只有旧文章仍完全落在当前材料范围内时，refresher 才会拿到旧稿并保留可用解释。参考 [维护上下文规划 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "支持比较旧输入与当前范围、识别变化和新增材料，以及仅在范围完整时复用旧稿。")

发布前还有最后一道保护：页面计划必须仍与任务开始时一致；动态范围文章的当前成员集合必须仍等于新稿记录的实际选择；每个固定依赖也必须是模型读取的版本。如果整理途中又加入一条聊天或调整目标，较早结果会被拒绝，不能覆盖最新输入。开启持续维护时，后台会观察最新范围并排入下一轮；未开启时，旧文仍保留，但需要手动重新整理。参考 [范围摘要与自动排队 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "支持自动维护启用条件、范围摘要、任务合并、再次变化续排与关闭行为。") [发布前范围与版本保护 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "支持发布前校验页面计划、动态范围实际成员和固定依赖版本。")

因此，“让聊天进入已有文章”的准确含义是：**先把聊天保存为原件并显式归入项目或主题，让文章跟踪同一范围，再由手动或自动维护生成并复核新稿**。项目过滤能帮助研究者在固定快照里找到相关背景，但不能代替明确归属，也不能判断新消息在语义上替换了哪条旧约定。当前尚未实现从聊天内容自动判断归属。参考 [项目与主题使用步骤 ↗](../../../docs/reader-first/project-contexts.md#L5 "支持保存归属、整项目跟踪、自动或手动更新以及范围内材料整体加入的操作链。") [项目调查的范围和边界 ↗](../../../docs/reader-first/project-contexts.md#L23 "解释项目目录、接受 groupIds 的搜索工具、快照冻结、共享调查边界与未实现自动归属。")
