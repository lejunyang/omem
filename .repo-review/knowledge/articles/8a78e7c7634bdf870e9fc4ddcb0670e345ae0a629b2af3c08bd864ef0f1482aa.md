# Agent 怎样把材料讲明白：自主调查、写作与补查

以一篇面向新人的功能文章为线索，解释阅读目标如何指导选材和调查，固定原件与背景快照的边界，Traex harness 如何在一个 ACP turn 内反复补读，以及研究、写作、独立复核、发布和来源更新怎样衔接。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 从新人真正要回答的问题开始

设想一个**教学示例**：你选中“功能设计.md”和对应的“实现.ts”，要为刚接触项目的开发者解释“用户输入怎样变成可见结果，应该去哪里修改”。输入是阅读目标、问题、场景和固定材料；可观察结果应是一篇围绕完整功能链组织的文章，而不是两个文件的摘要。当前写作规范也把默认路线安排为“场景 → 完整例子 → 必要概念 → 机制与取舍 → 修改入口”。参考 [读者优先的写作与验收 ↗](../../../docs/reader-first/writing.md#L1 "支持以具体场景和完整例子推进到机制与修改入口，并区分事实检查、读者检查和用户验收。")

页面计划把这个目标正式写成读者、场景、问题和入口路径。网页生成时还会校验用户选中的原件版本，把稳定材料 key 写入 brief，再异步启动知识管线。参考 [知识页面阅读计划 ↗](../../../config/wiki-pages.json#L143 "给出本页的目标读者、教学场景、核心问题、调查入口和分类路径。") [页面选材入口 ↗](../../../apps/server/src/knowledge/api.ts#L165 "实现固定 revision 选择校验、材料 key 写入 brief 和异步生成启动。")

```mermaid
flowchart LR
  A[阅读目标与选定原件] --> B[研究者追主流程并补背景]
  B --> C[作者组织连贯解释]
  C --> D[独立复核重新核对]
  D -->|通过| E[发布可追溯文章]
  D -->|需修订| C
```

这张图描述角色顺序，不是某次真实运行日志；具体的写作、复核和修订循环由知识管线编排。参考 [写作复核与修订循环 ↗](../../../apps/server/src/knowledge/pipeline.ts#L157 "实现作者、独立复核者、refresher 和仅发布 accepted 文档的角色顺序。")

<a id="scope"></a>
## 选材范围与调查背景不是同一个边界

`writePage` 先刷新当前状态；显式选材时，只把仍然存在的这些材料作为研究者、作者和复核者的原件范围，否则使用当前材料集合。研究者完成调查后，管线只把 reading、findings 和 gaps 交给作者。参考 [阅读目标进入调查流程 ↗](../../../apps/server/src/knowledge/pipeline.ts#L245 "实现显式材料范围、研究者完成条件，以及 reading、findings 和 gaps 向作者的交接。")

角色工作区把这些原件导出到 `originals/`，尽量保留代码与文档结构；`catalog.json` 记录材料身份、修订、路径和行数，`knowledge.json` 只列快照准入的既有文章。原件不是实时工作树，调查过程中不会悄悄换成新内容。参考 [原件与目录导出 ↗](../../../apps/server/src/knowledge/agent-research.ts#L134 "支持工作区如何导出固定原件、保留相对结构，并生成材料和既有知识目录。")

但“选中的原件”不等于“快照里只有这些内容”。当前知识生成调用没有传入 `visible` 或 `includeUnanchoredState`，准备阶段因而默认允许未锚定状态；快照仍会纳入空证据集的记忆，以及没有证据 id 的事项。带证据的记忆、事项和派生文章则必须满足选定 fragment、revision 或依赖准入。换言之，选材限制原件及其版本链，却没有把全部调查背景严格收窄到选材；若产品需要这种严格隐私边界，应修改快照准备策略，而不能只依赖页面选材。参考 [知识角色的快照准备 ↗](../../../apps/server/src/knowledge/pipeline.ts#L102 "显示知识管线调用 prepareAgentResearch 时未传 visible 或 includeUnanchoredState，是默认背景准入行为的起点。") [未锚定状态默认值 ↗](../../../apps/server/src/knowledge/agent-research.ts#L189 "实现未提供 visible 时 includeUnanchoredState 默认开启，并构造只读研究快照。") [背景状态的证据准入 ↗](../../../apps/server/src/knowledge/research-snapshot.ts#L153 "支持带证据状态按获准版本过滤，同时空证据记忆和无证据事项取决于 includeUnanchoredState。")

<a id="investigation"></a>
## 从候选命中补到完整因果链

研究者先按目录和少量业务词找入口，再按问题选择动作：读完整章节或函数、做混合搜索、查看定义与候选调用、补读既有知识及其原始依据，必要时查看固定历史或图片。原生 Read/Grep/Glob 适合沿文件结构连续阅读，omem MCP 适合材料目录、内部对象、语义搜索、章节和符号导航。候选调用不是类型解析后的完整调用图，搜索命中只是补读入口。参考 [自主调查工具分工 ↗](../../../docs/reader-first/agent-research.md#L15 "解释材料读取、搜索、知识与记忆、代码导航、历史、图片和最终提交工具的用途。") [原生读取与 MCP 互补 ↗](../../../docs/reader-first/agent-research.md#L42 "支持文件工具用于连续阅读，MCP 用于内部对象、检索和导航，以及候选关系的能力边界。")

回到教学示例：研究者从入口函数追到核心处理，却还解释不了“为什么写作时读到的是固定版本”，于是改搜 `snapshot` 和 `revision`，打开快照实现与设计说明，再形成“阅读问题 → 固定原件 → 搜索候选 → 整段补读 → 可见结果”的研究地图。作者拿到的是这张地图，不是可以直接当事实引用的运行日志；新增事实仍要回原件核对。研究者的角色合同也要求从一条主流程开始，只补会改变理解的关键分支。参考 [研究者的主流程调查方法 ↗](../../../packages/agent-runtime/roles/knowledge-researcher/1/prompt.md#L1 "规定研究者从实际问题追完整主流程、补关键分支，并把 findings 作为调查地图而非正文。")

<a id="acp-turn"></a>
## 一次 prompt 可以包含多轮工具调查

omem 为角色创建 ACP session，把任务工作目录、本机 MCP 和原生 skill 交给 Traex，并动态设置受支持的模型与 effort；随后宿主只调用一次 `connection.prompt`，直到 `end_turn` 才结束。参考 [ACP 会话与一次 prompt ↗](../../../apps/server/src/agents.ts#L292 "实现创建带工作目录和 MCP 的 session、动态配置模型与 effort，并运行到 end_turn。")

这里的“一次 prompt”是一个完整的 Agent turn，不是一次模型补全。turn 内的计划、工具调用、状态和 usage 会持续回传，所以 Traex harness 可以反复决定下一步、调用工具、读取结果并继续；omem 则负责阅读目标、固定材料、工具入口、输出合同、依赖和最终发布。参考 [turn 内事件回传 ↗](../../../apps/server/src/agents.ts#L232 "实现同一 Agent turn 中工具调用、计划、状态和 usage 的持续回传。") [omem 与 harness 的职责 ↗](../../../docs/reader-first/agent-research.md#L36 "直接解释 omem 管理目标、材料、工具和发布，Traex harness 管理调查步骤、工具调用与上下文。")

角色最终通过 `submit_result` 提交候选。合同或引用不合法时，工具把错误返回到同一个 turn，Agent 可以继续补读并重交；成功只保存经过校验的候选和读取审计，并不会直接绕过管线发布。参考 [候选提交与即时校验 ↗](../../../apps/server/src/knowledge/agent-research.ts#L909 "实现 submit_result 的合同校验、同 turn 错误反馈、候选保存和读取审计。")

<a id="handoff"></a>
## 研究地图、正文与复核各有责任

研究者交付 findings 与 gaps；作者在新的角色运行中拿到相同原件范围，可以再次打开实现、核对精确位置，再把调查地图写成面向读者的解释。独立复核者随后拿到草稿、阅读目标和原件，必须自行搜索并沿代表性输入核对关键因果，而不是信任研究笔记或作者选好的短引文。参考 [写作复核与修订循环 ↗](../../../apps/server/src/knowledge/pipeline.ts#L157 "实现作者、独立复核者、refresher 和仅发布 accepted 文档的角色顺序。") [独立复核的补读责任 ↗](../../../packages/agent-runtime/roles/knowledge-verifier/1/skills/omem-knowledge-verifier/SKILL.md#L22 "要求复核者独立搜索原件、沿代表性输入核对输出和关键因果，并检查读者能否行动。")

在教学示例中，如果正文把“候选 calls”写成“完整调用图”，复核者应要求修订；refresher 重新交付完整干净文章，只有 accepted 文档才能发布。正式材料依赖从正文引用开始；原生模式下，管线还会消费作者与复核者 trace 中的 `reads`，把**运行时可识别并记录的读取**纳入依赖。研究者的读取 trace 另行保存在 generation trace，不会自动加入 dependencies。参考 [正式依赖与研究记录 ↗](../../../apps/server/src/knowledge/pipeline.ts#L173 "实现正文引用起步、作者与复核者 trace 中已记录 reads 的依赖收集，并把研究结果另存于 generation trace。")

读取审计并不保证覆盖每一种 shell 阅读：运行时会识别直接文件路径和 Traex 投影出的 `parsed_cmd` read，但未被识别的 shell 读取不会自动进入 dependencies，正文引用因此仍是最低保障。研究发现若进入正文，作者应直接引用相应原件；这样即使补读审计漏记，来源变化仍能触发文章失效。参考 [原生读取的运行时识别 ↗](../../../apps/server/src/knowledge/agent-research.ts#L1005 "实现对直接文件路径和 parsed_cmd read 的识别，说明哪些原生文件读取能进入 trace 的 reads。") [读取依赖的覆盖边界 ↗](../../../docs/reader-first/agent-research.md#L30 "明确未被运行时识别的 shell 阅读不能宣称完整覆盖，正文引用仍是最低依赖保障。")

<a id="publication"></a>
## 发布记录正式来源，变化触发更新

发布前，仓储再次核对每个材料 digest 和子文章 revision；任何依赖已变化都会拒绝本次发布。通过后会保存不可变的新 revision、更新文章 head、维护未决问题，并记录本次知识变化。参考 [发布前依赖核对 ↗](../../../apps/server/src/knowledge/repository.ts#L122 "实现发布前校验依赖、保存不可变 revision、更新 head 和记录知识变化。")

之后 `refresh` 比较当前材料与文章记录的正式依赖。原件 digest、子文章 revision 或显式失效任一变化，都会把文章标成非 current，并沿文章依赖向上层传播；旧 revision 仍可按固定历史读取，不会静默跳到新版。参考 [来源变化与失效传播 ↗](../../../apps/server/src/knowledge/repository.ts#L178 "实现材料或子文章依赖变化后的非 current 标记及向上层文章传播。")

仓库适配层再把已接受文章写成 JSON 和 Markdown；Markdown 中的引用可返回原件或子文章。启动恢复时，依赖不匹配的资产会标为 stale，缺少子知识则标为 missing，而不是冒充当前文章。参考 [文章资产写入与恢复 ↗](../../../apps/server/src/knowledge/artifacts.ts#L8 "实现 JSON/Markdown 文章资产、可返回来源的链接，以及恢复时 stale 和 missing 状态判断。")

<a id="quality"></a>
## 自动检索与事实复核仍不能替代读者验收

检索负责提供候选，不负责替作者组织问题。当前仍可能把符号定义当成完整机制，让主题相关却不能回答问题的材料靠前；混合文档的单一用途和跨文件业务链也还不完整。Agent 后续补查成功，不代表第一轮召回已经好用。参考 [检索与阅读质量边界 ↗](../../../docs/reader-first/progress.md#L59 "记录符号、偏题材料、混合用途和跨文件业务链的能力边界，并明确复核和引用不能替代读者理解。")

独立复核能挡住事实错误、越界和关键条件遗漏，却不能证明新人真正读懂。还要看贯穿案例是否自然、术语是否在首次出现时解释、输入与可见结果是否清楚、读者能否定位下一步；引用多、工具调用多或模型给出 accepted 都不能替代用户验收。参考 [读者优先的写作与验收 ↗](../../../docs/reader-first/writing.md#L1 "支持以具体场景和完整例子推进到机制与修改入口，并区分事实检查、读者检查和用户验收。") [检索与阅读质量边界 ↗](../../../docs/reader-first/progress.md#L59 "记录符号、偏题材料、混合用途和跨文件业务链的能力边界，并明确复核和引用不能替代读者理解。")

改进体验时可按症状定位：页面为谁写、回答什么，改页面 brief；调查顺序和停止条件，改 researcher skill；原件导出、背景准入和调查工具，改 `agent-research.ts` 与 `research-snapshot.ts`；角色交接和依赖收集，改 `pipeline.ts`；ACP 会话与 turn 事件，改 `agents.ts` / gateway；发布和失效传播，改知识仓储。先区分“没召回、没补读、没讲清、没挡住错误”，才能观察改动究竟改善了哪一段。参考 [阅读目标进入调查流程 ↗](../../../apps/server/src/knowledge/pipeline.ts#L245 "实现显式材料范围、研究者完成条件，以及 reading、findings 和 gaps 向作者的交接。") [知识角色的快照准备 ↗](../../../apps/server/src/knowledge/pipeline.ts#L102 "显示知识管线调用 prepareAgentResearch 时未传 visible 或 includeUnanchoredState，是默认背景准入行为的起点。") [正式依赖与研究记录 ↗](../../../apps/server/src/knowledge/pipeline.ts#L173 "实现正文引用起步、作者与复核者 trace 中已记录 reads 的依赖收集，并把研究结果另存于 generation trace。") [来源变化与失效传播 ↗](../../../apps/server/src/knowledge/repository.ts#L178 "实现材料或子文章依赖变化后的非 current 标记及向上层文章传播。")
