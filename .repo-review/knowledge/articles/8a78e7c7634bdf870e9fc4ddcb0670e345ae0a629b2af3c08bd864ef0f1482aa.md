# 把材料整理成一篇真正能用的文章

从一个读者问题出发，说明页面计划如何同时确定目标与材料范围，研究者、作者和独立复核者怎样把固定原件变成可用解释；并解释维护时何时保留旧路线、何时重新组织，以及固定选材和项目动态范围如何让新聊天安全进入同一篇文章。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先回答读者的问题，而不是介绍文件

一篇能用的知识文章，核心不是把每份材料换一种说法，而是**围绕读者要解决的问题重组原始事实，并让解释仍能回到写作时的原件**。

以下是一则贯穿全文的教学示例：原件写着“预算是八十元”和“地点在图书馆”，文章把它们组织为参加者真正关心的“要准备多少钱”和“去哪里集合”。后来又保存一条消息：“场地改为东侧阅读室，小周负责签到。”只有这条消息被明确归入同一个“阅读小组”项目，它才会在下一次整理时进入文章；标题相似或正文提到同一活动，都不会自动建立归属。参考 [预算与地点例子 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L38 "支持原件中的预算和地点被重组为费用与集合两节的教学例子。") [后来消息进入项目范围 ↗](../../../docs/reader-first/project-contexts.md#L1 "解释保存归属、跟踪项目、重新整理以及范围正确不等于理解正确。")

这背后有三种不同的单位：Source 与 Revision 保存原件身份和每次内容版本；章节、函数、对话等结构块用于检索；文章跨材料回答一个读者问题。文章可以提供解释和导航，但不是另一份独立事实。参考 [保存检索与讲解单位 ↗](../../../docs/reader-first/architecture.md#L5 "解释 Source/Revision、结构块和跨材料页面的不同职责。")

<a id="page-plan"></a>
## 页面计划同时定义目的和调查边界

整理从**页面计划**开始。计划说明写给谁、读完要完成什么、处于什么场景、要回答哪些问题，并给出调查入口与材料范围。这样，系统面对的是一个读者任务，而不是“给每个文件生成一篇说明”。参考 [页面计划字段 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持读者、目标、问题、入口、目录路径与两种材料范围字段的语义。")

几种容易混淆的选择承担不同职责：

| 选择 | 表达什么 | 新增一条聊天时会怎样 |
| --- | --- | --- |
| `materialKeys` | 明确列举的原件范围 | 同一 Source 的新版仍在范围内；新的 Source 不会自动加入 |
| `contextIds` | 持续跟踪的项目或主题成员关系 | 每次整理重新解析成员；后来明确归属的新 Source 会加入，移出的会离开 |
| `topicPath` | 读者看到的文章目录分类 | 只组织文章，不会把同分类材料纳入调查 |
| `entryPaths` | 从哪里开始调查 | 是起读线索，不替代材料边界 |

`materialKeys` 与 `contextIds` 可以并用：用项目承载持续变化的主体材料，再固定加入少量范围外背景；运行时两部分取并集。只有两者都省略，计划才开放到全部合格捕获材料。参考 [页面计划字段 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持读者、目标、问题、入口、目录路径与两种材料范围字段的语义。") [页面材料范围解析 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "支持固定材料与项目当前成员取并集，以及两者省略时使用全部合格材料。")

<a id="new-chat"></a>
## 一条新聊天怎样进入已有文章

要让新聊天进入已有文章，需要把“它属于哪个项目”变成明确关系，而不是让模型猜：

1. 在“输入材料”中创建或选择项目/主题，并写清范围；保存聊天时同时选择归属。已有原件也可以在“所属项目与主题”中调整。
2. 编辑文章，选择“持续跟踪项目或主题”。范围内现有材料会整体加入；仍可额外固定选择范围外背景。若文章只讨论项目的一部分，应取消整项目跟踪，改为明确选材。
3. 重新整理文章。若开启“随所选材料自动更新”，成员新增、移出或换版会自动排队；未开启时手动点击“重新整理这篇”。
4. 调查、写作和复核通过后，新稿才替换当前稿。仅保存聊天或建立归属，不等于正文已经更新。参考 [后来消息进入项目范围 ↗](../../../docs/reader-first/project-contexts.md#L1 "解释保存归属、跟踪项目、重新整理以及范围正确不等于理解正确。")

归属连在稳定的 Source 身份上，而不是某一个 Revision 上。因此原件换版仍属于原项目；一个 Source 可以属于多个项目或主题。当前实现不会从文件路径、会话 ID、正文或相似标题推断项目。参考 [显式 Source 归属 ↗](../../../apps/server/src/contexts/repository.ts#L5 "支持项目与稳定 Source 的关联，并说明不从路径、会话或正文推断归属。")

每次整理时，系统把显式 `materialKeys` 与所有 `contextIds` 当前关联的 Source 求并集。动态范围的发布结果还保存**本次实际解析出的材料键集合**：计划表达未来继续跟踪什么，发布选择记录这次模型实际看到了哪些成员。参考 [页面材料范围解析 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "支持固定材料与项目当前成员取并集，以及两者省略时使用全部合格材料。") [动态范围的实际选择 ↗](../../../docs/reader-first/project-contexts.md#L15 "解释 contextIds 每次解析当前成员、发布保存本次实际材料键且范围中途变化不会覆盖。")

<a id="workflow"></a>
## 调查、写作和独立复核各解决一个问题

一次整理的主线是：**保存计划 → 解析当下材料范围 → 调查原件与必要背景 → 选择讲解路线 → 写成完整解释 → 独立补查并试读 → 通过后发布**。已有文章在新结果发布前继续可读。参考 [按当前范围启动调查 ↗](../../../apps/server/src/knowledge/pipeline.ts#L285 "支持写作前解析材料、生成维护上下文、运行研究者并把 composition 传入写作复核。")

**研究者**先回答“背景是否读够”。原生模式在本次获准的固定、只读快照中按需搜索和补读原件、结构、历史以及可见的既有知识或记忆；任务进行时不会悄悄换成主库里的新版本。已有文章与记忆只是背景，新事实仍要回原件核对。页面计划决定整次写作的可用范围；项目过滤只在获准快照内缩小发现范围，不能改变归属或扩大权限。参考 [固定研究快照与调查工具 ↗](../../../docs/reader-first/agent-research.md#L9 "解释固定只读快照、原件补读、派生背景地位和项目过滤边界。")

维护已有文章时，研究者还要回答“旧讲解路线是否仍适合当前读者”。研究结果中的 `composition` 有两种选择：路线清楚且只是局部事实或条件变化时选 `maintain`；旧结构已经遮蔽页面目的时选 `rewrite`。它还记录理由和建议路线，但这只是写作决策，不是事实结论、篇幅评分或质量分数。参考 [composition 合同 ↗](../../../packages/contracts/src/knowledge.ts#L82 "支持 maintain/rewrite、理由与讲解路线字段，并明确它是写作决定而非质量分数。")

**作者**回答“怎样让目标读者理解并行动”。在开头的例子里，作者可以据当前材料写预算、集合地点和签到安排，却不能自行补出未说明的时间或规则。选择局部维护时，refresher 保留仍有效的场景和解释；选择重新组织时，管线移除旧稿和旧章节的补丁上下文，让 writer 按当前原件、调查结论和新路线写完整文章。两种方式都保留同一页面身份、历史和材料范围。参考 [按当前范围启动调查 ↗](../../../apps/server/src/knowledge/pipeline.ts#L285 "支持写作前解析材料、生成维护上下文、运行研究者并把 composition 传入写作复核。") [维护或重组的管线分流 ↗](../../../apps/server/src/knowledge/pipeline.ts#L165 "支持 rewrite 时移除旧稿补丁上下文、向作者和复核者传递 composition、保留发布与复核流程。")

**独立复核者**在新会话拿到同一材料范围和完整草稿，自行补查事实，并尝试用文章回答页面问题。复核未通过时，两种路线都从刚生成的新草稿做局部修正；只有通过的文档会发布。独立模型复核仍不等于真实用户验收，最终还要看目标读者能否回答计划问题、理解首次出现的术语并执行下一步。当前实现已经接通维护与重组分流，但不能仅由 `mode`、引用数量或复核通过推出阅读质量改善。参考 [维护或重组的管线分流 ↗](../../../apps/server/src/knowledge/pipeline.ts#L165 "支持 rewrite 时移除旧稿补丁上下文、向作者和复核者传递 composition、保留发布与复核流程。") [读者目标与质量边界 ↗](../../../docs/reader-first/writing.md#L16 "支持按页面目标组织和试读，并说明 composition 与模型复核不能替代真实阅读质量判断。")

<a id="reader-result"></a>
## 读者得到文章，也得到继续核对的路径

发布结果按阅读意图区分：教程、解释和操作目标形成正式文章；`reference` 目标形成参考资料；对固定材料执行 `analyze` 得到内部笔记。正式文章进入主题目录、搜索和助手背景，参考资料进入独立参考目录且仍可检索，内部笔记不进入读者目录或知识召回。用途来自保存的阅读目标，不按路径、项目名或 key 前缀猜测。参考 [发布用途与来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L5 "支持正式文章、参考资料、内部笔记的用途差异，以及 citations、reviewSources、investigation 的分工。")

来源关系也分三种：正文 `citations` 支持附近论断；章节 `reviewSources` 登记未直接写进正文、但变化后必须复核的前提；`investigation` 记录角色实际读过什么。偶然读过一份材料，不会因此自动成为正文失效依据。参考 [发布用途与来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L5 "支持正式文章、参考资料、内部笔记的用途差异，以及 citations、reviewSources、investigation 的分工。")

点击正文引用时，服务端按文章依赖中保存的 digest 打开写作时的固定原件或文章版本。若固定版本不存在，会明确说明不可用，而不会静默跳到当前文字。这样读者既能顺着文章理解，也能回到当时支持结论的证据。参考 [固定引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L64 "支持按保存依赖打开固定原件或文章版本，并在缺失时给出不可用原因。")

<a id="changes"></a>
## 原文变化后，按章节判断哪些解释还能用

固定引用回答“当时依据了什么”，章节状态回答“这段解释现在是否仍适用”，两者不能混为一谈。引用始终指向写作时版本；适用性检查比较旧引用所在的完整 Markdown 章节或代码符号与当前版本。若新版只有一个同标题、同类型结构且完整文本相同，即使行号移动也可继续使用；作者身份、身份验证状态、引用或转发标记、事件时间这些参与比较的来源/事件属性发生变化时，会要求复核。图片存在、缺少引用行号或无法唯一定位结构时，也会分别保守地要求复核。标题、路径等其他任意元数据变化并不由这段比较自动判为失效。系统不会把旧引用自动改指新文字。参考 [引用上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持引用不重映射、明确列举参与比较的来源和事件属性、完整结构相同可容忍行号移动，以及图片或无法定位时保守复核。")

沿用开头的预算与地点例子：只在前面增加无关导读时，两节仍可检索，引用仍打开最初版本；把预算从八十元改为一百二十元时，费用节进入待核对并退出当前知识搜索，集合节继续可用。若集合节还把原预算登记为背景前提，那么预算变化也会让集合节待核对。参考 [局部变化与背景前提 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L93 "支持无关导读变化后章节仍可用、预算变化只影响相关节，以及 reviewSources 扩大受影响范围。")

这套判断用于**缩小复查范围**，不是自动证明语义不变。跨文件配置、调用者或运行环境若会改变本节解释，需要作者把对应原文登记为 `reviewSources`。整篇旧文仍留在目录并显示状态，当前搜索只返回仍适用的章节。参考 [章节适用性边界 ↗](../../../docs/reader-first/publication-lifecycle.md#L27 "解释当前检索只使用适用章节，并明确结构比较不是自动语义证明。")

<a id="maintenance"></a>
## 动态范围变化后仍走同一条安全更新路径

手动整理与自动维护复用同一条调查、写作和独立复核流程。自动维护默认关闭，开启前必须明确选择材料或项目/主题范围。开启后，系统用页面计划以及当前范围内每份材料的 key/digest 计算范围摘要；新聊天加入项目、材料移出项目或原件换版都会改变摘要并触发排队。连续变化会合并，运行中再次变化留给下一轮；关闭自动维护只取消自动任务，不取消用户明确发起的整理。参考 [自动维护范围摘要 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "支持自动维护启用条件、计划与材料版本摘要、任务合并和再次变化续排。") [持续维护行为 ↗](../../../docs/reader-first/publication-lifecycle.md#L39 "解释手动和自动维护共用持久队列、失败保留旧文及关闭自动维护的行为。")

维护不会把差异 hunk 当成语义结论。系统比较旧调查与依赖、旧发布选择和当前范围，把换版原件、新增材料、页面字段变化和受影响章节交给研究者；hunk 只是补读入口。只有旧文章的调查与依赖仍完全落在当前材料范围内，旧稿才会作为可评估的解释提供。研究者随后用 `composition` 决定局部维护或重组，而不是因为文章已经发布就强制保留结构。参考 [维护上下文与路线选择 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "支持变化只作为调查入口、旧稿有条件复用，并要求研究者选择局部维护或重新组织。")

发布前还有最后一道保护：页面计划必须仍与任务开始时一致；动态范围文章的当前成员集合必须仍等于新稿记录的实际选择；每个固定依赖也必须是模型读取的版本。如果整理途中又加入一条聊天或调整目标，较早结果会被拒绝，不能覆盖最新输入，旧文继续保留。参考 [发布前范围与版本保护 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "支持发布前校验页面计划、动态范围实际成员和固定依赖版本。")

因此，“让聊天进入已有文章”的准确含义是：**先把聊天保存为原件并显式归入项目或主题，让文章跟踪同一范围，再由手动或自动维护生成并复核新稿**。项目范围能帮助研究者找到相关材料，但不能代替明确归属，也不能判断新消息在语义上替换了哪条旧约定。当前尚未实现从聊天内容自动判断归属。参考 [后来消息进入项目范围 ↗](../../../docs/reader-first/project-contexts.md#L1 "解释保存归属、跟踪项目、重新整理以及范围正确不等于理解正确。") [项目调查边界与自动归属现状 ↗](../../../docs/reader-first/project-contexts.md#L23 "解释项目范围帮助发现但不判断替代关系，并确认尚未实现从内容自动归属。")
