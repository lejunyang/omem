# 从材料到可持续更新的读者文章

用“预算八十元、图书馆集合”的教学示例，解释 omem 如何从读者问题形成页面计划，在固定材料快照中调查，由作者写成可读讲解、独立角色复核后发布，并在原文变化时只标记真正受影响的章节。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 先看一次从原料到解释的变化

假设有一份教学材料《活动约定》，原文只有两项事实：“预算是八十元”“地点在图书馆”。最终页面不应只是复述这个文件，而应让第一次参加活动的人读完就知道：准备多少钱、去哪里集合、约定变化后怎样确认。于是同一份材料可以被组织成“费用”和“集合”两节，每个结论分别连回对应原文。这个例子来自仓库中的生命周期场景，不代表真实用户经历。参考 [活动约定示例 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L29 "支持教学示例的两项原始事实，以及按费用和集合组织成读者章节的可观察形态。")

关键区别是：**原件负责保存，结构块负责检索，文章负责讲清一个读者问题**。因此，文件名不是天然目录，函数也不是天然章节；页面可以跨材料组织解释，派生讲解帮助理解，却不成为新的独立事实。参考 [保存、检索与讲解分工 ↗](../../../docs/reader-first/architecture.md#L7 "解释为何文章围绕读者问题跨材料组织，而不是按文件逐一生成说明。")

<a id="brief"></a>
## 页面计划先定义读者要解决的问题

页面计划（brief）把“写什么”变成可保存的数据：页面类型、目标读者、读完能做什么、使用场景、待回答问题、主题路径和调查范围都在其中；入口路径只是调查起点，不等于文章结构。参考 [页面计划字段 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持页面类型、读者、目标、场景、问题、入口和明确材料范围的合同说明。")

当前网页把这件事做成两步：先选固定材料版本，再填写文章主题、想弄懂什么和写给谁看；这个入口目前提交的是 explanation 类型。参考 [两步整理入口 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L58 "支持当前网页收集固定材料、主题、阅读目标和读者，并提交 explanation 页面计划。") 服务端把所选 revision 转成固定 materialKeys；如果材料已经换版或不可用，会要求刷新后重选，避免调查过程中悄悄换成另一份内容。参考 [固定选材版本 ↗](../../../apps/server/src/knowledge/api.ts#L184 "支持服务端将 revision 选择解析为 materialKeys，并拒绝已更新或不可用的选择。")

计划会先独立保存，再进入写作状态。即使模型运行失败，阅读目标仍可保留并重试，所以“还没写成”不等于“页面意图丢失”。参考 [失败后保留页面计划 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L136 "展示页面计划独立保存、失败状态仍保留 plan 的实际行为。")

<a id="pipeline"></a>
## 调查、写作与独立复核各做一件事

调查者先在只读快照里建立材料目录和检索数据库；目录记录材料 key、固定 revision、路径与行数，已有文章也只在快照允许时作为背景进入。这样它可以补读完整章节、查符号或搜索相关材料，同时仍能回到固定原文核验。参考 [固定调查快照 ↗](../../../apps/server/src/knowledge/agent-research.ts#L181 "支持调查工作区保存材料目录、固定 revision、只读检索数据库和已准入文章目录。")

```mermaid
flowchart LR
  A[页面计划] --> B[调查缺失背景]
  B --> C[作者组织读者文章]
  C --> D[独立复核事实与页面目标]
  D -->|通过| E[发布]
  D -->|需修订| C
```

原生流程要求调查者自己完成补读并交出 findings 与 gaps，随后作者才写正文。作者解决的是“怎样让目标读者读懂”，不是把调查笔记原样发布；独立复核则在另一角色运行中检查引用、事实范围、时代和关键条件。参考 [调查完成后进入写作 ↗](../../../apps/server/src/knowledge/pipeline.ts#L266 "支持原生研究者必须自行完成调查，随后将 findings 和 gaps 交给作者的流程。") [独立复核职责 ↗](../../../packages/agent-runtime/roles/knowledge-verifier/1/skills/omem-knowledge-verifier/SKILL.md#L8 "解释独立复核如何核对固定原文、引用、事实范围和关键条件，而不是代写正文。") 复核若发现实质问题，草稿会带具体意见回到修订角色；只有 accepted 的文档才组装依赖并发布。参考 [写作复核与发布循环 ↗](../../../apps/server/src/knowledge/pipeline.ts#L161 "支持作者、独立复核、修订与仅发布 accepted 文档的完整编排，并展示依赖与调查轨迹的组装。")

<a id="content-types"></a>
## 文章、参考页和内部笔记不是一回事

三类产物按用途区分，而不是按文件路径猜测：

| 产物 | 面向谁 | 去哪里 |
| --- | --- | --- |
| 正式文章 | 想理解或完成任务的读者 | 主题目录、搜索、助手背景 |
| 参考资料 | 需要查字段、接口或配置的人 | 独立参考目录，也可作为背景 |
| 内部笔记 | 后续调查与分析过程 | 保留，但不进入读者目录和知识召回 |

参考 [三类知识产物 ↗](../../../docs/reader-first/publication-lifecycle.md#L9 "支持正式文章、参考资料和内部笔记的产生方式、展示位置与召回边界。")

一篇文章里还有三种来源关系。**正文引用**直接支持附近论断，读者可以点开；**reviewSources**记录未写进正文、但变化后必须重核该节的关键前提；**investigation**只记录研究者、作者和复核者实际读过什么。偶然读过的材料不会因此成为文章事实，也不会单独让正文失效。参考 [三种来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L19 "解释正文引用、章节背景前提和调查轨迹的不同作用及失效边界。") 发布时，材料依赖来自正文引用和 reviewSources，实际读取轨迹另存，这正是“证据”和“调查过程”分开的实现。参考 [证据依赖与读取轨迹 ↗](../../../apps/server/src/knowledge/pipeline.ts#L180 "支持发布时从 citation 与 reviewSources 构造依赖，并将实际读取另存为 investigation。")

<a id="reading"></a>
## 新读者看到的是文章，证据仍可逐层展开

发布后，知识库把“主题文章”和“参考资料”分成两个入口，并按保存的 topicPath 组织；分类帮助浏览，不等于依赖关系。参考 [主题文章与参考资料入口 ↗](../../../apps/web/src/knowledge/KnowledgeHome.vue#L343 "支持知识库按角色分入口、按主题路径展示文章并标记待更新状态。") 打开文章后，读者先看到标题、摘要和“读完这一篇”的目标，再按人读章节阅读；生成模型、复核者和时间折叠在“来源与生成记录”里，不抢占正文主线。超过两节时还会出现页内目录。参考 [文章阅读页面 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L69 "支持标题、摘要、阅读目标、章节、页内目录及折叠生成记录的最终阅读形态。")

在活动示例中，“准备八十元”可以打开预算原文，“去图书馆集合”可以打开地点原文。引用面板先解释关系和引用理由，再进入固定版本的原始材料范围或被引用文章的具体章节；目标不可用时会显示人能理解的原因。参考 [固定引用下钻 ↗](../../../apps/web/src/knowledge/KnowledgeFrame.vue#L83 "支持引用面板展示关系和理由，并打开固定子文章章节或原始材料范围；不可用时给出原因。") 因而，文章给出整体解释，参考页帮助精确查阅，固定引用则让读者继续追到当时真正依据的内容。

<a id="change"></a>
## 原文变化后，只重核受影响的理解

引用始终固定在写作时的版本；生命周期判断主要比较引用所在的完整 Markdown 章节或代码符号是否仍一致，来源身份、验证状态和事件时间等关键元数据变化也会要求重核。若只是前面插入导读、内容整体后移，旧引用不被自动改写，解释仍可继续使用。参考 [章节上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持引用固定旧版本、主要按完整章节或符号比较内容，并说明来源身份、验证状态和事件时间等关键元数据变化也会触发复核。")

活动示例展示了可观察结果：只改导读时，集合信息仍可搜索，引用仍指向旧 revision；把预算从八十元改成一百二十元后，“费用”变为待核对，“集合”仍是 current，搜索也不会继续用待核对的费用节回答。参考 [预算变化的局部影响 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L92 "展示导读移动不影响固定引用，以及预算变化后费用待核对、集合仍可检索的实际结果。") 如果集合方案还隐含依赖原预算，作者应把该前提登记为 reviewSources；预算变化时，集合节也会明确提示“背景前提已有变化”。参考 [背景前提变化 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L165 "展示 reviewSources 如何让正文未变但依赖预算的集合章节进入待核对状态。")

页面不会抹掉旧解释：对应章节显示原因，未受影响部分继续可读。参考 [保留旧解释并标出原因 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L76 "支持阅读页在对应章节显示待核对原因，同时保留旧解释和其他可读章节。") 读者点击“重新整理这篇”时，系统沿用已保存的 brief，以当前选定材料重新调查、写作和复核。参考 [沿用计划重新整理 ↗](../../../apps/server/src/knowledge/api.ts#L169 "支持重新整理复用已保存 brief，并用当前固定材料再次启动完整流程。") 这套机制定位的是**复查范围**，不是对语义不变的自动证明；当前也没有完整调用图或后台自动重写所有受影响页面。参考 [局部更新的能力边界 ↗](../../../docs/reader-first/publication-lifecycle.md#L27 "说明章节变化判断只是定位复查范围，当前没有完整调用图、自动语义影响分析或后台自动重写。")

<a id="change-points"></a>
## 想改进这条流程，从目的对应的入口下手

如果要改“页面计划能表达什么”，先看 brief 与知识文档合同；如果要改调查、作者、修订和复核的顺序，进入知识管线；如果要改原文换版后的章节状态，进入生命周期判断；如果要改读者怎样创建和阅读文章，则从整理弹窗、知识目录、文章页和引用面板入手。合同入口参考 [页面计划字段 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持页面类型、读者、目标、场景、问题、入口和明确材料范围的合同说明。")，管线入口参考 [调查完成后进入写作 ↗](../../../apps/server/src/knowledge/pipeline.ts#L266 "支持原生研究者必须自行完成调查，随后将 findings 和 gaps 交给作者的流程。") [写作复核与发布循环 ↗](../../../apps/server/src/knowledge/pipeline.ts#L161 "支持作者、独立复核、修订与仅发布 accepted 文档的完整编排，并展示依赖与调查轨迹的组装。")，更新判断参考 [章节上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持引用固定旧版本、主要按完整章节或符号比较内容，并说明来源身份、验证状态和事件时间等关键元数据变化也会触发复核。")，读者界面参考 [两步整理入口 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L58 "支持当前网页收集固定材料、主题、阅读目标和读者，并提交 explanation 页面计划。") [文章阅读页面 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L69 "支持标题、摘要、阅读目标、章节、页内目录及折叠生成记录的最终阅读形态。") [固定引用下钻 ↗](../../../apps/web/src/knowledge/KnowledgeFrame.vue#L83 "支持引用面板展示关系和理由，并打开固定子文章章节或原始材料范围；不可用时给出原因。")。

这几处共同维持一个边界：页面以读者问题组织，事实仍回到固定材料，调查记录不冒充证据，更新也不轻易抹掉仍然有用的解释。
