# 把材料整理成一篇真正能用的文章

以“预算八十元、图书馆集合”的教学夹具贯穿页面计划、固定快照调查、面向读者写作、独立复核、固定引用和章节级维护，并说明手动整理与默认关闭的持续维护如何共用持久队列。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="scenario"></a>
## 从两句活动约定开始

一篇能用的知识文章，不是把每个文件换一种说法，而是**围绕读者要解决的问题重组原始事实，并让解释仍能回到写作时的原件**。

贯穿本文的例子是一份测试夹具：原件只写了“预算是八十元”和“地点在图书馆”，产物则把它们组织成“费用”和“集合”两节，各自引用对应原句。**这只是教学示例，不是真实活动记录或模型运行实录。**参考 [活动约定教学夹具 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L38 "支持预算与地点两条原始事实，以及它们被组织成费用和集合两节的教学示例。")

对参加者来说，有用的问题不是“这个文件有哪些段落”，而是“要准备多少钱、去哪里集合”。omem 因而把三种单位分开：原件及版本保存事实，章节或函数等结构块服务检索，文章围绕一个读者问题跨材料讲解。派生文章可以引导理解，却不成为第二份独立事实。参考 [保存、检索与讲解单位 ↗](../../../docs/reader-first/architecture.md#L7 "解释原件、结构块和读者页面的职责差异，以及派生解释不是独立事实。")

<a id="page-plan"></a>
## 页面计划先定义读者问题

网页把创建过程分为两步：先选择材料，再填写主题、想弄懂什么和写给谁看。编辑旧文章时仍使用这两步，并明确提示重新整理后还是同一篇文章、旧版引用继续保留。参考 [两步创建与编辑界面 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L124 "支持先选材料再说明阅读目标，并说明编辑后保持同一文章和旧版引用。")

这些输入形成**页面计划**。合同中的计划包含页面类型、读者、目标、场景、问题、调查入口和可选主题路径；`entryPaths` 只是起读线索。`materialKeys` 若存在，就限定可调查的原件；若省略，合同允许在全部符合条件的已捕获材料中调查。参考 [页面计划合同 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持计划字段以及 materialKeys 可选、entryPaths 仅作入口的条件式范围语义。")

当前网页不是开放范围：提交新建或编辑请求时，服务端要求至少选择一份当前固定材料，并把所选版本换成 `materialKeys` 后保存计划、加入整理队列。网页在新建或目标改变时，还会暂时把目标同时作为场景和唯一问题，并把入口初始化为空；这只是界面默认值，不代表底层计划只能有一个问题。参考 [网页目标默认映射 ↗](../../../apps/web/src/knowledge/ArticleComposer.vue#L80 "支持新建或目标变化时用目标初始化场景和问题、入口为空。") [选材保存并排队 ↗](../../../apps/server/src/knowledge/api.ts#L207 "支持服务端校验固定材料版本、写入 materialKeys、保存计划并加入维护队列。")

在活动示例里，计划可以表达为：读者是参加者，目标是“出发前知道带多少钱、去哪里”，问题是“费用和集合地点分别是什么”。同样两句原文因此成为准备说明，而不是一篇“活动约定文件介绍”。

<a id="workflow"></a>
## 一次整理如何走到发布

主流程是：**保存页面计划 → 调查原件与必要背景 → 写成完整解释 → 独立补查和试读 → 通过后发布**。`writePage` 先保存计划并把页面标为写作中；成功后标为已发布，失败则记录失败状态。已有文章在新结果通过前不会被替换。参考 [页面生成状态主流程 ↗](../../../apps/server/src/knowledge/pipeline.ts#L258 "支持保存计划、写作状态、成功发布和失败状态，以及已有正文直到新稿发布前保持可用。")

原生模式会把本次获准的固定原件、历史以及范围内可用的既有知识导入只读研究快照。任务期间，主库发生变化不会让角色悄悄读到另一版。研究者可以列目录、搜材料、读完整章节或函数、看历史版本和候选调用位置；既有文章和记忆只提供背景，新增事实仍须回原件核对。原生会话没有旧宿主的三轮调查门槛；非 ACP 的兼容路径仍保留有界三轮流程。参考 [固定只读研究快照 ↗](../../../docs/reader-first/agent-research.md#L11 "支持固定原件导出、只读快照、调查工具、历史与既有知识仅作背景。") [原生与兼容研究路径 ↗](../../../apps/server/src/knowledge/pipeline.ts#L273 "支持按 materialKeys 确定范围、原生研究完成后写作，以及兼容路径的有界三轮调查。")

原生研究者必须自行完成读取，提交 `ready=true` 且没有遗留请求，才会把 findings 和 gaps 交给作者。若维护同一篇且旧稿仍在新选材范围内，作者角色改用 refresher；否则用 writer 从当前范围重写。参考 [原生与兼容研究路径 ↗](../../../apps/server/src/knowledge/pipeline.ts#L273 "支持按 materialKeys 确定范围、原生研究完成后写作，以及兼容路径的有界三轮调查。")

<a id="roles"></a>
## 研究、写作与独立复核各挡一道风险

**研究者**回答“背景是否读够了”。它从计划问题出发寻找原件、上下文与历史，而不是把目录顺序当成文章结构。

**作者或 refresher**回答“怎样让目标读者理解并行动”。在活动例子中，可以据原件写“准备八十元，到图书馆集合”，却不能自行补出集合时间、支付方式或参加资格。维护时，旧稿只帮助保留仍有价值的解释，不是事实来源。

**独立复核者**回答“事实、范围和页面目的是否都成立”。它在新会话拿到相同原件范围和草稿，自行补查，并尝试用文章回答页面问题；不是只检查作者挑好的引用。只有 accepted 的文档会发布；被拒绝的目标携具体问题交给 refresher，最多进行四轮写作与复核，仍有实质问题就不发布新稿。参考 [写作与独立复核循环 ↗](../../../apps/server/src/knowledge/pipeline.ts#L162 "支持 refresher 选择、独立 verifier、最多四轮修订和仅发布 accepted 文档。")

因此，独立复核不是润色，也不等于真实读者验收。工程上还应让目标读者判断：能否用文章回答计划问题、术语是否足够清楚、下一步是否可执行。参考 [阅读目标与验收标准 ↗](../../../docs/reader-first/writing.md#L16 "支持复核先尝试回答页面问题，并区分事实检查、读者检查和真实用户验收。")

<a id="reader-result"></a>
## 读者看到的是文章、用途和可追溯依据

阅读页展示标题、摘要、“读完这一篇”的目标、按问题组织的章节以及必要的待核对问题。某节需要更新时，页面在该节提示原因并保留旧解释；来源折叠区说明生成者、独立复核者和固定原件。参考 [文章阅读页面 ↗](../../../apps/web/src/knowledge/KnowledgeDocument.vue#L87 "支持阅读目标、章节级状态、正文问题和来源生成记录的呈现。")

发布物有三种用途：

| 用途 | 面向谁和什么任务 | 是否进入读者目录与默认召回 |
| --- | --- | --- |
| 正式文章 | 围绕教程、解释或操作目标连续讲解 | 是 |
| 参考资料 | 快速查字段、接口或状态 | 进入单独参考目录，也可搜索 |
| 内部笔记 | 保存明确选中材料的内部分析 | 否 |

用途由保存的阅读目标和发布意图决定，不按路径、项目名或 key 前缀猜测。来源关系也要分开：正文 `citations` 支持附近论断；章节 `reviewSources` 登记没有直接写进正文、但变化后必须复核的前提；`investigation` 只是角色实际读过什么的审计轨迹。偶然读过的材料不会仅因换版就让正文失效。参考 [发布用途与三种来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L9 "支持正式文章、参考资料、内部笔记的用途差异，以及引用、背景前提和调查轨迹的区别。")

点击引用时，API 用文章依赖中保存的 digest 解析固定文章版本或固定原件版本。界面先展示关系和引用理由，再打开相应范围；固定版本缺失时给出不可用原因，不会静默跳到当前文字。参考 [固定引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L66 "支持按保存依赖解析固定文章或原件版本，并返回明确的不可用原因。") [引用阅读界面 ↗](../../../apps/web/src/knowledge/KnowledgeFrame.vue#L84 "支持先展示关系和理由，再打开固定文章或原件范围。")

<a id="changes"></a>
## 材料变化后只让受影响章节退出当前召回

固定引用和“这段解释现在是否仍适用”是两件事。引用始终指向写作时的版本；适用性检查则比较旧版与当前版中引用所在的完整结构。若新版唯一存在同标题、同类型结构且完整文本相同，即使整体行号移动也可继续沿用；来源身份元数据变化、图片、缺少行号、无法定位结构或出现多个同名候选时会保守判变。系统不会把旧引用自动改指新文字。参考 [固定引用的上下文比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持引用不重映射，以及唯一同标题同类型完整结构不变时允许行号移动。")

活动夹具验证了三个分支：

- 只在预算章节前增加无关导读，费用与集合两节仍可用，引用仍打开最初版本。
- 把预算从八十元改为一百二十元，费用节进入待核对并退出当前搜索，集合节仍可读、可检索。
- 如果集合节另行登记“集合方案以原预算为前提”，同一次预算变化也会让集合节待核对。参考 [局部变化测试 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L93 "支持无关导读变化不影响章节、预算变化只使费用节待核对且集合节仍可检索。") [未引用前提变化测试 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L166 "支持通过 reviewSources 登记预算前提后，预算变化也会使集合节待核对。")

这套机制是**定位复查范围**，不是字符串或 AST 已经证明语义不变。共享搜索只返回仍适用的章节，但整篇旧文章仍留在目录并明确显示 `needs-review`；被其他文章引用时，状态沿所引固定版本和具体章节传播。跨文件配置、调用者或运行环境若会改变解释，需要作者登记为 `reviewSources`。当前没有完整调用图或自动语义影响分析。参考 [章节适用性及边界 ↗](../../../docs/reader-first/publication-lifecycle.md#L27 "解释当前章节级失效、搜索过滤、文章依赖传播和自动语义影响分析的边界。")

<a id="maintenance"></a>
## 手动整理和持续维护共用一条安全更新路径

文章仍可手动点击“重新整理这篇”或“调整材料与目标”。此外，现在可以开启**随所选材料自动更新**：它默认关闭，且只有计划已经明确 `materialKeys` 才能开启；只跟踪这篇文章选中的材料，不会按路径、项目名或相似词擅自加入新来源。新材料仍需通过调整选材或补充背景进入计划。参考 [持续维护的范围与触发 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "支持默认需显式开启、仅跟踪 materialKeys、合并变化和自动任务取消规则。")

手动请求与自动触发都进入同一种 `knowledge:maintain-page` 持久任务。连续变化会合并为一个页面请求，执行时读取最新选材；运行中再次变化会排下一轮。设置与待办可以跨服务重启恢复。关闭持续维护会取消尚未完成的自动任务，但不会取消用户明确发起的整理。失败会保留旧文，并避免对同一失败输入无限重跑；手动重试或新的材料版本可以再次执行。参考 [持续维护的范围与触发 ↗](../../../apps/server/src/knowledge/page-worker.ts#L64 "支持默认需显式开启、仅跟踪 materialKeys、合并变化和自动任务取消规则。") [持久队列行为测试 ↗](../../../apps/server/tests/knowledge-page-worker.test.ts#L33 "支持连续变化合并、重启恢复、失败保留旧文、重试和关闭自动任务的行为。")

维护不会从头遍历材料库。系统比较旧阅读目标、旧依赖和调查轨迹与当前选材，向角色提供变化字段、版本差异 hunk、新增材料和旧章节状态。hunk 只是补读入口，不是语义结论。只有旧稿的全部调查与依赖仍落在新范围内时，refresher 才能看到旧正文；若用户移除了旧来源，系统不把旧稿带入上下文，而由 writer 按新范围重写，避免恢复已经移出的事实。参考 [维护上下文规划 ↗](../../../apps/server/src/knowledge/maintenance.ts#L35 "支持基于旧依赖与调查记录计算变化，只在旧稿仍处于新选材范围时复用，并精简发布 trace。") [移除来源后不复用旧稿 ↗](../../../apps/server/tests/knowledge-pipeline.test.ts#L203 "支持旧来源被移出选择时切换到 writer，且三角色上下文不再暴露旧正文。")

发布前还会再次比较当前计划和所有固定依赖。若整理期间读者改变目标、加入补充材料或原件再次换版，较早结果不能覆盖最新计划和输入。参考 [发布前输入保护 ↗](../../../apps/server/src/knowledge/repository.ts#L206 "支持发布前比较当前计划与固定依赖，阻止过时结果覆盖最新输入。")

如果材料缺少会改变行动的信息，作者应留下结构化问题，而不是用常识补造。读者回答后，答案保存为新的原始材料、加入同一页面计划并标记待核对；下一轮调查、改写和独立复核都能读取它。开启持续维护时后台会排队，否则需要手动整理；保存回答本身不等于正文已经更新。参考 [补充回答成为新原件 ↗](../../../apps/server/src/knowledge/repository.ts#L305 "支持把读者回答保存为原始材料、加入页面计划并标记文章待核对。") [三角色读取补充背景 ↗](../../../apps/server/tests/knowledge-pipeline.test.ts#L153 "支持下一轮研究者、refresher 和 verifier 都收到回答材料，并保留旧文章版本。")

当前已接通的是“明确选材上的持久触发、完整重写与独立复核”，**不是自动语义影响分析，也没有证明复杂长文的模型维护质量稳定**。改进这条链路时，可分别从页面计划合同、研究快照、写作与复核流水线、维护上下文、持久队列、发布并发保护和章节适用性入手；验收既检查事实与固定引用，也检查新读者能否真正完成页面目标。
