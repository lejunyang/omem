# 把材料写成一篇能用的文章

用一份活动约定贯穿 omem 的知识生成过程：先把读者问题和调查范围写成页面计划，再由研究者补齐背景、作者重组事实、独立复核者自行核对，最后发布带固定依据的正式文章。文章同时说明正式文章、参考页与内部笔记的区别，固定选材与持续跟踪项目的差别，以及原文变化后如何把复查缩小到真正受影响的解释。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="from-facts-to-page"></a>
## 文章不是材料的复述，而是对读者问题的回答

把材料写成知识文章，关键不是“每份文件生成一段摘要”，而是先确定读者读完要解决什么问题，再跨材料组织答案。原件负责保留当时说了什么，检索结构负责帮助找到相关段落，文章负责把这些段落变成可理解、可行动的解释；文章能帮助理解，却不会取代原件成为另一份事实。参考 [问题驱动的知识生成 ↗](../../../docs/reader-first/architecture.md#L5 "支持原件、检索结构与文章承担不同职责，以及从阅读目的到调查、写作、检查、发布和增量更新的整体路线。")

下面全篇使用一个**教学示例**：一份活动约定写着“预算八十元、在图书馆集合”。如果只是复述原文，读者仍要自己判断该准备什么、该去哪里；面向参加者的文章则可以重组为“费用准备”和“集合安排”，说明八十元对应活动预算，集合地点是图书馆。后来又收到“改到东侧阅读室，小周负责签到”的聊天时，问题也不是把消息接在文末，而是重新回答：地点是否替代旧安排、签到人是谁、哪些费用约定仍然有效。

因此，一次完整生成可以概括为：

1. 明确读者、场景和要回答的问题；
2. 确定允许调查的材料范围；
3. 围绕问题补读必要背景；
4. 把事实重组为完整解释并绑定依据；
5. 让独立复核者自行查证，并试着用草稿回答原问题；
6. 通过后发布，在依据变化时重新检查受影响的部分。

这条路线把“保存了什么”和“读者需要理解什么”分开：前者保证可追溯，后者决定页面是否真的有用。

<a id="plan-purpose-and-scope"></a>
## 页面计划同时定义阅读目的和调查范围

页面计划有两层，缺一层都会让生成偏离目标。

| 层次 | 计划中的内容 | 在活动示例中解决什么 |
| --- | --- | --- |
| 阅读目的 | 页面类型、目标读者、读完后的目标、使用场景、要回答的问题 | 明确这是给参加者看的解释，要回答“准备多少费用、去哪里、变化后怎么确认” |
| 调查范围 | 明确选择的材料、持续跟踪的项目或主题，以及起读线索 | 决定活动约定、后来聊天和哪些背景可以进入调查 |

实现中，`reader`、`goal`、`scenario` 和 `questions` 描述目的；`materialKeys` 是明确选中的原件，`contextIds` 是持续跟踪的项目或主题成员，`entryPaths` 只是从哪里开始读，`topicPath` 只决定文章在人读目录中的位置。目录位置不会自动扩大调查范围，起读线索也不是只能读取的文件清单。参考 [页面计划的目的与范围字段 ↗](../../../packages/contracts/src/knowledge.ts#L64 "支持阅读目的字段、明确材料范围、动态项目范围、起读入口和主题目录之间的区别。")

固定选材和项目范围可以合用：运行时取“明确材料”与“所选项目当前成员”的并集；若两者都没有，底层计划语义才开放到全部合格材料。明确选择的材料已经不可用时，运行会要求先调整范围。参考 [计划如何解析材料 ↗](../../../apps/server/src/knowledge/repository.ts#L123 "支持明确材料与项目当前成员取并集、两者均未指定时使用全部合格材料，以及不可用明确材料会报错。")

对活动说明而言，较好的页面计划不是“总结 activity.md”，而是：

- 读者：准备参加活动的人；
- 目标：能确认费用、集合地点和变更后的安排；
- 问题：要准备什么、去哪里、谁负责签到、哪条新消息替代了旧约定；
- 范围：活动约定，加上“阅读小组”项目里的后续记录；
- 入口：约定文件或活动聊天，只用于帮助研究者开始调查。

这样，文件只是证据入口，问题才是文章结构的来源。

<a id="three-roles"></a>
## 研究者、作者和独立复核者解决不同问题

生成过程故意把“找到足够依据”“写成解释”和“检查解释”分开。三者在同一批获准材料上工作，但不会共享一个不断变化的主库视图：原生调查把本次获准原件、历史及相关知识背景封装成固定只读快照，任务中途不会悄悄换成新版本。研究者可以按需搜索和补读，作者仍可继续读取，复核者则在独立新会话中自行补查。参考 [固定只读调查快照 ↗](../../../docs/reader-first/agent-research.md#L9 "支持研究者、作者和独立复核者的读取能力，以及任务中途不悄悄切换原件版本。")

**研究者解决“还缺什么背景”。** 它从页面计划出发，搜索和补读原件、相关章节、调用者、测试或已有解释，直到能回答页面问题。已有旧文时，它还判断应保留清楚的阅读路线并局部维护，还是旧结构已经妨碍目标、需要重新组织。运行时只有研究已经完成且没有遗留读取请求，调查结论才交给作者。参考 [研究完成后才进入写作 ↗](../../../apps/server/src/knowledge/pipeline.ts#L285 "支持按页面计划解析当前材料、先运行研究者，以及只有研究完成且没有遗留读取请求时才交给作者。")

在活动示例中，研究者需要查清“东侧阅读室”是否属于同一活动、它是否替代“图书馆”、小周的角色是什么，以及预算有没有同时变化。它不能只因两个活动名字相似，就把另一场活动的记录混进来。

**作者解决“读者怎样理解和使用这些事实”。** 作者不按材料顺序抄写，而是围绕页面问题重组内容：把预算放进费用准备，把地点变更和签到人放进集合安排；直接论断绑定正文引用，未写进正文但会改变解释的重要前提登记为章节背景依据。

**独立复核者解决“完整草稿是否真的答对了”。** 它拿到草稿和相同材料范围后自行补查原件，并尝试用草稿回答阅读目标。事实、必要条件或页面目的有问题时，草稿进入返修；只有结论为 `accepted` 的文档才会组装依赖并发布。参考 [写作、独立复核与发布门槛 ↗](../../../apps/server/src/knowledge/pipeline.ts#L165 "支持复核者独立检查完整草稿、未通过进入返修，以及只有 accepted 文档才组装依赖并发布。")

这三种职责不能互相替代：研究者读过某条消息，不代表作者表达准确；作者带了引用，不代表页面回答了参加者的问题；复核通过是发布门槛，也不等于读者已经验收。

<a id="reader-result"></a>
## 读者拿到正式讲解，仍能回到写作时的原件

发布以后，读者面对的不是调查日志，而是一篇可在主题目录中阅读、搜索、继续追证的文章。系统把三类产物分开：

| 产物 | 用途 | 是否进入读者目录与知识召回 |
| --- | --- | --- |
| 正式文章 | 围绕入门、解释或操作目标回答问题 | 是 |
| 参考页 | 按查询对象组织接口、字段或事实 | 进入独立参考目录，也可检索 |
| 内部笔记 | 对明确选中的材料做内部分析 | 否 |

用途来自保存的阅读目标，不从文件路径、项目名或 key 猜测。正文引用说明某个论断依据哪里；章节背景依据记录“虽然没直接写进正文，但它变化后必须复查”的条件；调查轨迹只说明角色实际读过什么，偶然读到不等于正文依赖。参考 [三类产物与三种来源关系 ↗](../../../docs/reader-first/publication-lifecycle.md#L5 "支持正式文章、参考页、内部笔记的用途区别，以及正文引用、章节背景前提和调查轨迹的不同作用。")

在活动文章里，“预算八十元”可以链接到原约定，“改到东侧阅读室”可以链接到后来的聊天。点击引用时，系统按文章依赖中保存的版本标识打开**写作当时的原件版本**；如果该版本不可用，会明确显示不可用，不会悄悄跳到当前文字。参考 [固定版本引用解析 ↗](../../../apps/server/src/knowledge/api.ts#L64 "支持引用按文章依赖中的固定版本解析，缺失时明确不可用而不跳到当前原件或文章。")

这里可以用场景理解两个术语：

- **Source** 是同一份原件跨换版保持不变的身份，例如那份活动约定；
- **Revision** 是某次保存下来的具体内容，例如仍写着“图书馆”的旧版，或后来写着“东侧阅读室”的新版。

固定版本回答“这篇文章当时依据什么”。至于文章现在是否仍适用，则由下一节的章节状态回答。

<a id="change-and-review"></a>
## 原文变化后，只复查真正受影响的解释

材料更新时，系统不会把旧引用改写成新引用，而是判断旧依据所在的完整结构是否仍适用。来源身份、转述状态或事件时间等关键属性改变，引用缺少可定位范围、涉及图片，或者找不到明确结构时，都会保守地要求复查。普通章节或代码结构则要求新版中存在唯一的同标题、同类型上下文，而且完整文本相同；行号移动本身不构成变化。参考 [普通章节上下文是否仍适用 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L72 "支持来源属性检查、结构定位、完整上下文比较、不自动重映射旧引用，以及唯一一级标题时进入细分比较。")

活动原文还揭示了一个更细的边界。若一条引用跨过一篇 Markdown 文档的导读、预算和地点，而最小包围结构恰好是唯一的一级标题，系统不会把一级标题下所有后续内容都视为依赖。它把这个根范围拆成导读和互不重叠的下级完整章节，只选择与原引用范围相交的部分；新版中的对应部分必须按导读标记、标题和层级唯一找到，仍保持相邻顺序，并逐项全文相同。嵌套在预算下的“费用条件”属于预算完整章节，不会因拆分而遗漏。参考 [跨 Markdown 根范围的细分比较 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "支持将唯一根标题拆成导读与完整子章节，只比较引用相交部分，并要求新版对应部分唯一、相邻且全文相同。")

由此可以区分几种变化：

1. **只改引用范围之外的“筹备记录”。** 导读、预算和地点都没变，相关解释仍可用，引用仍打开旧 revision。
2. **把“费用不含交通”改为“费用包含交通”。** 这句话虽然不是引用中抽出的短句，却属于预算完整章节，因此“费用准备”需要复查。
3. **在原来覆盖的预算与地点之间插入“参加条件”。** 所选部分不再连续相邻，“费用准备”也需要复查，避免新增条件从比较中消失。

这些边界已有针对跨根范围、嵌套条件和跨度内插入章节的实现测试；较早的章节级场景也验证了预算变化只让费用节待复查，而地点节仍可搜索。参考 [跨根范围、嵌套条件与新增章节测试 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L137 "支持范围外筹备记录变化不影响费用节、嵌套费用条件变化触发复查，以及跨度内插入新章节也触发复查。") 参考 [预算变化只影响费用节 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L93 "支持导读变化不使文章失效、预算变化只标记费用节，而地点节继续可搜索且引用固定在原版本。")

还有一种依赖不会出现在正文引用里：如果集合方案实际上以预算为前提，作者应把预算登记为“集合安排”的章节背景依据。预算变化时，集合节也会进入待复查；这种传播只在作者明确登记前提后成立。参考 [背景前提传播到集合节 ↗](../../../apps/server/tests/knowledge-lifecycle.test.ts#L193 "支持作者登记 reviewSource 后，预算变化会使依赖预算的集合节进入待复查状态。")

这套机制的价值是**缩小复查范围**，不是证明新旧内容语义等价。跨文件配置、调用条件、运行环境或未登记的约定仍可能改变解释；结构比较只指出“哪里值得重看”，理解和改写仍由研究者、作者与复核者完成。

<a id="new-chat-loop"></a>
## 让一条新聊天进入已有文章

仅把新聊天保存到材料库还不够。要让“场地改到东侧阅读室，小周负责签到”进入已有活动文章，需要完成三步：

1. **把聊天明确归入项目或主题。** 在“输入材料”中选择或创建“阅读小组”，保存聊天时一并保存归属；已有材料也可以在原文页面调整归属。
2. **让文章持续跟踪这个范围。** 在“调整材料与目标”中选择“持续跟踪项目或主题”，并按需另选背景材料。
3. **重新运行生成。** 开启自动更新后，新成员、成员换版或移出会进入持久队列；未开启时手动重新整理。两条路径都会重新经过调查、写作和独立复核，而不是把消息直接拼进正文。参考 [项目材料进入文章的步骤与边界 ↗](../../../docs/reader-first/project-contexts.md#L3 "支持显式保存归属、文章持续跟踪项目、自动或手动重新整理、整个项目成员进入范围，以及范围正确不等于理解正确。")

归属是用户明确保存到稳定 Source 身份上的关系，与文章分类和正文引用彼此独立；实现不会根据文件名、会话 ID 或材料正文自动猜项目。参考 [项目归属不靠内容推断 ↗](../../../apps/server/src/contexts/repository.ts#L5 "支持项目归属是与分类和引用独立的显式 Source 关系，不从文件名、会话 ID 或正文推断。") 当前文档也明确说明：范围正确只保证材料有机会被调查，模型仍需判断地点是否替代旧安排、负责人角色是什么。参考 [项目材料进入文章的步骤与边界 ↗](../../../docs/reader-first/project-contexts.md#L3 "支持显式保存归属、文章持续跟踪项目、自动或手动重新整理、整个项目成员进入范围，以及范围正确不等于理解正确。")

这也解释了三种选材方式的差别：

- **跟踪项目或主题**：范围是动态的。后来明确加入该范围的聊天会在下一次运行中自动成为候选；项目成员整体进入，不能只在这篇文章里排除其中一项。若文章只讨论项目的一部分，应取消整项目跟踪，改用固定选材。
- **只选固定材料**：范围只包含所选原件。后来保存的新聊天不会因为内容相似而进入文章，必须手动加入选材。
- **两者合用**：项目成员提供持续范围，额外材料提供必要背景。

自动更新默认关闭，而且只有文章已经明确选择材料或项目范围时才能开启。队列会合并连续变化，运行中再次发生的变化留到下一轮；失败时旧文章继续可读，不会被失败草稿覆盖。参考 [自动维护的条件与行为 ↗](../../../docs/reader-first/publication-lifecycle.md#L45 "支持自动更新默认关闭、要求明确范围、连续变化合并、运行中变化进入下一轮以及失败保留旧文。")

发布前还有最后一道一致性检查：页面目标是否在运行中被修改、动态项目的实际成员是否改变、每个固定依赖是否仍是调查时的版本。任一项变化都会拒绝较早结果覆盖当前输入，并保留旧文，再按最新范围重新整理。参考 [发布前校验最新输入 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "支持发布前重新检查页面计划、动态范围实际成员和固定依赖版本，避免旧结果覆盖新输入。")

于是，一条新聊天进入已有文章的完整闭环是：**明确归属 → 动态范围变化 → 手动或自动排队 → 固定快照内重新调查 → 写作 → 独立复核 → 发布前再校验**。这里能确定的是材料进入范围和发布一致性机制；它们不会自动完成新旧消息的语义判断，也不能据此推断复杂大库或模糊归属下必然可靠。
