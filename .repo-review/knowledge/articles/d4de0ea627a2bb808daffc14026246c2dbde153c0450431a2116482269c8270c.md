# 规则变了以后：原文、记忆与待办如何更新

用“重试三次改为五次”和“明早跟进评审”两个相互独立的输入，解释原文保存、记忆提取与应用、来源换版后的失效和重核验、Wiki 重新整理，以及等待、检查时间、截止时间、暂缓和通知已读的差别。给出判断更新是否真正完成的状态尺，并说明如何依据当前实例状态判断后台是否会继续处理。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="separate-fact-and-action"></a>
## 先分清：规则变化不是新的交办

先看结论：**“规则从重试三次改为五次”更新的是事实；“明早帮我跟进评审”创建的是行动。** 两条信息可以有关联，但不能互相代替授权。

以下是贯穿全文的教学示例：

- 材料 A 原来写“评审失败后重试三次”，后来同一来源改成“重试五次”。系统应保存新版，并暂停使用依赖旧版的记忆；只有新版经过提取、核验和应用，当前记忆才真正变成“五次”。
- 材料 B 是当前用户另发的一条消息：“帮我跟进评审回复，明早提醒我检查。”这才是明确交办，可以形成一条事项。
- 不能因为材料 A 出现“评审”“重试”或“提醒”等词，就推断用户要求创建待办。当前助手在模型之外还有明确意图门槛：咨询或讨论即使让模型产出了建任务候选，也不会自动落库。参考 [明确交办意图门槛 ↗](../../../apps/server/src/assistant/runtime.ts#L208 "说明咨询问题不能仅因模型提出 create_task 就自动创建事项。") [讨论不转成个人任务的测试 ↗](../../../apps/server/tests/task-follow-up.test.ts#L83 "直接验证他人的承诺和普通讨论不会成为当前用户的事项。")

因此，阅读系统状态时要分别问四件事：**原话是否保存、当前事实是否已应用、解释文章是否仍适用、行动是否已创建或推进。**

<a id="capture-to-memory"></a>
## 一条原始记录怎样成为可用记忆

材料进入系统后，不会直接变成“系统认定的事实”。完整链路有四层：

1. **保存原文。** 系统按来源身份查找已有记录；内容变化时创建新的不可变版本、切换来源当前版本，并递增有效性 epoch。携带相同生产者与 event ID 的重复事件会复用捕获回执；同一来源的当前版本若内容指纹相同，也会复用该版本。原始材料会排入学习队列，模型派生材料不会再次自我学习。参考 [捕获事件与来源内容去重 ↗](../../../apps/server/src/store.ts#L150 "支持按生产者和事件 ID 复用捕获回执，并在同一来源当前内容相同时复用既有版本；内容变化时创建新版并推进来源状态。") [原始材料进入学习队列 ↗](../../../apps/server/src/store.ts#L351 "说明原始材料排 extract_claims，而派生材料被阻止自循环。")
2. **提取候选。** 后台提取器从固定版本中产生观察、记忆候选或放弃理由。运行前还会检查任务引用的版本是否仍是来源当前版本；来源已经前进时，旧任务以过期输入停止，不能把旧内容写回当前状态。提取器运行并保存输出后，若仍有待处理候选，才会创建后续的核验任务。参考 [学习任务拒绝过期输入 ↗](../../../apps/server/src/learning/pipeline.ts#L290 "支持模型运行前核对来源当前 head、sourceId 和 validityEpoch。") [提取完成后排队独立核验 ↗](../../../apps/server/src/learning/pipeline.ts#L550 "说明提取器先运行模型并保存输出，再为待处理候选创建 queued 的 verify_proposals 任务，因此 queued 只表示当前 job 尚未开始。")
3. **独立核验与治理。** 复核器必须逐条覆盖候选；随后 MemoryService 再校验证据片段、精确文字范围和来源版本。证据无效或与候选相悖会拒绝，噪声会忽略，含糊时间等软性不确定会暂缓，未经验证的他人承诺只保留为来源；清楚、受支持且影响有限的事实才会自动应用。跨来源冲突影响现行重要记忆，或整批影响超过自动处理预算时，才会进入“等待判断”。参考 [核验覆盖与摘要校验 ↗](../../../apps/server/src/learning/pipeline.ts#L604 "支持 verifier 必须逐条覆盖候选并匹配候选摘要。") [固定证据与来源版本校验 ↗](../../../apps/server/src/memory/service.ts#L252 "说明 MemoryService 检查证据范围、来源版本和当前读取状态。") [确定性应用政策 ↗](../../../apps/server/src/memory/service.ts#L755 "支持拒绝、忽略、暂缓、保留来源、等待判断和自动应用的条件区别。")
4. **应用并留下历史。** 真正应用会创建新的 memory revision，更新同一 memory 的 head、版本和状态，并把所依赖的来源版本与 epoch 记录为 current；更新不是覆盖旧修订。版本已经变化时会拒绝过期写入。参考 [记忆按修订原子应用 ↗](../../../apps/server/src/storage/repository.ts#L402 "说明更新创建新 revision、推进版本并保存当前来源依赖，且拒绝陈旧版本。")

所以，**原文已保存、提取任务完成、候选已核验、记忆已生效是四种不同完成度**。queued 只表示当前这一个 job 尚未开始：若排队的是最初的 extract_claims，提取模型尚未调用；若排队的是 verify_proposals，则提取模型已经完成，等待的是独立核验。某个 job 的 succeeded 也只表示该步骤结束；候选的 applied 才表示实际写入。材料处理页把这些 job 与候选状态分别展示。参考 [提取完成后排队独立核验 ↗](../../../apps/server/src/learning/pipeline.ts#L550 "说明提取器先运行模型并保存输出，再为待处理候选创建 queued 的 verify_proposals 任务，因此 queued 只表示当前 job 尚未开始。") [材料处理页区分任务和候选状态 ↗](../../../apps/web/src/LearningView.vue#L30 "支持界面分别展示 queued、succeeded、applied 等任务或候选状态；不把 queued 泛化为整条链尚未调用模型。")

<a id="source-refresh"></a>
## 来源换版后，先失效，再用新证据修复

同一来源出现新版时，系统先把依赖旧版本的关系标为 stale，并立即把对应记忆标为 invalidated；同时冻结本次受影响的记忆集合，创建 refresh 记录并排入后续处理。旧原文和旧记忆修订仍保留，因此可以解释“以前为什么记成三次”。参考 [来源换版立即失效旧依赖 ↗](../../../apps/server/src/store.ts#L249 "说明新版保存后旧依赖标 stale、记忆标 invalidated，并创建刷新任务。") [冻结刷新影响集合 ↗](../../../apps/server/src/learning/refresh.ts#L6 "说明 refresh record 保存受影响记忆集合，避免重复处理缩小范围。")

refresh_dependents 成功的含义只是：系统确认了影响并把新版送去重新提取。它不会直接宣布旧结论已经修好。只有新提取经过独立核验和 MemoryService 应用，而且同一记忆已经恢复 active、当前依赖确实指向新版，refresh 才会成为 applied；仍有未修复项时是 needs_review，来源又产生更新时是 superseded，没有受影响记忆时是 no_effect。参考 [刷新任务只负责重新排队 ↗](../../../apps/server/src/learning/pipeline.ts#L126 "支持 refresh_dependents 对新版重新安排 extract_claims，并在来源再次前进时标记 superseded。") [按真实应用结果核对刷新 ↗](../../../apps/server/src/learning/refresh.ts#L27 "说明调度成功不等于修复，只有 active 记忆依赖当前新版时才计为 repaired 和 applied。")

回到示例：现行测试把“retry limit is 3”换成“retry limit is 5”。换版瞬间，原记忆先变成 invalidated；流程排空后仍是同一个 memory id，版本加一、正文包含 5、状态恢复 active，refresh 才成为 applied，旧版的 3 仍可回读。另一个反例中，新材料不再支持旧事实：刷新调度 job 虽然 succeeded，记忆仍 invalidated，refresh 仍 needs_review。参考 [三次改五次的同一记忆测试 ↗](../../../apps/server/tests/learning-refresh.test.ts#L253 "验证旧记忆先失效，随后同一 ID 升级版本、依赖新版并保留旧原文。") [调度成功但仍需核对的反例 ↗](../../../apps/server/tests/learning-refresh.test.ts#L220 "验证新证据不支持修复时 refresh job 可 succeeded，但 refresh 仍 needs_review。")

这给出一个实用判断：**看到后台任务完成，不等于看到结论完成。** 要确认规则真的更新，应同时看当前记忆是否 active、版本是否推进、依赖是否指向新原文，以及 refresh 是否 applied。依赖已经 stale 的历史记忆也不能被直接恢复成 active。参考 [不能恢复带陈旧依赖的记忆 ↗](../../../apps/server/src/memory/service.ts#L1822 "支持历史记忆依赖 stale 时拒绝恢复为当前 active 版本。")

<a id="memory-vs-wiki"></a>
## 记忆重核验与 Wiki 重新整理是两条流程

两条流程共享固定 Source / Revision，但回答不同问题：

| 对象 | 要回答的问题 | 来源变化后的动作 | 真正完成的标志 |
| --- | --- | --- | --- |
| 记忆 | “当前事实还能不能直接记住？” | 旧依赖立即失效，并可排队重新提取、核验、应用 | 记忆恢复 active，依赖新版，refresh 为 applied |
| Wiki 文章 | “给这个读者的整段解释还成立吗？” | 按章节检查正文引用和背景前提，保留未受影响内容 | 显式重新整理、写作和独立复核后发布新版 |

Wiki 的固定引用不会悄悄跳到新原文。系统比较引用所在的完整 Markdown 章节或代码符号：内容没变但行号移动，可以继续 current；相关上下文或 review source 变化则 needs-review；固定材料或被引用文章不可读则 unavailable。引用的下层文章发生变化，也会把影响传到上层章节。参考 [固定引用按上下文判断变化 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "说明引用保持指向原版本，只比较完整章节或符号是否仍适用。") [Wiki 章节适用状态 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "支持 current、needs-review、unavailable 及上层文章受下层变化影响的规则。")

**needs-review 不是删除旧文。** 页面仍保留原来的解释，只标明受影响章节；整篇只有在所有章节都 current 时才算 current。重新整理则是显式流程：保存阅读目标，把页面置为 writing，完成调查、写作和独立复核后才 published；失败置为 failed。发布前若阅读目标或材料版本已经变化，旧结果会被拒绝，原有有效正文保留。参考 [Wiki 显式写作流程 ↗](../../../apps/server/src/knowledge/pipeline.ts#L251 "说明页面进入 writing，成功后 published，失败则 failed，并需要调查、写作和复核。") [发布前重验输入并保留旧文 ↗](../../../apps/server/src/knowledge/repository.ts#L206 "说明计划或材料版本变化会阻止旧结果发布，成功时才推进知识 head。")

一句话记忆：**重核验维护短事实的当前有效性；重新整理维护面向读者的解释。** 当前实现不会因为原件换版就自动重写 Wiki。

<a id="task-time-and-notification"></a>
## 等待、检查时间、截止时间和已读各管一件事

事项只有 open、waiting、done、cancelled 四种状态。waiting 表示行动受制于某个人或某个结果，并不表示完成，也不等于“已经设了提醒”。follow_up 中的字段需要分开读：参考 [事项状态与跟进字段合同 ↗](../../../packages/contracts/src/task-flow.ts#L3 "定义 open、waiting、done、cancelled，以及 waiting_on、next_check_at、snoozed_until 等字段。")

- **waiting_on**：正在等谁或什么结果。
- **next_check_at**：下一次由我检查进展的时间。
- **snoozed_until**：当前提醒暂缓到什么时候。
- **time_expression / timezone**：保存用户原话中的时间表达及其时区。
- **due_at**：事项本身最晚何时完成，不属于 follow_up。

等待对象和跟进时间必须来自当前明确指令，不能由模型猜。对示例“明早提醒我检查评审回复”，合理落库方式是 waiting_on=评审回复、next_check_at=明早解析出的时刻，而 due_at 仍为空；只有用户说“评审必须明早完成”时，明早才是截止时间。参考 [等待对象和时间必须来自当前指令 ↗](../../../apps/server/src/tasks/follow-up.ts#L5 "支持 follow-up 内容不能推断，必须保留用户当前原话与时区化时间。") [跟进时间与截止时间分离 ↗](../../../apps/server/src/assistant/message-workflows.ts#L3 "明确 waiting/check-in 使用 follow_up，实际 deadline 使用 due_at，未知时间保持为空。")

snooze 是把提醒推到 snoozed_until，并同步新的检查时间，同时保留原 waiting_on；它不改截止日期。complete、cancel 和 reopen 会清空 follow_up；已完成或已取消的事项要先 reopen，才能再等待、暂缓或改期。参考 [事项动作如何更新状态与时间 ↗](../../../apps/server/src/memory/service.ts#L102 "支持 snooze 保留等待对象且不改截止日，完成、取消、重开清除 follow-up。")

提醒器只扫描 open / waiting 事项。到 due_at 或 next_check_at 时生成站内通知，并按事项版本、触发种类和发生时刻保存回执，所以服务重启后可以补发一次，而重复轮询不会反复发送；done / cancelled 不再提醒。提醒正文也明确说明系统不会自动联系他人。参考 [持久且去重的站内提醒 ↗](../../../apps/server/src/tasks/follow-up.ts#L17 "说明仅扫描 open/waiting、按截止或检查时间触发、用回执去重且不自动联系他人。")

最后，**通知已读只表示“我看过这条通知”**。实现只写 notification.read_at；界面明确说明它不会批准变更、完成待办或取消后续提醒。参考 [已读只更新通知 ↗](../../../apps/server/src/store.ts#L633 "实现上标记已读只写 notification.read_at。") [通知中心解释已读边界 ↗](../../../apps/web/src/App.vue#L1067 "界面明确已读不批准变更、不完成事项，也不取消后续提醒。")

<a id="check-progress-and-limits"></a>
## 怎样判断哪些已完成，哪些仍待处理

可以按对象使用两把状态尺。

**材料与记忆**

- **queued**：当前 job 尚未开始。初始 extract_claims 排队表示提取尚未运行；后续 verify_proposals 排队则意味着提取已经完成，核验尚未运行。参考 [提取完成后排队独立核验 ↗](../../../apps/server/src/learning/pipeline.ts#L550 "说明提取器先运行模型并保存输出，再为待处理候选创建 queued 的 verify_proposals 任务，因此 queued 只表示当前 job 尚未开始。")
- **succeeded**：当前 job 已结束；若它只是提取或刷新调度，后面仍可能有核验与应用。
- **applied**：候选已经实际写入；对来源刷新，还要求所有受影响记忆都已由新版证据修复。
- **invalidated / needs_review**：旧结论不能再作为当前有效记忆，仍需新证据或人工处理。
- **awaiting_decision**：存在真正需要用户授权或取舍的高影响变化。
- **retry_wait / failed**：处理未完成，可查看错误并重试。
- **superseded**：这次刷新已被更晚的来源版本取代。

**Wiki 与事项**

- Wiki 看章节的 current / needs-review / unavailable；planned、writing、failed、published 是生成过程，不替代章节适用性判断。
- 事项看 status、waiting_on、next_check_at、snoozed_until 和 due_at；通知中心的 read 只表示提醒已读。

当前系统已经能主动保存原件和版本、给原始材料排学习任务、失效依赖旧版的记忆，并在**当前实例的自动处理确实启用、后台已运行且 Agent 配置可用**时继续提取、独立核验和应用清楚的低影响事实。不要把配置 schema 的字段缺省值误读成仓库实际启动默认值：若某份配置省略 learning，字段会回退到 enabled=false；但没有 `OMEM_CONFIG` 或 `omem.local.json` 时，启动会加载 `config/omem.example.json`，而当前示例配置明确设置 enabled=true。应用只有在启用且能找到对应 profile 时才创建 LearningPipeline。参考 [学习配置字段的缺省值 ↗](../../../apps/server/src/config.ts#L65 "说明配置对象省略 learning 或 enabled 字段时，schema 回退到 enabled=false；这不是仓库无本地配置时的最终启动值。") [配置文件的实际加载顺序 ↗](../../../apps/server/src/config.ts#L130 "说明启动优先读取 OMEM_CONFIG 或 omem.local.json；文件不存在时改读 config/omem.example.json。") [仓库示例配置启用学习 ↗](../../../config/omem.example.json#L67 "说明当前仓库示例配置明确设置 learning.enabled=true。") [按实际配置创建学习管线 ↗](../../../apps/server/src/app.ts#L121 "说明应用仅在 learning 已启用且找到对应 profile 时构造 LearningPipeline，缺 profile 会报错。")

最可靠的判断入口是“材料处理”页：**后台处理服务已启动**表示当前正在运行；**自动处理已启用，当前后台未运行**表示配置允许但此刻没有运行；**自动处理未启用**表示任务仍可排队、原文仍可保存和检索，但不会继续调用学习模型。参考 [材料处理页显示当前运行状态 ↗](../../../apps/web/src/LearningView.vue#L81 "说明界面区分自动处理未启用、已启用但后台未运行、后台已启动，并在未启用时解释原文仍可保存检索。")

仍需要用户或显式动作的部分包括：含糊时间的澄清、高影响冲突的决定、选择材料与阅读目标后重新整理 Wiki，以及由用户报告“对方已经回复”。当前没有自动联系对方、监听外部回复、周期回顾或日历；外部通知也需要独立集成。当前 SQLite / shared-token 运行方式是单用户实现。参考 [当前主动能力与外部边界 ↗](../../../docs/reader-first/operations.md#L33 "说明日常事项与站内提醒已支持，但没有自动监听回复、周期回顾或日历，且当前是单用户服务。")

若要修改实现，可从四个入口开始：原文保存与失效在 apps/server/src/store.ts；学习编排与重核验在 apps/server/src/learning/pipeline.ts、learning/refresh.ts；记忆和事项治理在 apps/server/src/memory/service.ts；跟进时间和提醒在 apps/server/src/assistant/message-workflows.ts、tasks/follow-up.ts。Wiki 的独立生命周期位于 apps/server/src/knowledge/pipeline.ts、knowledge/lifecycle.ts 和 knowledge/repository.ts。
