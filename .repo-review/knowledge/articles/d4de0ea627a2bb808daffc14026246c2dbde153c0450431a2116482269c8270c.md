# 规则变了以后：原文、记忆与待办如何更新

用“重试三次改为五次”和“明早跟进评审”两个例子，解释原件换版、记忆失效与重核验、Wiki 更新，以及等待、截止、提醒和已读状态之间的区别。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="two-paths"></a>
## 先分清两条互不授权的链

假设项目约定原来是“失败后重试三次”，现在同一份约定改成“五次”；与此同时，你另发一条消息：“帮我明早跟进评审回复。”前者是**事实来源换版**，后者才是**本人明确交办**。约定正文即使出现“评审”或“跟进”，也只是材料，不能替你创建事项；讨论、转述和他人承诺同样只能作为背景。参考 [消息与交办边界 ↗](../../../apps/server/src/assistant/message-workflows.ts#L2 "支持本人明确交办、讨论转述、等待跟进之间的权限区分，以及未知时间不得猜测。")

助手还会检查当前消息是否确有交办意图。即使模型提出创建事项，咨询问题也会被拒绝；只有持久化回执存在后，界面才会说“已创建”或“已更新”。因此，两条链可以同时进行，却不会互相授予行动权限。参考 [事项意图与持久化回执 ↗](../../../apps/server/src/assistant/runtime.ts#L729 "支持咨询问题不能创建事项，且成功文案只能依据实际持久化后的事项状态。")

<a id="material-to-memory"></a>
## 原始记录怎样成为可用记忆

保存先按“来源类型 + 来源标识”找到 Source：内容没变可复用当前版本，内容变化则追加不可变 Revision，旧版仍能回看。保存成功只证明原文已经落库。参考 [来源与不可变版本 ↗](../../../apps/server/src/store.ts#L171 "支持按来源身份查找 Source、内容变化时追加 Revision、相同内容复用当前版本。")

随后，非派生原件进入“提取候选”队列；提取器有候选时再排入独立核验，核验结果交给 MemoryService 决定应用、拒绝、暂缓或保留为来源。派生总结不会再次作为独立原件进入学习，避免系统用自己的总结证明自己。参考 [原件进入学习队列 ↗](../../../apps/server/src/store.ts#L351 "支持非派生原件排入候选提取，派生内容不作为独立证据再次进入学习。") [候选提取与核验入队 ↗](../../../apps/server/src/learning/pipeline.ts#L550 "支持提取器产生候选后再排入独立核验，没有候选时直接进行刷新对账。") [独立核验与批量决策 ↗](../../../apps/server/src/learning/pipeline.ts#L604 "支持核验覆盖候选、匹配摘要，并将整批结果交由 MemoryService 评估与应用。")

真正的“已记住”发生在应用事务里：它创建或更新记忆修订，同时写入变更、通知和 application receipt；更新还要求预期版本匹配，避免覆盖并发变化。参考 [应用事务回执 ↗](../../../apps/server/src/storage/repository.ts#L219 "支持实体变更、通知、交付意图和 application receipt 在同一提交事务中落库。") [记忆版本更新 ↗](../../../apps/server/src/storage/repository.ts#L402 "支持 active 默认状态、预期版本校验、不可变记忆修订和同一记忆 head 推进。")

所以判断进度时要分层：

| 看到的状态 | 能说明什么 |
| --- | --- |
| 原文已保存 | Revision 可阅读、可检索 |
| job 为 queued / succeeded | 某个后台步骤尚待处理 / 已结束 |
| proposal 为 applied，memory 为 active | 候选已实际成为现行记忆 |
| 有 application receipt | 应用事务已经提交 |

材料处理页也明确区分“处理完成”和“已应用”；后台学习未启用时，原文仍可用，但排队任务不会自行变成记忆。参考 [材料处理状态说明 ↗](../../../apps/web/src/LearningView.vue#L16 "支持 queued、succeeded、applied 等状态的用户含义，以及未启用处理时原文仍可使用。")

<a id="refresh"></a>
## “三次”改成“五次”后发生什么

同一 Source 写入“五次”的新 Revision 后，系统立即把仍依赖旧 Revision 的依赖标为 stale，把对应记忆标为 invalidated，并排入刷新任务。这里是**先撤下旧结论，再重新证明新结论**：处理中不会继续把“三次”冒充现行事实，旧 Revision 也不会被删除。参考 [换版后立即失效 ↗](../../../apps/server/src/store.ts#L234 "支持新 Revision 成为 head 后将旧依赖标为 stale、记忆标为 invalidated 并排入刷新。")

刷新会冻结本次受影响的记忆集合，再以新原件重新提取、核验。若新原件支持变化后的结论，更新同一个 memory；若不再支持，旧记忆保持 invalidated，而不是复制一条猜测的新记忆。更新同一记忆必须携带当前版本，成功后形成新的不可变修订。参考 [刷新完成判据 ↗](../../../apps/server/src/learning/refresh.ts#L6 "支持冻结受影响记忆集合，并按 active/current 实际依赖区分 no_effect、applied、needs_review 与 superseded。") [同一记忆重核验 ↗](../../../apps/server/src/learning/pipeline.ts#L181 "支持刷新携带失效记忆的身份、版本与作用域，供当前原件重核验。") [记忆版本更新 ↗](../../../apps/server/src/storage/repository.ts#L402 "支持 active 默认状态、预期版本校验、不可变记忆修订和同一记忆 head 推进。")

刷新状态应这样读：

- **no_effect**：没有现有记忆受影响。
- **queued**：已安排后续提取，尚未修复。
- **needs_review**：仍有冻结的记忆没有恢复为 active/current。
- **applied**：冻结集合全部在这次新 Revision 上恢复为现行记忆。
- **superseded**：处理期间来源又产生了更新版本。

调度任务成功只代表“已经排队”；最终状态按数据库中的实际应用与依赖对账，不以模型是否返回或 job 是否结束代替。参考 [刷新完成判据 ↗](../../../apps/server/src/learning/refresh.ts#L6 "支持冻结受影响记忆集合，并按 active/current 实际依赖区分 no_effect、applied、needs_review 与 superseded。")

<a id="wiki"></a>
## 记忆重核验不等于 Wiki 已更新

记忆刷新回答的是“助手现在应把哪条事实用于召回”；Wiki 更新回答的是“给读者的整篇解释是否已经基于当前材料重新调查、撰写并复核”。两者共享原件，但不是同一条队列。

材料依赖变化后，知识仓库会把受影响文章及其上层文章标为非 current；这只撤销“当前页”资格，不会自动改正文。参考 [文章依赖失效传播 ↗](../../../apps/server/src/knowledge/repository.ts#L178 "支持材料或文章依赖变化后将受影响知识页标为非 current，并沿文章依赖传播。") 要得到新文章，需要显式选择固定材料和阅读目标，经过调查、写作与独立复核；只有通过复核的文档才发布。API 返回 202 / running 只表示运行已经启动，之后才会变成 published 或 failed。参考 [调查写作与独立复核 ↗](../../../apps/server/src/knowledge/pipeline.ts#L157 "支持读者页经写作、独立复核，并且只发布被接受的文档。") [Wiki 运行状态 ↗](../../../apps/server/src/knowledge/api.ts#L165 "支持页面生成请求的 running、published、failed 状态，以及 202 仅代表已启动。")

因此“五次”已经成为 active memory 时，相关 Wiki 仍可能是非 current；反过来，文章发布也不代表个人记忆已应用。启动服务本身不会自动重做整库 Wiki。参考 [启动与知识生成边界 ↗](../../../README.md#L15 "支持启动不会自动生成整库 Wiki，而已启用的后台材料任务可以继续处理。")

<a id="task-time"></a>
## 明早跟进：等待、检查、截止和已读

在本例中，明确交办可形成一个 **waiting** 事项：

| 字段或动作 | 含义 |
| --- | --- |
| waiting_on | 正在等谁或什么结果，必须来自当前指令 |
| next_check_at | 明早回来检查进展的时间 |
| due_at | 事情真正必须完成的截止时间 |
| snoozed_until | 在此之前不再提醒 |
| status=waiting | 事项仍活跃，只是正在等待 |
| 通知已读 | 只记录你看过提醒，不会完成事项 |

waiting_on 和时间原话必须能在当前本人指令中找到，不能由材料或模型补猜。参考 [跟进信息必须来自本人指令 ↗](../../../apps/server/src/tasks/follow-up.ts#L5 "支持等待对象和时间原话须来自当前指令；短输入不能从上下文补猜 waiting_on。") 事项状态只有 open、waiting、done、cancelled；跟进字段与业务状态是分开的。参考 [事项状态与跟进字段 ↗](../../../packages/contracts/src/task-flow.ts#L3 "支持事项四种业务状态、跟进字段和可执行动作的正式合同。")

如果你说“帮我明早 9 点跟进评审回复”，示例结果应是：waiting_on=评审回复、next_check_at=明早 9 点、due_at=null。这里的等待对象和时间都来自这条当前指令；若只说“明早 9 点提醒我检查”而没有说明等待谁或什么结果，系统不能补猜 waiting_on，也不能直接完成要求 waiting_on 的 wait 动作。只有另说“周五前必须完成”，才设置截止时间。稍后提醒会移动检查/暂缓时间，改期才改变截止时间；完成或取消会清除跟进，终态事项要先重新打开才能再次等待或改期。参考 [跟进信息必须来自本人指令 ↗](../../../apps/server/src/tasks/follow-up.ts#L5 "支持等待对象和时间原话须来自当前指令；短输入不能从上下文补猜 waiting_on。") [等待改期与暂缓语义 ↗](../../../apps/server/src/memory/service.ts#L102 "支持 wait 必须有等待对象，并说明完成、取消、重开、等待、暂缓和改期分别如何改变状态、跟进字段与截止时间。")

到检查时间或截止时间，服务会生成站内通知并按事项版本与触发时刻去重；提醒文字明确表示“尚未确认收到回复”，也不会自动联系他人。参考 [站内提醒与防重 ↗](../../../apps/server/src/tasks/follow-up.ts#L17 "支持截止和跟进提醒、按事项版本与触发时刻防重，以及不会自动联系他人。") 点击已读只更新通知的 read_at，不修改事项。参考 [通知已读只改阅读时间 ↗](../../../apps/server/src/store.ts#L633 "支持已读操作只更新 notifications.read_at，不改变事项状态或跟进信息。")

<a id="boundaries"></a>
## 现在能主动做什么，下一步由谁完成

当前系统可以保存原件与历史版本；在后台学习启用时提取、独立核验并有限自动应用记忆；来源换版后先失效旧记忆再排队重核验。它也能依据本人明确指令创建或更新事项，运行中定时检查截止与跟进时间，并让你完成、取消、改期、暂缓或重开。参考 [当前个人流程 ↗](../../../docs/reader-first/progress.md#L23 "支持当前已有的记忆换版重核验、事项交办、等待、改期、完成、取消与站内提醒。")

它目前**不会**监听评审者的外部回复，也不会自动判断“已经收到”；通知已读也不代表事项完成。你仍需报告回复、明确完成或取消。Wiki 依赖变化会失去 current 状态，但重新调查和发布仍要显式触发。持续项目理解、周期回顾、日历和学习卡等也仍是后续能力；当前 SQLite/shared-token 边界是单用户。参考 [当前能力缺口 ↗](../../../docs/reader-first/progress.md#L41 "支持没有外部回复监听、周期回顾等能力，以及当前单用户边界。")

回到贯穿示例，最可靠的读法是：看到“五次”的新原文，只能说**材料已更新**；refresh=applied 且记忆 active，才能说**助手的现行记忆已更新**；Wiki 还要单独看到 published/current。看到“明早跟进”的持久化回执，可以说**事项已创建**；明早通知已读以后，它仍然 waiting，直到你明确结束它。
