# 规则变了以后：原文、记忆与待办如何更新

用“重试三次改为五次”和“明早跟进评审”两个彼此独立的教学输入，解释原文保存、候选提取与记忆应用、来源换版后的失效和重核验、Wiki 文章维护，以及等待、检查时间、截止时间、暂缓和通知已读的差别，并给出判断各流程是否真正完成的状态尺。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="separate-fact-and-action"></a>
## 先分清：规则变化不是新的交办

先看结论：**“规则从重试三次改为五次”更新的是事实；“明早帮我跟进评审”创建的是行动。** 两条信息可以有关联，但不能互相代替授权。

以下是贯穿全文的教学示例：

- 材料 A 原来写“评审失败后重试三次”，后来同一来源改成“重试五次”。系统应保存新版，并暂停使用依赖旧版的记忆；只有新版经过提取、核验和应用，当前记忆才真正变成“五次”。
- 材料 B 是当前用户另发的一条消息：“帮我跟进评审回复，明早提醒我检查。”这才是明确交办，可以形成事项。
- 不能因为材料 A 出现“评审”“重试”或“提醒”等词，就推断用户要求创建待办。助手先用确定性规则识别明确交办，咨询语气会阻止建任务；即使模型提出了 create_task，也不会因此直接落库。参考 [明确交办意图门槛 ↗](../../../apps/server/src/assistant/runtime.ts#L222 "说明咨询问题优先阻止 create_task，只有当前用户原话满足明确交办模式才进入建任务流程。") [讨论不会变成个人事项 ↗](../../../apps/server/tests/task-follow-up.test.ts#L83 "验证他人的承诺与普通讨论即使让模型提出 create_task，也不会创建当前用户的任务。")

因此，读系统状态时要分别问四件事：**原话是否保存、当前事实是否已应用、解释文章是否仍适用、行动是否已创建或推进。**

<a id="capture-to-memory"></a>
## 一条原始记录怎样成为可用记忆

材料进入系统后，不会直接变成“系统认定的事实”。完整链路有四层：

1. **保存原文。** 系统按来源身份查找已有记录。相同生产者与 event ID 的重复事件复用捕获回执；同一来源当前内容的指纹相同，也复用既有版本。内容变化时才创建新的不可变 revision，推进来源 head 和 validity epoch。原始材料会排入学习队列，模型派生材料不会再次自我学习。参考 [捕获去重与不可变换版 ↗](../../../apps/server/src/store.ts#L150 "支持按事件回执和内容指纹去重，以及新内容创建 revision、推进 head 与 validity epoch。") [原始材料进入提取队列 ↗](../../../apps/server/src/store.ts#L357 "说明原始材料排 extract_claims，而派生材料被阻止再次自我学习。")
2. **提取候选。** 后台提取器从任务固定的版本中产生观察、候选或放弃理由。模型运行前会核对来源 head、sourceId 和 validityEpoch；来源已经前进时，旧任务以 STALE_JOB_INPUT 停止，不能把旧内容写回当前状态。提取器保存输出后，只有仍待处理的候选才会排入 verify_proposals。参考 [学习任务拒绝过期输入 ↗](../../../apps/server/src/learning/pipeline.ts#L290 "说明模型运行前核对来源 head、sourceId 与 validityEpoch，不一致时抛出 STALE_JOB_INPUT。") [提取后才排独立核验 ↗](../../../apps/server/src/learning/pipeline.ts#L550 "说明提取器保存输出并过滤已处理事项候选，只有剩余候选才排 verify_proposals；无候选时直接核对刷新。")
3. **独立核验与治理。** 复核器先验证父任务、输出摘要和候选覆盖，再把整批候选交给 MemoryService。MemoryService 还会检查固定片段、来源 revision、精确文字或图片资产，以及读取时的 head 与 epoch 是否仍然有效。参考 [核验覆盖与整批治理 ↗](../../../apps/server/src/learning/pipeline.ts#L604 "说明 verifier 校验父任务、输出摘要、候选覆盖和 digest，再将整批候选交给 MemoryService。") [固定证据与来源读取校验 ↗](../../../apps/server/src/memory/service.ts#L252 "说明 MemoryService 检查片段、来源 revision、精确引用或资产，并核对读取时的 head 与 epoch。") 证据无效或与候选相悖会拒绝，噪声会忽略，证据不足、范围或时间不确定会暂缓，未经验证的他人事项只保留为来源；清楚、受支持且影响有限的结果才会自动应用。只有影响超出自动预算，或跨来源冲突确实触及现行重要知识或阻塞当前工作时，才进入“等待判断”。参考 [确定性记忆治理政策 ↗](../../../apps/server/src/memory/service.ts#L755 "支持 reject、ignore、defer、retain、awaiting_decision 与 auto_apply 的条件区别。")
4. **应用并留下历史。** 真正应用会创建新的 memory revision，以 expectedVersion 防止陈旧写入，推进同一 memory 的 head、version 和 status，并把所依赖的来源版本记录为 current；旧修订不会被覆盖。参考 [记忆按修订原子应用 ↗](../../../apps/server/src/storage/repository.ts#L402 "说明应用以 expectedVersion 防陈旧写入，创建新 revision、推进 head/version，并记录 current 来源依赖。")

所以，**原文已保存、提取任务完成、候选已核验、记忆已生效是四种不同完成度**。queued 只描述当前 job：extract_claims 排队表示提取尚未运行，verify_proposals 排队则表示提取已经完成、独立核验尚未运行。某个 job 的 succeeded 也只说明该步骤结束；候选的 applied 才说明实际写入。材料处理页把这些 job 与候选状态分别展示。参考 [提取后才排独立核验 ↗](../../../apps/server/src/learning/pipeline.ts#L550 "说明提取器保存输出并过滤已处理事项候选，只有剩余候选才排 verify_proposals；无候选时直接核对刷新。") [任务与候选状态分开展示 ↗](../../../apps/web/src/LearningView.vue#L25 "支持 queued、succeeded、applied、stale 等状态分别描述处理任务或候选结果。")

<a id="source-refresh"></a>
## 来源换版后，先失效，再用新证据修复

同一来源出现新版时，系统先把旧 memory dependency 标为 stale，并立即把依赖它的记忆标为 invalidated；同时冻结本次受影响的 memory ID 集合，建立 refresh record 并排入后续处理。旧原文和旧记忆修订仍保留，因此仍能解释“以前为什么记成三次”。参考 [来源换版立即失效旧依赖 ↗](../../../apps/server/src/store.ts#L255 "说明新版保存后旧依赖标 stale、相关记忆标 invalidated，并建立刷新记录和任务。") [冻结刷新影响集合 ↗](../../../apps/server/src/learning/refresh.ts#L6 "说明 refresh record 固定受影响 memory ID，避免重复投递因部分修复而缩小范围。")

refresh_dependents 成功只表示系统确认了影响，并让新版进入提取流程。它使用与捕获阶段相同身份的 extraction job，因此不会为同一新版启动第二个独立提取器；若来源再次前进，本次刷新会成为 superseded。参考 [刷新复用新版提取任务 ↗](../../../apps/server/src/learning/pipeline.ts#L126 "说明 refresh_dependents 核对来源仍为当前 head，并使用与捕获相同身份的 extraction job；来源前进时转为 superseded。") 真正的完成判断发生在 reconciliation：每条受影响记忆都必须恢复 active，其当前 head 依赖必须为 current、指向新版，而且来源 head 仍是该版；全部满足才是 applied，否则仍为 needs_review。参考 [按真实依赖核对刷新完成 ↗](../../../apps/server/src/learning/refresh.ts#L27 "说明只有每条记忆 active、当前依赖指向新版且来源 head 未变时，refresh 才是 applied。")

回到教学示例：现行测试把“retry limit is 3”换成“retry limit is 5”。换版瞬间，原记忆先变成 invalidated；处理完成后仍是同一个 memory ID，version 加一、正文包含 5、状态恢复 active，refresh 才成为 applied，旧版的 3 仍可回读。参考 [三次改五次的同一记忆测试 ↗](../../../apps/server/tests/learning-refresh.test.ts#L253 "验证旧记忆先失效，之后同一 memory ID 升级版本、依赖新版并保留旧原文。") 另一个反例中，新材料不再支持旧事实：refresh_dependents job 可以 succeeded，但记忆仍 invalidated，refresh 仍是 needs_review。参考 [调度成功但刷新未完成 ↗](../../../apps/server/tests/learning-refresh.test.ts#L220 "验证模型放弃时 refresh_dependents job 可 succeeded，而记忆仍 invalidated、refresh 仍 needs_review。")

因此，**看到后台任务完成，不等于看到结论完成。** 要确认规则真的更新，应同时看当前记忆是否 active、版本是否推进、依赖是否指向新原文，以及 refresh 是否 applied。带 stale dependency 的历史记忆也不能被直接恢复成 active。参考 [陈旧依赖不能直接恢复 ↗](../../../apps/server/src/memory/service.ts#L1822 "说明历史 memory revision 只要包含 stale dependency，就不能恢复为当前 active 版本。")

<a id="memory-vs-wiki"></a>
## 记忆重核验与 Wiki 文章维护是两条流程

两条流程共享固定的 Source / Revision，但回答不同问题：

| 对象 | 要回答的问题 | 来源变化后的动作 | 真正完成的标志 |
| --- | --- | --- | --- |
| 记忆 | “当前事实还能不能直接使用？” | 旧依赖立即失效，再提取、核验、应用 | 记忆恢复 active，依赖新版，refresh 为 applied |
| Wiki 文章 | “给这个读者的整段解释还成立吗？” | 按章节检查正文引用和背景前提，再维护或重组 | 新稿经独立复核并成功发布 |

Wiki 的固定引用不会悄悄跳到新原文。系统比较引用所在的完整 Markdown 章节或代码符号：内容不变但行号移动，可以继续 current；相关上下文或 review source 变化则 needs-review；固定材料或被引用文章不可读则 unavailable。下层文章的变化也会传到引用它的上层章节。参考 [固定引用按完整上下文判断 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L40 "说明引用保持绑定原 revision，只比较完整章节或符号是否仍适用，允许纯行号移动。") [Wiki 章节适用状态 ↗](../../../apps/server/src/knowledge/lifecycle.ts#L81 "支持 current、needs-review、unavailable，以及下层文章变化传播到上层章节的规则。")

**needs-review 不是删除旧文。** 维护已有文章时，调查者先判断旧稿是否仍有清楚的阅读路线，再显式选择两条路径：局部变化用 maintain，把旧稿交给 knowledge-refresher 保留有效案例和解释；旧结构妨碍阅读目标时用 rewrite，移除旧稿结构后由 knowledge-writer 根据当前原件重新组织。两条路径之后都要经过独立 verifier。参考 [文章维护与重组分流 ↗](../../../apps/server/src/knowledge/pipeline.ts#L165 "说明 composition.mode=rewrite 时移除旧稿结构并使用 writer，maintain 时沿用 refresher；两条路径都经过独立 verifier。")

页面整理仍是显式的发布流程：先保存阅读计划并进入 writing，调查、写作和复核成功后才 published，失败则 failed。发布前还会重新校验阅读计划、动态选材快照和所有依赖版本；任何一项在整理期间变化都会拒绝旧结果，保留已发布正文。参考 [Wiki 调查写作发布流程 ↗](../../../apps/server/src/knowledge/pipeline.ts#L272 "说明 writePage 保存计划并维护 writing/published/failed 状态，当前原件经研究后再进入写作与复核。") [发布前重验输入并保留旧文 ↗](../../../apps/server/src/knowledge/repository.ts#L215 "说明计划、动态选材或依赖版本变化会阻止旧结果发布，成功后才推进文章 head。")

文章可以选择开启“随所选材料自动更新”，但默认关闭，而且只跟踪明确选择的材料或项目/主题范围。开启后，原件换版只是把同一篇文章放入持久维护队列；真正的调查、写作、复核和发布条件没有被跳过，失败时旧版继续可读。参考 [可选的文章自动维护 ↗](../../../docs/reader-first/publication-lifecycle.md#L41 "说明自动维护默认关闭、只跟踪明确选材，使用持久队列且仍执行调查写作复核；失败保留旧文。")

一句话记忆：**重核验维护短事实的当前有效性；文章维护维护面向读者的完整解释。** 它们可以由同一次来源换版触发，但不会互相代替。

<a id="task-time-and-notification"></a>
## 等待、检查时间、截止时间和已读各管一件事

事项只有 open、waiting、done、cancelled 四种状态。follow_up 与截止时间需要分开读：参考 [事项状态与跟进字段合同 ↗](../../../packages/contracts/src/task-flow.ts#L3 "定义四种事项状态、follow_up 字段和独立的 dueAt/dueExpression。")

- **waiting_on**：正在等谁或什么结果，可以为空。
- **next_check_at**：下一次由我检查或提醒的时间。
- **snoozed_until**：当前提醒暂缓到什么时候。
- **time_expression / timezone**：用户原话里的时间表达及其时区。
- **due_at / due_expression**：事项本身最晚何时完成，不属于 follow_up。

这里有两种不同的提醒：

- “明早提醒我检查评审回复”可以写成 waiting_on=评审回复、next_check_at=明早解析出的时刻，而 due_at 为空。
- “2026 年 10 月 7 日 15 点提醒我找负责人确认验收结果”不表示正在等某个人，可以写 waiting_on=null、next_check_at=对应时刻、snoozed_until=null，due_at 仍为空。只有用户另行明确“验收必须在该时刻完成”，该时刻才是截止时间。当前合同明确允许没有等待对象的新提醒，运行测试也验证它只产生“事项待跟进”，不显示“截止时间”，重复扫描不会重发。参考 [提醒与截止时间分离 ↗](../../../packages/contracts/src/assistant.ts#L4 "明确提醒时间属于 follow_up.next_check_at，无等待对象时 waiting_on 可为空；仅明确完成期限才写 deadline。") [无等待对象的新提醒测试 ↗](../../../apps/server/tests/assistant-runtime.test.ts#L970 "验证新提醒保存 next_check_at、waiting_on=null、dueAt=null，到点只生成一次跟进通知且不显示截止时间。")

等待对象和时间表达必须来自当前明确指令，不能由模型猜；有检查或暂缓时间时，还必须保留用户当前原话中的 time_expression，并规范化为 ISO 时间。参考 [等待对象和时间来自当前指令 ↗](../../../apps/server/src/tasks/follow-up.ts#L5 "说明 waiting_on 与 time_expression 不能推断，且跟进时刻会规范化为 ISO。")

snooze 会保留既有 waiting_on，把 snoozed_until 同步为新的 next_check_at，并保持截止日不变。complete、cancel 和 reopen 会清空 follow_up；done 或 cancelled 的事项要先 reopen，才能再等待、暂缓或改期。参考 [事项动作更新状态与时间 ↗](../../../apps/server/src/memory/service.ts#L102 "说明 snooze 保留等待对象且不改截止日，完成、取消、重开清除 follow_up，并限制已关闭事项的后续操作。")

提醒器只扫描 open / waiting 事项。到 due_at 或 next_check_at 时生成站内通知，并按事项版本、触发种类和发生时刻保存回执，所以服务重启后可以补发一次，而重复轮询不会反复发送；done / cancelled 不再提醒。通知正文会分别写当前检查时间与当前截止时间，也明确说明系统不会自动联系他人。参考 [持久且去重的站内提醒 ↗](../../../apps/server/src/tasks/follow-up.ts#L17 "说明只扫描 open/waiting，按截止或检查时间触发，以事项版本和发生时刻去重，且不会自动联系他人。")

最后，**通知已读只表示“我看过这条通知”**。实现只更新 notification.read_at；界面明确说明它不会批准变更、完成待办或取消后续提醒。参考 [已读只更新通知 ↗](../../../apps/server/src/store.ts#L639 "实现层面说明标为已读只写 notifications.read_at。") [通知中心解释已读边界 ↗](../../../apps/web/src/App.vue#L1074 "界面明确已读不会批准变更、完成待办或取消后续提醒。")

<a id="check-progress-and-limits"></a>
## 怎样判断哪些已完成，哪些仍待处理

可以按对象使用两把状态尺。

**材料与记忆**

- **queued**：当前 job 尚未开始。extract_claims 排队表示提取未运行；verify_proposals 排队表示提取已完成、核验未运行。
- **succeeded**：当前 job 已结束；若它只是提取或刷新调度，后面仍可能有核验与应用。
- **applied**：候选已实际写入；对来源刷新，还要求所有受影响记忆都已由新版证据修复。
- **invalidated / needs_review**：旧结论不能再作为当前有效记忆，仍需新证据或人工处理。
- **awaiting_decision**：存在真正需要用户授权或取舍的高影响变化。
- **retry_wait / failed**：处理未完成，可查看错误并重试。
- **superseded**：这次刷新已被更晚的来源版本取代。

**Wiki 与事项**

- Wiki 看章节的 current / needs-review / unavailable；writing、failed、published 是生成过程，不替代章节适用性判断。
- 事项看 status、waiting_on、next_check_at、snoozed_until 和 due_at；通知的 read 只表示提醒已读。

判断后台是否会继续处理时，不要混淆三层配置与状态：

1. 配置 schema 在省略 learning 时回退到 enabled=false。参考 [学习配置字段缺省值 ↗](../../../apps/server/src/config.ts#L65 "说明配置对象省略 learning 时 schema 回退为 enabled=false。")
2. 启动时优先读取 OMEM_CONFIG 或 omem.local.json；文件不存在才读取 config/omem.example.json，而当前仓库示例明确设置 learning.enabled=true。参考 [配置文件实际加载顺序 ↗](../../../apps/server/src/config.ts#L130 "说明启动优先读取 OMEM_CONFIG 或 omem.local.json，不存在时才读取示例配置。") [仓库示例配置启用学习 ↗](../../../config/omem.example.json#L67 "说明当前仓库 fallback 示例配置明确设置 learning.enabled=true。")
3. 应用只有在 learning 已启用且能找到对应 profile 时才构造 LearningPipeline；启用却缺少 profile 会启动报错。健康状态又分别报告 processingEnabled 与 learning.running。参考 [按实际配置创建学习管线 ↗](../../../apps/server/src/app.ts#L122 "说明只有启用 learning 且找到对应 profile 才构造 LearningPipeline，缺 profile 会报错。") [健康状态区分启用与运行 ↗](../../../apps/server/src/app.ts#L220 "说明服务分别报告 processingEnabled 和 learning.running，不能把配置允许等同于后台正在运行。")

最可靠的用户入口是“材料处理”页：**后台处理服务已启动**表示当前正在运行；**自动处理已启用，当前后台未运行**表示配置允许但此刻没有运行；**自动处理未启用**表示原文仍可保存和检索，任务也可留在队列，但不会继续调用学习模型。参考 [材料处理页显示当前运行状态 ↗](../../../apps/web/src/LearningView.vue#L81 "界面区分未启用、已启用但未运行和后台已启动，并说明未启用时原文仍可保存检索。")

当前实现已经支持保存和检索原文、排学习任务、在后台实际运行且 Agent 可用时完成提取—独立核验—应用、来源换版后的失效与重核验、显式事项操作和持久站内提醒。仍需用户或显式动作的部分包括含糊时间的澄清、高影响冲突的决定、文章维护设置，以及由用户报告“对方已经回复”。当前没有自动联系对方、监听外部回复、周期回顾、日历或学习卡；SQLite / shared-token 运行方式仍是单用户实现。参考 [当前主动能力与外部边界 ↗](../../../docs/reader-first/operations.md#L35 "说明站内事项与提醒已支持，但没有自动监听回复、周期回顾、日历或学习卡，且当前为单用户服务。")

项目或主题目前可以作为文章选材与助手调查的明确范围，但新增记录不会按内容自动归属，而且该归属尚未成为记忆写入的 project_trusted。它不改变本文的授权边界：材料属于某个项目，不等于用户交办了事项。参考 [项目范围尚未进入记忆信任 ↗](../../../docs/reader-first/progress.md#L26 "说明项目或主题归属需明确指定，可用于文章和调查，但未接到记忆写入的 project_trusted，也不自动按内容归属。")
