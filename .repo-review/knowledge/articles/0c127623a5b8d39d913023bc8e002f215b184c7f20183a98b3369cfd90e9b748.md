# Code Wiki 与代码知识技术版图

该调研比较代码 Wiki、索引协议、语法解析、代码图谱、代码 RAG 和本地 embedding，建议借用 SCIP 数据模型、引入 Tree-sitter 结构层并移植 repo-map 算法；这些仍是研究结论和顺序化 PoC 计划。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="current-constraints"></a>
## 现状与治理约束

评估以 TypeScript/Vue、Fastify、单用户 SQLite 和本地隐私为边界。材料陈述当前已有固定 revision 与 fragment 引用、关键词检索和人工关联清单，但跨 revision 身份续接及语义检索尚未实现；未登记的代码与文档关系也不能自动成为 confirmed。[代码知识评估的当前约束 ↗](../../../docs/research/code-wiki-landscape.md#L5 "支持附近对技术栈、固定版本、检索现状、人工关系治理及未实现缺口的说明。")

<a id="reuse-decisions"></a>
## 复用组件而非整个平台

研究优先考虑 SCIP 的快照式符号模型、Tree-sitter 的 TS/Vue 结构化切片、Aider repo-map 的图排序以及本地 embedding。完整 Wiki 平台往往重复数据库、UI 与模型编排，生成散文又缺少不可变证据回链，因此结论是借鉴组件、协议和流水线，而非直接引入整个平台。[组件复用与平台取舍结论 ↗](../../../docs/research/code-wiki-landscape.md#L13 "说明建议复用哪些协议和算法，并解释完整平台及自动抽边为何不直接进入 omem。")

<a id="poc-sequence"></a>
## 验证顺序与依赖关系

计划依次验证 TS/Vue outline、SCIP 风格 occurrence 表、跨 revision 续接启发式、本地语义召回和 PageRank 上下文。P1–P3 是不依赖 embedding 的代码索引主线，P4 是平行项目；这些都是尚待执行并跨过验收门的计划，不能描述成现有能力。[代码索引 PoC 门 ↗](../../../docs/research/code-wiki-landscape.md#L281 "支持附近对五步验证顺序、验收门和 P1–P3 不依赖 embedding 的说明。")
