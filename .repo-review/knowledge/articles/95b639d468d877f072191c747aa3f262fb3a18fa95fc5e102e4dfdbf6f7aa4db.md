# 让飞书消息进入个人助理：订阅、读材料与跟进

面向希望定时查看飞书消息、又不改变原有消息状态的个人用户。用一个免打扰群里的直接提及案例，说明怎样发现可选会话、设置订阅或排除、开启与暂停采集，怎样判断文档、图片、附件和话题是否读全，以及为何“收到消息”“给出建议”“进入队列”和“形成记忆或事项”是四件不同的事。附机器人通知、后台服务检查、八分钟静默时限和当前仍需人工确认的事项。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="start"></a>
## 先记住四个不同的结果

本文用一个**教学示例**贯穿操作：需求群开着免打扰，同事直接 @你确认周三交付，并附上一份飞书文档和一张流程截图。这不是系统已经处理过的真实消息。

个人消息采集是只读的：它保存消息和资源，没有发送、回复、删除或标记已读的接口；已有机器人只承担另一路通知。因而最重要的判断不是“消息来了没有”，而是依次确认：

1. **已收到**：消息进入“最近消息与判断”。
2. **已读材料**：正文、文档、图片或附件各自显示读取状态；保存原件不等于理解内容。
3. **已排队整理**：完整材料可以交给 Agent，但排队和分类仍不是最终结果。
4. **已应用**：经过抽取、独立复核和治理后，才可能在记忆或事项中出现。

所以，示例里的“直接 @我确认周三交付”可以被判为“可能需要你行动”，却不会仅凭 @ 或一个分类标签自动创建待办。参考 [个人消息只读边界 ↗](../../../docs/reader-first/personal-messages.md#L1 "说明个人登录采集与机器人通知分离，采集器不发送、回复、删除或标记已读。") [标签只是建议 ↗](../../../apps/web/src/PersonalLark.vue#L274 "说明界面分类不是事项或记忆的最终应用结果。")

## 五分钟完成订阅和定时采集

如果你拿到的是安装包或正式发布版，先在运行服务的电脑上完成：

```bash
omem init
omem service start
omem open
omem lark login
omem lark status
```

公开 npm 版本在当前快照中**尚未上传**，因此 `npm install -g omem` 只能作为发布后的安装方式，不能假定现在从公共仓库一定安装成功。初始化也不会替你订阅消息、运行模型或发送通知。参考 [安装与初始化边界 ↗](../../../docs/cli.md#L5 "支持发布后的初始化命令、PM2 行为、休眠限制以及初始化不会自动订阅或运行模型。") [公开 npm 尚未上传 ↗](../../../docs/reader-first/progress.md#L21 "说明当前快照中的公共发布状态，避免把发布后命令写成当前必然可用。")

网页中的最短路径是：

1. 打开“飞书消息”，点**读取最近活跃会话**。这会刷新非免打扰候选，不会自动订阅。
2. 对已经出现在列表中的会话选择“订阅”；不想读取普通消息时选“仅提及时”；完全不读则选“排除”。
3. 设置同步间隔和新订阅首次回溯时间。默认分别是 5 分钟和 24 小时，可设范围为 1–1440 分钟、1–168 小时。
4. 勾选**开启定时采集**和需要的提及、资源选项，然后**保存设置**。
5. 需要马上检查时点“立即同步”。新库默认暂停；关闭定时采集时，立即同步也不可用。

这里有一个会直接影响首次配置的限制：发现操作明确排除当前处于免打扰的会话，最多读取 300 个候选。因此，示例中的需求群若从未被发现过，不能在它仍免打扰时靠“读取最近活跃会话”加入列表。直接 @你仍可由全局提及例外捕获；若要为该群设置“订阅”或“排除”，它必须已经保留在列表中，或者先在群未免打扰时发现一次。已有订阅不会因为后来免打扰或暂时不活跃而从列表消失。参考 [网页发现和会话列表 ↗](../../../apps/web/src/PersonalLark.vue#L100 "说明网页发现只报告非免打扰会话，界面允许为已保存的 stream 选择模式。") [发现排除免打扰 ↗](../../../apps/server/src/integrations/lark-personal/client.ts#L96 "证明发现明确携带 exclude-muted，最多取三页、每页一百条。") [只能设置已发现会话 ↗](../../../apps/server/src/integrations/lark-personal/service.ts#L102 "说明发现结果写入 stream，设置模式要求会话已在当前列表中。")

等价的日常 CLI 是：

```bash
omem messages discover --json
omem messages watch CHAT_ID
omem messages enable
omem messages sync
omem messages status
omem messages inbox --json
omem messages pause
```

暂停只停止调度，订阅、历史和同步位置会保留。参考 [个人消息 CLI ↗](../../../docs/cli.md#L112 "支持登录、发现、订阅、启用、同步、查看与暂停命令，以及暂停保留历史和订阅。")

<a id="selection"></a>
## 订阅、提及例外和排除怎样一起生效

三种会话选择不是同一强度的开关：

| 选择 | 普通消息 | 独立提及通道 |
| --- | --- | --- |
| 订阅 | 定时读取 | 开启提及例外时也会检查 |
| 仅提及时 | 不定时读取普通流 | 开启提及例外时可读取 |
| 排除 | 不读取 | 也不读取，优先级最高 |

回到示例：即使需求群尚未出现在会话列表中，只要“同时检查所有群里的 @我 / @所有人”已开启，**直接 @你**仍可能从独立提及通道进入。若该群此前已经发现并设为订阅，后来开启免打扰，普通订阅流会跳过免打扰时段并把位置推进到本轮结束；以后解除免打扰，也不会补拉整个静默期。关闭提及例外后，只剩普通订阅流。参考 [免打扰与提及分流 ↗](../../../apps/server/src/integrations/lark-personal/service.ts#L233 "说明免打扰普通流不补拉静默期，独立提及流仍运行，并区分直接提及和 @所有人。")

还要区分飞书的两个设置和 omem 的明确排除：

- **免打扰**：使发现列表排除当前免打扰会话，并让已有普通群流跳过静默期；它不自动挡住直接提及。
- **屏蔽 @所有人**：只过滤广播式 @所有人，不挡直接 @你。
- **omem 明确排除**：普通流和提及流都跳过，但只能对已在列表中的会话设置。

授权可见范围和搜索实际返回范围仍由飞书决定。代码已经接入 @所有人的查询语义和分流，但当前真实样本没有单独确认 @所有人命中，因此不要把它当成已完成的真实验收。参考 [提及真实验收边界 ↗](../../../docs/reader-first/personal-messages.md#L13 "支持免打扰、屏蔽 @所有人与直接提及的区别，并明确 @所有人真实命中尚未验收。")

<a id="materials"></a>
## 消息到了以后，检查材料读到了哪一步

在“最近消息与判断”里依次看四处：消息正文和“在飞书打开原消息”、**查看保存的材料**、折叠的“文档、图片与附件”、以及“判断依据与分类”。状态文案的含义很具体：

- **正文已读取**：解析结果已经进入这条材料。
- **原件已保存，仍需理解内容**：文件可下载，但不能据此说语义已经理解。
- **资源尚未读取**或具体错误：仍有缺口。
- 消息不是 `ready` 时可点**重新读取与判断**；它会用已保存的原始消息重做资源处理和判断，已明确排除的会话除外。

参考 [消息页可见状态 ↗](../../../apps/web/src/PersonalLark.vue#L284 "支持查看原材料、回飞书、重试以及资源的已读、已保存和失败状态。")

| 输入 | 当前会保存或提供什么 | 仍要检查什么 |
| --- | --- | --- |
| 文字、富文本、卡片 | 发言人、时间、展开正文、原始消息和固定材料 | 普通上下文只取此前已入库的 8 条，不是无限回溯 |
| 飞书 docx/wiki 链接 | 独立文档版本；成功后把文档内容加入本消息 | 不递归读取无限引用，嵌套资源受导入器能力限制 |
| 图片 | 下载原件；PNG/JPEG/WebP 且不超过 5 MB 时可交给支持视觉的 Agent | 文本决策模型不看像素；下载成功不等于图片已理解 |
| PDF/DOCX | 保存原件并交给 Docling 解析，成功后形成关联材料 | OCR、复杂版式仍可能读错；超过 20 MB 要单独导入 |
| TXT/Markdown/CSV/JSON/log | 不超过 200 KB 时作为文字加入 | 更大文件要单独导入 |
| 视频、音频、其他附件 | 保存可下载原件 | 当前没有自动转写或视频分析 |
| 话题 | 已返回的回复拆成独立消息保存 | 若仍有更多页或返回错误，会标记未读全；目前不继续分页补齐 |

即使资源失败，原始消息仍会保留。示例中的飞书文档可能显示“正文已读取”和“查看关联材料”；流程截图可能只显示“原件已保存，仍需理解内容”。遇到后一种情况，应先打开原件核对，再重试或人工处理，不要根据消息标签直接行动。参考 [各类资源处理范围 ↗](../../../docs/reader-first/personal-messages.md#L21 "支持文字、文档、图片、PDF/DOCX、文本附件和其他媒体的处理能力与限制。") [资源保存和读取实现 ↗](../../../apps/server/src/integrations/lark-personal/materials.ts#L60 "支持文档导入、图片格式与大小、可解析附件和原始消息保存的细节。")

<a id="decision"></a>
## 为什么收到消息还没有变成待办

一条消息要走完下面四步，才可能成为记忆或事项：

1. **收到并保存**：先保留原消息和能读取的资源。
2. **完整性检查**：资源失败、只有原件但无法供 Agent 阅读、话题未拉全或出现可疑指令时，状态留在 review，不自动整理。
3. **小模型建议**：判断安排、学习、业务、代码、关注原因、背景缺口和可疑指令。界面上的模型分数是模型置信度，不是准确率。
4. **Agent 与治理**：完整材料由 Agent 抽取候选；未处理候选再进入独立复核，最后由 MemoryService 整批裁决为自动应用、等待决定或拒绝。

参考 [消息进入学习的门 ↗](../../../apps/server/src/integrations/lark-personal/service.ts#L394 "支持完整性、可疑指令、高置信噪声和决策模型不可用时的实际分流。") [独立复核与整批裁决 ↗](../../../apps/server/src/learning/pipeline.ts#L723 "支持候选经独立复核后由 MemoryService 整批评估为自动应用、等待决定或拒绝。")

实际分流中，高置信噪声（至少 0.85）且没有资源时只保留原件，不进入自动学习；可疑指令留待检查；资源或话题未读全时也不进入学习。除此之外，完整且未删除的材料可以进入学习，**低分、决策服务不可用，或模型认为背景不足本身，都不是丢弃条件**。这正是示例中不能把“直接 @我”直接等同于“创建周三待办”的原因。参考 [决策模型没有写入权 ↗](../../../docs/reader-first/personal-messages.md#L34 "说明低分或服务不可用仍可走 Agent，分类标签不能直接写事实，排队不代表记忆已生成。")

还要确认学习后台真的开启：配置需有 `learning.enabled=true`，并让 `learning.profileId` 指向可用的 ACP profile，修改后重启。然后分别检查：

- `omem messages inbox --json`：消息、资源和建议；
- `omem jobs list` / `omem jobs show JOB_ID`：抽取或复核是否仍在排队、失败或完成；
- `omem memories list`：最终已应用的记忆；
- `omem tasks list`：最终已应用的事项。

“ready”“已排队”、模型标签、Agent 输出或复核运行都不等于事项已经应用；以最后两项为准。参考 [学习开关与结果查询 ↗](../../../docs/cli.md#L78 "支持开启 learning、配置 profile，并用 jobs、memories 和 tasks 区分处理中与最终结果。")

<a id="notifications"></a>
## 用已有机器人收变化和故障通知

个人登录负责**读取**，机器人绑定负责**通知**，这是两套授权。采集不要求机器人加入每个被读取的群，也不会把故障发回被采集群。

同一会话连续同步失败时，只在第一次记录并尝试向已有的 `owner_notification` 绑定排队通知；恢复后再通知一次。登录身份变化、登录失效或权限错误会保留同步位置，并让**本次同步作业失败**；它不会自动把定时采集设置改成暂停，也不会把会话改成“仅提及时”或“排除”。修复登录后，应重试作业或再次同步，并检查设置是否仍为 enabled：

```bash
omem lark status
omem lark login
omem messages status
omem messages sync
```

鉴权错误不自动重试；普通暂时性错误才按作业规则有限重试。没有有效机器人绑定时，变化仍留在站内，但不会发出机器人通知。服务如果彻底退出，也无法给自己发送故障消息；这类故障要靠后台重启和外部状态检查发现。参考 [同步失败与恢复通知 ↗](../../../apps/server/src/integrations/lark-personal/service.ts#L319 "支持连续失败只首次通知、恢复再通知；失败不切换全局或会话模式。") [鉴权作业直接失败 ↗](../../../apps/server/src/jobs/repository.ts#L640 "说明 auth 类错误重试上限为零，当前作业进入 failed，而不是自动暂停采集设置。") [通知与个人登录分权 ↗](../../../docs/cli.md#L139 "说明机器人复用已有绑定，与个人登录是两套授权。")

<a id="service"></a>
## 检查后台是否持续运行

安装版日常使用：

```bash
omem service status --json
omem status --json
omem messages status
omem messages inbox --json
```

需要控制进程时用 `omem service start|restart|stop`。后台由包内 PM2 管理：终端退出后继续运行，进程异常退出会退避重启，并限制为单实例；目标端口已有服务时会拒绝再启动一个采集实例。它**没有安装系统开机自启动**，电脑休眠时也不会采集。状态输出给出 PM2 状态、PID、重启次数、API 可达性和日志路径；状态检查本身不会启动服务。参考 [后台进程与日志状态 ↗](../../../apps/server/src/service-manager.ts#L64 "支持 PM2 单实例、自动重启、状态字段、日志路径、无开机自启和休眠限制。")

排障时分三层看：

1. `service status --json`：进程是否 online、API 是否可达、日志在哪里。
2. `status --json`：查看 `personalLark.enabled`、`running`、`subscriptions`、`failedStreams`、`lastSuccess`，以及 learning 是否运行。
3. `messages status` / `inbox`：定位具体流的最近错误，以及消息是 ready、review 还是 failed。

当前实现中，健康接口顶层固定返回 `status: "ok"`，同时把 `personalLark` 作为嵌套状态返回；服务管理器只据顶层 `status` 计算 API 是否健康，而两个 CLI 状态命令的非零条件分别是“PM2 非 online 或 API 未通过顶层检查”以及“接口顶层 status 非 ok”。因此 `failedStreams` 虽会出现在 JSON 中，却不会单独保证命令返回非零。不要只看一条绿色退出码，要实际检查上述字段和消息流错误。参考 [健康接口顶层状态 ↗](../../../apps/server/src/app.ts#L231 "证明健康接口顶层固定返回 ok，并将 personalLark 作为嵌套状态返回。") [服务管理器的健康判断 ↗](../../../apps/server/src/service-manager.ts#L42 "证明 service status 不启动守护进程，并只用接口顶层 status 判断 API 健康。") [两个状态命令的退出码 ↗](../../../apps/server/src/cli.ts#L126 "直接证明 service status 和 status 的非零退出码条件，不包含 failedStreams 单独失败。")

<a id="timeout"></a>
## Agent 还在输出时，不会因为总计八分钟被切断

短答：**持续有有效活动，就不会因为从启动起累计八分钟而必然中断。**

默认的 480000 ms 现在是连续无活动时限。ACP 初始化响应、有效会话更新、工具进展和模型输出都会续期；stderr 日志和宿主轮询不会。完全静默八分钟才超时。一个长工具如果一直没有进展事件，也可能触发静默超时，应按工具实际耗时提高 `idleTimeoutMs`。旧 `timeoutMs` 仍兼容，但也表示无活动时限；同时配置时 `idleTimeoutMs` 优先。默认没有总时长上限，只有显式配置 `maxDurationMs` 才会设置总上限，用户取消始终有效。参考 [八分钟是静默时限 ↗](../../../docs/cli.md#L160 "说明有效活动续期、无进展工具风险、兼容字段、可选总时限和取消行为。")

<a id="checklist"></a>
## 现在仍需你检查的五件事

完成配置后，用示例消息做一次人工走查：

1. **范围**：若需求群从未进入列表，确认全局提及例外能否收到直接 @；若要设置订阅或排除，先在非免打扰时发现它。真实 @所有人命中当前仍未验收。
2. **材料**：文档是否显示“正文已读取”，截图是否只是保存了原件；PDF/DOCX 的 OCR、复杂布局，视频音频和超大附件都不能仅凭“已保存”判断语义正确。
3. **话题**：是否出现未拉全或错误提示；有缺口就先重试并回飞书核对。
4. **最终结果**：到 jobs、memories、tasks 分别确认队列、记忆和事项。消息标签与 ready 状态不是应用结果，对方回复是否足以完成已有事项也仍需 Agent 调查。
5. **运行状态**：检查个人登录、PM2/API、`personalLark.failedStreams` 和具体消息流错误。鉴权失败后设置可能仍保持 enabled，修复登录后需主动重试或再次同步。公开 npm 仍未发布时，应使用你实际获得的安装包或开发环境说明。

参考 [当前个人消息缺口 ↗](../../../docs/reader-first/progress.md#L23 "汇总 @所有人、多媒体和自动跟进仍需人工验收的当前状态。") [消息材料与跟进待验收 ↗](../../../docs/reader-first/personal-messages.md#L21 "支持图片、附件、话题和最终跟进不能由保存或分类状态替代检查。")

开发排障只需从这些入口开始，内部字段和表名留在这里：

| `PersonalLark.vue` | 会话选择、资源状态和判断结果 |
| `service-manager.ts` / `agent-timeout.ts` | PM2 状态、日志位置、静默与总时限 |
