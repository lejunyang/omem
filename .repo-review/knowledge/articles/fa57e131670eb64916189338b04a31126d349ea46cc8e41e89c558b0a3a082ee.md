# Repo Review 开发编排器进程生命周期测试

该集成测试在临时仓库和动态端口上启动真实 dev-review 编排器，验证双端口预检、API/Web 就绪、跨平台终止、端口释放及 SQLite 文件句柄清理。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="harness"></a>
## 隔离的真实进程测试夹具

测试不使用固定 5180/5181，也不接触真实 `.repo-review` 数据，而是创建只含一个 TypeScript 文件的临时仓库，通过真实 `scripts/dev-review.ts` 子进程运行编排器；stdout 和 stderr 会持续排空并保留用于失败诊断。[临时仓库与子进程输出 ↗](../../../apps/server/tests/review-dev.test.ts#L105 "支持动态 fixture 的构造、真实 dev-review 子进程启动以及输出流收集方式。") 启动时明确传入 API 端口、Web 端口和 fixture 根目录，健康检查要求 review 模式以及非零 source、fragment 数，Web 根路径必须返回 200。关闭后还会等待真实 exit 事件并检查两个端口均已释放。[显式环境配置与就绪检查 ↗](../../../apps/server/tests/review-dev.test.ts#L201 "支持三个环境变量、health 与 SPA 检查、真实退出等待和双端口释放流程。")

<a id="platform-shutdown"></a>
## 端口预检与跨平台关闭合同

API 或 Web 任一端口已占用时，编排器都会退出并产生非零退出码，直接覆盖双端口预检失败合同。[API 与 Web 双端口预检 ↗](../../../apps/server/tests/review-dev.test.ts#L256 "直接支持 API 或 Web 任一端口被占用时编排器均以非零状态退出。") Windows 清理函数对精确编排器 PID 执行 `taskkill /T /F`，POSIX 分支则向该 PID 发送 `SIGTERM`。[精确进程终止的平台分支 ↗](../../../apps/server/tests/review-dev.test.ts#L116 "支持 Windows 对精确 PID 及其后代执行树回收，以及 POSIX 向精确 PID 发送 SIGTERM。") POSIX 专门用例通过 `child.kill("SIGTERM")` 触发编排器关闭处理器，并断言优雅退出码为 0；Windows 对同一路径不要求退出码为 0，而以最终树回收和端口释放为合同。[优雅关闭与退出码合同 ↗](../../../apps/server/tests/review-dev.test.ts#L306 "支持 POSIX 通过 SIGTERM 进入关闭处理器并断言退出码为 0，同时说明 Windows 强制终止路径不作同一退出码断言。")

fixture 只在等待编排器退出后删除，并允许轮询操作系统释放 SQLite/WAL 文件句柄；清理错误不会被吞掉。[文件锁释放与清理错误传播 ↗](../../../apps/server/tests/review-dev.test.ts#L164 "支持 SQLite/WAL 句柄释放轮询，并说明清理失败会单独抛出或与主错误合并。") 另有三轮循环，每轮分配新端口并创建新 fixture，用于暴露重复启动和终止中的竞争问题。[三轮重复启动终止 ↗](../../../apps/server/tests/review-dev.test.ts#L339 "直接支持三轮使用新端口和新 fixture 的启动、终止与清理循环。")

<a id="coverage-limits"></a>
## 测试未证明的范围

该测试证明开发编排器能让 health 与 SPA 就绪，并在受测关闭路径后释放端口和文件资源，但没有验证具体知识 API、同步结果、前端交互或业务 worker 行为。文件头还明确限定：目录删除轮询只是操作系统锁释放等待，不构成对全部后代进程的确定性追踪。[进程生命周期测试边界 ↗](../../../apps/server/tests/review-dev.test.ts#L1 "说明动态端口、平台终止合同及锁释放轮询不等于确定性追踪全部后代进程。") 因而无监听端口且未持有 SQLite 句柄的孤儿进程，仍可能逃过现有观测。
