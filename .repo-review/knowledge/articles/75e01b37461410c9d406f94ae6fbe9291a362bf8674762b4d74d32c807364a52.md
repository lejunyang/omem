# 从固定证据到可追溯代码知识

该文档是 Code Knowledge 的历史设计基线：在不可变 Capture 证据之上增加文件、符号、结构关系和派生理解，并以确定性 TS/Vue 解析作为首个切片。后续实现吸收了这一方向，但 repo-review 已进一步成为统一知识链的仓库适配与阅读视图，实际能力和缺口应以当前状态与覆盖报告为准。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose-and-status"></a>
## 解决代码结构与原始证据脱节的问题

早期 repo-review 已能保存不可变版本、固定片段和人工评审关系，但代码侧主要依赖正则分片与字符串符号，缺少精确位置、导出信息以及 imports、calls、routes 等结构语义。设计因此提出先用确定性解析生成文件、符号和结构边，再把人工关系与模型理解挂到同一证据链上；模型不可用时，结构浏览、搜索和追溯仍可工作。参考 [代码知识设计目标 ↗](../../../docs/implementation/code-knowledge-design.md#L12 "支持早期代码侧弱建模的问题，以及确定性结构层先于模型理解的设计目标。")

本文是**历史设计提案**，其中的阶段安排不能直接视为当前能力。文档要求以复审记录和状态页判断实际范围；后续复审保留了统一 Capture、Source、Revision、Fragment 的方向，同时纠正了“通用类型化投影已经完整实现”的过度表述。参考 [历史提案定位 ↗](../../../docs/implementation/code-knowledge-design.md#L1 "说明本文记录提案时的基线，设计项不等于当前已经实现。")、[方案复审结论 ↗](../../../docs/implementation/code-wiki-review-2026-09-29.md#L1 "支持统一证据链方向得到保留，同时原先实现程度的表述被复审纠正。")

<a id="model-and-evidence"></a>
## 代码图是证据链上的可重建投影

`CodeFile`、`CodeSymbol`、`CodeEdge` 和 `CodeUnderstanding` 被设计为原始 Source、Revision、Fragment 之上的类型化视图，而不是新的事实库；其中代码文件映射已有来源，符号通过 fragment 锚定不可变证据。参考 [证据链上的领域实体 ↗](../../../docs/implementation/code-knowledge-design.md#L82 "支持代码文件、符号、结构边和派生理解叠加于既有证据链，以及符号使用固定片段作为证据锚点。")

符号的逻辑身份由路径、限定名和类型确定，位置范围只对当前快照有效，签名用于展示与搜索。结构边另行表达 imports、exports、defines、calls 等关系，并记录解析器、人工 seed 或模型等来源；PoC 中的同文件名称级调用必须标记为候选。参考 [符号身份与位置 ↗](../../../docs/implementation/code-knowledge-design.md#L135 "支持符号身份、当前快照位置、签名字段和固定 fragment 锚点之间的区别。")、[结构边及其来源 ↗](../../../docs/implementation/code-knowledge-design.md#L154 "支持代码结构边与评审意图边分开存储、边类型、状态字段和 parser、seed、llm 三类来源。")、[确定性解析范围 ↗](../../../docs/implementation/code-knowledge-design.md#L366 "支持 TypeScript 与 Vue 解析器的选择、首期覆盖范围，以及同文件名称级 calls 必须标记为 candidate 的约束。")

派生理解保存输入指纹、未知项、状态和真实证据引用，失败或模型不可用不会阻塞原始证据读取；它也不会反过来作为独立事实进入提取队列。后续 P0 约束进一步明确，`code_*` 仅是可重建投影，界面必须显示人类可读名称，并让缺失或过期节点不可操作且说明原因。参考 [派生理解约束 ↗](../../../docs/implementation/code-knowledge-design.md#L187 "支持派生理解记录输入指纹、未知项、证据引用和状态，并且不作为新的独立事实进入提取队列。")、[可重建投影边界 ↗](../../../docs/implementation/code-knowledge-design.md#L505 "支持代码侧表不成为第二事实源，以及可见标签、失效节点和快照正文读取的约束。")

<a id="sync-and-lifecycle"></a>
## 同步、失效与兼容策略

同步时，解析器按符号位置在当前 head revision 中选择匹配片段；文件变化后产生新 revision，旧 fragment 随旧版本冻结，依赖旧锚点的关系转为 stale，再由下一次同步在新 head 上重新定位。缺失端点保留为可见的 missing，历史关系只改变状态而不删除。参考 [锚点与失效生命周期 ↗](../../../docs/implementation/code-knowledge-design.md#L214 "说明符号如何锚定固定片段，以及内容变化后旧锚点和关系如何失效并重新定位。")

新增代码表采用增量投影：不复制正文，不改写既有证据行，评审意图仍由原关系表与 `associations.json` 掌权；确定性标识和 upsert 让重复同步保持幂等。参考 [兼容投影策略 ↗](../../../docs/implementation/code-knowledge-design.md#L340 "支持不搬运正文、保留原关系权威、只增加新表和幂等同步的兼容原则。") 当前实测仍不解析跨文件调用，也没有跨 revision 的符号或 fragment 身份续接，代码变化后需要重新同步定位。参考 [当前代码图边界 ↗](../../../docs/implementation/status.md#L50 "确认跨文件调用与跨版本身份续接仍未实现，避免把设计目标误写为当前能力。")

<a id="delivery-and-current-scope"></a>
## 从分阶段设计走向统一知识流程

原路线按确定性解析、只读 API、Web 阅读、派生理解以及助手与飞书接入逐步交付；首个切片只覆盖到 Web 与只读 API，完整 assistant→memory→Lark 通路属于后续阶段。参考 [分阶段交付路线 ↗](../../../docs/implementation/code-knowledge-design.md#L441 "说明首个纵向切片与后续助手、检索和飞书接入之间的范围划分。") 解析方案优先使用已有的 TypeScript Compiler API 与 Vue SFC 编译器，首期覆盖顶层符号、导入导出、组件、路由和测试边界，跨文件类型分析、SCIP 与多语言解析明确不在范围内。参考 [确定性解析范围 ↗](../../../docs/implementation/code-knowledge-design.md#L366 "支持 TypeScript 与 Vue 解析器的选择、首期覆盖范围，以及同文件名称级 calls 必须标记为 candidate 的约束。")

当前产品已将仓库原始材料、复核文章和必要历史证据接入个人知识库，采用完整文章、页内导航和段末引用；通用知识流程还具备持久分析、独立复核及知识引导的原始证据召回。旧正文不会因界面统一而自动获得复核，具体完成度仍应以当前覆盖、失败和过期记录为准。参考 [统一知识阅读现状 ↗](../../../docs/implementation/status.md#L1 "说明当前仓库材料、复核文章、引用与知识处理已进入统一入口，同时完成度必须以覆盖记录判断。")
