# Code Knowledge 领域模型与第一纵向切片设计

这是一份历史设计提案：它以 Capture→Source/Revision/Fragment 为证据权威，规划可重建的代码 typed projection、确定性 TS/Vue 解析、结构关系、只读 API、Web 阅读及模型增强。后续材料表明，确定性代码图、Code Wiki 和共享阅读能力已经落地；2026-09-29 复审所述“代码角色尚未统一编排”也是当时限制，已被 2026-10-01 接入共用知识合同、持久分析与独立复核的进展替代。当前仍明确存在的边界包括跨文件 calls、跨 revision 身份续接，以及全库知识覆盖尚未完成。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="positioning"></a>
## 历史定位与设计目标

本文明确标注为历史设计提案，并以“事实／设计／未实现”区分提案时的代码基线和未来方案，因此其中的阶段表与缺口不能直接视作当前状态。[历史提案与状态标注 ↗](../../../docs/implementation/code-knowledge-design.md#L1 "支持本文记录提案时基线，当前能力应以复审和状态文档为准。") 它针对早期 repo-review 只有固定 fragment、字符串符号和评审意图关系，缺少精确代码结构的问题，提出先做不依赖模型的解析，再把 seed 与模型理解挂到统一证据链上。[Code Knowledge 设计目标 ↗](../../../docs/implementation/code-knowledge-design.md#L14 "支持早期弱建模问题以及确定性结构层与模型增强层的设计边界。") 后续复审认可这一方向，同时纠正了早期“通用 typed projection 已实现”的过度表述。[Code Wiki 复审核心判断 ↗](../../../docs/implementation/code-wiki-review-2026-09-29.md#L1 "支持统一证据链方向得到认可，同时早期实现范围曾被表述过度。")

<a id="model"></a>
## 投影模型、证据锚点与生命周期

Repository、Snapshot、File、Symbol、Edge 与 Understanding 都是原始来源之上的可重建投影，不替代 sources、revisions 和 fragments；符号位置属于当前快照，引用与检索最终锚定不可变 fragment。[代码领域模型 ↗](../../../docs/implementation/code-knowledge-design.md#L82 "解释代码实体是在既有来源、版本和片段之上的投影，以及符号的证据锚点。") 结构边与评审意图边分开表达，imports、defines、calls 等来自解析器，而 implements 等意图关系继续受人工 seed 约束。[结构化代码关系 ↗](../../../docs/implementation/code-knowledge-design.md#L154 "说明结构边与评审意图边的区分、来源及反向查询方式。") 文件变化后旧证据保持冻结，相关边转为 stale；无法解析的 locator 保留为 missing，不静默丢弃。[固定片段与失效语义 ↗](../../../docs/implementation/code-knowledge-design.md#L214 "支持符号锚定不可变片段，以及 stale、missing 和双端失效规则。") 兼容策略也要求只增量投影、确定性幂等重建，不复制正文或清空既有关系。[兼容投影策略 ↗](../../../docs/implementation/code-knowledge-design.md#L340 "支持新增代码表不搬运正文、不改写既有关系并可幂等重建。")

<a id="delivery"></a>
## 解析范围、交付路径与诚实降级

首切片选择 TypeScript Compiler API、Vue SFC 编译器和保守规则，以零新增依赖实现离线确定性解析；同文件名称级 calls 仅为候选，跨文件类型分析与多语言索引不在该阶段范围内。[TS 与 Vue 解析选择 ↗](../../../docs/implementation/code-knowledge-design.md#L366 "解释首切片的解析技术、覆盖范围以及跨文件分析限制。") 原计划按解析存储、只读 API、Web、派生理解和后续助手接入分阶段交付，其中 assistant、retrieval 与 Lark 通路当时明确尚未纳入首切片。[纵向切片阶段计划 ↗](../../../docs/implementation/code-knowledge-design.md#L441 "支持各阶段交付边界以及助手、检索和 Lark 当时属于后续工作的判断。") 模型不可用不影响结构图，派生理解必须记录 unavailable，不能用假摘要掩盖失败。[模型不可用时的降级原则 ↗](../../../docs/implementation/code-knowledge-design.md#L412 "支持结构层不依赖模型且不得生成虚假派生理解。") 文末追加的 P0 合同进一步规定内部 ID 与人类标签分离、missing/stale 节点不可操作，并只从快照固定正文读取源码。[Typed projection 的 P0 合同 ↗](../../../docs/implementation/code-knowledge-design.md#L505 "支持内部 ID 与展示标签分离、不可操作节点说明和快照固定正文读取约束。")

## 后续实现与被替代结论

2026-09-29 的实测已确认确定性 TS/Vue 代码图、Code Wiki Web 与证据 trail 可运行，同时保留跨文件 calls 和跨 revision 身份续接未实现等边界。[Code Wiki 实测能力与边界 ↗](../../../docs/implementation/status.md#L46 "支持确定性代码图已经落地，同时跨文件调用和跨版本身份仍受限制。") 同日复审还记录代码角色未完全进入统一持久任务和独立语义复核流水线；这是带日期的历史判断。[2026-09-29 架构边界 ↗](../../../docs/implementation/code-wiki-review-2026-09-29.md#L31 "证明代码角色未统一编排和缺少独立语义复核是复审当日的历史状态，而非无日期的当前结论。") 2026-10-01 的更新已经明确接入共用正文／引用合同、八种知识角色、持久分析、独立复核及仓库全材料适配，因此“统一代码角色编排仍有限制”不能再无时间限定地作为当前结论。[2026-10-01 通用知识流程进展 ↗](../../../docs/implementation/status.md#L15 "支持共用合同、八种知识角色、持久分析、独立复核和仓库全材料适配已经接入，替代早期编排限制。") 同期中文向量检索和来源更新后的 extractor／verifier／apply 闭环也已落地，替代了早期“无 embedding、refresh_dependents 未完成”的描述；但全库覆盖仍须以最新 verification 与 coverage 记录为准。[检索与来源更新闭环 ↗](../../../docs/implementation/status.md#L5 "支持中文语义检索和 refresh_dependents 重核验闭环已落地，同时全库覆盖仍需按当前报告判断。")
