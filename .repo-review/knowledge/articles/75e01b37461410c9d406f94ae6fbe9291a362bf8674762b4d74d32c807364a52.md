# 从代码快照到可追溯知识的 Code Wiki 架构

这份历史设计说明了如何在统一的 Capture→Source/Revision/Fragment 证据链上叠加可重建的代码类型投影。后续复审与状态记录确认，固定快照的 TS/Vue 代码图、人工关系投影和 Wiki 阅读已落地；跨文件调用与跨版本身份续接仍有限，原设计的分阶段路线不能整体视作现有能力。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决代码结构与原始证据脱节的问题

这套架构服务于“看懂代码结构，同时能回到当时原文”的场景。早期 repo-review 已能保存不可变 revision、固定 fragment 和人工评审关系，但代码侧只有正则分片与字符串符号，缺少精确位置、类型、导出信息及 imports、calls、route 等结构关系。设计因此提出先用确定性解析生成文件、符号和结构边，再把人工关系及模型理解挂到同一证据链；模型不可用时，结构浏览仍可工作。参考 [早期问题与设计目标 ↗](../../../docs/implementation/code-knowledge-design.md#L12 "说明早期代码侧缺少结构化符号和代码关系，并支持以确定性解析叠加人工及模型理解的设计动机。")

本文本身是历史设计提案，设计项不等于已交付能力，当前状态应以复审和状态页为准。后续复审也明确：repo-review 是本仓库的隔离运行配置与阅读视图，可提交 Wiki 是统一证据链的派生产物，不是第二套知识权威。参考 [历史提案标注 ↗](../../../docs/implementation/code-knowledge-design.md#L1 "证明目标文档明确区分事实、设计与未实现项，并要求以复审和状态页判断当前能力。") [复审核心判断 ↗](../../../docs/implementation/code-wiki-review-2026-09-29.md#L1 "支持 repo-review 是统一证据链的隔离配置和阅读视图，而不是独立知识权威。")

<a id="model"></a>
## 用可重建投影表达文件、符号与关系

核心模型由仓库、快照、文件、符号、结构边和派生理解组成，但不替换 `sources/revisions/fragments`。代码文件是 Source 的代码侧投影，符号通过固定 fragment 锚定证据；符号 range 只对产生它的快照有效，不承担跨版本的永久身份。参考 [符号投影与快照位置 ↗](../../../docs/implementation/code-knowledge-design.md#L135 "支持代码对象叠加于 Source、Revision 和 Fragment 之上，并明确符号位置只对当前快照有效。")

结构边与评审意图边分层：解析器可以生成模块归属、导入导出、定义、路由、测试和组件关系；单文件名称级调用与轻量组件引用只能作为候选。反向关系在查询时派生，派生理解可以记录未知项和失败状态，但不能成为新的独立事实来源。参考 [结构边与派生理解 ↗](../../../docs/implementation/code-knowledge-design.md#L154 "支持结构边类型、候选关系、反向查询派生，以及模型理解不作为独立证据的规则。")

文件变化后，旧 fragment 随旧 revision 冻结，依赖旧端点的关系转为 stale；解析不到的人工定位保留为 missing，不会静默消失。页面可以展示当前 range，但引用、关系和检索仍指向固定 fragment。参考 [固定引用与失效规则 ↗](../../../docs/implementation/code-knowledge-design.md#L214 "支持 range 仅属于当前快照、引用使用不可变 fragment，以及内容变化后的 stale 与 missing 生命周期。")

<a id="workflow"></a>
## 从固定材料生成可阅读的代码知识

处理流程可以概括为：

```mermaid
flowchart LR
  A[固定版本的捕获材料] --> B[确定性 TS/Vue 解析]
  B --> C[文件、符号与结构边投影]
  C --> D[人工评审关系与派生理解]
  D --> E[只读接口与 Wiki 阅读]
```

正文不搬入代码侧表，既有评审关系继续保持权威；新增表只保存可重复构建的投影，重复同步依靠确定性身份幂等更新，不清空原有证据。参考 [兼容投影策略 ↗](../../../docs/implementation/code-knowledge-design.md#L340 "支持不搬正文、保持既有评审关系权威、新表增量创建及同步幂等的迁移原则。")

最初方案选择 TypeScript Compiler API、Vue SFC 解析器和少量保守正则，以离线方式提取单文件 TS/Vue 符号、导入导出、路由与测试。存储、接口、Web、派生理解和助手接入原本分阶段推进，因此阶段清单只能说明当时的路线，不能单独证明各阶段均已交付。参考 [TS 与 Vue 解析方案 ↗](../../../docs/implementation/code-knowledge-design.md#L366 "支持首个确定性解析方案的选择、覆盖范围及跨文件调用不在 PoC 能力内的限制。") [分阶段实施路线 ↗](../../../docs/implementation/code-knowledge-design.md#L441 "证明存储、接口、Web、派生理解和助手接入原本是分阶段计划，不能由设计路线推断全部已经实现。")

<a id="current-boundaries"></a>
## 已落地能力与仍然存在的边界

后续复审确认，代码图只解析已经捕获的固定版本，代码与文档引用使用同批快照；首启和手动同步能够恢复材料、代码投影及已提交知识。运行数据库、索引和临时模型目录位于可重建的 runtime 目录，只有明确的 build 或 generate 才发布知识资产；默认启动不会自动调用模型。参考 [固定快照与恢复链 ↗](../../../docs/implementation/code-wiki-review-2026-09-29.md#L5 "支持代码图使用固定捕获版本、知识恢复链以及模型结果与人工内容保持区分。") [运行目录与启动行为 ↗](../../../docs/implementation/code-wiki-review-2026-09-29.md#L21 "支持运行数据和临时索引写入可重建目录、显式生成才发布资产，以及默认启动不调用模型。")

2026-09-29 的实测记录显示，确定性 TS/Vue 代码图、人工关系投影、Wiki 阅读和证据 trail 已经可用；其中的文件数和关系数只是历史快照。跨文件 calls、类型解析以及跨 revision 的符号或 fragment 身份续接仍未实现，名称级调用仍是候选。参考 [代码图实测与边界 ↗](../../../docs/implementation/status.md#L48 "支持确定性代码图已有实测，同时跨文件调用与跨版本身份续接仍未实现。")

项目随后把仓库材料、已复核文章和历史证据接入统一知识阅读与通用知识流程。旧界面或旧正文不会因此自动获得复核状态，未通过、过期或未生成的内容也不能计为完成。因此，最稳定的架构结论是：代码结构是统一证据链上的可重建视图，而非独立的 Code Wiki 产品。参考 [统一知识流程现状 ↗](../../../docs/implementation/status.md#L17 "支持项目已接入共用正文、持久分析和独立复核，并以覆盖记录排除未通过或过期内容。") [统一知识阅读更新 ↗](../../../docs/implementation/status.md#L1 "支持 Code Wiki 阅读能力已汇入统一入口，以及旧正文仍需真实分析和独立复核。")
