# Batch 2 提议、评估与纠正合同测试

验证提议处理链的严格数据边界：提议不等于已应用状态，更新必须携带并发版本，提议、核验和纠正分别使用受约束的批次信封。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="proposal-boundary"></a>
## 提议不是已应用事实

该测试把文档中的 Proposal v1 示例作为跨文档与代码合同夹具，确认它能被严格 schema 接受，同时明确提议对象本身不含 `state`，因此“模型提出任务”不能被解释为任务已经落地。[Proposal 示例与未应用语义 ↗](../../../apps/server/tests/contracts.test.ts#L10 "支持文档夹具可解析且 Proposal 不携带应用状态的结论。") 对对象添加未知的 `applied` 字段会失败，修改 kind 而不匹配对应 body 也会失败；update 操作若没有目标的预期版本同样被拒绝。[严格字段、Body 与 CAS 约束 ↗](../../../apps/server/tests/contracts.test.ts#L22 "支持未知字段、种类与正文不匹配、更新缺失预期版本均被拒绝。") 这些断言共同约束了结构一致性与 CAS 并发保护，避免松散模型输出绕过应用层决策。

<a id="batch-envelopes"></a>
## 分工信封与未覆盖行为

后续流程通过三个独立信封表达职责：ProposalBatch 记录提取角色的观察、提议和弃权；AssessmentBatch 由核验角色按提议摘要给出引文资产与语义结论；CorrectionProposal 则绑定待纠正对象、预期版本、作用域、替换内容、证据和来源。[批次评估与纠正信封 ↗](../../../apps/server/tests/contracts.test.ts#L42 "支持 ProposalBatch、AssessmentBatch 和 CorrectionProposal 的职责与关键字段说明。") 测试证明这些示例可以解析并保留关键字段，但没有执行提议应用、CAS 冲突、权限校验或纠正覆盖后的状态迁移；也未系统枚举每种 proposal kind、verdict、reason code 和非法嵌套字段。因此它验证合同形状，不证明完整业务工作流或独立核验质量。
