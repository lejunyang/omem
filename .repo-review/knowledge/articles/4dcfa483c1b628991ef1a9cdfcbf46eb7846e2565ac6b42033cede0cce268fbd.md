# 开发环境中的仓库知识合流

将仓库评审产生的当前知识、文章历史及其引用的旧版原始材料接入个人知识库，同时保持个人数据库独立，并避免历史导入覆盖实时文件版本。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose"></a>
## 解决什么问题

开发服务器需要让用户在个人知识入口中继续阅读仓库评审成果，但不能用评审数据库替换个人数据库。该入口以个人 `Store` 创建知识仓库，读取已发布文章，并仅在个人库与评审运行库不是同一目录时尝试补入历史证据。参考 [开发知识导入入口 ↗](../../../apps/server/src/knowledge/development.ts#L14 "支持该入口从个人 Store 创建仓库、读取发布文章并判断是否需要访问隔离评审库。")

评审侧本身使用隔离的运行目录；因此这里承担的是**显式合流**：把仓库材料作为个人库的新输入，而不是把两套存储混成一个数据库。延伸阅读：[评审运行库隔离 ↗](../../../apps/server/src/review/store.ts#L17 "说明评审数据位于独立运行目录，支持个人库与评审库保持分离的背景。")

<a id="history-flow"></a>
## 沿引用恢复历史证据

导入先按文章摘要建立历史集合，再检查文章依赖。若依赖指向尚未加载的旧文章版本，就从评审库的 `knowledge_revisions` 读取；若依赖指向个人库中缺失的 `omem:` 材料版本，则按稳定文件身份查找旧 revisions，只捕获摘要与依赖完全匹配的版本，并连同上下文、来源信息及图片内容写入个人库。参考 [历史依赖补齐流程 ↗](../../../apps/server/src/knowledge/development.ts#L23 "支持按文章依赖补齐旧文章、定位指定摘要的材料 revision，并将其捕获进目标 Store。")

```mermaid
flowchart LR
  A[已发布文章] --> B[补齐被引用的旧文章]
  B --> C[收集缺失的材料摘要]
  C --> D[从评审库定位旧 revision]
  D --> E[捕获到个人 Store]
  E --> F[恢复当前仓库材料与文章]
```

当前仓库文件随后才被捕获，意图是让实时版本保持为 head；之后恢复历史文章、刷新可读状态，并把无法恢复的历史文章汇总为告警而不中断整体启动。参考 [实时优先与恢复结果 ↗](../../../apps/server/src/knowledge/development.ts#L47 "支持先恢复实时内容、再恢复历史文章、刷新仓库并收集失败信息的执行顺序。")

<a id="boundaries"></a>
## 输入边界与失败语义

这段流程只追随文章依赖中的 `article` 与 `material`，且旧材料键必须以 `omem:` 开头；找不到匹配摘要的 revision 时不会猜测或用当前文件代替。评审材料采集还会排除派生知识目录、依赖与构建目录、私有环境文件、符号链接以及越界文件，从源头限制可进入知识管线的内容。参考 [仓库材料采集边界 ↗](../../../apps/server/src/review/materials.ts#L15 "支持对派生目录、私有配置、符号链接、超大文件等输入的排除或失败处理。")

历史文章恢复失败会保留标题和原因并继续处理；当前发布文章若不可用则不会进入可读目录。代码注释还明确：旧来源消失时历史内容仍可阅读，但未解析引用应由 API 禁用，刷新后标记为过期；此文件自身并不实现引用禁用规则。参考 [历史知识降级处理 ↗](../../../apps/server/src/knowledge/development.ts#L49 "支持旧来源缺失时仍保留历史阅读、恢复失败不覆盖整体结果以及引用交由后续刷新处理的边界。")
