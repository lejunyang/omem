# 作业仓储：持久化队列、租约执行与控制操作

该仓储以 SQLite 事务组织作业入队、带租约领取、执行留痕、结果收尾和幂等控制。稳定摘要与版本字段构成重复识别的查询身份，但真正的数据库级去重仍取决于当前材料未展示的唯一约束。

来源：gpt-5.6-sol 分析，gpt-5.6-sol 独立复核；模型解释仍可被原始证据纠正。

<a id="purpose_and_model"></a>
## 职责与持久化模型

`JobRepository` 将异步处理保存为可恢复的持久化状态机：作业记录包含输入摘要、角色与策略版本、状态、generation、租约、取消标记、结果和父作业；每次执行另存模型、提示词及技能指纹、用量与错误，角色输出还保留摘要和 trace，形成可审计的执行历史。[作业、执行尝试与角色输出模型 ↗](../../../apps/server/src/jobs/repository.ts#L11 "支持作业状态、租约、执行指纹、用量以及角色输出审计信息的持久化结构说明。")

入队使用 `BEGIN IMMEDIATE` 事务，捕获流程也可调用无嵌套事务版本，让证据与首个持久作业共同提交。代码会计算输入摘要，执行 `INSERT OR IGNORE`，再按工作区、类型、摘要和版本查询返回行；**被替代的旧结论**是“相同工作必然不会重复创建”，当前只能确认此插入与查询流程，数据库级去重是否成立还取决于未提供的唯一约束。[事务化入队与重复识别查询 ↗](../../../apps/server/src/jobs/repository.ts#L175 "支持事务边界、稳定摘要、INSERT OR IGNORE 以及随后按身份字段查询的准确流程，并说明去重结论依赖未展示约束。") 摘要通过递归排序对象键、忽略 `undefined` 并计算 SHA-256 获得；数组顺序仍被保留。[规范化稳定摘要 ↗](../../../apps/server/src/storage/digest.ts#L3 "说明对象键排序、undefined 过滤、数组顺序保留和 SHA-256 摘要的实现。")

<a id="lease_execution"></a>
## 领取、租约与执行留痕

Worker 可按类型或作业 ID 过滤候选，领取已到执行时间的排队/重试作业，或租约已过期的 leased/running 作业。旧 attempt 会先以 `lease_expired` 收尾，再检查当前 generation 的尝试上限；条件更新成功后才创建新 attempt 和随机 lease token，从而把竞争控制在事务与更新条件内。[作业领取与过期租约回收 ↗](../../../apps/server/src/jobs/repository.ts#L261 "支持候选筛选、过期 attempt 收尾、尝试上限、条件竞争更新及新 attempt 创建流程。")

`markRunning` 要求租约尚未到期；heartbeat 校验 token、状态和取消标记并延长租期，但没有检查原到期时间。运行配置与用量写入尚未结束的 attempt，角色输出仅可在 running 状态下事务化保存，并同时计算输出摘要和记录 trace。[运行转换与租约续期 ↗](../../../apps/server/src/jobs/repository.ts#L375 "支持 markRunning 的到期校验以及 heartbeat 未校验原租约到期时间这一差异。") [运行轨迹与角色输出保存 ↗](../../../apps/server/src/jobs/repository.ts#L404 "支持活动 attempt 元数据更新、running 状态约束、输出摘要及 trace 的事务化保存。") 这些方法定义了仓储协议，但材料未展示 worker 是否始终按领取、运行、保存输出、完成的顺序调用。

<a id="completion_retry"></a>
## 完成、失败与重试

成功收尾要求 token 匹配、状态仍为 leased/running、租约未过期且没有取消请求，随后结束 attempt、写入结果并清空租约。失败收尾则校验 token 与状态，将常见密钥和认证字段脱敏、压平换行并截断错误，再按类型决定是否进入 `retry_wait`。[成功收尾与分类失败重试 ↗](../../../apps/server/src/jobs/repository.ts#L538 "支持成功时的租约有效性检查、错误脱敏、分类重试阈值、generation 上限和指数退避。")

`bad_output` 的同类失败计数小于 2、`transient` 小于 3 时才可能自动重试，同时还受 generation 的 `maxAttempts` 限制；退避随同类错误次数指数增长。租约过期 attempt 也计入 generation 总数，因此反复失联最终会在领取阶段触发 attempt-limit 失败。

<a id="control_and_boundaries"></a>
## 控制操作与已知边界

取消与人工重试以 `requestId` 和载荷摘要提供幂等重放：同一请求可返回既有响应，不同载荷复用 requestId 会冲突；`expectedGeneration` 防止旧调用控制新一代作业。运行中取消只设置标记，成功作业要求补偿；人工重试仅接受 failed、cancelled 或 awaiting_decision，并递增 generation 后重新排队。[幂等取消与代次重试 ↗](../../../apps/server/src/jobs/repository.ts#L674 "支持请求幂等冲突、generation 乐观控制、不同状态下的取消语义和人工重试限制。")

控制接口会核对工作区，但按作业 ID 获取、attempt 查询与完成方法没有同样的显式工作区参数，因此不能据此宣称完整租户隔离。当前材料亦未包含表结构、调用者和测试；唯一约束、崩溃恢复整体时序及并发边界的实际保障仍需外部证据。
